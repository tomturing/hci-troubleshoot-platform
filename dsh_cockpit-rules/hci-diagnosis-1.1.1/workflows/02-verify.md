
# 阶段二：取证验证与动态诊断

## 目标

基于阶段一形成的初始排查计划，定位相关日志与信息，执行取证验证，判断故障假设，追溯根本原因，并根据新证据动态调整排查方向。

主 Agent 统一作出诊断决策，自行取证或按需通过 Workflow 调用通用子 Agent。

本阶段重点完成：
- 根据排查计划定位相关日志及信息。
- 通过直接查询或按需调用 Workflow 获取证据。
- 判断各排查方向是否成立。
- 根据新证据动态调整排查计划。
- 必要时检索案例库补充故障机制和验证方法。
- 追溯故障根因，判断是否满足诊断完成条件。

## 一、理解当前排查计划

- 以阶段一输出的初始排查计划作为正式取证起点。
- 明确当前主故障事件、诊断对象、时间范围及验证目标。
- 根据关联程度、验证价值和执行成本选择优先执行的方向。
- 不要求机械执行全部初始排查方向。
- 若缺少有效初始排查计划，应先补充规划，不直接开展正式根因验证。

## 二、定位日志与准备执行条件

### 1. 了解日志结构

- 读取 `knowledge/logs/INDEX.md`，根据当前验证目标逐级读取相关日志说明。
- 按需了解日志文件的位置、用途、格式、关键字段及对象关联方式。
- 不一次性加载全部日志知识。
- 日志知识用于辅助定位，实际位置与内容以当前信息包为准。

### 2. 定位相关信息

- 根据验证目标确定需要分析的日志、配置、告警、硬件信息或命令结果。
- 确定所需对象、所属节点、日志类型及可能的文件位置。
- 结合实际离线目录确认文件是否存在。
- 现有知识不足时，允许在授权范围内有限探索。
- 不凭空假设文件路径、日志字段或对象关联关系。

### 3. 确定查询范围与参数

- 优先围绕主故障对象及初始时间窗口开展查询。
- 使用已知 VMID、IP、HostID、任务 ID、磁盘 ID 等信息缩小查询范围。
- 对缺失的必要参数，可以通过已有日志和相关信息自主获取。
- 涉及多个对象或组件时，应明确必要的关联关系。
- 当故障机制涉及前置事件、持续异常或异步任务时，可以合理扩大时间范围。
- 不因默认时间窗口未找到异常，就直接排除故障假设。

### 4. 检查数据可用性

- 判断目标日志是否存在，是否覆盖故障时间及所需对象。
- 对缺失文件、无法获取的参数或不完整的数据，应记录具体情况。
- 可以使用其他有效证据进行交叉验证。
- 不要求在所有日志均可用后才能继续验证。

## 三、制定取证任务

主 Agent 根据当前验证目标组织执行任务。

### 1. 任务拆分原则

- 按独立取证目标拆分任务，而不是按日志文件数量机械拆分。
- 同一对象、相同目标且可以一次完成的查询尽量合并。
- 评估独立任务是否适合交给子 Agent，并根据查询成本和数据源重叠情况选择调度方式。
- 存在前置参数或对象依赖的任务，先完成必要的前置查询。
- 简单任务允许主 Agent 直接查询，不强制使用子 Agent。
- 不为增加并行数量而拆分无意义任务。

### 2. 任务下发要求

向子 Agent 下发任务时，应尽量明确：

- **任务 ID**：用于关联任务与结果。
- **日志编号**：当前 log_id。
- **取证目标**：需要确认什么事实或获取什么证据。
- **查询对象**：VMID、HostID、IP、任务 ID 等已知标识。
- **时间范围**：当前已知的相关时间窗口。
- **信息范围**：相关日志类型、配置或其他信息。
- **返回要求**：需要返回的客观结果及证据。
- **执行约束**：授权目录、只读权限及任务边界。

对尚不明确的参数，应说明已知条件与允许的获取方式，不编造具体值。

主 Agent 应明确需要什么证据，不要求提前指定每一条查询命令。

## 查询执行预算

### 1. 查询前评估

主 Agent 或子 Agent 执行查询前，应明确：

- 查询目标：需要验证什么。
- 查询对象：涉及哪些 VM、Host、任务或组件。
- 数据来源：优先使用哪些数据库、索引或日志文件。
- 查询范围：相关时间、文件及对象范围。
- 预期收益：查询结果可能如何影响当前判断。

### 2. 默认资源预算

以下参数作为初始执行预算，可根据实际任务合理调整：

| 控制项 | 默认预算 |
|---|---|
| 单次查询执行时间 | 20 秒 |
| 单次原始输出量 | 16 KB |
| 单次展示匹配日志 | 50 行 |
| 大规模扫描并发数 | 1–2 |
| Workflow 子 Agent 并发数 | 最多 3 |

执行限制应尽量通过实际工具实现；未具备工具层控制能力时，Agent 应主动遵循相应预算。

### 3. 查询优化

- 优先进行对象、时间及数据源过滤。
- 同一文件的多个关键词优先合并为一次查询。
- 同一数据源的相关统计尽量批量获取。
- 优先返回匹配数量、时间分布、关键位置和少量原始证据。
- 不默认输出所有匹配日志。
- 优先复用已有查询结果，避免重复扫描。
- 多个子 Agent 查询相同大型数据源时，应考虑合并任务。

### 4. 查询止损

出现以下情况时，应停止当前查询方式并调整策略：

- 查询耗时明显超出预期。
- 查询结果与当前验证目标缺少关联。
- 同一范围反复扫描但没有新增有效信息。
- 输出大量无关日志。
- 扩大范围无法明显提高验证价值。

停止查询后，可选择：
- 缩小对象或时间范围。
- 更换数据源。
- 合并查询条件。
- 使用已有结果。
- 暂停该方向并切换其他假设。

不得将查询超时或失败视为故障不存在。


## 四、按需调用 Workflow 取证

### 1. 调度规则

- DeepSeek Harness 自主决定是否调用 Workflow 和启动子 Agent，可选择直接取证、串行、并行或分批执行。即使任务相互独立，也可以直接完成或串行执行。
- 以执行稳定、取证准确、结果可靠为依据，综合考虑任务依赖、上下文需求、查询成本和共享资源。依赖前序结果的任务在结果可用后再启动，并行数量遵循实际运行环境的上限。
- 选择并行时，可以使用原生 `await parallel([() => agent(...), ...])`。连续写多个 `await agent(...)` 会按顺序执行，`phase(...)` 只标记阶段。
- 优先复用已有有效结果，避免重复调度。
- Workflow 负责取证执行，不负责整体诊断决策。

使用 `parallel(...)` 时，普通子任务失败的对应结果为 `null`。主 Agent 应结合 Workflow 状态说明失败，不得把 `null` 当作“未发现异常”。

### 2. 子 Agent 统一职责

所有子 Agent 均作为通用证据获取执行器，不按技术领域设置固定专业身份。

子 Agent 负责：
- 根据任务目标自主定位相关文件及信息。
- 自主选择合理的只读查询、过滤和关联方法。
- 必要时获取任务范围内的关联参数。
- 提取与验证目标直接相关的客观事实。
- 保留关键日志内容、时间及来源位置。
- 说明查询覆盖范围和数据限制。

子 Agent 不负责：
- 独立确认整体故障根因。
- 自主修改主 Agent 的整体排查计划。
- 擅自扩大调查到无关故障方向。
- 自行调用新的诊断 Agent 进行独立排障。
- 修改原始日志、系统配置或其他现场数据。

### 3. 子 Agent 任务内自主性

- 子 Agent 可以在既定目标内自主调整文件、过滤条件、查询方法及合理的时间范围。
- 需要关联参数时，可以自行查询获取。
- 发现与当前取证目标直接相关的新线索时，可以补充必要的上下文查询。
- 发现超出任务目标的新异常时，应返回线索，由主 Agent 决定是否深入。
- 不要求每次改变查询命令都向主 Agent 请示。
- 不得因局部发现而自行扩大整体诊断范围。
- 如果要查询更多的日志文件，先读取 `knowledge/logs/INDEX.md`，根据当前验证目标逐级读取相关日志说明

### 4. 证据返回格式

每个子 Agent 返回以下内容：

**任务信息**
- 任务 ID：
- 执行状态：完成 / 部分完成 / 失败

**客观发现**
- 实际发现的关键信息。
- 已覆盖范围内未发现的相关信息。
- 尚未获取或无法确认的内容。

**关键证据**
- 原始日志或信息内容。
- 文件来源及位置。
- 相关时间、对象及必要上下文。

**查询覆盖**
- 实际查询的文件或信息来源。
- 实际查询的对象与时间范围。
- 未覆盖的数据、查询限制或失败原因。

**补充线索**
- 与当前取证目标有关、但需要主 Agent 决策是否继续调查的新发现。

返回要求：
- 只返回客观事实与证据，不输出独立根因结论。
- 不返回大量无关原始日志。
- 不得编造日志内容、来源及查询结果。
- 未发现异常必须结合查询覆盖范围说明，不得直接表述为故障不存在。

### 5. Workflow 结果处理

- 主 Agent 接收当前批次 Workflow 的取证结果。
- 将各子任务结果与对应验证目标关联。
- 对重复证据进行合并，对冲突证据进行标记。
- 判断是否需要补充查询、修改计划或继续下一轮取证。
- 一轮 Workflow 结束后，由主 Agent 统一作出下一步诊断决策。
- 不将子 Agent 的推断自动作为最终根因判断。

## 五、分析证据与判断假设

### 1. 验证结果分类

根据现场证据判断各排查方向：

- **已确认**：关键事实已得到充分验证。
- **支持**：存在有效支持证据，但尚不足以确认。
- **排除**：通过有效的反证或具有充分覆盖范围的验证，可以否定该假设。
- **证据不足**：现有信息无法支持可靠判断。

注意：
- 未发现错误不自动等于排除。
- 查询失败不等于未发现异常。
- 日志缺失不等于故障不存在。
- 支持某个假设不等于已经确认其为根本原因。

### 2. 证据关联判断

判断证据是否与当前主故障相关：

- 时间是否关联。
- 故障对象是否关联。
- 是否存在合理的故障机制。
- 是否能够解释用户反馈的现象。
- 是否存在与当前判断矛盾的证据。

对缺少合理关联依据的异常，应降低优先级或停止深入分析。

### 3. 交叉验证

- 必要时结合日志、配置、告警、硬件信息及已有命令结果进行交叉验证。
- 关注不同证据之间的时间顺序和因果关系。
- 优先使用能够区分候选原因的关键证据。
- 不要求所有方向都进行多来源验证，应根据实际证据需求决定。

## 六、动态诊断与计划调整

主 Agent 根据每轮验证结果，决定后续调查方向。

### 1. 阶段内调整

以下调整可直接在本阶段完成：

- 细化查询对象、日志范围或时间窗口。
- 新增合理的故障假设。
- 修改候选原因及验证目标。
- 调整排查方向的优先级。
- 合并重复假设。
- 终止已充分排除或验证价值较低的方向。
- 根据证据增加新的独立取证任务。

调整时应明确：
- 触发调整的关键证据。
- 原计划需要改变的内容。
- 下一步需要验证的目标。

不要求每次调整都返回阶段一，也不要求重新输出完整排查计划。

### 2. 重新确认诊断起点

如果发现以下情况，应重新确认诊断基础：

- 原诊断对象可能错误。
- 原主故障事件可能识别错误。
- 故障时间或关键诊断前提发生实质变化。
- 原有计划已无法合理解释实际问题。

必要时重新执行阶段一中的对象确认和规划动作。

应复用已经确认的有效证据，不无理由从头分析。

### 3. 动态执行循环

根据实际情况持续执行：

取证 → 汇总证据 → 判断假设 → 调整计划 → 必要时继续取证。

初始计划是诊断起点，不是必须全部执行的固定检查清单。

## 七、案例库按需检索

案例库用于补充已知问题、产品特有机制、正常行为及验证方法，不直接替代现场诊断。

### 1. 检索触发条件

出现以下情况时，应检索案例库：

- 已发现明确异常，但无法合理解释其产生机制。
- 未发现明显异常，却无法解释用户反馈的现象。
- 只定位到直接触发原因，无法确认值得追查的上游原因。

以下情况由主 Agent 自主决定是否检索：

- 疑似产品特有机制或版本缺陷。
- 疑似已知问题、产品限制或特殊正常行为。
- 需要补充特定产品的验证方法。

如果根因已经明确、证据充分，且无需特定产品知识，可以不检索。

### 2. 案例使用规则

- 案例提供候选原因、故障机制知识及验证方法。
- 优先根据案例的必要匹配条件进行筛选。
- 将案例中的关键验证条件与现场信息进行对比。
- 案例匹配不能直接作为现场根因结论。
- 不符合必要条件或存在冲突证据时，不强行套用。
- 对案例提出的新假设，由主 Agent 判断是否需要补充取证。

### 3. 案例检索止损

- 不为检索而反复搜索大量相似案例。
- 未找到适用案例时，应回到现场证据或说明当前知识限制。
- 不得因案例库缺少匹配结果而直接认定问题不存在。
- 不因某个案例描述相似而忽略现场矛盾证据。

## 八、根因追溯与完成判断

### 1. 根因追溯

对已有证据支持的原因，进一步分析其故障机制和可能的上游原因。

应区分：
- 故障现象。
- 直接触发原因。
- 中间原因。
- 根本原因。

要求：
- 不得仅因某条排查思路成立就直接结束分析。
- 若当前原因是其他异常的结果，且存在合理、具有验证价值的上游原因，应继续追溯。
- 关键因果关系必须具有现场证据支持。
- 技术常识和合理推断不能直接替代现场根因证据。
- 不强制固定追溯层级或次数。
- 当继续追溯无法明显提升诊断价值时，应及时止损。

### 2. 根因完成判断

从四个维度判断：

**解释性**
- 当前原因能否解释用户现象及主要异常？

**因果性**
- 当前原因是否只是直接触发原因或中间结果？
- 是否仍有值得验证的关键上游原因？
- 是否还有需要继续下挖或者排查的建议，且当前还没有分析

**证据性**
- 根因及关键因果关系是否获得现场证据支持？
- 是否存在尚未解释的重要矛盾证据？

**可行动性**
- 当前结论是否足以指导问题处理？
- 如果证据不足，是否能够明确下一步验证动作？

### 3. 判断结果

- 根因解释充分、因果关系有证据支持，且不存在仍需追查的关键上游原因时，可以确认根因。
- 存在值得验证的上游原因时，应继续必要的追溯和取证。
- 证据不足且无法继续有效验证时，保留当前最深的可信原因，明确缺失环节。
- 未发现故障时，应判断已有证据是否能够解释用户现象，不得直接认定设备正常。
- 对正常行为或使用问题，应有相应依据支持。

### 2. 默认追溯预算

- 单条因果链路默认最多进行 8 轮取证判断。
- 连续 2 轮未取得能够明显改变诊断判断的新证据时，应立即重新评估继续价值。
- 对同一假设，不在相同数据和条件下反复执行等价查询。
- 达到不可观测边界时，不要求使用完剩余预算，应直接停止该方向。
- 预算耗尽时，只有存在明确可获取、可能显著改变结论的关键证据，才允许有限追加验证。

### 3. 每轮继续条件

继续追溯前，主 Agent 应判断：

- 是否仍存在需要确认的关键因果关系。
- 下一步是否有明确验证目标。
- 是否存在可获取的证据来源。
- 新证据是否可能确认、排除或区分候选原因。
- 继续验证是否具有合理收益。

如果以上条件无法支持继续追溯，应停止当前方向。

### 4. 不可观测边界

出现以下情况时，应停止当前追溯：

- 关键实现位于闭源组件中，现有日志无法反映必要的内部状态。
- 缺少源码、调试日志、运行状态或其他决定性证据。
- 已确认现有信息包不能支持进一步的内部机制验证。
- 后续查询只能重复已知事实，无法提高原因判断的确定性。

不得通过持续扫描无关日志来替代缺失的关键证据。

### 5. 预算结束后的处理

- 保留已确认的事实及当前最深的可信原因。
- 区分已确认根因、高可信疑似原因及尚未验证的内部机制。
- 明确尚存的关键证据缺口。
- 根据实际需要给出复现取证或补充信息建议。
- 不因预算耗尽而自动认定某个假设成立或被排除。


## 九、新异常相关性与排查止损

### 1. 新异常相关性判断

发现新的 ERROR、WARN、告警或其他异常时，应先判断：

- 是否涉及当前诊断对象。
- 是否位于主故障时间或合理影响范围内。
- 是否存在可能导致主故障的因果机制。

如果缺少合理关联，应记录为旁路异常或暂缓方向，不继续深层追踪。

即使异常发生在主故障时间窗口之外，只要存在合理的前置影响或持续因果关系，也允许必要的扩展验证。

### 2. 排查止损

每轮验证完成后，判断：

- 是否获取了与主故障相关的新证据。
- 当前假设是否仍具有合理的验证价值。
- 是否需要切换到其他排查方向。
- 是否存在重复查询或无目的扩展。
- 继续追溯能否改善根因判断或处理决策。

连续验证未取得有效进展时，应调整方法、切换方向或停止当前调查。

不得因为某个无关异常尚未解释清楚，就持续投入资源进行分析。

## 十、汇总验证结果

阶段结束前，主 Agent 应整理：

- 已验证的主要排查方向。
- 各方向的验证结果与判断依据。
- 关键证据及可追溯来源。
- 已确认的关键因果关系。
- 尚未确认的重要疑点。
- 当前最深的可信原因。
- 必要的下一步验证方向。

不要求输出所有底层查询过程，但必须保留足以支撑最终报告的关键事实。

## 十一、阶段结束条件

满足以下任一情况时，可结束本阶段：

1. **根因已确认**：证据能够解释主要故障现象，且关键因果关系成立。
2. **正常行为或使用问题已确认**：有充分依据解释用户现象。
3. **根因未确认**：现有信息不足以继续有效验证，或继续分析难以取得有价值的证据，已明确当前可信判断、证据缺口及下一步动作。

无论哪种情况，都应保留关键验证结果和证据来源。

## 十二、执行原则

- 主 Agent 始终负责诊断决策，子 Agent 只负责客观取证。
- 根据阶段一识别的任务依赖和现场条件选择取证方式，以执行稳定、取证准确、结果可靠为先。
- 初始计划允许动态调整，不要求逐项机械执行。
- 所有判断必须基于实际证据。
- 不得将错误日志、异常状态或直接触发事件直接认定为根因。
- 未发现异常时，必须结合实际查询覆盖范围解释。
- 必要时利用案例库补充知识，但必须结合现场证据验证。
- 遵循最小诊断对象、相关性判断与排查止损原则。
- 不要求验证所有可能原因，但必须完成必要的因果追溯。
- 优先复用已有证据，避免重复分析。
- 仅在授权范围内执行只读操作。

**核心要求：主 Agent 基于证据持续判断和调整，选择合适的取证方式，并将根因追溯到足以解释问题和指导处理的层级。**
