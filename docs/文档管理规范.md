## 一、文档用户

本文档系统服务于四类用户，所有文档的设计决策都从用户需求出发。

| 用户 | 典型触发场景 | 核心问题 |
|------|------------|---------|
| **AI Agent**（Copilot / Claude） | 每次对话开始，无历史上下文 | 系统现在是什么状态？我有哪些操作约束？ |
| **新成员工程师** | 第一天 / 接手任务 | 怎么把环境跑起来？为什么系统是这样设计的？ |
| **现有工程师** | 改功能 / 发版 / 出故障 | 这块的规范是什么？这个坑踩过吗？ |
| **未来的自己** | 离开数月后回来 | 当初为什么这样决策？现在系统实际是什么状态？ |

**最重要、最通用的需求：冷启动**

以上四类用户共享一个最高优先场景：**在没有任何上下文的情况下，快速重建完整认知，独立开始贡献**。AI Agent 的每次对话、新成员的第一天、自己休息数月后回来，都面对同样的冷启动问题。

`docs/README.md` 是冷启动的唯一入口。

## 二、设计原则：事件循环驱动

文档系统从实际工作循环中生长，不套外部框架。

```
需求 → 方案 → 任务 → 代码 → 部署 → 验证 → 新需求（循环往复）
```

每个循环产生**两类**文档，职责不同、生命周期不同：

```
┌──────────────────────────────────────────────────────┐
│  事件文档（Event Docs）                               │
│  需求 / 方案 / 任务 / 部署 / 验证                      │
│  · 带日期前缀，记录"当时发生了什么、为什么这样决策"      │
│  · 方案文档必须包含"为什么不选其他方案"                 │
│  · 事件完成后冻结，永久保留，不再修改                   │
│  · 核心用户：未来的自己（追溯历史决策）                 │
└──────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────┐
│  现行全量文档（Current Docs）                         │
│  需求说明 / 各设计主干 / 部署规格 / 测试指南 / ...     │
│  · 始终反映当前真实状态，以代码为准，非设计目标         │
│  · 每次相关事件完成后蒸馏更新，追加变更记录             │
│  · 每个主题只有一份，永远是当前权威                    │
│  · 核心用户：现有工程师 + AI Agent                    │
└──────────────────────────────────────────────────────┘
```

**文档腐化的根源**：事件完成了，但现行全量文档没有同步更新。PR 门禁的唯一目的是强制关闭这个缺口。

## 三、文档保鲜期分类

| 类型 | 说明 | 典型文档 | 腐化代价 |
|------|------|---------|---------|
| **实时型** | 代码即文档，工具自动生成，禁止手工分离 | 目录结构 / Alembic Migration / OpenAPI Spec / Helm Values / 单元测试 | 立即报错，无法忽视 |
| **事件驱动型** | 工作循环中持续产出，是腐化高危区 | 事件文档 + 现行全量文档 | 静默腐化，最危险 |
| **累积型** | 只增不改，漏记才危险 | `verify/pitfalls/`（避坑指南） | 漏记时才危险 |

## 五、README.md：冷启动入口规范

README.md 是所有用户的冷启动入口，结构固定：

**第一屏（30 秒读完，每个工作循环完成后必须更新）**

1. 系统现在是什么——当前部署拓扑，已实现功能清单（以代码为准）
2. 当前处于哪个阶段——进行中 / 已完成里程碑（一行概括）
3. 冷启动阅读路径——按顺序读这几个文件，即可独立开始贡献

**第二屏（按需查阅，渐进披露）**

- 文档导航：指向 `solution/` 各主干现行全量文档（主干引用分支，不展开细节）
- 操作入口：指向 `deploy/` 和 `verify/`

## 六、solution/ 与 task/ 一一对应原则

`solution/` 描述**做什么以及为什么（WHAT + WHY）**，`task/` 描述**怎么执行（HOW）**。两个目录结构完全镜像。

### 主干 vs 分支的定义

**主干**：系统级汇总文档，维护跨模块的全局视图，其他主题都与它有关联。
**分支**：模块/组件级专项文档，聚焦单一职责域，主干只引用它，不内联其细节。

| 判断标准 | 主干 | 分支 |
|---------|------|------|
| 覆盖范围 | 系统全局（多个模块都涉及） | 单一模块/组件 |
| 典型文档 | 系统架构、数据库设计、接口设计、可观测性设计 | AI助手、知识库、客户端 |
| 新增规则 | 由架构师决策，轻易不新增 | 新增模块时随之新增对应分支目录 |

### solution/ 与 task/ 镜像关系

| solution/ | task/ | 说明 |
|----------|-------|------|
| 主干 `系统架构.md` | 主干 `系统架构.md` | task 侧描述该主题的执行任务清单与完成状态 |
| 分支 `AI助手/方案.md` | 分支 `agent/agent任务.md` | 分支粒度一致，一方新增则另一方同步新增 |
| `events/YYYY-MM-DD-X.md` | `events/YYYY-MM-DD-X.md` | 同一工作循环，方案与任务事件同日期同主题 |

**强制规则**：
- 新建 `solution/{子模块}/` 时，必须同步新建 `task/{子模块}/`
- 提交方案事件文档时，必须同步提交对应任务事件文档
- solution 现行全量更新时，同步评估 task 侧是否需要更新

## 七、现行全量文档规范

### 7.1 变更历史节（新建必须，存量守增量）

每份现行全量文档必须有变更历史节，作为事件文档与现行文档的连接点。
但**存量与增量的口径不同**，不能一句「必须」把上百篇历史文档一次性杀掉
（2026-10-26 实测：203 篇现行文档中 134 篇尚无该节）：

| 场景 | 要求 |
|------|------|
| 新建现行全量文档 | **必须**建节，至少写一行「初版」 |
| 存量文档被实质修改 | **必须**在节内追加一行（修订内容 + 关联事件文档） |
| 存量文档尚无该节 | 下次实质修改时一并补建，**不要求回溯补齐历史** |

适用范围有一个显式边界：`*/pitfalls/` 下的条目文件与 `_index.md` 注册表**不另建**
变更历史节。每一个 V-xxx / PIT-xxx 条目本身就是一条带日期、根因与修复的变更记录，
而 `_index.md` 的编号注册表承担了「何时新增了什么」的追踪职责。再套一层变更历史节
只会得到两份口径不一致的记录。

不对存量做机械化回溯，理由很硬：「从 `git log` 反推变更历史」只能得到提交标题，
拼出的表格看着完整却不可信——读者无法据此判断哪次改动实际改变了结论。
这一列真正的价值在「关联事件文档」，而它只有在改动当下才写得准。
拿不到这个信息的回溯就是凑行数，反而把真信息涂成噪声。

执行方式（必须说清，否则「必须」等于空头承诺）：本节的三行口径**目前没有任何 CI
检查器强制**，依赖 PR 评审人工比对 diff 与本表——这是 V-036 点出的已知缺口，
升门禁前不得把它当成已兑现的强约束。与 §7.3 / §九 里那些有脚本兑现的
「必须」不同，这一条的违反不会报错，只会在下次想查原因时才发现轨迹断了。
2026-10-26 文档瘦身 Wave 3 已一次性补齐 46 篇（17 篇追加行、29 篇补建节），
逐篇写实文案与可复核证据见
[文档瘦身 Wave 3 现行文档准确性治理](solution/events/2026-10-26-文档瘦身Wave3现行文档准确性治理.md)。

```markdown
## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-04-05 | v2.1 | 新增 X 模块 | [2026-04-05-X方案](events/2026-04-05-X方案.md) |
| 2026-03-19 | v1.0 | 初版 | — |
```

### 7.2 主干与分支原则

- **主干文档**：只用链接引用分支，不内联细节，保持全局视图精炼
- **分支文档**：维护子模块完整内容，可引用主干，禁止逆向内联到主干

### 7.3 Frontmatter

```markdown
---
status: active          # active / archived（见 §7.3.1）
category: solution      # requirement / solution / task / deploy / verify / meta
audience: developer     # 受控词表，逗号分隔多值（见 §7.3.2）
last_updated: 2026-04-05
owner: team
---
```

现行全量文档没有"被取代"状态——内容直接更新，历史通过变更历史节追溯。

这五个字段由 `scripts/ci/check_docs_frontmatter.py` 在 `docs-governance` job 中以
`--full` 模式强校验（阻断级）。写下来就是为了能被执行——一条写在规范里、却没人检查
的「必须」，与没有这条规范完全等价。

为什么这里是阻断而不是建议：frontmatter 的唯一用途是让读者（含 Agent）按
`status` / `category` / `audience` 机械过滤文档。缺字段或写了词表外的值，过滤会
**静默漏掉**该文档——读者以为已看全，实际少看了几篇。静默漏掉比报错危险得多。

两处豁免及其理由：

| 路径 | 为什么不适用 |
|------|-------------|
| `*/events/` | 事件文档遵循第八章，记录的是「当时为什么这么决策」，不按现行契约维护 |
| `docs/archive/` | 归档件只读，frontmatter 冻结在搬入时刻 |

#### 7.3.1 `status` 描述文档生命周期，不描述功能状态

`status` 只有两个合法值：

| 取值 | 含义 | 约束 |
|------|------|------|
| `active` | 现行文档 | 默认值。功能是否已落地、是否只是提案，写入正文，不进 `status` |
| `archived` | 原地归档 | 内容已废弃/被替代，但因仍有现行文档引用而不搬入 `docs/archive/`。**必须**在正文首屏写明归档日期与客观依据 |

由此推出两条判据：

1. **`implemented` / `proposed` / `accepted` / `current` 都不是文档状态。** 一份描述「尚未落地方案」的文档，只要还在维护、还会被读者依据它行动，它就是 `active`——「未落地」是正文里的一个事实，不是一个文档状态。混用会导致按 `status` 过滤时把现行文档漏掉。
2. **`archived` 必须能被核实。** 正文首屏要给出「为什么判定它已死」的可复核证据（实库行数、代码删除提交号、被谁取代）。写不出证据的，只能改内容或另写事件文档，不能标 `archived`。

已搬入 `docs/archive/` 的文档不受本节约束（归档件只读，frontmatter 冻结）。

#### 7.3.2 `audience` 用受控词表，允许逗号分隔多值

一份文档常常同时服务多个角色（一份「生产者信号设计」既给开发看实现，也给测试看验证点，
还给安全看边界）。强制单值会逼作者丢掉真实读者，所以允许多值——但词表必须受控，
否则会退化成自由文本，也就无法机器校验。

| 取值 | 含义 |
|------|------|
| `agent` | 由 AI Agent 读取并作为执行依据 |
| `developer` | 写代码、改实现的人 |
| `operator` | 部署、发布、值守、执行手册的人 |
| `product` | 需求与范围决策 |
| `architect` | 跨模块架构与选型 |
| `qa` | 验证用例与验收标准 |
| `tester` | 联调与回归执行 |
| `sre` | 稳定性、容量、告警 |
| `security` | 权限、密钥、合规边界 |
| `reviewer` | 文档与代码评审 |
| `all` | 不限读者。**独占**，不得与其他值并列 |

规则：

1. 逗号 + 空格分隔，写 `developer, qa`，不写 `developer,qa` 也不写 `[developer, qa]`
2. 顺序不承载语义，不强制排序
3. 不得出现词表外的角色名（历史遗留的 `engineer` 一律视为 `developer`）
4. `all` 不能与具体角色并列——`all, developer` 自相矛盾

### 8.1 命名与存放

| 类型 | 存放目录 | 命名格式 |
|------|---------|---------|
| 需求事件 | `requirement/events/` | `YYYY-MM-DD-{中文主题}.md` |
| 方案事件 | `solution/events/` | `YYYY-MM-DD-{中文主题}.md` |
| 任务事件 | `task/events/` | `YYYY-MM-DD-{中文主题}.md` |
| 部署事件 | `deploy/events/` | `YYYY-MM-DD-{中文主题}.md` |
| 验证事件 | `verify/events/` | `YYYY-MM-DD-{中文主题}.md` |

### 8.2 方案事件文档必须包含的章节

```
## 背景与需求
## 方案（WHAT）
## 决策依据（WHY：为什么选此方案，为什么不选其他方案）
## 影响范围（哪些现行全量文档需要更新）
## 验收标准
```

"决策依据"章节是方案文档的核心价值，承担原 `adr/` 的职责，不再需要独立维护。

### 8.3 事件完成后

PR 合并时需满足：
1. 相关现行全量文档的变更历史节已追加（PR 门禁检查）
2. 事件文档的**决策脉络不修改、不删除**，永久保留

#### 8.3.1 事实断言可订正（强制留痕）

事件文档记录的是「当时为什么这么决策」，这部分是史料，改了就是伪造历史。
但事件里写下的**事实断言**（机制描述、因果链、验收判据）可能事后被实测证伪。
把已知错误的断言留在注明「永久保留」的文档里，等于给后人一张错地图——这比改历史更危险。

因此：**事实断言被证伪时，允许就地订正，但必须同时留下订正记录。**

| 可以做 | 不可以做 |
|---|---|
| 就地改写被证伪的事实断言，并在文末新增「YYYY-MM-DD 订正记录」节 | 悄悄改掉旧断言、不留痕迹 |
| 在订正记录里列「原断言 / 实测结果」对照表 | 删除原决策理由，或重新论证当时的选择 |
| 给出可复核的实测证据（命令、提交号、观测值） | 只写「已修正」而不给证据 |
| 更新 frontmatter `last_updated` | 改组他人事件文档的决策结论去论证当前立场 |

**订正记录的最小结构：**

```markdown
## YYYY-MM-DD 订正记录：{被证伪的假设}
### 被证伪的原断言      ← 表格：位置 / 原断言 / 实测结果
### 实测证据            ← 可复核：命令、提交号、观测值
### 正确的心智模型      ← 取代原断言的表述
```

**唯一判据：**一条断言只在**有实测证据把它证伪**时才可订正。「我怀疑它不对」不构成订正理由，只能另写讨论稿。
范例：[2026-04-10-解耦db-migrate镜像构建方案.md](solution/events/2026-04-10-解耦db-migrate镜像构建方案.md) 文末的 2026-10-26 订正记录。

#### 8.3.2 事件层失效引用的处置口径（2026-10-26 定稿）

事件层在 2026-10-26 分诊时实测 **527 条**失效引用（C1 262 / C2 0 / C3 265，分布在 188 篇），
按本节口径执行订正后为 **519 条**（减少的 8 条逐条可归因于下文）。**决定不做清零**——
理由见 §九：读者不照史料行动，为 CI 变绿把它们「修对」等于伪造历史。

但「不清零」不等于「不分诊」。527 条里混着少量**写下来当天就是假的断言**，
那是留给后人的错地图，属于 §8.3.1 的订正范围。分诊判据取自 git 历史，不取自人眼：

| 档 | 判据（`git rev-list --all --objects` 的全历史路径集） | 条数 | 处置 |
|---|---|---|---|
| ① 正常老化 | 目标的**完整路径**曾在历史中出现 | 185 | 保留：写时为真，后来才失效 |
| ② 写法示例 | 目标含 `...` / 通配符 / 无扩展名 | 24 | 保留：不构成路径断言 |
| ③ 链接不准 | 完整路径无匹配，但剥离 `YYYY-MM-DD-`、`NN_`、`NN-`、`T-` 前缀后**文件名有匹配** | 283 | 保留：意图与目标都真实，只是路径写法随目录重构失效 |
| ④ 真幽灵 | 剥离全部前缀后，该文件名在**任何路径、任何历史提交**中都不存在 | 35 | 逐条人工定性 |

第 ④ 档 35 条中，绝大多数依然是**合法计划**：原文带「（新建）」「（待创建）」「（如有）」
「或对应组件」或未勾选的 `- [ ]`——这类句子断言的是未来，**永不可被证伪**，保留。
剩余以既成事实口吻写下、且能给出实测正确值的，才就地订正并留订正记录；
执行结果见 [2026-10-26-文档瘦身Wave4事件层史料分诊.md](solution/events/2026-10-26-文档瘦身Wave4事件层史料分诊.md)，
该批订正采的是下方「行内标注 + 集中订正记录」形式。

动笔前必须先排掉判据的四类假阳性，否则会把正确的史料改成错的：

- **外部仓库路径**：`sop-agent/`、DSH 上游仓的 `docs/subsystems/web-server.md` 等（本仓不存在，它们属于别的仓库）；
- **未跟踪的工作区文件**：本地 rm 过但从未 `git add`，git 无法证明它没存在过；
- **语义改名**：如 `框架全景比较.md` → 实际是 `2026-03-21-AI框架全景比较.md`，前缀不是日期也不是编号；
- **「PR 内新增后未合并」**：这类文件本就不该进 main 历史（审计文档点名批评的正是它）。

**明文禁止**：把第 ③ 档 283 条一并「修对」。它们是当时的真实心智模型，改掉就抹掉了
目录重构的可追溯性；§8.3.1 的门槛是「被实测证伪」，不是「看着不顺」。

##### 订正留痕的两种形式（均合法，按量选轻的）

§8.3.1 只说「必须留订正记录」，没规定形式。批量订正时如果每篇都补一节 30 行的订正记录，
就会与「瘦身」目标直接对冲。两种形式都可以，但必须满足「读者在原位就能发现改动」：

| 形式 | 适用 | 要求 |
|---|---|---|
| 就地订正 + 本篇文末订正记录节 | 单篇重大证伪（影响读者对机制的理解） | §8.3.1 的最小结构：原断言表 / 实测证据 / 正确心智模型 |
| 行内标注 + 集中订正记录 | 同一根因波及多篇的轻量坏链 | 原路径**不得删除**，就地加括号注证伪结论；可复核证据集中在治理事件文档的一处列表 |

行内标注必须同时满足：① 保留原路径或原链接文字；② 同行给出证伪结论与正确值去处；
③ 集中记录里能按位置逐条反查。**不得只删不注**——那就是 §8.3.1 禁止的「悄悄改掉旧断言」。

> 工程副作用提醒：行内标注里的否定词（「不存在」「原路径」等）同时会令门禁豁免
> **同一行内其他无关坏路径**（见 §九 的堆词逃逸边界）。因此标注请写在单独一行或单独表格列，
> 不要与其他待检查的路径挤在同一行。

## 九、PR 门禁规则

### 工作循环关闭条件

> **循环关闭 = PR 合并 + 所有受影响的现行全量文档已更新 + README.md 第一屏已更新**

| 本次改动类型 | 必须更新的现行全量文档 |
|------------|-------------------|
| REST API 接口新增/变更/删除 | `solution/接口设计.md` |
| 数据库表结构变更 | `solution/数据库设计.md` |
| 新增/下线微服务 | `solution/架构设计.md` + `README.md` 第一屏 |
| 部署配置变更（Helm / 构建脚本） | `docs/deploy/部署指南.md` |
| 发布流程变化（CI / ArgoCD 策略） | `docs/deploy/发布指南.md` |
| 本地开发环境依赖变更 | `docs/deploy/部署指南.md` 第一部分 |
| AI 助手层架构变更 | `solution/agent/design/agent设计.md` |
| 可观测性配置变更 | `solution/可观测性设计.md` |
| 踩到新的可复现技术坑 | `verify/pitfalls/` 对应文件 + `_index.md` |
| 任何工作循环完成 | `README.md` 第一屏 |

### 文档腐化门禁（`scripts/ci/check_docs_rot.py`）

扫描器以仓库根为基准，分七类：C1 失效链接 / C2 缺图 / C3 失效仓库路径 /
C4 占位符 / C5 空文档 / C6 密钥泄露 / C7 版本矛盾。不是所有类别都阻断：

| 类别 | 门禁行为 |
|------|---------|
| C6 密钥泄露 | 永远阻断，不分存量/增量（安全红线不受文档分层影响） |
| C1/C2/C3 现行全量文档层 | **一律阻断**（`--current-blocking`，Wave 3 已归零） |
| C1/C2/C3 事件层 / 归档层 | 仅阻断落在本次改动行上的新增；存量只警告 |
| C4/C5/C7 | 只报告，不阻断 |

为什么现行层升为阻断而其余层不升：门禁的正当性只来自「读者会照着文档行动」。
现行层的失效引用就是真实故障；而 `*/events/` 与 `docs/archive/` 是史料，为了 CI
变绿把它们「修对」等于伪造历史（见 §8.3），只能保留存量。
事件层存量（分诊时 527 条、订正后 519 条）的分诊口径与「不清零」的正式决定见 **§8.3.2**，勿在后续 Wave 里重新评估。

五类引用语义豁免（均不得隐式降级，必须逐条打印供人工复核）：

| 豁免 | 不误报的对象 | 不覆盖的对象 |
|------|------------|------------|
| 目录链接 | `[task/](task/)` 指向存在目录，GitHub 渲染为目录页 | 目标目录不存在仍报错 |
| 行内代码 | 反引号内的 `![截图](URL)` 等字面语法示例 | 同一行反引号外的坏链接 |
| 否定语境 | 同行前 30 / 后 60 字符内带「不存在/已删除/曾用名/旧路径」等 14 词的历史陈述 | 超出窗口、或另起一行的修饰词 |
| gitignore | 被 `.gitignore` 刻意排除的路径，如仅本地生成的 `deploy/env/secrets.env`（仓库中不存在） | 非 git 仓库、未被忽略的坏路径 |
| `status: archived` | 已按 §7.3.1 声明作废并给出依据的文档 | C6 密钥检查不受此豁免 |

否定语境是一条**启发式**，不是密不防风的规则：在同一行里先写一个「不存在」，
就能让同行的其他坏路径一并逃过检查（实测已复现）。本轮选择不为此加机器学习
式的复杂度（区分「哪个对象被修饰」需要句法分析，误伤面反而更大），而是把控制
手段放在**可见性**上：每一条豁免都必须带理由逐条打印，评审时躲不掉。因此改文档
时不得靠堆词逃检查，而评审必须读豁免清单——两边都是人的职责，不是机器的。

可执行性本身也要有人检查：判定逻辑住在 `select_blocking()` / `is_current_layer()`
这两个纯函数里（内联在 `main()` 里等于只能靠手工造 git 状态才能验证），回归用例在
`scripts/ci/test_check_docs_rot_semantics.py`（34 项，含逐条「不许放宽」的反向用例、
「未开开关时行为不变」的守护用例，以及上面那条把「同行堆词逃逸」锁成受测行为的用例），与
`scripts/ci/test_check_docs_rot_changed_only.py` 一同登记在 `ci.yml` 的 paths-filter、
ruff check、ruff format 与 pytest 四处。未登记就等于没跑，这与 V-036「写了必须
却没人检查」是同一种失效，详见 V-037。

### CI Agent 检查（演进目标）

静态 CI 只能检查"有没有改文件"，无法判断"改了正确的文件且内容充分"。目标机制：CI Agent 读取 PR diff，语义判断本次改动类型，验证现行全量文档更新是否覆盖变更，不充分则阻断合并。

## 十、pitfalls/ 写入规则

避坑指南分两处，按坑点发生阶段归属，所有 AI Agent 自动路由加载：

| 坑点类型 | 归属目录 | 典型内容 |
|---------|---------|--------|
| 部署、发布、基础设施类 | `deploy/pitfalls/` | K8s/Helm、Shell 脚本、网络、Grafana |
| 代码验证、功能测试、服务调试类 | `verify/pitfalls/` | 调试原则、OpenClaw、前端、Python、状态机 |

**写入流程（两步必须在同一 PR 提交）：**

1. 在对应目录的 `_index.md` 注册表中分配新编号
2. 在对应分类文件中写入条目（**症状 / 根因 / 修复 / 预防**四要素）

**编号规则：** 全局唯一，顺序递增，废弃后保留占位注释，禁止复用。两个 pitfalls 目录编号空间独立互不干扰。

**内容边界：**

| 内容类型 | 应放位置 |
|---------|---------|
| 部署/基础设施可复现坑 | `deploy/pitfalls/` |
| 代码/服务验证可复现坑 | `verify/pitfalls/` |
| 操作步骤流程 | `deploy/` 现行全量文档 |
| 方案 / 决策依据 | `solution/events/` |

## 十二、特殊文档分类（非工作循环）

`docs/` 除工作循环五阶段外，还有三类固定子目录。它们不属于循环阶段，但受本规范全部规则约束。

### 12.1 user-guide/ — 终端普通用户使用手册

- **读者**：非开发者的普通终端用户（如何使用产品/功能）。
- **与工作循环文档的区别**：`solution/` 及以下偏"设计/实现/运维"视角；`user-guide/` 偏"操作结果"视角。
- **命名**：`{产品/功能}-使用手册.md`（中文，无编号无版本号）。
- **归位判定**：一份文档若主要回答"用户怎么用"，进 `user-guide/`；若主要回答"为什么这样设计/怎么实现"，进 `solution/` 对应分支。

### 12.2 contracts/ — 接口契约

- **内容**：机器可读的接口契约文件（如 OpenAPI `*.yaml`、Protobuf `*.proto`）。
- **与工作循环文档的区别**：`solution/接口设计.md` 是人工可读的设计说明（markdown）；`contracts/` 是机器可消费、可校验的契约源文件。两者互补，不可互相替代。
- **命名**：`{服务}-http-api.yaml` 等，全小写英文，与契约语言惯例一致。
- **约束**：契约文件不得写入人类密钥/明文口令（见 C6 硬门禁）；仅允许引用环境变量名。

### 12.3 archive/ — 历史归档
