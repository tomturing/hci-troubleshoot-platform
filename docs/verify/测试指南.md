## 一、环境管理

平台支持两种部署模式，**不可同时运行**（会产生端口与数据卷冲突），切换环境前请务必先停止当前环境。

### 1. 环境说明与访问方式

| 对比项 | Docker Compose 模式 | K3s 模式 (Helm) |
|---|---|---|
| **定位** | 本地开发、代码级调试、快速验证 | UAT测试、生产环境模拟、高可用验证 |
| **运行时** | Docker 本地容器 | K3s 集群 (containerd / docker runtime) |
| **入口网关** | 8000/3001/3002/3000 各服独立端口 | Traefik Ingress (统一 80/443 端口) |
| **外部 AI** | 容器直连外部网络 | 通过 K3s CoreDNS 解析外部网络 |

**服务访问对照表：**

| 访问目标 | Docker Compose 访问地址 | K3s 访问地址 (需替换为 WSL2 IP) |
|---|---|---|
| 客户端 UI | `http://localhost:3001` | `http://<WSL2_IP>.nip.io/` |
| 管理端 UI | `http://localhost:3002` | `http://admin.<WSL2_IP>.nip.io/` |
| API 网关 | `http://localhost:8000/api` | `http://api.<WSL2_IP>.nip.io/api/` |
| Grafana 监控 | `http://localhost:3000` | `http://grafana.<WSL2_IP>.nip.io/` |

*(注：部署脚本 `scripts/k3s-deploy.sh` 已自动化将系统入口绑定到全局 `*.<WSL2_IP>.nip.io` 子域名体系中，利用 Ingress 提供标准的七层负载均衡能力。获取 WSL2_IP: `hostname -I \| awk '{print $1}'`。测试期间请确保关闭本机的网络代理工具以防 Fake-IP 劫持域名)*

### 2. 一键启停指南

#### 2.1 Docker Compose 模式

启动平台与监控栈 (在项目根目录 `/mnt/d/hci-troubleshoot-platform` 下执行)：

```bash
# 后台启动业务容器
docker compose -f deploy/docker/docker-compose.yml up -d

# 后台启动可观测性栈 (Grafana, Loki, Tempo 等)
docker compose -f deploy/observability/docker-compose-obs.yml up -d
```

停止平台：

```bash
docker compose -f deploy/docker/docker-compose.yml down
docker compose -f deploy/observability/docker-compose-obs.yml down
```

#### 2.2 K3s 模式

若之前运行过 Docker Compose，请确保已经 `down`。

**启动 K3s 集群：**

```bash
sudo systemctl start k3s
# (可选) 若遇到 kubeconfig 权限报错，执行：
# sudo chmod 644 /etc/rancher/k3s/k3s.yaml
```

**部署/更新平台服务（自动构建缺失镜像）：**

```bash
./scripts/k3s-deploy.sh
```

**停止 K3s 集群：**

```bash
# 停止 K3s，停止所有相关容器
sudo systemctl stop k3s
```

### 3. 服务健康检查

无论哪种模式，都可以使用统一健康状态验证：

#### 3.1 命令行一键验证 (自动化检查)

如果运行在 **K3s 模式下**，直接执行提供的验证脚本即可完成全链路健康检查：

```bash
./scripts/k3s-verify.sh
```

该脚本将自动验证：K3s 核心组件、持久化存储 PVC、Helm 部署状态、所有 Pod `Running` 状态、以及 API 服务及 Web 页面的 HTTP 200 状态。

#### 3.2 手动检查命令

**Docker Compose：**
```bash
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
curl -sf http://localhost:8000/api/health
```

**K3s：**
```bash
kubectl get pods -n hci-troubleshoot
kubectl get pods -n hci-observability
```

### 4. 环境清理

当需要重置数据库和清除所有日志数据时，可执行清理操作。**警告：该操作将永久丢失所有历史工单、对话和监控数据。**

**4.1 Docker Compose 深度清理：**
```bash
docker compose -f deploy/docker/docker-compose.yml down -v
docker compose -f deploy/observability/docker-compose-obs.yml down -v
```

**4.2 K3s 深度清理：**
```bash
# 1. 卸载 Helm 发布
helm uninstall hci-platform -n hci-troubleshoot
helm uninstall hci-observability -n hci-observability

# 2. 删除持久化数据卷声明 (PVC)
kubectl delete pvc -l app.kubernetes.io/instance=hci-platform -n hci-troubleshoot
kubectl delete pvc -l release=hci-observability -n hci-observability
```

## 二、测试用例

测试执行需确保服务处于健康状态。对于特定的集成测试，请优先在 Docker Compose 模式下调测。

### 1. 单元测试 (Unit Tests)

测试平台核心微服务的业务逻辑和算法，不依赖外部数据库等组件。

**用例 1.1：Conversation Service 逻辑测试**
- **步骤：**
  ```bash
  cd backend/conversation-service
  uv run pytest tests/
  ```
- **预期结果：**
  100% Pass。测试应成功模拟 OpenClaw API 响应并验证内部代理与消息拦截逻辑。

**用例 1.2：Case Service 数据处理逻辑**
- **步骤：**
  ```bash
  cd backend/case-service
  uv run pytest tests/
  ```
- **预期结果：**
  涉及工单状态机流转的代码覆盖率正常且全部 Pass。

**用例 1.3：工具执行契约与 stderr 回归**
- **关联验证方案：** [2026-06-11-bash_exec容器化契约与工具调用前置校验验证方案](events/2026-06-11-bash_exec容器化契约与工具调用前置校验验证方案.md)
- **步骤：**
  ```bash
  uv run pytest -s backend/agent-service/tests/tools/test_container_exec.py backend/agent-service/tests/tools/test_semantic_validator.py backend/agent-service/tests/tools/test_executor.py -q
  uv run pytest -s backend/conversation-service/tests/unit/test_agent_exec_contract.py -q
  uv run pytest backend/agent-service/tests/tools/test_executor.py -q
  uv run pytest backend/agent-service/tests/unit/ -q
  ```
- **验证点：**
  - 双通道回传 `stderr` 且 `exit_code != 0` 时，后端保留真实 `stderr`。
  - `bash_exec` 缺少 `container` 时在真实执行前被校验拦截。
  - `bash_exec` 通过 `ContainerExecAdapter` 生成远端 docker/crictl/ctr 探测 wrapper，并保留 `container/original_command/built_command`。
  - 不支持的 `acli_exec` 命令路径被 catalog 校验拦截。

**用例 1.4：KBD QKV → QFK 三信号执行闭环与大输出回归**

- **步骤：**

  ```bash
  uv run pytest \
    backend/agent-service/tests/unit/test_kbd_differential.py \
    backend/agent-service/tests/unit/test_qkv.py \
    backend/agent-service/tests/unit/test_qfk.py \
    backend/agent-service/tests/unit/test_qfk_extractor.py \
    backend/agent-service/tests/tools/test_executor.py -q

  PYTHONPATH=backend/conversation-service:backend uv run pytest \
    backend/conversation-service/tests/unit/test_agent_exec_contract.py \
    backend/conversation-service/tests/unit/test_tool_event_persistence.py \
    backend/conversation-service/tests/unit/test_sse_queue.py -q

  PYTHONPATH=backend/kb-service:backend uv run pytest \
    backend/kb-service/tests/test_signal_text_extract_schema.py \
    backend/kb-service/tests/test_playbooks.py -q

  npm --prefix frontend/customer test -- --run
  docker run --rm \
    -v "$PWD/terminal_bridge:/src" -w /src golang:1.21-alpine \
    sh -c 'gofmt -w main.go main_test.go && go test ./...'
  ```

- **验证点：**
  - 生产等价 golden test 必须真实走 `task get → VM/HOST/END → lsof → PID → ps -p PID -o cmd= → CMD`，不能由 `task_logs` 上下文替代 QKV。
  - QKV 关键词规范化为 `keyword=启动虚拟机`、`is_failed=true`，实际语义包含 `-s failed -l 1`。
  - 三个 `tool_call.args` 非空，三个 `tool_result.status` 都进入终态并按同一 `exec_id` 持久化。
  - 字面量筛选必须覆盖 all/any、exclude、大小写、跨 WebSocket chunk 行边界以及无换行的最后一行。
  - stdout/stderr 共用 256 KiB 总预算；超限和非法 filter 都必须 Fail Closed。
  - QKV 残留 matcher、QFK 同时或都不配置 match/produces 时，保存和运行快照双门禁都应拒绝。
  - `cmd=` 输出配置 `include=[VM]`；反例必须证明复用 `include=[PID]` 或命令行不含 VM 时会返回 `QFK_NO_MATCH`。
  - 最终报告包含 VM/HOST/END/PID/CMD，不含 exec/evaluation ID、参数 JSON 和 raw stderr 噪音。

**用例 1.5：KBD 现场人工回归**

必须创建新工单/新会话，不复用曾被取消或使用旧 bridge 的会话。页面与日志同时满足以下条件才算通过：

1. 三张工具卡片参数非空，最终均不显示“正在等待输出”。
2. terminal_bridge 依次出现 `task get`、`platform node list`、`lsof`、`ps -p <PID> -o cmd=`。
3. `exec.done` 同时记录 `stdout_raw_len`、`stdout_len`、`stdout_filtered=true`、`output_overflow=false`。
4. 变量池包含 `VM/HOST/END/PID/CMD`，HOST 为节点 IP 而非节点名称。
5. 数据库同一会话存在三条按 exec_id 关联的 tool_result，且没有 running 状态。
6. 保存新工单号、三个 exec_id、原始/筛选后字节数和页面截图到对应验证事件文档。
7. 【关键信号执行结果】只展示用户态状态和结构化提取信息；内部 ID 与原始输出仅从审计链查询。

**用例 1.6：KBD 专家监督与运行效果数据闭环**

- **步骤：**

  ```bash
  cd backend/kb-service
  uv run --with pytest --with pytest-asyncio pytest \
    tests/test_kbd_review_metadata.py \
    tests/test_kbd_lightweight_lifecycle.py \
    tests/test_kbd_sync.py \
    tests/test_kbd_expert_maintenance.py \
    tests/test_signal_text_extract_schema.py \
    tests/test_playbooks.py -q

  cd ../agent-service
  uv run pytest tests/unit/test_kbd_differential.py -q
  ```

- **验证点：**
  - 删除 Signal 必须通过稳定 `signal_id` 和受控 `reason_code` 留下专家原因；拒绝展示数组下标和自由文本原因码。
  - 专家连续编辑必须以直接父 revision 作为 Diff 基线，历史改动不得在下一次保存时重复计数。
  - Agent 审计必须读取检索时携带的精确 KBD Dynamic Resource revision；查不到时跳过审计，禁止回退 active。
  - `runtime-metrics` 仅统计 Agent 实际产生的运行审计；`evaluation-export` 固定声明不具备可信 reviewer、Gold、Replay、真实客户执行和 Challenger。

**用例 1.7：KBD 专家修改统计、Proposal 配对与抽取质量闭环**

- **步骤：**

  ```bash
  uv run pytest -q backend/kb-service/tests
  uv run ruff check \
    backend/kb-service/app/models/kbd_revision.py \
    backend/kb-service/app/routes/admin.py \
    backend/kb-service/app/routes/extract_signals.py \
    backend/kb-service/app/services/kbd_revision_service.py
  uv run python scripts/ci/check_signal_schemas.py
  corepack pnpm --dir frontend --filter @hci/customer test
  corepack pnpm --dir frontend -r build
  uv run python scripts/ci/check_docs_naming.py
  git diff --check
  ```

- **验证点：**
  - 无当前 Expert 时“专家修改”为 0；同一 Signal 多字段变化只计一条；AI→AI 重抽不计入。
  - 发布后仍绑定当前 Proposal 的 approved/published Expert 继续参与统计；新 Proposal 重抽后旧 Expert 退出当前统计。
  - Expert 使用显式 `baseline_proposal_revision_id`；历史兼容沿 parent 链回溯，禁止按 history 顺序猜测。
  - evaluation export 默认只选择 approved/published Expert，不导出 working/opened/saved 中间稿。
  - 自动生成 timeout 的缺失/10/30 秒值收敛到 120 秒；明确特殊值不被覆盖。
  - 无其他下游消费者的 QFK producer 被拒绝并保留原因，自引用不算消费。
  - `/sf/cfg` 文件读取使用 `command + command_args`，不能出现 `qfk_system.resource_keyword`。
  - DDL 与 Prompt 迁移先在事务中验证并回滚；合并部署后再执行真实 KBD30880 LLM 重抽验收。

### 2. 集成测试 (Integration Tests)

测试微服务间的相互通信（如 Gateway -> Service -> Database / AI）。

**用例 2.1：工单微服务数据库连通性**
- **步骤：** 对 case-service 直接执行 CURL `GET http://localhost:8001/health`。
- **验证点：** 返回体中需包含 `"db_status": "connected"` 且状态码为 200。

**用例 2.2：SSE 对话流测试**
- **步骤：**
  1. 创建一个工单（`POST /api/cases`）并获取 `case_id`。
  2. 对该工单发送对话消息（`POST /api/conversations/{session_id}/message`），观察 SSE 流式响应。
