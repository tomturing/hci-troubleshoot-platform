# 日志包分片上传 HTTP 502：网关 60s 读超时验证

> **修复日期**: 2026-10-30
> **工单**: Q2026102801062（3.19 GiB 包，卡在 72/103 片）
> **影响环境**: staging（k3s + Traefik 3.6.9），生产同构，必然复现
> **关联**: `deploy/config/traefik-entrypoint-timeouts.yaml`、`scripts/ops/traefik-entrypoint-timeouts.sh`

---

## 📋 问题描述

### 现象

现场点击「上传到平台」后进度停在 **已传 72/103 片**，页头红条：

```
上传中断（已传 72/103 片）: 分片 74 上传失败: 平台返回 HTTP 502（平台暂时不可用，将退避重试）
```

连续 8 轮 attempt（04:07–04:41 UTC）全部停在同一位置，服务端最终 `delivery_status=failed`，制品未合并。

### 误导性线索（已逐条排除）

| 猜测 | 证据 | 结论 |
| --- | --- | --- |
| 平台发版导致不可用 | 全部业务 Pod `startTime=03:38Z`，交付 04:06 才开始；04:06–04:41 期间 `RESTARTS=0`、无 5xx 突增 | 排除 |
| case-service 崩溃/OOM | 无重启、无异常退出；日志里只有 `ClientDisconnect`（读 body 中断） | 排除 |
| 磁盘写满 | `dd oflag=direct` 落盘 268 MB/s，可用 236 GiB；72 片 2.3 GiB 正常落盘 | 排除 |
| 桥没重试 | 桥重试 8 轮、每轮每片再 3 次内层重试，是**预算耗尽**后停住 | 排除 |

## 🔍 根因定位

### 1. 502 由网关自己生成，不是业务返回

```bash
kubectl exec -n kube-system deploy/traefik -- wget -qO- http://127.0.0.1:9100/metrics \
  | grep 'traefik_service_requests_total{code="502",method="PUT"'
# traefik_service_requests_total{code="502",method="PUT",
#   service="hci-staging-case-service-8001@kubernetes"} 73
```

同期 case-service 侧没有一条 5xx，只有：

```
unhandled_exception  exc_type=ClientDisconnect
  path=/api/direct/log-collect-uploads/<task>/parts/73
  at log_collect_storage.write_part → async for chunk in chunks
```

即「网关先断开，后端读到一半发现客户端（网关）没了」。

### 2. 掐断时刻精确等于 60 秒

每轮 attempt 的墙钟间隔 = 3 × 61s + 退避，逐轮吻合（内层 `logCollectPartRetries=3`）：

| attempt | 结束时刻 (UTC) | 与上轮差 | backoff | 实测 |
| --- | --- | --- | --- | --- |
| 2→3 | 04:19:29 → 04:22:39 | 190s | 4s | 186s |
| 3→4 | 04:22:39 → 04:25:53 | 194s | 8s | 186s |
| 4→5 | 04:25:53 → 04:29:17 | 204s | 16s | 188s |
| 5→6 | 04:29:17 → 04:32:55 | 218s | 32s | 186s |
| 6→7 | 04:32:55 → 04:37:02 | 247s | 60s | 187s |
| 7→8 | 04:37:02 → 04:41:09 | 247s | 60s | 187s |

桥侧 `logCollectPartTimeout=5min`、`logCollectPartRetries=3`，只有**网关 60s** 能解释这个常数。

### 3. 60s 的来源：Traefik 默认值（配置从未真正生效）

排查时差点被 `last-applied-configuration` 注解骗过 —— 注解里写着
`globalArguments` + `readTimeout=120`，看起来「web 已放宽、只有 websecure 漏配」。
但 live spec 与容器 args 都否掉了这个结论：

```bash
kubectl get helmchartconfig traefik -n kube-system -o json | jq -r '.spec.valuesContent'
# 只有 ports（4888/4443），没有任何 globalArguments

kubectl get deploy traefik -n kube-system -o json \
  | jq -r '.spec.template.spec.containers[0].args[]' | grep respondingTimeouts
# 空
```

两个事实叠在一起：

1. chart 39.x **不把 `globalArguments` 渲染成容器参数**（同一份 values 曾在更早的
   版本里写过 `--entryPoints.web.http.tls=true` 并生效，说明 `additionalArguments`
   才是有效位置）；
2. HelmChartConfig 的 `valuesContent` 会**整体替换** Helm user values，某次 apply
   把它改成只有 `ports`，于是连历史参数一起消失。

因此 **web 与 websecure 两个入口都在吃默认 60s**，「web 早就放过宽」是假象。

`readTimeout` 语义是「读完整个请求（含 body）的最大时长」，于是**单分片越大、上行越慢，越必然被掐**：

- 前 72 片：04:07:10 → 04:16:22，约 7.7s/片（≈4.2 MB/s），安全；
- 第 73 片起：有效上行掉到 < 0.53 MB/s，32 MiB 分片需要 > 60s，请求必然被掐。

桥侧把 502 归入 `deliveryTransientError`（`terminal_bridge/delivery_runner.go:1128`），退避后**从同一片重来**，于是形成「永远在同一片失败的确定性重试」。

## 🔧 修复方案

### 1. 网关：给 websecure 配 600s 读/写超时（止血，主因）

新增 `deploy/config/traefik-entrypoint-timeouts.yaml`（K3s HelmChartConfig 声明式纳管），
由 `scripts/ops/traefik-entrypoint-timeouts.sh` 应用并校验：

```yaml
additionalArguments:                                 # 不是 globalArguments：chart 39.x 不渲染它
  - "--entryPoints.web.http.tls=true"                # admin-ui 依赖，漏写即退回明文 HTTP
  - "--entryPoints.web.transport.respondingTimeouts.readTimeout=120"
  - "--entryPoints.web.transport.respondingTimeouts.writeTimeout=120"
  - "--entryPoints.websecure.transport.respondingTimeouts.readTimeout=600"
  - "--entryPoints.websecure.transport.respondingTimeouts.writeTimeout=600"
```

> 为什么不是 patch Deployment：Traefik 由 K3s addon（Helm）管理，直接 patch 会被
> chart 重装回滚；而 `valuesContent` 是整体替换，必须把「与业务无关但别人依赖」的
> 参数（`web.http.tls=true`）一起写全，否则修一个洞会开另一个洞。

### 2. 平台：分片 32 MiB → 8 MiB（降低单请求暴露窗口）

`LOG_COLLECT_CHUNK_SIZE_BYTES` 默认 8 MiB（`backend/case-service/app/config.py`），
并在 Helm 显式注入（`caseService.logCollectStorage.chunkSizeBytes`），可按现场带宽继续下调。

- 8 MiB 在 0.5 MB/s 上约 16s，即使网关超时未放宽也不会必然失败；
- 分片大小随上传会话元数据落盘（`meta.json`），**只影响新会话**，正在续传的任务不会中途换片；
- 分片数从 103 增至 409（3.19 GiB 包），仅增加 HTTP 往返；服务端逐片落盘、合并仍流式，无额外内存/磁盘峰值。

## ⚠️ 部署回归：env 被渲染成科学计数法（同日修复）

首版合并（#1373）后 ArgoCD 同步 staging，case-service 直接 `CrashLoopBackOff`：

```
pydantic_core ValidationError: LOG_COLLECT_CHUNK_SIZE_BYTES
  Input should be a valid integer, unable to parse string as an integer
  input_value='8.388608e+06'
```

根因是模板写了一行 `{{ .Values...chunkSizeBytes | quote }}`：Helm 把 values 里的数字
解析成 float64，`quote` 用 `%v` 格式化，`8388608` 就成了 `8.388608e+06`；而
`SERVICE_PORT=8001` 这类小整数不会退化，所以这个坑一直没暴露。

处置与修复：

1. 先 `kubectl set env` 把值改回 `8388608` 恢复服务；
2. **临时关闭该 Application 的 selfHeal**（否则 3 分钟内会把错误值同步回来再崩一次）；
3. 模板改为 `| int64 | quote`，并在 CI「Helm template 渲染检查」后新增
   「数值型环境变量渲染格式检查」，断言渲染值是 `^[1-9][0-9]*$`（正反两向本地验证过）；
4. 合并后再恢复 selfHeal。

**教训**：`valuesContent` / 模板改动在「渲染成功」和「进程能起来」之间还有一层类型契约，
`helm template` 通过不等于容器可运行。

## ⚠️ 续传回归：改默认分片大小后，旧会话的分片几何自相矛盾

60 s 超时修好、现场重新点「上传到平台」后，上传**仍然失败**，但错误换了形状：

```
已传 72/409 片: 分片 73 上传失败: 平台返回 HTTP 500
服务端：LC-TRANSFER-002 分片 74 超过允许大小 8388608 字节
```

`409` 说明新会话按 8 MiB 算片数，`72/409` 里的 72 片却是旧的 32 MiB 分片 ——
**同一个响应里 `chunk_size=33554432` 与 `part_count=409` 互相矛盾**。

根因：`part_count_for()` / `expected_part_size()` 用的是**进程默认值**
`self.chunk_size`（8 MiB），而会话的真实分片几何记录在 `meta.json`（32 MiB）。
`init()` 的响应里 `chunk_size` 取自 meta、`part_count` 取自默认值，两者拼接后自相矛盾；
`record_part()` 更是直接用默认值当每片上限，于是桥按 32 MiB 切片、服务端按 8 MiB 卡。

这是「改默认值 + 存在旧会话」才触发的隐藏缺陷：正常场景（新会话）永远一致，
所以单测与 E2E 都覆盖不到；一旦现场降过默认值，所有未完成会话的续传都会坏。

修复：分片几何一律由会话 meta 决定，进程默认值只用于**新建**会话。
`part_count_for` / `expected_part_size` 增加 `chunk_size` 参数，`init` / `status` /
`record_part` / `complete` 四处调用点全部传 meta 里的值；新增单测
`test_reused_session_keeps_original_chunk_geometry`（旧会话 8 B/片 + 新默认 4 B/片），
反证过：把参数去掉，测试立刻复现现场那句「分片 N 超过允许大小」。

## 🔁 回滚

删除 `kube-system/HelmChartConfig traefik` 中的 websecure 两行即可回到 60s 默认；
分片大小通过 Helm values 回填 `33554432`，仅影响新会话。
