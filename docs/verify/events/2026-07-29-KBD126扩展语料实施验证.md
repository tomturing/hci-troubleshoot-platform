### 8.3 五态结果与案例裁决

SignalResult 保留五态：

| 状态 | 含义 | 对案例裁决的影响 |
|------|------|------------------|
| `SATISFIED` | 成功观察且证据成立 | 可支持 must/should，exclude 成立时排除 |
| `CONTRADICTED` | 成功观察且证据不成立 | 可形成反证 |
| `UNKNOWN` | 信息不足、缺变量或无可判定输出 | 保持 inconclusive |
| `ERROR` | 工具、权限、超时或解析失败 | 保持 inconclusive，不当反证 |
| `NOT_APPLICABLE` | scope 不适用 | 按适用性处理，不当普通失败 |

案例 Verdict 只允许：

```text
confirmed / rejected / inconclusive
```

## 九、工程 Contract fixture 与分层 Replay

4 条工程 fixture 均拥有四类 outcome-level Decision Replay：

| Scenario | 要证明的行为 |
|----------|--------------|
| `positive` | must 全满足且 should 达标时可以 confirmed |
| `strong_negative` | 强反证或 exclude 成立时 rejected |
| `unknown` | 缺证据不能被压成反证，必须 inconclusive |
| `error` | 工具错误不能被压成案例不成立，必须 inconclusive |

当前测试直接把上述 scenario 中预设的 `SATISFIED/CONTRADICTED/UNKNOWN/ERROR` 构造成 Signal outcome，再验证 Case Reducer/Conclusion Gate。它没有执行：

```text
raw stdout/stderr/envelope
→ parser/extract/matcher
→ Signal outcome
→ Case verdict
```

也没有执行：

```text
Capability/Signal args
→ QFK Handler
→ ToolSemanticValidator/aCLI Catalog
→ mocked or real terminal bridge
```

因此本节的“通过”只表示 Decision Replay 通过。真实执行门复核结果：
