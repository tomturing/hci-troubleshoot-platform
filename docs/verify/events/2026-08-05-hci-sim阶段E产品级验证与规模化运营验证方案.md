# hci-sim 阶段 E：产品级验证与规模化运营验证方案

> **证据状态：pending。** 本文定义产品级验收方法，不证明任何 KBD、20 次稳定性或 100+ 容量已经通过。历史 KBD 27123 单轮 P0 Golden E2E 仅是历史参考，不满足本文退出标准。

关联[需求](../../requirement/events/2026-08-05-hci-sim阶段E产品级验证与规模化运营需求.md)、[方案](../../solution/agent/events/2026-08-05-hci-sim阶段E产品级验证与规模化运营方案.md)和[任务](../../task/agent/events/2026-08-05-hci-sim阶段E产品级验证与规模化运营任务.md)。

## 验证目标

用独立 real/sim Oracle、Mutation、10～20 核心 KBD、20-repeat、1/10/50/100/200 容量、故障/安全演练和持续运营证据，决定哪些精确 KBD revision 和容量声明可标为 validated。验证失败或证据不足必须产生 blocked/gap/stale，而不是降低标准。

## 验证原则

1. **独立性**：真实 Run 与 sim Run 独立创建，Fixture/Matcher 不能互相自证。
2. **不可变性**：所有结论绑定代码、镜像、KBD、Bundle、配置和 Evidence digest。
3. **保留首次失败**：Retry 不覆盖 first-attempt 和 flaky。
4. **分层声明**：KBD 编译、TestRun、100 SSH Scenario、100 Agent、100 browser 分别结论。
5. **零容忍不变量**：串线、secret 泄漏、sim→real fallback、非预期真实访问必须为零。

## 样本选择与环境矩阵

核心 KBD 在执行前冻结 10～20 个，分层覆盖 Tool、Matcher、producer/consumer、多节点/容器、多 Signal Gate、output size 和 fault；未支持项保留在分母并标 gap。选择矩阵由 Product、KBD Expert 和独立 QA 签署。

| 环境 | 用途 | 关键控制 |
|---|---|---|
| 固定版本 sim staging | variants、repeat、mutation | 无 real credential/route，资源可观测 |
| 受控 real calibration | 独立真实 Oracle | 只读、授权、限额、审计、脱敏 |
| 容量环境 | 1/10/50/100/200 | 专用配额、固定拓扑、可重复数据集 |
| 故障环境 | Pod/DB/Redis/Registry/network | blast radius 限制、自动停止 |
| CI/nightly/periodic | 持续回归 | 依赖影响集、证据保留、waiver 到期 |

每个环境保存拓扑、replica/resource、autoscaling、DB/Redis/Registry 规格、网络策略、数据 seed、cache warm/cold 和观测查询。

## 容量执行协议

每一梯度至少包含 warm-up、稳定采样、fault window、恢复观察四段；持续时间以能覆盖 GC/cache/Lease 周期为准，并在执行前批准。固定：KBD/variant 分布、输出字节分布、到达模型、seed、Runner/Runtime replica 和 autoscaling 策略。

必须采集：

- Run throughput、passed/failed/inconclusive/reject；
- end-to-end 和 queue p50/p95/p99；
- CPU/RSS/GC/goroutine/fd/SSH session/channel；
- Registry/cache hit/miss/eviction/download bytes；
- Redis CAS/latency、DB pool/locks、outbox lag；
- streamed/output bytes、cleanup lag、orphan counts；
- 五层 canary 的 cross-scenario contamination。

任何一级正确性/隔离失败，停止更高级别；性能未达标也需先解释拐点和瓶颈，不能只增资源后删除首次结果。

## 认证阈值治理

- 关键安全/Conclusion mutation：100% detection。
- cross-scenario contamination、secret 泄漏、非预期 real access：0。
- 每 KBD 重复次数：至少 20，禁止用 Retry 凑数。
- 100 Scenario：必须有完整报告和零串线；具体 latency/throughput/flaky 阈值由阶段 E 试点实测后审批、版本化。
- 在阈值尚未批准前，结果只能标 baseline collected，不能标产品达标。

## 对抗性审查

- 故意选择一个当前 capability gap KBD，确认 dashboard 和分母不会消失。
- 用同源 Artifact 构造 real/sim 假差分，审查 provenance 独立性。
- 设计会通过宽 Matcher 但业务错误的 mutant，检验 Conclusion 层敏感性。
- 在容量运行中交换两个 Run 的迟到 exec-result，检验 attempt/run 绑定。
- 临近 waiver 到期制造退化，确认自动失效和阻断。
- 断开 metrics/trace exporter，确认测试不会因观测缺失误判 PASS；证据不足应 inconclusive。

Manifest 签名后不可修改；后续重新计算生成新版本并引用前一版本。Dashboard 只显示索引和衍生指标，原始证据必须按策略保留。

## 退出标准

- VE-01～VE-14、VE-16～VE-26 全部 PASS；VE-15 按声明范围分别 PASS 或明确 not-tested，不得借用 Scenario 结果。
- 10～20 核心 KBD 均有认证状态；validated 项满足差分、Mutation、variants、20-repeat，gap 项有 owner/SLA。
- 100 Scenario 零串线；200 受控降级并恢复；所有容量证据可复现。
- 故障、安全、持续回归、SLO/告警、waiver 和运营责任形成闭环。
- Product、KBD Expert、独立 QA、SRE、Security 基于签名 Evidence Manifest 签署具体声明。

只有满足退出标准后，才允许在现行文档中写“支持指定 KBD 自动构建仿真环境并验证效果”，且必须附适用 KBD/revision、容量和限制。否则应准确写为设计完成、实施中、试点或 capability gap。

## 失败分类与文档更新

分类：`sample_bias`、`provenance_not_independent`、`differential_drift`、`mutation_escape`、`variant_mismatch`、`flaky`、`capacity_saturation`、`cross_scenario_contamination`、`cleanup_leak`、`dependency_failure`、`security_incident`、`impact_miss`、`pipeline_bypass`、`alert_failure`、`waiver_violation`、`evidence_incomplete`。完成后同步需求、架构、接口、安全、部署、可观测性、任务、测试指南和 `docs/README.md` 的产品声明；任何 P0 事件还需走安全事件与 Bundle/基线撤销流程。
