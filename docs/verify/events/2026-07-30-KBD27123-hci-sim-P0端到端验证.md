## 4. 实施内容

### 4.1 hci-sim runtime

新增根级 Go module `hci_sim/`：

- 自定义 SSH Server，不启动 OpenSSH，不调用 `/bin/sh -c`；
- 只允许受控 `session`、`pty-req`、`env`、`exec` 和 controlled shell；
- Scenario Lease 绑定 test run、scenario、manifest hash、variant、mode、expiry 和 quota；
- 未知 Fixture 返回 exit 127 / `fixture_not_found`；
- policy deny 返回 exit 126，overload 返回 exit 75；
- canonical command fingerprint、bounded queue 和固定 worker pool；
- stdout/stderr 分流、chunk、delay、exit-status 和有界输出；
- OTLP Trace、JSON 日志、health/ready/status、Prometheus metrics；
- positive-realistic、negative、near-miss、permission、timeout Fixture。

### 4.2 Terminal Bridge

在 Windows/K3s 共用代码中增加：

- `execution_mode`、`test_run_id` 协议字段；
- `auth_type=lease` 和 `htp1.` token 识别；
- sim Lease 不追加真实 HCI 历史密码后缀；
- SSH env 传播 `TRACEPARENT/TRACESTATE/HTP_EXEC_ID/HTP_TEST_RUN_ID/HTP_NODE_IP/HTP_CONTAINER`；
- hci-sim 拒绝 env 时 fail closed；
- 自动节点 SSH 会话加入 WebSocket ownership tracker。

Bridge Smoke 首轮发现：默认会话断开后，自动节点会话未被 tracker 管理，导致 `hci_sim_ssh_connections_active=1`。修复后，显式 `ssh_disconnect` 和 WebSocket 断开都会清理默认会话及全部自动节点会话；回归测试验证相似工单前缀不会被误清理。

### 4.3 K3s / Helm

新增独立 Helm Chart `deploy/helm/hci-sim/`：

- Deployment、ClusterIP Service、ConfigMap Fixture；
- existing Secret 引用，Secret 内容不进入 Git；
- non-root、read-only rootfs、drop ALL、RuntimeDefault seccomp；
- readiness/liveness/startup probe；
- default-deny NetworkPolicy；
- 只允许 `hci-dev` Terminal Bridge 访问 TCP/2222；
- 仅允许 DNS 和 Tempo OTLP 出站；
- ResourceQuota、LimitRange、可选 PDB。
- 主 CI 的 Helm job 同时 lint/render `hci-platform` 与 `hci-sim`；镜像发布矩阵和本地 K3s build 清单均包含 `hci-sim`。

当前 live release：

```text
release=hci-sim
namespace=hci-sim-dev
replica=1
service ports=2222,8080
```

### 4.4 Headless Browser Runner

既有 `scripts/verify/terminal-bridge-browser-e2e.cjs` 增加 `password/Lease` 认证支持。私钥模式保持兼容；Lease 不写结果文件、不写控制台，只通过进程环境传入并填充当前 UI。

- Terminal Bridge 通过 NetworkPolicy 可以访问 hci-sim 2222，Agent E2E 已证明允许路径；

- hci-sim 到 Kubernetes API 的非必要出站被阻断；
- Pod 不挂载 ServiceAccount token、hostPath、runtime socket 或真实 HCI Secret。

## 6. 发现但不混淆的现存问题

### 6.1 CDD 完成后的再次用户输入会重采集

首次 Runner 在 S4 已完成后又自动发送“请继续自动诊断”，触发同一 conversation 再次执行 sig_001/sig_002/sig_003 和节点解析。稳定 signal exec_id 被复用，Artifact 按 `exec_id` 幂等更新，Diagnostic Item 未重复，但 SSH 物理命令确实再次执行。

该行为不是 hci-sim 串线，也不是本次干净单轮验收的重复；它暴露的是既有 CDD 跨轮完成态缺少结果复用门禁。建议后续增加：当 KBD revision、环境快照和结论均未变化时，S4 后普通“继续”直接返回已确认报告；只有显式“重新采集”才生成新 acquisition run 和新 exec namespace。

在该问题修复前：

- 不把“完成后再次继续不执行命令”列为已通过；
- 并发容量测试必须避免 Runner 自动追加无意义 follow-up；
- 物理执行数和 Artifact 数要分别统计，不能只看 Artifact UNIQUE 行数。

### 6.2 Artifact 尚无 fixture 专用列

当前 `bridge_execution_artifacts` 可通过 trace_id/exec_id 与 hci-sim Span/日志关联 fixture_id，但 Artifact 表本身没有 `scenario_id/fixture_id/fixture_manifest_hash` 专用列。P0 关联可审计，P1 控制面仍应补正式数据模型。

### 6.3 feature 分支手动 CI 不得自动晋级环境

为验证新增的 hci-sim 镜像构建门禁，本次在 `feat/hci-sim-p0` 上手动触发 `workflow_dispatch`。主 CI 原有 `auto-deploy-non-prod` 条件把任意分支的手动运行也视为可发布事件，导致未合并的 feature SHA 被同步到 dev/staging 环境仓；这与 Job 上方“仅 main push 触发”的设计注释和分支保护语义不一致。

本次已把环境晋级条件收紧为仅允许 `push && refs/heads/main`。`workflow_dispatch` 仍可执行测试、Helm 校验和镜像构建，用于验证新增 Dockerfile，但不再修改环境仓。误触发的 staging 标签已恢复到触发前最近一次 main 构建；dev 保留本次联调运行态。后续若需要手动晋级，应新增显式目标环境、受保护 Environment 和确认输入，不能把“手动构建”等同于“自动发布”。

## 7. 回滚

hci-sim 与 hci-real 物理隔离，回滚不会修改真实 HCI：

```bash
helm uninstall hci-sim -n hci-sim-dev
kubectl delete namespace hci-sim-dev
```

Terminal Bridge 的 sim 协议是向后兼容增量；真实 `ssh` 默认模式不变。观测 ConfigMap 如需紧急回退，应使用部署前备份恢复并重启 Alloy/Prometheus，不能恢复成长期缺少 `hci-sim-dev` 的声明式目标状态。

## 8. 后续门禁

进入 P1 前仍需：

1. 完成 Windows desktop Terminal Bridge compatibility smoke；
2. 完成独立 real/sim contract differential calibration；
3. 让 negative/near-miss/permission/timeout 经过真实 Bridge，关键变体再经过 Agent/CDD；
4. positive-realistic 重复至少 20 次并报告 flaky rate；
5. 补 cancellation/timeout 专用指标和 overload 压测；
6. 修复或正式接受 S4 后 follow-up 重采集语义；
7. 执行 1/10/50/100/200 容量梯度后，才宣称 100+。
