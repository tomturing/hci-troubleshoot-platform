## 二、 核心问题逐项解答 (First-Principles Explanations)

### 1. 截图 1：`user_input` 没有渲染效果？

*   **业务现象**：S0 确认分类后，AI 没有渲染 `user_input` 输入卡片，而是用纯文本询问用户硬盘 SN 或盘符。
*   **第一性原理剖析**：
    1.  **决策树 Schema 字段不一致**：数据库中存储的 `sop_document.tree_json` 中，节点 ID 字段为 `id` (例如 `"n-1"`)，节点名称字段为 `title` (例如 `"磁盘寿命到期"`)；而在 `agent-service` 的 `get_sop_node` 工具逻辑中，递归查找和结果序列化却使用的是 `node_id` 和 `name`。
    2.  **导航节点定位失败**：在 `nav.py` 的 `_find_node_in_tree` 递归匹配中，由于读取 `tree_json.get("node_id")` 得到 `None`，导致所有的节点查找（如匹配 `"n-1"`) 均以 `None` 告终，返回错误 `'节点 n-1 不存在于 SOP 决策树中'`。
    3.  **阻断变量请求流程**：由于无法定位 SOP 决策树的根节点 `n-1`，Agent 无法获知该节点需要收集哪些排障变量（如 `disk_sn`），进而**无法调用 `sop_request_variable` 工具**。
    4.  **降级为纯文本交互**：由于没有调用 `sop_request_variable`，后端没有产生任何 `AgentInteractiveRequest` 类型的 SSE 交互事件。因此，Agent 被动回退到了纯文本兜底对话模式，通过大模型自然语言在文本中让用户手动输入。

### 2. 为什么 `case`、`conversation`、`sop_execution`、`tool_result` 等表的 `trace_id` 还是不一样？

*   **业务现象**：这几张核心表的 `trace_id` 存在分叉与断裂。
*   **第一性原理剖析**：

```mermaid
graph TD
    Gateway["Gateway / Case Creation<br>(T1: 4aef966...)"] -->|1. 写入| CaseTable["case.trace_id = T1"]
    
    ConvCreate["POST /conversations<br>(T2: dc8aebc...)"] -->|2. get_current_trace_id()| ConvTable["conversation.trace_id = T2<br>(未继承 Case.trace_id)"]
    
    ConvTable -->|3. 显式读取并赋值| SopExecTable["sop_execution.trace_id = T2"]
    
    MsgStream["POST /messages/stream<br>(T3: 71a5fa9... / T4: dadd276...)"] -->|4. httpx context 丢失| AgentStream["agent-service /stream<br>(继承 HTTP 请求 Trace T3/T4)"]
    
    AgentStream -->|5. get_current_trace_id()| ToolTable["tool_result.trace_id = T3/T4"]
    AgentStream -->|6. get_current_trace_id()| AuditTable["audit_log.trace_id = T3/T4"]
```

1.  **会话继承工单 Trace 缺失 (Case $\to$ Conversation)**：
    *   工单创建接口产生首跳 Trace ID `T1` 并记入 `case.trace_id`。
    *   用户点击排障创建新对话时，`conversation-service` 接收到 POST 请求，并在 `create_conversation()` 服务层中直接调用 `trace_id = get_current_trace_id()`（即获取当前创建会话的 HTTP 请求 Trace ID `T2`），**并未从 `case` 表中查询并继承工单的 `trace_id`**，导致 Case 和 Conversation 从一开始即断裂。
2.  **SOP 执行成功继承会话 Trace (Conversation $\to$ SopExecution)**：
    *   当命中 SOP 创建 `sop_execution` 时，路由/服务层显式读取了 `conversation.trace_id` 并赋值给 `execution.trace_id`，因此二者一致（均为 `T2`）。
3.  **流式交互 HTTP 上下文丢失 (Conversation $\to$ AgentService $\to$ Tool/Audit)**：
    *   用户后续每次发送消息均是独立的 HTTP请求，FastAPI 中间件自动拦截并生成新的请求 Trace ID（如第一轮 `T3`，第二轮 `T4`）。
    *   虽然 `send_message_stream_only` 在启动时通过 `trace.attach(ctx)` 试图强行挂载会话 Trace ID `T2`，但在 FastAPI 的 ASGI 异步执行流中，手动挂载的 `NonRecordingSpan` ContextVars 在面对 Starlette 的 `StreamingResponse` 协程悬挂与流式迭代（Yield Points）时会被重置/覆盖。
    *   因而 `httpx` 客户端向 `agent-service` 发起请求时，携带的依旧是当前 HTTP 请求的主 Trace ID（`T3` 或 `T4`）。`agent-service` 接收后，异步审计日志服务在调用 `get_current_trace_id()` 时捕获的就是当前活跃的 `T3`/`T4`，从而落库在 `tool_result` 和 `audit_log` 中。

### 3. `tool_result` 表新增了很多 error（如缺少 `conversation_id`），该问题不是修改过了吗？为什么还有报错？

*   **业务现象**：工具执行日志显示 `acli_exec` 因 `"缺少 conversation_id，无法执行 acli 工具"` 执行失败。
*   **第一性原理剖析**：
    1.  **执行器单例初始化**：`CompositeToolExecutor` 在 `agent-service` 启动时作为 Singleton 实例化，其内部的 `self._conversation_id` 成员变量被初始化为 `None`。
    2.  **ReAct 引擎参数传递漏洞**：
        在 `react_engine.py` 的工具执行段，调用 `active_executor.execute()` 时：
        ```python
        result = await active_executor.execute(tool_name, tool_args)
        ```
        它仅传递了 `tool_name` 与 `tool_args`，**未通过关键字参数显式传递当前会话的 `conversation_id`**。
    3.  **SOP 执行器参数转发丢失**：
        当在 SOP 模式下时，`active_executor` 是包装后的 `SopToolExecutor`。该执行器虽然持有当前的 `self._conversation_id`，但它在将非 SOP 工具（如 `acli_exec`）转发给底层默认执行器时，调用的代码是：
        ```python
        # SopToolExecutor (sop_tools.py)
        return await self._default_executor.execute(tool_name, args)
        ```
        它**同样没有显式向下传递 `conversation_id=self._conversation_id`**！
    4.  **关键字参数降级为 None**：
        在 `CompositeToolExecutor.execute` 的定义中，`conversation_id` 是一个 **Keyword-only 参数**（`*, conversation_id: str | None = None`）。
        由于上述两层调用均未显式传递 `conversation_id=xxx`，导致它回退为默认的 `None`。而单例成员 `self._conversation_id` 也是 `None`，导致 `effective_conversation_id` 最终解析为 `None`，触发 `acli` 分类执行器的安全防线，返回报错。

### 4. 截图 2 中 Agent 确认主机改变，但截图 3 中 `sop_execution` 的 `context_variables` 字段却没有更新，这正常吗？

*   **结论**：这**完全正常**。
*   **第一性原理剖析**：
    1.  **变量更新时机**：根据排障平台设计，`sop_execution.context_variables`（变量池缓存）的更新是一项状态操作，只有在 Agent 成功执行 `sop_advance` 推进决策树节点，或者成功调用 `sop_request_variable` 提取变量入池时，才会在 API 层面触发更新。
    2.  **树定位故障导致状态停滞**：如问题 1 所述，由于决策树 JSON 字段匹配失败，在两轮对话中，Agent 所有的 `get_sop_node` 尝试均报错。
    3.  **无状态推进操作**：因为 Agent 无法正确定位其所在的决策树节点，也就无法在推理逻辑中发起 `sop_advance`（数据库日志证明 `sop_advance` 从未被成功运行）。所以，状态更新 API 根本没有被调用过，数据库中的 `context_variables` 字段自然保持了初始化时的历史状态而未发生任何改变。

### 5. 截图 4 中刚开始意图识别 S0 阶段，用户还没有确认分类，`has_sop` 为什么被置为 `true`？

*   **根本原因**：
    1.  **审计推断机制过于粗暴**：在 `PromptAuditService.write_prompt_audit` 中，`has_sop` 并非根据当前系统的状态机或确认分类逻辑判断，而是对发送给大模型（LLM）的**全部 Prompt 消息（包括 system prompt、history messages）进行贪婪的子字符串匹配**：
        ```python
        # prompt_audit.py
        if "SOP" in content or "sop" in content:
            has_sop = True
        ```
    2.  **S0 提示词触发匹配**：意图识别 S0 阶段，系统提示词模板（System Prompt）以及交互上下文中，包含了大量的指示词汇（例如：“判断该工单是否匹配已有 SOP”、“查找匹配的 SOP 树”等）。
    3.  因此，代码中只要检测到发送的 Prompt 文本中出现了 `"SOP"` 或 `"sop"` 字样，就一律自动将 `has_sop` 置为 `True`，导致在尚未选择分类的 S0 阶段就已经发生了误判。
