# KBD 轻治理首批能力验收用例

本文用于在 PR 合并、数据库迁移和服务部署完成后，验证当前已经实现的轻治理纵向切片。它验证的是平台能力，不等同于 122 条 Proposal 的业务正确性，也不等同于 Expert Gold 或客户现场完整 Replay。

## 一、测试前提

### 1.1 环境

- kb-service、api-gateway 和 admin-ui 使用同一版本镜像；
- `20260729020000_add_kbd_revision_lightweight_governance.sql` 已在目标 PostgreSQL 成功执行；
- Admin 页面可以访问 `/knowledge/kbd-review`；
- 测试账号使用真实管理员认证。当前代码仍有 legacy `currentUser=1`，在真实身份接入前，不能将 actor 记录称为可信 Expert Gold；
- 测试 KBD 使用隔离的 draft 条目，不能直接修改客户正在使用的 active 内容。

### 1.2 API 变量

以下命令只使用环境变量占位符，不要把 Support Cookie、Token 或会话信息写入仓库、日志或文档：

```bash
API_BASE="https://<admin-gateway>"
AUTH_TOKEN="<通过安全方式注入的内部测试令牌>"
KBD_ID="<隔离的 draft KBD id>"
```

## 二、首批人工验收用例

| 编号 | 能力 | 操作 | 预期结果 |
|---|---|---|---|
| KBD-REV-001 | Proposal 基线保留 | 打开 draft KBD，第一次修改标题或 Signal 并保存；调用 revisions API | 出现 `revision_type=proposal` 和 `revision_type=expert`；Proposal payload 与专家稿分开保存；`parent_revision_id` 正确；未创建 runtime active |
| KBD-REV-002 | 工作稿与发布分离 | 连续修改两次并分别保存，然后刷新详情 | `working_revision_id` 指向最新 Expert；`revision_no` 单调递增；Agent 当前 active revision/checksum 不变 |
| KBD-REV-003 | 相同 payload 的正式批准 | 不再修改内容，直接点击“完成审核并发布” | 新增独立 Expert Revision；`validation_summary.status=passed`；审核备注被保存；不能复用仅有 `status=saved` 的工作稿 |
| KBD-REV-004 | 乐观锁冲突 | 在两个浏览器打开同一个 draft；浏览器 A 保存后，浏览器 B 使用旧页面继续保存 | B 返回 409 `KBD_EDIT_CONFLICT`；页面提示刷新；A 的工作稿不被覆盖 |
| KBD-REV-005 | 已发布内容安全止血 | 对 `status=published` KBD 尝试普通编辑保存 | 返回 409；原 active revision/checksum 保持不变；页面提示使用 maintenance working（该入口尚未完成） |
| KBD-REV-006 | 撤回一致性 | 对已有 active 的 KBD 执行“退回草稿” | 同一事务内 `kbd_entry.status=draft` 且对应 `dynamic_resource_active` 被删除；Agent 不再通过该 active 指针消费 |
| KBD-VAL-001 | 即时静态 Validation | 在审核页修改标题、分类或 Signal，点击“验证当前内容” | 错误/警告带 `code`、`location`、`message`；Validation 不创建 runtime revision、不切 active；契约已声明但运行状态未知时显示 warning，而不是误报 usable |
| CAP-001 | Capability Descriptor | 打开 ToolManage 和 KBD Signal 能力状态，或请求 `/api/v1/kbd/capabilities` | 返回 11 个 shared contract；`runtime_status=unknown`、`verification_status=contract_only`；ToolManage 显示“配置不等于可执行能力” |
| CAP-002 | 未知能力 fail closed | 在隔离 draft 的 Signal 中填入未声明工具名并验证 | 返回 `CAPABILITY_MISSING` error；不能发布；不会因为 ToolManage 中存在一条数据库记录而变成可执行 |
| DIFF-001 | 稳定身份 Diff | 调整两个 Signal 的顺序，并只修改其中一个 Signal 的参数 | Diff 只报告对应 Signal `id` 的字段 replace；不把数组位置变化报告成整组删除/新增 |
| UI-001 | 专家主路径 | 从列表打开案例，查看版本/问题，编辑 Signal，保存，验证，再发布 | 全程在 `/knowledge/kbd-review` 完成；能看到 Proposal/Expert/Active；保存后立即有校验结果；发布后显示 exact runtime revision/checksum |

## 三、API 级复核命令

### 3.1 查询版本和生效指针

```bash
curl -fsS \
  -H "Authorization: Bearer ${AUTH_TOKEN}" \
  "${API_BASE}/api/v1/kbd/${KBD_ID}/revisions"
```

重点核对：

- `latest_proposal_revision_id`；
- `working_revision_id`；
- `history[].revision_type`、`parent_revision_id`、`checksum`；
- `history[].diff_from_parent`；
- `active_resource.revision` 和 `active_resource.checksum`。

### 3.2 无副作用 Signal Review

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer ${AUTH_TOKEN}" \
  "${API_BASE}/api/v1/kbd/${KBD_ID}/review-signals"
```

调用前后分别查询 revisions 和 active 指针。两者不应因 Signal Review 发生变化。

### 3.3 Capability Descriptor

```bash
curl -fsS \
  -H "Authorization: Bearer ${AUTH_TOKEN}" \
  "${API_BASE}/api/v1/kbd/capabilities"
```

验收条件：

- `source=code`；
- `count=11`；
- 至少包含 `qkv_alert`、`qkv_task`、`qkv_dialog`、`qfk_system`；
- 所有当前 Descriptor 的 `runtime_status=unknown`；
- 未知能力不出现在 capabilities 列表中。

## 五、当前不能通过上述用例推出的结论

- 不能推出 122 条 Proposal 业务正确；
- 不能推出 126 条已经完成 Expert Gold；
- 不能推出 Agent Handler/Validator 已在当前生产集群部署；
- 不能推出已发布 KBD 的 maintenance working 已完成；
- 不能推出完整 Evidence/Execution Replay 已完成；
- 不能推出专家修改已经自动训练或优化了 LLM；
- 不能把当前 engineering fixture、单元测试或 outcome-level Replay 称为客户现场验证。
