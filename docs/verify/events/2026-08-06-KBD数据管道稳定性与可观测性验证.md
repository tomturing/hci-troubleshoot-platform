在恢复测试前的 KBD 内容后，另行执行只读 Stage 6 审计（不触发任何 LLM 或数据库写入）：

```bash
uv run python -m data-pipeline.kbd.run review-signals \
  --ids 25656,27736,35987,34164,27582 \
  --output /tmp/kbd-validation-audit.json
```

结果：5 个案例均被读取；按 `PASS_SIGNAL_REVIEW`、`NEEDS_SIGNAL_REVIEW` 和 `BLOCKED_SIGNAL_REVIEW` 统计，发现 4 个
`REJECTED_LOG_CANDIDATE`。这属于现有 Proposal 的审计事实，不是本次 Vision 失败导致的错误放行。

测试前保存并恢复了 5 个 KBD 的 `status`、分类、图片、Signal 和 `content_md` 关键字段，
核对结果为 5/5 `RESTORED`。由于 IMPORT override 遵守不可变审计原则，本轮产生的 5 条导入审计/Revision
记录没有删除，便于追溯这次测试操作。

> 环境边界：本次命令运行的是本 PR worktree 中的 data-pipeline，但调用的 kb-service 是
> staging 当前已部署镜像，并非本 PR 构建镜像。因此本次真实验证覆盖了 Pipeline 的并行调度、
> 案例级状态、硬依赖阻断、CLI 和日志链路；服务端新增的共享 LLM 舱壁/统一重试已由自动化回归覆盖，
> 仍须在本 PR 镜像部署至 staging 后补做一次 Provider 成功路径验收。

这轮真实验证没有把 Provider 429 伪装成代码成功。它确认了改造后的重要安全性质：
Vision 失败会被保留为可排障失败，并严格阻断 Signal/Audit；不会出现旧实现中“部分图片统计完成，
但下游仍继续生成低质量 Signal”的错误放行。

另外，异步 Job 将 Provider 的 429 包装成 RuntimeError 时，data-pipeline 现在会恢复为稳定的
`LLM_RATE_LIMITED` 中文错误码，而不是笼统的 `PIPELINE_UNEXPECTED`；该回归由
`tests/unit/kbd/test_error_catalog.py` 覆盖。
