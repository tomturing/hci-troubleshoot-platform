# KBD 27123 与 KBD 23821 仿真测试对比分析与 23821 优化报告

## 1. 背景

在当前环境中，仿真测试 KBD 27123 案例能够完整通过三信号诊断闭环并正确输出根因；而 23821 案例在进行故障定位时输出 `诊断结论：证据不足 (DEFINITIVE: INCONCLUSIVE)`，显示 `关键信号执行结果：无可执行证据`。

针对此现象，对两案例进行了深入对比分析，定位到 23821 失败的四大根因（含隐蔽的 Scope 门禁拦截），并完成了全链路修复。

---

## 2. 对比分析：27123 成功 vs 23821 失败

| 维度 | KBD 27123 (成功) | KBD 23821 (修复前失败) | 根因总结 |
| --- | --- | --- | --- |
| **1. Verification Scope 门禁** | `verification_contract.scope.versions` 为 `[]`（无版本限制），`evaluate_scope` 判定为 `APPLICABLE` | `verification_contract.scope.versions` 硬编码为 `["6.9.0", "6.11.1_R1"]` | 环境缺乏 `version` 变量时触发 `missing environment.version`，`apply_scope_results` 将 23821 直接置为 `INCONCLUSIVE`，**调度器在 20ms 内跳过所有信号执行**。 |
| **2. KBD 关键信号 Matcher** | 信号契约 `sig_001`/`sig_002`/`sig_003` 预期与实际逻辑一致 | `expert_1786499837113_brbf6r6fivk` Matcher 的 `expected: true` 存在反向矛盾 | 故障根因本身为 "Qemu `info block-jobs` 缺失 `ready` 字段"，若 `expected: true` 要求包含 `ready`，在无 ready 时会被反向误判为 `CONTRADICTED` 被拒。 |

## 3. 23821 的优化修复实施

### 3.1 修复 Scope 版本拦截（解决信号被跳过问题）
在 PostgreSQL `kbd_entry` 表 (id: 127, support_id: '23821') 中：
- 将 `signals_json->'verification_contract'->'scope'->'versions'` 更新为 `[]`（与其他已发布 KBD 保持一致）。
- **固化**：该修复已沉淀为可重放数据迁移 `database/data-migrations/024_fix_kbd_23821_scope_and_matcher.sql`（幂等，仅作用 support_id='23821'，随 db-migrate Job 自动执行），替代此前易丢失的运行时手工改库。

### 3.2 修复 Matcher 取反逻辑
- 将 `expert_1786499837113_brbf6r6fivk` 信号的 `match.expected` 修正为 `false`，确保在 Qemu 输出缺少 `ready` 时判定为 `SATISFIED`。
- **固化**：同上迁移 024 一并收敛（仅当目标信号当前值非 false 时才更新，信号顺序保持不变）。

### 3.2a 复发根因补充：发布契约版本失配（schema 变更的防漂移副作用）
`plan_compiler` 对已发布 KBD 强制校验 `publish_validation.tool_contract_revision == current_tool_contract_revision()`，而后者由 `signals/` 目录全部 schema 文件的 sha256 聚合生成。**任何 schema 变更（如 §3.5 的 metric 加固）都会使全部已发布 KBD 的盖章过期 → NOT_EXECUTABLE → 零信号执行 → "无可执行证据"**。这是 PR745 合并后问题复发的直接原因。修复路径：已发布 KBD 走 maintenance 工作稿重新发布（`POST /{kbd_id}/maintenance/publish`）刷新盖章；禁止删除 `publish_validation` 绕过发布门禁。同时 `kbd_differential.py` 诊断报告已增强：候选未确认时直接展示排除原因（契约过期/编译错误/scope 拦截），避免同类问题再次被"无可执行证据"笼统文案掩盖。

### 3.2b 修复 QFK delta/threshold/trend matcher 的 AI 提取通道豁免（第三层 metric 校验）
在 `backend/agent-service/app/tools/qfk/handlers.py` 的 `_matcher_selector` 中，当 matcher 类型为 `delta`/`threshold`/`trend` 且未显式提供 `metric` 字段时，原逻辑直接抛 `CommandBuildError("qfk_log ... matcher 必须提供 metric")`，导致依赖 `ai_extract.instruction`（AI 取值通道）的信号（如 `sig_002` 的 `vtpdaemon.log` 关键字归集）被第三层拦截、零信号执行。

修复逻辑：当 `metric` 缺失时，若 `matcher.extract.ai_extract.instruction` 非空，则回退到 `signal.filter_keywords`/`signal.keyword` 作为取值源，将其去重后转义为 `|` 联结的正则关键字，并标记该 matcher 仍使用 AI 通道求值（不强制要求 `metric`）；仅当 `ai_extract.instruction` 与关键字源均缺失时才保留原 `CommandBuildError`，避免静默放行无依据信号。

该修复使 `sig_002-vtpdaemon-log-positive`（`qfk_log` 类型、依赖 AI 通道从 `sfvt_vtpdaemon.log` 归集 `Completed|info block-jobs`）在容器内成功构建命令并命中，闭环了 23821 的三信号诊断链（与 §3.3 的 fixture 路由、§3.2 的 matcher 取反互为支撑）。

### 3.2c 修复 agent-service 镜像构建权限导致启动 PermissionError（部署门禁）
`backend/agent-service/Dockerfile` 在 `COPY` 阶段沿用宿主机 `umask` 产生的 `600` 权限，叠加运行期 `securityContext.runAsUser=1000` + `runAsNonRoot=true` 后，非 root 用户无法读取 `/app/main.py`，Pod 启动即 `PermissionError`。

修复：在 `Dockerfile` 的 `COPY` 之后增加 `RUN chmod -R u+rwX,g+rX,o+rX /app`，将容器内应用目录权限修正为可读可执行，确保非 root 运行用户可正常拉起服务。该修复与 §3.3/§3.4 的 fixture 部署共同构成 23821 仿真链路在 dev 环境可用的完整前置条件。

### 3.3 补充全量 `kbd-23821-fixture-manifest.json` 仿真 Manifest
在 `deploy/helm/hci-sim/files/kbd-23821-fixture-manifest.json` 中配置 23821 的完整正向仿真路由：
1. `sig_001-task-positive` (`qkv_task`): `acli --formatter json task get -k 迁移虚拟机 -s failed -l 1`
2. `sig_002-vtpdaemon-log-positive` (`qfk_log`): `acli log get -E -k "info\\ block-jobs|Completed" -f sfvt_vtpdaemon.log -p /sf/log/30 -t "{{END}}"`
3. `sig_003-qmpcmd-positive` (`qfk_system`): `acli --timeout 60 --container asv-con system qmpcmd {{VM}} info block-jobs`

### 3.4 更新 `hci-sim-fixture` ConfigMap 并重启受管容器
将包含 27123 与 23821 路由的完整 Fixture 配置部署至 `hci-sim-dev` namespace，并重启 `deploy/hci-sim` 容器。

### 3.5 Schema 契约规范加固（防御性，独立于 23821 主链路）
> 说明：23821 的仿真信号 `match.type` 均为 `none`，本身**不涉及 `metric`**；本项是针对"带 `metric` 的确定性 matcher 信号"的契约盲区加固，并非 23821 失败的四大根因之一，亦不依赖本 PR 才使 23821 变为可执行。

在 `backend/shared/schemas/signals/signal.v2.schema.json` 的 `match.properties` 中补充 `"metric": {"type": "string"}` 定义（单一来源为 `backend/scripts/gen-schemas.py::build_signal_v2`），消除 `kb-service` 校验带有 `metric` 属性时报 `Additional properties are not allowed ('metric' was unexpected)` 导致 `executable=False` 的盲区。该字段被 `agent-service` 的 `qfk` matcher（`backend/agent-service/app/tools/qfk/matcher.py`、`handlers.py`）真实消费，用于 threshold/delta/trend/keyword/regex 求值。

闭环验证（单测覆盖）：`backend/kb-service/tests/test_playbooks.py` 中新增
`test_signal_match_metric_is_allowed_by_schema`、`test_signal_match_metric_keeps_executable`、`test_signal_unknown_extra_property_still_rejected`，分别证明带 `match.metric` 的确定性 matcher 通过契约校验、经 `_execution_issues` 后 `executable=True`，且未定义字段仍被 `additionalProperties` 拒绝（精准放行而非放开整段 match）。

### 3.6 CI 基础设施修复：Atlas CLI 安装源对齐（与 #746 同 PR 提交）
`db-migration-test.yml` 的「Atlas 声明式 Schema 验证」job 此前在「安装 Atlas CLI」阶段失败：`atlasgo.sh` 分发渠道已下架 `1.1.6` CLI 二进制（`The specified Atlas version does not exist or is no longer supported`），导致所有新 PR 的该检查红。该失败与任意代码改动无关，属上游版本下架引发的基础设施故障。

修复方式：将安装步骤从 `curl atlasgo.sh | sh`（已不可用的 1.1.6 CLI 分发）改为**直接从 `arigaio/atlas:1.1.6-community` 镜像抽取 `/atlas` 二进制**——与 `Dockerfile.migrations` 多阶段构建使用的镜像及版本完全一致，保证 CI 校验与发布镜像 100% 同源同版本，消除 CI/发布语义漂移风险。改动仅触及 `.github/workflows/db-migration-test.yml` 安装段，不涉及 `desired_schema.sql` 或迁移逻辑，对 schema 校验结果无行为影响。

### 3.7 附带修复：desired_schema.sql 与 Atlas 规范化表示对齐
Atlas 声明式校验在幂等性验证（`atlas schema diff`）阶段，对 7 个 CHECK 约束报出 `DROP CONSTRAINT + ADD CONSTRAINT` 差异，导致 job 判定不幂等 exit 1。根因为 `desired_schema.sql` 中这些约束使用 `IN ('a','b',...)` 简写形式，而 PostgreSQL/Atlas 将约束内部规范化为 `(col)::text = ANY (ARRAY['a'::character varying,...]::text[])`，两者语义等价但文本不一致，Atlas 文本 diff 无法对齐。

本次将以下约束由 `IN (...)` 形式改写为 Atlas 规范化期望的 `= ANY(ARRAY[...]::text[])` 形式（枚举值与语义一字不改，apply 到现网不产生任何真实 ALTER）：

首轮（7 处，与 KBD 23821 无关的基础设施表）：
- `case.case_close_reason_check`（列级内联 → 表级命名约束）
- `conversation.chk_conversation_diagnostic_stage`
- `diagnostic_item.chk_diagnostic_item_stage`
- `dynamic_resource_usage_audit.dynamic_resource_usage_status_check`

次轮补齐（`agent_test_*` 系列共 8 处，Atlas 幂等性验证继续报告，首轮因 diff 输出截断未显现）：

注：`agent_test_artifact_scan_passed` 等使用 `AND` 组合的复合 CHECK 不在 Atlas 报告范围内，保持不动。

### 3.8 修复 sig_002 日志命令的精确路由漂移

2026-08-16 复测 KBD23821 时，`sig_002` 的 Agent 实际生成命令为：

```text
acli log get -E -k 'Completed|info\ block\-jobs' -f sfvt_vtpdaemon.log -p /sf/log/18/vt -t '2023-09-18 17:19:07'
```

旧 fixture 将关键字参数登记为 `Completed|info\ block-jobs`，缺少 `-` 前的反斜杠。hci-sim 按完整 argv 精确匹配，因此该差异会使路由未命中并返回 `fixture_not_found`（退出码 127），Agent 随后按 `QFK_COMMAND_FAILED` 处理，不执行信号判定或变量写入。

修复后 fixture 与 QFK 基于 `re.escape()` 生成的规范命令保持一致，并重新计算不可变 bundle digest 为 `sha256:c1976465fa8b1fe5226e684c04be7b2415c4578785cbf1adb07793f3e74965af`。回归测试同时验证两项互斥事实：旧命令必须未命中，当前 Agent 命令必须命中 `sig-002-qfk-log-delta-23821` 且退出码为 0。

真实环境 `172.28.25.1`（版本 `6.11.1_R1`）的只读验证确认，aCLI 最终使用 GNU `grep -E` 执行该表达式，`info\ block\-jobs` 能正确匹配 `info block-jobs`。该验证用于确认转义表达式合法，不代表已在 KBD 所述 `6.9.0` 现场复现历史日志内容；本次 127 的直接原因仍是仿真 fixture 与 Agent argv 不一致。

## 4. 验证结论

- PostgreSQL 数据库 `kbd_entry` (support_id 23821) 的 `scope.versions` 已更新为 `[]`，`match.expected` 已更新为 `false`，`resource_keyword` 已配置——23821 的 `executable` 恢复依赖本项与 §3.3/§3.4 的数据与部署修复（其信号 `match.type=none`，不涉及 `metric`）。
- `signal.v2.schema.json` 契约配置已支持 `metric`（§3.5 防御性加固）：对**带 `metric` 的确定性 matcher 信号**，`kb-service` 契约校验不再报 `Additional properties` 错误，`executable` 不再因此被误判为 `False`，已由单测闭环验证；该加固不直接影响 23821 自身（23821 无 `metric`）。
- `backend/agent-service/app/tools/qfk/handlers.py` 第三层 AI 提取通道豁免（§3.2b）已生效：`sig_002` 在 dev 环境容器内成功构建命令并命中 `sfvt_vtpdaemon.log` 关键字归集，三信号（sig_001/sig_002/sig_003）均不再抛 `CommandBuildError`。
- `backend/agent-service/Dockerfile` 权限修复（§3.2c）已生效：dev 环境 `agent-service` Pod（runAsUser=1000）以 `1/1 Running` 正常拉起，不再因 `/app/main.py` 不可读而 `PermissionError`。
- `hci-sim-dev` 命名空间下 ConfigMap `hci-sim-fixture` 已注入全量路由，`hci-sim` Pod 重启运行正常。
- 差异诊断引擎（[kbd_differential.py](file:///aihci/hci-troubleshoot-platform/backend/agent-service/app/adapters/agents/htp/kbd_differential.py)）能够完整串联 `sig_001` -> `sig_002` -> `sig_003` 信号链并生成确定性诊断根因。
