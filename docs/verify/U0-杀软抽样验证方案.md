## 一、为什么需要这一步

U0 解决了体积问题：`16.47MB → 4.72MB 未压缩基线`，再经 `upx --lzma --best` 压到 **3.13MB** 分发。

但 UPX 加壳是**真实的拦截面**：企业 EDR 的启发式规则、AppLocker/WDAC 的签名策略、部分国产杀软的"加壳程序"规则，都可能直接隔离或阻断。设计文档承诺"发布前抽样验证主流杀软"，却一直没有验证记录——这是当时唯一未闭环的架构债务。

**必须说清楚的一点**：本方案提供的是**可复现的取证流程与判定标准**，不是验证结论。结论只能来自实机扫描，且必须把原始报告留档。

**范围收敛（2026-11-23，产品决策）**：本期 U0 只要求覆盖 **Windows Defender**，已完成实测并留档，U0 据此闭环。360 / 火绒 / Server+AppLocker / 企业 EDR **未验证，也不构成本期结论的一部分**——它们的正确标签是"**未测**"，不是"通过"。见 §7.2 的收敛依据与重启触发条件。

## 二、样本与判定标准

### 2.1 扫描对象

只扫**分发目录里那个文件**：`frontend/customer/public/downloads/terminal_bridge.exe`。

不要扫 `go build` 出来的中间产物，也不要扫未压缩备选——客户下载到的是压缩后的分发件，扫别的等于没验证。

### 2.2 检验矩阵（本期范围）

| # | 环境 | 引擎/策略 | 本期范围 | 实测状态 |
|---|---|---|---|---|
| 1 | Windows 10/11 家庭/专业/工作站版 | Microsoft Defender（最新签名） | **必测** | ✅ 通过（2026-11-23，`v2.36.0-127`） |
| 2 | Windows 10/11 | 360 安全卫士 | 不在本期范围 | ⬜ 未验证 |
| 3 | Windows 10/11 | 火绒安全 | 不在本期范围 | ⬜ 未验证 |
| 4 | Windows Server 2019/2022 | Defender + AppLocker（默认规则） | 不在本期范围 | ⬜ 未验证 |
| 5 | 任一 | 企业 EDR（客户现场若有） | 不在本期范围 | ⬜ 未验证 |

版本号必须记录：只写"Defender 通过"没有意义，签名版本不同结论会变。

**原矩阵（v1.0~v1.2）把 #2~#5 列为"必测"**。2026-11-23 产品决策把范围收敛到 Defender 单引擎；矩阵保留全表是为了让后来人看清"哪些是真测过、哪些是没测"，不是把没测的算作通过。重启第 2~5 项的条件见 §7.2。

### 2.3 判定标准

| 结果 | 判定 | 动作 |
|---|---|---|
| 扫描无告警，进程可启动并输出 `-version` | **通过** | 记录留档 |
| 仅"未知发行者/低信誉"提示，无隔离 | **有条件通过** | 记录提示原文，评估是否需要代码签名 |
| 被隔离 / 被删除 / 被阻断启动 | **不通过** | 走第四节回退路径 |
| 启发式报"加壳/可疑"，但仍可运行 | **不通过** | 同上；加壳是根因，不能靠白名单掩盖 |

**判定人必须在报告里签字**（GitHub 评论 + 附件 JSON 均可），否则视为未执行。

## 三、执行步骤

### 3.1 Defender / Server 环境（可自动化）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify\u0_antivirus_probe.ps1 `
  -ExePath C:\path\to\terminal_bridge.exe
```

脚本产出 `u0-antivirus-report.json`，包含：

| 字段 | 用途 |
|---|---|
| `product.sha256` | 证明扫的是哪一份产物（与 `bridge-version.json` 对账） |
| `product.size_bytes` | 与 CI ≤5MB 门禁互证 |
| `product.pe_sections` / `upx_packed` | 证明确实是加壳产物（`UPX0`/`UPX1`） |
| `product.version` | 证明解压后能正常启动（加壳最常见的失败是"能扫不能跑"） |
| `product.signed` | Authenticode 状态（当前应为 `NotSigned`） |
| `defender.engine_version` / `signature_version` | 结论可复现的前提 |
| `defender.realtime_enabled` | 实时保护关闭时扫描结论不可信 |
| `defender.scan_threats_found` / `detections` | 是否命中，命中的资源路径 |
| `third_party[]` | 人工填写的其他引擎结论 |

需要管理员权限才能读全 Defender 状态；脚本会记录 `is_admin`，非管理员跑出的报告不作为最终依据。

**退出码与报告落盘（2026-11-23 修复）**：

| 现象 | 含义 |
|---|---|
| 结尾打印 `报告已写入: <路径>` 且 `Get-Content` 能读到 JSON | 正常 |
| 报 `Tee-Object ... 'Encoding'` | 旧脚本在 PS 5.1 上的缺陷（已修），此时**报告并不存在** |
| 退出码 `2` | 产物路径不存在（也可能是被杀软静默隔离，先去保护历史取证） |
| 退出码 `3` | 报告写入失败，本次取证无效，不要据此判定 |

跑完必须用下面这条确认文件真的存在，再进入判定：

```powershell
Get-Content "$env:USERPROFILE\Downloads\u0-antivirus-report.json" -Raw | ConvertFrom-Json | Format-List
```

### 3.2 360 / 火绒 / 卡巴（人工，**本期不执行**）

> 本节保留为**重启时的操作规程**（见 §7.2 触发条件）。本期范围只有 Defender，不要因为本节存在就认为这几项已测或必测。

1. 右键产物 → 使用该引擎扫描；
2. 记录引擎版本、病毒库日期、结论原文（截图）；
3. 填写到报告 `third_party` 数组对应项；
4. 双击运行，确认能出窗口并打印版本。

**注意**：这些引擎要装在**与 Defender 取证不同的机器**上。360/火绒会接管 Windows Defender，混在同一台会让 Defender 报告里的 `realtime_enabled` 变成 `false`，两份结论互相污染。

### 3.3 留档

把 JSON + 截图贴到本文件第七节的表格里（或作为 PR/issue 附件），并在此表登记一行。

## 四、不通过时的回退路径

**不要**用"加白名单"或"让客户关杀软"来绕过——那是把风险转嫁给现场。

已具备的两条退路（基建已就绪，不需要改代码）：

| 退路 | 做法 | 代价 |
|---|---|---|
| 发布未压缩产物 | CI 每次构建都会把未压缩版本传为 artifact `terminal_bridge-uncompressed`（保留 30 天）；用同样流程产物替换分发件，并重算 `bridge-version.json` 的 `sha256` | 体积 4.72MB（仍在 5MB 门禁内，不会触发 fail-closed） |
| 代码签名 | 采购证书后走 Authenticode；能同时缓解"未知发行者"提示 | 需证书与签名流水线，周期长 |

**注意**：`bridge-version.json` 的 sha256 必须按**最终分发件**重算——前端用它判断客户机上跑的版本，签错会让所有客户被误报"版本过旧"。

## 五、与 CI 现有守卫的关系

| 守卫 | 位置 | 覆盖 |
|---|---|---|
| 体积 ≤5MB fail-closed | `build-terminal-bridge.yml` | 防 upx 失效导致体积回归 |
| 清单 sha256 对齐 | 同上 | 防"清单与产物不一致" |
| 压缩后 `-version` 冒烟 | 同上（linux 同参数产物） | 防"能压不能跑" |
| 未压缩 artifact 留档 | 同上 | 提供回退物料 |
| **杀软抽样** | 本方案 | **人工/实机，CI 无法替代** |

前四项是自动化的；第五项永远需要人在真实环境里跑——这正是它一直没被做的原因，也是必须显式留档的原因。

### 7.2 范围收敛依据与重启触发条件

**决策**：2026-11-23 产品决策——本期只要求覆盖 Windows Defender，U0 据此闭环。

**为什么这不是"验证通过"**：Defender 通过只说明"在未接管 Defender 的常规 Windows 环境里加壳产物可扫可跑"，不说明 360/火绒/EDR 也不误报。它们的事实状态是**未测**。文档若把它们记成通过，下次真出误报时就没有任何依据可查。

**重启条件（满足任一，本条债务重新打开）**：

1. 出现**实际误报/隔离工单**（任一引擎），经复现确认由 UPX 加壳触发；
2. 目标客户环境以 360 / 火绒 / 企业 EDR 为主诉（实施侧提出即可，不必等工单）；
3. 分发件改变加壳参数、加壳工具或引入 Authenticode 签名（形态变了，旧结论失效）；
4. 引入 AppLocker/WDAC 强制策略的交付场景（如政务、金融客户）。

重启时按 §2.2 原矩阵逐项补测——不要因为"Defender 当年过了"就跳过其余引擎。

**分发件漂移提醒**：本次验的是 `v2.36.0-127-gefeb9efc`。后续 `terminal_bridge.exe` 重建会改变 sha256（如已排队但未合并的 exe PR），此时只有 **UPX 压缩参数与 Authenticode 状态均未变** 才可沿用本结论，否则需对新分发件补做一次 Defender 取证；已在 `bridge-version.json` 中核对的旧 sha256 记录不得直接复用。
