# SSH 终端 SFTP 文件下载方案

## 关联任务

[2026-10-27-SSH终端SFTP文件下载任务.md](../../../task/custom-ui/events/2026-10-27-SSH终端SFTP文件下载任务.md)

---

## 背景与目标

日志收集的“打包上传”链路（直传与平台中转）在现场存在异常，但 `acli` 在 HCI 后台打包日志本身正常。因此现场需要一个**绕开上传链路**的兜底手段：

> 把已打包好的文件直接从 HCI 主机下载到 `terminal_bridge` 运行的那台机器上，类似 Xshell / MobaXterm 的 SFTP 面板。

由此确定三条硬性语义（决定了整个方案形态）：

| 维度 | 结论 | 理由 |
|------|------|------|
| 落点 | `terminal_bridge` 所在机器（桌面模式=工程师本机，集群模式=Pod 持久卷） | 用户要的是“文件在我手上”，不是“文件在浏览器缓存里” |
| 通路 | 不经浏览器、不经平台存储 | 上传/中转链路本身有故障，再串一层只会增加失败面 |
| 交互 | 路径输入 + 目录浏览 | 现场文件路径往往已知；但目录浏览让“不确定路径”时也能找到文件 |

非目标：远程文件管理（删除/改名/新建/上传）。面板是**只读下载器**，任何写操作都不提供入口。

---

## 第一性原理拆解（硬约束）

1. **会话已存在**：用户必须已经 `ssh_connect`，复用该 `*ssh.Client` 开 SFTP subsystem，**不做二次认证**（避免密码在前端/协议里再走一遍）。
2. **浏览器不能指定本地路径**：桌面模式 `AllowedOrigins=*`，任意本地网页都能连 `ws://localhost:9999`。一旦接受前端传入的本地绝对路径，等于把“任意文件写入”开放给所有网页。→ 落盘目录**只能由 bridge 决定**。
3. **文件名是攻击面**：远端文件名可能含 `../`、反斜杠、控制字符、Windows 保留名（CON/NUL/COM1）、结尾点或空格、超长 UTF-8。→ 一律清洗为安全的 basename。
4. **字节不能走 WebSocket**：一个 5 GiB 的文件走 WS 帧会撑爆内存与帧长限制。→ WS 只走元数据（目录项/进度/落地路径）。
5. **不能堵住交互式 shell**：下载发生在独立 goroutine，且与 shell 用不同的 SSH channel。
6. **设备差异**：部分 HCI 版本禁用 SFTP subsystem。→ 必须有降级通道，否则功能在部分客户环境直接不可用。

## 方案设计

### 传输通路

```
浏览器 ──WS(JSON,仅元数据)──> terminal_bridge ──SFTP subsystem──> HCI 主机
                                     │
                                     └── 落盘到本机目录（.part → rename）
```

- 主通路：`github.com/pkg/sftp` 在既有 `*ssh.Client` 上开 subsystem，`Open` + `Seek` 支持续传。
- 降级通路：subsystem 不可用时，改走 exec 通道 `tail -c +N <path>` 流式拉取（该模式在日志收集 P3 搬运中已现场验证）。此时目录浏览不可用，面板提示用户“请直接输入文件绝对路径”。

### 落盘目录探测

按可写性依次尝试，取第一个 `MkdirAll` 成功的目录（集群模式下 Pod 以非 root 运行，`$HOME` 往往不可写）：

1. `HCI_BRIDGE_SFTP_DIR`（显式配置）
2. `$HOME/Downloads/hci-sftp`（桌面模式，工程师本机直觉位置）
3. `/var/lib/terminal-bridge/downloads`（集群模式持久卷）
4. `$TMPDIR/hci-sftp`（兜底）

落盘目录通过 `download_dir` 回给前端并常驻展示——这是本功能唯一的“交付凭据”。

### 文件命名与冲突

- `sanitizeSftpLocalName`：`path.Base` → 非法字符与控制字符替换为 `_` → 裁掉结尾点/空格 → 空名回落 `download.bin` → 超 120 rune 保留扩展名截断 → Windows 保留名加 `_` 前缀。
- 同名文件**绝不覆盖**：同大小视为“上次已下完”（幂等跳过，`status=exists`）；不同大小改用 `-2`、`-3` 后缀。
- 续传：`.part` 残留即从该长度续传；续传前对已有片段重新做 SHA-256 摘要，保证最终摘要与远端一致。

### 一致性保证

- 下载中写 `<name>.part`，**校验大小一致后**才 `os.Rename` 成最终文件；大小不一致宁可失败也不留一个“看起来完整”的坏文件。
- 完成后回 `sha256`（完整文件的摘要）与 `duration_ms`，便于现场核对。

### 资源治理

| 约束 | 值 | 理由 |
|------|-----|------|
| 单文件上限 | 5 GiB（`HCI_BRIDGE_SFTP_MAX_BYTES` 可调） | 超过基本是误点（镜像/磁盘镜像），应走专门搬运方案 |
| 全局并发 | 2 | 再多会挤占交互式 shell 的带宽与 SSH channel |
| 进度节流 | 200 ms | 每 512 KiB 发一条会在弱网上把 WS 灌满，反而拖慢字节流 |
| 单次列表 | 2000 项（超出置 `truncated`） | `/sf/data` 下动辄上万条目，全量回包会撑爆帧并拖死 UI |
| 断连回收 | WebSocket 断开即取消该连接发起的下载 | 否则浏览器关掉后 goroutine 仍会把整个文件拉完，白占客户带宽 |
| 超时 | 下载不设总超时，只可取消 | 大文件耗时不可预估，固定超时会变成“越大越容易失败” |

## 协议契约

请求统一为 `type: "sftp_op"`，复用既有字段：

| 字段 | 说明 |
|------|------|
| `sftp_action` | `list` \| `download` \| `cancel` |
| `sftp_path` | 远端绝对路径；`list` 时为空表示“给我登录用户的 home” |
| `exec_id` | 下载任务 ID（`list` 可空），由**前端**生成，用于配对进度与取消 |
| `node_ip` | 会话键 `caseID@nodeIP` 的节点部分，缺了只能靠兜底匹配 |
| `trace_id` | 端到端链路追踪 |

**刻意不存在** `local_path` 等本地落点字段（见硬约束 2）。

响应三种：

| type | 时机 | 关键字段 |
|------|------|----------|
| `sftp_list_result` | 目录读取成功 | `sftp_data{path,parent,download_dir,entries[],truncated}` |
| `sftp_transfer_progress` | 准备/下载中/终态 | `sftp_data{task_id,phase,bytes,total_bytes,percent,transport,status,local_path,sha256,download_dir}` |
| `sftp_result` | 动作终态（含错误） | `error_type` + `message` + 可选 `sftp_data` |

错误短名（`error_type`，与 `vm_console` 一致：短名进结构化日志，不登记进 `log_collect` 的 `LC-*` 目录）：

`sftp_unavailable`、`session_missing`、`invalid_path`、`invalid_task`、`invalid_action`、`not_file`、`too_large`、`local_io_failed`、`remote_io_failed`、`size_mismatch`、`too_many_tasks`、`duplicate_task`、`cancelled`。

## 前端设计

- 面板位于 `TerminalPanel` 的终端舞台与命令输入区之间，**仅 `terminalState === 'C'`（已连接）时渲染**。
- 默认收起，点击标题展开；展开且列表为空时自动请求默认目录（远端 home）。
- 顶部常驻“保存到本机”路径 + 复制按钮；目录行点击=进入，文件行点击=下载；另有独立的“手动路径下载”输入框（SFTP 不可用时的唯一入口）。
- 进度按 `task_id` 过滤：只接受当前任务的进度，旧任务迟到消息直接丢弃，避免进度条被拉回。
- 目录请求 10 秒超时：旧版 bridge 不认识 `sftp_op` 会静默丢弃，不给超时就是无限转圈。
- SSH 断开（`cleanupSshWebSocket`）即清空目录快照：否则重连到另一台主机时面板会先展示上一台的目录，用户误点就把 A 机路径发到 B 机。

## 可观测性

- 结构化日志（`blog`）：`sftp.list`、`sftp.download_start`、`sftp.download_done`、`sftp.download_failed`、`sftp.download_exists`、`sftp.download_cancelled`、`sftp.cancelled`、`sftp.session_missing`、`sftp.session_fallback`、`sftp.unavailable`、`sftp.list_failed`、`sftp.rejected`、`sftp.exec_fallback`、`sftp.tasks_cancelled_on_disconnect`。
- Prometheus：`bridge_sftp_downloads_total`（真正开始传输的次数）、`bridge_sftp_download_errors_total`（失败次数）。
- 每条日志携带 `trace_id`（缺省用 `sftp-<task_id>` 兜底，保证单次下载可串起来）。

## 对抗性审查：方案会在什么条件下失败

| 失效场景 | 现状处置 |
|----------|----------|
| 远端禁用 SFTP subsystem | 自动降级 `tail -c +N` exec 通道；目录浏览明确报 `sftp_unavailable` 并提示改用路径直下 |
| 磁盘写满 / 目录不可写 | `local_io_failed` + 具体错误；不产生半成品最终文件（只有 `.part`） |
| 下载中断网 | `.part` 保留，重试自动续传；消息明确“已下载部分保留” |
| 远端文件下载中被改写 | 大小核对失败 → `size_mismatch`，宁可失败不留坏文件（时间戳校验未做，属已知边界） |
| 用户重复点击下载 | 同名同大小幂等跳过；不同大小生成新文件；并发上限兜底 `too_many_tasks` |
| 浏览器被恶意页面操控（desktop 模式 Origin=*） | 落盘目录写死由 bridge 决定，文件名清洗，无法越权写任意路径；但仍**不能**防御“诱导用户下载恶意目标文件到下载目录”，这是 Origin=* 的既有风险面 |
| 旧版 bridge 未升级 | 前端 10 秒超时并提示升级；不静默失败 |
| 超 5 GiB 文件 | 明确报 `too_large` 并给出实际大小与上限，不做“悄悄截断” |
