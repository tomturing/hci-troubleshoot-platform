# 日志收集「请先连接 SSH」改为可点击的「连接 SSH」

> 版本：v1.0
> 日期：2026-11-02
> 关联代码：`frontend/customer/src/components/LogCollectPanel.vue`、`frontend/customer/src/components/SshConnectDialog.vue`、`frontend/customer/src/stores/chat.ts`、`frontend/customer/src/App.vue`
> 关联文档：[日志收集会话状态自愈与中继重试方案](../../events/2026-10-28-日志收集会话状态自愈与中继重试方案.md)（本文收敛了其中"按钮置灰"一条）、[排障前置 Bridge 与 SSH 门禁设计](2026-11-02-排障前置Bridge与SSH门禁设计.md)

## 一、现场反馈

2026-11-02 工单 `Q202610291522` 现场截图：

1. 日志收集面板底部主按钮显示「请先连接 SSH」，且**置灰不可点**；
2. 同一屏右侧 SSH 终端里就有一个可点的「连接 SSH」按钮（弹统一登录框）；
3. 用户的问题很直接：**同一个"缺会话"的状态，为什么左边的按钮不能点、还得自己去右边找入口？**

## 二、根因（第一性原理）

按钮是"动作"的载体，不是"状态"的载体。

- 前置条件不满足时，正确表达是**把前置条件本身变成可执行的动作**（"连接 SSH"），
  而不是把主按钮禁掉、把条件写成一句只读文案；
- 上一版（2026-10-28）把 `disabled` 加上 `!sshConnected`、文案切成「请先连接 SSH」，
  出发点是把点击后的 toast 提前成秒级视觉反馈，**但代价是把用户带进了死胡同**：
  他被要求做一件事，界面上却没有做这件事的入口；
- 唯一的入口在右侧终端面板，而它属于**另一个功能域**——用户没有任何理由知道去那里找。

结论：主按钮在未连接时应当变成「连接 SSH」，点击即弹出与右侧终端**同一个**登录框；
能不能采集由同一个派生值判断，按钮语义随之切换，不新增第二个按钮。

## 三、方案

### 3.1 一个派生值决定按钮语义（LogCollectPanel.vue）

```ts
const canCollect = computed(() => sshConnected.value && nodeIpReady.value)
```

- 会话断了谈不上采集；
- 会话在但读不到主机时，采集消息没有 `node_ip`，bridge 的 `caseID@nodeIP` 一定查不到会话（`LC-ENV-006`）。

按钮：

| `canCollect` | 探测中 | 文案 | 可点 | 点击行为 |
|---|---|---|---|---|
| false | — | 连接 SSH | 是 | 打开统一 SSH 登录框 |
| true | 是 | 正在读取环境… | 否 | —（此刻没有第二条路） |
| true | 否 | 开始收集 | 是 | 原 `handleStart` |

### 3.2 复用统一登录框，不另造表单

`requestSshConnect()` 与右侧终端 `TerminalPanel.handleOpenSshDialog()` 同构：
先 `checkBridgeBeforeOpen()`（bridge 未运行则弹框给下载引导），再 `openSshFlowDialog()`。

新增弹框模式 `log-collect`（`stores/chat.ts`），只影响两件事：

- 标题：「连接 SSH（日志收集需要会话）」——用户得知道自己从哪来；
- **成功后不打开右侧终端**：日志收集的下一步是「开始收集」，
  再弹一个终端只会多一层要关的窗口（与 `LogCollectCaseDialog` 内嵌登录口径一致）。

### 3.3 登录成功后不需要额外刷新

`nodeIp`（= 当前会话主机）从空变有，`watch(nodeIp)` 已有逻辑会重探，
`prepareState` 回到 `ready`，按钮自动变回「开始收集」。

### 3.4 文案同时改掉"去右侧终端"的指向

| 位置 | 旧文案 | 新文案 |
|---|---|---|
| 表单上方提示 | 请先在 SSH 终端连接 HCI 节点… | 尚未连接 HCI 节点：点击底部「连接 SSH」登录后即可读取场景目录与节点清单 |
| 底栏 hint | 选择时间范围与采集模块后开始收集 | 采集依赖 SSH 会话：点「连接 SSH」登录后即可开始收集 |
| 探测失败原因 | 请先在 SSH 终端连接 HCI 节点 | SSH 会话未连接：请点击面板底部「连接 SSH」登录后再读取环境 |

## 四、对抗性审查

| 失效条件 | 处置 |
|---|---|
| 用错工单号登录 → 会话键变成 `别的单号@nodeIP`，probe 仍报 `session_missing` | `requestSshConnect()` 固定传 `props.caseId`（本面板绑定的工单），不从 `currentCase` 猜 |
| bridge 未运行就点「连接 SSH」 | 先 `checkBridgeBeforeOpen()`，弹框按结果进入 Bridge 引导（下载/重新检测），不把用户丢进表单 |
| 连点两次按钮打开两层弹框 | `sshConnectOpening` 单飞；且 `sshFlowDialogVisible` 是同一个可见性开关 |
| 弹框开着期间会话又断（或键盘触发） | `handleStart` 内部守卫原样保留，作为兜底拦截，不再依赖按钮禁用 |
| 断线后按钮又回到死胡同 | 按钮文案由 `canCollect` 派生，`sshConnectionState` 一变立即切回「连接 SSH」 |
| 会话在但读不到主机（`sshCurrentConfig.host` 为空） | `canCollect=false`，按钮仍是「连接 SSH」，提示条说明"已连接但读不到会话主机" |
| 登录后弹右侧终端干扰采集 | `log-collect` 模式显式 `open-terminal=false` |

## 六、遗留

- 右侧终端若在连接前就已打开，登录后它会自动进入已连接视图；而终端的输入消息用的是
  `currentCase.case_id`（不是本次登录的日志收集工单号）。当两者不同（用「指定工单号」采集）
  时，在终端里敲命令可能被 bridge 丢弃。属既有问题，与本次改动无关，需要单独收敛
  "终端绑定哪个 case_id"的口径。
- 真机 UI 走查未做（本机无浏览器自动化），上线前需在浏览器里实测
  「未连接 → 点连接 SSH → 登录 → 自动重探 → 开始收集」整条链路。
