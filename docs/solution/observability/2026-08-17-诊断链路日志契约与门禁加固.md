# 诊断链路日志契约与门禁加固

## 1. 结论

诊断链路的“可观测”必须同时满足：一次调用可关联、每个阶段有唯一终态、失败有稳定错误码、业务输出可验证但不泄露原文、指标可聚合且标签低基数。仅记录 HTTP 200、模型调用成功或一段输出预览，不足以证明分类、识图、信号抽取和 QFK 判定正确。

本次实现覆盖统一日志底座、分类、Vision、关键信号抽取、QFK AI 取值、QFK 命令执行与 Matcher 求值，并把 Agent 可靠性回归前移到 PR 阶段。

## 2. 第一性原理约束

1. OTel `trace_id/span_id` 是跨服务调用链权威；`case_id/conversation_id/signal_id/exec_id/artifact_id` 是业务关联键，不能互相替代。
2. 一个阶段事件必须有一个开始和且仅一个终态。业务可判定失败与运行时异常必须区分。
3. 普通日志不是证据存储。完整命令输出、图片、Prompt 和模型原始响应留在受限 Artifact/Langfuse；Pod 日志只保存字节数、SHA-256、证据行号和结构化摘要。
4. 未知质量不得伪造。Vision 模型没有标定置信度或字符框时，`confidence/bbox/ocr_coverage` 保持 `null` 并要求审核。
5. Prometheus label 只能使用有限枚举。工单、会话、信号、执行流水和异常自由文本只能进入日志或 Trace 属性。

## 3. 对抗性审查结果

| 攻击场景 | 旧风险 | 当前控制 |
|---|---|---|
| 提前返回 | QFK 解析、命令、提取失败没有统一终态 | 公开 `qfk_exec` wrapper 统一记录开始与终态 |
| 模型返回合法 JSON 但顺序错误 | 分类直接采用数组第一项 | 合法候选去重并按 score 降序 |
| 模型只返回非法分类 | 构造数据库不存在的 `未分类-000` | 502 fail-closed，禁止写入 |
| Matcher 抛异常 | 静默降级为 UNKNOWN | `matcher_evaluation_failed` + 稳定错误码 + traceback |
| Token/密码嵌套在异常或 payload | 原样落入 Loki | logger 递归脱敏、自由文本凭据净化 |
| 超大输出或 traceback | 放大内存、日志费用和敏感面 | 有界截断，保留原长度和 SHA-256 |
| 业务字段伪造日志信封 | `kwargs` 可覆盖 service/event/trace | 保留字段不可覆盖并记录冲突 |
| PR 绕过 Agent 可靠性回归 | 只在 main 合并后运行 | 相关代码变化在 PR 阶段运行 |

## 4. 统一日志安全契约

`StructuredLogger` 输出 `log_schema_version=1` 的单行 JSON。`log_schema_version/timestamp/level/service/event/message/trace_id/custom_trace_id/span_id` 为保留字段，业务参数不得覆盖。

以下键及常见后缀递归替换为 `[REDACTED]`：Authorization、API key、access/refresh token、password/passwd、secret、credential、cookie。自由文本同时清理 Bearer Token、`key=value` 凭据和 URL 用户密码。

普通字符串正文上限为 4096 字符，traceback 上限为 16000 字符。超限格式为：

```text
<前缀>...[TRUNCATED original_chars=<原长度> sha256=<完整净化文本摘要>]
```

## 5. 阶段事件契约

### 5.1 QFK 执行

| 事件 | 级别 | 关键字段 |
|---|---|---|
| `qfk_engine_started` | INFO | namespace、mode、case/conversation/signal/requested_exec、matcher type/expected/operator/value |
| `qfk_engine_finished` | INFO | status、error_code、execution/processing status、matched、exec_ids、artifact_ids、command/output hash、evidence line、duration |
| `qfk_engine_failed` | ERROR | `QFK_UNHANDLED_EXCEPTION`、traceback、全部关联字段 |

`qfk_engine_finished.final_matched=null` 表示执行或处理失败，不能解释成“业务条件不成立”。命令退出码非零继续返回 `QFK_COMMAND_FAILED`，不执行判定或变量写入。

对应指标：

- `hci_qfk_executions_total{namespace,mode,status,error_code}`
- `hci_qfk_execution_duration_seconds{namespace,mode,status}`

### 5.2 QFK AI 提取

| 事件 | 关键字段 |
|---|---|
| `qfk_ai_extract_started` | case/conversation、value_type、matcher_type、输入字节数 |
| `qfk_ai_extract_finished` | candidate_count、evidence_line_numbers、response_chars/hash、duration |
| `qfk_ai_extract_failed` | 稳定 `QFK_AI_*` 错误码和关联字段 |

模型原始 JSON 不写普通日志。要核对具体 `value/evidence_lines` 时，按同一 trace 在 Langfuse 查看原始 generation，再用 Pod 日志中的响应 hash 校验是否为同一次响应。

### 5.3 分类、Vision 与信号抽取

- 分类：`classify_llm_response` 记录响应 hash；`classify_response_accepted/rejected` 记录合法/非法候选数量和最终置信度。
- Vision：`vision_llm_response/parsed` 记录图片 hash、切片数量、模型响应 hash、OCR 行/字符数和耗时；Evidence provenance 保存原图与变换切片 hash。
- 信号抽取：`extract_signals_llm_response` 记录来源 KBD/SOP、来源 ID、Prompt 版本、格式重试、响应 hash 和候选数；完成事件记录通过/拒绝数量。
- Matcher：异常记录 `matcher_evaluation_failed`；证据不足记录 `matcher_evaluation_inconclusive`，两者都返回 UNKNOWN，不伪装为业务 False。

## 6. KBD23821 排查顺序

按 `case_id` 或 `trace_id` 检索，并按时间排列：

1. `qfk_engine_started`：确认 signal、matcher type、expected 和执行模式；
2. Terminal Bridge 的 exec 结果：确认退出码、exec_id、artifact_id；
3. `qfk_ai_extract_finished`：确认候选数和引用物理行；
4. `qfk_engine_finished`：确认 execution/processing status、error_code、final_matched；
5. Langfuse generation：仅在需要核对具体模型 JSON 时查看，并以响应 hash 交叉验证。

对“Completed 两个数值”的正常提取，普通日志应显示 `candidate_count>=1`、非空 `evidence_line_numbers` 和 `QFK` 终态 `processing_status=succeeded`。具体 `[completed,total]` 值属于证据内容，不复制进普通日志。

## 7. CI 与供应链门禁

- `agent-reliability-regression` 在相关 PR 和 main 上运行；变化感知覆盖 QFK/QKV、KBD differential、分类、Vision、信号抽取及共享 CDD/Signal 代码。
- Trivy 对 HIGH/CRITICAL 漏洞返回非零，构建被阻断。
- `post-merge-verify.sh` 从真实仓库根运行，并兼容 `set -e` 计数器语义。
- `post-merge-verify.sh` 的 Ruff formatter 在全仓基线建立前明确标记为跳过，避免 117 个存量格式差异形成恒定失败的伪门禁；Ruff lint 继续硬阻断。
- 合并后单测按服务隔离；根级运行 unit/security，各服务运行除 `tests/integration` 外的测试。依赖 PostgreSQL/Redis/K3s 的 integration 归入 E2E，避免把环境未就绪误报成代码回归。
- 本机没有全局 pnpm 时通过 `corepack pnpm` 执行前端依赖校验，不写入全局 shim。
- Python 与前端依赖校验都使用 frozen 模式，验证过程不得改写 lockfile。

## 8. 已知边界与后续专项

以下问题未在本次日志契约 PR 中伪称解决：

1. Vision/Signal Job Manager 仍是进程内状态，多副本或重启恢复需要 Redis/数据库持久化专项；
2. Conversation SSE 的队列容量与 heartbeat 需要独立的背压、断线和慢消费者测试；
3. Catalog PVC 的 `ReadWriteOnce + local-path` 不保证多 Pod 共享热更新，应改为 kb-service 单写并通过版本化 API/快照分发；
4. Vision 模型不返回逐字 confidence/bbox，不能从整体响应推导伪置信度；
5. 完整 Docker/PostgreSQL、真实 Provider 与 K3s 发布后验证仍是上线门禁，单元测试不能替代。

## 9. 验收标准

- QFK 所有返回路径都有一个终态事件，未捕获异常有失败终态；
- 日志中找不到测试 Token、密码、API key 或 URL 密码；
- 分类正常候选按 score 排序，所有非法候选被 502 拒绝；
- Vision 和信号抽取可通过 hash、计数、Prompt/模型版本确认同一次处理；
- Python lint、编译、定向测试、Agent 可靠性回归、文档门禁和 Workflow 语法检查通过。
