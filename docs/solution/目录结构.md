## 二、后端微服务 (`backend/`)

### 2.1 服务架构概览

项目采用微服务架构，包含 **7 个核心服务** + **1 个共享模块**：

| 服务 | 端口 | 职责 |
|------|------|------|
| `api-gateway` | 8000 | 统一 API 网关、WebSocket 管理、路由代理 |
| `case-service` | 8001 | 工单生命周期管理（6 态状态机） |
| `conversation-service` | 8002 | 对话管理、SSE 流式、上下文组装 |
| `agent-service` | 8003 | AI 推理引擎（大脑路由 + 多种 BrainAdapter） |
| `kb-service` | 8004 | 知识库 RAG 检索、SOP 管理、分类路由 |
| `scheduler-service` | 8005 | Pod 热备池调度、助手注册表 |
| `eval-service` | 8006 | AI 评估与质量统计 |
| `shared` | — | 共享模型、数据库、客户端、工具类 |

### 2.4 目录差异设计原因

| 差异维度 | 需要更多目录 | 需要更少目录 |
|---------|-------------|-------------|
| **数据持久化** | 有 PostgreSQL → `models/` + `repositories/` | 无数据库 → 只需 `services/` |
| **业务复杂度** | 复杂业务 → `schemas/` + `services/` 多文件 | 简单业务 → 极简结构 |
| **外部集成** | 多系统适配 → `adapters/` | 单一协议 → 无适配层 |
| **核心抽象** | AI 推理引擎 → `domain/` + `adapters/agents/` | 业务逻辑 → `services/` |
| **数据处理** | NLP/向量 → `utils/` + `config/` | 无处理 → 无工具层 |

## 九、设计原则

每个服务的目录结构反映其职责边界，遵循以下原则：

1. **不为未来设计** — 只创建当前需要的目录，不预留空目录
2. **职责驱动** — 目录边界与服务职责严格对应
3. **拒绝模板复制** — 不套用"标准微服务模板"，每个服务按实际需求定制
