## 1. 目标与边界

关键信号把 KBD 中可验证的排障经验表达为受控采集、确定性处理和证据裁决。信号不是自由命令，也不是模型推测；其结论必须能追溯到发布修订、采集对象、原始输出或制品、处理规则和 Trace ID。

```text
工单事实 / 已采集证据
  → 候选入口
  → 受控现场观察
  → 变量与依赖图
  → 只读诊断验证
  → 案例证据门禁
  → 操作效果验证
```

`qkv_case_context` 只参与候选入口；它不采集、不产出变量、不直接确诊。客户提供的原始日志、截图或文字可以进入受控证据路径，但是否能形成确定性判断取决于来源、完整性、对象关联和处理契约。

## 2. 能力目录

| 职责 | 工具 | 输入前提 | 结果 | 不承担的职责 |
|---|---|---|---|---|
| 语义入口 | `qkv_case_context` + `semantic_entry_profile` | 客户描述；强生产者完整未命中或分类没有强入口 | 待验证候选或补证据问题 | 采集、变量生产、根因裁决 |
| 直接现场观察 | `qkv_task`、`qkv_alert`、`qkv_dialog` | 已登记的查询关键词和参数 | 同一记录中的上下文变量与原始观察 | 自由命令执行 |
| 条件现场观察 | `qkv_vm_console` | 可信 HOST、VM_ID 与策略开关 | 截图、视觉观察、制品关联 | 任意 Monitor 命令或按键 |
| 只读诊断验证 | `qfk_log/service/system/vm/network/storage/hardware/platform` | 解析后的依赖变量与安全参数 | Matcher 结果或声明的变量 | 处置动作 |
| 操作效果验证 | `qkv_effect` | 已发生的操作或诊断期症状、封闭观测通道和期望锚点 | `achieved`、`not_achieved`、`inconclusive` | 执行该操作本身 |

工具注册、参数约束和可执行分类的唯一代码来源是 [acquirer_args.py](../../../backend/shared/schemas/acquirer_args.py)。前端选项、发布门禁、运行时能力和自动建模目录必须从这份目录派生，不能另行维护工具集合。

## 3. 契约与执行不变量

1. `signal.v2.schema.json` 与 `validate_signals_json()` 定义保存结构；参数语义由 `validate_acquire_args()` 定义。修改参数契约后必须运行 `make gen-schemas`。
2. 每条 producer 只有在**一条完整记录**覆盖全部声明的 `produces` 时，才能解锁下游依赖；不得跨记录拼接变量。
3. 变量冲突保持锁存，必须经显式决议才能恢复；后续恰好出现旧值不能依赖执行顺序自动解锁。
4. `SATISFIED`、`CONTRADICTED`、`UNKNOWN`、`ERROR`、`BLOCKED` 是不同事实。`UNKNOWN` 不得因布尔转换成为反证。
5. 共享 acquisition 只共享物理采集；每个 SignalRef 必须独立运行投影、取值、处理和判定。
6. `END → DATE` 是平台派生变量，用于按自然日检索日志；发布门禁、计划编译和运行时变量池必须一致。
7. 离线 CDD 除变量名外，还须传递变量的实际值、Evidence ID 和生产 SignalRef。消费者只使用已渲染参数；无实际值或同名值冲突时保持 `UNKNOWN`/`BLOCKED`，不能把占位符或后写入值下发。
8. 在线、离线、试运行应对同一发布修订与同一证据得到相同的变量、证据和状态；任何能力暂不支持时返回 `UNKNOWN`，不伪造通过。

## 4. 时序和效果验证

`qkv_effect` 复用受控观察通道，支持稳定等待、有限复查和三态结果。它适合验证“操作后预期是否达成”或 `symptom_confirm` 模式下的症状确认。

启用 `expectation.progress.mode=change_required` 后，effect 会比较同一受控观测原语的 SHA-256 输出快照：首个有效观测为 `baseline`，后续变化为 `in_progress`，连续无变化超过 `idle_after_seconds` 才为 `stalled` 并产生 `not_achieved`；复核窗口结束但仍在推进则保持 `inconclusive`。快照摘要、指纹和进展状态写入 effect 审计时间线。

该能力不开放目录、路径或 Shell 字段。`qfk_storage` 已可作为 effect 的受控存储快照观测通道：它仍受现有 aCLI 参数校验、资源选择器和只读边界约束，只输出安全的存储查询结果供指纹比较。迁移目录级文件快照仍需独立登记采集器，不能借 progress 配置绕过现有采集边界。

## 5. 验收矩阵

| 层级 | 必须验证 | 入口 |
|---|---|---|
| 结构 | Schema、参数、变量 DAG、发布门禁 | `uv run python scripts/ci/check_signal_schemas.py` |
| 处理 | 每类取值、Matcher、完整记录、冲突和三态 | `backend/shared/tests/`、各服务 unit tests |
| 等价性 | 同一证据的在线、离线、试运行状态与变量 | Agent/Diagnosis contract tests |
| 样例 | 原 Signal v2 与语义入口样例的数据库生命周期 | `make diagnosis-sample-e2e` |
| 仿真 | 分类完整候选、正例、反例、Bundle 路由 | `semantic-online-matrix`、`signal-v2-*-matrix` |
| 现场 | 真实授权对象、策略开关、Trace、Artifact 和错误码 | 发布后运行验收 |

单元测试、仿真通过和现场通过必须分别记录，不能互相替代。

现行机器可读示例位于 [signal-examples.json](../../contracts/signal-examples.json)，由 Schema CI 校验。说明性文档中的片段应引用该文件或明确标记为历史示例。
