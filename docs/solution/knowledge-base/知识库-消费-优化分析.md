# 知识库「消费」优化分析

> **文档目的**：以第一性原理分析当前知识库"消费"环节（检索召回、知识注入、Prompt 组装、AI 推理质量）的核心问题，结合业界最佳实践给出具体优化方案。
>
> **消费定义**：从 AI Agent 发起知识检索请求，到知识被注入 LLM context、影响最终回答的完整过程。
>

## 一、现状诊断

### 1.1 当前消费链路全景

```
用户发送消息
        │
        ▼
conversation-service
        │
        ├─ [S0] POST /api/kb/classify → 确定 category_id
        │
        ├─ [S1+] 并发：
        │         ├── POST /api/kb/sop/match(category_id)  → SOP 全文（Markdown）
        │         └── POST /api/kb/search(query, category_id, top_k=5) → KBD top-5
        │
        ▼
  组装 messages[]（四层 Prompt）
  ├── Tier1: AGENTS.md（角色定义）
  ├── Tier2: SOP Markdown 全文（如命中）
  ├── Tier3: KBD 5条案例（Markdown 片段）
  └── Tier4: 工单上下文 + 对话历史（最近20条）
        │
        ▼
  LLM（openclaw）
        │
        ▼
  回答用户
```

### 1.2 已实现的能力

- ✅ BM25 + 向量 RRF 混合检索（`search_engine.py`）
- ✅ `category_id` 过滤（避免跨领域召回）
- ✅ SOP category_id 直查（O(1)，不走向量）
- ✅ 检索耗时指标（`KB_SEARCH_DURATION_SECONDS`）

## 二、问题清单与优化方案

### 问题 1：整条 KBD 案例整体 embedding — 召回精度低

#### 当前问题

`kbd_entry` 整条 `content_md`（可能数千字）作为一个向量存储：

```python
# 当前：整条案例 → 一个向量
embedding = embed(content_md)   # 整条 Markdown，混合了症状/诊断/解决方案
```

**根本问题**：

```
用户 query: "虚拟机开机后立刻黑屏"
                ↓ embed
query_vector ≈ "屏幕/显示/黑屏/开机" 方向

kbd_entry embedding ≈ "磁盘I/O错误/更换磁盘/存储写入失败" 方向
（案例内容主要是根因和解决方案，症状描述占比小）

→ 余弦相似度低 → 召回失败！
```

实际上这个案例的**症状**（"开机黑屏"）可能和用户的 query 高度相关，但被稀释在整篇叙述中。

#### 根本原因（第一性原理）

Embedding 代表整段文本的**平均语义**，而用户 query 通常描述**症状**。把症状、根因、解决方案全部混在一个向量里，会让"症状向量"被稀释。

#### 优化方案：多粒度分层 Embedding

**方案 A（推荐）：独立字段分开 embedding**

配合生产优化中的结构化抽取（symptoms / root_cause / resolution），建立多向量索引：

```sql
-- 增加分字段向量（生产分析中已建议增加的字段）
ALTER TABLE kbd_entry ADD COLUMN symptoms_embedding vector(1536);  -- 症状向量
ALTER TABLE kbd_entry ADD COLUMN title_embedding   vector(1536);  -- 标题向量
```

**检索策略**：

```python
async def search_kbd_multivector(query: str, category_id: str) -> list[KbdEntry]:
    q_emb = embed(query)

    # 1. 症状向量检索（权重 0.5）
    symptom_results = await db.fetch_all("""
        SELECT id, 1 - (symptoms_embedding <=> :qv) AS score
        FROM kbd_entry
        WHERE category_id = :cat AND status = 'published'
          AND symptoms_embedding IS NOT NULL
        ORDER BY symptoms_embedding <=> :qv
        LIMIT 20
    """, {"qv": q_emb, "cat": category_id})

    # 2. 标题向量检索（权重 0.3）
    title_results = ...

    # 3. BM25 全文检索（权重 0.2）
    bm25_results = ...

    # RRF 融合
    return rrf_merge([symptom_results, title_results, bm25_results], weights=[0.5, 0.3, 0.2])
```

**效果预期**：将症状查询的召回率提升 30-50%（业界经验）。

**方案 B（简化）：Chunked Embedding**

如果无法立即执行结构化抽取，可以先做**滑动窗口分块**：

```python
# 按段落切块（每块 200-400 字，50% 重叠）
chunks = split_by_paragraph(content_md, max_tokens=300, overlap=0.5)
# 每块独立 embedding，存入 kbd_chunk 表
# 检索时 top-k 块 → 按 kbd_entry_id 聚合 → 去重召回案例
```

### 问题 2：SOP 注入为完整 Markdown 全文 — LLM 无法有效导航决策树

#### 当前问题

SOP 通过 category_id 直查后，将 `sop_document.content_md`（完整 Markdown，可能数千字）注入 Tier2 system message：

```python
messages = [
    {"role": "system", "content": f"【SOP 排障流程 | 来源: {title}】\n{content_md}"}
]
```

**根本问题**：

SOP 是决策树（有向图），但以线性 Markdown 注入时，LLM 处理它的方式是：
1. "读完整篇文章" 而非 "按分支导航"
2. 无法跳过不相关分支，全量阅读导致 context 膨胀
3. 如果 SOP 有 10 步、3 个主分支，LLM 可能混淆相互排斥的分支条件

**具体表现**：用户描述 A 类症状，但 LLM 可能给出 B 分支的解决步骤（因为两者都在同一份 SOP 文档里）。

#### 优化方案 A：SOP 节点级注入（按对话状态精准注入）

基于生产分析中的 SOP YAML 化方案，消费层改为**节点驱动导航**：

```python
class SopNavigator:
    """
    对话过程中的 SOP 状态机
    记录当前在哪个节点，按需注入下一步内容
    """
    def __init__(self, sop_yaml: dict, case_id: str):
        self.nodes = {n["id"]: n for n in sop_yaml["nodes"]}
        self.current_node_id = "start"
        self.case_id = case_id

    def get_current_context(self) -> str:
        """只注入当前节点的内容，而非整篇 SOP"""
        node = self.nodes[self.current_node_id]
        return f"""
【当前排障步骤：{node["title"]}】
{node["description"]}

**需要执行的检查**：
{self._format_checks(node.get("checks", []))}

**根据结果选择**：
{self._format_branches(node.get("branches", []))}
"""

    def advance(self, chosen_branch: str):
        """根据对话结果推进到下一节点"""
        node = self.nodes[self.current_node_id]
        for branch in node.get("branches", []):
            if branch["condition"] == chosen_branch:
                self.current_node_id = branch["next"]
                return
        self.current_node_id = node.get("fallback", "escalate")
```

**注入变化**：

```python
# 当前：全文注入（数千 token）
content = sop_document.content_md  # 5000 tokens

# 优化后：节点注入（300-500 token 每次）
content = sop_navigator.get_current_context()  # 500 tokens
```

**效果**：单次注入 token 数减少 80-90%，同时消除跨分支混淆。

#### 优化方案 B（短期过渡）：SOP 章节级注入

在 SOP YAML 化完成之前，按**章节标题切割**注入：

```python
def get_relevant_sop_section(sop_content_md: str, user_query: str) -> str:
    """
    使用 LLM 或关键词匹配找到与 user_query 最相关的 SOP 章节
    只注入该章节，而非全文
    """
    sections = split_by_h2(sop_content_md)
    # 向量相似度找最相关章节
    relevant = find_most_relevant(sections, user_query, top_k=2)
    return "\n\n".join(relevant)
```

### 问题 3：S0 分类错误会级联破坏整个检索链路

#### 当前问题

```
S0: 意图识别 → category_id = "虚拟机-003" (错误，实际应该是"存储-001")
        │
        ├── SOP 直查 WHERE category_id = "虚拟机-003" → 命中错误 SOP
        └── KBD 检索 WHERE category_id = "虚拟机-003" → 过滤掉了正确的案例
```

**S0 的分类错误在当前架构中是静默的**：No SOP → 跌落到 KBD 检索，但 KBD 检索同样受 category_id 过滤影响。

**问题的严重性**：如果 S0 分类错误率是 10%（假设），那么 10% 的对话一开始就走向了错误的知识轨道，且用户看不到任何提示。

#### 优化方案：分类不确定时的降级策略

```python
async def get_knowledge_for_query(query: str, category_id: str, confidence: float):

    # 策略1：高置信 → 严格过滤（当前行为）
    if confidence >= 0.80:
        sop = await get_sop_by_category(category_id)
        kbd_results = await search_kbd(query, category_filter=category_id, top_k=5)

    # 策略2：中置信 → 放宽过滤 + 加宽召回
    elif confidence >= 0.55:
        sop = await get_sop_by_category(category_id)   # SOP 仍强匹配
        kbd_results = await search_kbd(
            query,
            category_filter=None,   # KBD 不过滤分类！
            top_k=10,               # 多召回几条
            rerank=True             # 召回后 rerank 排序
        )

    # 策略3：低置信 → 全库检索 + 提示用户确认
    else:
        sop = None
        kbd_results = await search_kbd(query, category_filter=None, top_k=10, rerank=True)
        # 在回答中插入：「当前问题分类尚不明确，以下建议基于语义搜索，请确认是否符合您的场景」

    return sop, kbd_results
```

### 问题 4：四层 Prompt 可能撑爆 Context Window

#### 当前问题

```python
messages = [
    Tier1: AGENTS.md          # ~2000 tokens（角色定义，固定内容）
    Tier2: SOP 全文           # ~3000-8000 tokens（完整 SOP Markdown）
    Tier3: 5条 KBD 案例       # ~5000-10000 tokens（5条 × 1000-2000 tokens/条）
    Tier4: 工单上下文          # ~500 tokens
    历史对话：最近 20 条        # ~5000-10000 tokens
    当前消息                   # ~200 tokens
]
# 总计：15000-30000 tokens，轻松超过 16K context 窗口
# 如果使用 32K 模型，成本也很高（按 token 收费）
```

**实测风险**：当 SOP 较长（10+ 步）+ 历史消息多（20条）时，总 token 数可能超过模型限制，导致截断或报错。

#### 优化方案：分层 Token 预算管理

```python
TOKEN_BUDGET = {
    "tier1_agents_md": 2000,      # 固定，不压缩
    "tier2_sop":       2000,      # 限制：只注入当前相关节点/章节
    "tier3_kbd":       3000,      # 限制：每条案例最多 600 tokens，共 5 条
    "tier4_context":   500,       # 固定
    "history":         4000,      # 限制：最近 N 条，到 4000 token 为止
    "current_message": 500        # 固定
}
# 总预算：12000 tokens（留 4000 buffer 给回答）

def truncate_to_budget(content: str, budget: int) -> str:
    tokens = count_tokens(content)
    if tokens <= budget:
        return content
    # 从末尾截断
    return truncate_tokens(content, budget)

def truncate_history(messages: list, budget: int) -> list:
    """从最旧的消息开始丢弃，直到 token 数在预算内"""
    total = sum(count_tokens(m["content"]) for m in messages)
    while total > budget and len(messages) > 2:
        removed = messages.pop(0)
        total -= count_tokens(removed["content"])
    return messages
```

**KBD 案例精简注入**：

```python
def format_kbd_for_injection(entry: KbdEntry, max_tokens: int = 600) -> str:
    """
    只注入案例的关键信息，而非完整 content_md
    优先级：title > symptoms > root_cause > resolution（截断到 max_tokens）
    """
    parts = [
        f"【案例 #{entry.support_id}】{entry.title}",
        f"症状：{entry.symptoms or ''}",
        f"根因：{entry.root_cause or ''}",
        f"解决：{entry.resolution or ''}"
    ]
    result = "\n".join(p for p in parts if p.strip())
    return truncate_tokens(result, max_tokens)
```

### 问题 5：检索结果缺乏相关性再排序 — 召回 ≠ 有用

#### 当前问题

当前检索流程：
```
BM25 top-20 + 向量 top-20
        │ RRF 融合
        ▼
top-5 注入 Prompt
```

RRF 融合是**无监督的**：它只考虑 BM25 排名和向量相似度排名，不考虑：
- 案例是否和当前故障描述在**细节上**真正吻合
- 案例是否包含完整的解决方案（有些案例只有问题描述，没有解决步骤）
- 案例的**使用历史**（高正反馈案例应该优先）

#### 优化方案 A：Cross-encoder Reranker

```python
# 两阶段检索：
# 1. 粗排（当前的 BM25+向量 RRF）→ top-20
# 2. 精排（cross-encoder）→ top-5

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")  # 支持中文

async def search_with_rerank(query: str, category_id: str) -> list[KbdEntry]:
    # 粗排召回 20 条
    candidates = await search_kbd_rough(query, category_id, top_k=20)

    # 精排：query + 每条案例的 title + symptoms 组合打分
    pairs = [(query, f"{e.title}\n{e.symptoms}") for e in candidates]
    scores = reranker.predict(pairs)

    # 按精排分数重新排序，取 top-5
    ranked = sorted(zip(scores, candidates), reverse=True)
    return [e for _, e in ranked[:5]]
```

**业界实践**：RAG 系统中 cross-encoder reranker 是标配（Cohere Rerank、BGE-Reranker 等），可将 Precision@5 提升 15-25%。

#### 优化方案 B：使用反馈信号调权（长期）

```python
# 在 RRF 融合时加入使用历史权重
feedback_score = (entry.positive_feedback + 1) / (entry.retrieval_count + 2)  # Laplace 平滑
final_score = rrf_score * 0.7 + feedback_score * 0.3
```

### 问题 6：Knowledge Attribution 缺失 — 用户不知道答案来源

#### 当前问题

AI 回答用户时，不会标注回答来源于哪条 KBD 案例或哪份 SOP。用户无法：
- 判断答案是基于历史案例还是 LLM 自身训练知识（可能过时）
- 通过案例编号找到原始工单验证解决步骤
- 对特定案例进行"这条有帮助/没帮助"的反馈

#### 优化方案：强制来源归因（Source Attribution）

**Prompt 层面**：

```python
KBD_INJECTION_TEMPLATE = """
【历史案例参考】
以下案例来自实际排障记录，请在回答中引用相关案例编号（格式：案例#XXXXX）。

{cases}

**重要**：
- 如果以上案例与当前故障高度吻合，请明确引用
- 如果没有匹配案例，请说明"未找到直接匹配案例，以下建议基于领域知识"
- 不要将案例内容与自身知识混淆
"""
```

**前端展示**：

```
AI 回答：
根据案例 #34977（虚拟机磁盘 I/O 错误）的处理经验，您的问题可能是...

[📎 案例 #34977]  [👍 有帮助]  [👎 无帮助]
```

### 问题 7：对话历史策略粗糙 — 最近 20 条无差别保留

#### 当前问题

```python
# 历史消息：最近 20 条，全量传入
history = await get_recent_messages(case_id, limit=20)
```

**问题**：
- 早期对话（如"您好，能帮我看一个虚拟机问题吗？"）占 token 无贡献
- 已经"结案"的信息仍在历史中（如"好的，问题解决了"），但系统不会截断
- 没有**摘要压缩**：多轮诊断后，历史消息可以被摘要为"已排查：网络正常、磁盘正常"

#### 优化方案：滑动窗口 + 关键信息摘要

```python
async def build_history_messages(case_id: str, token_budget: int) -> list:
    all_messages = await get_all_messages(case_id)

    # 最近 5 条：完整保留（最相关）
    recent = all_messages[-5:]

    # 较早的消息：压缩为摘要
    older = all_messages[:-5]
    if older and count_tokens(older) > token_budget // 2:
        summary = await llm_summarize(
            older,
            prompt="请用3-5句话概括对话中已确认的诊断信息和已排查的项目"
        )
        return [{"role": "system", "content": f"【前期诊断摘要】\n{summary}"}] + recent

    return older[-10:] + recent   # 没超预算则直接用
```

### 问题 8：无检索质量可观测性 — 不知道检索是否有效

#### 当前问题

虽然有 `KB_SEARCH_DURATION_SECONDS`（耗时指标），但缺少：
- **命中率**：每次检索有多少比例找到了相关结果（非零召回率）
- **Precision@N**：召回的 top-N 条中真正相关的比例
- **SOP 命中率**：用 category_id 直查时找到 SOP 的比例
- **空结果率**：KBD 和 SOP 都没有召回时的频率（→ 用户体验最差的情况）

**没有这些数据，根本不知道知识库对 AI 回答有多大贡献。**

#### 优化方案：检索质量 Prometheus 指标

```python
# kb_service/search_engine.py 新增指标

KB_SEARCH_HIT_TOTAL = Counter(
    "kb_search_hit_total",
    "知识库检索命中计数",
    ["type", "hit"]  # type: sop/kbd, hit: true/false
)

KB_SEARCH_RESULT_COUNT = Histogram(
    "kb_search_result_count",
    "每次检索返回的结果数",
    ["type"],
    buckets=[0, 1, 2, 3, 5, 10]
)

KB_CATEGORY_CONFIDENCE = Histogram(
    "kb_category_confidence",
    "S0 分类置信度分布",
    buckets=[0.3, 0.5, 0.6, 0.7, 0.8, 0.9, 1.0]
)
```

**Grafana 看板建议**：
- SOP 命中率趋势（目标 > 80%）
- KBD Recall@5（被用户正反馈的案例被召回的比例）
- 分类置信度分布直方图（低置信比例 > 20% 需告警）
- 空结果率（目标 < 5%）

## 三、优化优先级矩阵

|------|---------|----------|--------|
| 问题1：多向量分层 embedding（症状独立向量） | 最直接提升召回精度 | 中（需生产结构化抽取配合） | **P0** |
| 问题4：Token 预算管理 | 防止超 context 崩溃 | 低 | **P0** |

| 问题7：对话历史摘要压缩 | 长对话质量提升 | 中 | **P2** |
| 问题8：检索质量可观测性 | 让优化有据可依 | 低（加 metrics） | **P1** |

## 四、关键依赖关系图

```
生产优化                          消费优化
─────────────────                 ──────────────────────────────
结构化抽取                  →     问题1：多向量分层 embedding
（symptoms/root_cause）           （症状向量独立 embedding）
```

## 五、讨论议题

请团队在审阅后确认以下决策：

1. **多向量 embedding**：是否接受在 `kbd_entry` 增加 `symptoms_embedding` 字段，并对现有 7000+ 发布案例重新计算向量？（前提是生产分析中的结构化抽取已完成）

2. **Token 预算管理**：是否在 `conversation-service` 中实现 token 计数和分层截断？需要引入 tiktoken 或类似库。

3. **Source Attribution**：是否修改 AI 回答中强制要求引用案例编号？这会改变当前 AI 的回答风格，需要评估用户体验影响。

5. **Reranker 引入**：cross-encoder reranker 需要额外计算资源（每次检索多一次 inference），是否在 K3s 中单独部署 reranker 服务？还是使用 API 版（Cohere Rerank API）？
