# 知识库「管理」优化分析

> **文档目的**：以第一性原理分析当前知识库"管理"环节（审核工作流、分类体系维护、知识生命周期、质量治理）的核心问题，结合业界最佳实践给出具体优化方案。
>
> **管理定义**：知识从 `draft` 状态到 `published` 状态，以及发布后的版本维护、过时处理、质量反馈的全过程。
>
> **关联文档**：[知识库设计.md](./知识库设计.md) | [知识库-生产-优化分析.md](./知识库-生产-优化分析.md) | [知识库-消费-优化分析.md](./知识库-消费-优化分析.md)

## 一、现状诊断

### 1.1 审核工作流现状

```
kbd_entry (status=draft)
        │
        ▼
  Admin UI「KBD管理」
  ├── 列表查看 + 分页
  ├── 点击详情
  │     ├── 查看 content_md 预览
  │     ├── 查看截图说明（accordion）
  │     ├── 选择确认分类（select 基线）
  │     └── 内联编辑原文
  │
  ├── PATCH /api/v1/kbd/{id}/approve → status=published → 触发 embedding
  └── PATCH /api/v1/kbd/{id}/reject  → status=rejected
```

**已发布数量**：7,000+ KBD 案例（目标），约 10 篇 SOP。

## 二、问题清单与优化方案

### 问题 1：人工审核是严重瓶颈 — 7000+ 案例无优先级

#### 当前问题

7,000+ KBD 案例进入 `draft` 状态后，全部依赖人工审核。审核员面对一个无差别的队列：
- 高价值的"复杂疑难案例"和低价值的"标准操作错误"排在一起
- 没有按分类过滤的审核视图（审核员无法专注于自己擅长的领域）
- 没有办法标记"待稍后处理"，只能 approve 或 reject

**后果**：审核员疲倦后倾向"一键 approve"，分类确认流于形式，低质量案例大量进入 published 状态。

#### 根本原因（第一性原理）

审核是**质量门控**的最后一道，但当前设计把它当作**翻页操作**。Gate 没有被设计成有意义的决策。

#### 优化方案 A：智能审核优先级排序

```python
def compute_review_priority(kbd_entry) -> int:
    """
    审核优先级评分（越高越优先展示）
    """
    score = 0

    # +30: AI 分类置信度高（可快速确认）
    if kbd_entry.ai_category_conf >= 0.85:
        score += 30

    # +20: 属于高频分类（常见问题，优先建库）
    if kbd_entry.ai_category_id in HIGH_FREQUENCY_CATEGORIES:
        score += 20

    # -20: AI 分类置信度低（需要仔细看）
    if kbd_entry.ai_category_conf < 0.60:
        score -= 20

    # +10: 有截图描述（内容更丰富）
    if kbd_entry.has_screenshots:
        score += 10

    # -10: OCR 质量标记为 low_quality
    if kbd_entry.ocr_quality == "low_quality":
        score -= 10

    return score
```

**Admin UI 增加**：
- 审核队列按优先级排序（高置信 + 高频分类优先）
- 按分类过滤视图（审核员可以只看自己专属的分类域）
- "稍后处理"按钮（将 draft 移入 `defer` 状态）

#### 优化方案 B：批量审核（相似案例一次确认）

对于高置信度（>0.90）且分类一致的成批案例，允许：
```
[✓] 案例 #34977  虚拟机-开机失败  [置信 0.93]
[✓] 案例 #34982  虚拟机-开机失败  [置信 0.91]
[✓] 案例 #35001  虚拟机-开机失败  [置信 0.88]
[批量确认分类] → approve 所选 (3)
```

业界实践：Snorkel AI、Labelbox 等数据标注平台的"批量确认"功能，在高置信样本上大幅提升标注效率。

### 问题 2：分类体系缺乏质量治理 — 分类树可能不准确或过时

#### 当前问题

分类树（约 198 个节点）通过 `category_baseline.yaml` 维护，通过 `import_from_yaml` 导入。存在：
- 分类树的**精准程度**没有度量（多少案例被正确分类？多少分类无案例覆盖？）
- 某些分类可能**分布极不均衡**：有的分类聚集了大量案例，有的分类是空节点
- 分类树建立在业务领域知识基础上，但随着 HCI 产品版本迭代，分类可能**过时**
- AI 分类使用的是**全量 198 个分类节点**每次都发给 LLM——效率低且 prompt 臃肿

#### 优化方案 A：分类分布可视化与质量指标

```sql
-- 分类覆盖度查询
SELECT
    c.code,
    c.name,
    c.level,
    COUNT(k.id) FILTER (WHERE k.status = 'published') AS published_count,
    COUNT(k.id) FILTER (WHERE k.status = 'draft')     AS draft_count,
    AVG(k.ai_category_conf)                            AS avg_ai_confidence
FROM kb_category c
LEFT JOIN kbd_entry k ON k.category_id = c.code
GROUP BY c.id, c.code, c.name, c.level
ORDER BY published_count DESC;
```

**建立告警规则**：
- 空分类（published_count = 0）超过 30 天 → 评估是否需要此分类
- 单分类聚集超过总量 10% → 评估是否需要细分
- 分类平均 AI 置信度 < 0.65 → 该分类定义可能不清晰，需要重新描述

#### 优化方案 B：分类描述优化（提升 LLM 分类准确率）

AI 分类的精准度很大程度取决于 `kb_category` 表中每个分类的描述是否清晰可区分。当前分类节点只有 `name` 和 `keywords`，建议增加：

```sql
ALTER TABLE kb_category ADD COLUMN description TEXT;   -- 详细描述，说明哪些案例归此类
ALTER TABLE kb_category ADD COLUMN example_cases TEXT[]; -- 典型案例 support_id，辅助 LLM 理解
ALTER TABLE kb_category ADD COLUMN is_active BOOLEAN DEFAULT true; -- 停用过时分类
```

#### 优化方案 C：Hierarchical 分类（两阶段 LLM）

当前把 198 个分类节点全部送给 LLM，prompt 过长且可能导致 LLM 注意力分散。业界最佳实践是**层级分类**：

```
第一步：先分 L1（约 10 个一级域）
  → "虚拟机" / "存储" / "网络" / "主机" ...

第二步：在确认 L1 后，只取该 L1 下的子分类（约 20-30 个）
  → "虚拟机 > 开机失败 / 克隆失败 / 快照失败 ..."
```

**效果**：LLM context 缩短 80%，分类精准度提升（受到的干扰更少）。

### 问题 3：知识无生命周期管理 — 过时知识污染检索结果

#### 当前问题

已发布的 KBD 案例没有：
- **过时标记**：2024 年的案例（基于旧版本 HCI）对 2026 年版本可能失效
- **版本关联**：案例没有记录适用的 HCI 产品版本号
- **使用频率追踪**：哪些案例被 AI 推荐但没有帮助到用户？

**后果**：过时或错误的案例被 RAG 召回，给出错误的排障建议，破坏用户信任。

#### 优化方案：知识生命周期字段

```sql
ALTER TABLE kbd_entry ADD COLUMN product_version VARCHAR(20); -- 适用 HCI 版本，如 "6.x"
ALTER TABLE kbd_entry ADD COLUMN valid_until DATE;            -- 失效日期（可选）
ALTER TABLE kbd_entry ADD COLUMN retrieval_count INT DEFAULT 0;    -- 被召回次数
ALTER TABLE kbd_entry ADD COLUMN positive_feedback INT DEFAULT 0;  -- 有帮助反馈数
ALTER TABLE kbd_entry ADD COLUMN negative_feedback INT DEFAULT 0;  -- 无帮助反馈数
```

**自动化治理规则**：

```python
# 每周执行的知识健康检查
def knowledge_health_check():
    # 规则1：被召回 20+ 次但无反馈 → 需要人工确认是否有效
    stale_candidates = query("""
        SELECT id FROM kbd_entry
        WHERE status = 'published'
          AND retrieval_count > 20
          AND (positive_feedback + negative_feedback) = 0
          AND published_at < NOW() - INTERVAL '90 days'
    """)

    # 规则2：负反馈率 > 50% → 自动移回 draft，通知审核员
    bad_quality = query("""
        SELECT id FROM kbd_entry
        WHERE status = 'published'
          AND (retrieval_count > 10)
          AND (negative_feedback::float / NULLIF(retrieval_count, 0)) > 0.5
    """)
```

### 问题 4：SOP 与 KBD 的审核工作流相同 — 缺乏差异化质量保障

#### 当前问题

SOP 和 KBD 走相同的 `draft → published` 流程，但两者的**重要性和质量要求截然不同**：

| 维度 | KBD 案例 | SOP 排障手册 |
|------|---------|------------|
| 数量 | ~7000 | ~10 |
| 单条影响 | 单个参考案例 | 整个排障决策树 |
| 错误后果 | 参考错误 | 整个排障流程错误 |
| 更新频率 | 直到案例过期 | 随产品迭代更新 |

#### 优化方案：SOP 增强审核流程

```
SOP 草稿
    │
    ▼
技术评审（Tech Review）
  - 检查所有命令是否可执行
  - 检查分支条件是否互斥且完整
  - 至少 2 人 Review
    │
    ▼
测试验证（Test Validation）
  - 对照实际环境验证每个分支
  - 记录验证环境版本
    │
    ▼
版本发布（Published）
  - 记录适用版本范围
  - 设置下次 Review 日期（建议 90 天）
```

**数据库字段**：

```sql
ALTER TABLE sop_document ADD COLUMN reviewer_2_id INTEGER;       -- 第二审核人
ALTER TABLE sop_document ADD COLUMN test_validated BOOLEAN DEFAULT false;
ALTER TABLE sop_document ADD COLUMN validated_version VARCHAR(20); -- 验证时的 HCI 版本
ALTER TABLE sop_document ADD COLUMN next_review_date DATE;
```

### 问题 5：无知识质量反馈闭环 — 用户反馈无法改善知识库

#### 当前问题

当 AI 给出错误答案时，没有机制将"这条知识是错的"的信号反传到知识库。对话结束就结束，没有：
- 对话中对特定知识条目的评分接口
- 工单完成后对"知识有效性"的评估
- 知识条目的使用效果统计

#### 优化方案：知识反馈接口

**对话结束时**（Conversation Service 触发）：

```python
# 对话结束时，记录本次用到的知识和用户反馈
async def record_knowledge_feedback(
    case_id: str,
    kbd_ids_used: list[int],
    sop_id: int | None,
    outcome: str,           # "resolved" / "unresolved" / "escalated"
    user_rating: int | None # 1-5
):
    for kbd_id in kbd_ids_used:
        await kb_service.post(f"/api/kb/kbd/{kbd_id}/feedback", {
            "outcome": outcome,
            "rating": user_rating
        })
```

**KB Service 接收端**：
```python
@router.post("/api/kb/kbd/{kbd_id}/feedback")
async def record_feedback(kbd_id: int, body: FeedbackRequest):
    await db.execute("""
        UPDATE kbd_entry
        SET retrieval_count = retrieval_count + 1,
            positive_feedback = positive_feedback + :pos,
            negative_feedback = negative_feedback + :neg
        WHERE id = :id
    """, {
        "id": kbd_id,
        "pos": 1 if body.outcome == "resolved" else 0,
        "neg": 1 if body.outcome == "unresolved" else 0
    })
```

### 问题 6：分类树 vs 实际案例分布不匹配

#### 当前问题

分类树是在业务需求阶段由领域专家设计的，但实际导入的案例可能在分类分布上极不均衡。例如：
- "虚拟机-开机失败" 可能有 2000 个案例
- "虚拟机-热迁移" 可能只有 3 个案例

这会导致 KBD 检索时某些分类的结果可靠而其他分类几乎没有参考价值。

#### 优化方案：基于实际分布的分类树优化

**分析脚本**：
```python
"""
定期运行：分析分类覆盖度，生成建议报告
"""
async def analyze_category_distribution():
    stats = await db.fetch_all("""
        SELECT
            c.code, c.name, c.level, c.parent_id,
            COUNT(k.id) AS total_cases,
            COUNT(k.id) FILTER (WHERE k.status = 'published') AS published_cases
        FROM kb_category c
        LEFT JOIN kbd_entry k ON k.category_id = c.code
        GROUP BY c.id
        ORDER BY total_cases DESC
    """)

    # 识别空分类
    empty = [s for s in stats if s.published_cases == 0]
    # 识别过于密集的分类（可能需要细分）
    dense = [s for s in stats if s.published_cases > 500]

    return CategoryHealthReport(empty=empty, dense=dense, stats=stats)
```

## 三、优化优先级矩阵

| 问题 | 影响面 | 实现复杂度 | 优先级 |
|------|--------|----------|--------|
| 问题1B：批量审核相似案例 | 直接减少人工成本 | 低（UI 改动） | **P0** |
| 问题2C：Hierarchical 两阶段 LLM 分类 | 提升分类精度，降低 LLM 成本 | 低 | **P0** |
| 问题5：知识反馈闭环 | 数据飞轮启动后长期收益极大 | 中 | **P1** |
| 问题3：知识生命周期字段 | 防止过时知识污染 | 低 | **P1** |
| 问题4：SOP 增强审核流程 | 保证 SOP 质量（排障核心） | 低（流程规范） | **P1** |
| 问题1A：智能审核优先级 | 改善审核效率 | 中 | **P2** |
| 问题6：分类分布分析脚本 | 长期分类体系健康 | 低 | **P2** |

## 四、讨论议题

请团队在审阅后确认以下决策：

1. **批量审核**：是否接受"相同分类 + 高置信度"的案例允许批量 approve？这意味着降低了逐条审核的要求，需要明确验收标准。

2. **知识反馈闭环**：前端对话结束时是否要增加"这次建议有帮助吗？"的评分交互？这会影响前端 UI 设计。

3. **Hierarchical 分类**：是否接受将分类改为两阶段 LLM 调用（先 L1 再 L2-L4）？需要修改 `classify.py` 和分类 prompt。

4. **SOP 版本管理**：是否在现有 SOP 上增加 `product_version` 字段并补充适用版本信息？可以分批完成。
