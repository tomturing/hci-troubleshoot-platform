# 根因信号抽取闭环方案

> **状态：已评审通过，进入分期落地（PR-1→PR-4）。** 本方案不针对任何单篇 KBD 做专项优化，
> 而是以「KBD 27736」为**反例证据**，定位「根因抽取」功能的结构性缺陷并给出系统性治本方案。
>
> **依赖**：本方案的前提是 executable 根因信号已在运行时被并入 CDD 消费（两轨消费，PR B /
> [#1161]，已合入 main（`4dbc3aef`）：`backend/kb-service/app/routes/playbooks.py::_signals` + `backend/shared/cdd/kbd_model.py::root_display_anchors`）。
> 因 #1161 已合并，本方案的闭包不变量在「运行时消费」面已是**硬门禁**——executable 根因既已并入 CDD 同等执行，就必须在抽取/编辑/发布三处真闭环。
>
> 关联主文档：[根因信号抽取方案](根因信号抽取方案.md)（现行抽取轨，双形态契约/门禁/Prompt）。
> 本方案是其**演进增量**，不推翻既有双形态契约，只补「闭环」这一缺失维度。

## 1. 背景：为什么「一个根因信号」不等于「一个可执行根因」

现行根因抽取（`root_signal_extractor.extract_root_signal`）的产物是**孤立的结论侧定位信号**：
或 `text`（关键词锚点），或 `executable`（`qfk_*` 消费者 + `match`）。它与关键信号轨
（`signals_json`）**完全解耦**——不复用其 produces、不感知其变量、不产出填补自身依赖的上游生产者。

在 PR B 之前，这无所谓：根因信号只做「候选圈定」，不进 CDD。PR B 把 **executable 根因并入 CDD
同一信号计划**（与关键信号同等执行/判定），于是「可执行」从一个**名义属性**变成了**真实运行契约**——
一个引用了 `{{HOST}}/{{ETHX}}/{{IP}}` 的 `qfk_system` 根因信号，若这些变量在现场无来源，
就**永远不会被评估**，KBD 永不收敛为定论。

### 1.1 反例证据（KBD 27736，非专项、可复算）

`kbd_entry.support_id=27736`（id=1，draft）现场根因信号：

```jsonc
{
  "match_type": "executable",
  "acquire": {"tool": "qfk_system",
              "args": {"host": "{{HOST}}", "command": "cat", "command_args": ["/sf/cfg/if.d/eth0"]}},
  "match":   {"type": "keyword", "mode": "all", "expected": ["address", "netmask", "gateway"]}
}
```

同 KBD 的唯一关键信号 `sig_001` 是 `qkv_dialog`，`produces:[{"name":"END"}]`。三个结构性死结：

1. **悬空依赖**：根因 require `{{HOST}}`，全 KBD 无任何信号 `produces HOST`。运行时
   `_resolve_template`（`kbd_differential.py` L1035-1047）解析不到即保留字面量 `{{HOST}}`，
   `_is_ip_address("{{HOST}}")=False` → 触发 `QFK_TARGET_HOST_UNRESOLVED`（L1912-1918）**停止执行**。
2. **实体写死**：`eth0` 是随现场变化的网卡名（本单冲突口恰为 eth0），换一张工单即失效——根因退化为
   「单工单快照」，丧失 KBD 复用价值。`address/netmask/gateway` 三关键词不含具体 IP，无法真正「校验」根因。
3. **闭环缺失**：抽取只吐了「消费/判定」这半环，从不产出填补 `HOST/ETHX/IP` 的「生产」半环
   （本应由 `qkv_task` 从失败任务消息 `本地网口（eth0）IP …100.88… 冲突` 抽取）。

**关键结论（第一性原理）**：27736 不是脏数据，是「只校验单信号形状、不校验依赖闭包」这一设计的**确定性产物**。
任何此类抽取都会持续产出「形状合法、运行时跑不动」的半截信号。治本必须把校验面从**单信号**升级到**闭环**。

## 2. 现行门禁校验了什么、漏了什么（代码事实）

`gate_executable`（`root_signal_extractor.py` L202-220）只校验三件事：
① `acquire.tool` 是 `qfk_*` 且在 `ACQUIRER_CATALOG` 内（禁 `qfk_var`）；
② `validate_acquire_args`——args 的**形状契约**；
③ `kbd_signal_read_only_violation`——只读安全。

| 缺口 | 现状 | 直接后果 |
|---|---|---|
| ① 依赖闭包 | 从不检查 `{{VAR}}` 是否有生产者 | 悬空 require，运行时阻断（27736 之 HOST） |
| ② 实体参数化 | 从不检测随现场变化的字面量 | 根因退化为单工单快照（27736 之 eth0/IP） |
| ③ 生产者共生 | 根因轨与关键轨解耦，不产出/不校验 producers | 消费者信号孤立，闭环另一半恒缺 |
| ④ 命令能力 | 从不验证 `acli system cat` 等子命令是否可用 | 静态合法 ≠ 运行时可执行 |

**平台早已具备闭环原语，缺的只是「前移」**：
`derive_signal_requires`（`shared/schemas/signal_output.py` L11-70）能从任意信号算出 require 集；
CDD 编译（`plan_compiler`）能聚合 producer 集；`distinctiveness`/`ConflictCorpus` 已是「抽取时跑
语料级校验」的先例。把 `requires ⊆ produces ∪ context` 这一判据接进抽取与发布门禁即可闭环。

## 3. 闭环的形式化定义与判据

**定义（可执行根因的充要条件）**：一条 `executable` 根因信号 C 在 KBD K 内「可执行」，当且仅当：

\[
\text{requires}(C)\ \subseteq\ \text{Produces}(K)\ \cup\ \text{ContextWhitelist}
\]
且 C 的 `acquire.args` / `match` 内**不含随现场变化的字面量实体**（或已变量化），且
C 的 `tool+command` 在采集环境**具备对应能力**。

- \(\text{requires}(C)\)：`derive_signal_requires(C)` 扫描 `acquire.args`/`match`/`produces.extract`
  得到的 `{{VAR}}` 全集。
- \(\text{Produces}(K)\)：K 内**全部信号**（关键轨 `signals_json` + 根因轨 bundle 的生产者）的
  `orchestrate.produces[].name` 并集，大小写归一。
- `ContextWhitelist`：**会话/环境可兜底的上下文变量**。`HOST` 为特例——`qfk_system` 的 `host`
  是**可选**（`required:["command"]`），省略即用 `env_context["node_ip"]`（会话所选节点，
  `kbd_differential.py` L1904）；故对「本地操作类」根因，正确做法是**不写 host**（零悬空）而非强造 HOST 生产者。
  白名单需显式枚举并注释来源，防止把「真悬空」误判为「上下文可兜底」。

**闭包分级（每条 executable 根因必产出一态）**：

| 分级 | 含义 | 处置 |
|---|---|---|
| `closed` | requires 全覆盖 + 无写死实体 + 能力具备 | 保留 executable，进 CDD |
| `dangling_requires:[v…]` | 有变量无来源且非白名单 | 补生产者（bundle）；仍不可 → **拒绝候选** |
| `hardcoded_literals:[x…]` | 命令/判定含随现场变化字面量 | 要求变量化；仍不可 → **拒绝候选** |
| `capability_missing` | tool/command 不在能力目录 | **拒绝候选** |

> **不可闭环一律判「拒绝候选」，不自动降级 text**（评审决策，详见 §5.4）：完全复用关键信号 `rejected_candidates` 语义。

## 4. 目标产物：从「单根因信号」到「闭环信号束（bundle）」

抽取的原子产物由「一组 consumer 信号」升级为**自洽的闭环束**，一次产出三类元素并整体过闭包校验：

1. **消费者**：结论判定信号（现有 `qfk_*`，不变）；
2. **生产者**：填补消费者全部 `{{VAR}}` 的 `qkv_task/qkv_alert/qkv_dialog`（`produces:[{name:HOST},{name:ETHX},{name:IP}]`），
   与关键信号轨同一契约（`_extract_by_produces` / `output_processing`）；
3. **变量契约**：每个变量声明来源（`path` 结构化投影 / `derive.feature` 文本抽取），可被审核 UI 展示与人工修正。

27736 的正确形态（示意，非专项）：

```jsonc
// 生产者（关键轨或 bundle 内）
{"acquire":{"tool":"qkv_task","args":{"keyword":"添加IP别名失败","is_failed":true}},
 "match":null,
 "orchestrate":{"produces":[
   {"name":"ETHX","path":"…"},                 // 若 acli task 记录有独立 interface 字段则 path 投影
   {"name":"IP","path":"…"}]}}                 // 否则走 output_processing.derive.feature（见 §5.5）
// 消费者（根因轨）
{"match_type":"executable",
 "acquire":{"tool":"qfk_system","args":{"command":"cat","command_args":["/sf/cfg/if.d/{{ETHX}}"]}}, // host 省略=本会话节点
 "match":{"type":"regex","mode":"all","pattern":"(?is)address\\s*=.*{{IP}}.*(?:netmask|gateway)"}}
```

## 5. 方案分层（所有信号、参数抽取同步考虑）

### 5.1 A｜抽取轨升级为闭环束

- `extract_root_signal` 输出契约扩为 `{consumers, producers, variable_contracts}`；
- Prompt 输入面**注入该 KBD 现有 `signals_json` 的 produces 词表**（让根因轨「知道」哪些变量已被
  关键信号产出，避免重复产出/悬空；沿用 `acquirer_catalog_text` 的「同源生成、门禁比 Prompt 不严」经验）；
- 新增「闭环自检」Prompt 段：产出 executable 消费者时，**必须同时给出其 `{{VAR}}` 的生产者或声明走
  `ContextWhitelist`（如本地操作省略 host）**；确实无法闭环的候选不硬造跑不动的 executable、
  也**不自动降级 text**，而是交 §5.4 判「拒绝候选」。

### 5.2 B｜新增 KBD 级「根因闭环校验器」= 单一事实源

纯函数（可单测、可离线试点）：

```
evaluate_root_closure(signals_json: list, root_signals: list, *, context_whitelist, capability_catalog)
  -> list[{signal_ref, closure_status, requires, resolved_by:[{var, by|producer_id|context}], literals, capability}]
```

- 判据即 §3 公式；复用 `derive_signal_requires` + 全信号 produces 聚合，**不新造依赖解析**；
- **三处强制接入**（覆盖全部写入路径，杜绝回潮，见 §7）：抽取装配后 / 人工逐条编辑保存 / 发布门禁。

### 5.3 C｜参数化门禁

扫描 executable 根因 `command_args`/`match` 的**随现场变化实体**（网卡名 `eth\d+|bond\d+|channel\d+`、
IPv4、设备 `/dev/\w+`、PID、实例化路径段），命中字面量 → 判 `hardcoded_literals`，要求改写为 `{{VAR}}`；
回喂给出「该变量化实体 + 建议标准变量名」。确定性正则黑名单，不依赖 LLM 自检。

### 5.4 D｜不可闭环 → 拒绝候选（对齐关键信号 `rejected_candidates`）

凡 `closure_status ≠ closed` 且 bundle 内仍无法补生产者/参数化/具备能力的 executable 根因候选，
**不降级为 text，而是判为「拒绝候选」**——完全复用关键信号既有语义（`signals_json.rejected_candidates`、
`SIGNAL_ALL_REJECTED` 收口、`signal_schema.py` L588「存在未处理拒绝候选不能自动降级」）：

1. **不收进 accepted 数组、也不转 text**：候选连同 `reason_code`（`ROOT_CLOSURE_DANGLING` /
   `ROOT_CLOSURE_LITERAL_NOT_PARAMETERIZED` / `ROOT_CLOSURE_CAPABILITY_MISSING`）与 `reason` 落**拒绝候选审计快照**（见 §6）；
2. **全拒显式收口**：某篇根因候选全部被拒 → 抽取出头处抛 `ROOT_SIGNAL_ALL_REJECTED`（带原因、`retryable`），
   绝不静默产出空数组伪装「无根因」（对齐 #1159 教训：失败要在离真因最近的收口处显式暴露）；
3. **发布阻断**：存在未处理拒绝候选即 422，不得自动降级放行（对齐 `signal_schema` L588）；
4. **人工显式动作**：审核 UI 逐条呈现拒绝原因与指引，专家可 **补生产者 / 参数化 / 删除 / 显式确认降级为 text**
   ——降级 text 从此是**可审计的人工决策**，绝非服务端自动行为。

原则（对抗性）：**自动降级会把「跑不动的可执行信号」洗成「看似合理的 text 锚点」，掩盖闭包缺陷本身**——
这正是关键信号 #1159 用 `SIGNAL_ALL_REJECTED` 消灭的「用无关降级掩盖上游失败」同类陷阱。半截信号必须**显式拒绝、转人工**。

### 5.5 E｜平台能力补齐（闭环的前置底座）

若 `ETHX/IP` 只存在于失败任务的**自由文本报错**里（非 `acli task get` 的独立结构化字段），
`produces.path`（仅 JSON 投影，`qkv_parser._extract_by_produces`）**取不到子串**，必须走
`output_processing.derive`；而 `qkv_output_processing._FEATURE_PATTERNS` 当前封闭集：
- `interface_name` 仅认 `网口：eth0`/`网口=eth0` **冒号形态**，匹配不到 `本地网口（eth0）` **全角括号形态**；
- **无 `ipv4` 特征**，`_NUMBER_RE` 会把 `100.88` 当小数截断；
- 且消息首个「网口」是 `channel4`（添加别名的口），根因要查的是「本地网口」eth0——**须锚定「本地网口」**。

故须按「提案+测试+文档」**扩两个确定性抽取特征**：`interface_name`（兼容 `（x）`/裸名/冒号 + `local` 锚定作用域）
与 `ipv4`。否则 §5.1 的「生产者抽取」在文本消息上无从落地——这是「参数抽取同步考虑」的硬依赖。
（封闭集合扩展遵循 `qkv_output_processing.py` 头注「不新增自由文本判定，扩展走提案+测试」。）

> **PR-2 已落地（2026-10-19，`feat/root-signal-closure-pr2`）**：在 `qkv_output_processing._FEATURE_PATTERNS` 封闭集内
> 新增/扩展三个确定性特征，实现较原提案有一处偏差校正：
> - `interface_name`：由「仅冒号」扩为**冒号/等号 或 全/半角括号**两形态皆命中（`网口：eth0`/`网口（eth0）`/`接口(ens33)`），
>   并强制捕获名首字符为字母，防把网口序号或 IP 数字误抽为接口名；旧冒号契约向后兼容。
> - **`local_interface_name`（新增独立特征，取代原「`local` 锚定作用域」设想）**：derive 单元无逐匹配锚点机制，
>   在单一扁平正则上引入 `scope` 属侵入式改造且难保证确定性；改为**独立锚定 `本地网口/本地接口/local interface`**，
>   从 `网口（channel4）…本地网口（eth0）` 稳定取 `eth0`，不误取先现的 `channel4`。符合「不新增自由文本判定」。
> - `ipv4`（新增）：四段十进制全格式地址，用 `group(1)` 捕获整串以适配 `_feature_extract` 统一取组；可从报错中抽出冲突地址。
>   「冲突 IP vs 掩码 vs 待加 IP」的**多命中择优**属 §5.1 bundle 组合层职责（PR-3），非单一特征职责。
> - 守护：`backend/shared/tests/test_qkv_output_processing.py` 新增 4 例（冒号/括号兼容、本地锚定不误取 channel4、ipv4 抽取、
>   未登记 feature 仍 fail-closed）。

### 5.6 F｜命令能力预检

抽取/发布时把 `tool+command` 比对**已知能力目录**（如 `acli system` 子命令白名单）；不可用 → 判 `capability_missing` → **拒绝候选**（决策②：不自动降级 text，见 §5.4）。真实环境能力以 terminal_bridge `probe.*` 探测结果回填（`tool_capability_missing` 归类），避免把幻觉命令当可执行。

> **实现拆分决策（对抗性审查，PR-2 未纳入命令级预检）**：仓库已有权威 acli 能力事实源
> `backend/shared/resolution/catalogs/acli_command_catalog.json`（`load_acli_catalog()`，如 `acli system ethtool`），
> 但它 **仅覆盖 acli**。根因命令大量使用 `cat`/`bash_exec` 等**非-acli** 合法命令，若此刻按 acli 白名单做命令级
> 门禁会把它们**误判 `capability_missing` 拒绝**（假阴性，严格劣于现状）。PR-1 已在**工具级**（`qfk_* ∈ ACQUIRER_CATALOG`）
> 设了安全边界；命令级预检需先具备覆盖非-acli 的能力事实源（或 `probe.*` 回填），故**拆到独立 PR**，本 PR 不引入不可靠门禁。

## 6. 数据契约变更

`root_signal_json` 每条 executable 信号新增（text 不需要闭包，可不带）：

| 字段 | 含义 |
|---|---|
| `requires` | `derive_signal_requires` 结果，展示依赖 |
| `resolved_by` | `[{var, by:"producer"|"context", ref:signal_id|"context_whitelist"}]`，可追溯闭环来源 |
| `closure_status` | §3 四态 |

**拒绝候选落库（对齐关键信号 `rejected_candidates`）**：`root_signal_json` 仍只存 **accepted** 数组
（CHECK `jsonb_typeof='array'` 不变）；不可闭环的 executable 候选**不进该数组、也不转 text**，而是持久化到**新增列
`root_signal_rejected_json jsonb`**（数组，元素 `{candidate, reason, reason_code}`，与 `signals_json.rejected_candidates`
同构），供审核 UI 逐条呈现、发布门禁判「未处理拒绝候选」、以及人工恢复/降级。**取消** `downgrade_reason` 自动字段
——降级为 text 改由人工显式动作产生（进 accepted 数组，`provenance` 记 `manual_downgrade=true` 溯源）。

**变量命名规范**：跨关键轨与根因轨统一**大写标准变量名**（`HOST`/`ETHX`/`IP`/`DEVICE`/`PID`/`VM_ID`…），
运行时解析已由 `_resolve_template` 大小写不敏感保证（L1043）。落库 CHECK 仍限 `jsonb_typeof='array'`（不因新字段变化）。

## 7. 门禁接入点（精确到函数）

| 写入路径 | 位置 | 改动 |
|---|---|---|
| 自动抽取装配 | `extract_root_signal_for_kbd`（`routes/extract_root_signal.py`）写回前 | 调 `evaluate_root_closure`：`closed` 保 executable；不可闭环 → 记 `root_signal_rejected_json`（拒绝候选，带 `reason_code`）；全拒显式抛 `ROOT_SIGNAL_ALL_REJECTED` |
| 人工逐条编辑 | `PATCH /kbd/{id}/root-signal`（`routes/extract_root_signal.py`） | ✅ PR-4 已接入（原「现仅跑 normalize → 加闭包门」）：形状门 `normalize_root_signal` 合规后复用**同一** `adjudicate_root_closure`（含 bootstrap 保守守卫）切分 accepted/rejected，不可闭环 executable 落 `root_signal_rejected_json`（不自动降级 text），写回同触两列；全拒显式收口，形状不合仍 422 |
| 发布门禁 | `review_kbd_signals`（`routes/admin.py`） | ✅ PR-4 先软后硬（原设计「否则 422」据实降级为软告警）：对 `closure_status∉{null,closed}` 的 executable 根因与未处理 `root_signal_rejected_json` 产 `warning` issue（`ROOT_SIGNAL_NOT_CLOSED` / `ROOT_SIGNAL_UNHANDLED_REJECTED`，`blocks_publish=False`）+ 指标 `hci_root_signal_publish_gate_total{reason}`，仅观测不阻断；待实测拒绝率收敛后由 PR-5 切硬 422（对齐 `signal_schema` L588「不能自动降级」） |

三处共用**同一** `evaluate_root_closure`/`adjudicate_root_closure`，保证「抽取即校验、编辑即校验、发布即校验」的单一判据；其中**抽取/编辑为写库前硬切分**（不可闭环即落拒绝候选列），**发布为审核期软告警**（PR-4 阶段先观测、PR-5 再切硬）。

## 9. 对抗性审查与边界

- **与旧「不进 CDD」约束的关系**：[根因信号抽取方案](根因信号抽取方案.md) §8「明确不做：不让根因信号进入 CDD
  producer/consumer 裁决」是 **PR B 之前**的约束，已被两轨消费**取代**；落地本方案时须同步改写该句为
  「executable 根因经闭包校验后并入 CDD，text 仅作报告锚点」，消除两份主文档矛盾。
- **HOST 不误伤（决策①已认可）**：本地操作类根因「省略 host」是合法闭环（走 node_ip 兜底），校验器**不得**因「没有 HOST 生产者」
  判悬空——`host` 字段缺省即不入 `requires`；只有**显式写了 `{{HOST}}`** 才要求闭环，否则拒绝候选。
- **拒绝不可过激**：只有 `command_args/match` 里**确属随现场变化**的实体才触发参数化；稳定路径
  （如固定日志 `/sf/cfg/if.d/` 目录、固定命令）不得误判为写死实体而误拒，白名单需可解释。
- **绝不自动降级 text（决策②）**：不可闭环候选一律走拒绝候选转人工（§5.4）——自动降级会掩盖闭包缺陷，
  复用关键信号「不能用无关降级掩盖上游失败」（#1159 / `signal_schema` L588）的同一条铁律。
- **跨轨解耦不破**：bundle 的生产者写入 `signals_json`（关键轨事实源），根因轨仍只落 `root_signal_json`；
  闭包校验是**读两侧、判一致性**，不把两侧物理合并（维持既有「独立列」决策）。
- **存量回刷**：不变量上线后，CI `--strict` 须扫全库现存根因信号闭包，把 27736 这类**现网存量反例全部检出并判拒绝候选**
  （从 accepted 移入 `root_signal_rejected_json`、阻断发布），不允许「旧数据豁免」留雷。

## 10. 测试守护（覆盖失败态优先）

1. 悬空 require：写 `{{HOST}}` 无 producer、非白名单 → `dangling_requires` → **拒绝候选**（不入 accepted、不转 text）；
2. 合法兜底：省略 host 的本地操作根因 → `closed`（不因缺 HOST 生产者误判）；
3. 参数化：`command_args` 含 `eth0`/IPv4 字面量 → `hardcoded_literals` → 要求变量化；稳定路径不误判；
4. 闭环 bundle：根因+producer 一次产出、`requires ⊆ produces` 通过、发布门放行；
5. feature 扩展：从 `本地网口（eth0）IP …100.88… 冲突` 确定性抽出 `ETHX=eth0`、`IP=100.88`，**不误取 channel4**；
6. 三处接入一致性：抽取/编辑/发布对同一 KBD 得出**同一** closure_status（幂等、无绕过）；
7. 存量 strict：把 27736 形状喂给 `evaluate_root_closure` 必判非 closed → 拒绝候选；
8. 全拒收口：某篇根因候选全部不可闭环 → 显式 `ROOT_SIGNAL_ALL_REJECTED` 带原因，不落空数组；
9. 发布阻断：`root_signal_rejected_json` 有未处理拒绝候选 → 发布 422，不自动降级放行；
10. 人工降级 text 是显式动作：审核端确认降级才进 accepted（`provenance.manual_downgrade=true`），服务端绝不自动做。
