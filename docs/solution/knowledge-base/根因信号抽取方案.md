# 根因信号抽取方案

本文维护「根因信号」这条与关键信号完全解耦的第二抽取轨：背景与摸底结论、双形态契约、
门禁设计、Prompt 管理对齐、试点结果与分阶段路线。关键信号生产链见
[关键信号抽取与建模设计](关键信号抽取与建模设计.md)，信号字段总纲见
[关键信号架构设计](关键信号架构设计.md)。

## 1. 背景与摸底结论

专家评审结论：现有 KBD 关键信号从「问题描述/告警/排查步骤」抽取，信号通用不独特，
检索与自动定位效果不达预期；而「根因」章节是已确认的结论性描述，天然携带全篇最独特
的故障特性。2026-10-12 对 100 篇已发布 KBD 根因摸底（分析脚本 `.local/rc_survey.py`、
`.local/rc_anchor_analysis.py`）：

- 根因锚点（错误码/路径/端口/版本号/文件名等）跨篇唯一率 **96%**，为四个章节中最高；
- 通用 token（无区分度词）数量 **0**；56/100 含机器可判定锚点（CJK 边界下实际更高）；
- **76%** 的根因锚点未被现有 signals_json 信号覆盖；信号 `source_section` 分布中
  root_cause **零出现**（`extract_signals.py::_VALID_SOURCE_SECTIONS` 有意排除根因，
  防止处置动作混入诊断输入——该禁区保持不变）；
- 缺陷类型分布：文件损坏 26、版本兼容 23、文件缺失 14 等；47/100 呈「特性+后果」二段式。

结论：根因值得单独一条抽取轨，但必须与关键信号**完全分开**——它是结论侧定位锚点，
不是排查过程输入。

## 2. 定位与三条轨道的边界

| 轨道 | 来源 | 匹配方向 | 用途 | 存储 |
|---|---|---|---|---|
| 关键信号（QKV/QFK） | 问题描述/告警/排查步骤 | 问题侧，producer→consumer | 引导逐步排查、CDD 裁决 | `signals_json`（v2） |
| 语义入口画像 | 问题描述/症状锚点 | 问题侧，匹配用户已提交上下文 | 无信号/受限案例的语义推荐 | `semantic_entry_profile` |
| **根因信号** | **整篇 KBD（结论侧定位信号）** | **结论侧，匹配现场证据/报错文本** | **快速圈定符合该根因特性的 KBD 集合** | `root_signal_json`（v2 顶层数组） |

硬约束（内部评审重设计，v2）：
- **不限条数**：一篇 KBD 可抽出全部「可确证根因」的定位信号（v2 顶层 JSON 数组），不再限制为一
  条最特殊锚点；实测均值 1.25 条/篇（S1 主锚口径，见 §10）；
- **输入放开到整篇**：抽取输入由仅 `root_cause` 改为整篇 `content_md`（缺失回退章节字段拼接），
  Prompt 占位符 `root_cause` → `kbd_content`；
- **只抽能确证根因的信号**：无关信号不输出；保留「禁止处置动作/解决方案语义」的既有护栏
  （防答案侧污染）；
- **溯源分层（trace_tier）**：信号 evidence 能逐字命中 `root_cause` 记为主锚（高信任），仅命中
  整篇其余章节记为 `content` 兑底（**强制 `needs_review=true`**），整篇都溯源不到即拒收；主锚优先，
  有主锚信号则不采用兑底信号；
- 与关键信号抽取解耦：不复用 `_VALID_SOURCE_SECTIONS`、不进 `signals_json`、
  不受 CDD/QFK producer-consumer 发布门禁约束；
- Prompt 管理方式**完全对齐关键信号**（见 §5）。

核心模块：`backend/kb-service/app/services/root_signal_extractor.py`（纯门禁+归一化，
LLM 经 `llm_call` 回调注入，保证可单测、可离线试点）。

## 3. 双形态契约（v2 多信号数组）

v2 顶层为 JSON 数组，每个元素为一条定位信号（不再限制为单对象）：

```json
[
  {
    "schema_version": 2,
    "role": "root_cause",
    "match_type": "executable | text",
    "signal_text": "一句话特性结论（≤60字）",
    "acquire": {"tool": "qfk_*", "args": {...}} 或 null,
    "match": {"type": "keyword|regex|state|boolean|threshold|exists", "mode": "all", "expected": ["..."]},
    "distinctiveness": {"category_conflicts": 0, "global_conflicts": 0},
    "provenance": {"source_section": "problem_description|alert_info|steps_text|root_cause|solution|operational_impact|recommendations",
                    "source_category_id": "...", "method": "llm_root_signal_v2",
                    "evidence": "整篇原文逐字摘录", "trace_tier": "root_cause|content", "confidence": 0.9,
                    "needs_review": false, "source_sha256": "sha256(content_md)"},
    "prompt_revision": "sha256:..."
  }
]
```

- **schema_version=2**：与 v1 单对象不同，顶层必为数组；落库 CHECK 只接受 `jsonb_typeof='array'`（或 NULL）。
- **provenance.trace_tier**：`root_cause`＝主锚（evidence 逐字命中根因，高信任）；`content`＝兑底
  （仅命中整篇其余章节，**强制 `needs_review=true`**）；tier=`none` 在归一化阶段拒收。
- **source_section** 由 v1 仅 `root_cause` 放开为章节枚举（`VALID_SOURCE_SECTIONS`），因输入已是整篇。
- **source_sha256** 指纹基线改为整篇 `content_md` 哈希（非仅根因）。
- **executable**：根因特性可通过 qfk_* 采集器在现场取证并判定时使用。`acquire.tool`
  取自 `ACQUIRER_CATALOG` 的 `qfk_*` 子集（**禁 qfk_var**，专家专属）；args 过
  `validate_acquire_args`（`backend/shared/schemas/acquirer_args.py`，与关键信号同一
  事实源）；再过 `kbd_signal_read_only_violation` 只读安全门
  （`backend/shared/schemas/kbd_signal_safety.py`）。
- **text**：无法映射采集器时降级（结论性谓词、版本兼容矩阵等）。`match.expected`
  为独特关键词列表，平台在已采集证据/告警文本/用户输入上做包含匹配。

## 4. 门禁设计（服务端拒收 > 信任模型自检）

抽取分两层：`gate_signals` 先把 LLM 产出的信号集收敛为合法列表，再逐条过 `normalize_root_signal`；
任一环节违规带原因回喂 LLM 重试一次（`extract_root_signal`，max_attempts=2；仍无可用信号则
`signals=[]`，绝不伪造）。**v2 部分成功语义**：单条门禁失败只丢弃该条并记入 `gate_errors`，不整篇失败：

1. **多信号门禁** `gate_signals`：接受 `signals` 数组 / `signal` 单对象 / 裸对象；按 `signal_text`
   归一去重；封顶 `max_signals=8`（防长输出噪声洪水，实测均值 1.25/最大 3，阀值宽裕）；空集拒收；
2. **溯源分层** `_trace_tier`：根据 `provenance.evidence` 逐字命中面判定 tier——命中 `root_cause`＝主锚、
   仅命中整篇＝`content` 兑底、整篇都溯不到＝`none`（拒收）；tier=`content` 强制 `needs_review=true`；
3. **executable 门禁** `gate_executable`：词表内 + `qfk_*` 前缀 + 禁 `qfk_var` +
   args 契约 + 只读安全门（kill/chmod/restart 等写操作命令直接拒绝）；
4. **text 门禁**：
   - `_flatten_keywords`：嵌套数组扁平化 + casefold 去重（试点发现 LLM 偶发返回
     `[["a","b"]]`，直接 `str()` 会把 list repr 当关键词落盘）；
   - 过短关键词（<4 字符）拒收——无法承担定位职责；
   - 纯数字/分隔符关键词（`_WEAK_KEYWORD_RE`，如 `0.95`）拒收并提示「版本号须带
     产品语境，如 HCI 6.11.1」；
   - 携带 acquire 拒收（形态分离）；
   - 关键词无法逐字溯源至 tier 目标（主锚→根因、兑底→整篇）→ **不拒收**，降级 `needs_review=true` 钉人工复核；
5. **provenance 门禁**：`source_section` 限 `VALID_SOURCE_SECTIONS` 章节枚举；evidence 非空；
   confidence 收敛到 0~1；
6. **主锚优先** `extract_root_signal`：tier=root_cause 的 `primary` 与 tier=content 的 `fallback` 分桶，
   `chosen = primary if primary else fallback`——只要根因级有信号就只取主锚，不用整篇兑底填充（防噪声稀释）；
7. **独特性度量** `ConflictCorpus.conflicts`：把信号关键词打在全库语料（draft+published 且根因非空）上
   做包含匹配，逐条统计 `category_conflicts`/`global_conflicts`（理想为 0＝唯一定位），
   作为审核辅助指标与 Prompt 迭代回归信号。

### 4.1 试点暴露的关键设计缝隙与修复（2026-10-12）

第一轮试点 20/20 成功但 **executable=0**（全部被迫退化 text）。对抗性审查定位根因：
**「门禁比 Prompt 严」**——`validate_acquire_args` 是 `additionalProperties:false` 的
严格契约，但 Prompt 只给了采集器一句话描述，LLM 猜不中字段名（file 传全路径、自造
keyword 字段），反复被拒后弃疗选 text。修复：

- `acquirer_catalog_text()` 内嵌与 `ACQUIRER_ARGS_SCHEMA` **同源生成**的 args 契约摘要
  （`_args_contract_lines`：必填字段带 `*`、描述截断、排除 timeout 等噪声字段），
  Schema 改动自动传导到 Prompt，不产生第二套手工维护的契约文档；
- 种子 Prompt 补充易错点：qfk_log 的 `file` 只收无目录 basename、`resource_keyword`
  是资源选择器不是匹配词、`command` 只填基础子命令（参数进 `command_args`）。

第二轮试点 executable 形态恢复（见 §6）。

## 5. Prompt 管理——与关键信号完全对齐

用户明确要求：根因抽取 Prompt 必须与关键信号 Prompt 一样支持 admin-ui 页面管理与热
加载。对齐方式（**零新增管理页面**，复用既有链路）：

| 环节 | 关键信号 Prompt | 根因信号 Prompt |
|---|---|---|
| 存储 | `system_prompt` 表，`stage='KEY'` | 同表同 stage，`name='kbd_extract_root_signal_v2'` |
| admin-ui | 「Prompt 管理」页 KEY tab 在线编辑/停用/版本化 | 同一 tab 自动枚举（`/api/v1/prompts` 按 stage 枚举，无按 name 白名单） |
| 加载 | `StrictPromptLoader.load_and_validate` 每次抽取热加载 | 同一 Loader、同法占位符契约校验 |
| 占位符契约 | Loader 校验 | `ROOT_SIGNAL_PLACEHOLDERS = [title, category_id, category_path, kbd_content, acquirer_catalog]`（v2：`root_cause`→整篇 `kbd_content`），不符即抛错 |
| 审计 | DynamicResource 编辑审计 | 同链路（同表同 stage） |
| 种子 | `database/seeds/02_system_prompts.sql` | 同一文件末尾追加（`ON CONFLICT (name) DO NOTHING`，不覆盖 admin-ui 自定义） |

> **种子位置的正确事实源（阶段二对抗性审查纠正）**：Prompt 种子**必须**放
> `database/seeds/02_system_prompts.sql`，由 Helm **db-seed-job（PostSync）** 应用。
> 阶段一曾把它放进 `database/atlas-migrations/`，该目录按仓库规范「仅 Schema」，且
> `scripts/db-migrate.sh` 只做 `atlas schema apply --to desired_schema.sql` + data-migrations +
> `desired_extras.sql`，**根本不会应用 atlas-migrations** —— 若保留该位置，生产路由会因
> 「system_prompt 里没有 `kbd_extract_root_signal_v2`」而 100% 抛 `PromptLoadError`（StrictPromptLoader
> 不静默降级，这是正确行为）。故该迁移文件已删除，种子并入 seeds/02；`load_prompt_template_from_sql`
> 相应改为**按 Prompt 名定位**（同一文件含多个 `$TEMPLATE$` 块，不能取首个）。

抽取内容要点（种子 v2）：输入段给整篇 `{kbd_content}`；目标段为「抽取全部能确定根因的定位信号
（不限条数）、无关信号不输出」；选取第一性原理排序「独特性 > 机器锚点 > 具体谓词」；禁处置动作/
解决方案语义（防答案侧污染）；双形态输出规则与 args 契约注意事项；evidence 逐字可溯源；输出前 6 项自检。

试点/单测可经 `load_prompt_template_from_sql` 离线加载种子 SQL（与线上热加载同法
校验占位符）；线上路径一律走 StrictPromptLoader 热加载。

## 6. 试点实现与结果

试点脚本：`scripts/kbd/extract_root_signal_pilot.py`（dry-run，只读 DB，结果仅落
`.local/root_signal_pilot.{jsonl,csv}`）。抽样：published 10 + draft 10，按机器锚点
6:4 分层、层内按分类轮转；冲突语料＝全库已发布根因。LLM 配置从 kb-service Pod env
导出，模型回退链 `ROOT_SIGNAL_MODEL→EXTRACT_SIGNALS_MODEL→CLASSIFY_MODEL→LLM_DEFAULT_MODEL`。

- 第一轮（修复前）：20/20 成功、19/20 全库唯一定位、needs_review=3，但 **executable=0**，
  且暴露嵌套数组关键词、纯数字关键词（`0.95`）两类脏数据；
- 第二轮（修复后，同抽样同 seed）：20/20 成功、**executable=1**（17569 qemu-server 分组
  残留 .conf → `qfk_system find`，契约/只读/占位符均合规）、**全库唯一定位 20/20**、
  needs_review=1（关键词改写痕迹钉人工复核）；嵌套与纯数字问题零复发，版本号均带
  产品语境（如「HCI 6.10.0_R2」）；
- 第三轮（executable 专项，用户要求 ≥10 条）：改 Prompt 为「优先 executable，能现场判定
  就不得降级 text」并内嵌 7 类可执行化映射示例（df/ls/cat/服务/端口/设备/日志）；
  指定 20 篇机器锚点密集的工单（published 10 + draft 10）→ **executable=16 text=4、
  20/20 成功、新口径全库唯一定位 18/20**（余 2 条 gc=1 为真实的同特性冲突：/run 分区满、
  /run/lock inode 满类多案例重叠，属治理有效信号）。评审文件：
  `.local/root_signal_pilot_executable评审.csv`。本轮另暴露并修复两处：
  - **qfk_log 的 file 隐含必传**：校验器里条件性必传但 JSONSchema `required=[]`，目录摘要
    标成可选致模型省略后两连拒 FAIL。修复：目录文本新增 `_TOOL_USAGE_NOTES`（与校验器
    实际语义对齐的隐含约束显式化：file 必传且须为已登记日志源 basename，无法确定文件名
    则不选 qfk_log），Prompt 同步标「必传」；模型惯性写全路径的场景由 `coerce_acquire`
    无损降级 basename（仅 file；path 是搜索目录相反方向不得归一），归一后仍过完整契约与
    只读门；
  - **冲突计数口径**：executable 的 expected 是现场输出判定串（如 "100%"），只拿它打根因
    语料会把不同目录的 df 案例误判冲突。修复：`_signal_match_tokens` 把采集具体资源
    （command_args 路径/file/service/port 等，排除占位符与纯选项）并入判定面，
    「同一资源对象＋同一判定串」同时命中才计冲突（唯一定位 14/18 → 18/20）。
- 形态选择经验结论：机器锚点密集批次的 executable 转化率可达 16/20；纯版本兼容/结论谓词
  型（如「HCI6.3.0_R2 不兼容 CentOS 7.9」）仍正确保持 text。
- **第四轮（全库无偏实测，n=200 纯随机按自然占比 published:draft=10:190，并发 5）**，
  评审文件 `.local/root_signal_random200.{csv,jsonl}`：
  - 抽取成功率 **96%**（192/200；8 篇失败均为偶发：LLM 超时 2 + 格式小瑕疵 6，无系统性缝隙）；
  - 形态占比实测：**executable 26%（95%CI 20~33%）/ text 74%**——修正了此前静态外推的
    45~60% 高估（正则锚点判断 ≠ LLM 可映射判断，以实测为准）；按全库 2720 篇回刷预计
    产出约 700 条可执行根因信号；
  - 分层差异显著：**published 70% vs draft 24%**（published 样本仅 10 篇、置信区间宽），
    主因是根因文本质量：published 经人工精编、硬锚点密度高；draft 多为 AI 生成泛化谓词。
    启示：回刷优先级应偏 published/高质量 draft；
  - 全库唯一定位 **97%**（187/192 冲突 0），needs_review 7%，二轮重试后成功 10%；
  - executable 工具分布：qfk_system 27 / qfk_log 8 / qfk_network 5 / qfk_vm 5 /
    qfk_hardware 3 / qfk_service 1，七类采集器均有真实命中，无堆单工具的偏科。

测试守护：`backend/kb-service/tests/test_root_signal_extractor.py`（28 例）——单信号
门禁、executable 六类拒收＋file 全路径 basename 无损归一（归一不降门禁）、text 扁平/去重/
纯数字/溯源/形态分离、回喂重试、失败不伪造、golden 端到端、冲突计数（含 executable 判定面
＝expected∧采集资源回归）、种子占位符契约、目录含 args 契约（防「门禁比 Prompt 严」复发）。

## 7. 阶段二落地：生产抽取链路与审核 UI

### 7.1 落库：`kbd_entry.root_signal_json`

- **声明式事实源** `database/desired_schema.sql`：`root_signal_json jsonb` + CHECK
  `ck_kbd_entry_root_signal_json`（v2：只允许 `NULL` 或 `jsonb_typeof='array'`，不再接受单对象）+ **GIN
  索引** `idx_kbd_entry_root_signal_gin`（`jsonb_path_ops`，部分索引 `WHERE root_signal_json IS NOT NULL`，
  支撑「数组内任一信号包含匹配」的审核队列查询；v1 两个标量表达式索引 `->>'match_type'`/
  `provenance->>'needs_review'` 对数组失效已删除）+ `ck_kbd_batch_job_type` 枚举含
  `extract_root_signal`；`database/atlas-migrations/20261013000000_add_kbd_entry_root_signal_json.sql`
  是同一批对象的**幂等**版（供已运行库的 direct apply 与审阅）。
- **双事实源同改**：因本 PR（#1147）尚未合入 main、无存量数据，故直接原地改未合并迁移与
  `desired_schema.sql`（不做存量迁移）；两处 CHECK/索引/COMMENT 必须逐字一致，否则 CI
  「Atlas 声明式 Schema 验证」幂等门禁会报 diff。
- **为什么它是独立列而不是塞进 `signals_json`**：根因信号与关键信号在语义、门禁、审核动线上
  都不同轨，混写会让关键信号的 v2 契约校验器被迫理解结论侧锚点。
- **为什么不入 `kbd_revision`**：它与 `ai_category_id` 同属「AI 派生元数据」，回刷不得产生新版本、
  不得影响发布盖章。由此推出一条硬约束：**写回路径不能用 `require_mutable_kbd` 守卫**（该守卫会对
  published 返回 409，直接与「全库回刷」需求冲突）；同理 UPDATE 只动 `root_signal_json` 一列，
  不触碰 `content_md`/embedding/tsv。
- **陷阱：`ck_kbd_batch_job_type` 有两个事实源，extras 才是现行赢家**（CI「Atlas 声明式 Schema
  验证」首次暴露）。`db-migration-test.yml` 的序列是
  `extras → atlas apply(desired_schema) → extras`，而 `database/desired_extras.sql` 对该 CHECK
  做的是**无条件 DROP + ADD**，因此它总是覆盖 atlas 刚写好的定义。只改 `desired_schema.sql` 会出现
  「apply 后仍有 diff」：`ALTER TABLE ... DROP CONSTRAINT ck_kbd_batch_job_type, ADD CONSTRAINT ...
  ('extract_root_signal'...)`，幂等门禁直接失败。**规则：凡 extras 里无条件重建的对象（含枚举型
  CHECK），扩值必须同时改 `desired_schema.sql` 与 `desired_extras.sql`。**extras 里当前无条件整值
  替换的 CHECK 共三个（`ck_kbd_batch_job_status`、`ck_kbd_batch_job_type`、
  `ck_kbd_batch_job_item_status`）均属此坑；`message_role` ENUM 是只补不删的
  `ADD VALUE IF NOT EXISTS`（不产生反向 diff），`updated_at` 触发器由 psql 幂等管理、
  Atlas Community 不纳管，故两者不坑。

### 7.7 CI 首轮真实暴露的两处（本地全量测试覆盖不到的拓扑差异）

| 失败门禁 | 症状 | 根因 | 修复 |
|---|---|---|---|
| Atlas 声明式 Schema 验证（幂等性） | `atlas schema apply` 后 `schema diff` 仍报 `DROP/ADD CONSTRAINT ck_kbd_batch_job_type` | CI 执行序列是 `extras → atlas apply(desired_schema) → extras`，而 `desired_extras.sql` 对该 CHECK **无条件 DROP + ADD**——它才是现行事实源；本轮只改了 `desired_schema.sql` | `desired_extras.sql` 同步加入 `'extract_root_signal'::varchar`，并就地注释「双事实源必须同改」规则 |
| 前端检查（单元测试 + 构建） | `Error: 未定位到仓库根，无法校验跨语言契约` | 该作业用 `sparse-checkout: frontend`（注释明写「前端门禁不消费后端源码」），仓根只有 `frontend/`；本地全量检出掩盖了这一拓扑 | 早期修复：删除前端的 `node:fs` 源码扫描、跨语言校验下沉后端。**v2 重设计直接废除了 `MIN_ROOT_CAUSE_LEN` 跨语言契约（输入放开整篇后不再需要前端阈值）→ 前后端钉值与 `TestCrossLanguageContract` 均删除，该坑连根消失（避坑 V-023 同步改写为退位记录）** |

两条的共同教训：**「本地全量测试全绿」不等于 CI 拓扑下可跑**——CI 作业各有 checkout 形态与执行
序列约束，跨目录读写与幂等断言必须先核对该作业定义；而 v2 更进一步的教训是：**契约本身也可能
被重设计推翻**（`MIN_ROOT_CAUSE_LEN` 跨前后端+测试三处同废），删除跨语言钉值时必须同步清理
后端镜像断言与避坑登记，否则留下悬空引用。

## 10. v2 实测对比数据与锁定结论（阶段一 n=100、决定溯源锚点策略）

内部评审把「输入放开到整篇」定为前提；分歧只在「每条信号的可信锚点/溯源校验锁在哪」，
三策略各跑同一批样本（从有根因的 2791 篇随机抽 100，同整篇输入，仅换溯源校验规则）：

| 策略 | 含义 | 接受信号 | ≥1信号篇 | 均值/篇 | 确证命中率 | 噪声率 | 泛化率 | 唯一定位率 | 均 global_conflicts |
|---|---|---|---|---|---|---|---|---|---|
| **S1 锁根因** | evidence 必须逐字命中 `root_cause` | 65 | 52 | 1.25 | **96.9%** | **3.1%** | 0% | **90.8%** | 0.37 |
| S2 溯源放开整篇 | evidence 命中任意章节即可 | 177 | 77 | 2.30 | 65.5% | 34.5% | 19.2% | 81.9% | 3.66 |
| S3 混合 | 根因为主 + 少量其余章节分层 | 177 | 77 | 2.30 | 65.5% | 34.5% | 19.2% | 81.9% | 3.66 |

关键数据：候选信号共 314 条（结构性合法 215），可溯源到 root_cause 的仅 65，可溯源到整篇的 177，
其中 112 条只能从其余章节（solution/steps 等）溯源——即 S1 相对 S2/S3 会「丢」这些信号；但
**S2 增量信号噪声率高达 52.7%**（新增部分一半以上是处置动作/泛化词/非根因噪声），且平均冲突度
从 0.37 劣化到 3.66（定位能力大幅下降）。按预先声明的决策规则（确证命中率 × 唯一定位率最高
且噪声率低于阈值），**S1 完胜**。

**锁定结论（选项 B：S1 主锚 + 整篇兑底强制转复核）**：既取 S1 的高信噪优势，又不完全丢弃
整篇才能看到的少数确证信号——实现为溯源分层：evidence 命中 root_cause 记主锚（高信任），
仅命中整篇其余章节记 `content` 兑底（**强制 `needs_review=true` 转人工**），整篇溯不到即拒；
主锚优先（`chosen = primary if primary else fallback`）。形式上 LLM 读整篇（满足「不限看的内容」），
但每条信号的可信锥仍锤在根因，低信任信号不隐身而是显式转人工。本阶段共跑≈ 300 次真实 LLM
（qwen3.8-flash、temperature=0、json_object、thinking disabled），token 389,810/70,674（prompt/completion）、
均时延 11.9s；密钥仅从 kb-service Pod env 注入进程，不落盘不入库。
