# KBD 知识生产、管理与多维消费完美架构设计方案

## 1. 架构设计背景与第一性原理

### 1.1 现状与技术妥协
当前 KBD（知识库条目）的数据链路在处理“特殊字面量字符”（如排障步骤与分割线中高频出现的星号 `*` 和下划线 `_`）时，采用了**“入库前提前转义 + 前端手写正则渲染”**的架构设计。
这种设计存在明显的局限性：
* **数据源语义污染**：在入库转换阶段（ETL Stage 3），调用转换工具将原始 HTML 转为带有反斜杠转义的 Markdown（如将 `os_type` 存为 `os\_type`，将 `***` 存为 `\*\*\*`）并存入 PostgreSQL。这导致数据库中的数据资产带有特定表现层的“杂质（Artifacts）”。
* **前端贪婪与裂变 Bug**：前端管理台（`KbdReviewView.vue`）为了解析 Markdown，使用了简易的手写正则表达式（`inlineRender`）。由于手写正则缺乏完备的词法语法分析能力，无法区分语法级界定符和普通字面量，迫使开发人员在两端引入诸如 `&#42;` 临时占位符等极其复杂、脆弱的妥协代码，且在特定 DOM 损坏或 `DESCRIPTION` 提取状态下极易诱发**“文字贪婪吸入”**和**“反斜杠无限裂变与星号吞噬”**等隐蔽 Bug。

### 1.2 第一性原理（First Principles）
回归到数据科学与软件工程的最基础假设：
> **数据是系统的核心资产，其生命周期远长于任何特定的前端表现层或展示框架；而表现格式仅仅是数据在某一特定时间、特定场景下的多维投影（Projection）。**

基于该原理，理想的 KBD 架构应当遵循**“数据语义纯净化”**与**“表现层状态机词法分析”**的两大核心理念，实现绝对的**语义与表现解耦**。

## 2. 完美整体架构设计方案

本方案旨在彻底废除现有的“数据层提前转义”和“前端手写正则”等妥协设计，构建一个**面向未来 AI/RAG 检索、多端一致性消费、基于 AST（抽象语法树）动态解析**的纯粹内容管理架构。

```
                    ┌──────────────────────────────────────────────┐
                    │            深信服 Portal 原始数据             │
                    └──────────────────────┬───────────────────────┘
                                           │
                                    ETL (Stage 1-3)
                                           │
                                ┌──────────▼──────────┐
                                │ 数据库纯净内容模型  │
                                └────┬────────────┬───┘
                                     │            │
                               双通道分流      双通道分流
                                     │            │
                         ┌───────────▼──┐      ┌──▼───────────┐
                         │ content_raw  │      │  content_md  │
                         └───────┬──────┘      └──────┬───────┘
                                 │                    │
                             RAG 消费                 │ API 传导 (JSON)
                                 │                    │
                         ┌───────▼──────┐      ┌──────▼───────┐
                         │LLM 向量检索  │      │ 前端标准AST  │
                         │(100%精准无噪)│      │  Markdown    │
                         └──────────────┘      │ 解析引擎     │
                                               │ (marked.js)  │
                                               └──────┬───────┘
                                                      │
                                                      ▼
                                                100% 完美的
                                                网页排版输出
```

### 2.1 数据库端：语义纯净的双通道模型设计（Model）
数据库中的字段应当保持 100% 的“语义干净”，拒绝任何形式的表现层提前转义反斜杠（如没有 `\_` 和 `\*`）。为了同时兼顾 **RAG 向量检索** 与 **富文本网页排版**，推荐采用**双通道数据分离存储**：

1. **`content_raw` 字段（语义消费通道）**：
   * **内容**：过滤掉所有 Markdown 语法标记、图片占位符和 HTML 标签的**纯文字文本**。
   * **用途**：专门供给 AI 代理、大语言模型（LLM）会话上下文以及向量 Embedding 计算，保证语义计算的相似度绝对精准，100% 消除无用标记噪音。
2. **`content_md` 字段（表现消费通道）**：
   * **内容**：保持最纯净、无任何反斜杠转义的**标准 Markdown 原文**（星号与下划线均以字面量保存，只在真正表示粗体时使用 `**`）。
   * **用途**：供给多端表现层 API 消费。由于其无冗余转义，无论终端 CLI 命令行、移动端、PDF 导出器还是网页端都能无缝直接阅读，无需任何“二次反转义”清洗。

### 2.2 前端表现层：标准 AST 词法状态机解析（View）
彻底废弃当前前端脆弱、简陋的正则表达式行内匹配函数（如 `inlineRender`），统一采用业界最成熟的标准 Markdown 解析引擎（如 `marked.js` 或 `markdown-it`）：
* **词法状态机分析**：标准 Parser 并非用正则进行粗暴全局替换，而是采用**有限状态自动机（FSM）**将 Markdown 源码解析为抽象语法树（AST）。
* **字面量与语法的完美隔离**：
  在标准 Parser 中，类似 `os_type` 里的单个下划线或 `1、虚拟机...` 里的单个星号，在词法分析时会自动被判定为 `text` 节点，而只有成对的 `**` 才会判定为 `strong` 节点。
  这使得**前端在运行时即可完美区分普通文本字符与标记语法，天然隔离所有误匹配冲突**，根本不需要数据库在入库时进行提前的 `\` 转义！
* **零占位符，零妥协代码**：彻底删除所有 `&#42;`、`\\\*` 等中转占位符和过滤正则，代码行数可缩减 80% 以上，且可维护性达到工业级水准。

## 3. 重构实施演进步骤

为了保证排障平台的平滑升级与业务零中断，我们规划了以下**四步走**的渐进重构路径：

### 阶段一：前端渲染器标准化（标准 Parser 注入）
* **动作**：在前端 `admin` 和 `customer` 模块中，通过 `pnpm add marked` 引入成熟的 Markdown 解析器，用其替代现有的 `renderMarkdown` 及手写正则。
* **兼容性**：标准解析器原生兼容旧有的带有少量转义符的数据，升级后页面的基础排版将立刻变得极为健壮。

### 阶段二：重构数据流水线转换器（ETL Ingestor 去转义化）
* **动作**：修改 `data-pipeline/kbd/converter.py` 的 HTML 转 Markdown 部分。
* **重构逻辑**：配置 `markdownify` 在转换时**关闭对下划线、斜杠和星号的自动转义功能**。确保生成的 Markdown 字段是纯净、标准的字面量。

### 阶段三：双通道模型改造（RAG 高级优化）
* **动作**：修改数据库 `kbd_entry` 表结构，新增 `content_raw` 字段。
* **重构逻辑**：在后端数据入库接口（`ingest.py`）中，当收到 `content_md` 时，使用正则过滤器（例如 `stripmd`）自动剔除 Markdown 格式标记，生成无噪的 `content_raw` 写入数据库，并重新驱动生成高精度的 Embedding 向量。

### 阶段四：数据全量重新 ETL 导入（资产重刷）
* **动作**：利用已有的本地 `cache/{support_id}/raw.json` 缓存，在项目根目录下通过流水线 CLI 命令全量重新覆盖跑一遍导入：
  ```bash
  PYTHONPATH=data-pipeline uv run python -m kbd.run import --excel --override --override-status all
  ```
* **效果**：数据库中现存的历史案例将被一次性、全自动地清洗为最完美的“纯净双通道数据资产”，重构圆满落地。

## 4. 架构设计的长远价值
* **100% 数据语义精准度**：消除了向量模型和 LLM 的字符干扰，极大提升 RAG 排障引导回复的质量。
* **极致的前端稳定性**：借力成熟开源社区的标准 Parser，彻底消除了由于手写正则引发的边界字符吞噬、贪婪吸入等长尾缺陷。
* **多渠道消费一致性**：最干净的 Markdown/纯文本源码让排障命令行和 PDF 报告生成变得无比清爽。
