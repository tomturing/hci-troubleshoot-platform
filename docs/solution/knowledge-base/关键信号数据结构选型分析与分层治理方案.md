## 一、 问题起源与现场现象

在工单 `Q2026072576263` 的诊断过程中，用户选择故障选项 `② 虚拟机-003 虚拟机开机失败`。Agent 正确匹配到了知识库条目 ID `1`（`support_id: 27123`，《【HCI-VT】虚拟机开机失败,报错虚拟机镜像忙，正在进行其他操作》），但在最终生成的诊断报告中输出如下异常：

```markdown
**现场证据（关键信号确认）**：
- 无
```

经排查，数据库中条目 ID `1` 完整保存有 3 个合规信号，但由于微服务重构（PR #611, Commit `cc7fc1a`）时移除了 `unwrap_signals()` 解包函数，导致 `agent-service` 使用 v1 时代的 `isinstance(signals, list)` 校验 API 返回的 v2 `dict` 信封（`{"schema_version": 2, "signals": [...]}`），断言失败后将信号列表静默清空为 `[]`。

这一故障引发了关于**"关键信号数据结构究竟应当选择 `dict` 还是 `list`"**的深层次技术讨论。本文基于第一性原理与业界通用范式，给出严谨推导与分层治理方案。

## 二、 第一性原理推导：问题的本质是什么？

基于第一性原理（First Principles），从数据结构的本质属性出发，必须剥离具体的 Python/SQL 代码实现，追问数据结构的本质：

### 1. `list`（列表/数组）的本质
- **属性**：同质元素（Homogeneous Elements）的**顺序集合**。
- **语义**：表达"一组具有相同 Schema 的数据实体"（如多条诊断信号）。
- **操作**：迭代（Iterate）、过滤（Filter）、按 index/顺序访问。

### 2. `dict`（字典/映射/对象）的本质
- **属性**：异质属性（Heterogeneous Properties）的**键值映射/容器**。
- **语义**：表达"一个由不同属性组成的复合实体或包含元数据的信封（Envelope）"。
- **操作**：按 Key 随机查找、版本标记、元数据附着。

### 本质矛盾
当前产生争议的原因，在于**将"持久化存储信封"与"业务领域数据主体"这两个不同维度的需求混在了一起**：
- **需求 A（元数据与版本控制）**：数据库需要记录 `schema_version: 2`，防止离线迁移或反序列化时无法识别 Schema 版本。这是 **`dict` (Envelope/Container)** 的天然职责。
- **需求 B（业务执行与 API 语义）**：Agent 诊断引擎和 API 消费端需要拿到的是"一组可被迭代执行的信号列表"。这是 **`list` (Collection/Array)** 的天然职责。

## 三、 业界三大最佳实践与设计范式

根据业界公认的软件设计标准（Google API Design Guide, OpenAPI 3.1, Kubernetes CRD Architecture, DDD）：

### 范式 1：CloudEvents / Kubernetes CRD 的信封模式（Envelope Pattern）
在 Kubernetes CRD 或 CloudEvents 规范中，**持久化/消息传输的根节点是一个 Dict 信封**，用于承载元数据（`apiVersion`, `kind`, `metadata`），而**具体的数据列表作为 payload 字段平铺在内部**：

```json
{
  "schema_version": 2,         // 元数据 (Envelope Metadata)
  "signals": [                 // 数据主体 (Domain Payload -> 必须是 List)
    { "id": "sig_001", "acquire": {...} },
    { "id": "sig_002", "acquire": {...} }
  ]
}
```

> [!IMPORTANT]
> **业界共识**：信封用 `Dict`，数据主体用 `List`。绝不能把信封本身当作数据主体，也不能让数据主体强行去充当信封。

### 2. RESTful API / OpenAPI 3.1 规范（防信封泄漏反模式）
在 OpenAPI / Zalando RESTful API Guidelines 中，规定：
- 资源属性若表达复数概念（如 `signals`），其类型必须定义为 `type: array`。
- **信封泄漏反模式（Envelope Leakage Anti-Pattern）**：如果 REST API 返回 `{ "id": 1, "signals": { "schema_version": 2, "signals": [...] } }`，会导致 API 消费者必须调用 `response.signals.signals` 才能获取数据，这是典型的**存储层实现泄漏到了传输层**。

### 3. 领域驱动设计（DDD）与防腐层（ACL - Anti-Corruption Layer）
在 DDD 架构中：
- **存储层（DB）**：可以使用 `dict` 信封 `{"schema_version": 2, "signals": [...]}` 保存到 `JSONB` 列。
- **防腐层（ACL / Serializer）**：在数据离开持久层（如 `kb-service` 序列化 DTO）时，**必须剥离存储信封**。
- **领域模型层（Agent Engine）**：`KBD.signals` 属性在内存中必须是纯粹的 `List[Signal]`，保持领域实体的洁净。

## 四、 四维严谨评估矩阵

| 评估维度 | 选择 `dict` 形态 `{"schema_version":2, "signals":[...]}` | 选择 `list` 形态 `[ Signal, Signal ]` | 最佳设计判定 |
| :--- | :--- | :--- | :--- |
| **1. 数据库持久化 (DB JSONB Column)** | **最优**。自带版本控制头，有利于 DB 级的离线 Schema 迁移与索引校验。 | **较差**。纯数组难以追加列级别的 `schema_version` 元数据。 | **持久化层选择 `dict` 信封** |
| **2. API 传输与 DTO 语义 (`kb-service`)** | **较差**。犯了"信封泄漏反模式"，API 结构臃肿（出现 `case.signals.signals`）。 | **最优**。符合 REST 规范，`signals` 字段直接输出数组 `List[Signal]`。 | **API 传输层选择 `list`** |
| **3. 代码类型系统与 IDE (Agent Engine)** | **较差**。违反 Python/TypeScript 类型定义，无法直接进行 `for sig in kbd.signals` 循环。 | **最优**。强类型 `List[Signal]`，IDE 补全良好，直接支持标准迭代。 | **领域模型层选择 `list`** |
| **4. 架构解耦与防腐 (ACL)** | **较差**。强制下游所有消费服务感知上游数据库的信封结构。 | **最优**。防腐层在边界处剥离信封，上下游实现高内聚低耦合。 | **防腐边界处剥离为 `list`** |

## 五、 最终判定结论与架构落地方案

**第一性原理的严谨判定为：**

> **v2 在系统不同分层中，应当分层适用：持久化存储层用 `dict` 包装，API 传输与领域模型层用 `list` 数据。**

### 1. 数据库存储层 (Storage Boundary)
PostgreSQL 列 `kbd_entry.signals_json` 保持 `dict` 结构：
```json
{
  "schema_version": 2,
  "signals": [ ... ]
}
```

### 2. 服务端 API 导出层 (`kb-service` ACL 防腐层)
在 `_entry_to_case_dict()` 中剥离存储信封，向 REST API 透出规范的 `list`：

```python
def _entry_to_case_dict(entry: KbdEntry, similarity: float) -> dict[str, Any]:
    """将 KbdEntry 转换为 agent-service 消费格式。"""
    raw_signals = entry.signals_json
    # 解包存储信封：若 DB 存的是 dict，剥离出内部 signals list 透给 API 消费者
    signals_list = raw_signals.get("signals", []) if isinstance(raw_signals, dict) else raw_signals
    return {
        "id": str(entry.id),
        "name": entry.title,
        "category_id": entry.category_id or "",
        "similarity": round(similarity, 4),
        "problem_description": entry.problem_description,
        "alert_info": entry.alert_info,
        "steps_text": entry.steps_text,
        "root_cause": entry.root_cause,
        "solution": entry.solution,
        "operational_impact": entry.operational_impact,
        "is_temporary": entry.is_temporary,
        "recommendations": entry.recommendations,
        "signals": signals_list,  # <--- 标准 List[Signal]
    }
```

### 3. Agent 客户端接收层 (`agent-service` 防御性容错)
遵从波斯塔尔法则 (Postel's Law)，在 `kbd_from_dict()` 中进行防御性解包容错：

```python
def kbd_from_dict(d: dict[str, Any]) -> KBD:
    """从 KBD 文档 dict 构造 KBD。"""
    signals = d.get("signals", [])
    # 容错解包：既能接收 API 标准直出的 list，又能兼容 DB 原始列对象 dict
    if isinstance(signals, dict):
        signals = signals.get("signals", [])
    elif not isinstance(signals, list):
        signals = []
    
    return KBD(
        id=d.get("id", ""),
        name=d.get("name", ""),
        root_cause=d.get("root_cause", ""),
        solution=d.get("solution", ""),
        similarity=float(d.get("similarity", 0.0) or 0.0),
        type=d.get("type", ""),
        signals=signals,  # <--- 保持内存模型为洁净的 List[Signal]
    )
```

## 六、 总结

| 系统分层 | 数据结构选择 | 核心原则 |
| :--- | :--- | :--- |
| **数据库持久化层** | `dict` 信封 `{"schema_version":2, "signals":[...]}` | 存储需要版本控制与元数据 |
| **API 传输层** | `list` 数组 `[Signal, Signal]` | RESTful 规范、防信封泄漏 |
| **领域模型层** | `list` 数组 `List[Signal]` | 类型安全、迭代友好 |
| **防腐边界** | 解包/剥离信封 | ACL 隔离存储与领域模型 |

通过分层治理，既保留了数据库层面的版本控制能力，又保持了 API 和领域模型的简洁性，符合业界最佳实践。
