# 关键信号抽取设计

> 本文记录 KBD/SOP 条目的「关键信号」抽取机制：包括整体设计、端到端流程、Prompt 热加载，
> 以及——重点——**LLM 如何抽取「前端信号」**，并配一个深信服案例实例说明。
> 对应实现位于 `backend/agent-service/app/tools/signal/` 与 `backend/kb-service/app/routes/admin.py`。

---

## 一、什么是「关键信号」

一份 KBD/SOP 排障案例本质是自然语言文本（「检查配置存储服务备节点异常告警」「在备节点看
mysql-managed.log 是否有只读错误」…）。「关键信号」就是把这些**模糊的排障步骤，翻译成结构化的可执行信号**。

设计上采用 PR498 的 **QKV–QFK 双核**思路，把信号分成两类，扮演「生产者 / 消费者」两种角色：

| 类别 | 角色 | 来源语义 | 干什么 |
|------|------|----------|--------|
| `frontend`（前端信号） | **生产者** | 涉及告警/任务/弹框查询 | 从现场**提取变量**（host、vm、end、target、errcode），写进变量池 |
| `backend`（后端信号） | **消费者** | 涉及日志/服务/系统指标诊断 | **消费**前端产出的变量，做健康度布尔判定 |

一次抽取往往是：先抽几条 `frontend`（先定位「谁、什么时候、哪个对象坏」），再抽几条 `backend`
（「据此去查日志/服务/指标是否存在异常」）。

---

## 二、端到端抽取流程

```text
KBD 详情页「抽取关键信号」按钮
  └─ POST /api/v1/kbd/{id}/extract-signals  (api-gateway → kb-service)
       ├─ kb-service：字段级分别抽取（详见第五节）
       │   ├─ 前端信号：对 title / problem_description / alert_info 三个字段【分别】调用前端 Prompt
       │   │   每字段可产出 0..n 条；三字段结果高度可能重复，按 (query, keyword) 去重合并
       │   └─ 后端信号：对 steps_text【逐步骤】调用后端 Prompt（一行 / 一个步骤对应一个后端信号）
       │   （root_cause / solution 不参与抽取；steps_text 全空则回退 content_raw）
       ├─ 远程调用 agent-service
       │   POST {AGENT_SERVICE_URL}/api/v1/signals/extract  {text, mode:"batch", prompt_name: 前端/后端 Prompt}
       │   （带 Bearer INTERNAL_API_TOKEN；单字段抽取失败不中断其他字段）
       └─ agent-service /extract：
           1. 从 system_prompt 表按名加载 SIG 子 Prompt（StrictPromptLoader，热加载）
           2. _render_prompt：解除双花括号转义 + 替换 {text}
           3. client.invoke(messages, response_format={"type":"json_object"})
           4. 解析 JSON → KeySignal.from_dict() 按类别路由构造
           5. signal.validate() 校验 → 返回 [s.extract() for s in signals]
       kb-service 把结果（前端在前、后端在后）json.dumps 写进 kbd_entry.key_signals(JSONB) 并落库
```

**热生效**：Prompt 每次请求从 `system_prompt` 表读取（`stage='SIG'`，由 `StrictPromptLoader` 按
`{text}` 占位符强校验），所以管理员在 admin-ui 改完 SIG 阶段 Prompt，下一次点「抽取」就立刻用新模板，
无需重启服务。种子数据在 `database/seeds/02_system_prompts.sql`
（两条：`kbd_signal_extract_v1` 单条 / `kbd_signal_batch_extract_v1` 批量，前端默认用 batch）。

## 三、Prompt 与占位符转义

seed 中 `stage='SIG'` 的两条模板结构一致（`app/tools/signal/template.py` 为源码镜像）：

```text
## 任务：你是 HCI 超融合排障专家，从下面文本提取关键信号
## 输入：<troubleshooting_text>{text}</troubleshooting_text>   ← {text} 是唯一真实占位符
## 关键信号分类：
   ### 前端信号：告警/任务/弹框 → FrontendSignal
   ### 后端信号：日志/服务/系统指标 → BackendSignal
## 提取规范：类别判别、关键字提取、{{host}}/{{end}} 变量占位、expected 取值
## 输出 JSON 格式 …
```

**占位符转义（关键坑点）**：模板既要给 LLM 看 JSON 示例，又要用 `{host}`/`{end}` 变量占位符。
若写成 `{host}`，`StrictPromptLoader` 会误判成「未知占位符」报错，Python 也会把它当 `.format` 变量。
因此存储时全部**双写**成 `{{host}}`、`{{ }}`、JSON 示例用 `{{"signal_category": ...}}`，只保留
`{text}` 一个单花括号。运行时 `_render_prompt` 先解转义再替换：

```python
prompt_template.replace("{{", "{").replace("}}", "}").replace("{text}", text)
```

用 `.replace` 而非 `.format`，避免用户文本里本身含 `{ }` 导致抛错。

## 四、抽取结果的数据结构

`extract()` 返回的字典即落库与前端展示对象。

**前端信号（frontend）**：

```json
{
  "signal_category": "frontend",
  "query": "alert",            // alert(告警类查询) / task(任务类查询) / dialog(弹框/对话类查询)
  "keyword": "备节点异常",     // 核心检索词，不要带具体命令
  "is_failed": false,          // 仅 task 时生效：是否只看失败任务
  "limit": 100,
  "description": "检查配置存储服务备节点异常告警"
}
```

**后端信号（backend）**：

```json
{
  "signal_category": "backend",
  "signal_type": "log_keyword",   // 还有 service_status/vm_state/network_check/storage_state/hardware_state/platform_state/system_metric
  "target": {
    "scope": "{{host}}",          // 运行时由前端信号产出的 host 渲染，如 node-001
    "resource": "mysql-managed.log",
    "path": "/sf/data/platform_database/"
  },
  "keywords": ["file system read-only"],
  "match_mode": "any",            // any(或) / all(与)
  "expected": true,              // true=期望出现；false=期望「不出现」
  "description": "在备节点检查数据库日志是否有只读错误",
  "container": null,             // 仅 service_status：asv/anet/host
  "sub_command": null            // 仅 vm/network/storage
}
```

> 抽取阶段只产出这份「配置」。真正的 `execute()`（调 QKV/QFK 引擎去查现场）是后续运行时能力，
> 不在抽取+落库+展示的范围内。

前端展示位于 `frontend/admin/src/views/KbdReviewView.vue` 的【关键信号】区块（在「来源元数据」与
「内容预览」之间），表格列：类别（前端/后端）、关键字、说明、类型/查询、目标/关键字。

## 五、实例详解：如何让 LLM 抽取「前端信号」

下面以深信服技术支持案例为例说明：
`https://support.sangfor.com.cn/cases/list?product_id=33&type=1&category_id=31793&isOpen=true`
（product_id=33 即 HCI 超融合；**注意 31793 是 `category_id`（某子类），并非单个 case 的 id**——
真实抽取应取该分类下的某条具体 case，抓取后落库为一条 KBD 条目）。

### a. 程序从哪几个字段抽取前端 / 后端信号

**关键澄清（v1.2 起生效）**：

> **前端信号与后端信号是「按字段 / 按步骤」分别抽取的，不是把整段文本混在一起让 LLM 自己分类。**

1. **前端信号：对三个字段【分别】抽取，再合并去重。**

   前端信号只来自界面侧字段，每个字段单独调用一次前端 Prompt（一次只喂一个字段文本），
   每个字段内部可能包含 0 个 / 1 个 / 多个前端信号；三字段产出的前端信号**高度可能重复**
   （同一告警在 title、problem_description、alert_info 里都提到），因此提取后按
   `(query, keyword 归一化)` 去重，只保留首次出现。

   | 字段 | 含义 | 是否参与前端抽取 |
   |------|------|------------------|
   | `title` | 标题 | ✅（单独抽一次） |
   | `problem_description` | 问题描述 | ✅（单独抽一次） |
   | `alert_info` | 告警信息 | ✅（单独抽一次） |
   | `steps_text` | 排查步骤 | ❌（属后端抽取） |
   | `root_cause` | 根因 | ❌ |
   | `solution` | 解决方案 | ❌ |
   | `recommendations` / `operational_impact` / `is_temporary` | 其它 | ❌（当前未纳入） |
   | `content_raw` | 纯文本去噪内容 | 仅 steps_text 全空时回退为后端抽取源 |

2. **后端信号：对 `steps_text`【逐步骤 / 逐行】抽取，一行对应一个后端信号。**

   后端信号来自排查步骤，每次把整段 `steps_text` 喂给后端 Prompt，要求 LLM **一行（一个步骤）
   对应一个后端信号**，顺序与原文步骤一致。

当前 `extract_kbd_signals` 的实际逻辑（即抽取来源与策略）：

```python
# 前端：title / problem_description / alert_info 分别抽，再按 (query, keyword) 去重
frontend_sources = (("title", None), ("problem_description", "问题描述"), ("alert_info", "告警信息"))
for field, label in frontend_sources:
    value = row.get(field)
    if not value or not value.strip():
        continue
    sigs = await _extract_signals_remote(value.strip(), prompt_name=SIGNAL_FRONTEND_PROMPT)
    # 只保留 signal_category == "frontend"，并按 (query, keyword) 去重
frontend_deduped = _dedup_frontend_signals(frontend_signals)

# 后端：steps_text 逐步骤抽；全空则回退 content_raw
backend_source = (row["steps_text"] or "").strip() or (row["content_raw"] or "").strip()
backend_signals = await _extract_signals_remote(backend_source, prompt_name=SIGNAL_BACKEND_PROMPT)

final_signals = frontend_deduped + backend_signals   # 前端在前，后端在后
```

**为什么前端要「分别抽 + 去重」而不是合并抽**：
- 三个字段语义不同（标题一句话、问题描述一段话、告警信息一条告警），合并抽容易让 LLM
  偏向某一字段而漏掉其它；
- 同一信号在三个字段里重复出现是常态，分别抽后统一去重，比让 LLM 在合并文本里"自行去重"更稳。

**为什么后端要「逐步骤抽」**：后端信号的本质是"在故障节点执行一条诊断命令并做布尔判定"，
天然是一行步骤一个动作，强制"一行对应一个信号"可避免多步被压成一个信号而丢失判定。

### b. 如何抽取前端信号（提示词是什么）

调用链：详情页按钮 → `kb-service /extract-signals`（拼接上文 text）→ `POST agent-service
/api/v1/signals/extract` `{text, mode:"batch"}` → 加载 `kbd_signal_batch_extract_v1` →
`client.invoke(..., response_format={"type":"json_object"})` → `KeySignal.from_dict` 按
`signal_category` 路由到 `FrontendSignal` → `validate()` → 返回。

前端信号的分类与字段约束，写在 `app/tools/signal/template.py` 的 Prompt 里（节选，**已改为按意图分类 + 保留告警修饰词**）：

```text
### 前端信号（frontend）
前端信号 = 到 HCI 控制台某个页面去查一条记录的「查询类动作」，按查询对象分三类：

- alert（告警）：到「告警中心」核对某条告警/异常/报错现象是否存在。
  面向「系统上报的现象/异常状态」，keyword【保留「告警/异常/报错/只读/断连」等修饰词，不要删掉】。
  例：原文「配置存储服务备节点异常告警」→ keyword="配置存储服务备节点异常告警"（明确就是一条告警）。

- task（任务）：到「任务中心」查看某个操作任务的执行结果。
  面向「用户/系统发起的操作动作」（迁移/扩容/重启/快照/升级…）；
  若出现「失败/不行/不了/错误/未成功/卡住/中断/超时」等否定词 → 基本可定 task 且 is_failed=true。

- dialog（弹框）：查看交互弹窗/二次确认/对话提示等人机交互记录。
  出现「弹框/弹窗/确认框/风险提示/报错提示」等词大概率是 dialog。

（以上均按意图判别，不依赖是否出现「告警/任务/弹框」字面字样）

前端信号示例：
```json
{{  "signal_category": "frontend",
     "query": "alert",
     "keyword": "配置存储服务备节点异常告警",
     "is_failed": false,
     "description": "检查备节点异常告警" }}
```

## 提取规范
1. 信号类别判别：**按意图/动作判别**，而不是按字面关键词。
   文本可能只写「登录控制台看 node-003 是否有配置存储服务异常」而没有「告警」二字——这仍是 alert 查询。
2. 关键字提取：alert 的 keyword【必须保留「告警/异常/报错」等修饰词】，明确这是一条告警/异常；
   task 的 keyword 取「操作动作+对象」（如「虚拟机迁移」）；dialog 取弹框中的核心提示信息。
3. query 取值：alert(告警) / task(任务，失败置 is_failed=true) / dialog(弹框)。
```

对应到数据模型（`app/tools/signal/frontend.py` 的 `FrontendSignal`）：

- `query`：`alert` / `task` / `dialog`（决定用 acli 哪类查询，按查询**意图**归类的三档）
- `keyword`：喂给查询的核心词，例如 `acli alert get -k "备节点异常"`
- `is_failed`：仅 `query=task` 时生效（是否只看失败任务）
- `limit`：最大返回条数（默认 100，校验范围 [1,200]）
- `description`：对该排障步骤的自然语言说明

### c. 实例：这条案例抽取出的前端信号实际长什么样

> ⚠️ 校准说明：深信服支持门户的会话与登录 IP 绑定，无法在本机沙箱中复用，**实时案例正文尚未抓取**。
> 下方为**结构化示意**：字段优先级、前端信号分类均按上文（a/b）的规则演绎，待你贴入一条真实案例正文后，
> 我会用真实文本替换本示例并校准字段选择。

**示意用的拼接文本（节选）**：

```text
[problem_description]
客户反馈 HCI 集群一台主机的配置存储服务告警，虚拟机磁盘 IO 偶发超时。

[alert_info]
告警：配置存储服务备节点异常（node-003），持续 5 分钟。

[steps_text]
1. 登录 HCI 管理台，检查 node-003 的配置存储服务备节点异常；
2. 查看是否有失败的任务；
3. 确认故障时间点的弹窗确认日志；
4. 在 node-003 上检查 /sf/data/platform_database/ 下的 mysql-managed.log 是否有 file system read-only 错误。
```

> 下方结果已是「前端三字段分别抽取 → 合并去重」后的最终信号数组（示意）。

**LLM 返回的 batch 信号数组（节选前端部分，示意；已保留告警修饰词）**：

```json
[
  {
    "signal_category": "frontend",
    "query": "alert",
    "keyword": "配置存储服务备节点异常告警",
    "is_failed": false,
    "limit": 100,
    "description": "检查 node-003 配置存储服务备节点异常告警"
  },
  {
    "signal_category": "frontend",
    "query": "task",
    "keyword": "虚拟机迁移",
    "is_failed": true,
    "limit": 100,
    "description": "查看虚拟机迁移任务是否失败"
  },
  {
    "signal_category": "frontend",
    "query": "dialog",
    "keyword": "弹窗确认日志",
    "is_failed": false,
    "limit": 100,
    "description": "确认故障时间点的弹窗确认日志"
  }
]
```

逐条解读：

| 信号 | query | keyword | 含义 |
|------|-------|---------|------|
| ① | `alert` | 配置存储服务备节点异常告警 | 去查这条告警，**keyword 保留「告警」修饰词**，明确就是一条告警 |
| ② | `task` | 虚拟机迁移 | 查**失败**的迁移任务，`is_failed=true` 只取失败态（靠「失败/未成功」等否定词判定） |
| ③ | `dialog` | 弹窗确认日志 | 查故障时间点的弹窗/对话确认日志 |

> 注意②、③即便案例正文里没出现「任务」「弹框」字眼，只要意图是「查任务/查弹框日志」，
> 也照样归为 `task` / `dialog`——这正是「按意图而非字面」分类的意义。

这 3 条 `frontend` 信号执行时（运行时 `execute()` → QKV 引擎）会从告警/任务/弹框结果里
**提取 `host`（如 node-003）、`end`（故障时间点）等变量**，写进变量池；随后同一条案例里抽出的
`backend` 信号（如「在 `{{host}}` 上查 mysql-managed.log 的 `file system read-only`」）会消费这些
变量，把 `{{host}}` 渲染成 `node-003` 再去做日志关键字判定。

```json
// 同案例抽出的后端信号（用于对照「生产者→消费者」关系），示意
{
  "signal_category": "backend",
  "signal_type": "log_keyword",
  "target": { "scope": "{{host}}", "resource": "mysql-managed.log", "path": "/sf/data/platform_database/" },
  "keywords": ["file system read-only"],
  "match_mode": "any",
  "expected": true,
  "description": "步骤4：在故障节点检查数据库日志是否有只读错误"
}
```

## 六、验证与落库

- `extract_batch_from_text` 逐条 `from_dict` 构造并 `validate()`，校验不过的单条跳过（记 warning），只保留合法信号。
- kb-service 把整个数组 `json.dumps(ensure_ascii=False)` 写进 `kbd_entry.key_signals`（JSONB，默认 `[]`）。
- 新库按 `database/desired_schema.sql` 建表；**已有库需手动**：
  ```sql
  ALTER TABLE kbd_entry ADD COLUMN key_signals jsonb NOT NULL DEFAULT '[]'::jsonb;
  ```
