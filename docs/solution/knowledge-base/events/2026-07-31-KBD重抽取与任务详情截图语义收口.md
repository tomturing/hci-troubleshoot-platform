# KBD 重抽取与任务详情截图语义收口

## 问题

KBD27123 在新版声明式 Extract 上线后仍出现两类相互矛盾的现象：

1. 点击“重新抽取”后，模型候选仍使用已经删除的文本取值字段和旧 Matcher mode，因而被当前 Schema 拒绝；
2. 任务详情通过模态窗口展示时，识图将“弹窗外观”当成语义类型，输出“弹框截图”，而不是能直接驱动 `qkv_task` 的“任务截图”。

根因不是运行时同时支持两套 Extract。重新抽取会从 `system_prompt` 表热加载 `kbd_extract_signals_v2`；此前该数据库 Prompt 仍保留旧示例。与此同时，重抽只覆盖 `kbd_entry.signals_json`，没有冻结新的 Proposal，页面的版本信息仍可能指向旧快照，造成“已重抽却仍像旧稿”的错觉。

## 决策

- 保存和运行时继续只接受新版声明式 Extract；不恢复旧字段兼容。
- 数据迁移 `015_align_signal_and_vision_prompts_to_current_contract.sql` 清理热加载 Prompt 中旧文本取值示例，新增唯一的 `rows + parser + columns[] + value_key` 指引，并把 Matcher mode 收口为 `or / and / not`。Prompt 由 Python `str.format()` 渲染，所有展示用 JSON 花括号必须以 `{{` / `}}` 转义；`016_escape_declarative_extract_prompt_literals.sql` 对已部署的 015 结果执行同样修复，避免 JSON 键名被误识别为运行时占位符。
- 每次草稿 KBD 重新抽取成功后，除更新 `signals_json` 外，还创建一条新的 LLM Proposal revision；旧 Expert revision 保留为不可变审计历史，但不再保留为当前工作稿指针。
- 截图分类以承载业务记录的可见字段为准，而非模态框容器外观。任务详情同时含“状态”“行为”及至少一个时间/对象/主机字段时，服务端确定性归类为“任务截图”。

## 新版文本取值形态

```json
{
  "type": "text",
  "parser": "whitespace_table",
  "rows": {
    "mode": "keywords",
    "include": ["{{VM}}"],
    "exclude": [],
    "include_mode": "all",
    "case_sensitive": true
  },
  "columns": [
    {
      "key": "PID",
      "selector": {"by": "index", "index": 2},
      "value_mode": "integer"
    }
  ],
  "value_key": "PID",
  "cardinality": "first",
  "source": "stdout"
}
```

行选择负责确定候选行；列选择负责从已选行读取一个或多个值。Matcher 与产出变量都可以复用同一份 Extract，且都通过安全转换管道；二者差异只在取值后的消费方式。

## 部署后验收：KBD27123

1. 数据迁移完成后，打开 KBD `27123` 并执行“重新抽取”。
2. 刷新详情：模型 Proposal 应变为新 revision；草稿状态下不应继续把旧 Expert revision 显示为当前工作稿。
3. 发布前检查不应再报已删除文本字段的 Schema 原始错误；本轮候选应符合当前 Schema，或因其他明确业务原因被拒绝。
4. 对图片 `img_0` 点击“重新识图”。截图包含状态、行为、起始/结束时间、对象类型等任务详情字段，TYPE 应为“任务截图”，后续信号建议应优先 `qkv_task`。
5. 普通只含错误标题和正文、没有任务字段的弹窗仍应保持“弹框截图”，不会被误判为任务。

## 边界

历史 `kbd_revision` 是不可变审计记录，不能原地篡改为新版。它们不进入运行时；需要重新作为当前 Proposal 使用时，必须由重新抽取产生新的合法快照。无法由截图可见字段确定为任务的通用弹窗，仍保持“弹框截图”，不凭文档上下文猜测。
