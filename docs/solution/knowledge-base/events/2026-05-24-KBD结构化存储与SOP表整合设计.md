# KBD 结构化存储 + SOP 表整合设计决策

> **状态更新（2026-07-14）**：本文为 2026-05-24 的历史决策记录。其中 `steps_json`（扁平工具步骤）方案已被 **ADR-1** 推翻并彻底移除（迁移 `20260714000000`，PR #545/#547），统一由 `signals_json`（关键信号集合，producer/consumer，占位符 `{{VAR}}` 大写）承载。详见《关键信号字段级分别抽取》。

## 背景与问题陈述

### 问题 1：KBD 无结构化存储，agent 无法执行步骤

`kbd_entry` 表原有设计只有一个 `content_md TEXT` 字段，存储完整 Markdown。
AI Agent 在案例差异诊断（CDD）场景需要消费"可执行步骤"，但 `content_md` 是面向人类渲染的聚合文本，无法直接提取为结构化工具调用序列。

**现象**：`InvestigationAgent` 的 `KBClient.search_cases_with_steps()` 返回的 `steps` 字段永远为空列表，
agent 无法根据 KBD 案例生成确定性的诊断步骤。

### 问题 2：sop_chunk 是死代码

`sop_chunk` 表设计参照 `kb_chunk`（RAG 向量检索），但 SOP 的消费模式完全不同：

- SOP 走**决策树遍历**（`sop_tree.tree_json`），不走向量召回
- `sop_matcher.py` 从文件系统关键字索引匹配分类，不查数据库
- SOP 全文通过 `sop_document.content_md` 注入 LLM System Prompt

全链路排查结论：

| 代码位置 | 读了什么 | embedding/tsv 被用了吗 |
|---------|---------|----------------------|
| `admin.py` 列表统计 | `COUNT(*)` 算 chunk 数量 | ❌ |
| `admin.py` approve | 遍历写入 embedding/tsv | ❌（写了但从不读） |
| `sop_matcher.py` | 不查数据库 | ❌ |
| `agent-service` | `sop_tree.tree_json` + `sop_document.content_md` | ❌ |

每次 approve 一个 SOP 文档都会调用 embedding API 为所有 chunk 生成向量，但这些向量**从未被任何 SELECT 查询**。这是纯粹的资源浪费。

### 问题 3：sop_tree 与 sop_document 是严格 1:1 关系，无必要分表

- `sop_tree.document_id` 有 UNIQUE 约束
- sop_tree 在 approve 时生成，写入时机确定，且失败时 tree_json = NULL 足以表达"未生成"状态
- 两表在所有查询路径上始终伴随出现，分表只增加 JOIN 复杂度

## 决策

### 决策 A：KBD 增加 8 大章节结构化字段 + steps_json

| 字段 | 类型 | 说明 |
|------|------|------|
| `problem_description` | TEXT | 问题描述 |
| `alert_info` | TEXT | 告警信息 |
| `steps_text` | TEXT | 有效排查步骤（自然语言 Markdown） |
| `root_cause` | TEXT | 根因 |
| `solution` | TEXT | 解决方案 |
| `operational_impact` | TEXT | 操作影响范围 |
| `is_temporary` | TEXT | 是否是临时解决方案 |
| `recommendations` | TEXT | 建议与总结 |
| `steps_json` | JSONB | 结构化工具步骤（`[{tool_name, tool_args_template, expected_pattern}]`）|

**设计哲学**：
- `content_md` 保留（含图片视觉描述，供 LLM context 和 UI 渲染）
- 8 章节字段是 source of truth，admin 编辑后重建 `content_md`
- `steps_json` 默认 `[]`，由 admin 手动/AI 填充（冷启动保护：search 接口仅返回 `steps_json != '[]'` 的条目）

**API 变更**：
- `GET /api/kb/kbd/search`（原 `/cases/search`，不存在）：新建，供 agent-service CDD 使用
- `POST /api/kb/kbd/ingest`：扩展接受 8 章节 + `steps_json`（向后兼容，全部有默认值）

### 决策 B：删除 sop_chunk，将 sop_tree 合并入 sop_document

**sop_chunk 处置**：直接删除，embedding/tsv 生成逻辑一并移除。
原 approve 流程中的 chunk embedding 计算代码全部删除，节省 LLM API 调用。

**sop_tree 合并方案**：在 `sop_document` 中新增 tree 相关列：

| 新增列 | 类型 | 说明 |
|--------|------|------|
| `tree_json` | JSONB | SOPNode 根节点完整 JSON；NULL = 未生成 |
| `tree_schema_version` | VARCHAR(20) | 解析器 schema 版本（默认 `sop-tree-v1`）|
| `tree_scenario_name` | VARCHAR(500) | 根节点名（冗余，方便按名称检索）|
| `tree_leaf_count` | INTEGER | 叶节点数量 |
| `tree_total_node_count` | INTEGER | 总节点数 |
| `tree_validation_status` | VARCHAR(20) | valid/warnings/error；NULL = 未生成 |
| `tree_validation_issues` | JSONB | ValidationIssue[] JSON |
| `tree_generated_at` | TIMESTAMPTZ | 树首次生成时间 |
| `tree_generator_version` | VARCHAR(50) | 解析器版本 |

**合并可行性分析**：

| 考量维度 | 分析结论 |
|---------|---------|
| 关系模型 | 严格 1:1，UNIQUE 约束 |
| 生命周期 | tree_json 在 approve 时写入，与 `kbd_entry.embedding` 完全类比 |
| 查询模式 | agent 查 tree_json 已有 document_id，合并后消除一次 JOIN |
| 大列性能 | tree_json 最大 ~200KB，PostgreSQL TOAST 自动处理；列表查询显式投影不 SELECT tree_json |
| 并发安全 | approve 时 UPDATE 单行，不影响其他行 |

**与 kbd_entry 的对称性**：
```
kbd_entry:   content_md + steps_json（一张表）
sop_document: content_md + tree_json（一张表）
```

## 影响范围

### Schema 变更
- `sop_document`：新增 9 个 tree_* 列
- `sop_chunk`：删除整表（含索引 idx_sop_chunk_document / tsv / embedding）
- `sop_tree`：删除整表（含索引 idx_sop_tree_document / json / scenario）

### kb-service 变更
| 文件 | 变更 |
|------|------|
| `models/sop_document.py` | 新增 9 个 tree_* 列；移除 chunks/tree 关联 |
| `models/sop_chunk.py` | 删除 |
| `models/sop_tree.py` | 删除 |
| `models/__init__.py` | 移除 SopChunk 导入 |
| `routes/sop_ingest.py` | 移除 sop_chunk 创建；`GET /{id}/tree` 改读 sop_document.tree_json |
| `routes/admin.py` | approve 移除 chunk embedding 逻辑；改写 tree 为 UPDATE sop_document；list/detail 用 tree_leaf_count 替代 chunk_count；update 移除 rechunk |

### agent-service / shared（无需变更）
- `GET /api/sop/{id}/tree` 端点 URL 不变，仅内部实现从 sop_tree 改为 sop_document
- `kb_client.get_sop_tree()` 行为不变

## 决策依据（反驳排除）

| 反对意见 | 反驳 |
|---------|------|
| "sop_chunk 可能未来有用" | 设计模式已改为决策树遍历，chunk RAG 与 SOP 消费模式不匹配，未来需 RAG 时应重新设计而非复活死代码 |
| "sop_tree 分表职责更清晰" | 字段名 `tree_*` 前缀已完整表达职责边界，与 `steps_json` 在 kbd_entry 的设计完全对称 |
| "tree_json 太大影响列表查询" | 所有列表查询均为显式列名（无 `SELECT *`），PostgreSQL TOAST 确保大值在不引用时不加载 |
| "生命周期不同（draft vs tree）" | sop_document 已有多个时间戳字段（created_at/reviewed_at/published_at），tree_generated_at 是其中一个；draft 时 tree_json = NULL 自然表达未生成状态 |
