# KBD 关键信号统一过滤、取值与输出方案

## 背景与需求

KBD 后端关键信号原本把“命令参数、日志检索关键字、输出筛选关键字、Matcher 关键字、变量取值”分散在多处表达。同一需求在不同页面可能使用逗号、换行或 Shell 管道，`qfk_log` 保存门禁又只认可 `resource_keyword/request_id`，不认可已经写在 `extract.rows.include` 中的有界筛选。KBD27736 因而出现了配置语义正确、运行时也有部分支持，但保存仍失败的跨层断裂。

本次收敛目标不是增加新的业务概念，而是把所有 QFK 统一为一条管道：

```text
信号输入/命令采集
→ 候选记录过滤
→ 取值（完整行 / 文本行列 / JSON 路径）
→ 可选 AI 提取
→ Match 布尔输出 或 Produce 类型化变量
```

## 发现的问题与反例

### 1. `keyword` 被错误地当作所有 QFK 的公共必填输入

`qfk_log` 的日志查询需要有界选择器，`qfk_system` 的命令本身却不需要 keyword；其 keyword 只可能属于执行后的候选记录过滤。若把 keyword 设为所有 QFK 的命令输入，会产生无人消费的幽灵字段，也会把“采什么”和“如何解释输出”混为一层。

### 2. “完整输出”名称掩盖了真实语义

整份 stdout 可能达到几十 MB，不能默认穿过 Bridge、WebSocket 和 Agent。用户真正需要的是“保留筛选后命中记录的整行，不截列”，而不是无界的原始物理 stdout。

反例：一行只含“检测到IP”，另一行只含“冲突”。若先拼接全文再做 AND，会错误判为同一条故障记录同时包含两个条件。

### 3. 包含与排除只有一套关系，无法表达精确规则

现状中 `include_mode` 可选 AND/OR，但 exclude 永远是“任一出现即排除”。这既不能表达“全部排除词同时出现才排除”，页面也没有告诉专家包含关系不会自动作用于排除关键字。

### 4. 命令失败可能与业务 False 混淆

业务输出只有 Match 的 True/False 或 Produce 的类型化值；但命令未执行、超时、非零退出、解析失败都不是 False。只保留 stdout 或复用 `matched=false` 会把“没有证据”误写成“证据不成立”。

### 5. 保存、命令编译与运行时对有界性的认识不一致

KBD27736 的 Produce 已配置 `extract.rows.include=["检测到IP", "冲突"]`，运行路径也能把它编译为 Bridge `output_filters`，但 kb-service 仍要求 `resource_keyword/request_id`，因此保存失败。若为了过门禁伪造 `resource_keyword`，同一过滤条件会被持久化两次并必然漂移。

### 6. `qfk_service` 暴露写动作

KBD 是自动诊断知识，不应通过服务信号执行 start/stop/restart。仅依赖抽取门禁不够；管理台和 Agent Handler 都应只允许 `status`，形成保存前和运行时的纵深防御。

## 第一性原理

1. **命令输入只描述如何取得原始事实**：host、command、file、service 等字段由具体 aCLI 工具决定，不由输出算法决定。
2. **候选过滤只缩小记录集合**：它逐条记录执行，不是最终业务判定；qfk_log 可把条件下推到 `-k/-E`，但平台仍须按同一规则复核。
3. **取值只做确定性结构变换**：完整行保留记录、文本行列选列、JSON 路径选节点，不执行自由 Shell、grep、awk 或 jq。
4. **AI 只能做有依据的后置摘取**：输入必须是前述取值确定的候选，返回值和引用行必须可逐字回查；AI 不替代 Match 的确定性 Predicate。
5. **执行状态与业务输出正交**：只有 execution 与 processing 均成功，业务 True/False 或变量值才有效。
6. **同一语义只持久化一次**：不在“完整行”下面另造 keyword 字段；统一保存为 `extract.rows`，工具所需的下推参数由编译器派生。

## 最终方案（WHAT）

### 1. 信号输入字段

QKV 保持固定 Produce：

```text
instruction / keyword / produces
```

QFK 公共输入：

```text
instruction / host / timeout / output mode
```

其中页面的“执行模式”只是对 Signal 结构的派生展示：存在 `match` 即为 Match，存在 `orchestrate.produces` 即为 Produce，两者严格二选一。不新增 `output.mode` 或其他重复持久化字段，避免执行模式出现两份真相。

工具特有输入：

| 工具 | 字段 | 约束 |
|---|---|---|
| qfk_log | file / time_window / request_id | 常规日志 file 必填；必须由 include 或 request_id 等确定性选择器限制结果 |
| qfk_system | command / command_args / container | command 必填；container 省略表示 host |
| qfk_service | service / action / container | service 必填；KBD action 只允许 status |
| qfk_vm/network/storage/hardware/platform | command | command 必填；不得带 Shell 管道 |

新建或未显式填写的 timeout 统一为 60 秒；历史文档中显式保存的 timeout 保持原值。

`qfk_service` 的新语义名是 `service/action`。为读取既有 Revision，本次迁移继续兼容历史 `resource_keyword/command`，但新编辑统一写新字段，运行时只取规范化后的 service/action。

`status-only` 是 KBD 自动诊断的领域门禁，不是共享 Signal Schema 的全局权限政策。共享 `action` 仍能表达 SOP 中另经风险分类与人工确认的 start/stop/restart；KBD 保存门禁同时检查新 `action` 和历史 `command`，Agent KBD Handler 再次拒绝非 status，避免一条只读规则误伤 SOP 处置契约。

### 2. 候选记录过滤

文本取值共用以下唯一配置：

```json
{
  "rows": {
    "mode": "keywords",
    "scope": "same_record",
    "include": ["检测到IP", "冲突"],
    "include_mode": "all",
    "exclude": ["测试数据", "模拟冲突"],
    "exclude_mode": "any",
    "case_sensitive": true
  }
}
```

逐记录定义：

```text
include_ok = include 为空
             或 include_mode=all 且本记录包含全部 include
             或 include_mode=any 且本记录包含任一 include

exclude_hit = exclude 非空
              且 exclude_mode=any 时本记录包含任一 exclude
              或 exclude_mode=all 时本记录包含全部 exclude

selected = include_ok && !exclude_hit
```

默认作用域固定为 `same_record`。因此跨两行分别出现 A/B 不能满足 include AND。页面将包含关系与排除关系分两行显示：

```text
包含关系：全部满足（AND）/ 任一满足（OR）
排除关系：任一出现即排除（OR）/ 全部同时出现才排除（AND）
```

中英文逗号都是关键字内容；多个关键字统一按换行输入。

### 3. 三种取值方式

| 取值方式 | 精确定义 | 适用场景 |
|---|---|---|
| 完整行 | 对候选过滤后的记录保留整行/整块，不截列 | 日志证据、AI 后置摘取、状态原文 |
| 文本行列 | 在候选记录上按受控表头/列号提取字段 | df、ps、计数器、表格文本 |
| JSON 路径 | 在合法 JSON 上按受控点号/数组下标取节点 | formatter=json 的结构化输出 |

原始 stdout/stderr 仍属于执行证据，不等同于“完整行”业务取值。页面把旧“完整输出”改名为“完整行”，并允许在该模式直接配置候选关键字；不重复增加 keyword 字段。

### 4. 可选 AI 提取

AI 提取位于确定性取值之后，对 Match 与 Produce 使用同一约束：

- Prompt 只包含筛选后的候选完整行和专家 instruction；
- AI 返回字面量必须存在于引用候选行；
- Match 的 True/False 仍由 Predicate 决定，AI 值只作为附加结果；
- Produce 的 AI 值通过全部校验后，与其他变量一起原子写入变量池；任一变量失败时不部分写入。

### 5. Match 与 Produce

```text
Match   = Predicate(Extract(Filter(Execution output))) → True / False
Produce = Cast/AI(Extract(Filter(Execution output))) → Typed Value → Variable Pool
```

Match 支持 keyword、regex、state、threshold、delta、trend、exists。新页面不再让用户使用通用 expected/NOT 组合表达反义；每类 Predicate 后续以显式正反操作符演进。为保证历史 Revision 可运行，本 PR 仍兼容读取既有 `expected` 和 keyword `not`，新建值固定为正向语义，不做破坏性 Schema 删除。

### 6. 执行与处理状态

底层执行采用标准进程事实：

```text
stdout / stderr / exit_code / duration / truncated / exec_id
execution_status = succeeded | failed | timed_out | cancelled
processing_status = not_started | succeeded | failed
```

命令非零退出、SSH 未执行或超时必须 `error != null`，且不得把 `matched=false` 当作有效业务输出。只有执行成功后才进入 Filter/Extract/Predicate/AI；处理失败也不得写变量池。

### 7. qfk_log 有界性与下推

常规 qfk_log 至少满足一项：

- 非空 `rows.include`；
- 非空 request_id；
- 其他已登记的确定性有界选择器。

exclude 单独存在不构成有界性，因为它可能保留整份文件。`rows.include` 是持久化的唯一过滤事实；编译器可把 include 粗筛下推为 aCLI `-k/-E`，Bridge 按 include/exclude 关系逐行过滤，Agent Extractor 再按相同 `same_record` 语义复核。下推只是性能优化，不是最终真相源。

## 兼容迁移

1. 新增 `exclude_mode`；缺失时按历史行为默认为 `any`。
2. `scope` 缺失时按 `same_record`；当前只允许该值。
3. 历史 Matcher 的 `expected/not` 继续读取；新 UI 不再鼓励生成新的通用取反组合。
4. 历史 qfk_service `resource_keyword/command` 在写边界和运行时归一为 `service/action`；新保存使用规范字段。
5. timeout 只改变新建/缺省值为 60，显式历史值不迁移。
6. 不新增数据库表或列；Signal v2 JSON Schema 与生成产物同步升级。

## 为什么不选其他方案

- 不在每个 QFK 输入区都增加 keyword：这会重复输出过滤事实，并使 qfk_system 出现伪命令参数。
- 不把“完整行”解释为无界 stdout：大输出会破坏传输、内存和 AI 上下文边界。
- 不用逗号分隔多关键字：日志字面量本身常含逗号，自动拆分不可逆；换行是明确的集合编辑协议。
- 不让 aCLI 的 OR 粗筛承担 AND 判定：粗筛只能缩小结果，最终必须由平台在同一记录上验证。
- 不让专家或 AI 写自由 Shell 管道：可执行文本无法可靠审计、转义和跨版本复现；受控 Extract 足以表达所需取值。
- 不把命令失败归为 Match False：两者的证据含义相反，会制造假阴性或在 NOT 条件下制造假阳性。
- 不一次性删除所有历史字段：不可变 Revision 是运行事实，破坏性删除会让已发布 KBD 无法回放。

## 四类完整验收矩阵

| 工具输入 | 输出模式 | 取值配置 | 完整场景 |
|---|---|---|---|
| qfk_log | Produce | 完整行 + include AND + exclude OR + AI | 同一行含“检测到IP”和“冲突”、排除模拟数据，AI 提取第一个 IP 并原子写入 `DUP_IP` |
| qfk_system | Match | 文本表格列 + threshold | 编译 `df -P /sf/log`，按表头提取 Use%，阈值命中返回 True |
| qfk_service | Match | 完整行 + state | 只允许编译 status，完整状态行取值后精确匹配 running |
| qfk_vm | Produce | JSON 路径 | 编译只读 VM 查询，从 formatter JSON 提取 VM ID 并写入 `VM_ID` |

每一项至少覆盖：Schema 保存校验 → Signal 运行时转换 → Handler 命令编译 → Fake Executor 的 stdout/stderr/exit_code → Filter/Extract/Predicate 或 AI → 最终布尔值或变量池。

## 影响范围

- shared：acquirer args、Signal v2 Schema 生成器与语义校验；
- kb-service：qfk_log 有界保存门禁、服务只读门禁与契约测试；
- agent-service：同记录过滤、qfk_log 下推派生、服务 status 纵深防御、执行状态；
- conversation-service / terminal_bridge / customer：`exclude_mode` 协议和边缘逐行过滤；
- Admin UI：完整行、包含/排除独立关系、服务只读动作与默认 60 秒；
- docs/verify：四类完整链路验收记录。

## 验收标准

- KBD27736 的 `qfk_log Produce + rows.include + AI` 可保存，不要求伪造 resource_keyword；
- include AND 只在同一记录中成立，跨行 A/B 不成立；
- include 与 exclude 同时配置时必须同时满足 `include_ok && !exclude_hit`；
- exclude_mode=all/any 在 Admin、Agent、Customer 和 Bridge 语义一致；
- 完整行支持候选过滤且不显示列配置；文本行列和 JSON 路径保持可用；
- qfk_service 新配置与运行时只允许 status；历史只读配置继续兼容；
- 命令失败/超时与业务 False 可区分，失败不进入变量池；
- 四类完整验收矩阵全部自动化通过；
- Schema 生成幂等、后端测试、Admin/Customer 构建、Go 测试和文档治理通过。
