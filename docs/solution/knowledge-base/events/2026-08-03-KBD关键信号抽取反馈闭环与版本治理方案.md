# KBD 关键信号抽取反馈闭环与版本治理方案

## 背景与需求

KBD30880 重抽后，页面在专家没有编辑的情况下显示“相对 AI Proposal 修改 36 项”。现场 revision 时间线证明 `36` 是一次 AI Proposal 相对旧 Proposal 的深度 JSON Diff，包含信号、Prompt 指纹、工具契约和 verification contract 等技术字段；第二次重抽后页面又未刷新 revision 接口，因此继续显示旧值。

同一轮抽取还产生质量回归：历史 Proposal 能识别失败任务 `qkv_task`，新 Proposal 却只产生两个 `qfk_system`，其中一条把 `/sf/cfg/gpu_info.ini` 全文产出为 `GPU_INFO_CONTENT`，没有任何下游信号消费；模型还显式写入 `timeout=10`，绕过了共享 120 秒缺省值。

需求不仅是修正一个数字或一个案例，而是恢复最初的学习闭环：准确区分 AI→AI 迭代与 AI→Expert 监督，并使模型回归可以被长期定位、筛选和复用。

## 方案（WHAT）

### 1. 三层状态模型

采用“当前状态、不可变血缘、数据集”三层模型：

```text
当前状态层
  latest_proposal_revision_id → 当前 AI Proposal
  working_revision_id         → 当前 Expert working（可为空）
  dynamic_resource_active     → Agent 当前生效版

不可变血缘层
  kbd_revision 完整 payload 快照
  Proposal / Expert parent 链
  baseline_proposal_revision_id 显式监督基线

数据集层
  从完成审核的 Proposal→Expert 配对生成评估候选
  working/opened/saved 中间稿默认不进入评估
  后续通过冻结 manifest 形成 Silver/Gold 数据集
```

专家主页面只呈现当前状态；历史默认不在主路径平铺。后台不删除有学习价值的历史。

### 2. 完整快照是权威，Diff 是派生数据

`kbd_revision.payload_json` 继续保存完整规范化快照。Diff 根据两份快照按需计算：

- 完整快照可以独立恢复、校验和回滚；
- JSON Patch 链会受中间损坏、Schema 演进、列表排序和 signal ID 变化影响；
- PostgreSQL JSONB/TOAST 对当前数据规模足够，图片与执行输出只保存引用，不复制大对象；
- 页面 Diff、统计数和训练特征都是派生结果，不能成为唯一事实源。

### 3. 显式 Proposal/Expert 配对

`kbd_revision` 新增：

```text
baseline_proposal_revision_id
```

语义：该 Expert Revision 明确审核的 AI Proposal。新 Expert 创建时沿直接 parent 链冻结基线；历史数据由迁移沿 parent 链回填。读取兼容顺序为：

1. 优先使用显式 `baseline_proposal_revision_id`；
2. 仅对迁移前或不完整夹具沿 parent 链回溯；
3. 不允许使用 history 顺序或当前 latest proposal 猜测。

相同 Expert payload 若基于不同 Proposal，仍是不同监督样本，幂等复用必须同时匹配 baseline。

### 4. 专家修改统计

审核接口返回独立摘要：

```json
{
  "status": "no_expert_draft | unchanged | modified",
  "proposal_revision_id": 44,
  "expert_revision_id": 46,
  "changed_signal_count": 2,
  "added_signal_ids": [],
  "removed_signal_ids": [],
  "modified_signal_ids": []
}
```

只比较 `signals_json.signals`，并以稳定 `signal.id` 为身份：新增、删除、修改各计一条；同一信号多个字段变化只计一条。无当前 Expert 时返回 0；发布后如 approved/published Expert 仍绑定当前 Proposal，则它仍是当前专家版本并参与统计。新一轮重抽切换 Proposal 后，旧 Expert 不得跨基线冒充当前版本。

前端显示：

```text
当前 AI Proposal
专家修改：0 条关键信号
```

重抽成功后同时刷新 KBD 详情、revision 状态和当前候选校验。

### 5. 评估导出只选择稳定配对

`evaluation-export` 不再选择 history 中第一份 Proposal，也不再遍历所有 Expert 中间稿作为独立目标。默认只导出：

- `review_metadata.review_state=approved`；或
- 兼容旧数据的 `origin=admin_review/admin_maintenance_publish`。

每个样本使用其显式 Proposal baseline，并返回 `diff_from_proposal`。工作稿仍保留审计血缘，但不默认进入评估。

“可评估”只代表形成了稳定 Proposal→Expert 配对，不代表可信身份、Expert Gold、Evidence Replay 或真实客户执行已经完成。

### 6. 版本保留与后续 GC 策略

长期保留：

- 被专家审核的 Proposal 基线；
- approved/published Expert Revision；
- 被 Agent 实际发布或消费的版本；
- 被 Bad Case、事故、评估集或训练集引用的版本；
- 具有明确专家原因码或用于 Prompt/模型回归比较的版本。

可限期保留：

- 未被查看且已被替代的 Proposal；
- 未提交或放弃的中间工作稿；
- 无新 checksum 的技术重试；
- 有独立敏感数据保留期的 raw response/artifact。

当前只实现 checksum 去重、明确 head 和评估筛选，不在本轮执行物理 GC。未来 GC 必须同时满足：不是 head、无 parent/child 依赖、无发布/运行/数据集/Bad Case 引用、达到保留期，并留下删除审计。

### 7. KBD30880 抽取质量修复

Prompt v1.8 增加最高优先级规则：

- 失败虚拟机任务且后续需要 HOST/VM 时，先生成 `qkv_task` producer；
- QFK producer 的每个产出变量必须至少被一个其他下游 signal `requires`；
- 配置文件字段的存在、缺失或状态直接生成独立 matcher；
- 正常参考截图不能被转换为故障主机必须命中的远程事实；
- QKV/QFK 默认显式写 `timeout=120`；
- evidence 使用多图时 `source_refs` 必须完整。

确定性后处理增加第二道门禁：

- 自动生成信号缺 timeout 或使用历史默认 10/30 时归一为 120；
- 拒绝无下游消费者的 QFK producer，并保留 rejected candidate 原文和原因；
- `/sf/cfg` 安全配置读取规范为 `qfk_system command="cat" + command_args=[path]`，禁止产生 `resource_keyword`；
- 不按 KBD ID 编写特判。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 第一性原理

持续优化模型需要同时保留 Source、exact Model/Prompt/Tool Contract、原始 Proposal、专家目标和运行 outcome。缺少 Proposal 历史无法识别回归；缺少稳定 Expert 配对无法构造监督；缺少 exact runtime revision 无法判断是知识错误还是执行能力错误。

### 对抗性审查

| 方案 | 优点 | 主要失败模式 | 结论 |
|------|------|-------------|------|
| 只留最新 AI + 最新 Expert | 简单、低存储 | 删除模型回归证据；无法比较 Prompt/模型；破坏审计和训练血缘 | 拒绝作为后台策略，只用于页面视图 |
| 所有 revision 永久保留并直接训练 | 信息最大化 | 自动保存、重试、半成品和 AI→AI 差异污染标签；同 KBD 被重复加权 | 拒绝直接训练；可作为原始血缘层 |
| 当前 head + 不可变里程碑 + 筛选数据集 | 当前业务简单，同时保持回归、审计和训练能力 | 需要明确配对、生命周期筛选和后续保留治理 | 采用 |

### 业界范式映射

- 不可变 revision + head pointer：对应数据版本和模型血缘常用模式；
- 完整 snapshot + 派生 Diff：避免长 Patch 链的恢复脆弱性；
- Bronze/Silver/Gold 分层：原始生成尝试、完成审核配对、可信 Gold 分开；
- Champion/Challenger：AI→AI 比较与 AI→Expert 监督分开统计；
- dataset manifest：训练集冻结后按 revision/checksum 引用，不直接扫描在线业务表；
- grouped split：未来训练/验证/测试按 support/source 分组，避免同一 KBD 不同 revision 泄漏。

## 影响范围

- 数据库：`kbd_revision.baseline_proposal_revision_id`、历史回填、索引和外键；
- KB Service：revision 创建、统计、评估导出和抽取后处理；
- Admin UI：专家修改语义与重抽后状态刷新；
- Prompt：seed 与已部署数据迁移同步升级至 v1.8；
- 测试：基线解析、评估候选、统计、dead producer、timeout、Prompt 契约和前端构建；
- 文档：知识库、数据库、接口、管理台和 Agent 现行文档同步更新。

## 验收标准

1. KBD30880 在专家未修改时显示 0，不再显示 AI→AI 的 36；
2. 同一 signal 多字段变化只计一条；
3. Expert 明确绑定真实 Proposal，重抽不改变旧监督配对；
4. evaluation export 不导出 working 中间稿，不用首个 Proposal 猜基线；
5. 无消费者 QFK producer 被拒绝并可审计；
6. 自动抽取的缺失/历史默认 timeout 归一为 120；
7. `/sf/cfg` 读取不再产生 `qfk_system.resource_keyword`；
8. Prompt/seed/data migration 契约一致且无非法 format placeholder；
9. 不删除历史 revision，不将未认证审核冒充 Expert Gold；
10. 后端、前端、数据库和文档治理检查通过。
