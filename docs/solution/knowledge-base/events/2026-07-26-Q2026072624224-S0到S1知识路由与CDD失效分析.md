# Q2026072624224：S0 到 S1 知识路由与 CDD 失效分析

## 1. 文档目的

本文归档工单 `Q2026072624224` 的现场证据、分析过程、代码调用链、数据库状态和最终结论，重点回答以下问题：

1. S0 已确认叶子故障分类后，S1 为什么仍使用客户模糊描述重新检索。
2. `human_escalation` 是否真的执行了人工升级。
3. KBD 检索为什么调用 `/embeddings`，以及 404 的直接原因。
4. FTS 是什么，为什么再次返回 0 篇 KBD。
5. `/api/kb/route`、embedding、FTS 在目标架构中应承担什么职责。
6. 如何从系统结构上禁止 Agent 虚构命令、结果和根因。

本文是只读调查结果。调查期间没有修改代码、数据库或 k3s 运行环境。

## 2. 核心结论

S0 的正确职责是把客户模糊描述转换为经确认的叶子故障分类。S1 必须把该分类作为知识候选资格的硬边界，完整加载分类下的 SOP 和全部已发布 KBD；自动执行能力通过独立的 `executable` 状态表达，不能让不可执行 KBD 从清单中消失。

当前实现偏离了这一设计：S1 虽然收到 `category_id=虚拟机-003`，却又从首条客户主诉构造 `user_query=虚拟机有异常`，依次执行 `/api/kb/route`、embedding 和 FTS。语义检索结果被错误地用作分类内知识的准入门禁，最终过滤掉了分类下真实存在且与现场故障吻合的 KBD 27123。

当检索返回空时，系统进入 `_process_fallback_mode()`，允许模型自由生成文本。该路径没有执行工具，也没有形成证据，却可以输出命令、命令结果和根因。这是本次大规模幻觉的直接出口。

## 3. 分析方法与证据来源

本次调查按照“运行状态 -> 日志时间线 -> 数据库事实 -> 源码控制流 -> 结论一致性”的顺序进行，避免只根据页面文本推断后端行为。

证据来源包括：

- k3s `hci-dev` 命名空间内 `agent-service`、`kb-service` 运行日志。
- PostgreSQL 中 `conversation`、`kbd_entry`、`sop_document`、`tool_result`、`diagnostic_item`、`terminal_operation`、`claim_evidence_link` 表。
- `InvestigationAgent`、KBD route、KBD search、embedding 和 CDD 实现源码。
- 工单页面时间线及工单 `Q2026072624224` 的会话数据。

证据判断遵循以下规则：

- 日志中的“开始执行”不能替代 `tool_result` 或终端执行记录。
- 模型输出文本不能作为系统状态或命令结果证据。
- KBD 被检索到只代表候选，不代表根因命中。
- 工具调用成功不等于 matcher 通过，更不等于根因成立。

## 6. 六项问题逐项分析

### 6.1 S0 已确认分类，S1 为什么仍调用 `/api/kb/route`

`InvestigationAgent.process()` 已明确接收 S0 输出的 `category_id`，但在 `investigation_agent.py:182` 又调用 `_build_retrieval_query(messages)`，从首条有效用户消息提取查询文本；随后在 `investigation_agent.py:225` 调用 `route_by_category(category_code, query, top_k=3)`。

`/api/kb/route` 在 `backend/kb-service/app/routes/route.py` 中执行：

1. 分类内 SOP 查询。
2. 分类内 KBD + FTS 查询。
3. 都为空时返回 `human_escalation`。

这里混淆了两个本质不同的问题：

- S0 回答“客户问题属于哪个故障分类”。
- S1 应回答“该分类下有哪些可执行知识，以及现场信号支持哪一篇”。

当前代码让客户最初的模糊描述再次决定分类内 KBD 是否有资格进入候选集，相当于让低信息量文本推翻已经确认的结构化分类。该实现与原设计严重偏离。

### 6.2 `human_escalation` 是否真的升级人工

没有。

`route.py:184` 只是返回：

```json
{
  "track": "human_escalation",
  "category_id": "虚拟机-003",
  "results": []
}
```

InvestigationAgent 只对 `track == "sop"` 存在实际处理分支。对 `human_escalation` 没有发出 `AgentEscalation`、没有创建升级记录、没有修改工单状态，也没有产生前端交互事件，而是继续执行 KBD search 和 fallback。

所以这不是“人工升级失败”，而是“从未尝试人工升级”。`human_escalation` 只是一个命名错误的检索空结果标签。

### 6.3 为什么调用 embedding，为什么返回 404

调用 embedding 的设计意图是通用 RAG：把用户描述转换为向量，在分类内对 KBD 做相似度排序。

现场配置为：

```text
LLM_BASE_URL=https://coding.dashscope.aliyuncs.com/v1
LLM_EMBEDDING_MODEL=embedding-3
```

`backend/kb-service/app/services/embedding.py:111` 将 Base URL 拼接为：

```text
https://coding.dashscope.aliyuncs.com/v1/embeddings
```

现场 HTTP 响应为 404，说明当前 Coding/Chat 网关没有提供代码所期望的 `/embeddings` 路由。这不是 KBD 内容问题，而是 provider 能力与配置契约不一致。

即使 provider 恢复，KBD 27123 的 embedding provenance 三个字段均为空，当前向量 SQL 的 `embedding_model = 当前模型` 门禁仍可能将它排除。

### 6.4 FTS 是什么，为什么返回 0

FTS 是 PostgreSQL Full Text Search。当前实现先使用 jieba 对中文分词，再通过 `tsvector`、`plainto_tsquery` 和 `tsv @@ query` 做全文匹配。

本次查询被解析为：

```text
'虚拟机' & '有' & '异常'
```

`&` 是 AND 语义，要求 KBD 索引同时包含三个词。KBD 27123 的 `tsv` 对该表达式计算结果为 `false`，因此返回 0。

FTS 的行为本身符合代码定义；错误在于系统把这个查询结果当成分类内 KBD 的资格判定。客户说“虚拟机有异常”，不能推导出分类下“虚拟机开机失败”案例不存在。

### 6.5 route、embedding、FTS 是否多余

在 S0 已确认分类后的正确性主链路上：

| 能力 | 正确定位 | 是否允许过滤分类内 KBD |
|---|---|---|
| 当前 `/api/kb/route` | 应停止被 S1 调用；保留兼容期后废弃 | 否 |
| embedding | 分类内 KBD 数量很大时的可选调度排序 | 否 |
| FTS | 管理端、全局搜索或可选调度排序 | 否 |
| category inventory API | 按分类返回全部已发布 SOP/KBD | 是主入口，但必须完整返回 |

因此，不是所有“检索技术”都要从平台删除，而是必须退出诊断正确性的准入路径。分类成员资格由发布状态和 `category_id` 决定，不能由 query similarity 决定。

### 6.6 如何严格禁止虚构

Prompt 只能降低概率，不能形成安全边界。严格禁止虚构必须依赖执行权限分离：

- 模型只能选择 `kbd_revision + signal_id`，不能提供自由命令。
- 服务端从不可变 KBD revision 编译工具和参数。
- 未注册工具、未解析变量、KBD 外命令在执行前拒绝。
- 每次执行必须生成 `exec_id`、输入哈希、实际输出和输出哈希。
- matcher 必须对实际输出做确定性求值，产生 `PASS/FAIL/UNKNOWN/ERROR`。
- 根因只能来自已确认 KBD 的原始根因字段，并关联证据 ID。
- 没有真实执行事件时，UI 只能显示“未执行”或“证据不足”。
- 无 KBD 时不能进入自由诊断 fallback，只能补充信息或显式升级人工。

## 7. CDD 实现中的进一步缺陷

本次问题暴露的不只是上游召回缺陷。`kbd_differential.py` 还存在以下结论级和算法级问题。

### 7.1 结论级缺陷

1. `is_definitive = len(remaining) == 1`：单候选只是候选集合大小为 1，不代表必要信号已经通过。
2. 只要 `remaining` 非空，就写入 S4 `root_cause`，并把状态设为 `confirmed`。
3. 报告把任意 `error is None` 的工具输出显示为成功证据，没有检查该步骤是否支持当前 KBD。
4. 候选相似度被写成“概率”，但向量相似度不是根因发生概率。
5. matcher 未通过、信号未执行、证据为空时，仍可能输出 KBD 的根因和解决方案。

### 7.2 算法理论错误

1. `_pick_best_step()` 选择“覆盖 KBD 数最多的工具名”，覆盖率不等于区分度。所有 KBD 都有的同一检查往往信息增益为 0。
2. 算法以 `tool_name` 去重，混淆了工具类型和信号身份。同一个 `qfk_system` 可以对应不同命令、参数和 matcher，不能视为同一步。
3. `_get_representative_step()` 任取第一个候选的参数模板代表其他候选，可能执行错误目标或错误命令。
4. `EARLY_STOP_THRESHOLD=2` 导致候选数小于等于 2 时不进入差分循环。
5. `match_ids` 为空时不淘汰候选，无法区分“有效负证据”和“执行错误/未知”。
6. LLM matcher 失败时默认所有候选为 True，会把未知误写成支持。
7. 最终停止条件是候选数量，而不是必要证据是否闭合。

### 7.3 执行契约未闭环

1. QKV/QFK 调用传入 `exec_id=None`，计划、执行和证据无法形成稳定关联。
2. 生产者信号静默执行，失败只写日志，后续仍可能携带未解析占位符继续执行。
3. 占位符解析失败时保留 `{{VAR}}` 原文，而不是阻断计划。
4. `diagnostic_item` 以“无异常”作为 `confirmed`，没有绑定 matcher 结果。
5. `claim_evidence_link` 不是 S4 的强制前置条件。
6. Agent API 在 `backend/agent-service/app/routes/agent.py:140` 主动过滤 `tool_call/tool_result`，真实执行对页面不可见。

## 8. 根因分层

### 8.1 架构根因

把“语义检索相关性”错误地放在“分类内知识资格”之前，没有将 S0 的确认结果定义为后续阶段的权威输入。

### 8.2 控制流根因

知识检索为空后进入自由文本 fallback，而不是进入“证据不足/人工升级”的受控状态。

### 8.3 算法根因

CDD 使用覆盖频率代替信息增益，使用候选数量代替证据充分性，并将 UNKNOWN 隐式折叠为保留或成功。

### 8.4 契约根因

KBD revision、signal plan、exec_id、tool result、matcher evaluation、evidence link 和 conclusion 之间没有强制的一对一链路。

### 8.5 呈现根因

真实工具事件被过滤，模型文本却可以直接显示，导致用户无法区分“系统执行事实”和“模型叙述”。

## 9. 本工单的合法结论

根据当前证据，只能得出以下结论：

1. S0 已正确确认 `虚拟机-003 / 虚拟机开机失败`。
2. 分类下没有已发布 SOP。
3. 分类下存在且仅存在一篇已发布 KBD：27123。
4. KBD 27123 与工单中的“虚拟机镜像忙”现象高度一致，应当进入候选集。
5. KBD 27123 的三条关键信号没有执行，所以不能确认其根因。
6. `ClwDRDBClient` 只能视为 KBD 27123 描述的待验证假设，不能视为本工单现场根因。

## 10. 后续设计基线

本次复盘产生以下不可违背的设计基线：

1. S0 经确认的分类是后续知识范围的权威来源。
2. 分类内全部已发布 KBD 必须完整进入候选集。
3. embedding/FTS 只能排序，不能执行准入过滤。
4. 单候选不等于根因确认。
5. UNKNOWN、ERROR、BLOCKED 不能作为支持证据。
6. 没有 `exec_id -> tool_result -> matcher -> evidence` 链路，不允许发布根因。
7. Agent 不拥有生成自由命令和自由根因的权限。
8. 无知识或证据不足必须显式升级，禁止自由推理伪装为诊断。

目标架构和实施方案见：[S0 分类驱动的 KBD 证据诊断与 CDD 闭环设计](2026-07-26-S0分类驱动的KBD证据诊断与CDD闭环设计.md)。

## 11. 修复实施结果（2026-07-26）

本复盘所列主链路缺陷已完成代码修复并部署到 `hci-dev`：

1. S1 使用已确认的 `虚拟机-003` 直接加载分类完整知识清单，不再使用客户原始模糊描述重新路由。
2. 实测清单为 0 篇 SOP、1 篇 KBD，KBD support_id 为 27123。
3. 27123 的 `sig_001` 从真实任务 907 获取 VM/HOST 并 PASS。
4. `sig_002` 和 `sig_003` 分别下发 KBD 定义的 `acli system lsof 4359974862144` 与 `acli system ps`。
5. 当前客户端未建立 SSH/terminal bridge，两条命令均超时并被标记 ERROR；系统未进入 S4、未输出 KBD 根因，转为显式人工升级。
6. 最终报告仍给出“参考案例 27123（未确认）”、原始链接、逐信号参数/outcome/exec_id，保证候选知识和失败证据可追溯。

正向 golden case 已证明三条 required signal 全部 PASS 时会输出参考案例 27123 及 KBD 原始根因/方案。运行环境的正向现场确认仍必须先满足浏览器侧 terminal_bridge + HCI SSH 的真实连接条件，禁止用 fixture 结果替代。
