# QKV 输出后处理设计与实现方案

## 1. 结论

平台不新增 `qfk_var` 或 `qkv_var` 采集信号。当前缺口位于 QKV 已经取得外部事实之后：现有 `qkv_alert`、`qkv_task`、`qkv_dialog` 可以把 JSON 记录投影成变量，但不能继续对这些输出做确定性判断、转换或抽取。

正确模型是同一 QKV Signal 内的可选后处理阶段：

```text
QKV acquisition
  -> produces：结构化字段投影
  -> output_processing：对投影值或原始输出继续处理
  -> assertion outcome / derived variable
  -> variable_pool 原子提交
```

这解决了图 1、图 2 暴露的重复配置问题：采集事实只配置一次，后处理不再伪装成另一个 Signal。

## 2. 第一性原理拆解

一个信号的不可再分事实只有四类：

1. **获取事实**：调用受控 QKV 原语取得告警、任务、弹框或结构化视觉结果。
2. **投影事实**：从每条 JSON 记录按 `produces[].path` 取出 `DESCRIPTION`、`HOST` 等输出变量。
3. **处理事实**：对已投影值执行有限白名单操作，例如取 JSON 路径、规范化字符串、比较百分数、从 description 抽取 VM 名称。
4. **提交事实**：只有类型和基数校验通过的派生值才能写入变量池；断言只产生结果，不写变量。

QFK 的 `match` / `produces[].extract` 不能直接替代第三步：QFK 的输入是它自己执行的命令 stdout/stderr，而 QKV 的输入是 JSON 记录和其中的文本字段。两者可以共享类型转换和证据校验库，但不能共享一份信号配置。

## 3. 配置契约

`output_processing` 位于同一个 Signal 的 `orchestrate` 下，是数组而不是新的 acquire 工具：

```json
{
  "id": "task-description-processing",
  "acquire": {
    "tool": "qkv_task",
    "args": {"keyword": "虚拟机无法启动", "limit": 100}
  },
  "orchestrate": {
    "produces": [
      {"name": "DESCRIPTION", "path": "description", "type": "string"}
    ],
    "output_processing": [
      {
        "id": "extract-vm-name",
        "mode": "derive",
        "input": "{{DESCRIPTION}}",
        "operation": "feature_extract",
        "target_variable": "VM_NAME",
        "value_type": "string",
        "cardinality": "exactly_one",
        "feature": "vm_name"
      },
      {
        "id": "assert-current-percent",
        "mode": "assert",
        "input": "{{DESCRIPTION}}",
        "operation": "compare",
        "value_type": "percentage",
        "operator": ">",
        "right": "90%",
        "cardinality": "exactly_one"
      }
    ]
  }
}
```

### 3.1 字段边界

- `produces` 只描述 QKV 返回记录如何投影；至少包含 `name`、`path`，可声明 `type`。
- `output_processing` 只引用当前记录已投影的变量或前一个处理单元产生的变量；不读取整个变量池。
- `mode=derive` 必须有 `target_variable`，恰好产生一个变量。
- `mode=assert` 不得有 `target_variable`，只产生 `PASS`、`FAIL`、`UNKNOWN` 或 `ERROR`。
- `id` 在同一 Signal 内唯一；处理单元按数组顺序执行，禁止循环和动态变量名。
- 默认 `scope=per_record`：QKV 多条记录逐条处理；需要唯一记录时显式使用 `cardinality=exactly_one`。

### 3.2 第一版白名单

| operation | 作用 | 必要参数 |
|---|---|---|
| `json_path` | 从对象输出中继续取嵌套字段（点号分隔；数组使用数字下标） | `path` |
| `trim` | 去除字符串两端空白 | 无 |
| `lower` / `upper` | 大小写归一化 | 无 |
| `split` | 按固定分隔符拆分 | `separator` |
| `compare` | 对 number/percentage/string 做确定性比较，只能用于 `mode=assert` | `operator`、`right` |
| `feature_extract` | 从半结构化 description 提取业务变量 | `feature` 或受控模板 |

任意 Shell、Python、正则脚本、表达式求值、动态字段名和 `{{*}}` 均禁止。

## 4. 执行和一致性

QKV 执行器先完成 acquisition 和 `produces` 投影，再在内存中建立当前记录上下文。处理单元的中间值只存在于本次记录上下文；全部 `derive` 结果通过类型、基数和冲突检查后，才一次性写入变量池。任意一个派生单元失败，禁止写入该单元及其后续单元的部分结果。

多记录语义必须显式：

- `per_record`：每条记录独立产生结果，变量值为数组或由 `exactly_one` 收敛为单值。
- `single`：要求整个 QKV 结果恰好一条记录，否则 `QKV_CARDINALITY_MISMATCH`。
- `all`：保留全部候选，仅允许数组类型；不能隐式挑第一条。

`compare` 是断言谓词，不是转换函数；若需要把字符串转换为数字或百分比，应在
`assert` 中声明 `value_type`，而不是用 `derive + compare` 生成一个看似布尔的变量。
`json_path` 只允许受控的点号路径和非负整数数组下标，不支持 jq、表达式或脚本。

相同 `acquire + args` 在未来可以共享一次真实采集；当前实现把 `produces + output_processing` 纳入去重键，只有完整契约完全相同才复用，确保不同 Signal 不会误用另一 Signal 的派生结果。

## 5. 真实场景

输入记录：

```text
主机（SVR_aCloud_670）的计算内存使用量（92.35 GB）超过阈值（92.34 GB），剩余：7.99 GB，使用率：92%
```

QKV 先产生：

```text
DESCRIPTION = 上述 description
```

后处理可以产生：

```text
CURRENT_PERCENT = 92
VM_NAME = ...
```

其中百分数比较只能在 `value_type=percentage` 下执行；多个百分数或没有稳定特征时返回基数错误/UNKNOWN，不得猜测目标值。

## 6. AI 兜底边界

AI 仅允许作为 `feature_extract` 在确定性特征没有稳定边界时的显式兜底：

```text
确定性提取失败
  -> 仅当配置 fallback=ai_extract 才调用模型
  -> 模型必须返回 evidence 引用和结构化值
  -> 值必须在原始 description 中逐字回查
  -> 类型/基数/范围校验通过后才可提交
```

AI 不参与 `compare`，不负责补造缺失字段，不读取整个变量池，也不能覆盖确定性提取结果。第一版实现不把真实模型调用放入 QKV 基础执行链路，先保留契约和离线评估接口。

## 7. 对抗性审查清单

| 攻击/边界 | 必须结果 |
|---|---|
| 同一 Signal 同时配置采集和后处理 | 合法；只有一条 acquisition，后处理在其后执行 |
| 新增 `qkv_var` 作为第二个 Signal | 设计门禁拒绝，避免重复采集/重复配置 |
| 多条任务记录却要求唯一 VM | `QKV_CARDINALITY_MISMATCH`，不选第一条 |
| `requires`/输入引用不存在 | 发布或加载阶段阻断 |
| 后处理包含 shell、脚本或动态变量名 | fail closed |
| 第一个 derive 成功、第二个 derive 失败 | 不写入本次后处理的任何派生结果 |
| AI 返回 evidence 中不存在的值 | 拒绝写入变量池并记录审计 |
| 相同 acquisition 被多个 Signal 复用 | 只共享原始采集，投影/后处理结果隔离 |

## 8. 可观测性

每个后处理单元沿用现有 `trace_id`、`session_id`、`exec_id`，并记录：Signal ID、processing ID、operation、输入来源哈希、结果状态、耗时、错误码和候选数量。原始 description 不复制到长期指标；完整证据仍由 QKV execution artifact 管理。

## 9. 验收标准

- 旧 QKV 配置无 `output_processing` 时行为完全不变。
- `DESCRIPTION -> feature_extract -> VM_NAME` 能通过确定性测试。
- `DESCRIPTION -> compare(percentage, >, 90%)` 能返回 PASS/FAIL/UNKNOWN。
- 多记录和重复派生变量均 fail closed。
- QKV、Signal Schema、管理接口和运行时测试全部通过。
- AI fallback 只有显式配置才可进入，基础 CI 不依赖在线模型。
