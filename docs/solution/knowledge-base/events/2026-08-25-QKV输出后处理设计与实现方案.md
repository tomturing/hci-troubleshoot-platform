# QKV 输出后处理复盘与 QFK 复用方案

## 结论

QKV 不需要一套独立的后处理语言。QKV 与 QFK 的真实边界只有输入不同：

| 信号 | 输入 | 已有能力 |
| --- | --- | --- |
| QFK | 命令的完整 stdout/stderr | `ValueExtract` 取值、Matcher 判断、AI 兜底、类型与基数校验 |
| QKV | qkv_alert/task 返回 JSON 中按 `produces[].path` 投影出的具体字段值 | 同一套判断、类型、基数和 AI 能力；额外只需要从 description 做业务特征提取和固定分割 |

因此，QKV 输出后处理必须是 QFK 既有处理单元的适配器，而不是新增 `processing_id`、`json_path`、`trim`、大小写转换、`zero_or_more` 等平行语义。

本方案使用第一性原理确认能力边界，并通过对抗性审查检查了重复建模、数组误用、AI 猜测和历史契约漂移问题。

## 1. 真实输入边界

qkv_alert/task 的完整返回是 JSON。例如：

```json
{
  "data": [{
    "description": "启动虚拟机（Server-IMG）失败，错误信息：虚拟机镜像忙，正在执行其他操作！\n",
    "host": "SVR_aCloud_670",
    "object_name": "Server-IMG",
    "errcode_tracing": "0x0100186F/0x010015BE",
    "vm": "4359974862144"
  }]
}
```

`produces` 已经完成 JSON 路径投影：

```json
"produces": [
  {"name": "DESCRIPTION", "path": "description"},
  {"name": "HOST", "path": "host"}
]
```

运行时上下文已经是：

```json
{"description": "...具体描述...", "host": "SVR_aCloud_670"}
```

所以后处理不能再次访问 JSON 路径，也不能把一个已经确定的字段重新当作“待清洗 JSON”处理。

## 2. 复用原则

QFK 已经是平台的单一事实源：

- `shared.signals.extractor.extract_value`：值类型转换和 `exactly_one/first/last/all` 基数选择；
- `shared.signals.matcher.evaluate_matcher`：keyword、regex、state、threshold、delta、trend、exists；
- `app.tools.qfk.ai_extractor.extract_ai_value`：候选行、用户 instruction、结构化结果、evidence 逐字回查和 fail-closed；
- `ValueExtractEditor` / `MatcherEditor`：QFK 管理台的成熟交互和提示。

QKV 只增加两个业务特有取值器：

- `feature`：从 description 的括号、字段标签、冒号、数字、字母数字组合等稳定特征中抽取变量；
- `split`：按明确分隔符拆分一个已投影字符串。

任何通用能力都必须复用 QFK，禁止在 QKV 重新实现。

## 3. 新契约

### 3.1 派生变量

```json
{
  "mode": "derive",
  "input": "{{DESCRIPTION}}",
  "name": "VM_NAME",
  "type": "string",
  "extract": {
    "type": "feature",
    "feature": "vm_name",
    "cardinality": "exactly_one"
  }
}
```

分割示例：

```json
{
  "mode": "derive",
  "input": "{{ERRCODE_TRACING}}",
  "name": "ERROR_CODE",
  "type": "array",
  "extract": {"type": "split", "separator": "/", "cardinality": "all"}
}
```

字段语义直接对应 QFK 产出变量：`name` 是变量名，`type` 是变量类型，`extract` 是第一步取值。QKV 的 feature/split 结果随后交给 QFK extractor 做类型和基数收敛。

### 3.2 断言判断

断言不再另造 `compare` 操作，而是直接嵌入 QFK Matcher：

```json
{
  "mode": "assert",
  "input": "{{PERCENT_CURRENT}}",
  "match": {
    "type": "threshold",
    "expected": true,
    "operator": ">",
    "value": 90
  }
}
```

所有 QFK Matcher 类型均可使用：关键字、正则、状态、数值阈值、首末差值、趋势和存在性。QKV 将已投影的具体值适配为 identity 文本，再调用同一 Matcher；PASS/FAIL/UNKNOWN 语义、evidence 和错误码保持一致。

### 3.3 AI 兜底

派生变量的 `extract.ai_extract.instruction` 与 QFK 完全相同，允许编辑人员提供受控的中文提取说明。例如：

```json
"ai_extract": {"instruction": "从描述中提取虚拟机名称，仅返回原文出现的名称"}
```

确定性 feature/split 失败后才调用 AI。AI 必须返回结构化值和 evidence 行，值必须逐字存在于输入原文，并通过类型、基数校验；否则 fail closed。AI 不能改变目标变量名、类型或判断结果。

## 4. 明确移除的重复设计

### 处理 ID

QFK 的“处理单元”不是配置字段，而是 UI 和执行流程的抽象。QKV 不新增 `processing_id`。处理单元由 `output_processing` 数组顺序定位，审计使用 Signal ID、变量名、Matcher 类型和 trace_id。这样与 QFK 的产出处理单元一致，避免用户填写没有业务意义的 `processing_1`。

### JSON 路径、trim、lower、upper

它们在 QKV 中没有真实用途：JSON 路径已经由 `produces[].path` 完成；QFK extractor 已经对文本行执行必要的空白处理；大小写敏感性由 QFK keyword/state 的既有 Matcher 语义决定。继续在 QKV 显示这些选项只会制造重复配置和错误暗示，因此新 UI 不提供。

### `zero_or_more`

QFK 的标准基数是 `exactly_one`、`first`、`last`、`all`。QKV 不再定义“零个或多个”这一新词。

`all` 的结果是一个数组，例如三个数值：

```json
{"type": "feature", "feature": "number", "cardinality": "all"}
```

得到 `[80, 92, 95]`。需要判断具体大小时，直接配置 QFK Matcher 的 `aggregation`：

```json
{
  "mode": "assert",
  "input": "{{DESCRIPTION}}",
  "match": {
    "type": "threshold",
    "aggregation": "max",
    "operator": ">",
    "value": 90,
    "expected": true
  }
}
```

`first_number`、`last_number`、`max`、`min`、`sum` 由 QFK Matcher 统一处理。若业务需要逐个元素执行命令，必须有明确的数组展开消费者；平台不能隐式取第一个值。

## 5. 管理台交互

QKV 编辑器与 QFK 采用同一信息架构：

```text
处理单元 N
├── 输入变量（已投影的具体值）
└── 第二步：派生变量 / 断言判断
```

派生模式只显示：变量名、变量类型、特征提取/分割、QFK 基数、可选 AI instruction。

断言模式只显示：QFK Matcher 类型及其参数。

不显示：处理 ID、JSON 路径、trim、lower、upper、QKV 私有 compare 表单、QKV 私有 AI fallback 下拉框。

## 6. 兼容和门禁

旧的 `id`、`operation`、`target_variable`、`value_type`、`zero_or_more` 载荷不作为新契约。服务端对历史载荷要么在迁移层显式转换为新形态，要么返回可操作的迁移错误；不能让新运行时继续同时维护两套语义。

发布门禁必须检查：

- `input` 只能引用 `produces` 或前序 derive 的变量；
- derive 的 `name` 不重复；
- QFK Matcher 字段完整且类型合法；
- AI instruction 长度和 evidence 规则满足 QFK 契约；
- hci-sim Bundle 保存规范化后的 processing 和派生变量集合；
- 同一 acquisition、不同 processing 仍是一个物理路由、多个逻辑消费者。

## 7. 对抗性审查结论

| 风险 | 处理 |
| --- | --- |
| QKV 再次实现 JSONPath | 禁止；JSON 已在 produces 完成 |
| QKV 与 QFK 比较结果漂移 | 统一调用 `evaluate_matcher` |
| 多值被静默取第一项 | 只允许显式 `first`；默认 `exactly_one` |
| AI 猜测不存在的值 | 复用 evidence 逐字回查，失败关闭 |
| UI 字段与真实能力不一致 | 隐藏 QKV 私有重复字段，沿用 QFK 术语 |
| hci-sim 与生产运行时语义不同 | Bundle 只保存契约，Agent 共享同一适配器执行 |
