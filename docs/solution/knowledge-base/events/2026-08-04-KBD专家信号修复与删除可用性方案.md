# KBD 专家信号修复与删除可用性方案

## 背景与需求

KBD30880 同时暴露了两个权威边界错误：Schema 错误被直接当专家文案，且删除意图被实现成“保存前端当前整份合并文档”。结果是专家不知道改哪里，也无法用删除从坏草稿中恢复。关联需求见 [KBD 专家信号修复与删除可用性需求](../../../requirement/events/2026-08-04-KBD专家信号修复与删除可用性需求.md)。

## 方案（WHAT）

1. 在共享 Signal Schema 增加 Matcher null 规范化：只删除当前 Matcher 类型的非必填 null；必填 null 原样交给校验器。
2. 将 `ValidationError` 转换为结构化专家问题：`signal_id/field_path/location/message/code/action`，保存、维护和发布共用。
3. KBD PATCH 增加互斥的 `delete_signal_id`。后端从数据库权威工作稿按稳定 ID 删除，重建 evidence policy、收敛 `minimum_should` 并执行 draft gate。
4. Admin UI 分离服务端权威文档与 `stagedSignalEdits/localSignalIds`。本地对象删除仅撤销；持久化对象删除只发稳定 ID；成功后保留其他本地草稿。
5. Candidate 在质量门禁后规范化可省略 null。写动作闭集检查 command 和 argv；顶层封闭只读命令的参数视为数据，非只读 wrapper/CLI 的明确状态子命令继续扫描。
6. state Matcher 与 keyword 一样要求字面 pattern 可从 evidence 追溯，阻止结构合法但运行时必然失真的状态值。

## 决策依据（WHY）

- 选择“按 Matcher 类型删除可省略 null”，因为 JSON `null` 与缺失不同，但 `exists` 根本不消费 pattern；全局删除 null 会掩盖 keyword/regex/state 的真实必填错误。
- 选择“后端按稳定 ID 删除”，因为删除是单对象意图，权威输入应是数据库工作稿；前端整份 PATCH 会把无关、未验证、未保存状态耦合到删除事务。
- 选择“结构化错误 + 前端定位”，因为错误字符串适合日志而非专家操作；稳定 ID 不受筛选和排序影响。
- 选择“闭集执行向量规则”，因为自由 Shell 风险推断误报不可控；只看 command 又会漏掉 argv 子命令和 wrapper 目标。

未选择的方案：

- 不在 UI 隐藏或改写所有 Schema 错误；这会失去字段级事实，且后端其他入口仍不一致。
- 不在删除前自动保存所有暂存编辑；这违反最小写入和用户明确意图。
- 不针对 KBD30880、33510 或具体 `sf_cli` 写 support_id/命令特例；同类模型变体会继续绕过。
- 不把所有 argv 中出现的写命令 basename 一律拦截；`ls /sf/bin/sfscp` 证明参数也可能只是只读数据。

## 影响范围

- 共享 Signal Schema 校验与 KBD Candidate 抽取；
- KBD draft/maintenance PATCH 和发布错误契约；
- Admin KBD 审核页的恢复、保存、删除与错误定位；
- KBD 写动作/Matcher 质量门禁；SOP 既有 solution 标注语义不变。

## 验收标准

满足需求文档全部验收项；后端目标/完整测试、Ruff、Schema 漂移、Admin 生产构建和 docs 治理全绿；第四批真实 Proposal revisions 连续且逐条结论可审计。
