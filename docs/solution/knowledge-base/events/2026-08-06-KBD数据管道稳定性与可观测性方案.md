# KBD 数据管道稳定性与可观测性方案

## 背景与需求

现行六阶段链路为 FETCH → IMPORT → {CLASSIFY ∥ VISION} → EXTRACT_SIGNALS → REVIEW_SIGNALS。CLASSIFY 与 VISION 在 IMPORT 后并行，EXTRACT_SIGNALS 严格等待两者成功；现场运行还发现图片级完成统计与 KBD 级进度可能不一致。

## 方案（WHAT）

### 1. 硬依赖与并发

```text
FETCH → IMPORT
             ├─ VISION ─────┐
             └─ CLASSIFY ────┼─→ EXTRACT_SIGNALS → REVIEW_SIGNALS
```

- VISION、CLASSIFY 都只依赖 IMPORT，并行执行。
- EXTRACT_SIGNALS 同时硬依赖 VISION 成功和 CLASSIFY 成功。Vision `needs_review`、部分失败、技术失败均不得进入 Signal 抽取。
- 低置信度分类仍可进入 Signal 抽取，但必须作为质量警告保留；如未来验证图片能改善分类，仅对低置信度案例触发一次补分类。
- CLASSIFY 读取 IMPORT 写入的 `title/problem_description/alert_info` 结构化字段，`content_md` 只作为呈现投影。

### 2. 案例级事实模型

图片级 `done/failed` 只用于描述图片处理；案例级状态由 `images_json` 的每个 seq 和 Evidence 质量聚合。API 返回的 `case_results` 与数据库聚合结果同时记录，若二者冲突则记录 `VISION_STATE_INCONSISTENT`，不得静默改写为普通失败。

阶段状态统一为 `pending/running/succeeded/warning/failed/skipped_existing/blocked_by_dependency/not_applicable`。依赖未满足的任务标记 `blocked_by_dependency`，幂等命中已有结果才标记 `skipped_existing`。

### 3. LLM 资源治理

kb-service 增加进程级共享 LLM Semaphore，VISION、CLASSIFY、EXTRACT_SIGNALS 共用；路由层关闭 SDK 内置重试，由共享治理器统一处理 429、5xx、连接错误和超时，遵守 Retry-After，使用 full jitter，鉴权/参数类 4xx 不重试。多副本的全局 QPS 仍以 Provider 配额和后续 Redis 限流器为准。

### 4. CLI 与日志

- 保留现有 `pipeline/fetch/import/vision/classify/extract-signals/audit` 非交互入口。
- 新增 `cli` 交互入口，危险操作需要 TTY 显式确认，非 TTY fail closed。
- 终端显示中文阶段摘要、完成/失败/警告/阻断、耗时和重试提示；`--json` 输出机器可读结果。
- 同时生成文本日志和 JSONL 排障日志，事件包含 run_id、trace_id、support_id、stage、job_id、error_code、retryable 等字段。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

- 选择并行 VISION/CLASSIFY：两者不存在硬技术依赖，串行会让分类覆盖率被 Vision 成功率支配。
- 保留 VISION→EXTRACT_SIGNALS 硬依赖：业务已确认截图包含关键信息，降级抽取会制造表面完成但质量不足的 Proposal。
- 选择结构化字段：并行时反向解析 `content_md` 会产生竞态，且内容投影不应反向成为事实源。
- 选择共享 Provider 舱壁：简单地把分类改成并发会与 Vision 争抢同一 endpoint，可能造成 429 和重试风暴。
- 不选择“所有阶段串行”：吞吐和故障隔离均差。
- 不选择“所有阶段无脑并发”：违反硬依赖并放大 Provider 限流。
- 不选择仅依赖 API 图片计数：图片级成功不能证明案例级 `images_json` 已完整持久化。

## 影响范围

- `data-pipeline/kbd/pipeline.py`、`progress.py`、`classifier.py`、`image_proc.py`、`extract_signals.py`、`run.py`。
- kb-service 分类、Signal 抽取和 Vision 运行时治理。
- 现行知识库设计、可观测性设计、知识库任务、README 冷启动入口。

## 验收标准

- 单测覆盖 DAG 分叉、双硬依赖交集、阻断状态和状态不一致事件。
- 20 KBD 正常/超时/429/部分图片失败/服务重启场景下，结果可恢复、可解释、无重复提交。
- P50/P95 总耗时、429、timeout、重试放大系数和各阶段覆盖率可从 JSONL/指标中统计。
