# 分类基线命名规范治理与叶子统一（解A 角色无关统一 ID）

> 唯一命名文法事实源：`backend/shared/utils/category_code.py`
> 唯一调用链标记：确定性迁移 `category_leaf_governance_v1`（`database/data-migrations/041_*.sql`）；重分类 `category_kbd_reclassify_v1`（`database/data-migrations/review_required/042_*.sql`，需人工签字）

## 1. 背景与根因

分类基线 `kb_category` 历史上混用三套 code 语义：域根 `{域}-L1`、叶子与部分分组 `{域}-L{级}-{序号}`、中间分组 `{域}-L{级}-{名称}`。由此产生三类持续问题：

- **角色与编码耦合**：`-L3-` 被误当成"叶子"的编码特征，但叶子/分组本质由树结构（是否有子节点）决定，与 code 无关。编码携带层级/角色信息导致跨级迁移、重排时编码集体失效。
- **分组泄漏到消费链路**：KBD/意图分类的候选目录曾把分组也作为可绑定项，导致工单绑到"跨集群迁移失败"这类大分组而非具体叶子，编排取值与推荐失准。
- **展示/导出/筛选三处不一致**：YAML 导出把全节点（含分组）落盘，回灌时被逐条当叶子解析 → 树被打平污染；筛选下拉扁平化后丢失分组上下文；选分组按精确 code 匹配返回空。

## 2. 解A：角色无关统一 ID 文法

| 节点角色 | code 形式 | 判定方式 |
|---|---|---|
| 域根（每域唯一） | `{域}-L1`（如 `虚拟机-L1`） | `parent_id IS NULL`，永不叶子 |
| 其余所有节点（叶子与分组一视同仁） | `{域}-{3 位补零序号}`（如 `虚拟机-017`） | 每域共享一个序号空间，新增按 `max(序号)+1` 自动分配 |

- **叶子 vs 分组**：纯由结构性 `NOT EXISTS (SELECT 1 FROM kb_category c2 WHERE c2.parent_id = c.id)` 判定，与 code 完全正交。分组仍可拥有 `{域}-{序号}` 形态的 code（角色无关）。
- **废弃**：`{域}-L{级}-{序号}`、`{域}-L{级}-{名称}`。
- **分组信息承载**：`parent_id` / `level` / `path_labels` / `name`，建树与展示从不解析 code。
- **新增/编辑约束**：`create` 缺 code 时 `next_node_code(domain, existing)` 自动分配；显式 code 走 `validate_code`（层级形式 / 名称形式分别定向纠错建议）；编辑态 code 不可改。

## 3. 分组信息在三处的"清晰、准确"展示

1. **分类基线页面**：`el-tree` 直接由 `parent_id` 建树（`useCategories.buildCategoryTree`），分组层级天然可见（原已满足）。
2. **KBD / SOP 筛选下拉**：由扁平 `el-select` 改为 **`el-tree-select`**（`node-key=code`，label=`{code}  {name}`，`filterable`）；点选**分组**时后端 `_resolve_category_subtree_codes` 用递归 CTE 按 `parent_id` 展开为"自身 + 全部后代 code"，KBD/SOP 列表以 `IN (子树)` 匹配 → 选分组即级联命中其子树叶子工单，杜绝"展示分组却筛出空"的误导。绑定/编辑下拉仍强制叶子（`leaf_only=true`）。
3. **YAML 导出**：`_generate_export_yaml` 改为 **leaf-only** —— 仅导出叶子，分组信息由每条叶子的 `path` 数组承载；`total` 为叶子数；头部注明"仅导出叶子 / 分组靠 path 承载"。与导入器（把每条 `categories` 当叶子、中间层从 path 前缀派生）形成闭合往返契约，消除分组被误导出→再导入当叶子→树被打平的污染。

## 4. 存量迁移

### 4.1 确定性迁移 `041`（`category_leaf_governance_v1`，自动应用）

只读 dry-run 对 live staging 计算，零撞号校验通过后由脚本生成 SQL，做无 AI 判断的手术：

| 处置 | 数量 | 说明 |
|---|---|---|
| purge 垃圾节点 | 6 | `E2E-*` / `semantic_e2e` / `semantic_route_e2e`（含其 kbd 引用置 NULL） |
| flatten 单子分组 | 5 | 提升唯一独子叶子、删除组（独子均为直接叶子，无 KBD 引用） |
| renumber 非合规 code | 114 | `{域}-L{级}-{序号/名称}` → `{域}-{序号}`（域上界 存储46/平台30/硬件45/网络23/虚拟机54） |
| 引用 remap | 131 | kbd/sop/conversation 随映射旧→新 |
| 引用置 NULL | 12 | 悬空会话 2 + E2E 引用 10 |
| 已合规叶子保留 | 2945 | 不动 |

- **外键处理**：`kbd_entry.category_id` 与 `sop_document.category_id` 上有 `REFERENCES kb_category(code) ON DELETE NO ACTION`（不可延迟）。迁移在同一事务内先 DROP 两个 FK、完成改名/remap/扁平化/删除后，按 `desired_schema` 原定义 re-ADD FK —— re-add 即自校验残留悬空。
- **结构重建**：按 `parent_id` 递归重建 `level` 与 `path_labels`，保证扁平化/上提后路径与层级自洽。
- **应用顺序**：`db-migrate.sh` Step1 先跑 data-migration 清洗数据，Step3 再由 atlas 依 `desired_schema.sql` 收敛 CHECK，二者天然有序。

### 4.2 重分类 `042`（`category_kbd_reclassify_v1`，**需人工签字后手工应用**）

159 条 distinct KBD 曾绑在多子分组上（共 225 引用行），属非法叶子绑定，且多子分组无法机械消歧 → 逐条 LLM 重分类。

- 引擎：集群内 `kb-service POST /api/kb/classify`（自带 LLM 凭据，**仅返回、不写库**）。
- 校验：推荐码必须为结构性叶子（非叶子/被删则从 top3 取首个合规叶子；仍无 → 转人工）。
- 翻译：推荐旧叶子码经 `041` 的 mapping 译为迁移后新码，保证 `042`（在 `041` 之后跑）命中已重命名的叶子。
- 产出：`review_required/kbd_reclassify_review.csv`（159 条全量清单，含置信、理由、当前/推荐码新旧）；`review_required/042_kbd_reclassify_off_groups.sql`（**仅对 158 条高置信合规叶子**生成 UPDATE，1 条 aSEC 代码缺陷案例无合规叶子推荐 → 仅入 CSV 待人工）。
- 落点保护：文件位于 `data-migrations/review_required/` 子目录，`migration-runner` 仅 glob 顶层 `*.sql`，故不被自动应用。

### 4.3 演练证据（live staging，事务内执行后 ROLLBACK，库零改动）

- 单跑 `041`：非合规 code=0、旧层级形式=0、E2E 残留=0；节点 328→317；`path_labels` 末元素≠name=0；kbd/sop/conversation 悬空=0。
- 合并跑 `041 + 042(自动段)`：FK 接受全部 158 推荐码；`category_id` 绑非叶子=**0**、`ai_category_id` 绑非叶子=**1**（唯一 needs_review，正确留人工）、悬空=0。
- 回滚后库恢复原状（节点 328 / E2E 6 / 旧形式 119）。

## 5. DB CHECK 约束

`database/desired_schema.sql` 的 `kb_category` 增加：

```sql
CONSTRAINT kb_category_code_format CHECK (
    code IS NULL OR code ~ '^[^-]+-L1$' OR code ~ '^[^-]+-[0-9]+$'
)
```

- 项目采用 atlas 声明式（`atlas schema apply --to desired_schema.sql`），desired_schema 为单一事实源；`atlas-migrations/` 目录非运行期依赖，故不额外加版本文件。
- CHECK 只约束 code 文法，**不约束叶子绑定**，因此与重分类解耦：CI 空库建表即带 CHECK（041 自然 no-op）；生产由 db-migrate 先 041 清洗、后 Step3 收敛 CHECK。
- 生产/CI 均无 kb_category 的 SQL 种子（运行期靠 YAML 导入，导入器已按解A 生成合规 code），CHECK 不会误伤种子。

## 6. 风险、回滚与应用顺序

1. 生产变更前建议备份（`kb_category` / `kbd_entry` / `sop_document` / `conversation`）。
2. `041` 幂等事务 + 内置 verify，任一断言失败即整体回滚。
3. 严格顺序：`041`（自动）→ atlas CHECK（自动，随后）→ 专家复核 CSV → `042`（人工手工 psql）→ 剩余 needs_review 工单人工归类。
4. `042` 只覆盖高置信合规叶子；needs_review 不自动改判。
