# KBD 人工复核标签事实模型纠偏方案

## 背景与需求

现场出现以下矛盾状态：KBD 是 `draft`，没有专家工作稿，Agent 未生效，当前内容是
AI Proposal，但普通 Signal 因 `review.require_human_confirm=false` 被显示为绿色
“已人工复核”。

根因是前端把“不需要运行时人工授权”错误解释成“已经发生人工复核”。用户要求将规则
收敛为一个简单原则：

> 先按现有 Signal 字段判断是否需要人工复核；不需要就不显示标签；需要时先显示
> “需人工复核”，该内容被专家审核保存后再变成“已人工复核”。

## 问题分析过程

当前逻辑读取：

```text
provenance.needs_review == true
OR review.require_human_confirm == true
```

二者任一成立，说明这条 Signal 需要人工复核。当前前端另外使用了两个错误推论：

```text
review.require_human_confirm == false
  → 已人工复核

KBD.status == published
  → 已人工复核
```

`false` 只表示“不要求额外授权”，`published` 只表示 KBD 生命周期，二者都不能证明专家
保存过当前内容。这就是未审核 AI Proposal 出现绿色标签的直接原因。

同时，只使用当前两个布尔值也不够：专家发布时系统可能归约这些待办字段，导致一条原本
“需人工复核”的 Signal 发布后标签直接消失。原始复核需求和专家保存事实必须由现有不可变
Proposal/Expert Revision 血缘派生，但不需要新增数据表或数据库字段。

## 方案（WHAT）

### 1. 唯一展示规则

```text
按现有逻辑不需要人工复核
  → 不显示标签

按现有逻辑需要人工复核 + 当前内容尚未被专家审核保存
  → 黄色“需人工复核”

按现有逻辑需要人工复核 + 当前内容已经被专家审核保存
  → 绿色“已人工复核”
```

对应三态：

| 派生状态 | 标签 |
|---|---|
| `not_required` | 不显示 |
| `needs_review` | 黄色“需人工复核” |
| `reviewed` | 绿色“已人工复核” |

普通、不需要人工复核的 Signal 即使已经随 KBD 发布，也不显示绿色标签。绿色只用于说明
“原本需要人工复核的待办已经由专家处理”。

### 2. 后端只读派生，不新增持久化数据

KBD 详情 API 顶层增加响应字段 `signal_review_facts`。这是读取时计算的 View Model：

```json
{
  "signal_review_facts": {
    "signal-001": {
      "status": "needs_review"
    },
    "signal-002": {
      "status": "reviewed"
    }
  }
}
```

没有条目或 `status=not_required` 的 Signal 不显示标签。第一版只返回 UI 必需的最小状态，
不增加原因码、审核人、Gold 或身份认证等与本问题无关的字段。

数据边界：

```text
新增数据库表：否
新增数据库列：否
新增 migration：否
修改 signals_json Schema：否
新增 API 只读派生字段：是
```

### 3. 派生方法

后端使用现有数据：

- 当前展示的 `signals_json.signals[]`；
- `latest_proposal_revision_id`；
- `working_revision_id`；
- 现有 Proposal/Expert Revision payload、parent 和 baseline；
- Expert Revision 的 actor/review state。

对每条当前 Signal：

1. 从当前 Signal 判断 `needs_review || require_human_confirm`；
2. 若专家发布时字段已经归约，则从该 Expert Revision 的直接父版本或 Proposal baseline
   恢复“这条 Signal 原本是否需要人工复核”；
3. 当前显示内容被一个专家保存的 Expert Revision 覆盖时，状态为 `reviewed`；
4. 需要复核但没有专家保存覆盖时，状态为 `needs_review`；
5. 原本不需要复核时，状态为 `not_required`；
6. 页面尚未保存的本地编辑和新增 Signal 不能继承旧绿色；仍按当前两个字段判断，需复核则
   显示黄色，否则不显示标签。

“专家保存覆盖”只比较当前显示的稳定 Signal ID 和内容；旧 Proposal 的 Expert Revision
不能覆盖重新抽取后的新内容。维护工作稿刚创建但尚未保存时，也不算专家已保存。

### 4. 前端只展示后端状态

前端删除现有以下推论：

```text
require_human_confirm=false → 已人工复核
published → 已人工复核
```

只按后端状态渲染：

```text
not_required / 无状态 → 不显示
needs_review          → 需人工复核
reviewed              → 已人工复核
```

若当前 Signal 是尚未提交的本地新增或编辑内容，即使服务端旧版本是 `reviewed`，页面也不继承
旧绿色；本地内容仍按当前两个字段显示黄色或无标签。保存成功并刷新详情后，才使用新的服务端
派生状态。

### 5. 场景结果

| 场景 | 结果 |
|---|---|
| AI Proposal，两个复核字段均为 false | 不显示标签 |
| AI Proposal，任一复核字段为 true | 需人工复核 |
| 上一行内容被专家审核保存 | 已人工复核 |
| 普通 Signal 随 KBD 被专家发布 | 不显示标签 |
| KBD 是 published，但 Signal 原本不需复核 | 不显示标签 |
| 重新抽取出需要复核的新 Proposal | 需人工复核 |
| 旧 Expert Revision 只覆盖旧 Proposal | 新 Proposal 不继承绿色 |
| 页面本地编辑尚未保存，当前仍需复核 | 需人工复核，不继承旧绿色 |
| 页面本地编辑尚未保存，当前不需复核 | 不显示标签，不继承旧绿色 |

## 决策依据（WHY）

1. 标签只服务于一个待办：是否需要人工复核，以及这个待办是否已经完成。
2. 不需要复核的普通 Signal 不展示标签，避免把“无待办”误说成“已经人工复核”。
3. 专家保存事实由现有 Revision 提供，既不相信前端猜测，也不新增可漂移的数据库布尔值。
4. Proposal/Expert Revision 已经保存发布前后的内容，可以恢复发布时被归约掉的原始复核需求。
5. Candidate 三态、机器执行门禁、可信身份和 Expert Gold 是其他问题，不进入本标签算法。

不采用以下方案：

- 不将所有 AI Proposal 一律显示“需人工复核”；只按现有两个字段判断。
- 不将所有 Expert/Published Signal 一律显示“已人工复核”；普通 Signal 不显示标签。
- 不新增 `is_expert_reviewed` 数据库列；审核事实继续使用现有 Revision。
- 不在前端继续增加 published、Agent active 等兼容分支；后端派生，前端展示。

## 影响范围

- kb-service：从现有 Revision 派生 `signal_review_facts`，随 KBD 详情返回；
- Admin UI：删除错误推论，按三态展示；
- 测试：覆盖无标签、黄色、专家保存后绿色及新 Proposal 不继承旧绿色；
- 现行全量文档：更新知识库设计、管理台设计和接口设计；
- 完成后更新 README 第一屏和验证事件。

## 验收标准

- 截图中的普通 AI Proposal 不再显示绿色，因它按现有字段不需要复核，所以不显示标签；
- `needs_review=true` 或 `require_human_confirm=true` 的 AI Proposal 显示“需人工复核”；
- 同一需要复核的当前内容被专家审核保存后显示“已人工复核”；
- 普通 Signal 无论是否发布都不显示复核标签；
- published、Agent active 和 `require_human_confirm=false` 不能单独产生绿色标签；
- 新 Proposal 不继承旧 Proposal 的专家保存状态；
- 本地未保存编辑不显示旧的绿色状态；
- 不新增表、列、migration，不修改 Signal v2 持久化 Schema；
- 后端、前端、文档治理和 CI 检查通过。
