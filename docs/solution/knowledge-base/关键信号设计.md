## 1. 文档定位

本文是 `qfk_var` 的现行方案与实现契约，描述它为什么存在、解决什么问题、如何配置、如何运行以及如何验收。当前已落地 Phase 1-3：共享确定性内核、Agent `assert/derive` 运行时、Schema/能力发现/数据库投影及管理端配置；Phase 4 的回放灰度与更广泛模板覆盖仍按本文验收标准持续扩展。

`qfk_var` 面向 KBD 的一个缺口：变量已经存在于变量池之后，KBD 还需要继续对这些变量进行确定性处理。例如：

```text
CPU_USAGE=91%              -> 解析百分比 -> 判断是否大于 90%
TASK_RECORD.object_name    -> 字段取值   -> 产出 VM_NAME
ALERT_DESCRIPTION_ZH       -> 四层 description 处理流水线 -> 产出 CURRENT_PERCENT
VM_INFO_JSON               -> JSON 路径  -> 产出 VM_ID
HOST + VM_NAME             -> 拼接       -> 产出 TARGET
```

真实 HCI 样本及其统计见[真实 HCI description 样本分析](events/2026-08-24-qfk_var真实HCI描述样本分析.md)。description 多为机器生成的半结构化模板文本。普通配置人员不应手写通用正则，而应选择输入变量和目标变量；运行时固定执行四层流水线，只有第四层在前三层无法确定时才启用受控 AI 兜底。

本文不把 `qfk_var` 设计成任意脚本工具，也不把变量池当成一个可以被隐式遍历和修改的全局对象。它是一个**单输出、显式多输入、确定性、可审计**的 KBD 信号节点。

## 2. 第一性原理与对抗性审查

### 2.1 第一性原理：变量池计算的最小闭环

变量池中的每个值都是一个事实记录，而不是一段可以任意执行的代码。一个可靠的变量处理节点只能由以下最小元素组成：

```text
显式输入变量
  -> 输入快照
  -> 类型/单位解析
  -> 白名单操作
  -> 一个确定性结果
  -> 结果证据和可选变量写入
```

由此得到硬约束：

1. 输入必须通过 `requires` 显式声明，不能隐式读取整个变量池。
2. 确定性处理必须是纯的、可重复的和可回放的，不执行 Shell；可选 AI 兜底必须隔离在确定性失败之后，且不能改变断言结论，只能返回经逐字回查的候选字面量。
3. 一个节点只产生一个业务结果；多步处理通过多个节点组成 DAG。
4. 缺失、无法解析和多匹配不能悄悄变成 `false`、空字符串或第一个值。
5. 结果必须能够追溯到输入变量、表达式版本、变量池快照、`trace_id` 和 `execution_id`。

### 2.2 对抗性审查：最容易失败的方案

以下方案明确不采用：

| 方案 | 失败原因 | 处理方式 |
|---|---|---|
| 允许 `eval`/Python/JavaScript 表达式 | 任意代码执行、不可审计、版本漂移 | 只允许固定操作和固定字段 |
| 默认把整个变量池传给处理器 | 依赖不可见、敏感数据越权、结果不稳定 | 只读取 `requires` |
| 解析失败当成 `false` | 把未知误判为否定，可能错误排除根因 | 返回 `unknown` 或 `error` |
| 百分比按数值大小自动猜单位 | `0.91` 的语义不确定 | 必须显式声明 `percentage` 或 `ratio` |
| 正则多匹配默认取第一项 | 日志顺序变化会导致结论漂移 | 默认 `exactly_one` |
| 派生结果直接覆盖旧值 | 旧证据被破坏，回放无法解释 | 默认冲突拒绝 |
| 一个节点同时写多个变量 | 部分成功导致变量池半更新 | 第一版严格单输出、原子写入 |
| 用普通 QFK Matcher 处理变量池 | Matcher 的输入契约是命令输出，不是变量快照 | 增加独立 `qfk_var` 输入模型 |

### 2.3 description 的四层处理流水线

对 HCI 的机器生成 description，四层是固定的处理边界，不是四个可以任意跳过或调换的用户操作。第一层发现候选值，第二层解释候选值，第三层验证结果，第四层只处理确定性规则覆盖不了的文本。

```text
description
  -> 第一层：确定性变量提取
  -> 第二层：变量命名和归一化
  -> 第三层：类型和基数校验
  -> 第四层：AI 兜底（仅在前三层无法确定时）
  -> 产出新变量
```

四层的职责如下：

| 层级 | 固定命令 | 负责什么 | 不负责什么 |
|---|---|---|---|
| 第一层 | 确定性变量提取 | 使用 `（）、<>、【】`、字段标签、冒号和已审核模板确定候选值边界，并保存原文证据 | 不决定最终变量名，不调用 AI，不猜测缺失值 |
| 第二层 | 变量命名和归一化 | 将候选映射为 `host`、`vm_name`、`disk_name`、`error_code` 等变量，并执行受控文本归一化 | 不从整句自由推断业务含义，不改变候选边界 |
| 第三层 | 类型和基数校验 | 验证 `string`、`number`、`percentage`、`exactly_one`、`zero_or_more` 等契约，完成必要的显式类型解析 | 不在多个候选中擅自挑选，不把失败改成 `false` |
| 第四层 | AI 兜底 | 仅处理没有稳定边界或出现新格式的文本，并返回带证据的原文字面量 | 不弥补数据源缺字段，不覆盖前三层的确定结果 |

第一层按以下优先级识别候选值：

1. **成对边界符号**：中文圆括号 `（...）`、尖括号 `<...>`、中文方头括号 `【...】`，以及已审核模板允许的 ASCII `(...)`、`[...]`。
2. **字段标签和冒号**：中文冒号 `：` 或 ASCII 冒号 `:` 后的值，例如 `源主机：node-a`、`错误码:E10023`。值边界由模板定义的结束标点、下一个标签或行尾确定，不能无限吞掉整句。
3. **数字特征**：整数、小数和百分数，例如 `96`、`7.99`、`92%`。数字必须保留原始字面量，并根据目标变量声明转换为 `number` 或 `percentage`；不能把 `0.91` 自动猜成 `91%`。
4. **字母+数字组合**：名称、标识符和编码，例如 `vm-001`、`eth0`、`E10023`、`Ubuntu-22.04-GPU`。允许模板注册的连字符、下划线、点号等字符；中文名称在有字段标签或边界时也可作为候选值。
5. **数字+单位组合**：例如 `7.99 GB`、`96GB`、`30s`。数字和单位作为一个候选值保留，单位必须来自受控单位表，转换后记录原始字面量和规范单位。
6. **已审核模板**：当值不满足通用词法特征，或同一行存在多个同类值时，使用带 `template_id` 和版本的模板确定边界、变量顺序及基数。

第一层的输出是候选片段，不是无证据的语义推断：

```json
{
  "raw_value": "92%",
  "span": {"start": 18, "end": 21},
  "context": "当前使用",
  "feature": "number_percent",
  "template_id": "memory_usage.zh.v1"
}
```

随后由第二层完成 `percent.current`、`host` 等目标变量命名和归一化，再由第三层校验类型和基数。普通 KBD 编辑人员只选择目标变量；四层规则由平台维护。

对抗性约束：符号本身不是充分条件。`启动虚拟机（内部重启）` 中的括号内容可能是操作描述；同一 description 也可能有多个百分比或多个主机。因此必须结合邻近标签、模板位置、类型和 `cardinality` 校验；无法唯一确定时返回 `unknown` 或 `ambiguous`，不能默认取第一个候选。

## 3. 与现有 QFK/KBD 的关系

现有后端 QFK 的基本模型是：

```text
qfk_system/qfk_vm/qfk_log/...
  -> 执行受控命令
  -> 获得 stdout 或结构化输出
  -> `match` 判断，或 `produces` 提取变量
```

`qfk_var` 的模型是：

```text
qfk_var
  -> 读取变量池快照
  -> 执行受控转换/抽取/比较
  -> 产生断言结果，或写入一个新变量
```

它不伪造主机命令，也不产生 Terminal Bridge 执行记录。执行记录中的命令列表为空，证据来源明确标记为 `variable_pool`。

`qfk_var` 与 `requires/produces` 的关系：

- `requires`：声明输入变量，并参与 CDD 依赖调度。
- `produces`：仅在 `derive` 模式中声明一个输出变量。
- `match`：`qfk_var` 不使用普通 `match`；`assert` 模式的判断规则直接位于 `acquire.args`。
- 变量池：负责保存输入事实和派生结果，不负责解释操作语义。

## 4. 两种运行模式

### 4.1 `assert`：对变量做判断

`assert` 用于产生一个 KBD 信号结论，不写入业务变量。

```text
requires 输入变量
  -> compare / exists
  -> satisfied | contradicted | unknown | error
```

示例：

```json
{
  "id": "check_cpu_usage",
  "acquire": {
    "tool": "qfk_var",
    "args": {
      "schema_version": 1,
      "mode": "assert",
      "operation": "compare",
      "left": "{{CPU_USAGE}}",
      "operator": ">",
      "right": "90%",
      "value_type": "percentage",
      "on_error": "unknown"
    }
  },
  "orchestrate": {
    "phase": "diagnostic",
    "requires": ["CPU_USAGE"],
    "produces": []
  },
  "provenance": {
    "category": "backend"
  }
}
```

执行语义：

```text
原值: "91%"
类型: percentage
规范值: 91
规则: 91 > 90
结果: satisfied
```

### 4.2 `derive`：转换/抽取后产出新变量

`derive` 用于把一个或多个已有变量转换成一个新变量。

```text
requires 输入变量
  -> field / feature_extract / json_path / string / cast / compose
  -> 一个结果
  -> 原子写入 produces[0]
```

示例：优先从任务记录的结构化 `object_name` 取得 VM 名称：

```json
{
  "id": "extract_vm_name",
  "acquire": {
    "tool": "qfk_var",
    "args": {
      "schema_version": 1,
      "mode": "derive",
      "operation": "field",
      "input": "{{TASK_RECORD}}",
      "path": "object_name",
      "value_type": "string",
      "on_error": "unknown"
    }
  },
  "orchestrate": {
    "phase": "diagnostic",
    "requires": ["TASK_RECORD"],
    "produces": [
      {
        "name": "VM_NAME",
        "type": "string",
        "path": "value"
      }
    ]
  },
  "provenance": {
    "category": "backend"
  }
}
```

成功后写入：

```text
VM_NAME = "<VM_NAME>"
source = qfk_var
operation = field
source_variables = [TASK_RECORD]
```

`derive` 的“单输出”不限制处理链只能有一步。例如要先抽取再标准化，应拆成两个节点：

```text
TASK_RECORD.object_name
  -> qfk_var(field)
  -> RAW_VM_NAME
  -> qfk_var(trim/lower)
  -> VM_NAME
```

这样每一步都可以单独验证、回放和定位失败原因。

## 5. `derive` 详细设计：变量池变量 → 转换/抽取 → 新变量

### 5.1 输入：变量池变量

输入引用统一使用双大括号：

```text
{{VARIABLE_NAME}}
{{OBJECT.FIELD}}
{{OBJECT.0.NAME}}
```

变量名遵循现有 KBD 约定，基础变量名使用大写字母、数字和下划线。点路径只用于读取对象或数组内部字段，不用于动态拼接变量名。

合法示例：

```text
{{DESCRIPTION}}
{{VM_INFO.NAME}}
{{DISKS.0.SERIAL}}
```

对于 alert/task，推荐变量池先保留一个有界的结构化记录（或同时保留等价字段）：

```json
{
  "id": 123,
  "type": "启动虚拟机",
  "host": "<HOST>",
  "vm": "<VM_ID>",
  "object_name": "<VM_NAME>",
  "status": 3,
  "errcode_tracing": "<ERROR_CODE>",
  "description": "<ZH_DESCRIPTION>",
  "description_lang": "zh_CN"
}
```

这使 `qfk_var` 可以写成 `field(path=object_name)`，而不是先把记录压扁成一段文本再猜测。只有当目标值只存在于 `description`（例如“当前使用率”“超过阈值”“变更前后值”）时，才使用 `feature_extract`。

不合法示例：

```text
{{*}}
{{POOL}}
{{PREFIX_ + NAME}}
```

每个引用都必须能映射到 `requires`。发布前校验器应扫描 `acquire.args`，自动推导引用集合，并要求其与 `orchestrate.requires` 一致。这样调度器可以在执行前阻断缺少依赖的节点。

### 5.2 输入快照

处理开始时，运行时一次性读取全部 `requires`，形成逻辑快照：

```json
{
  "snapshot_id": "vp-20260824-001",
  "variables": {
    "DESCRIPTION": {
      "value": "...",
      "type": "string",
      "version": 12,
      "updated_at": "2026-08-24T10:30:00Z"
    }
  }
}
```

同一次计算不能在中途重新读取变量池，否则可能出现输入版本不一致：第一次读取 `CPU_USAGE=80`，第二次读取变成 `91`，最终结果却没有明确对应哪一版事实。

若变量池尚未实现统一版本号，至少记录每个输入变量的更新时间、值摘要和快照摘要。

### 5.3 类型解析

转换前必须明确输入类型。推荐优先级：

1. 变量池记录的声明类型；
2. `qfk_var.args.value_type` 的显式类型；
3. 操作要求的固定类型；
4. 无法确定时返回 `QFK_VAR_TYPE_REQUIRED`。

不建议隐式类型转换。以下输入应有不同处理：

| 原值 | `value_type` | 规范值 |
|---|---|---|
| `"91%"` | `percentage` | `91` |
| `"91.5 %"` | `percentage` | `91.5` |
| `"0.91"` | `ratio` | `0.91` |
| `"91"` | `number` | `91` |
| `"true"` | `boolean` | `true` |

`0.91` 不自动解释为 `91%`。如果业务确实使用比例值，必须显式声明 `ratio`，并在比较时使用相同量纲。

### 5.4 转换/抽取操作

第一版操作集合如下：

| 操作 | 输入 | 输出 | 典型场景 |
|---|---|---|---|
| `field` | 结构化对象 | 字段值 | 从 `alert/log` 记录取 `object_name`、`vm`、`host`、`status`、`errcode_tracing` |
| `cast` | 标量 | 指定类型标量 | 文本转数字、百分比、布尔 |
| `string` | 字符串 | 字符串 | trim、大小写、split、replace |
| `feature_extract` | 业务描述字符串 | 字符串、数字或数组 | 从真实 HCI description 先提取特征候选，再映射 VM、主机、磁盘、百分比、错误码 |
| `json_path` | JSON 对象或 JSON 字符串 | 任意 JSON 标量/对象 | 提取 `vm.id`、磁盘序列号 |
| `compose` | 多个标量 | 字符串 | 生成目标标识或资源键 |
| `compare` | 一个或两个标量 | 布尔值 | 产生派生布尔变量 |
| `exists` | 一个变量/路径 | 布尔值 | 生成“字段是否存在”变量 |

每个节点仍然只产生一个 `produces`。数组结果仍是一个变量值，其类型可以是 `array<string>` 或其他明确的数组类型。

### 5.5 `cast`：显式类型转换

示例：

```json
{
  "mode": "derive",
  "operation": "cast",
  "input": "{{CPU_USAGE_TEXT}}",
  "value_type": "percentage",
  "on_error": "unknown"
}
```

输出：

```text
CPU_USAGE_TEXT = "91%"
CPU_USAGE = 91
```

适用场景：

- 命令输出或 QKV 结果写入的文本变量需要变为数值；
- 用户输入的布尔词需要归一化；
- 时间、百分比、数量等带单位文本需要进入后续判断。

不适用场景：

- 需要根据上下文猜单位；
- 一个字符串中包含多个不同量纲的数字；
- 需要复杂自然语言解析。

### 5.6 `string`：字符串标准化

建议每个 `string` 节点只执行一个函数：

```text
trim
lower
upper
split
replace
```

示例：

```json
{
  "mode": "derive",
  "operation": "string",
  "function": "trim",
  "input": "{{HOST_RAW}}"
}
```

适用场景：

- 去除命令输出的首尾空格和换行；
- 统一大小写后再进行比较；
- 将稳定分隔格式拆成数组；
- 替换已明确约束的展示前缀。

注意：`replace` 必须使用字面量字符串，不支持把任意正则作为替换脚本；普通用户的文本抽取统一走 `feature_extract`，高级正则仅作为专家维护的内部模板。

### 5.7 四层 description 处理：`feature_extract` 的固定流水线

`feature_extract` 是四层流水线的配置入口，不是只执行第一层的裸操作。用户选择输入变量和目标变量（例如 `vm_name`、`percent.current`），平台固定按以下顺序执行：

```text
第一层：确定性变量提取
  -> 第二层：变量命名和归一化
  -> 第三层：类型和基数校验
  -> 第四层：AI 兜底（仅在前三层无法确定时）
```

`feature_extract` 是 v1.3 的规范操作名；已存在的 v1.1 草稿若使用 `semantic_extract`，可在解析层作为兼容别名，但执行语义必须遵循上述四层，不得把 AI 提前到第一层或跳过第三层。平台内部可以为一个目标变量维护多个版本化模板，但模板细节不暴露给普通用户。

普通 KBD 编辑人员的配置边界是：选择一个输入变量和一个目标变量。目标变量注册表预先定义第二层的命名/归一化规则以及第三层的类型和基数默认值；编辑人员不能把 `string` 改成 `percentage`，也不能把 `exactly_one` 改成“取第一个”。专家新增目标变量时，必须同时提交四层规则、正例/负例、类型、基数和回放结果。

示例：从告警中文展示描述提取当前使用率：

```json
{
  "mode": "derive",
  "operation": "feature_extract",
  "input": "{{ALERT_DESCRIPTION_ZH}}",
  "target_variable": "percent.current",
  "value_type": "percentage",
  "cardinality": "exactly_one",
  "on_error": "unknown"
}
```

真实样本中的输入形态：

```text
主机（SVR_aCloud_670）的计算内存使用量（92.35 GB）超过阈值（92.34 GB），剩余：7.99 GB，使用率：92%
```

输出：

```text
CURRENT_PERCENT = 92
```

该例不能用“找到第一个数字”或“找到第一个括号”实现。第一层会发现 `SVR_aCloud_670`、`92.35 GB`、`92.34 GB`、`7.99 GB` 和 `92%` 五个候选；第二层依据 `主机`、`使用量`、`阈值`、`剩余`、`使用率` 标签将其分别命名和归一化；第三层确认 `percent.current` 是 `percentage + exactly_one`，确认 `memory.used` 是 `quantity + exactly_one`。选择 `percent.current` 时只接受 `使用率：92%`，选择 `memory.used` 时才接受 `使用量（92.35 GB）`。

第一版建议提供以下目标变量：

| 目标变量 | 类型 | 典型锚点 |
|---|---|---|
| `vm_name` | string | `虚拟机（...）`、`启动虚拟机（...）` |
| `host` | string | `主机（...）`、`主机<...>` |
| `storage_name` | string | `存储<...>`、`源存储：...`、`目的存储：...` |
| `disk_name` | string | `硬盘名称：...`、`硬盘/磁盘（...）` |
| `interface_name` | string | `网口（...）` |
| `percent.current` | percentage | `当前使用...%`、`使用率：...%` |
| `percent.threshold` | percentage | `超过阈值...%`、`超出阈值...%` |
| `memory.used` | quantity | `已使用：... GB`、`使用量（... GB）` |
| `memory.threshold` | quantity | `超过阈值（... GB）` |
| `memory.remaining` | quantity | `剩余：... GB` |
| `error_code` | string | `错误码：...` |
| `source_host` | string | `源主机：...` |
| `destination_host` | string | `目的主机：...` |
| `change_pair` | object | `从（...）变更为（...）` |

第三层的类型和基数契约包括：

- `exactly_one`：命中一个才成功；无命中返回 `unknown`，多命中返回 `ambiguous`；
- 第一版不提供 `first`：即使输入顺序稳定，也必须通过审核模板把边界和目标标签固定下来；
- `zero_or_more`：允许零个或多个候选，返回数组；`produces.type` 必须明确为数组类型。

普通编辑人员不选择四层中的某一层，也不直接选择“取第一个”等危险策略。默认使用 `exactly_one`；多值场景只有在目标变量注册表明确声明时才能使用 `zero_or_more`。

### 5.7.1 特征与变量的组合规则

单个特征通常不能唯一决定变量，必须组合使用：

| 特征组合 | 示例 | 结果 |
|---|---|---|
| 标签 + 成对符号 | `虚拟机（Ubuntu-26.04）` | `vm_name=Ubuntu-26.04` |
| 标签 + 冒号 + 数字单位 | `剩余：7.99 GB` | `memory.remaining=7.99 GB` |
| 标签 + 冒号 + 百分数 | `使用率：96%` | `percent.current=96` |
| 标签 + 成对符号 + 字母数字组合 | `网口（eth3）` | `interface_name=eth3` |
| 关系标签 + 两个候选 | `从（A）变更为（B）` | `change_pair={from:A,to:B}` |

其中冒号本身只表示“左侧标签与右侧值有关联”，不能决定值类型；数字本身也不能决定是容量、百分比、次数、时间还是版本号。只有标签、边界、词法类型和模板位置共同满足目标变量契约，候选才可成为输出变量。

### 5.7.2 数字、百分数和单位

数字词法至少支持：

```text
整数：      96
小数：      92.35
百分数：    92%、92.5 %
数字+单位： 7.99 GB、96GB、30s
```

约束如下：

- 可接受半角数字、小数点以及数字与单位之间的可选空格；负数和科学计数法仅在对应变量显式允许时开放。
- 百分号是类型证据；`92%` 可规范化为 `percentage=92`，同时保存 `raw_value=92%`。
- 单位匹配最长合法单位并区分大小写语义，例如存储容量中的 `GB` 不能静默当成 `Gb`。
- `7.99 GB` 必须作为一个 quantity 候选，不能拆成无单位的 `7.99`；是否换算为 bytes 由目标变量的显式规范单位决定。
- IP、时间和版本中的点号数字不能被小数规则截断。例如 `172.28.24.3` 不是四个小数，`Ubuntu-26.04` 也不是数值。

### 5.7.3 名称和字母数字组合

名称候选至少覆盖 ASCII 字母、数字、连字符、下划线和点号的组合，例如：

```text
SVR_aCloud_670
Ubuntu-26.04
Windows11-GPU
eth3
vm-disk-2.qcow2
```

不能以“必须同时包含字母和数字”作为唯一条件，因为现场资源名也可能是纯中文、纯字母或用户自定义字符串。字母数字组合是高置信词法特征，但必须与 `虚拟机`、`主机`、`网口`、`文件` 等标签、边界符号或已审核模板共同使用。

### 5.8 高级正则实现（不作为普通配置入口）

如果某个新 HCI 版本出现暂未登记的稳定格式，专家可以在高级配置中提交受限正则，但它必须通过发布门禁、样本回放和复杂度校验。真实样本中 VM 名称的内部实现正则可以是：

```regex
虚拟机[（(](?<VM_NAME>[^）)\r\n]+)[）)]
```

这只是实现细节，不应把 `vm_name=...` 这样的未验证格式写成默认 KBD 示例；也不允许把 `*` 当作量词或把 Shell 风格转义直接复制到 JSON。

如果输入是 JSON，必须使用 `json_path`，不能用正则替代结构化解析。

### 5.9 `json_path`：结构化路径提取

示例：

```json
{
  "mode": "derive",
  "operation": "json_path",
  "input": "{{VM_DESCRIPTION_JSON}}",
  "path": "$.data.vm.name",
  "cardinality": "exactly_one"
}
```

输入可以是变量池中的 JSON 对象，也可以是合法 JSON 字符串。第一版建议只开放：

- 对象字段访问；
- 数组下标访问；
- 有界的简单数组结果选择。

暂不开放复杂过滤器、递归扫描、函数调用和任意脚本表达式，防止路径执行成本不可控以及结果无法解释。

### 5.10 `compose`：多变量生成一个标识

`compose` 适合把多个已经标准化的变量拼成一个新变量：

```json
{
  "mode": "derive",
  "operation": "compose",
  "parts": ["{{HOST}}", "{{VM_NAME}}"],
  "separator": "/",
  "on_error": "unknown"
}
```

禁止把输入拼接成 Shell 命令、URL 请求或 SQL 片段。`compose` 的输出只是变量值，不能直接改变执行权限。

### 5.11 `compare`：生成派生布尔变量

`assert` 和 `derive` 都可以使用 `compare`，区别在于结果用途：

- `assert`：结果直接作为 KBD 信号结论；
- `derive`：结果写入一个 `boolean` 变量，供后续 KBD 节点使用。

示例：

```json
{
  "mode": "derive",
  "operation": "compare",
  "left": "{{CPU_USAGE}}",
  "operator": ">",
  "right": 90,
  "value_type": "percentage"
}
```

对应产出：

```json
{
  "name": "CPU_USAGE_OVER_90",
  "type": "boolean",
  "path": "value"
}
```

多变量比较示例：

```json
{
  "mode": "derive",
  "operation": "compare",
  "left": "{{CURRENT_VALUE}}",
  "operator": ">",
  "right": "{{THRESHOLD}}",
  "value_type": "number"
}
```

它只比较两个已经解析好的标量，不支持在一个节点里编写任意布尔表达式。复杂逻辑应拆成多个节点。

### 5.12 `exists`：生成存在性变量

示例：

```json
{
  "mode": "derive",
  "operation": "exists",
  "input": "{{VM_INFO.NAME}}"
}
```

输出必须是 `boolean`。需要区分：

- 路径不存在：`false`；
- 路径存在但值为 `null`：按配置决定是 `false` 还是 `unknown`；
- 变量本身未进入快照：运行时错误或阻塞，不得伪装成业务 `false`。

### 5.13 `ai_extract`：确定性失败后的受控兜底

AI 兜底必须显式配置，不能因为第一层、第二层或第三层失败就无条件自动调用。只有目标格式没有稳定边界、出现已知模板未覆盖的新格式，且调用方明确允许时，才能进入第四层。配置示例：

如果第一层已经发现多个稳定且有证据的候选，只是第三层基数不满足，这是 `ambiguous`，不是“新格式”，不得调用 AI 代替人工定义规则。

```json
{
  "mode": "derive",
  "operation": "feature_extract",
  "input": "{{ALERT_DESCRIPTION_ZH}}",
  "target_variable": "vm_name",
  "value_type": "string",
  "cardinality": "exactly_one",
  "fallback": {
    "type": "ai_extract",
    "instruction": "从候选告警描述中提取虚拟机名称，只返回原文中逐字出现的名称"
  }
}
```

执行顺序固定为：

```text
结构化字段
  -> 第一层：确定性变量提取
  -> 第二层：变量命名和归一化
  -> 第三层：类型和基数校验
  -> 校验成功：直接产出，不调用 AI
  -> 没有稳定边界/新格式：构造有界候选文本
  -> 第四层：AI 兜底
  -> AI 返回 value + evidence 引用
  -> 类型校验 + 原始字面量逐字回查
  -> 成功后才产出或写入变量池
```

`qfk_var` 应复用现有 QFK `ai_extractor` 的安全约束，但增加变量池适配层：标量输入作为一个逻辑候选项，数组输入按记录编号生成逻辑候选项，并把逻辑候选编号映射回变量池快照。AI 不得读取整个变量池，不得补造 description 中不存在的值，也不得改变 `assert` 的真假结论。

对于任务描述“没有主机能够启动这台虚拟机”这类没有 VM 名称的文本，即使启用 AI 也应返回 `unknown`；正确做法是读取 `log.object_name`。AI 兜底是处理格式不稳定，不是弥补数据源缺字段。

## 6. 失败、未知和冲突语义

### 6.0 当前实现配置矩阵

| 模式 | operation | 必须提供 | 变量池副作用 | AI 兜底 |
|---|---|---|---|---|
| `assert` | `compare` | `left/right/operator/value_type` | 不写入 | 禁止 |
| `assert` | `exists` | `input`（可选 `path`） | 不写入 | 禁止 |
| `derive` | `feature_extract` | `input/target_variable/value_type/cardinality` | 恰好写一个 `produces` | 仅无稳定边界/新格式 |
| `derive` | `field` / `json_path` | `input/path/value_type` | 恰好写一个 `produces` | 禁止 |
| `derive` | `cast` | `input/value_type` | 恰好写一个 `produces` | 禁止 |
| `derive` | `string` | `input/function` | 恰好写一个 `produces` | 禁止 |
| `derive` | `compose` | `parts` | 恰好写一个 `produces` | 禁止 |

`requires` 必须与所有 `{{VAR}}` 占位符集合完全相等；`qfk_var` 不读取整个变量池，不执行 Shell/aCLI。

### 6.1 处理状态

`qfk_var` 运行结果至少区分：

| 状态 | 含义 | CDD 影响 |
|---|---|---|
| `succeeded` | 已得到确定结果 | 继续处理 |
| `unknown` | 输入或匹配不足，不能确定 | 不得当作否定 |
| `ambiguous` | 候选值超过目标变量基数，无法唯一确定 | 按未知处理，不得默认取第一个 |
| `blocked` | `requires` 未就绪 | 保留依赖缺失原因 |
| `error` | 配置、类型、资源或运行时错误 | 按 `failure_effect` 处理 |
| `conflict` | 派生变量已存在且值不同 | 默认拒绝写入 |

稳定错误码包括：`QFK_VAR_REQUIRES_MISMATCH`（依赖声明不一致）、`QFK_VAR_BLOCKED`（依赖未就绪）、
`QFK_VAR_NO_STABLE_BOUNDARY`（无确定边界）、`QFK_VAR_CARDINALITY_MISMATCH`（稳定候选数与基数不符）、
`QFK_VAR_TYPE_MISMATCH`（类型校验失败）、`QFK_VAR_UNIT_MISMATCH`（数量单位不一致）、
`QFK_VAR_CONFLICT`（原子写入冲突）、`QFK_VAR_AI_FALLBACK_FAILED`（受控 AI 兜底失败）。

### 6.2 `on_error`

第一版仅建议 `unknown` 和 `error` 两种策略。不支持 `false`、空字符串或任意默认值作为通用错误兜底，因为这会掩盖输入质量问题。
当前运行时：`on_error=unknown` 将类型/路径/操作错误映射为 `UNKNOWN`，但仍不写入变量池；默认 `error` 保持执行错误。缺失 `requires` 始终为 `BLOCKED`，稳定多候选始终为 `ambiguous/UNKNOWN`。

### 6.3 原子写入

`derive` 只有在所有输入存在、类型解析成功、操作满足 cardinality、输出类型兼容、目标无冲突且审计记录可生成时才写入变量池。任一步失败，都不写入半成品变量。

## 7. 变量池写入契约

成功写入的变量建议带以下元数据：

```json
{
  "name": "VM_NAME",
  "value": "<VM_NAME>",
  "type": "string",
  "source": "qfk_var",
  "operation": "field",
  "operation_version": "1",
  "source_variables": ["TASK_RECORD"],
  "input_snapshot_id": "vp-20260824-001",
  "trace_id": "...",
  "execution_id": "...",
  "calculated_at": "2026-08-24T10:31:00Z"
}
```

第一版默认写入策略为 `reject_on_conflict`：目标变量不存在则写入；已存在且值相同可幂等成功；已存在且值不同则返回 `conflict`，不得覆盖。

## 8. 典型使用场景

### 场景一：CPU 使用率超过 90%

```text
CPU_USAGE="91%"
  -> qfk_var/assert/compare(percentage)
  -> satisfied
```

适合 `assert`，因为结果本身就是诊断信号。

### 场景二：先解析数值，再供多个节点复用

```text
CPU_USAGE_TEXT="91%"
  -> qfk_var/derive/cast(percentage)
  -> CPU_USAGE=91
  -> 多个下游 qfk_var/assert
```

适合 `derive`，因为规范化后的 `CPU_USAGE` 是可复用事实。

### 场景三：从任务记录取得 VM 名称（结构化字段优先）

```text
TASK_RECORD.object_name="<VM_NAME>"
  -> qfk_var/derive/field
  -> VM_NAME="<VM_NAME>"
```

只有当结构化字段缺失、且中文展示描述确实包含 VM 名称时，才选择：

```text
ALERT_DESCRIPTION_ZH="虚拟机（<VM_NAME>）的内存不足..."
  -> qfk_var/derive/feature_extract(target_variable=vm_name)
  -> VM_NAME="<VM_NAME>"
```

任务失败原因描述“没有主机能够启动这台虚拟机”通常不包含 VM 名称；此时必须使用 `log.object_name`，不能要求 description 抽取器凭空恢复名称。

### 场景四：从 JSON 变量取嵌套字段

```text
VM_INFO_JSON
  -> qfk_var/derive/json_path($.data.vm.id)
  -> VM_ID
```

优先于正则，因为 JSON 路径保留字段语义和结构边界。

### 场景五：两个变量比较

```text
USED_BYTES=90
CAPACITY_BYTES=100
  -> qfk_var/assert/compare(>, {{CAPACITY_BYTES}})
  -> contradicted
```

比较前必须保证两个变量具有同一量纲。

### 场景六：生成目标标识

```text
HOST="<HOST>"
VM_NAME="<VM_NAME>"
  -> qfk_var/derive/compose
  -> TARGET="<HOST>/<VM_NAME>"
```

结果仍需经过后续工具的主机/IP 安全校验，不能绕过目标门禁。

### 场景七：规范化后再判断

```text
RAW_STATE="  RUNNING  "
  -> trim
  -> STATE="RUNNING"
  -> lower
  -> STATE_NORMALIZED="running"
  -> compare/equal("running")
```

建议拆成多个节点，不在一个节点中同时完成多次转换和多个变量写入。

## 9. 复杂场景的拆解方法

### 9.1 多条件判断

第一版不支持在单节点中写 `CPU_USAGE > 90 && MEMORY_USAGE > 80`。应拆为：

```text
CPU_USAGE    -> CPU_OVER_90
MEMORY_USAGE -> MEMORY_OVER_80
CPU_OVER_90 + MEMORY_OVER_80 -> HIGH_LOAD
```

复杂逻辑应由多个节点的证据策略或后续受控 `boolean_combine` 表达。

### 9.2 多输出抽取

不建议一个正则同时写入多个业务变量。可以先产出一个结构化对象，再由多个后续 `json_path` 节点拆分：

```text
DESCRIPTION -> RAW_VM_RECORD
RAW_VM_RECORD -> VM_NAME
RAW_VM_RECORD -> HOST
RAW_VM_RECORD -> CLUSTER
```

### 9.3 全变量池综合评分

遍历整个变量池、统计所有异常项或生成综合评分，不属于第一版 `qfk_var`。这类能力需要独立的 `pool_score` 或 `pool_assert`，不能通过 `{{*}}` 逃避显式依赖。

## 10. 发布校验与调度

建议在共享 Signal Schema 中增加 `qfk_var` 专属规则：

- `args.schema_version` 必须存在且受支持；
- `assert` 必须有判断操作，`match=null`，`produces=[]`；
- `derive` 必须有转换/抽取操作，`match=null`，`produces` 恰好一个；
- 输入引用必须全部出现在 `orchestrate.requires`；
- 输出变量名称唯一、类型明确，不能覆盖输入变量；
- 操作字段只能使用对应白名单字段；
- 正则在发布时编译、长度和复杂度校验；
- JSON 路径的深度、返回数量和结果大小有界；
- 发布阶段检测循环依赖、自引用、不存在的生产者和类型不兼容。

运行时纳入现有 CDD DAG：

```text
上游 qkv/qfk producer
  -> 写入变量池
  -> qfk_var requires 满足
  -> 执行转换/判断
  -> 写入派生变量或产生 Signal outcome
  -> 下游继续调度
```

## 11. 可观测性和证据链

每次执行必须使用统一调用链：

```text
trace_id
  └── execution_id
       └── signal_id
            └── qfk_var operation
```

结构化日志字段：`trace_id`、`execution_id`、`signal_id`、`mode`、`operation`、`requires`、`produces`、`input_snapshot_id`、`status`、`error_code`、`duration_ms`、`output_type`。

禁止直接打印完整 description、日志片段、Token、密码或其他敏感值。建议指标：

```text
qfk_var_executions_total
qfk_var_execution_duration_seconds
qfk_var_unknown_total
qfk_var_errors_total
qfk_var_type_errors_total
qfk_var_cardinality_mismatch_total
qfk_var_conflicts_total
```

机器证据至少包含：输入变量、规范化输入、操作、规则、结果、快照和调用链标识；人类摘要必须与机器结果一致。

## 12. 安全和资源限制

第一版禁止 `eval`、`exec`、Shell、管道、命令替换、网络访问、自由 LLM 二次解释、动态变量名和通配符读取。显式配置的 `ai_extract` 兜底不属于自由解释：它只能从本节点已经选定的候选文本中提取逐字存在的值，并经过类型和证据回查。

建议上限：确定性单输入文本 1 MB、正则 pattern 4 KB、单次匹配 1000 条、单次输出 50 KB、JSON 路径深度 32、单节点计算 1 秒。进入 AI 兜底时沿用现有 QFK AI 提取器的更严格预算：最多 200 个候选项、序列化候选不超过 64 KiB。正则需在保存/发布阶段编译和复杂度校验。

## 13. 与 SOP `derived` 的边界

SOP 变量池已有受限 `derived` 表达式能力，主要服务 SOP 变量获取。`qfk_var` 是 KBD/CDD 中的显式信号节点，具备 Signal ID、KBD revision、CDD 调度、Signal outcome 和证据链。两者可以共享底层白名单转换库，但 KBD 不能直接依赖 SOP 的非信号执行路径，也不能把 SOP 表达式自动当成 KBD 诊断证据。

## 14. 版本化、幂等和冲突

`args.schema_version` 用于版本化配置语义。处理逻辑升级时保留旧版本解析器，直到对应 KBD revision 完成迁移。

幂等键建议包含：

```text
conversation_id + kbd_revision + signal_id
+ input_snapshot_id + operation_fingerprint
```

相同快照、相同 revision 和相同操作指纹可以复用结果，但仍需记录本次 `execution_id`，并标记 `replayed` 或 `idempotent_hit`。

## 15. 实施分期

### 阶段一：共享处理内核

- 参数模型和稳定错误码；
- `field`、`cast`、`string`、`feature_extract`、`json_path`、`compare`、`exists`；
- 复用现有 QFK 受控 AI 提取器作为显式兜底；
- 输入快照接口；
- 单元测试、资源限制和结构化日志。

### 阶段二：Agent/KBD 运行时接入

- 工具注册；
- `assert/derive` 执行分支；
- `requires/produces` 调度；
- 原子变量池写入和冲突检测；
- Signal outcome 和证据展示。

### 阶段三：Schema、管理端和生成约束

- 共享 Signal Schema 校验；
- KBD 编辑器操作配置；
- KBD 预览页展示输入、处理、输出和失败原因；
- Prompt 增加 `qfk_var` 生成约束。

### 阶段四：回放和灰度

至少覆盖百分比判断、单位歧义、特征候选单次/多次命中、标签映射、JSON 路径、两变量比较、缺失依赖、类型失败、变量冲突、循环依赖、AI 逐字回查、幂等重放和敏感日志检查。

## 16. 验收标准

### 功能

- 能对变量池已有百分比变量执行 `> 90%` 判断；
- 能从 `alert/log` 结构化记录优先取得 VM 名称；
- 能从真实 HCI 中文展示 description 按四层流水线抽取并校验 VM、主机、百分比、磁盘和错误码；
- 能在前三层没有稳定边界或出现新格式时，使用第四层受控 AI 提取器兜底，并逐字回查证据；
- 能从 JSON 变量按路径提取字段；
- 能用两个显式输入生成一个派生变量；
- 复杂处理可以拆成多个节点并按 DAG 顺序执行。

### 正确性

- 缺失、解析失败、多匹配不会变成 `false`；
- 百分比和比例不会自动混用；
- 同一输入快照重复执行结果一致；
- 派生变量写入是原子的；
- 已存在不同值默认拒绝覆盖。

### 安全与可观测性

- 不能执行任意代码或 Shell；
- 不能通过通配符读取整个变量池；
- 正则、JSONPath 和输入输出大小受限；
- 敏感值不出现在日志中；
- 每次执行有唯一 `trace_id`、`execution_id`、`signal_id`，并能追溯到输入变量和快照。

## 17. 明确不纳入第一版

以下能力不属于第一版 `qfk_var`：任意全变量池表达式、复杂布尔表达式、`map/filter/reduce`、批量重写全部变量、自动推断单位、LLM 辅助解析、用户自定义函数、动态变量名和一个节点输出多个业务变量。

如果未来需要综合评分、全局约束或变量池批处理，应单独设计 `pool_assert`、`pool_score` 或 `pool_normalize`，不能通过扩大 `qfk_var` 的隐式能力实现。
