# 信号双路并行与最少充分集设计

本文是「关键信号」与「根因信号」两条并行策略的**顶层设计**：同一目标的定义、两条路径的
边界、判据的三层结构（可求值 / 充分 / 最少）、运行时如何做到「互不影响」，以及落地与实测。

它**承接**而非替代两份既有主文档：

| 既有文档 | 已解决的问题 | 本方案的增量 |
|---|---|---|
| [根因信号抽取方案](根因信号抽取方案.md) | v2 多信号数组、整篇输入、溯源分层、审核 UI | 抽取的**判据质量**与**数量最小化** |
| [根因信号抽取闭环方案](根因信号抽取闭环方案.md)（PR-1~5 已交付） | **第 1 层「可求值」**：`requires ⊆ produces ∪ context`、硬编码字面量、能力预检、不可闭环转拒绝候选 | **第 2 层「充分」与第 3 层「最少」**，以及**运行时两路拆分** |

关键信号抽取链路（`signals_json`）仍以 [关键信号抽取与建模设计](关键信号抽取与建模设计.md) 为准，
本文只定义两条路径**共同的目标与共用的判据标准**。

## 1. 同一目标，两条策略

### 1.1 唯一目标（不变量）

> **平台通过信号快速判断「当前故障是否命中某篇 KBD」。**

这句话拆开有三个不可再分的约束，任何设计都必须同时满足：

1. **判断**：信号必须可被现场证据确定性求值，产出 true/false，不能只是描述；
2. **快速**：单篇参与判定的信号数决定采集次数与执行时延，越少越快；
3. **命中**：判为 true 必须真的属于该 KBD 的故障域（不能把健康态或其他根因误判进来）。

**信号不是摘要、不是展示物、不是排查清单。** 不能参与求值的文字，按定义不是信号。

### 1.2 两条路径，两种降本策略

人工审核不可取消（现阶段没有任何一条路径能独立达到可自动发布的准确率）。因此降低审核
工作量的路径只有两条，分别对应两个乘数：

\[
\text{审核工作量} \approx \text{篇数} \times \text{篇均信号数} \times \text{单条需纠错的概率}
\]

| 路径 | 数据源 | 降本策略 | 优化对象 | 现状 |
|---|---|---|---|---|
| **A 关键信号** | 标题 / 问题描述 / 告警 / 有效排查步骤（逐步骤抽取） | 提升**单条准确率** | 第三项「纠错概率」 | 325 篇 / 768 条 / 均 2.36 条 |
| **B 根因信号** | 整篇（只抽能确证根因的） | 减少**篇均信号数** | 第二项「信号数」 | 12 篇 / 12 条 / 均 1.0 条 |

两条路径**并行、互不影响**：

- 各自独立抽取、独立存储（`signals_json` / `root_signal_json`）；
- 各自独立求值、独立产出「是否命中」的判断；
- 任一路判错，**不得**污染另一路的结论。

### 1.3 为什么「根因路」是正确方向（而非无奈之举）

关键信号的天花板受**信息来源**限制，不是模型能力问题：排查步骤是**过程性**知识（怎么查），
天然含分支、现象、中间态，抽成判别谓词的判别力上限就低。根因是**结论性**知识（是什么），
天生适合做判别。所以两条路径不是「临时替代」，而是**长期并存的两个证据面**：过程侧负责
缩小候选，结论侧负责精确定位。

## 2. 第一性原理：判据的三层结构

### 2.1 什么是「一条正确的根因信号」

从「判断是否命中」这个目标正向推导，一条根因信号必须同时通过三层：

| 层 | 名称 | 判据 | 失败后果 | 现有覆盖 |
|---|---|---|---|---|
| L1 | **可求值** | 命令能执行、输出能产出该匹配串、变量有来源 | 恒不命中 → 该 KBD **永久 REJECTED** | ✅ 闭环方案 PR-1~5 |
| L2 | **充分** | 能排除「健康态」与「同分类其他每一篇」 | 恒真 → 该 KBD 变成**万能匹配** | ❌ 完全缺失 |
| L3 | **最少** | 去掉任一条，就不再充分 | 冗余 → 审核与采集成本翻倍 | ❌ 完全缺失 |

### 2.2 「最少充分集」的形式化

设 \(K\) 为本篇 KBD，\(C\) 为候选集（**同分类其他 KBD ∪ 健康态**），\(S\) 为本篇抽出的信号集，
\(P_s(e)\) 为信号 \(s\) 在证据 \(e\) 上的求值结果：

- **充分**：\(\forall c \in C\setminus\{K\},\ \exists s \in S\)，使 \(P_s(e_c) = \text{false}\)
- **最少**：\(\forall s \in S\)，\(S\setminus\{s\}\) 不充分

这个定义的价值在于：**它用一个概念同时表达了准确率与数量**。

- 「充分」自动蕴含**非恒真**（否则无法排除健康态）；
- 「充分」自动蕴含**判别力**（否则无法排除兄弟篇）；
- 「最少」就是**不可约性**，即冗余的定义。

所以不需要为「恒真」「撞车」「冗余」分别设计三套标准——**它们是最少充分集的三个必要条件**。

**注意「不强制 1 条」**：最少性只要求不可约，不要求基数为 1。真实场景中正当的多信号只有
三种情形（见 §2.4），此时 2~3 条才是「最少」。

### 2.3 由「充分」导出的硬结论：路内必须是 AND

「充分」的定义是**一组信号共同成立才够**，这是合取语义。

若某条路径内部采用 OR（任一成立即命中），则「最少充分集」必然退化为 1 条——因为任意一条
都能单独成为充分集，多出来的永远是冗余。**因此「部分 KBD 需要多条信号」这一事实，本身就
证明该路径内部是 AND。**

| 层次 | 语义 | 决策状态 |
|---|---|---|
| 关键路**路内** | AND（现状 99.9% 为 MUST） | 保持不变 |
| 根因路**路内** | **AND**（由「充分」定义决定） | 明确 |
| **跨路融合** | OR / 优先级 / 影子 | 见 §3.3 |

### 2.4 正当的多信号只有三种情形

| 情形 | 结构 | 说明 |
|---|---|---|
| **A 根因 + 触发条件** | 机制链两段，缺一不可 | 如「版本 R5」+「主机异常重启后启动失败」 |
| **B 复合状态（配置 ≠ 运行）** | 两个观测点交叉 | 如「`loadmod.conf` 有 nested=1」+「运行时 nested 未生效」 |
| **C 判别性补强** | 单条无法排除某兄弟篇 | 如「迁移失败」四篇同分类，需第二条区分 |

**同环节的并列证据不构成多信号**：若 B 是 A 的下游结果，说明判据不够精确，应合并或删除
下游，而不是当作「这篇需要多条」。

### 2.5 数量与语义的耦合（决定门禁优先级）

| 融合语义 | 恒真信号后果 | 恒不命中后果 | 必须先堵 |
|---|---|---|---|
| **AND** | 零信息、占位冗余 | **判死该 KBD** | **L1 可求值**（闭环方案已覆盖） |
| **OR** | **该 KBD 永久命中** | 零信息 | **L2 充分性（恒真）** |

**结论：门禁投入必须与融合语义匹配。** 现行实现是 AND（见 §3.1），所以闭环方案优先补 L1 是
正确的；一旦引入跨路 OR，L2 立即升为最高优先级，否则存量恒真信号会把 KBD 变成万能匹配。

## 3. 架构设计

### 3.1 代码事实：现行实现不是「两条路」

```python
# backend/kb-service/app/routes/playbooks.py:40
def _signals(entry):
    signals = [关键信号 ...]
    for root in _root_signals(entry):
        normalized = normalize_root_for_runtime(root)
        if normalized: signals.append(normalized)   # ← append 到同一列表
    return signals
```

`SignalRef` / `SignalPlan` **无 track / group / channel 字段**，`candidate_reducer` 只按 `kbd_id`
分组，`SUPPORTED ⟺ 该 kbd 所有 MUST SATISFIED`。而 `normalize_root_for_runtime` 不写
`required_for_support`，`_required()` 落到默认 `phase=='diagnostic'` → `True` → **根因信号全部为 MUST**。

所以现行实际语义是：

```
命中 = 关键信号(全 MUST) AND 根因信号(全 MUST)
```

这是**早融合**，与「两条并行、互不影响」直接冲突：

| 设计意图 | 实际发生 |
|---|---|
| 根因信号判错，不影响关键路 | 根因信号 CONTRADICTED → **整个 KBD 直接 REJECTED** |
| 两条路互为备份 | 两条路互为**前置条件** |
| 根因信号减少数量 → 更快 | 判定链从 2.36 条拉长到 3.36 条 → 更慢且召回更低 |

该缺陷在覆盖率 1.8%（275 篇 published 中 5 篇有根因信号）时**结构性隐形**：评估语料命中不到，
指标永远显示「无漂移」。全量回刷时才会集中暴露。

### 3.2 目标架构：track 维度 + 晚融合

```
kb-service /playbooks
  ├── 关键信号   → signal.track = "process"
  └── executable 根因 → signal.track = "root"
                    │
                    ▼
        compile_signal_plan（同一 plan，两 track 共存）
                    │
        ┌───────────┴───────────┐
   assessment[K#process]   assessment[K#root]      ← 各自独立 reduce
   （只取 track=process）    （只取 track=root）
        └───────────┬───────────┘
                    ▼
            fuse_track_states(mode) → 单 kbd 结论 → decide_conclusion
```

这是**晚融合（late fusion）**：两路各自求值、各自出结论，最后融合。相比早融合，它的关键
性质是「一路的求值失败不会改变另一路的 outcome」。

**唯一跨路共享的语义是 EXCLUDE**：排除项表达「这个 KBD 一定不是」，与证据来自哪条路无关，
因此任一 track 的 EXCLUDE 成立 → 整体 REJECTED（见 §3.5）。

### 3.3 融合策略（可配置，默认 OR）

| 模式 | 语义 | 用途 |
|---|---|---|
| `process_only` | 只用关键路 | 完全兼容改造前行为（回滚开关） |
| `root_or_process`（默认） | 任一路 SUPPORTED → SUPPORTED | 两路互为备份，最符合「互不影响」 |
| `root_only` | 只用根因路 | 验证根因路独立能力 |
| `shadow` | 结论只用 process，**root 只记录** | 灰度观察，零风险 |

**OR 模式的准入闸门**：根因路只有经**新版充分性门禁**（`provenance.gate_version >= 2`）产出的
信号才参与融合；无该标记的存量信号视为 `legacy`，只进影子统计。这样避免存量恒真信号
（如「三行配置」「nested=1」）在 OR 下变成万能匹配，也无需人工逐条标记。
存量准入的落地路径：不要让全部存量 KBD 等重抽，而是用 `scripts/ops/regate_root_signals.py`
重跑同一套确定性门禁后盖章（实测 9/10 准入，见 §7.2 举证一）；拒收与剪枝均落拒绝审计列。

### 3.4 门禁不对称（由 §2.5 推导）

| | 根因路（n≈1~2） | 关键路（n≈2.36） |
|---|---|---|
| 首要失效模式 | 一条恒真 → 万能匹配 | 一条恒不命中 → 判死 |
| 首要门禁 | **L2 充分性：健康态反证** | **L1 可求值**（闭环方案已覆盖） |
| 次要门禁 | L3 最少性、兄弟篇排除 | L2/L3 |

共用一套门禁是当前体系的空缺：现有 `gate_executable` 只解决「能不能执行」，恰好不解决任何
一条路的**首要**失效模式。

### 3.5 判定语义细则

- **SUPPORTED**：该 track 的 MUST 全 SATISFIED ∧ should ≥ minimum ∧ 该 track 的 excludes 全不成立；
- **REJECTED**：该 track 任一 MUST CONTRADICTED，**或任一 track 的 EXCLUDE 成立**；
- **融合**：
  - 任一 track SUPPORTED 且无全局 EXCLUDE → SUPPORTED；
  - 全部 REJECTED → REJECTED；
  - 否则 → INCONCLUSIVE / CANDIDATE（保留可继续采集的机会）。

## 4. 业界范式对照

| 范式 | 出处 | 在本文的映射 |
|---|---|---|
| **关联规则 lift** | 数据挖掘（support/confidence/lift） | 信号 = 前件，KBD = 后件。恒真信号 `support≈100%`、`lift≈1`（零信息量）。L2 充分性即「lift 必须显著 > 1」 |
| **鉴别诊断（differential diagnosis）** | 医学 | 多候选并列时必须逐项排除；对应「兄弟篇排除」与 EXCLUDE 层 |
| **最小可判别特征集** | 模式识别 / 特征选择 | 本文「最少充分集」的数学原型：不降低可分性的最小子集 |
| **晚融合 vs 早融合** | 多模态 / 检索融合 | §3.2 的 track 维度即晚融合；现行并集是早融合 |
| **LLM as proposer + deterministic verifier** | LLM 工程实践 | LLM 只产出候选，充分性/最少性由确定性规则裁决（§5.4） |
| **Hard negative mining** | 对比学习 | 抽取时注入同分类兄弟篇作为「必须排除的负样本」（§5.3） |
| **可证伪性（Popper）** | 科学哲学 | 一条判据必须能说出「什么情况下它为假」，否则不是判据（健康态反证） |

## 5. 判据的生产：LLM 侧设计

### 5.1 现行 Prompt 的五个结构性缺陷

| # | 缺陷 | Prompt 原文 | 对应实测错误 |
|---|---|---|---|
| P1 | 缺健康态反证 | 自检只问「能否与同分类其他 KBD 区分」 | 恒真判据能通过自检（三行配置、nested=1） |
| P2 | 「锚点即关键词」，缺输出形态约束 | 「存在硬锚点…锚点即信号关键词」 | 把 `ps -ef` 与「waiting for lock」绑定；臆造路径 |
| P3 | 缺上下游区分 | 只说「不能只是现象」 | 把根因的下游报错当根因信号 |
| P4 | 缺最小集/蕴含剪枝 | 「不限条数」 | 同环节上下游并存 |
| P5 | few-shot 只示范 keyword | match 示例仅 `{"type":"keyword"}` | 12/12 条信号全是 keyword，`state/exists/threshold` 全闲置 |

### 5.2 最少充分集的三条自检（写入 Prompt 自检段）

```
7. 充分性：这组信号合起来，能否排除「这台机器是好的」以及「同分类下其他每一篇」？
   若有一篇无法被排除，补一条能排除它的；补不出来则不输出。
8. 最少性：对每一条做反事实——删掉它，剩下的还能不能确证？能则删除该条。
9. 链结构：多条只在「根因 / 触发条件 / 运行时状态」不同环节时保留；
   同一环节的上游与下游只能留一条（留下游会放大误判）。
```

### 5.3 兄弟篇对比注入（hard negative）

抽取前取同分类最相似的 2~3 篇 `root_cause` 摘要，作为「必须排除的负样本」注入。数据已在
`ConflictCorpus` 中全库加载，成本近零，直接命中「同分类撞车」这一核心痛点。

### 5.4 谓词类型映射（把 text 从降级变成可工程化）

现行运行时支持 keyword / regex / state / boolean / threshold / exists，但抽取端只产出 keyword。
明确映射后可把大量 text 转成 executable：

| 根因形态 | 应选谓词 | 可证伪性来源 |
|---|---|---|
| 版本缺陷 / 兼容性 | `keyword`（带产品语境的完整版本串） | 版本不等于该值即假 |
| 目录/分区空间不足 | `keyword`（`100%`/`No space left`）+ 具体挂载点 | 未满即假 |
| 配置文件取值异常 | `keyword` 匹配**异常值**而非字段名 | 取到正常值即假 |
| 文件/目录残留 | `keyword`（文件名）+ `ls` | 不存在即假 |
| 日志确定性报错 | `keyword` / `regex` | 报错不出现即假 |
| 无法工程化的环境属性 | **不产出**（转候选 backlog） | — |

**`threshold` / `state` / `boolean` / `exists` 暂不进入抽取契约**：运行时 `_root_match_to_cdd` 只
无损还原 keyword/regex，其余静默丢弃。为保证「落库即有效」，抽取门禁只接受 keyword/regex。

## 7. 改进计划与落地情况（预期 vs 实测）

> 口径：本节把「设计预期」与「实测证据」严格分列。没跑过的一律标「未落地」，不用设计意图代替证据。

### 7.1 落地清单

### 7.2 实测举证

#### 举证一：存量根因信号的运行时准入率 0/12 → 9/10（passed）

改造前：12 个 `root_signal_json` 非空行、12 条信号，**全部没有 `provenance.gate_version`** → 被
`playbooks._signals()` 的准入闸门拦下，一条也不参与判定（既无收益，也不造成损害）。

用 `scripts/ops/regate_root_signals.py` 重跑 L2/L3 并盖章后（staging 实测，已落库）：

| 去向 | 条数 | 说明 |
|---|---|---|
| `passed`（运行时准入） | 9 | 分布在 kbd 1/10/574/627/718/739/1301/1772/2762 |
| `warning`（准入但不放行） | 1 | kbd 1：`likely_always_true`（判据为配置字段语义），只降级人工复核 |
| 拒收 `insufficient_discrimination` | 2 | kbd 1692：expected 全为 `lock, failed` 通用错误串；kbd 2266：`acquire.args.command=ps` 却判句子级描述 `waiting for lock` |

幂等性实测：第二次干跑 `变更 0 篇 / 拒收 0 条 / 剪枝 0 条`；已盖章信号原样保留、不参与二次剪枝
（尊重人工审核结论）。

**结论**：① L2 不是空跑——确定性规则拦下 2/12 = 16.7% 结构上无判别力的判据；② 存量资产无需重抽
即可贡献分流收益（9 条准入）。

#### 举证二（核心增量）：关键路判死时，根因路仍能独立命中

目标：KBD **627**（support_id **19088**，已发布，分类 `虚拟机-018`，同分类 67 篇 published）。
同一故障现场，只切换 `KB_SIGNAL_FUSION_MODE`：

| 融合模式 | 结论 | 命中 KBD | 目标分路状态 |
|---|---|---|---|
| `process_only`（改造前等价行为） | INCONCLUSIVE | — | `{process: REJECTED, root: CANDIDATE}` |
| `root_or_process`（默认） | PARTIAL | **627** | `{process: REJECTED, root: SUPPORTED}` |
| `root_only` | PARTIAL | **627** | `{process: REJECTED, root: SUPPORTED}` |

改造前两轨信号被 append 进同一列表、按 AND 归约：关键路任一 must 被反证即整篇落 CANDIDATE——
根因路再准也无法改变结论。改造后两路独立归约 + 晚融合，同一现场由根因路给出 SUPPORTED。
**这是「两条路互不影响」的直接举证。**

#### 举证三：判别力没有被 OR 融合稀释（零误命中）

| 场景 | `root_or_process` | `root_only` | `process_only` | 目标 627 |
|---|---|---|---|---|
| S3 健康态（仅通用噪声） | INCONCLUSIVE，不命中 | 不命中 | 不命中 | REJECTED |
| S4 同分类兄弟篇特征 | PARTIAL，命中 202/305/982 | INCONCLUSIVE，不命中 | PARTIAL，命中 202/305/982 | **REJECTED（不误命中）** |

健康态下根因路真正求值后 REJECTED（不是 BLOCKED），证明「不是万能匹配」；兄弟篇场景目标篇被两路
同时排除，说明根因信号的判别力成立。

#### 举证四：L3 剪枝不静默（新增，本次补齐）

门禁删信号必须可审计，否则审核人无法解释「LLM 给了 2 条、库里只剩 1 条」：

- 抽取路径：`outcome["pruned"]` 并入 `root_signal_rejected_json`（`reason_code=redundant_with_stronger_signal`
  + `redundant_with=<被保留的更强信号>`）；
- 人工编辑路径：与抽取**同标准**跑 `gate_minimality`，但**不 422**——人工显式提交的冗余是「可用但低效」，
  硬拒会阻断「先保存再逐步精简」的工作流；
- 指标独立：`hci_root_signal_pruned_total{reason_code}`，不计入 `rejected` 分母（否则门禁失败率被结构性
  剪枝污染）。

#### 举证四补：L3 方向性对抗审查修正（提交前自审发现，已修 + 已守护）

对 L3 做红队式审查时发现两处会**降低判别力**的真实缺陷（单测全绿也掩盖了）：

| 缺陷 | 触发形态 | 后果 | 修正 |
|---|---|---|---|
| 剪枝忽略 `match.mode` | `candidate=any[A]` 被 `stronger=any[A,B]` 严格包含 | `any` 超集不蕴含子集（命中 B 即成立）；剪掉后「A 未出现」不再被否证 → **REJECTED 翻成 SUPPORTED** | 规则 1/3 要求 `stronger.mode=all`；规则 2 要求判据集合**与** `mode` 同时相同 |
| 证据子串剪掉更强判据 | `candidate` 证据短但 `expected` 是超集 | 判别力下降（同一类事故） | 规则 3 要求 `candidate.tokens ⊆ stronger.tokens`；规则 4 只剪 text（不进运行时判定） |

另一处覆盖不足：`gate_sufficiency` 的 argv-only 命令判定用裸命令名比对，LLM 写 `/usr/bin/ps` 时
漏网 → 改取 `posixpath.basename`。

**守护**：`TestGateMinimality` 新增 4 例钉死方向性（any 超集不剪子集 / all 超集可剪 any 子集 /
证据短但判据更严不得剪 / 绝对路径命令仍判 argv-only），并登记避坑 `docs/verify/pitfalls/python.md` V-029。
原则：**剪枝必须证明「被剪项在逻辑上更弱」，不能只证明「它更短」**；证明不了就保留（L3 是成本优化，
误剪是正确性事故）。

### 7.4 诚实边界（对抗性审查登记，本次未解决）

1. **调度早停使 OR 模式下根因路常显 `INCONCLUSIVE`**：候选一旦 `SUPPORTED` 就不再是 active，剩余采集
   不再调度（未跑信号记 NOT_RUN）。故 S1「两路证据齐」时默认模式分路状态为
   `{process: SUPPORTED, root: INCONCLUSIVE}`——这是**省采集成本的早停**，不是判定错误；`root_only`
   下根因路才能显示 `SUPPORTED`。指标口径须按此解释，不能把 INCONCLUSIVE 读成「根因路判错」。
2. **`{{HOST}}`/`{{DATE}}` 的数据依赖**：根因 `acquire.args` 的这两个变量由关键路 `qkv_task` 生产者填充
   （`_fill_pool_from_qkv`，DATE 由 END 派生）。现场没有生产者命中时根因路 `BLOCKED → CANDIDATE`，
   而不是 REJECTED。这是**合法的共享现场上下文前提**（不是判定耦合），但会降低根因路的独立命中率。
   缓解方向：抽取时优先使用 `env_context` 已提供的 `{env_info, alert_logs, task_logs, node_ip}`。
3. **S4 暴露的既有缺陷（属关键信号轨，不在本次范围）**：982 的 must 只有 `qkv_task` 生产者
   （`keyword=迁移`），任何迁移失败任务都能满足 → 关键路 SUPPORTED。这种「producer-only must」没有
   判定语义，是关键路准确率低的根因之一；它反证了根因路「每条必须是可执行判定 + 过充分性门禁」更严格。
4. **门禁只覆盖确定性形态**：语义恒真（如「配置不正确」）仍依赖人工复核（`gate_status=warning` 或
   `needs_review`），不能宣称「门禁后无需人工」。
5. **L3 在存量上零剪枝**：10 条信号分散在 9 篇，单篇内无冗余样本；L3 的有效性由单测（判据包含 /
   证据包含 / 双形态 / 保序）与 Prompt 自检守护，**不代表**它在真实流量上同样低频或无效。

## 9. 风险与回滚

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| OR 融合放大误判 | 根因信号恒真 | `gate_version` 准入闸门；`warning` 不授予准入；存量经 regate 重审后只有 `passed` 参与 |
| 拆路后结论变 PARTIAL | 其他候选未被 rejected | 接受 PARTIAL（目标只要求「命中」，不要求「唯一」） |
| 门禁误杀 | 充分性规则过严 | 只对**确定性黑名单**（通用错误串、纯配置键名）硬拒，其余降 `needs_review` |
| 剪枝降低判别力 | L3 把「更短」当成「更弱」 | 每条剪枝规则显式带方向守卫（`stronger.mode=all` ∧ `candidate.tokens ⊆ stronger.tokens`）；证明不了即保留；4 例方向性单测 + V-029 避坑 |
| 两路采集成本上升 | 两路信号不同 | 采集按 plan 去重（同 tool+args 只执行一次，`qfk_log` 另以 matcher 参与模板指纹）；实测存量根因信号与关键信号高度重叠，增量采集少 |
| 回滚不降低采集成本 | 切 `process_only` 后根因信号仍在 plan 中 | 回滚只影响结论（只取关键路）；因根因与关键共用同一份 Verification Contract，从 plan 摘除根因会令 contract 引用缺失信号→候选 INCONCLUSIVE。需要「不采集根因」时应在抽取/发布侧关闭，而非运行时过滤 |

**回滚开关**：`KB_SIGNAL_FUSION_MODE=process_only` 把**结论**恢复到改造前（只取关键路）。

诚实边界：回滚是**结论级**而非**采集级**——在 `process_only` / `shadow` 下根因信号仍会被
compile 并按 tool+args 去重后采集（额外采集成本仍在）。这是有意选择：根因与关键信号共用
同一份 Verification Contract，从 plan 摘除根因 ref 会令 contract 引用缺失信号，把候选变成
INCONCLUSIVE（比多采一次更糟）。需要真正「零根因采集」时，应在抽取/发布侧关闭根因信号。
