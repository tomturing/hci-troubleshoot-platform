# 知识库「生产」优化分析

> **文档目的**：分析知识库"生产"环节（KBD ETL Pipeline、SOP 录入）中影响 **知识质量** 的核心问题，给出优化方案。所有优化均服务于同一目标：
>
> **唯一优化目标：提升生产知识的质量，进一步提升排障助手检索的准确性。**
>
> **生产定义**：知识从原始来源（深信服案例系统、人工编写文档）到进入平台数据库、被标记为 `draft` 状态的完整过程。
>
> **关联文档**：[知识库设计.md](./知识库设计.md) | [知识库-管理-优化分析.md](./知识库-管理-优化分析.md) | [知识库-消费-优化分析.md](./知识库-消费-优化分析.md)

## 一、现状诊断

### 1.1 KBD ETL Pipeline 整体现状

```
深信服案例系统（Portal）
        ▼
  scripts/kbd/run.py
        │
  ┌─────┴──────────────────────────────────┐
  │  Stage 1: fetch   抓取案例 HTML/附件    │
  │  Stage 2: vision  截图 OCR（LLM）      │
  │  Stage 3: import  写入 kbd_entry DB    │
  │  Stage 4: classify  AI 分类（LLM）     │
  └────────────────────────────────────────┘
        │
  Admin UI 人工审核 → published → embedding 生成
```

**当前质量问题根源**：
- KBD 内容是原始叙述文本，无结构化字段，整条做成一个向量——**导致 RAG 召回精度低**
- OCR 产出物（截图描述）纯靠 LLM，没有质量门控——**低质量内容静默进入数据库**
- AI 分类无置信度筛选——**错误分类后 RAG 检索范围从一开始就偏了**
- SOP 是线性 Markdown，不是决策树——**AI 无法程序化遍历，容易混淆分支**
- 所有 LLM 调用（OCR、结构化、分类）没有统一的输出评估机制——**质量无法度量，无从改进**

## 二、问题清单与优化方案

### 问题 1：KBD 知识结构缺失 — 整条叙述文导致 RAG 召回失准

#### 当前问题

`kbd_entry.content_md` 是从深信服 Portal 抓取的**原始 HTML 转 Markdown**，结构依赖工程师录入习惯，非常不规范：

```markdown
# 案例 34977：虚拟机开机失败
用户反映虚拟机无法开机，报错 "disk I/O error"。
检查了一下发现磁盘有问题。更换磁盘后恢复正常。
截图1: [图片OCR描述]
```

**为什么这会导致召回失准？**

RAG 检索的本质是"query 向量和案例向量的语义相似度"。用户描述的是**症状**，但当前案例向量是症状 + 根因 + 解决方案的**混合平均语义**：

```
用户 query embedding  ≈  "开机/黑屏/无响应" 方向
案例 content embedding ≈  "磁盘I/O/更换磁盘/存储写入" 方向（根因和解决方案占主导）

→ 余弦相似度低 → 相关案例召回失败！
```

症状描述在整篇叙述中占比小，被稀释。解决方案和根因文字更多，主导了向量方向——但用户在开始排障时并不知道根因，也不知道解决方案，他只能描述症状。

#### 优化方案：结构化抽取 Stage（新增 Stage 2.5）

在 Vision OCR 之后、import 之前，用 LLM 对原始案例文本做结构化抽取，拆分为独立语义字段：

**字段设计与用途**：

| 字段 | 在排障中的作用 | 是否做 embedding |
|------|------------|----------------|
| `symptoms` | **检索字段**：用户描述症状 → 匹配此向量 → 找到相似案例 | ✅ `symptoms_embedding` |
| `troubleshooting_steps` | **注入字段**：注入 AI context，告诉 AI"历史上这类问题怎么一步步排查" | ❌（全文注入） |
| `root_cause` | **假设字段**：注入 AI context，提供"可验证的假设"（"历史根因是 X，检查一下是否符合"） | ❌（全文注入） |
| `resolution_summary` | **结论字段**：简洁的最终解决方案，摘要注入 | ❌（全文注入） |
| `keywords` | **BM25 增强**：补充关键词提升全文检索召回率 | ❌（写入 tsv） |

> **说明**：`root_cause` 不做 embedding，因为排障开始时用户不知道根因，无法用根因向量检索。`root_cause` 的价值在于**注入时**给 AI 提供排查假设——"案例#34977 的根因是磁盘 I/O 错误，先验证这个方向"。

> **`troubleshooting_steps` 是核心**：这是历史排障过程中实际执行的检查步骤（有序列表），是指导当前排障的最直接参考，必须独立提取，不能和 resolution_summary 混淆。

**抽取 Prompt（v1）**：

```python
EXTRACT_PROMPT = """
你是一个故障案例结构化专家。从以下案例原文中提取信息，输出为 JSON。
缺失字段填 null，不允许编造原文没有的内容。

Schema:
{
  "symptoms": "【必填】用户最初报告的症状，一段话，保持原文措辞",
  "troubleshooting_steps": [
    "【必填】实际执行的排查步骤，有序列表，每步一条",
    "步骤2...",
    "步骤3..."
  ],
  "root_cause": "【必填】最终确认的根本原因，一句话",
  "resolution_summary": "【必填】最终解决方案的简洁描述，一句话",
  "keywords": ["关键技术词", "错误码", "组件名"]
}

案例原文：
{raw_content}
"""
```

**数据库 Schema 变更**：

```sql
ALTER TABLE kbd_entry ADD COLUMN symptoms            TEXT;           -- 症状描述（检索字段）
ALTER TABLE kbd_entry ADD COLUMN troubleshooting_steps JSONB;       -- 排障步骤（有序列表）
ALTER TABLE kbd_entry ADD COLUMN root_cause          TEXT;           -- 根本原因（注入假设）
ALTER TABLE kbd_entry ADD COLUMN resolution_summary  TEXT;           -- 解决方案摘要
ALTER TABLE kbd_entry ADD COLUMN keywords            TEXT[];         -- 关键词（BM25 增强）
ALTER TABLE kbd_entry ADD COLUMN extract_version     INT DEFAULT 0;  -- 抽取版本号（便于重新抽取）

-- 只对 symptoms 做独立向量（检索对齐用户 query）
ALTER TABLE kbd_entry ADD COLUMN symptoms_embedding  vector(1536);

-- 索引
CREATE INDEX idx_kbd_entry_symptoms_emb ON kbd_entry
    USING ivfflat (symptoms_embedding vector_cosine_ops) WITH (lists = 100);
```

**预期提升**：用户症状 query → 匹配 `symptoms_embedding`（同一语义空间），召回精度大幅提高；注入时 AI 获得结构化的排障步骤而非杂乱叙述，减少幻觉。

### 问题 2：截图 OCR 质量不稳定 — 低质量内容静默入库

#### 当前问题

- 批量运行时 82% 截图 OCR 返回"（无文字）"，API 限流导致的空返回
- OCR 结果**没有质量门控**：低质量描述和高质量描述一起进入案例正文，稀释向量语义
- 无法事后批量查询"哪些案例的截图描述是无效的"——文件系统无法 SQL 查询

#### 根本原因

OCR 输出是 LLM 产出物，必须有质量评估；但当前完全缺失。"无文字"的截图描述混入 `content_md` 后，不影响案例导入，却会污染后续的结构化抽取和 embedding 质量。

#### 优化方案 A：OCR 质量门控（拒绝低质量进入正文）

```python
def assess_ocr_quality(desc_text: str) -> str:
    """
    返回质量等级：ok / low_quality / empty
    """
    text = desc_text.strip()
    if not text or "（无文字）" in text or "无内容" in text:
        return "empty"
    if len(text) < 20:
        return "low_quality"
    # 重复字符检测（aaaaaa 类型的 OCR 乱码）
    if len(set(text)) < 5:
        return "low_quality"
    return "ok"

# 在 import stage：低质量截图描述不进入 content_md
quality = assess_ocr_quality(screenshot_desc)
if quality != "ok":
    # 记录质量标记，但不将此截图描述合并进案例正文
    mark_screenshot_quality(kbd_id, img_index, quality)
```

#### 优化方案 B：截图质量持久化到 DB（支持批量重处理）

纯文件存储无法回答"有多少案例需要重处理 OCR"。写入 DB 支持 SQL 查询，使批量重处理可操作：

```sql
CREATE TABLE kbd_screenshot (
    id              SERIAL PRIMARY KEY,
    kbd_entry_id    BIGINT REFERENCES kbd_entry(id),
    img_index       SMALLINT NOT NULL,             -- 截图序号
    original_url    TEXT,                          -- 原始附件地址
    ocr_backend     VARCHAR(20),                   -- easyocr/paddleocr/vision_llm
    ocr_quality     VARCHAR(20),                   -- ok/low_quality/empty
    ocr_text        TEXT,                          -- OCR 提取的原始文字
    vision_desc     TEXT,                          -- Vision LLM 语义描述
    created_at      TIMESTAMP DEFAULT NOW()
);
```

**DB 持久化的核心价值**（相比纯文件）：

```sql
-- 查询需要重新 OCR 的案例（文件系统无法做到）
SELECT DISTINCT kbd_entry_id FROM kbd_screenshot
WHERE ocr_quality IN ('empty', 'low_quality');

-- 统计各后端的质量分布（用于评估 OCR 后端效果）
SELECT ocr_backend, ocr_quality, COUNT(*)
FROM kbd_screenshot GROUP BY 1, 2;
```

### 问题 3：AI 分类质量无门控 — 错误分类影响整条检索链路

#### 当前问题

- classify stage 对 198 个分类做 LLM 意图匹配，返回 top-3 + 置信度
- 无置信度门控：`ai_category_conf = 0.3` 的极不确定结果也会写入 `ai_category_id`
- **后果是级联性的**：分类错误 → SOP 直查返回错误手册 → KBD 检索只在错误分类下过滤 → 整条排障链路从入口就偏了

#### 优化方案：分类置信度分级门控

```python
THRESHOLD_HIGH = 0.85   # 高置信：AI 建议可信，审核员快速确认
THRESHOLD_MED  = 0.60   # 中置信：审核员需仔细核对
# 低于 0.60 的结果：不写入 ai_category_id，标记为"需人工分类"

def apply_confidence_gate(conf: float, category_id: str) -> tuple[str | None, str]:
    if conf >= THRESHOLD_HIGH:
        return category_id, "high"
    elif conf >= THRESHOLD_MED:
        return category_id, "medium"
    else:
        return None, "low"   # 低置信不写分类，避免误导审核员
```

**数据库**：在 `kbd_entry` 增加 `ai_classify_quality VARCHAR(10)`（`high/medium/low`）。Admin UI 在 `low` 案例上显示醒目警告，让审核员意识到需要独立判断分类而非依赖 AI 建议。

### 问题 4：SOP 存为线性 Markdown — AI 无法程序化遍历决策树

#### 当前问题

SOP 通过上传 `.docx` 转 `content_md` 存储。存在：
- SOP 的本质是**有向无环图（DAG）**：节点是诊断步骤，边是条件分支
- 存成线性 Markdown = 把 DAG 强行拍平，丢失分支拓扑
- AI 拿到的是一篇线性文章，无法"在对话中按症状导航到对应分支"，极易混淆相互排斥的分支条件

#### 优化方案：SOP 采用 YAML 结构化格式

```yaml
# sop_vm_start_failure.yaml
id: sop-vm-start-failure
title: 虚拟机开机失败排障 SOP
version: "2.0"
category_id: "虚拟机-开机失败"
last_updated: "2026-05-12"

nodes:
  start:
    title: "开始：确认问题范围"
    description: |
      询问用户：是单台虚拟机还是多台同时无法开机？
      查看最近的变更操作记录。
    check:
      - prompt: "查看 vCenter 事件日志：`vcenter-cli events --vm {vm_name} --last 1h`"
    branches:
      - condition: "单台 VM 无法开机"
        next: "single_vm_diagnosis"
      - condition: "多台 VM 同时无法开机"
        next: "cluster_wide_diagnosis"
    fallback: "escalate"

  single_vm_diagnosis:
    title: "单台 VM 诊断"
    description: |
      检查 VM 配置完整性和主机资源。
    check:
      - prompt: "检查 VM 状态：`kubectl get vm {vm_name} -n {namespace}`"
      - prompt: "检查宿主机资源：`kubectl describe node {node_name}`"
    branches:
      - condition: "宿主机 CPU/内存不足"
        next: "resource_exhaustion"
      - condition: "VM 磁盘异常"
        next: "disk_issue"
      - condition: "配置文件损坏"
        next: "config_corruption"
    fallback: "unknown_single_vm"

  escalate:
    title: "升级处理"
    terminal: true
    actions:
      - "收集完整诊断信息：`kubectl logs`, `kubectl describe`, 事件日志"
      - "在工单中记录已排查的步骤和结果"
```

**迁移路径**：
1. 新建 SOP 强制使用 YAML 格式
2. 现有 10 篇 SOP 由 LLM 生成 YAML 草稿 + 人工校对
3. `sop_document` 表新增 `format` 字段（`markdown` / `yaml`），向下兼容

### 问题 5：LLM 调用缺乏评估机制 — 质量无法度量，无从改进

#### 当前问题

生产环节有 3 处 LLM 调用，均缺乏系统性评估：

| LLM 用途 | 当前评估方式 | 风险 |
|---------|------------|------|
| Stage 2：Vision OCR（截图语义描述） | 无，靠人工偶尔翻看 | 描述不准确导致案例向量语义偏移 |
| Stage 2.5：结构化抽取（symptoms/steps/root_cause） | 无 | LLM 可能编造原文没有的内容（幻觉） |
| Stage 4：AI 分类（category_id） | 有置信度但无分布统计 | 置信度虚高，实际错误率不清楚 |

**根本问题**：没有评估，就无法知道 LLM 的输出对知识质量的实际贡献，也无法科学地优化 Prompt。

#### 优化方案：建立 LLM 输出质量评估体系

**层次一：自动化规则校验（每条必做）**

在每个 LLM Stage 的输出写入 DB 之前，执行结构化校验：

```python
# Stage 2.5 结构化抽取的校验
def validate_extraction(result: dict, raw_content: str) -> ValidationReport:
    errors = []

    # 必填字段检查
    for field in ["symptoms", "troubleshooting_steps", "root_cause"]:
        if not result.get(field):
            errors.append(f"必填字段 {field} 为空")

    # 幻觉检测：抽取内容不应包含原文没有的专有名词
    # （用 keyword overlap 粗略检测）
    extracted_text = " ".join(str(v) for v in result.values() if v)
    if not has_keyword_overlap(extracted_text, raw_content, threshold=0.3):
        errors.append("抽取内容与原文相关性过低，疑似幻觉")

    # 长度合理性
    if result.get("symptoms") and len(result["symptoms"]) > 500:
        errors.append("symptoms 字段过长（>500字），可能未正确提取")

    return ValidationReport(passed=len(errors) == 0, errors=errors)
```

**层次二：抽样人工审查（定期执行）**

建立抽样审查流程，不依赖全量人工审核：

```python
# 抽样策略：每批次随机抽 5%，加上所有 validation 失败的条目
def select_for_human_review(batch: list[KbdEntry]) -> list[KbdEntry]:
    random_sample = random.sample(batch, max(1, int(len(batch) * 0.05)))
    validation_failures = [e for e in batch if e.extract_validation_passed == False]
    return list(set(random_sample + validation_failures))
```

Admin UI 增加"质量审查"模式：展示 LLM 抽取结果 vs 原文对比，审查员标记对/错，结果记录到 `kbd_entry.extract_reviewed`。

**层次三：版本对比评估（Prompt 迭代时）**

当需要改进 LLM Prompt 时，用对照组评估效果：

```python
# 评估脚本：对同一批案例跑两个 Prompt 版本，对比结果
async def evaluate_prompt_version(cases: list, prompt_v1: str, prompt_v2: str):
    results = {"v1": [], "v2": []}
    for case in cases:
        results["v1"].append(await extract_with_prompt(case, prompt_v1))
        results["v2"].append(await extract_with_prompt(case, prompt_v2))

    # 自动指标
    metrics = {
        "v1_empty_rate": calc_empty_rate(results["v1"]),
        "v2_empty_rate": calc_empty_rate(results["v2"]),
        "v1_hallucination_rate": calc_hallucination_rate(results["v1"], cases),
        "v2_hallucination_rate": calc_hallucination_rate(results["v2"], cases),
    }

    # 人工评分（抽取 20 条，每条打 1-5 分）
    return EvalReport(metrics=metrics, sample_for_human=random.sample(cases, 20))
```

**各 LLM 的具体评估指标**：

| LLM 用途 | 自动指标 | 人工审查关注点 |
|---------|---------|-------------|
| Vision OCR 截图描述 | 文本长度、关键词密度、空返回率 | 描述是否准确反映了截图内容 |
| 结构化抽取 | 字段填充率、幻觉率（keyword overlap）、步骤数合理性 | 是否准确抽取了症状/步骤，有无编造 |
| AI 分类 | 置信度分布、高置信错误率（抽样）、分类覆盖均匀度 | 低置信案例的实际正确分类是什么 |

**数据库记录评估结果**：

```sql
ALTER TABLE kbd_entry
    ADD COLUMN extract_validation_passed BOOLEAN,     -- 自动校验是否通过
    ADD COLUMN extract_validation_errors JSONB,        -- 校验错误详情
    ADD COLUMN extract_reviewed          BOOLEAN,      -- 是否经过人工抽样审查
    ADD COLUMN extract_review_score      SMALLINT;     -- 人工评分 1-5

-- 分类评估
ALTER TABLE kbd_entry
    ADD COLUMN ai_classify_quality VARCHAR(10);        -- high/medium/low（置信度分级）
```

## 三、优化优先级矩阵

| 问题 | 对知识质量的影响 | 实现复杂度 | 优先级 |
|------|--------------|----------|--------|
| 问题1：结构化抽取（症状/排障步骤/根因/摘要 独立字段） | **直接**：symptoms_embedding 对齐用户 query，召回精度根本提升 | 中（LLM + Schema + 新字段） | **P0** |
| 问题4：SOP YAML 结构化 | **直接**：AI 可程序化遍历决策树，不再混淆分支 | 中（增量迁移） | **P0** |
| 问题5：LLM 评估机制（自动校验 + 抽样审查） | **直接**：质量可度量，Prompt 优化有据可依 | 低-中 | **P0** |
| 问题3：AI 分类置信度门控 | **间接**：防止错误分类破坏 RAG 检索范围 | 低 | **P1** |
| 问题2A：OCR 质量门控 | **间接**：低质量 OCR 不进入案例正文，减少语义污染 | 低 | **P1** |
| 问题2B：OCR 结果持久化到 DB | **支撑**：使质量度量和批量重处理成为可能 | 低 | **P1** |

## 四、讨论议题
