## 1. 知识对象各负责什么

| 对象 | 内容 | 如何使用 | 不代表什么 |
|---|---|---|---|
| SOP | 已审核排障流程、决策树、变量策略 | 当前分类优先按流程排查 | 有 SOP 不代表故障已确认或已解决 |
| KBD 案例 | 标题、问题描述、报错、排查过程、根因、处理方法、截图和来源 | 参考推荐；配置完整信号后还能现场验证 | 历史根因不自动等于当前根因 |
| Signal | 采集、取值/变量、断言、依赖和证据作用 | 受控采集与确定性求值 | 信号数量不等于证据强度 |
| 语义画像 | 症状、锚点、范围、排除条件与可选澄清配置 | 为文本检索或受控验证提供可选增强 | 画像命中不等于现场确诊 |
| 发布快照 | 不可变内容、修订号、摘要和激活关系 | 固定本次使用的知识版本 | 工作稿保存不自动替换已激活版本 |
| Bundle / Collector / Collection Profile | 仿真现场或离线采集资源 | 按发布信号生成并独立审批/验证 | KBD 发布不等于这些资源已经就绪 |

SOP、案例内容、检索画像、信号与仿真资产不是同一个对象；不应为了让案例被搜索到而伪造一个信号。

## 2. “可以发布”与“可以执行”分开

| 能力 | 判定与使用 | 发布约束 |
|---|---|---|
| `reference_only` | 干净的空信号案例；按标题和问题描述推荐；不进 CDD，不生成采集器 | 内容、分类及审核要求仍保留；不要求画像、生产者或消费者 |
| `guidance_only` | 已有画像提供人工指引或未验证参考 | 画像与上下文信号成对，满足画像自身契约；不进入自动 CDD |
| `executable` | 通过信号执行契约的案例，进入强入口或受控语义验证 | 结构、变量 DAG、证据策略、只读边界、生产者和消费者覆盖等全部有效 |
| `capability_gap` / 契约错误 | 无可信验证能力或配置损坏 | 不会因标题相似自动获得执行资格；按治理或人工路径处理 |

`reference_only` 从信号文档派生，**不是**新增 KBD 生命周期状态，也不是手填到 `semantic_entry_profile.diagnosis_capability` 的新枚举。代码入口是 [knowledge_capability.py](../../../backend/shared/schemas/knowledge_capability.py)。

空信号但有过期抽取元数据、未处理拒绝候选或孤儿画像时，不能静默降级为参考知识。已有非法信号也不能通过隐藏信号错误绕过发布审核。

## 3. 生产到消费的版本链

```text
来源正文和图片
  → 导入 KBD
  → 分类 / 识图 / 可选信号生产
  → AI Proposal 与专家 Working 内容
  → 审核发布
  → 不可变 Published / active 快照
      ├─ 内容检索 → 未验证参考
      ├─ 信号执行 → CDD 证据结论
      └─ 资源同步 → 独立审批的仿真/离线资源
```

- `kbd_entry` 保存业务条目及当前工作信息；生命周期是 `draft / published / rejected / archived`。
- `kbd_revision` 保存 Proposal/Expert 等修订及父子关系。模型提案、专家确认、运行使用的修订分别追溯。
- 已发布条目修改走维护工作稿。显式发布后才切换运行时 active；版本锁冲突返回 409。
- 修改或重抽取不等于发布；运行中的证据不能归属到后来编辑的版本。
- 批量通过逐条复用发布门禁，并允许部分成功；重试创建新批次，保留原批次审计。
- 停用或归档是生命周期操作；不能通过覆盖正文冒充版本切换。

数据表、列及索引以 [desired_schema.sql](../../../database/desired_schema.sql)、[KbdEntry](../../../backend/kb-service/app/models/kbd_entry.py)、[KbdRevision](../../../backend/kb-service/app/models/kbd_revision.py) 为准。本文不再复制 SQL 定义，避免与迁移脱节。

## 4. 内容与呈现分离

原始 HTML 只提取语义文字、图片和来源，不继承厂商页面样式。正文使用平台 Markdown；图片引用、OCR/观察与人工确认分开保存。后端统一重建展示正文，前端负责样式。

截图可见文字、模型推断和专家确认是不同事实。抽取只能消费允许章节的证据；不能把解决方案里的删除/重启步骤抽成自动诊断命令。图片级成功也不能直接代替案例级完整性。

详细生产约束见 [信号抽取与建模](关键信号抽取与建模设计.md)，图像链路专项见 [图片识别](图片识别.md)。

## 5. 检索、分类清单与诊断的边界

| 服务行为 | 输入 | 输出 | 约束 |
|---|---|---|---|
| 分类知识清单 | S0 已确认分类 | 分类内已发布 SOP/KBD 及执行资格 | 不接收 Top-K 作为强信号 CDD 成员过滤条件 |
| 语义检索与参考推荐 | 用户已提交事实、发布快照、可选画像 | 待验证候选、未验证参考或补充信息 | 不能把检索分数当根因概率 |
| CDD | 可执行案例、信号与真实观察 | 候选状态和结论等级 | 相似度不得覆盖现场反证 |
| 管理端/兼容搜索 | 搜索条件 | 浏览或检索结果 | 不替代 Agent 当前分类诊断链 |

当前通用案例 embedding 包含标题、问题描述、告警及根因；标题推荐使用独立的问题侧文本，不将独立根因/解决方案字段拼入推荐向量。两种索引不能混称“标题相似度”。细节统一在 [语义检索与案例推荐](KBD语义检索与案例推荐设计.md)。

## 分类基线命名规范与叶子统一（解A，2026-10-11）

分类基线 `kb_category` 统一为「角色无关统一 ID」文法：域根 `{域}-L1`，其余叶子与分组一视同仁 `{域}-{3位序号}`，叶子/分组纯由结构性 `NOT EXISTS(parent_id)` 判定。kb-service 侧落地点：

- `routes/categories.py` `_generate_export_yaml`：导出 **leaf-only**，分组信息由每条叶子 `path` 承载，与导入器闭合往返，杜绝分组被误导出→回灌打平。
- `routes/admin.py` `_resolve_category_subtree_codes`：KBD/SOP 列表按分类筛选时用递归 CTE 展开子树，选分组即级联命中其子树叶子工单。
- `routes/classify.py` `fetch_categories_for_classify` + `repositories/category_repo.py` `create`：分类候选仅喂叶子；新增 code 缺省走 `next_node_code` 自动分配，显式 code 走 `validate_code`，编辑态 code 不可改。
- 存量迁移：`database/data-migrations/041_*.sql`（确定性 renumber/remap/flatten/purge，`category_leaf_governance_v1`）+ `database/data-migrations/review_required/042_*.sql`（158 条 KBD 绑分组→LLM 逐条重分类到叶子，需人工签字）。

完整方案与演练证据：`docs/solution/knowledge-base/events/2026-10-11-分类基线命名规范治理与叶子统一(解A)方案.md`。

## 根因信号轨与 `root_signal_json`（v2 多信号重设计，2026-10-13）

与关键信号完全解耦的第二抽取轨：从**整篇 KBD**（`content_md`）抽**全部可确证根因的定位信号**
（v2 顶层 JSON 数组，不限条数）；双形态 `executable`（携 `qfk_*` 现场判定）/ `text`（关键词包含）；
溯源分层 `trace_tier`：命中 `root_cause` 记主锚（高信任），仅命中整篇其余章节记 `content` 兑底
（强制 `needs_review=true` 转人工），整篇溯不到即拒；主锚优先。

- **数据面**：`desired_schema.sql` 新增 `root_signal_json jsonb` + CHECK `ck_kbd_entry_root_signal_json`
  （v2：仅允许 `NULL` 或 `jsonb_typeof='array'`）+ **GIN 索引** `idx_kbd_entry_root_signal_gin`
  （`jsonb_path_ops`，支撑数组内任一信号的包含查询；v1 两个标量 partial 索引对数组失效已删），
  并在 `ck_kbd_batch_job_type` 枚举里含 `extract_root_signal`。
- **它不入 `kbd_revision`**（与 `ai_category_id` 同属 AI 派生元数据）：回刷不得产生新版本、不得影响
  发布盖章。由此得到一条硬约束：写回路径**不能用 `require_mutable_kbd`**（会对 published 返回 409，
  与全库回刷需求直接冲突），且 UPDATE 只动 `root_signal_json` 一列，不触碰 `content_md`/embedding/tsv。
- **服务面**：`kb-service/app/routes/extract_root_signal.py` 提供单篇抽取（`?sync=true` 同步，否则
  202+job_id）、异步状态、冲突度只读预览三端点；输入为整篇（`content_md` 缺失回退章节拼接）；
  每次调用都经 `StrictPromptLoader` 现读 Prompt（零缓存，admin 改模板下一次即生效）；冲突度按
  **现场全库语料**逐条实测覆盖 LLM 自报值（TTL 缓存语料）；**部分成功**：单条门禁失败只丢该条并记
  `gate_errors`，不整篇失败；用**独立 `SignalJobManager` 实例**，因为 `submit()` 按 `kbd_id` 去重，与关键
  信号共用单例会让同一篇并发两类任务时拿错 job_id/结果；全门禁失败或 Loader 抛错时**不写库也不清空**。
- **批量与全库回刷**：`/batch/extract-root-signal`（按 ids）与 `/batch/extract-root-signal/backfill`
  （服务端选型：`statuses` 仅 draft/published、`only_missing`、`category_prefix`、单批上限 100），
  选型时排除已有 pending/running 明细的条目，否则驱动循环会反复排队烧 LLM；响应 `remaining` 为待刷余量。
- **人工逐条编辑** `PATCH /kbd/{id}/root-signal`（2026-10-17，对齐关键信号专家编辑体验）：请求体为
  完整根因信号数组，**保存即全量替换**（删除某条＝提交不含它的数组、新增＝追加、空数组＝清空）；
  复用抽取**同一套硬门禁**——先 `gate_signals` 去重/封顶，再逐条 `normalize_root_signal`（executable 的
  `qfk_*` 词表/args 契约/只读安全门 + 溯源逐字命中；text 的 keyword/regex + 逐字溯源），任一不合即
  **整体 422**（`ROOT_SIGNAL_NOT_CONFIRMING`，回传 `signal_text`+原因供前端定位），绝不部分落库；冲突度
  仍按现场语料实测、不采信前端自报；`prompt_revision` 标记为 `manual-edit`。与回刷同理：published 条目
  只动 `root_signal_json` 一列、不产生 `kbd_revision`、不影响发布盖章（故同样不加 `require_mutable_kbd` 守卫）。
- **Prompt 种子位置**：`database/seeds/02_system_prompts.sql`（由 Helm db-seed-job PostSync 应用）；
  **不是** `database/atlas-migrations/`——后者按规范仅放 Schema 且 `scripts/db-migrate.sh` 不会应用它，
  放错位置会使生产路由因「Prompt 不存在」而 100% 报 `PromptLoadError`。

方案、门禁与实测详情见 [根因信号抽取方案](根因信号抽取方案.md)；单测
`backend/kb-service/tests/test_root_signal_extractor.py`、`test_extract_root_signal_route.py`。

## 根因信号运行时：两条独立链路 + 晚融合仲裁（2026-10-20 重构，废除 2026-10-17 两轨并集方案）

> **本节取代** 2026-10-17 的「运行时两轨消费」：那份设计把 executable 根因归一后 **append 到 `KBD.signals`**、
> 并在 `shared/cdd` 里加 track 维度做早融合。它违反「根因信号不得影响关键信号链路」的硬约束——共享内核被污染、
> 淘汰根因链路必须改共享层、且根因发布契约残留会让第二套计划编译期全灭。本节的方案是**两套完全独立的计划 + 结论级晚融合**。

**四条硬约束（验收口径）**：① 根因信号的设计/编码不影响关键信号生产与消费整条链路；② 两条链路完整、独立、互不影响；
③ 任一条能单独启用与运行；④ 可并存赛马，后期可安全淘汰一条（删根因代码不影响关键链路，反之亦然）。

### 装配：kb-service 只做「纯新增字段」

[playbooks.py](../../../backend/kb-service/app/routes/playbooks.py) 对每条 KBD 追加一次 `**build_root_track_payload(kbd)`
（[root_signal_track.py](../../../backend/kb-service/app/services/root_signal_track.py)，唯一新增点：1 个 import + 1 次字典展开）：

| 字段 | 含义 | 谁来消费 |
|---|---|---|
| `root_signals` | 已过运行时准入闸门（`gate_version>=2` + `gate_status`）的可执行根因信号，已归一为 CDD matcher 形态 | 根因链路的第二套计划 |
| `root_executable` | 是否存在可执行根因信号（`root_signals` 非空） | 是否启动根因链路 |
| `root_snapshot_id` | 根因信号集合的 revision 指纹 | 快照可复现 |
| `root_display_anchors` | `match_type=text` 的人工核对锚点（无 acquire） | 报告展示通道 |

关键链路的字段（`signals`/`verification_contract`/`generation_metadata`/`publish_validation`/`executable`/`diagnosis_capability`…）
**取值与语义一律不变**；`playbooks._signals()` 不再合并任何根因信号。

### 编排层构造根因候选（核心：共享内核不认识根因）

`shared/cdd` **零改动**（`git diff eb420ada -- backend/shared/cdd` 为空）。根因候选由 agent-service 编排层
[root_track.py](../../../backend/agent-service/app/adapters/agents/htp/root_track.py) 的 `build_root_candidates(raw_cases)` 构造：

```python
base = kbd_from_dict(case)                  # 共用同一个 KBD 模型
kbd  = base.model_copy(update={
    "signals": root_signals,                # 只把 signals 换成根因信号
    "verification_contract": {},            # ← 关键信号的发布契约必须清空
    "generation_metadata": {},
    "publish_validation": {},
})
```

**为什么必须清空那三个字段**：`compile_signal_plan` 会用 `verification_contract` 校验「引用的 signal_id 是否都在
本计划里」。根因候选只含根因信号，若契约里还写着关键信号的 `k1`，编译期即报
`verification contract references missing signal: k1` / `expert publish validation status is invalid` / `undeclared external variables`，
所有根因候选变 `NOT_EXECUTABLE`。**真实 staging 反事实证明**：3 个可执行根因 KBD（18696/19088/44871）保留契约时
100% 编译失败，清空后 `compile_errors = {}`、4 个 signal ref / 4 次 acquisition 正常。

### 两条链路：各自 compile → 各自调度 → 各自归约 → 各自结论

| 阶段 | 关键链路（process） | 根因链路（root） | 共享？ |
|---|---|---|---|
| 计划 | `compile_signal_plan(候选KBD)` | `compile_signal_plan(根因候选)` | 否（两个 `SignalPlan` 对象） |
| 调度 | `ActiveDiagnosticScheduler` + `KBDDiagnostic` | `RootTrackDiagnostic`（独立实例） | 否（变量池/缓存互不可见） |
| 归约 | `reduce_candidates` | `reduce_candidates` | 否 |
| 结论 | `decide_conclusion` | `decide_conclusion` | 否 |
| 物理采集 | `_execute_acquirer` | 同左，但按「tool + 模板 args」物理指纹**复用关键链路输出** | 是（只复用 stdout，不复用判定） |

**关键链路结论完全不受影响**：[dual_track.py](../../../backend/agent-service/app/adapters/agents/htp/dual_track.py) 不在
`kbd_differential.py` 里插入任何根因分支，而是在 `diagnose_with_tracks` 内用**同一批 `StepResult`** 调用
`rebuild_process_track` 复算关键链路结论——即「重跑未修改的纯组件」，因此关键链路的生产/消费代码零侵入。

### 四模式与仲裁（[track_arbiter.py](../../../backend/agent-service/app/adapters/agents/htp/track_arbiter.py)，纯函数）

| 模式 | 行为 | 用途 |
|---|---|---|
| `process_only` | 只跑关键链路 | 与重构前**完全等价**（回滚基线） |
| `root_only` | 只跑根因链路 | 验证根因独立能力（赛马单跑） |
| `shadow` | 两路都跑，**结论只取关键链路**，根因结果只记录 | 灰度观察，零风险 |
| `dual`（默认） | 两路都跑，结论按仲裁融合 | 上线形态 |

仲裁真值表（**观测视图与结论视图分离**，融合明细写 `FusionOutcome.details`，不篡改各链路自己的结论）：

| 情形 | 结论 |
|---|---|
| 任一路 `EXCLUDE` 成立 | `REJECTED`（排除项与证据来源无关） |
| 任一路 `SUPPORTED` | `SUPPORTED` |
| 任一路 `CANDIDATE` | `CANDIDATE` |
| 全部 `REJECTED` | `REJECTED` |
| 全部 `NOT_EXECUTABLE` | `NOT_EXECUTABLE` |
| 其余（含全 INCONCLUSIVE） | `INCONCLUSIVE` |

**变量自足**：`root_only` 不执行关键的 `qkv_task` 生产者，故 `{{HOST}}`/`{{DATE}}` 只能来自 `env_context`
（工单/会话提供），`{{VMID}}` 无来源即 `BLOCKED`——**绝不从关键链路偷值**（偷值会把「无法判断」伪装成「已排除」）。
`dual`/`shadow` 下才用关键链路 `StepResult` 播种变量池（合法的现场上下文共享，不是判定耦合）。

### text 锚点：独立展示通道

`root_display_anchors` 由 [root_display.py](../../../backend/agent-service/app/adapters/agents/htp/root_display.py) 直接渲染为
报告末尾「根因特征（请人工核对）」小节，**零 `shared.cdd` 依赖**（纯数据入参），不进 signals/门禁/召回/仲裁。
`root_executable` 与 `root_display_anchors` 是**两条独立通道**：仅 text 的 KBD（`root_executable=False`）也必须展示锚点，
故 `investigation_agent` 的过滤条件是 `root_executable is True or root_display_anchors`。

### 赛马度量：两条链路同指标、同口径

| 指标 | 标签 | 用途 |
|---|---|---|
| `kbd_signal_track_outcome_total` | `track={process,root}` × `outcome` × `tool` | 信号级命中率：同一现场下两条链路各自的 SATISFIED / CONTRADICTED / BLOCKED 分布 |
| `kbd_candidate_fusion_total` | `fusion_mode` × `state` × `track_states` × `active_tracks` | 候选级：可区分「仅关键路命中」「仅根因路命中」「两路都命中」 |
| 日志 `signal_track_summary` | `process_level` / `root_level` / `supported_ids` / `conflicts` | 单次诊断的完整赛马快照（含 `fusion_details`） |

**信号级打点的成本边界**：根因链路在 `root_track._record_root_metrics` 写 `track=root`；关键链路由编排层在
`rebuild_process_track` 复算完成后写 `track=process`——即只在 `dual`/`shadow` 且存在根因候选时打点，
`process_only` **不为度量额外复算**（该模式的信号结果仍写入运行结果审计表）。因此赛马对比应在
`shadow`（两路都跑、结论只取关键）或 `dual` 下进行。

### 淘汰路径（赛马收敛时）

- 淘汰根因：删 `root_track.py` / `dual_track.py` / `track_arbiter.py` / `root_display.py` / `root_signal_track.py`，把
  `investigation_agent` 的调用改回 `self._kbd_diag.diagnose(...)`，并删除 `playbooks.py` 的 1 个 import + 1 次展开。
  关键链路不受任何影响（`test_signal_track_isolation.py` 在屏蔽根因模块 `sys.modules[name]=None` 后仍能编译并判定）。
- 淘汰关键：把模式固定为 `root_only` 即可；但 `RootTrackDiagnostic` **继承** `KBDDiagnostic` 以复用执行/判定原语，
  因此 `kbd_differential.py` 不能直接删除——要彻底移除关键链路，需先把执行原语抽成独立的库
  （如 `signal_runtime_primitives.py`），再删 `KBDDiagnostic`。**这是有方向的依赖：根因可独立下线，关键不能零成本下线。**
- 两种淘汰都**不需要**改 `shared/cdd`、数据库 schema。
