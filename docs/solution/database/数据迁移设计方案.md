# 数据迁移设计方案：Atlas 声明式 + ArgoCD Migration Job

## 1. 背景与问题

当前系统：

```
Git
 |
 v
Atlas 声明式模式
 |
 v
数据库 Schema
```

Atlas 声明式模式已经负责：

- 表结构（Table）
- 字段（Column）
- 索引（Index）
- 约束（Constraint）
- Schema Diff

但是业务演进过程中出现：

- 初始化数据补充
- 历史数据修复
- 字段数据回填
- 数据格式转换

这些属于**数据迁移（Data Migration）**，例如：

```sql
UPDATE system_prompt
SET stage = 'KEY'
WHERE name = 'kbd_extract_signals_v1'
  AND stage = 'KBD';
```

或者：

```sql
INSERT INTO config (key, value)
VALUES ('feature_x', 'enabled')
ON CONFLICT(key) DO NOTHING;
```

当前缺少：

- 自动执行机制
- 版本管理
- 执行记录
- CI/CD 集成

## 2. 设计原则

### 2.1 Schema 迁移与 Data 迁移分离

不要让 Atlas 声明式模式处理数据迁移。

职责分离：

| 类型 | 工具 |
|------|------|
| Schema 迁移 | Atlas 声明式 |
| Data 迁移 | Migration Runner |
| 发布编排 | ArgoCD |

最终架构：

```
                Git
                 |
                 |
        +-------+-------+
        |               |
        v               v

 Atlas Schema     数据迁移
 (desired_*.sql)  (data-migrations/)
        |               |
        |               |
        +-------+-------+
                |
                v
             ArgoCD
                |
                v
        Kubernetes Job
                |
                v
            数据库
```

## 3. Repository 设计

目录结构：

```
database/
├── desired_schema.sql        ← Atlas 声明式 Schema (DDL)
├── desired_extras.sql        ← 函数/触发器
├── data-migrations/          ← 新增：版本化数据迁移
│   ├── 001_xxx.sql
│   ├── 002_yyy.sql
│   └── 003_update_signals_stage.sql
├── atlas-migrations/         ← Atlas 迁移历史（仅 Schema）
└── seeds/                    ← 初始化种子数据
```

## 4. 数据迁移规范

### 4.1 命名规范

格式：`{版本号}_{描述}.sql`

例如：

```
001_添加默认角色.sql
002_回填用户等级.sql
003_更新信号阶段.sql
```

规则：

- 版本号永远递增
- 禁止修改已执行的迁移文件
- 新需求必须新增文件

### 4.2 幂等性要求

❌ 错误：

```sql
INSERT INTO config VALUES ('feature_x', 'true');
-- 第二次执行失败
```

✅ 正确：

```sql
INSERT INTO config (key, value)
VALUES ('feature_x', 'true')
ON CONFLICT(key) DO NOTHING;
```

### 4.3 大数据量迁移规范

禁止：

```sql
UPDATE user SET xxx = 'xxx';
-- 百万级数据会锁表
```

针对大数据量采用分批处理：

```sql
-- 分批更新，每批 1000 行
UPDATE user SET xxx = 'xxx'
WHERE id BETWEEN 1 AND 1000;
```

或使用 Migration Runner 的批量模式。

## 5. 状态管理

增加 `migration_history` 表：

```sql
CREATE TABLE IF NOT EXISTS migration_history (
    version VARCHAR(100) PRIMARY KEY,
    checksum VARCHAR(64),
    description VARCHAR(255),
    executed_at TIMESTAMP DEFAULT NOW(),
    execution_time_ms INTEGER
);
```

记录示例：

| 版本号 | 校验和 | 描述 | 执行时间 |
|---------|----------|-------------|-------------|
| 001 | abc123... | 添加默认角色 | 2026-07-15 12:00:00 |
| 002 | def456... | 回填用户等级 | 2026-07-15 12:01:00 |
| 003 | ghi789... | 更新信号阶段 | 2026-07-15 12:02:00 |

避免：

- 重复执行
- 漏执行
- 顺序错误

## 6. Migration Runner

创建 Migration Runner 脚本（集成到现有 db-migrate.sh）：

```
/app
├── db-migrate.sh
├── migration-runner.sh      ← 新增
├── desired_schema.sql
├── desired_extras.sql
└── data-migrations/
    ├── 001_xxx.sql
    └── 002_yyy.sql
```

执行逻辑：

```
启动
 |
 v
读取 migration_history 表
 |
 v
扫描 data-migrations/ 目录
 |
 v
找到未执行版本（按版本号排序）
 |
 v
执行 SQL（事务内）
 |
 v
写入 migration_history
 |
 v
继续下一个版本
 |
 v
退出
```

```yaml
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation,HookFailed

  # ... 复用现有配置
```

## 8. ArgoCD 发布流程

完整流程：

```
开发者
提交:
  - desired_schema.sql（Schema 变更）
  - data-migrations/xxx.sql（数据迁移）
        |
        v
CI 流水线
        |
        +----------------+
        |                |
        v                v
 Atlas 验证         迁移检查
        |                |
        +----------------+
        |
        v
合并到 main
        |
        v
ArgoCD Sync
        |
        v
PreSync Hook（db-migrate Job）
        |
        +----------------+
        |                |
        v                v
 数据迁移          Schema 迁移
 (migration-runner) (atlas apply)
        |                |
        +----------------+
        |
        v
应用部署
```

## 9. Hook 执行顺序

推荐顺序：

```
PreSync（同步前）:
  1. 数据迁移（migration-runner.sh）
  2. Schema 迁移（atlas schema apply）

Sync（同步）:
  3. 应用部署
```

但实际需要根据业务调整：

| 场景 | 顺序 |
|------|------|
| 新增字段 + 回填 | Schema → Data → App |
| 数据修复（无字段变更）| Data → App |
| 字段重命名 | Schema（新字段）→ Data（迁移）→ App |

## 10. 回滚策略

数据库回滚不建议依赖自动机制。

采用**前向修复（Forward Fix）**：

例如：

```sql
-- 错误的迁移
-- 004_错误状态.sql
UPDATE system_prompt SET stage = 'WRONG' WHERE ...;
```

不要回滚 004，而是新增：

```sql
-- 005_修复状态.sql
UPDATE system_prompt SET stage = 'KEY' WHERE stage = 'WRONG';
```

原因：

- 生产数据变更不可逆
- 前向修复更安全、可审计
- 避免回滚逻辑复杂化

## 11. CI 检查

流水线增加：

### SQL 语法检查

检查项：

- SQL 格式规范
- 禁止无条件 UPDATE/DELETE
- 必须包含幂等性保障

```bash
# 禁止
UPDATE user SET status = 'x';

# 必须
UPDATE user SET status = 'x' WHERE id > 0;
```

### 迁移测试

CI 创建临时数据库验证：

```bash
# 1. 启动临时 Postgres
# 2. 执行所有迁移
# 3. 验证 migration_history 完整性
```

## 12. 生产安全控制

### 数据库锁（可选）

避免多个环境同时执行：

```sql
-- 获取锁
SELECT pg_advisory_lock(12345);

-- 执行迁移
-- ...

-- 释放锁
SELECT pg_advisory_unlock(12345);
```

### 权限隔离

建议分离账号：

| 用户类型 | 权限 |
|----------|------|
| migration_user | ALTER, INSERT, UPDATE, DELETE |
| app_user | SELECT, INSERT, UPDATE |

不要共用账号。

## 13. 多环境策略

```
dev → staging → production
```

迁移要求：

- 相同 SQL
- 不同数据库
- 禁止 production-only SQL

## 14. 监控与审计

记录位置：

- `migration_history` 表（数据库层）
- ArgoCD Application Event（K8s 层）
- 日志（详细执行过程）

查询示例：

```sql
SELECT * FROM migration_history ORDER BY executed_at DESC;
```

## 决策总结

**采用方案**：

- ✅ Atlas 声明式（保持现有）
- ✅ ArgoCD PreSync Migration Job（复用现有）
- ✅ 版本化数据迁移 SQL（新增）

**不采用方案**：

- ❌ 切换 Atlas 版化迁移模式（破坏性大）
- ❌ 应用启动时迁移（启动依赖、分布式问题）
- ❌ 手工扩展 db-migrate.sh（缺乏版本管理）

这是当前架构下侵入最小、长期维护成本最低、最符合 GitOps 的方案。
