# KBD 关键信号两步处理交互统一方案

## 背景与需求

PR #677 已把 QFK 运行模型收敛为“执行输出 → 取值 → Match/Produce”，但管理台仍以两套不同页面表达同一契约：匹配模式把取值嵌套在 Matcher 内，产出变量则先显示变量名和类型，再在变量卡片中显示“声明式取值”。专家虽然能配置全部字段，却很难在首次阅读时确认执行顺序，也无法判断两种模式的取值能力是否真的一致。

关键字场景进一步放大了歧义：第一步 `extract.rows.include/exclude` 和第二步 `match.pattern` 都有关键字与 AND/OR。两者不是同一工作——前者选择要取得的记录，后者判断取得的值——但旧页面没有用稳定的信息层级表达这一点。

本轮需求是在不改变 Signal v2 Schema、后端执行语义和历史 Revision 的前提下，把管理台统一成以下两阶段模型：

```text
处理单元
├── 第一步：取值
│   ├── 取值方式
│   ├── 行选择
│   ├── 输出来源
│   ├── 结果数量
│   └── AI 后置提取
│
└── 第二步：判断 / 产出
```

## 发现的问题与分析过程

### 1. 数据契约统一，页面结构却不统一

匹配模式使用 `match.extract`，产出变量使用 `orchestrate.produces[*].extract`。两者都由 `ValueExtractEditor` 编辑，但旧页面结构不同：

```text
匹配模式：Matcher → 取值配置 → 判定配置
产出变量：变量名/类型 → 声明式取值
```

这种布局让复用停留在代码局部，用户仍然面对两套心智模型。字段名字、出现顺序、边框层级和说明文案的差异，还会让同一 Extract Schema 看起来像两种能力。

### 2. 取值关键字与判定关键字必须独立

两组关键字的形式相似，但职责不同：

```text
extract.rows.include/exclude：决定第一步取得哪些记录
match.pattern/mode：决定第二步是否返回 True
```

因此不能自动复制、合并、推导或去重，也不能把第一步的按关键字行选择弱化为 Matcher 的附属高级过滤。两组配置可以相同，也可以完全不同；平台只保证按顺序执行和分别校验各自 Schema。

### 3. 多变量不能共享一个全局取值结果

一个 Signal 可产出多个变量，例如 IP 来自完整行 + AI，VM ID 来自 JSON 路径。若页面只放一个全局“第一步：取值”，再在第二步列出多个变量，就会错误暗示所有变量共享同一个值。

因此每个变量必须拥有独立处理单元：

```text
处理单元 1：取值 A → 产出变量 A
处理单元 2：取值 B → 产出变量 B
```

### 4. “变量处理单元”和“第二步：产出变量”不是最终术语

处理单元是 Match 与 Produce 共用的抽象，不能在 Produce 分支改名为“变量处理单元”。第二步描述动作，应使用“产出”；变量名和变量类型作为该动作的参数显示。最终统一为：

```text
处理单元
第一步：取值
第二步：判断 / 第二步：产出
```

### 5. 一致性必须由共享组件保证

分别维护两套视觉相似的模板，会随着字段增加再次漂移。页面一致性必须由一个 QFK 处理编辑器和一个 ValueExtract 编辑器保证，而不是依靠开发者每次手工同步 CSS 与文案。

## 第一性原理

1. **执行事实先于业务输出**：命令失败、超时或非零退出时不进入取值，也不能返回有效 False 或写变量池。
2. **取值只回答“得到什么数据”**：完整行、文本行列、JSON 路径、结果数量和 AI 后置提取都属于第一步。
3. **判断/产出只消费第一步结果**：Matcher 不重新定义取值；变量值也不能绕过第一步另取数据。
4. **相似字段不代表相同职责**：取值关键字和判定关键字各自独立、完整、可用，只通过数据流先后关联。
5. **多个消费者必须有明确所有权**：每个 Produce 变量拥有自己的 Extract，不能依赖数组位置之外的隐式共享状态。
6. **一致性是契约的一部分**：同一字段在不同模式下必须保持相同组件、顺序、标签、默认值、说明、校验和响应式布局。

## 方案（WHAT）

### 1. 统一页面入口

QFK 编辑区使用同一个“执行结果处理”组件选择：

```text
匹配模式：输出 True / False
产出变量：校验后写入变量池
```

模式选择后始终显示可见的数据流：

```text
1 先取值 → 2 再判断
1 先取值 → 2 再产出
```

命令失败门禁固定显示在处理单元之前。

### 2. 匹配模式处理单元

```text
处理单元
├── 第一步：取值
│   └── 复用 ValueExtractEditor
└── 第二步：判断
    └── 判定类型及其确定性参数
```

Matcher 编辑器在嵌入处理单元时只显示 Predicate，不再重复显示取值区和外层 Matcher 卡片。独立使用 Matcher 编辑器的其他页面仍可显示完整两步内容。

### 3. 产出模式处理单元

每个 `orchestrate.produces[*]` 渲染一个独立处理单元：

```text
处理单元 N
├── 第一步：取值
│   └── produce.extract
└── 第二步：产出
    ├── 变量名
    ├── 变量类型
    └── 使用第一步取值结果
```

“添加变量”明确表示创建新的“取值 → 产出”处理单元。新增单元默认包含完整的 text Extract，不创建旧 `path` 字段。

### 4. 两组关键字保持完整独立

第一步仍正式提供：

```text
行选择：全部行 / 按关键字
包含关键字 / 排除关键字
包含关系 / 排除关系
区分大小写
```

第二步选择 keyword Matcher 时正式提供：

```text
判定关键字
关键字关系：OR / AND
```

前端不跨阶段复制、比较或删除关键字。后端继续依次执行 Extract 与 Predicate。

### 5. AI 后置提取保持在第一步末尾

AI 只接收确定性取值候选并返回可逐字回查的值。匹配模式由确定性 Matcher 判断 AI 后的值；产出模式在数量和类型全部校验后写变量池。AI 失败是处理失败，不冒充业务 False。

### 6. 页面与交互一致性

统一以下内容：

| 维度 | 统一规则 |
|---|---|
| 信息架构 | 处理单元 → 第一步取值 → 第二步判断/产出 |
| 字段顺序 | 取值方式 → 行选择 → 方式特有字段 → 来源 → 数量 → AI |
| 控件 | 同一概念使用同一 Element Plus 组件 |
| 标签宽度 | ValueExtract 和第二步表单统一 96px |
| 容器 | 相同步骤卡片、边框、内边距和连接箭头 |
| 状态反馈 | 每一步都有输出去向，最终显示 True/False 或变量池 |
| 响应式 | 窄屏时流程横向箭头转为纵向，字段不横向溢出 |
| 术语 | 只使用“处理单元”“第一步：取值”“第二步：判断/产出” |

## 决策依据（WHY）

### 为什么不合并取值与判断/产出

合并会让文本列、JSON 路径、AI 和 Predicate 再次互相污染，无法表达“先取状态列、再判断 running”或“先取日志行、再产出 IP”。两阶段是运行契约，不只是视觉分组。

### 为什么不弱化第一步关键字

第一步关键字是完整 Extract 能力，可独立服务完整行、文本行列和 AI。把它隐藏成 Matcher 的高级项会破坏 Produce 场景，也会错误暗示它只为最终判定服务。

### 为什么不为多个变量共享一个第一步

不同变量可能使用不同来源、路径、数量和 AI 指令。共享会制造无法表达的配置，或迫使页面再增加变量级覆盖，最终比独立处理单元更复杂。

### 为什么不继续在 KbdReviewView 中维护两套模板

旧问题本身就是两套模板漂移的结果。共享 `QfkProcessingEditor` 才能让字段顺序、术语和样式成为可测试的不变量。

## 兼容与边界

- 不修改 Signal v2 Schema、数据库表、API 和 Agent Runtime；
- 历史 Match/Produce Revision 按原结构加载，只改变编辑呈现；
- 历史 `expected/not` 继续只读兼容；
- QKV 的 `ProducesEditor` 不属于本次 QFK 两步处理单元，不改变其工具定义编辑语义；
- 真实命令执行状态仍由现有 execution/processing 契约保证，前端提示不能替代后端门禁。

## 影响范围

- `frontend/admin/src/components/editors/`：增加统一 QFK 处理组件，ValueExtract/Matcher 支持嵌入模式；
- `frontend/admin/src/views/KbdReviewView.vue`：删除两套分叉模板，接入共享组件；
- Admin 测试：新增处理单元结构、多个变量隔离、默认 Extract 和模式事件测试；
- 现行全量文档：更新 Admin 管理台设计、任务清单与 README 第一屏。

## 验收标准

- 匹配模式只显示一个“处理单元”，顺序为“第一步：取值 → 第二步：判断”；
- 每个产出变量显示独立“处理单元 N”，顺序为“第一步：取值 → 第二步：产出”；
- 页面不出现“变量处理单元”“第二步：产出变量”“声明式取值”旧术语；
- Match 与 Produce 复用同一个 ValueExtractEditor，取值字段顺序和样式一致；
- 取值关键字与判定关键字各自完整可编辑，互不复制、合并或去重；
- 更新一个变量的 Extract 不改变其他变量；
- 新增变量自动包含可保存的默认 Extract；
- Admin 组件测试、类型检查、生产构建和文档治理全部通过。
