# 分类树拖拽重排即时物化 code 方案

> 关联事实源：命名文法 `backend/shared/utils/category_code.py`；解A 治理方案 [`2026-10-11-分类基线命名规范治理与叶子统一(解A)方案.md`](../../knowledge-base/events/2026-10-11-分类基线命名规范治理与叶子统一(解A)方案.md)
> 唯一调用链标记：`repo_resequence_domain_*`（结构化日志事件，携带 `trace_id`）

## 1. 背景与根因

解A 确立铁律：**同级顺序即 code（`{域}-{3 位补零序号}`），无独立 sort 字段**。前端 `CategoryManageView.vue` 的 `sortTreeNodes` 每次 refetch 都按 `code.localeCompare` 重排树节点。

由此产生"拖拽完全无效果"的现象，根因两条：

1. `handleNodeDrop` 仅发送 `{parent_id}`，只改父子结构，**不携带位置、不改 code**。
2. 落库后 refetch，`sortTreeNodes` 按 code 字典序把视觉顺序**拍回原形**——拖出来的顺序与 code 无关，刷新即丢失。

结论：在解A 下，"改顺序"必须落到"改 code"，否则顺序无法持久化。这就是本方案要补的能力缺口。

## 2. 目标与范围

- 在管理台分类树把某个节点拖到目标父下的指定位置后，**把视觉兄弟顺序物化为整域 code**，刷新后顺序稳定不复原。
- 同步 remap 下游引用（KBD/SOP/会话按 code 引用），保证改名不产生悬空/错绑。
- **换父**（改父子结构）沿用已验证的 `update_parent_recursive`（防环 / L4 限制 / 递归级联 level·path·domain），在其之上叠加**重排**原语，二者职责正交。
- 不新增 sort 字段、不改 `parent_id`（整型主键引用 `kb_category.id`，重排 code 不动父子结构）。

## 3. 设计

### 3.1 数据流

```
拖拽落点 (el-tree)
  → handleNodeDrop 读目标父 childNodes 的新兄弟 code 全序 sibling_order
  → PUT /api/kb/categories/{code}/parent  body={parent_id, sibling_order}
  → update_parent_and_resequence → repo.move_and_resequence（**单事务**：共享一个 session + 唯一 commit）
        ├─ _do_update_parent(session, code, new_parent_id)  # 换父：结构/层级/路径级联（flush 不提交）
        └─ resequence_domain(..., ext_session=session)       # 重排：整域 DFS 重编号 + 引用 remap（复用 session、不单独提交）
     → 任一环节抛错 → async with 退出回滚（换父+重排整体撤销）→ commit 一次 → refresh 取回新 code
  → 返回 {category, resequence:{changed, mapping}}
  → 前端 fetchCategories 后按稳定 id_in_db 复位选中（整域 code 已变，只能用 id 定位）
```

### 3.2 `resequence_domain` 原语（`category_repo.py`）

前序 DFS 重编号，把目标父的兄弟顺序覆盖为 `sibling_order`、其余父按当前 code 序，整域重新分配 `{域}-{序号}`：

1. **加载本域**全部 `id/code/parent_id`（`WHERE domain=:d AND code IS NOT NULL`）。
2. **兄弟顺序校验**（防前端伪造/漏项）：`sibling_order` 去重后必须与目标父**实际子节点 code 集合完全一致**，否则抛 `ValueError`（重复 → "兄弟顺序存在重复 code"；不一致 → "兄弟顺序与目标父实际子节点不一致"）。
3. **DFS 重编号**：域根 `{域}-L1` 保持不占序号；其余节点（叶子与分组一视同仁）按访问序 `counter+1` 赋 `{域}-{counter:03d}`；子节点序优先用 `order_override`（目标父），否则按旧 code 序号，保证"分组紧跟其子树、序号连续"。
4. **无变更即 noop**：old→new 全等时直接返回 `changed=0`，不写库。
5. **单事务物化**（规避"置换碰撞"——新码常等于别的节点旧码）：
   - 捕获将被暂摘的 FK/CHECK 原始定义（`pg_get_constraintdef`），**环境若无则不新增**（staging 的 `kb_category` 当前无 `kb_category_code_format` CHECK）。
   - DROP `fk_kbd_entry_category_id` / `fk_sop_document_category_id` / `kb_category_code_format`（`IF EXISTS`）。
   - 本域全部转**唯一临时码** `'__tmp__' || id::text`（id 全局唯一 → 临时码天然互斥，彻底消除碰撞）。
   - 建 `TEMP TABLE renum_map(old_code, new_code, id) ON COMMIT DROP`，executemany 写入映射。
   - 临时码 → 新码（`UPDATE ... FROM renum_map WHERE k.id = m.id`）。
   - remap **全库按 code 引用分类的列**（旧码带域前缀，天然只命中本域引用）：有 FK 的 `kbd_entry.category_id` / `sop_document.category_id`；无 FK 但存 code 的 `kbd_entry.ai_category_id` / `conversation.category_id` / `offline_signal_collector_mapping.category_scope`（含通配 `*`，remap 用 `= old_code` 天然不命中，安全）/ `diagnosis_candidate.category_id` / `diagnosis_run.resolved_category` / `diagnosis_run.selected_category` / `diagnosis_session.resolved_category` / `diagnosis_session.selected_category`。存 label/域名而非 code 的列（`conversation.category_l1/l2`、`active_cases/case.category`、`signal_*`、`tool_definition.category`）不在范围。
   - 悬空引用置 NULL（重加 FK 前必须）。
   - 原样重建约束：CHECK 若有才重建；两个 FK 先 `NOT VALID` 再 `VALIDATE` 自校验残留悬空。

### 3.3 service / route

- `update_parent_and_resequence`（service）→ `move_and_resequence`（repo）：**单事务原子**——换父 `_do_update_parent` 与重排 `resequence_domain` 共享同一个 session，`_do_update_parent` 末尾 `flush()`（不提交，使重排同事务读到最新父子结构），重排以 `ext_session` 复用该 session（`owns_commit=False`），由 `move_and_resequence` **唯一 commit**。重排用 raw SQL 绕过 ORM，提交后 `refresh` 取回新 code。任一环节失败 → `async with` 退出整体回滚，不再存在“换父成功但顺序未物化”的部分成功态。
- `CategoryParentUpdateRequest` 新增可选 `sibling_order`；`update_category_parent` 返回体加 `resequence` 字段，日志透传 `sibling_order`。

### 3.4 前端（`CategoryManageView.vue`）

- `handleNodeDrop`：`dropType=inner` 取 `dropNode` 为父、否则取其 `parent`；从 `destParentNode.childNodes` 按当前 DOM 顺序读子节点 code 列表作为 `sibling_order`，随 `parent_id` 一并 PUT。
- 重排会改写整域 code，**只能用稳定 `id_in_db` 复位**选中与详情：记录 `prevSelId`，`fetchCategories` 后按 `(c.id_in_db ?? c.id) === prevSelId` 命中并 `fetchPublishedList(updated.code)`，找不到置 null。
- `sortTreeNodes` 保留（resequence 后 code == 视觉顺序，字典序天然自洽）。
- 后端 list（`grouped=True`）每条返回 `id=code`、`id_in_db`=DB 主键，前端据此区分业务键与稳定主键。

## 4. 风险与对抗性审查

- **remap 覆盖完整性（hotfix 补强）**：初版只 remap 4 个 FK/主链路列，以「列名含 category」全库命中检测复查发现真实漏网——`offline_signal_collector_mapping.category_scope`（staging 有 6 行真实 code，如 `虚拟机-003`）与 `diagnosis_*`（staging 空表但 `resolved_category = candidates[0]["category_id"]` 语义存 code）。已扩展为以「全库按 code 引用点」为事实源穷举（共 10 列），并对仅存 label/域名的列显式排除。悬空置 NULL 仍**仅限有 FK 的列**（`category_scope` 含通配 `*`、诊断列为历史快照，均不得被置 NULL）。
- **事务原子性（已加固）**：换父+重排下沉到 `move_and_resequence` 单事务（共享 session + 唯一 commit）。重排校验失败（如 `sibling_order` 与目标父实际子节点不一致）抛 `ValueError` → `async with` 未 commit 即退出 → SQLAlchemy 回滚，换父的 flush 一并撤销，**彻底消除**旧版“两步分提交”下“换父已提交、重排失败→树结构变了但顺序未物化”的部分成功窗口。`test_move_and_resequence_rolls_back_when_resequence_fails` 断言失败路径 `commits==0`，`..._commits_once_on_shared_session` 断言成功路径 `commits==1` 且 `resequence_domain` 复用同一 `ext_session`。
- **FK 不可延迟**：`kbd_entry`/`sop_document` 的 FK REFERENCES `kb_category(code)` 不可 DEFER，改名+remap 任一顺序都违 FK → 必须事务内 DROP→手术→重建，且重建前须清悬空（否则 VALIDATE 失败）。已覆盖。
- **置换碰撞**：纯按 id 设新码仍可能与别的节点旧码相同 → 用唯一临时码 `__tmp__||id` 中转，规避全部排列冲突。已覆盖。
- **孤儿/跨域引用**：DFS 仅访问 `parent_id IS NULL` 起连通分量；不连通的脏孤儿不重编号也不报错（非本方案引入的数据完整性问题）。
- **误置 NULL**：remap 后引用列已是新码、kb_category 亦为新码，EXISTS 命中不误清；仅真悬空才置 NULL。

## 5. 测试守护

`backend/kb-service/tests/test_categories.py`（`_fake_resequence_session` mock 分发 SELECT/pg_get_constraintdef/其余）：

- `test_resequence_materializes_group_adjacency`：目标父兄弟序覆盖后，验证"分组随子树相邻、整域序号连续"的 old→new 映射（changed=4）。
- `test_resequence_noop_when_already_canonical`：已合规（组紧跟子、序号连续）时 changed=0 不写库。
- `test_resequence_rejects_sibling_order_mismatch`：`sibling_order` 缺项 → 抛"兄弟顺序与目标父实际子节点不一致"。
- `test_resequence_remaps_all_code_referencing_columns`（`_fake_resequence_session` 记录 `executed_sql`）：断言 remap 覆盖含 `category_scope`/诊断列在内的全 10 列，且悬空清理不越界触碰含通配 `*` 的 `category_scope`。
- `test_move_and_resequence_rolls_back_when_resequence_fails`：patch 两个内核使重排抛错，断言 `_RecordingSession.commits == 0`（失败即整体回滚，无部分提交）。
- `test_move_and_resequence_commits_once_on_shared_session`：成功路径 `commits == 1`（唯一提交点），且 `resequence_domain` 以 `ext_session` 复用同一 session。

前端手动验证：拖拽某叶子到目标父指定位置 → 提示"已按新顺序重排 N 个分类编码" → 刷新页面顺序稳定 → 选中节点详情面板正确复位。
