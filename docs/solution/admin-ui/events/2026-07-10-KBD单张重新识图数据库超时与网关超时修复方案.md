## 背景与问题描述

在 KBD 管理台中，用户点击单张图片的重新识图按钮时，可能会遇到错误提示：`重新识图失败：KB Service unavailable`。

### 问题分析

1. **数据库长事务连接断开**：
   `reanalyze_kbd_images` 与 `reanalyze_single_image` 函数此前将数据库会话对象（`AsyncSession`）作为参数直接传入并由始至终持有该连接。由于重新识图需要压缩图片、从正文中解析上下文并多次调用大模型 API（伴随 client 级重试与 empty-result 外层重试），整笔操作耗时可能长达 2-6 分钟。在此期间，数据库连接在连接池中长期处于 `Idle in transaction` 状态，触发了 PostgreSQL 服务端或连接代理的空闲超时而断开，最终在最后 commit 写入时抛出 `InterfaceError: cannot call Transaction.commit(): the underlying connection is closed`。
2. **重试机制修复遗漏**：
   在此前的 PR #520 中，只为全量重新识图 `reanalyze_kbd_images` 添加了“回滚并重新建连查询后提交”的重试保护逻辑，但完全遗漏了单张图片重新识图的接口 `reanalyze_single_image`。
3. **大模型调用超时的级联叠加**：
   大模型单次调用超时 `LLM_TIMEOUT` 默认为 `60.0` 秒，客户端具备 `max_retries=2`。一旦发生 API 超时，单次识图第一阶段即消耗 180 秒（3分钟）。
   由于此前 `_vision_analyze` 将超时等调用异常吞掉并返回默认空字段，外层业务因无法感知接口出错，依然判定为“空结果”，并再次触发了“空结果重试”机制。这导致级联叠加后，单张图片重新识图的失败总用时长达 **360+ 秒（近 6.5 分钟）**，大幅超出了网关的保护时间。

---

## 方案（WHAT）

### 核心设计 1：数据库会话与耗时 API 调用彻底解耦

将原本包含 LLM 调用的长事务拆分为两个极短的事务，使长耗时的外部 API 请求完全处于数据库事务生命周期之外。
- **Stage 1 (短读取会话)**：从数据库中读取必要元数据、图片二进制及 Prompt 模板至内存中，并立即关闭 Session。
- **Stage 2 (网络调用)**：在不持有任何数据库连接的情况下，执行慢速网络大模型请求及重试。
- **Stage 3 (短写入会话)**：请求结束后开启新的极短 Session 写入并 Commit，同时配备断线自动重新查询机制。

### 核心设计 2：大模型超时调优与异常快速失败（Fail-Fast）

- **缩短超时设定**：将 `LLM_TIMEOUT` 的默认缺省时间由 `60.0` 秒下调至更加合理的 **`30.0` 秒**。
- **异常直抛（raise）**：改变 `_vision_analyze` 吞掉异常返回伪造空字段的模式。当发生超时或限流 429 等 API 级别异常时，大模型客户端重试 3 次后直接抛出异常，不再执行后续重复的多轮“空结果重试”。
- **网关超时保障**：将网关代理 `/reanalyze-image/{seq}` 端点的超时由 `120.0` 秒提高到 `240.0` 秒。

---

## 决策依据（WHY）

### 为什么选择 Fail-Fast 而非无限增大超时时间

1. **避免用户请求无限挂起**：无限增高网关超时会导致前端转圈时间过长，甚至可能因浏览器或中间 Nginx 超时被强行切断，造成不好的用户体验。
2. **快速暴露与处理故障**：大模型 API 重试 3 次（共 90 秒）依然不通时，表明远端服务极大概率已出现故障（如 429 频控或服务下线）。应当立即快速抛错（Fail-Fast），中断不必要的二次重试，并在网关防护时间内回传真实错误原因。

## 验收标准

- [ ] 单张/全量重新识图期间，数据库连接池不应保持闲置事务。
- [ ] 大模型接口发生 429 限流或超时时，总重试与报错返回时间被控制在 90 秒以内（快速失败），不触发空结果二次重试。
- [ ] 验收成功通过，测试 Case `26890` 的 `images_json` 在成功时能写入，在失败时能秒级报错返回实际错误。
