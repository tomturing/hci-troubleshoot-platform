## 背景与问题描述

在 KBD 管理台中，用户点击单张图片的重新识图按钮时，可能会遇到错误提示：`重新识图失败：KB Service unavailable`。

### 问题分析

1. **数据库长事务连接断开**：
   `reanalyze_kbd_images` 与 `reanalyze_single_image` 函数此前将数据库会话对象（`AsyncSession`）作为参数直接传入并由始至终持有该连接。由于重新识图需要压缩图片、从正文中解析上下文并多次调用大模型 API（伴随 client 级重试与 empty-result 外层重试），整笔操作耗时可能长达 2-6 分钟。在此期间，数据库连接在连接池中长期处于 `Idle in transaction` 状态，触发了 PostgreSQL 服务端或连接代理的空闲超时而断开，最终在最后 commit 写入时抛出 `InterfaceError: cannot call Transaction.commit(): the underlying connection is closed`。
2. **重试机制修复遗漏**：
   在此前的 PR #520 中，只为全量重新识图 `reanalyze_kbd_images` 添加了“回滚并重新建连查询后提交”的重试保护逻辑，但完全遗漏了单张图片重新识图的接口 `reanalyze_single_image`。
3. **网关代理超时时间不足**：
   在 `api-gateway` 路由中，单张图片识图代理超时被设定为过短的 `120.0` 秒。一旦 LLM API 连接卡顿或重试，网关首先触发超时并中断，向前端返回 `503 Service Unavailable`。

---

## 方案（WHAT）

### 核心设计：数据库会话与耗时 API 调用彻底解耦

将原本包含 LLM 调用的长事务拆分为两个极短的事务，使长耗时的外部 API 请求完全处于数据库事务生命周期之外。

### 具体步骤

1. **Stage 1: 极短的读取事务**  
   创建 `db_session`，读取 KBD 元数据、Prompt 模板及图片二进制到本地内存中，读取完毕后立即关闭事务并释放数据库连接。
2. **Stage 2: 纯网络调用**  
   在不占有任何数据库连接的情况下，调用 Vision LLM 接口，并在需要时进行重试。
3. **Stage 3: 极短的写入事务**  
   重新向连接池索取一个新的短暂 `db_session`，再次查询定位到该 KBD Entry，更新 `images_json` 字段与 Markdown 正文，提交并关闭。同时为该阶段加入断线重试的安全帽。
4. **提升网关超时**  
   将网关 `/reanalyze-image/{seq}` 端点的超时由 `120.0` 秒提高到 `240.0` 秒。

---

## 决策依据（WHY）

### 为什么选择解耦方案而非仅添加重连重试

1. **保障连接池不被饿死**：若识图接口长期占有 DB 连接，一旦有较多并发识图请求，会迅速耗尽数据库连接池（`pool_size=20`），直接影响到主线查询与写入业务的稳定性。
2. **从根本上规避 Idle 超时**：解耦后，事务只占用数毫秒，彻底从根源上消除了 idle 事务因外部 API 慢而导致的断线报错。
