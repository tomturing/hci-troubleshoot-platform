## 背景与问题描述

在 KBD 管理台中，用户点击单张图片的重新识图按钮时，可能会遇到错误提示：`重新识图失败：KB Service unavailable` 或 `重新识图失败：识图失败：Request timed out`。

### 问题分析与测试链路排查

为了定位大模型请求发生 `Request timed out` 的根本原因，我们对 `kb-service` 容器网络及大模型 API 网关展开了多维度的控制变量测试：
1. **数据库读取与图片压缩**：完全正常（耗时 <1s）。证明图片读取与 Pillow 压缩算法并非瓶颈。
2. **容器与宿主机网络链路**：完全正常。使用 `httpbin.org/post` 测试 100KB 大数据包的 HTTP 请求，无论是宿主机还是 Pod 内部均在 1s 内返回，排除了 K8s MTU 导致的大包碎片丢失和 Clash 网卡代理的全局阻断。
3. **OpenTelemetry 自动注入**：排除。我们排除了 `opentelemetry-instrumentation-httpx` 拦截后进行原生请求，仍然挂起。
4. **模型连接与多模态负载差异**：
   - 文本请求：调用 `qwen3.5-plus` 发送 `"hello"` 在 5s 内即返回。
   - **大文本/多模态请求**：向 `coding.dashscope.aliyuncs.com` 发送 >100KB 大文本或携带 base64 格式 `image_url` 的图片请求时，**所有模型（qwen3.5-plus、glm-5、qwen3.7-plus、kimi-k2.5）均无一例外陷入无限挂起，最终被 `LLM_TIMEOUT` 强制截断，导致 `Request timed out` 报错。**
   - **传 URL 格式请求**：一旦将 `image_url` 改为非 Base64 的 public HTTP 链接，该网关立即（在 5s 内）返回 `400 BadRequest`。

### 根因分析
`coding.dashscope.aliyuncs.com` 是阿里云百炼专为“编程计划（Coding Plan）”提供的专用域名，与 `sk-sp-` 开头的 API Key 绑定。该网关专门用于低延迟文本和代码类任务（如代码补全、对话），**其代理路由或解析组件对多模态 Base64 格式的大 Payload 负载支持存在缺陷，直接在网关级丢弃或挂起 TCP 流**，导致后端请求永久挂起。

## 方案（WHAT）

### 核心设计 1：数据库会话与耗时 API 调用彻底解耦

将原本包含 LLM 调用的长事务拆分为两个极短的事务，使长耗时的外部 API 请求完全处于数据库事务生命周期之外。
- **Stage 1 (短读取会话)**：从数据库中读取必要元数据、图片二进制及 Prompt 模板至内存中，并立即关闭 Session。
- **Stage 2 (网络调用)**：在不持有任何数据库连接的情况下，执行慢速网络大模型请求及重试。
- **Stage 3 (短写入会话)**：请求结束后开启新的极短 Session 写入并 Commit，同时配备断线自动重新查询机制。

### 核心设计 2：大模型超时调优与异常快速失败（Fail-Fast）

- **缩短超时设定**：将 `LLM_TIMEOUT` 的默认缺省时间由 `60.0` 秒下调至更加合理的 **`30.0` 秒**。
- **异常直抛（raise）**：改变 `_vision_analyze` 吞掉异常返回伪造空字段的模式。当发生超时或限流 429 等 API 级别异常时，大模型客户端重试 3 次后直接抛出异常，不再执行后续重复的多轮“空结果重试”。
- **网关超时保障**：将网关代理 `/reanalyze-image/{seq}` 端点的超时由 `120.0` 秒提高到 `240.0` 秒。

### 核心设计 3：多模态识图独立 API 端点分流（LLM_VISION_BASE_URL）

为了规避编程计划网关挂起多模态大包的限制，将文本与多模态的 LLM 通道进行彻底的**端点分流**：
- **新增环境变量支持**：`kb-service` 增加 `LLM_VISION_BASE_URL` 和 `LLM_VISION_API_KEY`（优雅回退至通用 `LLM_BASE_URL`/`LLM_API_KEY`）。
- **Dev/Staging/Prod 分流策略**：对于多模态识图服务，配置为通用的标准百炼网关（`https://dashscope.aliyuncs.com/compatible-mode/v1`）并搭配通用的 `sk-` 标准版 API Key（如 Staging 环境中的 key 均可正常多模态识图），从而完全绕开存在缺陷的 `coding` 编程专有子域。

## 决策依据（WHY）

### 为什么选择 Fail-Fast 而非无限增大超时时间

1. **避免用户请求无限挂起**：无限增高网关超时会导致前端转圈时间过长，甚至可能因浏览器或中间 Nginx 超时被强行切断，造成不好的用户体验。
2. **快速暴露与处理故障**：大模型 API 重试 3 次（共 90 秒）依然不通时，表明远端服务极大概率已出现故障（如 429 频控或服务下线）。应当立即快速抛错（Fail-Fast），中断不必要的二次重试，并在网关防护时间内回传真实错误原因。

## 验收标准

- [ ] 单张/全量重新识图期间，数据库连接池不应保持闲置事务。
- [ ] 大模型接口发生 429 限流或超时时，总重试与报错返回时间被控制在 90 秒以内（快速失败），不触发空结果二次重试。
- [ ] 支持通过配置 `LLM_VISION_BASE_URL` 和 `LLM_VISION_API_KEY` 独立路由 Vision 识图的 API 链路，成功绕过编程计划网关挂起大包的瓶颈。
- [ ] 验收成功通过，测试 Case `26890` 的 `images_json` 在成功时能写入，在失败时能秒级报错返回实际错误。
