# 分类树「合并子分类到本节点（折叠为叶子）」方案

> 日期：2026-10-12 ｜ 范围：kb-service 后端 + admin 前端分类管理页
> 关联：`docs/solution/admin-ui/events/2026-10-11-分类树拖拽重排即时物化code方案.md`、`database/data-migrations/review_required/043_collapse_vm009_group_to_leaf.sql`

## 1. 背景与动机

运维在整理分类基线时常需「删除某分组下的叶子、把该分组本身变成叶子」。典型诉求：删除 `虚拟机-009`（迁移分组）下的 L4 叶子 `010~015`，让 `虚拟机-009` 从分组退化为叶子并承接原 L4 的全部 KBD/SOP。

**为什么不能拆成「先批量把叶子 KBD 设为父节点 → 再删叶子」两步**（第一性原理）：

- `kbd_entry.category_id` / `sop_document.category_id` 对 `kb_category(code)` 的外键是 `ON DELETE NO ACTION`——既不 CASCADE 也不 SET NULL。有引用即拒删，既不会自动上移、也不会自动置空。
- 解A 铁律 + 应用层门禁 `is_category_leaf`：KBD/SOP 只能绑**叶子**。而删除叶子前父仍是分组，把 KBD 绑到分组会被发布门禁 422 拒绝。
- 已发布 KBD 受 `require_mutable_kbd` 写保护（409），批量改分类根本写不进。
- 两步之间（尤其中断）会留下「已发布 KBD 挂分组」的违规脏态——正是 042 迁移要清除的回潮。

结论：必须把「改绑 + 删除」合为**一个原子动作**，提交瞬间父自动无子→成叶子，终态合规、无中间脏态。本方案即 `review_required/043` 迁移的**产品化**。

## 2. 设计

### 2.1 后端（单事务原子折叠）

- `category_repo.py`
  - 新增模块级常量 `_CATEGORY_CODE_REF_COLUMNS`（全库 10 个「按 code 引用分类」的列，与 `resequence_domain` 同一事实源）与 `_DESCENDANTS_CTE`（递归后代，不含自身）。
  - 新增 `collapse_subtree_to_leaf(code)`：① 父存在性 + 域根拒绝；② 递归取全部后代，空则幂等 no-op（不写不提交）；③ 10 列改绑 `后代码 → 父码`（FK 因父码存在全程满足）；④ 单条 `DELETE ... WHERE id IN (SELECT id FROM d)` 删全部后代（FK NO ACTION 语句末检查，父子同删无碍）；⑤ 递归重建 `level`/`path_labels`；⑥ verify 门禁：父必须已成叶子 + 全库零悬空，否则抛 `ValueError` 整体回滚；⑦ **整域重排**（见 §2.1.2）；⑧ 唯一 `commit`，按稳定主键回取重排后的新码返回。
- `category_service.py`：`collapse_to_leaf(code)`，仅在 `collapsed_children>0` 成功后刷新内存缓存；失败异常上抛不刷缓存。
- `categories.py`：`POST /api/kb/categories/{code}/collapse-to-leaf`，`ValueError→400`；响应原样透传 repo 结果（含 `resequence` 摘要与重排后的 `code`）。

### 2.1.2 折叠后整域重排（消除 code 编号空洞，承接解A）

- **问题**：折叠删除后代后，同级 code 出现编号空洞（如 `010~015` 消失但后续兄弟仍为 `016`），违反解A「同级顺序即 code、连续无空洞」。首版折叠未重排，故 `虚拟机-006` 折叠 `009` 后其兄弟显示为 `007/008/009/016`。
- **修复**：在同一事务、verify 通过后、唯一 commit 之前，复用 `resequence_domain(domain, parent_id=None, sibling_order=None, ext_session=session)`——`sibling_order=None` 表示**不覆盖任何父的子女顺序**，仅按当前相对顺序对整域跑一次前序 DFS 连续重编号，并 remap 全库 10 个按 code 引用列（复用拖拽重排同款逻辑与临时码规避碰撞/约束暂摘重建）。折叠与重排共享同一 session 的**唯一提交点**，任一失败整体回滚，杜绝「内容已折叠但 code 未重排」的部分态。

### 2.1.1 网关代理（关键调用链，首版遗漏致 404）

- admin 前端的 `/api/kb/categories/*` **不直连 kb-service**，而是打到 api-gateway 的 `categories_router`（`routes/kb.py`，prefix `/api/kb/categories`，`Depends(require_admin)`）。该 router **逐条枚举**代理路由（`/{code}`、`/{code}/parent`、`/{code}/hit`、`/import` 等），非通用透传。
- **首版只在 kb-service 加了端点、漏加网关代理路由**，导致浏览器点击「确认合并」时网关返回 FastAPI 风格 `404 {"detail":"Not Found"}`（可观测性上表现为 `X-Trace-Id` 存在但状态 404）。
- **修复**：`routes/kb.py` 新增 `@categories_router.post("/{code}/collapse-to-leaf")` → 以 `_internal_auth_headers()` 代理到 kb-service 同名下游路径（无请求体）。

### 2.2 前端（防误点的详细确认）

- `useCategories.ts`：导出纯函数 `collectSubtreeInfo(node)`（子孙总数 + 直接子节点名清单），与组件解耦便于单测。
- `CategoryManageView.vue`：
  - 仅对**分组节点**（`data.children?.length`）在两处节点操作区（主树 + 分支树）显示「合并子分类到本节点」按钮（`FolderDelete` 图标）。
  - `handleCollapseToLeaf` **不直接执行**：先弹 `ElMessageBox.confirm`（`dangerouslyUseHTMLString`），详述「将删除 N 个子孙 / KBD·SOP·会话·诊断引用统一改绑到本节点 / 本节点转为叶子 / 细分粒度将合并丢失」并列出将被删子分类清单，按钮文案「我已了解风险，确认合并」+ 危险色，用户确认后才调后端并刷新。确认后 `fetchCategories()` 重取即自动呈现 §2.1.2 重排后的连续 code（前端无需改码逻辑）。

### 2.2.1 折叠父节点被「重弹」修复（点 006 箭头无反应）

- **根因**：树用 `:default-expanded-keys="expandedKeys"`（`node-key=id_in_db`）维护展开态。Element Plus 的 `default-expanded-keys` watcher 在数组变化时会对数组里每个 key 调 `node.expand(null, autoExpandParent=true)`——**展开子节点会向上冒泡自动展开其父**。当用户选中了 006 子树内的节点（如刚折叠的 `009`），其 key 残留于 `expandedKeys`；点击 006 折叠箭头时，旧 `handleNodeCollapse` 仅移除 006 自身 key，watcher 重跑仍会对残留的子孙 key 调 `expand(...,true)` 冒泡把 006 重新弹开，表现为「箭头点了没反应」。020 无被钉子孙故正常。
- **修复**：`useCategories.ts` 新增纯函数 `collectSubtreeKeys(node)`（递归收集节点自身 + 全部子孙的 `id_in_db ?? id`）；`handleNodeCollapse` 改为折叠时把**整棵子树的 key** 一并移出 `expandedKeys`，令 watcher 无可冒泡的残留子 key，折叠即时生效。

## 4. 风险与边界

- **域根不可折叠**：`is_domain_root_code` 直接拒绝，避免摧毁整域。
- **语义粒度损失**：折叠会把子分类的细分（冷/热迁移、跨/同存储）合并丢失，确认框已显式告警。
- **深子树**：递归 CTE 支持任意深度（不止 L4），一次性把整棵子树归并到目标父。
- **与 043 的关系**：043 为一次性 SQL 迁移（review_required，不自动应用）；本端点为可反复调用的 UI 原子操作，二者逻辑等价、互为补充。
