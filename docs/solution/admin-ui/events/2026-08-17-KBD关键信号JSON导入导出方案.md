# KBD 关键信号 JSON 导入导出方案

## 背景与需求

KBD 审核详情页只支持表单逐字段录入信号：「新增信号」选类型 → 内联编辑 40+ 个字段。在实际审核中产生两个痛点：

1. **跨 KBD 复用成本高**：一条成熟信号模式（例如"集群 ping + 丢包阈值判定"、KBD 27123 的"lsof 占用链"）要在每篇类似案例里重新手填；
2. **文档/协作与界面断层**：《KBD审核发布操作指南》、方案文档和 Agent 辅助产出的信号示例都是 `signals_json` v2 JSON 形态，审核员无法直接应用到页面，只能逐字段转录，转录过程本身又容易引入错误。

后端保存链路本就是整份 `signals_json` 提交（前端 `persistSignalList` → PATCH `/api/v1/kbd/{id}` 或 `/maintenance`，`reconcileSignalContract` 重建 `verification_contract.evidence_policy`），因此本功能实现为**纯前端改动**，无新后端接口。

## 已确认的交互决策

| 决策点 | 结论 |
|---|---|
| 导入合并语义 | **仅追加**，绝不覆盖/删除现有信号；不提供整份替换模式 |
| ID 冲突 | 与现有信号或批次内其他导入信号冲突时自动用 `createSignalId()` 重新生成，并在解析摘要中提示数量 |
| 导入信号的审核门槛 | provenance 统一重置为 `needs_review: true`（保留 Schema 允许的来源事实键），必须经 Signal Review 复核后才能发布 |
| 导出范围 | 仅单条信号「复制 JSON」（剪贴板），不做整份文档导出与文件下载 |
| 入口位置 | 「导入信号」按钮在信号区域 header「新增信号」旁；「复制 JSON」在每条信号卡片操作区 |

## 实现结构

| 文件 | 职责 |
|---|---|

| `frontend/admin/src/utils/signalImport.ts` | 导入/导出纯逻辑：`parseImportedSignalsJson`、`assignImportedSignalIds`、`countImportIdRegenerations`、`buildImportAnnotations`、`serializeSignalForExport`，零 Vue/fetch 依赖 |

## 导入 JSON 形态与归一化规则

接受三种形态，按序识别：顶层数组 → 信号数组；对象含 `signals` 数组 → 完整文档（只取 signals）；对象含对象型 `acquire` → 单信号。

**本地拦截（不发请求）**：空文本、JSON 语法错误、顶层非对象/数组、`signals` 非数组、元素非对象/缺 acquire/tool 为空（指明第几条）、超过 2MB 或 200 条。

**本地静默归一化（摘要展示）**：

| 归一化项 | 规则 | 原因 |
|---|---|---|
| role | 缺失/非法 → `must` 并计数 | `reconcileSignalContract` 按 role 重建 evidence_policy |
| id | 数字 → 字符串 | `signal.v2.schema.json` 要求 string |
| provenance | 仅保留 Schema 允许键（category/method/source_section/confidence/risk/needs_review/evidence/source_refs），强制 `needs_review: true` | Schema 为 `additionalProperties: false`，`expert_created` 等键不剥必 422；evidence/source_section/source_refs 是卡片「来源证据」区消费的事实，保留以免溯源空白 |
| review | 删除 | 审核状态不是内容，不能跨 KBD 携带 |
| 未知顶层键 | 剥离并记录 | signal 顶层同样 `additionalProperties: false` |
| match/orchestrate/args 缺失 | null / {} / {} | 对齐现有信号结构 |
| 文档顶层字段 | `verification_contract`、`generation_metadata`、`publish_validation` 等丢弃并记入摘要 | contract 由 `reconcileSignalContract` 按最终列表重建；`generation_metadata` 是不可变生产追溯事实，禁止被外来文档覆盖 |

**交给后端 422（前端不复制契约）**：逐工具 `acquire.args` 校验、match 内部结构、match/produces 互斥、变量依赖图。422 经 `buildSignalRequestError` 人类化后展示在弹窗，**文本保留、弹窗不关**供修改重试；PATCH 原子失败，内容未落库。

## 保存与失败路径

- 提交采用 `duplicateSignal` 的 append + `persistSignalList` 模式（非 `addSignal` 的本地草稿模式）：基线为 `signalList`（含暂存编辑与本地草稿，一并提交），导入信号追加在后；
- 每条导入信号生成一个 `change_annotation`（`signal_id` + 审核员选择的 `reason_code` + 可选备注），reason_code 复用现有 `changeReasonOptions`，满足后端 `normalize_change_annotations` 对 REASON_CODES 与 signal_id/path 的要求；
- 保存成功后 `refreshOpenedDetail()` 内部已含 `reviewCurrentSignals({ silent: true })`，needs_review 信号自动进入 Signal Review 结果，无需额外调用；
- lock_version 409（并发修改）：弹窗不关、文本保留，提示刷新后重试；不做自动 rebase 重放；
- maintenance 模式：`kbdEditEndpoint` 按条目状态自动选 `/maintenance`，导入无特殊分支。

## 导出（复制 JSON）

`serializeSignalForExport` 剥离 provenance/review 审核态字段后缩进序列化；剪贴板不可用（非 secure context/权限拒绝）时降级 `execCommand('copy')`，再失败提示手动复制。复制是只读操作，不受 `canEditCurrent` 限制；导出产物可直接粘贴回导入弹窗（roundtrip 有单测覆盖）。

## 测试覆盖

`frontend/admin/src/utils/__tests__/signalImport.spec.ts`（31 用例）：三形态解析、结构错误下标准确、超量/超大拦截、role/id/provenance/review/未知键归一化、ID 冲突与批次内重复、干跑计数与实际一致、annotations 结构、导出 roundtrip。

组件级未做 mount 测试（KbdReviewView 初始化依赖过重，现有 spec 均为轻依赖视图），以 PR 描述中的手工验证清单替代。

## 已知边界

- **重复导入不去重**：二次导入同一份 JSON 会再次追加（ID 全部重生），语义去重不可判定，靠弹窗说明与操作指南提醒；
- **多值变量/循环采集不支持**：一条信号不能对数组变量逐元素执行（如 ping 全部 iSCSI 服务器），需拆多条信号或收窄目标，与平台既有能力一致。
