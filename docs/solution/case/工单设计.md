## 2. 工单状态设计

```mermaid
stateDiagram-v2
    [*] --> created : POST /api/cases（工单创建）

    created --> confirmed : conversation-service 在 S0 完成后触发\n（写入 category_id）
    created --> cancelled : DELETE /api/cases/{id}

    confirmed --> in_progress : 用户选 C（升级人工）
    confirmed --> resolved : 用户选 A（问题已解决）
    confirmed --> cancelled : /close 命令 / 超时 / 管理员操作

    in_progress --> resolved : 人工完成
    in_progress --> closed : 直接关闭
    in_progress --> cancelled : 撤单

    resolved --> closed : Scheduler 回收 Pod 完成回调

    closed --> [*]
    cancelled --> [*]
```

**状态语义**：

| 状态 | 含义 | 对应 diagnostic_stage |
|------|------|----------------------|
| `created` | 工单创建，S0 意图识别进行中 | S0 |
| `confirmed` | 故障分类已确认，AI 推理进行中 | S1-S6 |
| `resolved` | 用户确认问题已解决，等待 Pod 回收 | S6（用户选 A 后）|
| `closed` | 终态，所有资源已释放 | 无 |
| `in_progress` | AI 退出，转人工处理 | S6（用户选 C 后）或 S0 失败 |
| `cancelled` | 用户放弃 / 超时 / 管理员关闭 | 任意 |

### 2.1 特殊转换路径

#### S0 意图识别失败（跳过 confirmed）

当 S0 阶段无法成功识别故障类型时（如用户描述模糊、反复分类失败），采用**特殊转换路径**：

```
created → in_progress (跳过 confirmed)
```

- **触发条件**：conversation-service 连续 S0 分类失败超过阈值
- **close_reason**：`s0_classification_failed`
- **目的**：跳过 AI 推理流程，直接移交人工处理

#### close_reason 枚举值

| 值 | 含义 | 适用场景 |
|---|------|---------|
| `user_command` | 用户主动关闭 | 用户发送 `/close` 命令 |
| `timeout` | 超时关闭 | 工单长时间无响应 |
| `abandon` | 用户放弃 | 用户断开连接或退出 |
| `admin_close` | 管理员关闭 | Admin UI 手动关闭 |
| `escalated` | 升级人工 | S6 用户选 C，转人工 |
| `s0_classification_failed` | S0 分类失败 | S0 意图识别失败直接转人工 |

## 3. 与对话诊断阶段的对应关系

> `case.status` 是业务合同层，面向用户/客服；`conversation.diagnostic_stage` 是 AI 推理内核层，面向 AI 过程。二者**正交独立**运行，仅在 5 个同步点发生状态联动。

### 3.0 诊断阶段常量定义

为避免代码中硬编码字符串，conversation-service 在 `app/models/diagnostic_state.py` 中集中定义：

```python
class DiagnosticStage:
    """诊断阶段常量"""
    S0_INTENT = "S0"        # 意图识别
    S1_LOCATION = "S1"      # 故障定位
    S2_HYPOTHESIS = "S2"    # 假设生成
    S3_VERIFICATION = "S3"  # 验证执行
    S4_ROOT_CAUSE = "S4"    # 根因确认
    S5_SOLUTION = "S5"      # 解决方案
    S6_CLOSURE = "S6"       # 验证闭环
    S0_FAILED = "S0_FAILED" # S0 意图识别失败（内部标记）

# 阶段标签映射（用于 UI 展示）
STAGE_LABELS = {
    DiagnosticStage.S0_INTENT: "S0-意图识别",
    DiagnosticStage.S1_LOCATION: "S1-故障定位",
    # ... 其他阶段
}
```

**使用规范**：
- 所有代码引用诊断阶段时必须使用常量，如 `DiagnosticStage.S0_INTENT`
- UI 展示时使用 `STAGE_LABELS[stage]` 获取中文标签
- `S0_FAILED` 仅用于内部状态标记，不写入 `conversation.diagnostic_stage` 字段

### 3.1 两层状态对照

```
business layer ──── case.status ────────────────────────────────────────────────
                 created     │    confirmed       │  resolved/in_progress │ closed
                             │                   │                       │
AI layer ──── conversation.diagnostic_stage ────────────────────────────────────
                  S0         │ S1 → S2 → S3/S4/S5 → S6                  │
                             │                   │                       │
                sync point 1 │              sync point 2/3          sync point 4
                (S0完成)      │           (S6 用户选 A or C)         (Pod 回收完成)
```

### 3.2 同步点明细

| 同步点 | 触发事件 | case.status 变化 | diagnostic_stage 变化 | 触发服务 |
|--------|---------|----------------|----------------------|---------|
| **SP-1** | S0 分类确认完成，`category_id` 写入 | `created → confirmed` | `S0 → S1` | conversation-service |
| **SP-1a** | S0 分类失败，直接转人工 | `created → in_progress`（跳过 confirmed）| 不变 | conversation-service |
| **SP-2** | S6 用户选 **A**（已解决） | `confirmed → resolved` | 保持 S6 | conversation-service |
| **SP-3** | S6 用户选 **C**（升级人工） | `confirmed → in_progress` | 保持 S6 | conversation-service |
| **SP-4** | Scheduler Pod 回收完成 | `resolved → closed` | 不变 | scheduler-service |
| **SP-5** | 用户 `/close` / 超时 / 管理员 | 任意 → `cancelled` | 不变 | case-service |

> **SP-1a 说明**：当 S0 连续失败时，采用特殊路径直接转入 `in_progress`，此时 `close_reason = s0_classification_failed`。

### 3.3 设计原则

1. **case-service 不直接感知 diagnostic_stage**：case-service 只暴露 `PUT /internal/cases/{id}/status` 接口，由 conversation-service 在适当时机调用，不主动轮询对话层。
2. **created 阶段不等于"未开始"**：工单创建后 AI 立即启动 S0（意图识别），`created` 代表"AI 正在识别故障类型"，而不是"等待处理"。
3. **S6 之后 case.status 不可再回 confirmed**：用户选 B（新报错）时只回退 `diagnostic_stage` 到 S1，`case.status` 保持 `confirmed` 不变，保证工单级别的连续性。
4. **cancelled 可从任意状态转入**：case-service 维护此规则，conversation-service 收到 cancelled 事件后停止推理。

### 6.1 工单号：唯一、可由用户指定，日志收集可跨客户端复用

工单号只有一个：`case.case_id`（`Q + YYYYMMDD + 5 位序号`）。历史上只由
`generate_case_id()` 生成；2026-10-23 起支持用户在日志收集入口显式指定。

规则：

- 格式与日期在 API 层强校验（`^Q[0-9]{8}[0-9]{5}$` + 日期可解析）；库层
  `ck_case_id_format` 兜底（允许 5~6 位序号，兼容同日溢出）；
- `generate_case_id()` 只统计 `^Q当天[0-9]{5,6}$` 的号：用户手工号参与 MAX 顺延以避免碰撞，
  非法/他日格式不进入 `CAST`，否则一个异常号会让当天所有自动建单 500；
- 日志收集入口 `POST /api/cases/resolve`：工单已存在则复用（不校验归属），不存在则用该号
  建档（`metadata.source=log_collect`），并发由主键冲突兜底；
- 日志任务鉴权从"工单归属"改为 `created_by`：同一工单号下不同客户端的任务互相隔离，
  只能看到/操作自己创建的任务；409 只返回脱敏摘要（状态/进度/是否本人）；
- `log_collect_task.ticket_no` 已删除：`acli -s` 与产物名直接使用 `case_id`；
- 交付完整性（2026-10-28）：`log_collect_task.integrity_state` 记录 P2 的端到端结论
  （`verified` = 客户端声明的整包摘要与平台合并结果一致；`unverified` = 无基线，仅做了传输层校验）。
  每次 `begin_delivery` 复位为 `unverified`，避免上一次的结论被当成这一次的证据。
  详见 [日志收集端到端完整性校验](../events/2026-10-28-日志收集端到端完整性校验.md)。

| 字段 | 语义 | 来源 |
|---|---|---|
| `case_id` | 唯一工单号，任务外键与归属（任务按 created_by 鉴权） | 用户指定或 `generate_case_id()` |

> 响应序列化坑：`origin_node_ip` 是 INET 列，asyncpg 返回 `IPv4Address` 对象，而
> `LogCollectTaskResponse` 声明为 `str`。缺转换会让 FastAPI 抛 `ResponseValidationError`
> （表现为"创建任务 500"），已在 `_coerce_inet` 统一转字符串。

## 6.2 日志收集「故障场景」字典（2026-10-29）

日志收集面板上的「故障场景」勾选项以前只有名字（`terminal_bridge` 内置短名），用户看不出
「这个场景收什么、什么症状该选、要跑多久」。这些文案无从 acli 获取，只能人工维护，
因此落到平台字典表 `log_collect_scenario`（属工单模块，与 `log_collect_task` 同域）。

边界（本表存在的全部意义）：

| 归字典管 | 不归字典管 |
|---|---|
| 短名 `label`、一句话释义 `summary` | 哪些 `-m` 枚举可用（集群 `acli log_collect create --help` 探测决定） |
| 采集内容 `collects`、典型症状 `typical_symptoms`、耗时 `duration_hint` | 任务状态机、采集与上传链路 |
| 互斥 `exclusive`、顺序 `sort_order`、启停 `enabled`、审核 `review_state` | 历史任务里已记录的 `value` |

接口（`app/routes/log_collect_scenarios.py`）：

- `GET /api/log-collect/scenarios`：客户读，`get_client_id` 鉴权；只返回 `enabled = true`，
  按 `sort_order, value` 排序；**查空只返回空数组不报错**（降级由前端回落 bridge 短名）；
- `/internal/log-collect/scenarios`：管理端，`require_admin_token`；GET 必须**含停用项**，
  否则运营无法把下线的场景重新启用；POST 命唯一约束回 409；PUT 按路径参数定位、
  `value` 不可改（不在更新模型里，请求体里出现也会被忽略）；
- 写入语义：`model_dump(exclude_unset=True)` 只写调用方显式给出的列（表格里改一个开关
  不得把未提交的长文本清空），列名过 `_UPDATABLE_COLUMNS` 白名单后才拼进 `SET`；
- 审计：每次写操作 `write_operation_audit(resource_type="log_collect_scenario")`，
  失败只记日志不影响业务结果；同一请求另记 `event=log_collect_scenario_write`。

种子数据：`database/seeds/06_log_collect_scenarios.sql`（seeds 通道，由 `db-seed` Job 在
PostSync 执行；幂等 `ON CONFLICT (value) DO NOTHING`）。**为什么不放 `data-migrations/`**：
存量库上 `db-migrate.sh` 是 Step 1 数据迁移在 Step 3 atlas apply 之前，新表的种子会撞上
「表还不存在」（2026-10-29 staging PreSync 事故，见
[事件文档](../events/2026-10-29-日志收集场景字典与Agent不联动.md) §七）。
`collects` / `typical_symptoms` / `duration_hint` 无 acli 原文可依，首版 `review_state`
均为 `pending_review`，需支持工程师审核后改为 `approved` 再对外。

> 互斥只在前端生效：后端仅校验枚举白名单与去重，`-m other,vm_suspend` 可直接提交。
> 2026-10-29 支持工程师实机确认该组合是**叠加**语义（两类日志一起收），故 seed 里
> `other.exclusive = false`；`exclusive` 列保留为字典能力，将来真出现互斥场景在管理台打开即可。

## 6.3 acli 插件期望态与票据化只读面（2026-11-18，链路收口 v2.0）

插件的**期望态**在本服务维护，**收敛动作**在客户侧发生：本服务只提供三份只读事实
（期望态清单、包字节、按工单签发的票据），不再持有任何 SSH 目标、凭据或下发任务状态。
运行时顺序、两阶段边界与失败语义见
[节点同步链路统一收口设计](../../plans/2026-11-18-节点同步链路统一收口设计.md) §3.3。

**三族路由与鉴权边界**（`app/routes/acli_plugins.py`，三族互不共用依赖，避免「管理令牌
被当成数据面凭据」与「客户身份被桥借用」两类越权）：

| 路由族 | 路径 | 鉴权 | 语义 |
|---|---|---|---|
| 管理面 `admin_router` | `/internal/acli-plugins/templates`、`/plugins`、`POST /specs` | `require_admin_token` | 只维护期望态：校验规格 → 写不可变 revision → 更新插件档案；**不产生任何下发副作用**，同规格重复保存按 `spec_hash` 幂等 |
| 客户面 `client_router` | `POST /api/acli-plugins/ticket` | `get_client_id` + `verify_case_exists` | 按 case 签发短期只读票据；`case_id` 为空直接 400 且不查库，工单不存在 404 |
| 同步面 `sync_router` | `/internal/acli-plugins/manifest`、`/package/{plugin_name}` | **只认** `X-Plugin-Ticket` | 桥的数据面：只读、无副作用；不读工单业务数据，不接受管理令牌与客户身份 |

**票据模型**（`app/services/plugin_ticket.py`，与日志收集证据票据同族范式）：

| 维度 | 实现 |
|---|---|
| 载荷 | 只有 `case_id` 与 `exp`；签名串 `acli-plugin-read:{case_id}:{exp}`，token 形如 `{exp}.{hex}` |
| 密钥 | `HMAC-SHA256(sha256("acli-plugin-read:" + INTERNAL_API_TOKEN))`——scope 加盐派生，不新增必填配置 |
| TTL | 签发时收敛到 `(0, ACLI_PLUGIN_TICKET_TTL_SECONDS]`（默认 600s，下限 60s），调用方给更大值一律截断：时长不是不可信客户端可协商的 |
| 校验 | 缺票 / 畸形 / 过期 / 签名不符 / 串用其他 case → 401「票据无效：{reason}」（`ticket_malformed`/`ticket_expired`/`ticket_signature_mismatch`）；**鉴权先于任何期望态读取** |
| 审计 | `acli_plugin_ticket_issued` / `acli_plugin_manifest_served` / `acli_plugin_package_served` 各记一条，只落票据摘要前 12 位，不落票据本身 |

**manifest 形状即桥的解析契约**：`{manifest_version: "2.0", case_id, plugins: […]}`，每项含
`name / version / spec_hash / update_mode / built_in / smoke_args / enable_completion / size /
files[] / register_item / package_ref / sha256`。两个易错点已钉进单测：

1. `register_item.last_updated_at` 是**构建时刻**，必须随 revision 固化在 `validation.compiled`
   里；若改为每次响应重算，桥会把它判成「有修改」而反复全量重装。compiled 缺失（历史脏数据）
   才回退 `compile_descriptor(build_descriptor(spec_json))` 重算，并留 `acli_plugin_compiled_missing`
   告警——回退是有痕迹的降级，不是静默。
2. 包通道三态：无包 → `package_ref` 为空，桥必须用内联 `files[]` 收敛；有包但缺 `.sha256`
   sidecar → `sha256` 为空，桥**不得拆包**（无法做完整性校验）；两者齐备才走下载。
   包路径由 `plugin_name` + `spec_hash` 内容寻址拼成，不接受调用方给定的路径片段。

**已随收口删除**：部署命令计划与浏览器回执端点、`acli_plugin_deployment` /
`acli_plugin_environment` 两张表、后台租约轮询协程与对应 ORM 模型、连接类 `ACLI_PLUGIN_*`
配置项（仅保留上面两项数据面配置）。表结构口径见[数据库设计](../数据库设计.md) 7.69。

## 6.4 日志收集交付包归属判定（2026-11-24）

`waitCollect` 的职责是确认“节点上这个包属于本轮采集”，不是判断“包的绝对时间早不早”。
因此 bridge 只使用**同一节点、同一时钟源**的两个读数，并用测得偏移校正：

1. 一条 SSH 命令取 `date +%s` 与 `stat -c %Y <archive>`；
2. `age = node_now - mtime`，节点时钟静态偏移在相减中抵消；
3. `mtime_on_bridge = mtime + (bridge_now - node_now)`，把包时间校正到平台时钟；
4. **只有 `age > 30 分钟` 且 `mtime_on_bridge` 早于作业创建时间 5 分钟以上才判旧包**；
5. `mtime > node_now + 2 分钟`（时钟回拨/未来时间）放行并记 WARN；
6. 旧包返回带 `LC-TRANSFER-011` 的 fatal 错误。

两个条件取“与”：交付排队导致 `age` 变大，但包是作业开始后产出的，`mtime_on_bridge` 会证明它是新的；
静态时钟偏差则被 `clock_offset` 抵消。证据事件 `delivery.archive_age_probe` 记录
`node_now/mtime/mtime_on_bridge/job_started_at/age_sec/threshold_sec/clock_offset_sec/verdict`。
补交付（`Direct` 模式）不经过该判定。

客户提示只陈述可证事实：“节点本地时间显示该包生成于 X 分钟前，超过交付时效”，
不再把 bridge 的提交时间写成“本次采集开始”。详见
[方案事件](../events/2026-11-24-日志收集包归属时钟鲁棒性.md)。

## 6.5 日志收集场景能力门禁（2026-11-26）

### 6.5.1 事实来源

「这台节点支持哪些场景」只有一个事实来源：目标节点 acli `log_collect create --help`
真实列出的专项，即 probe 返回的 `node_modules`。平台白名单（`probe.modules` /
`log_collect_scenario` 字典）只回答「acli 可能接受哪些名字」，不能回答节点是否装了对应专项。

旧实现把白名单当可选集合，节点 help 未列出的 `core` 仍可勾选；平台照常生成
`core.json` 槽位，bridge 备份原件时才发现文件不存在，最终报 `LC-SPC-003`
并提示「磁盘空间不足或权限不足」，把用户引向错误方向（Q2026112600025）。

### 6.5.2 三层约束

| 层 | 约束 | 失败时的行为 |
|---|---|---|
| 前端 | `probe.catalog_source=acli_help` 且 `node_modules` 非空时，只渲染交集；历史回填/重试也走同一过滤 | 不支持项不出现；历史项被移除时表单给出一次提示 |
| 后端 | `create_task` 在建任务前校验请求场景；先读 `payload.probe`，缺失时读桥侧 30 分钟内最近 `log_collect.probe` | 422 `LC-PLUGIN-016`，任务不落库、通道不建立 |
| bridge | `spcPrepareFailureReason` 只把 `cp: cannot stat ... No such file or directory` 归为 `spc_module_missing` | 展示「节点上没有所选专项」，不再伪装成备份失败 |

### 6.5.3 兼容边界

- `catalog_source=platform_default`、`node_modules` 为空、旧 bridge 不返回 `node_modules`：
  一律视为「能力未知」，不删用户选择，也不做 422 拒绝；
- 能力快照超过 30 分钟不用于拦截：节点可能刚升级，旧快照会把可用项误判为不支持；
- 自定义场景 `source=spc` 固定占用 `core` 槽位，与默认场景的 `core` 同规则校验；
  `source=config` 不依赖专项能力，只校验脚本与路径。
