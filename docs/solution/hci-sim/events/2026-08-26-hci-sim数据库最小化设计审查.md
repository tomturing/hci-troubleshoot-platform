# hci-sim 数据库最小化设计审查

## 1. 审查结论

当前 `hci_sim` 数据库的总体方向是合理的：独立数据库、Bundle 内容寻址、Run 幂等/CAS、审计和 Runtime 激活指针，解决了真实 HCI 与仿真环境隔离、重启恢复和 Bundle 漂移问题。

但当前实现存在明显的“控制面超前设计”：数据库已定义 17 张表、4 个 schema，而真正接线并持续产生业务数据的链路远少于表数量。当前不应继续新增 `fixture_library` 四到六张表；首先应把现有模型压缩为一个最小可运行闭环，再决定是否需要资产表。

建议目标不是立即删除全部表，而是分三类处理：

| 处理 | 对象 | 结论 |
|---|---|---|
| 保留并作为核心 | `control_plane.run`、`run_attempt`、`run_event`、`run_result`、`fixture.bundle`、`fixture.bundle_activation`、`audit.entity_event` | 有明确 Runtime/API/测试闭环，当前不可轻易合并 |
| 合并或降级 | `control_plane.scenario`、`fixture.dependency`、`fixture.provenance`、`run_outbox`、`stale_outbox` | 当前存在状态/职责重复或未接线；先缩小语义，必要时并入核心表/统一 outbox |
| 延后，不进入首期 | `runtime_instance`、`artifact.metadata/scan/approval`、独立 `fixture_library` | 只有 realistic Artifact、Scheduler、多 Runtime 或资产复用真正上线时才需要 |

## 2. 第一性原理：hci-sim 数据库到底必须保存什么

仿真 Runtime 的最小物理事实只有四个：

1. **要运行哪个 Bundle**：Bundle digest、对象位置、状态和 KBD/Tool/Policy 身份；
2. **一次测试是否可恢复**：Run 的幂等键、Bundle 绑定、状态版本和截止时间；
3. **一次运行发生了什么**：Attempt、事件序号、结果摘要；
4. **谁在什么时候改变了什么**：带唯一调用链的追加式审计。

因此，任何表都必须证明自己满足至少一个不可替代的不变量：

```text
表 -> 一个状态机或完整性边界 -> 一个生产写入方 -> 一个读取/恢复消费者
```

如果只有 schema、类型或单元测试，没有真实生产写入方和消费者，就不能把它当作已经完成的生产能力。

## 3. 当前四大领域逐项审查

### 3.1 `control_plane`

| 表 | 当前用途 | 实际状态 | 审查结论 |
|---|---|---|---|
| `scenario` | support_id/KBD revision/variant/input fingerprint | Bundle 编译和 Runtime 同步均写入 | **保留，但语义过宽**；当前常与 Bundle 1:1，应减少独立状态 |
| `run` | TestRun 生命周期、幂等和 CAS | `RunRepository` 创建、绑定 Case、更新状态 | **核心保留** |
| `run_attempt` | 重试/租约绑定 | `RecordLease` 和结果链路写入 | **核心保留** |
| `run_event` | 有序事件摘要 | `AppendEvent` 写入 | **核心保留** |
| `run_result` | 运行最终结果摘要 | `RecordResult` 写入 | **核心保留** |
| `run_outbox` | Run 事件可靠投递 | Repository 写入，reconciler 消费 | **保留但应统一 outbox 实现** |
| `runtime_instance` | Runtime 心跳/容量/分片 | 当前未发现生产写入方 | **首期延后或删除**；单 Runtime 不需要持久化实例目录 |

`scenario` 的问题不是完全无用，而是当前字段与 `fixture.bundle` 重复：两者都保存 support/KBD revision、variant、fingerprint 和生命周期。现行 Bundle Registry 中，一个冻结输入对应一个 scenario，一个 Bundle 绑定该 scenario；Run 也通过 Bundle digest 间接绑定 scenario。建议短期保留以兼容已有接口，长期将它降级为“Bundle 编译输入索引”，不再维护独立的第二套发布状态。

这意味着“收缩”不是立即删除 `scenario`：现有 `fixture.bundle.scenario_id` 和 `control_plane.run.scenario_id` 外键仍依赖它。第一步应停止新增业务状态写入，第二步再通过兼容视图/迁移评估是否能把它并入 Bundle，避免为了减少表数量破坏历史 Run 关联。

### 3.2 `fixture`

| 表 | 当前用途 | 实际状态 | 审查结论 |
|---|---|---|---|
| `bundle` | 不可变 Manifest 元数据和对象索引 | Bundle Registry、Runtime sync、Factory API 使用 | **核心保留** |
| `dependency` | Bundle 对 KBD/Tool/Policy 的依赖 | Compile/Sync 写入，MarkStale 查询 | **保留最小版**；不要提前扩展成通用资产图 |
| `provenance` | route→artifact 来源 | 当前写入逻辑对每个 route 与每个 artifact 做笛卡尔积，realistic 尚未正式接线 | **首期移出核心**；改为 Bundle 的 JSON provenance 或 realistic 上线时再建精确映射表 |
| `approval` | Bundle 专家/安全审批 | Registry 状态机和 API 使用 | **保留**，但可与统一审计复用事件，不要重复存大量状态 |
| `stale_outbox` | 依赖变化触发 stale | `MarkStale` 写入，未发现常驻消费闭环 | **与 run_outbox 合并为统一 outbox**，或在 stale worker 上线前延后 |
| `bundle_activation` | desired/active/previous 指针 | Runtime activator、恢复和回滚使用 | **核心保留**；它不是 Bundle 状态的重复，而是部署指针状态 |

### 3.3 `artifact`

`artifact.metadata`、`artifact.scan`、`artifact.approval` 的抽象适用于“真实客户日志采集→脱敏→扫描→双人审批→realistic Bundle”。但当前 Runtime 启动只构造 PG Artifact Repository，Bundle Factory 现有 API 没有真实采集、扫描和 Artifact 管理入口；生产链路仍以 synthetic/GitOps Manifest 为主。

结论：这三张表不是错误设计，但在 realistic 管线未上线前属于**预留控制面**。继续维护会制造能力幻觉。首期可以保留迁移但标记 `experimental`，或者从部署迁移中延后创建；禁止让页面显示“Artifact 已审核”而没有真实扫描器和对象存储证据。

### 3.4 `audit`

`audit.entity_event` 是跨领域都需要的通用追加式审计，记录 entity、action、actor、trace_id、前后状态摘要。它满足平台级调用链追踪要求，**应保留**。

当前不足是部分审批表自身又保存 decision/comment/actor，形成“状态表 + 审计表”双写。两者并不完全冗余：审批表用于快速判断门禁，审计表用于全局追溯；但必须规定审批表是当前投票投影，审计表是不可变事件源，不能各自演化出不同状态。

## 4. 当前设计的完整性缺口

“方向合理”不等于“生产闭环完整”。当前仍有以下缺口：

| 缺口 | 事实 | 影响 |
|---|---|---|
| 控制面接线不完整 | `internal/controlplane` 仍有参考内核，Runtime 主要通过 `RunRepository` 和手工/GitOps Manifest 工作 | API 能返回不代表完整状态机已成为唯一生产事实源 |
| realistic Artifact 未闭环 | Artifact Repository 有注册/扫描/审批原语，但没有真实采集、扫描器、对象存储和管理 API 的完整链路 | `artifact.*` 目前不能证明 realistic Bundle 已可生产发布 |
| stale 投递未闭环 | `fixture.stale_outbox` 有写入，当前没有等价的常驻消费/补偿链路 | 依赖变化可能记录了事件，但不能保证所有 Bundle 最终被标记 stale |
| 发布原子性不足 | 对象存储提交、数据库状态和 Runtime activation 仍跨多个步骤 | 可能出现 DB published 但 Runtime 未激活，或对象存在但状态未发布 |
| 资产管理缺失 | 当前 Bundle Factory 只能编辑 Bundle manifest，不支持模板/实例复用和独立检索 | 只能满足单次 Draft 编辑，不能形成长期模板库 |
| 基线版本未冻结 | 分类/Catalog 主要来自主库快照或文件热加载 | 历史 Bundle 只能依赖 checksum/compile_input，缺少可解释的基线内容快照 |

## 5. 过度设计和冗余点

### 5.1 四个 schema 不等于四个必须领域

`control_plane`、`fixture`、`artifact`、`audit` 是组织方式，不代表必须同时启用四条产品能力。当前最小部署实际上只需要：

```text
fixture.bundle + fixture.bundle_activation
control_plane.run/attempt/event/result
统一审计
```

`artifact` 是 realistic 数据准入子域，`runtime_instance` 是多副本调度子域，均不应因为未来路线图而阻塞当前 Bundle Factory。

### 5.2 两个 outbox

`control_plane.run_outbox` 和 `fixture.stale_outbox` 都是“待处理事件 + 重试 + processing 恢复”的同构可靠投递表。分成两张表会重复实现 claim、retry、恢复和指标。

建议后续统一为一张 `control_plane.outbox`：

```text
id, topic, aggregate_type, aggregate_id, event_type,
payload_digest, trace_id, status, attempts,
available_at, processing_at, processed_at, created_at
```

`topic=run|fixture_stale|activation` 区分消费者即可。迁移前必须完成旧表数据盘点和回放演练，不能直接删除历史事件。

### 5.3 `scenario` 与 `bundle` 双状态

`scenario.status` 和 `bundle.status` 都有 draft/validated/approved/published/stale/retired，容易出现一边 published、另一边 stale 的不一致。当前代码已出现按 Bundle 更新 Scenario 的补偿逻辑，这说明状态存在重复来源。

建议：

- `bundle.status` 作为唯一 Bundle 生命周期事实；
- `scenario` 只保存编译输入索引和 capability gap，不再维护完整发布状态；
- 若外部 API 必须返回 scenario 状态，则由查询视图从 Bundle 聚合，不再独立写状态。

### 5.4 `fixture.provenance` 当前不满足自身目标

表定义是 route→artifact 单值关系，但当前 `writeProvenances` 对每个 route 和每个 artifact 写入多行并依赖 `(bundle_id, route_id)` 冲突忽略，最终只保留“第一个 Artifact”，既不准确又不能支撑 route 级溯源。它属于设计债，不是应继续扩展的基础。

首期建议在 `fixture.bundle.compile_input` 中保存规范化的 `route_sources` JSON；等 realistic Bundle 真正需要逐 route 审计时，再引入严格主键为 `(bundle_id, route_id, artifact_id)` 的关系表。

## 6. 推荐的最小目标模型

### 6.1 首期保留

```text
fixture.bundle
fixture.bundle_activation
fixture.dependency（仅 KBD/Signal/Tool/Policy）
fixture.approval

control_plane.run
control_plane.run_attempt
control_plane.run_event
control_plane.run_result
control_plane.outbox（统一后）

audit.entity_event
```

共 10 个核心表（统一 outbox 后），足以支持：Bundle Draft/发布、Runtime 激活/回滚、TestRun 重试/结果、审计和依赖失效。

### 6.2 首期延后

```text
control_plane.runtime_instance
artifact.metadata
artifact.scan
artifact.approval
独立模板/实例/基线资产表
```

延后不是否定需求，而是要求先满足触发条件：

| 能力 | 触发新增条件 |
|---|---|
| `runtime_instance` | 多 Runtime 分片、容量调度或心跳恢复真正上线 |
| `artifact.*` | 真实 Artifact 采集器、对象存储、扫描器和审批 API 同时可用 |
| 模板/实例资产 | 同一模板被多个 KBD 复用，且 Bundle manifest JSON 已无法支持查询/编辑/复用 |

### 6.3 模板/实例需求的最小替代

在没有达到触发条件前，不新增 `fixture_library` schema。可先使用一个受控的 `fixture.bundle.compile_input` JSON 约定：

```json
{
  "assets": [
    {
      "asset_key": "qkv_dialog.vm_start_failed",
      "asset_type": "template|instance",
      "asset_revision": 1,
      "asset_digest": "sha256:...",
      "category_baseline": {"revision": "...", "checksum": "..."},
      "catalog_baseline": {"revision": "...", "checksum": "..."}
    }
  ]
}
```

这不是长期资产库，只是让当前 Bundle 具备最小可追溯性。等出现跨 KBD 复用、资产列表检索、独立审批和 stale 传播需求，再将该 JSON 迁移为一张 `fixture.asset_revision` 表；不要一开始拆成六张表和新 schema。

## 7. 对抗性审查

| 风险 | 证据 | 处理 |
|---|---|---|
| 表已建成但能力未接线 | `runtime_instance` 无生产写入方；Artifact 只有 Repository/测试 | 文档和 API 明确标记 experimental/pending，不以表存在宣称完成 |
| 未来模型绑架当前实现 | 先为模板、实例、Catalog 建六张表 | 先在 Bundle compile_input 保存摘要，达到触发条件再规范化 |
| 双 outbox 语义漂移 | run/stale 两表字段和 claim/retry 逻辑高度同构 | 设计统一 outbox，迁移时保留历史和幂等键 |
| scenario/bundle 状态冲突 | 两表均有完整生命周期枚举 | Bundle 为唯一状态源，Scenario 降级为索引 |
| provenance 伪精确 | 当前 route×artifact 笛卡尔积且主键冲突丢数据 | 首期 JSON 摘要；realistic 上线后再建严格关系 |
| 删除表破坏历史追溯 | Run、Bundle、Lease、审计通过 FK/ digest 引用 | 只允许 retire/软归档，删除前做迁移、备份和恢复演练 |

## 8. 实施顺序

1. 为所有 17 张表做生产写入/读取/保留策略 inventory，区分“已接线、测试专用、预留”。
2. 先修正状态事实源：Bundle 唯一生命周期，Scenario 只做输入索引。
3. 统一 `run_outbox` 与 `stale_outbox` 的事件模型，完成旧数据迁移和回放验证。
4. 暂不新增 `fixture_library`；Bundle Factory 先扩展 `compile_input.assets` 的摘要字段和校验。
5. 只有当真实复用和管理查询证明 JSON 不足时，再新增单一 `fixture.asset_revision` 表，而不是立即新增完整资产域。

## 9. 最终判断

当前 hci-sim 数据库不是“完全错误”，但确实过度设计了未来能力，并存在重复状态和未接线表。最合理的方向是：

```text
保留运行闭环 + Bundle 注册 + 激活 + 审计
收缩 Scenario 语义
合并两个 Outbox
延后 RuntimeInstance/Artifact/独立资产库
```

因此，对此前“直接新增 `fixture_library` 六张表”的建议进行修正：**现阶段不新增领域和六张表**。先用现有 Bundle 的冻结 JSON 记录模板/实例摘要，等真实复用规模和治理需求达到阈值，再以一张资产修订表渐进演进。

## 10. 17 张表的具体瘦身清单

“删除”必须区分为停用和物理删除。已部署环境不能直接修改首个迁移文件或执行无条件 `DROP TABLE`；应先 inventory、备份、回放和兼容迁移，再删除无生产引用的数据结构。

| 当前表 | 最小化动作 | 目标状态 |
|---|---|---|
| `control_plane.scenario` | 第一阶段保留只读兼容索引，停止独立生命周期写入；完成 `bundle.scenario_id`、`run.scenario_id` 回填后再合并/删除 | **最终删除或改为视图** |
| `control_plane.run` | 保留 | 核心 |
| `control_plane.run_attempt` | 保留 | 核心 |
| `control_plane.run_event` | 保留 | 核心 |
| `control_plane.run_result` | 保留 | 核心 |
| `control_plane.run_outbox` | 与 `fixture.stale_outbox` 合并为 `control_plane.outbox` | **旧表删除，新表保留** |
| `control_plane.runtime_instance` | 当前单 Runtime 无生产写入方；停止创建和读写 | **延后，最终可删除** |
| `fixture.bundle` | 保留 | 核心 |
| `fixture.dependency` | 保留，但只允许 KBD/Signal/Tool/Policy 等实际依赖 | 核心精简版 |
| `fixture.provenance` | synthetic 阶段移除；route 来源先进入 `bundle.compile_input.route_sources` JSON；realistic 真正上线后再评估重建 | **当前删除/延后** |
| `fixture.approval` | 保留 Bundle 审批投影；所有变化同步写统一审计 | 核心 |
| `fixture.stale_outbox` | 合并进统一 `control_plane.outbox`，迁移后删除 | **删除** |
| `fixture.bundle_activation` | 保留 desired/active/previous 指针和回滚状态 | 核心 |
| `artifact.metadata` | realistic Artifact 管线未上线前不创建新数据；保留历史只读或延后迁移 | **延后** |
| `artifact.scan` | 同上；没有真实扫描器时不得宣称已完成扫描门禁 | **延后** |
| `artifact.approval` | 同上；没有真实身份源和审批 API 时不作为发布依据 | **延后** |
| `audit.entity_event` | 保留，作为跨领域追加式审计和唯一调用链记录 | 核心 |

### 10.1 领域层面的变化

最小部署不再把四个 schema 都当作已启用产品域：

```text
保留并启用：control_plane、fixture、audit
延后/可选：artifact
不新增：fixture_library
```

`artifact` 不是马上从所有已部署数据库强制删除，而是从当前最小化能力基线中移出；待真实 Artifact 采集、对象存储、四项扫描、双人审批和发布 API 同时接线后再启用。

### 10.2 表数量变化

在完成迁移、统一 outbox、移除 provenance、收缩 scenario 并暂不启用 artifact/runtime_instance 后：

```text
当前：17 张表 / 4 个 schema
目标：约 10 张核心表 / 3 个启用 schema
```

如果为了兼容历史 Run 暂时保留 `scenario`，过渡期是 11 张表；这不是最终模型，也不应继续给 `scenario` 增加新的生命周期语义。

### 10.3 安全迁移顺序

1. 统计 17 张表的行数、外键、最近写入时间和调用方；没有生产写入方的表标记为 `deprecated`。
2. 已新增统一 `control_plane.outbox`；旧 `run_outbox`/`stale_outbox` 通过历史回填和 INSERT 镜像触发器兼容，观察窗口结束后再删除。
3. 已将 route provenance 规范化摘要写入 `fixture.bundle.compile_input.route_sources`，停止写 `fixture.provenance`。
4. 停止 `runtime_instance` 和 `artifact.*` 的新写入，保留只读窗口和备份恢复演练。
5. 将 Scenario 状态改为由 Bundle 聚合；完成历史外键回填后，再删除 `scenario` 表或替换为兼容视图。
6. 确认无读写、无激活指针、无历史审计引用后，按独立迁移删除旧 outbox、provenance、runtime_instance 和 artifact 表。

任何物理删除都必须保留迁移前导出、digest 对账和可回滚窗口；Bundle、Run、Result、Audit 不能级联删除。

### 10.4 第一阶段落地边界

代码与 `000005_minimize_control_plane.sql` 已完成第一阶段实现：Run/Result/Expire 和 Bundle stale 均进入统一 Outbox；Scenario 新写入固定为 `indexed`；Route 来源摘要随 Bundle 编译输入冻结。数据库迁移尚未在生产库执行，旧表物理删除、Artifact/runtime_instance 停止建表以及 Scenario 外键重构不属于本阶段。
