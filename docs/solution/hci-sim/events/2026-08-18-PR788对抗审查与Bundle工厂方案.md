# PR788 对抗审查与 Bundle 工厂方案

更新时间：2026-08-18

## 1. 结论

PR788 不是完整的 Bundle 工厂。它合入前提供的是 PostgreSQL Artifact/Bundle 生命周期适配器和 synthetic 批量 Manifest 编译器，尚未形成“真实采集 → 四扫 → 双审 → 可编辑 Draft → 发布 → Runtime 激活”的生产闭环。

本次按第一性原理把闭环拆成不可跳过的状态转换，并以对抗性审查逐项验证：

```text
published KBD active snapshot
  → C1 ready_for_artifact_binding
  → Artifact staged
  → four-scan evidence
  → Artifact expert + security approval
  → immutable Bundle draft
  → expert edit creates a new draft revision
  → compiler validation
  → Bundle expert + security approval
  → published object
  → Runtime activation
  → TestRun / Agent E2E
```

其中 `ready_for_artifact_binding` 只证明 KBD/Signal/Tool/Policy 已冻结并可绑定 Artifact，不表示 Artifact 已采集、Bundle 已发布或 Runtime 已生效。Runtime 消费的是 Fixture Manifest v2，不是 C1 Resolver JSON。

## 3. Bundle 工厂 MVP

管理端新增 `/admin/simulation/bundle-factory`，支持：

- 按 KBD 查看 Bundle、冻结 revision/checksum/digest、Route、variant、target、stdout/stderr、exit code、fault、Variables 和审批历史；
- 由 Gateway 调用 C1 Resolver，只有 `ready_for_artifact_binding` 才能生成 synthetic Draft；浏览器不能提交或猜测 KBD revision；
- 专家编辑 stdout、stderr、exit code、fault 和 Variables；argv 默认只读；
- 每次编辑必须填写原因，以父 digest 生成新 Draft revision，旧 Draft 不覆盖；
- Draft 修改者成为新 revision 创建者，不能自审；expert/security 必须是不同主体；
- 页面按 `draft → validated → approved → published` 展示状态，并显示 Runtime activation 状态；
- Gateway 为 C1、Registry 和发布动作传递唯一 `X-Trace-ID`，日志只记录 support_id/digest/actor，不记录输出正文或 Lease。

当前项目没有可用的 Admin 登录主体映射，MVP 由 Gateway 注入配置化 compiler/expert-editor/expert-reviewer/security/publisher 服务身份，编辑者和专家复核者保持分离。此模式可验证状态机但不能作为生产人工审批证据；接入企业身份源后，actor_id 必须来自已认证 claims，不能来自浏览器请求体或自定义 Header。

## 4. 已测闭环

| 环节 | 验证方式 | 当前证据 |
|---|---|---|
| C1 → synthetic Draft | Gateway 测试 + Bundle Factory API 测试 | 非 ready KBD 被阻断；revision 只来自 C1 |
| 采集登记 → 四扫 → Artifact 双审 | Memory 完整契约测试 + 临时 PostgreSQL 集成测试 | staged/scanned/approved 状态按序通过，同 actor 被拒绝 |
| 编译 → Draft → 专家修改 | Go API/Registry 测试 | 修改产生新 digest、parent digest、draft revision 和 reason |
| 校验 → Bundle 双审 → 发布 | Go API/Registry + PostgreSQL 集成测试 | creator 自审、同 actor 双角色、重复角色均失败关闭 |
| 对象重启恢复 | FileBundleObjectStore 测试 | 新实例可按 published content digest 读取对象 |
| Admin 页面 | Vue 测试 + production build | Route/冻结事实展示、结构化编辑 payload 和 reason 已验证 |
| Helm 部署 | `helm lint` + `helm template` | Controlplane Registry、PVC、只读根文件系统下的写挂载已渲染 |

## 5. 仍未完成的生产能力

以下项目不得因 Bundle 工厂页面可用而标记完成：

1. 真实 HCI 只读采集器、脱敏流水线和 Artifact 原始报告对象尚未接入。
2. Secret/PII/License/Schema 目前仍是扫描契约结果，不是四个独立扫描器及其报告、policy revision、finding 和报告 URI。
3. 配置化服务身份不是企业专家身份，不能形成生产责任审计。
4. 文件对象存储解决单副本重启丢失，但不是多副本 OCI/S3/WORM。
5. `Publish` 尚未用 outbox 原子协调对象提交、DB 状态和 Runtime activation。
6. Runtime 仍从 Helm ConfigMap 启动加载，发布返回 `pending_gitops_sync`；没有热加载、activation ACK、active pointer 或自动回滚。
7. 尚未完成 3 个异构 KBD、positive/negative/inconclusive、real/sim differential、mutation、20-repeat、1/10/50/100/200 并发和重启/回滚验收。

因此，本次可声明“Bundle Factory MVP 和控制面契约闭环已实现并通过代码/数据库测试”，不能声明“真实 KBD 生产采集到 Runtime 热生效的完整流程已完成”。
