# hci-sim 内部专家快速发布与双模式治理方案

> 状态：实施中  
> 日期：2026-08-19  
> 适用范围：Bundle 工厂、hci-sim Runtime、Admin UI 仿真测试  
> 决策：Internal Fast Path 为当前阶段默认路径，High Assurance Path 保留为后续可选能力

## 1. 背景与问题

Bundle 工厂和仿真测试只面向内部专家，当前目标不是对外提供高保证仿真资产，而是验证 Agent 的功能链路是否可用。评价标准只有三项：

1. 平台自动生成的 Bundle 是否足够接近 KBD 语义，让专家少修改。
2. 专家是否能快速查看、修改、校验和发布 Bundle。
3. 已发布 Bundle 是否能秒级热激活并立即构建测试环境。

现有流程把真实 Artifact、四扫、专家与安全双审、独立证明、发布和 GitOps 同步串成默认路径。它解决的是跨团队分发、真实数据治理和生产级审计问题，与当前内部功能测试目标不匹配。直接结果是：Bundle 可以显示为 `published` 和 `active`，但因为 `synthetic_fixture` 门禁仍无法构建环境；用户需要完成与目标无关的审批和证明，仍得不到可运行的闭环。

## 2. 第一性原理解构

内部功能仿真的不可约事实只有四项：

1. Runtime 必须拿到结构合法、路由唯一、命令可匹配的 Manifest。
2. 每条 Route 必须提供足以驱动 Agent 判断的 stdout/stderr，而不是占位 JSON。
3. 专家修改后必须形成新的不可变 digest，运行中的 TestRun 必须继续绑定旧 digest。
4. 发布和切换必须原子完成，并返回 Runtime ACK；不能依赖镜像重建或 GitOps 周期。

因此必须保留：Schema/Lint、Route 唯一性、未解析变量检查、Bundle digest、父版本、修改原因、TestRun digest pin、原子激活、回滚指针、调用链日志和指标。

默认不再强制：真实 Artifact、Artifact 双审、安全角色审批、独立证明和每次 Bundle 发布的 GitOps 变更。

## 3. 发布模式

### 3.1 Internal Fast Path（默认）

面向内部专家，目标为分钟级生成、秒级激活：

```text
KBD 发布
→ 自动生成 Bundle Draft
→ 专家查看和修改
→ 自动校验
→ 专家一键发布
→ Runtime 热激活
→ capability buildable=true
→ 构建仿真环境
→ 开始测试
```

状态机简化为：

```text
draft → published → active
```

`published` 前必须执行自动校验，但不要求把 `validated` 暴露为人工步骤。一次“校验并发布”请求完成自动校验、专家确认、不可变对象提交和 Runtime 激活，并返回同一调用链下的结构化结果。

Internal Fast Path 允许 `kbd-derived` Bundle 构建。当前 Manifest 继续使用 `SYNTHETIC=true` 表达“非真实设备采集”，但 capability 必须同时返回：

```json
{
  "release_profile": "internal_fast",
  "fixture_class": "kbd_derived",
  "buildable": true,
  "capability_warnings": ["not_real_artifact_replay"]
}
```

`synthetic` 在此模式下是质量标签，不是阻断条件。

### 3.2 High Assurance Path（可选）

仅在对外暴露、跨团队共享、生产诊断或合规要求出现时启用：

```text
真实 Artifact
→ 自动扫描
→ provenance 绑定
→ 专家审批
→ 安全审批
→ 独立验证
→ 发布
→ 激活
```

该模式继续拒绝 synthetic Bundle，要求 `positive-realistic` 和批准的 Artifact provenance。两种模式必须通过显式环境策略选择，不能根据调用方参数临时降级。

## 4. KBD 派生 stdout

自动生成 stdout 的事实来源按优先级排序：

1. KBD Signal `provenance.evidence` 中的真实问题描述或命令输出片段。
2. Signal `acquire` 中的工具、参数、关键词和 instruction。
3. Signal `match` 中的 matcher、阈值、期望值、最小样本数和提取规则。
4. Signal `orchestrate.produces` 中的变量名与路径。

生成规则：

- QFK 路由优先复用 provenance evidence；`delta` 等多样本 matcher 按 `minimum_samples` 生成满足判定的完整样本，不返回通用 `synthetic_record`。
- QKV 路由生成工具契约可消费的 JSON，包含 acquire keyword、失败状态、KBD instruction/evidence 和 produces 所需字段。
- matcher 为正向 keyword/exists 时，生成结果必须包含所需匹配事实；负向 matcher 不得写入被排除事实。
- 无法从 KBD 内容生成可校验输出时，Draft 创建必须返回结构化 capability gap，禁止静默回退到占位 JSON。
- 专家可在 Draft 编辑器直接修改 stdout、stderr、exit code、fault 和 variables，保存后生成子 revision。

这里的“真实可用”定义为：输出来自已发布 KBD 的证据与执行契约，并能被 Agent 的 matcher/extractor 正确消费。它不等同于真实设备 Artifact 回放，页面和测试报告必须明确标注 `kbd_derived`。

## 5. 热激活与多 Bundle 切换

Bundle 是不可变配置，Runtime 是加载并执行该配置的路由引擎。高频 Bundle 发布不进入镜像和 GitOps 发布链路。

热激活必须满足：

1. 发布对象完成 digest、Manifest 和 support_id 校验后写入 durable activation pointer。
2. Runtime 将新 Router 加入内存池并原子替换该 support_id 的 active digest。
3. ACK 成功后才向页面返回 `active`；失败返回 `pending/failed` 和 failure code。
4. 已开始的 TestRun/Lease 固定旧 digest，切换不改变运行中测试。
5. 任意已发布 Bundle 可以通过受控 activation API 秒级切换，不要求重新发布。
6. UI 必须读取 activation API，禁止把所有 published Bundle 固定显示为 `pending_gitops_sync`。

GitOps 只管理 Runtime 部署、基线 Bundle 和周期性归档，不参与专家每次修改后的热发布。

## 6. 最小版本与追溯模型

版本管理的目的首先是复现、差异比较和回滚，不是引入审批负担。Internal Fast Path 保留：

```text
bundle_digest
revision
parent_bundle_digest
creator
created_at
edit_reason
published_at
activation_generation
trace_id
```

已发布 Bundle 不允许原地修改。专家修改必须从 Draft 产生新 digest；TestRun 保存其 bundle digest，确保测试结果可重现。

## 7. 对抗性审查与防护

### 7.1 KBD 派生输出造成虚假通过

风险：自动输出满足 matcher，却与真实设备行为有差异。

防护：始终展示 `kbd_derived`；测试报告记录 fixture class；需要真实回放时切换 High Assurance Path，不把 Fast Path 结果声明为现场真实性证明。

### 7.2 单专家误改

风险：错误 stdout、重复 RouteKey 或未解析变量直接进入 Runtime。

防护：发布前强制自动 Lint、digest 校验、Route 冲突检查、输出非空检查和 smoke test。专家不能绕过自动校验。

### 7.3 热切换污染运行中测试

风险：同一 TestRun 前后命令命中不同 Bundle。

防护：Lease/TestRun 固定 digest；BundlePool 保留历史 Router，直到旧租约自然结束。

### 7.4 多 Bundle 误切换

风险：support_id 和 digest 不属于同一 Bundle，或 UI 显示状态与 Runtime 不一致。

防护：激活前校验 published、support_id、digest 和对象完整性；durable pointer 与内存 ACK 同链路；UI 以 activation API 为唯一事实源。

### 7.5 KBD evidence 含敏感内容

风险：provenance evidence 被直接写入 Bundle。

防护：自动生成阶段保留基础 secret scan；命中高危凭据时阻断，其余扫描结果作为 warning。该检查是自动门禁，不引入第二审批人。

## 8. 分阶段落地

### P0：Internal Fast Path 闭环

- 从 KBD evidence/acquire/matcher/produces 生成可消费 stdout，移除通用占位输出。
- 增加 `release_profile=internal_fast`，允许 `kbd_derived` Bundle 构建。
- 增加专家“一键校验并发布”，移除默认安全审批。
- 发布后立即热激活并返回 ACK。
- 增加任意已发布 digest 的受控秒级切换。
- Bundle 工厂展示真实 activation 状态和 fixture class。
- capability 返回 buildable、warning、active digest 和 profile。

### P1：专家体验和质量反馈

- stdout 对比、KBD evidence 来源展示和 matcher 命中预览。
- 自动生成质量评分：无需修改、轻微修改、重写。
- 记录专家修改字段，为后续生成器优化提供数据。
- 一键执行 Route smoke test 和 Agent 最小会话。

### P2：High Assurance Path

- 真实 Artifact 采集、自动扫描和 provenance。
- 可选安全审批与跨团队发布策略。
- Bundle 周期性导出和长期归档。

## 9. P0 验收标准

1. 对 KBD 23821 创建 Draft 时，三条 Route 均不出现 `synthetic_record` 占位 JSON；stdout 来自 KBD evidence 或契约派生。
2. 专家无需安全审批，可通过一次操作完成自动校验、发布和 Runtime 激活。
3. activation API 返回 `active_digest`，Bundle 工厂显示实际状态。
4. Internal Fast Path 下 capability 返回 `buildable=true`，同时保留 `not_real_artifact_replay` warning。
5. 发布后无需镜像更新、Pod 重启或 Argo 同步即可构建环境。
6. 同一 support_id 的两个已发布 Bundle 可在秒级切换；新 TestRun 使用新 digest，旧 TestRun 继续使用旧 digest。
7. 所有编译、发布、激活、切换和构建请求携带同一或可关联的唯一 trace ID，并提供成功、失败和耗时指标。
