# Q2026082575766 五层防御体系与仿真只读确认门禁修复方案

## 1. 概述与背景

在工单 **Q2026082575766** 的仿真测试会话中，Agent 进入 S1 阶段（调查分析），调用只读诊断工具 `qkv_task`（`risk_level=1`）查询历史失败任务时，界面弹出了“将执行操作：qkv_task... 确认执行 / 取消”卡片，要求用户手动点击“确认执行”，阻塞了自动化仿真测试流转。

本方案运用**第一性原理 (First Principles)** 与**对抗性审查 (Adversarial Review)**，对平台全局的五层纵深防御体系进行系统性梳理，修复执行模式字段重载导致的策略误判缺陷，并建立端到端五层防御的有效性与准确性验证规范。

---

## 2. 根因分析（第一性原理拆解）

### 2.1 底层事实链
1. **工具属性事实**：
   `qkv_task` 定义在 `database/seeds/03_qkv_qfk_tools.sql`，属于前端信号-历史任务查询工具，其 `risk_level = 1`（只读低风险）。即便 keyword 包含“启动虚拟机”，也仅用于过滤历史任务，不产生任何系统写副作用。
2. **策略门禁事实**：
   在 `PolicyService.evaluate_needs_confirm` 中，策略服务依据 `auto_execute_mode` 评估低危命令是否自动执行：
   - `safe-only` / `aggressive`：允许自动执行低风险（`risk_level <= 1`）工具，返回 `False`；
   - `off`：强制所有命令需要确认，返回 `True`；
   - 未知模式：Fail-Safe 降级为强制确认，返回 `True`。
3. **字段污染事实**：
   前端仿真测试组件（`SimulationConversation.vue`）传给 `conversation-service` 的请求元数据为：
   ```json
   { "metadata": { "execution_mode": "sim-ssh", "test_run_id": "..." } }
   ```
   这里的 `execution_mode: "sim-ssh"` 是**底层连接通道与数据源标识**（区分真实生产 HCI 与 `hci-sim` 仿真器）。
   然而在 `conversation_service.py:640` 中：
   ```python
   exec_mode = "safe-only"
   if metadata and "auto_execute_mode" in metadata:
       exec_mode = metadata["auto_execute_mode"]
   elif metadata and "execution_mode" in metadata:
       exec_mode = metadata["execution_mode"]  # 被错误赋值为 "sim-ssh"
   ```
   导致 `exec_mode="sim-ssh"` 透传给 `PolicyService`，未命中 `("safe-only", "aggressive")` 白名单，触发了安全兜底降级规则，强制要求人工确认。

## 4. 修复方案

### 4.1 `conversation_service.py` 逻辑解耦
严格解耦用户执行偏好（`auto_execute_mode`）与底层通道（`execution_mode`）：
- 优先读取 `auto_execute_mode`；
- 当仅存在 `execution_mode: "sim-ssh"` 时，将策略模式设为 `"safe-only"`（默认放行低危只读，严格阻断高危），避免将通道字面量直接当作策略模式。

### 4.2 `PolicyService.evaluate_needs_confirm` 增强防脆弱性
- 在 `policy_service.py` 中，显式将 `"sim-ssh"` 视为安全模式（`safe-only` 同等处理），支持仿真环境下低危（`risk_level <= 1`）工具免确认流转；
- 保持 `risk_level >= 2` 和 `require_all_confirm=True` 的前置强制阻断逻辑不变。
