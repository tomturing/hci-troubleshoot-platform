# KBD 审核发布操作指南

> 适用对象：KBD（知识库文档）审核人员、领域专家和平台管理员
> 适用范围：通过流水线导入平台、状态为“待审核”的 KBD
> 目标：把流水线生成的 AI Proposal（模型提案）修改、审核并发布为可供 Agent（智能诊断助手）生产使用的 KBD

## 一、审核发布的核心目标

KBD 审核不是单纯校对文章，而是把流水线生成的“AI 草稿”整理成一份 Agent：

- 看得懂：故障现象、根因和解决方案清晰且一致；
- 找得到：能够从任务、告警或弹框中识别故障及关键对象；
- 采得到：能够在正确的主机、容器或平台范围执行安全的只读检查；
- 判得准：能够根据采集结果支持、排除根因或产出后续变量；
- 可追溯：正文、截图、Signal（信号）、审核人和 Revision（修订）均可回溯。

```mermaid
flowchart LR
    A["流水线导入<br/>AI 草稿"] --> B["确认内容和分类"]
    B --> C["确认生产者信号<br/>故障发生了什么"]
    C --> D["确认消费者信号<br/>如何验证根因"]
    D --> E["预览命令和处理结果"]
    E --> F["运行发布前审查"]
    F -->|有问题| C
    F -->|通过| G["审核发布"]
    G --> H["Agent 生产使用"]
```

## 二、审核人员需要回答的六个问题

打开一篇待审核 KBD 后，依次回答以下问题：

| 审核问题 | 对应审核内容 |
|---|---|
| 这篇 KBD 描述的是什么故障？ | 标题、问题描述、根因、解决方案和分类 |
| Agent 如何发现这个故障？ | QKV Producer Signal（QKV 生产者信号） |
| Agent 需要采集什么信息确认或排除根因？ | QFK Consumer Signal（QFK 消费者信号） |
| 采集结果满足什么条件才能形成结论？ | Matcher（匹配模式）或 Produced Variable（产出变量） |
| 当前审核的是哪个版本，发布后哪个版本会供 Agent 使用？ | Proposal Revision（模型提案修订）、Expert Revision（专家修订）和 Agent Active Revision（Agent 当前生效修订） |
| 这篇 KBD 用于离线诊断时，关键证据是否能够被离线采集？ | Offline Collection Impact（离线采集影响） |

### 2.1 审核详情页检查区域总览

审核人员不应只检查正文和 Signal（信号）。当前审核详情页中的检查区域及其作用如下：

| 页面区域 | 主要作用 | 是否属于 KBD 发布硬门禁 |
|---|---|---|
| 基本信息与确认分类 | 确认故障内容和最终分类 | 分类缺失会阻止发布 |
| Version, Activation and Pre-publish Check（版本、生效与发布前检查） | 区分模型提案、专家工作稿和 Agent 生效版，并运行统一信号审查 | 审查阻断、版本冲突会阻止发布 |
| Source Metadata（来源元数据） | 核对案例来源、原始时间和导入人员等追溯信息 | 通常不直接阻止发布，但来源异常必须人工确认 |
| 正文与 Screenshot Evidence（截图证据） | 核对原文、OCR（图片文字识别）、观察事实和模型推测 | 没有统一的“必须有截图”门禁；错误证据必须修正 |
| Producer/Consumer Signal（生产者/消费者信号） | 定义 Agent 如何发现故障、采集证据和判定结果 | 是；必须存在有效 Signal，且至少有一条 QKV 生产者信号和一条 QFK 消费者信号 |
| Tool Capability and Command Preview（工具能力与命令预览） | 确认采集能力已声明、最终命令安全且可编译 | 能力或运行时契约被阻断时会阻止发布 |
| Offline Collection Impact（离线采集影响） | 判断离线采集资源是否覆盖当前 KBD 的证据需求 | 当前不阻止 KBD 发布；属于离线诊断后续同步门禁 |
| Review Identity and Note（审核身份与备注） | 记录谁审核、改了什么、还有什么待办 | 审核身份必填；备注用于审计和交接 |

## 三、审核操作流程

### 3.1 进入待审核列表

1. 打开管理端 KBD 审核页面。
2. 将状态筛选为“待审核”。
3. 可按案例 ID、标题、分类和 AI Confidence（AI 置信度）筛选。
4. 优先处理以下 KBD：
   - 未分类或分类置信度低；
   - 没有消费者信号；
   - Signal 数量异常；
   - 图片识别未完成；
   - 发布前审查存在阻断项。
5. 点击“详情”进入完整审核页面。

> 不建议仅根据列表信息直接发布。审核人员应至少检查正文、分类、生产者信号、消费者信号和最终命令预览。

### 3.2 确认正文和分类

先确认文章内容，再审核 Signal。至少检查：

- 标题是否准确描述故障；
- 问题描述是否说明用户实际看到的现象；
- 根因是否是明确的技术原因，而不是重复描述现象；
- 解决方案是否能够解决对应根因；
- 分类是否正确；
- 截图识别结果是否与原图一致；
- 正文中的命令、节点、服务、文件和日志名称是否真实存在；
- 正文、根因、解决方案和 Signal 之间是否存在矛盾。

判断标准：

> 如果隐藏全部 Signal，这篇文章本身是否仍然是一篇正确、完整、没有明显矛盾的排障案例？

如果答案是否定的，应先修改正文和分类，再继续审核 Signal。

### 3.3 确认来源元数据

Source Metadata（来源元数据）用于回答“这篇 KBD 从哪里来、何时产生、由谁维护”，包括原始案例模块、版本、创建/更新时间和导入人员等信息。

审核要求：

- 来源案例 ID、产品模块和版本应与正文一致；
- 原始更新时间明显早于适用产品版本时，应确认内容是否已经过期；
- 元数据只用于追溯，不能代替正文证据或 Signal 证据；
- 元数据异常但正文仍可确认时，应在审核备注中说明；无法确认来源真实性时应拒绝发布。

### 3.4 确认 Screenshot Evidence（截图证据）

截图区域不只是展示 OCR 文本，还区分不同可信层级：

| 字段 | 含义 | 审核口径 |
|---|---|---|
| FULL_TEXT（完整可见文字） | 模型从截图读取的原始文字 | 与原图逐项核对关键报错、对象名、时间和数值 |
| Observed Facts（观察事实） | 可以直接从截图看到的事实 | 可以作为 Signal 证据，但必须能在图片中找到 |
| Inferences（模型推测） | 模型根据截图作出的解释 | 未经专家确认不能独立作为事实型 Signal 或运行参数 |
| Quality Status（质量状态） | 图片是否清晰、识别是否完整 | 失败、截断或需复核时应重新识图或人工修正 |
| Evidence Provenance（证据溯源） | 图片摘要、模型和 Prompt 版本等 | 用于确认本次识图结果来自哪张图片和哪个模型版本 |

重新识图后，原有 Signal 可能被标记为 Stale（已过期）。此时必须重新抽取或重新确认 Signal，不能继续发布旧的推导结果。

## 四、生产者信号审核

### 4.1 生产者信号的作用

QKV Producer Signal（QKV 生产者信号）用于回答：

> 用户创建工单时，Agent 能够从任务、告警或弹框中获得什么已知信息？

### 4.2 选择生产者信号类型

| 信号类型 | 中文说明 | 使用场景 |
|---|---|---|
| `qkv_task` | 任务信号 | 故障来自任务失败，例如备份、迁移或虚拟机启动任务失败 |
| `qkv_alert` | 告警信号 | 故障来自系统告警，例如磁盘、网络、存储或硬件告警 |
| `qkv_dialog` | 弹框信号 | 故障信息只存在于页面弹框、截图或文本提示中 |

### 4.3 生产者信号属性

每条生产者信号需要审核以下属性。

#### 证据作用

| 证据作用 | 审核口径 |
|---|---|
| Must（必要证据） | 缺失后无法确认该案例或无法继续关键诊断步骤 |
| Should（增强证据） | 有它可以增强可信度，但缺失时仍可继续判断 |
| Exclude（排除证据） | 用于否定当前案例或排除某个候选根因 |
| Context（上下文证据） | 只提供变量或背景，不直接参与结论 |

不要把所有信号都设置为 Must（必要证据），否则 Agent 可能因为缺少次要信息而无法诊断。

#### 关键字

关键字应当是现场数据中真实存在且可检索的文字。

推荐：

```text
虚拟机备份失败
磁盘离线
连接存储失败
```

不推荐：

```text
检查一下备份任务为什么失败
可能是磁盘存在问题
需要进一步分析
```

后面这些内容属于说明或推测，不是可检索关键字。

#### 搜索目录和上下文行

主要用于 `qkv_dialog`（弹框信号）：

- 搜索目录必须是平台允许访问的固定目录；
- 上下文行只保留理解弹框所需的少量内容；
- 不要为了“保险”配置过大的搜索目录或上下文范围。

#### 产出变量

生产者信号应把后续排障需要的信息写入 Variable Pool（变量池），例如：

```text
NODE_IP
VM_ID
TASK_ID
DEVICE_ID
ALERT_TYPE
REQUEST_ID
```

审核要求：

- 变量名应准确表达含义；
- 同一个含义不要定义多个不同变量名；
- 变量类型必须正确；
- 变量值必须可以从生产者证据中稳定取得；
- 后续消费者信号引用的变量必须存在；
- 不要产出后续没有使用的无效变量。

## 五、消费者信号审核

### 5.1 消费者信号的作用

QFK Consumer Signal（QFK 消费者信号）用于回答：

> 为了确认或排除根因，Agent 需要到什么地方执行什么只读检查？

### 5.2 选择消费者信号类型

| 信号类型 | 中文说明 | 使用场景 |
|---|---|---|
| `qfk_log` | 日志检查 | 查询日志中的错误、关键字和时间范围 |
| `qfk_system` | 系统检查 | 查询进程、文件、系统状态和资源信息 |
| `qfk_service` | 服务检查 | 查询服务运行状态 |
| `qfk_vm` | 虚拟机检查 | 查询虚拟机状态和配置 |
| `qfk_network` | 网络检查 | 查询网络、端口、路由和连接状态 |
| `qfk_storage` | 存储检查 | 查询存储池、卷、链路和空间状态 |
| `qfk_hardware` | 硬件检查 | 查询磁盘、RAID（磁盘阵列）和硬件健康状态 |
| `qfk_platform` | 平台检查 | 查询平台级状态和元数据 |

### 5.3 第一层：确认在哪里执行

检查以下属性：

- Host（主机）；
- Container（容器）；
- Service（服务）；
- Action（动作）；
- Cluster Execution（是否集群执行）。

审核要求：

- 主机必须是明确值或来自生产者信号的变量；
- 容器必须与命令实际运行环境一致；
- 只有确实需要检查多个节点时才启用集群执行；
- 没有明确执行目标时，禁止默认在全部节点执行；
- 服务检查只允许只读状态动作，不能把启动、停止或重启作为诊断信号。

示例：

```text
主机：{{NODE_IP}}
容器：vtp
服务：backup-service
动作：status
集群执行：否
```

### 5.4 第二层：确认执行什么

根据不同采集类型，检查以下属性：

- Output Format（输出格式）；
- Time Window（时间范围）；
- File（文件）；
- Context Lines（上下文行）；
- Input Variables（输入变量）；
- Request ID（请求标识）；
- Execution Command（执行命令）；
- Input Command（输入命令）；
- Timeout（超时时间）。

重点检查安全性：

- 命令必须是查询、查看或读取类操作；
- 不允许 `start`、`stop`、`restart`、`delete`、`set`、`rm` 等修改动作；
- 不允许把解决方案中的修复命令当成诊断命令；
- 命令执行目标必须明确；
- 超时时间必须有上限；
- 输入变量必须由生产者信号或前序消费者信号提供；
- Request ID 必须来自当前工单或当前执行上下文；
- 页面提供 Command Preview（命令预览）时，必须展开检查最终执行命令。

### 5.5 第三层：确认如何处理执行结果

当前系统中，一条消费者 Signal 在以下两种处理模式中选择一种：

1. Matcher Mode（匹配模式）；
2. Produced Variable Mode（产出变量模式）。

#### 匹配模式

匹配模式用于回答：

> 采集结果中是否存在支持或排除某个根因的现象？

先审核取值配置：

- Value Extraction（取值方式）；
- Row Selection（行选择）；
- Cardinality（结果数量）；
- Output Source（输出来源），例如 stdout（标准输出）或 stderr（标准错误）；
- AI Extraction（AI 提取）。

再审核判断配置：

- Matcher Type（判定类型）；
- Keyword（关键字）或阈值；
- Combination Mode（组合关系）；
- Expected Result（期望结果）。

示例：

```text
从 stdout 中选择包含 error 的所有行
判定类型：关键字
关键字：connection refused
组合关系：任意命中
期望结果：命中
```

审核要求：

- 关键字必须能够在真实输出中出现；
- 判定规则必须可以明确得到 True（命中）或 False（未命中）；
- 不要使用自然语言推测代替确定性规则；
- 行选择和输出来源必须与命令实际输出一致；
- 结果数量必须符合现场真实情况。

#### 产出变量模式

产出变量模式用于回答：

> 从采集结果中提取什么数据，供后续 Signal 或 Agent 推理使用？

每个产出变量需要独立审核：

- Value Extraction（取值方式）；
- Row Selection（行选择）；
- Cardinality（结果数量）；
- Output Source（输出来源）；
- AI Extraction（AI 提取）；
- Variable Name（变量名）；
- Variable Type（变量类型）；
- Variable Value（变量值来源）。

当前页面支持一条消费者 Signal 产出多个变量，每个变量均有独立的取值规则。

审核要求：

- 变量名应使用稳定且容易理解的名称；
- 变量类型必须与实际结果一致；
- 单值和多值的结果数量配置必须正确；
- 不要让多个变量错误地共享同一个取值结果；
- 后续没有使用的变量应删除。

## 六、当前设计下的多处理结果表达方式

当前系统实际规则如下：

- 一条消费者 Signal 可以配置一个匹配判断；
- 或者配置一个或多个产出变量；
- 同一条消费者 Signal 不能同时配置匹配模式和产出变量模式。

因此，如果同一次采集既要判断结果，又要产出变量，需要在当前页面中拆成多条消费者 Signal。

例如，同一个硬件查询既要判断磁盘异常，又要提取磁盘序列号：

```text
消费者信号 A
├── qfk_hardware（硬件检查）
├── 查询磁盘状态
└── 匹配模式：是否包含 Predictive Failure

消费者信号 B
├── qfk_hardware（硬件检查）
├── 使用相同查询参数
└── 产出变量：DISK_SERIAL
```

如果需要执行两个不同判断，也拆成两条消费者 Signal：

```text
消费者信号 A：判断是否存在 Predictive Failure
消费者信号 B：判断 Reallocated Sector 是否超过阈值
```

审核时应确保拆分后的消费者信号具有一致的主机、容器、命令、时间范围和超时时间，避免同一采集意图出现不一致配置。

## 七、检查生产者和消费者能否连接

完成单条信号审核后，需要从头检查完整证据链：

```text
任务、告警或弹框
    ↓ 生产者信号
产出 NODE_IP、VM_ID、TASK_ID 等变量
    ↓ 消费者信号引用变量
在正确主机和容器执行只读检查
    ↓ 匹配或提取
得到支持或排除根因的结果
    ↓
Agent 形成诊断结论
```

重点检查：

- 消费者引用的变量是否有生产者或前序消费者提供；
- 变量名是否完全一致；
- Must（必要证据）是否真的决定结论；
- Exclude（排除证据）是否能够正确排除当前案例；
- 同一条证据是否被互相矛盾的规则解释；
- 是否存在只有采集命令、没有匹配或变量产出的消费者信号；
- 是否存在只有匹配规则、没有可执行采集方式的消费者信号；
- 多条消费者信号复用同一采集意图时，采集参数是否一致。

## 八、审核版本、生效状态和发布前检查

### 8.1 理解三个版本

页面“版本、生效与发布前检查”区域显示：

| 版本 | 含义 |
|---|---|
| Proposal Revision（模型提案修订） | 流水线或重新抽取生成的模型结果，是专家审核的基线 |
| Expert Revision（专家修订） | 专家修改并保存的工作版本，保存后仍未自动供 Agent 使用 |
| Agent Active Revision（Agent 当前生效修订） | 当前生产 Agent 实际读取的版本 |

必须牢记：

- Save（保存）只保存专家工作稿；
- Approve and Publish（审核通过并发布）才会切换 Agent 当前生效版；
- 修改已发布 KBD 时，应先创建 Maintenance Working Copy（维护工作稿）；
- 维护期间 Agent 继续使用旧生效版，只有“发布维护版”成功后才原子切换；
- 版本冲突表示页面打开后内容已被其他人修改，必须刷新并重新审核，不能覆盖提交。

### 8.2 运行 Signal Review（信号审查）

点击 Signal Review（信号审查），按页面提示逐项处理。

处理原则：

- Error（错误）必须修复；
- Warning（警告）需要人工确认，不能直接忽略；
- 使用“定位并编辑”跳转到对应信号；
- 修改正文、截图、分类或 Tool Contract（工具契约）后，如果 Signal 被标记为过期，需要重新抽取或重新确认；
- 所有暂存修改必须先保存；
- 最终命令预览必须与审核意图一致；
- 出现版本冲突时，应刷新页面后重新检查，不能覆盖其他审核人员的修改。

### 8.3 检查 Tool Capability and Command Preview（工具能力与命令预览）

每条消费者 Signal 还应检查：

- Acquire Tool（采集工具）是否已在 Tool Registry（工具注册表）声明并启用；
- Signal 参数是否满足该工具的 Args Schema（参数结构）；
- Command Preview（命令预览）能否编译出最终命令；
- SSH Target（SSH 目标主机）、容器和待替换变量是否符合审核意图；
- 命令是否只读、范围是否受控、超时时间是否合理；
- 命令预览失败时，不能根据正文中的示例命令猜测发布，应先修复工具模板或 Signal 参数。

### 8.4 Offline Collection Impact（离线采集影响）

Offline Collection Impact（离线采集影响）用于回答：

> 当前 KBD 所要求的消费者证据，在没有 SSH 在线诊断的场景下，能否通过离线采集器安全采集；KBD 变化后哪些离线资源需要重新同步或生成？

其关联链路为：

```text
KBD Consumer Signal（KBD 消费者信号）
  → Signal Mapping（信号映射）
  → Collector（安全采集器）
  → Collection Profile（采集画像）
  → Collection Plan（采集计划）
  → Collector Artifact（采集器制品）
```

问题场景归属只有一个权威来源：审核人员发布 KBD 时确认的 Final Category（最终分类，`category_id`）。
在线诊断和离线诊断使用同一分类编码；KBD 发布后自动进入离线资源同步范围，不需要再填写
`offline_scenario`、`offline_enabled` 或 `offline_capable`。因此审核人员必须重点确认最终分类准确，
不能依靠标题关键词或离线专属开关在下游纠正分类。

页面字段含义：

| 字段 | 含义 | 审核动作 |
|---|---|---|
| Collection Requirement（采集需求） | 当前 KBD 有多少项需要离线采集的证据需求 | 与消费者 Signal 数量和意图核对 |
| Valid Mapping（有效映射） | 多少项需求已经匹配到安全采集命令或模板 | 应尽量覆盖全部采集需求 |
| Affected Profile（影响画像） | 哪些采集画像引用了相关采集项 | 发布后记录需要增量同步的画像 |
| Historical Plan/Artifact（历史计划/制品） | 多少历史采集计划和制品基于旧资源生成 | 旧制品保持可追溯；新工单应在同步后重新生成 |
| Missing Mapping（缺失映射） | 有消费者 Signal，但找不到对应离线采集实现 | 记录 Signal ID、采集工具和命令/关键字，交由离线诊断管理员补齐 |
| Lifecycle Policy（生命周期联动规则） | 发布、退回草稿、归档或停用时下游资源如何变化 | 按提示执行增量同步、停用或重新生成 |

结果处理口径：

| 页面结果 | 对 KBD 发布的影响 | 后续动作 |
|---|---|---|
| 离线采集依赖完整 | 不阻止 KBD 发布 | 发布后执行 KBD Incremental Sync（KBD 增量同步），形成新的离线资源修订 |
| 离线采集依赖不完整 | 当前仍不阻止 KBD 发布 | 在审核备注记录缺失项；发布后补齐 Signal Mapping/Collector 模板，再同步并审核候选资源 |
| 影响信息暂时无法读取 | 不阻止 KBD 发布 | 记录平台检查失败，恢复后重新执行影响检查和增量同步 |

> Offline Ready（离线就绪）和 KBD Publishable（KBD 可发布）是两个不同结论。前者决定离线诊断资源能否激活或生成制品，后者决定在线 Agent 是否可以使用该 KBD。不能把离线映射缺失误写成 KBD 内容发布失败。

### 8.5 当前真正的发布硬门禁

当前代码会在发布时逐条检查：

1. KBD 正文存在，能够形成检索文本；
2. Signal 文档非空；
3. Signal 通过 Shared Resolution Runtime（共享解析运行时）发布审查；
4. Signal 满足发布 Schema（结构契约）和专家确认要求；
5. 至少存在一条 QFK Consumer Signal（QFK 消费者信号）；
6. 最终 Category（分类）不为空；
7. Lock Version（乐观锁版本）与提交时一致，没有并发修改。

Embedding（向量）生成失败时，当前代码会清除不可信旧向量并继续完成发布，后续需要单独补做向量生成；不能把“状态已发布”等同于“所有检索增强能力均已生成成功”。

Offline Collection Impact（离线采集影响）不在上述 KBD 发布硬门禁中。

### 8.6 离线采集影响与 KBD 生命周期

KBD 发布和离线采集资源生效是两个步骤：

1. KBD 审核发布后，Agent 可以使用新的 KBD Revision（KBD 修订）；
2. 该 KBD 自动按最终 `category_id` 加入离线同步范围；
3. 离线诊断管理员执行 KBD Incremental Sync（KBD 增量同步），生成并批准对应的 Collector（采集器）、Signal Mapping（信号映射）和 Collection Profile（采集画像）候选版本。

因此，离线采集映射缺失应记录为发布后的同步待办，不能简单理解为 KBD 内容本身错误。

## 九、填写审核备注并发布

审核备注建议说明：

- 修正了哪些正文内容；
- 是否修改分类；
- 新增、删除或调整了哪些生产者/消费者信号；
- 是否修改了执行命令或处理规则；
- 是否仍有离线诊断同步待办；
- 是否存在需要后续真实环境验证的事项。

审核备注示例：

```text
已确认案例分类为虚拟机备份失败；修正 qkv_task 关键字并补充 NODE_IP、TASK_ID 变量；
将日志检查限定到 vtpdaemon.log 和故障前后 30 分钟；命令预览为只读操作；
Signal Review 已通过。发布后需要执行离线诊断 KBD 增量同步。
```

确认审核身份、审核备注和发布前审查结果后，点击“审核通过并发布”。

## 十、批量审核与失败处理

批量识图、批量重新分类、批量抽取信号、批量通过和批量拒绝都会进入 Batch Job（批量任务）列表，并保留每个 KBD 的独立结果。

使用要求：

1. 点击批次“详情”，先看成功、失败和中断数量；
2. 对失败 KBD 查看 Error Code（错误码）、易读失败原因和完整错误详情；
3. 使用记录后的“查看”进入当前 KBD 完整审核页；
4. 使用“编辑”重新加载当前 KBD 后修复正文、分类、截图或 Signal；
5. 业务校验失败应先修复具体问题，不要直接反复点击“重试未成功”；
6. 原批次及错误结果保持不可变，新重试会形成新的 Batch ID（批次编号）。

批量通过是“逐条执行单篇 KBD 的全部发布门禁”，不是跳过审核的一键发布。一个批次允许部分成功；失败 KBD 不会影响已经成功发布的 KBD。

## 十一、发布完成的判断标准

发布成功后应确认：

- KBD 状态变为“已发布”；
- 已生成新的 Expert Revision（专家修订）；
- Agent Active Revision（Agent 当前生效修订）已更新；
- 原 AI Proposal 和历史 Expert Revision 仍可追溯；
- 已发布内容与审核工作稿一致；
- 若用于离线诊断，已记录后续 KBD 增量同步待办。

## 十二、最终发布检查清单

### 内容与分类

- [ ] 标题、问题描述、根因和解决方案正确；
- [ ] 分类已经人工确认；
- [ ] 截图识别结果可信；
- [ ] 正文与 Signal 之间不存在矛盾。

### 生产者信号

- [ ] 生产者信号类型选择正确；
- [ ] 证据作用合理；
- [ ] 关键字可以在真实数据中检索；
- [ ] 搜索目录和上下文行范围合理；
- [ ] 产出变量名称、类型和值来源正确。

### 消费者信号

- [ ] 至少有一条消费者信号；
- [ ] 消费者类型选择正确；
- [ ] 主机、容器、服务和集群执行范围正确；
- [ ] 输入变量均有明确来源；
- [ ] Request ID 来自当前执行上下文；
- [ ] 时间、文件和上下文行范围合理；
- [ ] 所有命令都是只读操作；
- [ ] 最终命令预览正确；
- [ ] 超时时间合理且有上限。

### 结果处理

- [ ] 匹配模式的取值方式、行选择、结果数量和输出来源正确；
- [ ] 匹配类型、关键字、组合关系和期望结果正确；
- [ ] 产出变量的取值方式、变量名、变量类型和值来源正确；
- [ ] 同一消费者 Signal 没有同时配置匹配模式和产出变量模式；
- [ ] 需要多种处理结果时，已按当前系统能力拆成多条消费者 Signal。

### 发布门禁

- [ ] 生产者能够提供消费者需要的变量；
- [ ] 没有未保存或已过期的 Signal；
- [ ] Signal Review 没有阻断错误；
- [ ] 审核身份已填写；
- [ ] 审核备注说明了重要修改和遗留事项；
- [ ] 已检查 Proposal Revision、Expert Revision 和 Agent Active Revision 的关系；
- [ ] 已核对来源元数据和截图 Evidence 的可信度；
- [ ] Tool Capability 已声明，Command Preview 与审核意图一致；
- [ ] 已确认 Offline Collection Impact 是否存在缺失映射；
- [ ] 已确认最终 Category 是在线、离线诊断共用的问题场景，且分类准确；
- [ ] 离线采集缺失项已记录为同步待办，没有误判成 KBD 发布硬门禁；
- [ ] 批量发布失败时，已进入批次详情按 KBD 查看原因并修复。

全部检查完成后，方可执行“审核通过并发布”。
