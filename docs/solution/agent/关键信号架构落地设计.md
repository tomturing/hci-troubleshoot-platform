## 1. 背景与决策

### 1.1 两方案回顾

| 维度 | 方案一（KeySignal 基类设计） | 方案二（字段级分别抽取） |
|------|---------------------------|------------------------|
| 核心思路 | KeySignal 抽象基类 + FrontendSignal/BackendSignal 派生 + SignalExtractor + VariablePool | acquirer + acquirer_args 绑定采集器 + produces/requires 变量绑定 + matcher 类型化求值 |
| 完成度 | ~20%（仅基类与数据模型骨架，运行时引擎走 qkv/qfk 独立实现） | ~80%（抽取路由 + DB Prompt + signals_json 持久化 + CDD 引擎均已落地） |
| 运行时状态 | **dead code**：`tools/signal/` 全部文件无生产调用 | **live**：`kbd_differential.py` -> `qkv/qfk` 引擎 + `extract_signals.py` 路由 |

### 1.2 核心决策

1. **方案一代码全部废弃删除**：`tools/signal/` 目录（7 文件 ~1051 行）在运行时无任何调用路径，仅 3 个 SystemTools facade 方法引用（自身也无生产调用），2 个测试文件覆盖。保留只增加认知负担。
2. **QFK 从枚举路由改为 namespace 字符串路由**：acli 的 namespace 是扁平字符串（`log`/`service`/`system`/`storage`...），`BackendSignalType` 枚举是多余的中间层。改为 `qfk.log`/`qfk.service`/`qfk.system` 等 namespace 命名，HandlerRegistry 用字符串 key 路由。
3. **QKV 从硬编码字段提取改为 produces 动态提取**：`parser.py` 当前按 query_type 硬编码提取字段（alert 取 7 字段、task 取 9 字段）。改为按 signal 的 `produces` 规格动态提取，`produces` 为空时保留硬编码兜底。
4. **matcher 类型对齐**：`extract_signals.py` 的 `VALID_MATCHER_TYPES`（5 种，无 regex）与 `kbd_differential._evaluate_matcher`（6 种，含 regex）不一致，统一为 6 种。
5. **ACQUIRER_CATALOG 更新**：QFK 名从 signal-type 命名（`qfk.log_keyword`/`qfk.service_status`...）改为 namespace 命名（`qfk.log`/`qfk.service`...）。
6. **QKV/QFK 注册到 tool_definition**：将 QKV/QFK 注册到 `tool_definition` 表，复用现有 `ToolManageView.vue` 管理入口，通过 `ProducesEditor.vue` 和 `MatcherEditor.vue` 提供可视化编辑，无需新建信号模板管理页。

### 1.3 设计原则（核心认知纠正）

> **人能参与且足够简单；LLM 能执行且足够准确。**

**关键认知纠正（2026-07-16）**：

| 修正前（错误理解） | 修正后（正确理解） |
|------------------|------------------|
| QKV/QFK 是确定性引擎内部组件，不该暴露给 LLM | **QKV/QFK 就是跟 acli/sop/scp 一样的 tool**，只是定位不同 |
| acli 限制是为了防止 QKV/QFK 被 LLM 调用 | acli 限制是**兜底安全网**：LLM 幻觉了要删系统文件，acli 会报错拒绝 |
| 信号抽取目的是"消除 LLM 幻觉" | 信号抽取目的是**把人获取信息时的隐藏经验工具化** |

**QKV/QFK 的定位**：

- QKV/QFK 是**工具（tool）**，跟 acli_exec、get_active_alerts、get_sop_node 等并列
- 关键差异在于它们需要支持**可配置的输入**和**可配置的输出**：
  - **可配置输入**：让 agent 知道传入什么参数（keyword、limit、is_failed 等）
  - **可配置输出**：自定义解析哪些结果存到变量池（produces 字段）
- 整个关键信号 + QKV/QFK 的设计是为了解决 **agent 不能执行 KBD 的问题**，而根因是获取信息依赖隐藏经验

**KBD 即语义 Playbook**：
- 抽取信号只是 toolize 隐藏经验，不是把 KBD 转成程序
- QFK 复杂在方法多样性（命令和参数）；QKV 复杂在结果多样性（解析的字段）
- Agent 受限访问后台，acli（封装在容器中）是对 agent 暴露的唯一接口

## 4. matcher 类型（改造后，6 种统一）

| type | 用途 | 关键字段 | 求值位置 |
|------|------|---------|---------|
| `keyword` | 关键字匹配 | pattern, mode(any/all), expected | QFK engine + _evaluate_matcher |
| `regex` | 正则匹配 | pattern, expected | _evaluate_matcher |
| `state` | 状态值匹配 | pattern, expected | _evaluate_matcher |
| `threshold` | 数值阈值 | pattern/value, operator, expected | _evaluate_matcher |
| `json_path` | JSON 路径取值 | path, expected_value, expected | _evaluate_matcher |
| `exists` | 存在性判定 | expected | _evaluate_matcher |
