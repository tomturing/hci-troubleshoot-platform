## 0. 现状盘点（基于 `feat/qkv-qfk-dual-core` 实测）

PR498/533 已把**运行时引擎**做完，但**"原始案例 → 关键信号"的抽取与持久化是断的**。下表为实测结论：

| 已有（PR498/533 已做） | 缺失（本次要补） |
|---|---|
| `tools/signal/base.py`：`SignalCategory(FRONTEND/BACKEND)` + `KeySignal` 抽象基类 | **抽取器**：只有 `extractor.py` 骨架，无"原始案例→信号"的 pipeline 阶段、无 Prompt、无 `signals_json` 落库 |
| `tools/qkv/`：`alert/task/dialog` 三种 QKV 采集 + JSON 解析 | **持久化**：`kbd_entry`/`sop_document` 无 `signals_json` 列；分支内 `converter.py` 曾硬编码 `steps_json: []`（已在 #547 清理，现仅输出 `signals_json`） |
| `tools/qfk/`：`HandlerRegistry`（log_keyword/service_status/vm_state/network_check/storage_state/hardware_state/platform_state/system_metric 8 类）+ acli 指令构建 | **前端"关键信号"区块**：`KbdReviewView.vue` 只动了内容预览解析，无专门面板 |
| `variable_pool/engine.py`：会话级全局变量池 + JIT 获取 + 三套占位符（`{{var}}`/`{var}`/`${var}`）+ derived 表达式 | **变量池与信号/工具的占位符不统一** |
| `tools/signal/variable_pool.py`：SignalVariablePool 桥接前端信号→变量池 | **QFK 复杂定义**：只有 keyword/state，缺 threshold/json_path 等求值器；采集器与变量池绑定关系未固化 |

**核心缺口一句话**：采集器引擎有了，但"怎么从案例里产出结构化信号"和"信号怎么落库 / 怎么跟变量池接"这两段是空的——这正是"细分的前端/后端信号抽取方法"与"QFK 复杂定义"不满意的根因。

## 1. 第一性原理：重定义"关键信号 × 采集器(QKV/QFK)"

排障知识的本质是一段**叙事**：*“该去哪里取什么证据、取到后说明什么”*。机器要可执行，必须把两个**正交**的关注点拆开：

1. **证据采集（怎么取到一个值）= 采集器（Acquirer）**：即 **QKV / QFK**，是*手段*。
2. **证据判定（取到后意味着什么）= 关键信号（KeySignal）**：是一条*不可变断言*（在目标上匹配某种模式 → 确认/排除某假设），是*语义*。

PR498/533 把 `frontend/backend` 当成了信号的**主分类轴**（前端=提取元数据、后端=布尔判定），这个"角色轴"方向是对的，但**抽取方法弱**：它是"每个 step 文本 → 抽一个信号"的扁平做法，精度低、且与变量池的耦合是隐式的。

**修正后的心智模型（本方案核心）**：

> **信号（Signal）= 判定契约**；**采集器（QKV/QFK）= 获取契约**。
> 一条信号通过 `acquirer` + `acquirer_args` **绑定**到一个采集器。
> - **生产者信号（Producer）**：用 **QKV** 取数 → 写入会话**变量池**（`host`/`vm`/`errcode`…）。
> - **消费者信号（Consumer）**：用 **QFK** 取数并判定 → **读取**变量池来渲染自己的 `target`，再做匹配。
>
> 所谓"前端信号/后端信号"，本质就是 **Producer（QKV 支撑，写变量）vs Consumer（QFK 支撑，读变量+判定）**。

## 2. 关键信号数据模型（修正版）

统一抽象（保留 PR 的 `KeySignal` 基类与 `SignalCategory`，补上变量绑定契约）。**占位符统一为 `{{VAR}}`**（见 §5）。

```python
# 通用：信号 = 判定契约
class KeySignal(BaseModel):
    id: str                      # 信号唯一 ID（同 KBD 内稳定，便于人工编辑/去重）
    signal_category: SignalCategory   # FRONTEND=producer / BACKEND=consumer
    keyword: str                 # K：从案例文本抽出的核心检索词（人读+检索）
    description: str | None
    acquirer: str               # 绑定的采集器：qkv.alert / qkv.task / qkv.dialog / qfk.log / qfk.service / qfk.system / ...
    acquirer_args: dict        # 采集器参数模板（含 {{var}} 占位符）
    # —— 变量绑定契约（PR 缺的关键一环）——
    produces: list[VariableSpec] | None   # 仅 producer：本信号向变量池写入的变量（name/type/path）
    requires: list[str] | None         # 仅 consumer：本信号渲染所需的变量名（必须 ∈ 变量池 schema）
    # —— 判定契约（consumer 用）——
    matcher: Matcher            # {type: keyword|state|threshold|json_path|exists, pattern, mode: any|all, expected: bool}

# 生产者（前端信号）→ QKV
class FrontendSignal(KeySignal):
    signal_category = FRONTEND
    # acquirer ∈ {qkv.alert, qkv.task, qkv.dialog}
    # produces: 例如 [{name:"host", path:"host"}, {name:"vm", path:"vm"}]

# 消费者（后端信号）→ QFK
class BackendSignal(KeySignal):
    signal_category = BACKEND
    # acquirer ∈ {qfk.log, qfk.service, qfk.system, qfk.vm, qfk.network, qfk.storage, qfk.hardware, qfk.platform}
    # requires: 例如 ["host","vm"]，渲染 acquirer_args.target 的 {{host}}
```

`Matcher` 把 PR 里散落的 `expected_pattern`（`__REGEX__:`/`__CONTAINS__:`/自然语言）升级为**类型化求值器**（见 §6），消除"自然语言判定"这种不可控分支。

## 3. 字段级分别抽取方法（重点改进）

**拒绝 PR 的"逐 step 抽一个信号"**。改为**按字段 × 按角色两段式、模式受限抽取**：

1. **字段级切片**：抽取只喂 `steps_text`（有效排查步骤）+ `root_cause`（要确认的结论）+ `alert_info` 三块（其余章节作上下文），而非整篇。
2. **角色分句**：先把 `steps_text` 切成*祈使子句*（"查看告警/检查任务/导出日志"→ 生产者）与*陈述子句*（"若日志含 X 则根因为 Y"→ 消费者）。
3. **受限词表 + 变量 schema 注入**：LLM 同时拿到
   - **采集器目录**（封闭词表）：`qkv.alert/qkv.task/qkv.dialog` + `qfk.*` 8 类及其参数 schema；
   - **变量池 schema**：当前可引用变量名（`host`/`vm`/`node_ip`…）。
   → 输出**严格类型化 JSON**，保证 `acquirer` 必合法、`requires` 变量必 ∈ schema（直接根治"LLM 编造 tool_name"这一 `steps_json` 老毛病）。
4. **后校验 + 回退**：凡 `acquirer` 不在目录、或 `requires` 变量不在 schema → 丢弃并记 reason，必要时二次 Prompt 修正；低置信/歧义信号标 `needs_review`（镜像 `classify` 的 low_confidence）。

> "字段级分别抽取"之"分别"= **按字段切、按角色（producer/consumer）切、按采集器类型切，三层分别**。

## 4. 完整闭环：原始案例 → 关键信号 → QKV/QFK → 执行 → 判定 → 消除

```
原始案例 HTML
  └─ converter.py（已有）提取 8 章节 → steps_text / root_cause / alert_info
       └─ 【新增】Signal Extraction 阶段（镜像 VISION）
             LLM + 采集器目录 + 变量 schema → SignalSet{producers[], consumers[]}
             校验 → 落库 kbd_entry.signals_json（与 sop_document 同构）
  └─ 诊断时（CDD 引擎改造，见 §9）
       Phase A 生产：跑所有 producer 信号（QKV）→ 填充会话变量池
       Phase B 消费：对每个候选 KBD 跑 consumer 信号（QFK）
                  · 用变量池渲染 target 的 {{host}}
                  · HandlerRegistry 构建 acli 指令 → 执行
                  · Matcher 求值 → 布尔
       └─ 贪心消除（沿用 _judge_matches 逻辑，只是 expected_pattern 升级为 Matcher）
```

闭环关键点：**变量池是 producer 与 consumer 之间的黑板（blackboard）**。QKV 写、QFK 读——这就是"QFK 需要跟变量池对接"的天然答案。

## 5. 变量池统一设计

- **唯一变量池 = 会话级全局变量**（`variable_pool/engine.py` 已实现，复用，不新建）。
- **统一占位符为 `{{VAR}}`**（决策②）。当前三套并存：`{{var}}`（CDD `_resolve_args`）、`{var}`（`engine.py:42` 正则带负向后顾）、`${var}`（`signal/variable_pool.py`）。统一为 `{{var}}` 理由：
  - CDD 热路径已是 `{{var}}`（一致性原则：热路径已有就不引入第三套）；
  - `{{ }}` 在 HCI 生态（Helm/K8s 用 `{{ }}`，Shell 用 `${ }`）里与 shell `${VAR}`、字面花括号碰撞最小；
  - LLM 抽取更稳（Jinja/Helm 语感）。
  - 改动点：`variable_pool/engine.py` 的 `_TEMPLATE_PLACEHOLDER_RE` 与 `signal/variable_pool.py` 的 `render_template` 都改认 `{{var}}`；`tool_args_template`/`acquirer_args`/`target` 同一套渲染、同一个池。
- **采集即变量获取，复用既有 acquisition_strategy**：把 QKV 产出映射成 `variable_schema` 条目，其 `acquisition_strategy` 用既有的 `tool_call`/`json_extract`/`derived` 之一（例如 `tool_call:qkv_alert`）。这样"工具参数模板"和"变量池"在**同一套获取框架**下收敛。
- QKV/QFK 都支持在 **admin-ui 工具管理页自定义调整**：QKV 的 3 方法、QFK 的 8 类 Handler 默认值与 Matcher 模式均可改。

## 6. QFK 复杂定义（决策③：3 段式 DSL + 5 类定型求值器）

把 QFK 定义为**声明式探针规范（小 DSL）**，三段分离（获取/判定/变量耦合）：

```yaml
probe:        { namespace: vm|network|storage|hardware|platform|system,
               sub_command: "list" | "asan disk list",
               args_template: {target: "{{host}}"} }
valuator:     one of                          # 定型枚举，非通用表达式语言
               keyword     # 命中关键字（any/all + expected）
               state       # service_status：asv/anet/host 的 status == expected
               threshold   # system_metric：解析数值并与 expected 比较（>,<,>=,<=）
               json_path   # 从探针 JSON 输出取路径值再判定
               exists      # 某对象/告警是否存在
bindings:     # 复杂定义的核心：探针输出路径 ↔ 变量 的双向绑定
               produces(output→var): json_path + 可选 derived 表达式（复用 §5 变量池引擎）
               requires(var→probe): {{var}} 模板（渲染 args）
```

- `HandlerRegistry` 保留 PR 的 8 类映射（好设计，沿用），每类补 `valuator` 分发；新增 `threshold`/`json_path`/`exists` 三种求值器覆盖非关键字场景。
- **不**把变量池那套 `_evaluate_derived_expression`（三元/函数 DSL）塞进 QFK `valuator`——那是代码执行面、LLM 难稳产、admin 不可审计。改为：**bindings 复用既有 derived 引擎**做 `output→var` 变换，`valuator` 自身只做定型判定。
- 业界对照：Prometheus `expr+for+labels`、Datadog `query+threshold+aggr`、K8s probe——都是 2~3 个正交字段的*定型*声明，而非图灵完备语言。
- 这样 QFK "支持复杂定义"= 组合 `probe + valuator + bindings`，且**全声明、可 admin 编辑**。

## 7. 持久化与 DB（决策④：KBD + SOP 通用）

**"关键信号"是来源无关原语**，故列同时加在两表，保证跨文档通用：

```sql
ALTER TABLE kbd_entry    ADD COLUMN signals_json jsonb NOT NULL DEFAULT '[]'::jsonb;
ALTER TABLE sop_document ADD COLUMN signals_json jsonb NOT NULL DEFAULT '[]'::jsonb;
-- 部分 GIN 索引
CREATE INDEX idx_kbd_signals ON kbd_entry
  USING GIN (signals_json) WHERE status='published' AND signals_json != '[]'::jsonb;
CREATE INDEX idx_sop_signals ON sop_document
  USING GIN (signals_json) WHERE status='published' AND signals_json != '[]'::jsonb;
-- 彻底移除 steps_json（开发测试阶段，无对外发布契约，不做兼容桥）
-- 同步删除清单见 §10 ADR-1：模型字段、ingest API、admin PATCH、converter 硬编码、
--           cases.py 检索门槛、kbd_differential 读取、及相关注释/测试 fixture
ALTER TABLE kbd_entry    DROP COLUMN IF EXISTS steps_json;
ALTER TABLE sop_document DROP COLUMN IF EXISTS steps_json;
```

- 抽取服务按 `source_type=kbd|sop` 参数化——KBD 读 8 章节，SOP 读决策树节点的诊断动作；运行时 QKV/QFK 引擎对来源无感知，只执行 SignalSet。
- **`steps_json` 在本轮全部移除**（开发测试阶段、无发布契约、去冗余）；`signals_json` 为**唯一字段**，引擎只消费它。

## 9. 与现有 CDD 引擎对接（ADR-1 落地）

### ADR-1：彻底移除 `steps_json`，仅保留 `signals_json`（决策①，修订）

- **修订背景**：上一版基于"实时系统数据契约演进安全性"建议 `steps_json` 限时共存。但当前环境为**开发测试阶段、平台未对外发布**，不存在发布契约/在线回滚诉求；阶段目标转为**设计合理、简单、去冗余**。
- **决议**：**彻底移除 `steps_json`**——列、模型字段、ingest/admin API、converter 硬编码、cases.py 检索门槛、CDD 引擎读取、及相关注释，全部删除。`signals_json` 为**唯一字段**，CDD 引擎只消费它，无回退、无特性开关、无 sunset 桥。
- **移除清单（落地时逐一核对）**：
  1. `kbd_entry`/`sop_document` 模型：删 `steps_json` 列与 ORM 字段；
  2. `ingest.py` / `admin.py` PATCH：删 `steps_json` 入参与写库；
  3. `converter.py`：删 `"steps_json": []` 硬编码；
  4. `cases.py`（`search_cases_with_steps` / `kbd_search.py`）：检索门槛由 `steps_json != '[]'` 改为 `signals_json != '[]'`；
  5. `kbd_differential.py`：由读 `steps_json` 改为读 `signals_json`（producers/consumers）；
  6. 所有提及 `steps_json` 的注释、文档、测试 fixture 一并清理。
- **对 ADR 编号说明**：原 ADR-1（共存）作废；本决策为其替代。

### ADR-2：占位符统一为 `{{VAR}}`（大写，强制校验）（决策②，修订）

- **大写强制**：占位符**必须全大写** `{{VAR}}`（变量名 `[A-Z][A-Z0-9_]*`，支持点分路径如 `{{NODE.IP}}`）。**禁止**小写/混合大小写 `{{var}}`/`{{Var}}`。
  - 理由：开发测试阶段追求简单一致；大写变量在排查脚本/日志/LLM 输出中一眼可辨，与 shell `${var}`、Markdown `{{ }}` 模板、以及自然语言彻底区分，降低误解析。
- **三套并存收敛**：原 `{{var}}`（CDD）/ `{var}`（engine.py 正则）/ `${var}`（signal 模块）统一为 `{{VAR}}` 大写。
- **强制校验（enforcement，必须有，不能只靠约定）**：
  1. **正则单一真相源**：`variable_pool/engine.py` 的 `_TEMPLATE_PLACEHOLDER_RE` 改为严格大写：
     `re.compile(r"(?<!\{)\{([A-Z][A-Z0-9_]*(?:\.[A-Z0-9_]+)*)\}(?!\})")`。
  2. **校验函数**：新增 `validate_placeholder_case(template: str) -> None`，扫描所有 `{{...}}` 占位符，凡不匹配全大写规范即抛 `ValueError`（含具体违规名与位置）。
  3. **接入点（三处强制）**：
     - `KeySignal.validate()`（信号模型校验）——信号落库前拦截非法占位符；
     - `variable_pool` 渲染入口 `render_template`/`_render_args_template`——渲染时再校验一次（防御性）；
     - **抽取 Prompt 指令**：`kbd_extract_signals_v1` 明确"占位符必须 `{{大写}}`，小写一律判为非法"。
  4. **单测**：`tests/unit/test_placeholder_uppercase.py` 覆盖合法/小写/混合/点分路径/嵌套等用例。
  5. （可选）CI 预提交钩子对 `.py`/`.md`/`.vue` 做一次正则扫描，阻断小写占位符入库。

### ADR-3：QFK DSL 粒度（决策③）

- 3 段式 `probe / valuator / bindings` 保留；`valuator` 固定 **5 类定型枚举**（keyword/state/threshold/json_path/exists），**不**引入通用表达式语言。
- `bindings.produces` 复用既有 derived 引擎做 `output→var` 变换；`valuator` 只做定型判定。

### ADR-4：SOP 一并包含 `signals_json`（决策④）

- 一次定义 `signals_json` 为跨文档原语（同 `KeySignal` 模型、同 QKV/QFK 引擎），抽取器 `source_type` 参数化，列同时加 `kbd_entry` 与 `sop_document`。
- 运行时引擎来源无关，唯一来源相关的是抽取与存取；边际成本低、避二次迁移债。
