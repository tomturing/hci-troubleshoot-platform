## Part 1：两份已有方案的对比分析（背景）

### 1.1 共享的核心逻辑链路

两份文档（[基类设计](./关键信号基类设计.md) 和 [字段级抽取](./关键信号字段级分别抽取.md)）都接受同一条主干：

```
原始案例（KBD/SOP 自然语言叙事）
   │  ① 抽取
   ▼
关键信号（KeySignal）：结构化、可机读的"判定契约"
   ├── FrontendSignal（前端/生产者）── 绑定 QKV ── 取数 ── 写变量池
   └── BackendSignal （后端/消费者）── 绑定 QFK ── 读变量池渲染 ── 执行 ── 判定
   │  ② 执行（LLM 驱动 QKV/QFK 引擎）
   ▼
变量池（黑板）：host / vm / time / errcode ...
   │  ③ 判定是否满足（匹配 -> 布尔 -> 贪心消除）
   ▼
诊断结论 + 证据链
```

两者都认同：**前端信号=QKV=生产者（写变量），后端信号=QFK=消费者（读变量+判定）**，"前端/后端"本质是"生产者/消费者"角色。变量池是两者之间的黑板。

### 1.2 三个本质区别

#### 区别 1：抽象轴不同 —— "信号 = 工具" vs "信号 ⟂ 工具"

| | 基类设计（文档一） | 字段级抽取（文档二） |
|---|---|---|
| 心智模型 | **信号与采集器一体**：FrontendSignal≈QKV，BackendSignal≈QFK，OOP 继承归到父类 | **信号与采集器正交**：信号=判定契约（语义），采集器=获取契约（手段），通过 `acquirer`+`acquirer_args` 绑定 |
| 表现 | `execute()` 直接焊死调用 `qkv_exec`/`qfk_exec` | `KeySignal` 有 `acquirer` 字段显式声明用哪个采集器 |

#### 区别 2：抽取方法不同 —— "逐 step 扁平抽取" vs "字段×角色×采集器三层分别抽取"

- **文档一**（被批评的做法）：整篇 KBD 喂 LLM，开放式生成 JSON，LLM 自由判别 frontend/backend
- **文档二**（改进做法）："分别"三层：
  1. 按字段切（只喂 `steps_text`+`root_cause`+`alert_info`）
  2. 按角色切（祈使子句→生产者，陈述子句→消费者）
  3. 按采集器类型切 + 受限词表（封闭采集器目录 + 变量池 schema 注入，输出严格类型化 JSON，后校验 + 回退）

#### 区别 3：判定能力与变量契约不同

| | 文档一 | 文档二 |
|---|---|---|
| 判定器 | `keywords` + `match_mode(any/all)` + `expected`（仅关键字） | 5 类定型求值器（keyword/state/threshold/json_path/exists）+ 3 段式 DSL（probe/valuator/bindings） |
| 变量契约 | 隐式（`${host}` 占位符无保障） | 显式（`produces`/`requires` 契约，可静态校验） |
| 占位符 | `${variable}`（三套并存） | 统一为全大写 `{{VAR}}` + 强制校验 |

### 1.3 工程闭环广度差异

文档一是**纯架构/OOP 重构文档**，文档二是**端到端落地方案**。后者覆盖了前者完全没碰的环节：持久化（`signals_json` 列）、抽取 pipeline（Stage 5）、Prompt 管理（`kbd_extract_signals_v1` 热加载）、审核门、前端面板、SOP 复用、批回填、ADR。

### 1.4 优劣势速览

**文档一**：简单、自洽、易上手，抓住了正确的角色轴，统一了命名——但只解决"怎么执行"没解决"怎么从案例产出信号"，抽取精度低，判定能力弱，变量耦合隐式，工程闭环缺失。

**文档二**：第一性原理更彻底（信号⟂采集器），抽取质量可控（封闭词表+后校验），判定表达力强且可控（5 类定型求值器），依赖显式可校验，工程闭环完整——但复杂度高，强约束带灵活性损失，"彻底移除 steps_json"有风险，抽取准确率仍是 LLM 上下限问题。

## Part 2：从第一性原理批判两方案各自的问题（质疑）

> 抛开两份文档的设计方向，从"把排障知识变成可机执行、可信任的诊断程序"这个本质问题出发审视。

### 2.1 文档一（基类设计）的问题

#### 问题 1：概念混淆——把"信号"和"采集器"焊死在类继承里

排障知识存在三个正交关注点：① 要查什么（诊断意图）② 怎么取数（采集手段）③ 取到后怎么判（评估逻辑）。文档一用 OOP 继承把三者压成一层：`FrontendSignal.execute()` 直接调 `qkv_exec`。

这违背了"策略与机制分离"原则。Kubernetes 把"期望状态"和"reconcile 逻辑"分开；OPA 把"策略"和"数据"分开；Ansible 把"task 描述"和"module 实现"分开。文档一相当于把策略写死在机制里。

#### 问题 2：最难的问题（抽取）被当成"LLM 调一下就行"

系统价值取决于"自然语言案例→结构化信号"的转换准确率。文档一用一个工厂方法 + 开放式 Prompt 处理，没有任何约束机制。业界 Instructor/Outlines/JSON Schema constrained decoding 的存在，正因为"让 LLM 自由输出 JSON 然后祈祷它对"是行不通的。

#### 问题 3：数据流没有类型契约，依赖关系隐式

BackendSignal 的 `target.scope = "${host}"` 没有任何机制保证 `host` 真的会被生产。相当于写程序用全局变量但不做类型检查。

#### 问题 4：判定能力只有关键字匹配

真实排障需要："CPU > 90%"、"服务状态 == running"、"告警是否存在"、"JSON 输出取路径值"。文档一的 `keywords + match_mode(any/all) + expected` 只能做最简形式。业界 Prometheus/Datadog/K8s probe 没有一家用"关键字列表"做唯一判定手段。

#### 问题 5：继承是错误的抽象工具

用 OOP 继承建模 frontend/backend 意味着信号类型是编译期固定的分类树。现代系统设计倾向组合优于继承——信号特征应是数据属性而非类型层级。

#### 问题 6：完全没有控制流建模

假设"先跑所有前端信号，再跑所有后端信号"的线性流程。真实排障有分支："如果告警类型是 A，检查 X；如果是 B，检查 Y"。

### 2.2 文档二（字段级抽取）的问题

#### 问题 1：重新发明轮子——5 类定型求值器 = 简化版 CEL

`keyword/state/threshold/json_path/exists` 本质是在重新实现一个受限表达式语言。业界已有 **CEL（Common Expression Language）**——Google 开源，K8s/Envoy 广泛使用，沙箱执行，非图灵完备，支持字符串/正则/列表/比较/逻辑组合。5 类求值器能表达的一切 CEL 都能表达，且更灵活、有标准库、LLM 训练数据中大量出现（生成质量更高）。JSON path 用 **JMESPath**（AWS CLI 标配）。

**本质问题**：自定义 DSL 的维护成本（文档、解析器、测试、LLM 适配、admin 培训）远高于使用标准方案。

#### 问题 2："字段级分别抽取"的语言学启发式是脆弱的

"把步骤切成祈使子句（→生产者）和陈述子句（→消费者）"是语言学规则，但自然语言排障文本不遵循：

> "检查 mysql-managed.log 中是否有 read-only 错误，如果有则说明磁盘故障"

一句话同时包含采集、判定、结论。强行切分丢失语义连贯性。抽取的难点不是"输出格式控制"（封闭词表能解决），而是"理解诊断推理逻辑"——文档二对后者没有本质改进。

#### 问题 3：过度工程化语法细节——占位符大写强制（ADR-2）

用一整个 ADR + 正则真相源 + 三处强制校验 + CI 钩子来保证 `{{VAR}}` 全大写，是在治理症状而非根因。真正的问题是"三套渲染引擎并存"——统一一个就够了。没有主流模板系统（Jinja/Helm/Mustache/envsubst）强制变量名大写。

#### 问题 4：封闭词表是中心化瓶颈

每新增一种诊断手段都要扩目录。业界 **MCP（Model Context Protocol）**模式——工具自描述，LLM 动态发现，而非硬编码进 Prompt。

#### 问题 5：ADR-1"彻底移除 steps_json"用"开发测试阶段"做挡箭牌

即便 dev/test，保留旧字段做 A/B 对照（旧抽取 vs 新抽取诊断准确率对比）是验证新方案有效性的最低成本手段。直接删等于自废验证能力。

#### 问题 6：仍然没有解决"证据聚合"和"控制流"

多了 `produces/requires` 和 `Matcher`，但仍在平铺信号列表层面思考。多信号判定结果如何聚合？整体置信度如何计算？诊断树如何遍历？都是空白。

## Part 3：修正前方案——诊断剧本 DAG（一个被推翻的提案）

> ⚠️ 本方案已被 Part 4 的认知对齐推翻，保留以记录完整思考过程。

### 3.1 核心主张

排障案例的本质是一段叙事："该去哪里取什么证据，取到后说明什么，基于结论再查什么"。这不是一堆孤立的"信号"，而是一个**有分支、有数据流、有结论的诊断过程**。因此知识的正确载体不是"信号列表"，而是**诊断剧本（Diagnostic Playbook）**——一个有向图，节点是诊断步骤，边是条件转移。

### 3.2 数据模型

```python
class DiagnosticPlaybook(BaseModel):
    id: str
    title: str
    category: str
    version: str
    trigger: Trigger
    context_schema: dict          # 诊断上下文的类型声明（JSON Schema）
    steps: list[PlaybookStep]     # DAG 节点（AcquireStep / DecideStep）
    conclusions: dict[str, Conclusion]
    confidence_threshold: float = 0.7

class AcquireStep(PlaybookStep):
    tool: str                     # 引用工具注册表中的工具名
    params: dict                  # 参数模板，含 {{VAR}} 占位符
    outputs: dict[str, str]       # 工具输出 -> 上下文变量的映射（JMESPath）
    condition: str | None         # CEL 表达式：何时执行此步

class DecideStep(PlaybookStep):
    condition: str                # CEL 表达式，求值于诊断上下文
    on_true: str                  # 下一步 id 或结论 key
    on_false: str
```

### 3.3 六个关键设计决策

1. **判定语言用 CEL，不造 DSL**——CEL 能表达文档二 5 类求值器的一切，还能组合，有标准库，LLM 生成准确率更高
2. **抽取是多阶段人机协作**——理解→草稿→静态验证→人工审核→试运行，五阶段
3. **工具注册表自描述，不硬编码进 Prompt**——MCP 模式，新增工具只需注册
4. **诊断上下文类型化，数据流可静态检查**——遍历 DAG 检查每个 `{{VAR}}` 引用是否有上游产出
5. **执行引擎是状态化 DAG 执行器**——支持条件分支、短路、跳过
6. **持久化为版本化剧本**——版本管理 + 状态机 + GIN 索引

### 3.4 方案对比总览（修正前）

| 维度 | 文档一 | 文档二 | 修正前方案 |
|---|---|---|---|
| 知识载体 | 信号列表 | 信号列表 | **诊断剧本 DAG** |
| 意图/采集/评估 | 三者焊死 | 意图⟂采集，评估焊在信号 | **三者完全解耦** |
| 判定语言 | 关键字匹配 | 5 类自定义 valuator | **CEL（标准）** |
| 控制流 | 无（线性） | 无（线性） | **DAG 条件分支** |
| 数据流契约 | 隐式 | 显式 produces/requires | **类型化上下文 + 静态检查** |
| 工具发现 | 硬编码 | 封闭词表 | **自描述注册表（MCP 模式）** |
| 抽取 | 一阶段 LLM | 一阶段 LLM + 受限词表 | **五阶段人机协作** |
| 证据聚合 | 无 | 无 | **结论带置信度** |
| 持久化 | 无 | signals_json | **版本化剧本** |

### 3.5 这个方案为什么被推翻

> 详见 Part 4。

修正前方案的根本错误：**它要把 KBD 转换成 YAML DAG，本质上是"把人读的文档翻译成机器读的程序"**。这违背了"我们在使用 agent，不是在写程序"的核心原则。

## Part 4：认知对齐与方向修正（关键转折点）

> 这一节记录了人类工程师对 AI 修正前方案的五个质疑，以及由此产生的方向性修正。这是整个讨论中最重要的转折。

### 4.1 工程师提出的关键认知

#### 认知 1：KBD 就是语义化的 Diagnostic Playbook

> "KBD 不就是语义化的 Diagnostic Playbook 么？我们之所以要抽'信号'就是为了让 LLM 好执行，LLM 最难的不是理解内容，而是准确执行。"

KBD 本身就是人写的诊断剧本（自然语言）。LLM 能读懂（理解不是难点），LLM 执行不准（获取信息才是难点）。因为获取信息依赖**隐藏经验**——哪个路径、哪个命令、哪个字段——这些不会写进 KBD 里。LLM 拿不到也无法准确获取信息。

**所以要做的是：把这部分隐藏经验工具化（放进工具里），然后告诉 LLM 怎么使用工具即可。** 而不是把整个 KBD 变成程序。

全把经验项整理出来告诉 LLM，LLM 容易有幻觉或看不到；把 KBD 全部转换成 Playbook 又不现实。

#### 认知 2：90% 的 KBD 没有分支，SOP 才是多叉树

> "90%以上的 KBD 是比较简单的，没有分支的情况；SOP 是同一类 KBD 按照信号的聚类，所有 SOP 是一个多叉树。"

因此，DAG 条件分支、置信度、版本化这些复杂能力，**应该是 SOP 考虑的事**，KBD 以简单、能用、易用为主。

#### 认知 3：先有 KBD，再能聚类成 SOP

> "我理解的诊断剧本 DAG，不是针对现已有 7000+ KBD，而是在我们抽取完 7000+ KBD 所有的信号后，按照 KBD 的故障场景进行分类，再在每个分类的 KBD 里面按照信号的概率优先级（数量大的优先级）再做聚类形成一棵多叉决策树。"

SOP 不是从零写的，是从 KBD 信号聚类来的。

#### 认知 4：完全解耦对 KBD 是否过度

> "意图/采集/评估如果三者完全解耦了，方不方便人来执行？有模板么？是枚举吗？LLM 好不好执行？本来做一个判断的，要多做两步准确性如何？"

KBD 信号应该是原子单元，不是拆成三步。

#### 认知 5：核心原则

> "就一个原则：人能参与且足够简单；LLM 能执行且足够准确。其实就是在尽可能少的调整 KBD 的同时保证 LLM 能准确执行完 KBD 中的所有步骤，我们是在使用 agent，不是在写程序。"

### 4.2 三个关键认知转折

| 转折 | 修正前的认知 | 修正后的认知 | 触发因素 |
|------|-------------|-------------|---------|
| 知识载体 | 应该把 KBD 转成诊断剧本 DAG | KBD 本身就是语义化的诊断剧本，只需抽信号 | "KBD 就是 Playbook" |
| 复杂度归属 | DAG/置信度/版本化应覆盖所有知识 | 复杂能力归 SOP，KBD 要简单 | "90% KBD 无分支；先有 KBD 才能聚 SOP" |
| 解耦粒度 | 意图/采集/评估应完全解耦 | KBD 信号是原子 bundle，不可拆 | "人能参与且足够简单；LLM 能执行且足够准确" |

### 4.3 修正前方案的错误本质

修正前方案犯了**"把知识工程当软件工程"**的错误：

| 维度 | 修正前方案（错误） | 修正后认知（正确） |
|---|---|---|
| KBD 角色 | 被转换成 YAML DAG 的源材料 | 人写给人的诊断剧本，保持原样 |
| 信号角色 | DAG 节点的一个属性 | 给 LLM 用的"信息获取工具包" |
| LLM 角色 | 执行预编译的 playbook | 读 KBD 原文 + 调信号工具 + 推理 |
| 目标 | 把知识变成程序 | 让 agent 能准确执行知识中的信息获取步骤 |

**核心原则**：Agent 在用 KBD 排障，不是在执行一个预编译的程序。LLM 读完 KBD 的自然语言步骤，遇到"需要获取信息"的步骤就调信号工具，拿到结果后继续推理。KBD 保持原样，只增量补充信号。

## Part 5：修正后方案——KBD 简单 + SOP 复杂分层（最终方案）

### 5.1 核心原则

> **人能参与且足够简单；LLM 能执行且足够准确。**
> 在尽可能少的调整 KBD 的同时保证 LLM 能准确执行完 KBD 中的所有步骤。
> 我们在使用 agent，不是在写程序。

### 5.2 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  KBD 层（案例）：简单、能用、易用                              │
│                                                             │
│  KBD 原文（自然语言，保持不变）                                │
│    + signals_json（扁平信号列表：producer + consumer）        │
│                                                             │
│  信号 = 原子单元（acquirer + acquirer_args + matcher）        │
│  判定器 = 5 类定型 matcher（keyword/state/threshold/          │
│           json_path/exists，现有架构已实现）                   │
│  控制流 = 无（线性，差分引擎贪心消除）                          │
│  变量流 = 变量池黑板（producer 写、consumer 读）              │
│  不需要：DAG 分支、CEL、置信度、版本化                         │
└─────────────────────────┬───────────────────────────────────┘
                          │ 信号聚类（按 category + 频率）
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  SOP 层（标准操作手册）：复杂能力放这里                        │
│                                                             │
│  tree_json（多叉决策树 DAG，从 KBD 信号聚类而来）              │
│                                                             │
│  控制流 = 多叉树分支（on_true/on_false）                      │
│  判定器 = CEL 条件表达式（复杂组合）                           │
│  变量流 = 类型化上下文 + 静态检查                              │
│  置信度 = 基于聚类频率                                        │
│  版本化 = 随 KBD 增长演进                                     │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 能力分层表

| 能力 | KBD（案例） | SOP（标准操作手册） |
|---|---|---|
| 本质 | 单个故障案例的诊断记录 | 同类故障案例的聚类决策树 |
| 结构 | **线性信号列表**（producer + consumer） | **多叉决策树 DAG** |
| 信号结构 | 扁平列表 | 决策树节点 |
| 判定器 | 5 类定型 matcher（现有，够用） | CEL 条件表达式（复杂组合） |
| 控制流 | 无（线性，差分引擎贪心消除） | 多叉树分支 |
| 变量流 | 变量池黑板（producer 写、consumer 读，现有） | 类型化上下文 + 静态检查 |
| 版本化 | 不需要（案例是事实记录） | 需要（聚类结果随 KBD 增长演进） |
| 置信度 | 不需要（单个案例无聚合意义） | 需要（基于聚类频率） |
| 人工参与 | 审核信号抽取结果 | 审核聚类决策树 |
| 生成方式 | LLM 从案例文本抽取 | 从同类 KBD 信号聚类 |
| 前置关系 | **先有 KBD**（必须有信号） | **后有 SOP**（从 KBD 聚类而来） |

### 5.4 KBD 层：保持现有架构，补全缺口

**现状已经基本对了**：`signals_json` 是扁平的 producer/consumer 列表，每条信号是 `acquirer + acquirer_args + matcher` 的原子单元。不需要 DAG、不需要 CEL、不需要三段解耦。

一条 KBD 信号就是**一个原子单元**：`用哪个工具取数 + 取什么参数 + 怎么判定`，三者在一条信号里捆在一起。理由：
1. **人审核时一眼看懂**：这条信号就是"用 qfk.log 在 mysql-managed.log 里搜 read-only，命中则确认"——一个完整语义
2. **LLM 执行时一步到位**：调一个工具，拿结果，判布尔，不需要拆成三步
3. **拆成三步反而降准确率**：本来一次工具调用就能完成的判定，拆成"声明意图→绑定采集器→写评估器"三步，每步都可能出错

#### 缺口 1：采集器目录覆盖不了真实案例（详见 Part 6 实证）

当前 8 类 QFK handler 全是 acli 命令，但真实 KBD 排障步骤大量使用主机级 shell 命令（`lsof`/`ps`/`df` 等）。需要新增 `host.shell` 采集器类型，把"怎么连主机、怎么执行、怎么解析"这些隐藏经验工具化。

#### 缺口 2：信号抽取的"判定依据"需更忠实于 KBD 原文

抽取 Prompt 应告诉 LLM：判定依据要提炼成可程序匹配的关键字，而非自然语言复述。

### 5.5 SOP 层：从 KBD 信号聚类形成决策树

```
7000+ KBD（每个都有 signals_json）
  │
  ├─ 按故障场景分类（category_id，已有）
  │     例：category 27123 = "虚拟机开机失败"
  │
  ├─ 同类 KBD 内按信号聚类
  │     例：10 个"VM 开机失败"KBD，8 个都有 qkv.task 查任务
  │         -> qkv.task 成为该类的高频信号（优先级高）
  │         -> 3 个有 host.shell 查进程占用 -> 中频
  │         -> 1 个有 qfk.storage 查存储 -> 低频
  │
  ├─ 按频率优先级排列，形成多叉决策树
  │     根节点：qkv.task 查任务（覆盖 80%）
  │       ├─ 任务报"镜像忙" -> host.shell 查进程占用（覆盖 30%）
  │       │    ├─ 确认第三方进程 -> 结论A
  │       │    └─ 未确认 -> qfk.storage 查存储（覆盖 10%）
  │       │         ├─ 存储异常 -> 结论B
  │       │         └─ 存储正常 -> 结论C
  │       └─ 任务报其他错误 -> 分支D...
  │
  └─ 输出：sop_document.tree_json（多叉决策树 DAG）
```

### 5.6 Agent 执行方式

```
用户工单："虚拟机开机失败，报镜像忙"
  │
  ├─ S0 意图路由 -> category 27123
  │
  ├─ S1 检索候选 KBD（signals_json 非空的已发布 KBD）
  │     -> 命中 KBD-27123、KBD-40652 等
  │
  ├─ S2 差分诊断（kbd_differential.py，已有逻辑）
  │     Phase A: 跑所有 producer 信号（qkv.task 查任务）
  │              -> 变量池: HOST=node-01, VM=7436939093432
  │     Phase B: 贪心消除，跑 consumer 信号
  │              -> host.shell: lsof | grep 7436939093432
  │              -> matcher: 输出含 .qcow2 且含 PID -> matched
  │              -> 剩余候选 KBD 缩减
  │
  ├─ S3 证据落库
  │
  └─ S4 根因确认 + 解决方案推荐
       -> KBD-27123 的 root_cause + solution（自然语言原文）
       -> Agent 向用户展示，用户确认
```

**关键**：Agent 在整个过程中**既读 KBD 原文（理解上下文和解决方案），又执行信号工具（准确获取信息）**。KBD 没有被转换成程序，信号只是让"获取信息"这一步变准确。

### 5.7 与修正前方案的差异

| 维度 | 修正前方案 | 修正后方案 |
|---|---|---|
| KBD 处理 | 转成 YAML DAG | 保持原文 + 扁平信号列表 |
| 信号结构 | DAG 节点属性 | 原子 bundle（acquirer+args+matcher） |
| 判定语言 | 全部用 CEL | KBD 用 5 类 matcher，SOP 用 CEL |
| 控制流 | KBD 就有 DAG | KBD 无分支，SOP 才有 DAG |
| 复杂度 | 高（所有 KBD 都要转 DAG） | KBD 低，SOP 高（但 SOP 是聚类的） |
| LLM 角色 | 执行预编译 playbook | 读 KBD + 调信号 + 推理 |
| 核心原则 | 知识工程（建模） | Agent 使用（工具化） |

## Part 6：真实案例 27123 落地验证（实证）

### 6.1 案例 27123 内容

**标题**：【HCI-VT】虚拟机开机失败，报错虚拟机镜像忙，正在进行其他操作

**排查步骤**（简化）：

```
Step 1: 在 HCI 控制台查看虚拟机任务详情，确认开机失败的报错信息
        -> 判断依据：任务详情显示"虚拟机镜像忙，正在执行其他操作"

Step 2: 登录发生故障的主机后台，检查虚拟机镜像文件是否被其他进程占用
        -> 命令：lsof | grep <vmid>
        -> 判断依据：输出中出现磁盘镜像文件 vm-disk-1.qcow2，被 PID 240132 占用

Step 3: 查询占用镜像文件的进程详情，确认是否为第三方程序
        -> 命令：ps auxf | grep 240132
        -> 判断依据：进程路径 /opt/ClwDRDBClient_2.0.230728/...，确认为第三方容灾程序

根因：虚拟机磁盘镜像被第三方容灾进程 ClwDRDBClient 占用
解决：kill -9 <PID>，重新开机
```

### 6.2 案例揭示的关键事实

#### 事实 1：隐藏经验不在 KBD 里，必须工具化

KBD 写的是"登录主机后台，检查镜像文件是否被其他进程占用"，但隐藏经验是：
- 怎么知道登录哪台主机？（需要从任务详情中提取 HOST）
- 用什么命令查？（`lsof | grep <vmid>`，KBD 里写了但 LLM 不一定知道怎么拼参数）
- VMID 从哪来？（从前端任务查询结果中提取）
- 输出怎么解析？（要找到 `.qcow2` 文件和 PID）

**这就是"把隐藏经验放进工具里"的最直接例证。**

#### 事实 2：现有采集器目录覆盖不了真实案例

Step 2/3 用的是 `lsof`、`ps auxf` 这类**主机级 shell 命令**，而当前 QFK 的 8 类 handler **全是 acli 命令**（`acli log/service/vm/network/storage/hardware/platform/system`）。这个案例的 Step 2/3 **根本无法用现有采集器目录中的任何一种来表达**。

这意味着对于 27123 这类案例，信号抽取要么抽不出来（acquirer 不在目录里被后校验丢弃），要么强行映射到不合适的类型。

#### 事实 3：90% KBD 确实没有分支

27123 的排查步骤是严格线性的：Step 1 → Step 2 → Step 3 → 根因。没有"如果是 A 则查 X，如果是 B 则查 Y"的分支。这印证了"90% KBD 没有分支"的判断——DAG 对 KBD 层是过度设计。

### 6.3 按修正后方案的信号抽取结果


**要点分析**：

2. **s2 的 `requires: ["HOST", "VM"]`** 显式声明依赖，s1 的 `produces` 提供这些变量——变量流契约闭环
3. **s2 的 matcher** 提炼自 KBD 判定依据"输出中出现 qcow2 文件并显示 PID"——从自然语言到关键字匹配
4. **s3 需要 PID**，但 s2 的 produces 里没有 PID——这说明 `host.shell` 采集器需要能从 `lsof` 输出中提取 PID 写入变量池。这是"隐藏经验"工具化的体现
5. **整个 KBD 原文保持不变**，只是多了这份 `signals_json`
6. **Agent 读 KBD 原文理解"为什么要查进程占用"，调 s2 信号准确执行"怎么查"**，拿到结果后自己推理"是不是第三方程序"

### 6.4 27123 聚类成 SOP 的示意

如果同 category 下有多个类似的"VM 开机失败"KBD，聚类后可能形成：

```

  │
  ├─ 根节点：qkv.task 查任务（覆盖 80% 的 KBD）
  │    ├─ 任务报"镜像忙" -> host.shell 查进程占用（覆盖 30%）
  │    │    ├─ 确认第三方进程 -> 结论：第三方程序占用镜像（置信度 0.9）
  │    │    └─ 未确认 -> qfk.storage 查存储（覆盖 10%）
  │    │         ├─ 存储异常 -> 结论：存储故障（置信度 0.8）
  │    │         └─ 存储正常 -> 结论：需人工介入（置信度 0.3）
  │    ├─ 任务报"超时" -> qfk.service 查服务（覆盖 20%）
  │    │    ├─ ...
  │    └─ 任务报其他 -> 分支...
```

**SOP 层才有**：DAG 分支、CEL 条件、置信度、版本化——这些复杂能力都在这里，KBD 层不需要。

## Part 7：决策记录与结论（沉淀）

### 7.1 最终决策

| 决策 | 结论 | 理由 |
|------|------|------|
| KBD 信号结构 | 扁平列表（producer + consumer），原子 bundle（acquirer+args+matcher） | 人能参与且足够简单；LLM 能执行且足够准确 |
| KBD 判定器 | 5 类定型 matcher（keyword/state/threshold/json_path/exists） | 现有架构已实现，够用，不引入 CEL |
| KBD 控制流 | 无（线性，差分引擎贪心消除） | 90% KBD 无分支 |
| KBD 原文 | 保持不变，只增量补充 signals_json | Agent 用 KBD，不是执行 KBD 程序 |
| SOP 结构 | 多叉决策树 DAG，从 KBD 信号聚类而来 | 先有 KBD 才能聚 SOP |
| SOP 复杂能力 | DAG 分支、CEL、置信度、版本化 | 复杂场景需要，但不该污染 KBD |
| 新增采集器 | `host.shell`（主机级命令执行） | 真实案例证明现有 8 类 acli handler 覆盖不了 |
| 信号抽取 | LLM + 封闭词表 + 后校验（文档二方案，保留） | 文档二的抽取方法是对的，只是判定器/控制流的归属层级需要修正 |

### 7.2 从两份文档中保留什么

| 来源 | 保留 | 原因 |
|------|------|------|
| 文档一 | KeySignal 基类 + FrontendSignal/BackendSignal 角色轴 | 角色轴正确，命名统一有价值 |
| 文档一 | 变量池生产者-消费者模式 | 变量流转机制正确 |
| 文档二 | 信号⟂采集器正交模型 | `acquirer`+`acquirer_args` 绑定方式正确 |
| 文档二 | 字段级分别抽取 + 封闭词表 + 后校验 | 抽取质量可控 |
| 文档二 | produces/requires 显式契约 | 变量流可静态校验 |
| 文档二 | 5 类定型 matcher | KBD 层够用，不需要 CEL |
| 文档二 | 工程闭环（signals_json 持久化、pipeline Stage 5、审核门、前端面板） | 端到端落地必要 |

### 7.3 从修正前方案中保留什么

| 来源 | 保留 | 去向 |
|------|------|------|
| CEL 标准表达式语言 | 保留 | **移到 SOP 层**——决策树节点的分支条件用 CEL，KBD 层用 5 类 matcher |
| 工具注册表自描述（MCP 模式） | 保留 | **KBD 和 SOP 共用**——新增采集器只需注册，不硬编码进 Prompt |
| 五阶段人机协作抽取 | 部分保留 | **简化后用于 KBD**——理解→草稿→验证→人工审核，试运行验证留到 SOP |

### 7.4 排除什么

| 排除项 | 理由 |
|--------|------|
| KBD 转 YAML DAG | KBD 本身就是语义化 Playbook，转程序是"把知识工程当软件工程" |
| KBD 层意图/采集/评估完全解耦 | 对 KBD 过度设计，拆三步降准确率 |
| KBD 层用 CEL | 5 类 matcher 够用，CEL 留给 SOP |
| KBD 层置信度/版本化 | 单个案例无聚合意义，案例是事实记录 |
| 占位符大写强制（ADR-2 的强制校验体系） | 过度工程化语法细节，统一渲染引擎即可 |
| 彻底移除 steps_json 无 A/B 对照 | 即便 dev 阶段也应有验证能力（但当前已移除，此为未来教训） |

### 7.5 落地顺序

1. **先 KBD**：补全 `host.shell` 等缺失采集器 → 优化抽取 Prompt → 人工审核 → 7000+ KBD 信号抽取
2. **后 SOP**：从已有信号的 KBD 按 category 聚类 → 形成决策树 → 人工审核 → SOP 决策树落库
3. **Agent 执行**：S2 差分诊断读 KBD + 执行信号 + 推理 → S4 根因确认 + 解决方案推荐

### 7.6 一句话总结

> **KBD 是人写给人的诊断剧本，信号是给 LLM 用的"信息获取工具包"。我们不改 KBD 原文，只把 LLM 执行不准的"隐藏经验获取"步骤工具化成信号。复杂能力（DAG 分支、置信度、版本化、CEL）全部留到 SOP 层——SOP 是从 KBD 信号聚类而来的决策树，不是人手写的程序。Agent 用 KBD 排障，不是执行 KBD 程序。**

## 附录 B：讨论中提出但未采纳的观点（供未来参考）

以下观点在讨论中被提出但最终未纳入修正后方案，记录以供未来决策参考：

### B.1 "占位符统一为大写并强制校验"（ADR-2）

**观点**：`{{VAR}}` 全大写 + 正则真相源 + 三处强制校验 + CI 钩子。

**未采纳理由**：过度工程化语法细节。真正的问题是"三套渲染引擎并存"，统一一个渲染引擎就够了。没有主流模板系统强制变量名大写。

**未来复活的条件**：如果实践中确实因大小写混淆导致频繁故障，可重新评估。

### B.2 "彻底移除 steps_json 无 A/B 对照"（对 ADR-1 的质疑）

**观点**：即便 dev/test，也应保留旧字段做新旧抽取准确率对比。

**现状**：`steps_json` 已被彻底移除（ADR-1 已落地）。此质疑仅作为未来教训记录——如果有类似的字段替换，应保留 A/B 对照能力。

### B.3 "意图/采集/评估完全解耦"

**观点**：三个关注点完全独立，信号只声明意图，采集器和评估器分别配置。

**未采纳理由**：对 KBD 层过度设计。KBD 信号是原子 bundle，拆三步降准确率。但这个思路对 SOP 层可能有价值——SOP 决策树节点的复杂组合逻辑可能需要更强的解耦。

### B.4 "五阶段人机协作抽取"

**观点**：理解→草稿→静态验证→人工审核→试运行，五阶段。

**部分采纳**：简化后用于 KBD（理解→草稿→验证→人工审核）。试运行验证留到 SOP 层。
