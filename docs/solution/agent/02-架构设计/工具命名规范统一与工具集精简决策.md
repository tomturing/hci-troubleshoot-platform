# 工具命名规范统一与工具集精简决策

> 本文归档"工具管理页面工具命名不一致"问题的第一性原理分析、业界最佳实践与范式对比，以及最终决策。
> 权威现行全量文档：[agent工具设计.md](./agent工具设计.md)、[数据库设计.md](../../数据库设计.md)。

## 背景与需求

工具管理页面（`tool_definition` 表）当前存在两种并存的命名风格，混在同一张表里：

| 风格 | 样例 | 归属 category | 语义模型 |
|------|------|--------------|---------|
| 下划线 `snake_case`（`{后端}_{动作}`） | `acli_exec`、`bash_exec`、`get_active_alerts`、`sop_advance` | acli / scp / sop | 一个名字 = 一个具体动作 |
| 点号（`{域}.{对象}`） | `qfk.hardware`、`qfk.log`、`qkv.alert` | qfk / qkv | 一个名字 = 一个命名空间下的子域 |

`tool_definition.tool_name` 列注释明确约定命名规则为 `{执行后端}_{动作}`，说明下划线是原始设计约定，点号是后来 QKV/QFK 关键信号体系引入时"另起炉灶"的产物。

**根因（为什么会出现不一致）：**

1. **历史分层**：`acli_exec` 系为第一批工具，遵循老约定 `{后端}_{动作}`。
2. **心智模型不同**：QKV/QFK 是后引入的"关键信号"体系，设计者按"命名空间/领域"建模，用点号表达 `qfk`（域）→ `.hardware`（子域）的层级归属。
3. **缺少护栏（convention drift）**：`tool_name` 仅有 `UNIQUE` 约束，**无正则/字符集校验、无 lint、无强制规范**，系统对两种风格一视同仁（都直接作为 LLM function-calling 的 `name` 透传），两种风格得以长期共存而不报错。

一句话根因：**命名规范未被"代码化/约束化"，导致约定随人随时间漂移。**

## 方案（WHAT）

采用三项动作统一命名并精简工具集。

### 决策一：定规范并代码化（治本，防止再漂移）

统一命名规范为 `snake_case`，正则：

```
^[a-z][a-z0-9_]{0,63}$
```

- 首字符必须为小写字母；仅允许小写字母、数字、下划线；长度 1–64。
- **禁止点号 `.`**、大写字母、连字符及其他字符。

代码化落点：

1. **后端契约校验**：在 `backend/conversation-service/app/routes/tool_definition.py` 的 `validate_tool_payload()` 中新增 `tool_name` 正则校验，不合规返回结构化错误码（如 `TOOL_NAME_INVALID_FORMAT`），在创建/更新/发布校验链路生效。
2. **数据库约束**：在 `tool_definition` 表新增 `CHECK` 约束（如 `chk_tool_definition_tool_name_format`），从存储层兜底。
3. **前端表单校验**：在 `frontend/admin/src/views/ToolManageView.vue` 的 `tool_name` 输入项新增同一正则的即时校验，保存前阻断非法命名。

### 决策二：迁移点号工具（11 个：QKV 3 + QFK 8）

将所有点号命名重命名为下划线（前缀即领域，语义无损）：

| 旧名 | 新名 | category |
|------|------|----------|
| `qkv.alert` | `qkv_alert` | qkv |
| `qkv.task` | `qkv_task` | qkv |
| `qkv.dialog` | `qkv_dialog` | qkv |
| `qfk.log` | `qfk_log` | qfk |
| `qfk.service` | `qfk_service` | qfk |
| `qfk.system` | `qfk_system` | qfk |
| `qfk.vm` | `qfk_vm` | qfk |
| `qfk.network` | `qfk_network` | qfk |
| `qfk.storage` | `qfk_storage` | qfk |
| `qfk.hardware` | `qfk_hardware` | qfk |
| `qfk.platform` | `qfk_platform` | qfk |

迁移需同步处理以下连带引用（rename 的影响面）：

- `database/seeds/03_qkv_qfk_tools.sql` 的 `tool_name` 与文件头注释。
- `tool_result` 表历史审计数据中的 `tool_name`（数据迁移/映射）。
- `dynamic_resource` 已发布 revision 的 `resource_name`（GitOps 快照）。
- SOP / KBD / Skill 中 `dependencies: [{resource_type:"tool", resource_name:"qfk.hardware"}]` 之类的引用。
- 建议加一层旧点号名 → 新下划线名的别名/兼容映射灰度过渡，确认线上无残留引用后再删除别名。

### 决策三：精简工具集（删除 6 个不常用工具）

从种子文件与数据库中删除以下 6 个工具（均位于 `database/seeds/01_tool_definitions.sql`）：

| 工具名 | 说明 |
|--------|------|
| `acli_plugin_asys` | acli 诊断插件，低频 |
| `acli_plugin_netdoctor` | acli 网络诊断插件，低频 |
| `acli_plugin_vm_start` | acli VM 启动插件，低频 |
| `acli_plugin_vm_suspend` | acli VM 挂起插件，低频 |
| `get_cluster_detail` | 集群详情查询，低频 |
| `get_vm_list` | 虚拟机列表查询，低频 |

删除方式：从 `01_tool_definitions.sql` 移除对应 `INSERT`，并在数据库中删除记录（配套迁移脚本 `DELETE FROM tool_definition WHERE tool_name IN (...)`）。删除前确认无 SOP/KBD 依赖引用这 6 个工具。

## 决策依据（WHY）

### 第一性原理：tool_name 首先是 LLM function name

`tool_name` 在系统中同时承担 4 个角色：LLM function-calling 的 `name` 字段、运行时路由 key（`TOOL_REGISTRY[tool_name]`）、数据库唯一标识 + 审计外键（`tool_result.tool_name`）、GitOps 资源名（`dynamic_resource.resource_name`）。其中**最强硬约束来自第一个角色**。

主流 LLM 对 function `name` 的字符集约束为：

```
^[a-zA-Z0-9_-]{1,64}$   （OpenAI 官方；Anthropic、Gemini 字符集基本一致，均不含点号）
```

因此：

- `acli_exec` ✅ 合法。
- `qfk.hardware` ❌ **点号不符合官方 function name 规范**。当前"能跑"依赖网关/模型的宽松处理，一旦更换模型或开启严格校验随时可能被拒——这是兼容性地雷，而不仅是风格不一致。

**结论的决定性一票**：既然 tool_name 首要身份是喂给 LLM 的 function name，就必须首先满足其字符集约束；点号违反了这条最底层约束，故点号方案在此语境下是"错误"，而非"风格差异"。

### 业界最佳实践与范式对比

**点号 `.` 的正统用法**是"结构化标识符 + 独立解析器"场景：Java 包名 `com.company.module`、Prometheus/OTel 指标 `node.cpu.usage`、gRPC `package.Service/Method`、MCP 中 `server` 与 `tool` 是**两个独立字段**而非拼成 `server.tool`。共同点是层级会被解析器拆开处理。而 LLM function name 是**扁平字符串**，模型不会解析 `qfk.hardware` 的层级，点号在此不带来任何结构收益，反而破坏字符集约束。

**`snake_case` 是 tool/function 命名的事实标准**：OpenAI 官方示例（`get_current_weather`、`get_stock_price`）、Anthropic tool use 示例（`get_weather`）、LangChain / LlamaIndex 等 agent 框架默认全部 `snake_case`。原因：LLM 训练语料中函数名以 `snake_case`（Python 生态）为主，模型对 `snake_case` 的"可调用函数"联想最强，**能实际提升工具选择准确率**。

**如何表达领域/层级而不用点号**：用下划线拍平（`qfk_hardware`、`qkv_alert`），前缀即领域，语义无损、合法、与老工具统一，LLM 仍能从前缀感知归属。

### 方案对比

| 维度 | 点号 `qfk.hardware` | 下划线 `qfk_hardware`（采用） |
|------|--------------------|------------------------------|
| LLM function name 合规 | ❌ 不符合官方正则 | ✅ 完全合规 |
| 工具选择准确率 | 偏低（非主流语料风格） | 更高（与训练语料一致） |
| 一致性/可维护性 | 双风格并存，认知负担高 | 单一风格，可校验、可 lint |
| 是否符合既有 SSOT | ❌ 违反列注释约定 | ✅ 回归自身 `{后端}_{动作}` 约定 |

**最终结论：`snake_case` 下划线为唯一标准，点号淘汰，并通过正则 + DB CHECK + 前端校验将规范固化下来，从机制上防止再次漂移。**

### 为什么同时精简工具集

工具全部作为 function-calling 注入 LLM，工具越多则 prompt token 越多、工具选择干扰越大。删除 6 个低频工具可降低上下文噪声、提升工具选择准确率，并与本次命名治理一并收敛工具目录，减少后续维护面。
