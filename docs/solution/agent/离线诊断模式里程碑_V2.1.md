## 一、术语表

| 术语 | 解释 |
|---|---|
| KBD | Knowledge Base Document（知识库文档），结构化知识案例，包含现象、信号、根因和方案 |
| `signals_json` | KBD 中的诊断信号，描述证据查询和 matcher 规则，不再直接作为任意 Shell 命令来源 |
| Collection Profile | Collection Profile（采集画像），定义 Mandatory（必收）、Recommended（建议）、Conditional（条件）和 Deep-dive（深度补采） |
| Collection Plan | Collection Plan（采集计划），结合工单上下文、场景、对象和版本生成的一次具体计划 |
| Collector Registry | Collector Registry（采集器注册表），保存经共享采集编译器产生并经审批的采集定义、参数、风险、输出契约和不可变修订；不单独解释 KBD 采集语义 |
| Shared Acquisition Compiler | Shared Acquisition Compiler（共享采集编译器），将 KBD 采集意图、Tool Registry（工具注册表）契约和 QFK Handler（处理器）能力统一编译为 Execution Contract Revision（执行契约修订） |
| Collector Artifact | Collector Artifact（采集器制品），根据 Collection Plan 生成并签名的客户侧采集器 |
| DiagnosticEvidenceBundle | Diagnostic Evidence Bundle（诊断证据包），客户侧采集器生成的标准文件包；避免与现有 Prompt `EvidenceBundle` 重名 |
| Evidence Assessment | Evidence Assessment（证据评估），对证据包安全性、完整性、时间覆盖、对象覆盖和可诊断范围进行评估 |
| `terminal_bridge` | terminal bridge（在线终端桥接通道），在线模式通过 SSH 实时执行命令 |
| Offline Evidence Provider | Offline Evidence Provider（离线证据查询器），P0 支持日志、JSON、命令输出、基础指标和证据状态 |
| Shared Source | Shared Source（共享代码源），生产运行时唯一允许使用的根目录 `backend/shared` 实现 |
| AcquisitionProvider | AcquisitionProvider（采集提供者接口），屏蔽在线实时执行和离线证据查询的数据通道差异 |
| Shared CDD Runner | Shared CDD Runner（共享差分诊断运行器），统一在线/离线的取值、匹配、变量依赖、候选归约和结论门禁 |
| Execution Contract Revision | Execution Contract Revision（执行契约修订），共享采集编译器输出的不可变执行语义快照 |
| Signal Evaluation | Signal Evaluation（信号评估），对外支持 MATCHED（匹配）、NOT_MATCHED（未匹配）和 UNKNOWN（未知） |
| Conclusion Policy | Conclusion Policy（结论策略），将 CDD 内部结果映射为分级报告 |
| Diagnosis Level | Diagnosis Level（诊断等级）：Confirmed（已确认）、Probable（高概率）、Suspected（疑似）、Insufficient（证据不足）、Conflicted（证据冲突） |
| Supplement Plan | Supplement Plan（补充采集计划），首次证据不足时生成的一次增量计划 |
| Diagnosis Session | Diagnosis Session（诊断会话），关联工单、采集、证据、诊断、补采、审核和报告 |
| Diagnosis Run | Diagnosis Run（诊断运行），针对当前证据集合执行的一次分析；补采后生成新 Run |
| Golden Evidence Set | Golden Evidence Set（黄金证据集），已确认根因并由专家标注的历史证据包集合，用于回放和验收 |
| Diagnosis Service | Diagnosis Service（诊断服务），负责领域控制面、权限、审核和审计 |
| Diagnosis Worker | Diagnosis Worker（诊断工作进程），负责隔离解密、扫描、解压、标准化和分析任务 |
| EvidenceItem | Evidence Item（不可变证据项），只追加保存证据来源、时间、摘要和对象引用 |
| Run Manifest | Run Manifest（运行清单），记录一次诊断依赖的所有资源版本和内容哈希 |
| Runbook | Runbook（处置手册），供工程师执行和验证的标准步骤 |
| Legal Hold | Legal Hold（法务保全），阻止合规数据被生命周期或删除请求清理 |

## 二、总体目标与阶段划分

| 阶段 | 定位 | 核心成功标准 |
|---|---|---|
| P0 | 精简 HCI V1，受控客户试点 | 2 个 HCI 场景；安全采集；UNKNOWN（未知）；证据完整性；分级报告；工程师审核 |
| P1 | HCI 规模化增强 | 备份/迁移、自动补采、多节点、时间线、类型化证据、跨分类检索和更多场景 |
| P2 | VDI V1 | Windows 和 VDI 登录、认证、资源获取场景，客户自助 |
| P3 | 性能与体验诊断 | 故障黑匣子、卡慢掉线、抓包、外设和低风险自动处置 |

P0 正式验收场景：

1. 虚拟机启动失败；
2. 磁盘、RAID（磁盘阵列）和明确硬件告警。

## 四、P0 总体周期和组织方式

### 4.1 计划周期

若从零建设，精简 P0 计划周期为 **8～12 周**；当前编码已具备主要技术链路，剩余重点是
生产环境接入、黄金案例、容量安全验证和客户试点，不再按新增功能数量计算完成度。

前提：后端、Agent、前端、安全/平台和诊断知识团队并行投入，并且企业身份、对象存储和
密钥管理平台已有可接入能力。若三项均需本项目从零建设，周期按 **12～16 周**规划。

客户试点、安全整改和运行验证必须保留独立窗口；不得用已经实现的 P1 兼容代码替代
两个首发场景的真实效果验收。

关键路径依赖：Golden Evidence Set（黄金证据集，G-01）、存量 KBD `sub_command` 安全审计（B-02）、身份与租户方案（A-01）和威胁模型（A-02）必须在 Week 0 前置启动。任何一项未冻结，不进入外部客户试点。

### 4.2 内部迭代

| 内部迭代 | 周期 | 目标 |
|---|---:|---|
| P0.0 | 第 0～2 周 | 架构与威胁模型、身份权限、领域契约、Bundle Schema、Golden Evidence Set |
| P0.1 | 第 2～7 周 | 安全采集、Collection Plan、签名采集器、对象存储和上传安全链路 |
| P0.2 | 第 5～10 周 | Evidence Assessment、离线证据适配、结论策略、分级报告和审核 |
| P0.3 | 第 8～10 周 | 精简前端、黄金案例回放、安全和性能验证 |
| P0.4 | 第 10～12 周 | 内部灰度、客户试点、恢复演练、整改和发布评审 |

三个迭代有重叠并行，不是严格串行。

## 五、P0 工作流与任务拆解

## 5.1 工作流 A：领域模型与 API

当前编码进度：

- B-01、B-03～B-09 已具备主要控制面和制品链路：Profile（采集画像）与 Collector
  （采集器）由已发布 KBD 动态同步产生，不再以历史“4 个 Profile、15 个 Collector”作为
  当前基线或验收目标；双签名、吊销、标准 Manifest（清单）、AES-256-GCM
  Envelope Encryption（信封加密）和 Signal Mapping（信号映射）已具备；
- HCI API Collector（HCI 接口采集器）只允许固定相对 `GET`，凭据由执行时
  `HCI_API_TOKEN`（HCI 接口短期令牌）注入且不进入产物；Manual Attachment
  Guide（人工附件采集指引）生成指定附件路径；
- 多密钥 KMS 托管属于生产平台适配，未配置时正式生成/解密默认拒绝；
- B-02 是存量内容安全审计，不是剩余编码项，仍作为发布门禁。

> 当前实施状态：E-01～E-07 已完成兼容实现，但精简 P0 通过
> `DIAGNOSIS_ENABLE_AUTOMATIC_SUPPLEMENT=false` 关闭客户自动补采；证据不足时进入工程师审核队列。
> 完整 P1 验收并显式开启后才允许一次自动补采，补采后仍不足则转专家或远程兜底，不允许循环补采。

| 编号 | 任务 | 主要内容 | 预估 |
|---|---|---|---:|

自动灰度、自动回滚或质量运营已经完成。

KBD 发布只校验结构化信号；Collector、Mapping（映射）和 Profile 的完整性及安全性在
Offline Resource Sync（离线资源同步）候选发布门禁中校验。Execution Contract Revision、
完整快照和共享确定性契约属于 P0 诊断正确性底座；自动灰度、跨版本批量回放和质量指标触发的
自动回滚继续留在 P1。

### P1 退出标准

- HCI 正式场景覆盖不少于 8 个；
- 稳定期无远程解决率 ≥60%；
- 平均补采轮次 ≤1；
- UNKNOWN 高频原因可量化并持续下降；
- 规则变更具备自动回归门禁。
- KBD 增删改能够输出受影响采集资源，证据要求变化不会静默混用新规则和旧制品；
- 历史 Diagnosis Run（诊断运行）可以按完整 KBD 修订版本集合和内容哈希复现；
- Collector 与 Profile 可在空业务数据环境由已发布 KBD 首次全量同步建立，不依赖种子；
- 同步候选发布、驳回、失败和最近批次回滚均可按批次、操作者、理由、资源差异、KBD 来源
  修订、Watermark（同步游标）和 `trace_id`（链路追踪标识）完整追溯；
- Collector 安全问题可以按修订版本阻断新生成并撤销尚未过期的受影响制品。

## 十三、主要风险与阶段门禁

| 风险 | 阶段门禁 |
|---|---|
| Collection Profile 覆盖不足 | 每场景专家评审 + 黄金案例回放 |
| 存量命令不安全 | 全量审计并映射 Registry 后才可进入采集器（P0.2 前完成） |
| 黄金案例收集进度 | Week 0 前置启动，按场景专家标注已确认案例；收集不达标则顺延回放验证窗口，不压缩案例质量 |
| UNKNOWN 过高 | 上线前统计原因，Mandatory 完整率 ≥90% |
| KBD 候选被误当根因 | 分级报告 + 工程师审核强制门禁 |
| 大包耗尽服务资源 | 异步 Worker + 任务配额 + 压力测试 |
| 客户数据泄露 | 脱敏、加密、租户隔离、限期留存和删除审计 |
| 证据不足 | 明确列出缺失项并转工程师人工补充，不输出确定性根因 |
| 试点无远程率不达标 | 不扩大客户范围，先优化 Profile 和规则 |
| 正式身份或对象级授权未就绪 | 不进入外部客户试点，不使用 `client_id` 或占位 Token 替代 |
| 诊断文件入口污染 KBD 服务 | P0 独立 Diagnosis Service/Worker，网关只承载控制面 |
| Bundle 与现有 Prompt EvidenceBundle 重名 | 文件模型统一使用 DiagnosticEvidenceBundle |
| 结论等级与现有 CDD 语义漂移 | 使用版本化 Conclusion Policy，并纳入在线/离线回放 |
| Compose 与生产镜像加载不同 Shared Source | 删除服务内副本，真实构建生产镜像并执行导入、OpenAPI 和健康检查 |
| 同一 QFK 在线/离线编译为不同采集行为 | 统一 Shared Acquisition Compiler，冻结并校验 Execution Contract Revision 和语义指纹 |
| 历史计划或 Run 回读实时 KBD | 运行时只读完整不可变快照；变更后旧计划结果不变，新计划提示修订变化 |
| 工具名/分类/命令粗匹配串错证据 | 固化 KBD Revision + Signal ID 到 Collector/Plan/Evidence/Evaluation 的精确引用链 |

## 十四、最终里程碑定义

P0 完成不以“离线文件能被 Agent 搜索”为标准，而以以下闭环为标准：

> 受控试点客户能够创建 HCI 诊断会话，下载并运行安全签名采集器，上传标准证据包；
> 平台基于冻结快照，由在线/离线共用的采集编译器、Provider 契约和 CDD Runner 完成
> 安全检查、证据完整性判断和诊断，通过 UNKNOWN（未知）避免错误排除，生成分级
> Draft（草稿）报告；证据不足时明确缺失项并转工程师；工程师审核后发布客户报告；
> 全过程可按 KBD Signal 精确追溯和复现，并达到两个首发场景的上线门槛。
