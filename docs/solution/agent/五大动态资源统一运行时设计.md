# 五大动态资源统一运行时设计

## 一、目标

平台需要支持五类动态资源：

- KBD：历史案例和知识条目
- SOP：排障流程和决策树
- Tool：外部动作能力和执行契约
- Skill：过程性知识包和领域解析能力
- Prompt：Agent 系统提示词和编排模板

这五类资源不能各自实现一套加载、发布、缓存、审计和热更新机制。它们应该共享一个“动态资源运行时”公共模块，由统一机制保证可运行、可插拔、热生效、可审计、可回滚。

## 二、第一性原理

动态资源的生命周期不是“保存一行数据库记录”，而是：

```
编辑草稿
  -> 校验引用和契约
  -> 发布新版本
  -> Agent 按策略热加载
  -> 执行或注入
  -> 记录使用版本和结果
  -> 可回滚到旧版本
```

因此，五类资源都需要同一组基础能力：

| 能力 | 说明 |
|---|---|
| 资源标识 | `resource_type + name + version + revision` 全局唯一 |
| 状态机 | draft / published / archived / disabled |
| 契约校验 | schema、占位符、依赖引用、输出结构、权限边界 |
| 依赖图 | 资源引用资源，例如 SOP 变量引用 Skill、Skill 引用 Tool |
| 热加载 | 修改发布后 Agent 不重启也能感知 |
| 缓存失效 | TTL、revision 比对、主动刷新事件 |
| 执行接口 | 不同资源有不同 runner，但共享 loader/audit/cache |
| 审计 | 每次使用记录资源版本、输入摘要、输出摘要、trace_id |
| 回滚 | 激活旧版本，而不是脚本反向修改数据 |

## 三、统一资源模型

建议新增公共模块 `backend/shared/dynamic_resource/`，承载跨服务通用能力。

### 3.1 逻辑表结构

可以先在现有表上兼容实现，长期收敛为统一元数据模型：

```sql
dynamic_resource_revision (
  id bigint primary key,
  resource_type varchar(32) not null,
  resource_name varchar(128) not null,
  version varchar(64) not null,
  revision bigint not null,
  status varchar(16) not null,
  content_json jsonb not null,
  contract_json jsonb not null,
  dependency_json jsonb not null default '[]',
  checksum varchar(128) not null,
  trace_id varchar(64),
  created_at timestamptz not null,
  published_at timestamptz,
  unique(resource_type, resource_name, revision)
);

dynamic_resource_active (
  resource_type varchar(32) not null,
  resource_name varchar(128) not null,
  active_revision bigint not null,
  updated_at timestamptz not null,
  primary key(resource_type, resource_name)
);

dynamic_resource_usage_audit (
  id bigint primary key,
  resource_type varchar(32) not null,
  resource_name varchar(128) not null,
  revision bigint not null,
  consumer varchar(128) not null,
  conversation_id uuid,
  case_id varchar(64),
  trace_id varchar(64),
  exec_id varchar(64),
  input_hash varchar(128),
  output_hash varchar(128),
  status varchar(32) not null,
  error text,
  created_at timestamptz not null
);
```

短期不必立刻迁移现有表，但所有现有表必须补齐等价字段或由适配器映射：

| 资源 | 当前表 | 统一映射 |
|---|---|---|
| KBD | `kbd_entry` | `resource_type=kbd`，name=`id/support_id` |
| SOP | `sop_document` | `resource_type=sop`，name=`id/category_id` |
| Tool | `tool_definition` | `resource_type=tool`，name=`tool_name` |
| Skill | `skill_definition` | `resource_type=skill`，name=`skill_name` |
| Prompt | `system_prompt` | `resource_type=prompt`，name=`name` |

### 3.2 公共接口

```python
class DynamicResourceLoader:
    async def get_active(resource_type: str, name: str) -> ResourceSnapshot: ...
    async def list_active(resource_type: str, filters: dict | None = None) -> list[ResourceSnapshot]: ...
    async def validate(snapshot: ResourceSnapshot) -> ValidationResult: ...
    async def resolve_dependencies(snapshot: ResourceSnapshot) -> list[ResourceSnapshot]: ...
    async def audit_usage(snapshot: ResourceSnapshot, usage: UsageRecord) -> None: ...

class DynamicResourceCache:
    async def get_or_load(key: ResourceKey, loader: Callable) -> ResourceSnapshot: ...
    async def invalidate(resource_type: str, name: str | None = None) -> None: ...
```

公共模块只管加载、校验、缓存、依赖和审计，不直接理解 KBD/SOP/Tool/Skill/Prompt 的业务语义。

## 四、五类资源目标运行时

### 4.1 KBD

当前状态：

- KBD 已通过 `kbd_entry` 管理、发布和检索。
- 消费侧主要是检索/匹配，不是可执行资源。
- 命中统计已有，但使用的资源版本和输入证据审计不足。

缺口：

- KBD 作为资源缺少统一 revision 和 usage audit。
- KBD 与 SOP/Skill/Tool 的依赖关系没有显式表达。
- KBD 匹配结果进入 S4 后，缺少可追溯版本快照。

目标：

- KBD 发布生成不可变 revision。
- Agent 引用 KBD 时记录 `kbd_id + revision + score + query_hash`。
- KBD 内容可作为 Skill/Prompt 的引用资料，但必须通过依赖图声明。

### 4.2 SOP

当前状态：

- SOP 有 `sop_document`、`tree_json`、`variable_schema`。
- SOP Markdown 更新与 `variable_schema` 合并存在旧值保护副作用。
- SOP 变量来源支持固定 strategy，但 provider 模型不完整。

缺口：

- `variable_schema` 没有完整依赖图、输出绑定、工具参数模板、派生变量。
- SOP 发布时没有强校验引用的 tool/skill/prompt 是否存在且启用。
- SOP 运行审计没有记录所用 SOP revision。

目标：

- SOP 发布时生成不可变 `tree_json + variable_schema` revision。
- 变量声明支持：
  - `env`
  - `tool`
  - `skill`
  - `derived`
  - `user_input`
  - `user_confirm`
- 变量 provider 统一走 `VariableProvider` 插件协议。
- SOP 执行实例记录 `sop_revision`，避免执行中 SOP 被编辑后语义漂移。

### 4.3 Tool

当前状态：

- `tool_definition` 表是 LLM 可见工具元数据 SSOT。
- PR1 已引入 `ToolRegistryManager`，ReAct/Composite 执行前通过短 TTL 从 DB 刷新工具定义。
- PR1 已删除 `BridgeRelayExecutor` 对 `get_failed_tasks` 的命令拼接特判，改为统一消费 `usage_template`。
- PR1 已让 `bash_exec` 容器边界从 `tool_definition.parameters_schema.properties.container.enum` 进入 ReactEngine、语义校验和 BridgeRelayExecutor，管理端不再写死具体容器集合。
- PR1 已让幻觉检测基于当前工具 registry 快照，不再使用内置默认工具清单。
- 执行层仍有部分通用路由分支和本地安全规则。

缺口：

- 工具管理页修改后已可通过 TTL 热生效，但缺少主动发布事件和 revision 比对。
- `usage_template` 已覆盖前置查询工具和插件命令模板，但还没有统一描述所有执行边界、输出契约和环境维度。
- 风险规则、独立容器 catalog、语义校验 catalog 未统一数据化。
- HTTP/SCP 类工具缺少通用执行后端。

目标：

- `ToolRunner` 按 `execution_backend` 选择执行器：
  - `bridge_command`
  - `http_request`
  - `sop_local`
  - `internal_api`
- 工具定义发布后通过 revision 热加载。
- 执行器不按具体工具名写业务分支；具体命令、HTTP path、参数模板都来自资源定义。
- 风险规则独立为动态资源，执行时按当前 revision 加载。

### 4.4 Skill

当前状态：

- `skill_definition` 表和管理页面已经存在。
- PR1 已新增 `DynamicSkillRunner`，SOP 变量池的 `skill_call` 会按次读取 active `skill_definition` 并调用 LLM 生成结构化 JSON。
- PR1 已移除 Python 内置 `disk_vendor_lifetime` 厂商规则；Python `_SKILL_REGISTRY` 只保留迁移期通用注册表能力。
- PR1 已支持 `output_path`、`depends_on` 和动态 Skill 结果绑定。

缺口：

- Skill 已能运行，但尚未纳入统一 resource revision/cache/audit。
- `allowed_tools` 尚未接入真实工具调用授权。
- Skill 保存/发布时缺少统一依赖校验、输出契约校验和循环依赖检测。

目标：

- 建立 `SkillRunner`：
  - 加载 active skill revision
  - 注入 `instructions_md`
  - 注入允许的 tools
  - 注入输入上下文
  - 调用 LLM 或规则解释器
  - 返回结构化 JSON
- SOP 变量可声明：
  ```json
  {
    "acquisition_strategy": "skill_call",
    "acquisition_tool": "hci-alert-parsing",
    "output_path": "node_ip"
  }
  ```
- `skill_definition` 保存/发布时校验 `allowed_tools` 存在。
- Python 内置 skill 只能作为迁移期兼容 provider，不能作为新增业务能力入口。

### 4.5 Prompt

当前状态：

- Prompt 内容已在 `system_prompt` 表。
- `StrictPromptLoader` 每次按名称加载并校验占位符。
- 但 prompt name、阶段编排和 expected placeholders 写在 Agent 代码中。

缺口：

- Prompt 内容热生效，但 Prompt 编排不热生效。
- 无统一 prompt slot，例如 `sop_react_new` 当前绑定具体 `s1_sop_react_new_v1`。
- Prompt 使用审计需统一到动态资源 usage audit。

目标：

- 建立 `prompt_slot`：
  - `slot_name`
  - `active_prompt_name`
  - `expected_placeholders`
  - `consumer`
- Agent 代码读取 slot，不写死具体 prompt name。
- Prompt 发布时校验占位符、依赖资源和最大长度。
- 每次构建 system prompt 记录所有 prompt revision。

## 五、统一热生效机制

推荐采用“revision 比对 + 短 TTL + 主动刷新”的组合：

| 机制 | 作用 |
|---|---|
| revision | 每次发布生成递增版本，运行时可比对是否过期 |
| TTL cache | 避免每次 token 流都打 DB，默认 30-60 秒 |
| admin publish event | 管理页面发布后写 Redis pub/sub 或版本表 |
| fail-loud | 加载失败不静默回退到旧硬编码 |
| execution snapshot | 长执行过程固定资源 revision，避免中途漂移 |

## 六、统一校验机制

资源发布前必须执行公共校验：

| 校验 | 说明 |
|---|---|
| schema 校验 | JSON Schema、Markdown frontmatter、Prompt placeholders |
| 引用校验 | tool/skill/prompt/kbd/sop 引用必须存在且启用 |
| 权限校验 | Skill allowed_tools、Tool risk、SOP 变量来源 |
| 输出契约 | Skill/Tool output_path 必须可解析或声明为可选 |
| 循环依赖 | SOP 变量 depends_on、资源 dependency graph 不允许循环 |
| 可观测性 | resource revision、trace_id、exec_id 字段可落审计 |

## 七、实施拆分

### PR-1：内置/硬编码治理

- 已完成硬编码审计和治理边界。
- 已删除 Python 内置业务 Skill 规则，`skill_call` 接入 `skill_definition` 动态运行器。
- 已收敛 `env_injection` 为确定性字段直取，复杂告警/任务解析交给动态 Skill/Tool。
- 已为工具 registry 增加短 TTL 热刷新，删除 `get_failed_tasks` 工具名命令特判。
- 已将 `bash_exec` 容器集合改为从工具定义 JSON Schema 读取。
- 已删除幻觉检测的内置默认工具清单，改为消费当前工具 registry 快照。
- 已支持 SOP 变量 `depends_on`、`output_path`、`fallback_strategy` 的解析、合并和运行时拦截。

### PR-2：统一动态资源运行时

- 新增 `dynamic_resource` 公共 loader/cache/audit/validator。
- Tool registry 从短 TTL 过渡到 revision 比对 + 主动刷新事件。
- SkillRunner 纳入统一资源 revision、allowed_tools、usage audit 和发布校验。
- SOP 变量 provider 收敛为公共插件协议，并补齐 `derived`、拓扑调度和工具参数模板。
- Prompt slot 支持阶段编排动态化。

### PR-3：SOP 变量方案重审与优化

- 基于动态 Skill 实现 `hci-alert-parsing` 解析 `node_ip/alert_type`。
- 基于通用工具模板实现 `smart_info`。
- 基于 `derived` 或动态 Skill 实现 `is_sys_disk`。
- 基于 PR1 已修复的 `merge_variable_schema`、`depends_on`、`output_path`，重审磁盘寿命 SOP 的最终变量声明和运行时验收。

## 八、验收标准

PR-2 完成后，以下场景必须成立：

- 在技能管理页面新增并启用 `hci-alert-parsing`，新的 SOP 执行可调用该 Skill，并在审计中记录 Skill revision。
- 在工具管理页面修改工具描述或模板，不重启 agent-service，下一轮工具列表和执行模板使用新 revision，且支持主动刷新。
- 在 Prompt 管理页面切换 slot 指向的新 Prompt，不改代码即可生效。
- SOP 发布时若引用不存在的 tool/skill，发布失败并返回明确错误。
- Agent 审计记录能回答：本轮使用了哪些 KBD/SOP/Tool/Skill/Prompt，各自 revision 是多少。
