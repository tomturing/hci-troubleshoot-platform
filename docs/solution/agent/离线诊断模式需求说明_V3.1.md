## 0. P0 范围收敛决策

本节优先级高于后续历史设计明细；出现冲突时以本节为准。

| 类别 | 精简 P0 | 后续版本 |
|---|---|---|
| 场景 | 虚拟机启动失败、硬盘或 RAID（磁盘阵列）硬件告警 | 备份失败、迁移失败及更多场景在黄金案例达标后逐个开放 |
| 客户流程 | 填写故障、下载签名工具、执行采集、上传初始包、等待诊断、查看已审核报告 | 自动补采、报告版本对比、客户自助删除 |
| 采集执行器 | Direct Command Collector（直接命令采集器） | HCI API Collector（HCI 接口采集器）、Manual Attachment Guide（人工附件采集指引）产品化 |
| 安全 | 签名、摘要、有效期、加密证据包、安全解包、隔离 Worker（工作进程） | 多密钥运营、签名吊销中心、独立信任库运营页面 |

向后兼容，但不得据此扩大 P0 发布承诺。

## 1. 背景与问题

### 1.1 现状

HCI 智能排障平台已具备在线诊断能力：Agent（智能诊断代理）通过 `terminal_bridge`（在线终端桥接通道）连接故障主机，根据 `signals_json`（KBD 诊断信号定义）执行工具命令，通过 matcher（证据匹配器）和 KBD（知识库文档）匹配生成诊断报告。现有 CDD 内核已经支持 `PASS / FAIL / UNKNOWN / ERROR / BLOCKED`，P0 在其上增加离线证据获取适配，不重新实现候选归约和结论门禁。

目前售后仍主要依赖：

- 客户开放远程后人工排查；
- 客户零散提供日志后人工检索；
- 证据不足时多次补日志；
- 同类问题依赖不同工程师个人经验。

### 1.2 仅替换数据通道的不足

仅将 `terminal_bridge` 替换为 `offline_file_searcher`，可以解决网络隔离和 SSH 权限问题，但不足以成为真实客户可用的正式版本：

- 采集内容完全依赖 KBD signals，场景基础证据可能缺失；
- 任意 `sub_command` 自动进入脚本存在安全风险；
- 数据模型偏重文本日志，指标、配置和硬件状态覆盖不足；
- 缺失证据可能被 matcher 误判为未命中；
- 上传后缺少 Mandatory 证据完整性和时间覆盖判断；
- 首次包不足时缺少清晰的人工补充和转工程师兜底；
- KBD 命中容易被直接展示为确定根因；
- Agent 结论缺少工程师审核发布机制；
- 原始证据默认永久保存存在合规风险。

### 1.3 解决思路

P0 建设精简 HCI V1：

- 使用最小 Collection Profile（采集画像）规划场景证据；
- 使用安全 Collector Registry（采集器注册表）生成签名采集器；
- 统一封装日志、基础指标、配置、硬件、任务和变更；
- 上传后先完成安全和证据完整性检查；
- 通过 Offline Evidence Provider（离线证据查询器）向 Agent 提供证据；
- matcher 至少支持 `MATCHED / NOT_MATCHED / UNKNOWN`；
- 诊断按 Confirmed、Probable、Suspected、Insufficient、Conflicted 分级；
- 证据不足时明确输出 Insufficient（证据不足）并转工程师；
- Agent 报告经过工程师审核后再发布客户报告。

## 2. 产品目标

### 2.1 功能目标

- 根据工单上下文、故障场景、对象和时间生成 Collection Plan；
- 通过安全 Collector 生成签名 Linux 采集器；
- 采集器生成标准 DiagnosticEvidenceBundle（诊断证据包）；
- 上传后自动完成安全校验、完整性检查和基础证据标准化；
- Agent 能够离线查询日志、JSON、命令输出和基础指标；
- 离线模式复用现有 KBD、matcher 和报告框架；
- 缺失证据返回 UNKNOWN，不得作为反向证据；
- 证据不足时转工程师人工补充，不输出确定性根因；
- 报告分级并由工程师审核后发布；
- 支持规则快照、重新分析和全过程审计。

### 2.2 体验目标

首次诊断对用户呈现为三个阶段，而不是承诺三个点击或三个同步步骤：

1. 创建诊断会话并选择场景、对象和时间；
2. 下载并运行签名采集器；
3. 上传证据包，等待异步处理，并查看经工程师审核后发布的诊断结果。

上传重试、异步分析和工程师审核是阶段内子流程。证据不足时由工程师联系客户补充，
精简 P0 不向客户暴露自动补采、Run（诊断运行）和证据合并等内部概念。

### 2.3 质量目标

| 指标 | P0 目标 |
|---|---:|
| Mandatory 证据完整率 | ≥90% |
| 采集器执行成功率 | ≥95% |
| 已知问题 Top-1 命中率 | ≥80% |
| 已知问题 Top-3 召回率 | ≥95% |
| 证据不足时错误输出 Confirmed | 0 |
| 在线/离线相同证据 matcher 一致率 | ≥99% |
| 报告证据可追溯率 | 100% |
| 未经审核直接发布客户结论 | 0 |
| TOP 场景无远程解决率 | 试点期 ≥40%，稳定期 ≥60% |

> 指标口径：两个首发场景分别考核，不得使用总体平均值掩盖单场景不达标；每个场景
> 上线评估至少包含 30 个经专家确认且证据可回放的案例。`not_applicable`（不适用）
> 不进入 Mandatory（必采）分母，`skipped_by_user`（用户跳过）和采集失败计入未完成。
> Top-1/Top-3 以专家确认根因为 Ground Truth（真值）。

## 5. 核心业务对象

```text
Case（工单）
└── DiagnosisSession（诊断会话）
    ├── IncidentContext（故障上下文）
    ├── CollectionProfileSnapshot（采集画像快照）
    ├── CollectionPlan（采集计划）
    │   └── CollectionItem（采集项）
    ├── CollectorArtifact（采集器制品）
    ├── DiagnosticEvidenceBundle（诊断证据包）
    │   └── EvidenceItem（不可变证据项）
    ├── EvidenceAssessment（证据评估）
    ├── DiagnosisRun（诊断运行）
    │   ├── SignalEvaluation（信号评估）
    │   ├── RuleEvaluation（规则评估）
    │   ├── KBDCandidate（知识库候选）
    │   └── DecisionEvidence（决策证据）
    ├── SupplementPlan（补充采集计划，P1 兼容对象）
    ├── RemediationPlan（处置计划）
    ├── VerificationBundle（验证证据包，P0 仅预留）
    └── DiagnosisReport（诊断报告）
```

所有新增持久化业务表必须包含 `trace_id`、创建时间、更新时间和必要的租户字段。`EvidenceItem` 是不可变审计事实；现有 Fact（事实）表可作为推理投影，但不得覆盖或替代原始证据。

### 5.1 核心状态机

`DiagnosisSession`（诊断会话）状态：

```text
created → plan_ready → collecting → uploading → assessing
        → diagnosing → review_pending → published → closed
```

允许的旁路状态（精简 P0 只启用取消和技术失败恢复；其余保留领域兼容）：

- 任意未结束状态可进入 `cancelled`；
- 可恢复错误进入 `failed`，重试后回到失败前阶段；
- P1 可由 `assessing / diagnosing / review_pending` 进入 `supplement_required`，补采完成后
  回到 `assessing`；
- P1/P2 可由删除申请进入 `deletion_pending`，完成后进入 `deleted`；Legal Hold
  （法务保全）生效时禁止删除。

`DiagnosisRun`（诊断运行）状态：

```text
queued → running → succeeded | failed | cancelled
```

同一会话同一证据集合只允许一个活动 Run；P1 补采后必须生成新的证据集合版本和新的
Run（诊断运行），不覆盖历史运行。
精简 P0 只产生首次 Run（诊断运行）；多 Run 规则供 P1 兼容流程使用。

## 6. 功能需求

## FR-001 创建诊断会话【P0】

### 入口

- Customer UI（客户界面）独立地址 `/offline-diagnosis?case_id={case_id}`；
- Customer UI（客户界面）创建工单时选择“无 SSH 创建工单”后跳转上述独立地址；
- 售后工作台 → 新建诊断会话。

### 请求信息

- `case_id`；
- `product_line=HCI`；
- `selected_scenario`；
- `selected_category`（可选，默认由场景映射生成）；
- `incident_start_time`；
- `incident_end_time`；
- `timezone`；
- `affected_objects`；
- `impact_scope`；
- `current_status`；
- `recent_change_description`。

### 业务规则

- 工单号、故障时间和故障对象必填；
- “无 SSH 创建工单”是 Offline Diagnosis（离线诊断）的显式模式边界：工单创建成功后默认打开“离线诊断”，只建立当前工单上下文，不创建 Conversation（对话）、不调用 Agent（智能体），也不得把建单前暂存的问题描述作为首条对话消息发送；
- 原 Customer UI（客户界面）根地址 `/` 必须保持原聊天、工单和 SSH 交互，不挂载离线诊断按钮或抽屉；独立地址缺少 `case_id` 时提供已有工单号输入入口，不得自动创建工单；
- 用户后续主动进入在线对话时，必须重新执行明确的发送动作，离线建单时暂存的问题描述不得自动重放；
- 用户选择分类作为分析起点；
- 创建后生成唯一 `diagnosis_session_id`；
- 保存 Incident Context 快照；
- P0 仅允许创建正式支持场景或标记为“实验场景”的会话；
- 创建请求必须携带 `Idempotency-Key`（幂等键）；同一租户、工单和幂等键重复请求返回原会话；
- `selected_scenario` 表示产品化场景，`selected_category` 表示初始 KBD 分类，`resolved_category` 表示诊断后归属，三者不得混用；
- `resolved_category` 只能由诊断过程写入，客户创建请求不得指定。

## FR-002 Collection Profile（采集画像）【P0】

### 目标

为每个 P0 正式场景定义最小可用证据集合，不再完全依赖 KBD signals 聚合。

### 采集项分级

- `mandatory`；
- `recommended`；
- `conditional`；
- `deep_dive`。

### Profile 字段

```yaml
profile_id: 虚拟机-027
display_name: 虚拟机备份失败采集画像
product_line: HCI
```

## FR-004 安全 Collector Registry（采集器注册表）【P0】

### 目标

所有交付客户执行的采集动作必须来自已审批 Collector，不允许直接执行 KBD 中的任意 `sub_command`。

KBD Signal 必须通过精确 `KBD Revision + Signal ID` 映射引用已审批 Collector Revision
（采集器修订）及其输出契约。现有在线 Tool（工具）定义复用能力启停、参数校验、风险等级和
动态版本机制，但 Collector 使用独立数据模型、审批状态和制品生命周期。最终命令由
Shared Acquisition Compiler（共享采集编译器）生成，在线与离线不得各自维护等价命令规则。

### Collector 定义

```yaml
collector_id: kbd_qfk_hardware_example
platform: linux
executor: command
argv_template: ["acli", "hardware", "disk", "list", "--formatter", "json"]
parameter_schema:
  type: object
  properties: {}
  additionalProperties: false
risk_level: read_only
timeout_seconds: 30
max_output_mb: 10
supported_product_versions:
  - "5.x"
  - "6.x"
review_status: approved
output_contract:
  schema_id: raid_status_v1
  media_type: application/json
  output_path: commands/raid_status.json
approved_by: user_xxx
approved_at: "2026-07-24T09:00:00+08:00"
version: 1.0.0
execution_contract_revision: "sha256:..."
```

> 存量事实表中的 `executor: shell` 只作为内部兼容枚举名；新契约统一使用
> `executor: command` 和不可变 `argv`（参数数组）。客户侧 Go 运行时不得调用 `/bin/sh`
> 或其他 Shell（命令解释器），也不得把命令模板文本交给解释器。

无参数 Collector 也必须使用上述完整 JSON Schema（JSON 模式），不能使用空对象。

### P0 必须具备

- Collector 白名单；
- 共享采集编译器和可追溯的 Execution Contract Revision（执行契约修订）；
- 参数类型、枚举、长度、路径和控制字符校验；
- 超时和最大输出限制；
- 退出码、stdout、stderr 记录；
- 风险等级；
- 支持版本；
- Collector 版本；
- 禁用状态；
- 审批人和审批时间。

### P0 不强制具备

- 自动灰度发布；
- 根据质量指标触发的无人值守自动回滚；
- 跨版本批量回放。

人工同步预检、差异审核、发布、驳回、历史查询和最近批次回滚属于当前控制面能力。

## FR-005 生成签名采集器【P0】

### P0 执行器

- Direct Command Collector Artifact（直接命令采集器制品）；

HCI API Collector（HCI 接口采集器）和 Manual Attachment Guide（人工附件采集指引）
已有底层兼容实现，但不作为精简 P0 的客户产品入口和验收执行器。

### 要求

- 采集器必须数字签名；
- 提供文件 SHA-256；
- 默认只读；
- 执行前展示采集项、权限、预计耗时、大小和敏感数据类型；
- 每个 Collector 单独执行并记录状态；
- 单个 Collector 失败不终止整体采集；
- 变量优先自动发现，无法解析时要求用户确认；
- Customer UI（客户界面）在生成包含节点级采集项的计划前必须采集“采集器执行节点”；生成制品时将该值作为 `target_node`（目标节点）提交；
- 采集计划成功但制品生成失败时必须保留计划展示，并允许用户补填或选择执行节点后单独重试制品生成；制品成功后明确展示“下载签名结构化采集制品”和 Verification Bundle（验证包）入口；
- 支持完全离线运行；
- Verification Bundle（验证包）必须内置 `hci-collect-linux-amd64`（Linux x86_64
  静态 Go 运行时）和签名的 Runtime Manifest（运行时清单）；客户解压后直接执行二进制，
  不依赖 Python、pip、cryptography、OpenSSL、glibc、`/bin/sh`、Bash 启动器或访问公网；
- Go 运行时必须先以可信第二通道指纹固定受信根，再校验自身 SHA-256、采集制品、Manifest
  （清单）和 Revocation List（吊销清单），全部通过后方可显示范围并执行采集；
- 内嵌 `case.json`（工单上下文）必须由同一受信根签名，并校验其 `session_id`（会话标识）
  与 Collector Artifact（采集器制品）一致，防止跨工单替换；
- 支持执行后清理临时文件；
- 采集器中不得出现未注册命令。
- Direct Command（直接命令）项必须以不可变 `argv`（参数数组）进入签名制品，由 Go
  运行时直接创建进程；禁止调用 Shell（命令解释器）和命令转发器。HTTP 请求、超时控制、
  stdout/stderr（标准输出/标准错误）截断及 execution manifest（执行清单）均由 Go 完成。
- Customer UI（客户界面）在下载和执行前必须逐项展示签名制品内固化的实际 `argv`
  （参数数组）、HCI API（HCI 接口）请求方法与路径或 Manual（人工采集）指引；Admin UI
  （管理界面）必须提供 Collector Artifact（采集器制品）执行清单详情。展示数据必须来自
  不可变签名制品，不得使用可能已被后续修改的当前 Collector（采集器）模板代替。

### 凭据与信任链

- HCI API Collector 如需访问客户本地 HCI API，应使用客户本地签发或执行时输入的短时凭据；云端平台会话令牌不能作为完全离线环境的依赖；
- 凭据只在内存或受控临时文件中存在，执行完成后立即清除，不得写入 manifest、DiagnosticEvidenceBundle 或执行日志；
- 采集器使用 Detached Signature（分离式签名），签名元数据至少包含 `algorithm / key_id / signed_at / expires_at / artifact_sha256`；
- 完整工具包携带校验程序；客户主页面只展示一个“下载完整采集工具包”入口，
  SHA-256（摘要）和公钥指纹放在可展开的安全明细中；
- P0 依赖短有效期和固定受信根拒绝过期或未知 `key_id`（密钥标识）；签名吊销清单和
  多密钥运营作为 P1/P2 增强，不作为客户操作前置步骤；
- 输出 DiagnosticEvidenceBundle 支持 Envelope Encryption（信封加密），manifest 记录算法、`key_id` 和加密数据密钥封装信息，不记录明文密钥；
- 平台只在隔离 Worker 中解密，明文临时文件随任务完成清理；具体密钥托管、轮换和应急吊销写入架构设计与威胁模型。

### 变量解析优先级

1. 环境自动发现；
2. Incident Context；
3. 用户执行前确认；

### 当前编码状态（2026-07-31）

- `GET /api/internal/collectors` 按审批状态和启用状态列出 Collector；
- `PUT /api/internal/collectors/{collector_id}` 创建或更新草稿；
- `POST /api/internal/collectors/{collector_id}/review` 批准或拒绝；
- `POST /api/internal/collectors/{collector_id}/disable` 禁用；

  （修订版本）；
- 更新、审批和禁用使用 `If-Match`（条件更新头）及 `ETag`（实体标签）乐观锁；
- 批准时发布不可变 dynamic resource revision（动态资源修订版本），制品只从该快照
  解析命令；
- 已实现 JSON Schema（结构模式）参数校验、`argv`（参数数组）逐参数约束，以及对管道、
  重定向、命令替换、多命令拼接和通用 Shell（命令解释器）间接执行的拒绝策略。

KBD Signal（知识库诊断信号）显式映射已通过

### 当前编码状态（2026-07-29）

已实现 Direct Command Collector（直接命令采集器）、HCI API Collector（HCI 接口
采集器）和 Manual Attachment Guide（人工附件采集指引）的统一 Linux 编排制品。
精简 P0 只开放 Direct Command Collector，其余实现保留用于后续版本：

- 仅解析计划中的 `active`（当前激活）项，排除 `deferred`（待激活）项；
- 按目标节点生成，多节点或未解析 `source_node`（来源节点）时要求显式节点；
- 校验 Collector 已审批、已启用、只读且支持当前产品版本；
- 使用不可变 Collector revision（采集器修订版本）渲染命令；
- 每项独立超时，stdout（标准输出）与 stderr（标准错误）共享总输出上限；
- 单项失败不终止整体，并记录退出码、输出字节数和截断状态；
- 使用 Ed25519 Detached Signature（Ed25519 分离式签名），返回 SHA-256、签名、
  `key_id`、公钥、指纹、签名时间和有效期；
- 新制品使用 `schema_version=1.2` 和 `artifact_type=structured_collector`，结构化执行清单
  和 Manifest（清单）分别签名；
- 提供单密钥 Trust Store（受信根）、24 小时有效的签名 Revocation List
  （吊销清单）和 Verification Bundle（验证包）；
- Go 离线运行时要求输入可信第二通道公钥指纹，不联网安装依赖，并在执行采集前拒绝未知
  `key_id`、运行时/制品/清单篡改、过期、吊销和陈旧吊销清单；
- 未配置签名私钥时默认拒绝生成；平台撤销记录操作者、时间、原因码和 trace。
- 未配置证据包 RSA-3072 加密私钥时，服务端必须在生成 Collector Artifact（采集器制品）
  阶段提前拒绝；下载 Verification Bundle（验证包）和 Go 运行时开始采集前必须再次校验
  `bundle_encryption`（证据包加密配置），不得延迟到完成采集后的加密打包阶段才报错；
- 历史缺少加密公钥的已签名制品不得原地修改，必须撤销旧制品、重生成 Collection Plan
  （采集计划）并签发新制品；本地 Compose 可运行 `make diagnosis-dev-keys` 生成持久化开发密钥，
  生产环境必须由 KMS（密钥管理服务）或 Secret（密钥对象）注入；
- HCI API Collector 仅允许固定相对路径 `GET`，凭据通过运行时
  `HCI_API_BASE_URL`（HCI 接口基础地址）和 `HCI_API_TOKEN`（HCI 接口短期令牌）
  注入；令牌不进入结构化制品、Manifest 或证据包；

- Go 离线运行时生成标准包并使用 HCIEB2（第二版 HCI 加密证据包）分块
  AES-256-GCM Envelope Encryption（信封加密）和 RSA-OAEP-SHA256
  （RSA 最优非对称加密填充）密钥封装；每个 1 MiB 明文块使用独立 Nonce（随机数）和
  AAD（附加认证数据），不得将完整证据包一次性读入内存；历史 HCIEB1 只读兼容；

### 运行时与任务制品生成时机

- `hci-collect-linux-amd64` 是通用 Trusted Runtime（可信运行时），不内置 KBD、Profile、
  工单、节点和时间窗口，按平台版本提前编译、签名、测试并随 Diagnosis Service 镜像发布；
- 客户创建离线诊断后，平台必须基于当时已发布 KBD、已生效 Collection Profile、已审批
  Collector revision、目标节点和故障时间窗，实时生成 Collection Plan 和签名结构化制品；
- KBD/Profile 日常变更只触发后续计划和任务制品更新，不要求重新编译 Go 运行时；只有执行协议、
  安全门禁或密码学实现变化时才重建运行时；
- 历史计划和制品必须保持不可变，不得被后续 KBD/Profile 同步覆盖；错误制品通过到期或
  Revocation List（吊销清单）停用后重新生成；
- Verification Bundle（验证包）由提前发布的通用运行时和实时签发的任务制品组成。
- 隔离 Diagnosis Worker（诊断工作进程）完成 magic number（魔数）、路径穿越、
  符号链接、压缩炸弹、配额、恶意标记、文件声明和哈希校验，并在任务结束清理明文。

生产多密钥轮换/KMS 托管通过密钥适配器接入，未配置时正式制品生成或解密默认拒绝；
历史 `schema_version=1.0` 制品没有 Manifest 签名，必须重新生成。

- Ed25519（爱德华曲线数字签名）保护 Runtime/Artifact（运行时/制品）的平台签发来源和内容完整性；
- HCIEB2 的 AES-GCM 保护生成后证据包的机密性和位级完整性，任何分块、头部、顺序或长度篡改都必须拒绝；
- 平台加密公钥不是客户侧身份凭据，持有公钥的人理论上可以构造新的合法密文。因此通过密码学校验
  不等于证明执行节点、系统时钟、命令输出或人工附件真实；
- 报告必须分别展示 Artifact 绑定、执行节点、时间覆盖、证据内部一致性和来源可信度。要求强现场
  身份时，应增加 TPM/TEE（可信平台模块/可信执行环境）设备证明或受管终端身份。

## FR-007 上传诊断证据包【P0】

### 功能

- 精简 P0 客户入口只支持初始包；`supplement`（补采）和 `verification`（验证）类型
  保留兼容枚举及内部接口，不纳入首版验收；
- 支持分片上传和断点续传；
- 上传时提交或由平台计算 SHA-256；
- 上传后进入隔离区；
- 记录上传人、时间、来源 IP、包版本和类型；
- 原始包进入对象存储。

### 安全校验

- 文件类型和 magic number 校验；
- `manifest.json` schema 校验；
- 路径穿越防护；
- 符号链接防护；
- 压缩炸弹检查；
- 内容策略与 EICAR（反恶意软件测试字符串）哨兵检查；若环境配置真实反恶意软件引擎，
  追加引擎扫描结果；未配置时必须明确标记“扫描引擎未配置”，不得显示为“病毒扫描干净”；
- 解压总大小限制；
- 文件数量限制；
- 单文件大小限制；
- 包内文件 SHA-256 一致性校验。

### 架构约束

- 大文件不得经 API Gateway、kb-service 或其他 Web 进程完整转发；
- 平台创建 Upload Session（上传会话）后，客户端使用分片或预签名地址直传对象存储；
- 上传完成接口校验分片、整体大小和整体 SHA-256，成功后才创建 DiagnosticEvidenceBundle；
- 上传会话支持 `initiated / uploading / completing / completed / aborted / expired / failed` 状态；
- DiagnosticEvidenceBundle 处理状态为 `uploaded → quarantined → scanning → extracting → assessing → ready`，任一步可进入 `rejected` 或可重试的 `failed`；
- 解密、扫描、解压和索引必须通过隔离异步 Worker 执行；
- 不得在 Web 请求进程中把全量文件内容加载到内存；
- 分析工作目录必须隔离并设置 CPU、内存、磁盘和超时配额；
- 重复 `complete` 请求必须幂等；SHA-256 相同且业务键一致的重复 Bundle 不得重复进入分析；
- 失败上传支持重试或显式 `abort`，过期分片按生命周期策略清理。

## FR-011 Signal Evaluation（信号评估）状态【P0】

### P0 状态

| 状态 | 含义 |
|---|---|
| MATCHED | 证据存在且支持该 Signal |
| NOT_MATCHED | 证据存在且明确不支持该 Signal |
| UNKNOWN | 证据缺失、采集失败、不可读、变量未解析或时间范围不覆盖 |

现有 CDD 内部结果按以下方式适配，不改变原归约器语义：

| CDD 内部状态 | 离线接口状态 | 原因保留 |
|---|---|---|
| `PASS` | `MATCHED` | `matched` |
| `FAIL` | `NOT_MATCHED` | `not_matched` |
| `UNKNOWN` | `UNKNOWN` | 原未知原因 |
| `ERROR` | `UNKNOWN` | `execution_error` |
| `BLOCKED` | `UNKNOWN` | `dependency_blocked` |

### Matcher 类型全覆盖要求

共享 `evaluate_matcher`（`backend/shared/signals/matcher.py`）支持
全部 7 种确定性 Matcher 类型：`keyword`、`regex`、`state`、`threshold`、
`delta`、`trend`、`exists`。离线 Signal Evaluation 必须复用同一实现，
**不得因 matcher 类型不支持而将信号降级为 UNKNOWN**。

具体要求：
1. 离线 `OfflineEvidenceProvider` 产出的证据文本需经
   `extract_output_values`（`backend/shared/signals/extractor.py`）
   按 `match.extract` 规范执行结构化取值（行选择、列选择、JSON 路径、
   基数、类型转换）；
2. 取值结果送入 `evaluate_matcher` 求值，7 种类型均须支持；
3. `evaluate_matcher` 返回 `matched=None`（无法确定）时，交由 LLM 兜底或
   标记为 UNKNOWN 并注明原因（如非法正则、样本不足），不得静默丢弃；
4. **禁止行为**：跳过 `match.extract` 直接对原始文本做扁平 keyword 匹配；
   因 matcher 类型为 `regex`/`state`/`delta`/`trend`/`exists` 返回
   "matcher 无法解析证据内容"。

### 返回示例

```json
{
  "signal_id": "s2",
  "state": "UNKNOWN",
  "reason": "RAID controller event was not collected",
  "required_for_conclusion": true,
  "evidence_status": "collection_failed",
  "evidence_refs": []
}
```

### 业务规则

- `UNKNOWN` 不得被计入反向证据；
- 关键 Signal 为 UNKNOWN 时，不得输出 Confirmed；
- `NOT_MATCHED` 必须证明对应证据存在且有效；
- P1 增加 Signal 级 `CONFLICTED`。

## FR-013 Agent 离线诊断【P0】

### 流程

1. 加载 DiagnosisSession（诊断会话）、Incident Context（故障上下文）和 EvidenceAssessment（证据评估）；
2. 判断当前是否具备诊断条件；
3. 通过 Offline Evidence Provider 查询已采集证据，按 `match.extract` 规范提取结构化取值；
4. **调用共享 `evaluate_matcher` 对提取后的证据执行确定性求值**，生成 MATCHED / NOT_MATCHED / UNKNOWN；
5. 生成 KBD 候选和主要故障域；
6. 计算诊断等级和置信度；
7. 证据不足时输出 Insufficient（证据不足）并标记缺失证据；
8. 生成 Draft（草稿）报告，进入工程师审核或人工补充证据流程。

### 架构核心：离线 = Shared CDD + AcquisitionProvider 适配【当前已实现】

离线诊断必须委托根目录 Shared CDD（共享候选驱动诊断）组件。在线 `KBDDiagnostic` 保留
流式工具事件编排，离线分析注入 FrozenEvidenceProvider（冻结证据提供器）；两者共用信号计划、
依赖调度、Matcher/Extract（匹配/提取）、候选归约和 Conclusion Gate（结论门禁）语义。

```text
离线诊断流程 = Shared CDD Runner + OfflineEvidenceProvider 适配

1. 加载 Collection Plan 冻结的完整 KBD/Mapping 修订和离线证据 (evidence_item 表)
2. 构造 OfflineEvidenceProvider (实现 AcquisitionProvider 接口)
3. 委托 SharedCDDRunner.diagnose(candidates, provider=offline_provider, ...)
   → 内部全部复用在线代码路径:
     compile_signal_plan → provider.execute → extract_output_values
     → evaluate_matcher → variable_pool → reduce_candidates
     → ConclusionGate
4. 持久化结果 (signal_evaluation, diagnosis_candidate, run_manifest)
5. 结论等级映射 (CDD 四级 → 离线五级)
6. 生成报告 → 审核 → 发布
```

**AcquisitionProvider 接口**：

```python
class AcquisitionProvider(Protocol):
    async def acquire(self, acquisition) -> AcquisitionRunResult:
        """执行或查询一次采集，并按精确 SignalRef 返回认识论结果。"""
        ...
```

- 在线实现：`BridgeRelayProvider`（WebSocket → terminal_bridge → SSH）
- 离线实现：`OfflineEvidenceProvider`（evidence_item 表查询）

**组件归属**：

| 组件 | 代码归属 | 复用方式 |
|---|---|---|
| `evaluate_matcher` | `backend/shared/signals/matcher.py` | 在线离线直接共用 |
| `extract_output_values` | `backend/shared/signals/extractor.py` | 在线离线直接共用 |
| Shared Variable Pool（共享变量池） | `backend/shared/cdd` | 在线离线共用 produces/requires 语义 |
| 候选状态机 | `backend/shared/cdd` | 委托 Shared CDD Runner |
| 结论门禁 | `backend/shared/cdd` | 委托 Shared CDD Runner |
| 结论等级映射 | 版本化 `ConclusionPolicy` | CDD 四级 → 离线五级，由 `diagnosis-service` 实现 |
| `AcquisitionProvider` 接口 | `backend/shared/` | 在线离线各自实现同一接口 |

### 约束

- Agent 不得将 UNKNOWN 当作反向证据；
- 证据不足时不得输出 Confirmed；
- 所有结论必须引用 `evidence_ref`；
- 结论与处置建议分离；
- KBD 候选仅是诊断输入；
- 大模型只用于摘要、表达和相似案例，不覆盖规则结果；
- Agent 自由形式 Thought 不作为审计内容展示；
- **离线 matcher 求值必须与在线使用同一代码路径，不得因 matcher 类型不支持而静默降级为 UNKNOWN**。

## FR-014 分级诊断报告【P0】

### 诊断等级

| 等级 | 中文含义 | 规则 |
|---|---|---|
| `Confirmed` | 已确认 | 唯一候选受支持，关键 Mandatory 证据完整且无未解决冲突 |
| `Probable` | 高概率 | 主要证据支持且候选显著领先，但仍缺少非阻断性确认信息 |
| `Suspected` | 疑似 | 仅形成候选方向，或多个候选尚未充分排除 |
| `Insufficient` | 证据不足 | 证据覆盖不足，无法形成有效判断 |
| `Conflicted` | 证据冲突 | 同一判断存在相互矛盾且均可信的正反证据 |

### 报告结构

```json
{
  "diagnosis_level": "Probable",
  "summary": "...",
  "resolved_domain": "storage",
  "primary_hypothesis": "...",
  "confidence": 0.88,
  "supporting_evidence": [],
  "counter_evidence": [],
  "excluded_causes": [],
  "missing_evidence": [],
  "recommended_recovery": [],
  "risk_and_rollback": [],
  "root_cause_validation": [],
  "supplement_plan_id": "sp_xxx",
  "matched_kbds": [],
  "publish_status": "draft"
}
```

### 报告规则

- `Insufficient` 不显示确定性根因；
- `Conflicted` 明确展示冲突证据；
- `Probable` 必须说明仍缺少什么；
- `Confirmed` 必须满足版本化的关键证据规则；
- 修复建议必须注明风险、回退和验证步骤；
- 报告必须引用 EvidenceItem；
- Agent 生成后默认 `draft`。
- 等级必须由版本化 Conclusion Policy（结论策略）计算并写入 `conclusion_policy_version`；
- 当前在线 CDD 的 `DEFINITIVE / PARTIAL / INCONCLUSIVE / NO_MATCH` 通过显式策略映射，不做简单枚举重命名。

## FR-015 报告审核与发布【P0】

### 状态

| 状态 | 中文含义 |
|---|---|

## FR-022 Collector Lifecycle（采集器生命周期）与 KBD 变更治理【基础闭环已实现】

### 目标

建立 KBD（知识库文档）、Offline Signal Mapping（离线信号映射）、Collection Profile
（采集画像）、Collector Definition（采集器定义）、Collection Plan（采集计划）和
Collector Artifact（采集器制品）之间可审计、可回放的变更边界，避免 KBD 更新后静默
使用不匹配的旧采集范围。

### 生成策略

- Collector Definition 和 Collection Profile 必须提前完成审批并发布不可变修订版本；
- Collector Artifact 在诊断会话、目标节点、故障时间窗口和 Collection Plan 确定后，
  由已审批修订版本按工单即时组装和签名；
- 不为不同工单提前生成或跨工单复用通用制品；同一计划和目标节点允许幂等返回同一制品；
- 制品默认保持短有效期，过期后必须基于仍然有效的计划和采集资源重新生成。

### KBD 驱动同步

- Collector 和 Collection Profile 不维护独立业务种子；首次 Full Sync（全量同步）从当前
  已发布 KBD 建立基线，后续 Incremental Sync（增量同步）只处理上次成功发布后新增的
  KBD 动态修订；
- 增量边界使用 KBD `dynamic_resource_revision.id`（动态资源修订序号）作为 Watermark
  （同步游标），KBD 发布、重新发布和已发布版本撤回均必须产生可消费的修订事件；
- 已发布 KBD 退回草稿、归档或停用时，必须在同一事务中追加
  `status=disabled + contract.lifecycle.tombstone=true` 的不可变修订并移除运行时 Active Revision；
  修订须保留 KBD ID、上一发布内容身份和离线场景元数据，供增量同步定位并禁用失去来源的
  Collector（采集器）、Offline Signal Mapping（离线信号映射）和 Collection Profile（采集画像）。
  相同正文重新发布时也必须产生高于墓碑的新修订序号；
- 同步只解析不可变 KBD Revision 中的完整 `signals_json`，不从 KBD 自然语言正文生成命令；
  采集命令由 Shared Acquisition Compiler（共享采集编译器）根据 Safe Acquirer Catalog
  （安全采集能力目录）、Tool Revision 和 Execution Contract Revision 编译；
- Preview（同步预检）生成 Candidate Revision（候选修订）和资源差异，不得影响当前生效版本；
- 管理员审核通过后，Collector → Offline Signal Mapping → Collection Profile 在同一数据库
  事务中发布；任何一步失败必须整体回滚并记录失败结果；
- 在线诊断与离线诊断必须共用 KBD 审核发布时确认的最终 `category_id`（分类编码）作为问题场景；
  所有已发布 KBD 默认参与离线资源同步，不得再要求 `offline_capable`、`offline_enabled` 或
  `offline_scenario` 等离线专属开关；
- 未知采集工具、无安全目录定义、缺少有效最终分类或游标发生并发冲突时，受影响资源不得发布；
  同步批次必须展示已发布 KBD 数、共用场景 KBD 数、分类异常 KBD 数、影响场景和候选资源数，
  禁止将已发布 KBD静默跳过。

### 版本回退与审计追溯

- 只允许对最近一次成功发布的 Sync Batch（同步批次）执行人工 Rollback（回滚），避免跳过
  中间依赖版本造成资源组合不一致；
- 回滚恢复发布前的 Active Revision（生效修订）、事实数据和 Watermark，但不得删除不可变
  修订，不得修改历史 Collection Plan、Collector Artifact、Diagnosis Run 或报告；
- 每次 Preview、Publish（发布）、Reject（驳回）和 Rollback 都必须分别记录 `started`
  （已开始）以及 `succeeded`（成功）或 `failed`（失败）Audit Event（审计事件）；
- 每个 Audit Event 必须保存批次内递增 `event_sequence`（事件序号）、操作者、理由、动作、
  结果、时间、`trace_id`（链路追踪标识）和详情；每个同步批次必须保存起止游标、KBD 来源
  修订、资源 Before/After（变更前/后）快照、校验结果、错误原因和计数；
- 候选被驳回、发布失败或回滚失败后，批次、差异和事件均不得删除，管理端仍可检索和查看。

### KBD 变更分类与处理

| 变更类型 | 处理规则 |
|---|---|
| 标题、根因、方案等知识内容变化 | 不影响已生成制品；只影响后续诊断内容和报告 |
| Signal Matcher（信号匹配规则）变化 | 执行规则回放并重新校验 Offline Signal Mapping；不直接改写制品 |
| Evidence Requirement（证据要求）变化 | 输出受影响场景、Collection Profile（采集画像）和 Collector（采集器）清单；完成映射及资源版本升级后，新计划使用新版本 |
| KBD 下架或删除 | 后续规则集不再使用；历史 Run 和报告继续引用原快照 |
| Collector 安全缺陷 | 禁止新制品引用问题修订版本，并撤销引用该版本且尚未过期的制品 |

### 一致性要求

- 面向离线诊断的 KBD Signal 必须按精确 `KBD Revision + Signal ID` 映射到已审批、已启用且
  输出契约兼容的 Collector Revision；不得仅按 `tool/category/command` 模糊匹配；
- KBD 发布流程必须生成 Change Impact Report（变更影响报告），列出受影响场景、
  Collection Profile、Signal Mapping（信号映射）和 Collector；
- 普通 KBD 变更不得修改、覆盖或自动撤销历史 Collector Artifact；
- 当证据要求变化导致旧采集范围不足时，管理员通过 Regenerate（重生成）创建新的
  Plan Revision（计划修订）；旧计划标记为 `superseded`（已替代），对应的可下载制品自动撤销；
- Diagnosis Run Manifest（诊断运行清单）必须保存本次使用的完整 KBD revision set
  （KBD 修订版本集合）、资源标识和内容哈希，不得只保存已发布数量与最后更新时间；
- Collection Plan 必须冻结完整 `verification_contract`、`generation_metadata`、
  `publish_validation` 和 Signal 内容；Diagnosis Run 必须只消费该快照，不得重新查询当前
  `kbd_entry` 或当前 Mapping；
- 已完成报告默认按原规则快照复现；如用户选择 Latest Rules Reanalysis（最新规则重新分析），
  必须创建新的 Diagnosis Run，并保留新旧规则和报告差异。

### 验收标准

- KBD 新增、修改、下架时均能生成可审计的变更影响报告；
- 仅修改知识内容不会导致采集计划、制品或 Collector 修订版本变化；
- 新增离线证据要求但缺少有效映射时，KBD 的离线可用状态被阻断或明确标记不可用；
- 证据要求变化时，受影响旧制品显示可能过时，并可生成绑定新修订版本的新计划和制品；
- Collector 安全撤销可以按修订版本找到并撤销所有尚未过期的受影响制品；
- KBD 后续更新或删除后，历史报告仍可按 Run Manifest 中的具体资源修订版本复现。
- 首次全量同步后可从零生成 Collector、Signal Mapping 和 Profile，不依赖业务种子；
- 未发生 KBD 修订时重复增量预检不得生成资源变更；
- 候选发布前当前生效资源保持不变，发布成功后同步游标与资源版本一起原子推进；
- 最近发布批次回滚后，资源生效指针和同步游标恢复，历史修订与历史制品保持不变；
- 对成功、驳回、发布失败和回滚失败的同步动作，均可按批次查看完整有序事件和变更快照。

> 当前实现采用“候选同步、人工发布、局部版本快照”的弱生命周期耦合：KBD 发布不再反向依赖
> 已存在的 Collector 映射，避免首次无种子状态下形成循环门禁；缺失或不安全的采集要求改在
> Offline Resource Sync 发布门禁中阻断。普通 KBD 修改不会静默改写生效资源或历史制品。
> 精确信号映射、完整 KBD/Mapping 快照消费和执行契约联动已完成。按单个 Collector revision
> （采集器修订版本）选择性批量撤销、自动灰度和质量指标驱动自动回滚继续作为 P1 增强项。

## FR-023 Matcher/Extract 在线离线一致性【代码契约已实现，生产样本验收待完成】

### 目标

保证同一 KBD 信号 + 相同证据内容，在线模式和离线模式产生相同的 matcher 判定结果。

### 背景

在线 KBD 诊断引擎支持 `keyword`、`regex`、`state`、`threshold`、`delta`、`trend`、
`exists` 共 7 种确定性 Matcher 类型和结构化 `match.extract` 取值规范。共享 Matcher/Extractor
已经位于 `backend/shared/signals`，离线诊断已通过统一 AcquisitionProvider 和 Shared CDD
Runner 走完与在线相同的调用路径；生产发布前仍需用专家确认的 Golden Evidence Set 完成内容验收。

### 功能要求

1. **AcquisitionProvider 接口定义**：在 `backend/shared/` 定义 `AcquisitionProvider`
   抽象接口（`execute(acquisition, resolved_args) → AcquisitionResult`），
   在线 `BridgeRelayProvider` 和离线 `OfflineEvidenceProvider` 分别实现；
2. **共享 Matcher 实现**：以 `backend/shared/signals/matcher.py` 和
   `backend/shared/signals/extractor.py` 为唯一权威实现；Agent 内兼容模块只能重新导出，
   不得复制或维护等价算法；
3. **离线证据提取适配**：`OfflineEvidenceProvider.execute()` 返回原始 stdout/
   stderr，由共享 `extract_output_values` 按 `match.extract` 规范执行结构化
   取值（行选择、列选择、JSON 路径、基数、类型转换）；
4. **全类型覆盖**：离线 matcher 求值必须支持 `keyword`、`regex`、`state`、
   `threshold`、`delta`、`trend`、`exists` 全部 7 种类型（含 `exists`），
   以及 `mode`（or/and/not）和 `expected` 翻转语义；
5. **不可判定处理**：`evaluate_matcher` 返回 `matched=None` 时，记录原因
   （如非法正则、样本数不足、未知类型），交由 LLM 兜底或标记为 UNKNOWN；
6. **禁止行为**：跳过 `match.extract` 直接对原始文本做扁平 keyword/equals 匹配；
   因 Matcher 类型分支缺失而返回“matcher 无法解析证据内容”；
   在离线侧独立维护一套 matcher 逻辑并声称与在线等价；
   在 `diagnosis-service` 中独立调用 matcher 而不通过 `AcquisitionProvider` 接口。

### 验收标准

- AC-M01：`AcquisitionProvider` 接口在 `backend/shared/` 定义，在线
  `BridgeRelayProvider` 和离线 `OfflineEvidenceProvider` 分别实现并通过接口
  一致性测试；
- AC-M02：从 Golden Evidence Set 中选取至少 20 个案例，每条信号分别经在线
  `evaluate_matcher` 和离线 `evaluate_matcher` 求值，判定结果一致率 ≥99%；
- AC-M03：任一条信号因 matcher 类型不支持而返回 UNKNOWN 的数量为 0；
- AC-M04：离线 `extract_output_values` 的输出结构与在线一致（相同输入 →
  相同 `ExtractionResult`）；
- AC-M05：`evaluate_matcher` 返回 `matched=None` 的场景有明确的 LLM 兜底或
  UNKNOWN 原因记录，不静默丢弃。

## FR-025 离线模式 produce 变量处理【P0，V3.3 新增】

### 目标

离线诊断模式正确执行生产者信号的 `produces` 变量产出，维护变量池使消费者信号的

1. **变量池初始化**：从 Diagnosis Session 的 `IncidentContext` 和
   `affected_objects` 中提取初始变量（故障对象、时间窗、影响范围、节点 IP 等），
   注入到共享 `VariablePool` 实例；
2. **生产者信号 produce 执行**：通过 `AcquisitionProvider` 接口，在线 CDD 内核
   调用 `OfflineEvidenceProvider.execute()` 获取 QKV 信号数据，经共享
   `extract_output_values` 取值后，写入共享 `VariablePool`；
3. **消费者信号变量注入**：在线 CDD 内核从共享 `VariablePool` 读取
   `orchestrate.requires` 声明的依赖变量，注入到 `OfflineEvidenceProvider.execute()`
   的 `resolved_args` 参数中。缺失前置变量且无默认值的信号标记为 `BLOCKED`
   （`reason=dependency_blocked`），不执行也不得判定为 `NOT_MATCHED`；
4. **依赖拓扑排序**：在线 CDD 内核的 `ActiveDiagnosticScheduler` 按依赖拓扑
   排序执行信号评估。离线模式下可跳过调度器（证据已全量可用），但必须维持
   produces→requires 的拓扑顺序以确保变量在消费前已产出；
5. **变量池快照**：Diagnosis Run 结束后将共享 `VariablePool` 最终状态写入
   Run Manifest 作为审计记录。

### 验收标准

- AC-V01：包含 `produces` 声明的 QKV 信号成功将变量写入离线变量池；
- AC-V02：消费者信号的 `requires` 变量从变量池正确读取并注入 Collector 参数；
- AC-V03：前置变量缺失时 CDD 内部结果标记为 `BLOCKED`，不得当作普通 `UNKNOWN` 或
  `NOT_MATCHED`；对外三态接口映射为 `UNKNOWN` 时必须保留 `reason=dependency_blocked`、
  缺失变量和预期生产者；
- AC-V04：同一 Diagnosis Run 的 Run Manifest 包含变量池最终状态快照。

## FR-026 QKV 前端信号离线数据来源适配【P0，V3.3 新增】

### 目标

QKV 生产者信号（alert/task/dialog）在离线模式下从证据包获取数据，而非实时查询
HCI API。

### 数据来源对照

| QKV 信号 | 在线数据来源 | 离线数据来源 | 证据包目录 |
|---------|------------|------------|----------|
| `qkv_alert` | 实时 `acli alert get` | 证据包中预采集的告警 JSON | `commands/` |
| `qkv_task` | 实时 `acli task get` | 证据包中预采集的任务 JSON | `commands/` |
| `qkv_dialog` | 实时 `acli log get` | 证据包中预采集的日志文件 | `logs/` |

### 功能要求

1. **QKV Collector 必要性继承**：被 Mandatory（必需）消费者依赖、且没有其他可信来源的
   QKV 生产者必须纳入 Collection Profile 的 `mandatory` 项；仅用于 Context（上下文）或
   Recommended（建议）证据的 QKV 不得无差别升级为 Mandatory；
2. **结构化数据保留**：QKV Collector 的输出需保留完整结构化数据（JSON 原始
   输出或完整日志文本），因为 `produces` 变量的取值依赖 JSON 路径或文本行列解析；
3. **日志路径适配**：`qkv_dialog` 的搜索路径（`/sf/log/today`、
   `/sf/log/today/vt`）需在客户侧采集时覆盖；如客户环境日志路径不同，
   Collection Profile 需提供条件采集规则；
4. **离线 Provider 查询适配**：`OfflineEvidenceProvider.query()` 对 QKV 信号
   的查询（alert/task 的 JSON 路径查询、dialog 的关键字搜索）需返回与在线
   `qkv_exec` 相同结构的产出数据。

### 验收标准

- AC-Q01：两个首发场景的 Collection Profile 中 QKV Collector 为 `mandatory`；
- AC-Q02：离线 Provider 对 QKV 信号的查询结果与在线 `qkv_exec` 返回结构一致；
- AC-Q03：QKV produce 变量成功写入离线变量池并被下游 QFK 信号消费。

## 8. API 设计

> P0 新建独立 `diagnosis-service`（诊断服务）和隔离 `diagnosis-worker`（诊断工作进程），不把不可信大文件入口部署到 `kb-service`。API 使用独立诊断领域前缀，不使用 `/api/admin/` 作为客户接口。API Gateway 只代理控制面请求，大文件经预签名地址直传对象存储。
>
> 服务边界：诊断领域共享契约先在 `backend/shared/` 定义，文件模型命名为 `DiagnosticEvidenceBundle`，避免与现有 Prompt `EvidenceBundle` 冲突。服务间接口变更遵循 G-4 三步法（先向后兼容新增，再更新调用方）。与 `case-service`（工单服务）、`conversation-service`（对话服务，可选集成）的调用统一继承 `InternalHTTPClient` 并显式 `raise_for_status()`。
>
> 所有创建、完成、审核、发布、重试和删除接口支持 `Idempotency-Key`；并发更新使用资源版本号或 `If-Match`，错误响应统一包含 `code / message / trace_id / retryable / details`。
>
> 现有 `conversation-service` 的 `diagnostic_item` 用于在线会话中的假设、验证、根因和方案记录，可复用其展示和证据关联思路，但不作为 DiagnosisRun 或 DiagnosisReport 的权威存储。

当前 API Gateway（接口网关）已按白名单开放 `/api/diagnosis-sessions/**`、
`/api/internal/collection-profiles/**`、`/api/internal/collectors/**`、
`/api/internal/offline-signal-mappings/**`（离线信号映射）和诊断内部任务路径，
控制面请求体限制为 1 MiB。开发模式校验 `INTERNAL_API_TOKEN`（内部接口令牌）及
`X-Tenant-ID / X-Actor-ID`；正式模式只透传 Bearer JWT（承载式身份令牌），由
Diagnosis Service 使用 OIDC（开放身份连接）公钥验签并从签名 Claim（声明）读取
租户、客户、用户和角色，浏览器身份头会被丢弃。DiagnosticEvidenceBundle
（诊断证据包）分片数据面不加入网关代理。
客户和管理前端通过宿主登录层提供的
`window.__HCI_AUTH__.getAccessToken()`（获取短期访问令牌）动态读取 OIDC Access
Token（开放身份连接访问令牌）；令牌不写入 `localStorage`（浏览器本地存储），
生产构建不打包 `VITE_INTERNAL_API_TOKEN`（内部接口令牌）。本地开发模式仍可显式
配置开发令牌。宿主尚未完成登录或令牌过期时，请求不携带伪造身份并由网关默认拒绝。
Collector Artifact（采集器制品）签名私钥通过 Diagnosis Service 专用 Secret
（密钥对象）注入，不得放入所有后端服务共享的 Secret。

### 8.4.1 创建上传会话

```http

```

请求字段：

- `file_name`；

UI（客户界面）或 Admin UI（管理界面）Origin（来源）发起同源上传；本地 UI Nginx
（反向代理）关闭请求缓冲，生产 Ingress（入口）配置更长路径优先级，二者均绕过 API
Gateway（接口网关），将不超过 64 MiB 的单个分片直接流式转发到
Diagnosis Service（诊断服务）。本地 Customer UI 的浏览器请求因此解析为
`http://localhost:3001/api/direct/diagnosis-uploads/...`，不得直接依赖内部服务端口 `18008`。

只有直传地址配置为独立上传域名或外部对象存储时，Diagnosis Service 才需要响应可信 UI
Origin 的 CORS（跨来源资源共享）`OPTIONS`（预检）请求。允许来源必须由
`DIAGNOSIS_ALLOWED_ORIGINS` 显式配置，禁止使用 `*`；只允许 `PUT / OPTIONS` 方法，以及
`Content-Type`、`X-Upload-Token`、`X-Part-SHA256`、`traceparent` 和 `tracestate` 请求头。

```http

```

- 会话列表按租户隔离，支持 Session ID（会话标识）、工单、客户、状态和负责人查询；
- 重试只允许处理 `failed`（失败）且未达到最大次数的技术失败任务，`rejected`
  （安全拒绝）包必须在隔离区处置，不得直接重试；
- 安全事件接口只返回失败码、摘要、哈希、大小和 Security Results（安全结果），不得返回
  证据正文或对象存储位置；
- 终止会话必须停止未完成上传和待执行任务；
- 精简 P0 默认页面只使用会话、转派、重试、终止、报告审核和安全事件接口；
- Profile（采集画像）、Trust Store（信任库）、Revocation List（吊销清单）、治理和
  审计聚合接口作为后续版本兼容能力保留。

工具执行语义统一来自 Shared Acquisition Compiler（共享采集编译器）：

- Tool Registry（工具注册表）管理页维护能力启停、风险等级、版本、编译器标识和由根共享
  Schema 生成或校验的 `parameters_schema`（参数模式）；
- KBD 同步禁止使用 Diagnosis Service（诊断服务）内置的第二套命令目录；编译器不存在、
  KBD 必需参数无法解析、运行能力未验证或工具不是只读时阻断；
- `qfk_log`（后端日志信号）的 Catalog（能力目录）、候选路径、探测状态和最终 `acli log get`
  参数必须与当前 Agent Resolution Runtime（解析运行时）和 Handler（处理器）一致，不得回退为
  `journalctl` 或自造静态模板；
- `usage_template`（使用模板）只适用于能够静态表达的普通 ACLI 插件工具；QKV/QFK 不得因模板
  为空而在已有共享编译器能力时被判定为不可用；
- KBD 派生参数必须从 Collection Profile（采集画像）传递并冻结到 Collection Plan Item
  （采集计划项），签名制品使用该快照渲染命令，调用方不得临时覆盖；
- Tool 或 Execution Contract Revision（执行契约修订）变化时，Incremental Sync（增量同步）
  必须自动发现并重算受影响场景；全量同步仅用于首次基线或主动对账；
- 待人工复核且契约不完整的 KBD 信号跳过并显示 Warning（警告），不得生成猜测命令；已经
  确认的信号若仍缺少必需参数则阻断同步发布，并返回 KBD ID、案例号和 Signal ID（信号标识）。

同步与版本验收要求：

- Sync Batch（同步批次）同时保存 KBD/Tool 起止游标、两类来源修订及 Checksum（校验和）；
- 同步生成的 Collector 和 Collection Profile 必须标记 `managed_by=kbd_sync`，管理 API 和 Admin UI
  均禁止对它们单项编辑、审批和禁用；
- Rollback（回滚）必须同时恢复 Active Revision（生效修订）、事实表、治理归属、来源元数据和双游标；
  Rollback 不得改写上游 KBD/Tool 修订；上游未修正时，下次增量预检必须再次呈现该变更；
- Collection Profile 发布时冻结 Collector 依赖修订，Collection Plan Item（采集计划项）保存
  `collector_revision/collector_version/collector_checksum`（采集器修订/版本/校验和），Artifact（制品）
  严格按该修订生成；
- `database/seeds/03_qkv_qfk_tools.sql` 仅负责首次部署的 Tool Capability Bootstrap（工具能力引导），
  冲突时不覆盖管理员配置；不得存在独立的离线采集规范种子。

## 11. 技术风险与缓解措施

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| KBD 采集意图、Tool Registry 和 QFK Handler 契约不一致 | 无法安全生成采集器或在线/离线执行不同命令 | 由 Shared Acquisition Compiler 统一编译并冻结 Execution Contract Revision；不兼容项阻断发布 |
| Collection Profile 证据覆盖不足 | 完整率低、补采多 | 使用历史工单和专家评审建立首批 Profile |
| 静态证据无法覆盖偶发性能问题 | 无法确认根因 | 不纳入 P0 正式承诺，P3 建故障黑匣子 |
| 大包解压耗尽资源 | 平台不稳定 | 异步 Worker、流式读取、任务配额和隔离目录 |
| UNKNOWN 比例过高 | 诊断命中率低 | 按场景优化 Profile，统计高频缺失证据 |
| Agent 将 KBD 候选当根因 | 错误结论 | 分级报告、证据规则和工程师审核 |
| 客户不接受原始数据上传 | 无法诊断 | 采集预览、脱敏、加密、最小采集和删除能力 |
| 证据不足无法判断 | 继续依赖远程 | 明确缺失项，转工程师人工补充、专家或远程兜底 |
| 规则更新导致历史结果变化 | 审计不一致 | 冻结完整 KBD/Signal、映射、Profile、Collector、执行契约和诊断算法快照，运行时禁止回读实时表 |
| 签名密钥泄露 | 采集器可信性失效 | HSM/密钥管理、轮换、吊销和审计 |
| 当前客户身份仅为弱标识 | 越权和跨租户风险 | P0 接入正式身份，服务端解析租户和角色并执行对象级授权 |
| 文件领域对象与现有 EvidenceBundle 重名 | 模型和导入语义混乱 | 文件对象统一命名 DiagnosticEvidenceBundle，现有对象后续改名 PromptEvidenceBundle |
| 大文件经网关或 Web 服务转发 | 超时、内存和磁盘耗尽 | 上传会话 + 对象存储直传 + 隔离 Worker |
| 当前 Fact 更新覆盖历史值 | 无法满足不可变审计 | 新建只追加 EvidenceItem，Fact 仅作为可重建推理投影 |
| 仓库存在两份同名 `shared` 包 | Compose 与生产镜像行为不一致，甚至启动失败 | P0 删除服务内副本，只允许根目录 `backend/shared`，增加生产镜像导入测试 |
| 在线与离线分别解释 QFK acquire | 同一 Signal 采到不同证据并产生不同结论 | 使用同一 Shared Acquisition Compiler、Provider 契约和跨模式语义指纹回归 |

## 13. 最终产品定义

> 离线诊断模式是面向 HCI 和 VDI 售后场景的异步故障证据诊断系统。精简 P0 通过
> 安全 Collector（安全采集器）、签名采集工具、标准 DiagnosticEvidenceBundle
> （诊断证据包）、证据完整性、UNKNOWN（未知）、分级报告和工程师审核，在不连接客户
> 环境的情况下完成两个首发 HCI 场景的故障域定位与处置指导。证据不足时明确转工程师
> 人工补充；自动补采、复杂治理和更多场景在真实案例验证后逐步开放。
