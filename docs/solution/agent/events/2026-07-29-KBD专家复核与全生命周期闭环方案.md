# KBD 轻治理、自动化优先的知识生产消费闭环方案

## 一、结论

HTP 的目标不是建设一个复杂的人工审核和流程管理系统，而是把 7000+ Support 案例逐步转化为 Agent 能稳定理解、验证和执行的知识。

Human-in-the-loop 在当前阶段是模型和平台尚不成熟时的质量兜底，不是系统永久中心。方案采用以下总原则：

> 自动化优先、单专家兜底、复用现有平台、最小版本化、能力代码化、异常才人工介入。

目标闭环为：

```text
Support Source
→ LLM Proposal Revision
→ 自动 Validation
→ 当前阶段：单专家确认或修改
→ Expert Revision
→ 现有 Dynamic Resource Revision / Active
→ Agent 消费与运行反馈
→ LLM 评估、优化与新 Proposal
```

未来达到质量门槛的低风险知识可以由自动策略批准，专家只处理低置信、能力缺口、高风险和运行 Bad Case：

```text
自动 Validation
→ release policy
   ├─ 高置信、低风险、历史评估达标 → 自动发布 + 抽样
   └─ 低置信/新能力/异常/高风险   → 单专家确认
```

本方案明确取消或暂缓：

- 不新建第二套 Proposal 专家复核系统；
- 不建设双审、禁止自批和会签；
- 不把 `kbd_entry` 立即降为纯 projection；
- 不新增十几张 Source/Bundle/Approval/Release/Event 治理表；
- 不建设 Catalog v0→Registry v1 的长阶段；
- 不把技术步骤暴露成多个人工步骤；
- 不把专家审核设为永久唯一发布权威。

## 二、事实口径与当前基线

截至 2026-07-29，必须维持以下精确口径：

```text
126/126 真实来源完整；
122 条是自动 LLM Proposal；
4 条是 engineering Contract fixture；
4 条只完成 Schema、QFK Handler Build 和 outcome-level Decision Replay；
仅 KBD27123 的全部 QFK 路径通过当前 ToolSemanticValidator；
完整 Evidence/Execution Replay 尚未完成；
0/126 Expert Gold；
0/126 完成正式业务专家批准。
```

工程测试、Schema 通过、Handler 能构建命令，都不能被表述为业务专家 Gold 或客户现场可执行。

Support Cookie、Token 和会话信息不得进入仓库、日志、文档或配置。

## 三、第一性原理

### 3.1 知识闭环只需要解决四类问题

1. 模型生成了什么，必须保留，不能被专家修改覆盖；
2. 专家确认了什么，必须可定位、可持续维护；
3. Agent 当前消费哪个版本，必须稳定、明确、可回滚；
4. KBD 声明的动作在 Agent 侧必须有确定的执行语义。

工作台、双审、Registry、Approval Set、Event Sourcing 都只是可能的实现手段，不是目标。

### 3.2 永久技术不变量

无论未来是否取消人工审核，都必须保留：

- 原始模型 Proposal 不被覆盖；
- Expert Revision 与 Proposal 可对比；
- 已发布版本不可被普通保存静默改变；
- 保存专家草稿不触发 Agent 生效；
- 发布、撤回、回滚与 Agent active 状态一致；
- Agent 使用可定位到 exact runtime revision；
- 未支持、错误、截断、不完整证据 fail closed；
- 客户侧执行经过参数、权限、超时和安全边界；
- 线上 Bad Case 能回溯到 Source、Proposal、Expert、Capability 和运行 revision。

### 3.3 当前阶段策略

- 所有 KBD 默认单专家审核；
- 同一专家可以修改、确认并发布；
- UI 保持一个主动作“完成审核并发布”；
- 系统后台自动完成保存、校验、revision、active、检索和审计；
- 未修改且校验通过的案例后续支持批量确认；
- 能力缺口进入普通工程迭代，不建设审批型能力需求系统。

### 3.4 当前不建设

- 独立第二套审核应用；
- 双审队列、禁止自批、多人 Gold Set；
- 全量 CQRS/Event Sourcing；
- 十几张生命周期治理表；
- Capability Registry 数据库；
- 多 channel active pointer；
- 平台内复杂的能力需求审批流；
- 任意 Shell 作为生产 Agent 兜底。

## 四、当前代码审计结论

### 4.1 现有 KBD 审核入口可以增强

现有路由 `/knowledge/kbd-review` 已指向 `KbdReviewView.vue`。页面已有：

- 列表、筛选和分类统计；
- KBD 详情、章节编辑和分类编辑；
- Vision 结果、Observed Facts、Inferences 和 provenance 展示；
- QKV/QFK 分组展示；
- Signal 参数、match、produces/requires 和安全管道转换编辑；
- 重新分类、重新识图、重新抽取；
- 审核通过并发布、拒绝、重新发布和退回草稿。

缺口是版本和交互语义，不是缺少页面。因此直接增强现有入口，必要时只进行内部组件化。

### 4.2 当前 `kbd_entry` 是单行可变状态

`kbd_entry` 同时保存章节、Vision、Signal、分类、检索字段、审核和发布状态。模型重跑、专家修改和发布都可能覆盖同一行，无法长期保存多次 Proposal 和专家维护版本。

但这不意味着需要从零建设完整版本系统。项目已存在：

- `dynamic_resource_revision`：不可变运行时快照；
- `dynamic_resource_active`：当前 active 指针；
- `dynamic_resource_usage_audit`：Agent 使用 revision 审计。

缺口只剩 Proposal/Expert 工作版本的 append-only 保存。

### 4.3 发布语义审计发现的两个真实缺陷与本轮止血

1. 原实现编辑已发布 `kbd_entry` 时会调用 `ensure_published()`，普通保存可能立即创建 revision 并切 active；
2. 原实现“退回草稿”只修改 `kbd_entry.status`，没有撤销 `dynamic_resource_active`，Admin 状态和 Agent 实际状态可能不一致。

2026-07-30 已完成最终维护形态：已发布 KBD 的普通 PATCH、Pipeline ingest、重新分类、重新识图和 Signal 抽取均受统一状态门禁保护，异步任务最终写回前会二次检查发布状态；专家可在原审核页创建独立 maintenance working，保存和放弃均不改变旧 active，只有显式“发布维护版”才在同一事务中更新兼容主记录、冻结批准 Expert Revision 并切换 `dynamic_resource_active`。不新增 Active 表。

### 4.4 专家界面信息收敛原则（2026-07-30 已实施）

专家主路径只展示同时满足以下条件的信息：

1. 专家能理解它与当前 KBD 的关系；
2. 专家能在当前页面采取明确动作；
3. 动作结果能立即保存并重新 Validation。

因此：

- `runtime_status=unknown` 不再作为逐 KBD 专家 warning；它进入 `platform_status`，不阻断内容审核，也不计入专家待办；
- 原始 generation/prompt SHA-256 不在主路径平铺，主路径只显示模型、未修改/人工修改/已过期和 Diff 数量，完整哈希进入“生成追溯详情”；
- Capability 已声明时不显示“运行待探测”标签；只有能力未声明且专家可以更换工具时才显示；
- 图片模型 provenance 进入折叠追溯详情，截图类型、可见文字、Observed Facts、Inferences 和语义描述保留直接编辑入口；
- 校验面板每条问题必须包含可读说明、位置和可执行动作；`qkv_dialog` 引用任务截图时可一键定位并建议切换 `qkv_task`；
- 已发布状态不显示不能执行的模型重跑操作；专家先创建维护工作稿，再编辑并显式发布。

这不是隐藏风险。平台状态仍以结构化数据保留给运维和开发，只是不把不可处理的工程状态伪装成专家任务。

### 4.5 当前工具管理不是可执行能力的单一事实源

Admin 工具管理当前能够：

- CRUD `tool_definition`；
- 编辑说明、调用模板、参数 JSON Schema、示例、风险级别和启用状态；
- 为 QKV/QFK 提供有限的 produces/matcher 表单；
- 保存时生成 `dynamic_resource_revision`。

但可执行语义仍分散在：

- `backend/shared/schemas/acquirer_args.py` 的参数契约；
- `backend/shared/schemas/signals/*.json`；
- Agent `HandlerRegistry`；
- QKV/QFK runtime model；
- `ToolSemanticValidator`；
- CDD compiler 和 matcher/extractor。

因此，在 Admin 新增或修改一条 `tool_definition` 并不自动获得新的 Agent Handler，也不能证明共享 Schema、Validator 和 runtime 一致。

结论：现有工具管理对普通 ReAct 工具说明较易用，但对 KBD Capability 的通用性、扩展性和端到端一致性不足，需要升级为“能力状态展示和配置入口”，不能把 executable semantics 当作可热编辑数据。本轮已完成最小运行发现闭环：Agent 内部端点按当前进程真实导入状态报告 Handler、Validator、Terminal Bridge Executor 和 usable；Gateway 将结果按 `capability_id` 合并到 shared Descriptor。Agent 不可达时仍返回参数契约并诚实保留 `unknown`，不得把数据库 Tool Definition 冒充可执行实现。

## 五、目标数据模型：只增加最小 revision

### 5.1 `kbd_entry` 保持主记录和兼容入口

当前阶段不删除、不重写、不把 `kbd_entry` 立即降为纯 projection。它继续承担：

- KBD identity 与 `support_id`；
- Admin 列表和当前详情；
- 现有检索兼容；
- 当前工作内容的兼容列；
- 当前状态和统计字段。

### 5.2 新增唯一核心表 `kbd_revision`

```text
kbd_revision
- id
- kbd_entry_id
- revision_no
- revision_type: proposal | expert
- parent_revision_id
- payload_json
- checksum
- generation_metadata
- validation_summary
- actor_id
- actor_type: llm | expert | migration | system
- trace_id
- created_at
```

约束：

- revision append-only；
- 同一 KBD revision_no 单调递增；
- 工作稿自动保存默认按 type+checksum 幂等复用，避免无意义版本；
- 正式批准即使 payload 与工作稿完全相同，也冻结一条独立 Expert Revision，保留批准门禁、审核备注和 parent；
- Proposal 与 Expert 使用同一个 payload schema；
- Expert Revision 指向其所基于的 Proposal/Expert parent；
- 原始 LLM 标准化结果长期保留；
- raw response 如需保留，使用受限对象存储引用和 hash，不在普通页面展示敏感内容。

`kbd_entry` 只增加少量指针/并发字段：

```text
latest_proposal_revision_id
working_revision_id
lock_version
```

当前 active 继续由 `dynamic_resource_active` 表达，不新增 `kbd_active_release`。

### 5.3 为什么不能只加 `llm_json/expert_json`

固定两列只能表达一轮模型和一轮专家，不能表达：

- 同模型重试；
- 模型升级 Challenger；
- 专家多次维护；
- 发布后再次优化；
- 历史对比和回滚；
- 按模型、Prompt、字段统计差异。

把无限历史塞进 `kbd_entry.metadata` 数组会反复重写大行、并发覆盖、难索引、难分页、难回滚。一个固定行不适合表达数量不确定的不可变历史，因此一张 append-only revision 表是长期目标下的最小必要复杂度。

### 5.4 工作稿、发布稿和运行时的关系

```text
LLM Proposal Revision（只读）
    ↓ 专家打开
Expert Working Revision（可持续保存）
    ↓ 完成审核并发布
Dynamic Resource Revision（不可变运行时快照）
    ↓ activate
Dynamic Resource Active
```

- 保存工作稿：不创建 active，不更新 embedding，不改变 Agent；
- 完成审核并发布：后台校验后创建 Expert Revision 和 runtime revision，再切 active；
- 发布使用 `lock_version` 做乐观并发保护；若生成 embedding 期间知识发生变化，则返回 409 且不发布旧内容；
- 已发布维护：先创建新的 Working Revision，旧 active 持续服务；
- 撤回：明确删除/停用现有 active pointer，不用 `status=draft` 冒充下线；
- 回滚：把 active 指回仍兼容的历史 runtime revision，不修改历史行。

## 六、专家审核体验

### 6.1 复用现有页面

不新建菜单、应用、登录和第二套队列。增强 `/knowledge/kbd-review`，将大文件逐步拆为内部组件：

- `KbdReviewList`；
- `KbdReviewDetail`；
- `ProposalExpertDiff`；
- `ImageEvidenceEditor`；
- `SignalEditor`；
- `ValidationSummary`。

### 6.2 专家必须能回答三个问题

打开案例后，平台必须让专家在不理解内部架构的前提下知道：

1. 哪里有问题：按字段显示错误、警告、低置信和模型/专家差异；
2. 如何修改：所有 LLM 产物就地使用类型化编辑器，不要求手改整段 JSON；
3. 修改是否有效：保存前实时校验，发布后可以立即按 exact revision 预览/验证。

### 6.3 页面信息架构

顶部：

- Support ID、标题、分类、当前状态；
- 原始案例入口；
- 当前 active revision；
- 自动校验总览：只统计专家能通过当前 KBD 编辑处理的错误和警告；平台部署状态不计入专家待办。

主区：

- “专家最终稿”为默认视图；
- “模型原稿”只读可折叠；
- “当前生效版”只读可折叠；
- 修改字段显示 Diff；
- 只显示有问题的字段过滤器。

可编辑内容：

- 标题和八大章节；
- 分类与 AI 分类理由；
- Vision 类型、OCR/可见文字、Observed Facts、Inferences、描述和质量状态；
- Signal 新增、删除、复制、排序；
- capability、args、match、extract、produces、requires、role、provenance；
- 声明式阈值和比较条件；
- manual_only/unsupported 等自动化状态。

底部操作：

```text
保存当前修改
完成审核并发布（draft 的主按钮）
发布维护版（published maintenance working 的主按钮）
拒绝/暂不处理（次要动作）
```

后台可以依次执行 revision、Validation、runtime snapshot、active 和索引，但专家只完成一个主动作。

### 6.4 即时验证

“立马生效验证”必须区分验证和正式生产 active：

- 保存后立即运行静态 Validation；
- 提供“验证当前草稿”动作；当前已实现无副作用静态 Schema/Capability Contract Validation，真实 Agent compile/replay 尚未接通，不得把静态通过写成现场可执行通过；
- Validation 报错定位到具体字段和 Signal；
- 通过后点击“完成审核并发布”，同一请求完成 active 切换；
- 页面刷新并显示新的 runtime revision/checksum；
- 提供 Agent 侧 dry-run/受控环境验证入口时，必须明确目标、输入变量和运行环境；
- 修改后不能要求专家等待另一批次发布或去其他页面找版本。

常规路径：

```text
打开 → 确认/修改 → 完成审核并发布
```

有错误路径：

```text
打开 → 点击问题定位 → 就地修改 → 实时校验 → 发布 → 立即查看新 revision/验证结果
```

已发布维护路径：

```text
打开 Agent 生效版
→ 创建维护工作稿
→ 就地修改并保存（Agent 仍使用旧 active）
→ 静态 Validation
→ 显式发布维护版
→ 同事务切换 runtime active；失败时旧 active 不变
```

### 6.5 专家视图与平台视图分层

同一事实可以保留，但不应全部平铺给专家：

| 信息 | 专家主路径 | 追溯/平台路径 | 原因 |
|---|---|---|---|
| 必填字段缺失、Signal Schema 错误 | 展示，并提供定位/编辑 | 同步保留 | 专家能理解并处理 |
| `qkv_dialog` 引用任务截图 | 展示“优先改为 qkv_task”，可一键定位 | 同步保留 | 属于知识裁决 |
| Capability 未声明 | 展示“更换采集类型” | 记录能力缺口 | 专家可先修知识，也可交给开发补能力 |
| Runtime unknown、Handler/Executor 部署状态 | 不进入专家问题数 | `/api/v1/kbd/capabilities` 平台诊断 | 专家无法通过修改当前 KBD 解决 |
| generation/model/prompt 完整 SHA | 仅显示模型与人工修改状态 | “生成追溯详情”折叠展示 | 审核无需阅读哈希，评估仍需保留 |
| 图片 SHA、模型 provenance | 不平铺 | “识图追溯详情”折叠展示 | 不影响当前事实编辑 |

这条分层规则是产品契约：任何新增信息在进入专家主路径前，必须同时回答“专家看得懂吗”和“专家现在能处理吗”。任一答案为否，就进入追溯或平台诊断路径。

## 七、知识无法消费时的快速 Capability 闭环

### 7.1 问题分类

KBD 无法消费不能统一归因于“模型错了”，必须机械分类：

1. `knowledge_error`：案例/模型知识错误，现有工具已能表达；
2. `mapping_error`：有能力但 Signal 参数或变量映射错误；
3. `capability_missing`：平台没有所需 typed action/operator；
4. `capability_incompatible`：能力存在但目标环境/版本不支持；
5. `runtime_error`：工具链、权限、连接或现场状态异常；
6. `evidence_incomplete`：输出截断、缺失或不可判定。

只有第 3 类进入新能力开发，避免把数据错误误当工具缺口。

### 7.2 单一 Capability Descriptor

当前不建设 Registry 数据库。从代码中自动生成只读 Capability Descriptor：

```json
{
  "capability_id": "qfk_system",
  "version": "1",
  "kind": "consumer",
  "args_schema": {},
  "output_schema": {},
  "supported_matchers": ["keyword", "exists"],
  "handler_status": "implemented",
  "semantic_validator_status": "implemented",
  "runtime_status": "available",
  "safety": {"read_only": true},
  "source": "code"
}
```

来源统一为现有代码：

- shared args Schema；
- signal/output Schema；
- Agent HandlerRegistry；
- semantic validator；
- matcher/extractor 支持；
- 必要的 runtime/deployment 状态。

Prompt、Pipeline、Admin、Compiler 和测试读取同一 descriptor。数据库 `tool_definition` 可继续保存人类说明、示例和启用配置，但不能单独宣称 executable capability 已实现。

### 7.3 Admin UI 中的快速闭环

审核页对每条 Signal 显示：

- 可用：绿色，可直接编辑和验证；
- 参数不合法：红色，定位字段；
- 能力未实现：橙色，说明缺少 handler/operator；
- 环境不兼容：橙色，说明目标版本；
- 仅人工：灰色，不进入自动诊断。

专家发现缺口时点击“记录能力缺口”，系统自动携带：

- KBD ID、revision 和 Signal ID；
- 原始知识片段和截图来源；
- 诊断意图；
- 期望输入、输出和判断；
- 当前最接近 capability；
- Validation 错误码；
- 受影响案例数量（可异步统计）。

第一阶段不建设能力需求状态机，可生成普通工程 backlog/结构化 JSON，并支持复制或跳转到工具管理。避免专家重复描述技术细节。

### 7.4 开发者增加能力的最短路径

例如需要“统计目录 A 下文件数量并判断是否超过阈值”：

```text
1. 定义 typed action：filesystem.count_entries
2. 定义 args：path/filter/max_entries/timeout
3. 定义 output：count/complete/truncated/error
4. 实现只读 handler
5. 补充权限、超时、截断和边界测试
6. Capability Descriptor 自动出现
7. 原阻塞 Proposal 自动重新 Validation
8. 专家在原页面验证并发布
```

这是一条普通代码迭代，不需要 Catalog/Registry 审批。

### 7.5 工具管理如何演进

现有 ToolManage 的定位调整为：

- 展示工具和 Capability 的综合状态；
- 编辑人类说明、示例、展示名和允许的配置；
- 只读展示代码声明的 args/output/schema/handler/safety；
- 明确区分 `configured`、`implemented`、`deployed`、`usable`；
- 不能通过只改数据库 Schema 伪造 Handler 已存在；
- 新 Capability 提供模板、文档和测试入口，实际 executable semantics 仍由代码发布。

短期验收标准：

- 专家从 KBD Signal 一键跳到对应 capability；
- 页面能明确回答“为什么不可执行”；
- 开发完成后不需要专家重新手输 Signal；
- descriptor 更新后原 KBD 可立即重验；
- 缺口可按 capability 和受影响 KBD 聚合。

### 7.6 为什么生产不能用自由 Shell 兜底

KBD 是数据，Handler 是代码。允许 LLM/Admin 热编辑任意 Shell 等于让知识数据获得客户侧任意代码执行能力，会破坏：

- 参数和权限边界；
- 可复现性；
- 输出结构；
- 超时和截断语义；
- 审核内容与实际执行的一致性；
- Prompt Injection 防线。

开发/测试环境可以由开发者显式使用受控 Shell 验证意图，但依赖实验 Shell 的 KBD 不进入客户侧生产 active。快速实验和生产安全通过环境隔离同时满足，不通过降低生产边界换取速度。

## 八、利用专家修改数据优化 LLM

### 8.1 专家修改不是一段 review_note，而是监督学习数据

每次审核应保留：

```text
Source Revision
LLM Proposal Revision
Expert Revision
字段级 Diff
Validation Before/After
模型、Prompt、参数和时间
Capability 状态
最终发布与运行结果
```

Proposal 和 Expert 使用同一个规范 payload schema，才能稳定计算差异。

### 8.2 稳定对齐单位

按以下层级生成训练/评估样本：

- KBD 级：是否可发布、主要错误类型；
- 字段级：分类、章节、Vision、Signal、Contract；
- 图片级：截图类型、Observed Facts、Inference；
- Signal 级：保留、新增、删除、修改；
- 属性级：tool、args、match、extract、role、provenance。

Signal 必须使用稳定 ID；数组下标只用于展示，不能作为跨版本身份。无法直接 ID 对齐时，使用来源引用、工具、角色和语义相似度辅助匹配，并标记对齐置信度。

### 8.3 结构化 Diff

对每个字段记录：

```text
operation: keep | add | delete | replace
path: /signals/sig_x/acquire/args/command
before
after
reason_code
expert_note（可选）
```

reason_code 优先自动推断并允许专家快速修正：

- source_missed；
- screenshot_misread；
- fact_inference_confused；
- wrong_category；
- wrong_capability；
- invalid_argument；
- missing_signal；
- redundant_signal；
- unsafe_command；
- unsupported_semantics；
- threshold_or_match_error；
- wording_only。

不要求专家为每个字符修改填写原因，只对删除关键信号、改变事实、改变执行语义等重要修改提示选择原因。

### 8.4 三类优化输出

1. **评估集**：Expert Revision 成为冻结的回归期望，评估新模型/Prompt；
2. **Prompt/Schema 优化**：按错误聚类修正规则、示例和校验器；
3. **训练数据**：经脱敏和质量筛选后形成 Source→Expert、Proposal→Expert preference/SFT 样本。

不要把所有专家修改直接用于微调。先区分：

- 知识错误；
- 能力缺口；
- Schema 不足；
- UI 误导；
- 纯措辞调整。

能力缺口不能通过训练 LLM“学会”一个平台不存在的工具；它应进入 Capability 开发。

### 8.5 Champion/Challenger

新模型或 Prompt 只对冻结 Source 产生 Challenger Proposal，不覆盖 Expert 或 Active：

```text
Frozen Source + Gold Expert
→ Champion Proposal
→ Challenger Proposal
→ 字段级质量、稳定性、可执行性比较
→ 达标后更新生成配置
```

核心指标分层统计：

- 分类准确率；
- Vision Observed Facts precision/recall；
- Inference 误当事实率；
- Signal coverage；
- Signal precision；
- args Schema pass；
- semantic validator pass；
- expert edit distance；
- no-change approval rate；
- capability missing rate；
- execution/evidence replay pass；
- 线上 UNKNOWN/ERROR/rollback/Bad Case 率。

不能只看整体平均值，必须按产品、分类、截图类型、Signal 类型和 Capability 分层，避免强势类别掩盖弱势类别。

### 8.6 主动学习和专家负担下降

根据以下优先级安排专家：

1. 模型分歧；
2. 低置信；
3. 新 Capability；
4. 高风险执行；
5. 线上 Bad Case；
6. 代表性抽样；
7. 高置信重复样本批量确认。

随着 no-change approval rate、replay pass 和线上效果提升，逐步从全量审核演进到抽样和异常审核。

## 九、单专家审核和未来自动发布

### 9.1 当前策略

```text
专家编辑
→ 点击“完成审核并发布”
→ 自动 Validation
→ 通过则创建 Expert Revision 和 runtime revision
→ 切 active
```

不启用：

- 双审；
- 禁止自批；
- 多人会签；
- 审批策略管理页；
- Gold Approval Set。

目标态审核身份必须从可信登录态取得，后端不能信任前端任意提交 reviewer_id。当前仓库没有 Admin SSO/认证上下文，因此本轮移除了固定 `currentUser=1`，首次发布时显式要求填写审核人 ID，并在 Revision 中标记 `identity_status=unverified_body_reviewer_id`。这批记录可用于功能验证和差异分析，但不得计为认证 Expert Gold；待平台提供可信 SSO/认证头后再切换为零额外操作的登录身份。

### 9.2 未来策略

发布资格：

```text
publishable
= schema_pass
∧ semantic_pass
∧ capability_supported
∧ safety_pass
∧ release_policy_pass
```

`release_policy_pass` 当前为单专家确认，未来可为自动策略。原始 LLM 输出不能无门槛直发，但 Human 也不是永久唯一权威。

## 十、自动化成熟度路线

### M0：全量单专家

- 当前 122 Proposal 全部单专家；
- 收集结构化 Diff；
- 建立首批 Expert Gold；
- 不双审。

### M1：差异优先和批量确认

- UI 只突出错误、低置信和 Diff；
- 未修改且 Validation 通过的案例批量确认；
- 按类别抽样。

### M2：高置信低风险自动发布

- 在 Expert Gold 和运行数据上达到门槛；
- 低风险类别自动发布并抽样；
- 新能力、低置信和异常仍由专家确认。

### M3：专家只处理异常

- 模型分歧；
- Capability 缺口；
- 高风险；
- 线上 Bad Case；
- 漂移和质量退化。

自动发布门槛不在没有 Gold 数据时凭空设定。先完成 122 条专家基线，再按真实分布制定分层阈值和置信区间。

## 十一、最小实施路线

采用小型纵向切片，不再执行长 P0→P4 治理建设：

### L0：文档和当前行为止血

- 固化轻治理决策；
- 禁止已发布普通编辑隐式切 active；
- 撤回同步处理现有 active；
- 修复真实审核身份和 review note；
- 保持 126 条事实口径。

### L1：最小 revision

- 新增 `kbd_revision` 和少量 `kbd_entry` 指针；
- 对现有 Proposal 做初始快照或按访问懒初始化；
- 专家保存产生 working/expert revision；
- 模型重跑产生新 Proposal，不覆盖 Expert/Active。

### L2：现有页面增强

- Proposal/Expert/Active Diff；
- 问题导航；
- 类型化全字段编辑；
- 实时 Validation；
- 一个“完成审核并发布”主按钮；
- 发布后显示 exact runtime revision。

### L3：Capability 快速闭环

- 代码生成 Capability Descriptor；
- 审核页显示 supported/unsupported/incompatible；
- 结构化能力缺口；
- ToolManage 展示代码契约与实现状态；
- 完成一个真实能力如 `filesystem.count_entries` 的纵向验证。

### L4：LLM 改进闭环

- 字段/Signal 级 Diff 数据集；
- 错误分类和评估报表；
- Champion/Challenger；
- 主动学习；
- 达标类别逐步自动发布。

每个切片都必须贯通：

```text
生产 → 审核 → 发布 → Agent 消费 → 反馈
```

## 十二、验收标准

### 12.1 标准

- Proposal、Expert、Active 可定位；
- Agent exact revision 可追溯；
- 数据与 executable code 边界明确；
- Capability Schema/Handler/Validator 一致；
- fail closed 和生产安全不因简化而降低。

### 12.2 简单

- 只新增一张 KBD revision 核心表；
- 复用现有 dynamic resource 表；
- 不新建审核应用和审批系统；
- 不建设 Registry；
- 常规专家路径只有打开、确认/修改、发布。

### 12.3 易用

- 专家能看到哪里有问题；
- 专家能就地修改全部 LLM 内容；
- 错误定位到具体字段；
- 修改后立即 Validation；
- 发布后立即显示 active revision 和验证入口；
- Capability 缺口自动携带上下文，不让专家重新描述。

### 12.4 自动化

- 专家修改结构化进入评估数据；
- 新模型不覆盖 Gold/Active；
- 可按类型计算 no-change、precision、coverage 和 replay；
- 低风险知识未来可由自动策略发布；
- 专家队列随质量提升逐步缩小。

## 十三、已确认决策

1. 发布对象必须是通过 Validation 的明确 revision；批准来源当前为单专家，未来允许自动策略；
2. 复用并增强现有 `/knowledge/kbd-review`，不新建第二套工作台；
3. 当前全部单专家，允许修改后直接发布，不双审、不禁止自批；
4. Proposal、Expert 和运行时 revision 保留，敏感 raw response 脱敏隔离；
5. `kbd_entry` 保持主记录，新增唯一 `kbd_revision`，复用 dynamic resource；
6. 使用小型纵向切片，不建设长阶段治理门；
7. 使用代码生成 Capability Descriptor，不建设 Catalog→Registry；生产不开放自由 Shell；
8. 现有 active 不被迁移脚本静默改变，发布、撤回和回滚统一操作现有 dynamic active。
