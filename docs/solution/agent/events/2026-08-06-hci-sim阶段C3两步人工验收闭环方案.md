# hci-sim 阶段 C3 两步人工验收闭环方案

## 1. 架构

```text
Step 1: acceptance.sh → C1 capability API → Go synthetic compiler → Manifest/Lease → hci-sim 单副本
Step 2: Custom UI → terminal_bridge (auth_type=lease, execution_mode=sim-ssh) → SSH :2222 → exact RouteKey
```

`bootstrap` 是控制面适配器，不读取 KBD 编辑态，也不把数据库内容直接挂载进 Runtime。它只接受 C1 的 `resolved` 字段，并使用显式白名单把首个只读 `qkv_task` Signal 编译成合约级 synthetic route。Route 的输出为人工构造、脱敏、可重复 JSON。

## 2. Manifest 与 Lease

Manifest 绑定 `support_id/kbd_revision/kbd_checksum/tool_contract_revision/policy_revision`，variant 固定为 `positive-minimal`，Bundle digest 由 Manifest 语义内容计算；Runtime 启动时再次校验。Lease 使用 htp2 HMAC-SHA256，绑定 `test_run_id/scenario_id/support_id/kbd_revision/bundle_digest/variant/virtual_node/container/execution_mode`，15 分钟过期，4 会话、200 命令、4 KiB 输出配额。

## 3. Bridge/UI 适配

Terminal Bridge 已支持 `lease` 认证，并且只在完整 `htp2.* + sim-ssh` 上启用 simulation 标记。Custom UI 增加“仿真租约”认证选项和可选 TestRun ID，Lease 原样放入 SSH password，不添加真实 HCI 的密码后缀；普通 password/key 逻辑保持不变。无工单初始状态新增独立的“仿真租约连接（dev）”入口，避免把 synthetic Lease 误送入真实 HCI 环境采集流程。

Linux/K3s 联调必须显式启用 terminal_bridge Pod，并让 Customer UI runtime-config 指向同源 `/terminal-bridge` 或受控的 Linux Bridge 地址；runtime-config 为空时，前端会按桌面兼容逻辑连接浏览器所在机器的 `localhost:9999`，这不属于 Linux 三段链路。

## 4. 安全与失败策略

- 非白名单 KBD、C1 gap、过期/漂移 capability 直接失败。
- Runtime 对未发布 variant、命令近似匹配、shell 操作符和 host 猜测全部拒绝。
- Lease 只写入本地 `connection.json`（0600），脚本只输出路径和脱敏字段；应用日志、审计和 UI 持久化不得包含 token。
- hci-sim dev 验收使用持久化 host key，避免同一 `<host>:<port>` 每次重跑触发 Bridge `known_hosts` 指纹漂移；生产运行时不复用该验收 key。
- 当前脚本仅用于 dev 单副本人工闭环；生产需要 PostgreSQL CAS、对象存储、Artifact Gate、Scenario API 和多副本共享 Lease Store。
