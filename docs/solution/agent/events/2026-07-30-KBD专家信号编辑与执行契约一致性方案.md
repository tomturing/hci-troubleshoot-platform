# KBD 专家信号编辑与执行契约一致性方案

## 背景与需求

专家在已发布 KBD 的维护工作稿中删除关键信号时，KBD30880（现场误报为 30808）出现：

```text
signals_json 不符合 v2 契约：verification_contract.context 引用了不存在的 signal_id: sig_004
```

被删除的 `sig_004` 是“参照正常 GPU 主机的配置文件格式”。原文只是正常
`/sf/cfg/gpu_info.ini` 的说明示例；现场可能没有正常 GPU 主机，且当前 `HOST`
就是异常主机。它不应作为 `qfk_system` 的可执行检查。专家删除它是正确的。

本事件解决的不只是这个案例，而是专家必须可安全完成的新增、删除、复制、角色调整、
排序和保存：修改后立即得知是否可发布，发布前 Agent 绝不消费半编辑数据。

## 根因分析

同一“证据作用”原先有两份可变事实：

```text
signals[].role                                  专家编辑的必要/增强/排除/上下文
verification_contract.evidence_policy.<role>[]  Agent 按 signal_id 消费的分组
```

前端删除仅移除了 `signals[]` 元素；保留完整旧文档时没有同步删除 policy 中的
`sig_004`。后端拒绝保存是正确的：放行会让专家以为已删除，而 Agent Contract 仍
引用幽灵信号。问题是双事实来源和编辑保存实现，不是 `sig_004` 不能删除。

另外，原保存和发布共用“至少一个必要证据”的严格校验，使专家不能逐步完成编辑。

## 方案（WHAT）

### 1. 角色单一事实来源与执行投影

`signal.id + signal.role` 是专家可编辑的唯一角色事实来源。每次保存都由共享的
`reconcile_verification_contract()` 重建 Agent 的 `evidence_policy`：

- 只引用当前仍存活的稳定 signal ID；
- 每条信号只属于一个角色；
- 保留 `case_id`、`scope`、变量等 Contract 元数据；
- `minimum_should` 自动收敛到当前增强证据数量；
- 兼容缺失 `role` 的历史数据：优先从旧 policy 回填，否则保守地设为 `must`。

LLM 抽取路径也接入该归一化，不能再让 LLM Proposal 中的 policy 与 Signal 实际角色
漂移。

```text
专家编辑 signal.id / signal.role
          ↓  后端权威归一化（前端只做同规则即时预览）
verification_contract.evidence_policy
          ↓
Agent 编译与执行
```

### 2. 保存与发布分层

| 阶段 | 允许状态 | 结果 |
|---|---|---|
| 保存 Expert Working Draft | 结构、参数、matcher/produces、变量引用和 Contract 引用均合法；可暂时没有必要证据 | 只写 append-only Expert Working Revision，Agent active 不变 |
| 发布/维护版发布 | 在上述基础上，稳定 ID 唯一、至少一条必要证据、完整发布门禁通过 | 冻结 Expert Revision 并原子切换现有 Dynamic Resource Active |

这不是放宽生产安全：草稿可逐步编辑，生产仍严格 fail closed。删除最后一条必要证据
会出现“发布前请至少保留一条必要证据”的可操作提示，而不是 Schema 字段路径。

### 3. 专家界面交互

- 删除确认说明角色影响、是否会收敛增强证据门槛、原始正文/截图不会被删除；
- “上下文证据”明确标为“仍执行”，避免把它误解为纯文字说明；纯示例应保留在正文或
  图片 Evidence，不应创建为 QFK；
- 保存后立即运行当前专家稿静态检查；校验只返回专家能处理的中文提示和定位动作；
- 前端会先按角色重建 payload，后端仍为权威校验和 canonical 回写，不能绕过前端保存
  脏 Contract；
- 排序只改变展示/阅读次序，不改变稳定 ID 与 Contract 成员关系。

## 决策依据（WHY）

**为什么不让专家手工编辑 `evidence_policy`？** 这会要求专家理解 ID 数组、最小
门槛和运行时编译细节；并且所有增删改都需双处同步，必然重新产生悬空引用。派生数据
必须只有一个写入口。

**为什么不直接删除后端校验？** 校验是 Agent 的最后安全边界。去掉它会产生“UI 删除
成功、Agent 仍执行”的静默错误，风险高于显式 422。

**为什么不把 `context` 解释为非执行注释？** 只要它仍是 `signals[]` 中的 QFK，Agent
就会执行。说明性知识应在 KBD 原文/截图 Evidence；可执行上下文证据必须具有可获得的
目标、变量和判断语义。

**为什么不新建工作台或治理表？** 使用既有 KBD 审核页、`kbd_revision` 和
Dynamic Resource Active；本轮只新增无状态共享归一化模块，没有数据库迁移和审批流程。

## 影响范围

| 范围 | 变化 |
|---|---|
| `backend/shared/schemas` | 新增 Contract 重建与专家问题翻译；草稿/发布校验分层 |
| `kb-service` | maintenance 与 draft PATCH 均 canonicalize；LLM 抽取同规则；Validation 返回可处理问题 |
| Admin UI | 删除影响说明、前端即时投影、角色标签和发布问题定位 |
| Agent | 不改执行器接口；读取到的 Contract 不再含已删除或角色漂移的 Signal |
| 数据库 | 无新增表、字段或迁移；revision/active 语义不变 |

## 验收标准

- [x] KBD30880 型 `context sig_004` 删除后 policy 不再引用该 ID，`must/should` 保持正确；
- [x] 专家可暂时保存没有必要证据的工作稿；发布检查给出中文、可处理的修复动作；
- [x] 角色从 `context` 改为 `must` 后 Contract 同步移动且不重复；
- [x] 新增、复制、恢复、删除和排序均经过同一保存归一化；
- [x] 前端构建和后端定向回归通过；
- [ ] 在 dev Admin UI 以 KBD30880 完成人工删除→保存→检查→发布/放弃维护稿验证（部署后执行）。
