# hci-sim 阶段 E：产品级验证与规模化运营方案

## 背景与需求

阶段 D 证明可以通用地执行 TestRun，但不能凭少量成功 Run 推导仿真与真实环境等价、Fixture 能发现错误、100+ 场景隔离或系统可持续运营。阶段 E 建立产品声明所需的独立 Oracle、差分、Mutation、核心 KBD 认证、容量梯度、SLO 和变更治理。

需求见[阶段 E 需求](../../../requirement/events/2026-08-05-hci-sim阶段E产品级验证与规模化运营需求.md)。

## 方案（WHAT）

### 1. 产品声明门禁模型

```text
KBD testability
  + Bundle provenance/approval
  + real/sim differential
  + mutation sensitivity
  + variant correctness
  + 20-repeat stability
  + capacity/isolation
  + security/operations
  = validated KBD revision / product capability declaration
```

门禁绑定精确 KBD revision、Bundle digest、Tool/Policy/Compiler/Runtime/Agent revision 和证据时间窗。任一强制项缺失只能标为 `candidate`、`blocked` 或 `capability_gap`，不能显示为 validated。

### 2. Real/Sim 差分契约

真实和仿真必须创建两个独立 Run，由 `calibration_group_id` 关联；真实 Run 使用受控、只读、授权、限额的校准环境，绝不由 sim Run fallback 触发。

比较层：

| 层级 | 比较内容 |
|---|---|
| Command | tool/acquisition、规范化 argv、node/container、顺序。 |
| Transport | stdout/stderr shape、exit、chunk/timeout 可观察语义。 |
| Artifact | schema、字段、类型、提取变量和 hash/provenance。 |
| Matcher/Signal | matcher trace、true/false/unknown/error。 |
| Conclusion | Gate、evidence references、最终结论和解释。 |

差异策略是版本化配置：允许时间戳、随机 ID、批准的匿名化值和无语义空白差异；禁止缺行、字段/类型变化、stdout/stderr 改道、exit 差异、变量基数变化、Matcher/Signal/Conclusion 差异和证据断链。

比较器先结构化再比较，不用纯文本相似度替代契约。超阈值自动阻断认证并将相关 Bundle stale；误报只能通过有 owner、理由、截止日期和复核人的 waiver 处理。

### 3. Mutation Framework

Mutation 在编译后和端到端两个层级运行：

- Fixture mutation：关键字、大小写/近似词、阈值边界、stdout/stderr、host/node/container/path、producer 缺失/多值/类型、命令参数/顺序；
- Runtime fault：timeout、permission、disconnect、truncate、overload；
- Workflow mutation：Signal 顺序、依赖缺失、重复/迟到 exec-result、attempt 混入。

每个 mutation 都有“期望被哪一层捕获”的 oracle。指标：

```text
mutation_detection_rate = detected_non_equivalent_mutants / valid_non_equivalent_mutants
```

等价 mutation 由专家审查后从分母排除并保留理由。关键安全/结论 mutation 必须 100% 检出；总体阈值由试点数据确定后版本化，未定阈值前不得宣称达标。

### 4. 核心 KBD 选择和认证包

首批 10～20 个 KBD 采用分层抽样，而非只选容易通过者，至少覆盖：

- 不同 Tool/acquisition；
- regex、数值阈值、JSON/表格/多行等 Matcher；
- producer/consumer、多节点/容器和多 Signal Gate；
- positive/negative/near-miss/unknown/error；
- 小/中/大输出和 timeout/permission；
- 已知复杂或当前 capability gap。

每个认证包包含 owner、选择理由、精确 revision、approved Artifact、published Bundle、variant matrix、差分、mutation、20 次稳定性、已知限制、waiver 和证据链接。无法编译的 KBD 仍计入样本并展示 gap，防止选择偏差。

### 5. 稳定性与 Flaky 治理

每个核心 KBD 的 Golden positive 在固定版本与环境下至少连续/分时重复 20 次，保留每次首次结果。分别统计：

- first-attempt pass rate；
- final pass rate；
- flaky rate 和失败聚类；
- p50/p95/p99 duration；
- fixture miss、inconclusive、infra error；
- 资源清理残留。

自动重试只能产生新 Attempt，不能改写首次结果。flaky 阈值在试点后由质量负责人批准；超阈值 KBD 不进入 blocking suite，必须有 owner 和修复 SLA。

### 6. 容量与隔离梯度

按 `1 → 10 → 50 → 100 → 200` 并发 Scenario 逐级测试，前一级正确性和资源门禁失败时不进入下一级。每级固定 Bundle 组合、输出分布、fault 比例、到达模型、持续时间和 warm/cold cache 条件。

采集：吞吐、p50/p95/p99、queue wait/reject、CPU/RSS/GC/goroutine、SSH session/channel、输出字节、cache hit/miss/eviction、Registry/Redis/CAS、DB connection、cleanup lag 和 cross-scenario contamination。

三个声明分别验收：

1. 100 个并发 SSH Scenario；
2. 100 个并发 Agent workflow；
3. 100 个真实浏览器/UI 会话。

阶段 E 的最低产品门禁是 100 Scenario 零串线并有显式过载行为；这不自动等价另外两个声明。200 是容量边界探索，不要求无拒绝，但要求受控降级、无污染和可恢复。

### 7. 故障与安全演练

在各容量级注入 Runtime/Runner Pod 重启、Registry/DB/Redis 短时故障、网络延迟/断连、Lease expiry/revoke、磁盘/对象损坏、queue overload 和取消风暴。验证无状态恢复、CAS、幂等、reconciliation 和证据完整性。

安全演练验证：Bundle secret/PII 注入被阻断、伪造/重放 Lease 被拒绝、任意 URL/命令/host 无法注入、sim 网络不能访问真实 HCI、日志和 Artifact 无密钥、跨租户/Run 不可读。任何串线、secret 泄漏或非预期真实访问为 P0，立即停止并撤销基线。

### 8. 持续回归和影响分析

依赖图从 KBD/Signal/Tool/Policy/Artifact/Compiler/Runtime/Bridge/Agent revision 映射到 Bundle 和认证用例：

- PR：执行 changed-component contract tests、受影响 KBD 小型 variants/mutations；
- nightly：执行 10～20 核心 KBD 全 variants、稳定性抽样和故障回归；
- 周期任务：完整 20-repeat、容量阶梯、real/sim calibration 和安全扫描；
- 发布前：按风险合并上述门禁并生成产品声明快照。

失败默认阻断相应发布。waiver 必须包含 scope、owner、风险、补偿控制、截止日期和批准人，到期自动失效。

### 9. SLO、仪表盘和告警

运营视图按环境/版本显示：

- KBD testability、validated/stale/gap backlog 和 age；
- Run passed/failed/inconclusive、fixture hit/miss、lease reject、queue overload；
- mutation detection、differential drift、flaky；
- duration/throughput/resource/cost；
- cleanup leak、cross-scenario contamination 和安全事件；
- owner、最近证据、waiver 和下一动作。

SLO 在阶段 E 基线测试后以实测容量设定，不把设计估算写成目标事实。初始强不变量不依赖统计阈值：cross-scenario contamination、secret 泄漏和非预期真实 HCI 访问必须为零；一旦发生立即告警并停止相关测试。

### 10. 证据与可复现性

每次认证/容量任务生成不可变 Evidence Manifest：代码 SHA、镜像/Bundle/Artifact digest、KBD/Tool/Policy revision、环境配置、数据集 seed、Run 列表、原始指标查询、日志/trace/report URI、测试工具版本和结论签名。

Evidence 对象按保留策略存储；仪表盘只是索引，不是唯一证据。产品声明必须链接具体 Evidence Manifest，且明确有效时间窗和适用版本。

### 11. 运营责任模型

| 角色 | 责任 |
|---|---|
| KBD owner/expert | 语义、Artifact 和 capability gap。 |
| Compiler/Runtime owner | 编译正确性、数据面和容量。 |
| Agent/Bridge owner | 真实协议与业务回归。 |
| QA owner | 独立 oracle、mutation、稳定性和发布结论。 |
| SRE | SLO、容量、告警、故障演练和运行手册。 |
| Security | 数据、身份、网络隔离和事件响应。 |
| Product owner | 声明范围、风险接受和优先级。 |

每个失败必须落到上述 owner 和 SLA；无 owner 的 gap 不允许通过 waiver 长期悬空。

### 12. 产品声明状态

建议在 KBD testability 中使用：

```text
unsupported → candidate → validated
       │           │           ├→ stale
       └→ gap      └→ blocked  └→ retired
```

只有全部强门禁通过的精确 revision 可标记 validated。对外声明必须区分“支持指定 KBD 编译”“支持 sim TestRun”“核心集产品级 validated”“100 Scenario validated”，不得用一个布尔字段涵盖不同能力。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 为什么真实 HCI 仍是独立 Oracle

仿真是对真实可观察契约的模型，不是事实本身。完全由 sim/Matcher 互相验证无法发现共同错误；周期性、受控的真实校准是可信度来源。

### 为什么 Mutation 比单纯覆盖率更重要

代码覆盖率只能证明路径被执行，不能证明错误输出会被测试拒绝。Mutation 直接检验 Fixture、Matcher 和 Conclusion 对关键语义变化是否敏感。

### 为什么从 10～20 个分层核心 KBD 开始

任意 KBD 全覆盖在能力图未知时不可兑现；单个 27123 又没有代表性。分层核心集能暴露 Tool/Matcher/变量链能力边界，并形成可持续扩展的认证模板。

### 为什么容量必须阶梯推进

直接跑 200 会掩盖最早的非线性拐点，也难以区分容量、正确性和故障恢复问题。逐级门禁能定位极限，并验证过载而非只追求一个峰值数字。

### 为什么不把 100 Scenario 等同 100 Agent/浏览器

SSH Runtime、Agent workflow 和 UI/browser 的资源模型与瓶颈不同。合并声明会用较轻负载替代较重链路，导致不可审计的容量夸大。

## 验收标准

- 10～20 个分层核心 KBD 有精确 revision 的认证包，gap 也可见且有 owner；
- 核心 KBD 关键 variants、Mutation、real/sim differential 和 20-repeat 稳定性达到批准阈值；
- 1/10/50/100/200 梯度证据完整，100 Scenario 零串线，200 过载可控；
- Pod/Registry/Redis/网络/cancel 等故障不污染其他 Run，且可自动收敛；
- PR/nightly/周期校准能按依赖图运行并产生不可变证据；
- SLO、告警、waiver、owner 和 stale/gap/flaky/drift 形成运营闭环；
- 安全演练证明无 secret 泄漏、无 sim→real fallback、无非预期真实访问；
- 只有上述证据齐备后，才可声明“支持指定 KBD 自动构建仿真环境并验证效果”。
