# QFK 系统执行域与统一文本取值方案

## 背景与需求

专家审核 KBD40061 时提出了两个必须从事实出发解决的问题。

第一，HCI 的 `acli --container` 是 aCLI 的全局参数。它的语义是由 aCLI 在目标
HOST-OS 上选择 `asv-con`、`vn-con`、`vn-agent` 或 `vs-cp-manager` 执行域；不是
Terminal Bridge 的 `container_exec` 参数。旧链路将 `qfk_system.container=asv-con`
传给 Bridge，实际会构造“进入 asv-con 后运行 acli system …”。由于容器内没有
`acli`，配置本身与运行命令矛盾。

第二，`df` 只是 Shell 文本输出的一个例子。为每类输出建设专用 capability 或在
Matcher 内维护 `df` 特判都不能扩展。平台已有 `produces[].extract` 的安全文本取值，
Matcher 必须复用完全相同的 Schema、运行时和界面，而非再维护第二份 grep/awk 逻辑。

## 方案

### 1. qfk_system 的准确边界

```text
HOST / {{HOST}}
  → Terminal Bridge 选择 SSH 会话（不拼 aCLI --host）
  → qfk_system 编译完整 aCLI 命令
  → acli_exec 在 HOST-OS 原样执行
  → aCLI 按可选 --container 选择内部执行域
```

新的声明字段保持扁平、可读：

```json
{
  "host": "{{HOST}}",
  "cluster": false,
  "container": "asv-con",
  "timeout": 120,
  "formatter": "json",
  "command": "df",
  "command_args": ["/sf/log"]
}
```

其实际命令为：

```bash
acli --timeout 120 --formatter json --container asv-con system df /sf/log
```

字段职责如下。

| 字段 | 唯一职责 | 不能承担的职责 |
|---|---|---|
| `host` | Bridge/SSH 目标节点 | aCLI 全局参数、容器名 |
| `cluster=true` | 添加无值 flag `--cluster` | `host=cluster` 的新写法 |
| `container` | 添加 `--container <aCLI 枚举>` | Bridge 进入容器 |
| `timeout` | aCLI 内层 `--timeout N`；Bridge 外层超时使用同一预算 | 隐含无限超时 |
| `formatter` | 添加 `--formatter` | 解析器或 Matcher |
| `command_args` | 每项安全转义后追加 | 自由 Shell 脚本 |

Bridge 的 `container` 只保留给 `bash_exec/container_exec`。`acli_exec` 和所有
`qfk_system` 调用必须发送 `container=null`。历史 `qfk_system.container=host` 读取
时无损归一为“省略 aCLI `--container`”：旧语义本来就是 HOST-OS，不改执行含义；新
Schema 不再把 `host` 作为 aCLI 容器枚举暴露给专家。

### 2. 同一份安全文本取值

```text
完整 stdout/stderr
        ↓
TextExtract（include/exclude、行基数、列、分隔符、类型）
        ├── Produces adapter：写入变量池
        └── Matcher adapter：聚合 → 比较 → Signal outcome
```

`TextExtract` 是唯一 Schema：`orchestrate.produces[].extract` 与
`match.extract` 都引用它。唯一运行时提取器返回匹配行、选中行、原始值、转换值，
因此运行证据可说明“为什么得到 54”，而不是只留下一个结果。

专家可按 grep/awk 的心智模型编辑，但实现只接受声明式安全子集：

- 包含/排除行相当于受控 grep；
- `column=5` 相当于受控 `awk '{print $5}'`；
- `value_mode=number` 支持 `54% → 54`、`21.5ms → 21.5`；
- 不执行用户输入的 grep、awk、管道、重定向或任意 Shell；
- 输出截断且完整缓存不可得时 Fail Closed，不能从摘要作出阈值结论。

### 3. KBD40061 的规范配置

```json
{
  "acquire": {
    "tool": "qfk_system",
    "args": {"host": "{{HOST}}", "command": "df", "command_args": ["/sf/log"], "timeout": 120}
  },
  "match": {
    "type": "threshold",
    "extract": {
      "type": "text", "source": "stdout", "include": ["/sf/log"],
      "column_mode": "index", "column": 5, "delimiter": "whitespace",
      "cardinality": "all", "value_mode": "number"
    },
    "aggregation": "max", "operator": ">", "value": 80, "expected": true
  }
}
```

给定两行 `54% /sf/log`，证据为 `raw_values=["54%", "54%"]`、
`values=[54,54]`、`max=54`、`54 > 80=false`。若一行是 `83%`，`max=83`，结果为真。
这不是 df 专用代码；其他稳定文本输出可用同一规则。

## 决策依据

采用“声明式提取 + 定型 predicate”符合可观测性与规则引擎的通用范式：采集、
提取、聚合、比较各自可审计，且同一输入必得同一结果。它比自然语言提示或 LLM
临场解释稳定，也比让专家填写任意 Shell 更安全、可重放。

不采用以下方案：

1. 为 `df` 单独建设 `filesystem.usage/v1`：只覆盖一个输出形态，会把任意 Shell
   输出膨胀为 capability 注册表，增加审核和迭代成本；
2. 保留 `df`/`Use%` 特判：不能解释、不能迁移到其他命令，且未来输出变形会再次误判；
3. 让 Bridge 进入 aCLI 容器：违背实机 aCLI Usage，容器内没有 aCLI；
4. 执行专家输入的 grep/awk：存在 `system()`、重定向、转义和审计/replay 失控风险。

## 影响范围

- 参数事实源：`shared/schemas/acquirer_args.py` 与生成的 Signal v2 Schema；
- 执行：QFK SystemHandler、QFK Engine、aCLI Executor、语义 Validator；
- 消费：KBD Differential 的完整输出、边缘 output_filter 和变量依赖推导；
- 专家界面：`qfk_system` 的 aCLI 执行域说明及共用 `TextExtractEditor`；
- 数据：不新增表。新字段保存在既有 `kbd_entry.signals_json` 和 immutable revision payload；
- 验证：Handler 命令、Bridge 边界、`--cluster`、百分比取值、双行聚合、Schema 及依赖推导。

## 验收标准

1. `asv-con` 产生 `acli --container asv-con system …`，而 Bridge payload 的
   `container` 为 null；
2. `--cluster` 被当作无值全局参数，不吞掉 namespace；
3. `match.extract` 和 `produces[].extract` 用同一函数并产生同样的转换值；
4. `54%` 可精确转换为 54，阈值/等值边界与 `max` 聚合可重复验证；
5. 管道仍在保存边界拒绝，完整输出不可取得时仍 Fail Closed；
6. Admin 页面明确区分“目标主机”“aCLI 执行域”和“集群执行”，专家不需要理解
   Bridge 内部实现即可编辑；
7. 本轮不宣称完成真实客户环境 Execution Replay、122 条专家复核或 Expert Gold。
