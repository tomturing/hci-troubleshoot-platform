# KBD 最小回放证据契约与正式专家复核启动方案

## 背景与需求

PR #650 已将专家修订原因、精确 KBD runtime revision、CDD 编译和逐 Signal outcome 写入长期审计，但一条 outcome 还不能独立回答两个问题：后续调查能否定位到当时实际使用的 KBD、计划、输入与 Terminal Bridge 执行证据；以及专家开始正式复核后，哪些记录只是未认证身份的专家修订，哪些事实可以用于工程/模型分析。

同时，专家审核页的“来源证据”是只读溯源信息。它被置于 QFK 执行模式和判定字段之间，会打断专家按“可执行字段 → 判定 → 辅助信息”的阅读顺序。专家提出将其固定放到每张信号卡片的最下方，默认保持收起。

## 方案（WHAT）

### 1. 正式专家复核从现有轻量路径开始

不创建新工作台或审批流。专家继续在 KBD 审核页完成分类、截图 Evidence 和 Signal 的新增、删除、排序、编辑与显式发布：

```text
原始案例 / LLM Proposal
  → 专家工作稿（reason_code / 删除原因）
  → 显式发布的 Dynamic Resource revision
  → Agent 精确 revision 消费与运行审计
```

当前 `reviewer_id` 仍是 `unverified`；因此每次专家修订都可以进入“正式复核工作量和差异数据”的统计，却不能被称为可信 Expert Gold。正式复核的知识判断只能由实际专家作出，平台和自动化测试不能替代该判断。

### 2. 在既有运行审计中加入最小 Replay manifest

每个 `kbd_diagnostic_outcome` 审计的 `metadata_json.replay_manifest` 增加以下内容：

| 部分 | 保存内容 | 不保存内容 |
|---|---|---|
| 不可变知识定位 | KBD `resource_type/name/revision/checksum` | KBD 正文副本 |
| 计划定位 | `plan_id`、`snapshot_id` | 另一份可变计划正文 |
| 环境与参数 | `environment_hash`、每次采集的 `acquire_args_hash` | 主机、变量、命令参数明文 |
| Signal 判定 | `signal_ref_id`、`signal_id`、`evaluation_id`、工具、outcome | stdout/stderr、日志正文 |
| 证据查找 | `conversation-service.bridge_execution_artifacts` + `exec_id` | artifact 内容副本 |

该 manifest 的固定事实边界为：

```json
{
  "kind": "kbd_execution_replay_manifest",
  "readiness": {
    "evidence": "referenced | partial | absent",
    "execution": "not_available",
    "replayable": false
  }
}
```

`evidence=referenced` 只表示“本次已执行的 Signal 留有按 `exec_id` 查询 Terminal Bridge artifact 的引用”；它**不**表示 artifact 尚未过期、已获授权、已脱敏或已成功读回。`execution=not_available` 明确表明当前没有重放 runner，不能把 manifest 称为 Evidence Replay 或 Execution Replay。

### 3. 专家页面的来源证据位置

QKV 和 QFK 信号卡片均按以下顺序展示：

```text
可执行采集字段 → 输入/输出或判定字段 → 工具高级字段 → 来源证据（默认收起、只读）
```

来源证据继续显示来源段落/截图引用与逐字证据原文，供专家在需要时追溯；它不是可编辑事实，也不会参与 Agent 运行。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 为什么先采用“引用 + 哈希 + 不可变版本”

回放的最小第一性条件是“可定位同一次输入、同一份知识和同一份执行证据”。把客户日志全文复制到 `dynamic_resource_usage_audit` 虽然看似方便，却会引入敏感数据扩散、保留期不一致、审计表膨胀和多份证据漂移。已有 Terminal Bridge artifact 是原始输出的权威存放位置，因此审计只保存可验证的引用与哈希。

### 为什么 manifest 必须显式不可重放

一次诊断结束并不保证 artifact 仍存在，也不保证未来有相同 HCI、会话权限、Handler、Validator 和 Bridge 版本。若把“存了 exec_id”宣传成回放成功，后续模型评估会把不可复核样本误当 Gold 证据。显式 `replayable=false` 让系统能够先积累可追溯关联，同时保持事实诚实。

### 为什么不先新建 Replay 表或重型工作流

目前 replay 没有独立的执行生命周期、人工审批步骤或高频跨对象查询需求；新表只会复制现有审计和 artifact 关联，却不能解决授权、脱敏或重放 runner 缺失。把 manifest 放入已有的版本化运行审计中，是最小、可演进的选择。等 artifact 读回、脱敏和 replay runner 稳定后，再根据真实查询基数决定是否正规化。

### 为什么不把来源证据放到卡片顶部

专家首要任务是判断“应该采什么、在哪里采、怎么判定”。来源证据服务于有疑问时的追溯，而不是编辑动作；放在中间会使不可操作信息打断可操作字段。默认收起并放在卡片末尾，满足“看得到时能理解、需要时可追溯”的原则。

## 影响范围

- `backend/agent-service`：CDD 运行审计增加 `replay_manifest`；不改变诊断结论和正常执行路径。
- `frontend/admin`：QFK 来源证据移到每张 Signal 卡片末尾；QKV 已处于卡片末尾，保持一致。
- `dynamic_resource_usage_audit`：仅扩展既有 `metadata_json`，不新增表、不变更 SQL Schema。
- 文档：更新 Agent、Admin、任务、测试与冷启动入口；新增同一工作循环的方案、任务、验证事件文档。

## 验收标准

1. 每次有精确 KBD revision 的 Agent 运行审计都产生 `replay_manifest`；
2. manifest 含 resource revision/checksum、计划标识、环境/参数哈希、Signal evaluation 和 artifact 查找键；
3. manifest 不含 stdout/stderr、客户日志、环境变量或参数明文；
4. manifest 明确 `replayable=false` 和未完成 blocker；
5. QFK 与 QKV 的来源证据默认收起且位于各自卡片末尾；
6. 单元测试、前端生产构建、Schema Contract、文档治理检查均通过；
7. 不宣称已完成 Evidence Replay、Execution Replay、可信 Expert Gold 或真实客户环境回放。
