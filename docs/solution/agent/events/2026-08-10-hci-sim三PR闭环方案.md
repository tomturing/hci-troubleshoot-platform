# hci-sim A～E 三 PR 纵向闭环设计

## 1. 设计判断

把每个错误拆成独立 PR 会造成“修了局部 YAML、但没有证明调用链”的局部最优。反过来把所有代码塞进一个 PR 会使 review、回滚和数据库迁移风险不可控。本方案用三个纵向切片：每个切片都从用户可观察入口穿过数据、控制、执行和证据边界；切片之间用不可绕过的 Go/No-Go 门禁串联。

## 2. 目标拓扑

```text
Admin UI 仿真测试
   │  build/status/logs/start
   ▼
API Gateway → Control Plane API
   │                  │
   │                  ├─ hci_sim.control_plane/fixture/artifact/audit
   │                  ├─ TestRun ↔ Bundle digest ↔ KBD revision
   │                  └─ Agent environment context（不可变绑定）
   ▼
K3s Scheduler/Runner ── short-lived Lease ── terminal_bridge
                                               │
                                               ▼
                                  hci-sim.hci-sim-dev:2222
                                               │
                                               ▼
                                  exec-result / Artifact / Oracle
```

## 3. 安全和数据边界

- `hci_sim_runtime` 只拥有四个 schema 的 DML；`hci_sim_migrator` 只用于迁移；owner 不登录；平台业务角色默认拒绝 `CONNECT hci_sim`。
- Runtime 的连接配置只从 `HCI_SIM_DATABASE_URL` 或 Secret 引用读取。启动时解析数据库名必须等于 `hci_sim`；变量为空、数据库名错误、连接失败均停止启动。
- Bundle 原始对象进入 content-addressed object store；数据库只保存 metadata、size、schema、signature、digest 和受控 URI。Lease 明文只在签发/连接的瞬时内存中存在。
- Bridge 只按受签名 Lease 的 `execution_mode` 和 target 选择 sim；不能根据 host、端口、用户名或字符串子串猜测 simulation。
- 所有 API 的状态转换使用数据库事务 + version/CAS；事件使用 outbox，重复投递必须幂等。

## 4. PR1 实现设计

1. ArgoCD 将 Secret/ConfigMap/Job 作为 `PreSync`，按 `-10/-9/-8` 波次创建，消除隐式普通资源依赖。
2. 将 `deploy/helm/hci-sim` 纳入 dev GitOps Application，目标 namespace 为 `hci-sim-dev`，使用不可变镜像 tag、外部 Secret、ConfigMap fixture 和 default-deny NetworkPolicy。
3. Runtime 增加 `DatabaseConfig`/`DatabaseManager` 启动门禁；在没有真正持久化 Store 前，生产 profile 禁止启动为“可执行”状态，开发 synthetic profile 必须显式标记并限制为 smoke。
4. Bridge E2E 验证包含 DNS、NetworkPolicy、SSH host key、Lease claims、command fingerprint、exit code、exec-result 和 trace/run ID 透传。

当前实现已先落地数据库启动边界：`HCI_SIM_DATABASE_REQUIRED=true` 时 Runtime 必须拿到 PostgreSQL URL，且 URL 的数据库名必须精确为 `hci_sim`；没有持久化 Repository 前，不能把该检查误写成“Runtime 已经使用数据库”。

## 5. PR2 实现设计

- Python Control Plane API 负责认证、resolve、build job、状态/日志 SSE、TestRun 生命周期；Go Runtime 只做数据面，不直接暴露控制 API。
- PostgreSQL Repository 映射 `control_plane.*`、`fixture.*`、`artifact.*`、`audit.*`，所有写操作带 `version` 和 idempotency key；失败补偿通过 outbox/reconciler。
- Fixture Compiler 读取已发布 KBD active revision 和 Tool/Policy contract，冻结输入 fingerprint；23821 必须有 approved Artifact provenance，无法提供时返回 capability gap。
- Admin UI 页面只消费结构化状态和脱敏日志；日志默认折叠、可展开/关闭；“开始测试”由后端状态决定，不由前端猜测。
- 创建工单动作使用现有 Case API，自动填入仿真 SSH environment 信息，标题和描述是唯一必填人工字段；TestRun ID 写入环境上下文和工单审计。

## 6. PR3 实现设计

- Affected-set 计算：变更 KBD/Tool/Policy/Compiler/Runtime/Bridge 时只运行受影响小集合；nightly 运行 10～20 个核心 KBD，周期任务运行全量和容量。
- Differential 比较分层保存 command/stdout/stderr/exit/variables/matcher/signal/conclusion/evidence；允许差异必须版本化并有审批人和到期时间。
- Mutation 以关键结论和安全边界 100% 检出为硬门禁；等价 mutation 需要独立理由。
- 容量按 1→10→50→100→200 梯度执行，任一级出现串线、secret、真实访问或 cleanup leak 立即停止升级。

## 7. 反模式审查结论

| 反模式 | 为什么不成立 | 强制替代 |
|---|---|---|
| 每个 YAML/小 bug 单独 PR | 只证明局部资源，无法证明链路；PR 数量和回滚复杂度失控 | 将 Hook 修复纳入 PR1 基础运行面 |
| 继续扩展 synthetic catalog | 只模拟信号，不证明真实 Artifact/Oracle | approved Artifact + immutable Bundle |
| 直接把内存 Registry 当生产控制面 | 重启丢状态，多副本 CAS/审计/权限均缺失 | PostgreSQL Repository + outbox |
| 把 126 条 capability ready 当作 126 条可测试 | ready 只表示快照可绑定 Artifact | 每条 KBD 必须有 published Bundle 和证据 |
| 前端直接拼 SSH/Lease | 可绕过状态机、审计和授权 | API 签发、TestRun 绑定、UI 只展示结果 |
| 手工 kubectl patch/edit 作为配置 | GitOps 漂移且不可回滚 | 环境仓库 Application/values + Argo 同步 |
