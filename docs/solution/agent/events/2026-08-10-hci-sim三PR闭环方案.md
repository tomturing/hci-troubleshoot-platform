# hci-sim A～E 三 PR 纵向闭环设计

## 1. 设计判断

把每个错误拆成独立 PR 会造成“修了局部 YAML、但没有证明调用链”的局部最优。反过来把所有代码塞进一个 PR 会使 review、回滚和数据库迁移风险不可控。本方案用三个纵向切片：每个切片都从用户可观察入口穿过数据、控制、执行和证据边界；切片之间用不可绕过的 Go/No-Go 门禁串联。

## 2. 目标拓扑

```text
Admin UI 仿真测试
   │  build/status/logs/start
   ▼
API Gateway → Control Plane API
   │                  │
   │                  ├─ hci_sim.control_plane/fixture/artifact/audit
   │                  ├─ TestRun ↔ Bundle digest ↔ KBD revision
   │                  └─ Agent environment context（不可变绑定）
   ▼
K3s Scheduler/Runner ── short-lived Lease ── terminal_bridge
                                               │
                                               ▼
                                  hci-sim.hci-sim-dev:2222
                                               │
                                               ▼
                                  exec-result / Artifact / Oracle
```

## 3. 安全和数据边界

- `hci_sim_runtime` 只拥有四个 schema 的 DML；`hci_sim_migrator` 只用于迁移；owner 不登录；平台业务角色默认拒绝 `CONNECT hci_sim`。
- Runtime 的连接配置只从 `HCI_SIM_DATABASE_URL` 或 Secret 引用读取。启动时解析数据库名必须等于 `hci_sim`；变量为空、数据库名错误、连接失败均停止启动。
- Bundle 原始对象进入 content-addressed object store；数据库只保存 metadata、size、schema、signature、digest 和受控 URI。Lease 明文只在签发/连接的瞬时内存中存在。
- Bridge 只按受签名 Lease 的 `execution_mode` 和 target 选择 sim；不能根据 host、端口、用户名或字符串子串猜测 simulation。
- 所有 API 的状态转换使用数据库事务 + version/CAS；事件使用 outbox，重复投递必须幂等。

## 4. PR1 实现设计

1. ArgoCD 将 Secret/ConfigMap/Job 作为 `PreSync`，按 `-10/-9/-8` 波次创建，消除隐式普通资源依赖。
2. 将 `deploy/helm/hci-sim` 纳入 dev GitOps Application，目标 namespace 为 `hci-sim-dev`，使用不可变镜像 tag、外部 Secret、ConfigMap fixture 和 default-deny NetworkPolicy。
3. Runtime 增加 `DatabaseConfig`/`DatabaseManager` 启动门禁；在没有真正持久化 Store 前，生产 profile 禁止启动为“可执行”状态，开发 synthetic profile 必须显式标记并限制为 smoke。
4. Bridge E2E 验证包含 DNS、NetworkPolicy、SSH host key、Lease claims、command fingerprint、exit code、exec-result 和 trace/run ID 透传。

当前实现已先落地数据库启动边界：`HCI_SIM_DATABASE_REQUIRED=true` 时 Runtime 必须拿到 PostgreSQL URL，且 URL 的数据库名必须精确为 `hci_sim`；没有持久化 Repository 前，不能把该检查误写成“Runtime 已经使用数据库”。

## 5. PR2 实现设计

- Python Control Plane API 负责认证、resolve、build job、状态/日志 SSE、TestRun 生命周期；Go Runtime 只做数据面，不直接暴露控制 API。
- PostgreSQL Repository 映射 `control_plane.*`、`fixture.*`、`artifact.*`、`audit.*`，所有写操作带 `version` 和 idempotency key；失败补偿通过 outbox/reconciler。
- Fixture Compiler 读取已发布 KBD active revision 和 Tool/Policy contract，冻结输入 fingerprint；23821 必须有 approved Artifact provenance，无法提供时返回 capability gap。
- Admin UI 页面只消费结构化状态和脱敏日志；日志默认折叠、可展开/关闭；“开始测试”由后端状态决定，不由前端猜测。
- 创建工单动作使用现有 Case API，自动填入仿真 SSH environment 信息，标题和描述是唯一必填人工字段；TestRun ID 写入环境上下文和工单审计。

## 6. PR3 实现设计

- Affected-set 计算：变更 KBD/Tool/Policy/Compiler/Runtime/Bridge 时只运行受影响小集合；nightly 运行 10～20 个核心 KBD，周期任务运行全量和容量。
- Differential 比较分层保存 command/stdout/stderr/exit/variables/matcher/signal/conclusion/evidence；允许差异必须版本化并有审批人和到期时间。
- Mutation 以关键结论和安全边界 100% 检出为硬门禁；等价 mutation 需要独立理由。
- 容量按 1→10→50→100→200 梯度执行，任一级出现串线、secret、真实访问或 cleanup leak 立即停止升级。

## 7. 反模式审查结论

| 反模式 | 为什么不成立 | 强制替代 |
|---|---|---|
| 每个 YAML/小 bug 单独 PR | 只证明局部资源，无法证明链路；PR 数量和回滚复杂度失控 | 将 Hook 修复纳入 PR1 基础运行面 |
| 继续扩展 synthetic catalog | 只模拟信号，不证明真实 Artifact/Oracle | approved Artifact + immutable Bundle |
| 直接把内存 Registry 当生产控制面 | 重启丢状态，多副本 CAS/审计/权限均缺失 | PostgreSQL Repository + outbox |
| 把 126 条 capability ready 当作 126 条可测试 | ready 只表示快照可绑定 Artifact | 每条 KBD 必须有 published Bundle 和证据 |
| 前端直接拼 SSH/Lease | 可绕过状态机、审计和授权 | API 签发、TestRun 绑定、UI 只展示结果 |
| 手工 kubectl patch/edit 作为配置 | GitOps 漂移且不可回滚 | 环境仓库 Application/values + Argo 同步 |

## 8. PR3 收口实现与不可逾越边界

### 8.0 不可变镜像晋级闭环

hci-sim 不写入 `hci-platform-env` 的业务镜像 values，而由本仓库的
`deploy/gitops/argo-apps/local/hci-sim-dev.yaml` 直接声明。main push 的最小镜像
矩阵只在 `hci_sim/**` 或其 Dockerfile 输入变化时包含 hci-sim；构建成功后，独立的
`verify-hci-sim-gitops` job 使用 GHCR `packages:read` 读取刚推送 tag 的 OCI manifest
digest，并强制校验 Argo Application 已通过 PR 固定到同一 digest。仓库 main ruleset
要求变更经过 PR，GITHUB_TOKEN 不得绕过审查直接回写；因此 digest 更新本身必须作为
发布 PR 的一部分，CI 只做 fail-closed 校验。PR 不运行镜像构建/校验 job，普通 PR 的
检查时间不受影响；任何 digest 解析失败、GitOps 漂移或非 main 来源均阻断晋级，不能
退回 `latest`/`dev-local`。

本 PR 将产品入口和运行时最小契约放进同一个纵向切片：

1. `frontend/admin` 新增 `/simulation` 路由和“仿真测试”页面。KBD_ID、标题、描述写入浏览器 localStorage；构建失败重试不会清空表单；构建成功前开始测试和创建工单均禁用；详细日志可展开/关闭。
2. hci-sim HTTP 控制契约为 `POST /v1/simulations/build` 和 `POST /v1/simulations/test-runs`。build 只允许请求与已加载 immutable fixture 相同的 KBD，同时返回冻结的 `environment_context`；签发的 connection 明确带 `execution_mode=sim-ssh`、TestRun ID、Bundle digest。test-runs 要求 connection 与 environment context 的 TestRun、KBD、执行模式完全相等，拒绝缺少或串线的请求。生产必须由 Secret 注入 `HCI_SIM_CONTROL_TOKEN` 并由 API Gateway 代理，`HCI_SIM_ALLOW_INSECURE_CONTROL_API` 默认关闭，不能把 Runtime 端口直接暴露给浏览器。
3. Helm 支持外部 `HCI_SIM_DATABASE_URL` Secret、可选 image digest 和 values 选择的 fixture ConfigMap；GitOps Application 明确目标 namespace 为 `hci-sim-dev`，但 digest、Secret 和真实 Bundle 必须由发布/环境仓库注入后才允许同步。
4. 23821 fixture 文件故意带 `SYNTHETIC=true` 和 facts boundary。任何把该文件或本地 `.hci-sim-run` 当作 approved real Bundle 的做法均违反设计。

因此，“页面能显示/HTTP 能返回”只代表契约层完成；生产控制面持久化、Agent context 写库、K3s 受管部署、真实 23821 Bundle 和 E 级证据仍是明确的 Go/No-Go 能力缺口。

## 9. P1 持久化控制面第一切片（2026-08-10）

### 9.1 为什么先做 Repository，而不是继续扩展 synthetic fixture

第一性原理上，TestRun 的核心不变量是“重启后仍能找到同一个不可变绑定”，而不是“进程内能签发一次 Lease”。当前 `RunStore` 的 map 在 Pod 重启、多副本和网络重试下都会丢失幂等键、版本和状态，因此继续添加 fixture route 不能解决控制面正确性。

### 9.2 已实现边界

- `database.Open` 只接受已经通过 `hci_sim` 数据库名校验的 URL，并在启动前 Ping；不接受主库 URL 或未配置连接。
- `RunRepository` 以一个事务 upsert `control_plane.scenario`、幂等插入 `control_plane.run`，并用 `external_id` 保留现有 `run-...` 对外 ID，内部 UUID 继续承担关系完整性。
- 相同 `idempotency_key + request_digest` 返回原记录；相同 key 的不同请求返回 `idempotency_conflict`。
- `UpdateStatusCAS` 使用 `version` 条件更新，旧 Worker 只能得到 `run_version_conflict`，不能覆盖新状态。
- 所有 Repository 字段排除 Lease 明文、私钥、原始 Artifact 和任意客户 URL。

这只是持久化基础切片。Runtime HTTP build/TestRun 仍需下一切片接入该 Repository、Attempt/Event/Result/outbox 和重启恢复；在接线完成前不得宣称已实现生产持久化。

## 10. P1 Runtime 接线切片（2026-08-10）

本切片把最小可观察控制流接到同一 PostgreSQL 边界，避免“Repository 文件存在但生产入口仍写内存”的假完成：

1. Runtime 启动时若 `HCI_SIM_DATABASE_URL` 已配置，立即通过 `database.Open` Ping；URL 的数据库名必须精确为 `hci_sim`。`HCI_SIM_DATABASE_REQUIRED=true` 且无法连接时进程直接退出，绝不回退 `hci_troubleshoot` 或内存状态。
2. `POST /v1/simulations/build` 先验证请求 KBD 等于当前 immutable fixture，再以 `Idempotency-Key` 和请求摘要写入 Scenario/Run。同一 key 同一摘要重放得到同一 external TestRun ID；摘要不同返回 `409 idempotency_conflict`。未配置数据库时仅保留本地 synthetic 单元契约，生产 Helm 必须开启 required。
3. Lease 签发成功后仅把 `sha256(JTI)` 写入 `control_plane.run_attempt`，并通过 version/CAS 将 Run 从 `requested` 推进到 `leased`。Lease 明文、密码、私钥永不写库；持久化失败则不给调用方返回连接信息。
4. `POST /v1/simulations/test-runs` 除原有 `sim-ssh`/KBD/TestRun 显式绑定外，查询 hci_sim 中的 Run，校验 Bundle digest，随后用 CAS 推进到 `preparing`（已 leased 的重试保持 leased）。不存在或串线返回明确的 `409`，不得创建悬空工单。
5. 应用侧使用 `uuid.New()` 生成内部 Run/Attempt ID，迁移不要求 Runtime 具备 `pgcrypto` 或 DDL 权限；数据库角色仍只有四个 schema 的 DML。

Gateway 必须透传浏览器的 `Idempotency-Key` 到 Runtime；否则网络重试会在 Runtime 侧被视为不同请求。Gateway 只注入服务端控制 Token，绝不把 Token 或 Lease 返回给浏览器之外的日志/追踪字段。

这仍不是完整生产控制面：Run Event/Result、outbox/reconciler、重启恢复和 Agent context 落库尚未完成，必须保持 `pending/capability_gap`，不能用 API 200 或 Pod Ready 替代这些证据。
