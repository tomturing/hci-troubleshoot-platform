# KBD 关键信号图片来源门禁收敛修复方案

## 背景与需求

PR #673 的原始目标是阻断根因、解决方案等答案侧图片绕过文本字段隔离进入 KBD 关键信号 Prompt。首版实现已按图片所属章节过滤输入，但同时增加了“只要 Candidate 有 `source_refs`，完整 `provenance.evidence` 必须逐字出现在每个截图区域”的规则。

KBD27736 证明该规则越过了原目标：其 evidence 是 `steps_text` 的原句，`img:2` 则提供 eth0/channel4 配置的辅助事实。图片本身已合法进入 Prompt，却因正文句不在 OCR 中被错误拒绝；真正的脱敏 Matcher 问题被提前遮蔽。

## 方案（WHAT）

1. 保留图片所属章节白名单：仅 `title`、`problem_description`、`alert_info`、`steps_text` 的图片可进入 Signal Prompt；`root_cause`、`solution`、未知章节图片一律排除。
2. 保留图片内容最小化：只传 OCR `text_lines`、`fields`、`observed_facts` 与质量状态，不传 `context_before/context_after`、DESCRIPTION、inferences 或 legacy desc。
3. 由过滤后且未被长度限制截断的图片区域建立 `source_ref` 集合。Candidate 如填写 `source_refs`，每一项必须属于该集合；否则以 `run_failed` 保留到 rejected candidates。
4. 删除 `provenance.evidence` 与截图原子事实的逐字强绑定。正文 evidence 与诊断截图可联合支持一个 Candidate；单一 evidence 字段不能表达逐证据原子级来源关系。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 第一性原理

本次边界的对象是“哪些信息可进入模型输入”，不是“如何为每个综合诊断结论建立完整证据图”。只要 solution 图片在 LLM 调用前被过滤，它就无法成为关键信号的输入来源；候选是否完整可运行，继续由既有 Matcher、Catalog、Schema 与只读门禁判断。

### 为什么保留 source ref 集合检查

模型输出的图片编号可能指向 solution 图、不存在的图，或因长度限制未实际进入 Prompt 的图。检查集合成员关系能保证审核页显示的图片来源没有越过本轮输入边界，且不需要推断图片与正文之间的自然语言等价关系。

### 为什么不做整句 evidence 的图片逐字校验

`evidence` 既可来自正文，也可来自截图，还可概述多来源事实。要求其同时逐字存在于每个 source ref 会制造假阴性；若未来要逐原子审计，应新增 evidence item 与 source 的一对一数据模型，而不是扩张本次输入隔离门禁。

## 影响范围

| 范围 | 影响 |
|---|---|
| `backend/kb-service` | 图片输入白名单和来源集合校验保持；移除 evidence-to-OCR 强匹配。 |
| KBD27736 | `img:2` 的合法引用不再被误拒；该 Candidate 仍由脱敏 Matcher 等后续门禁决定。 |
| 既有 KBD 数据 | 不自动重抽、覆盖或发布；仅专家显式重抽时使用新逻辑。 |
| 文档与测试 | 记录首版规则的回归，补充正文证据与辅助图片联合引用测试。 |

## 验收标准

1. solution/root_cause/未知章节图片及其自由上下文不进入 Signal Prompt；
2. 诊断章节图片的真实区域 ref 可被 Candidate 引用；
3. 被过滤或未实际输入的图片 ref 被拒绝；
4. 正文 evidence 与合法诊断图 ref 可以共存，不触发图片逐字追溯错误；
5. KBD27736 型 Candidate 继续到 Matcher 门禁并给出脱敏 pattern 的真实拒绝原因；
6. 不自动修改任何既有 KBD revision 或发布状态。
