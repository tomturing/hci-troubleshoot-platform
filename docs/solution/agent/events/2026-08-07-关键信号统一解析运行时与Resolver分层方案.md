# 关键信号统一解析运行时与 Resolver 分层方案

> 本事件归档六个相关问题：解析能力是否应统一、`qfk_system` 的边界如何划分、“解析内核”是否是合适命名、知识生产门禁与运行时消费校验如何分工、解析规则如何维护和扩展，以及如何设计实现“关键信号统一解析运行时”。
>
> 本文是方案事件文档，描述 WHAT + WHY；实施任务见 [对应任务文档](../../../task/agent/events/2026-08-07-关键信号统一解析运行时与Resolver分层任务.md)。
>
> 关联现行全量文档：[agent设计.md](../02-架构设计/agent设计.md)、[agent工具设计.md](../02-架构设计/agent工具设计.md)、[qfk_log统一日志采集解析与判定设计.md](../02-架构设计/qfk_log统一日志采集解析与判定设计.md)。

## 背景与需求

当前 KBD/Signal 链路存在多种“模型输出可读、但不一定可执行”的输入：

```text
qfk_log：服务名、basename、部分路径、版本目录、轮转/压缩文件
qfk_system：acli.vm.config.get 与 acli vm config get 的表示漂移
qfk_vm/network/storage/hardware/platform：命令、参数、版本能力漂移
qfk_service：服务组、服务名、只读动作的组合约束
qkv_alert/task/dialog：查询参数、输出契约和变量提取规则
变量：{{HOST}}、{{END}}、{{VM}} 等运行时值未解析或类型不符
```

仅依赖 LLM Prompt 无法保证执行正确性；仅依赖保存时校验又无法知道目标 HCI 的当前版本、文件布局和能力状态。因此需要统一的解析生命周期，同时保留领域语义边界。

本方案要达到的最终不变量是：

```text
未经 Schema 校验、Catalog 编译、能力解析和安全验证的 Signal，不能进入执行器。
```

## 六个问题与结论

### 问题一：解析能力是否维护多个，还是共用一个？

**结论：共用一个解析平台，不维护多个相互独立的解析内核，也不建立一个包含所有业务分支的超级解析器。**

采用：

```text
Shared Resolution Runtime
├── LogResolver             qfk_log：日志文件、目录、日期、归档
├── SystemResolver          qfk_system：Shell 上的 aCLI 系统命令
├── DomainResolver          qfk_vm/network/storage/hardware/platform：aCLI 领域命令
├── ServiceResolver         qfk_service：服务组、服务名、只读动作
├── QkvResolver             qkv_alert/task/dialog：QKV 查询和输出契约
└── VariableResolver        {{HOST}}/{{END}}/{{VM}}：变量来源、类型、依赖
```

共享平台提供：

```text
SignalIntent、ResolutionPlan、ResolvedAcquisition
Schema 校验、Catalog 加载、别名索引、状态机、错误码、安全策略、探针接口、审计
```

领域 Resolver 提供：

```text
该领域的候选展开、版本规则、能力探测、唯一性判断和执行参数编译。
```

这样避免两种极端：

| 方案 | 主要问题 |
|---|---|
| 多个独立解析器 | Schema、错误、Fail Closed、审计和候选排序容易漂移 |
| 一个超级解析器 | 日志路径、命令语法、服务能力互相污染，分支和安全边界不断膨胀 |
| 共享平台 + 领域插件 | 共用生命周期和安全契约，保留领域语义隔离；采用此方案 |

### 问题二：`qfk_system` 是否应与 `qfk_log`、`qfk_service` 合并？

**结论：`qfk_system` 单独保留。**

`qfk_system` 的本质是：

```text
在 HCI HOST-OS 或指定 aCLI container 中执行受控 Shell 形式的系统命令。
```

它与日志、服务的解析对象不同：

```text
qfk_log       → 文件目标和日志内容
qfk_service   → 服务组、服务名和只读动作
qfk_system    → Shell 上的 aCLI token、参数、执行域和命令能力
```

因此 `qfk_system` 使用 `SystemResolver`，单独维护：

```text
command_id
namespace
tokens
arguments schema
container policy
readonly/risk policy
target-version capability
```

例如：

```text
LLM 输入：acli.vm.config.get
规范 token：['vm', 'config', 'get']
最终命令：acli vm config get
```

命令内部必须优先保存为 `argv/token list`，最后一层才渲染为 Shell 字符串；禁止直接对任意字符串做点号替换后执行。

`qfk_vm`、`qfk_network`、`qfk_storage`、`qfk_hardware`、`qfk_platform` 归入 `DomainResolver` 类别，共享 aCLI 命令语法和能力探测框架，但各自使用独立的 domain Catalog 和参数 Schema。

### 问题三：“解析内核”是否是最好的名称？

**结论：内部实现可以使用“解析内核”，对外和架构文档采用更准确的正式名称：`Shared Resolution Runtime`，中文为“关键信号统一解析运行时”。**

“解析内核”容易产生两个误解：

```text
误解一：它只是一个 parser，负责把字符串转换成字符串。
误解二：它是一个低层执行内核，天然拥有执行权限。
```

实际职责包括：

```text
规范化意图
编译解析计划
运行时能力解析
候选验证与消歧
安全边界
执行前状态判断
审计和 evidence
```

因此正式命名采用：

```text
Shared Resolution Runtime
关键信号统一解析运行时
```

“Resolver”表示领域插件；“Runtime”表示它贯穿生产编译、运行解析和审计生命周期；“Kernel”可以作为内部代码包或实现层昵称，但不作为唯一架构概念。

领域 Resolver 的正式名称和稳定 `resolver_id` 采用与工具域一一对应的短名称：

| 正式名称 | `resolver_id` | 对应能力 |
|---|---|---|
| `LogResolver` | `log` | `qfk_log` |
| `SystemResolver` | `system` | `qfk_system` |
| `DomainResolver` | `domain` | `qfk_vm/network/storage/hardware/platform` |
| `ServiceResolver` | `service` | `qfk_service` |
| `QkvResolver` | `qkv` | `qkv_alert/task/dialog` |
| `VariableResolver` | `variable` | `HOST/END/VM` 等变量 |

这些名称是文档、代码类名、注册表和审计字段的规范名称。aCLI、日志目标、QKV 查询等具体技术语义保留在各 Resolver 的 Catalog、Schema 和包命名空间中，不再编码进 Resolver 类名，避免同一能力出现多套难记的名称。

### 问题四：它与知识生产门禁、qfk_log 执行前消费校验如何分工？

**结论：三个模块继续保留，但必须调用同一个解析平台，不能各自维护近似规则。**

职责划分如下：

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 关键信号抽取 | 从正文/截图得到候选语义和逐字证据 | 不决定最终物理路径或执行命令 |
| 知识生产门禁 | Schema、安全、Catalog 可编译性、变量依赖、命令/日志计划完整性 | 不假设某一台 HCI 当前文件一定存在 |
| Shared Resolution Runtime | 把候选编译成计划，并在运行时调用领域 Resolver | 不替代业务 Matcher/Parser |
| qfk_log/qfk_system 消费校验 | 执行前按现场主机、变量和能力验证计划 | 不接受未经 Resolver 验证的原始字符串 |
| Executor | 执行已验证的结构化命令 | 不负责猜测、纠错或补全语义 |
| Matcher/Parser | 解释执行输出并作业务判定 | 不负责目标定位 |

保存时流程：

```text
原始输入
  → SignalIntent
  → Shared Runtime.compile
  → LogResolutionPlan/AcliCommandPlan
  → 生产门禁
  → 专家审核/发布
```

执行时流程：

```text
已发布 Plan
  → 变量解析
  → 目标 HCI 能力探测
  → Shared Runtime.resolve
  → ResolvedAcquisition
  → 消费校验
  → Executor
```

生产门禁和消费校验不是重复模块：

```text
生产门禁保证“知识可解释、可编译、可审核”；
消费校验保证“计划在当前环境可执行、目标唯一、证据真实”。
```

### 问题五：解析规则如何维护、存储和新增导入？

**结论：规则源文件 Git 化、算法 Python 化、运行快照不可变、数据库保存生命周期和审计。**

建议目录：

```text
backend/shared/log_resolution/
├── core/                    共享模型、编译器、状态机、安全、审计
├── resolvers/               log/acli_system/acli_domain/service/qkv/variable
├── probes/                  aCLI help、路径、归档、版本能力探针
└── catalogs/                声明式 YAML/JSON 规则
```

Catalog 的权威来源是 Git 文件，数据库不直接热改执行语义。数据库可保存：

```text
草稿、专家审核状态、已发布 Plan 版本、运行时 ResolvedTarget、失败统计和审计。
```

新增规则流程：

```text
新增/修改 Catalog
  → Catalog Compiler
  → Schema/别名冲突/安全根/能力 handler 校验
  → 领域 fixture 和版本矩阵测试
  → 代表性 HCI 只读 Canary
  → PR 审核
  → 发布不可变 catalog_version
```

新增普通日志或新版本路径只增加 Catalog 数据；只有出现新的解析语义或新的协议，才修改 Resolver Python 代码。

### 问题六：如何设计实现这个“关键信号统一解析运行时”？

**结论：采用确定性的 Python/Pydantic Runtime、Git 版本化声明式 Catalog、注入式只读能力探针和统一 Resolver Registry；LLM 只产生 `SignalIntent`，不产生可直接执行的命令或路径。**

这个结论来自一个可审计的不变量：解析结果必须同时回答“它是什么”“依据什么规则”“在这台 HCI 上是否存在/支持”“执行时到底使用什么绝对目标”。因此运行时不是一个字符串 parser，而是一个小型编译器加能力验证器。它应被设计为纯编译阶段和有现场副作用边界的解析阶段，避免把环境事实混入知识生产。

#### 6.1 分层结构

```text
SignalIntent
      │  Schema/安全/引用检查
      ▼
Runtime.compile() ── Catalog Compiler ──► ResolutionPlan（可发布、可审计）
      │                                      │
      │ 变量绑定、能力探针、候选验证        │ catalog_version / 规则指纹
      ▼                                      ▼
Runtime.resolve() ── Resolver Registry ──► ResolvedAcquisition
                                              │ verified == true
                                              ▼
                                      Consume Gate → Executor
                                              │
                                              ▼
                                      Matcher / Parser
```

实现上分为六层，边界必须稳定：

| 层 | 责任 | 关键产物/约束 |
|---|---|---|
| Contract | 定义跨 Resolver 的输入输出、状态和错误码 | `SignalIntent`、`ResolutionPlan`、`ResolvedAcquisition`、`ResolutionIssue`；Pydantic 严格校验 |
| Compiler | 把意图和 Catalog 编译为候选计划 | 别名、错别字映射、argv、变量依赖、版本条件、路径安全根、歧义策略；禁止网络和现场写操作 |
| Resolver | 实现领域语义 | `LogResolver`、`SystemResolver`、`DomainResolver`、`ServiceResolver`、`QkvResolver`、`VariableResolver`；不跨域猜测 |
| Probe | 读取目标环境事实 | aCLI `version/help`、路径/符号链接、归档成员、服务 capability；接口可注入，便于离线测试 |
| Gate | 控制状态迁移和执行权限 | compile gate、publish gate、consume gate、executor gate；只有 `verified` acquisition 才能执行 |
| Audit | 保存可重放证据 | catalog/resolver 版本、输入摘要、候选顺序、探针结果、最终绝对路径/argv、失败码、时间和 TOCTOU 指纹 |

#### 6.2 代码形态与职责分配

首选 Python 实现，因为现有 Agent Service、Schema 和测试基础均为 Python；Pydantic 负责边界数据模型和反序列化，不承担路径或命令语义。Catalog 使用 Git 中的 JSON/YAML（当前实现为 JSON）声明稳定规则，启动或发布时由 Catalog Compiler 编译为只读索引；数据库只保存发布快照、草稿和运行审计，不作为执行语义的热修改入口。

Runtime 的最小接口应保持窄而确定：

```python
plan = runtime.compile(intent, catalog_version="...")
acquisition = runtime.resolve(
    plan,
    context=RuntimeContext(host="...", end="...", vm_id="..."),
    probe=CapabilityProbe(...),
)
executor.execute(acquisition)  # 仅接受 acquisition.verified is True
```

其中 `CapabilityProbe` 必须是依赖注入接口：线上实现执行只读 SSH/aCLI/path 查询，单元测试实现内存文件树和固定 capability fixture。Resolver 不直接创建 SSH 连接、不写文件、不解压归档；它只消费探针返回的证据并进行候选排序、唯一性判断和参数编译。

#### 6.3 状态机和 Fail-Closed

```text
EXTRACTED → COMPILED → NEEDS_PROBE → RESOLVED
                         │               │
                         ├─ INVALID      ├─ AMBIGUOUS
                         ├─ UNSUPPORTED  └─ NOT_FOUND
                         └─ PROBE_ERROR
```

状态迁移必须单向且有结构化 `failure_code`。未知命令、未知日志源、未解析变量、多个同优先级候选、路径越过允许的安全根、归档无法证明成员存在时全部 Fail Closed；不得通过“最像的字符串”或 LLM 再猜一次来绕过门禁。`ResolvedAcquisition` 必须携带 `verified=true`、唯一目标、完整 `argv` 或 `absolute_path`，否则 Executor 拒绝。

#### 6.4 Catalog Compiler 和发布流程

Catalog Compiler 在 CI 和发布时执行以下检查：Schema 合法性、`resolver_id`/`capability_id` 唯一性、别名和 typo 冲突、路径安全根、版本区间可判定性、命令参数 Schema、archive handler 存在性，以及候选排序是否可能产生不可消解并列。编译产物包含 `catalog_version` 和规则指纹，运行时只加载完整且不可变的版本。

新增或修改规则必须经过：

```text
Catalog PR → Compiler → fixture/版本矩阵 → 只读 HCI canary
           → 专家审核 → 发布 catalog_version → Runtime 加载
```

新增普通路径、服务别名或命令参数优先修改 Catalog；只有新增解析语义、探针协议或归档格式才修改 Python Resolver，并必须增加回归测试。回滚通过选择旧 `catalog_version` 完成，不能在数据库中手改线上规则。

#### 6.5 为什么不把实现交给 LLM、Handler 或 Executor

LLM 适合从文本/截图抽取候选和证据，但无法证明现场存在性、唯一性和版本能力；Handler 适合编排工具输入输出，不应复制一套路径/命令规则；Executor 只应执行已验证的 argv/绝对路径，若在此处猜测会把知识错误变成现场副作用。统一 Runtime 将确定性规则、现场事实和执行权限分开，既能离线重放，也能在对抗性输入下 Fail Closed。

#### 6.6 最小可观测性和测试矩阵

每次 compile/resolve 都应输出结构化事件（不得记录凭据）：输入摘要、catalog/resolver 版本、候选及淘汰原因、探针证据、最终目标、耗时、失败码和文件 inode/size/mtime 指纹。测试至少覆盖：别名/错别字、D/DD/today、符号链接、普通 gzip 与 tar.gz 区分、未知命令、参数类型、跨域命令、变量缺失、并列候选和探针异常；线上先以只读 canary 验证，再允许执行。

### 补充专题：QkvResolver 如何处理“开启虚拟机”这类关键词错误？

`qkv_task -k` 与 `qfk_log` 的文件名定位有相同的不变量：LLM/用户输入只是候选，不是 aCLI 的最终规范值。不同之处在于，QKV 的关键字是查询条件；错误纠正若过度激进，可能把一个任务类型误查成另一个任务类型。因此必须采用“规范化动作 ID + 有界别名 + 现场验证”的三级流程，而不是直接对任意中文字符串做模糊搜索。

#### QKV 关键词解析流程

```text
原始关键词：开启虚拟机
        │
        ▼
文本规范化：Unicode、空白、标点、同义字清洗
        │
        ▼
动作本体匹配：vm.power_on
        │       ├─ 规范中文：启动虚拟机
        │       ├─ 允许别名：开启虚拟机、开机虚拟机、启动 VM
        │       └─ 错别字候选：仅来自受控 alias/编辑距离规则
        ▼
查询计划：keyword_candidates=[启动虚拟机, 开启虚拟机]
        │
        ├─ 先查规范词
        ├─ 无命中再按上限查别名
        ├─ 记录每次 match_count 和返回样本
        └─ 多候选无法消歧 → AMBIGUOUS，禁止猜测
```

动作本体是稳定的内部标识，不应把中文展示词当作主键：

```json
{
  "action_id": "vm.power_on",
  "query": "task",
  "canonical_keywords": ["启动虚拟机"],
  "aliases": ["开启虚拟机", "开机虚拟机", "启动VM", "开虚拟机"],
  "negative_aliases": ["恢复虚拟机", "重启虚拟机"],
  "status_policy": "status_is_separate_filter"
}
```

`negative_aliases` 很重要：`启动`、`重启`、`恢复`、`开机`在自然语言中相近，但在 HCI 操作语义中不是同一动作，不能只依据编辑距离合并。

#### 词典来源和可信等级

建议把候选词分成四类，并在审计中记录来源：

| 来源 | 用法 | 是否可自动执行 |
|---|---|---|
| 专家审核的 Action Catalog | 规范词、稳定别名、反例词 | 可以；优先级最高 |
| aCLI/产品文档 | 命令描述、官方动作名称 | 经审核导入后可以 |
| `log_translation` 聚合出的 `type` 对 | 发现历史中实际出现的中英文动作标签 | 只能作为候选证据，不能直接发布为别名 |
| LLM/编辑距离/向量相似度 | 生成待审核候选 | 不能直接执行 |

`log_translation` 是实例翻译记录，但可以通过聚合稳定的 `type` 对提取词汇证据；必须忽略或降权 `object_name`、`description` 中的动态主机/VM/参数。`alert_translation` 同理只能帮助建立告警事件词汇，不应拿来充当 task 动作词典。

#### 有界回退而不是无限模糊查询

QkvResolver 的运行时回退应满足：

1. 先使用规范词查询；
2. 无命中时最多尝试固定数量的已审核别名（建议 3 个）；
3. 每次查询记录 `keyword_tried`、`match_count`、首条样本的 `type/action_id`、时间窗口和状态过滤；
4. 只有一个候选产生与动作 ID 一致且满足上下文约束的结果时才 `VERIFIED`；
5. 多个候选都有命中但动作 ID 不一致时返回 `AMBIGUOUS`；
6. 所有候选都无命中时返回 `NOT_FOUND`，并保留规范词与别名列表；
7. 不得让“模糊命中”直接变成成功，也不得无界地扩展同义词。

查询结果不能只用 `exit_code==0` 判断成功。至少要区分：

```text
query_executed
match_count
canonical_action_match
result_time_range
result_status_distribution
```

#### 结构化条件优先于文本关键词

若 Signal 已知 `HOST`、`VM`、`END`、`status` 或 `UPID`，应优先把它们转成 aCLI 的结构化选项：

```text
task + keyword + HOST + END + failed
  → -k <canonical> -H <host> -t <absolute-time> -s failed
```

若动作词仍不可靠，但已有 `UPID`、主机、VM ID 或明确时间，应优先使用：

```text
-u/--upid
-H/--host
-v/--vm-id
-t/--time
-s/--status
```

这样可以把“关键词纠错”从唯一识别条件降级为辅助条件，减少同义词和翻译差异导致的漏查。

#### 对当前实现的明确判断

当前 `QkvResolver` 已完成：

```text
query 类型校验
keyword 非空校验
limit 限制
alert/task/dialog 命令模板编译
```

当前尚未完成：

```text

```

因此“开启虚拟机 → 启动虚拟机”的能力目前仍属于待实施设计，不能宣称当前 Runtime 已经自动支持。

## 统一运行时对象模型

### `SignalIntent`

表示模型或专家输入的结构化意图，不是最终命令。

### `ResolutionPlan`

表示保存时编译的候选布局、命令 token、变量依赖、归档策略和歧义策略。

### `ResolvedAcquisition`

表示运行时已经验证的目标和执行输入：

```python
class ResolvedAcquisition(BaseModel):
    resolver_id: str
    capability_id: str
    argv: list[str]
    target: dict[str, Any]
    verified: bool
    candidates_tried: list[str]
    resolution_rule: str
    catalog_version: str
```

`qfk_log` 的 `target` 可以包含：

```text
absolute_path、source_id、family、parser、archive_kind
```

`qfk_system` 的 `target` 可以包含：

```text
namespace、command_id、container、host、capability_version
```

二者使用同一个输出封装，但内部 target 语义不同。

## LLM 边界

LLM 可以：

```text
识别服务别名
提取命令候选
提取截图中的文件名
提出错别字候选
生成 evidence 和 confidence
```

LLM 不可以：

```text
决定最终绝对路径
判断目标文件存在
决定 D/DD 或版本布局
发明 Catalog 中不存在的命令
绕过 Resolver 直接执行 Shell
```

未知命令、未知日志源和多候选都必须 Fail Closed，并返回结构化原因。

## 决策依据（为什么选此方案，为什么不选其他方案）

### 不采用“每个工具一套独立解析内核”

会造成：

```text
Schema、错误码、Fail Closed、能力探测、审计和版本语义漂移。
```

### 不采用“一个万能 Resolver”

会造成：

```text
qfk_log 的路径安全规则污染 aCLI 命令规则；
命令兼容逻辑不断进入核心 if/else；
新增领域变更范围过大；
安全边界组合爆炸。
```

### 不采用“LLM 直接纠错并执行”

LLM 可以提出近似候选，但不能证明：

```text
命令存在、文件存在、版本支持、目标唯一、路径安全。
```

### 不采用“只保留保存门禁”

保存时通常无法知道目标 HCI 的真实版本、目录、压缩和能力状态。

### 不采用“只在消费前动态猜测”

会使错误知识长期留在数据库，每次执行重复纠错，并把知识问题转化为运行时误诊风险。

## 验收标准

### 架构验收

- [ ] 存在唯一 Shared Resolution Runtime 注册入口。
- [ ] `qfk_log`、`qfk_system`、`DomainResolver`、`qfk_service`、QKV 和变量均通过统一 Resolver 接口接入。
- [ ] `qfk_system` 与 `qfk_log`、`qfk_service` 分离；`qfk_vm/network/storage/hardware/platform` 归入 DomainResolver。
- [ ] 原始 LLM 字符串不能直接进入 Executor。

### 命令解析验收

- [ ] `acli.vm.config.get` 可规范化为 `['acli', 'vm', 'config', 'get']`。
- [ ] Catalog 外的命令返回 `UNSUPPORTED_COMMAND` 或 `CAPABILITY_UNAVAILABLE`，不执行。
- [ ] 内部优先使用 token/argv，不通过未经验证的字符串替换构造 Shell。

### 日志解析验收

- [ ] vtpdaemon 覆盖 D/DD、vt/根目录、today、gzip rotation 等已知布局。
- [ ] 运行时返回已验证的 `absolute_path` 或结构化失败原因。
- [ ] 多候选时 Fail Closed 并保留 candidates_tried。
- [ ] blackbox tar.gz 使用专用 archive handler，不能当普通文本 gzip 处理。

### 治理验收

- [ ] Catalog 规则来自 Git 版本化文件并有 compiler 校验。
- [ ] 数据库只保存草稿、发布版本、运行审计和反馈，不直接热改执行语义。
- [ ] 新增命令/日志源必须附带 Catalog fixture、版本矩阵和能力探针测试。
- [ ] 生产门禁与消费校验共用同一 Resolver/Catalog，不维护近似副本。
