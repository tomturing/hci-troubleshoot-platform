# KBD 发布消费一致性与专家审核易用性方案

## 一、问题与结论

KBD30880 已证明“数据库保存成功、Expert Revision 和 Dynamic Resource Active 一致”仍不足以证明 Agent 会消费：旧 Proposal 携带的 `generation_metadata.tool_contract_revision` 与当前代码契约不同，KB 清单把已发布 KBD 标为 `executable=false`。KBD40061 又暴露了旧抽取器同时维护 `signals[].role` 与 `verification_contract.evidence_policy`，两份事实冲突后，专家只编辑无关字段也会改变执行语义。

本轮采用轻量、可演进的修复，不新增流程系统和数据库表：

```text
LLM Proposal 原始生成指纹（不可变）
              ↓
专家编辑 + 当前 Schema/参数/变量 DAG 发布门禁
              ↓
publish_validation（独立发布盖章）
              ↓
Dynamic Resource Active
              ↓
Agent 继续编译真实 Handler、变量 DAG 和判定器
```

核心原则：

1. 生成事实与发布事实分开，不能为了让当前版本通过而覆盖 LLM 原始指纹；
2. Admin 发布门禁与 Agent 消费 freshness 使用同一份工具契约 revision；
3. 发布盖章只证明当前静态契约通过，不冒充真实客户环境执行成功；
4. 旧 role/Contract 冲突以历史运行时已经消费的 Contract 做一次读取规范化，Proposal 保持不可变；
5. 页面主路径只展示专家能理解、能处理的信息，高级工程字段默认收起。

## 二、发布盖章设计

### 2.1 为什么不能覆盖 generation_metadata

`generation_metadata.tool_contract_revision` 表示 LLM 生成 Proposal 时使用的工具契约，是后续评估“模型当时看到了什么”的必要输入。专家发布时把它改成当前 hash 会伪造生产历史，使 Proposal→Expert 差异和 Champion/Challenger 评估失真。

因此在 `signals_json` 增加可选对象：

```json
{
  "publish_validation": {
    "schema_version": 1,
    "status": "passed",
    "tool_contract_revision": "<当前全部 Signal Schema 的 SHA-256>",
    "validator": "expert_publish_gate"
  }
}
```

数据库仍使用现有 `kbd_entry.signals_json JSONB` 与 revision payload，不新增列或表。该字段由 Schema 生成器产生并受 CI 漂移检测。

### 2.2 发布与消费规则

Expert 初次发布、重新发布和 maintenance 发布统一执行：

1. 规范化历史 role/Contract 冲突；
2. 重建证据策略投影；
3. 校验 v2 JSON Schema；
4. 校验 `acquire.args` 运行语义；
5. 校验 QKV produces、QFK match/produces 二选一；
6. 校验稳定 Signal ID；
7. 校验 diagnostic 变量 DAG、未声明外部变量与循环依赖；
8. 写入当前 `publish_validation`；
9. 再次校验最终持久化文档；
10. 冻结 Expert Revision 并切换 Dynamic Resource Active。

KB 分类清单和 Agent Plan Compiler 的 freshness 规则为：

```text
有 publish_validation
  → 校验发布盖章状态和当前 tool_contract_revision
无 publish_validation、但有 generation_metadata
  → 兼容校验原始生成状态和 revision
两者都无
  → 兼容 engineering fixture/历史手工数据，继续执行其他硬门禁
```

Agent 不信任盖章替代运行编译，仍继续校验 Handler 命令构建、变量依赖、证据策略与 matcher。真实 Evidence/Execution Replay 仍是另一层验收。

## 三、历史角色冲突规范化

### 3.1 根因

旧 KBD40061 Proposal 中：

```text
signals[].role：五条全是 must
verification_contract：sig_002、sig_003 是 should，minimum_should=1
```

历史 Agent 一直消费 Contract。若新编辑器无条件以 role 重建 Contract，专家只修改 `produces` 或说明也会把五条全部改成 must，这属于隐式语义漂移。

### 3.2 兼容规则

- 新保存数据：`signals[].role` 是专家编辑事实源，Contract 是单向投影；
- 读取旧冲突数据：先以已有 Contract 回填冲突的 role，再交给专家；
- 专家保存：形成新的 Expert Revision，role 与 Contract 从此一致；
- 原 Proposal Revision 不更新、不回写，保留 LLM 原始错误用于评估；
- Signal 增删、复制、排序仍以稳定 `id` 对齐，与数组下标无关。

该设计不需要一次性改写不可变 revision，也不会让未审核旧数据在后台静默改变。

## 四、替代证据与 QKV 锚点

四类证据语义：

| 类型 | 专家可见文案 | 结论语义 |
|---|---|---|
| must | 必要证据（必须满足） | 所有 must 必须成立 |
| should | 增强证据（按门槛满足） | 至少满足 `minimum_should` 条 |
| exclude | 排除证据（出现即排除） | 任一成立即排除本 KBD |
| context | 上下文证据（执行但不参与结论） | 执行并保留证据，不改变结论 |

`qkv_alert OR qkv_task` 表达为：

```json
{
  "should": ["sig_alert", "sig_task"],
  "minimum_should": 1
}
```

若 task 必须、alert 只是加分项，则 task 设 must，alert 设 should，并把 `minimum_should` 设为 0。

页面新增“增强证据至少满足 N 条”编辑入口。两个生产者都返回 `HOST/END` 时，变量池采用固定优先级：

```text
qkv_task > qkv_alert > qkv_dialog
```

因此 task 记录存在时总是作为下游 qfk_log 的锚点；task 不存在时才使用 alert/dialog，结果不依赖异步执行顺序。

## 五、END 与 qfk_log

`END` 是跨工具标准变量，变量池只保存 HCI 本地绝对时间。显式 `produces` 与旧硬编码抽取现在调用同一时间规范化逻辑；qfk_log 再按日志族转换：

```text
whitebox       → acli log get ... -t 'YYYY-MM-DD HH:MM:SS'
blackbox       → Catalog/Handler 按 END 定位 YYYYMMDD 目录
vn_blackbox    → Catalog/Handler 按 END 定位日期目录
```

专家主界面只显示说明、主机、时间、文件、判定、匹配内容、期望、超时和只读输入变量。`source_family/path/parser/.gz` 放入“日志定位高级设置”：

- file 只填 basename；
- path 为空表示默认 `/sf/log` 通用定位，不误称精确 Catalog 命中；
- source_family 为空/auto 表示按文件和路径推断；
- parser 对关键字/正则审核通常无须编辑；
- `.gz` 开关只表示显式 path 下搜索归档，普通 whitebox 由 END 和 aCLI 自动定位、解压。

## 六、阈值判定

KBD40061 的 `df` 输出包含表头 `1K-blocks`，通用 `first_number` 原来会取到 1，而不是 `Use%=54`。Matcher 现在识别标准 `df` 表头并确定性读取首条数据行的 Use%：

```text
Filesystem 1K-blocks Used Available Use% Mounted on
/dev/sda5   ...                         54% /sf/log
```

与 80 比较的实际值为 54。专家仍可在“指标字段”填写 `/sf/log`，只解析包含挂载点的行；普通非 df 输出继续保持既有数字聚合语义。

## 七、专家页面信息架构

1. role、matcher、匹配模式、期望结果使用中文括号直接解释；
2. Evidence 放入每条 Signal 内“来源证据”折叠卡片，默认关闭；
3. 生成模型/Prompt/指纹保持在“生成追溯详情”，默认关闭；
4. qfk_log 工程字段放入高级设置；
5. threshold 不再被前端错误要求填写 keyword pattern；
6. 发布门禁错误继续转换为专家可操作的中文说明。

Evidence provenance 是原始事实，不直接覆盖。专家对 Signal 的增删与修改通过 revision diff 表达，不篡改 Proposal 原始来源。

## 八、数据库与迁移

本轮不新增数据库表、字段或索引。`publish_validation` 是现有 JSONB 契约的可选扩展：

- 新 Expert 发布自动写入；
- 旧 Proposal Revision 保持不可变；
- 已发布但没有盖章的 KBD 必须在部署后显式发布 maintenance，不能在读请求中自动认证；
- 显式发布后 Dynamic Resource 生成新 revision，Agent active 指向带盖章内容；
- 不能用 SQL 批量伪造“已通过当前代码校验”的事实。

## 九、本轮明确不做

按用户 2026-07-31 的范围决定，本轮不修改：

1. Embedding 失败时清空/保留旧向量的行为；
2. qfk_system 默认执行边界改为 host；
3. qfk_system 与宿主机/容器命令的最终边界。

此外仍未完成：可信 Admin SSO、真实客户环境 Agent compile/replay、完整 Evidence/Execution Replay、reason_code、评估导出、Capability Gap 聚合、122 条正式专家复核、Champion/Challenger 和 Expert Gold。

## 十、回滚

- 旧消费者忽略新增 JSON 字段；新消费者在无发布盖章时回退原 generation 规则；
- 发布失败不切 active；
- 删除 `publish_validation` 即恢复旧 freshness 行为；
- 历史规范化只发生在读取副本，未保存时不改数据库；
- qfk_task 优先级只影响同名变量冲突，不改变单生产者 KBD。
