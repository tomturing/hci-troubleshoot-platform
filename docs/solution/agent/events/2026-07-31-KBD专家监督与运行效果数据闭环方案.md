# KBD 专家监督与运行效果数据闭环方案

## 1. 结论

在不引入重型审批工作流、不虚构真实客户执行结果的前提下，本轮先闭合**可由现有平台独立产生**的数据：专家修订原因、专家删除原因、Agent 实际消费的精确 KBD 运行时版本、CDD 编译结果、逐信号 outcome、Capability Gap、发布后使用效果、失败模式统计，以及供后续模型评估使用的结构化导出。

不能由代码单独产生的数据——可信专家身份、Expert Gold、Evidence/Execution Replay、真实客户环境执行、Challenger 与 Champion/Challenger 对比——保持显式未完成状态，不能以静态校验、hci-sim 或 Mock 替代。

## 2. 第一性原理与目标边界

KBD 的知识正确性不是单一字段，也不是一次审核按钮能够证明。至少有四个独立事实：

1. **来源与模型稿**：LLM 基于哪个原始案例、截图和 Prompt 产生了什么 Proposal；
2. **专家修订**：专家对哪一个稳定字段或 `signal_id` 作了何种改动，以及为什么；
3. **发布内容**：Agent 在某次诊断真正读取的是哪一个不可变 Dynamic Resource revision；
4. **运行效果**：该版本被 CDD 编译、调度和判定后，每个 Signal 的实际 outcome 是什么。

若缺任一环，后续模型优化只能看“结果像不像”，无法区分截图识别错误、信号遗漏、工具参数错误、能力缺口或现场执行失败。因此本方案以**可追溯的最小事实链**为目标，而非新增一个流程管理系统。

```text
原始案例 / 截图
        │
        ▼
LLM Proposal Revision（generation_metadata）
        │
        ▼
Expert Revision（payload_json + review_metadata）
        │ 显式发布
        ▼
Dynamic Resource KBD Revision（精确 resource_revision）
        │ Agent 实际诊断消费
        ▼
CDD Compiler + 每个 Signal outcome
        │
        ▼
dynamic_resource_usage_audit
        ├── runtime-metrics：使用效果 / 失败模式
        ├── capability-gaps：平台工程待办
        └── evaluation-export：后续评估与训练样本出口
```

`payload_json` 仍是知识正文唯一事实源。`review_metadata` 不保存第二份 before/after 正文，而是通过 `parent_revision_id + payload_json` 重算 Diff 后，给每个变化补充受控 `reason_code`；这样不会形成两份可能漂移的知识。

## 3. 十四类数据的分层决策

| 数据 | 本轮状态 | 依据与实现边界 |
|---|---|---|
| `reason_code` | 已落实 | `kbd_revision.review_metadata.change_summary` 保存受控原因码；未标注项仅保守推断并标记 `reason_source=inferred`。|
| 可信 reviewer actor | 暂不做 | 依赖 Admin SSO/签名身份。现有 `reviewer_id` 只能标记 `unverified_body_reviewer_id` 或 `unavailable`。|
| 专家删除原因 | 已落实 | 删除 Signal 必须选择原因，可填说明；绑定稳定 `signal_id`，不绑定页面数组下标。|
| Expert Gold 状态 | 仅落实否定资格 | `expert_gold.status=not_eligible` 与 blockers 可导出；不生成 Gold。|
| 当前 Tool Contract 成功编译结果 | 已落实真实运行记录 | 发布静态校验与真实 CDD 编译分开；Agent 诊断时记录 `plan.compile_errors` 和 compiler 名称。|
| Evidence Replay | 暂不做 | 需要可寻址、可脱敏、可重复输入 Parser 的原始 Evidence artifact。|
| Execution Replay | 暂不做 | 需要完整 Handler/Validator/Bridge/Artifact 可重放契约。|
| 真实客户环境执行结果 | 暂不做 | 必须有客户侧环境和授权；Mock、fixture、hci-sim 都不等价。|
| 每个 Signal outcome | 已落实 | 记录 `SATISFIED/CONTRADICTED/UNKNOWN/ERROR/BLOCKED/NOT_APPLICABLE`、失败模式和关联 ID。|
| Capability Gap | 已落实 | 由 Signal 引用工具与 Capability Descriptor 派生聚合，只供平台工程治理，不显示为专家普通待办。|
| 发布后的使用效果 | 已落实 | 按实际运行审计聚合资源使用状态、候选状态、编译状态和 Signal 分布。|
| Challenger 输出 | 暂不做 | 应以冻结来源和可信 Expert Gold 为基线，当前不能将未认证稿冒充 Gold。|
| Champion/Challenger 对比 | 暂不做 | 依赖 Challenger 与 Gold 基线。|
| 失败模式分层统计 | 已落实 | 聚合 `dependency_unresolved`、`tool_execution_error`、`matcher_indeterminate`、`scope_not_applicable`。|

## 4. 已实现设计

### 4.1 专家监督数据

在既有 `kbd_revision` 增加 `review_metadata JSONB NOT NULL DEFAULT '{}'`，不新增审批、Gold 或 Registry 表。它保存：

- `review_state` 与诚实的 `identity_status`；
- 受控原因码、可选说明、`expert|inferred` 来源；
- 专家删除 Signal 的稳定 `signal_id` 绑定；
- 当前不能称为 Gold 的 blockers。

删除界面要求专家选择原因；正文与截图 Evidence 不删除，仅从 Agent verification contract 移除 Signal。连续保存时，Diff 相对**直接父 Expert revision**计算，避免将以前已经修订的数据重复归为本次修订。

### 4.2 运行时消费与结果审计

Agent 从检索响应携带的 `resource_revision` 精确读取已加载 KBD revision，绝不在诊断结束时回读 active。因为运行过程中若新版本发布，回读 active 会把旧版本的结果错误归属到新版本。

审计复用 `dynamic_resource_usage_audit`，不复制原始 stdout/stderr：

- `input_hash` / `output_hash` 继续保存摘要；
- `metadata_json` 保存计划、候选状态、CDD compiler 结果和逐 Signal outcome；
- 原始命令输出仍由 Terminal Bridge artifact 管理；
- 审计写失败只记录 warning，不能中断客户侧诊断。

`UsageStatus.SUCCESS/FAILED` 表示资源消费链是否正常完成；`SUPPORTED/REJECTED/INCONCLUSIVE` 表示案例判定，两者不能混为一谈。例如一个信号被反证并不意味着审计写入失败。

### 4.3 面向后续改进的只读出口

新增三个工程侧只读接口：

| 接口 | 用途 | 不能据此声称的事实 |
|---|---|---|
| `GET /api/v1/kbd/capability-gaps` | 聚合未声明或运行时未验证的工具能力及受影响 KBD | 不代表专家必须修改 KBD，也不证明生产 Handler 不可用。|
| `GET /api/v1/kbd/runtime-metrics` | 聚合实际 Agent 运行的消费、编译、outcome 与失败模式 | 不等同真实客户环境 replay。|
| `GET /api/v1/kbd/evaluation-export` | 导出 Proposal→Expert→Diff/reason→runtime 的样本 | 不执行 Challenger，也不输出 Expert Gold。|

导出固定携带 `facts_boundary`，将可信身份、Gold、Replay、真实客户执行、Challenger 全部标为 `false`。后续可在脱敏环境中以原因码聚类 Prompt/Schema 问题、构建评估集或偏好数据；只有满足可信身份和回放门槛后，才可筛选 Expert Gold 子集训练或比较模型。

## 5. 为什么不采用其他方案

### 不新建 Workflow / Gold / Registry 多表

这些概念当前没有独立生命周期、独立查询基数或跨对象事务需要。新增表会引入同步、权限和状态迁移成本，却不能产生缺失的客户执行证据。现有不可变 revision、Dynamic Resource revision 和 JSONB 元数据已经足以承载最小闭环；当未来 Gold 具备可信身份、证据/执行回放、独立发布门禁和大量跨 KBD 查询需求时，再将稳定部分正规化。

### 不把发布静态校验称为编译或执行成功

静态 Schema/Capability 契约只能说明输入格式可接受；真正的 CDD 编译在 Agent 取得具体候选、变量依赖和 runtime revision 后才发生；真正执行还需要客户侧 Bridge 与 HCI。把前者冒充后者会污染评估数据，直接导致模型优化方向错误。

### 不让专家处理 Capability Gap

专家负责知识事实与可执行 Signal 的编辑；Handler 部署、Catalog 缺口和平台能力是工程问题。将其混进专家审核页会显示“看得见但处理不了”的信息，违背专家易用性原则。

## 6. 验收标准与未完成边界

本轮验收：

1. 专家删除 Signal 可选择受控原因，且原因与稳定 `signal_id` 落入 Expert revision；
2. 连续专家编辑仅记录相对直接父版本的 Diff；
3. Agent 运行审计使用精确 `resource_revision`，缺失时跳过，绝不回退 active；
4. CDD compile、逐 Signal outcome、失败模式可以聚合和导出；
5. 原始执行输出不复制进评估审计表；
6. 工程接口与文档明确标注事实边界。

仍未完成：可信 Admin SSO、122 条正式专家复核、0/126 之外的 Expert Gold、Evidence/Execution Replay、真实客户环境回放、Challenger 与 Champion/Challenger 对比。它们是下一阶段的前置条件，不是本轮的隐含交付。
