# 智能体单步交互与单步命令执行控制方案

> [!IMPORTANT]
> 本方案针对系统当前“排障助手可能会在单次对话中同时输出多个问题（增加用户认知负载）或同时发起多个工具命令执行（增加高危环境运行风险）”的缺陷，提出了基于第一性原理的“单步交互契约（Single-Turn Interaction Contract）”重构设计。
>
> 方案由两部分构成：
> 1. **Prompt 强约束（提问维度限制）**：用于控制大模型的生成策略，使其每次只提问一个问题。由管理员在 Prompt 管理页面手动录入更新。
> 2. **代码硬性卡控（命令维度限制）**：在 ReAct 执行引擎中实施物理拦截，防止大模型并发下发多条 Shell 命令，确保排障操作的原子性与事务安全性。

---

## 一、 第一性原理与设计范式

根据 **人机协作控制理论（Human-Agent Interaction Control）** 与 **分布式系统状态机契约**：

1. **认知负载最小化（Cognitive Load Minimization）**：
   在复杂的 HCI 运维场景中，用户的注意力是稀缺资源。当 Agent 在一个气泡里堆砌 3 个以上跨度极大的问题时，会造成用户理解困难、回复格式混乱，进而破坏大模型的 Context 质量。每次只询问“当前最迫切的一个未知变量”，是保证数据收集准确率的唯一解。
2. **状态变迁原子性与事务化（State Transition Atomicity）**：
   超融合后台的诊断/修复动作多数属于非幂等的有状态命令。大模型并行输出并执行多个命令（如同时检查 IP、检测 SSD 状态和重启服务），会导致系统状态难以追踪。必须实现**“单步执行-结果观测-下一步决策”**的顺序串行循环（Serialized Loop）。
3. **业界最佳实践（LangGraph / CoALA 范式）**：
   - **LangGraph** 的 `Interrupt` 机制：当工作流需要用户输入时，立即挂起（Pause）当前 Graph，只显式抛出一个变量填报要求，直到接收到输入后再推进到下一个 Node。
   - **ReAct 串行卡点**：在涉及环境写操作或敏感读操作时，限制 LLM `tool_calls` 的最大并行度为 1，进行单步阻断。

## 二、 方案设计与实现

### 2.1 Prompt 优化方案（用户手动页面配置）

大模型直接打印多个问题的根源在于现有的系统提示词（如 [base_methodology_v1](file:///aihci/hci-troubleshoot-platform/database/seeds/02_system_prompts.sql#L107)）中，S1 阶段描述为 **“向客户提出 1-3 个精准确认问题”**。大模型会机械式地执行此“1-3”的指令，导致一次性输出多个问题。

#### 优化点 1：方法论模板 (base_methodology_v1)
请在平台“Prompt 管理”页面中，找到 `base_methodology_v1`（或对应的系统方法论配置项），将标准诊断流程中的 S1 和 S3 阶段描述进行如下微调：

* **修改前**：
  ```text
  S1 故障定位：向客户提出 1-3 个精准确认问题，定位到最小故障分类
  S3 验证执行：逐一执行诊断命令，收集系统状态证据
  ```
* **修改后**：
  ```text
  S1 故障定位：每次交互仅向用户提出 1 个最精准的澄清问题。如需收集特定环境参数，优先调用 sop_request_variable 工具获取。严禁在单次回复中罗列多个问题。
  S3 验证执行：每次 Thought 中只允许下发 1 个诊断命令工具调用，待观察到 Tool 输出后再决定下一步动作。严禁并发调用多个命令工具。
  ```

#### 优化点 2：增加系统级交互契约 (在 base_identity_v1 中追加)
为强化控制，建议在 `base_identity_v1`（或系统身份 Prompts）的最下方，追加如下【单步协作契约】：

```text
【单步协作契约（极其重要）】
1. 单步提问原则：无论处于什么诊断阶段，在向用户反馈时，你的发言中最多只能包含 1 个澄清问题或 1 个待确认的变量询问。严禁输出问题列表。
2. 单步工具原则：你在每轮思考中，只能输出 1 个 `tool_calls` 动作。严禁在同一次响应中批量执行多个命令或同时调用多个检索工具。
```

### 2.2 代码硬限制方案（ReAct 引擎串行阻断）

大模型即便有 Prompt 约束，在某些复杂场景下仍有可能绕过约束，一次性发起多个 `tool_calls`（Function Call）。为此，必须在 [ReactEngine.execute](file:///aihci/hci-troubleshoot-platform/backend/agent-service/app/adapters/agents/htp/react_engine.py) 代码层构筑物理防线。

#### 1. 限制单轮 Tool Call 并行度为 1
在 `ReactEngine` 执行工具调用循环时，如果大模型返回了多个 `tool_calls`，在进入 `for tc in invoke_result.tool_calls` 循环前，物理截断只保留第一个：

```diff

-                        "function": {

-                        },
-                    }

+                    original_tools=[tc.name for tc in active_calls],
```

#### 2. 工具列表控制 (针对 S1 等提问动作的降级)
在 [SopToolExecutor](file:///aihci/hci-troubleshoot-platform/backend/agent-service/app/adapters/agents/htp/sop_tools.py) 执行 `sop_request_variable` 时，如果返回的 `VariableRequestResult` 指明需要用户输入（`needs_input=True`），代码层会抛出挂起中断。

配合 Prompt 限制后，大模型会老老实实通过调用 `sop_request_variable` 单步发出对变量的卡片请求，而不会在自然语言文本中罗列未捕获的常规变量提问。

## 四、 一案一链分布式 Trace ID 关联设计

根据 **第一性原理** 故障链路观测机制，工单诊断周期的全部环节必须可通过同一个 `trace_id` 追踪检索。

### 4.1 核心关联流

```mermaid
graph TD
    Case["Case (trace_id = T1)"] -->|继承| Conv["Conversation (trace_id = T1)"]
    Conv -->|继承| SopExec["SOP Execution (trace_id = T1)"]
    Conv -->|OTel Context 绑定与传播| MsgStream["Streaming Response (trace_id = T1)"]
    MsgStream -->|HTTP Headers (traceparent)| AgentSvc["Agent Service (trace_id = T1)"]
    AgentSvc -->|OTel Context 自动提取| ToolAudit["Tool Result (trace_id = T1)"]
    AgentSvc -->|OTel Context 自动提取| PromptAudit["Audit Log (trace_id = T1)"]
```

### 4.2 包含 `trace_id` 的所有表及其关联流分析

当用户在端侧发起工单，随后经历 AI 对话、SOP 诊断以及工具执行时，数据库中全部 14 张包含 `trace_id` 属性的实体表，其流转与染色绑定机制如下：

#### 1. 工单与客户实体层 (Root)
* **`case` 表**：
  * **设计机制**：前端调用 POST `/api/cases` 时，`api-gateway` 产生/透传第一个追踪 ID（设为 `T1`），落库为 `case.trace_id = T1`。
* **`user` 表**：
  * **设计机制**：临时用户（Client ID 绑定）随工单创建而在同一个 API 事务中创建，落库为 `user.trace_id = T1`。
* **`customer` 表**：
  * **设计机制**：由管理员导入/创建，通过对应管理接口请求的 Trace 链自动记录，落库为 `customer.trace_id = T1`。

#### 2. 交互会话与消息层
* **`conversation` 表**：
  * **设计机制**：会话创建是单独的异步网络请求。我们通过 `create_conversation` 查询 Case 的 `trace_id` 并覆盖，实现**会话继承工单 Trace**：`conversation.trace_id = case.trace_id = T1`。
* **`message` 表**：
  * **设计机制**：每次发送消息，我们在 `send_message_stream_only` 头部提取会话的 `trace_id` 并将其挂载到 OpenTelemetry 的活跃 Span 追踪上下文（Context）中。保存消息时的 `get_current_trace_id()` 自动返回并存储 `message.trace_id = T1`。
* **`session` 表**：
  * **设计机制**：用户/客户的 Web 登录与会话管理在网关或 `conversation-service` 验证请求时发生，通过 OTel 中间件提取首跳请求的 Trace 并关联，落库为 `session.trace_id = T1`。

#### 3. 诊断与执行状态层
* **`sop_execution` 表**：
  * **设计机制**：命中 SOP 创建诊断实例时，我们通过路由直接获取关联 `conversation` 的 `trace_id` 并赋值给 `execution.trace_id`，实现**执行实例继承会话 Trace**：`sop_execution.trace_id = conversation.trace_id = T1`。
* **`diagnostic_item` 表**：
  * **设计机制**：在执行诊断树节点或更新诊断项状态时，状态机判定逻辑通过当前活跃协程的 OTel 上下文自动提取当前活跃 Trace ID，落库为 `diagnostic_item.trace_id = T1`。
* **`skill_definition` 表**：
  * **设计机制**：技能定义/导入/更新由管理端触发，在同步/导入请求生命周期中通过 OTel 自动提取并落库，关联 Trace ID。

#### 4. 智能体审计与工具层
* **`tool_result` 表**：
  * **设计机制**：ReAct 引擎在写入工具执行审计记录时，显式透传当前上下文的 Trace ID，如果为空则调用 `get_current_trace_id()` 从活跃 OTel Context 中动态 fallback 捕获，落库为 `tool_result.trace_id = T1`。
* **`audit_log` 表**：
  * **设计机制**：大模型（LLM）的 Prompt/交互记录在异步写审计日志时，通过绑定的上下文变量（contextvars）在异步协程中自动 fallback 捕获活跃 Trace ID，落库为 `audit_log.trace_id = T1`。

#### 5. 运维与环境采集层
* **`terminal_operation` 表**（SSH 网页终端操作录制）：
  * **设计机制**：当工程师通过 Monitor 图标发起 SSH 终端诊断时，网关的 WebSocket 握手或命令 API 承载了客户端请求，`terminal.py` 在执行命令记录时自动读取当前追踪上下文，落库为 `terminal_operation.trace_id = T1`。
* **`environment` 表**：
  * **设计机制**：环境数据由采集引擎异步或同步发起，采集请求上下文与排障主流程 Trace 绑定，落库为 `environment.trace_id = T1`。
* **`assistant_evaluation` 表**：
  * **设计机制**：用户提交工单评分或质量反馈时，前端将当前的 `trace_id` 携带在请求头中发送至后端落库，保存为 `assistant_evaluation.trace_id = T1`。

### 4.3 第一性原理关联总结

根据追踪染色的第一性原理，关联关系总结如下表所示：

| 数据库表 | 业务含义与作用 | `trace_id` 来源及传播染色路径 |
| :--- | :--- | :--- |
| **`case`** | 故障诊断工单表（核心 Root） | 💡 **Root (首跳网关)**: 网关或 case-service 接收工单创建请求时产生 Trace ID `T1` 并作为主链路根标识落库。 |
| **`user`** | 系统操作用户表 | 💡 **Root 同步关联**: 与用户账号/工单创建在同一根 HTTP 事务中，通过上下文或当前请求 Trace 自动落库关联。 |
| **`customer`** | 客户基本信息表 | 🧬 **OTel Context 自动捕获**: 客户管理模块创建或导入客户时，自动从 HTTP 头部或 Span 提取活跃 Trace ID 染色落库。 |
| **`session`** | 用户/客户 Web 登录会话表 | 🧬 **OTel Context 自动传播**: 用户登录/鉴权握手时，通过 Gateway 将当前 Trace 上下文自动序列化并落库。 |
| **`conversation`** | 工单排障对话表 | 🔗 **ID 级继承**: 对话创建时，服务层显式从对应的 `case` 表中读取 `trace_id` 并将其写入，继承为 `T1`。 |
| **`message`** | 对话消息历史表 | 🧬 **OTel Context 动态传播**: 在流式消息处理协程（`send_message_stream`）中绑定 OTel Context，保存消息时自动抓取。 |
| **`sop_execution`** | SOP 决策树执行状态表 | 🔗 **ID 级继承**: SOP 实例创建时，路由层/服务层显式读取 `conversation.trace_id` 写入，继承为 `T1`。 |
| **`diagnostic_item`** | 状态机诊断条目表 | 🧬 **OTel Context 自动捕获**: 状态机在判定执行逻辑中，自动获取当前活跃协程上下文中的 Trace ID 并落库。 |
| **`tool_result`** | Agent 工具执行结果表 | 🧬 **OTel Context fallback 注入**: ReAct 引擎写入审计时传入活跃 Context，未传入时从 Context 变量 fallback 动态捕获。 |
| **`audit_log`** | Agent 与 LLM 交互提示词审计表 | 🧬 **OTel Context fallback 注入**: LLM 交互异步审计回调中，利用复制的 ContextVars 线程局部变量自动捕获上下文 Trace。 |
| **`environment`** | 环境诊断数据采集表 | 🧬 **OTel Context 自动传播**: 采集后台接收排障 Agent 的采集命令时，自动解包并传递 Trace 链路头落库染色。 |
| **`terminal_operation`** | SSH 网页终端操作录制表 | 🧬 **OTel Context 自动传播**: 终端 WebSocket 握手或 API 承载了客户端请求，执行录制审计时从当前活跃 Trace 提取。 |
| **`skill_definition`** | 技能库/Markdown 知识定义表 | 🧬 **OTel Context 自动捕获**: 技能上传、覆盖或同步更新时，通过 HTTP 接口的 `traceparent` 上下文承载 Trace ID 落库。 |
| **`assistant_evaluation`**| 排障助手服务质量评估表 | 🧬 **OTel Context 自动捕获**: 对话结束后，前端提交评估报告，在评估流程中由前端通过 HTTP header 携带 Trace ID 并写入。 |

### 4.4 实现策略

1. **工单与用户级联绑定**：
   在 Gateway 流量入口或 REST 核心控制器首跳中，采用 OpenTelemetry 拦截器注入统一的 `traceparent`；若客户端未携带，则自动生成。`case` 和 `user` 等根信息基于该 Context 绑定落库。
2. **会话创建继承**：
   在 `conversation-service` 创建会话时，底层会通过 SQL 查询关联的工单（`case`）的 `trace_id`。如果存在，新创建的会话将直接继承该 ID 作为自身的 `trace_id`。
3. **SOP 实例创建继承**：
   在命中 SOP 创建 `sop_execution` 记录时，底层会提取当前会话（`conversation`）的 `trace_id` 并将其写入 SOP 执行状态记录中。
4. **流式分析上下文传播**：
   在 `send_message_stream_only` 启动时，服务层会根据当前会话的 `trace_id` 动态构建 OpenTelemetry `SpanContext` 并激活它。所有在这个上下文内启动的操作（包括消息落库、调用 `agent-service` 发起 HTTP 请求）都会自动继承并带上这个 Trace ID。
5. **工具/Prompt 审计落库提取**：
   下沉至 `agent-service` 的 `ToolAuditService` 与 `PromptAuditService` 在异步写日志落库时，若传入 Graves / 参数 `trace_id` 为空，会通过 `get_current_trace_id()` 动态捕获当前活跃上下文中的分布式 Trace ID，保证 100% 成功填充相同的 trace ID。
6. **其他旁路实体（环境、技能、评估、终端）染色**：
   通过全局 `InternalHTTPClient` 自动向下游微服务透传 `traceparent` 请求头，并在各自的数据库写入钩子（Hooks）或 Service 中通过全局追踪拦截器抓取 Trace ID 写入相应字段。
