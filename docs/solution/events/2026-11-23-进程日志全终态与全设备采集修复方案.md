# 2026-11-23 进程日志全终态与全设备采集修复方案

## 背景与需求

2026-11-23 管理端排查发现，工单 `Q2026112300736` 与另外四个工单的「进程日志」页签为空。
对 staging 全库取证（`log_collect_process_log` / `log_collect_task` / `bridge_execution_logs`）：

| 事实 | 数字 | 证据 |
|------|------|------|
| 工单无任何进程日志行 | 295 / 365（80.8%） | 按 `case_id` 去重，`bool_or(p.task_id is not null)` |
| 任务无任何进程日志行 | 559 / 647 | 同上，按 `task_id` |
| 已有日志的工单数 | 70 | 185 行全部 `status=ok`、`content_gz` 非空 |
| 已有日志覆盖的主机数 | 66 | **每个工单恰好一个 host**，即 SSH 发起节点 |
| 11-23 新任务有日志但页签仍空 | `Q2026112300736/a6b7799b` 等 | 同工单前一任务 `47094253` 有 2 行 |

需求依据 `docs/requirement/events/2026-11-12-日志收集可观测性与显示口径统一.md`：

- 第 76 行：**无论成功失败**，acli 收集结束后将**各采集主机**的日志同步到云端；
- 第 77 行：**运行期持续采集 + 本地磁盘 spool，终态补一轮**，避免失败时证据丢失；
- 第 78 行：目录为空也要落一条 `empty` 记录，区分「没日志」与「没回传」；
- 第 88 行：验收项「成功与失败任务均有进程日志记录（含 empty）」**至今未勾选**；
- 第 100 行：假设「各主机日志已由 acli 汇总到发起节点目录」，需逐台扇出时「另行验证」。

**第一性结论**：需求写明的三件事（失败也采、各主机都采、空目录落记录）在代码里一件都没做到；
第 100 行的假设已被库证伪——185 行日志只来自 66 个发起节点，不存在"acli 汇总各主机日志"的事实。

## 三个独立根因（不是同一个 bug）

### 根因 1：唯一触发点绑死在成功终态

`terminal_bridge/internal/logcollect/log_collect.go:519-528` 是全仓唯一调用点：

```go
if progress.NodeState == "completed" {
    if evidenceCfg, ok := EvidenceFor(msg.ExecID); ok {
        go func() { ...; collectNodeLogs(...) }()
    }
}
```

`HandleLogCollect` 的 10 个 action 分支（probe/create/progress/stat/transfer/cancel/restore_*/capabilities/default）
中，SPC 拒绝（`:231-247`）、create 失败（`:284-355`）、用户取消（`:655-674`）、acli 安装失败
（`internal/acli/acli.go:601-620`）全部 `return`，没有 `completed` 状态，因此零进程日志。
失败时落到的是 `failure-snapshot`（插件文件存在性 + `df`）和 `Raw/output_preview`，
无法回答「acli 到底为什么失败」——而这恰恰是进程日志的首要价值。

### 根因 2：采集范围只有 SSH 发起节点

`collectNodeLogs(ctx, s *sshx.SSHSession, cfg EvidenceConfig)` 里的 `s` 来自 `b.ResolveForNode(msg)`
（`:39`），是**单个** SSH 会话；采集命令只在该会话执行，上报 `payload.Host = cfg.NodeIP`
（`log_collect_node_logs.go:169`）。`cfg.ExpectedHosts` 虽从 `msg.IPs` 解析出全量目标
（`log_collect_evidence.go:115,129-145`），但进程日志链路**完全没有引用它**。
bridge 确有逐台 fanout（`log_collect_spc_fanout.go`），但只用于 SPC/脚本写入，不采日志。

### 根因 3：progress 消息丢失 exec_id，成功任务也采不到

前端 `LogCollectPanel.vue:4420` 轮询调用 `sendAndWait(ws, 'progress', {}, 60000)`，
options 为空 → `terminal.ts:836` 产出 `exec_id: undefined`。`log_collect.progress` 事件的
`task_id` 字段直接来自 `msg.ExecID`（`log_collect.go:570`），staging 实测：
`Q2026112300736` 的第二次任务 20 条进度事件 19 条 `task_id` 为空，唯一带值的还是旧任务 ID；
`Q2026112300357` 843 条全空，`Q2026112300730` 177 条全空。
`EvidenceFor("")` 取不到配置 → 即使 `completed` 也不会调用采集。

## 方案概述（WHAT）

三项改造，按依赖顺序实施：

1. **exec_id 鲁棒化**：前端所有 WS 动作统一注入当前 `exec_id`；bridge 侧按 `case_id` 反查最近证据配置作兜底；
2. **全终态触发**：把采集从「成功门」移到「终态钩子」，成功/失败/取消/超时均采，空目录落 `empty` 行；
3. **全设备扇出**：复用现有 SPC fanout 的 `ssh root@ip` 通道，遍历目标主机逐台采集，`host` 字段填真实来源机。

存量 295 个工单**不补采**（无现场 SSH 会话、无证据票据），页面继续按事实显示空态与归因文案。

## 详细设计

### 1. exec_id 鲁棒化

**前端（web，即时生效）**：在 `sendAndWait` 的统一发送层（`LogCollectPanel.vue:2252-2269`）
注入当前任务的 `execId`（来源 `resumedTaskId` / create 返回的 `task_id`），
让 progress/cancel/stat/transfer 都带 `exec_id`。轮询调用点 `{}` 不再需要逐处补。

**bridge（需 exe 重装，纵深防御）**：`EvidenceFor(taskID)` 为空时，
按 `case_id` 在 `EvidenceConfigs` 中反查最近注册且 `task_id` 非空的配置，并落
`log_collect.evidence_fallback` 事件记录「期望 exec_id / 实际采用 task_id / case_id」。
约束：仅当该 case 在内存中只有一个有效配置时才回退，多任务并存时不猜，避免错采。

### 2. 全终态触发与多轮去重

**触发钩子**：在 `HandleLogCollect` 的 `defer`（`:104-109`）中加入终态判定，
以 `outcome` / 错误码 / `action` 判定是否触发 `collectNodeLogs`，并把 `phase` 传入：

| 场景 | phase | 触发点 |
|------|-------|--------|
| create 下发成功、安装阶段完成 | `init` | create 分支末尾（此时 `acli.log`/`cmd_output` 已产生） |
| progress 首次到达 `completed` | `terminal` | 现有 `:519` 位置，改用统一函数 |
| SPC 拒绝 / create 失败 / acli 安装失败 | `terminal_failed` | 各分支 `return` 前设置终态标记，由 defer 触发 |
| 用户取消 | `terminal_failed` | cancel 分支发回包后由 defer 触发 |

**空目录落库**：`parseNodeLogPaths` 返回空时（`:151-155`），不再只发事件，
改为 POST 一条 `status=empty`、`size=0`、`content_gz=NULL` 的记录，
满足需求第 78 行「区分没日志与没回传」。

**多轮去重键**：现有 `evidenceOnce` key 为 `"process-logs:"+cfg.TaskID`（`node_logs.go:139`），
多轮会被第二轮静默跳过。改为 `process-logs:<taskID>:<phase>`；
数据库唯一键 `uq_lcpl_task_host_path_digest(task_id, host, path, COALESCE(sha256,''))` 需增加
`phase` 维度，否则不同轮同一文件因内容相同被 `ON CONFLICT DO NOTHING` 吞掉。

> **对抗性审查**：`init` 轮可能采到安装失败的关键日志，不能被后续 `terminal` 轮覆盖；
> 因此保留多轮共存，管理端默认展示 `terminal` 轮、无 `terminal` 时回退 `init` 轮，
> 不删除任何一轮。单任务 20 MiB 上限按轮独立计算（每轮 20 MiB），
> 避免第一轮吃满预算导致终态证据丢失。

### 3. 全设备扇出

**主机清单**（按优先级）：
1. `cfg.ExpectedHosts`（create 时 `msg.IPs` 解析，非空时直接用）；
2. `ips=all` 时调 `cluster.NodeList(s, ctx)`（`cluster.go:162-174`，`acli --formatter json platform node list`）；
3. 两者都失败：只采发起节点，并落 `process_logs_unavailable` 事件说明清单缺失。

**扇出执行**：遍历主机，复用 `cluster.RunOnHostStreams(s, ctx, ip, local, script)`：

```go
// local=true 本机直连；否则 ssh -o BatchMode=yes -o ConnectTimeout=5 root@ip <script>
out, stderr, code, err := cluster.RunOnHostStreams(s, ctx, ip, isLocal, nodeLogListCommand())
```

`local` 由 `cluster.LocalAddresses(s, ctx)` 判定（`cluster.go:148-160`），避免 ssh 自己。
每台主机独立走 `parseNodeLogPaths` 白名单 + 优先级 + `tail -c` + gzip + sha256，
`payload.Host` 填当前主机 IP（不再是固定 `cfg.NodeIP`）。

**可观测性与隔离**：
- 单台不可达 / 读失败：落 `process_log_failed` 事件（带 `host`、`error`），**不中断**其它主机；
- 每台结束落 `process_logs_collected` 事件（带 `host`、`found`、`collected`、`skipped`、`bytes`）；
- 总量预算：单任务 20 MiB 为**全局**上限，按主机数均分初始额度，
  未用完的额度汇总给后续主机；超限按 `nodeLogPriority` 保留高价值文件并标记 `truncated`。

**安全边界**：路径白名单（`/sf/log/today/acli` 下 `.log`、`..`/NUL 拒绝）保持不变；
`X-Evidence-Ticket` 仍绑定 task_id；扇出只执行只读命令，不下发删除/写入。

## 决策依据（WHY）

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| A. 终态钩子 + SSH 扇出（选中） | 复用已验证的 SPC fanout 通道；不依赖 acli（坏掉时仍可采）；失败路径全覆盖 | 需 exe 重装；每台 SSH 有 5s 超时成本 | ★★★★★ |
| B. 让 acli 汇总各主机日志到发起节点 | 改动小，bridge 仍只扫一台 | 假设已被库证伪；/acli 是独立仓库需现场发版；acli 坏掉时恰好没日志 | ★☆☆☆☆ |
| C. 平台侧下发多会话逐台采集 | 前端逻辑清晰 | 用户要连 N 次 SSH，体验差；与「一次 create 采全集群」的需求冲突 | ★★☆☆☆ |
| D. 只在 create 时采一次 | 改动最小 | 采集过程日志尚未产生；失败恰恰发生在 create 后，无法诊断 | ★☆☆☆☆ |

选择 A 的第一性理由：进程日志的价值是「acli 自身坏掉时仍能看到为什么坏」，
因此采集通道必须与 acli 解耦、且覆盖失败终态；SSH 只读扇出是现有 SPC 写入已验证的同一条通道，
权限前提（root 免密、`BatchMode=yes`）在生产已经成立，不是新假设。

## 测试策略

- **单测**：终态触发矩阵（成功/失败/取消/SPC 拒绝）、`EvidenceFor` 回退、
  fanout 单机不可达不阻塞、`phase` 去重、`empty` 落库、预算分配；
- **集成**：staging 新下发一个多主机工单，验 `host` 字段覆盖全部目标；
  人工在 S3 注入失败、手动取消各一次，验失败路径有日志或 `empty` 行；
- **真浏览器**：管理端进程日志页签显示多主机行，失败工单显示权威失败日志，界面无删除命令；
- **回归**：295 个存量工单数字不因本方案变化（不伪造存量证据）。

## 验收标准

- [ ] 成功、SPC 失败、用户取消、acli 安装失败四类任务均有进程日志行（含 `empty`）；
- [ ] 多主机任务（≥2 台）的进程日志 `host` 覆盖全部可达目标；不可达主机有明确失败事件；
- [ ] 新任务的 `log_collect.progress` 事件 `task_id` 非空率 100%；
- [ ] 同任务不同轮日志共存且管理端默认只展示终态轮；
- [ ] `docs/requirement/events/2026-11-12-日志收集可观测性与显示口径统一.md` 第 88 行验收项勾选；
- [ ] Go 单测 / 前端 vitest / 文档五门禁 / 真浏览器端到端全部通过。
