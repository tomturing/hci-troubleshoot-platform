# 日志收集准备阶段触发与勾选交互修复

## 背景与需求

#1225 上线后，staging 实测发现日志收集面板"看起来没变化"：打开面板后既没有
「正在读取集群环境…」，也没有「环境准备失败」，而是长期停在

- 故障场景下方：`尚未读取集群目录，当前展示平台内置项`
- 目标主机下方：`未获取到节点清单，请按 acli -i 格式手填 IP`

同时现场还有两个体验问题：

1. 故障场景与目标主机都是下拉多选，选项被折叠成 `+N`，用户看不到全量可选项；
2. 在"指定工单号"弹框里登录 SSH 后，采集仍然报 `LC-ENV-006 SSH 会话不存在（需先 ssh_connect）`。

## 方案概述 (WHAT)

四项改动，全部围绕"用户一打开面板就能看到真实环境"这一条验收线：

1. 准备阶段探测改为 **挂载即触发**（`watch(visible, ..., { immediate: true })`）；
2. 故障场景改为 **勾选框全量平铺**，不再折叠；
3. 目标主机改为 **勾选框全量平铺**（含 IP、名称、主控标记），`all` 与"全选"双向等价；
4. bridge 侧 `log_collect` 在精确会话键失配时 **按节点 IP 回退复用**；
   同时"指定工单号"弹框的 SSH 登录补传 `case-id`；
5. 抽屉改为 **从左侧弹出**（`direction="ltr"`），不再从右侧滑出。

## 详细设计

### 1. 探测为什么没触发

```text
stores/chat.ts:  confirmLogCollectCase() 里
                 logCollectCaseId = resolved; logCollectVisible = true   ← 同一 tick
App.vue:137     <LogCollectPanel v-if="chatStore.logCollectCaseId" v-model="logCollectVisible" />
LogCollectPanel.vue:720  watch(visible, ...)  ← 无 immediate
```

`v-if` 让组件"带着 `visible=true` 首次挂载"，非 immediate 的 watcher 看不到初始值，
`prepare()` 一次都不会执行，`prepareState` 恒为 `idle`，于是 UI 落进 idle 兜底文案。
修复：给 `watch` 补 `immediate: true`，并在回调内保留 `nodeIpReady` 守卫
（节点为空时不探测，直接回 idle）。

同时把 `el-form :disabled` 从 `running || prepareState==='probing'` 放宽为 `running`：
探测期间只锁"开始收集"按钮，表单仍可编辑，避免 bridge 响应慢时整面板像卡死。

### 2. 会话键与会话归属

bridge 的会话键是 `caseID@nodeIP`（`sessionKey()`），而日志收集面板用
`props.caseId` 发消息；"指定工单号"弹框里的 `SshConnectSection` 此前没有传 `case-id`，
`connectSSH` 退化成 `terminal-only`，于是"界面显示已连接、采集却报会话不存在"。

修复分两层：

- 前端：`LogCollectCaseDialog` 给 `SshConnectSection` 补 `:case-id="caseId"`，
  新登录直接绑定当前工单；
- bridge：`handleLogCollect` 在精确键失配后调用 `sessionByNodeIP()`，
  按节点 IP 复用同一 bridge 实例内的任意会话（精确后缀匹配，避免 `10.1.1.1` 命中 `10.1.1.11`），
  并打 `log_collect.session_fallback` 事件日志便于追溯。

### 3. 勾选框语义

| 交互 | `form.ips` | 说明 |
|------|-----------|------|
| 不勾任何主机 | `all` | 后端契约里"空选择"= 全部，UI 上表现为全选 |
| 勾选全部主机 | `all` | 等价，避免把 20 台 IP 拼成长串 |
| 勾选部分主机 | `ip1,ip2` | 与 acli `-i` 参数一致 |

`hostChecked` 计算属性负责双向映射；取消到 0 台时回写 `all`，杜绝"一台都不采"的歧义。

## 决策依据 (WHY)

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| A：`immediate: true`（选中）| 一行修复，行为与"每次打开都探测"一致 | 依赖组件挂载时机 | ★★★★★ |
| B：去掉 `v-if` 常驻挂载 | 挂载早于 visible | `caseId` 为空的空窗期要额外守卫，且常驻会保留上一次探测结果 | ★★★☆☆ |
| C：在 store 打开面板处显式触发探测 | 触发点唯一 | 跨组件耦合，面板自身的生命周期语义被削弱 | ★★☆☆☆ |

**为什么选 A**：探测属于"面板打开"这一事件，watcher 是它的自然归属；
`immediate` 只是补齐"初始值也是打开"这一事实。B 会引入上一次会话的陈旧状态，
C 把 UI 生命周期外泄到 store，两者都比 A 更难维护。

**为什么勾选框替代下拉**：故障场景最多十余项、节点清单最多几十项，
下拉的 `collapse-tags` 会把选中项折叠成 `+N`，用户必须点开才能确认；
平铺勾选框一次看全，且"取消勾选"比"在下拉内部点 ×"少两次交互。

**为什么 bridge 加同节点回退而不是改会话键**：会话键 `caseID@nodeIP` 被
终端、注入命令、控制台操作等多条链路共用，改语义影响面大；
日志收集只需要"操作者 + 节点"这一层身份，bridge 又是单用户本地进程，
按节点回退不存在跨用户越权，改动面最小。

### 权衡与妥协

- 同节点回退意味着"同一 bridge 上不同工单可能共用一条 SSH 会话"。
  这正是期望行为：会话属于人 + 机器，不属于工单；工单只决定采集结果归档到哪张单。
- 勾选框在节点很多（>50）时会占满面板高度，暂不做虚拟滚动；
  现场节点规模为个位数到十几台，先按简单实现。

### 会话键错位：为什么"终端能跑 acli，采集却说没有会话"

现场复现（bridge 日志）：

```
bridge.resolveSession: nodeIP=172.28.25.1 无匹配会话，需自动连接
log_collect.session_missing  node_ip=172.28.25.1
```

而同一时刻右侧 SSH 终端可以正常执行 `acli`。差异来自**建会话与用会话的键不一致**：

- `ssh_connect` 消息没有 `node_ip` 字段（`SshConnectOptions` 里从来没有），
  bridge 把会话存成 `sessionKey(caseID, "")` → 键就是 `caseID`；
- `log_collect` 带 `node_ip`，按 `caseID@nodeIP` 查找 → 永远查不到；
- 唯一兜底 `b.get(caseID)` 只在"终端与工单同 caseId"时命中，
  而顶部「SSH 终端」入口的 caseId 会退化为 `terminal-only`。

第一版回退（按 `@IP` 后缀匹配 `sessionByNodeIP()`）对这类**键里根本没有 IP** 的会话无效，
所以必须补齐两层：

| 层 | 改动 | 作用 |
|----|------|------|
| 前端 | `connectSSH` 发 `ssh_connect` 时带上 `node_ip = host` | 新会话键直接是 `caseID@nodeIP`，与查找键一致 |
| bridge | 新增 `sessionByAddressHost()`，按会话 `address` 的主机部分匹配 | 覆盖"已经连好、键里没有 IP"的存量会话，无需重连 |

`sessionByAddressHost()` 用 `net.SplitHostPort` 取主机部分并 `EqualFold` 比较，
避免端口差异与前缀误判；匹配命中的会话会打
`log_collect.session_fallback`（`match=address_host`）便于追溯。
