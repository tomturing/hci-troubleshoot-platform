## 一、为什么要有这份快照

插件把收集定义放在每台节点的 `<deploy>/support_bundle_cluster/spc/*.json`，
`init_pars.py` 每次运行现场读取，改完即生效。但这些文件：

- 不同集群/插件版本内容会漂移，管理端编辑器不能依赖某台机器在线；
- 需要能被追溯：管理员勾选的是哪一版条目。

因此平台内置一份 11 份文件的快照（随镜像发布），带 sha256；节点真实清单由后续
的「从集群刷新」覆盖，刷新前后对比 sha256 即可看出漂移。

## 二、11 份清单的事实

| 文件 | 条目 | 说明 |
|---|---|---|
| other / system / host_offline | 各 75 | action 项完全相同，仅 note 不同 |
| vm_start / vm_suspend | 各 77 | 同上，比 other 多 2 条 script |
| performance | 40 | 命令与日志混合 |
| compute | 52 | **不在 const_modules 白名单**，只能 sfd_main -s 使用 |
| core | 4 | core/dump 文件 + 两条 ls 命令，带时间范围 filters |
| network / storage / slowdisk | 各 1 | 单条 script，收集范围由脚本决定，不是空文件 |

## 三、可用性标注（关键）

`-c` 的 paths 只做逐条 `cp -r`，不做 glob、不认 filters、不执行命令；
未命中的路径会被 `os.path.exists` 判假后**静默跳过**。因此目录里每条都要标出
能否用于 `-c`：

| 条件 | usable_by_config |
|---|---|
| action=copy 且无 `*` 且无 filters | 是 |
| 含 `*` | 否（config 不做 glob） |
| 含 filters（include/exclude/时间范围） | 否（config 不认过滤） |
| action=command / script | 否（config 不执行命令） |

当前统计：other 75 条中 26 条可用于 `-c`，其余 49 条只有在 B 方案（覆写 spc）下才生效。
这直接量化了「`-c` 覆盖不了完整 spc」的边界。

## 四、接口

    GET /internal/log-collect/custom-scenarios/catalog   # 管理端，INTERNAL_API_TOKEN

返回模块 → note 小节 → 条目，条目保留 filters、date_placeholders、docker、interpreter，
并带 has_wildcard / needs_date_expand / usable_by_config 三个派生标记。

## 五、刻意未做

- 不改条目数据模型：非 copy 条目现在存不下，前端勾选会与保存契约冲突，
  因此把「勾选非 copy 条目」留到数据模型升级的 PR，避免做出一个存不进去的编辑器；
- 不做节点实时读取：先有稳定快照，probe 刷新在 bridge 扇出改造时一起做。
