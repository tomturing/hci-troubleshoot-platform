# CI 发布链路按影响范围收敛方案

## 1. 设计原则

镜像构建是发布产物，不是每次 main push 的固定仪式。只有当变更可能进入某个 Dockerfile 的 `COPY` 输入，或改变其构建参数/依赖时，才启动该镜像。无法精确归类的共享输入采取保守扩散，宁可多构建一个镜像，也不允许漏构建导致环境使用旧代码。

## 2. 影响闭包

| 输入 | 受影响镜像 |
|---|---|
| 单个 `backend/<service>/**` 或该服务 Dockerfile | 对应 backend 镜像 |
| `backend/shared/**` | 全部 backend 镜像 |
| `.dockerignore` | 所有业务镜像 |
| `frontend/customer/**` / `frontend/admin/**` | 对应 UI 镜像 |
| `frontend/shared/**`、workspace package/lock/npmrc | customer-ui、admin-ui |
| `terminal_bridge/**` | terminal-bridge |
| `hci_sim/**` | hci-sim |
| db schema/extras/data migration/迁移脚本 | db-migrate |
| 文档、测试、Helm values、CI 配置 | 不构建业务镜像 |

计划由 `scripts/ci/resolve_image_build_plan.py` 在已有 `changes` runner 中生成，输出动态 matrix 和环境仓库服务 key。根 `pyproject.toml` 与 `uv.lock` 虽触发 Python 测试，但不被当前服务 Dockerfile COPY，故不构建镜像。hci-sim 没有平台环境仓库 key，因此只构建，不参与平台 values 同步。

## 3. 工作流收敛

- `docs-naming-convention.yml` 和 `module-doc-sync.yml` 删除，规则合并到已有 `CI / docs-governance` job；两项保持信息性检查和原有旁路标签，不再重复 checkout、Python setup 和 runner。
- `build-db-migrate` 由 `changes` 输出直接 job-level gate，无 schema 变更时不启动 runner。
- `build-and-push` 使用 `fromJSON(needs.prepare.outputs.image_matrix)`，发布 tag 只对实际构建的 matrix 成员生成。
- `auto-deploy-non-prod` 将 `SERVICES_CSV` 限定为本次实际构建且可由环境仓库管理的服务；database-only 变更只更新 dbMigrate，hci-sim-only 变更不触发平台环境同步。
- 增加 job timeout、保留同分支 `cancel-in-progress`，并新增仅手动触发的 P50/P95 时延报告。

## 4. 安全与回滚

所有第三方 action 固定到当前版本对应的 commit SHA。影响闭包脚本发生错误时发布计划直接失败，不会产生部分错误 tag；动态矩阵只减少无关构建，不改变已选服务的构建、Trivy 上报和部署前置依赖。

## 5. 未采用的方案

- 不把所有 job 合并为一个大 job：会丢失独立失败信号并降低并行度；
- 不按最短路径猜测共享依赖：Dockerfile 使用根上下文，漏报 shared/lock 输入会发布旧镜像；
- 不把时延报告放在 PR：观测本身不应增加 PR gate；
- 不删除 Go/Helm/Atlas/Trivy 证据，仅收窄其启动条件。
