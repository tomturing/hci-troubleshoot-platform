# Q2026082664908 / KBD26980 仿真日志变量路由问题归档

## 结论

本次信号 `expert_1787100603104_e34f46ae3c4f` 未命中，不是 `sfvt_vtpdaemon.log` 中没有故障日志，也不能归因于操作者手工修改了已生成配置。直接原因是 Bundle 路由的最终 argv 与 Agent 实际执行 argv 不一致，hci-sim 在 Matcher 执行前返回 `fixture_not_found`，因此 Matcher 没有获得日志内容。

根因是 Bundle 工厂跨层处理 `{{VM}}` 的顺序缺陷：发布审查阶段先对包含占位符的日志关键词执行 `re.escape()`，随后 hci-sim 只按原始 `{{VM}}` 形式替换变量，导致变量模板无法被正常渲染。KBD26980 是当前已发布 KBD 中唯一直接把 `{{VM}}` 放入 `qfk_log` `rows.include` 的案例，因此该缺陷只在此类链路暴露。

## 变量触发链

KBD 原始 Matcher：

```json
{
  "type": "exists",
  "extract": {
    "rows": {
      "mode": "keywords",
      "include": ["Get {{VM}} from vmlist or conf failed, current vm list cnt"]
    }
  }
}
```

原有生成顺序：

```text
Get {{VM}} ...
  -> re.escape()
Get\ \{\{VM\}\}\ ...
  -> hci-sim strings.ReplaceAll("{{VM}}", "SIM-VM-26980")
未替换
```

在线 Agent 的顺序不同：

```text
{{VM}}
  -> SIM-VM-26980
  -> re.escape()
SIM\-VM\-26980
```

因此在线 Agent 和 Bundle 工厂产生了不同的 selector。扫描 staging 已发布 KBD 后，只有 26980 的 `qfk_log` `rows.include` 直接引用 `{{VM}}`，这解释了同类 Bundle 较多但仅该案例暴露问题。

## 次生差异

当前 active Bundle 还经过多次专家编辑，目标路由存在两项独立差异：

1. active Bundle 保存的路径为 `/sf/log/1`，Agent 根据日志 Catalog 选择 `/sf/log/1/vt`；
2. Bundle 的 argv 中保留了 shell 外层单引号，而 Agent 分词后的 argv 不包含这些引号。

hci-sim 按完整 argv 精确匹配，任一差异都足以导致 `fixture_not_found`。这两项差异属于后续 Bundle 编辑/制品漂移，不能替代或掩盖最初的 `{{VM}}` 跨层变量问题。

另外，`sig_003` 的正向 Fixture 输出包含 `vmid: SIM-VM-26980`，而 Matcher 期望 VM 不存在；这是另一个独立的 Fixture 样本错误，与本次日志命令未命中不是同一故障。

## 修复方案

本次代码修复包括：

1. `build_log_selector()` 增加 `preserve_placeholders` 选项。Bundle 发布审查保留 `{{VAR}}`，只转义占位符以外的字面量；在线 Agent 仍在变量解析后使用默认安全转义。
2. hci-sim Bundle 编译器识别日志 `-k/--keyword` 参数，对模板变量值执行与 Python `re.escape()` 兼容的正则字面量转义；普通参数和 stdout 继续使用原始替换。
3. hci-sim 同时兼容新格式 `{{VAR}}` 和历史 Bundle 中的 `\{\{VAR\}\}`，避免旧制品升级运行时立即失效。
4. 编译器修订从 `bundle-factory-v2` 提升为 `bundle-factory-v3`，使相同 KBD 按新算法生成新 Bundle，不复用旧算法产物。
5. 增加 selector、发布审查命令和 hci-sim 编译器的跨层回归测试。

对抗性审查结论：不能取消 `re.escape()`，否则普通日志关键词会被解释为正则并产生注入或误命中；也不能对所有变量全局转义，否则 stdout 和普通命令参数会被破坏。因此转义只在日志 selector 参数中启用，并保留旧制品兼容分支。
