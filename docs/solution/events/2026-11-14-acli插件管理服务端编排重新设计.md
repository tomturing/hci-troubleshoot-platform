# acli 插件管理：服务端编排重新设计

## 背景与需求

PR #1508 的「acli 插件配置下发页面」已由 PR #1509 整体回滚（基线 `ccb50f25`）。回滚原因不是功能跑不通，而是架构与需求不符：它把 admin-ui 浏览器变成了第二个 bridge 中继，页面直接连本机 `ws://localhost:9999`、由管理员在页面填 SSH 凭据与目标节点、由前端组装部署脚本并自行把「成功」回执写回数据库，服务端没有参与下发。

用户的原始需求复述（已确认）：

1. HCI（安装过 acli 的 24/25 环境）自身有一套插件管理机制；
2. 这套机制有严格的校验与配置要求（wrapper / manifest / 注册项 / 逐文件 hash / 冒烟）；
3. 两个业务动作：**新增插件**（如 lmt 排障工具）、**更新已有插件**（如 `netdoctor`），且都要在 HCI 上**实时生效**；
4. 在 admin-ui 新增**管理页面**，用于验证 acli 插件管理机制、维护插件所需的全部信息，并**通过平台 → terminal_bridge → HCI 这套已实现的通路**完成下发与生效；
5. lmt 只提供了脚本和使用说明，其余插件信息需要在平台侧补齐；同时要为「后续再新增插件」提供一份需要补充哪些信息的模板。

> **命名口径（重要）**：工具名是 `lmt`（小写字母 L 加 `mt`），**不是**数字 `1` 开头的写法。24 环境现场路径 `/sf/data/local/acli/plugins/log_collect/tools/lmt_collect_info/` 可佐证。新实现的插件标识、常量、模板、页面文案与验证证据统一用 `lmt` / `hci_lmt_check`；已回滚的 PR #1508 里以数字 `1` 拼写的插件名与脚本常量一律不得沿用。

### 上一版的五处根本偏差

| # | 上一版 | 本设计 |
|---|--------|--------|
| 1 | admin-ui 浏览器直连 desktop bridge | 平台服务端作为 WS 客户端连 bridge，浏览器只发配置 |
| 2 | 页面表单出现 `node_ip` / SSH 口令 / 私钥 | 页面零凭据；目标环境与凭据由服务端托管，页面只选「环境」 |
| 3 | 前端拼部署命令、前端 POST 回执 | 服务端 Builder 生成脚本与 `exec_id`，服务端收 `exec_result` 后落库 |
| 4 | 页面是「执行命令 + 看日志」的调试面板 | 产品级管理页：规格、版本、校验、发布状态、历史、模板 |
| 5 | 只有 lmt 的硬编码样例，无新增模板、无内置插件更新路径 | 可下载的结构化信息模板 + 内置插件覆盖的独立安全策略 |

## 方案概述 (WHAT)

**一句话**：把「插件规格」变成平台服务端的事实源；管理员在 admin-ui 只维护规格并点击「保存并下发」，服务端自动完成校验、生成不可变版本、创建下发任务、以自身托管的凭据直连 terminal_bridge 通道部署到 HCI，并按 `exec_result` 收敛状态。页面全程不接触 bridge 地址、SSH 凭据与部署命令。

### 端到端链路

```
admin-ui（JWT，仅插件规格）
  → api-gateway /api/v1/acli-plugins（require_admin，重签 INTERNAL_API_TOKEN）
  → case-service admin API（事实源 + 校验 + 版本化 + 任务入队）
  → case-service 后台 worker（租约 / 重试 / 幂等）
      → WebSocket 客户端（服务端发起，凭据来自 K8s Secret / 环境配置）
          → terminal_bridge：bridge_hello → ssh_connect → ssh_exec_process
          → HCI：原子部署脚本 + 真实冒烟调用
          ← exec_result（exec_id / trace_id / 部署自检结果）
  → case-service 落库回执 + 状态收敛
  → admin-ui 轮询展示「已生效 / 失败原因 / 下发历史」
```

`deploy_id` → `exec_id` → `trace_id` 三键贯穿管理页、服务端日志、bridge 日志与数据库回执。

### 组件与职责

| 组件 | 职责 | 明确不做 |
|------|------|----------|
| `PluginSpec` 模型 | 插件元数据、脚本与附加文件、参数声明、冒烟参数；不可变 revision + `spec_hash` | 不存主机、口令、私钥、bridge 地址 |
| `PluginEnvironment` 模型 | 环境代号（24/25）、`node_ip`、SSH 端口、认证方式、凭据**引用**（Secret key） | 不存凭据明文，不向前端返回凭据 |
| `SpecValidator` | 校验 acli 硬性契约：命名、manifest 15 字段、wrapper shebang/0755/`"$@"`、逐文件 SHA-256、注册表字段、smoke 参数 | 不在前端做最终校验 |
| `PluginBuilder` | 确定性生成 wrapper、manifest、注册项、补全片段、原子部署脚本、`spec_hash` | 不直接执行任何命令 |
| `BridgeDeployClient` | 服务端 WS 客户端：`ssh_connect` → `ssh_exec_process` → 等 `exec_result`，超时/断连可重试 | 不在浏览器里运行，不复用 `TerminalService._connect_ssh` |
| `PluginDeployRelay` | 状态机 worker：抢租约、心跳、指数退避、`claim_stale`、幂等收敛 | 不依赖某个浏览器在线 |
| admin-ui | 列表 / 新建 / 编辑 / 版本 / 保存并下发 / 状态 / 历史 / 模板下载 | 不出现凭据、命令、WS 地址、调试日志 |

### 数据模型（正交状态，参考 `LogCollectRelayService`）

- `acli_plugin_spec`：`spec_id`、`plugin_name`、`revision`、`spec_json`（元数据 + 文件树）、`spec_hash`、`validation`、`created_by`、`created_at`。每次编辑生成新 revision，历史不可变。
- `acli_plugin`：`plugin_name` 唯一，指向 `current_spec_hash`、`desired_spec_hash`、`enabled`、`update_mode`（`third_party` / `builtin_override`）、`created_at`、`updated_at`。
- `acli_plugin_deployment`：`deploy_id`、`plugin_name`、`revision`、`spec_hash`、`environment`、`node_ip`（冗余快照）、`status`、`lease_owner`、`lease_until`、`attempt`、`exec_id`、`trace_id`、`bridge_result`、`verification`、`error_code`、`created_at`、`finished_at`。
- `acli_plugin_environment`：`env_code`、`display_name`、`node_ip`、`ssh_port`、`auth_type`、`credential_ref`（Secret key 名）、`bridge_url`（可空，走默认集群 Service）、`enabled`。

状态机：`draft → validating → validated → pending → claimed → running → succeeded | failed`；`failed` 按指数退避重试至上限，`claim_stale()` 回收过期租约，`_finish()` 幂等收敛。`spec_hash` 覆盖规范化 spec 与全部文件字节，相同 hash 重复发布直接幂等返回，避免把 HCI 反复重写。

### 凭据与网络边界

- **（v1.2 订正）** 页面提交体只含插件规格 + 目标会话（`case_id + node_ip`，来自 bridge `list_sessions`），**没有** `env_code` 环境白名单、没有凭据、没有 IP 输入。目标环境就是「custom-ui + terminal_bridge 当前已登录的 SSH 会话」，任何这样登录的环境都可下发，24/25 只是联调环境、不是产品边界。服务端**不读凭据、不发 `ssh_connect`、不新建 SSH 连接**，只复用同一 bridge 进程内已存在的会话发 `ssh_exec_process`。
- 默认 bridge 目标是集群内 `terminal-bridge` Service（cluster 模式）。`terminal_bridge/main.go` 的 `originAllowed()` 对空 `Origin` 放行并注明「非浏览器客户端由上层网络边界负责鉴权」，因此服务端 WS 客户端不需要伪造浏览器 Origin；但 Helm 的 `terminal-bridge` NetworkPolicy 需新增两条：放行 case-service Pod 入站 9999、放行到真实 HCI 的 22 端口出站（默认只放行 `hci-sim`）。
- 本机 dev 联调时真实 24/25 仅 Windows desktop bridge 可达，因此允许用 `ACLI_PLUGIN_BRIDGE_URL` 覆盖目标地址。**覆盖的只是服务端连接地址，发起方仍是 case-service**；这与上一版「浏览器直连」有本质区别，也是端到端验证的正确口径。

### acli 运行时契约（24 环境实测，2026-11-13）

- 路径：插件根 `/sf/data/local/acli/plugins`、注册表 `plugin_register.json`、补全 `/sf/cfg/acli/etc/completion/bash_completion.conf`、临时区 `/sf/data/local/acli/tmp`、CLI `/sf/bin/acli`。
- 手工插件四要素：`<name>/plugin`（wrapper，0755 + shebang + 原样透传 `"$@"`）、`<name>/bin/<script>`、`<name>/manifest.json`（15 个必填字段，`hash` 覆盖除自身外全部文件的 SHA-256）、`plugin_register.json` 中的注册项；可选 Tab 补全。
- 禁止 `acli plugin install`（`.aclix` 需厂商签名 + `/support/tmp` 门禁）；注册表必须 `jq` 写临时文件后 `mv` 原子替换；`flock` 与 install/uninstall/sync 共用 `plugin_register.lock`；`built_in` 第三方插件固定 `false`，不改出厂清单 `plugins.json` 与初始化水位 `last_built_in_plugins_init.json`。
- HCI 定制系统**无 `base64`、无 `python3`**：落盘统一用 shell 内建 `printf '%b'`；已有 `jq` / `flock` / `sha256sum`。
- 生效验证不能只看 `--help`：必须真实执行 `/sf/bin/acli --timeout 60 <name> <smoke_args>`，输出非空且退出码 0 才算 `succeeded`。`smoke_args` 纳入 `spec_hash`。

### 内置插件更新（`netdoctor`）的独立边界

现场 `netdoctor` 注册项 `built_in=true`、`source=1`，属于出厂内置插件。覆盖更新必须：

1. 页面显式选择「覆盖内置插件」并在二次确认里看到风险说明（默认 `third_party` 模式禁止写入 `built_in` 项）；
2. 服务端保留 `id` / `name` / `built_in` / `source`，只更新 `version` 与 `last_updated_at`，manifest 的 `source` 保持 1；不触碰出厂清单与初始化水位；
3. 强制先备份 `netdoctor/` 原目录与注册表到 `<TMP_BASE>/backup/<deploy_id>/`，备份失败即中止；下发历史保留「回滚到上一版本」入口；
4. 冒烟使用 netdoctor 真实只读参数，失败自动还原备份。

### 新增插件信息模板

新增 `docs/solution/admin-ui/acli插件新增信息收集模板.md`，同时由服务端 `/api/v1/acli-plugins/templates` 返回可下载的结构化 JSON 模板：列出 manifest 15 字段、目录结构、wrapper 模板、注册项模板、脚本约束、冒烟参数与验收清单，并给出 lmt 的已补齐示例。「只给了脚本和说明」的新插件可按模板逐项补齐，不必再读代码。

## 决策依据 (WHY)

| 候选 | 为什么不选 |
|------|-----------|
| 复用 `agent-exec` + SSE + customer-ui 中继 | 该链路要求某个 customer 浏览器在线、绑定真实 `conversation_id`/`case_id`；admin 保存配置后无法保证有人在会话页，不能支撑「保存即实时生效」，且会把管理动作伪装成 LLM 工具调用 |
| admin-ui 浏览器直连 desktop bridge（上一版） | 凭据暴露在页面与本地存储、无法审计、无法重试/租约、平台服务端不是事实源；用户已明确否定 |
| `TerminalService._connect_ssh()` asyncssh 直连 HCI | 绕过 terminal_bridge，违背「复用已实现通路」，且绕开 bridge 的会话隔离、日志与 trace 体系 |
| 服务端调用 `acli plugin install` | 24 环境实测签名与路径门禁不可行 |
| 把凭据写进插件表 | 与「页面不暴露凭据」冲突，且明文入库有泄密风险；改为环境表 + Secret 引用 |

选择「服务端 WS 客户端直连 terminal_bridge」的理由：它是唯一同时满足「复用 bridge 协议与通道」「服务端可编排、可重试、可审计」「页面零凭据」「无需浏览器在线」的方案；`main.go` 已允许空 Origin 的非浏览器客户端，改动集中在 NetworkPolicy 与凭据托管，不改动 bridge 协议。

- 后端：`backend/case-service` 新增模型、校验器、Builder、WS 下发客户端、状态机 worker、admin 路由；`backend/api-gateway` 新增 `require_admin` 的专属路由（不使用 `/api/v1/tools/{path:path}` 泛代理）；`backend/case-service/app/main.py` 起后台 task。

## 验收标准

1. **链路口径**：在 admin-ui 保存配置后，服务端日志出现「任务入队 → WS 连接 → `ssh_connect` → `ssh_exec_process` → `exec_result` → 回执落库」；页面网络请求里**没有**任何 `ws://` / `password` / `private_key` / `node_ip` 字段；bridge 日志的 `trace_id` 与 DB 回执一致。
2. **新增插件**：按模板补齐 lmt 排障工具信息并「保存并下发」后，24 环境 `acli --formatter json plugin list` 出现新插件，注册表 `built_in=false`，`acli --timeout 60 <name> <smoke_args>` 真实输出巡检结果且退出码 0；页面状态 `succeeded`。
3. **更新内置插件**：编辑 `netdoctor` 版本并二次确认下发后，HCI 上版本与文件 hash 实时变更、`built_in=true` 与 `source=1` 保持不变、备份存在、冒烟通过。
4. **失败与幂等**：断连/超时自动重试且租约不重复执行；同一 `spec_hash` 重复点击不产生第二次写入；失败时页面显示具体 `error_code` 与阶段。
5. **实时性**：从点击到页面显示「已生效」不需要刷新页面、不需要打开 customer-ui、不需要人工 SSH。
