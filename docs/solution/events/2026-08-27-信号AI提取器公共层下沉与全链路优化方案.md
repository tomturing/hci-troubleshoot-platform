# 信号 AI 提取器公共层下沉与全链路优化方案

> **日期**：2026-08-27  
> **状态**：已实施  
> **分类**：架构重构 / 信号处理 / 依赖解耦 / 可观测性  
> **方法论**：第一性原理 (First Principles) 与 对抗性审查 (Adversarial Review)

---

## 1. 背景与问题定义

在 HCI 排障平台的演进过程中，AI 输出再加工能力最初由 QFK（命令探针）引入，物理文件落地于 `backend/agent-service/app/tools/qfk/ai_extractor.py`。

随着平台信号系统的发展，QKV（前端信号提取与产出变量后处理）、Signal Dry Run（试运行演练）以及 KBD（差异化提取）均接入了统一的 AI 后处理契约。然而，物理目录的滞后导致了以下架构痛点：

1. **依赖拓扑倒错与架构异味 (Bad Smell)**：
   * `app/tools/qkv/engine.py` 内部被迫通过本地函数包装并跨模块导入 `from app.tools.qfk.ai_extractor import extract_ai_value`；
   * `shared/signals/qkv_output_processing.py` 位于共享公共层，因不能反向依赖 `app.*`，被迫采用动态参数 `ai_extractor: Any` 回调注入，破坏了公共信号内核的自闭环能力；
   * `app/routes/signal_dry_run.py` 与 `kbd_differential.py` 在非 QFK 流程中强耦合 QFK 目录。
2. **可观测性与审计数据失真**：
   * `StrictPromptLoader` 统一加载 Prompt 时，`consumer` 字段被硬编码为 `agent-service.qfk.ai_processing`，导致所有 QKV 和 Dry Run 的动态资源审计记录均被误标为 QFK；
   * Prometheus 指标与日志事件带有片面的 `qfk_` 前缀，缺乏调用来源维度（`source / signal_type`），导致运维看板无法区分探针与前端信号的指标与报错。
3. **架构对称性缺失**：
   * 确定性提取已位于 `shared/signals/extractor.py`，Matcher 已位于 `shared/signals/matcher.py`，AI 契约位于 `shared/signals/ai_processing.py`，但 AI 执行引擎孤悬在 `app/tools/qfk/`。

---

## 2. 第一性原理 (First Principles) 推导

从不可再分的物理与逻辑底层事实出发：

```
[底层事实 1] ai_extractor 的依赖项仅包含 Python 标准库和 shared.* (observability, signals, prompt_loader)。
             它对 app.* (agent-service 本地上下文) 是 0 依赖。
                                ↓
[底层事实 2] AI 提取/再加工是平台通用的信号后处理基础设施，不仅服务于 QFK，
             还服务于 QKV、Signal Dry Run、KBD 差异化提取等多种场景。
                                ↓
[正向推导]   ai_extractor 必然属于 backend/shared/signals/ai_extractor.py，
             与确定性提取、模式匹配、契约校验构成自闭环的公共信号内核。
```

## 3. 对抗性审查 (Adversarial Review)

| 攻击视角 / 质疑点 | 极限压测与事实核查 | 审查结论与加固措施 |
| :--- | :--- | :--- |
| **质疑 1：`shared` 模块定位是否允许包含异步 LLM 调用和 DB I/O？** | 检查 `shared/` 现有模块：`shared.utils.prompt_loader` 包含 DB Session I/O，`shared.observability.langfuse` 包含 LLM Generation 观测埋点，`shared.resolution` 包含运行时解析。 | **通过**。`shared` 层在架构中即承载跨模块业务运行时，`ai_extractor.py` 的依赖集完全在 `shared` 允许范围内。 |
| **质疑 2：物理迁移是否会破坏现有的测试 Mock 或动态 Monkeypatch？** | 审查全局所有测试与调用方，已统一更新至 `shared.signals.ai_extractor`。 | **通过**。彻底删除 `app/tools/qfk/ai_extractor.py`，不留冗余别名与历史技术债务。 |
| **质疑 3：是否应该合并进 `ai_processing.py`？** | `ai_processing.py` 是无 I/O 的纯数据契约与校验函数；`ai_extractor.py` 是含 I/O 与可观测性的执行流引擎。 | **否决合并**。保持“数据契约层”与“执行引擎层”单一职责分离。 |

---

## 4. 优化实施方案

### 4.1 目录与模块归宿重构
1. **下沉与新建** `backend/shared/signals/ai_extractor.py`：包含完整 AI 提取执行引擎，支持参数化 `consumer` 与 `signal_type`；
2. **彻底删除** `backend/agent-service/app/tools/qfk/ai_extractor.py`：所有生产调用与测试全部平移至公共层，不保留技术债务；
3. **公共门面** `backend/shared/signals/__init__.py`：导出 `extract_ai_value`, `AIExtractionResult`, `apply_output_processing_async` 等。

### 4.2 依赖解耦与适配器清理
1. `shared/signals/qkv_output_processing.py`：直接默认引入 `extract_ai_value`，不再强制要求调用方注入 `ai_extractor` 回调；
2. `app/tools/qkv/engine.py`：删除 `_qkv_ai_extractor` 冗余适配器函数，直接调用 `apply_output_processing_async`；
3. `app/routes/signal_dry_run.py`：直接从 `shared.signals.ai_extractor` 导入。

### 4.3 可观测性与审计校准
1. `extract_ai_value` 增加 `consumer: str = "agent-service.signal.ai_processing"`，调用方按实际场景传入：
   * QFK 探针：`consumer="agent-service.qfk.ai_processing"`
   * QKV 变量：`consumer="agent-service.qkv.ai_processing"`
   * Signal 试运行：`consumer="agent-service.signal_dry_run.ai_processing"`
2. 日志统一上报 `signal_type`，确保日志和追踪平台能精准定位调用来源。
