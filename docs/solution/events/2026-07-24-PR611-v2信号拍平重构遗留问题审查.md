## 一、总体结论

PR #611 标题/描述仅声明"修正 sig_004 工具错配 qfk_storage->qfk_system"，实际承载 65 文件、+5513/-2508 的大规模改动，包含三件本应独立的工作：

1. **v2 信号契约"拍平"重塑**：`acquire.args.target.{scope,resource,path,time_window}` 嵌套对象 -> 扁平 `host`/`file`/`container`/`path`/`time_window`；`sub_command` -> `command`；`description` -> `instruction`；删除 `_v1_legacy`。
2. **删除 v1↔v2 桥接层**：`backend/shared/schemas/signal_migration.py`（含 `migrate_signal_document`/`to_legacy_signal`/`unwrap_signals`/`normalize_qfk_keyword_alias`）、`backend/scripts/migrate_signals_v1_to_v2.py`。
3. **7 个服务的 pydantic v2 配置迁移**（`class Config` -> `model_config = ConfigDict`）。

**结论**：后端契约层（`acquirer_args.py`、`signal.v2.schema.json`、`gen-schemas.py`、`admin.py` 调用清理）的 v2 拍平与 v1 清理基本完整自洽；但存在 **2 个阻断级缺陷**（数据迁移崩溃阻断部署、前端保存 422）、**1 个运行时崩溃**（qfk_service 执行必崩）、**多处半迁移与文档失同步**。"彻底清理 V1、完整重构为 V2"的目标未完全达成。

## 三、阻断级问题（CRITICAL）

### C1. 数据迁移 010 把 v2 对象当裸数组遍历，崩溃阻断部署

**文件**：`database/data-migrations/010_flatten_v1_signal_fields.sql:77-84`

```sql
FOR r IN EXECUTE format(
    'SELECT id, signals_json FROM %I WHERE signals_json IS NOT NULL AND signals_json != ''[]''::jsonb', tbl
) LOOP
    SELECT jsonb_agg(_flatten_v1_signal_fields(s))
      INTO new_arr
      FROM jsonb_array_elements(r.signals_json) AS s;        -- ❌ signals_json 是对象不是数组
    EXECUTE format('UPDATE %I SET signals_json = $1 WHERE id = $2', tbl)
      USING COALESCE(new_arr, '[]'::jsonb), r.id;            -- ❌ 写回裸数组，破坏 v2 包装
END LOOP;
```

**证据链**（v2 的 `signals_json` 是 `{schema_version, signals}` 对象，非裸数组）：

- `backend/kb-service/app/routes/admin.py:564` 注释"signals_json 现为 {schema_version, signals} 对象"，`_load_signals_json(raw).get("signals", [])`。
- `backend/kb-service/app/routes/extract_signals.py:589-595` `_signals_to_v2` 返回 `{"schema_version": 2, "signals": signals}`。
- `backend/shared/schemas/signals/signal.v2.schema.json`：`type:object, required:[schema_version, signals]`。
- WHERE 子句 `signals_json != '[]'` 不排除 v2 对象，故 v2 行会被选中。

**后果**：`jsonb_array_elements(object)` 抛 PostgreSQL 错误 `cannot extract elements from an object`，DO 块回滚，`scripts/migration-runner.sh` 因 `ON_ERROR_STOP=1` 失败 -> 阻断 db-migrate Job -> 阻断 ArgoCD 部署。只要库里有任意一条已抽取信号的 KBD/SOP（PR#608/#609 后必然存在）即触发。即使输入是 v1 裸数组，写回 `COALESCE(new_arr,'[]')` 也是裸数组，违反 v2 schema。

**加重因素**：PR #611 描述只声明"009 迁移已在 dev 库执行验证"，**010 从未在 dev 验证**；且 `db-migration-test.yml` 不执行 data-migrations（见 M11），此崩溃不会被 CI 捕获。

### C2. 前端 qfk_service 编辑态仍绑 `sub_command`，保存必 422

**文件**：`frontend/admin/src/views/KbdReviewView.vue:1800-1804`

```vue
<template v-if="sigTool(signalEditDraft) === 'qfk_service'">
  ...
  <el-select v-model="signalEditDraft.acquire.args.sub_command" size="small">   <!-- ❌ v1 残留 -->
```

同一文件 qfk_system 等其它 qfk 工具编辑态（:1788/:1816）已改 `acquire.args.command`，读态（:1727）也读 `command`，**唯独 qfk_service 编辑态漏改**。`qfk_service` 的 `acquirer_args.py` 契约字段为 `command` 且 `additionalProperties:false` --用户编辑 qfk_service 信号保存时，`validate_acquire_args`/`validate_signals_json` 以"含未注册字段 sub_command"422 拒绝。

## 四、严重问题（MAJOR）

### M3. `_signal_to_qfk` 读 `service`/`action` -> qfk_service 运行时必崩

**文件**：`backend/agent-service/app/adapters/agents/htp/kbd_differential.py:1076-1077`

```python
signal_data = {
    ...
    "command": args.get("command"),
    "container": args.get("container", "asv-con"),
    "service": args.get("service"),            # ❌ v2 契约无此字段
    "action": args.get("action", "status"),    # ❌ v2 契约无此字段
}
```

v2 契约 qfk_service 的 args 是 `resource_keyword`/`container`/`command`，**无 `service`/`action`**；LLM 抽取 + `validate_acquire_args` 强制保证真实数据只有 `resource_keyword`/`command`。故 `signal.service=None` -> `ServiceHandler.build_commands`（`backend/agent-service/app/tools/qfk/handlers.py:182-185`）抛 `CommandBuildError("服务名称必须通过 service 字段提供")`。**qfk_service 信号 100% 执行失败。**

**回归证据**：合并前的 `qfk/signal.py:112-114` 的 `_coerce_legacy_fields` 曾做 `service <- args.resource_keyword` / `action <- args.sub_command` 映射。PR #611 删除了 `_coerce_legacy_fields`（signal.py -233 行），却未把该映射迁入 `_signal_to_qfk`。同文件 `_signal_to_qkv`（:1010-1012）已正确读 v2 的 `keyword`/`is_failed`/`limit`，证明 qfk 侧是遗漏而非有意。

### M4. 前端读态绑 `description`/`end` -> 说明列、结束时间列恒显 `-`

**文件**：`frontend/admin/src/views/KbdReviewView.vue:1660 / 1711 / 1722`

```vue
<!-- 1660（生产者读态）/ 1711（消费者读态）-->
<span>{{ sigArgs(item.sig).description || '-' }}</span>   <!-- ❌ v2 用 instruction -->
<!-- 1722 -->
<span>{{ sigArgs(item.sig).end || sigArgs(item.sig).target?.time_window || '-' }}</span>  <!-- ❌ v2 用 time_window -->
```

而编辑态（:1671/:1746）已绑 `acquire.args.instruction`、:1782 已绑 `time_window`。**PR #611 只迁移了编辑态绑定，漏迁读态** --这是系统性的前端半迁移。迁移 010 跑完后 `description`/`end` 必为空，只读视图说明列与结束时间列全部显示 `-`。

### M5. 迁移 010 产生违反 schema 的字段

**文件**：`database/data-migrations/010_flatten_v1_signal_fields.sql:32-40`

`target.scope->host`、`target.path->path`、`target.time_window->time_window` 对**所有工具无条件执行**。但契约中：`qfk_service` 不允许 `host`（其 args 仅 `command`/`container`/`resource_keyword`/`instruction`/`timeout`）；`path`/`time_window` 仅 `qfk_log` 允许；其它 qfk 工具均 `additionalProperties:false`。若旧 qfk_service 数据有 `target.scope`，迁移后产生 `host` -> 后续 admin 保存 422。迁移本身不校验（直接 UPDATE），非法数据静默落库，下次保存才暴露。

### M6. 迁移 010 丢弃多数工具的 `target.resource` -> 数据丢失

**文件**：`database/data-migrations/010_flatten_v1_signal_fields.sql:41-46`

`target.resource` 仅落 `file`(qfk_log)/`container`(qfk_service)，对 qfk_system/vm/network/storage/hardware/platform **直接丢弃**。这些工具契约有可选 `resource_keyword`，v1 `target.resource` 语义上应映射 `resource_keyword`，迁移未做。

### M7. ACQUIRER_CATALOG 文案仍用 `<sub_command>` 并注入 LLM prompt

**文件**：`backend/kb-service/app/routes/extract_signals.py:80-85`

6 个 qfk 工具的 catalog 描述仍是 `acli system <sub_command>`，且该文本被格式化进 LLM prompt（:641-660 `acquirer_catalog_text`）。而 prompt 规则 6 要求 `command`。catalog 内部也不自洽（qfk_log 用新扁平名，qfk_system 等用旧 `sub_command`）。可能诱导 LLM 产出 `sub_command` 字段被 schema 422 拒绝。

### M8. 008/seed/atlas 三处 prompt 副本与 009 不同步

`008_update_kbd_extract_signals_v2_prompt.sql`、`database/seeds/02_system_prompts.sql`、`database/atlas-migrations/20260723000000_seed_kbd_extract_signals_v2_prompt.sql`、`20260723000002_update_kbd_extract_signals_v2_prompt.sql` 四处副本彼此一致，但**都与 `009_fix_kbd_extract_signals_v2_sig004_qfk_system.sql` 不一致**：副本仍是旧示例（sig_004=qfk_storage），009 是修复后的 sig_004=qfk_system。`seeds/02` 用 `ON CONFLICT (name) DO NOTHING`（:673），全新环境若 009 未执行会拿到错误 prompt。

### M9. 文档系统性认知偏差：`end` 与 `qfk_service.host`

- `docs/solution/agent/02-架构设计/QKV_QFK信号模型v2参考.md:230`：qfk_log 字段表列 `end`（契约是 `time_window`），且漏列 `path`。
- `:242`：qfk_service 字段表列 `host`（契约不允许，与 M5 呼应 --系统性误认 qfk_service 有 host）。
- `docs/solution/agent/02-架构设计/QKV_QFK信号配置操作指南.md`：JSON 示例仍用 `"end"`（契约用 `time_window`）。

### M10. RFC 文档把已删组件标为"✅已实现"

`docs/solution/agent/02-架构设计/关键信号数据模型分层重构RFC.md`（本 PR 未修改）：:391/473/477 把已删的 `signal_migration.py`、`migrate_signals_v1_to_v2.py` 标"✅已实现"；:414/415/479 描述已删的 `_v1_legacy`/`sigLeg` 为现有组件；:319-333 仍用旧字段 `resource`/`end`/`sub_command`/`target`。应更新或标注"历史文档"。

### M11. 009/010 迁移无 CI 覆盖

`.github/workflows/db-migration-test.yml` 只做 Atlas Schema 验证，**不执行 data-migrations**（无 `migration-runner` 调用）。C1 的崩溃、M5/M6 的数据问题都不会被 CI 捕获。

### M12. 删除 `normalize_qfk_keyword_alias` -> 存量 QFK `keyword` 别名回归

PR #611 删除 `signal_migration.py`（含 `normalize_qfk_keyword_alias`），但迁移 010 **不处理** `keyword`->`resource_keyword` 别名。若存量库有 QFK 信号的 `acquire.args.keyword` 历史别名：GET 读态有 `resource_keyword || keyword` 兜底可显示，但**编辑保存时** `additionalProperties:false` 会以"含未注册字段 keyword"422 拒绝 --正是 PR #607/#609 当初引入 `normalize_qfk_keyword_alias` 修复的坑。是否构成回归取决于存量数据，需核实生产 `signals_json` 是否仍含 QFK `keyword`。

## 六、已核实为正确 / 与本 PR 无关

- **`admin.py`**：`signal_migration` import 已移除，GET/PATCH 改用 `_load_signals_json`（纯 JSON 解析无归一），PATCH 仍走 `validate_acquire_args`+`validate_signals_json` 双校验 + `CAST(:signals_json AS jsonb)` 落库，无悬挂引用。
