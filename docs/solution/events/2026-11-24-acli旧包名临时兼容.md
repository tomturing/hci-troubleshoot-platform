# acli 旧命名安装包临时兼容方案

## 背景与需求

见[需求事件文档](../../requirement/events/2026-11-24-acli旧包名临时兼容.md)。

现状链路（`terminal_bridge/internal/acli/acli.go`）：

1. `probeAcliLatest` 从响应头 `Content-Disposition` 取文件名，交给 `parseAcliRemoteName`；
2. `parseAcliRemoteName` 只认 `^acli_(\d+\.\d+\.\d+)_` 与 `_(\d{8}\d{6})\.acli$`；
3. 解析结果为空 → `acliSyncDecision` 里 `Probed=false` → `reconcile.Compare` 走
   `probe_failed_no_desired` 降级 Skip → `HandleAcliSync` 在 `if !needInstall` 处直接返回，
   下载/上传/安装三段代码（`downloadAcliPackage` / `uploadAcliPackage` / `installAcliPackage`）完全不执行。

## 方案概述 (WHAT)

新增一条**临时**解析分支：新命名完全落空且文件名以 `acli-installer_` 开头时，
按旧命名取"尾部打包时间"与"可选版本段"，让 `remoteBuild` 非空、`Probed=true`，
重新进入既有的"版本优先、日期兜底、禁降级"判序。

改动集中在 `terminal_bridge/internal/acli/acli.go` 与对应单测，不改调用链、不改判定骨架。

## 详细设计

### 解析规则

| 目标 | 正则/实现 | 说明 |
|------|-----------|------|
| 旧命名识别 | `strings.HasPrefix(name, "acli-installer_")` | 仅用于发证据与决定是否尝试旧分支 |
| 可选版本段 | `^acli-installer_(\d+\.\d+\.\d+)_` | 形如 `acli-installer_1.0.1_x86-c86_64_...` |
| 尾部打包时间 | `^acli-installer_[A-Za-z0-9_.\-]+?_(\d{4})-(\d{2})-(\d{2})_(\d{2})-(\d{2})-(\d{2})\.acli$` | 输出 `YYYY-MM-DD HH:MM:SS`，与既有 `buildTime` 同格式 |

字符集限定为字母数字与 `._-`：文件名来自远端响应头，虽然落点已经过
`sanitizeAcliFilename` 白名单收敛，但解析层不应把含 `/` 的名字当成官方包。

### 判定结果（逻辑推演，已被单测锁定）

以实测旧包 `acli-installer_x86_64_2026-05-20_17-33-24.acli` 为远端期望：

| 节点现状 | 远端解析 | 判定 | 理由 |
|---------|---------|------|------|
| `1.0.12-preview` / 2026-01-28 | `("", 2026-05-20 17:33:24)` | Install `version_outdated` | 版本不可比，日期严格更新 |
| `1.0.0` / 2026-05-20 17:22:16 | 同上 | Skip | 同日视为同一版本 |
| `1.0.3` / 2026-10-29 | 同上 | `downgrade_blocked` | 本地更新，禁止降级 |
| 未安装 | 同上 | Install `not_installed` | 未安装优先 |

### 可观测性

新增证据事件（WARN）：

```text
acli_sync.legacy_package_name
fields: remote_filename, parsed_version, parsed_build
```

它是**回滚观察点**：发布侧恢复新命名后，该事件不再出现，方可删除兼容代码。
`acli_sync.build_parse_failed` 保持原语义（只在旧命名也解析不出时触发）。

## 决策依据 (WHY)

### 方案选择

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| A. 桥侧临时兼容旧命名（选中） | 不依赖发布侧排期；改动局部；可单测覆盖；可观察回滚 | 短期维护两套命名 | ★★★★☆ |
| B. 等发布侧恢复新命名 | 零代码改动 | 节点永久停在旧构建，现场业务被阻塞；无法控制时间 | ★☆☆☆☆ |
| C. 恢复旧格式全功能兜底（含旧包路径猜版本） | 覆盖面大 | 需要猜版本号，会再次引入"猜出来的时间戳进判序"风险（Q2026101401677） | ★★☆☆☆ |
| D. 仅在 UI 提示"源已退化" | 无解析风险 | 不解决"装不上/不升级"，工单仍阻塞 | ★☆☆☆☆ |

### 为什么选 A

第一性原理：本次缺的不是"能力"，而是"期望态证据"。包本身可用
（实测 18,718,164 字节、sha256 `e370be40…`，当天 6 台节点用同一 sha256 安装成功），
唯一缺失是"它是什么版本"。旧命名里日期是可验证的事实，版本号在部分旧包里也带，
因此只需把事实取出来，让既有判序继续工作即可。

### 为什么不选 C

`parseAcliRemoteName` 的既有注释已经写明：猜出来的时间戳会直接进判序，比解析失败更危险。
本次只接受"文件名里明确存在的日期"，缺日期仍返回空串，保持 fail-closed。

## 影响范围

### 受影响的模块

- `terminal_bridge/internal/acli/acli.go`：解析函数与证据事件。
- `terminal_bridge/internal/acli/acli_sync_output_test.go`：解析用例与判定用例。
- 判定骨架 `terminal_bridge/internal/shared/reconcile` 与安装链路三段：无改动。

### API 兼容性

无接口变更。WS 消息新增一个证据事件，前端不依赖它。

## 回滚方案（重要）

满足任一条件即可整段删除：

1. 发布侧恢复 `acli_<版本>_<架构>_<YYYYMMDDHHMMSS>.acli` 后，
   `acli_sync.legacy_package_name` 事件连续 7 天为 0；
2. 发布侧明确通知旧包下线。

回滚步骤：

1. 删除 `acli.go` 中 `acliLegacyVersionRe` / `acliLegacyBuildRe`、
   `isLegacyAcliPackageName`、`parseLegacyAcliRemoteName` 及 `parseAcliRemoteName` 里的旧命名分支；
2. 删除 `acli_sync.legacy_package_name` 证据事件；
3. 把 `TestParseAcliRemoteName` 的三条旧命名用例改回"落空"，删除
   `TestAcliLegacyPackageCompatibility`。

## 测试策略

- 解析层：新命名逐字节不变（现有 2 条用例保持）；旧命名带/不带版本段、缺时间戳、含路径片段。
- 判定层：`preview 落后→升级`、`同日→不装`、`本地更新→禁降级`、`未安装→装`。
- 全量：`terminal_bridge` 目录下 `go test ./...` 与 `gofmt -l`。
