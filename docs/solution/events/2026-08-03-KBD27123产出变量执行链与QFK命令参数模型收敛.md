# KBD27123 产出变量执行链与 QFK 命令参数模型收敛方案

> 关联工单：`Q2026080352822`、`Q2026080323483`；KBD：`support_id=27123`、`kbd_entry.id=1`。
> 对应任务：[KBD27123产出变量执行链与QFK命令参数模型收敛任务](../../task/hci-sim/events/KBD27123产出变量执行链与QFK命令参数模型收敛.md)。

## 背景与需求

本轮现场反馈包含两个连续问题，以及一个在审核界面反复造成误配置的建模问题：

1. `Q2026080352822` 中第二个信号执行 `acli --timeout 10 system lsof` 后约 10 秒超时，工具展示 `exit_code=-1`，用户无法判断是 KBD 配置、环境检查还是执行环境故障。
2. 将同一信号超时调整为 120 秒后，`Q2026080323483` 的远端命令已成功，但工具仍显示失败，第三个信号因缺少 `PID` 被阻塞。
3. KBD 管理端的 `qfk_system` 同时出现两个名为“命令参数”的字段；而“执行命令”本身又能填写普通参数。用户每次识别/审核都要手动删除冗余参数，且无法判断该字段是否只有 `qfk_system` 才有。

目标不是通过掩盖报错把 KBD 标为成功，而是建立可审计的执行、结果处理、变量产出和根因判定链路，并收敛命令模型，防止同类配置再次进入已发布 KBD。

### 现场证据与时间线

| 工单 | 阶段 | 可验证事实 | 结论 |
|---|---|---|---|
| `Q2026080352822` | `qkv_task` | 已解析 `VM`、`HOST`、`END`，目标节点为 `172.28.25.4` | 不是 QKV、路由或环境采集服务失败 |
| `Q2026080352822` | `qfk_system/lsof` | `exec_id=7ada2b18-59be-55a4-8c27-3abe9b9f897e`，`acli --timeout 10 system lsof` 在约 `10001 ms` 后 `timed_out=true`、`exit_code=-1`、stdout/stderr 均 0 | revision 22 未显式设置超时，落入运行时默认 10 秒 |
| 环境人工复核 | `lsof` | `acli system lsof | grep 18864231143` 返回 `flock`、`sleep` 两行，均含 `/18864231143.vm/vm-disk-2.qcow2` | VM 行筛选与“第 2 列 PID”取值规则正确；`UID 65535` 的 pwd 警告是 stderr 警告，不是超时根因 |
| 历史现场 | 全量 `lsof` | 耗时约 `20.5–34.3 s`，原始输出约 `39–61 MB` | `lsof` 必须显式使用足以覆盖历史 P95 的超时；120 秒有余量 |

| `Q2026080323483` | 结果处理 | `tool_result.error=QFK_MATCHER_MISSING: QFK 判定必须配置新版 match.extract` | 失败发生在 Agent 的 QFK 处理分支，不在命令执行环境 |
| `Q2026080323483` | 下游信号 | `ps` 工具状态为 `blocked_dependency`，缺少变量 `pid` | 上游实际输出没有进入 `produces` 提取，故 PID 未写入变量池 |

现场成功的两行示例为：

```text
flock      8369 root ... /18864231143.vm/vm-disk-2.qcow2
sleep      8370 root ... /18864231143.vm/vm-disk-2.qcow2
```

对同一输出按当前 `produces` 的文本取值规则复放，得到 `PID=8369`。这证明 `{{VM}}` 的边缘字面量行筛选、空白分列后的第 2 列、整型转换均没有问题；问题是取值函数根本没有被调度。

## 分析结论

### 结论一：第一张工单是 KBD 数据层的超时配置缺失，不是环境检查异常

`qfk_system` 执行路径在未填写 timeout 时使用默认值 10 秒（`kbd_differential.py` 中 `args.get("timeout", 10)`）。而全量 `lsof` 是已知大输出命令，历史耗时已超过该值，因此 revision 22 的配置不能满足真实环境。revision 23 增加 `timeout: 120` 后，命令在约 22 秒完成并正常返回，已直接验证此结论。

人工命令中的 `lsof: no pwd entry for UID 65535` 只表示 `lsof` 无法将某个 UID 映射为本地 passwd 条目；它出现在 stderr，不会导致 Bridge 给出 `exit_code=-1`，也不会否定 PID 取值结果。

不能把 `18864231143` 填到“资源/命令参数”来代替行筛选。`lsof 18864231143` 把数字当作 `lsof` 的查询对象，在同环境实测会快速返回 exit `1` 和空输出；VM ID 不是 lsof 的文件、PID 或用户查询语义。该信号的正确语义仍是执行全量 `lsof`，在受控执行边缘用 VM ID 对 stdout 做字面量行筛选。

### 结论二：第二张工单暴露运行时代码缺陷，不是 KBD 的 PID 配置错误

当前 `sig_002` 是合法的“产出变量模式”：`match=null`，并在 `orchestrate.produces` 中声明从 lsof 结果产出 `PID`。调用方原本会在 QFK 成功后调用 `_fill_pool_from_qfk()` 写入变量池，但 `qfk/engine.py` 在真实命令成功、且已获得完整输出后，仍无条件要求 `signal.matcher` 并返回 `QFK_MATCHER_MISSING`。调用方因 error 短路，后续提取永远不会执行。

因此，当前故障状态应拆成两个阶段展示：

| 阶段 | Q2026080323483 的实际结果 | 正确用户含义 |
|---|---|---|
| 命令执行 | 成功：exit 0，约 22 秒，2 个筛选结果行 | 环境检查已取得可信证据 |
| 结果处理/变量提取 | 失败：`QFK_MATCHER_MISSING` | Agent 未能消费成功输出，PID 未产生 |
| 下游调度 | 阻塞：缺少 `PID` | 不应误报 `ps` 命令本身执行失败 |

### 结论三：sig_003 的判定词与 KBD 根因含义错位

该 KBD 的根因文义是“第三方容灾进程 `ClwDRDBClient` 占用镜像”。但当前第三个信号执行 `ps -p {{PID}} -o cmd=` 后匹配 `{{VM}}`。VM ID 出现在命令行最多只能说明该进程的命令参数引用了此 VM，不能证明进程身份是 `ClwDRDBClient`。

本次现场真实进程为 `flock` / `sleep`，并非 `ClwDRDBClient`。即使修复变量产出而沿用 `{{VM}}` matcher，仍可能将无关占用误判为“第三方容灾程序占用”。这个问题独立于超时和 producer 缺陷，必须在 KBD 契约中修正。

### 结论四：用户对“命令参数”体验的判断成立，根因为三条重叠的表达路径

`qfk_system` 目前同时保留：

| 内部字段 | 当前界面/语义 | Handler 行为 | 问题 |
|---|---|---|---|
| `command` | “执行命令”；实际允许空格和普通参数 | 直接拼入 `acli system` 后 | 可以填写 `ps -p {{PID}} -o cmd=`，与结构化参数重复 |
| `command_args` | 顶部第一个“命令参数”；一行一个参数 | 逐项追加到命令 | 新增的安全 argv 表达，却没有唯一入口 |
| `resource_keyword` | 底部第二个也叫“命令参数” | 仍作为一个位置参数追加 | 历史资源选择器被误用为命令参数，和前两者完全重叠 |

这不是单纯文案问题：`SystemHandler` 依次追加 `command`、`command_args`、`resource_keyword`，因此保留两个同名输入会改变实际命令。该字段的历史来源是早期通用 QFK “资源/主题选择器”；历史迁移为避免丢失 `target.resource` / 旧 `keyword` 将其映射为 `resource_keyword`，之后又引入了 `command_args`，但没有同步从 `qfk_system` 的 Schema、UI、Prompt 与 Handler 中收敛旧路径。

字段并非只有 `qfk_system` 才存在，但只有它把两条路径同时以“命令参数”暴露并真正追加执行：

| 工具类别 | `command_args` | `resource_keyword` 现状 |
|---|---|---|
| `qfk_system` | 已消费 | 已消费且追加到命令，形成重叠 |
| `qfk_log` | 未使用 | 仍有独立的日志资源/主题语义 |
| `qfk_service` | 未使用 | 实际是服务名语义 |
| `qfk_vm/network/storage/hardware/platform` | 未使用 | Schema 虽有字段但通用 Handler 未消费，属于幽灵字段 |

系统 Prompt 仍含“将 `{{VM}}` 写入 `resource_keyword`”的旧示例，正是识别结果不断生成冗余字段、人工需要反复删除的直接诱因。

## 方案（WHAT）

### 1. 修复 QFK 产出变量模式（P0）

为 QFK 执行引入显式 `execution_mode="produce" | "match"`：

- `produce`：允许 `match=null`；远端命令成功后必须返回供 `produces` 使用的完整、已受边缘限制的输出，随后由 KBD 调用方提取并写入变量池。
- `match`：保留现有 matcher 判定逻辑；未配置 matcher 才返回配置错误。
- 禁止通过“有无 matcher”隐式猜测模式；模式由信号语义校验和调用请求共同决定。

最小修复可先使“无 matcher 且声明 produces”的成功 QFK 不再触发 `QFK_MATCHER_MISSING`，并回传 `complete_outputs`。最终实现仍应落到显式模式，避免以后新增消费者时再次发生控制流冲突。

必须新增真实端到端回归，而不是只测 `_fill_pool_from_qfk()` 辅助函数：

```text
qfk_system lsof（按 VM 安全行筛选）
  -> produces.PID（第 2 列，first，int）
  -> qfk_system ps -p {{PID}} -o cmd=
```

该测试应断言：远端成功输出进入变量池、第二步得到调度、且两阶段状态分别正确记录。

### 2. 固化 KBD27123 的信号契约（P1）

推荐的规范化配置如下。它是发布前应审核的目标数据；在运行时代码修复和发布流程完成前，不得将其描述为“已全部生效”。

| 信号 | 规范化命令及超时 | 输入/产出 | 判定 |
|---|---|---|---|
| `sig_001` | `task get ...` | 产出 `VM`、`HOST`、`END` | producer，`match=null` |
| `sig_002` | `command="lsof"`、`command_args=[]`、`timeout=120` | 在 stdout 以 `{{VM}}` 作字面量行筛选；从第 2 列取第一个 PID | producer，`match=null`，不填写 `resource_keyword` |
| `sig_003` | `command="ps"`、`command_args=["-p", "{{PID}}", "-o", "cmd="]`；超时可采用 10–30 秒 | 消费 `PID`；必要时先产出 `PROCESS_CMD` | 若根因保持不变，精确匹配 `ClwDRDBClient`；不得用 `{{VM}}` 代替进程身份 |

若产品需要识别多类占用程序，应让 sig_003 先产出 `PROCESS_CMD`，再由明确的分类规则区分 `ClwDRDBClient`、系统辅助进程和未知进程；不得把任何含 VM ID 的命令行视为第三方容灾根因。

### 3. 收敛 qfk_system 命令模型与审核界面（P2）

面向审核者只保留一个可编辑字段“命令（不含 `acli system`）”，允许自然填写：

```text
ps -p {{PID}} -o cmd=
```

保存时前后端使用受控分词、变量校验和命令白名单，将其规范化为唯一内部形式：

```json
{
  "command": "ps",
  "command_args": ["-p", "{{PID}}", "-o", "cmd="]
}
```

并在界面展示最终编译预览，例如：

```bash
acli --timeout 120 system ps -p 8369 -o cmd=
```

`qfk_system.resource_keyword` 从新建配置、审核 UI、抽取 Prompt 和最终命令拼接中移除。现存旧值先进入迁移和人工复核队列，不盲目追加到新命令；尤其禁止把 VM ID 自动迁成 `lsof` 参数。兼容期可接受旧 `command` 含参数，保存时安全分词并迁移到 `command_args`；不安全、无法分词或同时包含 `command_args` 与旧 `resource_keyword` 的数据必须拒绝发布并提示人工处理。

其它工具同步消歧：`qfk_service.resource_keyword` 改名为 `service_name`，`qfk_log` 使用表达日志源的 `topic` / 日志资源字段；通用 QFK 的资源字段要么由 Handler 实际消费，要么从 Schema 删除，禁止继续保留“可保存、不可执行”的幽灵字段。

### 4. 增加发布门禁与可解释状态（P1）

发布前静态校验与最小 replay 必须覆盖：

- `match=null + produces` 的 producer 模式真实可执行；不允许被 matcher 规则误拦截。
- `qfk_system` 不可同时包含 `command_args` 与旧 `resource_keyword`。
- matcher 的对象必须与 KBD 声明的根因/证据角色一致；进程身份判断不得匹配 VM ID。
- `lsof` 等高输出命令必须显式声明不低于历史 P95 的 timeout；本 KBD 最低为 120 秒。
- Handler 编译命令、边缘筛选和变量提取的最小 replay 必须通过。

客户工具卡片应独立展示“命令执行”和“结果处理/变量提取”状态。命令 exit 0 而解析失败时，卡片不得统称“执行失败”，而应说明输出已取得、失败发生在哪一处理阶段，以及对下游变量的影响。

## 决策依据（WHY）

### 为什么不把 VM ID 填入命令参数或 resource_keyword

这会改变 `lsof` 的查询语义。数字 VM ID 不是 lsof 的有效查询对象，实测会得到 exit 1 与空输出；即使某些命令可接收资源名，`resource_keyword` 也不应成为“任意参数槽”。本场景需要的是对已执行全量 lsof 的安全输出行筛选，现有边缘筛选能精确、可审计地完成该任务。

### 为什么不开放 shell 管道或让用户写 grep

`grep` 只能解决一次表面筛选，却带来 shell 注入、转义、审计和跨环境可用性问题。结构化字面量筛选和 `command_args` 提供相同的表达能力，并能由 Schema、Handler、Bridge 分层校验。

### 为什么不能只把下面的“命令参数”改名

仅改文案会保留三条可写、可拼接命令的路径，实际命令仍可能被重复追加或被旧 Prompt 污染。必须同时收敛 Schema、UI、Prompt、Handler 和历史数据迁移，才能消除根因。

### 为什么不能用一个固定 matcher 绕过 QFK_MATCHER_MISSING

给 producer 加一个无意义 matcher 会让“变量采集”伪装成“根因判定”，既可能阻断正确输出，也会把偶然命中的文本当作诊断结论。producer 与 match 是不同执行模式，必须由运行时显式支持。

### 为什么 sig_003 必须匹配 ClwDRDBClient 而不是 VM ID

KBD 的诊断结论需要回答“谁占用了文件”，而非“该进程是否提到这台 VM”。当前 `flock/sleep` 的现场证据恰好说明两者不同。使用进程身份特征，或先产出命令行再分类，才能避免将未知/系统占用误报为第三方容灾程序。

## 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A1 | `lsof` 超时 | 未显式配置 timeout 的大输出 `lsof` 无法通过发布校验；KBD27123 使用 120 秒配置在现场 22 秒执行成功 |
| A2 | producer 端到端 | `match=null + produces` 的 `lsof` 成功后返回可提取输出，变量池写入 `PID=8369`（或现场实际 PID） |
| A3 | 下游调度 | `ps -p {{PID}} -o cmd=` 在 PID 写入后被调度，不再出现 `blocked_dependency: pid` |
| A4 | 根因准确性 | `ClwDRDBClient` 才能满足该特定根因；`flock/sleep` 必须显示为不满足或未知，不得诊断为第三方容灾程序占用 |
| A5 | 命令界面 | 新建 qfk_system 只显示一个命令编辑入口和最终编译预览；保存后内部 argv 唯一且可复现 |
| A6 | 历史兼容 | 旧 `command` 含参数可安全迁移；含旧 `resource_keyword` 的歧义数据不静默追加，需迁移或人工复核 |
| A7 | 语义一致性 | Schema、Prompt、Admin UI、Handler 和实际编译命令对 `command_args` / resource 字段的定义一致；无幽灵字段 |
| A8 | 状态可解释 | 命令 exit 0、解析失败时，用户可分别看到“命令执行成功”和具体解析错误；下游显示“依赖变量缺失” |
| A9 | 回归保护 | 单元、集成和端到端 replay 同时覆盖 producer 链路、命令编译、边缘筛选、提取值与工具卡片状态 |

## 当前处置状态与边界

- revision 23 已在数据层将 `sig_002.timeout` 调整为 120 秒，并由 `Q2026080323483` 验证远端命令不再超时。
- 本事件文档提出的 producer runtime 修复、sig_003 语义修正、命令模型收敛、UI 与发布门禁均尚待实施和回归；不得因第一阶段命令成功而宣称整条 KBD 已修复。
- 本轮仅完成问题分析与文档归档，不修改线上配置以外的运行时代码，不将 `flock/sleep` 解释为 `ClwDRDBClient`。
