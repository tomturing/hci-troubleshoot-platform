## 一、现场事实

同一工单在 100 秒内被连点 5 次（客户看到的信息不足以判断问题，只能反复重试）：

| 时间（UTC+8） | error_code | error_message |
|---|---|---|
| 11-11 03:35:48 | LC-PLUGIN-008 | 任务下发后节点未建立采集任务；请核对节点 acli 版本与所选专项… |
| 11-12 10:28:04 | LC-PLATFORM-011 | 场景未能写入全部目标节点（节点不可达：172.28.24.2；可用节点为 0） |
| 11-12 10:28:44 | LC-EXEC-003 | **（空）** |
| 11-12 10:29:14 | LC-EXEC-003 | **（空）** |
| 11-12 10:29:44 | LC-PLUGIN-008 | 任务下发后节点未建立采集任务… |

这 5 条实际踩在**三个互不相同**的阶段上，但界面上它们都显示为一句「日志收集失败」：

1. **场景清单扇出失败**（SPC 层，create 之前）：平台要把场景清单逐台写入节点，失败被统一写成「节点不可达」，且丢失 stderr；
2. **acli create 执行失败**（EXEC 层）：节点真实返回 `收集专项core不存在！`，但取原因的函数一遇 `FATA[...]` 包装行就直接返回包装行，前端 `normalizeErrorMessage` 再把这一行过滤掉 → `error_message` 变成空串，原因彻底消失；
3. **create 后节点未接单**（PLUGIN 层）：`LC-PLUGIN-008` 的语义是「按任务 ID 查不到任务」，而这里根本没有建立任务，处置动作完全不同（一个是任务 ID 问题，一个是 acli 版本/专项问题）。

## 二、根因（逐层可验证）

| 层 | 文件 | 缺陷 |
|---|---|---|
| bridge 取原因 | `terminal_bridge/log_collect.go` `logCollectFailureLine` | 遇 `FATA` 立即返回包装行；且带时间戳的行被整行跳过，真实原因可能整句丢失 |
| bridge 失败分类 | `terminal_bridge/log_collect_spc_fanout.go` `runSpcOnHost` | 任何错误一律 `spcErrUnreachable`；`runQuickCommand` 只在 stdout 为空时才拿 stderr 兜底，脚本先打赢 marker 再失败时 stderr（`Read-only file system`、`Permission denied`）被静默丢弃 |
| bridge 聚合 | `spcClassifyHosts` / `spcRejectionMessage` | 只回 `written` 计数，逐台原因不落地；`written==0` 时文案写「可用节点为 0」（与集群可用节点数混淆） |
| backend 归因 | `log_collect_error_attribution.py` `_RULES` | 只有泛化规则（ENV/EXEC/PLATFORM），没有 SPC 层；「场景未能写入全部目标节点」落到 011 未归因 |
| frontend | `LogCollectPanel.vue` | 失败态只有一句状态文案；无码时也不指向任务详情，用户只能再点一次 |

## 三、修复内容

### 3.1 错误码（唯一真源）

`backend/shared/resolution/catalogs/log_collect_error_catalog.json` 新增 SPC 层与 2 个 PLUGIN 码，Go 侧 `log_collect_errors.go` 同步定义常量：

| 码 | 含义 | 用户该做什么 |
|---|---|---|
| LC-SPC-001 | 场景清单目录缺失 | 核对节点平台版本与目录是否被移动（`/sf/data/local` 等） |
| LC-SPC-002 | 场景清单目录不唯一 | 节点上存在多份清单，平台无法判断写哪一份，先人工确认 |
| LC-SPC-003 | 场景清单备份失败/回读不一致 | 查目录可写、磁盘余量与权限 |
| LC-SPC-004 | 场景清单写入被拒绝/校验不一致 | 查只读挂载、空间、SELinux/权限 |
| LC-SPC-005 | 场景清单回滚失败 | 节点清单可能停留在平台内容，须人工核对后恢复备份 |
| LC-SPC-006 | 目标节点 SSH 连接失败 | 查节点在线、防火墙、known_hosts |
| LC-SPC-007 | 目标节点 SSH 认证失败 | 查免密配置与近期密钥变更 |
| LC-SPC-008 | 目标节点命令执行超时 | 查节点负载与磁盘 IO |
| LC-SPC-009 | 场景清单文件缺失 | 补齐槽位清单文件 |
| LC-SPC-010 | 多台节点写入失败且原因不同 | 逐台看 `detail.spc_hosts[].error_code/error_detail`，先修 SSH/认证类 |
| LC-PLUGIN-015 | 下发后节点未建立采集任务 | 核对 acli 版本与所选专项，换内置专项做 A/B 对照 |
| LC-PLUGIN-016 | 节点上没有所选专项 | 去节点确认专项是否存在，或改选内置专项 |

### 3.2 bridge

- `classifySpcCommandError(err, diag, step)`：按「传输层（认证/超时/不可达）→ 文件系统与权限（只读/空间/权限）→ 步骤兜底」三档分类，**不再默认判「节点不可达」**；`ssh:`/`dial tcp` 才判连接失败。
- `runSpcOnHostStreams`：stdout 与 stderr 分开返回。stdout 只用于 marker 解析（stderr 里的 `/bin/sh: ...` 会被目录解析误当成路径），stderr 进入 `error_detail`。旧实现丢弃 stderr 是「只报不可达」的直接原因。
- 拒绝时逐台保留 `Code + Message`：同因给精确码，多因给 `LC-SPC-010`；`written==0` 时把每台失败原因都写进文案（原先只剩「成功 0 台」）。
- `logCollectFailureLine`：先剥时间戳再判断；中文关键词 + 英文关键词（`error`/`failed`/`not found`…）；`FATA`/`level=fatal` 只作最后兜底。
- `logCollectModuleMissing`：识别「收集专项…不存在」→ `LC-PLUGIN-016`，不再落 `LC-EXEC-003`。
- 「下发后未建立任务」改 `LC-PLUGIN-015`；`LC-PLUGIN-008` 只保留「按任务 ID 查不到」的真实语义。

### 3.3 backend 归因与数据

- `_RULES` 前置 SPC 规则（必须先于 ENV/EXEC 泛化规则，否则「节点 SSH 认证失败」会被抢成 `LC-ENV-007`），并为历史文案加兜底（`场景未能写入全部目标节点`、`收集专项`、`未建立采集任务`）。
- `062` 规则表同步（fresh install 用）；**062 已在 staging 执行过，改它不会重跑**，故新增 `064_log_collect_error_code_spc_fix.sql` 做历史订正：
  - `LC-PLATFORM-011`（未归因占位码）按新规则子集重新归因；
  - 旧语义 `LC-PLUGIN-008` 且文案写明「未建立采集任务」→ `LC-PLUGIN-015`；
  - 每条改动把旧码写进 `detail.error_code_derivation.before_code`，可逐行回滚核对；幂等、不动上游精确码。

### 3.4 frontend

- `services/logCollectErrorHints.ts`：13 个码的 `title/check/fix` 唯一映射，未知码返回 `null`（不编造原因）。
- `components/LogCollectDiagnosis.vue`：诊断卡（结论 + 码 + 原始原因 + 如何检查 + 如何处理）。
- 面板在**表单态失败**与**结果态失败/取消**两处都渲染诊断卡（隔天回来查看主要走结果态，原先只在表单态）。
- 失败 patch 回填最新任务，避免诊断卡读到上一轮的码。
- 结果态顶部横幅（`buildResultHeadline`）改为「错误码 + 结论 + 先按『如何检查』确认、再按『如何处理』修复、确认原因消除后才重新收集」；无码时指向 `error_message` / `create_output`，不编造结论；取消态不再直接催重新收集。

### 3.5 对抗性复验补漏（v1.1）

v1.0 合并后用真实 Chromium 打开结果态页面，截图发现**第一屏**还留着旧的泛化横幅：
「失败原因见下方错误信息，可点右下角「重新收集」再试一次。」——正是把客户推向连点 5 次的那句话。
单测只断言了标题「该工单上次采集失败」，因此没抓到描述文案。修正后横幅把规范码与结论直接摆到第一屏，
与下方诊断卡形成「先定位 → 再处理 → 确认后再重收」的顺序，不再出现「再试一次」。

## 五、失效边界与遗留

1. **bridge 不会自动更新**：本次 bridge 改动必须在现场重装桌面端 exe 后才生效；旧版 bridge 仍会发空文案 + 旧码，此时 064 订正与前端诊断卡只能兜住「码」这一层。
2. 历史上的 2 条 `LC-EXEC-003` 空文案**无法还原**（原因从未落库，`create_output` 也未在旧代码中保存）——前端会按 EXEC-003 给出「查 create_output / 记录任务号」的指引。
3. `LC-SPC-010` 是聚合码，逐台原因在 `detail.spc_hosts`，面板只展示聚合结论，不会替用户猜单台原因。
4. 目录探测步骤若遇到「权限不足」，会归到该步骤码（如 `LC-SPC-001`），结论偏保守；原始 stderr 一定在 `error_detail` 里，排障以它为准。
