# 日志收集场景字典与 Agent 不联动

## 一、现场提出的三个问题

1. 点开「日志收集」后，右侧排障 Agent 仍然并排可见，用户以为可以让 Agent 参与收集日志；
2. 右侧应该展示登录后的 SSH 终端（采集本来就在终端里跑 `acli log_collect`）；
3. 截图里 acli 透出的「故障场景」十几项，用户不知道每一项收什么、该选哪个。

前两条是**界面语义**问题，第三条是**信息缺失**问题，但它们的根因是同一个：
日志收集这条路的能力边界从来没在界面上说清楚。

## 二、先核实的三条事实（推翻了此前的默认理解）

改代码之前先把「现在到底怎么跑」查清，否则容易改错地方：

| # | 原本的（错误）理解 | 核实结果 |
|---|---|---|
| 1 | 「故障场景」10 项由集群 acli 透出 | **不是**。`parseLogCollectModuleCatalog` 只用来确认集群支持 `-m` 枚举；label 与顺序一律取 `terminal_bridge/log_collect.go` 的 `logCollectModuleLabels` + `logCollectModuleCatalogOrder`。面板上「目录来自集群 acli」的真实含义只是「集群返回过至少一个枚举」 |
| 2 | 默认勾选项与工单症状有关 | 恒为 `vm_suspend`（`form.modules` 初值），与工单内容无关 |
| 3 | 后端会挡住互斥组合 | **不会**。后端只校验枚举白名单 + 去重，`-m other,vm_suspend` 可以同时提交 |

另外两条实现层面的约束，直接决定了方案选型：

- `TerminalPanel` 的 `onBeforeUnmount` 会调用 `disconnectSSH()`。任何导致组件卸载的“搬位”
  （例如把 xterm 实例挪到中央区）都会**断掉用户的 SSH 会话**；
- `enforceOverlayExclusive('right')` 在窄屏下开右栏会反向关闭 `logCollectVisible`。
  自动开终端时若不先判 overlay，会把用户刚打开的日志面板关掉。

## 三、方案

### 3.1 中央 Agent 隐藏 + 复用右栏终端（不搬 xterm）

| 选项 | 结论 |
|---|---|
| 把 xterm 组件搬到中央区 | ❌ 组件卸载 ⇒ `disconnectSSH()` ⇒ 会话中断 |
| 中央留白收起 + 复用右栏终端 | ✅ 宽度让给日志表格与终端，会话零风险 |

- `resolveWorkspaceLayout` 新增 `centerHidden` 入参：单开取 `viewport - RAIL_WIDTH(48)`
  并允许突破 `leftMax/rightMax`；双开时左栏 `clamp(偏好比, leftMin, leftMax)`、右栏吃掉全部剩余，
  两栏之和恒等于视口，`centerMaxWidth` 返回 0；
- `App.vue` 的 `<main>` 收为 `flex: 0 0 0; width: 0; overflow: hidden`——**不能用 `display:none`**，
  否则两侧不会重新分配像素；`ChatWindow` 用 `v-show`，会话消息、滚动位置、输入草稿必须保留；
- overlay 分支**忽略** `centerHidden`（覆盖态本来就是一次看一块）；
- 三种情况不隐藏、改为标题栏常驻 `el-tag`「日志收集进行中 · 与排障 Agent 不联动」：
  SSH 未连接、bridge 未运行、右栏被文件下载占用。这时藏掉 Agent 只会让中间空一块。

自动切终端用 `watch(logCollectVisible)`，一处覆盖 header 按钮、rail 图标、建单引导卡、
工单号弹框四条入口；前置条件是 `sshConnectionState === 'connected'`、右栏未被文件下载占用、
且「两侧都开」的求解结果不是 overlay。**关闭日志收集不关右栏终端**——那条会话用户可能还在用。

### 3.2 故障场景字典（入库 + 管理端可维护）

字典只描述**展示事实**，不定义能力边界：

```
acli probe（能力边界）  ──┐
                          ├─→ 交集 = 客户端可选场景
log_collect_scenario（文案）─┘
```

- `database/desired_schema.sql` 新增表 `log_collect_scenario`（Atlas 声明式，唯一权威）；
  `database/seeds/06_log_collect_scenarios.sql` 幂等 seed 10 行（`ON CONFLICT (value) DO NOTHING`）。
  **种子必须走 seeds 通道而非 data-migrations**：存量库的 data-migrations 跑在 Atlas 之前，
  INSERT 会撞上「表还不存在」（合并后 staging 实测事故，见 §七）；
- case-service：客户读 `GET /api/log-collect/scenarios`（只出 `enabled`，按 `sort_order, value`）；
  管理端 `/internal/log-collect/scenarios`（`require_admin_token`，`value` 不可改，写操作落
  `operation_audit`）；
- api-gateway：客户读单独一条 `GET /api/log-collect/scenarios`（**不复用** `/tasks{path}` 前缀代理，
  那条按工单归属做 BOLA，而字典是平台级配置）；管理端 `/api/v1/log-collect-scenarios` 以
  `INTERNAL_API_TOKEN` 重签下游，操作者取 `X-Admin-User` 或 JWT `sub` 兜底；
- 客户端：`prepare()` 内与 probe **并行**拉字典，字典失败只降级不阻塞探测；以 probe 的 `modules`
  为能力边界，按 `value` 补文案并套用字典顺序，缺失项追加尾部；三层回退
  （字典 → bridge 短名 → 原值 + 「平台未维护该场景说明」）；`exclusive` 项双向禁用（当前无互斥项）；
- 文案改正：`catalogSourceText` 拆成两行——「可选场景由集群 acli 提供（读取于 hh:mm:ss）」
  与「场景说明来自平台字典（更新于 …）」。

## 五、两点待确认事项的结论（2026-10-29 已确认）

1. **文案审核在管理台完成，没有额外的“发布”动作**：支持工程师在「日志收集场景」页的
   「编辑说明」弹窗内逐条审核，`review_state` 由 `pending_review` 改为 `approved` 即为对外可用；
   表格里的橙/绿 `el-tag` 只是状态展示，修改入口在弹窗（不另设发布按钮）。
2. **`-m other,vm_suspend` 是叠加语义，不是互斥**（两类日志一起收）。据此：
   - seed 里 `other.exclusive` 由 `true` 改为 `false`，`summary` 补为「可与具体专项叠加」；
   - `exclusive` 列与客户端双向禁用逻辑**保留**（字典能力，当前无一项启用），
     仍由合成字典的用例保护——将来真出现互斥场景，管理台打开开关即生效；
   - 为什么要改：当初按 help 原文「不收集上述n个场景日志」推断为互斥，若照此强制，
     会把客户合法的叠加诉求挡掉。列存在语义误判时，改数据比改代码便宜，这也是把互斥
     放进字典（而不是写死在 `LogCollectPanel`）的收益。

## 六、落地时被门禁挡下的两处历史债

### 6.1 变更历史表「版本在前」，门禁看不见表里的日期行

`docs-governance` 首次红灯并不是文档内容有问题，而是 `check_docs_changelog.py` 报
「实质修改（节外改动 N 行）但变更历史节缺真实日期数据行」。根因不在脚本（两篇分别报 91 行 / 4 行）：

- 脚本把「数据行」定义为**首列**匹配 `YYYY-MM-DD`（`is_data_row`），据此天然排除表头与
  `|---|---|` 分隔行，也挡住 `| | | |` 这类空壳——这是 §7.1 模板的机器投影；
- 而 `接口设计.md` 与 `架构设计.md` 的变更历史表是历史遗留的「版本 | 日期 | 变更内容」列序，
  `架构设计` 更把日期整体加粗为 `**2026-10-29**`。两处都让整节对门禁**不可见**：
  行确实加了，判据读不到。

处理方式：把两表前两列对齐模板（日期去粗体前置），**内容逐字未改**，纯搬位 132 行；
脚本对每行断言「首列=日期、版本列未丢、尾部单元格集合不变、单元格数不变」后才落盘，
因此这次改动不可能夹带文案变更。两行变更记录里各补一句来由，读者不必反推。

教训（可复用）：门禁是结构性的，「表里有一行日期」不等于「门禁看得见那一行」。
新增文档若沿用旧列序，加行再多也过不了；一次性对齐模板后，这篇文档后续的增量就都能被判定了。

### 6.2 表格单元格里的竖线必须转义

管理端三个方法写在一起时是 `GET\|POST\|PUT`：Markdown 表格里未转义的 `|` 会被当成列分隔符，
把一行撑成多列、后面的文案整体错位。文档里描述 HTTP 方法组合时按 `GET\|POST\|PUT` 写。

## 七、合并后 staging PreSync 失败：种子数据放错了通道

PR #1355 合并（06:25）、CI 晋级非生产环境（06:29）之后，ArgoCD 的 PreSync Hook
`db-migrate` 没能跑通：Job 6 秒内退出，连试 5 次（至 06:41）后放弃，
`hci-platform-staging` 停在 `OutOfSync`，四个 Deployment 全部停在旧镜像，
`log_collect_scenario` 在库里不存在。

### 7.1 取证：失败的 hook 资源被自动删除，只能自己复现

hook 带 `HookFailed` 删除策略，ArgoCD 失败后立即删 Job 与 Pod，日志如风而逝。
用同镜像（`db-migrate:20261029-0629-cfc2cc2`）+ 同环境变量起一个 `sleep` 调试 Pod，
手工执行 `/db-migrate.sh` 才拿到真因：

```
▶️  Executing migration: 056 (log collect scenario seed)
BEGIN
psql:/data-migrations/056_log_collect_scenario_seed.sql:89:
  ERROR:  relation "log_collect_scenario" does not exist
❌ Migration 056 failed
====== Migration Summary ======
Executed: 0 / Skipped: 51 / Failed: 1
```

### 7.2 根因：存量库的执行顺序是 DML 早于 DDL

`scripts/db-migrate.sh` 的顺序是 **Step 1 数据迁移 → Step 2 函数 → Step 3 atlas apply**
（Step 0 的「先建表」只在**全量空库**走）。存量 staging 库跳过 Step 0，于是 056 的
`INSERT INTO log_collect_scenario` 跑在**本次才建的表**前面；`set -e` 又让整个 Job
在 Step 1 就中止，Atlas 连建表的机会都没有——**重试多少次都不会自愈**。

这个顺序本身没有错（存量库要先搬数据、再用新约束收敛），错的是把「新表的初始数据」
放进了只该碰既有表的 `data-migrations/`。

### 7.3 为什么 CI 没拦住

`db-migration-test.yml` 走的是**空库路径**：先 `atlas schema apply` 全量建表，
**再**跑 `data-migrations/*.sql`。空库上表早已存在，056 顺利执行，CI 全绿——
恰好把「存量库 DML 早于 DDL」这条差异遮住了。这是典型的「门禁路径与生产路径不一致」，
比没有门禁更贵：它给出的是确定性的错误信心。

### 7.4 修复

1. 文件移到 `database/seeds/06_log_collect_scenarios.sql`。seeds 由 `db-seed` Job 在
   **PostSync**（hook-weight 0，晚于 db-migrate 的 -5）执行，此时 Schema 已收敛；
2. `db-migration-test.yml`：paths 补 `database/seeds/**`；新增 Step 2e 按序执行
   `seeds/*.sql`（与 db-seed Job 同序）与 Step 2f 字典断言（10 行、无互斥项、
   `other` 必须 `exclusive=false` 且 `sort_order=100`），把「叠加语义」这个已确认事实
   也钉进门禁；
3. `database/README.md` 新增「新表 + 初始数据的落点」小节与铁律第 6 条：
   新表铺数据 → `seeds/`；既有表搬数据 → `data-migrations/`。

### 7.5 教训

- **表与数据同批上线时，先问「谁先执行」**：声明式 DDL 与版本化 DML 在不同的 step，
  顺序反了就会「必然失败 + 永不重试成功」；
- **幂等不等于可用**：`ON CONFLICT DO NOTHING` 解决重复执行，解决不了依赖对象不存在；
- **门禁要跑生产同序**：CI 里空库与存量库是两条路径，只验一条等于没验另一条。

## 八、第二层缺口：种子改动根本到不了集群（#1358 合并后发现）

### 8.1 现象：CI 全绿，集群没任何变化

#1358 合并进 main（178171cd）后，main 流水线全绿，但 staging 依旧 `OutOfSync`、
`to_regclass('public.log_collect_scenario')` 仍为 `NULL`、Deployment 仍停在修复前的镜像。
回看该次 run 的镜像计划：`db-migrate: 否`——镜像构建、晋级非生产、ArgoCD 同步
**全部 skipped**。也就是说，这轮修复压根没有「出门」。

### 8.2 根因一：种子不在任何镜像里

`database/seeds/` 只被 Helm 打包成 PostSync Hook 的 ConfigMap，**不参与任何镜像构建**。
而升不升级由镜像 tag 决定：`数据库/seeds` 变 → 无新 tag → 不重建 → 不晋级 → ArgoCD
不 sync → PostSync 永不触发。CI 也不会发现，因为 `db-migration-test.yml` 在空库上
直接 `psql -f seeds/*.sql`，与镜像/晋级链路无关。

> **更正（2026-10-29 晚，审查后）**：上段末尾的「不晋级 → 不 sync」把**晋级**当成了
> **sync** 的充分条件，这是错的。实测 `9e9820a`（07:44，tag 0718→0743）与 `2e25313`
> （07:50，0743→0748）两次晋级都成功了，但 app 全程 `Synced`，集群从未出现对应
> db-migrate Job。原因是该提交只改 `dbMigrate.image.tag`，而这个值只被 hook 模板引用，
> ArgoCD 不比较 hook 资源，因此看不到任何差异。真正的缺口是「触发器」，详见 §九。

### 8.3 根因二：重命名把「删了旧路径」藏了

即使退一步——`DB_MIGRATE_PATHS` 里本来就有 `database/data-migrations/`——也拦不住：
`git mv data-migrations/056_x.sql seeds/06_x.sql` 被 git 判为**纯重命名**，
`git diff --name-only` 对 R 项**只输出目标路径**，源目录下的删除在清单里不可见。
本次 squash 后的文件清单只剩 `database/seeds/06_log_collect_scenarios.sql`，
`data-migrations/` 的删除完全消失。

> 这是一个通用的采集级缺陷：任何「从白名单目录里移出」的改动都会被同一个机制抹掉，
> 包括将来的 `backend/` → `docs/` 等场景。

### 8.4 修复

1. **种子进镜像**：`Dockerfile.migrations` 新增 `COPY database/seeds/ /seeds/`，
   `scripts/db-migrate.sh` 新增 **Step 5**（Atlas 收敛之后、按文件名顺序 `psql -f`），
   与 PostSync `db-seed` 构成「同源双通道」，两边均幂等；
2. **白名单**：`scripts/ci/resolve_image_build_plan.py` 的 `DB_MIGRATE_PATHS` 加
   `database/seeds/`——种子变更必须产生新 tag；
3. **采集层**：`changed_files()` / `changed_files_between()` 统一改为
   `git diff --no-renames`，把重命名的源路径还原回清单；
4. **回归测试**：`test_seeds_change_triggers_db_migrate_rebuild`（白名单）与
   `test_rename_out_of_watched_dir_is_visible`（真建一个仓库跑 `git mv`，断言源路径
   必须出现在清单里）。后者不靠 mock，直接锁住 git 的真实行为。

### 8.5 教训

- **「CI 绿」只证明你验的那条路径通了**：本次两条链路（SQL 正确性、镜像与晋级）
  各自都绿，但它们的**交集**没人验——种子从来没被「从镜像走到集群」验证过；
- **配置数据也属于制品**：只要某个目录的内容决定集群状态，它就必须能产生新制品版本，
  否则运维会得到一个「改了却没反应」的静默系统；
- **工具默认行为也是设计输入**：git 的重命名识别、`--name-only` 的输出口径，直接决定
  了门禁看得见什么，写白名单逻辑时必须显式关闭这类「聪明行为」。

### 8.6 恢复动作

修复 PR 未合前的紧急恢复：对 main 手动 `workflow_dispatch`、`promote_target=staging`
（全量重建镜像 → 晋级 env 仓 → ArgoCD 同步 → PreSync 建表 → PostSync 灌 10 行）。
后续同类事故的标准动作是：**先 manual dispatch 让集群回到与 main 一致，再合修复 PR**。

## 九、第三层：触发器缺失与自愈链不可达（#1359 合并后发现）

### 9.1 现象：修复已上线、镜像已更新，但 Step 5 从未执行

#1359 合并（2af56151）后，env 仓分别产出 tag `20261029-0743-2af5615`、`20261029-0748-aa9cb29`，
build 与晋级均 success。但 `kubectl -n hci-staging get job | grep db-migrate` 只有旧的
`-0748-a`之前的 `db-migrate-20261029-0718-...-010`，app 一直 `Synced`——新镜像里的 Step 5
一次都没跑过。

### 9.2 根因一：hook-only 变更不会产生漂移

ArgoCD 的漂移对比**跳过 hook 资源**（PreSync/PostSync 的 Job、拿来做顺序的 ConfigMap/Secret）。
主库迁移的全部输入只存在于两类地方：hook Job 的镜像 tag，与镜像内的文件。因此当一次晋级
**只改 `dbMigrate.image.tag`** 时，渲染结果里变化的全是 hook 资源 → app 保持 `Synced` →
PreSync 永不重跑。

同一机制下还有一个更隐蔽的形态：凭证类资源（`hci-sim-db-credentials`）也是 hook，轮换密码
同样不会被看见——改了 values，Secret 停在旧值，而没人会收到任何提示。

### 9.3 根因二：自愈策略存在却永远触发不了

`templates/hooks/hci-sim-db-migrate-job.yaml` 早就写了 `hook-delete-policy: BeforeHookCreation,HookFailed`
并配了容器内的前置校验（「放弃本次执行以触发 HookFailed 自愈」）——设计是对的。但依赖对象
缺失时，Pod 停在 **`CreateContainerConfigError`**（Pending，**不是 Failed**），容器根本没起来，
校验代码没机会执行，Job 也不会失败：`HookFailed` 清理与重试永远不会发生。
实测显式 sync 后在 PreSync 上挂了 8 分钟无任何进展——这是**永久态**，不会自己好。

### 9.6 教训

- **「部署成功」与「变更生效」是两个命题**：镜像 build/promote 绿只说明制品运输到位，
  不说明集群会去用它。判断生效必须看「谁来触发」，而不是看流水线颜色；
- **自愈逻辑的触发条件也是设计的一部分**：`HookFailed` 写得再对，只要失败永远不发生，
  它就是死代码。「卡住」比「失败」更危险，因为告警抓不到、重试也不会来；
- **不要用 hook 承载需要被比较的状态**：hook 是执行器，不是状态载体。状态必须有一个
  普通资源当锚点，否则整个系统对 Git 不可见；
- **对抗性审查要针对自己的结论**：本次第一轮结论把「晋级」当「sync」、把「未证实」当「已查明」，
  是审查阶段才被自己推翻的——复盘文档里宁可写「未闭合」，也不要写一个听起来完整的因果链。

#### 9.7.3 机理取证：deadline 是唯一的杠杆（隔离实验）

为了把「有无 deadline」的差别单独量出来（与 ArgoCD 解耦），在 `hci-staging` 里用两个一次性 Job
跑同一条件（`envFrom` 引用不存在的 Secret，镜像与 hci-sim 迁移 Job 同为 `postgres:15-alpine`），
结束后已删除两个 Job：

| 对照组 | Pod 状态 | Job 结果 |
|----------|----------|----------|
| `activeDeadlineSeconds: 30` | `CreateContainerConfigError`（Pending）| **30s 后 `Failed / DeadlineExceeded`**，job-controller 随后删 Pod |
| 不设 deadline（`backoffLimit: 0`）| `CreateContainerConfigError`（Pending）| **持续 `active=1`、无任何 condition**（即永久挂起，实验后人工删除）|

两张表合起来就是缺陷二的完整因果：同一个不可达状态，有 deadline 才能变成 `Failed`，
`Failed` 才能喂给 `HookFailed`，`HookFailed` 才能让 retry 拿到一干净起点。

#### 9.7.4 仍未闭合：Secret 为何反复缺席（含取证局限）

受控实验意外拍到：`hci-sim-db-credentials` 在 10:54:21 / 11:09:57 / 11:11:24 三次被创建，
却在 10:59–11:09 与 11:10–11:11 两个窗口里均为缺席。**删除者尚未查明**，不得写成已知情。

取证局限（必须连同数据一起记）：本轮采样粒度为 12 秒，而 hook Secret 的策略是
`BeforeHookCreation`（每次 sync 先删自建的再重建），因此「采样拍到 ABSENT」有两种互斥解释：
（a）delete→create 之间的正常空窗被采样撞上；（b）存在真正的第三方删除。前者只能解释秒级窗口，
解释不了 10:59–11:09 这整 10 分钟（期间 kubelet 持续报 `secret … not found`，且无任何 sync 在重建它）。

下一轮收口方式（不推测、只可实验）：
1. 用 `kubectl get secret -w` 或 inotify 式的持续监听代替 12s 采样，把空窗时长测出来；
2. 查 K3s API server 审计（当前集群未开审计，需先打开 `--audit-log-path`）才能拿到「谁删的」；
3. 做一次只留一个 op 在飞、且中途不被后续 op 取代的实验，看空窗是否消失——这能把
   「连续 op 交叠时的先删后建」与「外部删除」分开了。在该实验完成前，本次修复只主张「即使 Secret
   反复缺席，链路也能自动收敛」，不主张「已消除缺席」。
