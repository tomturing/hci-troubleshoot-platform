# 桥接版本随证据请求上报

## 背景

2026-11-24 排查 `Q2026112400942`（P2 中继 149 分钟 0 字节）时，需要回答一个最基本的问题：**这台客户机上跑的是哪个 bridge 版本？** 结果平台侧无解。

## 缺口（三条，逐条查证）

| 可能来源 | 实际 |
|---|---|
| `bridge_execution_logs.event='bridge.startup'` | 全表 145 个实例都有，**唯独本单实例缺失**。该事件在进程启动时发出，那一刻浏览器通常还没连上，只能走桥侧日志直传；旧 exe 的直传固定发 gzip 而服务端不解压（2026-10-28 才修），失败即永久丢失。本实例最早事件是 06:33:22 的 `session.created`，正是回采通道建立的时刻，之前一片空白 |
| `log_collect_network_probe.bridge_version` | 近 7 天 470 条**全为空**。后端 schema 有这一列，但 Go 侧 grep 不到任何 `BridgeVersion` 字段——从未实现写入，是列死字段 |
| 事件 extra 里搜 `v2.x` | 该实例 451 条事件中 0 条命中 |

结论：版本只能到客户机桌面翻本地日志，无法在平台闭环归因。

## 改动

| # | 内容 | 位置 |
|---|---|---|
| 1 | `evidence.SetBridgeVersion()` / `BridgeVersion()` 注入缝（atomic，空串可清空用于测试复位） | `internal/shared/evidence/evidence.go` |
| 2 | 证据请求统一带 `X-Bridge-Version` 头；版本为空时**完全省略该头** | `internal/logcollect/log_collect_evidence.go` |
| 3 | 装配层用 `getVersion()`（ldflags 注入串）注入，业务域不认识构建元数据 | `cmd/bridge/main.go` + `evidence_wire.go` |
| 4 | 后端白名单校验（`[0-9A-Za-z._+()-]{1,64}`），非法值当没上报 | `app/routes/log_collect_evidence.py` |
| 5 | 落库写 `log_collect_task.detail.bridge_version`，SQL 带 `IS DISTINCT FROM` 只在变化时写 | 同上 |
| 6 | 接入三个高频端点：`/metrics`（P2 交付全程）、`/network-probe`（每个任务第一枪，并回填那个死列）、`/artifact-manifest`（覆盖无 metrics 流的 P1 直传） | 同上 |

## 对抗性审查

- **写放大**：metrics 每 2 秒一条，无条件 UPDATE 会把这个高频端点变成写入热点。用 `COALESCE(detail->>'bridge_version','') IS DISTINCT FROM :version` 收敛成"版本变了才写"，稳态零写入。
- **空头覆盖**：旧 exe / 未注入环境不发头，后端拿到空串直接 return，不会把已有版本覆盖成空。
- **脏值**：版本串来自客户端，只接受版本串常见字符并限长 64，避免任意文本落进 detail 后在管理后台渲染。
- **旧 exe 兼容**：不发头也不影响鉴权与业务语义，只是这条数据缺版本字段，与现状等价。
- **P1 直传**：直传没有 transfer-metrics 流，版本挂在 artifact-manifest 上，保证两种交付模式都能归因。

## 验证

- Go：`go test ./internal/shared/evidence/... ./internal/logcollect/...` 通过；新增 `version_test.go`（注入/去空白/清空）与 `log_collect_evidence_version_test.go`（带头 / 空版本不发头）。
- 后端：`pytest tests/unit/test_log_collect_evidence_bridge_version.py` 14 passed（白名单边界、非法不写库、`IS DISTINCT FROM` 存在性、三端点声明了该头）。
- 端到端：需新 exe 安装后观察 `log_collect_task.detail.bridge_version` 是否等于 `v2.37.0-13-g7ea91e5d`。

## 遗留

- **旧 exe 不生效**：修复只在新 exe 里；已安装的旧版本（含本单 `81afb2ee`）仍然不发头，这批存量任务只能继续靠 `bridge.startup` 或现场取。
- `detail.bridge_version` 目前只用于归因取证，客户面板未展示；是否在面板/dev 详情里呈现待定（避免把构建信息暴露给最终用户）。
- 本单暴露的另一个信息缺口不在本次范围：`acli_sync.plugin_snapshot` 的 `phase=before` 快照 `nodes`/`missing` 为空，采集前插件基线没留下。
