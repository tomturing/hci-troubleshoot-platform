## 一、问题与可验证的物理事实

工单 Q2026110901673（场景 `vm_start`，节点 192.168.254.200）连续两次点「开始收集」都在 15~17 秒内被判 `failed`，界面提示「节点上已无任务，采集中断」。平台库与节点事件给出的事实如下：

| 事实 | 证据 |
|------|------|
| 两条任务均 `status=failed`、`progress=0`、`error_code` 为空、`archive_path` 为空，`relay_status`/`delivery_status` 均为 `none` | `log_collect_task` 任务 `50b0cb4b`、`225f2f6f` |
| `acli log_collect create` 返回 `exit_code=0`，输出含 cgroup 报错与 Python2.7 `logging` Traceback | `bridge_execution_logs.log_collect.create.extra.output_preview` |
| create 之后 0s / 6s / 30s / 60s 的 `log_collect progress` 均回「收集任务不存在！」、`node_state=none`、`archive_exists=false` | `bridge_execution_logs.log_collect.progress.extra` |
| 节点产物路径无包 | 节点自报的 `/sf/data/local/acli/tmp/data/log_collect/Q2026110901673.zip` 的 `stat`/`ls` 诊断 |
| create 与 progress 落在同一节点、同一桥实例 | 两者 `node_ip` 同为 192.168.254.200、`bridge_instance_id` 同为 `1f10edda`，无 `session_fallback` 事件 |

**结论**：不是「采集中途断了」，而是 `create` 之后节点从未建立任务，平台在下发 6 秒后就把它写成失败。

### 已排除的干扰解释

- **P2 / 日志服务器不可达**：探测 `curl` 连续 3 次 `context deadline exceeded` 后走 P2 是正确降级；本例从未进入上传阶段。
- **SSH 会话被 TMOUT 踢掉**：`auto-logout`/`remote_eof` 发生在两次失败之后，是终端挂机的后续现象。
- **专项参数非法**：`vm_start` 在 `terminal_bridge/log_collect.go` 白名单内；专项非法时节点会报「收集专项X不存在！」而非「收集任务不存在！」。
- **会话路由到错误节点**：见上表，节点与桥实例一致。
- **acli 一定崩溃**：Python `logging.emit/format` 的 Traceback 通常经 `handleError` 只写 stderr 而不终止进程；它是伴随现象，不足以断言进程崩溃。节点侧真因仍需现场用完整输出确认。

## 二、平台侧三处缺陷

1. **退出码不等于任务存在**。bridge 的 `case "create"` 只看 `exitCode`；PTY 通道把 `ssh.ExitError` 归一化成 `nil`，acli 包装脚本又可能吞掉内部异常，因此 `exit_code=0` 无法证明任务已建立。create 分支结束后没有任何正向确认。
2. **证据链断在落库**。`log_collect.create` 事件只存前 512 字节输出，而 Python Traceback 的最后一行异常类型恰在尾部；完整输出虽经 WebSocket `Raw` 回给前端，但前端在 `status==='ok'` 时完全忽略，失败任务因此查不到定因材料。
3. **判定层对 `none` 没有冷启动宽限**。`SESSION_ADOPT_GRACE_MS`（10 分钟）只约束 `completed`；`nodeState==='none'` 一旦出现立刻 `patch_failed`，且主流程调用 `decideNodeSync` 时未传 `requireSessionAdopt`。失败文案统一写「采集中断」，无法区分「曾经跑过之后消失」与「这次根本没接单」；`error_code` 在成功下发路径上无人赋值，恒为空。

## 三、修复内容

### B2 可观测性（先合，独立可回滚）

- `terminal_bridge/log_collect.go`：create 输出改为 `stripAnsi` → 通用脱敏 → 上传票据脱敏 → `formatOutputPreview`（头 48KiB + 尾 16KiB），`Raw` 与事件 `output_preview` 同源；新增 `output_len`、`output_truncated`；`Message` 只保留 500 字摘要，避免把大段原文塞进异常。
- `frontend/customer/src/components/LogCollectPanel.vue`：create 回包的 `raw` 再脱一次 Bearer、限长 16KiB 存为 `createOutputEvidence`；任务失败时以 `detail.create_output` 合并写入。服务端 `detail` 按字典合并，不会冲掉 `baseline_report_hash` 与 `probe`。
- 同一 `trace_id` 贯穿 create 事件、WebSocket 回包与任务 `detail`，满足按调用链反查完整路径。

### B1 bridge 正向确认

- 新增 `confirmLogCollectCreate`：有界 3 次、间隔 2 秒、总预算 12 秒（远小于 `handleLogCollect` 的 180 秒主预算），查询 `log_collect progress` 并复用 `classifyLogCollectNodeState`。
- **三态结论，不用布尔**：见到 `running` 为 `confirmed`；连续明确「无任务」或节点 `abnormal` 为 `not_established`；查询失败、超时、出现残留 `completed`/解析降级一律为 `unknown`。`unknown` 保持 `ok` 并打 WARN，由前端有界等待兜底，绝不把桥侧抖动误判成采集失败。
- 只认 `running`：acli 是节点级单任务且 `progress` 不带任务 ID，下发瞬间读到的 `completed` 可能是上一轮任务的残留报告。
- `not_established` → `status=error` + `LC-PLUGIN-008`（`ErrPlugTaskNotFound`，目录已有，未新增码）；结论写进 `log_collect.create_ack` 事件、`log_collect.create` 事件与 WebSocket `log_data.create_ack`。

### B3 前端判定

- 新增 `CREATE_ACK_GRACE_MS = 90s`（短硬上限，不复用 10 分钟窗口）：仅当「本次会话亲自下发 + 从未见过 running + 未超窗」时把 `none` 降级为 `wait_refresh`。
- 超窗后 `patch_failed` 的文案按 `sessionAdopted` 分流：见过 running 才是「采集中断」；从未见过则明确「任务下发后节点未建立采集任务」，并给出核对 acli 版本与专项的指引。
- `SyncAction` 增加 `errorCode`，自动对账与主流程抛出前都优先采用判定层码，`error_code` 不再恒为空。
- 主流程 `pollUntilCollected` 补传 `requireSessionAdopt`，否则宽限门不生效。

## 四、验收标准

1. 同类现场（create `exit_code=0` 但节点无任务）不再出现 `error_code` 为空的「节点上已无任务，采集中断」；失败记录带 `LC-PLUGIN-008`、`detail.create_output` 与可读的「未建立采集任务」文案。
2. `log_collect.create_ack` 事件含 `result`、`node_states`、`trace_id`；`log_collect.create` 事件含 `create_ack`、`create_ack_states`、`output_len`、`output_truncated`。
3. 正常采集不因宽限期被延迟收敛：`none + archivePath` 仍 `patch_completed`，`completed` 的 L1 归属门逻辑不变，接管历史任务不等待。
4. `failed` 仍是终态，只允许用户显式「接管」走 `failed → collecting`。
5. 单测：Go `TestConfirmLogCollectCreate` 覆盖三态与取消边界；TS 判定层覆盖宽限、超窗、见过 running、接管、无包回归。
6. UI 验收用真浏览器：模拟点「开始收集」，确认失败提示不再误导、提示区 `clientHeight >= scrollHeight`。

## 五、回滚与失效边界

- 回滚顺序：先回滚 B1（行为变更），B2 可独立保留；B3 的宽限是独立常量，可单独调小或关闭。
- 宽限必须有硬上限，否则真实接单失败会被掩盖成永久转圈；`pollUntilCollected` 本身有 1 小时上限，90 秒窗口不与之冲突。
- 确认阶段认 `completed` 会放行上一轮残留报告，重演「3 秒假完成」；完整输出含上传票据，落库前必须脱敏且限长。
- **只改平台不能修节点 acli**：本次改动只让失败说真话、可定位，现场仍需按「只读核对 → 换专项 A/B 对照 → 拿完整输出」确认 acli 1.0.0 与节点环境（cgroup v2）的兼容性，否则重试仍会失败。
- 两条历史 `failed` 任务不得用 SQL 直接改成 `completed`；只能「重新收集」或走状态机允许的接管边。
- 客户现场节点本机不可达，真机端到端只能客户侧执行；不得用伪造节点报告把现场工单推成完成。
