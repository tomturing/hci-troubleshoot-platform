# KBD 生产者信号产出变量别名（alias）设计方案

## 背景与需求

PR#790（feat: KBD生产者信号使用产出变量目录）合并后，QKV 生产者信号的产出变量名由自由输入升级为工具目录下拉选择，实现了"变量名 → JSON 路径"的不可拆分绑定，效果优秀。

但该改动引入了新问题：**同一个 KBD 内若有两个生产者信号都需要产出同名变量（如 `END`），两者的变量名选项相同，运行时写入变量池时第二个信号的值会覆盖第一个，后续消费者信号的对比逻辑失效。**

典型场景：两段时间区间各取一个 `END`，之后对比两段区间的告警发生数。PR#790 之前可手动填 `END1`、`END2`；PR#790 之后只能从目录选 `END`，无法区分。

## 方案（WHAT）

### 核心设计：引入 `alias` 字段（KBD 级局部变量名）

每个 `orchestrate.produces` 条目的结构从：
```json
{ "name": "END", "path": "end" }
```
扩展为：
```json
{ "name": "END", "path": "end", "alias": "END1" }
```

| 字段 | 含义 | 维护者 | 作用域 |
|------|------|--------|--------|
| `name` | 工具目录标准变量名，从下拉选择 | 工具管理 | 全局（工具层） |
| `path` | JSON 提取路径，跟随目录联动 | 工具管理 | 全局（工具层） |
| `alias` | KBD 级局部变量名，手动填写 | KBD 审核者 | 局部（KBD 级） |

**有效变量 key 计算规则（单一真相源）**：
```
effective_key = alias.trim() if alias else name
```

运行时写变量池、消费者信号 requires 引用，一律使用 effective_key。

### 向下兼容

`alias` 字段可选，缺失时 `effective_key = name`，旧版 KBD 数据无需迁移，完全向后兼容。

## 决策依据（WHY）

### 为什么选此方案

1. **最小破坏性**：`alias` 是纯新增字段，不修改 `name`、`path` 的含义，不影响工具目录数据结构。
2. **职责分离清晰**：工具层负责"变量的语义标准化"，KBD 层负责"变量的局部命名"，两层各自内聚不交叉。
3. **向下兼容**：字段可选，旧数据无需迁移，降低风险。
4. **单一规则入口**：`effective_key` 计算逻辑集中在一处（前后端各一个辅助函数），不散落多处。

### 为什么不选其他方案

| 备选方案 | 否决原因 |
|---------|---------|
| 在工具目录中新增 END1、END2 条目 | 违背目录语义：目录应是标准化语义标识，不应承载业务局部命名。且每个 KBD 的区分需求不同，目录会无限膨胀。 |
| 改为 name 字段可自由输入 | 完全回退到 PR#790 之前的状态，丢失目录带来的路径自动绑定和标准化收益。 |
| 在 requires 侧做聚合（同名 produces 取数组） | 改变变量池语义（单 key 对应多值），影响所有下游消费者，侵入性极强。 |

## 验收标准

1. 同一 KBD 配置两个 QKV 生产者信号，均选 `END`，分别设 alias `END1`、`END2`，保存成功。
2. 信号 JSON 存储正确：`{ name: "END", path: "end", alias: "END1" }`。
3. 消费者信号 `requires: [END1, END2]` 校验通过。
4. 无 alias 的旧 KBD 行为不变：有效 key 仍为 `name`。
5. Bundle 工厂编译仿真 fixture 使用 `END1`/`END2` 作为 key。
6. 前端单元测试通过，后端信号校验测试通过。
