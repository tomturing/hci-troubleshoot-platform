# 2026-11-17 P2 交付链尾归档核验方案

## 背景与需求

见 [需求事件文档](../../requirement/events/2026-11-17-P2交付链尾归档核验.md)。

## 一、5888 接口到底检查了什么

在 0.2 主机 `/acli/app.py:1395` 逐行确认：

1. `filename` 必须整体匹配 `Q` + ASCII 13 位数字 + `.zip`（`validate_filename` 用 `re.fullmatch` + `FILENAME_STRICT_PATTERN`，堵住 Unicode 数字、尾部换行和只从头匹配）；
2. 取 `case_id = filename[:-4]`，拼出 `os.path.join(UPLOAD_FOLDER, case_id)`，即 `/sf/log/{工单号}/`；
3. 只有该目录存在时，列出文件并挑满足以下任一项的条目：文件名等于 `Q{工单号}.zip`，或以 `Q{工单号}-` 开头且以 `.zip` 结尾（同名不覆盖时的改存名）；
4. 用 `os.path.isfile` 过滤，再按 `os.path.getmtime` 取**最新一条**；
5. `os.stat` 返回 `size / mtime / stored_name / target_path`；无候选时返回 `found=false`。

**结论**：这是真实检查 `/sf/log/<工单号>/` 下是否存在对应 zip 的落盘侧权威接口，设计合理；`stored_name` 回报实际落盘名，不假设等于请求名。但它**不回答字节级完整性**：`sha256` 固定为 `null`，因为大包逐字节读会阻塞其它上传；摘要只在 24 小时内有效的 `/upload_status/<upload_id>` 有。因此平台判据只能使用"存在 + 体积 + 落盘时间"，不能声称验过摘要。

## 二、清理前提下如何判断"归档成功"

5888 的 `lifecycle_clean.py cases` 是水位驱动清理：高于 96% 开始、低于 90% 停止，受 180 天合规下限与单次 500 GB 上限约束。当前机器 cron 只启用了分片清理，工单清理由人工/水位触发，但设计上必然会发生。

这决定了探测策略必须区分"确认时刻的事实"与"现在的状态"：

| 问题 | 本方案答案 |
|------|-----------|
| 批量还是单个？ | **在线链路只做单任务探测**：P2 relay success 时对该工单查一次，不扫全表。历史对账是一次性只读报告，不是运行期机制。 |
| 一次还是定期多次？ | **一次有界探测**：最多 3 次，间隔 0/2/6 秒，且只有 `archive_missing` 才重试（异步合片竞态）；`size_mismatch / stale_archive / probe_error` 是确定性结论或无法证实，不再重试。没有周期性轮询。 |
| 已成功的会重复探测吗？ | **不会**。核验通过即写 delivered；reconcile 的 `settle_delivered_relays` 只处理 `delivered + running/pending`，不会再碰它；`claim_stale` 也排除 delivered。只有用户主动补交付才会重新走一次新链路。 |
| 历史已交付但后来被清理怎么办？ | **不反转**。5888 已确认过的工单不因后续清理被改成失败；没有确认快照的历史工单保持原 `relay_status` 口径。因为"现在不存在"无法区分"从未落盘"与"正常清理"。 |

全库只读对账（458 任务 / 251 工单）发现 4 张 delivered 但当前无归档，正是上述区分的现实案例；其中 `Q2026110666666` 的合片 worker 两次记录成功落盘并给出 sha256，但目录现已不存在且无删除日志，进一步说明不能用"当前缺失"反推"当初失败"。

## 三、实现

### 1. 统一判据

新增 `backend/case-service/app/domain/log_collect_archive.py::judge_archive()`，P1/P2 共用：

- `found=false` → `archive_missing`；
- 体积非法 → `archive_size_invalid`；
- 落盘体积小于任务记录值 → `size_mismatch`（截断只可能变小；不要求相等，P1 的 `expected_size` 是插件自删前的峰值观测）；
- mtime 早于任务创建超过 300 秒 → `stale_archive`（防止同名历史包被当成本次结果）；
- 否则 `verified`。

原 P1 `_judge_p1_archive` 改为薄包装，避免两套口径漂移；删除重复常量。

### 2. P2 终态收口

- `LogCollectRelayService._confirm_archive()`：在 `_run()` 拿到 `upload_status=done` 之后、`_finish(success)` 之前调用 `SangforRelayClient.archive_status()`，产出快照：
  `verified / reason / filename / stored_name / target_path / expected_size / archived_size / archived_at / checked_at / attempts / source=archive_status`。
- `_finish(..., archive_confirmation=...)`：
  - 确认通过 → `delivery_status=delivered`、`delivery_finished_at=now`；
  - 未通过 → `delivery_status=queued`、`delivery_error=链尾归档核验未通过（原因）`、`delivery_finished_at=NULL`；`relay_status=success` 与 `status=completed` 不变，用户仍可用既有补交付入口；
  - detail 按字典合并写 `archive_confirmation`，不整块覆盖既有证据。
- `archive_confirmation` 加入 `_PUBLIC_DETAIL_RESERVED_KEYS`，浏览器 PATCH 不能伪造。
- 管理端 `_EVIDENCE_DETAIL` 透传该键。

### 3. 展示层

- `delivery_evidence_ok()`：有快照时以 `verified` 为准；无快照的历史任务保留原 `relay_status` 口径，避免批量翻转。
- 契约新增条件 `archive_unconfirmed`「归档链尾未确认」，未确认的 P2 在任务进展中显式可见，但结论仍是 `unfinished`，不冒充成功。

### 4. 可观测性

新增结构化日志 `archive_tail_confirm task_id=... filename=... verified=... reason=... attempts=...`，与既有 `trace_id` 链路并行；终态日志补 `chain_verified` 字段。

## 影响范围与测试

- 新增 domain 判据模块；改 P1 路由、relay 服务、service 保留键、管理端投影、展示层与契约七份生成物。
- 定向测试 107 例通过：覆盖共享判据四种结果、P2 确认/未确认两条链路、快照合并、历史口径兼容、P1 判据不回归。
- 全库只读对账脚本结果见上一轮事件文档与记忆；本次不自动改写任何历史行。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 5888 探测短暂失败导致误判未交付 | 不把 `probe_error` 当否定结论；保留 queued 并给原因，用户可补交付重验 |
| 清理后历史任务被批量改错 | 历史任务无快照时保持原口径；确认过的任务不重探 |
| 同名历史包冒充本次结果 | `stale_archive` 用 300 秒回看窗口拦截 |
| P1/P2 判据漂移 | 共用 `judge_archive()`，P1 原函数仅保留薄包装 |
