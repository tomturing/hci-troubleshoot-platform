# P1 直传票据闭环（2026-11-03）

## 一句话

5888 启用 `ACLI_UPLOAD_TOKEN` 后，节点 acli 的直传（P1）在 `/init_upload` 被 401 全量打回；本次用「平台签发 per-task 票据 + bridge 注入请求头 + 5888 验签 + 平台回读归档核验」把 P1 链路补齐，**acli 与 5888 的既有上传协议都不改**。

## 现象与定位

现场工单 `Q2026110300278`：界面显示「正在发送到日志服务器：失败（100%）」，随后自动切到 P2 并成功交付。

对齐证据：

| 来源 | 事实 |
|---|---|
| 5888 服务端日志 | `11:11:14.787`、`11:11:16.916` 两次 `鉴权失败: /init_upload from 111.17.220.178` |
| 平台任务库 | `11:11:16` 记 `upload_state=重试中`，`11:11:21` 变 `失败` |
| acli 行为 | `upload_state` 从未出现「发送中」，直接「重试中→失败」，即卡在 init 阶段 |
| 反证 | 10-31 起 5888 收到的成功 `init_upload` 全部来自平台代传（python-httpx）/浏览器/本机，无一个 acli 客户端 |

根因两件事叠加：

1. **acli 不会携带任何认证头**：平台只下发 `-u <url>`（`terminal_bridge/log_collect.go` 默认 `http://acli.sangfor.com.cn:5888/`），没有注入位。
2. **默认路径被推上这条必然失败的路**：可达性探测 `curl <logServerURL>` 打的是 5888 根路径 `/`，而 `/` 免鉴权、永远 200；`200–499` 一律判「可达」→ 前端默认 P1。判据（网络可达）与目标（能否直传）分叉。

## 方案

```
平台 case-service          terminal_bridge(SSH)           节点 acli              5888
  │ 签发 p1.v1.<payload>.<sig>      │                        │                    │
  ├────────────────────────────────▶│ 拼 -L 0:Authorization:Bearer <ticket>        │
  │                                 ├───────────────────────▶│ 原样带头发上传 ────▶│ HMAC 验签
  │                                 │                        │                    │ 绑产物名
  │ POST /tasks/{id}/verify-archive │                        │                    │
  ├────────────────────────────────────────────────────────────────────────────────▶
  │ 比对 found / size / mtime                                                      │
  │ 通过→delivered；不通过→failed + LC-TRANSFER-007                                 │
```

### 契约

| 项 | 值 |
|---|---|
| 票据格式 | `p1.v1.<base64url(payload_json)>.<hex_hmac_sha256>` |
| 签名对象 | `p1.v1.<base64url(payload)>` 整串（含前缀），防格式升权 |
| payload | `{"v":1,"cid":工单号,"fn":产物名,"iat":签发秒,"exp":过期秒,"jti":随机}"` |
| 有效期 | 默认 12h（覆盖采集 30min + 上传 2h），两端允许 300s 时钟漂移 |
| 传输 | `-L 0:Authorization:Bearer <ticket>`（**不是** `-H`：`-H` 对全局生效，会把凭据发给 acli 访问的每一个地址） |
| 密钥 | 平台 `LOG_COLLECT_P1_TICKET_SECRET` ←→ 5888 `ACLI_P1_TICKET_SECRET`，两侧同值 |
| 核验端点 | `GET <5888>/archive_status?filename=Q...zip` → `found/size/mtime/stored_name/target_path` |

**为什么用 HMAC 而不是非对称**：两种模式下「密钥泄露即可伪造」，而 5888 与平台都不在客户环境；非对称换来的「验签方不持签发密钥」收益有限，代价是给 case-service 镜像新增密码学依赖（实测当前镜像 `import cryptography` 失败）。

**为什么票据不进 URL**：URL 会进 `ps`、进 bridge 的 command 字段、进 `detail`，凭证一旦进这些地方就等于写进排障材料。

## 改动清单

### 5888（`/acli/app.py`，独立部署）

- `verify_p1_ticket()`：HMAC 验签 + 过期 + 产物名绑定，错误码与平台侧同名（`bad_signature`/`expired`/`filename_mismatch`/…）。
- `_require_auth` 分流：`p1.v1.` 前缀走票据；其余仍走全局 `ACLI_UPLOAD_TOKEN`（P2 与手工上传页不受影响）。
- `GET /archive_status`：按产物名回报落盘事实；同名改存 `{工单号}-{时间戳}.zip` 时取最新一条。
- 审计日志：`[P1] 票据通过/拒绝: case=… jti=… path=… filename=… from <ip>`，失败必带 reason。

### 平台 `case-service`

- `app/services/p1_ticket.py`：签发与校验（纯标准库）。
- `POST /api/log-collect/tasks`：P1 任务在响应里附 `p1_ticket` / `p1_ticket_expires_at`；**票据不进库**（12h 就过期，存下来只是废票）。
- `POST /api/log-collect/tasks/{id}/verify-archive`：回查 5888 归档，比对 `found` / `size` / `mtime`，写 `delivery_status` 与 `detail.delivery_evidence`。
- `config.py`：`LOG_COLLECT_P1_TICKET_SECRET`、`LOG_COLLECT_P1_TICKET_TTL_HOURS`。
- 错误码新增 `LC-TRANSFER-007 直传归档核验未通过`（catalog + Go 常量同步）。

### `terminal_bridge`

- `log_collect` 创建消息新增 `upload_ticket`；拼装时注入 `-L 0:Authorization:Bearer …`，票据字符集白名单 `^[A-Za-z0-9._-]{16,600}$`（bridge 拼的是 shell 命令，acli 自己不防注入）。
- `redactUploadTicket()`：把票据从 `Detail` 与 `command` 日志里替换为 `[REDACTED]`。**不能只靠通用脱敏**——`sensitiveTextPatterns` 靠 `password|token|secret` 关键词匹配，`Authorization: Bearer x` 一个关键词都没有。
- 探测新增 `acli_supports_upload_header`（取 `acli log_collect create --help` 原文里的 `--url-header`/`--header`）：老版本 acli 没有该参数，P1 必然 401，前端据此置灰。
- 进度事件新增 `upload_error`（上传块内首个失败行）与 `upload_raw_tail`（上传阶段输出尾部 512 字）。此前 `upload_state` 只有「失败」两个字，无法区分 401 / 超时 / 网络。

### 前端 `customer`

- 建任务后取 `p1_ticket` 随 WS create 下发；**拿不到票据时当场改走 P2**，并把落库路径改回 `bridge_relay`（不让界面显示一次假失败）。
- `p1Disabled` 增加 acli 能力判据（仅在明确 `false` 时禁用，老 bridge 不返回该字段时按未知处理）。
- `patch_delivered` 之前调用核验接口：不通过则写 `delivery_status=failed` + `LC-TRANSFER-007`，并报错而不是「同步成功」。核验接口不可用时保持旧行为（不能用「核验不了」否掉一条本来成立的结论）。

## 部署与切换顺序

```bash
# 1) 生成密钥（64 位 hex）
openssl rand -hex 32

# 2) 先配 5888（只加环境变量，代码已兼容：密钥为空则不启用票据通道）
sudo systemctl edit acli-5888   # Environment=ACLI_P1_TICKET_SECRET=<hex>
sudo systemctl restart acli-5888

# 3) 再配平台（values.yaml → secrets.p1TicketSecret）并升级
#    未配置时 case-service 不签发票据，前端自动降级 P2 —— 不会发出无凭据直传
helm upgrade ...

# 4) 验证
curl -s "http://acli.sangfor.com.cn:5888/archive_status?filename=Q2026110300278.zip" -H "Authorization: Bearer <ticket>"
```

**回滚**：删除 `secrets.p1TicketSecret` 并升级 → 平台停止签发票据 → 前端自动走 P2。5888 侧的 `ACLI_P1_TICKET_SECRET` 可保留（无票据通过时不影响全局 Bearer 通道）。

| 层 | 用例 | 结果 |
|---|---|---|
| 平台票据 | 签发/验签、篡改载荷与签名、过期与时钟宽限、产物名不匹配、非票据输入、密钥未配置双向拒绝 | 16 passed |
| 5888 鉴权与核验 | 正确票据放行、无凭证/坏签名/过期/跨工单 401、全局 Bearer 不受影响、归档缺失/存在/改存取最新、非法文件名 400 | 22 passed（真实 venv） |
| bridge | `-L` 注入形态、无票据不注入、注入型票据被拒、脱敏后无原文、上传错误抽取、采集失败不污染 upload_error | 通过；全量 `go test ./...` 无回归 |
| 前端 | 类型检查 + 全量单测 | 526 passed |

跨语言契约由 5888 测试独立实现签发、平台侧独立实现验签，两侧对同一票据达成一致。

## 已知边界（必须知道）

1. **核验锚点是「大小 + 时间窗」，不是摘要**：P1 链路上平台没有源包副本，且 acli 上传成功后插件会自删压缩包，事后无法补算 sha256。因此能拦住截断上传、错包与历史同名包，拦不住「同大小的损坏文件」。完整摘要校验仍只在 P2。
2. **核验不通过通常不可恢复**：节点包已被删，只能重新采集。UI 已明确提示，不假装可重试。
3. **`-L` 的实际生效性依赖 acli 1.0.0 的既有能力**：帮助文本已列出该参数，但真实上传链路上的行为需要在现场首次执行时确认（判据：5888 日志出现 `[P1] 票据通过` 且无 `鉴权失败: /init_upload`）。若实测不生效，按设计降级为 P2——不会比现状更差。
4. **探测仍只回答「网络可达」**：`acli_supports_upload_header` 补上了节点能力，但「平台是否已配密钥」只有建任务时才知道，因此前端在建任务后还有一次「无票据则改 P2」的兜底。
