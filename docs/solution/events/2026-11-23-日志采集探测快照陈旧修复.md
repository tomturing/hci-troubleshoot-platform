# 日志采集探测快照陈旧修复（Q2026112300145）

## 文档信息

- **版本**: 1.0
- **创建日期**: 2026-11-23
- **状态**: 已修复，前端单测覆盖
- **关联代码**: `frontend/customer/src/components/LogCollectPanel.vue`、`src/components/__tests__/LogCollectPanel.spec.ts`
- **关联工单**: Q2026112300145

---

## 一、现象

acli 刚安装/升级完成，日志采集面板仍显示安装前的版本与「节点清单获取失败」；用户必须手动刷新页面（F5）才能看到新快照。

## 二、根因

事实复查（`scheduleFactRecheck`）在采集中一律 `return` 丢弃。而 acli 安装与采集在下发流程里是**紧邻事件**（本工单相隔 13 秒），复查时机恰好全部落在 `running` 为真时：

1. **调用侧丢弃**：`scheduleFactRecheck` 只要 `running` 为真就直接返回，不记录任何待办。
2. **定时器侧丢弃**：30 秒复查定时器到期时若采集已开始，回调同样直接返回。安装成功后 30 秒才到期，用户十几秒内就点了「开始收集」，因此这条路径必然被丢弃——这才是本工单的实际路径。
3. **重探被去重时无复查**：安装成功后内部重探可能因 `prepareState === 'probing'` 复用进行中的探测而返回 `false`；旧实现只在 `prepareState === 'failed'` 分支安排复查，去重分支被静默跳过。
4. **复查预算耗尽**：预算（`PROBE_RECHECK_MAX = 3`）被「装好但还没同步」的失败复查耗光后，即便安排复查也会被上限拦掉。

四条叠加的结果是：**采集结束后没有任何事件能再触发探测**，快照永久停在安装前。

## 三、修复

不改变「采集中不探测」这条物理约束（探测要连发多条 SSH 命令，会和采集抢同一个会话），只把「丢弃」改成「延后」：

| 位置 | 改动 |
|---|---|
| `scheduleFactRecheck` | `running` 为真时置 `recheckPendingAfterRun = true` 并返回，不再静默丢弃 |
| 30s 复查定时器回调 | 到点时 `running` 为真同样置 pending，而不是 `return` |
| `watch(running)` | 采集进入终态时若存在 pending，清标记并补做一次复查 |
| `markAcliInstalled` | 安装成功后 `probeRecheckCount = 0` 重开预算；并把 `scheduleFactRecheck()` 移出 `failed` 判断，`!refreshed` 时统一调用（去重与真失败都安排） |

约定：pending 只在采集终态消费一次；复查仍走 30s 节奏（会话刚释放时立刻探测风险更高，且与既有低频策略一致）。

## 四、验收

新增用例「安装收尾时尚在 running：复查不丢弃，阶段结束后自动补探」，覆盖完整现场时序：

1. 首探：acli 未安装、节点清单为空；
2. 安装失败落卡片 → 点「重试安装」进入 `installing`（`running = true`）；
3. 安装成功 → 内部重探；
4. 重探失败 → 不改写安装结果，但复查必须排上；
5. 收尾把 `stage` 还原为 `idle` → 被推迟的复查补做；
6. 补探读到装好后的真值，界面自动点亮（`1.0.1`、清单非空），无需 F5。

对抗性验证：把业务代码回退到缺陷版本后，该用例在第 6 步失败（`expected 2 to be 3`，补探未发生）；修复后通过。前端全量 56 个文件 / 762 例通过，`vue-tsc -b` 与 `vite build` 均无错误。
