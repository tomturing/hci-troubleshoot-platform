# 2026-09-23 统一认证系统设计方案

> 事件文档：需求 → 方案阶段产出。方案完成后冻结，永久保留，不再修改。
> 关联任务文档：[task/events/2026-09-23-统一认证系统设计方案.md](../../../task/events/2026-09-23-统一认证系统设计方案.md)

## 背景与需求

### 现状：平台"认证"不是真认证

| 问题 | 代码事实 |
|------|---------|
| 匿名访客被自动签发身份 | `api-gateway/app/middleware/identity.py` 的 `IdentityMiddleware` 对无 Cookie 请求直接 `issue_identity()`（`uuid4` + HMAC），`require_user` 永不 401 |
| 管理员无操作者身份 | `frontend/admin/nginx.conf:64-66` 注入共享静态 Bearer `INTERNAL_API_TOKEN`；所有管理员共用同一令牌，服务端无法区分"谁" |
| 管理操作大面积无追溯 | 仅 `diagnosis_management_audit` 记录 `actor_id`；KBD / Prompt / 工具 / SOP 管理（`system_prompt`、`tool_definition`、`skill_definition`、`kbd_revision`）**无 `created_by`/`updated_by`** |
| 归属双体系、追溯断链 | case 侧用 `client_id`/`user_id`，diagnosis 侧用 `tenant_id`；唯一连接点 `diagnosis_session.case_id`；唯一追溯手段是 `trace_id`（请求维度，非账号维度） |
| 审计 actor 无法 join 账号 | 全部 5 张 audit 表的 `actor_id`/`actor` 均为 `varchar(128)` **自由字符串、无 FK `user`** |
| 单一静态密钥三职 | `INTERNAL_API_TOKEN` 同时充当服务间 Bearer、Cookie HMAC 密钥、出口签名密钥；泄露即全平台管理员 |

### 需求（本次确认）

1. 两套认证（customer / admin）**独立互不影响**
2. **customer 与 admin 均采用账号密码**（微信登录延后为可选迭代；`user_credential` 通用凭证模型保留，未来加微信无需改表）
3. 符合业界最佳实践与范式
4. 尽可能**保留现有系统交互方式**
5. 账号与工单等数据**完整关联**，所有操作**可通过账号追溯留存**

### 本次目标定位（双重目的）

**目的一（当下）：彻底闭环安全漏洞**

本次登录功能的首要目标是消除 SRC-2026-5358 遗留的安全缺陷，**而非建设完整账号体系**：

| 待闭环缺陷 | 本次如何解决 |
|-----------|-------------|
| 管理面"网络可达 = 管理员" | admin 强制账号登录，移除 `INTERNAL_API_TOKEN` 静态令牌注入 |
| 所有管理员共用同一令牌，操作者不可辨 | 每人独立账号 + JWT `sub` + `operation_audit.actor_user_id` |
| KBD / Prompt / 工具 / SOP 管理完全无操作者记录 | 全量接入 `operation_audit` |
| 客户身份是随机串，匿名工单成孤儿 | 实名账号绑定，`case.user_id` 即账号主键 |
| 单一静态密钥兼三职，泄露即全平台失守 | RS256 + JWKS 非对称签名，`kid` 可轮换 |

**目的二（长远）：为完整账号管理与权限校验打基础**

本次同时确立可扩展的结构基础，使后续「正常账号注册 / 登录 / 账号管理 / 权限校验」能够**无门槛演进**（加能力，而非改结构）：

| 扩展点 | 结构性基础（本期落地） | 未来可直接扩展的能力 |
|--------|---------------------|-------------------|
| 多凭证 | `user_credential` 1:N + `credential_type` | 微信 / 手机号 / 邮箱验证码 / 企业微信 / OIDC SSO |
| 多角色 | `user.roles` jsonb + GIN 索引 | 只读审计员、一线支持、租户管理员等角色体系 |
| 主体域 | `user.realm` | 渠道商 / 合作伙伴 / 服务账号等主体类型 |
| 标准令牌 | JWT（`sub` / `realm` / `roles` / `aud`）+ RS256 + JWKS | 接入外部 IdP、跨服务统一鉴权、细粒度 RBAC / ABAC |
| 统一审计 | `operation_audit`（`actor_user_id` + `trace_id`） | 合规审计导出、行为分析、责任追溯体系 |
| 账号管理面 | admin-ui 账号管理（增删改 / 改密 / 启停 / 强制下线） | 自助注册审核、找回密码、角色分配 UI |

**边界声明（避免过度设计）**

本期**只做结构性预留，不做完整功能**。以下明确**不在**本期范围，但均可基于上述结构直接追加（无需改表或重构）：

- 角色增删 UI 与权限矩阵管理界面
- 自助注册门户、找回密码、短信 / 邮箱验证
- 组织架构与租户（tenant）体系打通
- 细粒度 ABAC / 数据级权限
- 第三方 SSO Provider 实现（**仅保留 adapter 扩展位**，不接入具体 IdP）

### 已确认的设计分支（用户决策）

| 分支 | 决策 |
|------|------|
| 登录方式 | customer 与 admin **均为账号密码**；放弃微信开放平台资质申请（门槛高、周期不可控）。微信作为后续可选凭证类型，数据模型已预留 |
| 客户登录策略 | **强制登录才能建工单**（归属最清晰） |
| 管理员强度 | **仅账号密码**（简单优先），配套补偿控制见 §3.4 |
| 管理员账号管理 | DB 存储 + admin-ui 账号管理界面（种子初始化首个管理员） |
| 数据模型 | **统一主体**：customer 与 admin 都是 `user`，差异只在凭证方式与角色 → Subject + Credential(1:N) + Role 范式 |

## 方案（WHAT）

### 3.1 总体架构：独立 auth-service + 统一主体模型

新增 `auth-service`，**只做认证**（账号、凭证、会话、签发/轮换/吊销令牌、登录审计）；**授权留在原处**——现有 `CUSTOMER_ROLE`/`ADMIN_ROLE` 与权限集合（`CREATE_ROLES`/`ARTIFACT_ROLES`/…）及 `test_auth.py` 双向契约**全部保留**，仅把 actor 来源从自报头换成 JWT。

```
customer-ui ─┐
             ├─→ api-gateway（验签 JWT，构造 actor）─→ 各业务服务
admin-ui   ─┘         ↑
                      │ JWKS 公钥（缓存）
                 auth-service（签发 RS256 JWT）
                      ├─ user / user_credential / user_role
                      ├─ 账号密码校验 argon2id（customer + admin，按 realm 隔离）
                      └─ [未来扩展] 微信 OAuth2 / 其他 IdP adapter
```

**职责边界**：`user_*` = 主体域（谁）；`auth_*` = 认证运行时域（会话、登录审计）。

### 3.2 数据模型（统一主体 + 通用凭证）

#### 表清单

| # | 表 | 状态 | 作用 | 域 |
|---|-----|------|------|-----|
| 1 | `user` | **扩展** | 统一主体（customer + admin）+ `roles` jsonb + `token_version` | 主体 |
| 2 | `user_credential` | **新增** | 通用凭证 1:N（password / wechat / phone / oidc…） | 主体 |
| 3 | `auth_session` | **新增** | 登录会话 / 吊销 / 强制下线 | 认证 |
| 4 | `auth_audit` | **新增** | 登录成功失败 / 改密 / 凭证变更 | 认证 |
| 5 | `operation_audit` | **新增** | 全操作按账号追溯（跨模块通用） | 审计 |

> **新增表 4 张**（角色不独立建表，改用 `user.roles jsonb`，理由见 §4.13）。

**扩展 `user` 表**（加列，不改现有列语义）：

```sql
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS realm       varchar(16) NOT NULL DEFAULT 'customer'; -- customer|admin
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS status      varchar(16) NOT NULL DEFAULT 'active';
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS nickname    varchar(128);
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS avatar_url  text;
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS roles        jsonb NOT NULL DEFAULT '[]'::jsonb;
ALTER TABLE "user" ADD COLUMN IF NOT EXISTS token_version int  NOT NULL DEFAULT 1;
ALTER TABLE "user" ALTER COLUMN client_id DROP NOT NULL;   -- admin 无端侧 client_id
```

角色以 jsonb 数组存储（如 `["platform_admin"]`），配合：

```sql
CREATE INDEX IF NOT EXISTS idx_user_roles ON "user" USING gin (roles);  -- 按角色反查（低频）
```

- `roles` 采用 jsonb **而非独立 `user_role` 表**，取舍见 §4.13
- `token_version`：改角色 / 停用账号时 +1，使已签发的 JWT 立即失效（见 §3.8）

- `realm`（主体域）与 `user_type`（`temporary`/`authenticated`，认证状态）**正交**，两者都保留
- `client_id` 放宽为可空是**唯一破坏性改动**：admin 无端侧 `client_id`；PostgreSQL 的 `UNIQUE` 允许多个 `NULL`，故多个 admin 行不冲突。customer 流程与 `case.client_id NOT NULL` **完全不变**

**新增 `user_credential`（通用核心，1:N）**：

```sql
CREATE TABLE IF NOT EXISTS user_credential (
    credential_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         uuid NOT NULL REFERENCES "user"(user_id) ON DELETE CASCADE,
    credential_type varchar(32)  NOT NULL,      -- password | wechat | phone | oidc ...
    identifier      varchar(255) NOT NULL,      -- 用户名 | 微信 unionid | 手机号
    secret          text,                       -- argon2id hash | 微信 openid
    extra           jsonb NOT NULL DEFAULT '{}'::jsonb,  -- 第三方 profile / MFA secret
    failed_attempts int NOT NULL DEFAULT 0,     -- 凭证级失败计数
    locked_until    timestamptz,                -- 凭证级锁定
    status          varchar(16) NOT NULL DEFAULT 'active',
    last_used_at    timestamptz,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_usercred_type_ident ON user_credential(credential_type, identifier);
CREATE INDEX IF NOT EXISTS idx_usercred_user ON user_credential(user_id);
```

一个 user 可挂多种凭证 → **未来 admin 支持微信 / customer 支持密码，只需插入一行凭证，不改表结构**。

**新增 `user_role`**：`(user_id, role)` 联合主键，支持多角色（如同时 `platform_admin` + `support_engineer`）。

**新增 `auth_session`**（命名说明见 §4.6）：`session_id, user_id, realm, refresh_token_hash, ip, user_agent, expires_at, revoked_at, created_at, trace_id`。

**新增 `auth_audit` / `operation_audit`**：字段范式**对齐现有 `diagnosis_management_audit`**（团队已熟悉的形状），并补可 join 的强关联：

```sql
CREATE TABLE IF NOT EXISTS operation_audit (
    audit_id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    actor_user_id uuid REFERENCES "user"(user_id) ON DELETE SET NULL,  -- ★可 join 的强关联
    actor_display varchar(128),                    -- 快照（服务/系统/已删除账号仍可读）
    actor_realm   varchar(16),                     -- customer / admin / system
    actor_roles   jsonb NOT NULL DEFAULT '[]'::jsonb,
    action        varchar(64)  NOT NULL,
    resource_type varchar(64)  NOT NULL,
    resource_id   varchar(128),
    result        varchar(16)  NOT NULL DEFAULT 'success',  -- success/denied/failed
    details       jsonb NOT NULL DEFAULT '{}'::jsonb,
    trace_id      varchar(64)  NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now()
);
```

`auth_audit` 同构，额外记录 `ip` / `user_agent`（登录事件的安全属性）。

**不新增表**：第三方 OAuth 的 `state`（防 CSRF）若未来启用，使用短期 HMAC 签名串放入 Cookie，不落库（本期账号密码不涉及）。

### 3.3 customer：账号密码登录（微信延后为可选凭证）

customer 与 admin 同样采用账号密码，差异仅体现在 `realm`、凭证隔离、会话时长与锁定策略上。

**登录流程**：`POST /api/auth/customer/login {identifier, password}` → 匹配 `user_credential(type='password')` 且该 user 的 `realm='customer'` → argon2id 校验 → 签发 JWT（`aud=hci-customer`）→ 下发 `hci_cust_session`（HttpOnly / Secure / SameSite，7 天）。

**账号来源：轻注册（摩擦最低，推荐）**

1. 游客进入 customer-ui 可浏览、查看引导、填写工单草稿（**保留现有交互**）
2. 点击「提交工单」时引导**设置密码**（仅需「用户名 + 密码」两步，不做手机 / 邮箱验证码）
3. 系统以会话 `client_id` 找到（或创建）临时 `user` → 置 `user_type='authenticated'` + 写入 `password` 凭证 → 立即以该账号提交工单
4. admin-ui 同时支持运营**代开客户账号**（B2B 场景），代开账号首次登录强制改密

**为什么是"轻注册"而非完整注册**：客户在此场景的目标是"提交工单"，而非"拥有一个账号"。把注册压缩为"设个密码"，既满足强制登录的归属要求，又最大程度保留原有免登录体验、降低流失。

**历史匿名工单零迁移**：登录时用会话 `client_id` 找到临时 user → 升级为 `authenticated` + 写入密码凭证；`case.user_id` **不变** → 历史工单自动归属该账号，无需数据迁移。

### 3.4 admin：账号密码登录

- 密码哈希 **argon2id** + 恒定时间比较；强密码策略（≥12 位、禁弱密码）
- `POST /api/auth/admin/login` → 校验 → 签发短时效 JWT + `hci_admin_session`（`SameSite=Strict`）
- **移除 `admin/nginx.conf` 的静态令牌注入**与前端硬编码 `VITE_INTERNAL_API_TOKEN`（`KbdReviewView.vue` 等 8 处）→ 消除"共用令牌无追责"

**「仅账号密码」的补偿控制（公网管理面的必要加固）**：

| # | 控制项 | 说明 |
|---|--------|------|
| 1 | 失败锁定 | 同凭证 5 次失败锁 15 分钟（指数退避）；同 IP 限流 |
| 2 | 登录审计 | `auth_audit` 记录成功/失败/登出/改密，含 IP + UA |
| 3 | 异常告警 | 新 IP / 异地登录、连续失败触发告警 |
| 4 | 会话可控 | 登出即吊销；账号管理界面可强制下线 |
| 5 | 网络补偿 | 建议 `admin-guard` sourceRange 收敛到管理员公网 IP |
| 6 | MFA 预留 | `user_credential.extra` 预留 `mfa_secret`/`mfa_enabled`，本期不启用 |

> **残余风险（诚实告知）**：仅密码 + 公网可达仍面临撞库 / 钓鱼 / 暴力破解；上述措施**降低但不消除**，建议二期启用 TOTP 或 IP 白名单。

### 3.5 与现有系统整合（最小侵入）

- **保留 `case` / `user` 写入路径不变**：case-service 仍按 `client_id` UPSERT `user` 再建 `case`；认证只在其上补充 `user_type` / 凭证 / `realm` → 现有建单主链路**零改动**
- **网关改造**：`IdentityMiddleware` 优先解析 JWT 构造真实 actor；无 JWT 时仍签发匿名 Cookie（保留游客浏览），但匿名 actor **无建单 / 管理权限**；`_resigned_upstream_headers` 的 actor 改为从 JWT 派生 → **根除自报头伪造**
- **前端保留**：`window.__HCI_AUTH__.getAccessToken()` 契约保留（用 session Cookie 换短期 access token，内存缓存），现有 diagnosis 上传等调用零改动
- `case.user_id` 即账号主键 → 追溯链路 `case → user` **直接可达**，无需额外绑定表

### 3.6 账号-数据关联与全量追溯

- 统一 actor：`{user_id, realm, display, roles}` + **`trace_id`**（唯一调用链）
- `operation_audit` 覆盖：admin 全部写操作（KBD / Prompt / 工具 / SOP / 诊断管理 / 账号管理）与 customer 建单 / 上传 / 删除
- diagnosis 侧保留 `tenant_id`，增加 `actor_user_id`（网关从 JWT 注入）→ 诊断数据可按账号追溯
- **增值补齐（不新增表，只加列）**：给现有 5 张 audit 表各补 `actor_user_id uuid REFERENCES "user"(user_id)`（可空，兼容服务 / 系统操作），使**历史审计也能逐步 join 到账号**，否则新系统只覆盖"未来"，历史仍断链

### 3.7 令牌与密钥

- **RS256 非对称**（私钥仅 auth-service 持有），JWKS 端点 `/.well-known/jwks.json`；网关 / 服务缓存公钥验签 → auth-service 短暂不可用时**已登录用户不受影响**
- 复用 `diagnosis-service` 已有 `OidcJwtIdentityVerifier`（RS256/ES256/EdDSA + JWKS 缓存）与预留的 `DIAGNOSIS_IDENTITY_MODE=oidc` 分支
- Claims：`iss / sub(user_id) / aud / realm / roles / iat / exp / jti`
- 密钥按 realm 分（`kid` 前缀 `cust-` / `adm-`），支持多 kid 并存平滑轮换 → **根治 `INTERNAL_API_TOKEN` 一密钥三职问题**
- 会话 Cookie：`hci_cust_session`（7d）/ `hci_admin_session`（**4h 绝对 / 30min 空闲**，配合 §3.8 的 `token_version` 即时失效）

### 3.8 令牌失效与角色变更（token_version）

**问题**：角色随 JWT 携带，若管理员被降权或账号被停用，其已签发令牌在过期前**仍然有效**——最长可继续以管理员身份操作整个会话时长。这是"权限校验能否真正落地"的硬缺口，与角色用 jsonb 还是独立表**无关**（两种存储方案共有）。

**方案**：`user.token_version`（默认 1）+ JWT 携带版本号：

| 触发 | 动作 | 效果 |
|------|------|------|
| 改角色 / 停用 / 删除账号 | `token_version = token_version + 1` | 该用户所有已签发 JWT **立即失效** |
| 用户改密 | `token_version + 1` | 强制其他设备重新登录 |
| 网关验签 | 比对 JWT 内 `tv` 与库内当前值 | 不符 → 401，前端跳登录 |

**实现要点**：

- `token_version` 随用户加载进入 JWT claims（字段 `tv`）
- 网关验签**不需要每次查库**：版本号短 TTL 缓存（如 30s）比对；`auth_session` 记录签发时版本，吊销会话即失效
- admin 会话时长由 8h **缩短为 4h**（绝对）/ 30min 空闲，缩小缓存延迟下的暴露窗口
- 该机制属**结构性**能力（事后补需改令牌与核心链路），故纳入本期（符合 §4.12 判定标准）

### 3.9 可观测性

| 维度 | 内容 |
|------|------|
| 指标 | 登录成功率 / 失败率、凭证锁定数、活跃会话数、令牌签发与验签失败数、轻注册完成率 |
| 日志 | 结构化日志，全链路 `trace_id` + `user_id` + `realm`；禁止记录密码 / 令牌明文 |
| 链路追踪 | 登录链路（前端 → 网关 → auth-service → 数据库）端到端 trace；与现有 Tempo 体系一致 |

### 3.10 分阶段落地（双开关，每阶段可回滚）

`AUTHN_ENFORCE_ADMIN` / `AUTHN_ENFORCE_CUSTOMER` 两个 feature flag 独立控制：

| 阶段 | 内容 | 风险 |
|------|------|------|
| 0 | schema + auth-service 骨架 + JWKS | 零影响 |
| 1 | admin 登录上线（先灰度），保留 internalGuard | 低 |
| 2 | customer 账号密码登录（含轻注册），观察转化 | 低 |
| 3 | 开启建单强制登录 | 中（转化率） |
| 4 | 历史匿名工单认领 | 低 |
| 5 | 全面下线共享令牌 + 全量 `operation_audit` | 中 |

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 4.1 为什么新增独立 auth-service，而不是网关内嵌

内嵌会让 api-gateway 同时承担路由、鉴权、账号存储、凭证校验、令牌签发、第三方 OAuth 对接——职责膨胀，且认证相关的高频写（登录、会话）与网关转发耦合，故障域重叠。独立服务可独立扩容、独立限流、独立演进（加 MFA / 企业微信只加 adapter）。

### 4.2 为什么不接入外部 IdP（Keycloak / Authing）

外部 IdP 虽省事，但：① 引入新组件与运维负担；② 微信扫码仍需自定义适配器；③ 与平台既有的内部身份体系（`INTERNAL_API_TOKEN`、角色重签）整合复杂。平台已有 `OidcJwtIdentityVerifier` 与 `oidc` 模式分支预留，自建 auth-service 可直接复用这些资产。

### 4.3 为什么「统一 `user` 主体 + `user_credential` 1:N」，而不是 customer/admin 分表

初版设计曾提出 `customer_account` + `admin_account` 两张账号表，被否，理由：

1. **本质同一**：customer 与 admin 都是平台用户，差异仅在「凭证方式」与「授权角色」，不在主体本身
2. **未来可互换**：后续 admin 可能支持微信、customer 可能支持密码 → 分表会导致同一个人两处账号或重复建模
3. **扩展零改表**：新增登录方式 = 插入一行凭证，而非加列 / 加表
4. **追溯更直接**：`case.user_id` 就是账号主键，无需 `user → account` 多一跳

### 4.4 为什么必须新增 `user_credential`，而不是把密码 / unionid 直接加到 `user` 表

1. **1:N 关系**：一个用户可同时有微信 + 密码 + 手机等多种凭证，扁平加列会产生 `password_hash` / `unionid` / `phone` 稀疏列且无法表达多凭证
2. **约束表达**：`UNIQUE(credential_type, identifier)` 才能正确表达"同一微信只能绑一个用户"且"用户名在密码类型内唯一"；平铺列做不到类型隔离的唯一性
3. **锁定粒度**：失败锁定是**凭证级**（密码被撞库不应冻结微信登录）

### 4.5 为什么 admin 不能放进原 `user` 表的 `client_id` 体系

`user.client_id varchar(255) NOT NULL UNIQUE` 语义是"前端生成并持久化的端侧标识"。管理员没有端侧 `client_id`，硬塞需伪造值（如 `admin-xxx`），污染语义与唯一键空间。因此改为**放宽 `client_id` 为可空**（而非伪造），由 `realm` 区分主体域。

### 4.6 为什么登录会话表叫 `auth_session`，不叫 `user_session`

平台 `session` 表已被 conversation-service 占用，语义为 **SSE 长连接凭证**（`desired_schema.sql:2168`，绑定 `case_id NOT NULL`）。文档 `docs/solution/agent/02-架构设计/agent设计.md:1030` 明确记载该约定（`sop_execution` 因此不命名为 `sop_session`）。故认证域统一 `auth_*` 前缀（`auth_session` / `auth_audit`），与主体域 `user_*` 分层，避免与 SSE 语义混淆。

### 4.7 为什么 RS256 + JWKS，而不是继续用共享密钥 HMAC

现状 `INTERNAL_API_TOKEN` 一个静态密钥兼任服务间 Bearer、Cookie HMAC、出口签名三职，泄露即等于全平台管理员，且无 `kid` / 版本 / 轮换机制。RS256 非对称 + JWKS 使验签方只需公钥，私钥不外泄，支持多 kid 平滑轮换。

### 4.8 为什么不复用现有 audit 表，而要新增两张

现有 5 张 audit 表**全部域专用**且硬绑定业务实体：

| 表 | 绑定 | 能否承载通用操作审计 |
|----|------|-------------------|
| `audit_log` | `conversation_id` NOT NULL FK，仅 `audit_type='prompt'` | ❌ 语义为 Prompt 构建 |
| `diagnosis_management_audit` | `tenant_id` NOT NULL + FK `diagnosis_session` | ❌ 诊断域专用 |
| `diagnosis_legal_hold_audit` | `session_id` NOT NULL | ❌ 法务保全专用 |
| `dynamic_resource_usage_audit` | `consumer` 为服务名，无 actor | ❌ 资源 revision 追踪 |
| `vm_console_audit_event` | `capture_id` FK | ❌ 截图事件流 |

复用会语义混杂且受外键约束限制。但**字段范式复用 `diagnosis_management_audit`**（`actor_*` / `action` / `resource_*` / `result` / `details` / `trace_id`），保证团队认知与查询模式一致。

### 4.9 为什么 `operation_audit` 要新增 `actor_user_id` FK

现有所有 audit 表的 `actor_id` 是**无外键的自由字符串**，数据库层无法 join 到账号，这是"操作不可追责"的技术根因。新增可 join 的 `actor_user_id`，同时保留 `actor_display` 字符串快照（兼容服务账号 / 系统操作 / 已删除账号）。

### 4.10 为什么 customer 从「微信扫码」改为「账号密码」

原计划 customer 走微信开放平台网站应用扫码，评估后放弃，原因是**前置门槛高且不可控**：

1. 需开放平台**开发者资质认证**（企业主体 + 营业执照 + 法定代表人 / 对公验证 + 年费 + 逐年复审）
2. 需**域名 ICP 备案**（授权回调域必须为已备案域名）
3. 需公网回调可达且走 443；审核周期不可控（通常 1–3 工作日，驳回补材料会翻倍）
4. 本地 / 内网环境**无法调试**（微信服务器需回调公网域名），拖慢开发节奏

相比之下，账号密码**零外部依赖**，可与 admin 复用同一套认证引擎，立即可开工。

### 4.11 既然两端都用密码，为什么不退化成 `user` 表加一列 `password_hash`

表面看两套都是密码，似乎一张 `user` 表加 `password_hash` 就够。仍保留 `user_credential` 1:N 模型，理由：

1. **凭证类型随时可能回潮**：本次因门槛放弃微信，不等于永久放弃。退化为单列后，未来加微信需重新建模（加列 + 改唯一约束 + 数据迁移）；1:N 模型下只需新增 `credential_type='wechat'` 一行数据
2. **customer 与 admin 的凭证必须隔离**：`realm` 不同但同为 `password` 类型，共用一列则无法表达"同一用户名在客户域与管理域各有一个账号"，也无法按 realm 施加不同锁定策略
3. **多凭证是常态**：密码找回、手机号登录、运维代开临时口令，都需要同一主体挂多条凭证
4. **成本极低**：多一张表的代价远小于未来返工

### 4.12 为什么「打基础」不等于「建完整账号中心」

"为后续完整账号管理与权限校验打基础"容易被误解为本次要一并实现注册门户、找回密码、角色管理 UI、ABAC 权限等。这会导致两个后果：① 范围膨胀，**拖慢真正紧急的安全闭环**；② 在缺乏真实需求时猜测设计（违背 YAGNI）。

因此本期严格区分两类工作：

| 类别 | 判定 | 本期 |
|------|------|------|
| **结构性的**（表结构、令牌形态、actor 模型、凭证抽象） | 事后补代价极高，往往要改表 / 改核心链路 | ✅ **做** |
| **功能性的**（UI、验证方式、权限矩阵细节、第三方 Provider） | 可独立追加，与结构设计解耦 | ❌ **不做** |

**判定标准**：*"以后要加它，是否需要改表 / 改令牌 / 改核心链路？"* —— 需要则本期做，不需要则留作后续迭代。

这条边界同时保护了本期的两个目的：既能立刻闭环安全漏洞，又不给未来能力设卡。

### 4.13 为什么角色用 `user.roles` jsonb，而不是独立 `user_role` 表

**性能不是决策因素**。运行时权限校验读的是 JWT claims（登录时角色已加载进令牌），对每个请求而言角色存储**零查询**。真正会查库的只有三个冷路径：

| 场景 | jsonb | 独立表 | 结论 |
|------|-------|--------|------|
| 登录时加载角色（按 user_id） | 行内读取，主键命中顺带带出，0 次额外 IO | 需索引查找 `user_role` 返回 N 行 | jsonb 略优 |
| 按角色反查用户（列出所有 platform_admin） | `roles @> '[...]'`，加 GIN 走索引；无索引则全表扫 | B-tree 索引，天然支持 | 独立表更自然，可加 GIN 弥补 |
| 统计角色分布 | 需 `jsonb_array_elements_text` 展开 | 直接 GROUP BY | 独立表更方便（低频，不敏感） |

平台用户量级（1000–10000）下，即使完全不加索引，全表扫描也在毫秒级（PostgreSQL 顺序扫描约百万行/秒量级），**不构成瓶颈**。

**真正的取舍是"值域约束"，而非性能**：

| 影响项 | jsonb | 独立表 + CHECK/FK |
|--------|-------|------------------|
| 孤儿数据（用户删除后角色残留） | ✅ **不存在**（内嵌在 `user` 行） | ✅ 有 FK 则不存在 |
| 级联删除 | ✅ 自动 | 需显式 `ON DELETE CASCADE` |
| **非法角色名**（如拼错成 `admn`） | ❌ DB 层拦不住 | ✅ `CHECK (role IN (...))` / FK 角色字典表 |

> 澄清一个常见误解：**jsonb 不会造成孤儿数据**——角色内嵌在 `user` 行，用户删除时角色随行消失，引用完整性反而比"忘记加级联的独立表"更强。失去的只是**角色名合法性**的 DB 层约束，其后果是写入拼错的角色名后该用户权限静默不匹配（表现为"什么也做不了"），排查成本较高。

**因此采用 jsonb，并以三项低成本措施补偿**：

1. **应用层角色白名单**：写入前校验 ∈ 已知集合（复用现有 `_INTERNAL_ROLES` / `CUSTOMER_ROLE` 常量），并补单测（与 `test_auth.py` 现有契约同风格）→ 把 DB 层失去的 CHECK 搬到应用层
2. **GIN 索引**：`USING gin(roles)`，为低频反查与未来数据增长留边界
3. **变更审计**：角色改动写 `operation_audit`（本来就要做）

**未来迁回独立表的触发条件**（届时一次性 `INSERT SELECT` + `jsonb_array_elements_text` 迁移即可，成本低）：按角色反查成为高频热路径、角色数量膨胀到每用户数十个、或需要复杂角色统计与 RBAC 建模。
