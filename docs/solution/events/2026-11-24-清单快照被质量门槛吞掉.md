# 清单快照被质量门槛吞掉，S7 永远停在「未知」

## 现象

客户界面「证据回传」（S7）显示 **未知**，但平台侧证据其实早就到了：

- `log_collect_artifact_manifest` 表里该任务**有完整清单行**（source/quality/reason/entry_count 齐全）；
- 任务 `detail` 里却**没有** `artifact_manifest` 快照；
- `detail.evidence_error` 为空、`capabilities` 正常，所以派生层只能落 `unknown`（`log_collect_display.py:801-810`）。

命中的 5 条任务（2026-11-24 排查 `Q2026091700436` 时发现）：

| 工单 | 任务 | 状态 | 清单质量 |
|---|---|---|---|
| Q2026091700436 | `60a0a2e6` | completed | invalid / unreadable |
| Q2026112301059 | `0f63aafc` | completed | invalid / unreadable |
| Q2026112400992 | `2410d2c4` | completed | invalid / unreadable |
| Q2026112401156 | `bdcf6a40` | completed | invalid / unreadable |
| Q2026112400585 | `03d79904` | failed | **ok / ok（9 entries）** |

最后一条最刺眼：清单完全正常，用户却看不到「证据已回传」。

## 根因

`put_artifact_manifest` 把**两类互不相同的事实**塞进同一条 jsonb 更新，再用一个质量条件挡住整条 UPDATE：

```sql
SET detail = COALESCE(detail,'{}') || jsonb_build_object(
        'artifact_quality', ..., 'artifact_reason', ..., 'artifact_evidence', ...,
        'artifact_manifest', <快照>)          -- 两类事实写在一起
WHERE task_id = :task_id
  AND (detail ->> 'artifact_quality' IS DISTINCT FROM 'ok' OR :quality = 'ok')  -- 整条被挡
```

质量门槛的本意是「已经确认 ok 的，不要被后来的更差结论覆盖」。但清单快照回答的是**另一个问题**——「证据有没有到达」。两者被绑在同一条语句里，于是质量一旦被判过 ok（或判过别的值），这一次上报的清单事实就一起丢失；而装清单的真表已经写成功，造成「表里有、detail 里没有」的裂缝。

客户面板只拿任务行（避免 N+1），S7 唯一的数据源就是 detail 快照（`_evidence_manifest`），所以裂缝直接表现为「未知」。

## 修复

### 1. 写侧：快照无条件写，质量仍受保护

`backend/case-service/app/routes/log_collect_evidence.py`：把一条 UPDATE 拆成两个 jsonb 合并——

- `'artifact_manifest'` 直接并入，**不带任何条件**；
- `artifact_quality / reason / code / evidence` 放进 `CASE WHEN (质量门槛) THEN ... ELSE '{}' END`，保留「已 ok 不被更差结论覆盖」的语义；
- 去掉 WHERE 里的质量判断。

### 2. 存量：迁移 069 逐字段回填

`database/data-migrations/069_log_collect_manifest_snapshot_backfill.sql`：

- 只补「真表有行、detail 无快照」的任务，取每任务**最新**一行清单；
- 快照字段逐项取自真表（source/quality/reason/entry_count/entry_total_bytes/has_encrypted/trace_id/inspected_at），**不推断、不造数**；
- 行内审计写 `detail.display_audit`（migration-069 + before 摘要），不建备份表（Atlas 声明式 schema 会 DROP 未声明的表）；
- 幂等：`COALESCE(detail ? 'artifact_manifest', false) = false`，重跑影响 0 行；
- 收尾带不变量校验：**只要有清单行，任务行就必须有快照**。

全库命中 9 条：4 条 11-18~11-20 的历史任务 + 5 条 11-24 的。回填后 8 条显示「证据已回传 + 包不可读」，1 条（`03d79904`）显示「证据已回传 + 清单正常」。

## 验证

- 新增 `backend/case-service/tests/unit/test_artifact_manifest_snapshot.py`（2 例结构断言）：
  - WHERE 子句里不得出现 `artifact_quality`（那是当年吞掉快照的闸门）；
  - `artifact_manifest` 必须写在 `CASE` 之前（无条件），`artifact_quality` 必须在 `CASE` 之内。
- 对抗性验证：`git checkout HEAD --` 回到修复前的实现，两例**全部失败**（一条精确指出 WHERE 里的 `artifact_quality`），恢复后通过。
- `backend/case-service/tests/unit` 下 `-k "evidence or artifact or log_collect"`：**548 例通过**；ruff 通过。
- 迁移在 staging 上以只读事务演练：`would_update = 9`，`ROLLBACK` 后残留 0 行（幂等键生效）。

## 边界

- 回填的快照不含 `expected_hosts / missing_hosts / unexpected_hosts`——这三项当时只写进快照、没有落表，无法还原。展示层不消费它们（`_artifact_payload` 只用 quality/reason/entry_count/entry_total_bytes），S7 判据也只要求 `received is true`。
- 本次没有改变「包内容好不好读」的判定：质量仍是 invalid 的任务依旧标 invalid，只是不再连带把「证据已回传」这件事丢掉。
- 历史上是否还有别的路径能把快照写丢（例如同一任务被多次重采）未逐一考古；不变量校验（有清单行必有快照）作为门禁留在迁移里，后续再出现同类裂缝会在部署时直接报错。
