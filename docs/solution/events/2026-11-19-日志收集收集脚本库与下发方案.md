# 2026-11-19 日志收集「收集脚本」库与下发方案

## 变更历史

| 日期 | 版本 | 变更摘要 |
|------|------|---------|
| 2026-11-19 | v1 | 初版：脚本库数据模型、管理端 API、场景清单联动、bridge 分块写入与终态还原 |
| 2026-11-20 | v2 | 支持无后缀脚本与子目录（`vs_script/...`）；解释器改为 shebang 优先、取消后缀硬拒绝；导入抽屉改为常驻投放区（可拖拽、可重选） |

## 背景与需求

默认场景与自定义场景的清单条目里，`action=script` 的 `path` 一直是**自由输入的文件名**。脚本实体只存在于 HCI 节点的插件脚本目录：

```
<插件工作目录>/<脚本子目录>/
```

由此产生三个问题：

1. 管理员手填的文件名可能不存在，失败发生在节点执行时，现场分不清是配置错还是插件缺文件；
2. 平台无法修改脚本行为，只能让现场手工改节点文件，改完既无审计也无版本可回溯；
3. 任务记录只有清单摘要，没有「当时节点上跑的是哪一版脚本」的证据。

需求：在管理端新增「收集脚本」页，支持新增/导入/编辑、版本历史；场景清单的动作选择「脚本」时路径改为下拉；下发前由平台把最新脚本随任务写到节点，任务结束还原。

## 方案概述 (WHAT)

整套语义**照抄默认场景**（这是本次最重要的决策，见 §决策）：

| 默认场景概念 | 脚本对应物 |
|---|---|
| 随镜像发布的 `data/spc_catalog/*.json` 快照 | 随镜像发布的 `data/script_catalog/index.json`（**仅 3 条示例**，不含真实清单与源码） |
| `log_collect_default_scenario` 只存被改过的模块 | `log_collect_script` 只存被改过的脚本 + 平台新增脚本 |
| 未覆写的模块零行为变化 | 未覆写的内置脚本不下发 |
| UI「平台默认快照 / 已自定义 vN / 恢复默认」 | 完全相同的交互 |
| 下发时覆盖 `spc/<slot>.json`，终态还原 | 下发时覆盖 `script/<code>`，终态还原 |

与默认场景的唯一增强：**脚本保留每一版原文**。默认场景是单主键只留最新版，脚本被任务引用后必须能回放历史内容，因此用 `(script_id, revision)` 复合主键。

## 详细设计

### 1. 数据模型

`log_collect_script`（`database/desired_schema.sql`）：

| 字段 | 语义 |
|---|---|
| `script_id` + `revision` | 复合主键；同一 code 的每次保存新增一行，历史永久可回放 |
| `code` | **相对插件 `script/` 的路径**（如 `demo_check.py`、`vs_script/vs_collect_upgrade_info.py`），最多三层；也是 spc 条目的 `path`。创建后不可改，改名等于新建 |
| `interpreter` | `python` / `bash`。判定顺序 shebang → 后缀 → 默认 bash；手选值优先，与 shebang 冲突时只提示不拒绝 |
| `content` / `content_sha256` / `content_bytes` | 原文与摘要；摘要用于下发前比对与任务证据 |
| `change_note` | 变更说明（编辑必填），构成可读的历史 |
| `source` | `manual` / `import` / `baseline` |
| `enabled` | 停用后保存场景与创建任务两处都会被挡住 |

任务侧新增 `script_codes` / `script_sha256` / `script_hosts` / `script_restore_status`，与 `spc_*` 并列而不是合并：脚本与清单是两条独立还原通道，混成一个状态无法表达「清单已还原、脚本还残留」。

### 2. 服务端行为

- 仓库内只放 3 条示例条目（文件名/解释器/大小/摘要/二进制标记），真实基线由环境变量 `LOG_COLLECT_SCRIPT_BASELINE_INDEX` 注入。是否可被场景引用、可被编辑由清单里的 `ref_usable` 决定；子目录条目（`vs_script/...`）与顶层条目同级可用。
- `code` 的校验：服务端 `CODE_RE` 允许最多两层子目录（总长 64，与库表列一致），拒绝绝对路径、`\\`、`..`、空段（`a//b`）与尾随斜杠；bridge 用同口径正则 + `path.Clean` 比对二次收窄。
- 列表 = 基线 + 库中最新 revision；`revision=0` 且 `customized=false` 表示平台默认快照。
- 保存 = 追加 revision；恢复默认 = 删除该 code 的全部行，退回快照；删除仅限平台新增脚本且无任何场景引用。
- 引用反查：扫描默认场景覆写行 + 各自定义场景最新 revision，删除/停用前给出引用清单。
- 保存场景时校验 `action=script` 的 `path`：命中库且已停用 → 422；未命中 → 视为引用节点自带脚本，允许。

### 3. 下发链路（与 spc 同构）

```
POST /api/v1/log-collect/tasks
  → 服务端先算 spc_files（只读）
  → 解析其中 action=script 的 path，取库中最新版本，内联 script_files[]
  → 停用/删除的引用直接 409，不建任务（顺序从"建任务后"提前到"建任务前"）
  → 证据落库：task.detail.scripts + script_codes/script_sha256
custom-ui（纯透传，零 UI 变更）
  → bridge create 消息带 script_files
terminal_bridge
  → 先写 script/（分块 printf 追加 → sha256 校验 → chmod 0755 → 原子 mv）
  → 再写 spc/
  → 执行 acli log_collect
  → 任务终态 / 失败 / 桥重启 → 逐台还原
```

bridge 侧细节：

- 分块 16KB：`MAX_ARG_STRLEN` 为 128KB，单引号转义最坏膨胀 4 倍，16KB×4=64KB 仍安全；按 UTF-8 字符边界切，不切断多字节字符。
- 备份 `<file>.platform.<task_id>.bak`；节点原本没有该文件时写一个 `.platform.<task_id>.created` 标记（内容是目标路径），还原时凭标记删除。
- 写前自愈：先恢复历史备份、再清理历史 created 标记，然后才备份本次原件——保证 `cp` 备份的永远是插件原件。
- 一台写失败 → 已写节点全部回滚，拒绝下发（节点间跑不同版本脚本，产物无法解释）。
- 能力位 `platform_scripts`：旧桥不认识 `script_files` 会静默丢弃，客户侧必须先探测，不支持就报错而不是「成功但少采」。

### 4. 联动（admin-ui）

- `DefaultScenarioPanel` / `CustomScenarioPanel` 的 `action=script` 行改用 `ScriptPathSelect`：
  - 选项来自脚本库，停用项置灰并标注；
  - 最后一项「自动输入」切手填，兼容节点自带脚本；
  - 当前值不在库中（历史数据/自由输入）自动进入手填模式，不吞值。
- 新页签「收集脚本」在「自定义场景」右侧，提供列表、编辑抽屉、版本历史抽屉、导入/新增、启停、恢复默认。
- 编辑/导入抽屉：`目录`（下拉可选手输，选项来自现有脚本的真实目录）+ `文件名` 两个字段，拼成 `code`；解释器是可选下拉（自动/python/bash），校验后显示判定依据。
- 导入不再依赖系统文件框的 `accept` 白名单：抽屉内常驻「点击选择 / 拖拽到此处」投放区，可反复替换；因此无后缀脚本（`dpcollect` 等）也能直接拖进来。

## 决策与放弃项

1. **不做命名空间隔离（`pl_` 前缀）**：一开始提议平台脚本统一前缀、禁止覆盖内置脚本；用户指出这与默认场景范式矛盾——默认场景本来就是覆写内置资产。已撤回，改为与默认场景完全同构。
2. **不做「锁定脚本 revision」**：曾建议场景条目锁定脚本版本。实际 `serialize_spc` 是白名单序列化，`script_revision` 无法进入 spc（acli 契约不接受未知字段），要锁定必须让下发链路重新查库拼条目，复杂度与收益不匹配。最终语义：**场景引用按库中最新版本下发**，任务证据记录当时的 revision + sha256，历史可解释性由证据保证。
3. **不新增 ACLI 插件下发通道**：脚本与清单都由持有 SSH 会话的浏览器侧 bridge 执行，服务端只生成文本、不连桥、不持凭据。
4. **兜底 `restore_script` 动作已实现（bridge 侧），客户侧自动触发暂未接**：当前靠「bridge 任务终态自动还原 + 下次写入前自愈」覆盖；bridge 进程被杀且任务未终结时，需平台显式发 `restore_script`（协议已就绪）。
5. **仓库内不留真实清单与源码（合规硬约束）**：初版曾把设备脚本目录整体打包（含厂商源码、真实文件清单与路径），推送前发现本仓库是 **PUBLIC**，已改为仓库内只保留 3 条虚构示例；真实清单由环境变量 `LOG_COLLECT_SCRIPT_BASELINE_INDEX` 注入，源码永不入库。代价：编辑内置脚本时必须由管理员导入或粘贴内容。
6. **不复制节点脚本到平台**：需要"查看/编辑节点上现有脚本"时应走 bridge 读取（P2），不通过镜像或仓库携带。

## 验证方法

1. 管理端：编辑 `demo_check.py` → 粘贴内容 → 保存 v1 → 版本历史出现 1 行 → 再保存 v2 → 列表显示「已自定义 · v2」→ 恢复默认 → 退回「平台默认快照」且历史仍保留。
2. 场景联动：默认场景选 slowdisk → 动作改「脚本」→ 路径下拉可见脚本库 → 选「自动输入」可手填 → 保存成功；把脚本停用后再保存 → 422 且提示脚本名。
3. 下发：客户侧建任务 → 节点上 `script/demo_check.py` 内容与平台 v2 一致（sha256 比对）、权限 0755；任务结束后 `cmp` 备份与原件一致。
4. 失败路径：把脚本改成引用一个已停用的脚本 → 创建任务返回 409，任务列表不新增记录。
5. 旧桥：用不含 `platform_scripts` 的桥建任务 → 客户侧明确提示升级，不发起采集。
6. 无后缀脚本：把节点上的 `dpcollect`（带 `#!/bin/bash`）拖进导入抽屉 → 校验显示 `interpreter=bash`、依据 `shebang` → 保存成功；再选 python 手存 → 保存成功但提示"与 shebang 不一致"。
7. 子目录：目录填 `vs_script`、文件名填 `vs_collect_upgrade_info.py` → 列表 code 为 `vs_script/vs_collect_upgrade_info.py` → 场景引用该路径建任务 → 节点上该子目录文件被覆写且任务结束还原（备份在同目录）。
8. 路径穿越：直接调 `/validate` 传 `../../etc/x`、`a//b`、`/abs/x` → 均返回 422。

## 已知遗留

1. 客户侧未自动发 `restore_script`（见决策 4）。
2. 子目录条目已支持编辑与引用（v2）。待真机确认：spc 条目 `path` 写成 `vs_script/xxx.py` 时，acli 是否按工作目录相对解析子目录——bridge 只负责写文件、不解释该 `path`。
3. 单个数百 KB 的脚本下发到 3 节点约 20+ 条 SSH 命令/节点，耗时数秒；如需优化可改为单会话多命令执行。
4. **与并行 R0 重构的关系**：R0（`main.go` 拆包到 `app/`、`internal/`）已暂停，等本功能提交后再继续。新增的 `log_collect_script.go` / `log_collect_script_fanout.go` 仍在 `package main`，R0 恢复时需要随 `log_collect*.go` 一起迁移，否则会与新包形成两套文件写入实现。
5. 场景条目不锁定脚本 revision（见决策 2）：管理员改脚本后，下一次任务即使用新版本，除非任务已经在创建时冻结了证据。

## 部署方式

1. 数据库：通过 Helm hook `db-migrate-job` 应用 `database/desired_schema.sql`，即 `helm upgrade` 部署时自动完成（dev 环境为 K3s + `postgres-0`，不使用 `make db-sync`，后者走 docker compose）。
2. 桥：`bash scripts/build_terminal_bridge.sh` 重新产出 exe 与 `bridge-version.json`，替换后需校验 `/status` 与 `bridge_hello`（本次新增能力位 `platform_scripts`）。
3. 前端：admin-ui 与 customer-ui 常规构建发布。
