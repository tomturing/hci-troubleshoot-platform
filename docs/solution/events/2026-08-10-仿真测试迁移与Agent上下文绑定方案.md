# 仿真测试迁移与 Agent 上下文绑定方案

## 1. 背景与需求

本方案响应 [仿真测试迁移与 Agent 上下文绑定需求](../../requirement/events/2026-08-10-仿真测试迁移与Agent上下文绑定需求.md)。现场证据已经证明：仿真 Lease 能建立 SSH，但 terminal-only 流程没有环境数据，KBD scope 因缺少 `product/version/components` 变为 `UNKNOWN`，Agent 因 fail-closed 不执行任何 Signal。

这不是增加一个页面按钮可以解决的问题。必须把“构建一个可运行仿真环境”和“用该环境运行一个可审计 Agent TestRun”建模为控制面资源。

## 2. 第一性原理

完整 Agent 仿真测试至少需要六个相互一致的对象：

```text
KBD Revision
→ Scenario
→ immutable Fixture Bundle
→ Runtime Instance
→ Lease/TestRun
→ Case/Conversation + Agent Context
```

若只提供 SSH host/password，Agent 无法知道这个环境适用于哪个产品、版本、组件和 Signal；若只注入 scope 而没有 Bundle/Runtime，则 Agent 会向不存在的 route 发命令。设计不变量为：

1. 一个 TestRun 固定一个 KBD revision、Bundle digest、Scenario 和 execution mode；
2. Agent context 来自已发布 Bundle/TestRun，不由浏览器自由填写；
3. Case 创建和 TestRun 绑定必须幂等且可审计；
4. “环境 Ready”必须同时包含 Runtime readiness 和 Bundle/Lease 可执行性；
5. 仿真证据永远带 `simulation=true`，不能污染真实 HCI 统计；
6. Custom UI 不承载内部测试控制面，Admin UI 不绕过既有 Agent/Bridge 协议。

## 3. 方案（WHAT）：产品与组件边界

### 3.1 Custom UI 退场范围

Custom UI 删除：

- “仿真租约连接（dev）”按钮；
- Lease auth 选项和 hci-sim 默认 host/2222/sim 逻辑；
- connection.json 粘贴/解析和 recommended command 提示；
- `execution_mode=sim-ssh/test_run_id` 的仿真 UI 分支；
- 仿真专项测试和文案。

保留客户真实流程：

- 普通密码/密钥 SSH；
- “连接 SSH 并创建工单”；
- 环境采集、对话、终端和 Agent 工具卡片；
- Windows desktop Bridge 兼容能力（若产品仍需要）。

“恢复到引入仿真租约 PR 之前”通过行为 diff 和 git 基线验证，不使用破坏性 checkout 覆盖其他已合入修复。

### 3.2 Admin UI 新模块

新增路由：

```text
/admin/simulation-tests
```

侧边栏名称：

```text
仿真测试
```

页面由四个区域组成：

1. KBD_ID 与环境构建操作区；
2. 构建阶段/进度/状态卡；
3. 可展开、折叠、关闭的事件日志区；
4. TestRun、工单、Signal 结果和结论证据区。

## 4. 目标端到端架构

```text
Admin UI
  │ POST /api/admin/simulation/builds
  ▼
Simulation Control API
  │ resolve published KBD revision/capability
  │ compile/register immutable Bundle
  │ schedule K3s hci-sim Runtime
  ▼
hci_sim DB ── build/run/event state
  │
  ├─ SSE/游标日志 ───────────────> Admin UI
  │
  └─ ready TestRun + short-lived Lease
             │
Admin UI 创建仿真工单并绑定 context
             │
             ▼
Agent Service ── agent_exec_command SSE ──> Admin UI
             │                               │
             │                               ▼
             │                    同源 K3s terminal_bridge
             │                               │ SSH sim-ssh
             │                               ▼
             └──────── result ◀──────── K3s hci-sim
```

Admin UI 嵌入/复用共享的工单、SSH 和对话组件，但不复制一套独立 Agent 协议。适合共享的组件移动到 `frontend/shared`；客户专属视觉和路由不直接跨应用 import。

## 5. 环境构建状态机

```text
idle
  → validating       校验 KBD_ID、发布 revision、capability
  → resolving        固定 KBD/tool/policy revision
  → compiling        生成 Fixture Bundle
  → registering      digest、审批和依赖登记
  → scheduling       创建/选择 hci-sim Runtime
  → probing          readiness + route contract smoke
  → ready

任一阶段 → failed
活动阶段 → cancelling → cancelled
ready → stale/expired
```

### Ready 定义

只有以下同时满足，按钮才启用：

- KBD status published；
- active revision/checksum 与 Bundle 依赖一致；
- Bundle status published；
- 所有 required Signal 都有 route 或被明确标记为预期 blocked 变体；
- Runtime ready；
- Lease issuer/audience/host key/端口可用；
- build 未 stale/expired。

## 6. Admin UI 交互设计

### 6.1 环境构建

```text
KBD_ID [23821] [环境构建]

阶段：编译 Fixture  60%
[▶ 展开详细日志] [关闭]

[开始测试（置灰）]
```

按钮规则：

- 空值/非数字：前端提示，服务端再次校验；
- build active：环境构建按钮变为“取消构建”或禁用重复提交；
- ready：开始测试启用；
- failed：保留日志和 KBD_ID，允许带新 idempotency key 重试；
- stale/expired：开始测试禁用，提示重新构建。

### 6.2 构建日志

日志是结构化 BuildEvent，不是容器 stdout 直接透传：

```json
{
  "seq": 42,
  "build_id": "...",
  "stage": "compiling",
  "level": "info",
  "code": "BUNDLE_ROUTE_COMPILED",
  "message": "已编译 required Signal",
  "progress": 60,
  "retryable": false,
  "at": "..."
}
```

敏感字段由服务端白名单序列化；浏览器只持久化 build_id、游标和 UI 展开状态，不保存 Lease。

### 6.3 开始测试与创建工单

点击“开始测试”后服务端先原子 reserve TestRun，前端再打开工单弹窗。弹窗字段：

```text
只读：KBD_ID、revision、scenario、runtime、execution_mode=sim-ssh
用户填写：标题、描述
隐藏且不回显：Lease password、内部 token
按钮：连接 SSH 并创建工单
```

按钮提交调用一个编排 API，保证：

```text
创建/获取幂等 Case
→ 创建/获取 Conversation
→ TestRun 绑定 case/conversation
→ 获取一次性连接能力
→ Admin UI 建立 K3s Bridge WebSocket/SSH
→ Agent context 可见后启动测试
```

若 SSH 失败，Case/TestRun 保留为明确失败或可重试状态，不丢失用户标题和描述。

## 7. 控制面 API 设计

建议新增服务边界（可先由现有后端承载，接口路径保持独立）：

```text
POST   /api/admin/simulation/builds
GET    /api/admin/simulation/builds/{build_id}
GET    /api/admin/simulation/builds/{build_id}/events?after_seq=
POST   /api/admin/simulation/builds/{build_id}/cancel
POST   /api/admin/simulation/builds/{build_id}/test-runs
GET    /api/admin/simulation/test-runs/{test_run_id}
POST   /api/admin/simulation/test-runs/{test_run_id}/bind-case
POST   /api/admin/simulation/test-runs/{test_run_id}/lease
GET    /api/admin/simulation/test-runs/{test_run_id}/evidence
```

### 幂等键

- build：`admin + support_id + requested_revision + request_id`；
- TestRun：`build_id + variant + request_id`；
- bind-case：`test_run_id` 唯一；
- Lease：每次签发新 jti，旧 Lease 立即过期或受 max session 限制。

## 8. TestRun 到 Agent Context 显式绑定

### 8.1 Context 契约

Agent 不再从空的主库 `environment` 猜测仿真 scope。TestRun 提供只读、签名/校验后的 context：

```json
{
  "simulation": true,
  "execution_mode": "sim-ssh",
  "test_run_id": "...",
  "scenario_id": "kbd-23821-positive-full",
  "support_id": "23821",
  "kbd_revision": 2,
  "bundle_digest": "sha256:...",
  "product": "HCI",
  "version": "6.9.0",
  "components": ["虚拟机"],
  "topology": [],
  "virtual_node_id": "SIM-HCI-NODE-01"
}
```

### 8.2 绑定时序

```text
TestRun ready
→ bind case_id/conversation_id（唯一约束）
→ conversation/agent 请求按 case_id 获取 SimulationContext
→ 校验 TestRun running + bundle digest + revision freshness
→ merge 到独立 simulation_context 命名空间
→ CDD scope evaluator 使用该上下文
→ Agent 执行 Signal
```

真实 `environment` 与 `simulation_context` 不混写。Agent 一次运行只能选择其一：

```text
execution_mode=ssh     → real environment
execution_mode=sim-ssh → simulation context
```

双轨同时存在时直接拒绝，避免仿真数据污染客户诊断。

## 9. KBD 23821 完整 Fixture 设计

当前 positive-minimal 只有 `qkv_task` route。完整正向变体新增：

```text
Scenario: kbd-23821-positive-full

Route 1 sig_001 qkv_task
  output: failed migration task
  produces: VM, HOST, END

Route 2 sig_002 qfk_log
  input: HOST + END
  output: repeated Completed SIZE of SIZE without ready
  matcher: delta/required samples satisfied

Route 3 expert_* qfk_system
  input: HOST + VM
  output: block-job state matching expected legacy behavior
  matcher: keyword/expected satisfied
```

同时提供至少两个负向变体：

- `negative-ready-present`：ready 字段正常，KBD 不应被支持；
- `inconclusive-missing-log`：required route 缺失/超时，结论必须 INCONCLUSIVE，不能输出根因。

Bundle 必须冻结 exact argv、output、exit code、matcher 输入、produced variables、limits 和 digest。

## 10. 安全与权限

- Admin UI 需要 `simulation:build`、`simulation:run`、`simulation:view` 权限；
- Build/Run 审计记录管理员身份、request id 和资源 revision；
- Admin UI 不显示/持久化 Lease password，只在建立 WebSocket 时使用受限能力；更优方案是服务端签发一次性 HttpOnly/短期 token 并由 Bridge 兑换；
- hci-sim 不接受任意 shell，未知 RouteKey 拒绝；
- Bundle 编译器不信任浏览器上传的命令或 stdout；
- sim-ssh NetworkPolicy 不允许访问真实 HCI 网段。

## 11. 可观测性与证据模型

每次测试必须形成：

```text
BuildEvent[]
TestRun/Attempt
Bridge websocket/ssh/exec events
hci-sim lease/route/exec events
Agent tool_call/tool_result
SignalOutcome[]
Conclusion
```

Admin 页面按同一 TestRun 展示分层时间线，但不能把“SSH 成功”渲染为“Agent 通过”。结论至少区分：

```text
runtime_passed
agent_definitive_passed
agent_correctly_rejected
inconclusive
infrastructure_failed
```

## 12. 对抗性审查

| 场景 | 期望行为 |
|---|---|
| KBD_ID 不存在/未发布 | validating 失败，禁止构建 |
| 构建中重复点击 | 返回同一 build 或 409，不重复资源 |
| KBD 在构建后更新 | build 标记 stale，禁止开始测试 |
| 页面刷新 | 通过 build_id/after_seq 恢复，不丢日志 |
| 日志包含 secret | 服务端拒绝/脱敏并告警 |
| ready 后 Runtime 崩溃 | readiness 失效，开始测试禁用或签发前重检 |
| 开始测试双击 | 只创建一个 TestRun/Case |
| Lease 过期 | 明确 EXPIRED，要求重新签发，不复用密码 |
| TestRun 未绑定 context | Agent 不启动并显示缺失绑定，而不是“证据不足” |
| sim 与 real context 同时存在 | fail-closed，拒绝运行 |
| Fixture 只有部分 required Signal | 构建门禁失败或明确 inconclusive 变体，不能冒充 full |
| Browser/Bridge 断开 | TestRun attempt 失败可重试，新 attempt 使用新 Lease |
| hci_sim DB 不可用 | 仿真页面失败，主业务工单不受影响 |

## 13. 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 为什么移动到 Admin UI

仿真环境构建、Bundle/Lease/TestRun 管理属于内部测试控制面，需要管理员权限和详细构建日志。放在 Customer UI 会扩大攻击面、混淆真实/仿真语义，并迫使客户前端携带内部控制面代码。

### 为什么复用共享组件而不是 iframe/复制 Custom UI

iframe 会引入鉴权、Origin、路由和状态同步问题；整份复制会快速产生两套 SSH/工单/Agent 协议。将通用逻辑移动到 shared，Admin 组合自己的工作流，边界更清晰。

### 为什么不把 simulation context 写入主库 environment

这会把 synthetic 数据伪装成客户环境，污染诊断、审计和统计，也与 hci_sim 独立数据库目标冲突。显式命名空间和 execution mode 才能保证双轨隔离。

### 为什么不继续手工 recommended_command

手工命令只验证 Runtime/Bridge route，不验证 Agent 是否加载正确 KBD、执行全部 required Signal、处理变量依赖和产生正确结论。

### 为什么先绑定 Context 再扩展 23821 Bundle

没有 Context，CDD 在第一步 scope gate 就停止，扩展更多 route 无法被执行；先打通调度前置条件，才能用实际 Agent 流量验证 Bundle。

## 14. 实施顺序及跨组依赖

```text
1. K3s terminal_bridge 可用
2. hci_sim DB 边界/控制面 API 可用
3. Admin 仿真测试页面与 Build 状态机
4. TestRun → Case/Conversation → Agent Context 绑定
5. 23821 positive-full + negative variants
6. 移除 Custom UI 仿真代码
7. 完整 E2E、观察和旧入口退场
```

Custom UI 移除代码可以先开发，但最终合入/发布必须确保 Admin 新入口和回滚方案可用，避免出现测试能力空窗。

## 15. 影响范围

- `frontend/customer/`：移除仿真专项代码
- `frontend/admin/`：新增仿真测试页面、路由、状态和对话容器
- `frontend/shared/`：抽取安全可复用的 SSH/工单/执行组件和协议
- API Gateway、Simulation Control API、case/conversation/agent-service
- K3s terminal_bridge、hci-sim Runtime/Bundle compiler
- hci_sim DB TestRun/Build/Event 表
- Helm/Ingress/NetworkPolicy/Secrets
- Admin/Customer/Agent/数据库/接口/可观测性现行文档

## 16. 验收标准
