# 2026-11-23 采集停滞可辨识与探测缺命令单列

## 背景

失败工单误标修复（2026-11-20）上线后留下四项「刻意未做」。本次先复核这四项是否仍是缺口，
再只动真正成立的部分：

| 遗留项 | 复核结论 | 本次动作 |
|---|---|---|
| `stat` 不依赖节点命令 | 已是 `stat -c %s` → `ls -l` 两级 + 三态结论；再往 SFTP 走，子系统本身也可能被禁，收益边际 | 不做 |
| `exit=127` 单列 | 语义已区分（126/127 判「命令不可用」），但错误码仍是 `LC-TRANSFER-006`，客户看到「或通道异常」无从下手 | **做** |
| 会话断连置 `queued` | 任务 `status` 枚举没有 `queued`；回到 `queued` 会重新下发 `create`，节点上可能已采一半 → 重复采集（Q2026111900421 三任务共用目录） | **改向** |
| `acli capabilities` 预检 | 前端已在用 `capabilities` 做证据能力 fail-closed；`platform_scripts` 门禁桥侧已写明不做（旧桥静默忽略，先探测会多一次往返且引入第二个静默分支） | 不做 |
| 5888 手工上传回流 | 派生层明确「交付未登记（含手工上传）按失败处理，禁止翻正」，回流会重演伪证据误判 | 不做 |

结论：四项里只有一项成立（127 单列），另一项被替换成正确的形态（不置 `queued`，而是
让用户能判断「还该不该等」）。

## 改动

### 1. `LC-ENV-009`：节点缺探测命令

`remote.ArchiveProbe` 新增 `Unavailable`，与既有 `Level` 分离：

- `Level` 回答「哪一级给出了结论」（stat / ls / missing / none）；
- `Unavailable` 回答「结论未知的原因是不是命令跑不起来」。

归因用新方法 `commandMissing()`，**只认 126/127 与「命令不存在/不认识该参数」文本**，
刻意不含 `permission denied`。原因是对抗性检查发现的：`ArchiveProbeToolMissingRe` 原本
含 `permission denied`，如果直接复用，权限拒绝会落到「节点缺命令」，客户被引去放开命令
白名单，而真正要改的是目录权限。

分流结果：

| 情形 | 错误码 | 客户动作 |
|---|---|---|
| 两级都命令缺失 | `LC-ENV-009` | 恢复命令 / 放开白名单 |
| 一级缺失 + 一级超时 | `LC-TRANSFER-006` | 重连 |
| 权限拒绝 | `LC-TRANSFER-006`（diag 带 `Permission denied`） | 改权限 |
| 通道异常 / 取消 | `LC-TRANSFER-006` | 重连 / 重试 |

### 2. `progress_stalled`：进度长时间未变化

`log_collect_display.is_progress_stalled` 只对 `status=collecting` 判定，阈值
`thresholds.progress_stall_minutes = 20`，依据 `updated_at`。

三条边界：

- **不覆盖 packaging/uploading**：打十几 GB 的包、分片排队都有合法长静默，用同一阈值
  会把正常长任务报成中断，用户据此重采反而制造重复产物。
- **与 `task_stalled` 互斥**：任务级停滞看 `created_at`、阈值 24 小时；两者同时成立时
  只显示更具体的 `progress_stalled`，避免同屏两条「停滞」。
- **只说「进度没有变化」**：`updated_at` 是 SQLAlchemy `onupdate`，同值重复上报不产生
  UPDATE。若写「没有收到心跳」，就会把「节点按时上报但卡在同一个百分比」错报成通信中断。

## 边界与重启条件

- 20 分钟是契约值，改动需走 PR；若出现「正常采集静默超过 20 分钟」的实测工单，先调阈值
  再考虑分阶段阈值，不要直接删判定。
- `LC-ENV-009` 目前只由 `stat` 动作上报；`progress` 里的探测是纯展示，不参与归因。
- 若将来节点普遍禁 SFTP 且 shell 裁剪更严重（连 `ls` 都没有），`LC-ENV-009` 会变成高频码，
  届时应改为 SFTP 直读而不是继续加命令。
