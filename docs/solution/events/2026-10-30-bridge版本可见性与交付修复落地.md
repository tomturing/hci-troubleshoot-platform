# bridge 版本可见性与交付修复落地

- 日期：2026-10-30
- 关联：Q2026103000994 / PR #1380（交付源包守卫）/ PR #1382（exe 重建）
- 涉及：`scripts/build_terminal_bridge.sh`、`.github/workflows/build-terminal-bridge.yml`、`frontend/customer`（store / 连接区 / 工具函数）

## 一、要解决的问题

交付源包守卫（提交后包被重新生成时提前判死）只存在于**新版 bridge** 里。而 bridge 是装在客户机上的
exe，平台发版只把新 exe 放进 `public/downloads/`：

- 仓库里没有任何 bridge 自更新逻辑（`self_update` / `auto_update` 均无命中）；
- 客户机不重新下载安装，跑的就还是旧版；
- 旧版既不报错也不提示，只是继续按老逻辑每片 500 —— **修复在代码里，却没到现场**。

结论：光修 bug 不够，还必须让"这台机器跑的是不是平台当前分发的那一版"变成**可见事实**。

## 二、底层事实（为什么这样实现）

| 事实 | 出处 |
| --- | --- |
| bridge 连上浏览器即下发 `bridge_hello`，其 `message` 就是构建期注入的版本号 | `terminal_bridge/main.go` 握手首包 `Message: getVersion()` |
| 版本号来自 `git describe --tags --always --dirty`，构建时才知道 | `scripts/build_terminal_bridge.sh` 的 `-X main.Version=$GIT_VER` |
| 前端早已消费 `bridge_hello`（取 `detail` 当实例号） | `frontend/customer/src/stores/chat.ts` |
| 下载目录 `/downloads/` 是 `try_files $uri =404`，文件不存在就真 404，不会回落 index.html | `frontend/customer/nginx.conf` |

由此得到最小方案：**版本清单必须由构建产出**（前端写死一个版本号等于制造第二份真相），
前端拿「握手包里的版本」与「清单里的版本」做等值比较。

## 三、实现

### 1. 构建期产出清单（与 exe 同源）

`scripts/build_terminal_bridge.sh` 在构建成功后写 `public/downloads/bridge-version.json`：

```json
{ "version": "<git describe>", "commit": "<sha>", "build_time": "<utc>", "goos": "windows", "goarch": "amd64" }
```

**只在 `GOOS=windows && GOARCH=amd64` 时写**：清单描述的是"下载目录里那个可执行文件"。
本地或 CI 用 `GOOS=linux` 冒烟跑一次就把清单改成 linux 版本，会让全部客户被误报"版本不一致"。

### 2. CI 一起提交，且 fail-closed

`build-terminal-bridge.yml` 原先只 `git add` exe。清单缺失时若只提交 exe，前端会拿**旧清单**去比
**新 exe**，于是所有人被误报不一致——所以这里显式 `exit 1` 让流水线红，而不是发一个说谎的清单。

### 3. 前端比对（fail-open，不阻断任何操作）

`frontend/customer/src/utils/bridgeVersion.ts`：

| 情形 | 行为 |
| --- | --- |
| 两侧版本都存在且相同 | 不提示 |
| 两侧版本都存在且不同 | 提示 + 「重新下载」按钮 |
| 本机无版本（老桥不带 `message`） | 不提示 |
| 清单 404 / 离线 / 解析失败 | 不提示 |

「判断不了」必须与「不一致」严格区分：把前者当后者，老桥、清单缺失、离线三种情况会同时变成全量误报。

比对只比版本串，不比 commit：`git describe --tags --always` 在非 tag 提交上本身带 commit 后缀，
版本相同即源码相同；再比 commit 会让"同一 tag 重新出包"误报。

### 4. 展示位置

`SshConnectSection.vue` 根节点下（状态切换之外），已连接与连接成功两种态都能看到。
文案写成「**不一致**」而不是「你的版本过旧」——用户可能自编译了更新的 bridge。

## 五、已知边界

1. **只提示，不自动更新**：这不是自动升级。真正让旧版消失需要下载替换 + 重启，属独立课题。
2. **依赖 `bridge_hello.message`**：早于该字段的 bridge 不带版本，永远不提示（无法区分"旧到没有版本号"和"没连上"）。
3. **清单随 exe 同 PR 落地**：本次改动合并后，直到下一次 CI 重建 exe 的 PR 合并，
   `/downloads/bridge-version.json` 都不存在 → 期间一律不提示（安全降级）。
4. 提示出现一次即常驻，不提供"我知道了"忽略态；是否打扰按现场反馈再调。
