# 2026-11-23 滚动发布不中断在途任务（统一 grace + 主动收盘 + 任务交还）

## 背景

历次发布都出现过同一类投诉：正在跑的诊断对话突然断在半句、工具调用被标成「失败」、
知识库解析任务轮询 404。共同点是**发布把在途工作杀掉了**，而界面上给出的原因全都
指向"业务失败"，导致排查方向被带偏。

诉求有两条，必须先拆开：

1. 统一各服务的 `terminationGracePeriodSeconds`；
2. Pod 重新发布**不影响**正常跑的任务。

## 第一性原理：grace 不是保险

`terminationGracePeriodSeconds` 的语义只有一条：**把 SIGKILL 往后推**。它不提供任何
交接、保存、续跑能力。grace 到点，进程里的东西一律消失。所以"发布不影响任务"不能靠
调大 grace 达成，必须回答一个问题：**在途工作此时在哪、谁来接**。

按"工作在哪"分四类，机制完全不同：

| 形态 | 例子 | 谁拥有状态 | 正确做法 |
|------|------|-----------|---------|
| 请求内流（状态同进程） | conversation-service SSE | 本进程事件循环 | 发收盘帧后主动结束，前端重连 |
| 请求内流（状态在别处） | conversation → agent-service 推理 | agent-service 进程 | 只能等它跑完；断开时必须报"换副本"而不是"失败" |
| 请求外后台任务 | kb-service vision/signal job | 本进程内存 | 登记句柄，退出前 join |
| 独立 worker | diagnosis-worker | DB 租约 | 不再取新任务，跑不完就交还 pending |

### 一个被忽略的事实：uvicorn 会等在途请求

uvicorn 0.27 收到 SIGTERM 的顺序是：**停止接新连接 → 等待现有连接自然结束 →
才执行 lifespan shutdown**。本地实测（8s 的 SSE，第 1.5s 发 SIGTERM）：流完整跑到
8.33s，客户端拿到全部帧和 `[DONE]`。

这解释了两件事：

- 长 SSE 不会因为"Pod 进入 Terminating"而立即断，**grace 就是在途流的预算**；
- 在 lifespan shutdown 里置"正在退出"标志是**死代码**——流必须先自己结束才轮得到
  lifespan，而"要不要结束"又依赖那个标志。

第二个结论直接否掉了初版设计。修法是把信号处理**挂在 uvicorn 之上**（lifespan
startup 时 `signal.signal` 覆盖并转发给原 handler），信号到达瞬间置位。同一实验下，
流在 0.6s 内就发出 `server_restart` 并收盘。

## 收盘协议：`server_restart`

服务端在流尾发一帧并结束，**不再发 `[DONE]`**：

```
event: server_restart
data: {}
```

`[DONE]` 是"正常收尾"的信号，前端收到会复位状态、放弃重连。发布收盘必须让它走另一条
分支，否则用户就停在半句话上。

前端行为（`frontend/customer/src/stores/chat.ts`）：

- 识别 `server_restart` → 复位 `isStreaming` → **退避 2s** 后重新 `resume-stream`；
- 续写流里最多重连 2 次，收到 `[DONE]` 时把计数清零；
- 发布收盘时**不把 running 的工具调用标成 `failed`**——上游其实还活着，标失败是误报；
  只有真正的正常收尾（无 `server_restart`）才继续标失败，避免把真失败一起吞掉。

## 改动清单

### 1. grace 单一事实源（Helm）

`deploy/helm/hci-platform/values.yaml` 的 `workloadDefaults.gracePeriods` 是唯一出处，
`hci.gracePeriod` helper 统一渲染，`hci.workloadPodSpecExtras` 注入到每个 Deployment。
preStop 睡眠复用同一来源并校验必须小于 grace。

| 工作负载 | grace(s) | 依据 |
|---------|---------|------|
| conversation-service | 300 | SSE 对话流，含 ops-agent 长推理 |
| agent-service | 300 | 推理请求内完成，断开即丢失上下文 |
| case-service | 300 | 大包制品上传/合并 |
| diagnosis-worker | 180 | 单任务收尾窗口 60s + preStop 10s |
| kb-service | 120 | job 收尾上限 60s |
| diagnosis-service | 120 | 批量任务请求内并发 |
| api-gateway / terminal-bridge / ops-agent-service | 60 | 网关只需发出收盘帧 |
| scheduler-service | 45 | 只触发，不承载任务 |
| default | 30 | 其余无状态服务 |

不再允许用 `<serviceKey>.terminationGracePeriodSeconds` 另开旁路——那会让"谁真正决定
grace"分裂成两个事实源。

### 2. conversation-service：可 join 的落库 + 有序收尾

- `ShutdownCoordinator`（`app/services/shutdown_coordinator.py`）：`track()` 登记后台
  task，`drain(timeout)` 有界等待，超时取消并报 abandoned。`begin_shutdown()` 幂等
  （信号与 lifespan 都会调，重复调用不得重置计时）。
- 落库从 Starlette `BackgroundTasks` 改为登记任务：`BackgroundTasks` 不暴露句柄，
  SIGTERM 后可能整段丢失 → "用户看得到回复、库里没有"。顺序仍是主回复先于交互卡。
- 主 SSE 流用 `asyncio.wait_for(merge_queue.get(), 1.0)` 轮询，保证退出标志 1s 内可见；
  续写流同样改成 pull 循环（`async for` 会一直挂在 `await` 上）。
- **不能用 `asyncio.wait_for(anext(gen))`**：超时会取消 `anext`，async generator 被取消
  后无法继续迭代。改用 `ensure_future` 保留 pending，超时只表示"这一秒没数据"。

### 3. api-gateway：唯一需要"理解"事件的透传层

网关只透传字节，上游的 `server_restart` 本来就能穿过。缺的是**它自己被替换**时：
grace 到期 SIGKILL 直接切断 TCP，前端拿不到任何帧，表现为网络错误。

于是在透传循环里检查退出标志，命中就先发送**已拿到的这一帧**再补收盘帧——先发再收盘，
避免把上游真实产出的内容丢掉。

### 4. kb-service：job 句柄登记 + 有界收尾

vision / signal / root-signal 三类 job 都是 `asyncio.create_task` 启动、单次 30~60s，
uvicorn 不等它们。改为 `track_job_task` 登记，退出时 `drain_job_tasks`（上限 60s）。

顺序是硬约束：**先 drain、再 `reconcile_interrupted_batch_jobs`**。反过来会把还在跑的
批量任务先标成中断，而 job 继续写结果，状态自相矛盾。

明确**不引入 Redis**：这些 job 是幂等短任务，跨进程持久化的成本大于收益；Pod 换掉后
由调用方重新触发即可（前端有对应入口）。

### 5. diagnosis-worker：退出时交还任务

不再取新任务 → 给在跑任务收尾窗口（60s）→ 收不完就 `release_task` 放回 `pending`，
并带 `WHERE status='running' AND locked_by=:worker_id` 条件——多 worker 同时退出时
不能把别人的任务抢回去。

### 6. agent-service：不改代码，改语义

它不需要自己收盘：uvicorn 会等在手请求跑完，grace 300s 就是推理预算。真正要修的是
**失败归因**——`agent_client` 原本把上游一切异常都报成 `{"type": "error"}`，用户看到
「推理请求异常」。现在：

- `ConnectError` / `RemoteProtocolError` / `ReadError` → `server_restart`（换副本重连）；
- 其余异常（鉴权、解析、下游业务报错）仍是 `error`，不能伪装成重启。

## 新增可观测事件

| 事件 | 服务 | 含义 |
|------|------|------|
| `shutdown_signal_received` | conversation-service | 收到 SIGTERM，附带在途任务数 |
| `shutdown_signal_install_failed` / `shutdown_signal_unavailable` | conversation-service | 信号拦截失败（只能退化为等 grace） |
| `shutdown_drained` | conversation-service | 收尾完成，含 `abandoned`（>0 表示发布真的丢活） |
| `service_shutdown_abandoned` | conversation-service | 超时放弃的在途任务 |
| `agent_upstream_restart` | conversation-service | 上游 agent-service 流中断，转交前端重连 |
| `agent_client_connect_interrupted` / `agent_client_stream_interrupted` | conversation-service | 上游连接/流中断（带 `error_type`） |
| `gateway_shutdown_signal` | api-gateway | 网关收到 SIGTERM |
| `gateway_sse_closed_for_restart` | api-gateway | 在途 SSE 已收盘并让前端重连，含 `closed_streams` |
| `job_tasks_drained` | kb-service | vision/signal job 收尾完成 |
| `kb_service_jobs_abandoned_on_shutdown` | kb-service | grace 内没收完，job 随进程消失 |
| `diagnosis_worker_task_released` | diagnosis-worker | 任务交还 pending |

判读口径：`shutdown_drained.abandoned`、`job_tasks_drained.abandoned`、
`kb_service_jobs_abandoned_on_shutdown.abandoned_jobs` 长期非 0，说明 grace 或收尾窗口
不够，而不是"偶发失败"。

## 已知边界（对抗性审查结论）

1. **超过 grace 的推理仍然会断**。推理上下文只在 agent-service 内存里，无法转移；
   超过 300s 被 SIGKILL 时前端重连 2 次后会停住，需要用户重发。要彻底解决只能做推理
   状态外置，成本远高于收益。
2. **kb job 在 Pod 替换后需要重新触发**。这是刻意的取舍，不是遗漏。
3. **preStop 10s 计入 grace**：所有 drain 上限都按"preStop + drain < grace"配置。
4. **收盘帧本身可能丢失**：客户端此刻已断开时无从交付，只能靠前端下次操作时重新拉历史。
5. 网关的 60s 够用，是因为它发完收盘帧就结束，不需要等上游写完。

## 验收

单元/构建：

- `uv run --frozen pytest backend/conversation-service/tests backend/api-gateway/tests backend/kb-service/tests backend/diagnosis-service/tests`
- `cd frontend/customer && pnpm test && pnpm build`

staging 演练（每项都要看事件，不只看界面）：

1. 发起一个 ops-agent 长对话，流式输出中触发 conversation-service 滚动发布
   → 期望：流尾出现 `server_restart`，前端 2s 内自动续接，日志有 `shutdown_drained`
   且 `abandoned=0`。
2. 同上但发布 api-gateway → 期望：`gateway_sse_closed_for_restart`，前端重连后继续收内容。
3. 发起 KBD 视觉拆解 job，跑的过程中发布 kb-service
   → 期望：`job_tasks_drained` 且 `abandoned=0`；若 Pod 被强制删除则接受重新触发。
4. 发布 diagnosis-worker 且手上有 running 任务
   → 期望：`diagnosis_worker_task_released`，任务回到 `pending` 被新 worker 接走，
   而不是卡到 900s 租约超时。
