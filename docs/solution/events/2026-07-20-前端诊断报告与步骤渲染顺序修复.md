# 前端诊断「先报告后诊断」渲染顺序修复 — 分析与修复

> 本文档是 2026-07-20 一次工作循环的**方案事件文档**，记录对客户端 UI
> （`frontend/customer/src/stores/chat.ts`）流式消息渲染顺序缺陷的排查与修复决策。
>
> 触发工单：`Q2026071923606`（KBD 诊断合入 PR #574 后的现网复测）。

---

## 一、现象与预期

- **现象**：诊断输出时，UI **先**展示诊断报告（含匹配到的 KBD 链接），**再**展示诊断
  步骤卡片，视觉上呈现「先给结论、再补过程」。
- **预期**：应先执行诊断、匹配部分或全部前端/后端信号，**之后**才提示对应 KBD 链接，
  即顺序应为「诊断步骤 → 工具执行 → 最终报告（含 KBD 链接）」。

## 二、全链路排查（确认根因在前端，而非后端）

按事件产出与透传链路逐层核查：

1. **agent-service `diagnose()`**：顺序正确——先产出 `kbd_diag_step` /
   `kbd_diag_confirm`（诊断步骤事件），再 `yield` 报告文本（`text_chunk`，内含 KBD
   链接），最后 S4。
2. **agent-service 路由 `agent.py`**：SSE 按事件顺序透传，无重排。
3. **conversation-service `AgentClient` / 路由**：按序透传，无重排。
4. **frontend `chat.ts`（根因所在）**：流式一开始就 `push` 一个空的「AI 报告气泡」；
   诊断步骤的 `tool_call` / `interactive_request` / `agent_exec_command` 卡片在流式
   期间被 `push` 到它**之后**；报告 `text_chunk` 虽在流末尾才到达，却写进那个**最前**
   的气泡——于是视觉上「报告在顶、诊断卡片在底」，表现为「先报告后诊断」。

## 三、修复方案

最小、单点、纯前端修复：在流式 `finally` 收尾时，将该「AI 报告气泡」`splice` 出来再
`push` 到消息列表**末尾**。

- 修复后顺序：`诊断步骤 → 工具执行 → 最终报告（含 KBD 链接）`，符合「先诊断、匹配信号
  后再提示 KBD 链接」的预期。
- **无副作用**：普通对话（流式期间无工具卡片被 push）时，报告气泡本就是末尾元素，
  `reportIdx < length - 1` 条件不成立，逻辑为 no-op。

### 改动点

- `frontend/customer/src/stores/chat.ts`：流式 `finally` 分支新增报告气泡「移至末尾」
  逻辑（在 `isStreaming` 置 false 之前执行）。

## 四、验证

- 前端 lint 0 错误。
- 预期效果：现网复测 `Q2026071923606`，可见顺序变为「诊断步骤/工具执行 → 最终报告
  （含 KBD 链接）」。
- 注意：该改动为前端源码，需重新构建/重启 `frontend/customer` 后在环境复测生效。
