# 日志收集上传 500：存储卷缺失与错误不可定因

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：case-service 增加日志存储卷；新增 LC-PLATFORM-007/008 与 problem 文案链路；前端不再显示裸 500 | [日志收集 bridge 执行通道](2026-10-22-日志收集bridge执行通道.md) |

## 一、现象

工单 Q2026102701294：日志收集面板探测正常（`/sf/bin/acli`、版本 1.0.0、可采节点 1 个），
节点侧 `acli log_collect progress` 显示「收集完成 100%」，但平台任务失败，面板只显示：

```text
Request failed with status code 500
```

## 二、第一性原理：拆成两个独立事实

1. **上传要落盘**：P3 分片上传把分片写到 `LOG_COLLECT_STORAGE_ROOT`（默认
   `/var/lib/log-collect`），合并时再写一份等大的 `.tmp`。
2. **容器不可写**：case-service 以 uid=1000 运行，镜像内 `/var/lib` 属 root:0755，
   该目录不存在也无法创建；Deployment 此前没有任何卷挂载。
3. **错误信息被丢弃**：`LocalLogCollectStorage.__init__` 抛 `PermissionError`，全局兜底
   返回 `{"error":{"code":"INTERNAL_ERROR","message":"服务内部错误"}}`，而前端 axios
   只展示 `Request failed with status code 500` —— 三层信息各自断链，现场无从下手。

结论：**只要走 P3 上传就必然 500**（不是概率），且报错无法定因。

## 三、修复

### 3.1 存储（根因）

- 新增 `templates/case-service/pvc.yaml`（`case-service-log-collect`，RWO，
  `caseService.logCollectStorage.size` 默认 50Gi）；
- Deployment 挂载到 `mountPath` 并显式注入 `LOG_COLLECT_STORAGE_ROOT`（路径与卷同源声明）；
- Pod 级 `fsGroup=1000`（全局基线已有）让 kubelet 把卷属组调整为可写；
- `strategy: Recreate`：RWO + 本地文件系统，禁止新旧 Pod 同时挂载。

### 3.2 存储层自检

`LocalLogCollectStorage`：

- `mkdir` 失败 → `LogCollectStorageUnavailableError`，文案含**目录、运行 uid、系统原因、处理建议**；
- 构造后写探针文件（`mkdir` 成功 ≠ 可写，只读挂载/ACL 只有在真正写时才暴露）；
- `check_capacity(required)` 在 init 前校验剩余空间（`required = 包体 × 2`，含合并临时文件）；
- 合并阶段 `ENOSPC` 同样映射为容量异常，不退化成未知 500。

### 3.3 错误码与文案

| 码 | HTTP | 含义 | 详情里必须有的具体事实 |
|---|---|---|---|
| `LC-PLATFORM-007` | 503 | 日志存储目录不可写 | 目录路径、uid、errno 原因、修复建议 |
| `LC-PLATFORM-008` | 503 | 日志存储空间不足 | 需要多少、可用多少、目录 |

- `build_problem` 增加 `user_hint` / `ops_hint`（"下一步怎么办"的单一来源）；
- 全局兜底 500 的 message 带上 `方法 + 路径 + request_id`，body 也带 `request_id`，
  未知异常不再只有一句「服务内部错误」。

### 3.4 前端展示

`shared/src/api.ts` 响应拦截器把 problem 提升为可读消息，输出格式：

```text
[LC-PLATFORM-007] 日志存储目录不可写：/var/lib/log-collect（运行用户 uid=1000，原因：Permission denied）…；建议：…
```

- 只做增强：后端没有结构化 problem 时保持 axios 原行为（防回归）；
- `error.problem` 保留结构化字段，供需要分层的组件使用。

## 四、测试方案

### 4.1 单测

| 层级 | 用例 | 断言 |
|---|---|---|
| 存储 | `Path.mkdir` 抛 `PermissionError` | 异常文案含目录、`uid=`、原因、挂载建议 |
| 存储 | 写探针抛 `PermissionError`（只读挂载） | 构造期即失败，文案含 `Read-only file system` |
| 存储 | `disk_usage` 剩余 1B | 文案含「空间不足」、所需量、可用量、清理/扩容建议 |
| 服务 | `init` 时容量不足 | `LC-PLATFORM-008`、503、文案含「空间不足」 |
| 路由 | 存储构造失败 | `HTTPException` 503、`detail.code=LC-PLATFORM-007`、含路径与 `user_hint` |
| 前端 | `formatApiProblem` | `[码] 详情`、标题不重复、无字段时退回 request_id |
| 前端 | 拦截器 | 503 problem → `error.message` 含码、`error.problem` 可读；非结构化 500 → 保持原文 |

### 4.2 Helm 渲染

```bash
helm lint deploy/helm/hci-platform
helm template hci-platform deploy/helm/hci-platform -n hci-staging \
  --set secrets.postgresPassword=x --set secrets.internalApiToken=x \
  --set secrets.jwtSecret=x --set secrets.llmApiKey=x > /tmp/render.yaml
# 断言：PVC 存在、deployment 含 mountPath = /var/lib/log-collect、
# LOG_COLLECT_STORAGE_ROOT 同值、volumes.claimName 指向该 PVC、strategy=Recreate
```

### 4.3 staging 端到端

1. **正常路径**：重新打开工单 → 采集 → 上传。期望：任务 `completed`，`archive_path` 有值，
   容器内 `ls /var/lib/log-collect/objects/<case>/` 能看到 zip。
2. **只读故障注入**（验证文案，不验证根因）：
   ```bash
   kubectl -n hci-staging exec case-service-<pod> -- chmod 500 /var/lib/log-collect
   # 调 init upload 接口
   # 期望：HTTP 503，code=LC-PLATFORM-007，detail 含目录与 Permission denied
   kubectl -n hci-staging exec case-service-<pod> -- chmod 700 /var/lib/log-collect
   ```
3. **容量不足**：临时把 `LOG_COLLECT_STORAGE_ROOT` 指到小容量 emptyDir（或用 `fallocate`
   占满测试卷），init 时声明一个大于剩余空间两倍的 `total_size`。期望：503 +
   `LC-PLATFORM-008`，文案含「需要 / 可用」。
4. **未知异常兜底**：请求一个会抛非业务异常的路由，期望 500 body 含 `request_id`，
   前端提示含方法、路径与编号（不再只有 `Request failed with status code 500`）。
5. **回归**：恢复权限后再传一次，期望成功（`get_upload_storage` 失败不缓存半成品实例）。

## 五、边界

- 存储卷默认 `50Gi`，只覆盖单包 20GiB 的峰值需求；长期归档清理仍需运维策略。
- `Recreate` 会在升级窗口内让 case-service 短暂不可用（控制面无状态请求重试可接受）。
- 未知异常仍无法自动给出"具体原因"：诚实的做法是给出定位编号，而不是猜测性归类。
