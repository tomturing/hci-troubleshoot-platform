## 一、问题与可验证的物理事实

工单 Q2026112001180 的日志收集面板在阶段一（工具安装）成功后，弹出红色提示：

> 插件同步未完成（manifest_unreachable）：期望 0 个，新增 0、覆盖 0、跳过 0，失败 0

平台库与桥日志给出的事实：

| 事实 | 证据 |
|------|------|
| 三次 `acli_sync` 全部紧跟一次 `acli_plugin_sync.manifest_failed`，原因码均为 `manifest_unreachable` | `bridge_execution_logs`（07:53:21 / 07:53:55 / 07:56:49） |
| 失败原文为 `tls: failed to verify certificate: x509: certificate signed by unknown authority` | 同上 `extra.detail` |
| `platform_url` 为 `https://acli.sangfor.com.cn:4443`，即 staging 平台入口，且为自签证书 | 同上 `extra.platform_url`；`delivery_runner.go` 同源注释 |
| 阶段一正常：acli 1.0.3 安装成功、三节点插件目录 `present=true` | `acli_sync.install_done` / `node_plugin_verify` |
| 期望态从未拉到，因此回执计数全 0 | `acli_plugin_sync.manifest_failed` 后无 `manifest_fetched` |

**结论**：不是插件规格错误、不是票据错误，是**桥用系统信任链去校验一个自签平台**——该前提在客户内网永远不成立。

## 二、根因（三层，缺一层都不能解释「修了也不生效」）

1. **策略层**：阶段二拉 manifest 的 `insecure` 取 `msg.TransferTLSInsecure`，而前端 `buildAcliSyncMessage` 只下发 `platform_url` / `plugin_ticket`，从不下发 `tls_insecure`，该值恒为 `false`。交付通道 2026-10-27、桥日志直传通道 2026-10-28 都栽在同一前提上，阶段二属于同族缺口的最后一处。
2. **兜底层**：交付通道命中 `uplink.IsUntrustedCertificateError` 会自动放宽一次并留痕（`delivery_runner.go`），阶段二没有这层。
3. **错误链层（隐蔽）**：`newAcliPluginError("manifest_unreachable", err.Error())` 把底层错误压成字符串，`errors.As` 再也穿透不到 `*url.Error` 里的 x509 原因。**只补重试、不补错误链，重试判定会恒为 false**——这是本次实现过程中被单测当场抓到的坑。

## 三、修复

### 3.1 证书策略

`fetchAcliPluginManifest` 改为「严格 → 仅证书不受信才放宽一次 → 回报 relaxed」：

- 默认路径不变：先用系统信任链严格校验；
- 仅当 `!insecure && uplink.IsUntrustedCertificateError(err)` 时用放宽 client 重试**一次**；
- 重试成功返回 `relaxed=true`，调用方写 `acli_plugin_sync.tls_relaxed` 留痕（只写桥日志，不上屏）；
- 重试仍失败则**报放宽后的原因**（它更接近真相，例如平台确实 502），不保留第一次的握手错误。

### 3.2 错误链

`acliPluginError` 增加 `cause` 字段与 `Unwrap()`，新增 `wrapAcliPluginError(code, cause)`；传输层失败一律走 wrap，原因码给人看、错误链给机器判定。

### 3.3 不重试的边界（刻意为之）

| 情况 | 行为 | 理由 |
|------|------|------|
| 401 | 直接 `plugin_ticket_rejected`，不重试 | 放宽证书无法修复鉴权，重试会掩盖票据问题 |
| 5xx | 直接 `manifest_http_error`，不重试 | 服务端已表态，重试只延迟失败 |
| 超时 / DNS 失败 | 不重试 | 不是信任链问题，放宽无意义 |
| 清单解析/校验失败 | 不重试 | 内容问题，与 TLS 无关 |
| 公网 `http://` 平台地址 | 直接 `platform_url_insecure` | 放宽证书不等于放开明文，票据不得裸奔 |

## 四、验证

新增 `acli_plugin_manifest_tls_test.go`，用 `httptest.NewTLSServer`（自签根，等价现场）：

| 用例 | 断言 |
|------|------|
| 自签 + 未授权 | 放宽后成功，`relaxed=true`，平台侧恰好收到 1 次请求 |
| 回环 http（信任链成立） | 不触发放宽，`relaxed=false`，请求 1 次 |
| 已授权放宽 + 5xx | `manifest_http_error`，不重试 |
| 已授权放宽 + 401 | `plugin_ticket_rejected`，不重试 |
| 自签 + 放宽后 502 | 报 `manifest_http_error`（放宽后的真因），`relaxed=false` |
| 自签 + 已授权放宽 | 直接成功，`relaxed=false`，请求 1 次 |
| 公网 http | `platform_url_insecure` |

补充：`go test ./...`（terminal_bridge 全量 15 包）通过，`gofmt` 无差异。

## 五、残留与边界

- **本次不改变 `LC-PLUGIN-015` 的判定**。同面板的「下发后节点未建立采集任务」是另一条链路：`acli log_collect create` 退出 0 但节点侧任务未注册，与插件期望态无关（若真缺专项插件会报 `LC-PLUGIN-016`）。该单的节点侧可疑事实为 cgroup v2 路径不存在与 `/sf/etc/vtp-rpc/vtp-rpc-ssl.pem` 缺失，需节点侧只读核对后单独处置。
- 放宽只在**单个函数的单次调用**内生效，不写全局状态；票据鉴权不放松。
- 桥需重出 exe 才能到达现场（合并 ≠ 到达客户机）。
