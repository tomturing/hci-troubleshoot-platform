# hci-sim P0–P1 纵向设计：从 capability 到 KBD 27123 Result

## 1. 设计判断

对抗性审查首先问“成功到底证明了什么”：UI 点击没有请求是前端状态机缺陷；`sim-case-*` 是身份伪造缺陷；初始现场 Runtime revision 1 与主库 active revision 24 是权威性差异。三者不能靠改按钮文字或 HTTP 200 掩盖，必须沿数据流建立可验证的绑定；最终发布已升级并对齐到 revision 25。

## 2. 目标架构

```text
Admin UI
  ├─ GET capability ──> API Gateway ──> hci-sim HTTP control plane
  ├─ POST build ──────> API Gateway ──> hci_sim Run + signed Lease
  └─ POST TestRun ────> API Gateway ──┬─> case-service（真实 Q... Case）
                                     └─> hci-sim TestRun（绑定 case_id）
        │
        └─同源 WebSocket /terminal-bridge
             └─K3s terminal_bridge ──SSH/2222──> hci-sim
                                                   └─Run Event
        └─POST Result ───────────────> hci_sim Run Result
```

## 3. Capability 设计

Runtime 从只读 Manifest 计算实际加载值，环境变量只声明审计范围：

| 字段 | 语义 |
|---|---|
| `runtime_revision` | 当前不可变 Fixture 的 revision（最终现场为 25） |
| `requested_revision` | 权威来源声明的 active revision（最终现场为 25） |
| `authority_scope` | `runtime_fixture` 或显式 `dev_golden` |
| `buildable` | support ID、Bundle digest、授权范围均满足 |
| `capability_gap` | `kbd_not_loaded`、`kbd_revision_mismatch`、`synthetic_fixture` 等结构化原因 |

`dev_golden` 不是“忽略 mismatch”的隐式开关，而是必须在 Helm/GitOps 中显式声明的开发授权范围；revision 不一致时仍 fail closed。最终发布的 revision 25 Bundle 已消除 mismatch。

## 9. 最终实现补充

Build 在一个 PostgreSQL 事务内注册 Scenario、published Bundle metadata 和 Run。事务对 manifest digest、schema version、object URI、object digest 与 size 做严格校验；相同 digest 幂等，任何元数据冲突均回滚。这样 Runtime 能执行 Bundle 与 `hci_sim.fixture.bundle` 权威事实不会再分叉，capability matrix 也不再依赖进程内状态猜测。

Agent 会话不再执行前端固定 smoke。Conversation Service 只接受 TestRun 返回的 `sim-ssh` 上下文，Agent 根据 KBD signal 发起 task、lsof、ps；只有结构化命令证据与 Agent 结论都满足时，Gateway 才允许提交 `passed`。`failed` 和 `inconclusive` 显式传播，禁止用 SSH Ready 或 exit code 0 单独推导产品结论。

## 4. Case/TestRun 事务边界

Gateway 负责跨服务编排，因为浏览器不应持有 case-service 地址，也不应把 Case 伪造逻辑放在 Runtime：

1. 校验标题/描述，调用 case-service `POST /api/cases/`。
2. 取得真实 `Q...` 后复制 payload，注入 `case_id` 和 `environment_context.case_id`，调用 Runtime TestRun。
3. Runtime 在 `control_plane.run` 上执行 `BindCase`：空值首次绑定、相同值幂等、不同值 CAS 冲突。
4. Runtime 失败时 Gateway 最佳努力关闭新建 Case；关闭失败只记录结构化告警，不覆盖原始 Runtime 错误。

这个顺序优先保证“一个成功响应必然有真实 Case”。代价是 Runtime 故障时可能短暂出现已关闭 Case；该代价可审计、可补偿，比成功响应含伪身份更安全。

## 5. Admin UI 状态机

```text
idle → capability_check → building → succeeded
                                  └→ failed（保留表单）
succeeded --开始测试--> ready_to_create_case
ready_to_create_case --提交--> creating_case → bridge_smoke → passed
                                             └→ failed（可重试）
```

“开始测试”只做 `ready_to_create_case` 的 UI 迁移，避免按钮语义与“连接 SSH 并创建工单”重复；后者才发 TestRun 请求。三条命令按顺序发送 `ssh_exec_process`，任一 exit 非 0 或超时即失败关闭 WebSocket。

## 6. 安全与故障设计

- Capability 仍由 Gateway 注入 Runtime Token；浏览器拿不到控制 Token。
- Lease 密码不进日志、localStorage、Case payload 和 Result；测试结束立即清除内存字段。
- Bridge WebSocket 固定同源 `/terminal-bridge`，沿用 K3s NetworkPolicy，仅允许到 hci-sim TCP/2222。
- 失败分类区分 capability、case-service、SSH handshake、exec、Result persistence；不把所有错误压成“HTTP 409”。
- Runtime 只接受 `sim-ssh`，不因 host 名称回退真实 HCI。

## 7. 反例审查结论

| 反例 | 为什么拒绝 |
|---|---|
| 点击按钮只展开日志 | 没有状态迁移，也没有可追踪动作 |
| 保留 `sim-case-*` | 无法查询平台工单、Agent 或权限边界 |
| 把 active revision 改写进旧 Fixture | 破坏 digest/来源真实性 |
| 只验证 Pod Ready/HTTP 200 | 不证明 WebSocket、SSH、命令、Result 或数据库绑定 |
| 让 Admin 直接 curl Runtime | 绕过 Gateway Token 和 NetworkPolicy |

## 8. 回滚

回滚镜像即可恢复旧 UI/Runtime；新增 API 为兼容性新增，不删除既有 build/result 路径。数据库 `BindCase` 只写已有 JSONB 字段，可随镜像回滚，不需要 destructive migration。
