# 2026-11-24 LC-INSTALL-010 误报修复（前置插件校验时序倒置）

## 现象

`terminal_bridge` 新 exe 到达现场后，3 个互不相关的客户集群、4 个采集任务全部在
create 前被 `LC-INSTALL-010` 拒绝：`Q2026112300987`（2 次）、`Q2026111300153`、
`Q2026112400088`，涉及 acli 1.0.0 / 1.0.1、P1 直传与 P2 中继两种交付路径。
全库该错误码首次出现于 `2026-11-23 16:23:29+00`，此前为 0。

失败现场快照（`detail.failure_snapshot`）三例完全一致：

| 事实 | 值 |
|---|---|
| `/sf/data/local/acli/plugins/log_collect/plugin` | 存在且非空（36949 / 37102 字节） |
| `/sf/data/local/acli/plugins/log_collect/manifest.json` | 存在且非空（13494 / 13629 字节） |
| `/sf/data/local/acli/plugins/log_collect/tools/lmt_collect_info/progress.json` | `exists=false` |
| 磁盘 | 28% / 39% / 32% |

同一 bridge 的 `acli_sync.node_plugin_verify`（`phase=after`）判 8 台节点
`present:true`、`missing:null`；节点 `acli.log` 显示 `built-in plugin init complete`，
无 rsync/unlinkat 报错。两套判据自相矛盾。

## 根因（第一性原理）

`progress.json` **不是 acli 安装包落盘的静态文件**，而是节点 `sfd_main.py` 在采集任务
启动后创建并持续更新的运行时进度文件。成功工单的
`/sf/log/today/acli/plugins/log_collect/collection_log.log` 原文：

- `sfd_main.py[line:364] ... run cmd: echo '{"status": "pending", "progress": 0}' > /sf/data/local/acli/plugins/log_collect/tools/lmt_collect_info/progress.json, code: 0`
- `sfd_main.py[line:680] ... update progress.json collect result data success`

`docs/solution/events/2026-11-23-日志收集失败兜底P0.md` 引入的前置校验
（`terminal_bridge/internal/logcollect/log_collect_preflight.go`）在 **create 之前**
用 `[ -s ]` 要求该文件存在且非空，缺失即拒绝并给 `LC-INSTALL-010`。这等于把
「本次采集才会产出的结果」当成「开始前必须具备的前提」：全新安装或重装 acli 后
该文件必然不存在，于是 100% 误拦截。旧 exe 没有这道检查，直接 create，由
`sfd_main.py` 自行创建，因此此前 51 单同版本采集正常完成。

## 定责

- 报错产生方：客户机 `terminal_bridge` exe 的 create 前置校验；
  `backend/case-service` 与 `frontend/customer/src/components/LogCollectPanel.vue`
  只负责落库与展示。
- 缺陷引入方：PR #1617（commit `f4622bcb`，2026-11-23 13:24 +0800）。
- 生效链路：#1618（18:38 +0800）/ #1630（20:34 +0800）自动重建 windows exe
  合并 → 现场人工重装 → 2026-11-24 00:23（节点本地时间）首单被拒。
- acli 安装器、平台后端、客户现场环境均无责。页面给的「重新安装 acli」建议
  在误报场景下无效且有害（重装会清空插件目录，见
  `docs/solution/events/2026-11-23-日志收集失败兜底P0.md` 记录的 `Q2026112300134`）。

## 修复

1. `terminal_bridge/internal/logcollect/log_collect_preflight.go` 拆分两类清单：
   `logCollectInstallArtifacts()` 只含 `plugin` 与 `manifest.json`，是唯一允许阻断的
   安装期事实；`logCollectRuntimeProgress` 改名为运行时产物，仅用于失败现场快照取证，
   不参与任何阻断判定。
2. `log_collect.plugin_preflight` 事件补 `trace_id / case_id / node_ip / task_id`，
   并显式记录 `blocking_paths` 与 `observation_only_paths`，事后可直接回答
   「这次为什么没查进度文件」，避免运行时路径被重新塞回阻断清单。
3. `terminal_bridge/internal/logcollect/log_collect.go` 把证据上下文传入校验，
   使该事件纳入同一调用链。
4. `terminal_bridge/internal/logcollect/log_collect_preflight_test.go` 补三条边界：
   全新安装无 `progress.json` 必须放行、真缺 `plugin` 仍必须拒绝、失败快照仍保留
   运行时文件作为观测证据。

**不改契约**：`contracts/log_collect_display.json` 中 `LC-INSTALL-010` 的语义仍是
「安装后内置插件不完整」，在 `plugin` / `manifest.json` 真缺失时文案与
「重新安装 acli」的处置建议依旧正确；本次只纠正触发判据，避免把修复扩散到
七份生成物与两端 UI。

## 验证

- `terminal_bridge` Go 单测、`gofmt`、`go vet`、`go build` 全量通过（含 `-race` 与
  `telemetry` tag 的 CI 门禁项）。
- 判定层端到端：`TestPluginProbeCommandEndToEndOnFreshInstall` 在临时目录里只放
  `plugin` / `manifest.json`（不建 `tools` 目录），用真实 `sh` 执行生成的探测命令，
  走完「命令生成 → shell 输出 → 解析 → 放行」；再删除 `plugin` 走「拒绝」分支。
  不依赖真实 SSH 节点即可复现「全新安装放行 / 插件残缺拒绝」两种现场。
- 未改任何 `frontend/` 与 `backend/` 文件，页面文案与展示逻辑零变更；
  UI 端到端验收随现场 exe 生效一并执行（见下）。

## 部署边界与现场验收

`terminal_bridge` 是客户机 exe，仓库无自更新机制。合并后必须等
`build-terminal-bridge.yml` 自动重建并合并 exe PR，再由现场人工重新下载安装；
**合并源码不等于修复到达节点**。验收清单：

1. 三个现场各新建一次采集（历史 `failed` 任务不订正、不复活）。
2. `bridge_execution_logs` 出现 `log_collect.plugin_preflight_ok`，且事件里
   `blocking_paths` 只有 `plugin` / `manifest.json`。
3. `collection_log.log` 出现 `sfd_main.py` 写入 `progress.json`，任务最终 `completed`。
4. `log_collect_task` 不再新增 `LC-INSTALL-010`；客户页面不再出现「安装后内置插件
   不完整」红条与「重新安装 acli」提示（真浏览器按人工操作流程确认）。
5. 反向回归：人为构造 `plugin` 缺失的节点，仍应被 `LC-INSTALL-010` 拒绝，
   证明 P0 的原始防护未被削弱。
