# 2026-11-17 日志收集任务进展与周期筛选方案

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-11-17 | v1.1 | 纠正压测清理数量（39→7）与待补交付入口结论；新增过滤栏与运营标记修复 | [后续方案](./2026-11-17-日志收集过滤栏与运营标记修复.md) |

## 背景与需求

见 [需求事件文档](../../requirement/events/2026-11-17-日志收集任务进展与周期筛选.md)。四个改动看似分散，底层只有两件事：入口的初始状态属于前端局部状态；「全部」是"取消时间过滤"而不是"一个更大的天数"。

## 方案概述 (WHAT)

1. 页签激活值由 `ref('default')` 改为 `ref('upload')`，页签文案改为「任务进展」；不改路由、不改缓存、不引入 URL 参数。
2. 周期下拉增加 `:value="0"` 的「全部」选项，并绑定 `@change="search"`，让周期切换与「查询」共用同一函数。
3. 后端把 `days` 校验放宽为 `ge=0`，`days=0` 时 `since/until` 传 `None`，筛选构造器不追加时间边界；无其它条件时返回 `TRUE` 防止空 WHERE。
4. 用 staging 真实任务行调用权威 `derive()` 做近 7 天审计，而不是按 `status/delivery_status` 自行推断标签。

## 详细设计

### 1. 前端改动

- `frontend/admin/src/views/LogCollectScenarioView.vue`：默认页签 `upload`，标签「任务进展」。页面注释补充默认落点理由。
- `frontend/admin/src/views/components/LogUploadPanel.vue`：周期下拉增加「全部」并绑定 `@change="search"`。`search()` 原本就会重置分页、递增进度轮询序号并重新加载，因此复用它即可保证"选择即查询"与「查询」按钮完全同构。

### 2. 后端契约

- `days: int = Query(7, ge=0, le=90, description="...；0 表示全部")`。
- `since, until = (None, None) if days == 0 else (now - timedelta(days=days), now)`。
- `_build_filters` 参数改为 `datetime | None`，仅当二者都非空时追加 `created_at >= :since / <= :until`；最终 `" AND ".join(clauses) or "TRUE"`。这样"全部 + 无其它筛选"和"全部 + 工单号筛选"都能生成合法 SQL。
- 结构化日志新增 `days=days`，与既有 `trace_id` 一同输出，便于按周期对账查询量与耗时。

### 3. 决策依据 (WHY)

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| `days=0` 哨兵（选中） | 改动最小、前后端类型不变、与原 1~90 连续 | 需文档明确 0 的语义 | 采用 |
| 新增 `all=true` 布尔参数 | 语义显式 | 前端要同时维护两个参数，易出现 `days=7&all=true` 冲突 | 否 |
| 用一个很大的天数（如 9999） | 前端零改动 | 仍是时间窗口，且受 `le` 校验约束；语义是假的 | 否 |

对抗性审查要点：
- 空 WHERE 会让 SQL 语法错误 → 用 `TRUE` 兜底，并写单测钉死。
- 只发 `change` 不发 `update:modelValue` 的测试无法反映真实下拉行为 → 单测按 Element Plus 的真实事件顺序模拟。
- 空列表时批量证据查询会跳过，SQL 条数从 5 降到 3 → 单测按真实分支断言。
- 默认页签改变会让依赖"初始即默认场景"的既有测试失效 → 测试辅助函数显式切页签，并新增默认落点断言。

## 近 7 天任务审计（2026-11-11 ~ 2026-11-17）

口径：从 staging `log_collect_task` 取近 7 天全部 191 行，逐行调用 `backend/case-service/app/domain/log_collect_display.py::derive()`。

| 标签 | conclusion | 任务数 | 唯一工单 |
|------|-----------|-------|---------|
| 进行中 | pending | 11 | 11 |
| 已交付 | success | 0 | 0 |
| 已交付 · 有疑点 | partial | 81 | 70 |
| 未完成 · 待补交付 | unfinished | 3 | 3 |
| 失败 | failed | 49 | 26 |
| 已取消 | cancelled | 47 | 29 |

`11+0+81+3+49+47=191`，与总行数一致；六个桶由 `derive()` 单点派生，标签本身没有前后端两套口径。

### a. 第一排标签准确性

- **整体准确**：六桶互斥且可加，与第一排卡片同源；`success=0` 不是渲染故障，而是"只有交付证据成立且包内容校验通过才算已交付"的口径结果。
- **「进行中」有语义漂移**：11 单中 5 单创建超过 24 小时，最长约 126.7 小时（Q2026111110000、Q2026010100001、Q2026111201157 等）。按状态机 `phase != settled` 判 pending 没错，但把停顿 5 天的任务与真在途混在一张「进行中」卡里会掩盖问题。
- **「已取消」混入压测噪音**：47 单中 **7 单**带 `pentest-cleanup / test_cleanup / ssrf_*_cleanup` 标记，其余 34 单是 `error_message='用户取消'` 的真实业务取消。此前把 `LC-HTP-002`（本次失败未能自动归因）的 39 单误当成压测清理，是错误归因；现已按原始错误文本重新核对。

### b. 非「已交付」标签的具体问题与改进建议

1. **已交付 · 有疑点（81 单 / 70 工单）**：73 单归因 `LC-BRIDGE-005`（S7 包内容清单未回传），直接原因是 2026-11-16 07:07Z 前 ingress 漏配 `/api/direct/log-collect/` 直连规则，随后又暴露 `artifact-manifest` 的 jsonb 绑定 500 与 `network-probe.samples` 422。#1517/#1526 已合并并于 2026-11-17 00:47Z 部署，部署后未再出现新的证据上报失败事件；但存量任务不会自动补传，因此 partial 是事实正确，不能改写成 success。
   - 建议：提供"证据补拉/重算"入口，对 5888 已回查通过（`p1_archive_check.verified=true` 或 `relay_status=success`）的任务按 task_id 重新拉取四张证据表；不要让用户重采。用一单完整的新采集验收 manifest 表确实写入，再宣布闭环。
2. **失败（49 单 / 26 工单）**：`LC-PLUGIN-015` 15 单（下发后节点未建立采集任务，多为 acli 版本与专项不匹配）、`LC-EXEC-003` 13 单（节点命令非零退出）、`LC-5888-002` 4 单、`LC-ENV-004` 4 单、`LC-ENV-006` 3 单（SSH 会话不存在）、`LC-SPC-001` 3 单（场景清单目录缺失）、`LC-TRANSFER-008` 2 单（客户机磁盘不足，样例仅余 745.3 MiB 而需要 1.2 GiB）。重复重试集中：Q2026110302155 有 8 次、Q2026111300683 有 6 次；Q2026110302155 的 `LC-SPC-010` 原始输出为"节点不可达，可用节点为 0"，与已知双 spc 目录 + find 退出码误报问题吻合。
   - 建议：下发前做专项存在性与节点能力预检（fail-closed，直接给出具体节点和完整输出）；对同一工单连续 ≥3 次同类失败自动停止重试并提示换专项做 A/B 对照；磁盘与 5888 可达性在预检阶段阻断，不要等包生成后才失败。
3. **未完成 · 待补交付（3 单）**：全部为 `bridge_relay` + `delivery_status=queued`，采集已完成（其中 Q2026111400027 包已有 20.6 GB），归因 `LC-5888-002`（日志服务器不可达）。这是可续传的中间态，不是失败。
   - 更正：**平台已提供续传/补交付入口，现场用户已知如何使用**，无需再建。经 0.4 → 0.2 免密 SSH 核对：`Q2026111600133` 已有 279 MB 规范归档，`Q2026111400027` 已有 18.9 GB 规范归档（两单均已补录）；仅 `Q2026111301229` 在 5888 上无对应目录。此处原建议作废。
4. **进行中（11 单）**：5 单停滞超 24 小时，其中 Q2026111201130 已 113 小时仍 `collecting/none`，Q2026010100001 卡在 `pending/queued` 且报"平台副本不存在：/tmp/ok"（疑似验证数据混入运营库）。
   - 建议：在 `derive()` 增加 stalled 条件（按阶段预期时长与最后上报时间），与真在途分开展示；验证/压测工单打标记并从运营统计中默认过滤。
5. **已取消（47 单）**：7 单为压测/验证清理，34 单为真实用户取消。前者原归因落在 `LC-HTP-002`（未能自动归因）。
   - 已修复：压测文本统一映射为 `LC-HTP-004`「验证 / 压测清理」（info 级），运营看板默认排除；详见 [后续方案](./2026-11-17-日志收集过滤栏与运营标记修复.md)。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 「全部」查询的数据量远大于近 7 天 | 慢查询 | 保持分页与白名单过滤；结构化日志记录 days 与耗时便于观察 |
| 存量 partial 被误读为平台故障 | 用户重复采集 | 归因明确指向 S7 证据链路；详情给出调用链，不改写状态 |
| 压测数据污染运营看板 | 统计失真 | 本文给出打标与过滤建议，后续迭代落地 |
