# 壳工单归属认领、任务作用域授权与「上传到平台」入口可见性

## 一、现象（2026-11-13 staging，Q2026111301229）

1. 日志采集已完成（6/6 主机、454MB、`delivery.submitted` 57 片），但交付停在
   `delivery_status=queued`、`pull_offset_bytes` 为空，平台零字节。
2. 用户换浏览器重进同一单号，面板顶部提示「该工单属于其他会话身份……建议换用本人
   名下的工单号，或直接用当前工单重新采集」——**只告知、无出路**。
3. 结果卡片同屏出现「失败（17:13）」与「交付已登记但未完成（可点上传到平台重试）」，
   而「上传到平台」按钮要等一段时间才出现（此时 SSH 面板仍在"正在连接"）。
4. 用户因此倾向点「重新收集」，而重采会覆盖节点上那份尚未交付的 454MB 包。

## 二、根因（四个独立缺陷叠加）

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | `case-service` 建单写 `Case(metadata=...)`，而 ORM 真实属性是 `metadata_`；`metadata` 是 SQLAlchemy declarative 保留名，赋值只生成实例影子属性，从未落库 | 所有「日志收集任务 Q…」工单 `metadata = '{}'`；`Case(metadata_=...)` 修正后新单带 `{"source":"log_collect"}` |
| 2 | 归属校验只有 `case.client_id == 当前身份` 一条口径，而同一个人换浏览器/清 Cookie 会换 `client_id` | 本单 `case.client_id = task.created_by = fd9aad…`，当前会话身份不同 → `resolve` 返回 `owned=false` |
| 3 | `_conclusion` 把「已结束 + 未交付」一律判 `failed`，但 `delivery_status=queued` 是可续传的中间态 | 同屏「失败」+「可点上传到平台重试」 |
| 4 | `canUploadFromNode` 只认节点实时对账结论，对账需先建 bridge 会话再 stat | 面板刚打开时 `nodeAction` 为空 → 不渲染按钮，用户只能干等 |

第 2 条的要害不是"提示"，而是**没有任何合法出路**：采集层允许跨身份复用单号，写入层
却硬拒，用户唯一可点的动作是重新采集——恰好会覆盖现场唯一的那份包。

## 三、修复

### 1. 落库 bug + 历史回填

- `backend/case-service/app/services/case_service.py`：`Case(metadata=...)` → `metadata_=...`，
  并加注释防止回退。
- `database/data-migrations/066_log_collect_shell_case_metadata_backfill.sql`：只回填
  「标题匹配 + 无 source 标记 + 零会话零消息」的行，带 `metadata.backfill` 审计与
  `DO $verify$` 不变量校验；幂等，可重复执行。

### 2. 结论口径：`queued ≠ failed`

- `log_collect_display._conclusion` 新增 `unfinished`（`未完成 · 待补交付`，tone=warning）。
- `handoff_pending` 条件从 `delivery_status == "none"` 扩到 `("none", "queued")`，
  保证结论与条件同屏不打架。
- 契约 `contracts/log_collect_display.json` 同步 + 重新生成 `log_collect_display_generated.py`。
- 结论由五桶扩到六桶，**管理端分桶必须同源扩容**，否则 `Σby_conclusion != total` 会触发
  「统计恒等式异常」假告警：`_CONCLUSION_KEYS`、`AdminPathSummary.by_conclusion` 默认值、
  管理端 `bucketKeys/bucketLabels` 与 `ConclusionBuckets` 类型同步；`unfinished` 不并入
  旧字段 `failed`（它仍可补交付，并入失败会再次劝退用户）。

### 3. 任务作用域授权（单一判定点）

- 新增 `backend/shared/security/case_access.py::resolve_data_access`，放行仅两条：
  工单归属；**或**壳工单（`metadata.source=log_collect` 且零会话零消息）且本人有采集任务。
  真实业务工单（有会话）不走第二条，避免"猜中工单号 + 点一次采集"即可跨客户读取。
- `conversation-service/routes/bridge_logs.py`：手动上传与批量回采共用该判定。
- `case-service GET /api/cases/{case_id}/data-access` + `api-gateway/routes/terminal.py`：
  终端录像读写改用该判定（此前只校验 `case.client_id`）。

### 4. 认领（显式、可审计）

- `POST /api/cases/{case_id}/claim`（case-service）+ 网关 `POST /api/cases/{case_id}/claim`。
- 门禁：非本人；壳工单；无在途交付（`pulling/uploading/relaying`）；
  原身份最后活动 ≥ `LOG_COLLECT_CLAIM_IDLE_SECONDS`（默认 600s），否则 409 带原因码。
- 转移范围：`case.client_id/user_id` + 该单号下原身份的全部 `log_collect_task.created_by`
  （产物与录像按任务维度授权，只转工单会看不到旧包）。
- 审计：`case.metadata.claims`（保留最近 5 次）+ 每个任务 `detail.claim`；
  不新建表（Atlas 声明式 schema 会 DROP 额外表）。
- 前端：归属提示条内嵌「认领并继续」，不可认领时显示原因（`CLAIM_BLOCKED_REASON_TEXT`），
  不再只丢一句"建议重新采集"。

### 5. 「上传到平台」入口可见性

- `canUploadFromNode` 两级判据：对账明确 `adopt+deliver` → 立即给；对账未回 →
  平台记录（`archive_path` + `archive_size` 且非 `acli_direct`）即可先给入口，点击时 stat 校验。
- 新增 `deliverUploadFromNode()`：强制 `nodeAdoptMode='deliver'`，避免对账未回时
  默认 `resume` 把"传已有包"变成"再采一遍"。
- 结果态提示行增加「正在与节点核对包状态…」，让等待可见。

## 五、现场处置（本单）

- 该单号属 `fd9aad…`，本次会话身份不同；由于是壳工单（0 会话 0 消息）、任务
  `updated_at` 冻结在 07:50，满足认领条件：**认领 → 续传那 57 片**，不要重新采集。
- 若原身份仍在另一浏览器活跃，认领会返回 409 `owner_active`，先让原会话退出。
