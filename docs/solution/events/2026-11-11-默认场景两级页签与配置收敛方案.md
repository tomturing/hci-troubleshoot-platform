# 默认场景两级页签与配置收敛方案

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-11-11 | v1.0 | 初版：两级页签、物理删列、证据补 revision | 本文 |

## 第一性原理推导

- 场景枚举是**固定闭集**（acli `-m` 白名单 10 个），不会增减 → 不需要搜索、筛选、分页、列表滚动。
- 用户一次只查看或编辑**一个**场景 → 最小充分结构是「选择器 + 当前详情」，把 10 个场景全部渲染（哪怕收起）都是冗余。
- 选择器与顶部 `日志上传 | 默认场景 | 自定义场景` 同构，因此最优形态是**两级页签**；二级用更小字号与浅底区分层级，窄屏用横向滚动而不是换行成网格。
- 页面上的文字要么服务于「用户此刻的决定」，要么服务于「系统如何工作」；后者由交互自解释，不再保留。

## 页面方案

- 一级：`日志上传 | 默认场景 | 自定义场景`；二级：10 个场景短名横向平铺。
- 当前场景详情两张卡片：`场景概要`（枚举值只读、短名、释义、排序、启用、编辑说明、保存概要）、`默认收集清单`（状态/条目数、条目表格、新增收集项、校验并预览、保存清单、恢复默认）。
- 互斥、采集内容、典型症状、耗时提示收进「编辑说明」弹窗，主界面不占列。
- 无 alert、无说明小字、无搜索、无筛选、无新增场景。

## 数据契约

- 物理删列（迁移 059）：
  - `log_collect_scenario`：`review_state` + CHECK、`updated_by`、`created_at`、`updated_at`。
  - `log_collect_default_scenario`：`item_count`、`config_sha256`、`config_bytes`、`enabled`、`updated_by`、`created_at`、`updated_at`。
  - 保留 `module_code / items / revision / trace_id`；`trace_id` 是唯一调用链硬约束。
- `LogCollectDefaultScenario` 去掉 `TimestampMixin` 继承，否则 ORM 会 SELECT 已删除的时间列。
- **不动** `log_collect_custom_scenario`（被任务按 `(scenario_id, revision)` 引用）与 `log_collect_task`（50 列是历次交付事故的排障证据，`integrity_state` 有 15 个消费文件）。
- `build_spc_files()` 每项增加 `revision`；`task.detail.manifest` 增加 `revision: {slot: n}`，快照模块为 0。
- 清单读取异常不再静默回退：写 `manifest.mode = native_fallback`、`degraded = true` 与 `trace_id` 到 `detail`，便于定责。
- `POST /internal/log-collect/scenarios` 保留但按 `M_WHITELIST` 校验，非法枚举 400、重复 409；前端不再提供入口。
- 种子 `06_log_collect_scenarios.sql` 同步去掉 `review_state` 列，避免 PostSync 播种失败。

## 对抗性审查

| 风险 | 处理 |
|------|------|
| 双层页签被误读成 13 个并列页签 | 一级 52px/14px 白底，二级 44px/13px 浅底 |
| 10 个页签窄屏溢出后换行成网格 | 用 el-tabs 横向滚动箭头，不换行 |
| 显式保存 + 频繁切页签 = 改动静默丢失 | 父组件汇总概要/清单两路 dirty，切换前二次确认 |
| 停用场景不可点则无法重新启用 | 仅灰显，不禁用点击 |
| 删列后 ORM / 种子 / 单测残留引用 | 同步改 ORM、seed、schema、测试，并过 Atlas 门禁 |
| 把必要反馈当注释删掉 | 保留失败原因、升级桌面桥、30 天上限、未保存确认、互斥冲突提示 |
| 自定义场景「视觉互斥、底层叠加」反直觉 | 模式标签改为「自定义场景（含基础日志）」，本次不改下发语义 |
| 清单服务降级被解释为「平台按自定义清单收了」 | 降级证据落 `detail.manifest` |

## 与既有能力的关系

bridge 逐槽位扇出、`capabilities` 旧桥 fail-closed、`spc_files` 一次性载荷均不变；本机改动不触及 Go bridge，因此**不需要重建 `terminal_bridge.exe`**，也不需要现场重装。
