# 2026-11-18 日志收集场景语义与 S7 证据判定修复方案

## 背景与需求

见 [需求事件文档](../../requirement/events/2026-11-18-日志收集场景语义与S7证据判定修复.md)。

## 方案概述 (WHAT)

1. **场景语义独立于 modules**：创建时把场景快照写入 `detail.scenario`，响应暴露 `scenario_kind/scenario_label/scenario_slot`；前端「收集场景」优先显示场景名。
2. **S7 判据改为「有证据即成功」**：证据端点把清单摘要写入 `detail.artifact_manifest`，派生读快照；`quality=unknown` 不再判失败。
3. **证据未到给等待**：交付终结后 120s 窗口内 S7 为 `waiting`，窗口外为 `unknown`；只有 `detail.evidence_error` 存在时才 `failed` + `LC-BRIDGE-005`。
4. **桥显式上报失败**：新增 `/tasks/{id}/evidence-error` 端点，桥在证据 POST 失败时写入 `detail.evidence_error`。
5. **节点侧读取去掉 shell 依赖**：`tail -c` 取包尾窗口，Go `archive/zip` 解析中央目录；窗口不足自动放大到 16 MiB。
6. **前端终态加密对账**：终态后若证据仍在等待窗口内，轮询间隔由 30s 降到 10s，证据到达后自动回落。

## 详细设计

### 1. 场景快照（用户语义 vs 技术槽位）

```python
scenario_snapshot = {
    "kind": "custom", "id": ..., "revision": ..., "code": ..., "label": "test",
    "source": "spc", "item_count": ...,
}
```

- 写入 `detail.scenario`，与 `modules` 并存；`modules` 保持被覆写的 `["core"]`（acli 物理约束，`-m core` 不能改）。
- 名称必须快照：场景可改名或删除，历史任务仍要能回答「当时选的是哪个」。
- `resolve_scenario_display()` 是唯一读取入口；无快照的历史任务按 `default` 处理，不猜。

前端：

```ts
if (task.scenario_kind === 'custom') {
  return label ? `${label}（自定义场景）` : '自定义场景（已删除）'
}
```

### 2. S7 判定四分支

```python
if isinstance(manifest, Mapping) and manifest:      # 证据已回传（真表或 detail 快照）
    statuses["S7"] = "success"
elif _evidence_disabled(detail):                    # 桥无证据能力
    statuses["S7"] = "skipped"
elif _evidence_error(detail):                       # 桥显式上报过失败
    statuses["S7"] = "failed"
elif evidence_pending:                              # 交付刚终结、窗口内
    statuses["S7"] = "waiting"
else:                                               # 没数据就是没数据
    statuses["S7"] = "unknown"
```

删除原分支 `quality == "unknown" and delivered → failed`。归因码只在 `_evidence_error` 时挂载。

### 3. 证据清单快照

`PUT /tasks/{id}/artifact-manifest` 在回写 `artifact_quality/reason/evidence` 的同时写：

```json
"artifact_manifest": {
  "received": true, "source": "node_zip", "quality": "invalid",
  "reason": "unreadable", "entry_count": 0, "readable": false,
  "has_encrypted": false, "inspected_at": "...", "trace_id": "..."
}
```

这样客户面板只拿任务行也能判 S7 成功（避免 N+1 查窄表）。成功写入时用 `- 'evidence_error'` 作废旧失败陈述。

### 4. 证据失败陈述端点

`POST /tasks/{id}/evidence-error`（`X-Evidence-Ticket` 鉴权，同数据面）：

```json
{"kind": "artifact-manifest", "error": "证据上报 HTTP 404: ..."}
```

只写事实；已收到成功清单的任务拒绝写入（旧失败不得覆盖新成功）。

### 5. 节点侧读取

```go
// 512 KiB 先试；中央目录更大时退到 16 MiB
raw, stderr, code, err := s.runQuickCommandBytes(ctx, "tail -c <window> <path>")
manifest, err := fillManifestFromZipTail(raw, size, path)   // zip.NewReader(tailReaderAt, size)
```

- `tailReaderAt` 只暴露尾部窗口，`zip.NewReader` 读 EOCD / 中央目录即可完成解析。
- 加密包依然可读（`-Z1` 与 `zipinfo -t` 的时代结束）：`has_encrypted` 如实上报。
- 失败时 `evidence` 带 `exit_code`、`stderr`、`tail_window_bytes`，不再是一句无信息的「读取不可用」。

### 6. 前端终态对账

```ts
EVIDENCE_WAIT_WINDOW_MS = 120_000
EVIDENCE_WAIT_POLL_INTERVAL = 10_000
```

`evidenceStillPending()` 依据服务端派生结果（`delivery_status=delivered` 且 S7 非 success/skipped、且终态时间在窗口内）决定间隔；窗口外回落 30s。

## 决策依据 (WHY)

| 决策 | 备选 | 理由 |
|---|---|---|
| S7 回传成功即成功 | 要求 entry_count>0 | 加密包/极简宿主机下内容永远可能不可读；把两件事混在一起会让「链路正常」也被判失败 |
| 场景名称快照进 detail | 前端按 ID 查字典 | 场景改名/删除后历史不可解释；快照是唯一能回到「当时」的证据 |
| 失败只认显式陈述 | 继续用 quality 猜 | 「没收到」与「传失败」必须可区分，否则归因码永远误导排查方向 |
| 尾窗 + Go 解析 | 继续用 unzip/zipinfo | 宿主机极简（无 base64 先例）+ 全条目加密，两条命令都不可靠 |
| 前端窗口内加密对账 | 后端在派生时等待 | 派生必须在毫秒级完成；等待只能是展示层的重试节奏 |

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| 超大包中央目录超过 16 MiB | 内容不可读 | 低 | evidence 记录窗口大小与失败原因；S7 仍可成功 |
| `tail -c` 在个别 busybox 不支持 | 读取失败 | 低 | 失败带 exit code/stderr，可直接定位；不阻塞采集与交付 |
| 证据窗口 120s 内仍未到达 | 显示未知而非失败 | 中 | 桥上报失败时走 evidence_error，变成明确失败 |
| 场景快照字段增多 | detail 体积 | 低 | 仅 7 个标量字段 |
| 老任务无快照 | 仍显示 modules 文案 | 确定 | 属事实正确：历史记录未保存用户语义，不能伪造 |
