# 日志采集失败终态与节点完成态之间的交付死锁

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：定位 `failed` 终态 + 节点 `completed` 被误映射为 `patch_completed`，导致 409 无限重试、289 MiB 日志包永远交付不出去；改为走合法边接管续交付，并补 4xx 写库熔断与平台侧错误码回写 | 无独立任务文档 |

## 一、现场事实（工单 Q2026102701294，staging，2026-10-27）

三份证据互相独立：平台数据库、case-service 访问日志、节点侧 bridge 本地日志（用户导出）。

| 时间（UTC） | 来源 | 事件 |
|---|---|---|
| 07:48:52 | `log_collect_task` | 任务 `26c119b8-1daa-483c-8428-15aa00ce7107` 创建，节点 `10.250.0.7` |
| 07:48:56 | bridge `d45af234` | `log_collect.create` 成功 |
| 07:48:57 ~ 07:52:55 | bridge | `progress` 连续回传，百分比递增至 85% |
| **07:53:04** | `log_collect_task` | **平台写 `failed`**，`error_message="Request failed with status code 500"`，`error_code=NULL` |
| **07:53:06.811** | bridge | **节点侧 `completed`**，`archive_path=/sf/data/local/acli/tmp/data/log_collect/Q2026102701294.zip`，`archive_bytes=302845641`（289 MiB） |
| 08:12 ~ 09:20 | 后端访问日志 | `PATCH /api/log-collect/tasks/26c119b8...` 每 ~30 秒一次，全部 `409 LC-PLATFORM-003 非法状态转换：failed → completed`（20 分钟 16 次量级） |
| 09:17:18 ~ 09:20:07 | bridge `b951e203`（新构建 `f2631377`） | `probe` / `progress` 全部成功，节点仍稳定报 `completed`；平台侧 409 循环照旧 |

两条关键判据：

1. **平台失败早于节点完成**（07:53:04 < 07:53:06.811）。所以这次 `failed` **不是**上传/交付失败，而是采集等待期内的某次平台 HTTP 调用异常。上一轮"上传 500"的推断在此被现场证据推翻——当时节点还没出包，平台根本没有上传请求。
2. **物证在节点、状态在平台，二者永久背离**：289 MiB 的包实实在在躺在节点磁盘上，平台却因终态不可复活而无法交付，也没有任何合法出口。

## 二、根因

| # | 根因 | 代码位置 |
|---|---|---|
| R1 | 对账矩阵把「平台 `failed`/`cancelled` + 节点 `completed`」映射成 `patch_completed`，而后端状态机里 `failed` 的唯一合法出口是 `→ collecting`（接管）。这是**确定性冲突**，不是竞态：无论重试多少次都必然 409 | `frontend/customer/src/services/logCollectSync.ts` `decideNodeSync` |
| R2 | 对账没有 4xx 熔断。`catch` 只弹一条 warning，30 秒后照旧重发同一请求 → 日志刷屏，且**永不推进交付** | `LogCollectPanel.vue` `syncNodeState` `applyPatches` |
| R3 | 失败落库只写 axios 原文，丢掉拦截器已提取的结构化 `problem.code` → `error_code` 恒为 NULL，事后无法回答"500 是谁发的" | `LogCollectPanel.vue` `handleStart` catch |

R1 的语义错误值得单独说明：把 `failed` 硬改成 `completed` 是**撒谎**——平台侧根本没有产物（`archive_path` 为空、`upload_mode` 为空、`relay_status=none`）。正确动作是承认节点真相，走合法边回到 `collecting` 后立刻按 `completed` 收尾，再继续交付；这条边后端早已提供，只是前端从未走。

## 三、改动

| 文件 | 改动 |
|---|---|
| `frontend/customer/src/services/logCollectSync.ts` | ① `failed`/`cancelled` + 节点 `completed` + **包仍在** → `adopt`（`adoptMode='deliver'`），不再 `patch_completed`；② 节点 `completed` 但包已被移除 → `none` + 「重新采集」提示，不写库、不产生 409；③ `SyncAction` 新增 `adoptMode`，`buildSyncNotice` 区分「接管继续」与「继续交付」 |
| `frontend/customer/src/components/LogCollectPanel.vue` | ① 接管按钮按 `adoptMode` 显示「继续交付」；② 新增 `syncPatchBlocked`：任何 4xx 立即停止自动写库，并 `getTask` 回拉真实状态；用户显式接管/纠偏/重新采集时解除；③ `platformErrorCode()` 把 `error.problem.code` 随 `patch failed` 落库 |
| `frontend/customer/src/services/__tests__/logCollectSync.spec.ts` | 新增 2 条回归护栏：`failed+completed+有包` 必须 `adopt` 且不等于 `patch_completed`；`failed+completed+无包` 必须 `none` |
| `frontend/customer/src/components/LogCollectPanel.vue` | 顺带修 #1311 引入的 TS2345：`sendAction` 的联合类型含 `delivery_*`，传给 `buildLogCollectMessage` 前需显式收窄（既有缺陷，`vue-tsc -b` 会红） |

## 四、刻意不做的事

- **不放宽后端状态机**（不新增 `failed → completed`、也不新增 `failed → uploading`）。`failed` 是终态这一约束本身是对的，它防止"采集没成功却被标成完成"；本案缺的不是这条边，而是调用方没走已有那条边。
- **不为这次 500 编造结论**。07:53:04 那次异常的确切来源**无法从现网回溯**：Loki 只采集 `hci-observability`（staging 应用日志不入库），当事 Pod 已因 PVC `Recreate` 策略轮换，`error_code` 又为空。R3 修复后同类问题下次会直接带 `LC-*` 码落库，届时可定因。

## 五、遗留（独立缺陷，不在本 PR）

| # | 问题 | 影响 |
|---|---|---|
| L1 | bridge 日志直传 `x509: certificate signed by unknown authority`：`log_upload.failed` 每 30 秒重试一次，`queued` 从 7 单调涨到 58，**只增不减** | 桥日志永远到不了云端，本次排查完全依赖用户手工导出本地文件 |
| L2 | 上传队列无上限、无落盘兜底，TLS 失败时静默堆积 | 长时间运行会持续占用内存且无任何可见告警 |
