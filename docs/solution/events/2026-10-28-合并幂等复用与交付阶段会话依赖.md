# 合并成品幂等复用，交付重试不再被 SSH 断连否决

## 一、范围说明（与 #1339 / #1342 的关系）

同一现场（Q2026102800720，3.6 GiB P2 交付失败）共暴露三族缺陷，处理关系如下：

| 缺陷 | 修复位置 |
|---|---|
| complete 把分钟级合并跨在 DB 事务里，被 30s 空闲超时杀掉 | **#1339 已修**（merge 前显式结束只读事务） |
| 落库后立即提交，消除代传触发的行锁自死锁 | **#1342 已修** |
| 重试每次重写整包（3.6 GiB × 4 次，白写） | **本 PR** |
| 上传/收尾阶段被 SSH 断连判 `needs_reauth` | **本 PR** |

## 二、缺陷 1：重试重写整包

**第一性原理**：complete 失败后的重试，其物理输入（110 个分片 + 一次成功合并的成品）没有任何变化；变化只在「元数据写库」这最后一步。重试却从合并开始重跑，等于把 3.6 GiB 重写 4 遍——峰值磁盘翻倍、每次又都超过 30s，重试注定原地打转。

**修复**（`log_collect_storage.py`）：

- 合并成功（原子 `os.replace` 之后）立即在 `meta.json` 写 `merged = {size, sha256}`；
- 重试进入 merge 时，若成品仍在且大小与 marker 一致，直接复用 `(size, sha256, object_key)`，不重写、也不重算 SHA-256（20 GiB 重算与重合并同价，复用就失去意义）；
- marker 的生命周期止于 `delete_multipart`：成功收尾会连 meta.json 一起删除，不会泄漏到下一次会话。

**对抗性审查**：

- *复用会不会用到坏对象？* marker 只在 rename 成功后写入，复用前校验大小；大小不符即回落到完整合并。分片与成品在目录上分离，半成品只可能是 `.tmp`（rename 前已清理）。
- *marker 被手工篡改？* 平台对象目录 fsGroup 受限；且 marker 只能「跳过重写」，最终一致性和 sha256 校验仍由 complete 的声明校验兜底。

## 三、缺陷 2：交付重试被 SSH 断连否决

**第一性原理**：交付四段链路（节点 → 客户机 → 平台 → 5888）中，「上传 / 收尾」两段的输入是**已完整落盘的本地副本**，全程不碰 HCI。把会话要求一刀切套在所有阶段，等于让「节点连接掉了」去否决一件与节点无关的事。

现场正是这条错误绑定收尾：平台收尾连续 4 次 500 的几分钟里 SSH 会话被回收，第 5 次重试在 `phaseUploading` 被当成凭据失效判死——而当时 110/110 片已在平台、本地副本完整。

**修复**（`delivery_runner.go`）：

- 新增 `deliveryPhaseNeedsNode`：仅 `waiting_collect` / `pulling` 需要节点；
- `requireSessionForPhase` 只在真需要节点时把「无会话」判为 `needs_reauth`；
- 上传/收尾阶段会话缺失时继续推进：本地副本缺失会得到普通失败（可重试/可诊断），不再伪装成「请重新认证」。

**对抗性审查**：

- *放宽会不会把半截包搬走？* 不会。包完整性仍由 `waiting_collect` / `pulling` 阶段的 EOCD 校验把关；上传阶段的输入是已校验的本地副本。
- *SSH 掉线靠 #1339 的保活是否已够？* 保活降低概率，但浏览器关闭、bridge 重启、租约回收仍可能回收会话。阶段判定是**本质修复**：让状态机不再依赖它不需要的资源。

## 四、验证

- `test_log_collect_upload.py::test_complete_retry_reuses_merged_object`：第一次 complete 在 flush 失败，重试后成品 mtime 不变、结果正确；
- `terminal_bridge/delivery_session_test.go`：锁住「阶段 × 会话」依赖矩阵；
- case-service 全量单测、terminal_bridge `go test ./...`、ruff 全绿。

## 五、运维备注

- 已交付任务可能残留整包大小的 `multipart/<task_id>/` 临时分片（失败重试期间未走到 delete_multipart）；确认 `delivery_status=delivered` 后可人工清理释放空间。
