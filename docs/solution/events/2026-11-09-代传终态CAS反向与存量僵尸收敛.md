# 代传终态 CAS 反向与存量僵尸收敛

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-09 |
| 版本 | v1.0 |
| 类型 | 缺陷修复（服务端状态机） |
| 影响面 | case-service 代传终态收敛、reconcile 周期接管、staging 12 条历史记录 |

## 一、现象

staging 实库中 12 条任务长期满足 delivery_status=delivered、relay_status=running、
relay_chunk_index=relay_chunk_total-1。日志每轮打印 terminal_converged status=success，
但分片不再推进也不报错；reconcile_relays_loop 每 60 秒把它们重新捞起，形成永久空转。

## 二、根因

LogCollectRelayService._finish 的 CAS 条件加在了错误分支：

    if not error:                       # 成功收敛
        stmt = stmt.where(delivery_status != delivered)

成功收敛本身就是写入 delivered 的那次 UPDATE。第二次执行（发布后 reconcile 重跑、
补交付、旧代 relay 再次确认成功）WHERE 已不成立，整条 UPDATE 被过滤，
relay_status 永远写不成 success。

而注释声明的保护目标是「旧代 relay 迟到的失败回写不得把已交付改回去」，
失败分支反倒没有 CAS，方向正好相反。

## 三、修复

| 位置 | 改动 |
|---|---|
| _finish | CAS 改由 status != success 判定：成功终态幂等无条件写；只有失败回写被挡住 |
| claim_stale | 增加 delivery_status != delivered：已交付不得再拉起整包上传 |
| reconcile_relays_once | 抢占前先调用 settle_delivered_relays() |

新增 settle_delivered_relays()：把 (delivered 且 running/pending) 一次性收敛为
relay_status=success、status=completed、progress=100，finished_at 用 coalesce 保留原值。
修正后的 _finish 只防新增，存量 12 条由启动时与每轮 reconcile 自动订正，不引入人工 SQL。

## 四、验证

- 新增 4 条单测：成功收敛不被已交付挡住、失败回写仍受 CAS 保护、
  抢占跳过已交付、存量订正写入终态；启动接管用例 mock 同步补齐；
- pytest tests/unit/test_log_collect_relay.py：51 passed；
- pytest tests/unit（排除本地缺 zstandard 的 test_dsh_diagnosis_ingest.py）：289 passed。

## 五、上线后观测

    select count(*) from log_collect_task
    where delivery_status=delivered and relay_status in (running,pending);
    -- 期望 0

部署后首个 reconcile 周期内 12 条应变为 success，周期性 terminal_converged 日志消失。
