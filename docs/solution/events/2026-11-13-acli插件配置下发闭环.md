# acli 插件配置下发闭环方案

## 背景与需求

管理台「工具管理」下新增「acli插件」子页面（位于「agent工具」左侧，原「工具注册表 / 工具管理」统一改名「agent工具」）。页面要维护 acli 手工插件所需的全部关键信息，并在保存/更新后经 terminal_bridge 自动下发到客户 HCI，使插件落盘、注册、补全并真实生效；首个插件参考《[HCI-V1] 1mt 排障工具使用方法》实现只读巡检。

## 方案

- **运行时契约**：沿用 24 环境实测的 acli 方案 B（直接落盘 + 注册）。`acli plugin install` 因 `.aclix` 签名与 `/support/tmp` 门禁不可行；手工插件只依赖四要素：`<name>/plugin`（wrapper）、原始脚本、`<name>/manifest.json`（逐文件 SHA-256）、`plugin_register.json` 注册项，以及可选的 Tab 补全。
- **平台事实源**：新增 `acli_plugin`（插件定义）与 `acli_plugin_deployment`（下发回执）。DDL 同步落在 `database/desired_schema.sql` 与两份 Helm `postgres-init-configmap.yaml`。SSH 口令只在页面 `ssh_connect` 时输入（前缀语义或免密私钥），不落库。
- **Builder**：由插件配置确定性地生成 wrapper、manifest、注册项、附加文件与 `spec_hash`；生成原子部署脚本，经 `flock` 互斥 → 备份 → 写文件并逐文件 sha256 自证 → `jq` 临时文件 + `mv` 原子替换注册表 → 补全追加 → `acli plugin list` / `--help` / 冒烟命令验证，任一环节失败自动回滚。HCI 定制系统无 `base64`/`python3`，落盘统一用 shell 内建 `printf '%b'`，不依赖外部解码器。
- **下发通道**：复用 terminal_bridge 的 `bridge_hello` → `ssh_connect` → `ssh_exec_process` 隔离通道，按 `exec_id` 收 `exec_result`；`deploy_id` / `trace_id` / `exec_id` 贯穿页面日志、bridge 日志与数据库回执。
- **配置更新**：页面编辑后保存即自动重新下发；`spec_hash` 覆盖规范化 spec 与全部文件字节，用于幂等与漂移检测。历史回执在页面可查。

## 端到端验证（2026-11-13）

链路：admin-ui 页面 → descriptor → terminal_bridge WS → 24 环境 HCI → `exec_result` → 回执落库 → 页面「已生效」。

- 页面：从参考模板创建 `hci_1mt_check`，并验证编辑版本后重新保存下发（动态更新）。
- bridge：按换版规范使用 `v2.36.0-14-gcec78f5a-dirty`，免密私钥认证，收到 `bridge_hello` / `ssh_connected`。
- HCI：`acli --formatter json plugin list` 显示 `hci_1mt_check v0.0.1 第三方包 开启`；注册表 `built_in=false`；补全已追加；`acli --timeout 60 hci_1mt_check -m env -c cpu_load` 输出负载、运行时长与「巡检完成」。
- 回执：`exit=0`、设备侧 `ACP_RESULT status=success`；数据库 `last_deploy_status=success`，`acli_plugin_deployment` 记录 `status=success / exit_code=0`；bridge 日志 `EXEC_ISOLATED_START → exec.request → exec.start → exec.done` 与 `trace_id` 对齐。
- 证据：`.local/bridge-monitor/acli_plugin_e2e_result.json`、同名截图与 `.local/session-24-acli-plugin/`（均为本地 `.local/` 产物，不入库）。

## 部署前提与已知边界

- 本机 dev 环境的 K3s Pod 以非 root 只读运行且 ArgoCD `selfHeal=true`，验证阶段使用「新构建 admin-ui dist + 本机联调网关 + 容器内临时承载同一份后端模块 + 常驻 bridge」的联调栈；平台原生 `/admin/` 生效需要 CI 构建镜像并由 ArgoCD 同步。
- dev 的定时 `db-migrate` Job 会按镜像内的 `desired_schema.sql` 收敛 Schema；镜像带上本 PR 的新表后不再出现「新表被清理」的漂移。
- 联调栈是临时进程，Pod 重建后即失效；在新镜像同步完成后须在原生页面重跑一次页面级端到端以完成最终闭环。
