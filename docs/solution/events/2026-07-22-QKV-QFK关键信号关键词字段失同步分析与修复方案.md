# QKV / QFK 关键信号关键词字段失同步问题分析与修复方案

> 本文档基于工单 `Q2026072257185`、KBD `27123`（support_id=27123，库内 id=1）的真实现场排查产出。
> **当前状态：方案待评审，尚未实施。** 文末"实施任务清单"仅在用户确认后执行。

## 背景与需求

用户在 KBD 27123 中把 qkv_task 信号的关键词从 `启动虚拟机失败` 改为 `启动虚拟机`，预期 agent 下次诊断执行：

```
acli --formatter json task get -k '启动虚拟机' -s failed -l 100
```

实际回采（`bridge_execution_logs`，`created_at=2026-07-22 10:02:31`，**晚于编辑时间 09:50**）执行的是：

```
acli --formatter json task get -k '启动虚拟机失败' -l 100
```

即：(a) 关键词仍是旧值；(b) 没有 `-s failed`。用户质疑"修改根本没生效 / agent 用了老信号"。

本次需求：对 qkv / qfk 两类关键信号做**前后端全面分析**，定位问题根因、影响范围，并给出解决方案。

## 问题现象（两层）

1. **关键词失同步（编辑不生效）**：前端改了关键词，agent 运行时仍用旧关键词。
2. **`-s failed` 丢缺失**：qkv_task 的 `status="failed"` 没有被转成命令里的 `-s failed`。

注意这两层是**独立的缺陷**：第 1 层影响所有信号类型；第 2 层仅 `qkv_task` 暴露（只有 TASK 查询才会拼 `-s failed`）。

## 全面分析（前端 + 后端）

### 一、数据模型：一条信号里存在多个"关键词"字段

`kbd_entry.signals_json` 是信号数组。实测两类信号结构如下（均来自本环境库）：

**QKV 信号（qkv_task / qkv_alert / qkv_dialog）**

```json
{
  "id": "s1",
  "acquirer": "qkv_task",
  "keyword": "启动虚拟机",                       // ← 顶层（前端编辑器实际改的字段）
  "acquirer_args": {                             // ← agent 实际读取的参数袋
    "limit": 100,
    "status": "failed",                          // ← 有 status，但没有 is_failed
    "keyword": "启动虚拟机失败"                  // ← agent 读这里（旧值，没被编辑改动）
  },
  "produces": ["qkv_task_result"]
}
```

**QFK 信号（qfk_log / qfk_system / qfk_service / qfk_vm / ...）**

```json
{
  "id": "s2",
  "acquirer": "qfk_log",
  "keyword": "绑定vgpu命令失败",                 // ← 顶层（镜像）
  "matcher": { "type": "keyword", "pattern": "绑定vgpu命令失败", "mode": "contains" }, // ← agent 读这里
  "acquirer_args": { "keyword": "vgpu", "resource": "{{HOST}}" }  // ← 注意：这是"日志资源/主题"，语义完全不同
}
```

**核心观察**：一个信号里至少有 2~3 个"疑似关键词"的字段，但**只有一个**是 agent 实际读取的权威源，其余是镜像或异义字段。

### 三、前端编辑 / 保存路径：只写顶层 `keyword`

`admin/src/views/KbdReviewView.vue`：

- 接口 `KeySignal`（行 44-58）包含 `keyword`、`acquirer_args`、`matcher` 三个字段。
- 展示：qkv 卡片显示 `item.sig.keyword`（行 1551），qfk 卡片显示 `item.sig.keyword`（行 1598）。
- **编辑输入**：qkv（行 1556）与 qfk（行 1633）都只绑定 `v-model="signalEditDraft.keyword"`（**顶层**）。
- `startEditSignal`（行 608-634）：对原信号做深拷贝进 draft，并 `if (!draft.keyword && draft.keywords) draft.keyword = draft.keywords` 做归一化；**不触碰 `acquirer_args.keyword` 也不触碰 `matcher.pattern`**。
- `saveSignalEdit`（行 641-651）：

### 四、持久化与抽取路径：放大风险

- `admin.py:1670-1672`（`update_kbd_entry`）：直接 `signals_json = :signals_json::jsonb` 整块落库，前端发什么存什么 → 前端的失同步被**忠实地固化进数据库**。
- `extract_signals.py:384-392`（`_persist_signals`）：整体覆盖 `signals_json`；抽取输入仅为叙述性字段（title/problem_description/alert_info/steps_text）。→ 若对条目**重新抽取信号**，会用原始正文重新生成，把人工改过的 signals 整体覆盖回旧值。
- `parser.py:286`（qkv TASK）：抽取只写 `status`（来自 item.status/process），**不写 `is_failed`**。→ 与 agent 只读 `is_failed` 形成第二层失配，导致 `-s failed` 永远缺失（即便未编辑也存在）。

### 五、初始为何一致、编辑后为何失同步

LLM 抽取时把顶层 `keyword` 与 `acquirer_args.keyword` / `matcher.pattern` **一并写齐且一致**，所以"刚抽完"的信号是好的。问题只发生在**人工通过 UI 改关键词**之后：UI 只动顶层，嵌套/匹配字段纹丝不动，agent 读嵌套 → 用旧值。这解释了为什么"一改就坏"。

## 根因结论

1. **缺少单一事实来源（SSOT）**：一个"查询关键词"概念被存成多个字段（qkv：顶层 + `acquirer_args.keyword`；qfk：顶层 + `matcher.pattern` + 异义的 `acquirer_args.keyword`），写方（前端）与读方（后端 qkv/qfk）对"哪个是权威"理解互相矛盾。
2. **前端只暴露顶层 `keyword` 可编辑**，后端却读嵌套/匹配字段 → 任何人工编辑都必然产生失同步，且被整块落库固化。
3. **`is_failed` / `status` 双字段失配（qkv_task 专属）**：抽取写 `status`、agent 读 `is_failed`（缺位即 False）→ `-s failed` 永不拼出。
4. **重抽取/重入库整体覆盖 signals_json**（从原始叙述字段再生）→ 人工编辑有被静默回滚的风险。
5. **命名过载**：qfk 把"日志资源/主题"也叫 `acquirer_args.keyword`，与"匹配关键词"同名，加剧混乱。

## 影响范围

| 信号类型 | 关键词失同步（编辑不生效） | `-s failed` 缺失 |
|---|---|---|
| `qkv_alert` | ✅ 是（读 `acquirer_args.keyword`，UI 只写顶层） | 无（alert 无 `-s failed`） |
| `qkv_task` | ✅ 是 | ✅ 是（`is_failed`/`status` 失配） |
| `qkv_dialog` | ✅ 是 | 无（dialog 无 `-s failed`） |
| `qfk_log/system/service/vm/network/storage/hardware/platform` | ✅ 是（读 `matcher.pattern`，UI 只写顶层） | 无（qfk 无此 flag），但存在 `acquirer_args.keyword` 语义混淆 |
| 其他（刚 LLM 抽取、未人工编辑） | ❌ 暂未失同步 | ❌（但 qkv_task 的 `-s failed` 仍缺失，属第 3 点） |

**结论：不是只有 `qkv_task`。"编辑关键词不生效"是 qkv 全家族 + qfk 全家族的系统性问题；`-s failed` 缺失是 `qkv_task` 独有症状。**

## 解决方案（WHAT + WHY）

### 方案 A：删除重复字段，确立唯一权威源（修订：直接删，不"降级保留"）

> 修订说明：原稿写"顶层 keyword 降级为派生镜像"。经排查，存储态顶层 `keyword` 的实际读取方只有 4 处——前端展示（`KbdReviewView.vue:1551` qkv / `:1598` qfk）、前端编辑绑定（`:1556` / `:1633`）、后端 `from_dict` 备用路径（`qkv/signal.py:85` qkv / `qfk/signal.py:92` qfk）。**运行时 agent 路径（`_signal_to_qkv`→`FrontendSignal.keyword`、`_signal_to_qfk`→`BackendSignal.keyword`）并不读存储态顶层 `keyword`，而是读 `acquirer_args.keyword` / `matcher.pattern`；生产 SQL 也无 `s->>'keyword'` 查询。** 因此顶层 `keyword` 是纯死字段，应**直接删除**而非保留为镜像——删字段比留镜像更彻底（无同步机制、无同名混淆、字段面更小）。

- **QKV**：唯一权威 = `acquirer_args.keyword`。**直接删除存储态顶层 `keyword`。**
  - 前端展示（`:1551`）改读 `item.sig.acquirer_args.keyword`；编辑绑定（`:1556`）改写 `acquirer_args.keyword`。
  - `from_dict`/`qkv_load`（`signal.py:85`、`engine.py:64`）统一读 `acquirer_args.keyword`，与 agent 路径一致。
  - 抽取管线（`extract_signals`）只写 `acquirer_args.keyword`，不再写顶层 `keyword`。
  - 存量迁移：对所有 `signals_json` 元素删除顶层 `keyword` 键。
- **QFK**：唯一权威 = `matcher.pattern`（匹配关键词）；模型字段 `BackendSignal.keyword`（list）由它喂入，保留。
  - **删除存储态顶层 `keyword`**（它是 `matcher.pattern` 的镜像）。
  - 前端展示（`:1598`）/编辑绑定（`:1633`）改读/写 `matcher.pattern`。
  - `BackendSignal.from_dict`（`qfk/signal.py:92`）改从 `matcher.pattern` 取关键词，而非顶层 `keyword`。
  - 抽取管线只写 `matcher.pattern`。
  - **`acquirer_args.keyword`（值如 `"vgpu"`，是资源/主题过滤）并非冗余字段，而是"异义同名"字段 → 重命名为 `acquirer_args.resource_keyword`**（并同步读取处），彻底消除"关键词"同名重载。

> WHY：删字段比留镜像更彻底——无同步机制、无同名混淆、字段面更小；唯一需补的是把极少数读取方（前端展示/编辑、`from_dict`）指向权威源，并做一次存量字段清理。 rename 资源字段则是为了消除"同名不同义"的隐患。

### 方案 B：`is_failed` 多源判定（QKV task）

```python
raw = args.get("is_failed", None)
is_failed = bool(raw) if raw is not None else (
    str(args.get("status", "")).lower() == "failed"
    or "失败" in str(keyword)
)
```

- 同步：抽取器（`parser.py`）对 TASK 显式写 `is_failed`；或前端为 qkv_task 暴露 `is_failed` 开关。
> WHY：让 `status`、关键词文本里的"失败"都能正确驱动 `-s failed`，不再因字段名不一致而静默丢过滤条件。

### 方案 C：前端编辑器必须读写"agent 实际读取的字段"

- qkv 关键词输入绑定 `signalEditDraft.acquirer_args.keyword`（**删顶层 `keyword` 后不再有镜像可写**，UI 直接改权威源）。
- qfk 关键词输入绑定 `signalEditDraft.matcher.pattern`（删顶层 `keyword` 后，UI 直接改 `matcher.pattern`）。
> WHY：编辑器必须写入 agent 读取的字段，否则编辑永远不生效。删掉顶层死字段后，"误改镜像"的物理可能也被一并消除（见附录三）。

### 方案 D：防止重抽取覆盖人工编辑

- 为信号增加 `manual_edited` 标记 / 版本号；重新抽取信号时，**不覆盖人工编辑过的信号**，或要求显式确认。
> WHY：避免"改了又被抽回旧值"的静默回滚（本次已观察到 raw 正文仍含旧关键词，重抽必回滚）。

### 方案 E：不变量与测试

- 保存时断言：qkv 信号不得再出现顶层 `keyword` 键；qfk 信号 `matcher.pattern` 必存在且 `acquirer_args.resource_keyword`（改名后）与匹配关键词语义隔离；`is_failed` 与 `status` 同向（`status=="failed"` ⇒ `is_failed` 必为 true，否则报错而非静默通过）。
- 单元测试：设 `acquirer_args.keyword` → 命令含该关键词；`status=="failed"` 或关键词含"失败" → 命令含 `-s failed`；`matcher.pattern` 变更后命令随之变更。

### 方案 F：存量数据迁移（一次性）

- 对所有 `kbd_entry.signals_json` 元素：删除顶层 `keyword` 键（qkv/qfk 均删）；将 qfk 的 `acquirer_args.keyword`（资源/主题）重命名为 `acquirer_args.resource_keyword`；对 qkv_task 且 `status=="failed"` 补 `is_failed=true`。
- 本次已对 KBD 27123（id=1）将 `acquirer_args.keyword` 修正为 `启动虚拟机`、`acquirer_args.is_failed` 置 `true`；删除其顶层 `keyword` 后不会回退（因权威源已正确），且不再有"改名=新增"式并存。

## 附录三：字段必要性审计与理想数据模型（第一性原理）

> 本附录将上文"第一性原理分析"沉淀为可评审的文档：含直接结论、职责拆分、字段膨胀机制、逐字段必要性判定、必要/不必要/异义 分类、理想数据模型，以及"增量 vs 重构"的实施策略判断。

### 一、直接结论

- **两个信号 JSON 作为"扁平大表"都不合理**：真正必需的执行字段很少；当前 20+ 字段中，一部分必要但被错误压平混排，另一部分是**死字段 / 冗余副本 / 异义同名**，属演化债。
- **字段并非都必要**：约 1/3 是可删或可改名的（顶层 `keyword`、`status`、qfk 的 `keyword` 同名坑、若干疑似未消费字段）；真正驱动执行的只占少数，且本应按职责分层。

### 二、第一性原理：一个信号对象承载了 5 种有界上下文

按"单一职责 / 有界上下文"原则，一条信号被 5 类消费者使用，本应各有字段边界：

| # | 职责（有界上下文） | 字段 | 消费者 | 是否进执行路径 |
|---|---|---|---|---|
| ① | 采集契约 | `acquirer` + `acquirer_args` | qkv/qfk 工具 | ✅ |
| ② | 触发契约 | `matcher`（qfk） | 差分引擎 | ✅ |
| ③ | 编排/依赖 | `produces` `requires` `phase` `action` `target` `container` `timeout` | 差分引擎 | ✅ |
| ④ | 来源与质量 | `signal_category` `confidence` `source_section` `extraction_method` `risk` | 抽取评分、前后端分流 | ❌ 仅评分/路由 |
| ⑤ | 审核/工作流 | `needs_review` `require_human_confirm` `expected` | UI、运行时闸门 | ❌ 仅门控 |

**根本问题**：这 5 类职责被摊平进同一个 dict，无嵌套隔离。于是"执行该信什么"和"谁抽的/质量多高/要不要人确认"混在一起，任一消费者加字段都直接污染全局。

### 三、为什么字段这么多（机制，而非设计）

无 schema owner，每个子系统按需往同一张表塞字段：
1. **LLM 抽取器**加 provenance：`extraction_method` / `source_section` / `confidence` / `risk`（评分用；证据 `extract_signals.py:172,185` 读 `source_section`、`confidence`）。
2. **UI 编辑器**加 review 态：`needs_review` / `require_human_confirm`（证据 `kbd_differential.py:86`、`extract_signals.py:222` 读 `require_human_confirm`）。
3. **差分引擎**加编排：`phase` / `action` / `produces` / `requires` / `container`（证据 `kbd_differential.py:88,848,997`、`parser.py:267`）。
4. **qfk 引入** `matcher` 触发语义，但顶层 `keyword` 没删，形成副本。
5. **手动编辑**又强化顶层 `keyword` 作"显示字段"。

每步局部合理，合起来即"无人统管的大扁平表"——典型**偶然复杂度（accidental complexity）**。

### 四、逐字段必要性判定（基于真实代码读取证据）

**QKV（qkv_task）**

| 字段 | 后端是否读取 | 判定 |
|---|---|---|
| `acquirer` `acquirer_args.keyword` `limit` `is_failed` | ✅ 执行路径 | **必要**（执行契约①） |
| `produces` `requires` `phase` `action` `target` `container` | ✅ `kbd_differential`/`parser`/`executor` | **必要**（编排/执行③） |
| `signal_category` `confidence` `source_section` | ✅ 分流/评分 | **必要但属④**，应与执行字段隔离 |
| `require_human_confirm` | ✅ 闸门 | **必要（⑤）** |
| `description` `instruction` | ✅ 解析/展示 | 必要（人类可读） |
| `risk` `extraction_method` `expected` `match_mode` `needs_review` `timeout` | ❌ 后端未检索到读取 | **疑似死/未消费**（不进执行路径，需二次确认） |
| 顶层 `keyword` | ❌ agent 不读 | **不必要，删** |
| `acquirer_args.status` | ❌ agent 不读 | **不必要，删**（由 `is_failed` 派生） |

**QFK（qfk_log）**

| 字段 | 判定 |
|---|---|
| `matcher.{type,pattern,mode,expected}` | **必要**，且 `pattern` 是关键词唯一权威源（②） |
| `acquirer_args.resource` | **必要**（资源定位） |
| 顶层 `keyword` | **不必要，删**（= `matcher.pattern` 副本） |
| `acquirer_args.keyword`（值 `"vgpu"`） | **异义同名**：资源/主题非匹配关键词 → 不删，**重命名 `resource_keyword`** |

### 五、必要 / 不必要 / 异义 一句话总结

- **必要且正确**：①采集契约、②触发契约、③编排字段、④ provenance（应隔离）、⑤ review 闸门。
- **不必要（应删）**：顶层 `keyword`（死副本）、`acquirer_args.status`（死字段）、以及若干疑似未消费字段（`risk`/`extraction_method`/`expected`/`match_mode`/`needs_review`/`timeout`，需二次确认，但不进执行路径）。
- **异义同名（应重命名非删）**：qfk 的 `acquirer_args.keyword` → `resource_keyword`。

### 六、第一性原理的理想数据模型

按"每个概念只存在一次、按职责嵌套"重构，而非继续摊平：

```jsonc
{
  "id": "s1",
  "acquire": {                                    // ① 采集契约（唯一权威）
    "tool": "qkv_task",
    "args": { "keyword": "启动虚拟机", "limit": 100, "is_failed": true, "status": "failed" }
  },
  "match": { "type": "keyword", "pattern": "绑定vgpu命令失败", "mode": "any" },  // ② qfk 触发（关键词唯一权威）
  "orchestrate": { "phase": "diagnostic", "action": "status", "produces": [...], "requires": [...], "container": "asv-con", "target": {} },  // ③
  "provenance": { "category": "backend", "method": "llm_field_level_v1", "source_section": "steps_text", "confidence": 0.85, "risk": 1 },  // ④ 隔离
  "review": { "require_human_confirm": false, "needs_review": false }            // ⑤ 隔离
}
```

收益（第一性原理）：
- **关键词 SSOT**：qkv 只在 `acquire.args.keyword`、qfk 只在 `match.pattern`，顶层副本彻底消失 → "改了不生效"结构性消失。
- **失败标志唯一**：`is_failed` 是唯一开关，`status` 删除或由其派生 → `-s failed` 永不丢。
- **职责隔离**：执行路径只读 `acquire`/`match`/`orchestrate`；评分只读 `provenance`；闸门只读 `review` → 改 UI/评分不会污染执行。

### 七、实施策略判断：增量优化 vs 嵌套重构

> 结论：**本次缺陷修复采用"在现有扁平结构上的增量优化"，不混入嵌套重构。** 嵌套理想模型作为独立的后续 RFC/重构任务跟踪。

| 维度 | 增量优化（本次采用） | 嵌套重构（理想形态） |
|---|---|---|
| 能否根除本次事故 | ✅ 能（删死字段+统一权威源+`is_failed` 多源） | ✅ 能 |
| 改动面 | 小（删/改名几个字段 + 统一读取点） | 大（全量 `signals_json` 迁移 + 所有读取方改写） |
| 回滚风险 | 低 | 高（涉及库结构迁移） |
| 是否解决"扁平混排"结构债 | ❌ 未解决（仅消除事故相关字段） | ✅ 彻底解决 |
| 工期 | 短 | 长，需独立排期 |

**理由**：本次事故根因是"缺 SSOT + 死/冗余/异义字段"，增量方案已能彻底消除事故且风险低；嵌套重构虽更干净，但是一次数据模型级变更，波及所有读取方与全量数据迁移，应单独评审与排期，不应混入缺陷修复以免放大风险、模糊验收边界。
