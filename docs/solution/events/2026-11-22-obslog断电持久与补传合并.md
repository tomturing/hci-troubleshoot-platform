## 一、两个问题

| # | 缺陷 | 后果 |
|---|---|---|
| P1-3 | `persistLocked` 写入不 `fsync`（全包 `grep Sync()` = 0） | 断电/硬崩溃丢最后若干条；"重启后仍在磁盘"只在 OS 刷盘后成立，但文档未写明 |
| P1-6 | `mergeSeedLocked` 逐条 `sort.Search` + `copy`，O(n²) | 5000 条补传时插入动作吃掉 2s 扫描预算，补传进度上不去 |

## 二、第一性拆解

### P1-3：fsync 该放在哪

先问"哪一刻的数据丢失是不能接受的"。三种候选：

| 位置 | 代价 | 能解决什么 |
|---|---|---|
| 每条日志 `fsync` | publish 热路径每条一次系统调用 + 日志提交，慢盘客户机直接拖慢日志产生侧（P1-4 已证明该路径对 IO 放大敏感） | 最彻底 |
| **按上传轮次 `fsync`**（本次采用） | 每轮一次，且 `unsyncedBytes==0` 时直接跳过 | 丢失窗口 = 最近一轮 |
| 只在退出时 `fsync` | 最便宜 | 断电仍然全丢 |

关键事实：**游标只在批次确认成功后前进**。所以"已上传"的数据即使本地丢了也不影响平台侧完整性；真正需要收敛的是**尚未上传的尾部**——它丢了平台完全不知（连 gap 都没有）。而尾部丢失量与"上次刷盘到现在"的写入量正相关，与"上传是否发生"无关。

因此刷盘点选在 **worker 每轮取批之后、发送之前**（`flushOnce` 持锁区间内），并在 **滚段关档之前** 再刷一次（旧段此后不再被写，但它可能还没被游标消费完）。

### P1-6：为什么可以批量

入队条件是 `entry.Seq > u.maxQueuedSeq`——**新条目一定比已入队的大**。这带来两个可依赖的性质：

1. 同一批 `pending` 内部 seq 严格递增；
2. `pending` 全部大于既有队列中的实时条目，只需整体插到有序区之后。

于是逐条 `sort.Search` 插入（每条约 O(n) 移动）可以换成"收集一批 → 一次稳定排序"。`Seq=0` 的 stderr 包装条目原本就是"append 到尾部"，稳定排序保持其相对顺序即可等价。

## 三、实现

**P1-3**
- 新增 `unsyncedBytes`：`persistLocked` 写成功后累加，`syncOutboxLocked` 成功后清零；
- `syncOutboxLocked`：`outbox == nil || unsyncedBytes == 0` 直接返回（避免慢盘上空转持锁）；
- `flushOnce`：`copy(batch, source[:size])` 之后调用（持 `u.Mu`，保证与滚段/关闭互斥）；
- 滚段：`Sync()` → `Close()` → 新建段，并清零 `unsyncedBytes`；
- fsync 失败：`log.Printf` 留痕一次，**不置 `persistOK=false`**。理由：个别文件系统与杀软过滤驱动会返回伪失败，把它当磁盘故障会让整条直传停摆，代价远大于丢最后几条。

**P1-6**
- `mergeSeedLocked` → `mergeSeedBatchLocked(entries []LogEntry)`：append 后 `sort.SliceStable`；
- `scanLogFile`：局部 `pending` 收集，每 `seedMergeBatchSize=512` 条 flush 一次；
- `defer flushPending()` 兜底，覆盖预算用尽 / 尾部不完整行 / 队列满等所有提前返回路径——
  这一点必须做，因为 `maxQueuedSeq` 已在锁内推进，条目若滞留在局部变量里就是**永久漏发**。

## 五、明确的降级语义（不再默认"掉电也不丢"）

| 场景 | 丢失范围 |
|---|---|
| 正常退出 | 无（退出前有 flush 路径） |
| 进程被 kill | 无（数据在页缓存，内核仍在；重启从游标重读） |
| 断电 / 主机崩溃 | 最近一轮未刷盘的尾部；平台长期不可达处于退避时，最坏放大到退避上限 **60s** 的写入量 |
| 磁盘满 | 有界丢弃 + gap 留痕（P0-2 已修，本次不改） |

## 六、遗留

- 未做"每条即持久"，属于**知情取舍**：单 exe 跑在客户机慢盘上，逐条 fsync 会把日志产生侧拖到不可用。
- 若后续需要更强保证，方向是 group commit 的显式 batch（`fsync` 与上传解耦，由独立刷盘 goroutine 按时间片驱动），而不是把 `fsync` 塞进 `persistLocked`。
