# 交付等待阶段契约漏改与跨节点会话兜底

## 现场现象

工单 `Q2026112500592`（任务 `a41ba262-b837-47c6-a348-3f73ed37f71a`，P2 中继 `bridge_relay`，bridge `v2.38.0-1-gd7e15fa9`）：

- 采集侧成功：07:06:43Z `done=2/total=2`、`node_state=completed`，包 `2,404,882,140 B`、6 个条目、清单完整；
- 交付侧 07:06:44Z 提交 287 片后 **44 分钟零字节**：`pulled_bytes=0`、`uploaded_parts=0`，`log_collect_transfer_metric` 0 行；
- 期间 4 次 `delivery.node_unreachable`（`acli log_collect progress` 连续 3 次 `no-session`），第 5 次后 `phase=failed`，平台 07:50:51Z 落 `failed / LC-PLATFORM-011`（未归因兜底码）；
- 同时 `log_collect.metric_failed` 累计 **1300 条**，全部是 `stage='waiting'` 被 `/metrics` 以 422 拒绝；
- 页面全程显示"正在上传平台：0/287 片"。

关键节点信息：本单涉及 4 个 IP——`.35`（发起）、`.38`（探测/acli 同步）、`.36`/`.37`（实际采集）。`07:26:40Z` 只有 `.35` 的会话被 `remote_eof` 销毁，`session_keys` 仍残留 `.38`。

## 根因（三层叠加，一个触发者）

1. **契约三端不一致（可见性）**：#1648 在 bridge 生产端 `transferStageFor()` 新增了 `waiting`，并同步了展示契约与生成物，但**漏改接收端 Pydantic `Stage` Literal 与 DB `ck_lctm_stage`**。bridge 每条 waiting 上报都被 422 拒绝，平台 `detail.transfer` 快照永远缺失，派生层 `progress=null`，面板只能显示"上传中 0/N 片"。
2. **跨节点会话兜底（致命）**：`.35` 会话销毁后，`ResolveForNode` 前三级（exact / default_key / node_ip）全部落空，兜底到 `OnlySessionForCase` 返回了 `.38` 的会话；装配层 `Wrap()` 只判指针非空、不判 `Client` 存活，交付把 `acli log_collect progress` 发到另一台机器的僵尸会话上，每轮 `no-session`。
3. **重排不重建会话 + 状态不回写（放大）**：`retrying` 只是进程内重投同一个 `*deliveryJob`，不重建会话、不回写平台 `delivery_attempts`（该字段是用户签发交付代际，不是 bridge 重试计数）。5 次预算耗尽后直接失败，界面仍停在 `queued/0`。

触发者：`#1648`（2026-11-24 17:44 合入）让等待阶段与重排路径第一次被高频走到，把上述两个长期存在的缺口串成了活锁。同版本 exe 的 `Q2026112500823` 正常交付成功，说明它不是充分条件。

## 对抗性审查

- **为什么不用 `LC-ENV-006`（SSH 会话不存在）？** 该码语义是"会话不存在、需先 `ssh_connect`"；本场景是"会话解析到了但已关闭，甚至落到了另一台节点"。处置虽然都是重连，但本码明确"包与已传分片均保留、无需重新采集"，且可用于统计跨节点误投。
- **拒绝 `only_session_for_case` 会不会让单节点场景多一次重连？** 会，但只在该节点已无会话时发生；这是正确性优先的代价，且 `ReconnectDeliveryNode` 命中后即恢复。多节点下它防止的是"命令发错机器"。
- **`waiting` 只是新增枚举，会不会影响旧读数？** 不影响：历史数据从未成功写入 waiting，不需要回填；展示契约与前端标签早已有该值。
- **`Alive()` 判 `Client != nil` 是否足够？** 它能识别 `Close()` 后的僵尸会话（本单的直接形态）；半开但 `Client` 非空的连接由 C 项的超时兜底，二者互补。
- **`retrying` 改显示会不会掩盖真实失败？** 不会：`retrying` 是 bridge 明确声明的中间态，失败终态会走 `phase=failed` 并携带错误码；界面同时显示重试次数，用户不会把"重建中"误读为卡死。
