# QKV 关键信号关键字 × 分类基线校验设计（输入容忍 + 实时基线）

> 本文档是对 `2026-07-22-QKV-QFK关键信号关键词字段失同步分析与修复方案.md` 的**补充决策**：
> 前者解决"字段写错位置导致编辑不生效"，本文档解决"keyword 填了什么值、由谁校验、按什么标准校验"。
> 二者正交——字段位置对了，仍可能因"关键字与分类基线语义不对齐"或"生产者类型选错"而让信号恒为假。
>
> **当前状态：方案评审中。第 4.1 节前端已落地（未提交），第 4.2/4.3 节后端与 prompt 软规则为建议、未实现。**

## 背景与需求

### 一、纠错起点：QKV 关键字的真实本质

上一轮交互中，我把 QKV 生产者的关键字举例成了"磁盘被拔出、镜像忙"这类自然语言描述。这是**错误的**——QKV 生产者不是前端文本匹配，而是去平台自身的记录库里检索"某类故障是否发生过"：

```bash
acli <task|dialog|alert> get -k <keyword>       # keyword 是 acli 检索词
```

由此推导出 QKV 关键字与 QFK 文本匹配关键词是**完全不同的两类东西**：

- **QFK 关键字**：在前端/日志文本里做 `contains` 匹配，是"自由描述性"的。
- **QKV 关键字（acli `-k`）**：是对平台**任务/告警记录**做的检索词，必须能命中平台真实记录的命名，即与本案例所属**分类基线标签**语义对齐。

若 keyword 与平台记录命名对不上 → 查不到记录 → 信号恒为 `false` → 漏诊。所以 QKV 关键字是**与分类基线双向绑定的特有字段**，不是 QKV/QFK 共有字段。

### 二、约束一：KBD 是人写的，输入须容忍

KBD（知识库案例）由人工编写，内容**偏口语化、有同义词、甚至错别字**（如"磁盘被拨出""镜象忙"）。

**结论性边界**：
- **输入（KBD 原始正文）必须容忍**：LLM 抽取阶段要能兜住错别字/同义词，绝不因原文不标准而拒抽或报错。
- **输出（抽取出的 keyword）可以做校验**：但只能做**软告警**，不能硬拒、不能阻断抽取。

换言之：校验的矛头指向"抽取结果的质量提示"，而不是"原始输入的合法性审查"。

### 三、约束二：分类基线（198 类）是动态的，校验须基于实时数据

分类基线（`category_baseline.yaml` → 导入 `kb_category` 表）目前约 198 条叶节点，但其**不是固定词表**——它会根据后续实际排障情况被运营**持续调整、增删、改名**（来源最初是结构图导出的 `mm` 文件，属静态快照）。

**结论性边界**：
- 校验逻辑**不得**把"硬件部/结构图那版 198 类"硬编码进代码或 prompt 常量。
- 校验必须读取**运行时实时基线**（`category_repo` 从 DB 取 `get_all_active()`，或前端 `useCategories` 已加载的实时分类），基线变了校验随之变，避免"校验规则比基线还旧"的腐化。

### 四、本次范围与目标

| 项 | 内容 |
|---|---|
| 问题 | QKV 关键字填错值 / 选错生产者类型 / 与分类基线语义不对齐，导致信号恒假且静默漏诊 |
| 目标 | 在"输入容忍 + 实时基线"两个约束下，对 QKV 关键字抽取提供**软校验**能力，提升关键信号抽取与执行的准确性 |
| 不做什么 | 不硬拒 KBD 输入、不写死 198 类词表、不对关键字做强阻断 |

## 第一性原理分析

### 一、为什么 QKV keyword 必须绑定分类基线

1. **keyword 是检索词，不是自由描述**。`-k` 是对平台任务/告警记录的匹配。自然语言描述（"磁盘被拔出"）对不上记录命名 → 查空 → 信号恒假。
2. **分类基线是平台故障的权威词表**。每个案例都归属其中一类，keyword 应从该案例所属分类基线标签派生，语义对齐。
3. **生产者类型 ↔ 故障性质强绑定**（平台把不同性质故障存不同子系统）：
   - 任务失败型（标签多以 `失败/卡住/异常/不达预期` 结尾，如 `虚拟机开机失败`）→ 任务记录 + 弹框 → `qkv_task` / `qkv_dialog`
   - 告警型（标签以 `告警` 结尾，如 `虚拟机CPU或内存占用过高告警`）→ 告警记录 → `qkv_alert`
   - **类型选错（如给"开机失败"用 `qkv_alert`）会查错子系统、返回空 → 信号恒假**，这是准确性第一杀手。

### 二、输入 vs 输出的容忍度边界

```
KBD 原文（输入）──[LLM 抽取，兜底错别字/同义词]──▶ 抽取出的 keyword（输出）
       容忍 ✅                                         │
                                                      ▼
                                          软校验：与实时分类基线语义对齐？
                                          不匹配 → warnings（进人工复核），不阻断 ✅
```

- **输入容忍**：原文"镜象忙""磁盘被拨出"不能成为抽取失败的理由；LLM 有责任在抽取阶段归一化到正确 keyword。
- **输出校验**：抽出的 keyword 若与实时基线语义明显不沾边，应给提示（软告警），但不推翻抽取结果。

### 三、实时基线 vs 静态硬编码

分类基线由运营维护、随排障实践演进。若把词表写死在代码/prompt：

- 基线新增一类（如新故障 `序列号过期告警`），写死的校验永远不认识它 → 误报"不匹配"；
- 基线改名（如 `虚拟机开机失败` → `虚拟机启动失败`），写死的规则立刻失准。

因此校验必须**运行时读取实时基线**，且只对"性质（任务失败型/告警型）"这类**结构性特征**做判断，而非对"具体 198 个词"做枚举。

### 四、准确性收益的归因

- 让"选错类型"在编辑期就被软告警拦下（前端即时反馈）→ 避免信号恒假。
- 让"抽出的 keyword 与实时基线对不上"在抽取管线被标记 → 进人工复核队列，避免静默漏诊。
- 两层都**不阻断**，符合"输入容忍"要求。

## 决策依据（WHY：为什么这样选，为什么不选其他）

### 决策 1：校验只对"输出"做，且只软告警、不阻断

- **选**：校验作用于抽取出的 keyword，产出 `warnings`/高亮提示，不拒绝、不拦截。
- **不选（硬拒/强阻断）**：KBD 输入本就口语化、有错别字，硬规则会误杀正确抽取，违背"输入容忍"。且 QKV 信号是诊断关键路径，硬拒会导致整条案例不可用，代价过高。

### 决策 2：校验用实时基线数据，不硬编码"硬件部静态内容"

- **选**：前端复用 `useCategories` 已加载的实时分类；后端在 `_validate_signal` 内调用 `category_repo.get_all_active()` 取实时标签做模糊匹配。
- **不选（写死 198 类）**：基线会被运营持续调整，写死即腐化、且无法识别新增类，反而制造误报。

### 决策 3：两层校验（前端即时软校验 + 后端抽取管线软校验），而非只做一层

- **选**：前端负责"编辑期即时反馈"（类型↔性质强冲突高亮）；后端负责"抽取期兜底"（对 LLM 抽出的 keyword 与实时基线做模糊匹配，标记进 `warnings`）。
- **不选（只做一层）**：前端只覆盖人工编辑、覆盖不到 LLM 自动抽取；后端只覆盖抽取、反馈太晚（要等抽取跑完）。两层互补、互不替代。

### 决策 4：前端用"性质正则启发式"而非"拉全量实时基线逐条匹配"

- **选**：前端 `qkvKeywordMismatch()` 仅用"是否含 `告警` / `失败|卡住|不达预期`"这一**结构性性质**判断类型↔关键字是否冲突。它不依赖任何硬编码词表，天然满足"实时 + 容忍"。
- **不选（前端拉全量 198 类逐条模糊匹配）**：性质判断已能拦下"准确性第一杀手（类型选错）"，且无需把基线细节搬进前端；逐条匹配昂贵、且和后端职责重叠。后端才是做"全量实时模糊匹配"的合适位置。

### 决策 5：seed prompt 只加"软规则"，不写死词表

- **选**：在 `02_system_prompts.sql` 的 `kbd_extract_signals_v2` 增加"QKV keyword 应取自本案例**实时**分类基线标签；任务失败型用 `qkv_task`/`qkv_dialog`，告警型用 `qkv_alert`"的**指导性软规则**。
- **不选（在 prompt 里枚举 198 类）**：prompt 是静态种子，写死词表会与实时基线脱节，且撑大 token、降低抽取聚焦度。

## 方案（WHAT）

### 4.1 已落地：前端生产者编辑区即时软校验（`frontend/admin/src/views/KbdReviewView.vue`）

> 状态：代码已写入工作区，**未提交、未合入**。

新增辅助函数（性质判断全部基于正则，不引用任何硬编码词表）：

```ts
// 采集类型旁标注"任务失败型/告警型"（来自实时基线的结构性质，非词表）
function qkvNatureLabel(tool: string): string {
  if (tool === 'qkv_alert') return '（告警型故障 · 分类基线）'
  if (tool === 'qkv_task' || tool === 'qkv_dialog') return '（任务失败型故障 · 分类基线）'
  return ''
}
// keyword 的 placeholder 与注释随类型动态切换，实例取自分类基线真实标签
function qkvKeywordPlaceholder(tool: string): string {
  if (tool === 'qkv_alert') return '告警型关键字，如 虚拟机CPU或内存占用过高告警、序列号过期告警'
  if (tool === 'qkv_task') return '任务失败型关键字，如 虚拟机开机失败、虚拟机快照失败'
  if (tool === 'qkv_dialog') return '任务失败型弹框关键字，如 虚拟机创建失败、磁盘替换失败'
  return '关键字，取自分类基线，如 虚拟机开机失败 / …告警'
}
// 软校验：类型 ↔ 关键字性质 强冲突（保守规则，避免误报）
function qkvKeywordMismatch(sig: SignalV2): boolean {
  const tool = sigTool(sig)
  const kw = String(sigArgs(sig).keyword || '')
  if (!kw) return false
  const hasAlert = kw.includes('告警')
  const hasFailVerb = /(失败|卡住|不达预期)/.test(kw)
  if ((tool === 'qkv_task' || tool === 'qkv_dialog') && hasAlert && !hasFailVerb) return true
  if (tool === 'qkv_alert' && hasFailVerb && !hasAlert) return true
  return false
}
```

编辑区改造：

- 新增**采集类型**行，旁注性质：`qkv_task/qkv_dialog →（任务失败型故障·分类基线）`、`qkv_alert →（告警型故障·分类基线）`。
- `keyword` 的 placeholder、说明文字随类型切换（实例取自分类基线真实标签，非泛化自然语言）。
- 固定一条**校验规则注释**：任务失败型走 `task/dialog`、告警型走 `alert`，选错会查不到记录、信号恒为假。
- 命中 `qkvKeywordMismatch` 时高亮为告警色（仅提示，不禁用保存）。
- 新增样式 `.signal-nature`、`.field-hint.keyword-check.is-warn`。

**为什么满足两个约束**：① 不对 KBD 输入做任何硬性校验（编辑时错别字/同义词 keyword 不被拦截，只软提示）；② 正则只判"性质"、不枚举 198 类，天然不写死硬件部静态内容。

### 4.2 建议（未实现）：后端抽取管线软校验（实时基线）

在 `backend/kb-service/app/routes/extract_signals.py` 的 `_validate_signal`（或 `_validate_and_collect_signals`）增加一步「QKV keyword × 实时分类基线」校验：

```python
# 伪代码：在抽取完成后、落库前
async def _validate_qkv_keyword(sig: dict, cat_repo: CategoryRepository) -> list[str]:
    warnings: list[str] = []
    tool = sig.get("acquirer", "")
    if tool not in ("qkv_task", "qkv_dialog", "qkv_alert"):
        return warnings
    kw = str((sig.get("acquirer_args") or {}).get("keyword", "")).strip()
    if not kw:
        return warnings
    # 取实时活跃分类（运行时数据，绝不硬编码 198 类）
    live = await cat_repo.get_all_active(leaf_only=True)
    labels = [c.name for c in live]
    # ① 性质一致性：qkv_alert ↔ 告警型；qkv_task|dialog ↔ 任务失败型
    is_alert_tool = tool == "qkv_alert"
    kw_is_alert = "告警" in kw
    kw_is_fail = bool(re.search(r"失败|卡住|不达预期", kw))
    if is_alert_tool and kw_is_fail and not kw_is_alert:
        warnings.append(f"qkv_alert 关键字疑似任务失败型（含'失败'），建议改用 qkv_task/qkv_dialog")
    if (not is_alert_tool) and kw_is_alert and not kw_is_fail:
        warnings.append(f"{tool} 关键字疑似告警型（含'告警'），建议改用 qkv_alert")
    # ② 与实时基线的模糊匹配（容忍错别字/同义词：用包含/编辑距离，而非全等）
    if not any(_fuzzy_match(kw, lb) for lb in labels):
        warnings.append(f"关键字'{kw}'与实时分类基线无近似匹配，请确认是否拼写/归类有误")
    return warnings
```

要点：

- **实时**：`cat_repo.get_all_active()` 每次校验都读 DB，基线变动后校验自动随之变动。
- **容忍**：① KBD 原文的错别字/同义词由 LLM 抽取阶段兜底（输入容忍），此处只校验输出；② 模糊匹配用"包含/编辑距离"而非全等，避免轻微错别字误报。
- **软失败**：所有结果进 `warnings`，**不阻断抽取、不拒绝落库**，仅进人工复核队列。

### 4.3 建议（未实现）：seed prompt 软规则

在 `backend/kb-service/database/seeds/02_system_prompts.sql` 的 `kbd_extract_signals_v2` 增加：

> QKV 关键字（acli `<task|dialog|alert> get -k`）必须取自**本案例所属分类基线**的实时标签，与基线语义对齐；任务失败型（标签含"失败/卡住/异常/不达预期"）用 `qkv_task`/`qkv_dialog`，告警型（标签含"告警"）用 `qkv_alert`。若不确定分类，优先保证关键字能命中平台记录命名，不要编造词表外的词。

（注意：只写"性质规则"，**不枚举** 198 类具体词，避免与实时基线脱节。）

### 4.4 反模式（明确不得做的事）

| 反模式 | 原因 |
|---|---|
| 把 198 类词表硬编码进代码或 prompt 常量 | 基线动态演进，写死即腐化、误报新增/改名类 |
| 对 KBD 原始输入做硬性校验/拒抽 | 违背输入容忍，错别字/同义词会误杀正确抽取 |
| 类型与关键字强冲突时硬拒保存/硬拒抽取 | 阻断诊断关键路径，代价过高；软告警即可 |
| 用全等匹配判断 keyword 是否命中基线 | 不容忍错别字/同义词，制造大量误报 |

## 验收标准

1. **输入容忍**：在 KBD 原文存在错别字/同义词时，LLM 仍能正常抽取 QKV 信号；前端编辑错别字 keyword 不被拦截、仅按需软提示。
2. **实时基线**：后端（若实现 4.2）校验读取运行时 `category_repo` 实时数据；人为在 Admin 增删/改名一个分类基线后，校验行为随之变化（非写死）。
3. **类型↔性质软告警**：前端在 `qkv_task/dialog` 填入"…告警"类、或 `qkv_alert` 填入"…失败"类关键字时，出现可识别的高亮告警；但不阻止保存。
4. **不阻断**：任何一层校验的不匹配都只产生 `warnings`/提示，绝不拒绝抽取或保存。
