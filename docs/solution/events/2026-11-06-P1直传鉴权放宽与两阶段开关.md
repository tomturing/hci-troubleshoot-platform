# P1 直传鉴权放宽与两阶段开关（2026-11-06）

## 一句话

5888 启用上传鉴权后，节点 acli 的直传（P1）在 `/init_upload` 被 401 全量打回并自动降级 P2；根因是 acli 传输层把认证参数解析后丢弃，导致请求永远不带认证头。本次**不改本仓库任何代码**，在 5888 侧加两阶段开关：阶段一临时放行匿名 P1 直传保证业务可用，阶段二待 acli 修复后一键恢复强鉴权。

> 本文记录的状态是 **2026-11-06 当日**的阶段一临时态，不是最终态。改动全部落在 `192.168.0.2:/acli`（独立本地 git 仓库、无 remote）与 systemd 单元，本 PR 只新增这份事件文档。

## 为什么要补充这份文档

1. **给并行排查的其他 Agent 一个同因判据。** 当前有多个 Agent 同时处理 `https://acli.sangfor.com.cn:4443/` 上大量用户遇到的日志收集问题，这些工单里可能包含与本文同一个根因。本文把「现场表现 → 可机械比对的日志/字段指纹 → 排除项」写成速查表，让其他 Agent 直接判「是/不是同因」，避免对同一根因反复做黑盒探测、反复设计凭据注入方案、甚至重复提交互相冲突的修复。
2. **给后续优化留一条闭环线索。** acli 的上传认证能力修复完成后，本 PR 会被重新交给 Agent 审查，按文末「阶段二闭环清单」快速完成：确认票据真正到达 → 切换强鉴权 → 补验收 → 收敛残留。没有这份文档，后续 Agent 只能从零重建因果链，也无法解释「为什么线上现在是匿名放行的」。

## 一、问题现象

### 1.1 用户侧真实使用路径（工单 `Q2026110666666`）

使用者在 4443 日志收集面板点「重试」，完整经过：

| 步骤 | 现场表现 | 与本次根因的关系 |
|---|---|---|
| 首次重试选 `core` 专项 | `收集专项core不存在！`，命令 0 秒退出，任务 `failed` / `LC-EXEC-003` / `progress=0` | **无关干扰项**：该节点 `acli log_collect create --help` 的专项枚举只有 `vm_suspend/vm_start/host_offline/network/storage/slowdisk/performance/system/other` 9 项，没有 `core`；面板显示的 `modules_count=10` 是旧缓存值 |
| 同期 cgroup 告警 | `open /sys/fs/cgroup/cpu/cpuset.cpus: no such file or directory` | **无关噪声**，不是失败点 |
| 改选 `other` 专项 | 采集正常完成，产物约 204 MiB | 排除采集侧问题 |
| 上传阶段 | **P1 直传失败，自动降级 P2** | 本文根因 |
| 最终交付 | P2 代传成功，`/sf/log` 下出现完整 zip | 掩盖了 P1 已废的事实 |

关键的用户体验是「**P1 报错后降级为 P2，任务最终看似成功**」，而不是「彻底失败」。这带来两个高频误判：

- 看到 `/sf/log/Q.../` 下有包就以为 P1 成功 —— **P2 的第二跳同样是平台代传写到 5888，落点是同一个目录**，判通道必须看 UA 与 `log_collect_task.upload_mode`，看目录无效。
- 把失败归到包大小、网络或采集侧 —— 实际卡在 `init_upload` 的第一步，`upload_state` 从未出现「发送中」，直接「重试中 → 失败」。

### 1.2 同因判定指纹（给其他 Agent 直接比对）

| 数据源 | 字段 / 日志 | 命中值 |
|---|---|---|
| 5888 journal | 鉴权失败 | `鉴权失败: /init_upload ... scheme=none header=no`（`scheme=none` 表示请求完全无认证头） |
| `log_collect_task` | `upload_mode` | `bridge_relay` |
| `log_collect_task.detail` | `upload_mode_switched_from` | `acli_direct` |
| `log_collect_task.detail` | `upload_mode_switched_reason` | `日志服务器上传失败：失败，可改用 P2 中转` |
| 5888 journal | 成功 `init_upload` 的 UA | 只有 `python-httpx`（平台 P2 代传）/ 浏览器 / 本机验证，**没有 acli 的 `python-requests/2.18.1`** |
| 时间边界 | 5888 启用 `ACLI_UPLOAD_TOKEN` 之后（2026-10-31） | 该时间点之后 P1 直传成功数为 0 |

四条同时成立即可判为同因。另有一条放大机制：`probeLogCollectEnv` 用 `curl <logServerURL>` 打 5888 根路径 `/`，而 `/` 免鉴权、永远返回 200；探测又把 `200–499` 全判为 `LogServerReachable`，前端据此默认选 P1 —— **用「网络可达」这一个布尔回答了「能否带凭据直传」**，于是面板稳定把用户推上必然 401 的通道。

### 1.3 排除清单：以下现象不是这个根因

| 现象 | 实际归属 |
|---|---|
| `收集专项core不存在！` / `LC-EXEC-003` / 0 秒退出 | 专项枚举与节点 acli 版本不匹配 |
| `parse_ok=false`、`platform_default`、卡在 `collecting` / `0%`、不降级 P2 | acli 输出英文导致 bridge 解析失败（PR #1445 / exe #1447 已修，但**现场 exe 不自动更新，需人工重装**） |
| `Case Service unavailable` 503、已交付却写 `failed` | case-service OOMKilled + 前端把瞬时 503 当终态，见 [2026-11-06-代传OOM与503误判终态](2026-11-06-代传OOM与503误判终态.md) |
| 长请求 502 | 入口读超时（与鉴权无关） |
| 10-28 ~ 10-30 的直传失败（形态为「发送中 → 重试中 → 失败」） | 发生在启用鉴权**之前**，撤鉴权不能修复这一类 |
| 探测字段 `acli_supports_upload_header=false` | 出现在 `acli_installed=false` 时，属假阴性，不能当版本能力结论 |

### 1.4 已知同类工单

`Q2026110300278`（见 [2026-11-03-P1直传票据闭环](2026-11-03-P1直传票据闭环.md)）、`Q2026110601054`、`Q2026110486009`、`Q2026110666666`。这些单的共同点是「P1 401 → 降级 P2」，差别只在降级是否顺利、以及是否叠加了输出语言/状态机问题。

## 二、根本原因

### 2.1 直接根因：acli 传输层把认证参数解析后丢弃

源码审查结论（由用户侧的对抗性审查给出，非本仓库代码）：`remote_transfer.py` 的 `http_transfer`、`TransferToSangfor.upload_init`、`chunk_upload` 是最小实现——

- `headers={}` 硬编码，解析得到的 `remote_dict["headers"]`、`auth` / `basic_auth` **从未传入** `requests.post(...)`；
- `-u` 只接受 3 个 sangfor 官方域名并硬编码拼接 `/init_upload`，自定义 path 被前缀吞掉；
- 因此 `-H`、`-L`、`-U/-P` 属于「解析层支持、传输层不用」的死参数。

黑盒实测（每次只改一个变量）：

| 尝试 | 5888 观测 | 结论 |
|---|---|---|
| `-H 'Authorization: Bearer <ticket>'` | 上传请求无 Authorization 头 | 无效 |
| `-L 0:Authorization:Bearer <ticket>` | 同上，无 `[P1] 票据通过` | 无效 |
| `-U probe -P probe`（Basic） | `scheme=none header=no` | 无效 |
| `-u http://acli.sangfor.com.cn:5888/p1/probe/` | 仍收到 `/init_upload` | 自定义 path 被丢弃 |
| `acli config --help` | `错误：未知的命令或者命名空间(config)` | 无持久化配置入口 |
| `acli log_collect --help` | 只有 `cancel/create/progress` | 无单独 `upload/send` 可验证 |

**推论**：acli 发出的上传请求天然不带任何认证头；5888 一旦开启鉴权，P1 必然 100% 401。这是「能力缺失的实现缺陷」，不是「参数用法不对」。

### 2.2 先前方案为什么被证伪（防止重复修复）

2026-11-03 的 P1 票据闭环（PR #1429）在平台侧完整实现了 HMAC 票据签发、bridge 注入 `-L`、5888 验签、`/archive_status` 回读核验，但**真实 acli 上票据从未到达**：判据是若票据到达而验签失败，5888 会打 `[P1] 票据拒绝` 并带 `reason`，而现场日志两者都没有。11-06 改用全局 `-H` 后仍 401。

结论写死在这里：**在 acli 传输层修复之前，任何继续在平台侧「换参数注入凭据」的方案都是无效功**，包括桥侧本地反向代理（`-u` 不认自定义域名）、URL 拼接 token（path 被吞）等。

### 2.3 为什么人工页面上传从来不需要提供凭据

用户曾问「acli 上传 5888 需要认证，人工在页面上传需要吗？我怎么从来没有提供过？」——答案是凭据被服务端/前端隐式注入了：

- 5888 的 `index()` 把 `AUTH_TOKEN` 内联进 `upload.html` 的 `<meta name="upload-token">`，前端 axios 自动设置 `Authorization: Bearer ...`；
- 平台 4443 页面的人工上传走 case-service 代传，由服务端读取 `LOG_COLLECT_RELAY_TOKEN` 发 Bearer。

**两者都不是 acli 客户端**，所以「人工能传」完全不能证明「P1 能传」。另外，token 明文内联在免鉴权的首页 HTML 里，本质更接近共享口令 / 反扫描口令，不是用户身份认证，不应据此高估防护边界。

## 三、最终决策

用户决策原话：`现在的鉴权代码先保留，并做好注释；现阶段先选择对直传放宽，保证P1可以正常使用。现在P1都无法正常使用。acli完成功能的修复后，我们再一键开启鉴权`。

即采用**两阶段开关**：保留全部鉴权代码与票据能力并加注释，阶段一放宽 P1 直传保证业务可用，阶段二 acli 修复并分发后一键恢复强鉴权。

| 备选 | 为什么否决 |
|---|---|
| 继续在平台侧换参数注入凭据 | 已被 2.2 的黑盒实测证伪，acli 传输层不用这些参数 |
| 直接撤掉 5888 的 `ACLI_UPLOAD_TOKEN` 全局放行 | 会把 P2 代传、人工上传页、`/archive_status` 的鉴权一起丢掉，范围远大于需要 |
| 先修 acli 再恢复业务 | 现场 bridge exe 不会自动更新，需人工重装分发，业务当下持续不可用 |
| **两阶段开关（选中）** | 功能立刻可用；鉴权代码、票据通道、审计日志零删减；一条命令可回退到强鉴权 |

**放宽不等于关鉴权**，边界必须写清，否则后续 Agent 会误判：

- 仅「完全无认证头」且路径在白名单内才放行：`/precheck`、`/init_upload`、`/upload_chunk`、`/upload_status/<id>`；
- `/archive_status` 仍强制鉴权；
- 带错头、错 token、`?token=` 的请求**不**回落匿名，仍 401；
- P1 票据验签、全局 Bearer、Basic 解析、`scheme/header/user` 审计日志全部原样保留；
- 匿名放行按请求打审计日志 `[P1] 匿名直传放行(临时): path=... mode=relaxed`，启动打 `[P1] 鉴权模式: relaxed(临时匿名直传放行)`。

## 四、解决方案

### 4.1 落地清单（均在仓库外的 5888 节点）

| 位置 | 内容 |
|---|---|
| `/acli/app.py` | 两阶段开关注释块、`P1_REQUIRE_AUTH`、匿名白名单、匿名放行分支与审计日志；保留原有全部鉴权代码 |
| `/etc/systemd/system/acli-5888.service.d/p1-auth.conf` | `Environment=ACLI_P1_REQUIRE_AUTH=0`（阶段一） |
| `/acli/switch_p1_auth.sh` | `on` / `off` 一键切换：改 drop-in → `daemon-reload` → `restart acli-5888` |
| `/acli/README_P1_AUTH.md` | 两阶段说明、放宽范围、验收记录、回滚与阶段二前置条件 |
| `/acli/app.py.bak.p1basic`、`/acli/app.py.bak.p1relax` | 两轮改动前的回滚点 |

`P1_REQUIRE_AUTH` 是模块级常量、进程启动时求值，因此**切换必须重启进程**；systemd restart 会中断 in-flight 分片，已落盘分片与会话不丢，但切换要避开在传任务。

### 4.2 验收：真实 acli 端到端跑通（非模拟请求）

先做边界验证：无头 `init_upload` 200、错头 401、无头 `/archive_status` 401、全局 Bearer 200、正确 P1 票据 200、无头分片/状态请求到达业务层（400/404 而非 401）。

再用现场工单 `Q2026110666666` 做真实 acli 直传（北京时间 2026-11-06）：

| 时刻 | 事实 |
|---|---|
| 19:36:48 | `[P1] 匿名直传放行(临时): path=/init_upload filename=Q2026110666666.zip from 113.108.13.8`；UA `python-requests/2.18.1`；`file_size=213982824` |
| 19:36:52 ~ 19:38:25 | 21 个分片连续放行，全程**零** `鉴权失败: /init_upload` |
| 19:38:25 | `Upload completed`，97.38 秒，2145.83 KB/s |
| 会话终态 | `status=done`、`progress=100`、`uploaded_size == file_size`、`error=null`、`sha256=e45d664a…` |
| 归档 | `/sf/log/Q2026110666666/Q2026110666666.zip` 213982824 字节；旧包让位改名为 `Q2026110666666-20261106175423.zip`（规范名=最新，旧包带戳） |
| 平台任务 `cfc33db2` | `status=completed`、`progress=100`、`upload_mode=acli_direct`、`delivery_status=delivered`、`relay_status=none`、`switched_from` 空、无错误码 |

从下达到终态 3 分 14 秒；同工单上一单走 P2 用了 5 分 42 秒。**P1 未降级 P2，鉴权这一关与整条上传链路均已闭环。**

### 4.3 残留与已知边界（闭环时不要漏）

1. `integrity_state=unverified`、`archive_sha256` 为空：5888 已回报 sha256 且体积一致，但平台侧**没有回读摘要**（P1 票据方案里的 `verify-archive` 依赖票据，而票据在 acli 侧未生效）。属校验缺口，不是交付失败。
2. 撤/放宽鉴权只能消除 401 这一类直传失败；1.3 列出的其它根因不受影响。
3. 英文输出解析失败导致的卡 `collecting`，需要现场重装新版 bridge exe 才生效，与本改动无关。
4. 阶段一上传链路对匿名开放，安全边界回退到 2026-10-31 加固之前，是**临时**取舍。
5. 本次改动未进任何版本库：可追溯性只靠 5888 侧的 README、备份文件与服务日志，本 PR 用于补齐平台仓库侧的记录。

### 4.4 阶段二闭环清单（后续 Agent 按序执行）

1. 修 `remote_transfer.py`：把 `remote_dict["headers"]` 与 `auth` 透传进 `init_upload` / `chunk_upload` / `complete` 的 `requests.post(...)`，去掉 `headers={}` 硬编码。
2. 新版 acli 分发到目标节点；注意客户机 bridge exe 不会自动更新，须现场重装。
3. 跑一单 P1，确认 5888 日志出现 `[P1] 票据通过`、且无 `鉴权失败: /init_upload`；**这是能否切回强鉴权的唯一判据**，不要用 acli 版本号或平台代码状态代替。
4. 确认无在传分片后执行 `sudo /acli/switch_p1_auth.sh on`（会 restart，避开在传任务）。
5. 复验：无头 `init_upload` 401、正确票据 200、全局 Bearer 200、`/archive_status` 仍 401、真实单 `acli_direct` + `delivered`。
6. 评估恢复 `verify-archive` 摘要回读，消除 `integrity_state=unverified`。
7. 更新本文状态，并在相关事件文档中补记阶段二结论。
