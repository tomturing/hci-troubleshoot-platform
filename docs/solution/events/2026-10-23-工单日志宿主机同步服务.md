# 工单日志宿主机同步服务设计

> 状态：设计定稿，待实现
> 日期：2026-10-23
> 关联回滚：`revert(dsh): 回滚 ticket-sync 实现，DSH 回到官方镜像（#1202 #1206 #1207）`

## 1. 背景

### 1.1 旧方案为什么废弃

工单同步能力最初被实现为 DSH 的**客户端插件 + 宿主插件**，通过 patch 对上游
`deepseek-harness` 做二次开发后构建镜像。该实现已经回滚，原因如下：

| 问题 | 事实 |
|---|---|
| 工具链能力缺失 | DSH 运行在 Alpine，`unzip` 是 BusyBox 的软链，不支持 `-P`（密码）与 `-Z1`（清单）；`df` 不支持 `--output`；`realpath` 不支持 `-m`。其中 `df` 一项导致可用空间恒为 0，所有工单一律判定存储不足 |
| 改动面过大 | 2208 行新增，34 个文件，横跨插件注册、slots 契约、Typert 远程协议、构建配置 |
| 反馈闭环过长 | 每次修复要重新打镜像、推仓库、滚动更新，单次 10 分钟以上 |
| 与产品定位冲突 | DSH 是通用诊断工作台，工单同步是一次性的内部交付动作，不属于产品能力 |

### 1.2 新方案

**把同步与解压移出集群，作为宿主机上的一个独立常驻服务。**

DSH 侧只保留一件事：一个已存在的 hostPath 挂载点，用于让用户在文件选择器里
看到解压产物。DSH 镜像使用官方 npm 包，不做任何代码改动。

## 2. 目标与非目标

### 2.1 目标

1. 在 admin-ui 的「DSH 诊断」页面输入工单号，点击按钮即可触发同步与解压。
2. 同步走 SSH，不要求 0.2 侧部署任何 HTTP 服务或改动任何配置。
3. 解压产物落在宿主机目录，DSH 通过 hostPath 直接可见，无需重启或改镜像。
4. 全程可观察：前端能看到实时进度，失败时能拿到明确原因。
5. 服务可以在一台机器上独立部署、独立调试、独立回滚。

### 2.2 非目标

- 不做多节点调度：当前部署是单节点，hostPath 已绑定节点。
- 不做权限体系：入口复用 admin-ui 的登录态，服务本身只监听内网地址。
- 不做工单缓存策略：产物由使用者手动清理，服务只负责构建。
- 不改动 DSH 的任何行为，包括工作区选择逻辑。

## 3. 硬约束

全部来自实测，不是推断：

| 约束 | 实测值 |
|---|---|
| 工单号格式 | `^Q\d{13}$` |
| 源路径 | `acli@192.168.0.2:22468:/sf/log/<工单号>/<工单号>.zip` |
| 源目录权限 | `root:root 755`，`acli` 可读不可写 |
| 源侧工具 | `/usr/bin/rsync` 存在；`/sf/log` 现有 962 个工单目录 |
| 归档特性 | ZipCrypto 全条目加密，压缩率约 4.4%，展开比 1.5x–20x |
| 体积分布 | P50 ≈ 989 MB，P90 ≈ 8.1 GB，最大 93 GB；抽样实测 6.4 GB |
| 嵌套深度 | 实测 3 层（`zip → sp_<ip>.tgz → cmd-output/*.tar.gz`） |
| 目标目录 | 宿主机 `/sf/tickets`，属主 `node:node`，权限 750 |
| 宿主工具 | Info-ZIP `unzip`（支持 `-P`）、GNU tar 1.35、coreutils 9.4 |
| 宿主运行时 | Python 3.12.3、uv 0.10.9、Node 24.14.1，无 Go |
| 免密登录 | `~/.ssh/config` 已配置 `Host 192.168.0.2 → acli:22468`，密钥 `~/.ssh/id_ed25519` |

## 4. 总体架构

```
浏览器
  admin-ui  /dsh-diagnosis（Vue）
    ├ 工单号输入框
    ├ 「同步日志」按钮  ──► POST /ticket-sync/jobs
    └ 2s 轮询          ──► GET  /ticket-sync/jobs/{ticketId}
          │
          │ 同源，经 admin-ui 的 nginx 反代
          ▼
宿主机 192.168.0.4:18080
  hci-ticket-sync（Python + uv + systemd，User=node）
    ├ POST /jobs          立即返回 202，后台执行
    ├ GET  /jobs/{id}     返回阶段与进度
    ├ DELETE /jobs/{id}   取消
    └ GET  /health        健康与磁盘余量
          │
          ├ ① rsync over ssh 拉取归档 → /sf/tickets/.tmp/<id>-<uuid>/
          ├ ② 逐层解压、校验、裁剪
          └ ③ rename 原子发布 → /sf/tickets/<id>/
          ▼
/sf/tickets/<工单号>/            （宿主机本地路径，服务直写）
          │ hostPath，DSH 已有挂载能力
          ▼
DSH Pod（官方镜像 @deepseek-ai/dsh@0.2.1-rc.2，零代码改动）
  用户在文件选择器中选择 /data/tickets/<工单号>/
```

### 4.1 为什么服务放在宿主机而不是容器里

| 判据 | 宿主机服务 | 容器内服务 |
|---|---|---|
| 写 `/sf/tickets` | 本地路径，直接写 | 需要 hostPath 挂载到该容器 |
| 修改后生效 | 重启进程，秒级 | 重建镜像 + 滚动更新，分钟级 |
| 工具链 | GNU 完整能力 | 基础镜像决定，可能缺失 |
| 对现有服务影响 | 零 | 需要改 Deployment / 镜像 / RBAC |
| 代价 | 脱离 GitOps，属「宠物」部署 | 与平台范式一致 |

当前阶段选择宿主机：该功能是内部工具，失败重跑成本极低，反馈速度优先。

## 5. 目录契约

```
/sf/tickets/
├── <工单号>/                    最终产物，用户在 DSH 中选择这一层
│   ├── log_list.json
│   ├── sp_10.46.16.71/
│   │   └── cmd-output/
│   │       └── ...
│   └── ...
├── .tmp/
│   └── <工单号>-<uuid>/         解压中间态，启动时清空
└── .trash/
    └── <工单号>-<时间戳>/       被替换的旧版本
```

**约定**：

- 产物**不套额外层级**：`/sf/tickets/<工单号>/` 直接就是解压内容，避免用户多点一层。
- `.tmp` 与 `.trash` 以点开头，文件选择器默认不展示。
- 目标已存在时，先比对「文件数 + 总字节」，一致则直接返回 `ready`（幂等），不一致则移入 `.trash` 后重新发布。

## 6. 服务设计

### 6.1 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 宿主机已装；Go 未安装，不引入新工具链 |
| 依赖管理 | uv | 全局规范；`uv sync` 生成隔离 venv |
| HTTP | FastAPI + uvicorn | 三个端点，需要异步；自带 OpenAPI 便于联调 |
| 传输 | `rsync --partial --inplace` | 源侧已确认可用；自带续传、校验、进度 |
| 解压 | 外部 `unzip` / `tar` | 重活交给 C 实现；Python `zipfile` 不支持 ZipCrypto |
| 进程管理 | systemd | 宿主机标准做法，`Restart=always` |
| 状态存储 | 进程内存 | 单实例部署；重启后任务丢失，重跑即可 |

### 6.2 模块划分

```
tools/ticket-sync/
├── pyproject.toml
├── app/
│   ├── main.py         FastAPI 应用、端点、任务表
│   ├── config.py       环境变量加载与校验
│   ├── fetcher.py      rsync 调用与进度解析
│   ├── extractor.py    分层解压、路径校验、配额
│   └── models.py       Job 状态与错误码
└── tests/
    └── test_extractor.py
```

### 6.3 任务状态机

```
queued ──► fetching ──► extracting ──► ready
   │           │            │
   └───────────┴────────────┴──► failed
   │
   └──► cancelled
```

状态迁移由单一协程推进，对外只暴露当前快照。

### 6.4 并发控制

- 同一工单：内存锁，重复提交返回 `409 job-running`。
- 全局：信号量限制为 **2** 个并发任务。理由是单块磁盘的顺序吞吐上限，并发更高只会互相拖慢。
- 排队中的任务在 `queued` 状态，前端展示「排队中」。

## 7. 接口

### 7.1 创建任务

```
POST /jobs
Content-Type: application/json

{"ticketId": "Q2026102100147"}
```

| 状态码 | 响应 | 场景 |
|---|---|---|
| 202 | `{"ticketId":"...","phase":"queued","acceptedAt":"..."}` | 已受理 |
| 400 | `{"error":"invalid-ticket-id"}` | 格式不匹配 |
| 409 | `{"error":"job-running"}` | 同工单已在执行 |

### 7.2 查询进度

```
GET /jobs/{ticketId}
```

```json
{
  "ticketId": "Q2026102100147",
  "phase": "extracting",
  "receivedBytes": 6852429066,
  "totalBytes": 6852429066,
  "extractedBytes": 12884901888,
  "fileCount": 3120,
```

`phase` 取值：`queued` / `fetching` / `extracting` / `ready` / `failed` / `cancelled`。

### 7.3 取消

```

```

取消会终止子进程并清理 `.tmp/<id>-<uuid>/`。

### 7.4 健康检查

```
GET /health
→ {"status":"ok","version":"1.0.0","diskFreeBytes":536870912000,"activeJobs":0}
```

## 8. 错误码

| code | 触发条件 | 前端展示 |
|---|---|---|
| `invalid-ticket-id` | 工单号不匹配 `^Q\d{13}$` | 工单号格式错误，应为 Q + 13 位数字 |
| `not-found` | 源侧文件不存在 | 该工单在 0.2 上不存在 |
| `too-large` | 归档超过 20 GiB | 工单包过大，超过单工单上限 |
| `bad-password` | unzip 返回密码错误 | 归档密码错误，请联系运维 |
| `archive-corrupt` | 头部校验失败 | 压缩包已损坏 |
| `no-space` | 剩余空间低于红线 | 服务器磁盘空间不足 |
| `quota-exceeded` | 展开后超限 | 解压体积异常，已中止 |
| `depth-exceeded` | 嵌套超过 4 层 | 归档嵌套层级异常 |
| `ssh-failed` | ssh/rsync 非零退出 | 无法连接 0.2 |
| `extract-failed` | 其他解压错误 | 解压失败，请查看服务日志 |

## 9. 解压策略

### 9.1 分层流程

```
第 1 层：<工单号>.zip          unzip -P <pwd> -q -d <dst>
第 2 层：*.tgz / *.tar.gz      tar -xzf -C <同名目录>
第 3 层：同第 2 层
第 4 层：同上（深度上限）
```

每一层处理完都执行一次审查：

1. **逃逸清理**：遍历符号链接，`realpath` 后不在当前根内的一律删除。删除失败同样终止，不允许 fail-open。
2. **配额累计**：已写字节 > 400 GiB 或文件数 > 50000 时终止。
3. **空间检查**：`shutil.disk_usage` 剩余低于 60 GiB 时终止。
4. **损坏判定**：解压进程返回码非零时，按 stderr 关键字映射错误码。

### 9.2 为什么不递归到任意深度

实测最深 3 层。固定上限 4 层既覆盖真实数据，也避免恶意归档构造的无限嵌套。
超限时明确报 `depth-exceeded`，而不是静默丢弃。

### 9.3 原子发布

```
1. 解压至  /sf/tickets/.tmp/<id>-<uuid>/
2. 全量校验通过
3. 若目标存在 → rename 到 /sf/tickets/.trash/<id>-<ts>/
4. rename /sf/tickets/.tmp/<id>-<uuid>/  →  /sf/tickets/<id>/
5. 成功后再清理 .trash（保留最近一次）
```

关键点：**步骤 4 是同一文件系统内的 rename，原子且不需要额外空间**。这是保证用户
永远看不到半成品目录的唯一手段。

## 10. 部署

### 10.1 目录与权限

```
/opt/hci-ticket-sync/                属主 node:node
├── .venv/
├── app/
└── pyproject.toml

/etc/hci-ticket-sync/                属主 node:node，目录 700
├── ticket-sync.env                  600
└── id_ed25519                       600
```

### 10.2 配置文件

`/etc/hci-ticket-sync/ticket-sync.env`：

```dotenv
TICKET_SOURCE_HOST=192.168.0.2
TICKET_SOURCE_PORT=22468
TICKET_SOURCE_USER=acli
TICKET_SSH_KEY=/etc/hci-ticket-sync/id_ed25519
TICKET_ARCHIVE_PASSWORD=<归档密码>
TICKET_ROOT=/sf/tickets
TICKET_LISTEN_HOST=192.168.0.4
TICKET_LISTEN_PORT=18080
TICKET_MAX_ARCHIVE_BYTES=21474836480
TICKET_MAX_EXTRACT_BYTES=429496729600
TICKET_MIN_FREE_BYTES=64424509440
TICKET_MAX_FILES=50000
TICKET_MAX_DEPTH=4
TICKET_CONCURRENCY=2
```

密码只存在此文件，不入库、不进集群 Secret、不进镜像。

### 10.3 systemd unit

`/etc/systemd/system/hci-ticket-sync.service`：

```ini
[Unit]
Description=HCI 工单日志同步服务
After=network-online.target

[Service]
Type=simple
User=node
Group=node
WorkingDirectory=/opt/hci-ticket-sync
EnvironmentFile=/etc/hci-ticket-sync/ticket-sync.env
ExecStartPre=/bin/sh -c 'rm -rf /sf/tickets/.tmp/* 2>/dev/null || true'
ExecStart=/opt/hci-ticket-sync/.venv/bin/uvicorn app.main:app \
  --host ${TICKET_LISTEN_HOST} --port ${TICKET_LISTEN_PORT} \
  --no-access-log
Restart=always
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

说明：`User=node` 是硬要求。`/sf/tickets` 属主是 `node:node`，以其他身份运行
要么写不进去，要么写出的文件 DSH 无法读取。

### 10.4 DSH 侧挂载

values：

```yaml
tickets:
  enabled: true
  hostPath: /sf/tickets
  mountPath: /data/tickets
```

Deployment 增加一个卷与一个挂载点，可写、不设 readOnly。除此之外 DSH 无任何改动：
镜像仍是官方 npm 包，启动参数、token 机制、sidecar 均不动。

### 10.5 admin-ui 侧

1. `frontend/admin/nginx.conf` 增加反代：

```nginx
location /ticket-sync/ {
    set $upstream ${TICKET_SYNC_UPSTREAM};
    proxy_pass $upstream;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_read_timeout 30s;
}
```

2. `frontend/admin/Dockerfile` 增加默认值
   `TICKET_SYNC_UPSTREAM=http://192.168.0.4:18080`。

3. `DshDiagnosisView.vue` 的 `dsh-actions-bar` 内增加工单号输入框、同步按钮与进度区。

## 11. 安全

| 面 | 措施 |
|---|---|
| 入口 | 只经 admin-ui 登录后访问；nginx 只代理三个端点 |
| 监听 | 绑定 `192.168.0.4`，不监听 `0.0.0.0` |
| 工单号 | 服务端强制 `^Q\d{13}$`，拒绝任何路径分隔符 |
| SSH 私钥 | `0600`，属主 node，仅用于 `acli@0.2` |
| 密码 | 仅本地 env 文件；不写日志、不出现在响应中 |
| 进程 | `NoNewPrivileges`、`PrivateTmp`，以非特权用户运行 |

**已知残余风险**：`unzip -P <密码>` 会让密码出现在该进程的 `argv` 中，宿主机上
其他用户可通过 `ps` 看到。当前宿主机为单用户运维环境，接受此风险；若未来引入
多租户，需改为在进程内解密或使用支持密码的库。

## 12. 可观测性

- 日志：写 stdout，由 journald 收集。每条任务日志带 `ticket=<工单号> job=<uuid>`。
- 关键节点：受理、开始拉取、拉取完成（字节数与耗时）、每层解压（层号、字节、文件数）、发布完成、失败（错误码与 stderr 摘要）。
- 指标：`/health` 暴露活跃任务数与磁盘余量；需要接入监控时再加 `/metrics`。
- 排查入口：`journalctl -u hci-ticket-sync -f`。

## 13. 验收

| 场景 | 期望 |
|---|---|
| 113 MB 工单 | 端到端 < 30 s |
| 989 MB 工单 | 端到端 < 3 min |
| 6.4 GB 工单 | 端到端 < 20 min，前端进度持续更新 |
| 不存在的工单号 | 5 s 内返回 `not-found` |
| 格式错误的工单号 | 立即返回 `invalid-ticket-id` |
| 密码错误 | 返回 `bad-password`，不留下 `.tmp` 残留 |
| 重复点击 | 第二次返回 `409` |
| 服务重启 | `.tmp` 被清空，可重新触发 |
| 目标已存在且一致 | 直接返回 `ready`，不重复解压 |
| DSH 选择目录 | 能看到完整文件树，可正常读取 |

## 14. 回滚方案

1. `systemctl disable --now hci-ticket-sync`
2. 删除 `/etc/systemd/system/hci-ticket-sync.service` 后 `systemctl daemon-reload`
3. 删除 `/opt/hci-ticket-sync` 与 `/etc/hci-ticket-sync`
4. helm 侧移除 `tickets` 卷与挂载
5. admin-ui 侧移除反代与按钮

数据目录 `/sf/tickets` 不删除，避免误伤已同步产物。

## 15. 与旧方案对比

| 维度 | 旧（DSH 内实现） | 新（宿主机服务） |
|---|---|---|
| 改动范围 | 34 文件 / 2208 行 | 约 8 文件 / 700 行 |
| DSH 镜像 | 二开源构建 | 官方 npm 包 |
| 工具链 | BusyBox，缺 `-P`/`-Z1` | GNU，能力完整 |
| 修改生效 | 重建镜像 + 滚动更新 | 重启进程 |
| 影响现有容器 | 需改 DSH 镜像与 helm | 不涉及任何容器 |
| 状态一致性 | 同进程内天然一致 | 单实例内存状态 |
| 运维范式 | GitOps | systemd（例外） |
| 失败恢复 | Pod 重启可能中断 | 服务重启后重跑 |

## 16. 实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| S1 | 本地跑通：命令行触发单工单同步与解压 | `/sf/tickets/<id>/` 内容完整 |
| S2 | 封装 FastAPI 三端点与任务表 | `curl` 可创建任务并查到进度 |
| S3 | systemd 部署 + 配置分离 | 重启后自动恢复监听 |
| S4 | DSH 挂载 + admin-ui 输入框与轮询 | 页面点击即可完成 |
| S5 | 三档体积压测与异常场景回归 | 第 13 节全部通过 |
