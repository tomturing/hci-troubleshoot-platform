# KBD 任务管理命令与参数重构方案

## 背景与需求

`data-pipeline/kbd` 的本质是任务管理工具。旧 CLI 把同一个阶段拆成不同命令和覆盖参数（`--force-fetch`、`--override`、`--failed-only`、`--resume-run-id` 等），导致“是否执行、执行结果、是否重做”被不同参数重复表达，组合语义依赖操作者猜测。需求是删除旧入口和兼容层，建立六个 Stage 的统一生命周期模型，并让每次选择可审计、可重现。

六个 Stage 为 `fetch`、`import`、`classify`、`vision`、`extract-signals`、`review-signals`；Vision 还必须记录每个图片子任务的结果。

## 方案（WHAT）

### 1. 一个任务模型

每个 `support_id + stage` 是一个任务，状态只保留三类事实：是否执行（`executed`）、是否成功（`success`）、是否要求重做（`rework`）。包含多个子任务的 Stage 以 `support_id + stage + item_id` 记录子状态，案例状态由子任务聚合。

### 2. 一个入口、四种互斥模式

统一入口：

```bash
uv run python -m data-pipeline.kbd.run task \
  --ids 29351 --stages vision
```

模式严格三选一：

| 模式 | 选择条件 |
|---|---|
| 无模式参数（默认） | 未执行或失败 |
| `--resume` | 仅未执行 |
| `--failed` | 仅失败 |
| `--rework[=STATUS_LIST]` | 不论成功/失败均重做；默认只处理 `draft`，支持 `draft,published,rejected,archived` 多选 |

`--resume`、`--failed`、`--rework` 任意组合在 argparse 阶段直接报错。`--rework` 状态允许 `draft`、`published`、`rejected`、`archived`；published 任务不能覆盖当前生效版本，必须进入 maintenance working revision，并重新经过专家/运行时审查后才能发布。

六个 Stage 子命令保留为统一入口的便捷别名，并且完全共享上述参数。`cli` 作为统一 `task` 的交互式前端保留；旧的 `pipeline`、`--force*`、`--override*`、`--failed-only`、`--resume-run-id` 不再暴露或兼容。

### 3. 输入范围与执行实例分离

`--ids`、`--excel`、`--id-file`、`--run-id` 为互斥的任务范围输入。`--run-id` 只读取历史运行生成的不可变 manifest（ID、请求阶段、已选任务），不再复用为本次日志 ID；每次执行生成新的 `execution_id`。交互式 `cli` 默认按“手动 ID、历史 run-id、ID 文件、Excel”顺序展示范围来源，并列出最近 10 个 manifest 供选择。

### 4. Stage DAG 与计划审计

依赖为：

```text
fetch → import → (classify ∥ vision) → extract-signals → review-signals
```

`--stages` 默认 `all`；指定阶段时自动补齐未满足的前置依赖。执行前必须输出用户请求阶段、依赖补齐阶段、最终阶段和各阶段任务数量，禁止静默补齐。已成功的依赖只作为 ready，不会重复调用；本次选中但失败的依赖会明确阻断下游。

### 5. 状态持久化

`KBD_LOGS_DIR/task-state.json` 是跨运行任务账本，使用临时文件替换写入；`KBD_LOGS_DIR/task-manifests/<execution_id>.json` 是不可变任务清单。运行 progress 仅记录观测，不代替任务真相。Vision 结果须保存案例级及图片 `seq` 级状态。

## 决策依据（WHY）

- 统一参数直接对应任务生命周期的三个事实，消除阶段专用开关的同义重复和组合歧义。
- 默认“未完成 + 失败”符合无人值守修复的最小惊讶原则；`resume` 和 `failed` 是明确的排障边界。
- `rework` 单独表达破坏幂等性的意图，状态范围显式化，避免误重做 published 数据。
- 历史范围与当前 execution 分离，manifest 不可变，才能重现“当时到底选了什么”。
- DAG 自动补齐解决阶段单跑的边界错误，同时把补齐计划打印出来，兼顾易用性与可审计性。
- `cli` 只作为统一 `task` 的交互式参数收集器，执行仍复用同一计划和编排路径，避免两套语义长期漂移。

## 影响范围

- CLI：`data-pipeline/kbd/run.py`；编排：`pipeline.py`；阶段实现增加统一 `rework` 传递。
- 状态：新增 `task_manager.py`、`task_state.py` 及 manifest 文件。
- 文档、单元测试和操作手册同步更新。
- published rework 只产生 maintenance working revision，不改变当前发布版本。

## 验收标准

1. 四种模式的选择集合分别为 pending+failed、pending、failed、all，三者任意组合参数校验失败。
2. `--stages` 默认 all；指定阶段的依赖按 DAG 补齐并在计划中可见。
3. `--run-id` 只能读取不可变 manifest，当前 execution_id 独立生成。
4. Vision 能审计到每张图片的执行与成功/失败状态；失败案例不会被历史数据库行伪装成 ready。
5. 旧入口和旧参数不再出现在 `--help`，相关旧单元测试已删除/改写。
6. KBD 单元测试、后端相关测试、ruff 和 `git diff --check` 全部通过。
