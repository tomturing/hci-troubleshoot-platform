## 一、问题与可验证的物理事实

客户 Windows 现场（`v2.36.0-79-gb4850cf7`，即端口修复版）双击 exe 后"闪退"，页面持续显示「SSH Bridge 未运行」。日志事实链：

| 事实 | 证据 |
|------|------|
| 端口没有冲突：`bridge.listening` 记录 `127.0.0.1:9999` 就绪 | seq3 |
| 进程存活 18 秒后退出 | 02:57:36.259 → 02:57:54.556 |
| 退出是**优雅退出**：`bridge.shutdown` `signal=terminated`、`active_sessions=0`、`uptime_seconds=18` | seq6 |
| 全程**没有一条 `bridge.connected`**（连接与探针都会落该事件） | `terminal_bridge/dispatch.go:33` |
| 无 `bridge.panic`、无 `bridge.port_conflict` | seq 连续 1→6 |

## 二、根因一：`terminated` 在 Windows 只可能来自三种控制台事件

Go 1.25 `src/runtime/os_windows.go` 的 `ctrlHandler`：

```go
case _CTRL_C_EVENT, _CTRL_BREAK_EVENT:
    s = _SIGINT        // 日志 signal=interrupt
case _CTRL_CLOSE_EVENT, _CTRL_LOGOFF_EVENT, _CTRL_SHUTDOWN_EVENT:
    s = _SIGTERM       // 日志 signal=terminated
```

由此可排除：Ctrl+C（会显示 `interrupt`）、panic（有 `bridge.panic`）、`taskkill /F` 与任务管理器「结束任务」及安全软件强杀（走 `TerminateProcess`，收不到任何信号，只会「有 startup 无 shutdown」）。

结论：本次是**控制台窗口被关闭**（`CTRL_CLOSE_EVENT`），不是崩溃、不是被强杀。同时暴露一处**错误认知**：原注释写着"Windows 关闭控制台窗口走 TerminateProcess，进程收不到任何信号"，与 runtime 实现相反，会把排障者引向"被强杀"的错误结论。

## 三、根因二：页面探测从未到达进程

18 秒零 `bridge.connected` → 前端一次探测都没打到本机端口。前端连的是 `ws://localhost:<port>`（`terminal.ts` 历史实现），而 Bridge 只绑 `127.0.0.1`（IPv4 回环）：

- `localhost` 在部分 Windows（hosts 写死 `::1`、或 IPv6 优先且不回退）上解析到 `::1`，连接不到 IPv4-only 的监听；
- 系统/浏览器代理若未排除回环地址，`ws://localhost:9999` 会被代理吞掉，握手不达本机。

两者都表现为"进程明明在跑、页面一直说未运行"，与本次日志完全吻合。

## 四、修复

| 层级 | 改动 | 位置 |
|------|------|------|
| 可观测性 | 注册只读控制台探针（`SetConsoleCtrlHandler`，处理器返回 `FALSE` 以保证 runtime 的 SIGINT/SIGTERM 投递不受影响），把事件码记进 `bridge.shutdown.extra.console_event` | `terminal_bridge/console_ctrl_windows.go`、`terminal_bridge/console_ctrl_other.go` |
| 认知纠错 | 重写退出信号注释，明确 CTRL_CLOSE/LOGOFF/SHUTDOWN → SIGTERM，只有 TerminateProcess 才无声消失 | `terminal_bridge/main.go` |
| 探测 | 桌面模式探测/连接串由 `ws://localhost:<port>` 改为 `ws://127.0.0.1:<port>` | `frontend/customer/src/api/terminal.ts` |
| 引导文案 | 「未运行」引导补「窗口不要关闭」与「确认浏览器未通过代理访问 127.0.0.1」 | `frontend/customer/src/components/SshConnectSection.vue` |

## 五、验收标准

| 编号 | 场景 | 期望 |
|------|------|------|
| V1 | 双击启动后关闭控制台窗口 | 日志 `bridge.shutdown` 带 `signal=terminated` + `console_event=ctrl_close`，进程正常退出 |
| V2 | Ctrl+C 退出 | `signal=interrupt` + `console_event=ctrl_c` |
| V3 | `taskkill /F` | 只有 `bridge.startup`，无 `bridge.shutdown`（与关窗可区分） |
| V4 | 浏览器打开页面点「重新检测」 | 日志出现 `bridge.connected`，页面转「已连接」 |
| V5 | 浏览器配置了不排除回环的系统代理 | 页面仍能连上（连接串已是 `127.0.0.1`），或错误提示指向代理排查 |

本地已验证：`gofmt` / `go vet` / `go test ./...`（Linux，含新增空实现用例）、`GOOS=windows GOARCH=amd64` 交叉编译与测试编译通过；前端 `vitest run` 与 `vite build`（含 `vue-tsc`）通过。Windows 侧 `console_event` 与 `127.0.0.1` 探测需现场按 V1/V4/V5 复验。

## 六、失效边界（对抗性审查）

- `console_event` 依赖 `SetConsoleCtrlHandler` 注册成功；窗口化（无控制台）运行时会失败并静默降级，只少一个诊断字段，不影响退出行为。
- 探针只在 Windows 生效；Linux/macOS 平台 `console_event` 缺省，退出原因仍由 `signal` 表达。
- 改 `127.0.0.1` 只解决"解析/代理把回环流量带走"，不解决"用户没点刷新"这类流程问题——引导文案已补一句，但探针仍需用户触发或页面轮询。
- 用户关窗仍会导致 Bridge 退出（本次刻意不改退出语义）：真正消除该形态需 GUI 子系统 + 托盘常驻，属产品口径变更，不在本次范围。
