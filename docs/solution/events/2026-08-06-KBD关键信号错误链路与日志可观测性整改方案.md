# KBD 关键信号错误链路与日志可观测性整改方案

## 背景与需求

KBD23821 编辑保存失败时，前端仅显示“关键信号未满足当前关键信号规则”，网关只留下 422，kb-service 没有足够上下文。复现 payload 后确认第二条信号使用 `qfk_log` 采集 `sfvt_vtpdaemon.log`，Catalog 将其识别为 `vtpdaemon/timestamped_lines`，该日志源只允许 `keyword/regex/state/threshold/exists`，不支持 `delta`。同时 `minimum_samples=2` 与 `cardinality=last` 存在后续样本不足风险。

本事件将错误定位、日志记录、HTTP 错误协议和指标统一为可检索、可关联、可行动的契约。

## 方案（WHAT）

1. Signal 校验响应返回稳定 `code/location/signal_id/field_path/validation_reason/action`，明确“改哪条信号、哪个字段、允许哪些值”。
2. StructuredLogger 支持历史标准 logging 的 `%s` 调用，统一输出 `log_schema_version=1`，补齐 `critical`。
3. 所有服务注册 HTTPException、RequestValidationError 和未捕获异常处理器，日志记录 method/path/status/code/detail/request_id/trace_id，响应返回诊断响应头。
4. API Gateway 对 KBD 下游所有非 2xx 记录状态、错误码、字段定位和下游关联 ID，并透传 `X-Trace-Id`、`X-Request-ID`、`Retry-After` 等头。
5. kb-service 接入 HTTP 黄金信号指标，��新增 `hci_kbd_signal_validation_total{code,operation}`；KBD 保存开始日志只记录 payload digest、大小、信号数量和 ID，不记录正文/token。
6. Admin 前端兼容 `detail` 与共享 `error` envelope，展示稳定错误码和诊断编号，并按 signal_id 自动聚焦。

## 决策依据（WHY：为什么选此方案，为什么不选其他方案）

- 采用结构化字段 + 稳定错误码，因为自由文本无法聚合查询，也无法驱动前端定位和告警。
- 采用网关与下游双层记录，因为只在任一层记录都会丢失责任边界；完整 payload 不进入日志，避免敏感信息泄漏和高基数。
- 采用 request/trace 双 ID：trace 用于分布式链路，request 用于单次 HTTP 诊断；不以任意一方替代另一方。
- 采用 Prometheus 计数器而非从日志反推错误率，避免采样、轮转和采集故障导致统计失真。
- 不把所有 HTTP 错误改成新的 envelope，保留现有 `detail` 兼容性，降低前端和外部调用方迁移风险。

## 验收标准

- KBD23821 payload 返回 422 时包含 `QFK_LOG_PREDICATE_UNSUPPORTED`、`signals[1]` 对应 signal_id、`match.type`、允许 predicate 列表。
- 网关日志可按 kbd_id、operation、code、signal_id、field_path、trace_id/request_id 查询，且不包含 Authorization 或完整 payload。
- 标准 `%s` 日志调用不抛异常，`critical` 输出完整异常信息；HTTPException 和请求体校验错误均有日志与诊断响应头。
- kb-service `/metrics` 产生 HTTP 请求指标和 signal validation 计数器。
- 前端能解析两种错误响应，展示错误码/诊断编号并聚焦信号；三个 LLM 长任务的成功/失败弹框保持不自动消失。
- Python lint、后端测试和前端构建通过。
