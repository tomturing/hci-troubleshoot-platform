# SOP 变量来源运行时门禁补强方案

## 背景

PR #450 已把 SOP Markdown 中的 `acli`、`container_exec`、`host_exec` 和裸 bash 命令归一化为结构化 `tool_calls`，并在 `sop_advance` 进入目标节点前检查缺失的 `user_input/user_confirm/env_*` 变量。

测试「磁盘寿命到期」时又发现一个更早的绕过路径：LLM 可以在调用 `sop_advance` 之前，先执行 `bash_exec/acli_exec`，自行判断 Markdown `【变量声明】` 中要求 `user_input` 的变量。例如：

```markdown
| is_sys_disk | boolean | user_input | 是否是系统盘 |
```

从第一性原理看，这不是单纯 Prompt 遵循度问题。变量声明的“来源”是 SOP 作者给出的控制面契约，不能只靠 LLM 自觉遵守；系统需要在工具执行前把该契约变成硬约束。

## 根因

当前链路有两层校验，但仍不完整：

1. `get_sop_node` 会把当前节点和候选分支的 `required_variables` 暴露给 LLM。
2. `sop_advance` 会在推进到目标节点前阻断缺失变量。
3. 但 `bash_exec/acli_exec` 等真实诊断工具在 `SopToolExecutor` 中直接委托给默认执行器，缺少 “before tool_call” 变量来源门禁。

因此，如果 LLM 没有先推进节点，而是直接执行诊断命令，就能绕过 `sop_advance` 的门禁。

## 设计目标

- 保持 SOP Markdown 低成本写法，不要求作者改 JSON。
- 不影响非 SOP 模式的普通诊断工具调用。
- 不阻断 SOP 导航工具本身：`get_sop_node`、`sop_request_variable`、`sop_advance` 必须继续可用。
- 对 `user_input/user_confirm/env_*` 等受控来源变量 fail-closed：变量未就绪时，不允许先执行真实诊断工具替代该变量来源。
- 返回结构化工具结果，让 ReAct 下一轮能按 `next_tool_call=sop_request_variable` 自我修正，前端工具卡也能正常闭合。

## 方案

在 `SopToolExecutor` 增加运行时变量来源门禁：

1. 对 SOP 导航工具直接放行。
2. 对其他真实工具调用前，读取 conversation-service 的当前 SOP 执行实例，获得 `current_node_id` 和 `context_variables`。
3. 从 kb-service 获取 SOP 决策树和 `variable_schema`。
4. 检查当前节点及其直接子节点引用的变量。
5. 若变量来源属于 `user_input/user_confirm/env_injection/env_context/env:*`，且 `context_variables` 中没有有效值，则不执行真实工具，返回：

```json
{
  "ok": false,
  "error": "sop_variable_gate_blocked",
  "message": "SOP 当前节点依赖变量 is_sys_disk，且该变量尚未按声明来源获取。请先调用 sop_request_variable。",
  "missing_variables": [
    {
      "name": "is_sys_disk",
      "type": "boolean",
      "acquisition_strategy": "user_input",
      "description": "是否是系统盘"
    }
  ],
  "next_tool_call": {
    "tool_name": "sop_request_variable",
    "args": {
      "variable_name": "is_sys_disk",
      "reason": "是否是系统盘"
    }
  }
}
```

## 边界

- v1 只检查当前节点和直接子节点。原因是当前节点决定“此刻该做什么”，直接子节点决定“下一步可选分支”；全树扫描会把未来分支变量提前阻断，误伤正常诊断。
- `tool_call/skill_call/sop_default` 不纳入本门禁。它们的来源本身允许系统自动获取或计算，应由 `sop_request_variable` 的策略引擎处理。
- 若无法读取执行实例、决策树或变量 schema，不做硬阻断，仅记录 warning 后放行，避免基础服务短暂异常导致 SOP 完全不可执行。后续可按验证结果收紧。
- 本门禁不替 LLM 自动调用 `sop_request_variable`，只返回 `next_tool_call`。这样工具调用路径仍保持可观测、可审计。

## 对用户问题的回答

该问题不主要由 Markdown 导入或编辑造成。导入/编辑会影响 `variable_schema` 是否正确落库，但这次额外发现的本质原因是运行时少了“真实工具调用前”的控制面门禁。即使 `variable_schema` 已正确保存为 `user_input`，只要门禁只放在 `sop_advance`，LLM 仍可在推进前先调用 `bash_exec`。

## 验收标准

- 当前节点或候选分支依赖 `user_input` 变量且未就绪时，`bash_exec/acli_exec` 不下发真实执行，返回 `sop_variable_gate_blocked`。
- 返回结果包含 `missing_variables` 和 `next_tool_call=sop_request_variable`。
- `get_sop_node/sop_request_variable/sop_advance` 不受门禁阻断。
- 变量已在 `context_variables` 中有非空值时，真实工具正常委托给默认执行器。
- 非 SOP 模式不受影响。
