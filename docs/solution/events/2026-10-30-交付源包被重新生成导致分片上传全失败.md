# 交付源包被重新生成导致分片上传全失败

- 日期：2026-10-30
- 现场工单：Q2026103000994
- 涉及：`terminal_bridge`（`delivery_handlers.go` / `delivery_job.go` / `delivery_runner.go`）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 界面报「平台返回 HTTP 500（平台暂时不可用）」，重试 8 轮后失败 | `deliveryRunner.runJob` 对该错误判定为 transient，预算取 `maxDeliveryTransientAttempts` |
| 提交时平台会话 total_size = 69,010,358 字节，切片 9 片（8 MiB × 8 + 末片 1,901,494） | 提交消息 `total_size` 即 init 会话返回的 total_size |
| 交付期间节点上的同名包被重新生成，变成 172,261,027 字节 | `prepareDirect` 用节点上 stat 到的真实大小覆盖了 `job.SourceSize` |
| 每片上传都被平台拒绝，且拒绝原因与分片内容无关 | 平台按**会话建立时的** total_size 校验每一片的 offset/length |

## 二、根因

交付作业里只有一个「大小」字段 `SourceSize`，它承担了两个互相冲突的语义：

1. **本地拉取的切片依据**——必须以节点上此刻的真实大小为准。历史缺陷「末片长度算错」正是
   沿用前端 stat 的旧值导致的，所以拉取前会覆盖成真实大小。
2. **平台会话的分片基线**——在上传 init 时就固定了，**不随文件变化**。

一旦包在提交之后被重新生成，第 1 条要求跟着新大小走，第 2 条仍按旧大小校验，两者分叉。
后果不是「偶发一片 500」，而是**每一片都对不上**：末片长度从 1,901,494 变成 8,388,608，
重试 8 轮必然全失败。界面把每片的 HTTP 500 翻译成「平台暂时不可用」，把用户的注意力
引向平台日志，而真正的原因在节点上——包变了。

## 三、本次改动

### 1. 拆出只写一次的会话基线

`deliveryJob` 新增 `SubmittedSize`：在 `handleDeliverySubmit` 建作业时写一次，
之后**任何阶段都不覆盖**（已持久化作业缺该字段时为 0，视为老数据）。

`SourceSize` 保留原语义（可被节点真实大小覆盖），不再兼职基线。

### 2. 两处守卫，都走 fatal（不重试）

`sourceSizeGuard(submitted, current)` 在同一字节都不放过；任一为 0 时放行（信息不足，
保持向后兼容）。

| 位置 | 时机 | 拦住什么 |
| --- | --- | --- |
| `prepareDirect` | 拉取**之前** | 补交付场景下包已被重新生成——避免白拉几十 GB |
| `upload` | 拉取之后、切片之前 | 拉取完成后本地副本被替换，或恢复旧作业时基线缺失 |

判定为 `deliveryFatalError`（不是 transient）是本改动的关键：会话基线不会因为等待而
重新对齐，重试只会把同一个 500 重复 N 轮。`runJob` 据此直接落 `phaseFailed`。

### 3. 错误文案指向真正的原因

文案包含两个具体字节数与明确动作：

> 源包已变化（提交上传时 69010358 字节，当前 172261027 字节），本次上传已作废：
> 平台上传会话仍按提交时的大小校验，继续上传只会每片都失败。
> 请重新点击「上传到平台」；若要交付最新内容，请先重新采集

同时**不得**出现「平台暂时不可用」——把责任推给平台会让现场去查平台日志。

## 四、验证

| 用例 | 期望 |
| --- | --- |
| `submitted == current` | 放行 |
| `submitted == 0`（老前端未上报） | 放行，保持原有行为 |
| `current == 0`（stat 失败） | 放行，交由后续环节报错 |
| 变大 / 变小 / 只差 1 字节 | 拦下，且必须是 `deliveryFatalError`、不得被识别为 transient |
| 错误文案 | 含「源包已变化」「本次上传已作废」「请重新点击」与具体字节数，不含「平台暂时不可用」 |

单测：`terminal_bridge/delivery_source_guard_test.go::TestSourceSizeGuard`。

## 五、已知边界

1. **基线为 0 时不做判断**：老前端（未上报 total_size）与恢复出来的历史作业都拿不到基线，
   此时退回原行为——仍可能重演本故障，但不会误杀正常作业。取舍是「宁漏不误杀」。
2. **只比对字节数，不比对内容**：同大小覆盖（重新打包后恰好等长）无法靠本守卫发现，
   需要 content digest，属后续项。
3. **平台侧仍会返回 500**：本改动只负责把「必然失败的 N 轮重试」提前成一次明确失败，
   不改变平台对超长/超短分片的判定。
