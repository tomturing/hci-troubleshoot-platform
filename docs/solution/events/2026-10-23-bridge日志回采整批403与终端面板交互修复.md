# bridge 日志回采整批 403（日志通道静默失效）与终端面板交互修复

## 一、现象

staging（acli.sangfor.com.cn:4443）用户反馈三件事：

1. SSH 终端黑色面板头部重复显示「SSH 终端」（与抽屉标题重复，且被挤压换行）；
2. 「📹 终端历史」按钮点击无任何反应；
3. 浏览器网络面板中 `POST /api/bridge-logs` 持续返回 **403 Forbidden**。

## 二、实测证据（2026-10-23 hci-staging）

```
# 最近落库时间：距离实测时间已断 3 天
total=16135  first=2026-09-01 10:28  last=2026-10-20 01:51

# 当前 conversation-service pod（5h14m）内
bridge_log_ownership_forbidden = 471 次（case_id 分布：Q2026101401684 × 357，terminal-only × 132）
bridge_logs_ingested           = 0 次
```

结论：**不是"部分日志延迟"，而是回采通道整体失效**——只要客户端一旦产生过一条越权/伪工单号的日志，
其后所有合法日志都进不来。403 响应体长度 43 字节，与 `{"detail":"无权操作此工单的日志"}` 完全吻合，
可确定 403 来自 conversation-service 的批次归属校验，而非网关鉴权。

`Q2026101401684` 在 `case` 表中的 `client_id = ui-verify-manual`，与当前浏览器 Cookie 身份
（`b0b79f63…`）不一致；`terminal-only` 是前端"无工单 SSH 会话"的伪工单号，`case` 表必然查不到。

## 三、根因链（四个环节叠加）

| # | 环节 | 缺陷 |
|---|------|------|
| 1 | bridge 侧 | 无工单会话的日志 `case_id = terminal-only`，不是真实工单号 |
| 2 | 前端入队 | `forwardBridgeLog` 原样透传 `case_id`，只对"空值"做兜底，伪工单号被当成真工单 |
| 3 | 后端校验 | `_verify_batch_ownership` 对批次内**全部** case_id 严格校验，任一不存在/不属主即整批 403 |
| 4 | 前端重试 | 把 403 当可重试错误，指数退避重试 5 次后丢弃整批，且在 `localStorage` outbox 中反复恢复 |

其中第 3 步是放大器：它把"一条脏数据"升级为"整条可观测链路失效"。安全目标本是
**不写入他人工单的日志**，而整批拒绝只是把合法日志一起枪毙，属于用错了手段。

## 四、修复

### 4.1 后端：逐条归属过滤，替代整批 403

`conversation-service/app/routes/bridge_logs.py`

- `_verify_batch_ownership` 改为返回 `forbidden: set[str]`，不再抛 403；
- `_authenticate_batch` 返回 `(user_id, forbidden_cases)`；
- `ingest_bridge_logs` 写库前按 `case_id or fallback_case_id` 判定，越权条目计入 `forbidden` 后跳过，
  其余条目正常落库；响应新增 `forbidden` 计数。
- 手动上传 `/api/bridge-logs/upload` 仍保留整单 403（单次显式动作，整单拒绝语义清晰）。

安全边界未变：越权 case 的日志一条都不会写入；仅不再因单条越权拒绝整批。

### 4.2 前端：伪工单号归一 + 永久错误不重试

`frontend/customer/src/stores/chat.ts`

- 新增 `normalizeBridgeLogCaseId`：`terminal-only` / `default` / 空值统一归一为当前工单；
  没有当前工单则丢弃并计数（原 `bridgeLogDroppedCount` 机制保留）；
- `flushBridgeLogs` 发送前对整批再归一一次（覆盖 `localStorage` outbox 中的历史脏条目）；
- 4xx（除 408/429）判定为永久错误：只失败一次，立即丢弃本批并写入 `__bridgeLogStats.lastError`
  （`http_403: …`），不再指数退避重试拖死后续日志。

### 4.3 终端面板交互

`frontend/customer/src/components/TerminalPanel.vue`、`ChatWindow.vue`

- 删除面板头部重复的「SSH 终端」标题；
- 「终端历史」不再按 `terminalState === 'A'` 静默禁用。原因：已连接但无工单（terminal-only 会话）
  时按钮可点，父组件 `currentCase` 为空直接 `return`，表现为"点了没反应"。
  现改为可点击 + 明确提示「终端历史按工单归档，请先创建工单或在日志收集中指定工单号后再查看」，
  tooltip 同步说明。
- 回放目标工单改为 `currentCase?.case_id || logCollectCaseId`：日志收集入口在无聊天工单时
  会按用户指定的工单号建档/复用（见 4.4），采集会话的录像就挂在该工单上。只看 `currentCase`
  会让"日志收集已建单"的用户依然点不出历史。

### 4.4 日志收集与工单的关系（澄清一个常见误解）

日志收集入口**确实会建单**，但有条件：`POST /api/cases/resolve` 的语义是
"该工单号不存在 → 用该号建档（`client_id` = 当前身份）；已存在 → 直接复用"。因此：

- 输入一个平台里不存在的号 → 立刻建单，终端历史/回采都能用；
- 输入一个**已存在但属于其他身份**的号 → 不建单，直接复用对方的工单号。此时 bridge 侧
  产生的日志会带上该 `case_id`，而回采落库要求 `case.client_id == 当前身份`，
  于是这些日志**必然被拒**（本次修复后是逐条跳过，不再阻塞其他工单）。
- 无论哪一种，绑定的工单此前只写进 `logCollectCaseId`，没有写进 `currentCase`，
  所以"日志收集建了单但终端历史仍无反应"是两个独立缺陷叠加的结果。

### 4.5 跨身份复用他人工单：`resolve` 暴露 `owned`

问题：`POST /api/cases/resolve` 允许复用他人工单（方案 A）。采集能成功，但日志回采
（`bridge_execution_logs`）与终端录像回放（`/terminal-recordings`）都要求
`case.client_id == 当前身份`，跨身份复用会 100% 被拒——用户只看到“采集完成、日志没上来”。

修复（不破坏“用外部单号补采”的运维场景，只把事实提前告知）：

- case-service：`resolve_case_for_log_collect` 返回 `(case_id, created, owned)`；已存在时
  `owned = existing.client_id == client_id`，新建时 `True`，并发冲突后重新查库确认归属；
- `POST /api/cases/resolve` 响应新增 `owned`；
- customer：store 新增 `logCollectCaseOwned`，面板在 `owned === false` 时显示警告条
  「该工单属于其他会话身份」，明确“采集可继续，但日志回传与录像回放会被拒绝”；
- customer：`flushBridgeLogs` 把成功响应里的 `forbidden` 计入 `dropped`，`ingested`
  不再按 `batch.length` 虚增（消除“已入库”的静默误报）。

向后兼容：旧后端不返回 `owned` 时前端按已归属处理（`owned !== false`），不误报。

## 六、遗留与边界

- **跨身份复用他人工单已可见**：`resolve` 现返回 `owned`，面板会提前告知“日志回传会被拒”，
  但工单归属本身仍未被拒绝（方案 A 保留）。若后续要求“日志一定能回传”，需把策略改为
  拒绝复用他单，或回采时自动落回一个本人可写的采集单。
- 越权工单（如 `ui-verify-manual` 造的测试工单）在浏览器中被继续使用时，其**终端录制回放**
  （`/terminal-recordings`）仍会被整单拒绝；这属于"浏览器持有他人工单"的独立问题，
  需从工单分配/身份恢复侧解决，不在本次范围。
- 后端未对 `terminal-only` 做特殊处理：伪工单号是前端约定，归一责任保留在客户端，
  避免服务端硬编码前端协议值。
