# 中继卡顿可见性与重试留痕

- 日期：2026-10-31
- 关联：Q2026102801062（代传长任务期间界面只有 running，无法判断是在传还是已卡死）
- 涉及：`backend/case-service`（model / relay service / snapshot）、`database/desired_schema.sql`、`frontend/customer`

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 单片上传超时 300s，期间 `relay_chunk_index` 不前进 | `SangforRelayClient(chunk_timeout=300.0)`；index 只在该片**成功后**才写 |
| `relay_status` 五态里没有"卡住"，一直是 `running` | `ck_log_collect_relay_status` 约束 |
| `relay_restarts` 记的是"会话被丢弃重建"次数，不是重试轮次 | `_run` 中仅 `init_upload` 重建时 `restarts += 1` |
| 失败原因只在**终态**落库（`_finish`），中间轮的失败原因完全丢失 | `_run_with_retry` 的 catch 分支只做退避，不写库 |

## 二、根因

界面只有一个粗粒度状态（`running`），而**"正在传一片很慢"和"进程已经卡死"在状态机上是同一个值**。
用户唯一的观测量是进度数字，而这个数字在单片 300s 窗口内必然不动——于是"不动"既不能证明坏，也不能证明好。

再加一层：瞬时失败被重试吞掉了。重试成功时用户永远不知道"刚才失败过一次"；重试耗尽时只剩终态那一句，前面几轮发生了什么不可考。

**结论：缺的不是更短的超时，而是让"过程"可见。** 缩短超时只会把同样的不可见性搬到更短的时间尺度上。

## 三、本次改动

### 1. 新增三列（Atlas 声明式，改期望 Schema + 模型）

| 列 | 语义 |
| --- | --- |
| `relay_attempt integer NOT NULL DEFAULT 0` | 当前（或最近一次）**整轮**尝试序号，与 `relay_restarts`（会话重建次数）严格区分 |
| `relay_last_error text` | 最近一次失败原因（含瞬时失败），截断 2000 字符 |
| `relay_last_error_at timestamptz` | 该原因的时间点 |

### 2. 写入时机（都在已有事务里，不新增写放大）

- **每轮开始** `_save(attempt=N)`：同时刷新 `relay_updated_at`，兼作"进程还活着"的心跳；
- **每次 catch** `_save(last_error=...)`：先落库再决定是否重试，避免瞬时失败的原因被重试吞掉；
- **成功终态** `_finish(success)` 清空 `relay_last_error` / `relay_last_error_at`：已交付的任务不该挂着一条历史错误，否则现场第一反应是"是不是又坏了"。

### 3. 透出与展示

`snapshot()` 增加 `relay_attempt` / `relay_last_error` / `relay_last_error_at`；前端 `describeRelayProgress`
把它们拼进进度行：

| 快照 | 展示 |
| --- | --- |
| 第 3 片 / 共 10 片，第 1 轮 | `第 3/10 片` |
| 同上，第 3 轮 | `第 3/10 片 · 第 3 次尝试` |
| 同上，且上一轮失败 | `第 3/10 片 · 第 3 次尝试 · 上次失败：5888 返回 503` |
| 只有总片数 | `共 409 片，准备中` |
| 什么都没有 | `准备中`（不编造） |

第 1 轮是常态，**不**显示"第 1 次尝试"——只有真的重试过才占位，避免每行都带噪声。

顺带修掉结果态另一处「归档失败（详见平台任务记录）」：结果态本身就渲染 `error_code`/`error_message`，
再把用户指去查同一份数据，只会让"记录是空"的现场更困惑。

## 五、已知边界

1. **超时值未动**：`chunk_timeout` 仍 300s。本次只解决"看不出来"，不改变"慢片要不要更早放弃"这个策略问题。
2. **`relay_last_error` 是"最近一次"而非"全部"**：只保留最后一条，多轮历史不落库（保留全量需要事件表，另立项）。
3. **列默认 0 / NULL**：存量任务不受影响，前端对缺失值一律降级为"准备中"。
4. **断点续传仍以 `relay_chunk_index` 为准**：本次不改续传判定，只增加展示字段。
