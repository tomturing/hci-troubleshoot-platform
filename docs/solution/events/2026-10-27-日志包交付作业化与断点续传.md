# 日志包交付作业化：断点续传与资源自适应

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：交付状态落盘为 job、执行权从浏览器搬到 bridge、P1 失败自动降级 P2、complete/relay 由 bridge 收尾、按资源自适应并发 | 无独立任务文档 |

---

## 一、要解决的问题

「日志包交付」指把 acli 在 HCI 节点上产出的 zip（几十 MB ~ 20 GB）送到日志服务器。
它与 bridge 自身运行日志是**两条完全不同的链路**：

| | bridge 运行日志（证据链） | acli 日志包（交付链，本文） |
|---|---|---|
| 体积 | KB | GB |
| 生产者 | bridge 进程 | 节点上的 acli 插件 |
| 链路 | bridge → 平台 | HCI → bridge 本地 → 平台分片 → 日志服务器 |

旧交付链的 5 个断点：

| # | 断点 | 后果 |
|---|---|---|
| 1 | 执行权在浏览器（`sendAndWait('transfer', 2h)`） | 页面一关，无人驱动 |
| 2 | 状态只在 goroutine 内存 | 进程一死全丢，只能重头来 |
| 3 | 失败即终止 | 弱网一次抖动 = 整包重传 |
| 4 | 没有可恢复的作业概念 | 「接管」只能重新 create |
| 5 | `complete + relay` 由前端调 | 上传完成后关页面 → 包在平台但不归档 |

## 二、三条产品决策（本次落地口径）

### 决策 1：P1 仍为默认，但失败时**自动降级 P2**

P1（acli 直传日志服务器）不占 bridge 带宽与 CPU、少一次中转，实测稳定性更好，因此保持默认。

关键事实：**插件只有直传成功后才自删压缩包**（见 `probeLogCollectArchiveSize` 注释）。
所以 P1 失败时源包仍在节点上 → 可以无损切到 P2 续传。

落地：`finishP1` 抛错时执行 `fallbackToP2`：

1. 用 `stat` 确认源包还在（不在 = 多半其实传成功了，不降级）；
2. 平台任务标 `upload_mode=bridge_relay`；
3. 走与 P2 完全相同的作业化交付。

这样既保留「P1 快且不占资源」，又不会因为直传失败而丢包。

### 决策 2：`complete + relay` 由 bridge 收尾

新增数据面端点 `POST /api/direct/log-collect-uploads/{task_id}/complete`：

- 鉴权用 `X-Upload-Token`（init 时签发、绑定 task_id），**不需要客户 Cookie**；
- 合并成功后由平台**自动触发代传**（`relay_service.trigger` 幂等）；
- 因此整条链从 submit 到归档都不再依赖浏览器。

### 决策 3：并发按主机能力自适应，且可强制兜底

| 维度 | 默认 | 高配 | 上限 |
|---|---|---|---|
| 跨任务并发 | 1 | 内存≥8GB 且 CPU≥8 核 → 2 | 2 |
| 任务内分片并发 | 1 | 4GB/4 核 → 2；8GB/8 核 → 4 | 4 |

- 内存探测：Windows `GlobalMemoryStatusEx`（可用物理内存）、Linux `/proc/meminfo` 的 `MemAvailable`；
- 分片缓冲预算只用可用内存的 **1/8**，再按 `chunk_size` 折算；
- 探测失败一律回落到 **1**（宁可慢，不可抖）；
- 强制覆盖：`HCI_BRIDGE_DELIVERY_CONCURRENCY`（1–4）、`HCI_BRIDGE_DELIVERY_TASKS`（1–2）。
- **拉取永远单流**：多流会打爆 HCI 的磁盘 IO，且 `tail -c +N` 本身是顺序读。

## 三、状态机与持久化

```
created → waiting_collect → pulling → uploading → completing → done
              ↑                │          │            │
              └──── retry ─────┴──────────┴────────────┘
```

落盘：`<日志目录>/delivery-jobs/dj-<task_id>.json`，`tmp + rename` 原子写，
每 10 个分片或每 64MB 拉取落一次盘；终态保留 7 天后清理。

job_id 由 `task_id` 派生（`dj-<task_id>`），**前端不需要保存**：重开面板/重连后
直接用同一个 id 查 `delivery_status` 即可接上。

## 四、断点续传矩阵

| 中断点 | 恢复 | 不重做 |
|---|---|---|
| 拉取中断 | 按本地文件 size `tail -c +N` 续读 | 已拉字节 |
| 上传中断 | `uploaded_parts` 跳过 | 已传分片 |
| bridge 进程被杀 | 重启扫描 job 目录，回到中断阶段 | 全部 |
| 重启后无 SSH 凭据 | 标 `needs_reauth`，前端重连后 `delivery_resume` | 全部 |
| 本地临时包丢失 | 从 0 重拉，已传分片仍跳过 | 已传分片 |
| 平台分片会话过期 | 401 → `needs_reauth`，前端重新 init | 服务端已收 |
| 浏览器关闭 | **不做任何动作** | 全部 |

## 五、不干扰 acli 采集的三条硬保证

1. `waiting_collect` 阶段**只读** `acli log_collect progress`，绝不 `create`/`cancel`；
2. 完成判据是 `done == total && total > 0`，不是百分比；
3. 拉取只用 `tail -c +N` 只读，不写、不改 mtime、不锁文件。

## 六、可观测

事件：`delivery.runner_started`（含并发决策原因）/ `delivery.submitted` / `delivery.recovered` /
`delivery.collect_finished` / `delivery.job_finished` / `delivery.cancel`。

WS 消息：`delivery_submit` / `delivery_status` / `delivery_resume` / `delivery_cancel`
→ 回 `delivery_result`（`log_action` 区分，`log_data` 为 job 快照）。

## 七、验收

| # | 场景 | 判据 |
|---|---|---|
| V1 | 拉取中杀 bridge | 重启后从 `pulled_bytes` 续，不重拉全部 |
| V2 | 上传中杀 bridge | 重启后跳过 `uploaded_parts` |
| V3 | 采集中关页面 | 作业继续，重开面板接上轮询 |
| V4 | P1 直传失败且包仍在 | 自动切 P2 并完成归档 |
| V5 | P1 成功（包已删） | 不降级，原错误照实抛出 |
| V6 | 低配机（≤4GB） | 并发恒为 1，无换页抖动 |
| V7 | 上传令牌过期 | `needs_reauth`，重连后可续 |

单元测试覆盖：job 落盘/恢复/终态过滤、进度计算、分片去重、并发夹紧与内存预算。

## 八、边界（本 PR 不做）

1. 会话租约（WS 关闭仍销毁会话）——独立议题；
2. P1 的"部分成功"识别（插件既没自删又没报错）仍按失败处理；
3. 跨机器接管（作业文件不跨机器同步）。
