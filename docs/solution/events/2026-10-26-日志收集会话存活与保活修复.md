# 日志收集：会话假连接、失败定位与 SSH 保活

## 背景与需求

客户现场在「日志收集」面板连续遇到同一句报错：

```text
SSH 会话不存在（需先 ssh_connect）
```

两次现象连起来看才是完整问题：

1. 第一次：探测成功（架构/acli/可用空间都是真实回包），点「开始收集」后立刻报上面这句；
2. 第二次：**重新登录 SSH 之后仍然报同一句**，且阶段条停在第一步「探测」，看起来像根本没开始。

第二个现象排除了「浏览器 WebSocket 抖动导致会话被连坐销毁」这一解释——重登会重建会话，
若只是抖动，重登后应当恢复。因此需要重新拆解：**会话到底是什么，什么时候会消失，UI 凭什么
认为它还活着**。

## 事实核查（改动前的真实行为）

### 1. 会话的唯一载体是 Pod 内存 map

`terminal_bridge/main.go` 中 `Bridge.sessions` 是 `map[string]*SSHSession`，键为 `caseID@nodeIP`。
会话被删除只有四条路径：

| # | 路径 | 代码位置 | 现场特征 |
|---|---|---|---|
| 1 | 终端 WebSocket 断开 → 连坐清理 | `main.go` `handle()` defer 中 `ownedSessions.drain()` | 日志出现 `bridge.disconnected` |
| 2 | 远端 shell EOF | `main.go` `on_output_start()` 尾部 `onExit()` | 前端收到 `ssh_disconnected` |
| 3 | 同键再次 `ssh_connect` 覆盖 | `main.go` `case "ssh_connect"` 开头 | 两条同键 `ssh.connected` |
| 4 | 显式 `ssh_disconnect` / Pod 重启 | `main.go` `case "ssh_disconnect"` | 全部会话同时消失 |

### 2. 「当前 SSH 会话」是假连接

`LogCollectPanel.vue` 的 `sessionHost` 在未连接时回退到 `chatStore.lastSshHost`，而后者来自
`localStorage['hci_last_ssh_config']`（`chat.ts` `readLastSshHost`），跨刷新、跨重登都保留。
于是：

- SSH 已断开 → `sshConnectionState` 变 `disconnected`；
- 面板不卸载（`App.vue` 用 `v-if="logCollectCaseId"`，面板开着就不重建）；
- 界面继续显示「172.x 当前 SSH 会话」；
- `nodeIpReady` 只判断字符串非空，`handleStart` 只校验 `targetNode`，**不看连接状态**；
- 点「开始收集」→ 发一个注定失败的 `log_collect create` → `session_missing`。

`openLogCollect()` 的拦截只在**打开面板那一刻**生效，之后再断线没有任何通道能让面板感知。

### 3. 两套 `ssh_connect` 参数

| 路径 | 位置 | 是否带 `node_ip` |
|---|---|---|
| SSH 终端连接 | `chat.ts` `connectSSH()` | 带，键为 `caseID@host` |
| 建单集成流程 | `chat.ts` 创建工单后的连接 | **不带**，键退化为 `caseID` |

键退化的会话只能靠 `sessionByAddressHost()` 兜底（要求会话 `address` 的 host 与 `nodeIp`
逐字符相等），前两级（精确键、`@IP` 后缀）必然不命中。

### 4. 失败时阶段条恒停在第一步

`stepActive` 没有 `failed` 分支，落到 `return 0`；`progressStatus` 只把下面的进度条标红。
因此无论失败发生在采集、上传还是归档，阶段条都显示「卡在探测 + 一个红叉」。

### 5. 全程没有 SSH 保活

`ssh.ClientConfig` 只设了建连超时，全仓没有 `keepalive@openssh.com`、没有对底层 TCP 显式设置
`SetKeepAlive`。终端空闲或日志采集长跑时，这条连接上一个字节都不流，防火墙/NAT 老化映射后
会被静默丢弃；`x/crypto/ssh` 自身不做任何探测，半开连接要等到下一次业务写入才暴露。

## 方案概述 (WHAT)

1. **bridge 两层保活**：TCP `SetKeepAlive(30s)` + 应用层每 30s 发 `keepalive@openssh.com`
   （`HCI_BRIDGE_SSH_KEEPALIVE_SECONDS` 可调，`0` 关闭）。探测失败或 10s 无响应即 `close()`
   会话，让 pty 读循环 EOF 后走既有 `onExit` 清理，不新增清理链路。
2. **消除假连接**：`sessionHost` 只在 `sshConnectionState === 'connected'` 时有值；
   `handleStart` 与「刷新进度」前校验连接态，断开时提示重连而不是发必败请求。
3. **失败定位**：新增 `failedStep`，在 `stage` 变成 `failed` **之前**记录当时的步骤；
   `stepActive` 增加 failed 分支，`el-steps` 用 `process-status="error"` 标红真实失败步骤。
4. **键统一**：建单集成流程的 `ssh_connect` 补 `node_ip`，与终端连接用同一把键。
5. **可观测**：`log_collect.session_missing` 事件增加 `requested_key`、`active_sessions`、
   `session_keys`；保活失败记 `ssh.keepalive_failed`。

## 详细设计

### 1. 为什么保活失败要 `close()` 而不是直接摘除会话

会话的生命周期清理只有一条权威链路：`on_output_start` 的读者退出 → `onExit()` →
`b.remove(key)` + 前端 `ssh_disconnected`。保活若自己 `remove`，pty 读循环仍在跑，
会出现「map 里没了、goroutine 还在」的悬空会话，且前端收不到断线通知。
因此保活只负责**判定**，清理仍交给既有链路。

### 2. 探测口径：`REQUEST_FAILURE` 不算失败

`SendRequest("keepalive@openssh.com", true, nil)` 在服务端不认识该请求时返回
`(false, nil, nil)`——这是链路正常的证据（OpenSSH 会回 `REQUEST_FAILURE`）。
只有传输层错误、或超过 `sshKeepAliveProbeTimeout`（10s）无响应才判定失效。
后者是必需的：半开连接上写操作可能永久阻塞，不能让保活 goroutine 自己卡死。

### 3. 显式建连换取 TCP 保活

`ssh.Dial` 内部用 `net.DialTimeout`，无法指定 `KeepAlive` 周期。改为
`net.DialTimeout` → `SetKeepAlive`/`SetKeepAlivePeriod` → `ssh.NewClientConn` → `ssh.NewClient`。
副作用：地址拼接必须换成 `net.JoinHostPort`，否则 IPv6 字面量会解析失败（`go vet` 会直接报）。

### 4. 前端为什么不再回退 `lastSshHost`

`lastSshHost` 的正当用途是**预填登录表单**，不是「会话存在」的证据。把它当作连接态使用，
会同时造成两种误判：界面显示已连接（用户被骗），以及请求发往不存在的会话（噪音日志）。
断线时 `nodeIp` 为空 → `nodeIpReady=false` → 面板显示「请先在 SSH 终端连接 HCI 节点」，
这是事实陈述，不是错误。

### 5. `failedStep` 的取值时机

```text
catch (error)
 → errorMessage = ...
 → failedStep = stepActive      // 此刻 stage 还是 creating/collecting/uploading
 → stage = 'failed'             // 之后 stepActive 才会读 failedStep
```

顺序颠倒的话，`stepActive` 一看到 `failed` 就返回 `failedStep`（此时还是 0），仍然停在第一步。

## 对抗性审查（改动会怎么坏）

| 风险 | 结论 / 处理 |
|---|---|
| 客户环境禁 ping 类全局请求，保活被误判 | 只认传输层错误；`REQUEST_FAILURE` 不算失败。仍不放心可设 `HCI_BRIDGE_SSH_KEEPALIVE_SECONDS=0` 关闭 |
| 探测期间用户正在执行长命令 | 探测走独立全局请求，不占用 pty channel；10s 超时上限保证不影响业务 |
| 保活误关正常会话 | 单测覆盖「健康链路 150ms 内连续探测不被误杀」 |
| 会话关闭与 `close()` 竞态 | `close()` 由 `s.closed` 保证幂等，`done` channel 只关一次；保活 goroutine 由 `done` 退出 |
| 断线后用户看不到「上次连过哪台」 | `lastSshHost` 仍用于重新登录时预填，仅不再冒充当前会话 |
| `process-status="error"` 在 simple 模式下不生效 | 属展示降级，`errorMessage` 与红色进度条仍是权威信息，不影响任务状态机 |
| 建单流程补 `node_ip` 改变既有会话键 | 键从 `caseID` 变为 `caseID@host`，与终端连接一致；`sessionByNodeIP` 兜底仍可用 |

## 测试与验收

单元测试（`terminal_bridge`）：

- `TestKeepAliveProbeSucceedsOnHealthySession`：健康链路探测返回 nil，连续探测不关闭会话；
- `TestKeepAliveClosesSessionOnBrokenLink`：底层连接断开后保活识别失败并关闭会话；
- `TestKeepAliveIntervalFromEnv`：`0` 关闭探测、`45` 生效为 45s；
- 全量 `go test ./...`、`go vet ./...` 通过。

前端：`pnpm build`（含 `vue-tsc`）与 `pnpm test`（220 用例）通过。

验收口径（人工）：

1. 面板打开后手动断开 SSH → 面板「发起节点」变为空并提示先连接，「开始收集」不再发出请求；
2. 采集失败时阶段条停在**真实失败步骤**并标红，而不是停在「探测」；
3. `bridge.log` 中出现 `log_collect.session_missing` 时，能直接用 `active_sessions`
   区分「会话没了」还是「键对不上」；
4. 终端空闲超过保活间隔后仍可正常输入，日志无 `ssh.keepalive_failed` 抖动。
