# 日志收集全链路错误码设计

## 一、为什么需要先定义错误

日志收集的链路是：

```
Custom-UI → 平台 API → terminal_bridge → SSH/PTY → HCI acli → 插件 → 各节点采集 → 打包/上传
```

7 段链路、跨 3 个信任域（浏览器 / 平台 / 客户环境）。没有统一错误语义时，现场只能看到
"失败了"，无法回答三个问题：**哪一层失败、谁该处理、能不能重试**。

因此采用业界通行的三件套：

1. **分层错误码**（gRPC status / AWS error taxonomy 思路）：错误码本身编码"层"，用于定界；
2. **RFC 7807 Problem Details**：HTTP 错误返回结构化 `type/title/status/code/layer/retryable`；
3. **OpenTelemetry Semantic Conventions**：`error.type` 承载错误码，`trace_id` 贯穿全链路。

## 二、命名规范

```
LC-<LAYER>-<NNN>
```

| 层 | 含义 | 定界依据 |
|---|---|---|
| `ENV` | 环境与前置条件 | 架构、acli 是否存在、磁盘、5888 可达性、SSH 会话、节点在线 |
| `INSTALL` | acli 安装 | 下载 → 上传 → 安装 → 验证 |
| `EXEC` | 命令执行 | PTY 申请、超时、非零退出、会话等待 |
| `PLUGIN` | 插件语义 | 参数校验、任务冲突、采集/取消失败、进度解析 |
| `TRANSFER` | 制品交付 | 包缺失、校验和、分块上传、续传、大小限制 |
| `PLATFORM` | 平台服务 | 鉴权、归属、状态机、并发、数据库 |

单一真源：`backend/shared/resolution/catalogs/log_collect_error_catalog.json`
（错误码、层、阶段、责任方、可重试性、HTTP 状态、用户提示、运维提示）。

## 三、错误对象结构

### 3.1 平台 HTTP（RFC 7807 子集）

```json
{
  "type": "urn:hci:log-collect:error:LC-PLATFORM-003",
  "title": "非法状态转换",
  "status": 409,
  "code": "LC-PLATFORM-003",
  "layer": "PLATFORM",
  "owner": "platform",
  "retryable": false,
  "detail": "非法状态转换：completed → collecting",
  "trace_id": "0af7651916cd43dd8448eb211c80319c"
}
```

### 3.2 bridge WebSocket（`log_collect_result` / `acli_sync_result`）

新增字段（保留 `error_type` 作为人类可读短名，向后兼容）：

| 字段 | 含义 |
|---|---|
| `error_code` | 规范错误码（如 `LC-EXEC-001`） |
| `error_layer` | 层（与错误码前缀一致） |
| `error_owner` | `customer` / `platform` / `product` |
| `error_retryable` | `true` / `false` / `manual` |
| `trace_id` | 与任务一致的链路 ID |

### 3.3 OTel

```
span.status = ERROR
span.attributes:
  error.type   = "LC-EXEC-001"     # 规范错误码，便于按码聚合
  error.layer  = "EXEC"
  error.owner  = "customer"
  error.retryable = false
exception.message = 内部细节（不含敏感信息）
```

## 四、定界规则（核心）

1. **谁失败谁出码**：bridge 只在自身层失败时生成 `LC-EXEC-*`；HCI/插件失败由 bridge 包装为
   `LC-PLUGIN-*` 或 `LC-EXEC-003`，并把插件原始输出放入 `cause`。
2. **禁止改写**：平台**不得**把 bridge 的错误码映射成自己的码；只原样落库 `error_code`，
   在 `detail` 中保留 `bridge_error_code`。
3. **一次失败只有一个主码**：多因并存时按"最靠近用户可行动"的层选主码，其余进 `causes[]`。
4. **不得静默降级**：PTY 申请失败、进度解析失败等必须显式出码（`LC-PLUGIN-009` 明确标注
   "非失败降级"），禁止用"默认成功"掩盖。

## 五、可重试性（三态）

| 值 | 含义 | 前端行为 |
|---|---|---|
| `true` | 瞬时故障，原参数重试大概率成功 | 展示"重试"按钮，自动重试 ≤3 次（指数退避） |
| `manual` | 需人工处置后重试（清磁盘、恢复节点、升级 bridge） | 展示"处理指引"，不自动重试 |
| `false` | 参数/语义错误，重试无意义 | 展示"修改参数"，禁止重试 |

重试预算：`probe` 3 次 / `create` 1 次（避免重复下发）/ `progress` 不重试（下一轮轮询即可）。

## 六、责任方与升级路径

| owner | 判定 | 升级路径 |
|---|---|---|
| `customer` | 环境/网络/磁盘/权限/节点状态 | 现场处理；平台给出可执行命令 |
| `platform` | 平台服务、鉴权、状态机、并发 | 平台值班；看 trace + 指标 |
| `product` | 兼容性、文案变化、已知缺陷 | 提单到产品；附 `error_code` + `raw` |

## 七、与日志的关系

每次出码必须同时产生一条结构化日志：

```json
{
  "event": "log_collect.error",
  "level": "ERROR",
  "trace_id": "...",
  "case_id": "...",
  "node_ip": "...",
  "extra": {
    "error_code": "LC-PLUGIN-010",
    "layer": "PLUGIN",
    "stage": "collect",
    "retryable": "manual",
    "cause": "plugin exited 1",
    "raw_preview": "..."
  }
}
```

日志经 `bridge_log` 回采落到 `bridge_execution_logs`，与任务 `trace_id` 同源，
远端可直接按 `trace_id` 拉出：**平台请求 → bridge 动作 → 命令 → 插件输出 → 错误码**。

## 八、典型链路示例

5888 不可达且客户机磁盘不足，走中转失败：

```
LC-ENV-005 日志服务器不可达（probe，retryable=manual，owner=customer）
  └─ 选择 bridge_relay
       └─ LC-ENV-004 磁盘不足（upload，retryable=manual，owner=customer）
            └─ LC-TRANSFER-003 分块上传失败（upload，retryable=true，owner=customer）
```

前端按层展示三段色带，用户一眼看出"不是 acli 的问题，是客户机磁盘与网络"。

## 九、落地与校验

| 位置 | 内容 |
|---|---|
| `log_collect_error_catalog.json` | 单一真源（错误码全集） |
| `terminal_bridge/log_collect_errors.go` | Go 常量 + `errorPayload()`；单测断言与 JSON 一致 |
| `case-service/app/schemas/log_collect_errors.py` | Python 读取 + `problem()`；单测断言一致 |
| `case-service/app/routes/log_collect.py` | HTTP 错误按 §3.1 返回 |

一致性测试是最关键的一环：**任何一侧新增错误码而另一侧未同步，CI 直接失败**，
避免双侧漂移导致"码在日志里有、平台不认"。
