# 2026-11-23 代传发布中断与分片边界让位

## 背景

Q2026112300730（7.66 GiB，785 片）在 case-service 滚动发布窗口内代传中断：

- 5888 实际只收到 **168 片**（`/upload_server.log` 13:32:39 起 168 次 `upload_chunk 200`），
  第 169 片返回 `400 No form data in chunk upload`；
- 5888 的 `/archive_status?filename=Q2026112300730.zip` 返回 `found=false`，
  `/sf/log/Q2026112300730/` 目录从未生成；
- 平台侧却是 `relay_status=success`、`delivery_status=delivered`、
  `integrity_state=verified`，且 `detail` 里没有 `archive_confirmation`。

结论：包没到日志服务器，平台却显示已交付。三个缺陷叠加造成，缺一条都不会这么安静。

## 根因

### 1. 终态订正只看「到平台」，不看「到 5888」

`settle_delivered_relays()` 的条件是
`delivery_status=delivered AND relay_status IN (running, pending)`，直接写
`relay_status=success`。

而 `delivery_status=delivered` 由上传服务在**平台对象存储合并完成**时写入，
语义是「产物到了平台」，与「已归档到 5888」是两跳。

事发时新 Pod 启动即执行该语句（日志 `日志包代传终态订正 count=1`），
把旧 Pod 正在跑的任务判成了完成。

### 2. 优雅退出直接 cancel，切断在途分片

`shutdown_relays()` 对每个在飞任务调用 `task.cancel()`。取消打在正在发送的
`/upload_chunk` 上，请求体只发了一半，5888 解析不到 multipart，返回 400。

uvicorn 的优雅期只保护 HTTP 在途请求，不保护进程内 `asyncio` 后台任务，
所以 `terminationGracePeriodSeconds: 300` 在这里不起作用。

### 3. 交还的 pending 永远不会被重新接管

`claim_stale()` 带 `delivery_status != 'delivered'`。P2 任务在平台落库那一刻就是
delivered，这个条件对所有 P2 任务恒假：旧 Pod 交还的 pending 没有任何实例会捡，
代传失去「接力」能力。

## 改动

### 1. 订正只认链尾核验（`log_collect_relay_service.py`）

- `settle_delivered_relays()` 增加 `detail->'archive_confirmation'->>'verified' = 'true'`；
- 没有核验证据的历史行不再被写成 success，而是留在 running/pending，
  由租约过期后的 `claim_stale` 真正重跑。

### 2. 接管判据改为 relay 自身终态（`log_collect_relay_service.py`）

- `claim_stale()` 的 `delivery_status != 'delivered'` 改为 `relay_status != 'success'`；
- 配合 `_claimable()` 已有的 pending/过期 running 条件，发布交还后下一轮
  reconcile（60s 内）即可续传。

### 3. 分片边界让位（`log_collect_relay_service.py`）

- 新增进程级 drain 信号：`begin_drain()` / `drain_requested()` / `reset_drain()`；
- 新增 `RelayDrainingError`：分片循环在**每片开始前**检查，命中即抛出，
  **绝不打断正在发送的请求**；
- `_run_with_retry` 捕获后只 `release([task_id])`（running → pending），
  不写 failed、不写 last_error、不计 attempt；
- 复用会话时若 5888 返回 `status=done`（上次已收齐、只是没写终态），
  跳过上传直接做链尾确认，避免被终态会话的 409 打成失败。

### 4. 优雅退出改为「先等、后强制」（`routes/log_collect.py`）

- `shutdown_relays(wait_seconds=120)`：先 `begin_drain()`，再
  `asyncio.wait(timeout=wait_seconds)`；
- 只有超时仍未结束的任务才 `cancel()`；
- `reconcile_relays_once()` 与 `_run_relay_gated()` 在 drain 期间不再接新任务、
  不再启动排队任务。

## 兼容与回滚

- 全部为服务端改动，无数据库迁移、无接口变更、无需重新构建 bridge exe；
- 老任务（无 `archive_confirmation`）不会被订正为 success，会回到 pending 并由
  `claim_stale` 重跑；重跑复用 `relay_upload_id`，从 `relay_chunk_index+1` 续传；
- 若 5888 会话超过 24h 已过期，`upload_status` 返回 404 → 自动重建会话重传整包，
  这是语义上唯一正确的兜底。

## 对抗性审查

- **双写风险**：drain 与 reconcile 可能同时让两个实例看到可接管状态。接管仍走
  `trigger()` 的条件 UPDATE（Postgres 行锁），只有一个实例能把状态改成 running。
- **长时间单片**：若某片在弱网下耗时超过 `wait_seconds`，会退化为强制 cancel，
  仍可能产生一次残缺请求；这是有界退让，不是绝对保证。300s 的 grace 与
  120s 的等待留出了余量。
- **drain 只覆盖代传**：大包合并在 HTTP 请求内完成，由 uvicorn 优雅期保护；
  本次不改。
