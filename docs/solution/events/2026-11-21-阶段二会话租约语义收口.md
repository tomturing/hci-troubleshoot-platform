# 方案事件：阶段二会话租约语义收口

- 日期：2026-11-21
- 范围：`terminal_bridge`（会话下沉到 `internal/shared/session` 的收尾）
- 结论：会话租约的三处口径不一致已收敛，直传拉取不再暴露在空闲回收窗口内

## 变更历史

| 日期 | 版本 | 变更摘要 |
|------|------|---------|
| 2026-11-21 | v1.0 | 初版：夹具走 Set、refs 降级为状态位、直传补长任务保护 |

## 1. 背景

阶段二把 SSH 会话从 `app.Bridge` 下沉为 `internal/shared/session.Hub`。下沉本身完成，
但留下了三处"代码说一套、运行做一套"的地方，且都被测试掩盖着：

1. 测试直接往会话表塞会话，造出生产不可达的状态；
2. 引用计数 `refs` 看起来是多持有者计数器，实际只会是 0/1；
3. 日志包直传的长时间拉取没有被任何会话保护覆盖。

三者都不是"功能没做"，而是"语义与事实不符"——这类问题不修会在下一次故障排查时
把人带偏，因此在本阶段一并收口，不单独排期。

## 2. 问题一：测试夹具绕过了引用计数

### 现象

迁移后共有 15 处测试用 `app.Bridge{Sessions: ...}` 或 `b.Sessions[k] = v` 直写会话表
（`internal/logcollect/log_collect_test.go`、`cmd/bridge/main_test.go`、
`ssh_input_routing_test.go`）。`Bridge` 已不再持有会话表，编译期失败。

### 为什么不加一个"直写注入"入口

第一版实现确实加过 `Hub.Inject`（直写 map、不登记 refs）。它被否决，理由是：

- 会话表的唯一写入口必须同时维持"入表即 refs=1"，否则 reaper 立刻可回收；
- `Inject` 造出的状态（refs 缺失、idleAt 缺失）在**生产中不可达**，测试断言的
  "会话仍在"属于侥幸而非语义；
- 存在第二写入口，就永远有人用它绕过不变量。

最终夹具改为走生产入口 `Set`：

- `app.NewBridgeWithSessions(map)`（`internal/app/bridge.go:47`）内部循环调用 `Set`；
- 需要空闲态的用例显式调 `ReleaseSession`，与线上完全同构。

同时把 7 处 `&app.Bridge{}` 空字面量改为 `app.NewBridge()`：`Hub` 是嵌入指针，
空字面量下任何会话方法调用都是 nil 解引用 panic，而编译期不报错。

### 补齐新包的测试

`internal/shared/session` 此前没有任何测试，而它现在是会话语义的唯一所有者。
新增 `hub_test.go` 锁定四条根基：

- 入表即持有：`Set` 之后即使 idleAt 被推到一小时前，也不进回收候选；
- 释放是降级不是销毁：归零后会话仍在表内，空闲超 TTL 才成为候选；
- `ForgetLease` 必须清干净簿记，否则空闲表留下幽灵键、reaper 每轮命中；
- `ttl <= 0` 表示关闭回收，直接返回空。

## 3. 问题二：refs 是状态位，不是计数器

### 事实

`refs` 只有 `Set` 一处写 1、`Release` 一处减，而减到 >1 的分支**在生产中不可达**：
复用会话的第二条连接（日志面板、交付续传）只做 `Get`，不会增加持有数。
也就是说，代码宣称的"多条连接共用、全部走了才算空闲"并未实现。

### 为什么不是补一个 Hold 把多持有者做出来

评估过，结论是净负收益，不实施：

- **救不到目标场景**：真正危险的是"浏览器全关、后台作业还在跑"，此时没有主体可以
  Hold，`refs=0` 就是对现实的正确描述；
- **能救的场景不需要救**：页面还开着时 refs=1，本来就安全；
- **失效模式更隐蔽**：计数型保护漏写一次 `Release` 就永久不归零，会话与 SSH 连接
  双泄漏且无任何日志；租约式保护（业务活跃窗）到期自动失效，这也是本仓库
  `internal/sshx/tuning.go:33` 已经写下的取舍。

因此把语义改成事实并写进注释（`internal/shared/session/hub.go:147`、`:350`）：

- `refs` 明确为 0/1 状态位，注释写明"不要累加，没有对称递减点"；
- `Release` 签名从 `(idle bool, refs int)` 收敛为 `(idle bool)`，删掉不可达分支；
- 复用连接的安全边界写清楚：靠 `MarkBusy` / `BeginLongTask` 的活跃窗，不靠持有计数。

## 4. 问题三：直传拉取脱离所有会话保护（本次唯一行为变更）

### 证据链

| 环节 | 事实 | 位置 |
| --- | --- | --- |
| 异步化 | 每条 WS 消息起独立 goroutine，与浏览器连接解耦 | `cmd/bridge/ws_routes.go:513` |
| 预算 | 拉取 + 分片上传给 2 小时 | `log_collect_transfer.go:42` |
| 现有保护 | 入口一次 `MarkBusy()`，活跃窗 15 分钟，之后无续期点 | `log_collect.go:1599`、`sshx/tuning.go:37` |
| 拉取期无长任务 | 全仓 `BeginLongTask` 仅交付在用 | `delivery_runner.go:1112` |
| 归零时点 | 页面关闭 → 逐键 `ReleaseSession` → refs=0、idleAt=now | `cmd/bridge/dispatch.go:69` |
| 回收时点 | 15 分钟窗过期 + 5 分钟租约 ≈ 断开后 20 分钟 | `app/lifecycle.go:96` |

### 失败路径

页面关闭 → 15 分钟后活跃窗失效 → 再过 5 分钟 reaper 判定空闲 → `DestroySession`
→ `session.Close()` → `PullArchive` 的 SSH 通道断开 → 整包作废。此时前端已关，
无人看到失败，任务落 `failed`。

9.59 GiB 一类包在内网千兆下约 10–16 分钟（安全），弱网 5 MB/s 约 32 分钟（必然触发）。
弱网是本产品的主场景（见 2026-11-06 Q2026110600112 弱网活锁），因此不是理论风险。

### 修复

`handleLogCollectTransfer` 开头成对登记长任务（`log_collect_transfer.go:248`）：

```go
if s != nil {
    s.BeginLongTask()
    defer s.EndLongTask()
}
```

标记期间 `ReapCandidates` 直接跳过该会话；结束即恢复租约判定，上限由 2 小时的
`logCollectTransferTimeout` 兜底，不会出现"忘减一次永久保护"。

### 同类嫌疑已排除

`log_collect_spc_fanout.go:1298`、`log_collect_script_fanout.go:463` 的后台协程
每 15 秒轮询一次并 `MarkBusy()`（`spcRestorePollInterval = 15s`），相对 15 分钟窗口
有 60 倍余量，属"有续期点的租约"，无需长任务计数。

## 6. 遗留

- 合并后需等自动 exe 重建 PR 落地，并由现场人工重装，改动才会到达客户机；
- 历史已被回收导致的 `failed` 任务不会自愈，只能重新触发收集或补交付；
- 本次不引入多持有者计数，若将来真出现"同一会话被多条连接长期共用且业务动作稀疏"
  的场景，应优先延长/续期业务活跃窗，而不是引入计数器。
