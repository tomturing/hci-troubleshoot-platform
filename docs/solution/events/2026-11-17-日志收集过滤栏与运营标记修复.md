# 2026-11-17 日志收集过滤栏与运营标记修复方案

## 背景与需求

见 [需求事件文档](../../requirement/events/2026-11-17-日志收集过滤栏与运营标记修复.md)。核心不是"过滤按钮失灵"，而是**失败被静默吞掉后旧数据继续冒充查询结果**。

## 方案概述 (WHAT)

1. 后端白名单与前端下拉闭合；所有筛选项即时查询；查询失败清空旧结果并显式告警。
2. 在契约单一事实源新增 `task_stalled` / `synthetic_test` 两个条件与 `LC-HTP-004` info 归因码，重新生成七份产物。
3. 后端列表默认以 `error_message` 正则排除验证/压测任务，列表、总数、汇总三条 SQL 共用同一 `WHERE`。
4. 接受用户纠正：续传/补交付入口已存在，不做重复建设；用 SSH 取证修正归档结论。

## 详细设计

### 1. 过滤栏链路修复

- `backend/case-service/app/routes/log_collect_admin_tasks.py`：`VALID_STATUSES` 补 `creating`、`relaying`，`VALID_DELIVERY` 补 `cancelled`。此前这些值在前端可选、后端必 400，错误被 `load()` 的 catch 收进一行小字，表格与统计保持旧值，用户看到的就是"过滤完全不能使用"。
- `frontend/admin/src/views/components/LogUploadPanel.vue`：
  - 六个筛选项的 `change` / `keyup.enter` 均调用 `search()`；
  - `load({ clearOnError: true })` 在显式查询失败时清空 `rows/total/summary/progressMap`，并用 `ElMessage.error` 显式告警；10 秒自动刷新不清空，避免瞬时抖动造成整表闪烁；
  - 新增「包含验证/压测」复选框，默认关闭，纳入重置。

### 2. 契约驱动的运营标记

在 `contracts/log_collect_display.json` 增加：

| 变更 | 内容 |
|------|------|
| `condition.task_stalled` | 任务长时间无进展 |
| `condition.synthetic_test` | 验证 / 压测任务 |
| `thresholds.task_stall_hours` | 24 小时 |
| `fault_catalog.LC-HTP-004` | tone=info，标题「验证 / 压测清理」，动作「无需处理；运营看板默认隐藏此类任务」 |
| `fault_matchers` / `attribution_rules` | `pentest-cleanup`、`test_cleanup`、`ssrf_test_cleanup`、`ssrf_probe_cleanup` → `LC-HTP-004` |

七份生成物全部由 `scripts/gen_log_collect_display.py` 重建，`--check` 与 `verify_log_collect_contract.py` 通过。

### 3. 派生层语义

- `is_task_stalled(task, now)`：只在 `derive_phase != settled` 且 `created_at` 超过契约 24 小时阈值时为真；与 60 秒传输停滞 `stalled` 并存但互不替代。真实数据命中 10 单。
- `is_synthetic_task(task)`：只认 `error_message` 中的测试标记正则，不按工单号猜测，避免误伤真实工单。真实数据命中 13 单，全部得到 `LC-HTP-004` info 归因与 `synthetic_test` 条件。
- 后端默认查询用 `COALESCE(t.error_message, '') !~* :synthetic_marker`；`COALESCE` 不可省，否则 NULL 与正则比较为 NULL 会误删正常任务。实测 191 → 178 行。

### 4. 对抗性审查记录

- 直接调用 handler 时 FastAPI `Query(False)` 默认值是对象而非 bool，导致压测过滤被悄悄跳过；已改为普通 `bool = False`，FastAPI 仍会生成 query 参数。
- 契约门禁要求 signal 码必须有可达匹配规则且前缀与责任组件一致；错误码从 `LC-TEST-001` 改为 `LC-HTP-004`，并补齐 `fault_matchers`。
- 上轮把 `LC-HTP-002`（未能自动归因）的 39 单误当成压测清理；SQL 核实压测标记只有 13 单（其中 cancelled 7 单），已纠正文档。
- 上轮建议"提供续传/补交付入口"是错的：入口已存在且现场用户会用；SSH 核实三张单中两张已在 5888 生成规范归档（`Q2026111600133.zip` 279 MB、`Q2026111400027.zip` 18.9 GB），`Q2026111301229` 无对应目录。

## 影响范围

- `contracts/log_collect_display.json` 与七份生成物；
- `backend/case-service/app/domain/log_collect_display.py`、管理端只读路由及单测；
- `frontend/admin` 的 API 类型、任务进展组件及单测；
- README 与上一轮方案文档的数据订正、本轮三层事件文档。

## 测试策略

- 后端：79 例定向通过（派生 30+ 例、管理端筛选 49 例），覆盖枚举闭合、压测默认过滤、NULL 安全、停滞条件与归因映射。
- 前端：19 例通过，覆盖六个筛选项传参、压测开关、失败清空旧结果。
- 契约：`gen_log_collect_display.py --check` 与唯一出处门禁通过。
- 浏览器：Chromium 实测默认请求无压测参数、待补交付/任务下发中筛选即时生效、开关传参正确、400 后旧数据消失。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 压测正则漏标新标记 | 只认明确文本，宁可漏标不误伤；新增标记需同步契约 matcher 与正则 |
| 过滤失败清屏影响自动刷新观感 | 只有显式查询清屏；自动刷新失败仅显示错误条 |
| 24 小时阈值对长任务过严 | 阈值来自契约，可调整；仅作为条件展示，不改变结论与状态机 |
