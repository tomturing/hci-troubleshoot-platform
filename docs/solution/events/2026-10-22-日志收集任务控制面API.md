# 日志收集任务控制面（PR-3b）

## 一、为什么放在 case-service 而不是新服务

原设计曾计划独立 `log-collect-service`，但第一性原理下这不是最优：

1. 日志收集任务是**工单附属制品**，与 `environment` 同级，天然属于 case 域；
2. 新服务需要 Dockerfile / Helm Chart / 网关路由 / CI 镜像矩阵 / 独立迁移链路，
   成本远大于收益；
3. `case-service` 已具备 `get_client_id` + `verify_case_ownership` 的 BOLA 防护，
   直接复用即可，避免重新实现鉴权。

结论：在 `case-service` 内新增表与路由；若未来需要独立扩缩容再拆服务。

## 二、职责边界

```
Custom-UI ──HTTP──► case-service（任务登记/状态机/进度/制品元数据）
    │
    └──WS──► terminal_bridge（真实执行：probe/create/progress/cancel）
                  │ SSH + PTY
                  ▼
              HCI 节点 acli log_collect
```

**平台不执行命令、不推断进度**：`status/progress/detail` 全部由前端把 bridge 轮询结果
回写。`origin_node_ip` 必须落库，因为 `acli log_collect progress` 只反映发起节点的本地视图。

## 三、表结构

`log_collect_task`（迁移：`database/atlas-migrations/20261022000000_add_log_collect_task.sql`）

| 字段 | 说明 |
|---|---|
| `task_id` | 主键 |
| `case_id` | 工单外键，`ON DELETE CASCADE`；同时作为 acli `-s` 与产物名（全平台唯一工单号） |
| `origin_node_ip` | 发起节点（`inet`），progress 轮询必须路由回此节点 |
| `modules` / `ips` / `extra_paths` | `text[]`，与 acli `-m/-i/-p` 对应 |
| `date_from` / `date_to` | `date`，跨度 ≤30 天 |
| `status` / `progress` | 状态机与总进度 |
| `arch` / `acli_version` | 环境探测结果（便于事后核对安装行为） |
| `upload_mode` | `acli_direct` / `platform_direct` / `bridge_relay` / `none` |
| `archive_path` / `archive_size` / `archive_sha256` | 制品元数据（大文件交付在 PR-3d） |
| `detail` | 主机明细与上传状态快照（jsonb） |
| `error_code` / `error_message` | 失败语义 |

关键约束：

```sql
CHECK (ticket_no ~ '^[A-Za-z0-9_-]{1,32}$')
CHECK (date_to >= date_from AND date_to - date_from <= 30)
CHECK (progress BETWEEN 0 AND 100)
UNIQUE INDEX uq_log_collect_task_active_case ON log_collect_task (case_id)
  WHERE status NOT IN ('completed', 'failed', 'cancelled')
```

部分唯一索引是**并发防线的最后一道**：应用层先查活跃任务给出友好报错，数据库保证
并发窗口内不会出现两个活跃任务——两个采集任务同时跑会互相 `kill -9` 并覆盖产物目录。

## 四、状态机

```
pending → probing → installing → collecting → packaging → uploading → completed
   └───────────────┴──────────────┴────────────┴───────────┴──→ failed / cancelled
```

允许跳步（未安装 acli 可 `probing → collecting`；无上传可 `packaging → completed`），
但：

- 终态（completed/failed/cancelled）**不可复活**；
- 进行中**进度不可回退**——回退通常意味着轮询路由到了错误节点，读到旧任务或空任务；
- `completed` 强制 `progress=100`（插件 final 阶段偶发不刷新总进度）。

## 五、API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/cases/resolve` | **工单号解析/建档**：存在则复用，不存在则按该号创建（日志收集专用） |
| POST | `/api/log-collect/tasks` | 创建任务（同工单仅一个活跃，冲突 409，附 `active_task` 脱敏摘要） |
| GET | `/api/log-collect/tasks?case_id=` | 按工单分页列表 |
| GET | `/api/log-collect/tasks/{task_id}` | 任务详情 |
| PATCH | `/api/log-collect/tasks/{task_id}` | 回写状态/进度/制品元数据（409 = 非法转换或进度回退） |
| POST | `/api/log-collect/tasks/{task_id}/cancel` | **仅改平台状态**，真正终止需前端经 bridge 执行 `acli log_collect cancel` |
| POST | `/api/log-collect/tasks/{task_id}/uploads` | 初始化分片会话（幂等，签发短期 `upload_token`） |
| GET | `/api/log-collect/tasks/{task_id}/uploads` | 查询已上传分片（断点续传） |
| POST | `/api/log-collect/tasks/{task_id}/uploads/complete` | 流式合并分片并落库制品元数据 |
| POST | `/api/log-collect/tasks/{task_id}/uploads/abort` | 中止上传并清理临时分片 |
| POST | `/api/log-collect/tasks/{task_id}/relay` | 异步代传 5888（抢占式，重复调用不产生并发上传） |
| GET | `/api/log-collect/tasks/{task_id}/relay` | 代传状态与断点位置 |

### 5.0 鉴权模型（2026-10-23 调整为方案 A）

| 操作 | 校验 | 说明 |
|---|---|---|
| `POST /api/cases/resolve` | 客户签名身份 | 工单已存在（含属于其他客户端）→ 复用；不存在 → 用该号建档 |
| `POST /api/log-collect/tasks` | 仅校验**工单存在** | 允许跨客户端复用同一工单号（换设备补采） |
| 任务查询/更新/取消/上传/代传 | **`task.created_by == client_id`** | 非创建者统一 404；同一工单号下任务互相隔离 |
| 任务列表 `?case_id=` | 工单存在 + 只返回本人任务 | 看不到他人任务 |

**409 结构化响应**（前端据此展示「查看任务状态」）：

```json
{"detail":{"code":"LC-PLUGIN-007","status":409,"title":"该工单已有进行中的日志收集任务",
 "active_task":{"task_id":"…","status":"collecting","progress":42,"created_by_me":true,"created_at":"…"}}}
```

`active_task` 已脱敏：不含 `origin_node_ip`、`ips`、`archive_path`。`created_by_me=false` 时前端只展示状态，
不提供接管/取消。

> 错误码目录（`shared/resolution/catalogs/log_collect_error_catalog.json`）按父目录逐级查找，
> 同时兼容仓库 `backend/` 与镜像 `/app/` 两种布局；文件缺失/损坏时降级为通用 Problem，
> 不再抛异常。此前固定 `parents[3]` 在镜像里算成 `/shared/...`，会让 409 冲突响应变成 500。

### 5.1 网关代理契约（2026-10-22 补齐）

#1192~#1204 只在 case-service 注册了上述端点，api-gateway 未注册 `/api/log-collect/*`；
staging 实测网关 `404`（直连 case-service 为 `401`），customer-ui 面板一下发任务就失败。
补齐后的契约：

| 维度 | 约定 |
|---|---|
| 入口 | `api-gateway/app/routes/log_collect.py`，前缀通配 `/api/log-collect/tasks{path}`（GET/POST/PATCH/DELETE） |
| 身份 | `require_user` 取服务端 Cookie 的 client_id，再经 `sign_client_identity` 重签 `X-Client-ID` / `X-Client-Signature`；客户端自报身份头不转发 |
| 响应 | 状态码与 RFC 7807 错误体原样透传，网关不改写业务错误码 |
| 体积 | 控制面请求体 ≤ 1 MiB；分片数据面（32 MiB）不经网关，由 ingress 将 `/api/direct/log-collect-uploads` 直连 case-service |
| 超时 | 默认 30s；`/uploads/complete` 为 600s（20 GiB 流式合并） |
| 演进 | 前缀通配：case-service 新增控制面端点无需再改网关，避免再次出现"后端有路由、网关 404" |

前端入口侧（同 PR）：`App.vue` 的 header 按钮保留为常驻入口，同时在建单后由
`LogCollectEntryCard` 主动引导一次；「暂不需要」按 `case_id` 记忆，换新工单重新出现，
保证既不打扰也不丢入口。

## 七、可观测性与日志回传

### 7.1 全链路 trace

```
Custom-UI（创建任务，拿到 trace_id）
   └─ log_collect 消息携带 trace_id
        └─ bridge blog（trace_id 为空时兜底：log_collect → lc-<exec_id>，acli_sync → acli-sync-<case_id>）
             └─ WS bridge_log → 前端回采 → /api/bridge-logs → conversation-service
                  └─ bridge_execution_logs(trace_id, event, extra, event_id, span_id)
```

平台侧兜底：`create_task` 在 `trace_id` 为空时生成 `uuid4().hex`（32 位小写 hex），
保证任何任务都有一条可检索链路，不需要依赖前端自觉。

### 7.2 日志事件清单

| 阶段 | 事件 | 关键字段 |
|---|---|---|
| 任务 | `log_collect.start` | action、task_id、ticket_no、modules、日期、ips、路径数量 |
| 任务 | `log_collect.done` | outcome、duration_ms、task_id |
| 探测 | `log_collect.probe` | architecture、acli 版本/构建时间、available_mb、日志服务器可达性与延迟、note |
| 探测 | `log_collect.session_missing` | 缺少 SSH 会话（提前失败也要留痕） |
| 创建 | `log_collect.create` | 命令（脱敏）、exit_code、error、输出摘要 |
| 创建 | `log_collect.rejected` | 参数校验失败类型与原因（工单号/专项/日期/IP/路径/URL） |
| 进度 | `log_collect.progress` | parse_ok、percent、done/total、状态文案、压缩包路径、上传地址与状态、主机数、原始输出长度 |
| 取消 | `log_collect.cancel` | exit_code、error、输出摘要 |
| 安装 | `acli_sync.start` | force、min_disk_mb、是否自定义下载地址 |
| 安装 | `acli_sync.version_check` | 架构、当前版本/构建、远端构建、need_install、探测错误 |
| 安装 | `acli_sync.up_to_date` | 已就绪，无需安装 |
| 安装 | `acli_sync.arch_probe_failed` / `arch_unsupported` | 架构探测失败或不支持 |
| 安装 | `acli_sync.download_done` / `download_failed` / `download_bad_status` / `download_request_failed` | 包名、大小、HTTP 状态 |
| 安装 | `acli_sync.upload_done` / `upload_failed` | 目标路径 |
| 安装 | `acli_sync.install_done` / `install_failed` | exit_code、安装器输出摘要（含集群分发节点） |
| 安装 | `acli_sync.installed` / `verify_failed` | 安装后版本、构建时间、验证输出 |
| 安装 | `acli_sync.disk_insufficient` | 可用/要求 MB |

所有事件均带 `trace_id / case_id / node_ip / custom_ui`，`extra` 中的命令经
`redactCommand` 脱敏，输出经 `truncateString` 截断（≤1024 字符），避免日志反噬。

### 7.3 进度语义（再次强调）

`progress` / `detail` 只是**快照**：权威进度源是 HCI 的 `cluster_progress.json`，
前端应直接展示 bridge 的实时返回，平台快照仅用于任务列表兜底。
`PATCH` 推荐只在状态跃迁与终态调用（每任务 ≤6 次），避免写放大与双源冲突。
