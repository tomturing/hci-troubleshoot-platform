# 主干后端门禁按影响范围收敛方案

## 1. 第一性原理

一次 CI 运行的价值等于「它为本轮变更产生的新证据」。判定一个 job 是否该在本次
main push 启动，只有一个充分条件：

```
该 job 的输入（被读取的文件集合）在本次 push 的变更清单内
```

镜像构建侧已经实现了这条原则：`scripts/ci/resolve_image_build_plan.py` 按
Dockerfile 与实际 `COPY` 输入计算影响闭包，纯文档 push 不构建任何业务镜像。
但 `Lint` / `unit-tests` / `integration-tests` / `security-tests` 仍对每次 main push
无条件全量执行，且发布链又把它们的 `success` 作为前置条件——于是"没有新证据的
回归"变成了发布路径上的固定等待时间。

## 2. 背景与需求

### 2.1 实测数据

run `35067086697`（main push，squash 合并 #1051，变更仅为 `frontend/**` 与
`docs/**`）各 job 实际耗时：

| 阶段 | 耗时 | 是否为发布链前置 |
|---|---|---|
| docs-governance（变更探测 + 镜像计划） | 62s | 是（入口） |
| **unit-tests（8 个后端服务完整回归）** | **239s** | 是 |
| integration-tests | 109s | 是 |
| security-tests | — | 是 |
| 构建并推送镜像（仅 admin-ui） | 84s | — |
| 晋级非生产环境 | 14s | — |

同一 PR 在 `pull_request` 事件下（run `35066945128`）只有 3 个门禁运行，其余 12 个
job 为 `skipped`——说明 PR 阶段早已按影响范围收敛，主干阶段没有。

### 2.2 需求

1. 纯 `frontend/**` / `docs/**` 变更的 main push 不启动后端门禁层，发布链直接进入
   镜像构建与晋级；
2. 任何可能改变后端门禁输入的变更，仍然运行与今天完全等价的全量回归；
3. 判定失败（取不到 diff、清单为空、出现未知路径）时**必须**回落到全量，不允许
   把"判定不出来"当成"不需要跑"。

## 3. 方案（WHAT）

### 3.1 判定：白名单 + 失败关闭

新增 `scripts/ci/resolve_main_test_scope.py`，输入"本次 push 的变更文件清单"，输出
`required`（是否需要后端门禁层）：

```
变更清单为空                                                     → required=true
变更清单中存在任一非白名单路径                                    → required=true（并报出该路径）
变更清单全部落在 frontend/、docs/、README.md、AGENTS.md、CLAUDE.md → required=false
```

白名单的准入标准不是"看起来和后端无关"，而是**逐 job 核对过没有任何步骤读取该
路径**：

| 路径 | 是否入白名单 | 依据 |
|---|---|---|
| `frontend/**` | 是 | 由 `frontend-check` 独立承担完整回归 |
| `docs/**` | 是 | 仅被 `docs-governance` 的信息性 step（`check_docs_naming.py`、`check_docs_rot.py`、`check_module_doc_sync.py`）读取，这些 step 在 `changes` job 内，永远执行 |
| `README.md` / `AGENTS.md` / `CLAUDE.md` | 是 | 同上，纯文档 |
| `deploy/**` | **否** | `REQUIRE_HELM=1 make config-contract-check`（unit-tests 步骤）读取 compose 与 Helm 契约；`integration-tests` 也用 `deploy/docker/docker-compose.yml` 起 PostgreSQL |
| `backend/**`、`tests/**` | **否** | 门禁本体输入 |
| `scripts/**`、`database/**` | **否** | `check_signal_schemas.py`、Atlas schema 与迁移链路输入 |
| `uv.lock`、`pyproject.toml`、`Makefile`、`conftest.py` | **否** | 全量门禁的依赖与测试基础设施输入 |
| `.github/workflows/**` | **否** | 门禁定义自身 |

### 3.2 diff 起点：最近一次成功发布基线，不是相邻 commit

`main-test-plan` 使用 `release-baseline.outputs.base_sha`（与镜像计划同一基线，
即"最近一次真正成功构建过业务镜像的 run"）作为 diff 起点，而不是
`github.event.before`。原因与镜像收敛一致：被后续 push 取代的那一轮 main push
（上一轮 run 尚未完成就到达新 push）其变更从未被任何一轮回归覆盖，若按相邻 commit
计算会被整段跳过；以成功发布基线为起点，这段未回归的后端改动仍留在清单内，
`required` 保持 `true`。

### 3.3 发布链门禁语义

`release-metadata` 与 `prepare` 的前置条件由"三个测试 job 必须 `success`"改为：

```
backend_gate_required != 'true' ||
(unit-tests == success && integration-tests == success && security-tests == success)
```

`required=true` 时该表达式与改前**完全等价**；只有 `required=false` 时接受 `skipped`，
而此处的 `skipped` 是判定结果本身，不是证据缺失。`changes` job 的
`backend_gate_required` 输出缺省值为 `'true'`，因此非 push-main 事件
（`workflow_dispatch`、被人为修改的调用）自动走完整门禁。

### 3.4 本轮落地范围与二期

本轮只落地 3.1–3.3：**只解决"变更完全不在后端门禁输入内"这一确定性子集**，判定
不引入任何新映射表，风险面最小。

二期（独立 PR）：把"后端变更也只跑受影响服务"从 PR 阶段推广到 main 阶段，判定
粒度从"全量 / 不跑"改为"受影响服务集合"。二期必须先解决三个耦合点，本轮不做：

1. **覆盖率基线**：main 的 unit-tests 分批 `--cov-append` 后检查 `≥60%` 并上传
   codecov；只跑部分服务会使覆盖率必然下降，需要显式决定"targeted 时跳过
   `--cov-fail-under` 与 codecov 上传"还是"改为周期性全量校准"。
2. **粒度上限**：现有 PR 判定 `resolve_pr_fast_test_targets.py` 的
   `MAX_FAST_SERVICES = 1`、把 `backend/shared/**` 视为全局依赖、且
   kb-service 无 `tests/unit/` 子目录即升级全量——在 main 上（累计 diff）会导致
   绝大多数 push 仍被判为全量，收益不稳定，需要改为"服务闭包"判定。
3. **非 Python 层**：`config-contract-check`、`hci_sim`/`offline-collector` 的 Go
   运行时测试、Helm 探针对齐是仓库级或正交检查，不能跟着"哪个后端服务变了"走。

## 4. 决策依据（WHY）

### 方案 A：只放开 `prepare` 的 `needs`，测试照跑全量

不选。CI 关键路径（`prepare` → `build-and-push` → 晋级）不变，只是把等待从
"发布链被阻断"改成"runner 分钟数被消耗"，耗时收益为零。

### 方案 B：main 上取消后端测试层，只信 PR 门禁

不选。PR 的入口条件（fork、Merge Queue、直推、路径过滤）与 main 不同，main 是
发布源，需要自己完整的证据链；删除该层等于删掉发布的最后一道自动防线。

### 方案 C：直接复用 `paths-filter` 的 `frontend` 输出

不选。`frontend` 输出中的确定性判定 step（`fe-real`）仅在 `pull_request` 事件
执行，push 事件下该输出为空，用它做条件会把所有 push 判成"无前端变更"；
`dorny/paths-filter` 的 `frontend` 过滤器又存在 PR #747 记录过的边界误判。

### 方案 D：直接把 PR 的 targeted 判定搬到 main

不选（本轮）。可行性成立，但受 3.4 的三个耦合点限制：覆盖率门禁会误报，且
`MAX_FAST_SERVICES = 1` 在累计 diff 下命中率低，收益不可预期。先落确定性收益，
二期单独评审覆盖率策略后再做。

### 为什么跳过 `config-contract-check` / Go 运行时测试是安全的

`unit-tests` 里的 `REQUIRE_HELM=1 make config-contract-check` 与 `hci_sim` /
`offline-collector` 的 Go 测试确实不读 `frontend/**` 或 `docs/**`，但它们**读**其他
输入。跳过它们的合法性来自归纳不变式，而不是"它们看起来和我们无关"：

- diff 起点是**最近一次成功发布基线**，即上一轮走到 `prepare` 成功的 run；
- 该 run 能走到 `prepare`，只可能因为「它当时 `required=true` 且三类测试 success」
  或「它当时 `required=false`」；
- 无论哪种情况，被校验的输入集合此后未再变化——因为若变化过，本次 diff 里就会
  出现非白名单路径，`required` 必然回到 `true`。

因此白名单成立时，这些检查的输入与"上一次它们被实际执行并成功"的时刻逐字节等价。
这条归纳与镜像构建闭包依赖的前提是同一个，不引入新的假设。

### 为什么白名单式判定而不是黑名单

黑名单要求"穷举所有会影响后端门禁的路径"，漏一项就是静默漏测；白名单要求
"证明这些路径不被任何门禁步骤读取"，漏一项只会导致多跑一次（可接受的浪费方向）。
失败方向必须朝着"多跑"而不是"少跑"。

## 5. 影响范围（现行全量文档更新）

| 文档 | 更新点 |
|---|---|
| `docs/deploy/发布指南.md` | 变更历史追加本轮；§3.3 依赖关系与 §3.4 触发条件汇总中 main push 的 Lint / unit-tests / integration-tests / security-tests 触发条件改为"按后端门禁范围" |
| `docs/README.md` | 第一屏里程碑追加本轮 |

不涉及接口、数据库、服务拓扑与可观测性变更，`solution/接口设计.md`、
`solution/数据库设计.md`、`solution/系统架构.md` 无需更新。

## 6. 验收标准

1. 纯 `frontend/**` + `docs/**` 的 main push：Lint / unit-tests / integration-tests /
   security-tests 全部 `skipped`，`release-metadata`、`prepare`、镜像构建与晋级正常
   完成，端到端时长降到镜像构建本身的量级。
2. 含任一 `backend/**` / `deploy/**` / `scripts/**` / `database/**` / `tests/**` /
   锁文件 / workflow 的 main push：四个 job 全部运行，行为与改前一致。
3. 取不到 diff 或清单为空：四个 job 全部运行（失败关闭），并在 step 日志给出
   `::warning::`。
4. `scripts/ci/test_resolve_main_test_scope.py` 覆盖白名单命中、白名单外路径、
   空清单、混合变更与根级未知文件五类断言。
5. `workflow_dispatch` 手动触发始终执行完整后端门禁，可作为强制全量通道。
