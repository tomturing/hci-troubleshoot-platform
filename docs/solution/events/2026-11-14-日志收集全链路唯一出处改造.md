# 2026-11-14 日志收集全链路「唯一出处」改造

## 背景

客户侧一次「场景清单目录缺失」失败，同屏出现四处结论互相矛盾的说法：

1. 进度条下的 `error_message` 长句；
2. 平台结论区两条「桥接端版本较旧，暂无该数据」+ 一条「观察事实：未取到有效日志」；
3. 红色诊断卡（`LC-SPC-001` + 如何检查/如何处理 + 同一句长句）；
4. 顶部红色弹框「htp平台：平台未给出可识别的错误码」。

第 4 处尤其严重：明明有明确错误码与完整原因，弹框却说平台没给码，并把 `LC-SPC-001`
按关键词兜底成 `LC-HTP-002`。管理端「首个异常点」同样会显示这个兜底码。

## 根因（第一性原理）

把「报错」拆到不可再分的五层后发现，每层都有多个权威：

| 层 | 改造前出处数 |
|---|---|
| 事实产生（terminal_bridge） | 71 个运行时码统一，但中文文案散在 12+ 个 Go 文件 文件 |
| 传输/落库 | `error_message` 在 5 处被改写或包装 |
| 字典/派生 | **9 处**：契约 20 码、后端 catalog 71 码、`_RULES` 85 条、迁移 062/064、Go 元数据、前端 `HINTS` 20 条、codegen py/ts |
| 呈现模板 | custom-ui 16 组件 + 10 utils + verify 页；admin-ui 3 模板 + 5 张自建映射表 |
| 可观测性 | trace 4 处断链、日志收集专属指标/告警为 0 |

决定性事实：契约的 20 个展示归因码与后端 catalog 的 71 个运行时码**交集为 0**，
但语义重叠 ≥4 组；前端 `HINTS` 的 20 码与契约也**交集为 0**。所谓「统一整改」
（#1488 / #1490 / #1499）是三条叠加链路，从未合并成一份字典。

## 方案：扩展而非重建

保留 `contracts/log_collect_display.json` 的全部既有键名与 codegen 产物名，
把 schema 升到 v3，把所有手写字典的内容收进这一个 JSON：

- `fault_catalog`：**91 条**，用 `kind` 区分 `runtime`（71，可进 `error_code`）
  与 `signal`（20，仅供三段五组件证据定界）。原来「前缀绑定组件」「每码必须有
  匹配规则」两条校验会误拒全部 71 个运行时码，已改为只对 `signal` 生效。
- `attribution_rules`：**85 条有序规则**。必须单独保留顺序；曾把它们按码聚合进
  `fault_matchers` 的尝试会破坏「具体到泛化」的优先级（客户机磁盘满会被泛词抢走）。
- `aliases`：语义重叠码显式登记，CI 断言无环、目标存在。
- `ui`：状态/交付/模式/统计桶标签、无数据四态文案、兜底文案、
  `render_policy`（同视图 `error_message` 与 `error_code` 各最多 1 次、
  `error_code_authoritative=true`、未进入采集时不输出 `artifact_missing`）。
- `observability`：唯一调用链（`X-Trace-ID` / 5888 侧 `X-Request-ID`）、
  事件名枚举、日志必填字段、指标清单、命令式删除禁词。

`scripts/gen_log_collect_display.py` 现生成**七份产物**，原本手写的五份文件
（后端 catalog JSON、前端 `frontend/customer/src/services/logCollectErrorHints.ts`、新增 `frontend/shared/src/logCollectUi.ts`、
`backend/case-service/app/services/log_collect_attribution_rules_generated.py`、Go 码表）全部降级为生成物。
`gen --check` 保证任何一处手改都会漂移。

## 本次改动

**契约与生成器**：schema v3；`validate_contract` 放宽前缀/matcher 校验并新增别名、
呈现策略、禁词、补码规则闭合校验；`_py_literal` 改用 `pprint.pformat`
（此前用 `json.dumps` 会把布尔 `retryable: false` 写成非法 Python）。

**后端**：`backend/case-service/app/services/log_collect_error_attribution.py` 的 `_RULES` 改为引用生成物；
网关 `FORWARDED_REQUEST_HEADERS` 补 `x-trace-id`；P2 代传在 `httpx.AsyncClient`
层注入 `X-Request-ID = task.trace_id`。

**custom-ui**：失败态状态行不再重复 `error_message`（原文只在诊断卡出现一次）；
平台结论区的两条「桥接端版本较旧」合并为按判据分流的一条；观察事实在
「失败且未进入采集」时过滤掉必然派生的 `未取到有效日志`；
顶部弹框优先用 `error_code`，且无权威码时不再谎称「平台未给出可识别的错误码」；
`LC-SPC-010` 文案里「多台节点」这个错误量词已纠正。

**admin-ui**：`STATUS_TEXT / DELIVERY_TEXT / MODE_TEXT / bucketLabels` 四张手写表
改为契约生成物；空态按「未进入该环节 / 明确旧桥 / 真无数据」分流。

**门禁与文档**：新增 `scripts/verify_log_collect_contract.py` 与
`.github/workflows/log-collect-contract.yml`；门禁会拦截手写映射表回归、
生成物被手改、禁词进入文案、别名/规则悬空。

## 第二批：遗留项一次收口（同一 PR）

**先纠正三处事实，再动手**（对抗性审查）：

1. 迁移 `066` 已被壳工单元数据回填占用 → 新增迁移实际是 `067`；
   且 **schema/列/索引的唯一权威是 `database/desired_schema.sql`（Atlas 声明式）**，
   迁移文件只做 DML 订正，不能建表建索引，更不能建持久备份表。
2. 四张证据表**已有** `trace_id` 列，缺的是索引；`log_collect_task.trace_id` 可空，
   存量存在空值，强行 `NOT NULL` 会撞迁移。改为「补索引 + 如实回填缺口」。
3. `frontend/customer/verify/VerifyApp.vue` 的字典表**已是全 91 码**，
   缺的只是批量截图/断言脚本；不需要重写验收页。
4. 上轮生成的 `contractTitle` 是**死代码**——没有任何 Go 代码消费它。
   这比「中文没删」更严重：唯一出处生成了却没被使用。
5. `error_payload` 不必新增列：`detail.spc_hosts` / `create_output` / `write_audit`
   已在库里，admin 详情复用即可，避免 schema 扩张。

**terminal_bridge**：`spcErrorTitle` 的 13 条手写中文标题全部删除，改由
`validationErrorCode` 映射到规范码后读 `contractTitle`；聚合句、逐台明细与
「回滚失败」叠加风险改由 `ui.go` 模板渲染。Go 单测的期望文案也改为从契约
生成物取，并新增 `TestContractCatalogIsConsumed` 防止码表再次退化成死代码。
**判断**：`blog()` 日志与 `Message` 现场原始输出是可观测性证据，不是平台 UI 文案，
予以保留；要收敛的是「平台给用户看的报错文案」。

**展示串归契约**：`ui.headline`（横幅 20 处）、`ui.admin`（分区标签）、`ui.go`
（桥侧模板）追加到契约，`logCollectDelivery.ts`、`LogCollectDiagnosis.vue`、
`LogCollectPanel.vue`、验收页夹具全部改为引用。**值保持不变**，因此既有断言不因
搬运而失效，但前端不再有第二份横幅文案。

**数据层**：`database/desired_schema.sql` 补 6 个调用链/对账索引；
`database/data-migrations/067_log_collect_contract_trace_backfill.sql` 把
`cancelled_by_user` / `corrected_by_node` 迁出 `error_code`（取消/纠正是动作不是
失败类别，动作写进 `detail` 审计），历史缺 `trace_id` 的行**只标记缺失、不伪造 ID**
——造一个与任何真实请求都无关的 ID，会让「按链路检索」看似有效实则指向空。
后端两处写入点与前端取消态诊断卡一并修正，避免清空码后弹出误导的失败兜底。

**可观测性**：`backend/shared/observability/metrics.py` 新增 3 个有真实埋点的应用指标
（归因来源 / 契约漂移 / 调用链缺口），埋点收在 `LogCollectService` 保存边界；
`deploy/helm/hci-platform-obs/rules/alert_rules.yml` 新增 4 条告警，
`deploy/helm/hci-platform-obs/rules/alert_rules_test.yml` 补 1 正 2 反 promtool 用例。
**所有规则只用应用指标并加空序列门控**，不依赖 node-exporter（其缺失曾让磁盘/内存
告警长期静默）。

**展示形态**：新增 `frontend/customer/src/components/LogCollectStatusCard.vue`，
form 失败态与 result 结果态共用同一份渲染；横幅不再重复拼「观察事实」，

## 5888 现网的处理（对抗性审查结论）

原方案准备改日志服务器代码以透传 `X-Trace-ID`。只读探测 `acli@192.168.0.2:22468`
后发现 现场日志服务器的 Flask 入口 已有 `@app.before_request` 的 `_assign_trace_id()`：
它优先复用上游 `X-Request-ID`，并写进日志 `trace=` 与响应头。
因此**现网零改动、零重启、零提权**——平台侧在 P2 代传注入请求头即可闭合断链④。
22 端口 refused，22468 免密可用。P1 直传由节点 acli 插件发起，不经平台，
仍需在插件侧带同一请求头，列为现场侧遗留项。

## 遗留项（现场侧 / 验证边界，不在本 PR 代码范围）

1. **P1 直传插件侧调用链**：P1 由节点 acli 插件直发 5888，不经平台；插件源码
   不在本仓库（在 `192.168.0.2:/acli` 与客户节点），需现场在直传请求上带
   `X-Request-ID` = 任务 `trace_id`。5888 侧已支持复用该头，平台不能代劳。
2. **bridge exe 现场重装**：新码表与文案随仓库自动构建，但 exe 不会自动到达
   客户机。现场未重装前旧桥仍发旧长句，由保存边界的 85 条有序补码规则兼容，
   平台侧展示已正确；结构化逐台明细需新 exe 上报后才完整。
3. **前端业务专有中文串**：门禁基线 7227 含模板里的业务说明、按钮、注释与
   非报错文案。本次收敛的是「报错 / 结论 / 状态 / 空态 / 横幅」口径；
   业务专有文案不进契约，避免把契约膨胀成全平台文案大字典。
4. **验证边界**：本机无 `promtool` 与 Postgres。4 条告警规则 + 3 个 promtool
   用例由 CI `helm-validate` 执行（YAML 已用 PyYAML 校验：9 groups / 17 tests）；
   迁移 067 与 6 个索引由 CI `db-migration-test` 执行。真浏览器逐码与几何
   校验在本机 chromium 实际跑过。
