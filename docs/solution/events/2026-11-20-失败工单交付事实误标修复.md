# 方案事件：失败工单交付事实误标修复

## 变更历史

| 日期 | 版本 | 变更摘要 |
|------|------|---------|
| 2026-11-20 | v1.0 | 初版：确定「证据优先、只读核对、审计订正」三层方案 |

## 背景与需求

见 [需求事件](../../requirement/events/2026-11-20-失败工单交付事实误标修复.md)。核心约束：5888 的同名归档有手工上传、历史包、截断包三种伪证据，不能凭"有包"直接翻状态。

## 方案概述（WHAT）

1. **派生层**：`_conclusion()` 在有 `archive_check.verified` / `archive_confirmation.verified` / `delivery_evidence=archive_verified` 时，先于 `status=failed` 判 `success/partial`。
2. **观测层**：`destination_progress()` 允许对 failed 行一次性只读核对；前端把 `state=done` 文案改为转述 5888 的 size/sha256，不再声称已与源包比对。
3. **展示层**：列表增加「本工单已有归档」标记，与「最近一次尝试失败」并列，解决重试覆盖成功。
4. **归因层**：新增 `LC-TRANSFER-011`，把"节点包 mtime 早于采集开始"从 `/sf/data/local` 磁盘关键词中剥离。
5. **数据层**：以 `task_id` + 证据条件双重 WHERE 的 SQL 订正 5 行，原值写入 `detail.data_correction.before`。
6. **巡检层**：独立只读脚本按工单号查 `/archive_status`，输出 missing / stale / size_mismatch / verified 四类判定。

## 决策依据（WHY）

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| A. 证据优先 + 审计订正（选中） | 保留状态机不变；可回滚；能挡伪证据 | 需要同步改展示与派生 | ★★★★★ |
| B. 直接允许 `failed→completed` 批量翻状态 | 改动小 | 会把手上传/旧包/截断包一起翻正，破坏状态机 | ★ |
| C. 只在 UI 隐藏失败 | 零后端改动 | 数据库仍错，其他消费方继续误判 | ★★ |

选择 A：第一性原理要求以"权威证据"为唯一事实源；对抗性审查要求任何翻正都被证据约束、且保留原值。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 198 个 partial 行被证据优先级改变 | 中 | 仅在 `status=failed/delivery=failed` 且证据为真时生效；补单测锁定 |
| 5888 被巡检打爆 | 中 | 4 并发 + 定时单次；不进入列表轮询 |
| 订正误伤手工上传 | 高 | 只按 5 个明确 task_id + 证据字段 WHERE，写入 before 快照 |
