# 工单 Q2026060669426 排障系列缺陷修复设计方案

本方案旨在针对工单 `Q2026060669426` 排障流程中暴露出的四个典型缺陷进行深度定位并提供彻底的修复方案。

---

## 1. 缺陷深度分析与根本原因

### 1.1 缺陷一：lsblk 命令执行超时（返回 `[exit_code=-1]` 且耗时 32s）

- **现象**：左侧 AI 助手自动执行命令 `lsblk -d -o NAME, SIZE, ROTA, TYPE, MODEL, SERIAL | head -30` 超时（32s），但在右侧 SSH 终端手动执行时却能正常秒回。
- **定位**：
  1. **命令本身的区别**：左侧 AI 生成的命令在字段逗号后带有空格（`NAME, SIZE, ...`），而右侧手动执行的没有。在 Linux 中，这会导致 `lsblk` 命令将 `SIZE` 及后续字段误识为设备名，报错 `lsblk: unknown column: NAME,` 并立即退出。
  2. **为何会超时 32s**：
     - 当 AI 执行命令时，它被发布到前端。前端利用 `chat.ts` 的本地 WebSocket 向 `terminal_bridge` 写入经过包装的带退出码捕获脚本的命令行：
       ```bash
       lsblk -d -o NAME, SIZE, ... | head -30; status=$?; printf '\n__EXEC_DONE_<execId16>:%s\n' "$status"\n
       ```
     - 此时，由于 `terminal_bridge` 申请的是交互式带有回显（PTY ECHO）的 Shell 会话，写入该命令后，SSH 会话的 stdout 字节流中会**立刻回显输出这一长串命令原文**。
     - 命令原文回显中正好包含了用于做结束判定的 Marker：`__EXEC_DONE_<execId16>:%s`。
     - `terminal_bridge` 里的 `checkMarkers` 方法使用了简单的子串过滤，误匹配了 **PTY 的命令回显**，误以为命令已经执行完毕，并提前注销了该命令在 Bridge 端的数据通道监听器。
     - 此时由于前端 `chat.ts` 注册 `waitForExecResult` 的微小时差（在异步 `send` 之后同步 `register`），这个瞬间回传的回显结果被前端丢弃。而当命令真正执行完时，由于 Bridge 端已经没有监听器，真实的退出码和输出再也无法发回。
     - 最终导致前端等待 35s 超时，而后端 `agent-service` 的 Redis `blpop` 先于 32s 超时中断，强行返回了 `exit_code=-1`。

### 1.2 缺陷二 & 三：禁用工具报错“更新工具状态失败” & 保存编辑报错“HTTP 500”

- **现象**：在工具管理页面切换启用状态，或编辑保存 `get_vm_list` 时，页面报错且后端返回 500。
- **定位**：
  - 查询 `conversation-service` 容器日志发现致命报错：
    ```python
    File "/app/app/routes/tool_definition.py", line 169, in update_tool
      logger.info(event="tool_updated", tool_name=t.tool_name, tool_id=t.id, message="更新了工具定义")
    TypeError: Logger.info() missing 1 required positional argument: 'msg'
    ```
  - 原因是在 `/app/app/routes/tool_definition.py` 中导入了标准 Python `logging` 模块：
    `logger = logging.getLogger(__name__)`
    然而在代码中却使用了结构化日志传参规范（如 `logger.info(event=..., message=...)`）。标准库 `Logger.info()` 不支持关键字参数，导致抛出 `TypeError` 并中断数据库更新事务提交。

### 1.3 缺陷四：get_vm_list 的 `limit: 3` 参数来源 & `NoneType` 执行报错

- **现象**：在工具管理中没有定义 `{"limit": 3}`，但 AI 执行时却带有此参数，且工具执行抛出 `'NoneType' object has no attribute 'execute'` 错误。
- **定位**：
  1. **参数来源**：`get_vm_list` 在数据库的 `parameters_schema` 中确实有 `limit` 字段参数（默认值 20）。AI 在诊断执行过程中为了限制结果长度以防上下文溢出，自主决策将 `limit` 改为了 `3`。
  2. **`NoneType` 报错原因**：
     - 在当前环境中，环境变量中 `REACT_ENABLED` 被设置为了 `false`。
     - 后端 `agent-service` 的 `app/main.py` 仅在 `REACT_ENABLED=true` 时才会实例化 `scp_client` 与 `acli_client`。
     - 但在主诊断大脑 `InvestigationAgent` 中，无论 `REACT_ENABLED` 为何，都会初始化 `CompositeToolExecutor`。由于上面没有初始化客户端，导致复合执行器的 `self._scp` 为 `None`。
     - AI 在诊断时，对 category 为 `scp` 的工具 `get_vm_list` 进行调用，最终在 `CompositeToolExecutor` 中执行了 `self._scp.execute()`，引起 `NoneType` 崩溃。

## 2. 改造方案设计

### 2.1 缺陷一修复：过滤 PTY 命令回显中的判定 Marker

为了防止 `terminal_bridge` 误匹配 PTY 的命令回显而提前注销通道，我们不能简单地依赖 `strings.Index` 搜索。我们可以在匹配到 Marker 标识时，判定该行中是否包含 Shell 命令行特有的字符（如 `status=` 或 `printf`）。如果包含，说明此行只是 PTY 的命令回显（Echo），应直接忽略，继续等待真正的执行结果输出。

#### 改造点：`terminal_bridge/main.go` -> `checkMarkers`
```go
			// 解析 exit_code
			var exitCode int
			if _, err := fmt.Sscanf(markerLine, markerPrefix+"%d", &exitCode); err != nil {
				// 如果解析失败，且该行明显是命令回显（带有控制字符或 script 特征），则忽略它
				if strings.Contains(markerLine, "status=") || strings.Contains(markerLine, "printf") {
					continue
				}
				exitCode = -1
			}
```

### 2.2 缺陷二 & 三修复：替换为统一的结构化日志记录器

将 `tool_definition.py` 中错误的本地 Logger 替换为共享模块的 `get_logger`。

#### 改造点：`backend/conversation-service/app/routes/tool_definition.py`
```python
from shared.observability.logger import get_logger
logger = get_logger(__name__)
```

### 2.3 缺陷四修复：安全初始化执行客户端与防御性 `None` 检查

1. 无论 `REACT_ENABLED` 开关如何，只要环境变量中有相关配置，就在启动时安全地（使用 `try-except` 包裹防止没有配置其他环境变量时导致 Crash）初始化 `scp_client` 与 `acli_client`，以防诊断大脑（S1-S4 阶段）没有工具执行能力。
2. 在 `CompositeToolExecutor.execute` 中添加对 `self._scp` 和 `self._acli` 的 `None` 值判断。如果为 `None`，返回结构化错误而非抛出未捕获异常崩溃。

#### 改造点：`backend/agent-service/app/main.py`
- 将客户端初始化移出 `if settings.REACT_ENABLED:`。
- 修改 `CompositeToolExecutor.execute` 对于 `self._scp` 调用的保护。
