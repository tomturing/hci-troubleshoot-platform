# 日志收集：custom-ui 与 HCI 的两端状态对齐

## 一、问题：两个状态机，一套投影

一次日志收集有两个独立状态：

| 侧 | 载体 | 特点 |
|---|---|---|
| 平台 | `log_collect_task`（DB） | 由前端在关键节点 PATCH 写入 |
| 节点 | `acli log_collect`（插件，按 ticket 维度） | 唯一真相，但只能通过 bridge 执行 CLI 才能观测 |

异步必然导致漂移。2026-10-26 工单 `Q2026101401683` 出现三套并存的状态：

- 任务表：`failed(16:03)` / `completed 100%(19:01)` / `failed(19:03)`
- 节点终端：`收集任务异常结束！0%，三节点 79%`
- 面板：进度 0%，底部报「日志收集分析任务正在执行」+ ANSI 乱码

### 根因（第一性原理）

1. **真相源错配**：平台把"前端某一次 PATCH"当真相，节点只在创建后那几秒被观测，之后永不复核。
2. **完成判定过松**：`percent >= 80 || status 含"完成"` 就落终态。同一 ticket 重复 create 时 acli 会返回**上一次任务**的完成报告（实测 `done=1/total=1`，而集群 3 节点），平台据此写 completed 并挂上旧包路径。
3. **状态语义缺失**：插件说的是「异常结束」，既不含"完成"也不含"失败"，前端既不判完成也不判失败，按 5s 间隔空转到 720 次（1 小时）超时。
4. **终态后无对账、无清理**：任务转 failed 后节点任务仍在跑，插件单任务互斥 → 后续 `create` 一律被「任务正在执行」拒绝，形成僵尸任务。
5. **统计口径三套**：acli 原文 `8/3（已收集完成 0/采集总数 3）`、bridge 解析 `done=0/total=3`、UI 渲染 `${status}（${done}/${total}）`，用户无法判断真实进度。

## 二、对齐机制

### 2.1 真相源

**节点态是唯一真相，平台任务是投影**。投影允许被节点覆盖，覆盖必须留痕。

### 2.2 节点态归一化（bridge 侧）

`log_collect.progress` 新增 `node_state`，把中文文案收敛为枚举：

| node_state | 判据（优先级从上到下） | 含义 |
|---|---|---|
| `abnormal` | 状态含 异常结束 / 失败 / 错误 | 任务异常终止，必须清理 |
| `completed` | 状态含 完成 | 正常完成 |
| `running` | 状态含 进行中 / 收集中 / 上传中 / 打包 / 准备；或 percent/done/hosts 非空 | 正常推进 |
| `none` | 状态含 不存在 / 无任务 / 暂无 | 节点上已无任务 |
| `unknown` | 其余 | **不做任何写操作** |

> 2026-10-26 二次修正：**删除** `archive_mtime` / `archive_exists`。
> P1 直传成功后插件会自删压缩包，`stat` 在成功路径上必然失败，
> 这条"时间证据"既不成立、又会把真完成永久判成"无法确认"。

### 2.3 报告归属：下发时锚定，而不是事后猜

`acli log_collect progress` 是 **ticket 维度**的：同一工单重复 create 时，
下发后的头几次仍是**上一次任务**的报告。所以要判断的不是"节点完成得对不对"，
而是"这份报告属于哪一次下发"。

```
基线 = create 之前读到的 progress 原文指纹（前端 hashReport：长度 + FNV-1a 32）
归属 = 当前报告指纹 ≠ 基线指纹 ? 本次任务 : 上一次任务的旧报告
```

- 基线随任务落库（`log_collect_task.detail.baseline_report_hash`）：
  关面板、换浏览器、重启后接管都能继续判归属；
- 指纹相同 → `wait_refresh`：**不落终态、不算失败、不计数**，继续自动刷新；
- 没有基线可比（历史任务 / 旧 bridge）时，只用两条**只做否决**的兜底：
  `progress.total ≠ expectedHosts`、报告主机与目标主机无交集；
- 两条兜底也拿不到结论 → `unknown`，**按节点态为准**。
  证明不了"报告是旧的"，就不该把真完成卡在采集中。

> 现场（`Q2026101401683` / 21:57）：节点 100%、上传成功、压缩包已被插件自删。
> 旧实现要求"完成必须拿出一条正向证据"，而两条证据（包 mtime、报告已刷新）此时都拿不到，
> 于是面板永久提示"既没有新的节点报告，也拿不到压缩包时间"，平台停在 `collecting`。
> 判据的方向错了：不需要证明节点是对的，只需要识别报告是旧的。

### 2.4 对账映射表

| 平台态 | 节点态 | 动作 |
|---|---|---|
| 任意 | 旧报告（指纹与基线相同） | `wait_refresh`：等待本次任务的报告 |
| collecting | running | 正常推进；进度快照每 10% 落一次 |
| collecting | completed | `patch_completed` |
| collecting | abnormal | `patch_failed` |
| collecting | none（有包路径） | `patch_completed` |
| collecting | none（无包） | `patch_failed`（采集中断） |
| failed / cancelled | running | `adopt`：一键接管，继续跟进 |
| failed / cancelled | abnormal | `cancel_retry`：一键清理并重试 |
| failed / cancelled | completed | `patch_completed` |
| completed | running | 提示冲突，**不自动回退**（归档是既成事实，重收请点「重新收集」） |
| completed | abnormal | 提示核对归档产物 |
| 无任务记录 | running / abnormal | `warn_node_busy` + 一键清理 |
| 任意 | unknown | `none`（不猜） |

### 2.5 对账时机

| 时机 | 说明 |
|---|---|
| 打开面板 / 查看任务状态 | 覆盖"上次会话断在半路"留下的旧投影 |
| 点「开始收集」前 | 前置守卫：节点有未结束任务时直接拦截；同时读取并锚定基线 |
| 「刷新进度」 | 读节点态 → 覆盖平台态 |
| 自动轮询（每 5s） | **与「刷新进度」同一个函数**：读节点态 → 归属判定 → 映射落态 |

自动与手动必须同源：此前自动轮询只读平台快照，而平台快照不会自己变，
于是节点早已 100%、面板仍停在 0%，"自动刷新"看起来像没生效。

### 2.6 一键动作（不需要 SSH）

- **接管继续**：平台终态 → `collecting`，清除 `finished_at` / `error_code` / `error_message`，随后按任务实际交付路径收尾（`upload_mode=acli_direct` 或 `remote_url` 非空 → 等直传完成；否则走中转）。
- **取消并重试**：先经 bridge 执行 `acli log_collect cancel`，确认节点任务终止后再写平台终态，最后用当前表单重新下发。
- **以节点为准纠正**：仅当"平台已归档 + 节点仍在跑 + 报告已刷新（指纹与基线不同）"同时成立时开放。
  报告没刷新时已被 `wait_refresh` 拦住，不会走到这里。
- 三者都**不自动执行**：接管、清理、纠正都会改变生产状态，交给用户点一次；
  自动只做"状态修正"（`patch_completed` / `patch_failed`）。

### 2.7 安全边界

- 只对任务锚定的**发起节点**对账，多节点不合并判断（避免误取消其他机器上的任务）。
- `node_state=unknown` 一律不动。
- 绝不自动 create / 自动重试：重复采集的代价远大于状态短暂不准。

### 2.8 接管态的展示契约

平台在 `create` 时就落库了 `modules` / `date_from` / `date_to` / `ips` / `upload_mode` / `origin_node_ip`，
这是"这次下发了什么"的唯一权威记录。接管（刷新页面、换浏览器、点「查看任务状态」）时必须：

- **回填表单**：模块、时间范围、目标主机一律来自任务记录，而不是表单默认值
  （默认值会让用户以为"这次只采了 all 全节点"，实际可能只选了 1 台）；
- **置为只读并说明来源**：任务进行中不可改参数，面板要写明"参数来自平台任务记录"；
- **重新收集时复用**：`startRecollect` 用同一条任务记录预填，用户只改需要改的项。

外部任务（不经本平台 `create`，直接在节点上执行 `acli log_collect`）只能看到节点侧信息：

| 能拿到 | 拿不到 |
|---|---|
| 状态文案、总进度、主机列表与各自百分比、压缩包路径、上传状态 | 故障场景（modules）、时间范围（date_from/date_to） |

`acli log_collect progress` 的报告里根本没有后两者，平台也没有对应任务记录，
因此这类任务一律按 `warn_node_busy` 提示"非本平台下发，模块与时间范围无法获取"，
不做任何推测填充。

## 三、可观测性

- bridge：`log_collect.progress` 日志记录 `node_state`；不再 `stat` 压缩包（少一次远端命令）。
- 前端：对账结论与一键动作走 `ElMessage` + 面板提示条，文案含判定依据（`buildSyncNotice`）；
  「更新于 hh:mm:ss」由每次对账刷新，自动刷新是否在跑一眼可见。
- 平台：判失败/完成时把 `action.reason` 写入 `error_message`，事后可追溯"依据什么改的状态"。

## 四、验证

| 场景 | 期望 |
|---|---|
| P1 直传成功、压缩包已被插件自删 | 5s 内自动落 completed，进度 100% |
| 接管态（换浏览器/重启）打开面板 | 从 `detail.baseline_report_hash` 恢复基线，正常对账 |
| 下发后节点仍打印上一次完成报告（指纹与基线相同） | 不写 completed，提示"仍在等本次任务的报告"，自动刷新继续 |
| 节点报告已刷新 | 按节点态直接落态，不再附加完成判据 |
| 节点「异常结束」 | 立即 failed，不空转 |
| 平台 failed、节点 running | 面板出现「接管继续」/「取消并重试」 |
| 节点有僵尸任务时点开始 | 被前置守卫拦截，不产生 failed 任务记录 |
| 重新收集 | 清空上一轮快照与基线，先提示"等待新报告"，绝不秒跳 100% |
| 自动刷新 vs 手动刷新 | 同一函数、同一结论、同一时间戳语义 |
