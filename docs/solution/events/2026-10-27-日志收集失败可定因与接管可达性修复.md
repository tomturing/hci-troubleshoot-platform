# 日志收集失败可定因与接管可达性修复

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：修复失败原因丢失、错误码不回写、探测事实不落库、failed 任务不恢复导致接管不可达 | 无独立任务文档 |

---

## 一、现场事实（staging，2026-10-23 ~ 2026-10-27）

| 观测项 | 数值 | 说明 |
|---|---|---|
| 任务总数 / 工单数 | 38 / 10 | `log_collect_task` |
| failed | 23（61%） | 10 个工单中 9 个至少失败过一次 |
| `error_code` 有值 | 3 / 38（其余 35 个为 NULL） | 3 个都是 `cancelled_by_user` |
| `arch` / `acli_version` 非空 | 0 / 38 | 探测结果只存在于前端内存 |
| `completed` 且 `archive_size` 为空 | 12 / 12 | 交付链路另一议题（#1296 已修，部署滞后） |
| `log_collect.create` 失败且 `error` 为空 | 19 / 19 | 桥侧日志里 `{"error": ""}` |

失败原因原文分布：`错误：未知的命令或者命名空间(log_collect create)` ×10、`日志收集分析任务正在执行` ×6、磁盘 <6GB ×4、SSH 会话不存在 ×2、平台 500 ×1。

**时间线校准（重要）**：6 次“正在执行”全部发生在 #1277（2026-10-26 19:46 北京）之前，修复后 19:55 起 create 全部成功、10-27 零复现。因此“平台无接管机制”不成立——接管（adopt）已实现且生效，本文件只修它的**可达性**。

## 二、根因

| # | 根因 | 代码位置 |
|---|---|---|
| R1 | `runCommandPty` 把 `ssh.ExitError` 归一化成 `exitCode` 后返回 `err=nil`，`errString(err)` 恒为空 → create 失败的 `error` 字段永远写不进去 | `terminal_bridge/log_collect.go` `runCommandPty` / create 分支 |
| R2 | 失败以 `throw` 抛出，桥侧 `log_collect_result.error_code` 在异常链里丢失；落库 `patch failed` 时没有带码 → 错误码目录无法统计与分流 | `LogCollectPanel.vue` 主流程 catch、对账 patch |
| R3 | 探测事实（arch / acli_version）只存在前端内存，create 未落库；关面板/换端后证据消失，无法回答“哪版 acli 失败” | `LogCollectTaskCreate` / `create_task` / 前端 create 调用 |
| R4 | `restoreTaskState` 只恢复“进行中 → 已完成”，**不恢复 failed**。失败后重开面板 `currentTask=null`，preCreate 守卫拿到 `platformStatus=null`，把“本平台已判失败、节点仍在跑”误判成 `warn_node_busy`（文案还写“非本平台下发”），接管按钮不可达 | `restoreTaskState` / `decideNodeSync` / `syncNodeState` |
| R5 | 落终态后 `stopAutoSync()`，failed 任务不再对账，用户不手动点“刷新进度”就永远看不到「接管」 | `triggerAutoSync` / `syncNodeState` |
| R6 | `error_message` 直接取桥侧原文，混入 ANSI 颜色码与 `FATA[0000] execing command in container` 包装行 | 前端失败回写 |

## 四、验收标准

1. 桥侧 create 失败时 `log_collect.create` 的 `error` 字段非空，且不含 ANSI 转义。
2. 平台 `failed` 任务 `error_code` 形如 `LC-<LAYER>-<NNN>`（不再是 NULL）；`error_message` 只有一行、不含 `FATA[...] execing command in container`。
3. 新建任务后 `arch` / `acli_version` 落库非空。
4. 任务 failed 后关闭面板再打开：面板停在失败态（不是空白表单），节点仍在跑时出现「接管」按钮；点「接管」后平台回到 collecting 并继续跟进。
5. 终态任务对账间隔为 30s（不再是 5s 空转，也不再完全停止）。
6. 回归：`uv run pytest backend/case-service/tests/unit/`、`vue-tsc -b`、`vitest run`、`go test ./...` 全绿。

## 五、明确不做（本 PR 边界）

- 不改接管（adopt）/ 纠正（correct）状态机与判定矩阵。
- 不改变跨客户端复用同一工单号的能力（方案 A 维持），只补文案。
- 不做日志收集工单自动关闭（业务决定：保持 created）。
- 不做 acli 能力前置校验、磁盘余量拦截、平台结构化事件日志、制品持久卷（另批）。

## 六、回滚

纯代码回滚，`git revert` 本 PR 即可；无数据库 schema 变更（`arch` / `acli_version` / `error_code` 均为既有列）。已写入的 `arch`/`error_code` 属增量事实，回滚后闲置不影响旧逻辑。
