# DSH 双实例与离线诊断接入

## 目标

在不改变既有 `admin/dsh-diagnosis` 和 `/dsh` 服务的前提下，增加一套独立的 HCI
单 Agent 离线诊断 Harness。新实例使用精确锁定的插件组合：

| 插件 | 版本 | 职责 |
|---|---:|---|
| `deepseek-harness-wecom` | 0.1.33 | 企业微信通道 |
| `deepseek-harness-session-bi` | 0.1.21 | Session BI、规则包和运营台账 |
| `hci-offline-diagnosis-bundle` | 0.4.1 | HCI 单 Agent 离线诊断 Preset |

旧实例继续使用 `deepseek-harness-wecom-offline-0.1.22.tgz`，不迁移旧会话，也不复用旧
Service 或 token 文件。

以上 `.tgz` 均由独立的 `dsh_plugins` 源码子项目构建；平台仓的 `dsh/plugins/` 只保存
版本化发布制品。插件升级时先在 `dsh_plugins` 构建新制品，再更新平台仓制品和环境仓
对应实例的 `dsh.plugins.packages`，不能把 `dsh/plugins/` 当作源码目录直接开发。

新实例的运营 BI 规则包原始内容另由仓库根 `dsh_cockpit-rules/` 持久化，按
`<rule-package-id>-<version>/` 保存 `manifest.json`、workflow 和 knowledge 内容；它是规则
原始内容事实源，不是插件 `.tgz`。Session BI 默认将数据文件写入
`$DSH_HOME/session-bi/records.json`，规则包使用 `$DSH_HOME/session-bi/rule-packages`，
规则源回退到 `WECOM_WORKSPACE_ROOT`，会话分析目录回退到 `WECOM_RULE_WORKSPACE_ROOT` 或
`$DSH_HOME/session-bi/work-ticket-rules`。只有需要改变默认布局时才覆盖
`DSH_SESSION_BI_*` 变量；规则内容更新必须新增版本目录，不覆盖历史版本。

## 运行拓扑

```text
admin-ui /admin/dsh-diagnosis         -> /api/dsh/launch        -> dsh.hci-dsh:8080
admin-ui /admin/dsh-offline-diagnosis -> /api/dsh-offline/launch -> dsh-offline.hci-dsh:8080

旧 DSH:     /dsh/         + dsh_home/token/workspace
新 HCI DSH: /dsh-offline/ + dsh-offline token/home/workspace
```

同一 Helm Chart 通过 `namePrefix=dsh-offline` 生成第二套资源；两套 release 共用 namespace
内已存在的 image pull、LLM 和 WeCom Secret，但每个实例的 DSH profile、token、工作区、
会话文件和 nginx 反代路径均独立。新 release 关闭 shared Secret 的管理开关并设置 sync wave，
避免两个 ArgoCD Application 争抢同名 Secret。新页面使用管理员鉴权后的 launch token，浏览器
不接触集群内部 Service。

## 配置边界

- 旧 `/dsh` 的入口、插件、API 和页面不改，保障已有诊断链路可回滚。
- Compose 中旧实例继续读取 `DSH_*` / `WECOM_*` 变量；新实例完整读取独立的
  `DSH_OFFLINE_*` / `DSH_OFFLINE_WECOM_*` 变量，再映射为容器内插件所需的 `WECOM_*`
  和 `HCI_*` 名称；Session BI 的台账、规则包和分析目录使用独立 DSH_HOME 下的默认值，
  避免 LLM、插件、知识根目录、规则工作区、WeCom 凭据和反代地址发生隐式串用。
- Compose 的两个服务显式共用 `docker-dsh:latest` 镜像；这是镜像层复用，不是运行态配置
  复用，两个服务仍分别使用不同的 profile 参数、插件列表、卷、网络别名和 proxy。
- Session BI 客户端固定请求绝对 `/api/deepseek-harness-session-bi/*`，管理台 Nginx 将其
  用 307 改写到 `/dsh-offline/api/*`，由新 DSH sidecar 继续剥离前缀；不把 DSH Cookie
  作用域扩大到平台根 `/api`。
- 新实例由 GitOps Application `hci-platform-dsh-offline-{dev,staging,prod}` 管理，路径为
  `/dsh-offline`，管理台菜单为「DSH离线诊断」。
- 双仓部署下，旧 DSH 基线由 `hci-platform-env/environments/<env>/dsh-values.yaml` 维护，
  offline 实例的插件组合、`pluginEnv`、hostPath/Ingress 开关和 Secret 管理开关由
  `dsh-offline-values.yaml` 维护；平台仓的 ArgoCD Application 只引用这两层 values，不再内联环境参数。
- 旧 DSH 使用 `dsh-plugin-credentials`，新 DSH 使用独立的
  `dsh-offline-plugin-credentials`；两个 Secret 必须分别写入各自 WeCom 机器人的
  `WECOM_BOT_ID` / `WECOM_BOT_SECRET`，不能因共用镜像而共用机器人身份。
- 管理台旧 DSH 与离线 DSH 页面共用同一个 `DshTicketSyncPanel`，后端 `/ticket-sync`、任务状态、
  工单产物目录和清理记录保持单套实现；两页只是分别展示同一套工单日志能力。
- 新实例只读使用 `DSH_OFFLINE_WECOM_WORKSPACE_ROOT` 作为 HCI 知识与支持包根目录（默认
  `/data/tickets`）；Session BI 数据写入其独立
  DSH 家目录。生产若需要跨 Pod 保留台账，应再为 `home.hostPath` 配置已由 uid/gid 1000
  预创建的独立目录，不能指向旧实例家目录。
- Compose 新实例的 `DSH_OFFLINE_TICKETS_PATH` 是宿主机源路径，卷目标由
  `DSH_OFFLINE_WECOM_WORKSPACE_ROOT` 决定；两者必须保持同一个容器内工作区路径，否则
  WeCom 初始化阶段的 `realpath` 会因目录不存在失败。
- `deepseek-harness-session-bi` 和 HCI bundle 要求 Node 24.9+，镜像基础运行时因此升到
  `node:24.9.0-bookworm-slim`；DSH CLI 版本仍锁定 `0.2.1-rc.2`，不随 npm latest 漂移。

## 验收

1. `helm template` 同时渲染旧 release 与 `namePrefix=dsh-offline` release，资源名不冲突，
   Service 分别为 `dsh`、`dsh-offline`。
2. 后端匿名/普通用户访问两个 launch API 均被 `require_admin` 拒绝；管理员响应只返回
   同源相对路径，且两个路径不同。
3. 管理台菜单顺序为「可观测性 → 日志收集 → DSH诊断 → DSH离线诊断 → 分类基线」。
4. 新实例 profile 的三个 tgz 文件名与表格完全一致，旧实例仍指向 `.22` 文件。
5. 前端构建、API Gateway DSH 单测、配置契约检查和 Helm lint 通过。

## 本地 Compose 反代注意事项

2026-11-13 验收时两个 iframe 入口均返回 502，但两个 DSH 容器均已正常启动并生成
launch token。根因是 Compose 的 `host.docker.internal` 由 `extra_hosts` 写入 admin-ui
容器的 `/etc/hosts`，而 `frontend/admin/nginx.conf` 使用变量式 `proxy_pass` 后会强制
通过 `resolver 127.0.0.11` 做 DNS 查询；Docker embedded DNS 不返回该 `extra_hosts`
记录，于是 `/dsh/` 与 `/dsh-offline/` 都报 `host.docker.internal could not be resolved`。

Compose 配置现改为字面量 `proxy_pass`，让 Nginx 在启动期按 `/etc/hosts` 解析；Kubernetes
仍使用 Helm 注入的独立 Service 与动态 resolver 配置。验收应同时检查静态资源为 200、两个
DSH token 接口为 200，以及 iframe 首个请求不再为 502。

随后发现经宿主机发布端口代理还会受 Docker Desktop 的 `host.docker.internal` IPv4/IPv6
选择和端口回环影响，表现为上游连接失败后被 admin-ui 记录成 404。Compose 现改为让
admin-ui 直接访问同一网络中的 `dsh:8080` 与 `dsh-offline:8080` sidecar；Kubernetes
配置仍由 Helm 注入独立 Service。
