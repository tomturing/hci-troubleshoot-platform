## 一、要解决的问题

PR #1311《日志包交付作业化》合入后，main 的完整回归 CI 飘红，唯一失败项是前端构建：

```
customer build: src/components/LogCollectPanel.vue(717,46): error TS2345:
Argument of type '"create" | ... | "delivery_submit" | "delivery_status" |
"delivery_resume" | "delivery_cancel"' is not assignable to parameter of type
'"create" | "progress" | "cancel" | "probe" | "stat" | "transfer"'.
```

两层问题，必须分开看：

1. **代码层**：`sendAndWait` 的 `action` 联合类型被加了四个 `delivery_*` 值，但 else 分支仍把它
   整体传给 `buildLogCollectMessage`（形参只接受 6 个 log_collect 动作）。运行时分流其实是对的
   （前两个分支已把 `acli_sync` 与 `delivery_*` 接走），错的是类型没有随之收窄。
2. **流程层（真正的根因）**：PR 阶段的前端快门禁**只跑 `vite build`**，`vue-tsc` 被注释明确
   留给「完整回归」。于是 #1311 的 PR 检查全绿、顺利合入，类型错误直落到 main 才被发现。
   `vite build` 走 esbuild 转译，**只剥类型不做类型检查**，对这类错误天然免疫——把「构建成功」
   当成「类型正确」是这次漏网的唯一原因。

同一天还撞出第二件同类事：PR #1314（会话租约改造）的 `set()` 在已持 `b.mu` 时调用了
自己再加锁的 `holdSession()`——Go 的 `sync.Mutex` 不可重入，构成自死锁。它让
`terminal bridge simulation-auth gate` 在 `format, test and vet` 步骤上**卡满 10m17s 被 job
超时杀掉**，而不是快速失败——因为 `go test` 不写 `-timeout` 时默认 10 分钟才 panic，
而该 job 的 `timeout-minutes` 也是 10。

两件事的共同点：**失败信号被门禁设计延后了**——一个延后到合入以后，一个延后到 job 被杀。
本 PR 就是把这两个信号前移。

## 二、修复

### 2.1 代码层：已由 #1313 修，本 PR 不重复改

`sendAndWait` 的 else 分支已写成显式收窄：

```ts
buildLogCollectMessage(
  props.caseId,
  // 上面的分支已排除 acli_sync / delivery_*，走到这里只剩真正的 log_collect 动作，
  // 显式收窄，避免带前缀的联合类型被 TS 拒绝（TS2345）。
  action as 'probe' | 'create' | 'progress' | 'cancel' | 'stat' | 'transfer',
  { ...(options as any), nodeIp: nodeIp.value },
)
```

本 PR 曾把这段改成 `LogCollectAction` / `DeliveryAction` 两个命名别名，但别名只是把同一件事
写得更便于以后对齐，收益不抵与 #1313 撞车带来的重复审阅成本，因此已回退，只保留上述写法。

不改成运行时 type predicate + 兜底 `throw`：那会把「新增动作忘记加分支」的信号从
**编译期**降级成**运行期**，恰恰废掉本次唯一能拦住问题的机制。

### 2.2 流程层之一：PR 快门禁补上 `vue-tsc`

`.github/workflows/ci.yml` 的「构建前端工作区」步骤，PR 快路径改为先类型检查再构建：

```bash
pnpm --filter "@hci/$FRONTEND_SCOPE" exec vue-tsc -b
pnpm --filter "@hci/$FRONTEND_SCOPE" exec vite build
```

代价实测：customer 与 admin 各自的 `vue-tsc -b` 在干净检出上约 30~60s，远小于一轮 main 红身
（重跑完整回归 + 事后热修）的成本。

边界：本改动只在 `IS_PR=true && FRONTEND_SCOPE!=full` 的快路径新增步骤，push/main 与
workflow_dispatch 的完整回归路径不变（那里本就跑包含 `vue-tsc -b` 的 `build` 脚本）。

### 2.3 流程层之二：`go test` 加显式 `-timeout`

`hci-sim-go.yml` 的 terminal_bridge 步骤与 `build-terminal-bridge.yml` 的同类步骤，统一改为：

```bash
go test -timeout 180s ./...
go test -race -timeout 180s ./...
```

为什么是 180s：terminal_bridge 套件实测单测 9.9s、race 11.2s，180s 是 15 倍余量；两次
`go test` 最坏 6 分钟，仍容得下同一步骤里的 race 构建与 `go vet`，不会反而把 job 撞破 10 分钟。

为什么只改 terminal_bridge：`hci_sim` 与 `offline-collector` 的 `go test -p 4 ./...` 本次没有
实测数据，给它们拍一个超时值属于盲猜，宁可先不动（见第五节遗留）。

锁重入本身属于 #1314 的代码缺陷，已提到它的分支上修（`holdSession` → `holdSessionLocked`）
并随 #1314 一同合入，不放进本 PR：门禁 PR 不该兼任业务修复的载体。

## 三、为什么同类问题以后不会再溜过

| 防线 | 拦截的失效形态 | 本次之前 | 本次之后 |
|------|--------------|---------|---------|
| PR 快门禁 `vue-tsc` | 类型不匹配、联合类型收窄失效 | 只跑完整回归，PR 全绿即合入 | PR 阶段即失败 |
| `vite build` | 打包配置、导入解析、资源缺失 | 有 | 有（不变） |
| 完整回归 `build` | 全量类型 + 构建 | 有，但已是「事后」 | 仍是兜底 |
| `go test -timeout` | 死锁、挂死、泄漏的 goroutine | 靠 10 分钟 job 超时兜底，现象是“慢” | 180s 即 panic，带完整 goroutine 栈 |

`vite build` 与 `vue-tsc` 不是重复劳动：前者判「能不能产出包」，后者判「类型是否自洽」，
只跑前者等于把类型系统当注释用。

## 四、验收

新门禁不会把现存 PR 卡住。**前提说明**：本 PR 自身只改 `.github/workflows/` 与 `docs/`，
没有前端改动，所以 CI 的「前端检查（单元测试 + 构建）」job 直接 skip——新增的 `vue-tsc -b`
并不在本 PR 上执行。因此下面这些是在本地把新命令逐条跑出来的结论，真正在 CI 上生效
需等下一只带前端改动的 PR（届时它会自动拦或自动放）：

- `pnpm --filter "@hci/customer" exec vue-tsc -b` → 退出码 0，无输出
- `pnpm --filter "@hci/admin"    exec vue-tsc -b` → 退出码 0（两个 scope 都会被新门禁覆盖）
- `pnpm --filter "@hci/customer" exec vite build` → 构建成功
- `pnpm --filter @hci/customer test` → 37 files / 362 tests 全通过
- `scripts/ci/resolve_pr_frontend_targets.py` 只会输出 `admin | customer | full`：
  `full` 走原有完整回归分支（本就含 `vue-tsc -b`），新命令只作用于前两者；
  两个包各自的 `package.json` 都以 `vue-tsc -b && vite build` 为 build 脚本且持有 `vue-tsc` devDependency
- `-timeout 180s` 已在 CI 上实测生效：#1314 的 `terminal bridge simulation-auth gate`
  从 **10m17s fail**（卡到 job 被杀）变为 **39s pass**；#1315 自身带新参数跑出 47s pass，
  证明该值不会误伤正常套件

回归对照（同一命令在三个节点上的结果）：

| 分叉点 | `vue-tsc -b` | PR 快门禁 |
|--------|-------------|-----------|
| #1311 合入后的 main | 报 TS2345 | 全绿（只跑 `vite build`）→ 这就是缺口 |
| #1313 合入后的 main | 退出码 0 | 全绿 |
| 本 PR | 退出码 0 | 多了类型检查这一道 |

Go 超时那一半的样本（在 #1314 分支上实测）：修复前 `go test -timeout 150s` 直接
`panic: test timed out`，栈顶落在 `lifecycle.go` 的 `b.mu.Lock()`；修复后同一测试 0.00s 通过，
`go test -timeout 240s ./...` 9.9s、`go test -race -timeout 300s ./...` 11.2s 全绿。
即“先报错、后变快”两个目标均成立。

## 五、遗留（本 PR 不做）

- `hci_sim` 与 `offline-collector` 的 `go test -p 4 ./...`（ci.yml）仍未加 `-timeout`：本次没有
  它们的实测时长，盲拍一个值可能把正常慢的套件推成假失败；需先采集一轮基线再定。
- `admin` 与 `customer` 的 `test` 脚本没有并入门禁的 fast-fail 顺序优化，属性能议题。
- `docs/solution/events/` 下若干文档 frontmatter 的 `status` 取值仍与词表不一致，
  由文档治理专项处理，不与本热修混在一处。
