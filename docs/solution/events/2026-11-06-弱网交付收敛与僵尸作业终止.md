## 一、现场事实

| 观测 | 数值 | 来源 |
| --- | --- | --- |
| 源包 | 1.94 GB / 233 片 | `log_collect_task.detail` |
| 平台已收 | 19 片 | 同上 |
| 总上行 | ≈ 34 KB/s | 交付时段 `bridge_execution_logs` 的字节增量 |
| 并发 | 2 路，单路 ≈ 19 KB/s | `delivery.job_started` |
| 单片预算 | 300 s | `logCollectPartTimeout` |
| 两轮结束时刻 | 13:17:59 / 13:33:02 | 与开始时刻精确相差 3×300 s |

8 MiB 一片在 19 KB/s 下需要 **440 s**，而预算是 300 s。每一轮的 3 次重试全部在同一片上空转，
15 分钟后作业整体重试，再从同一片开始——平台侧 19/233 从此再没动过。

## 二、根因（按"为什么会发生"排序）

### 1. 错误链断裂让自适应失效（最致命）

`wrapTransientTransport` 构造 `deliveryTransientError` 时只把底层错误 `err.Error()` 拼进字符串，
没有实现 `Unwrap()`。于是上层 `isPartTimeoutError` 用 `errors.Is/As` 判断一律为 false：

- 超时不被识别成"超时" → `roundTimedOut` 恒为 0；
- `nextUploadPace` 认为"没有超时证据" → 永远返回原节奏。

**自适应代码即使写对了也不会生效。** 这是"改了却没效果"类问题的典型形态：
错误的类型信息是控制流的一部分，任何包装都必须保留 `%w` / `Unwrap`。

### 2. 判据选错：用固定墙钟衡量一条速率未知的链路

正确的不等式是 `chunkSize / 单路速率 < 单片预算`，而单路速率 = 总带宽 / 并发数。
三个量里只有 chunkSize 是平台固定的（续传中途不可改），所以提高并发会让每一路都更慢。
**并发不是更多车道，是把同一根管子切得更细。**

修复前的判据是"单片 300 s 到点即失败"，它无法区分"链路慢"与"链路死"，
只能靠 3 次重试 + 15 分钟一轮的方式反复交学费。

### 3. 进度黑洞

平台已收多少片只存在于 bridge 内存与平台侧，`log_collect_task` 没有任何字段反映
"这一轮到底推进了没有"。现场与值守只能看到"上传中"，无法判断是慢还是死。

### 4. 被顶替的作业没有被真正终止

三个独立缺陷叠加：

1. **取消注册竞态**：`runJob` 先读 `job.Superseded`，再注册 `r.cancels`（两次取锁）。
   读到 false 之后、注册之前被 `submit` 顶替时，`staleCancel` 取不到取消函数（还没注册），
   旧作业从此收不到任何取消信号，会一路拉包、发 PUT、甚至收尾。
2. **锁外改写共享结构**：`submit` 在锁外把 `stale.JobID` 改成 `-superseded`，
   与旧 goroutine 的读并发；`defer delete(r.cancels, job.JobID)` 落到另一个键上，
   取消函数成孤儿。
3. **无副作用护栏**：`upload` 的 PUT、`complete`、`discardDeliveredCopy`、`discardLocalCopy`
   都不检查"我还是不是执行者"。而本地副本与 journal **都按 task_id 命名**，
   新旧两代指向同一个文件——僵尸收尾删掉的正是新作业正在上传的包，或把 journal 的
   分片数覆盖回旧值。

平台侧已有 epoch fencing（`delivery_epoch = delivery_attempts + 1`，令牌绑定代际），
能挡住"僵尸写平台分片"；但它挡不住僵尸删本地副本、覆盖 journal、白占内存。
**本地副作用必须由本地护栏兜住，不能依赖对端版本。**

## 三、修复

### 判据替换：墙钟 → 单调量增量 + 停摆

| 旧 | 新 |
| --- | --- |
| 作业 6 h 硬超时 | 48 h 绝对上限 + **30 min 无进展**判停摆 |
| 单片 300 s 固定预算 | 并发 × 预算随实测速率收敛（1 路 ~ 资源上限，1 s ~ 20 min） |
| 失败即计一次 attempt | **有进展的失败不计 attempt**（`Attempt = 0`） |

- `delivery_runner.go`：`deliveryJobMaxTimeout = 48h`、`deliveryStallTimeout = 30m`、
  `watchStall` 每 30 s 采样 `progressSignature`（已传分片数 + 已拉字节 + 阶段）；
  停摆触发后 `LastErrorCode = delivery_stalled` 并重排。
- `delivery_stall.go`（新增）：`stallTracker` 纯逻辑，可注入时钟单测。
- `delivery_pace.go`：`nextUploadPace` 由本轮样本推导下一轮节奏；
  `paceMinPartTimeout` 变量化仅供测试，生产仍读 `logCollectPartTimeout`。
- 错误链修复：`deliveryTransientError` 增加 `err` 字段与 `Unwrap()`；
  `isPartTimeoutError` 增加 `context deadline exceeded` 文本兜底。

### 执行者资格护栏（fencing）

- `deliveryRunner.ownerIntact` / `fence`：判据是"仍占着该任务的执行位"，
  而不是"收没收到取消信号"。
- `saveJob` / `saveJobLocked`：所有 19 处落盘统一入口，被顶替的作业不写 journal。
- `submit`：不再改 `stale.JobID`，改为浅拷贝副本落盘 `-superseded.json`。
- `runJob`：**检查与注册取消函数在同一把锁内**，关掉"永远收不到 cancel"的窗口。
- 副作用护栏：分片 PUT（每次尝试前）、`complete`、`discardDeliveredCopy`、
  `discardLocalCopy` 全部过闸；`upload` 不再对被取消的作业无条件写 `completing`。

### 进度回写

- `log_collect_upload_service.record_part` → `update_upload_progress`：
  每 5 片或 ≥ 2 s 回写一次 `detail.upload_progress`（末片必报），
  用 `detail || jsonb_build_object(...)` 库内原子合并，避免两副本读-改-写互相覆盖。
- 进度失败**绝不影响分片上传**（异常全吞并清理节流记录）。
- 前端 `describeUploadProgress` 三段式：刚刚 / N 分钟前 / 已 N 分钟未动（链路可能已停滞）。

## 四、验收

弱网用例 `delivery_weak_link_test.go`：共享带宽池模拟"同一根管子被切细"，
比例与现场一致（64 KiB / 1 s / 2 路 / 60 KB/s ≈ 8 MiB / 300 s / 2 路 / 34 KB/s）。

两条硬性验收标准：

1. **第一轮必须一片都传不上去**——否则用例没复现死结，后面的成功是假通过；
2. **第二轮必须两片全送达**，且节奏已被收敛成 1 路 / 2 s。

只断言"发生了重试"没有意义：原地重试正是当时的故障。

其余覆盖：`delivery_fencing_test.go`（资格护栏 8 例）、`delivery_pace_test.go`（节奏推导边界）、
`delivery_stall_test.go`（停摆判定）、`test_log_collect_upload_progress.py`（节流与失败隔离）、
前端 `logCollectDelivery.spec.ts` / `LogCollectPanel.spec.ts`（现场文案回归）。

## 五、可观测性

| 事件 | 触发时机 | 关键字段 |
| --- | --- | --- |
| `delivery.progress_renewed` | 有进展的失败，attempt 归零 | `uploaded_parts`、`pulled_bytes`、`attempt_before` |
| `delivery.stalled` | 30 min 无进展 | `signature`、`stall_timeout`、`phase` |
| `delivery.pace_adjusted` | 节奏变化 | `parts_before/after`、`part_timeout_before/after_sec`、`round_*` |
| `delivery.superseded` | 新会话顶替旧作业 | `old_job_id`、`task_id` |
| `delivery.superseded_skipped` | 注册取消函数时才发现被顶替 | `stage=register` |
| `delivery.local_discard_skipped` | 僵尸作业被拦住，不删共享副本 | `local_path`、`reason` |

排查入口：`log_collect_task.detail.upload_progress`（平台视角进度）与
`bridge_execution_logs`（桥视角节奏）对齐看，能直接区分"慢"与"死"。

## 六、回滚

- 全部为新增字段/新增事件，`detail` 无 schema 变更，旧前端可忽略 `upload_progress`。
- 若需回退自适应：清空作业文件的 `pace` 字段即回到 `defaultUploadPace`（并发与 300 s 常量）。
- 停摆看门狗可通过 `deliveryStallTimeout` 常量调整；它只影响"判定无进展"的时长，不改变重试语义。

## 七、遗留

- `detail.upload_progress` 目前只回写分片数，未回写"本轮实测速率"；
  现场若要判断"再传多久"，需要结合 `delivery.pace_adjusted` 的 `measured:*KB/s`。
- 弱网用例依赖 `paceMinPartTimeout` 变量，属测试专用开关，生产代码不得改写它。
