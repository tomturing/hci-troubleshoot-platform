# 2026-11-03 客户机磁盘满导致日志包交付失败（Q2026110300988）

## 一、现象

工单 `Q2026110300988`（节点 `192.19.4.248`，x86_64，acli 1.0.0）：

| 事实 | 数据 |
|---|---|
| 交付路径 | `bridge_relay`（P2 经平台中转） |
| 采集结果 | `completed`，节点包 `92325257` 字节（88.0 MiB） |
| 平台交付状态 | `delivery_status=failed`，`error_code` 为空、`error_message` 有值 |
| 界面显示 | 「交付已登记但未完成（可点「上传到平台」重试）」+「拉取中断（已拉 9355264 字节）：写入本地文件失败…」 |
| 桥版本 | `v2.33.0-18-gf9282a80`（2026-10-30 构建） |

用户看到的是一句「拉取中断」，与真实原因（客户机 C 盘写满）毫无关系。

## 二、证据链（UTC+8）

| 时间 | 事件 | 关键字段 |
|---|---|---|
| 14:49:01 | `delivery.submitted` | `part_count=12`、`chunk_size=8388608`、`source_size=92325257` |
| 14:49:02 | `delivery.job_finished`（attempt=1） | 已拉 `1753088` 字节 → `There is not enough space on the disk` |
| 14:49:05 / 10 / 18 | attempt 2/3/4 | 1.75 MB → 1.84 MB（续传有效，但每轮只前进几十 KB） |
| 14:49:35 | attempt=5 → `phase=failed` | **5 次重试 33 秒跑完** |
| 14:50:00 | 用户点「上传到平台」（`direct=true`） | 同时 `delivery.save_failed`：`C:\Users\luo\Desktop\HCI-TerminalBridge-Logs\delivery-jobs\dj-….json.tmp` 也写不进 |
| 15:02:05 | 再次重试 | 已拉 `9355264` 字节后 ENOSPC，31 秒烧完 5 次 |

判定依据：

- 报错是 Windows `ERROR_DISK_FULL(112)`，不是网络错误；
- 连几 KB 的 job json 都写不进 → **整盘满**，不是 Temp 目录权限/路径问题；
- 同机当天先后落过 8.6 GB、2.3 GB、1.6 GB 三个副本，均未删除；
- 节点包仍在（`archive_deleted=f`），无需重新采集。

## 三、根因

| # | 位置 | 缺陷 |
|---|---|---|
| 1 | `terminal_bridge/delivery_disk_windows.go` | `freeDiskBytes` 恒返回 0，「宁可漏检不可误拦」→ 所有 Windows 客户机都跳过预检 |
| 2 | `terminal_bridge/delivery_runner.go`（旧 pull 预检） | 只有 `free > 0` 才判、需求不含余量、无并发视角 |
| 3 | `terminal_bridge/delivery_runner.go`（错误包装） | 任何 pull 错误都被包成「拉取中断（已拉 N 字节）」，ENOSPC 被伪装成网络中断 |
| 4 | `terminal_bridge/delivery_runner.go`（重试预算） | ENOSPC 未分类，按普通失败 1/2/4/8 秒退避 5 次，33 秒内空转完 |
| 5 | 全仓无删除逻辑 | 交付成功后本地副本永久留在 `%TEMP%\hci-log-collect\`，GB 级副本直接吃满 C 盘 |
| 6 | `terminal_bridge/log_collect_transfer.go`（进度步进） | 固定 64 MiB 步进，88 MB 的包全程不上报，`pulled_bytes` 落库恒为 0 |

## 四、修复

| # | 位置 | 改动 |
|---|---|---|
| 1 | `terminal_bridge/delivery_disk_windows.go` | 用 `GetDiskFreeSpaceExW`（`golang.org/x/sys/windows`）取 `FreeBytesAvailableToCaller`，含配额语义；UNC 补尾部 `\`；探测失败仍返回 0 放行 |
| 2 | `terminal_bridge/delivery_disk.go`（新增） | `diskNeed`（`remaining + max(64 MiB, 5%)`）、`precheckDisk`、`isLocalDiskFull`（errno 112/39/28 + 文案兜底）、`deliveryDiskFullError`、`deliveryErrorCode` |
| 3 | `terminal_bridge/delivery_runner.go` | 预检改用 `precheckDisk` 并落 `delivery.disk_precheck`；pull 失败回填真实 `PulledBytes`；ENOSPC 转成 `deliveryDiskFullError`；磁盘满 `budget=1` 且直接 `phase=failed` |
| 4 | `terminal_bridge/delivery_runner.go` | `advance()` 在 complete 成功后调用 `discardDeliveredCopy`，交付即删本地副本 |
| 5 | `terminal_bridge/delivery_local_store.go`（新增） | 副本对账：`delivered` 立即删、失败终态按 TTL（默认 72h）、孤儿按保护窗口（1h）、超容量（默认 8 GiB）按最旧优先；非终态引用绝不删；支持 `HCI_BRIDGE_KEEP_LOCAL_DAYS` / `HCI_BRIDGE_LOCAL_MAX_MB` / `HCI_BRIDGE_CLEANUP_DRY_RUN` |
| 6 | `terminal_bridge/delivery_job.go`、`terminal_bridge/delivery_handlers.go` | job 增 `last_error_code` / `local_deleted_at`；视图增 `error_code` / `local_deleted` |
| 7 | `terminal_bridge/log_collect_transfer.go` | `progressStep`：按总量 1% 并夹在 [4 MiB, 64 MiB]，88 MB 包约 22 次上报 |
| 8 | `log_collect_errors.go` + `backend/shared/resolution/catalogs/log_collect_error_catalog.json` | 新增 `LC-TRANSFER-008`（客户机磁盘空间不足，owner=customer，retryable=manual，http 507） |
| 9 | `frontend/customer/src/components/LogCollectPanel.vue` | 轮询失败时保留 `view.error_code`；`error_code` 每次终态失败都以最新一次落库；结果卡片按 `LC-TRANSFER-008` 展示清理指引（含 need/free/path） |

## 五、验证

- `terminal_bridge`：`go build`（linux + windows 交叉）、`go vet`、`go test ./...` 全部通过；
  新增 `delivery_disk_test.go`（预检边界、errno 识别、错误码映射、进度步进）、
  `delivery_local_store_test.go`（交付即删、失败保留、TTL、孤儿窗口、超量淘汰、dry-run、禁用开关、**非终态引用绝不删**）。
- 错误码单一真源校验：`TestErrorCatalogMatchesGoMeta` 通过（Go 常量表与 JSON 双向一致）。
- 前端：`vue-tsc -b` 通过；`vitest run LogCollectPanel.spec.ts` 61 项通过，
  新增「磁盘满展示清理指引」与「交付失败把 LC-TRANSFER-008 落库」两条用例。

## 六、运维开关与现场处置

| 变量 | 作用 |
|---|---|
| `HCI_BRIDGE_KEEP_LOCAL_DAYS` | 默认 3；`-1` 关闭所有清理（保留现场）；`0` 表示失败终态也立即删 |
| `HCI_BRIDGE_LOCAL_MAX_MB` | 中转目录总量上限，默认 8192 |
| `HCI_BRIDGE_CLEANUP_DRY_RUN=1` | 只统计不删除，首发观察用 |
| `HCI_BRIDGE_DISK_PRECHECK` | 预留：`off` 跳过预检 |

现场恢复步骤：

1. `dir /s %TEMP%\hci-log-collect` 查看历史副本，删除不再需要的大包；
2. 清理 `C:\Users\<user>\Desktop\HCI-TerminalBridge-Logs`（盘满时它也在失败）；
3. 确认可用空间 > 500 MB 后点「上传到平台」，从残包或 0 续传。

## 七、并发准入（2026-11-03 补齐）

单任务预检只看"自己还差多少 vs 当前可用"，两个 GB 级作业各自都"够"，
一起写就会把盘写满——失败点又回到 `write()` 的 ENOSPC。补齐后的判定：

```
准入需求 = 本次剩余字节 + 安全余量 + 同目录其它进行中作业的未落地字节
```

- 新增 `LC-TRANSFER-009`（客户机交付并发容量不足，owner=customer，manual，507），
  与 `008` 的处置动作区分：`008` 清目录，`009` 等其他作业完成；
- 失败时 `delivery.disk_precheck` 事件带 `reserved_bytes`，运维可据此判断空间被谁占着；
- 只统计同目录、非终态、`source_size > 0` 的作业：不同卷互不挤占，大小未知按 0 处理
  （宁可放行，也不要把"未知"当成"已占满"而误拦一次本来能完成的交付）；
- 顺带修复：`runJob` 的重试预算此前没有对磁盘满收敛，`deliveryDiskFullError`
  仍会走 5 次退避（约 33 秒空转）；现在磁盘满与并发不足都只跑 1 次。

## 八、遗留

1. `resource.sample` 磁盘指标未纳入（并发准入目前用即时探测 + 作业占用累加）；
2. bridge exe 不自动更新：合并后需重建 exe 并现场重装，否则客户机仍跑旧逻辑；
3. 磁盘满时 `delivery-jobs/*.json` 也写不进，作业状态只存内存——进程重启后该 job 消失，需前端重新提交。
