# spc 扇出写入与生命周期恢复

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-10 |
| 版本 | v1.0（设计，未实现） |
| 范围 | bridge 覆写 spc/<slot>.json、逐台备份恢复、体积预检 |
| 前提 | 用户已确认：占用 core 槽；bridge 登录用户为 root |

## 一、为什么必须扇出

`sfd_main.py` 只把 `single_collect.py` SSH 下发到每台目标节点，**不推送 spc 文件**；
节点上的 `init_pars.get_spc_action` 每次现场 `open(spc_path)` 读取本机那份。
因此：

- 只写发起节点：其余节点仍按旧清单收集，**没有任何报错**（文件缺失只 warning）；
- 必须写到每一台目标节点，且逐台证明写下去的内容与平台签发一致。

## 二、路径不能硬编码

spc 目录由 `ABSOLUTE_DEPLOY_PATH` + `SPC_DIR_KEY` 拼出，不同集群/版本可能不同。
现场导出的路径是 `/sf/data/local/acli/plugins/log_collect/tools/lmt_collect_info/support_bundle_cluster/spc`，
但**不能假定所有集群一致**。方案：

    find /sf/data/local -maxdepth 6 -type d -name spc -path '*support_bundle_cluster*'

- 命中 0 个：拒绝 create，提示该节点未安装/路径不符；
- 命中 1 个：使用；
- 命中多个：拒绝，避免写错版本；

## 三、时序（任一步失败即全量回滚）

1. 枚举目标主机（`-i all` 取在线全集，指定 IP 取列表）；
2. 每台：`test -e` 确认 `<spc>/core.json` 存在，读取并记录原 sha256；
3. 每台：复制为 `core.json.platform.<task_id>.bak`，校验备份 sha256；
4. 每台：base64 写入新 `core.json`，回读校验 sha256（复用 config 的 base64 写法，禁 heredoc）；
5. 全部通过才执行 `acli log_collect create -m core ...`；任一台失败 → 逐台从备份恢复并拒绝 create；
6. 任务终态（`progress` 完成或产物交付）：逐台恢复备份 + 校验 sha256；
7. 落库 `spc_slot / spc_sha256 / spc_hosts / restore_status / restore_error`。

## 四、失败兜底（三层）

| 层 | 触发 | 动作 |
|---|---|---|
| 启动扫描 | case-service 启动 | 查 `restore_status=pending` 的任务，逐台尝试恢复 |
| TTL | 超过 2 小时仍未终态 | 强制恢复并把任务标 failed，避免清单永久被占 |
| 结果页 | 每次任务 | 展示 restore_status；失败标 config_warning 并给出残留路径 |

恢复失败时，节点上残留的是「平台自定义清单」，而不是 `core` 原清单。
这就是选择 core 槽的代价，因此 UI 必须显式告警，不能静默。

## 五、体积预检（补插件缺失的兜底）

`tar_max_size` 在当前 `single_collect` 流程不生效，`/cfs/*`、dump 会原样打包。
create 前需在发起节点执行 `df` 取 `/sf/data/local` 可用空间，按场景条目预估：

- 预估 > 可用 × 0.8 → 拒绝，并给出两个具体数字；
- 预估未知（条目未标体积）→ 允许但提示。

## 六、安全约束

- 扇出命令必须带 `-o BatchMode=yes -o ConnectTimeout=5`：裸 `ssh` 在 host key 未确认时
  会挂在 tty 等待，后台任务直接卡死；
- 执行用户必须是 root（`main.go` 已把 admin 映射为 root），才能写 spc 目录并复用其 known_hosts；
- 写入内容只来自平台签发的 spc 文本，bridge 侧再按条目白名单校验一次（action/path/filters 结构）。

## 七、实现前仍需确认

1. `find` 在受限 shell 下是否可用（若不可用，降级为按现场给的绝对路径 + 存在性校验）；
2. 节点间免密 SSH 在目标客户环境是否普遍成立（acli 依赖它，但平台应显式预检）；
3. `-m core` 时插件是否只读 `core.json`（已由 init_pars 代码确证，不需要再验）。
