# spc 扇出写入与生命周期恢复

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-10 |
| 版本 | v1.1（已实现，2026-11-10 落地；与 v1.0 设计稿的差异见第八节） |
| 范围 | bridge 覆写 spc/<slot>.json、逐台备份恢复、体积预检 |
| 前提 | 用户已确认：占用 core 槽；bridge 登录用户为 root |

## 一、为什么必须扇出

`sfd_main.py` 只把 `single_collect.py` SSH 下发到每台目标节点，**不推送 spc 文件**；
节点上的 `init_pars.get_spc_action` 每次现场 `open(spc_path)` 读取本机那份。
因此：

- 只写发起节点：其余节点仍按旧清单收集，**没有任何报错**（文件缺失只 warning）；
- 必须写到每一台目标节点，且逐台证明写下去的内容与平台签发一致。

## 二、路径不能硬编码

spc 目录由 `ABSOLUTE_DEPLOY_PATH` + `SPC_DIR_KEY` 拼出，不同集群/版本可能不同。
现场导出的路径是 `/sf/data/local/acli/plugins/log_collect/tools/lmt_collect_info/support_bundle_cluster/spc`，
但**不能假定所有集群一致**。方案：

    find /sf/data/local -maxdepth 6 -type d -name spc -path '*support_bundle_cluster*'

- 命中 0 个：拒绝 create，提示该节点未安装/路径不符；
- 命中 1 个：使用；
- 命中多个：拒绝，避免写错版本；

## 三、时序（任一步失败即全量回滚）

1. 枚举目标主机（`-i all` 取在线全集，指定 IP 取列表）；
2. 每台：`test -e` 确认 `<spc>/core.json` 存在，读取并记录原 sha256；
3. 每台：**写前自愈** —— 若该节点存在别的任务留下的 `core.json.platform.*.bak`，
   先把其中最新的一份放回 `core.json`，再备份；顺序颠倒会把上一轮平台清单当成
   "原件"永久存下，原件就再也回不来了；
4. 每台：复制为 `core.json.platform.<task_id>.bak`，用 `cmp -s` 证明备份与原件逐字节一致；
   本任务的备份已存在时不覆盖（重试同一任务不能把原件换成平台内容）；
5. 每台：base64 写入新 `core.json`，**用 base64 回读逐字节比对**（不用 sha256：
   `sha256sum` 在裁剪系统上可能缺失，缺了等于"写完没有证据"），不符即用备份就地回滚；
6. 全部通过才执行 `acli log_collect create -m core ...`；任一台环境坏 → 全量回滚并拒绝 create；
7. 任务终态（`progress` 完成 / 产物交付 / 2 小时到期 / 从未 running 空轮询 8 次 / 进度连续
   3 次失败）：逐台恢复备份并核对。**恢复不删除备份**——它是节点上那份原件的副本，
   留着才能让任意一次重放（bridge 协程 / 平台收尾 / 人工重试）继续幂等成立；
8. 落库 `spc_slot / spc_sha256 / spc_hosts / restore_status`。逐台错误落在
   `spc_hosts[].error`，不单独开列——恢复只关心"这台还原了没有"。

## 四、失败兜底（已实现：三层 + 一个前置条件）

| 层 | 触发 | 动作 | 执行者 |
|---|---|---|---|
| 就地回滚 | 单台写入未回读通过 | 立刻用本任务备份还原该台，输出 `SPC_WRITE_FAIL` | bridge |
| 全量拒绝 | 任一台环境坏 / 点名节点不可达 / 写入成功数为 0 | 全量还原并拒绝 create —— 绝不让节点之间用不同清单收集 | bridge |
| 后台协程 | create ok 后任务进入终态 | 逐台还原并核对，回执让平台改写 `restore_status` | bridge 常驻进程 |
| 平台收尾 | 前端主流程退出（成功/失败/取消） | 发 `restore_spc` 幂等重放；备份不存在返回 skipped，仍按 success 记 | 前端 |
| 人工重试 | 结果页「重试还原」 | 同上，兜住"bridge 重启 + 页面已关"同时发生的情形 | 前端 |

**为什么平台还要发一次**：bridge 的内存态随进程消失，`watchSpcRestore` 协程也就没了；
而备份名自描述（`<file>.platform.<task_id>.bak`），无需内存即可重放。
恢复请求之所以必须幂等，是因为它会被这三条路径重复投递。

**写库口径**：只有拿到逐台结果才写 `restore_status` 终值；通道异常一律保持 `pending`。
把"结果未知"记成 `failed` 与 relay 那次误判（Q2026110601054）属同一类错误。

恢复失败时，节点上残留的是「平台自定义清单」，而不是 `core` 原清单。
这就是选择 core 槽的代价，因此结果页必须显式展示并可重试，不能静默。

## 五、体积预检（**未实现**）

`tar_max_size` 在当前 `single_collect` 流程不生效，`/cfs/*`、dump 会原样打包。
设计上 create 前应在发起节点 `df` 取 `/sf/data/local` 可用空间并预估体积，本轮未落地，
因此体积风险与 `-c` 场景一致：只能事后从 `available_mb` 与失败信息判断。

## 六、安全约束

- 扇出命令必须带 `-o BatchMode=yes -o ConnectTimeout=5`：裸 `ssh` 在 host key 未确认时
  会挂在 tty 等待，后台任务直接卡死；
- 执行用户必须是 root（`main.go` 已把 admin 映射为 root），才能写 spc 目录并复用其 known_hosts；
- 写入内容只来自平台签发的 spc 文本，bridge 侧再按条目白名单校验一次（action/path/filters 结构）。

## 七、实现状态与遗留

已实现（bridge `log_collect_spc_fanout.go` + 平台/前端收尾）：

- 逐台写入、备份保真校验、写前自愈、就地回滚、全量拒绝；
- create 回执携带 `spc_slot / spc_sha256 / spc_hosts / restore_status=pending`；
- `restore_spc` 动作：幂等重放，缺 `spc_slot`/`ips` 时按默认槽位与集群节点清单恢复；
- 前端：create 回执落库逐台证据、主流程退出时兜底还原、结果页展示「待还原/已还原」并支持重试。

与 v1.0 设计稿的差异：

| 设计稿 | 实际实现 | 原因 |
|---|---|---|
| case-service 启动扫描 `restore_status=pending` | 未实现 | 平台不掌握节点清单归属，扫描只能重复下发命令而没有新证据；bridge 备份名 + 平台 `restore_spc` 已覆盖同一场景 |
| TTL 2 小时强制恢复并把任务标 failed | 改为 bridge 侧 `spcRestoreMaxWait` 2 小时到期恢复 | 恢复是节点侧事实，平台无法自行执行；把任务标 failed 更不对——采集可能已经成功 |
| 回读校验用 sha256 | 用 base64 逐字节比对 | `sha256sum` 在裁剪系统上可能缺失，缺了等于"写完没有证据" |
| `restore_error` 单列 | 逐台错误落 `spc_hosts[].error` | 恢复只关心"这台还原了没有"，无需再开一列 |
| 体积预检 | 未实现 | 见第五节 |

仍待现场确认：

1. 目录探测命令（`find`）在受限 shell 下的行为；不可用时需按现场给的绝对路径降级；
2. 节点间免密 SSH 在目标客户环境是否普遍成立——`BatchMode=yes` 下无免密会直接失败，不会挂住，但会表现为"节点不可达"；
3. `-m core` 时插件只读 `core.json`（已由 `init_pars` 代码确证，不需要再验）。
