# 日志收集结果态字段顺序与压缩包大小采集

## 一、现场反馈

1. 结果态描述表最后一行是「归档状态 | 产物位置」，长路径排在右列，行高被撑成两行，
   左侧短文案下方留白，读起来别扭，希望两者左右互换。
2. 「压缩包大小」长期显示「未记录」，怀疑平台拿不到这个值。

## 二、第一性原理：大小到底谁能给

压缩包字节数的权威来源只有三个，逐个排除：

| 来源 | 可行性 | 结论 |
|---|---|---|
| 插件 `acli log_collect progress` 文本输出 | 实机样本只有「压缩包路径 / 总进度 / 主机明细」，**不含字节数** | 不可用 |
| 节点上的压缩包文件本身 `stat -c %s` | 只有文件存在时才量得到；P1 直传成功后插件**立即自删** | 上传窗口内可用 |
| 日志服务器（5888）上的归档对象 | 与平台无查询契约，`remote_url` 是上传端点而非对象地址 | 当前不可用 |

平台侧唯一的写入点是 P2 的 `completeUpload`（分片合并时由服务端量出 `size` 并落库）。
所以结论是：**P1 的 `archive_size` 从来没有采集链路，不是偶发缺失**——
`2026-10-23-日志收集完成态优先展示.md` 里 P1 只回填了 `archive_path`，没有大小。

## 三、方案

### 3.1 字段顺序交换

```
发起节点 | 交付路径
收集场景 | 时间范围
目标主机 | 压缩包大小
产物位置 | 归档状态      ← 原来是「归档状态 | 产物位置」
```

理由：长路径放左列，按阅读顺序先给"东西在哪"，再用右列短文案给"处于什么状态"；
两列时行高本来就由长内容决定，让长内容占左列可以避免右侧出现"短文案 + 大片空白"。

### 3.2 bridge 在进度查询时顺带量大小

`terminal_bridge/log_collect.go` 的 `progress` 分支新增：

- `logCollectProgress` 增 `archive_size`（`omitempty`），只做信息字段；
- `probeLogCollectArchiveSize()`：路径为空 / 规范化失败 / 文件不存在一律返回 0，
  **不产生错误、不参与完成判定**（归属仍靠报告指纹比对，见 2026-10-23 文档）；
- 日志 `log_collect.progress` 增加 `archive_size` 字段，便于线上确认是否量到。

前端：

- `ProgressSnapshot` 增 `archive_size?`；
- P1 完成回调（`finishP1`）与轮询纠正（`patch_completed`）把 `archive_size` 一起 PATCH，
  已有值优先保留，避免 P2 记录被 0 覆盖；
- 结果态空值文案改为「未记录（直传后压缩包已删除）」，说清原因而不是干巴巴的「未记录」。

### 3.3 列数阈值回调到 600

上一轮把描述表两列阈值降到 560px，实测 570px 两列时「P1 直传日志服务器」会折成
「P1 直传日志 / 服务器」，比单列更碎。按「96px 字段名 + ≥140px 值」反推，
两列需要 600px，故回调。570px 单列时 76 字符路径可一行放下，反而更整齐。

## 四、对抗性审查

| 场景 | 结论 |
|---|---|
| 小包在两轮轮询（5s）之间传完并删除 | 量不到，仍显示未记录；文案已说明原因，不误导 |
| 采集阶段压缩包尚未生成 | `stat` 失败返回 0，不影响进度显示 |
| 同一路径被下一次任务覆盖 | 每次 progress 都重新 `stat`，不缓存，避免拿到上一次的字节数 |
| 路径含空格/特殊字符 | 复用 `normalizeArchivePath` + `shellQuote`，与 P2 `stat` 同一套校验 |
| P2 记录被同步纠正 | `snapshot.archive_size || currentTask.archive_size || undefined`，不会被 0 覆盖 |
| `stat` 拖慢进度查询 | 单次 `stat -c %s` 走非 PTY 通道，毫秒级；仅路径非空时执行 |
| 历史记录 | 存量任务库中仍是 NULL，只能新任务生效；不做事后回填（无从获取） |

## 五、验收

- 单测（`LogCollectPanel.spec.ts`）：
  1. 字段顺序断言 `['产物位置', '归档状态']`，且正常大小显示为 `100.0 MB`；
  2. P1 无大小时显示「未记录（直传后压缩包已删除）」。
- 浏览器实测（Playwright，1920×1080 双开 570px 抽屉）：
  - 字段顺序为 发起节点 / 交付路径 / 收集场景 / 时间范围 / 目标主机 / 压缩包大小 / 产物位置 / 归档状态；
  - 有大小显示 `700.0 MB`，无大小显示原因文案；
  - 570px 单列，路径一行放下。
- `terminal_bridge`：`go build ./...`、`go vet ./...`、`go test ./...` 通过。

## 六、局限与后续

- P1 小包（上传耗时 < 轮询间隔）仍可能拿不到大小；若要根治，需要在日志服务器侧
  提供对象元数据查询契约，或在插件完成回调里带 `archive_size`（需 acli 配合）。
- 本文档只解决"能拿就拿、拿不到说清楚"，不编造数值。
