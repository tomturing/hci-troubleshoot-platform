# SSE 空闲保活治理（工单 Q2026092130181 网络错误根因修复）

> 方法论：第一性原理（First Principles）+ 对抗性审查（Adversarial Review）。
> 本文先拆解物理/逻辑最底层事实，再给出原始方案，最后以红队视角压测方案边界。

## 一、第一性原理：根因拆解

把"诊断进行到一半浏览器报 network error"这个问题拆到不可再分的事实层：

1. **浏览器与后端之间有一道反向代理**（customer nginx，`frontend/customer/nginx.conf`
   的 SSE location 配置了 `proxy_read_timeout 300s`）。这是唯一对"空闲连接"计时的环节。
2. **SSE 是长连接**，代理按"距上一次收到字节的秒数"判断空闲。只要 300s 内没有任何字节
   流过，代理就掐断连接 → 浏览器 `EventSource`/fetch 抛网络错误。
3. **后端链路内部其实没有超时**：`conversation-service → agent-service` 的 SSE 客户端用的是
   `httpx.AsyncClient(timeout=None)`（`backend/conversation-service/app/services/agent_client.py`），
   所以"内部"连接不会因为空闲而断；只要源流活着，它就一直等。
4. **真正让 SSE 长时间零字节的是后端长耗时操作**：动态 skill（如 `hci-alert-parsing`）
   调用非流式 LLM（`OpenClawAssistant`，`AI_CLIENT_READ_TIMEOUT_SEC` 默认 120s），
   单次调用最坏 2 个 endpoint × 120s = 240s，期间 SSE 不产生任何业务字节。

**结论（最底层事实）**：问题不在 LLM 超时本身，而在于"长耗时期间 SSE 没有任何字节输出"
触发了代理的空闲掐断。因此**治本修复 = 在空闲窗口周期注入字节（心跳）**，与后端操作耗时长短解耦。

## 二、原始方案（第一性原理推导）

在 `conversation-service` 的两条浏览器侧 SSE 流（诊断主链路 `POST /message`、
页面刷新重接 `GET /resume-stream`）注入**SSE 注释行心跳**（以 `:` 开头，浏览器/前端解析器自动忽略，
不进入业务事件），周期远小于代理空闲超时（默认 20s << 300s）。

- 心跳字节流过 nginx → `proxy_read_timeout` 永不被触发 → 连接保活，与后端阻塞时长无关。
- 代理 SSE location 已配置 `proxy_buffering off`，字节即时向下游 flush，心跳即时生效。
- 前端解析器显式跳过 `:` 注释行，绝不污染 `content`。
- 新增 `SSE_KEEPALIVE_TOTAL` 指标 + `sse_keepalive_start` 日志，满足可观测性（指标/日志/链路）。

## 三、对抗性审查（红队压测边界条件）

1. **心跳任务会不会泄漏/悬挂？** 包装器在 `finally` 中 `cancel()` 并 `gather(..., return_exceptions=True)`
   回收生产者与心跳任务；客户端断开（StreamingResponse 被取消）时同样走 `finally`，无悬空协程、
   无 "Task exception was never retrieved" 告警。已由单测 `test_keepalive_cancellation_is_clean` 覆盖。
2. **源流结束后还发心跳吗？** 源结束 → 生产者放入哨兵 → 包装器 `break` → `finally` 取消心跳。
   不会在 `[DONE]` 之后无限发心跳。单测 `test_keepalive_terminates_after_source_ends` 覆盖。
3. **心跳注释行会不会破坏前端解析？** SSE 规范中 `:` 开头即注释；前端 `streamAIResponse` 与
   `resume-stream` 两个解析循环均显式 `else if (line.startsWith(':')) continue`。单测与手动确认。
4. **只改 conversation-service 够吗？** 是。内部 `httpx(timeout=None)` 无空闲超时，整条代理链
   （nginx → api-gateway → conversation-service → agent-service）看到的都是同一份字节流，
   心跳覆盖全部环节。
5. **会不会误伤正常短响应？** 正常响应 < 20s 内即有业务字节，心跳仅在"真实空闲"间隙补发，
   不影响 TTFT 与内容顺序。
6. **能否关闭/调参？** `SSE_HEARTBEAT_ENABLED=false` 或 `SSE_HEARTBEAT_INTERVAL_SEC<=0` 时
   透传源流（便于排障/压测）；间隔可配，必须远小于代理 `proxy_read_timeout`。

## 四、附带修复（防御纵深 + 前端体验）

- **前端网络错误可重试**：`streamAIResponse` 的 catch 区分网络错误（network / Failed to fetch /
  AbortError），设置 `sseNetworkError` 状态并渲染可重试横幅（`ChatWindow.vue`），提供
  `retryLastMessage()` 用最近一次用户消息重发，避免"请重新发起诊断"的沉默失败。
- 该修复不改变后端根因（心跳才是治本），仅提升失败可见性与可恢复性。

## 五、改动清单

- `backend/conversation-service/app/config.py`：新增 `SSE_HEARTBEAT_ENABLED` / `SSE_HEARTBEAT_INTERVAL_SEC`。
- `backend/conversation-service/app/routes/conversations.py`：新增 `sse_keepalive` 包装器，
  包装 `POST /message` 与 `GET /resume-stream` 两条 SSE 流。
- `backend/shared/observability/metrics.py`：新增 `SSE_KEEPALIVE_TOTAL` 指标。

- `frontend/customer/src/components/ChatWindow.vue`：网络中断可重试横幅。
- `backend/conversation-service/tests/unit/test_sse_keepalive.py`：5 项单测覆盖保活/透传/终止/清理。
