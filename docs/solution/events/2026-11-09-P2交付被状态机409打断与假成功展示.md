## 一、用户在界面看到什么

结果态横幅是**绿色成功**「该工单已完成日志收集」，交付路径写着「P2 经平台中转」，
步骤条 4/4、进度条 100%。用户在节点侧也确认采集确实完成，于是合理判断"P2 已经成功"。

但同一时刻的事实是：平台 `objects/Q2026110900356/` 不存在，日志服务器
`GET /archive_status?filename=Q2026110900356.zip` 返回 `{"found":false,"status":"missing"}`。

3. 5888 侧 `found=false`——归档件根本没生成。

## 三、根因

### 1. 主流程与自动对账并行写同一行状态机（直接原因）

前端有两条**都会写平台状态**的链路：

- 主流程 `handleStart → resumeTaskFlow → pollUntilCollected → runP2`；
- 5 秒/30 秒一次的自动对账 `startAutoSync → triggerAutoSync → syncNodeState`。

`resumeTaskFlow` 入口会 `stopAutoSync()`，但用户中途**关掉再打开抽屉**时，
`restoreTaskState` 为了接管/刷新会重新 `startAutoSync()`，并立刻发一次对账——
它并不检查"主流程是否还在跑"。于是两条链路同时存在：

```
对账：syncNodeState → decideNodeSync(collecting, completed) → PATCH completed  ✅ 03:39:54.48
主流程：runP2 → PATCH uploading                                            ❌ 409（completed 是终态）
```

异常一路抛到 `handleStart` 的 catch，`runDeliveryJob` 从未执行——会话已经开好，
但没有任何执行者。这类竞态只要对账抢先就必然发生，与网络、acli、HCI 都无关。

### 2. `completed` 被当成"已交付"（界面假成功）

`status` 是**采集结论**，与"字节有没有出客户内网"没有因果关系；这一条在
`logCollectSync.ts` 与 `resultArchiveText` 里已经写明。但展示层有三处仍在混同：

- `showResult(task)` 无条件 `stage = 'done'`，而 `stage='done'` 的文案是
  「日志已归档到日志服务器」、进度条 `success`、步骤条 `4/4`；
- `statusText` 只要 `stage==='done'` 就输出"已归档"；
- 结果态横幅 `resultHeadline` 只判断 `status !== failed/cancelled` 就给
  `type='success'`「该工单已完成日志收集」。

真正诚实的只有「归档状态」那一行（`delivery_status=queued` → "交付已登记但未完成"），
但它被绿色横幅与 4/4 步骤条盖过去了。用户据此认为 P2 成功，是设计缺陷而不是误读。

### 3. 留了一条无人接管的空会话（放大因素）

`/deliver` 已登记 `delivery_status=queued`，但推进它的只有 bridge 的交付作业，
而作业从未提交。平台没有任何后台任务会"捡起 queued 会话继续传"，因此这条会话
会永久停在 0/64，直到用户手动点「上传到平台」。

## 四、修复

### 1. 主流程独占状态机写权限

新增 `mainFlowActive` + 代际 `mainFlowSeq`：

- `handleStart` 打开开关，`finally` 中按代际关闭（旧流程迟到的 finally 不得抢新流程的锁）；
- `startAutoSync` / `triggerAutoSync` 在开关打开时直接返回；
- `restoreTaskState`（重开抽屉）在开关打开时直接返回，不再插一条对账；
- 手动 `refreshProgress`、`switchDisplayTask` 同样跳过写库对账（仍展示平台快照）。

### 2. 交付不再被采集状态机绑架

新增 `advanceToUploading(taskId)`：已是终态则跳过；PATCH 命中
`409 + LC-PLATFORM-003` 时拉回真实任务记录并**继续交付**，其余错误照旧抛出。
判据抽成纯函数 `isStatusTransitionRejected`，只认这一个码——同为 409 的
`LC-PLUGIN-007`（已有进行中的任务）必须原样抛出。

对抗性审查补的边界：`cancelled → uploading` 同样返回 `LC-PLATFORM-003`。若无条件
继续交付，用户已取消的包会被照常发到日志服务器（违背意图的对外副作用）。因此
吞掉 409 后必须用**服务端最新状态**裁决：`canResumeDeliveryAfterReject(status)`
只在 `completed` 时放行，`cancelled` / `failed` / 取不到状态一律中止本次交付。

### 3. 展示以交付证据为准

- 新增 `hasDeliveryEvidence(task)`：P2 只认 `relay_status=success` 或
  `delivery_status=delivered`；P1 另认"插件直传成功后自删压缩包"。
- 新增 `buildResultHeadline({status, delivered, when})`：采集完成但无交付证据时
  给 `warning`「该工单已完成日志收集，但日志尚未交付」，并明确"可点上传到平台，
  不需要重新采集"；只有真交付才给绿色 success。
- `showResult` 的 stage 改为 `hasDeliveryEvidence ? 'done' : 'idle'`；
  `statusText` 的 done 分支同样按证据区分；
  `refreshProgress` 的 `completed → done` 映射也加上证据判据。
- `handleStart` 的 catch：采集结论已是 `completed` 时，交付段失败只提示
  「日志尚未交付…可点上传到平台重试」，不写 `status=failed`、不诱导重新采集。

## 五、验收

1. 单测：`pnpm vitest run`（含新增 `hasDeliveryEvidence` / `isStatusTransitionRejected` /
   `buildResultHeadline` 用例，以及三条源码结构约束用例）。
2. `vue-tsc -b` + `vite build` 通过。
3. 现场复现口径：让对账在 `/deliver` 之后抢先写 completed，主流程仍应完成
   `delivery_submit` → 分片上传 → 合并 → 代传；最终 `relay_status=success`。
4. 结果态：`delivery_status=queued` 且 `relay_status=none` 的任务，横幅必须是
   warning 且文案含"尚未交付"，不得出现绿色 success。

## 六、遗留

- Q2026110900356 本身尚未交付：包仍在节点（528,505,772 B），会话 `d7cffae5…`
  的 64 片为空。在面板点「上传到平台」（direct 补交付）即可复用该会话续传，
  不需要重新采集。
- bridge 的 `handleDeliverySubmit` 对参数拒绝只回前端 `delivery_result`、不写桥日志，
  排障时"桥侧零痕迹"既可能是没收到，也可能是收到了但被拒——该盲区不在本次范围。
- 跨浏览器标签页无法靠前端锁互斥；本次修复的兜底是"交付不因状态机拒绝而中断"，
  多标签场景下仍可能出现一次 409 被吞的可观测噪音。
