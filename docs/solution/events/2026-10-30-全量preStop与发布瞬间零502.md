# 全量 preStop：把「发布瞬间的 502」从单个服务的补丁升级为平台约束

- 日期：2026-10-30
- 涉及：`deploy/helm/hci-platform/templates/_helpers.tpl`、`deploy/helm/hci-platform/templates/*/deployment.yaml`（13 个）、`deploy/helm/hci-platform/values.yaml`、`deploy/helm/hci-platform/tests/prestop_coverage_test.yaml`、`scripts/ci/check_prestop_coverage.py`、`.github/workflows/ci.yml`、`deploy/helm/hci-platform-obs/rules/alert_rules.yml`
- 关联：`2026-10-30-case-service发布空窗归零与双进程临时文件隔离.md`（PR #1384）、`2026-10-30-观测命名空间白名单与发布可用性度量.md`（5xx 度量口径）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| PR #1388 之前，chart 里 13 个 Deployment 一个 `lifecycle.preStop` 都没有 | `grep -rn 'preStop' deploy/helm/hci-platform/templates` 为空 |
| 没有 preStop 时，发布瞬间必然有一小段「请求打到已停止监听的旧 Pod」 | 经 Traefik 对 case-service 施压 2338 次，旧 Pod `Killing` 的同一秒起连续 ~2s 出现 **28 个 502** |
| 同期 endpoints 全程非空 | 采样 188 次 `ep=0` 出现 0 次 —— 说明 502 不是「没人服务」，而是「服务者已闭眼」 |
| 13 个运行中的业务容器都能执行 shell | 逐个 `kubectl exec -- /bin/sh -c 'sleep 0'`，13/13 返回 OK（见第四节的反向条件） |
| terminal-bridge 本身有优雅退出 | `terminal_bridge/main.go`：`signal.Notify(SIGTERM)` + `server.Shutdown(ctx)` |

## 二、根因（第一性原理）

「请求会不会打到正在死的 Pod」由**两个彼此独立、互不感知的时钟**决定：

- **时钟 A（控制面）**：Pod 收到 `deletionTimestamp` → 从 EndpointSlice 移除 → 经 kube-proxy / Traefik 各自的速度传播到每一条转发路径。staging 实测约 2s。
- **时钟 B（进程）**：收到 SIGTERM 后停止 accept 的速度。uvicorn 是毫秒级。

只有 **A < B** 才没有 502。而 Kubernetes 的默认行为是「A 开始时立刻发 SIGTERM」，即 A 与 B 同时起跑，A 永远慢一步——所以**这是平台的默认缺陷，不是某个服务写错了代码**。

必须把两件事分开：

| 机制 | 回答的问题 | 回答不了的问题 |
| --- | --- | --- |
| `maxUnavailable=0` / `maxSurge=1` | 还有没有别的 Pod 在服务 | 流量会不会正好打在已经闭眼的那个上 |
| `preStop` | 闭眼前再等多久（把 B 推后到 A 之后） | 新 Pod 是否已经 Ready（那要靠 Deployment 控制器） |

`preStop` 是唯一能在**不改变发布策略**的前提下消除这个差集的机制。

## 三、修复设计

1. **共享 helper** `hci.preStopLifecycle`（`_helpers.tpl`）：一次实现、13 处 include，避免 13 份各写各的。
   - 取值顺序：`global.preStopSleepSeconds`（默认 10）→ `<serviceKey>.preStopSleepSeconds` 覆盖 → `0` 关闭。
   - 渲染期硬校验：`sleep >= terminationGracePeriodSeconds` 直接 `fail`，因为那等于「preStop 先吃掉优雅期，超时后 kubelet 直接 SIGKILL」，在途请求照样丢。
2. **默认 10s**：对实测 2s 留 5 倍余量。代价是每次发布每个 Pod 多 10s，新 Pod 早已接管流量，不影响可用性。
3. **case-service 去掉内联块**：PR #1388 的内联实现改为 include，渲染结果一字未变（见下的 diff 口径）。
4. **测试锁两层**（缺一不可）：
   - `deploy/helm/hci-platform/tests/prestop_coverage_test.yaml`：9 个默认就渲染的服务逐个断言 `preStop.exec.command == ["/bin/sh","-c","sleep 10"]`，并断言 `global.preStopSleepSeconds=0` 时不写 `lifecycle`；
   - `scripts/ci/check_prestop_coverage.py`：`diagnosis-service` / `diagnosis-worker` / `ops-agent-service` / `terminal-bridge` 默认 `enabled=false`，单测渲染不出来，因此额外做**源码层**检查（凡 `kind: Deployment` 的模板必须 include 该 helper）+ **渲染结果层**检查（`helm template` 产物里的每个 Deployment 必须有 `preStop`）。
   - 只做渲染层检查会漏掉 4 个未启用的服务；只做源码层检查会把「include 了但参数写错」放过去。
5. **验收口径换成绝对值**：`rate()` / `increase()` 看不见「序列诞生前已发生的增量」，首次 5xx 永远读作 0。详见 `2026-10-30-观测命名空间白名单与发布可用性度量.md` 的 C3 与 `GatewayServerErrorFirstSeen`。

渲染 diff（staging values 全量，13 个 Deployment）：新增 13 处 `lifecycle.preStop`，case-service 的长注释被替换为一行（渲染出的 `lifecycle` 完全相同），**没有任何其他字节变化**。

## 四、对抗性审查：什么条件下会失效

| 失效条件 / 攻击 | 后果 | 兜底 |
| --- | --- | --- |
| 某个镜像没有 `/bin/sh` 或 `sleep`（distroless / scratch） | preStop 执行失败 → kubelet 只记一条事件、照常 SIGTERM → 「配了但没生效」，且无声 | 已对 13 个运行容器逐个实测（13/13 OK）。新增服务需照做：`kubectl -n <ns> exec <pod> -- /bin/sh -c 'sleep 0'`；换成 distroless 时必须改用二选一（镜像内自带 `sleep`，或应用侧实现「收到 SIGTERM 先等 A 再退出」） |
| preStop 失败但不阻断终止 | 以为有保护，实际没有 | 验收时看 Pod 事件里有没有 `FailedPreStopHook`；只看 YAML 是否有 `preStop` 字段不够 |
| `preStopSleepSeconds >= terminationGracePeriodSeconds` | 优雅期被 preStop 吃光，kubelet SIGKILL，在途请求全丢 | 模板直接 `fail`（单测锁住错误消息） |
| 新增服务漏 include | 该服务继续有 502 窗口 | 门禁同时查源码与渲染结果，新模板不加就是 CI 红 |
| 发布耗时增加 10s | 成本，不是故障 | 新 Pod 先 Ready 才停旧 Pod，可用性不受影响 |
| 应用不处理 SIGTERM（直接退出） | preStop 只解决「新请求不打进来」，解决不了在途请求被截断 | uvicorn 自带优雅退出；terminal-bridge 已核实有 `server.Shutdown`；新增 Go/其他语言服务需自查 |
| 节点宕机 / SIGKILL / OOM | preStop 完全不执行 | preStop 防的是「计划内发布」，pod 级故障要靠多副本与探针，不在本机制覆盖范围 |
| 把 `rollout.strategy` 改回 `Recreate`（如换 CSI） | 空窗从 0 变成「Recreate 固有时间 + 10s」，比不改 preStop 更长 | 可接受：Recreate 本身已有空窗，preStop 只是把它拉长 10s；真要缩短就把该服务 `preStopSleepSeconds` 置 0 |
| `hci-platform-dsh` / obs chart 的 Deployment 不在门禁范围 | 那些工作负载仍有同样缺陷 | 已知边界：obs 多为数据库/带锁存储，发布策略需另行判断；DSH 独立 chart，待其需要可用性时再纳入 |
| 有人把 `global.preStopSleepSeconds` 置 0 | 全平台静默退化 | helm-unittest 断言默认值必须是 10，改 0 会红 |
| 首次上线时 13 个 Deployment 同时滚动，单节点上 surge 出一倍 Pod | 资源不足 → 新 Pod 卡 `Pending`，发布停住（旧 Pod 仍在服务，用户无感） | 实测容量充足：节点 16C/31GiB，staging 现 requests 1.13C/5568MiB，叠加 13 个 surge 约 2.2C/10.4GiB；实际内存用量峰值预估 ~20GiB < 31GiB |
| 门禁写了但永远绿（本次反复踩过的坑） | 回归锁形同虚设 | 已做双向反向验证：删掉一个模板的 include → 源码层报 1 条；`--set global.preStopSleepSeconds=0` 渲染 → 渲染层报 9 条 |

## 五、验收口径

发布一次后检查：

```bash
# 1. 每个 Deployment 都真的带 preStop（渲染结果为准，不看模板意图）
helm template hci-platform deploy/helm/hci-platform -f <staging-values> \
  | grep -c 'preStop:'        # 期望 13

# 2. 运行中的 Pod 确实有这个 hook，且没执行失败
kubectl -n hci-staging get pods -o json \
  | jq '[.items[].spec.containers[].lifecycle.preStop] | length'
kubectl -n hci-staging get events --field-selector reason=FailedPreStopHook   # 期望空
```

```promql
# 3. 发布前后的 5xx 绝对值必须完全相等（不要用 increase 下结论，见观测文档 C3）
sum by (service, code) (traefik_service_requests_total{code=~"5.."})
```

判据：**施压脚本 0 异常**（PR #1388 那一轮 2338 次 / 28 个 502，本轮应为 0），且发布窗口内 endpoints 空窗为 0。

## 六、与历史决策的关系

- PR #1388 只给 case-service 加了 preStop（当时是为了收拾 #1384 验收暴露的 502）。本文把它变成**平台级约定**：新增服务默认就有，不需要有人记得加。
- 本文**不改变**任何服务的发布策略：数据库 / 带锁存储（obs chart 的 clickhouse 等）仍然应该是 `Recreate`，`maxUnavailable=0` 这类参数对它们没有意义。
- `2026-10-30-case-service发布空窗归零…` 里的「endpoints 非空即发布无损」被本文修正为**必要条件而非充分条件**：endpoints 非空只证明有别的人在服务，用户侧 5xx 才是判据。
