# 采集告警统一派生：交付成功后仍要说清「包可能不完整」

## 一、问题：摘要一致不等于内容有效

工单 Q2026112300867（节点 10.30.2.35，P2，206 MiB）的客户界面同时出现绿色"已交付 · 完整性已校验"和一条红色"平台未记录到可定位的错误码"，且用户下载的压缩包无法解压。

对抗性核对后确认两件事互不矛盾：

1. **交付链无责**：节点源包摘要、bridge 拉取摘要、平台合并摘要、5888 实际归档文件四处 SHA-256 完全相同（`ab04433f…`），26/26 分片齐全。摘要一致只证明"平台副本 == 节点源包"。
2. **源包本身内部损坏**：节点 `collection_log.log` 记录 `15:12:23 failed add /sf/etc/isv-guide/version1.0/uinfor/certificate.png to tar, error: [Errno 5] Input/output error`。Python 2.7 `tarfile.add()` 先写 512B header（声明 size=185669）再 `copyfileobj` 写内容，EIO 在第 5632 字节中断；`do_copy_jobs` 的 `except` 只记日志、不回退 tar 流，后续条目接在残数据后。实测 tar 流 1.63 GB、共 4425 个成员，Python `tarfile` 在 3067 个成员后停止，GNU tar 报 `Skipping to next header`，ticket-sync 报 `extract-failed`。

平台库里其实**已经有这份证据**（`log_collect_process_log` 存了 `collection_log.log` 正文），但 `put_process_log` 只写窄表、不写 `detail` 快照，而客户面板只读任务行（避免 N+1），所以派生层 `derive()` 永远看不到它，`error_code` 为空，界面只能打"无码"兜底文案。

## 二、整体盘查：三类日志源都没进派生层

| 数据源 | 典型错误信号 | 优化前状态 |
|---|---|---|
| `log_collect_process_log`（节点 acli 日志正文） | `failed add ... to tar` 的 EIO / not exists、`SF_DCODE` 命令失败 | 在库、不可见 |
| `bridge_execution_logs`（桥事件 WARN/ERROR） | `archive_size_probe=missing`、`spc_restore_abandon`、`tls_relaxed` | 在库、不可见 |
| `log_collect_task.detail`（已有快照） | `evidence_error`、`artifact_quality` | 部分已派生 |

其中既有真告警（EIO 导致坏包），也有良性噪音（`tls_relaxed` 是自动放宽成功、`HCI not update` 是常态）。整体优化必须**按"是否影响产物可信度"分级抽取**，而不是把所有 WARN 都推给客户。

## 三、设计：一处抽取、两端消费

### 3.1 抽取层（`domain/log_collect_alerts.py`）

纯函数 + 规则表，从采集插件日志正文抽取结构化告警：

- **error 级** `LC-COLLECT-001`：`failed add ... to tar ... Errno 5 / Input/output error`。`tarfile.add` 已写 header 但写入中断，tar 流被写坏 → 包可能不完整。
- **warning 级** `LC-COLLECT-002`：`failed add ... not exists`。add 前就抛错、header 未落盘，tar 结构不受影响 → 个别文件未纳入。
- **忽略**：`acli.log` 的 `SF_DCODE` 命令退出、`HCI not update`、`get_gpuinfo exit 1`、`tls_relaxed`、`permission denied` 等非规则覆盖原因。来源白名单限定 `plugins/log_collect/collection_log.log`。

告警结构含 `code / source / node_ip / file / line / collected_at / trace_id`，证据行截断到 500 字符，快照有界 20 条。

### 3.2 汇聚点（写侧）

`routes/log_collect_evidence.py::put_process_log` 在正文落库后旁路调用抽取层，把告警 upsert 进 `detail.collect_alerts`：

- 同 `source` 由本次重算替换（重采干净后告警自然消失）；
- 按 `code+source+file` 去重；
- 派生失败只记日志，不影响证据上报回执。

不修改 bridge、不需要重出 exe（现场 exe 不会自动更新，见历史记录）。bridge WARN 的抽取可未来复用同一规则表接入，本次 PR 不含。

### 3.3 消费层（读侧）

`domain/log_collect_display.py::derive()` 新增 `display.collect_alert` 与 condition `collect_alert_observed`：

- **不改 `_conclusion`**：交付成功仍是 `success`，告警与交付结论正交。若把告警塞进 `_build_stages` 的 signals，会让"首个异常点"落到 S4、与 `conclusion=success` 自相矛盾，故明确禁止。
- `collect_alert` 只含规范码与客户文案（来自契约 `action/check/fix`）；证据原文 `file/line/source` 只留在 `detail.collect_alerts`，不进客户视图。

### 3.4 两类用户分层（客户三问 vs 专家原文）

契约 `contracts/log_collect_display.json` 为每个码同时定义：

- 客户字段：`title_zh / problem / action / check / fix`——custom-ui 呈现"是什么问题 + 错误码、如何确认、如何处理"；
- 专家字段：`admin_detail / evidence`——admin-ui 的【日志收集】【任务进展】抽屉以表格展示 `file / line / node_ip / source / collected_at / trace_id`。

前端表现：

- 横幅（`logCollectDelivery.ts`）：已交付 + 告警 → type 降为 `warning`，标题仍"已交付"，描述为 `[错误码] 客户文案`；无告警时保持既有"描述为空"行为。
- 结果态状态卡（`LogCollectStatusCard.vue`）：新增独立"采集告警"卡，用契约的 `check/fix` 呈现三问，明确与失败诊断卡区分。
- admin-ui（`LogUploadPanel.vue`）：结构化原文折叠面板新增"采集告警原文"表格，附调用链。

`no_code` 兜底文案在 `shared/logCollectUi.ts` 与契约 JSON 同源，避免漂移。

## 四、契约与生成物

新增 `LC-COLLECT-001`、`LC-COLLECT-002` 与 condition `collect_alert_observed`。七个生成物由 `scripts/gen_log_collect_display.py` 同步（Python/TS/Go/catalog/hints/UI/rules），禁止手改生成物；`--check` 校验一致性。

## 五、验收

1. `python3 scripts/gen_log_collect_display.py --check` 通过；
2. 后端 `test_log_collect_alerts.py`：来源白名单、EIO/not exists 分级、噪音忽略、幂等合并、有界、primary 优先级；
3. 前端 `logCollectDelivery.spec.ts`：已交付 + 告警 → warning + 错误码 + 不出现 no_code；无告警时不回归；
4. 浏览器：custom-ui 已交付告警单显示"已交付 + [LC-COLLECT-001] + 三问"；admin-ui 任务进展显示原文表格；
5. 真单回放：Q2026112300867 的 `collection_log.log` 应抽出 1 条 IO + 2 条 PARTIAL，`detail.collect_alerts` 写入后 `derive()` 产出对应 `collect_alert`。

## 六、未覆盖
