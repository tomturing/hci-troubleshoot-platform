# KBD 诊断引擎：抽取剥离 / 写操作门禁 / 分类器补漏 / 确定性顺序 — 分析与修复

> 本文档是 2026-07-18 一次工作循环的**方案事件文档**，记录对 KBD 差异诊断引擎
> （`agent-service/app/adapters/agents/htp/kbd_differential.py`）与信号抽取链路
> （`kb-service/app/routes/extract_signals.py`、QFK 风险分类器
> `agent-service/app/tools/acli/classifier.py`）的六项分析与对应修复决策。
>
> 核心目标：**诊断只读**——agent 只确认"是哪篇 KBD"并返回 `root_cause`/`solution` 原文，
> 不执行任何写操作；同时消除结论的随机性、修复"写操作免确认自动跑"的安全倒挂。

---

## 一、背景与需求

原系统存在四类问题，归纳为六项分析点：

1. **抽取层（治本）**：能否在抽取时剥离 `solution`/`root_cause` 输入？当初为何加入 `solution`？
   当前只做诊断（靠标题 / 问题描述 / 告警信号 / 有效排查步骤 4 个字段确认 KBD），不做处理。
2. **校验层**：`_validate_signal` 对 `qfk_vm`、`qfk_system` 增加"写操作子命令拦截"
   （`start/stop/kill/delete` 等），从有效排查步骤抽出的写操作一律不自动执行，必须人工授权。
3. **执行层**：只跑 `phase=diagnostic` 信号；通过"门禁"再次严判拦截写操作；全部通过后
   只返回 KBD 的 `root_cause` + `solution` 原始文本，并注明证据（KBD 标题做成可点击超链接）。
4. **分类器补漏**：`acli system kill/...` 及非 `acli` 写命令包进 `system` 子命令时，应补
   `risk=2/3` 规则，避免"写操作免确认自动跑"的安全倒挂。
5. **第一性原理 + 贪心循环随机性**：解决 `len(remaining)=1 ≤ 2` 时执行顺序的确定性问题，
   并核实之前怀疑的"贪心循环导致 KBD 顺序随机"是否成立。
6. **20 篇同类 KBD（80–140 信号）的判定机制**：到底是"命中相同信号就打分"还是其他形式？

---

## 二、六项分析与决策（WHAT + WHY）

### 2.1 抽取层剥离 solution（治本）— 已做

**决策**：`extract_signals.py` 的 `extract_signals_for_kbd` 现在向抽取 LLM 传入
`root_cause=""`、`solution=""`，并把这两个章节从合法来源 `_VALID_SOURCE_SECTIONS` 移除，
`_infer_source` 一律回退到 `steps_text`。即根上不再把"根因 / 解决方案"喂给抽取 LLM。

**当初为何加入 solution（根因）**：
抽取 prompt 模板（`002_...sql`）的 `source_section` 枚举含 `root_cause`/`solution`，
且 `_infer_source` 对"有 matcher 的消费者信号"回退到 `root_cause`。设计意图是想把
解决方案章节里**夹杂的观察性判定句**（如"若重新执行开机仍报 X 则…"）也抽成消费者信号。
但设计未区分"观察性判定"与"处置动作（祈使）"，于是 `acli vm start`、`kill -9` 这类
**写操作祈使句**被一并当成关键信号——这正是 27123 类工单错误的源头。

**结论**：当前只做诊断、靠 4 个字段确认 KBD 并取出 `root_cause`/`solution` 原文，
剥离 `solution`/`root_cause` 作为输入正确且治本。诊断性检查本就在 `steps_text`（有效排查步骤）里。

### 2.2 校验层：写操作子命令拦截 — 已做

`extract_signals.py` 新增：
- `WRITE_OP_SUB_COMMANDS`（start/stop/kill/delete/rm/format/reboot/migrate/clone/snapshot…）
  与 `_DESTRUCTIVE_SUB_COMMANDS`；
- `_is_write_op_signal()`：对 `qfk_*` 后端信号按 `sub_command` 切词命中词表即判写操作；
- `_validate_signal()` 后端分支就地标注 `phase="solution"` / `require_human_confirm=True` /
  `risk=2或3`。

这类信号**不丢弃**（可能确实是排查步骤里需人确认的动作），但执行层绝不自动跑，必须人工授权。
执行层 `kbd_differential.py` 还有一道**纵深门禁** `_signal_requires_human()`：即使 schema
未带标记，只要 `sub_command` 命中写动词就拦截。满足"从有效排查步骤抽出的写操作一律不自动执行、
请求人工授权"。

### 2.3 执行层：只跑诊断 + 门禁 + 只返原文 — 已做

`kbd_differential.py` 改动：
1. **候选确定性排序**：`remaining.sort(key=lambda k: (-k.similarity, str(k.id)))`，
   消除结论与并列选择的随机性。
2. **写操作门禁**：贪心主循环与确认分支在**执行前**调用 `_signal_requires_human()`，命中则
   不自动执行，记录 `StepResult(error="写操作/处置动作：诊断阶段不自动执行，需人工授权")`，
   并 `yield AgentInteractiveRequest(...)` 向前端推送"需人工授权"交互卡（含 risk 元数据）。
3. **报告只返原文**：`_generate_report → _build_diagnostic_report` 现在只输出：
   - `### 诊断结论：[KBD标题](/kbd/{id})`（**可点击超链接**，模板 `KBD_DETAIL_URL_TEMPLATE = "/kbd/{id}"`）；
   - `**根因（原始文本）**` + `**解决方案（原始文本）**` 原文；
   - `**现场证据**`：每条关键信号的现场确认结果（✓ / ✗ / 需人工授权）。
   不再用 LLM 改写，避免二次加工偏差。

> 注：`/kbd/{id}` 为前端详情路由占位，部署时按 admin-ui 实际路径微调 `KBD_DETAIL_URL_TEMPLATE`。

### 2.4 分类器补漏：修复"安全倒挂" — 已做

**关键根因（代码实证）**：`qfk/engine.py` 虽把命令硬编码成 `risk_level=1, policy="auto"`，
但 `executor.py` 对 `acli_exec` 会**重新用 `classify_acli` 求值并覆盖传入值**。所以
`classifier.py` 的规则对 QFK 路径**是生效的**——只是它**缺了 `acli system kill` 等规则**，
导致 `kill` 仍被默认判 `risk=1` 静默自动跑。这就是"安全倒挂"：
`acli vm start` 走 `risk=2` 要确认，`kill` 反而免确认。

`classifier.py` 已补（按 risk 降序，首个命中获胜）：
- risk=3：`acli system rm -rf / mkfs / dd if=`、`acli system rm|del|format`
- risk=2：`acli system <kill|killall|pkill|reboot|shutdown|halt|poweroff>`、
  `acli system systemctl start/stop/...`、`acli system chmod|chown|mv|remove|delete`

现 `acli system kill -9 240132` → risk=2（confirm），`acli system ps auxf`/`lsof` → risk=1（auto），
`acli system rm -rf` → risk=3（block）。

### 2.5 第一性原理 + 贪心循环随机性（实证）

**结论：贪心循环不会导致 KBD 顺序随机。** 代码实证：

- `diagnose` 主循环是 `while len(remaining) > EARLY_STOP(=2)`。当 `len(remaining) ≤ 2`
  （27123 单候选正是此情形），**主循环一次都不进**，直接走"确认分支"，按 `remaining` 列表顺序
  遍历候选、再按 `kbd.signals` 列表顺序跑**后端**信号。
- `remaining` 的顺序由检索 `search_cases_with_steps` 决定：按向量余弦相似度降序。
  `signals` 列表顺序 = 抽取 LLM 产出顺序 = KBD 内容顺序。所以单候选场景下执行顺序**完全确定**，
  与贪心循环无关。
- 即便 `len(remaining) ≥ 3` 进入贪心，`_pick_best_step` 用 `Counter.most_common`，在给定
  `remaining` 顺序下也是确定的（Counter 保序）。已在 `diagnose` 入口加 `(-similarity, id)`
  稳定排序，使 `remaining[0]` 与并列选择**可复现**。

真正的"不确定性"若来自检索层 pgvector 的并列相似度排序，不是贪心循环；已用入口确定性排序消除。

**业界范式（诊断即"鉴别诊断协议"）**：
单/少候选时，KBD 本身就是一份**有序诊断剧本**，应按
"前端生产者(优先级最高) → 后端消费者(文档顺序)"自顶向下执行，而非按"覆盖频率"贪心重排——
后者只在多候选需要**鉴别剔除**时有意义。多候选真正需要"鉴别"时，应改用**信息增益 / 最大区分度**
选步（"20 questions" 决策树），而非当前"选覆盖最多者"（频率最高往往是最共享、最不具区分度的步，
反而慢）。当前 `EARLY_STOP=2` 的早停使多数同质分类根本不进贪心，故影响不大。

### 2.6 20 篇同类 KBD（80–140 信号）的判定机制

**不是打分，是"集合过滤（淘汰制）"**，代码实证：

1. **检索收窄**：`search_cases_with_steps(top_k=15)` 先用向量相似度从同类筛出候选集 `C`
   （最多 15 篇，不是 80–140 全量）。
2. **逐轮淘汰**（主循环 `len(C) > 2` 时）：
   - `_pick_best_step`：统计每个工具(acquirer)在候选中的**覆盖频率**，选最高频者；
   - 执行该工具，拿到真实输出 `raw_output`；
   - `_judge_matches`：对 `C` 中每篇 KBD，用其 `matcher`/`expected_pattern`（正则/包含/LLM）
     判断"该 KBD 对此步的预期是否命中输出"，返回**匹配的 KBD id 集合**；
   - **过滤**：`remaining = [k for k in C if k.id in match_ids]`——**不命中的被淘汰**，命中的保留；
   - 重复直到 `len(remaining) ≤ 2` 早停。
3. **收口**：`is_definitive = (len==1)`；否则报告剩余 2 篇（均不确定），取 `remaining[0]`
   （相似度最高）作主结论。

**所以机制是"命中即保留、不命中即淘汰"的集合运算，不是对相同信号累加打分。** 80–140 信号里
大量是跨 KBD 共享的（qfk_log/qfk_system 等公共采集器），真正起鉴别作用的是**各 KBD 独有、
且 expected_pattern 不同的那几个信号**。

**已知弱点（后续演进）**：
- 选"最高频"步 ≠ 最高区分度，可能需多轮才能分出；理想是信息增益选步；
- 若某 KBD 的共享步 `expected_pattern` 缺失或 LLM judge 误判，会错误淘汰/保留；
- 早停在 ≤2，至多锁定 1 篇，极端情况剩 2 篇需人工二选一。

## 三、关键追问：工单 Q2026071755113 为何首步是 acli vm start 而非 qkv_task

> 现象：27123 单候选工单，执行轨迹的**第一步可见步骤**是
> `QFK诊断信号提取执行: acli vm start`，而按 KBD 内容顺序，
> 第一个信号应是 `qkv_task 启动虚拟机失败`（前端生产者信号）。

### 3.1 代码路径实证（两层原因叠加）

**原因 A — 代码执行顺序（结构性，与数据无关）：**
1. `qkv_task 启动虚拟机失败` 是 `signal_category == "frontend"` 的**生产者**信号；
2. 单候选 27123 → `len(remaining)=1 ≤ 2` → 贪心主循环**一次不进**；
3. **Phase A `_run_producers`（`:756-814`）确实跑了 `qkv_task`**，但它是**静默执行**：
   - 不 `yield` 任何 `AgentStageUpdate`（无可见步骤事件）；
   - 不写入 `steps_executed`；
   - 只把产出(produces)写入会话变量池（黑板）；
4. **确认分支（`:418-427`）遍历 `kbd.signals` 但 `if s.get("signal_category") != "backend": continue`，
   直接跳过前端生产者信号**，只重放 `backend`（qfk）信号。

因此可见轨迹里：Phase A 的 `qkv_task` 不可见，确认分支从第一个 `backend` 信号开始重放——
`acli vm start` 成了"第一步可见步骤"。这**不是 KBD 顺序随机**，而是
"生产者静默执行 + 确认分支只重放后端"导致的**可见顺序**与 KBD 内容顺序的表面错位。

**原因 B — 数据问题（本次已修复的根因）：**
该工单在**修复前**处理。`acli vm start` 来自 27123 的**解决方案**章节
（"返回 HCI 控制台，重新执行虚拟机开机操作"）。旧抽取链路把 `solution`/`root_cause`
喂给抽取 LLM（见 2.1），于是这句**写操作祈使句**被当成了"关键后端诊断信号"抽出来，
且排在 `lsof`/`ps auxf` 等真正诊断信号之前。叠加上原因 A，它就成了第一步可见步骤。

### 3.2 修复后的预期

- **抽取层（2.1）**：`solution`/`root_cause` 不再入抽取输入 → `acli vm start`（solution 章节写动作）
  **不会被抽出**；27123 的有效后端信号只剩 `lsof | grep <vmid>`、`ps auxf | grep <PID>` 等真正诊断步骤；
- **执行层（2.3 + 2.4）**：即便还有写操作信号命中，`_signal_requires_human` 门禁会拦截并请求人工授权，
  绝不自动跑；
- **可见顺序**：第一步可见步骤将是第一个 `backend` 诊断信号（如 `lsof | grep <vmid>`），
  且 `qkv_task` 虽在 Phase A 静默执行，其作为"前端生产者"的优先级仍高于后端（变量池先于消费者填充）。

### 3.3 已识别的设计缺口（已修复）

确认分支原先"关键信号确认"证据**刻意排除了前端生产者信号**（`if s.get("signal_category") != "backend": continue`），
这与"前端信号优先级 > 后端"原则（原任务第 5 点背景）相悖，也会跳过真正最具区分度的关键信号
（`qkv_task` 本身）。**现已修复**：确认分支改为**按 KBD 内容顺序遍历全部 `signals`**，
前端生产者作为"已确认的生产者证据"纳入报告与步骤事件（`category` 字段标注信号类别），
不再 `continue` 跳过。前端生产者在 Phase A 已静默跑过并填充变量池，此处重放为只读、可幂等，
仅用于补全证据链与顺序，使可见顺序与 KBD 内容顺序一致、且覆盖关键前端信号。

> 修复位置：`kbd_differential.py` 确认分支（原 `:418-423` 的 `signal_category != "backend"` 过滤已移除）。

## 五、验收标准

1. 抽取接口对含解决方案写动作的 KBD，不再产出 `acli vm start`/`kill -9` 类 `phase=diagnostic` 信号；
   即便产出写操作信号，也带 `require_human_confirm=True` / `phase="solution"` / `risk≥2`。
2. 单候选诊断：可见步骤首步为真正的诊断型后端信号（如 `lsof`），写操作信号只记录并推送人工授权，
   不自动执行。
3. `acli system kill -9 <PID>` / `acli system reboot` 经 `classify_acli` 判定为 risk≥2；
   `acli system ps auxf` / `lsof` 保持 risk=1。
4. 相同输入多次诊断，候选排序与结论可复现（无随机性）。
5. 诊断报告仅含 `root_cause`/`solution` 原文 + 现场证据 + 可点击 KBD 标题超链接，无 LLM 改写。
