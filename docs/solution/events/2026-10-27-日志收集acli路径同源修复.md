# 日志收集 acli 路径同源修复（探测通过、采集报 command not found）

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：统一 log_collect 全通道 acli 解析，消除裸命令依赖 PATH 的缺陷 | [日志收集 bridge 执行通道](2026-10-22-日志收集bridge执行通道.md) |

## 一、现场现象

日志收集面板显示探测成功（`acli 1.0.0 / 探测于 15:27:06 /sf/bin/acli`），但一点「采集」就报：

```text
bash: acli: command not found
```

同一节点上运维手敲 `which acli` 得到 `/sf/sbin/acli`，看起来"命令明明存在"。

## 二、第一性原理：两个现象根本不是一件事

拆到不可再分的三个事实：

1. **探测走绝对路径**：`logCollectAcliCandidates = ["/sf/bin/acli", "/sf/sbin/acli"]`，
   第一个存在且 `--version` 有输出就 `exit 0`，第二个不再检查 —— 所以面板必然显示 `/sf/bin/acli`，
   与登录 shell 的 PATH 顺序（`which` 命中 `/sf/sbin`）无关；
2. **执行走裸命令**：`create` / `progress` / `cancel` 当时直接下发 `acli log_collect …`，
   而 `runCommandPty` 是 `ssh.Client.NewSession()` + `CombinedOutput`，**不经过**
   `wrapContainerCommand` 的 `export PATH="$PATH:/sf/bin:/sf/sbin…"` 前缀；
3. **sshd 非交互会话的默认 PATH 不含 `/sf/bin`、`/sf/sbin`**（仅 `/usr/bin:/bin` 一类），
   因此裸 `acli` 必然 127。

三者相乘的结论：**探测的"能看见"和执行的"能跑到"取自两套互不相同的解析逻辑**。
探测绿、采集红不是环境偶然，而是代码结构决定的必然结果。

## 三、修复

统一为一个解析入口 `logCollectAcliInvoke(args)`：

```text
export PATH="$PATH:/sf/bin:/sf/sbin:/usr/sbin:/usr/local/bin";
__acli=""; for p in /sf/bin/acli /sf/sbin/acli; do [ -x "$p" ] && __acli="$p" && break; done;
[ -z "$__acli" ] && __acli=$(command -v acli 2>/dev/null);
[ -z "$__acli" ] && { echo __ACLI_ABSENT__ >&2; exit 127; }
"$__acli" <args>
```

覆盖动作：

| 动作 | 修复前 | 修复后 |
|---|---|---|
| 版本探测 | 自带绝对路径解析 | `buildAcliVersionCommand` 复用 `logCollectAcliResolve` |
| help（场景目录） | `export PATH…; acli …` | `logCollectAcliInvoke("log_collect create --help")` |
| node list（可采节点） | `export PATH…; acli …` | `logCollectAcliInvoke("--formatter json platform node list")` |
| create | 裸 `acli log_collect create …` | `logCollectAcliInvoke(command)` |
| progress | 裸 `acli log_collect progress` | `logCollectAcliInvoke("log_collect progress")` |
| cancel | 裸 `acli log_collect cancel` | `logCollectAcliInvoke("log_collect cancel")` |

设计要点：

- **同源**：候选列表、PATH 前缀、PATH 兜底只有一份实现，探测显示的那份就是执行用的那份；
- **失败语义统一**：解析不到 `acli` 时输出 `__ACLI_ABSENT__` 并 `exit 127`，调用方按「工具缺失」处理，
  不会误判成插件业务失败；
- **展示与执行分离**：`buildLogCollectCreateCommand` 仍返回不含 `acli` 本体的参数串，
  前端 `Detail` 与桥侧日志展示 `acli log_collect create …`（可读），实际下发的是自解析命令。

## 四、验证

- 单测：
  - `TestLogCollectAcliInvokeUsesResolvedPath`（create/progress/cancel/help/node_list 五个动作都必须含
    PATH 前缀、绝对路径候选、`command -v acli`、`exit 127`、`"$__acli" <args>`，且不得出现裸 `; acli `）；
  - `TestLogCollectCreateCommandRequiresInvoke`（参数串不得含 `acli` 本体，防双份）；
  - `TestBuildAcliVersionCommandPrefersAbsolutePath`（版本探测仍绝对路径优先）。
- 真实 shell 端到端（临时测试，跑完删除）：把候选替换为临时假二进制、PATH 置空 → 命令仍成功执行
  `ARGS:log_collect progress`；候选全部不存在 → `__ACLI_ABSENT__` + exit 127。
- `go test ./...`、`go vet ./...`、`gofmt -l .` 全绿。

## 五、边界与遗留

- `/sf/bin` 优先于 `/sf/sbin` 仍可能导致"面板显示旧版"：本修复只保证**同一份二进制**，
  不解决"两份二进制版本不同时该选哪份"。能力探测（`log_collect create --help` 能否解析）
  比路径序更接近真实可用性，后续可考虑改为能力优先。
- node list 失败时 `catalog_note` 现在带输出首行，可直接区分「旧版无该子命令」与「清单为空」。
- 仿真会话（hci-sim）无 `log_collect` fixture，本次改动不涉及仿真通道。
