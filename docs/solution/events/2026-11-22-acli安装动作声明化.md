## 一、现状（实测，不是引述）

`HandleAcliSync` 是 655 行的单一函数（`acli.go:78-733`），11 个阶段。其中**两处已经声明化**：

- 阶段 4 版本判定：`acliSyncDecision` 构造 `DesiredState{KindAcliBinary, Version: VersionOrdered}` 并调 `reconcile.Compare`
- 阶段 11 落盘校验：`acliLandingDescriptor` 构造 `DesiredState{KindPluginBundle}` 逐节点探测

**只有阶段 10（执行安装）没有**：`buildAcliInstallCommand` 手拼 `export PATH=...; <dest> --install --force`。

骨架侧其实一切就绪：`InstallSpec`、`SmokeSpec`、`InstallAcli`/`InstallRegisterPlugin` 常量、`Deps.InstallFunc` 注入点全都存在，`InstallAcli` 却只有骨架自己的测试引用过（`pipeline_test.go:461`）——**定义了一个槽，从没人往里放东西**。

## 二、第一性拆解

### 声明化的粒度是「动作」，不是「文件」

插件部署脚本（`renderAcliPluginDeployScript`，140 行）在一个 SSH 会话里完成 `mv 备份 → 写多文件 → 注册 → 自检`。把它拆成 `FileSpec[]` 会破坏原子性与失败回滚。

所以声明化的正确形态是：**动作声明 + 域内唯一渲染器**，`Args` 只承载渲染所需的最小事实。给 acli 安装就是 `Args=[destPath]`——版本与摘要属于传输阶段的事实，塞进来只会让声明变成"把所有入参抄一遍"。

### default 分支必须报错

一旦渲染器留 `sh -c` 兜底，声明化就退化成"多一层间接寻址"，且未登记的动作会被静默放行。因此 `renderInstall` 的 `default` 直接返回错误，`installAcliPackage` 渲染失败时按"命令未执行"返回，绝不退化成兜底命令。

## 三、本轮改动

**1. acli 安装动作声明化**
- 新增 `acliInstallSpec(destPath) → InstallSpec{Kind: InstallAcli, Args: [destPath]}`
- 新增 `renderInstall(ctx, r, d)`：唯一实现，签名与 `reconcile.Deps.InstallFunc` 一致（未来可直接注入，避免"声明一套、执行另一套"）
- `installAcliPackage` 改为经渲染器取命令；删除 `buildAcliInstallCommand`

**2. 插件链路登记纠偏**
- `reconcile` 新增 `KindPluginSet = "plugin_set"`，加入 `ValidKind`/`AllKinds`
- `kinds` 新增 `ModeDomainLocal`：域内自持 Observe/Compare/Act/Receipt，循环跑在域内
- `kinds_wire` 把插件同步从 `plugin_bundle` 拆出，`plugin_bundle` 的 Note 明确"只做只读校验"

## 四、插件链路的实测结论：它不缺声明化

| 骨架要素 | 插件链路的对应物 |
|---|---|
| `DesiredState` | `acliPluginDesired{Name, Version, SpecHash, Files[], RegisterItem, SmokeArgs}` |
| `NodeFact` | `acliPluginHostState{ProbeErr, DigestComparable, Register, Files[]}` |
| `Compare → Plan` | `compareAcliPluginState → (action, reason)`，5 态（install/overwrite/skip/failed/unreachable） |
| Activate + 回滚 | 脚本内 `.old.$DEPLOY_ID`，"无备份不删" |
| Receipt | `AcliPluginStageReceipt`（逐插件明细 + 计数 + warnings） |

**它已经是 domain-local 收敛循环，完成度高于 acli 二进制。** 之前的登记把它记在 `plugin_bundle` 上（`ModeDeclarative`，只读校验），属于**登记比实际弱**——与 SPC 的 `intent_only`（登记比实际强）方向相反、危害相同：没人能从登记册判断该看哪儿。

因此对插件**不做**装饰性的 `InstallSpec`：它需要的不是"再声明一层"，而是"被正确登记"。

## 五、为什么不把编排接进 `reconcile.Run`

| 障碍 | 事实 | 硬接的后果 |
|---|---|---|
| 集群冒烟 | `--install --force` 在发起节点执行、内部向集群分发；`verifyClusterPluginLanding` 需要 `*session.Hub` 逐节点探测 | 骨架 `SmokeFunc` 只给单节点 `remote.Runner` → 冒烟退化成验本节点，重演 Q2026111700614「47 个空目录被安装成功掩盖」 |
| 包复用与断点 | `findRemoteAcliPackage` + `verifyReusedRemotePackage` 省掉重复上传 20MB；`retryStage=upload` 可跳过下载 | 骨架 `writeFiles` 只有 `WriteFile/CopyFile`，`FileSpec.Source.Offset` 未被使用 → 功能丢失 |
| 无账本语义 | `KindAcliBinary` 是 CompareOnly，节点被第三方清空必须重探 | 走 Run 要处理 `Store` 的 Skip 语义，与定位冲突 |

一句话：**骨架的编排契约是「单节点 + 有账本 + 无包复用」，acli 是「集群 + 无账本 + 有复用」。** 类型可以借，编排不能硬套。

## 七、剩余（W3/W4，未做）

- **W3**：把 11 阶段收敛语义显式化（`Observe → Compare → Act → Verify` + 幂等声明 + 复用 `reconcile.Result`）。
  前置是**测试地基**：`HandleAcliSync` 目前零测试覆盖，且阶段无法脱离重排被单测覆盖——正确形态是"抽一个阶段 → 补该阶段测试 → 下一个"，边抽边测，而不是先搭地基再重排。
- **W4**：扩展骨架契约（多节点 Smoke / 包复用 / 无账本模式），让两条链路真正进 Run。
  必须等 W3 完成后才知道该扩什么；且 `reconcile.Run` 的现有消费者是 logcollect 配置下发（已上线），不能与 acli 重排塞进同一个 PR。
