- 日期：2026-10-28
- 现场工单：Q2026102800331（P1 直传）、Q2026102800332（无任务）、Q2026102800720（P2 上传完成、代传未发起）
- 涉及：`terminal_bridge/log_collect.go`、`frontend/customer`、`case-service`

## 二、根因

1. **节点清单 JSON 截取脆弱**：旧实现取"首个 `{` 到末个 `}`"。acli 会在清单前打印
   `{"@timestamp":...}` 形式的运行日志，首个 `{` 命中日志行，拼接结果必然 `Unmarshal` 失败。
   即使 acli 修好 cgroup 读取，只要这行日志还在，清单仍为空。
2. **交付路径展示读错来源**：进行中页面按当前探测结果渲染路径标签，而不是任务记录
   `upload_mode`；一次 10 秒超时的探测就能把"实际 P1"显示成"P2"。
3. **探测结论会覆盖用户选择**：`pathMode` 在探测失败时被静默改成 P2，用户没有明确决策。
4. **探测快照不随任务落库**：失败任务无法自证"当时那台机器是什么状态"。
5. **无请求级审计**：任务表存的是服务端归一化结果，回答不了"用户当时选了什么"。
6. **跨工单归属不可判断**：progress 事件 `task_id` 为空，回包不带 ticket；acli 是节点级单任务，
   同一节点可能跑着别的工单。

## 三、本次改动

### bridge（Go）

- `parseLogCollectNodeList` 改为从每个 `{` 起点用 `json.Decoder` 解码，只接受含 `data` 数组的对象；
  日志行、提示符、多个 JSON 并列都不再污染解析。
- `OutMessage.TicketNo` 原样回显请求工单号；probe/create/progress 三类回包都带。
- `log_collect.progress` 事件补 `ticket_no`、`task_id`、`archive_exists`。
- 新增用例：日志噪声、多个 JSON 并列、非法 IP 去重。

### case-service

- `LogCollectTaskCreate.probe`：下发前探测快照（acli 版本/构建/架构/节点数/目录来源/可达性/两类失败原因）。
- `_build_task_detail`：快照写入 `detail.probe`，单字段超过 1024 字符截断，整体超过 8 KiB 降级为最小集合。
- `operation_audit` 写入：`log_collect.create` 记录 `upload_mode`、`remote_url_set`、模块/日期/IP、
  `acli_version`、`arch`、`probe`，`trace_id` 与任务一致；审计失败不阻断建单。
- `environment_service._extract_env_info` 透传 `node_count_error`。

### customer-ui

- 交付路径标签改读 `currentTask.upload_mode`；无任务时才显示"建议"。
- 探测失败不再静默切 P2：仅在探测确认可达时给默认 P1；未选择时下发前拦截并说明风险。
- 探测失败拆成两条独立告警（节点清单 / 日志服务器），完整原文可复制，不再截断 200 字符。
- `progress` 请求携带 `ticketNo` 与 `execId`；回包 ticket 与本单不一致时不采用该进度，并提示
  节点上存在其它工单的任务。
- 环境数据新增节点清单采集命令（可选命令，失败不阻断建单），解析出 `host_count`；
  失败时写 `node_count_error`，界面显示"节点数未采集（原因）"而不是 `?节点`。

### 存储与索引

- `log_collect_task` 新增 `object_key / object_size / object_sha256`（迁移 055，含历史回填），
  与 `archive_*` 解耦：P1 的 `archive_path` 是节点绝对路径、P2 是对象 key，混用导致
  "平台有没有留包"只能进容器 `ls`。
- complete 成功后同时写 `object_*`，产物索引不再依赖文件系统探测。

### 新增查询接口

- `GET /log-collect/tasks/artifacts?case_id=`：回答"平台有没有留包、多大、sha 多少"。
- `GET /log-collect/tasks/probes?case_id=`：探测历史（含两类失败原文），面板折叠展示。

### 其他

- P1 交付文案标注"节点自报，平台无独立回执"，并在 `detail.delivery_evidence` 记录判定依据。
- 自动轮询连续 3 次失败升级为可见告警，不再永久静默。
- 节点清单主命令失败时尝试备选 `host list`，仍失败则记录主命令错误首行（区分"命令缺失/执行报错/真没节点"）。
- 目标主机 `all` 与具体 IP 互斥（前端与平台双侧拒绝），空白项不计为主机。

## 四、验收

1. 构造 `日志行 + 节点 JSON` 混合输出，`parseLogCollectNodeList` 必须解析出全部节点（已覆盖单测）。
2. 已有任务时，界面交付路径必须等于 `upload_mode`，探测结果变化不影响该标签。
3. 探测 `log_server_reachable=false` 时，下拉路径不得自动变成 P2；未手选时下发被拦截并提示。
4. 新建任务的 `detail.probe` 含 `hosts_count/catalog_note/note/log_server_reachable/acli_version`。
5. `operation_audit` 能按 `resource_id=<task_id>` 查到 `log_collect.create`，`details.upload_mode` 与任务一致。
6. 同一节点存在其它工单采集时，progress 回包 ticket 不一致 → 不渲染该进度、出现提示。
7. 环境卡节点数为"未采集（原因）"而非 `?节点`。
