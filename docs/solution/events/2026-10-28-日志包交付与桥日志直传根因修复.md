# 2026-10-28 日志包交付与桥日志直传：五个根因与修复

## 一、现象

工单 `Q2026102801014`（节点 `192.168.1.20`，x86_64，acli 1.0.0）：

| 事实 | 数据 |
|---|---|
| 采集 | 成功，`/sf/data/local/acli/tmp/data/log_collect/Q2026102801014.zip` = 12 863 365 257 字节（11.98 GiB） |
| 任务状态 | `completed` / `progress=100` / `upload_mode=bridge_relay` |
| 平台侧收到 | **0 个分片**（`delivery.job_finished` 的 `uploaded_parts=0`） |
| 桥日志直传 | 27 次 `log_upload.failed`，`platform HTTP 500`，队列 6 → 34，退避到 32s |
| 3 天内全局 | `log_upload.failed` 2169 次；`delivery.job_finished` 62 次，`phase=failed/retrying` 占绝大多数 |

用户看到的是"日志收集已完成"，实际是**包只存在于客户机**，平台一份字节都没有。

## 二、根因（五个，互相独立）

### 2.1 主因：TMOUT=600 连坐，12 GiB 在物理上搬不完

HCI 交互式 shell 有 `TMOUT=600`（2026-10-22 已实测，注入源未定位，属深信服定制）。
本次 4 天内 `ssh.disconnected` 的 `duration_seconds=600` 出现 **24 次**，全部 `reason=remote_eof`。

交付拉取用的是一条独立 exec 通道（`tail -c +N` 流式），本不受 TMOUT 影响；
但 bridge 把**主交互 shell 退出**当成整条 SSH 连接失效，直接 `destroySession`，
把正在跑的 exec 通道一起带走。于是：

- 实测拉取速率 6 039 797 760 字节 / 626 秒 ≈ 9.6 MB/s；
- 600 秒窗口最多搬 ≈ 5.7 GiB，而包是 11.98 GiB；
- 结论：**在"shell 退出即会话失效"的前提下，这个包永远传不完**，与网络好坏无关。

### 2.2 自签证书：分片上传 0 片成功

平台在客户内网使用自签证书（staging `acli.sangfor.com.cn:4443` 已确认）。
交付通道的放宽依赖 `job.TLSInsecure`，该字段来自前端下发的 `tls_insecure`——
**customer 前端全仓 0 处引用**，于是恒为 false：

```
分片 2 上传失败: Put "https://acli.sangfor.com.cn:4443/api/direct/log-collect-uploads/.../parts/2":
tls: failed to verify certificate: x509: certificate signed by unknown authority
```

`已传 0/14 片`、`已传 0/15 片` 就是这么来的。

### 2.3 收尾 500：DB 事务跨越分钟级文件合并

`complete_upload_direct` 先用同一 session 读任务（SELECT 即开启事务），
然后 `storage.merge` 把 384 个分片流式合并、算 SHA-256——12 GiB 需要数分钟。
`DatabaseManager` 建连时设了 `idle_in_transaction_session_timeout=30000`（30 秒），
PostgreSQL 到点会**主动 kill 该连接**，随后 `flush()` 必然抛：

```
sqlalchemy.exc.InterfaceError: (asyncpg ... InterfaceError) connection is closed
[SQL: UPDATE log_collect_task SET archive_path=... ]
```

6 小时内该错误 **62 次**，全部落在 `complete` 与少量 `parts` 请求上；
桥侧看到的是「平台收尾失败 HTTP 500」，而分片其实已经全部传完（3.8 GiB 的包就是这样白传）。

### 2.4 桥日志直传 100% 失败：两层都不解 gzip

`log_uploader.sendBatch` 固定发 `Content-Encoding: gzip`（弱网优化，100 条压缩后通常 < 20KB）。
而 api-gateway 的 `/api/bridge-logs/direct` 直接 `await request.json()`、
conversation-service 同名端点用 Pydantic body 解析，**两层都不解压**：

- 网关：JSON 解析失败 → 500；
- 绕过网关直连 conversation-service:8002 → 400 `There was an error parsing the body`。

实测同一端点发明文 → 401（说明路由与转发链路正常，只是令牌无效），发 gzip → 500。

### 2.5 附带风险：客户机磁盘与收尾超时

- 12 GiB 副本要完整落到客户机再分片上传，原来没有空间预检，写满一半才 ENOSPC，
  报错还伪装成"拉取中断"；
- 收尾请求复用分片超时（5 分钟），慢盘上合并没写完桥就先断开，
  服务端随后才落库——桥侧只看到 `ClientDisconnect`。

## 三、修复

| # | 位置 | 改动 |
|---|---|---|
| 1 | `terminal_bridge/main.go` | 新增 `shellHeartbeatInterval=120s`：拉取期间向交互式 shell 注入 NUL（Ctrl-@），bash 里等价 set-mark，无回显、不进历史，纯粹重置 TMOUT |
| 2 | `terminal_bridge/main.go` | 新增 `longTasks` 计数；`on_output_start` 发现 shell `remote_eof` 且有长任务时只摘 shell、**保留连接**（事件 `session.shell_eof_detached`） |
| 3 | `terminal_bridge/lifecycle.go` | 空闲租约回收跳过有长任务的会话（浏览器关闭是大包交付的常态，不能据此回收） |
| 4 | `terminal_bridge/delivery_runner.go` | 分片/收尾命中 x509 → 自动置位 `TLSInsecure` 并留痕 `delivery.tls_relaxed`，按 transient 重试；与桥日志直传通道策略一致（只放宽 TLS，不放松令牌鉴权） |
| 5 | `terminal_bridge/delivery_runner.go` | 收尾超时独立为 30 分钟（`deliveryCompleteTimeout`） |
| 6 | `terminal_bridge/delivery_disk_unix.go`、`terminal_bridge/delivery_disk_windows.go` | 拉取前算本地可用空间，不足直接给出"需要/可用"的具体数字（Windows 侧保守返回 0，宁可漏检不可误拦） |
| 7 | `case-service/log_collect_upload_service.py` | `merge` 前显式 `commit()` 结束只读事务，合并后再 flush 开新事务——**绝不让分钟级 I/O 跨在事务里** |
| 8 | `api-gateway/routes/bridge_logs.py` | `/direct` 按 `Content-Encoding` 解压后再解析，转发上游时发明文 JSON |
| 9 | `conversation-service/routes/bridge_logs.py` | `/api/bridge-logs/direct` 改为手工读 body + 解压 + `model_validate_json`，非法 gzip 返回 400 而不是 500 |

## 四、验证

- `terminal_bridge`：`go build`（linux + windows）、`go vet`、全量 `go test` 通过；
  新增 `TestReaperKeepsSessionWithLongTask`、`TestShellHeartbeatStopIsIdempotent`、
  `TestUploadAgainstSelfSignedPlatformAutoRelaxesOnce`（首次必失败且不落片 → 自动放宽 → 字节完整送达）。
- `case-service`：`tests/unit` 140 passed；新增 `test_complete_ends_transaction_before_merge`
  （断言合并前 commit 恰好一次、合并中不再提交）。
- `conversation-service`：新增 gzip 解压、明文兼容、坏 gzip 400 三个用例。
- `api-gateway`：新增 gzip 解压转发、明文兼容、坏 gzip 400 三个用例。

## 五、遗留

1. 前端仍未下发 `tls_insecure`。bridge 已自动兜底，但语义上应由前端在用户确认自签时显式声明。
2. 拉取依赖浏览器建立过的 SSH 会话；bridge 重启或客户机断网后仍需人工重连才能 resume。
   断点续传本身可用（本地文件大小 + `tail -c`）。
3. 桥日志直传的 outbox 仍在客户机磁盘上限内退避重试；修复部署前积压的批次会在恢复后补传。
