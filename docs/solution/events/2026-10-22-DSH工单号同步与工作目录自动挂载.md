# DSH 工单号同步与工作目录自动挂载方案

## 背景与需求

### 需求原话

> 1、在 dsh 诊断工作台，新增一个输入工单号的功能
> 2、输入工单号点击确定的后能立马从 0.2 上把对应工单号的目录同步到 0.4 上面
> 3、同步后自动解压
> 4、Deepseek 自动选择解压后的目录作为 Workspace Directory
>
> dsh 现在在 k3s 的容器中，我们把 `/sf/log` 挂载到 k3s 的容器中

### 需求消歧（把 4 句话翻译成可验收的行为）

| # | 原始表述 | 消歧后的行为契约 | 不在范围内 |
|---|---|---|---|
| 1 | 新增输入工单号的功能 | 在"选择工作目录"的同一入口提供第二项入口；工单号格式由服务端强制校验，失败即拒 | 不做工单列表/搜索/最近使用 |
| 2 | 点击确定后立马同步到 0.4 | 点击确定即**入队并返回**（不阻塞在 HTTP 请求里），客户端转入进度视图；"立马"指 ≤ 1s 出现 `syncing` 状态，而非 ≤ 1s 完成 | 同步的传输实现由另一 agent 提供，本方案只定义调用契约 |
| 3 | 同步后自动解压 | **递归解到叶子**：zip 解到 `<工作根>/extract`；其中每个 `sp_<ip>.tgz` **流式管道**展开；若展开结果中仍有 `.tar.gz/.tgz/.zip`，继续递归解开，直到无可解压缩包或触达深度上限 4（依据见 D4，实测存在 3 层工单）。需要 zip 密码（见 D10），全过程做硬水位保护（见 D11） | 不做 rar/7z/zst；不无限递归（深度上限 4） |
| 4 | 自动选择解压后的目录作为 Workspace Directory | 解压成功后，客户端自动 `createWorkspace({ path: 解压目录 })` 并把该目录作为新会话 cwd；等价于操作者手选了这一层目录 | 不改 DSH 的 workspace 持久化语义；不写 system prompt |

### 关键前置事实（全部为本机实测取证，非推测）

| 事实 | 证据（2026-10-22 实测） | 对方案的硬约束 |
|---|---|---|
| 0.2 的 `/sf/log` 下有 **954** 个工单目录（父目录 link count 956，含 `.`/`..`） | `du -sb /sf/log/*/ \| wc -l` = 954 | 必须按下标直取，不能全量扫描 |
| 工单目录名 = `Q` + 13 位数字，另存 `.bak` 后缀目录（如 `Q2025082701888.bak`） | `ls -la /sf/log` | 校验正则 `^Q\d{13}$`；`.bak` 必须拒绝 |
| 每个工单目录内**只有一个文件**：`<工单号>.zip` | `ls -la /sf/log/Q2026012500018` 仅 `Q2026012500018.zip` | 同步单位是**单文件**，不需要 rsync 目录树 |
| zip 内是**散文件**，不是单一子目录：`sp_<ip>.tgz`、`_members`、`cfgmaster_ini`、`log_list.json`、`collect_record.txt` | `unzip -l /sf/log/Q2026101301363/Q2026101301363.zip` | 解压根 `extract/` 是"日志根"，内层 tgz 再展开到其子目录 |
| **zip 内全部条目加密**（ZipCrypto），无密码无法读取任何文件，连 `collect_record.txt` 也读不到 | `zipinfo -v` 对 4 个抽样包（113M/989M/8.1G/5.5G）输出 `file security status: encrypted`，命中数 = 条目数 | **自动解压必须有密码来源**；无密码时需求 3 无法自动完成（见决策 D10） |
| zip 对主体 `sp_<ip>.tgz` 的压缩率仅 **4.4%**（118261906 / 123480748） | `unzip -v /sf/log/Q2026101301363/...zip` | zip≈tgz；解压可采用**流式管道**（`unzip -p \| tar -x`），不落中间 tgz |
| 存在坏包/占位包：`Q2025052718316.zip` 仅 **1 字节**，`Q2026081101509.zip` 332 字节 | `ls -la /sf/log/Q2025052718316/` | 解压前必须做完整性校验，坏包要给出独立错误码而非"解压失败" |
| **密码已验证可用**（运维统一密码，落 Secret）；解出的 tar 根为 `sf/`、`tmp/`、`etc/`，日志在 `sf/log/` 下 | `unzip -P <pwd> -p ... cfgmaster_ini` 输出 `[master] cfgmaster=...`；`tar -tz` 首行 `sf/log/boot.log` | 解压后路径是 `extract/sp_<ip>/sf/log/...`，Agent 需知道这一层前缀 |
| 递归到叶子后展开比在 **1.5x ~ 20x** 间跳变：7.0MB→139.8MB（**20.0x**）、302MB→≈2.9GB（≈10x）、51.3MB→≈300MB（≈6x）、118MB→0.813GB（6.9x）、965MB→1.44GB（1.5x） | 逐条目 `unzip -P ... -p <zip> <entry> \| tar -tzvf \| awk '{s+=$3}'` | 系数只能用于**事前粗筛**，放行判据必须是事中水位（D11） |
| 递归后**文件数**不可小视：302MB 包第一层即 **9257 个文件**，内部还有 **15 个压缩包**（最大 104MB 的 `LOG_cgroup.txt.zip`） | `find $d -type f \| wc -l`；`find ... -name '*.zip'` | 需要 `maxFiles` 上限与"已解文件数"进度；`file-reference-local` 的索引有 `maxEntries`，超限会截断（不崩但 Agent 找不到） |
| 抽样两包 **symlink = 0**，但日志包普遍含 `/var/log` 类链接，不能按 0 设计 | `tar -tzv \| grep -c '^l'` = 0 | 每层解压后必须扫描并删除逃逸链接（见 D4 边界） |
| 954 个工单中 >1G 有 449、>2G 有 288、>8G 有 56、**>20GiB 仅 5 个**（92.5G / 79.6G / 35.9G / 28.2G / 22.4G） | `du -sb /sf/log/*/ \| awk` 分桶统计 | 20GiB 上限只挡 0.5% 的工单，代价可接受 |
| 体积分布极不均匀：P10≈113M、P30≈381M、中位≈989M、P70≈2.5G、P90≈8.1G、**最大 93G**；0.2 总量 2.2T | `du -sh /sf/log/*/ \| sort -h` | 必须有容量上限、串行队列、可取消 |
| 0.4 根分区剩余 **746G**，`/sf/log` 与 `/` 同一 LV | `df -h / /sf/log` | 单机可承接，但 8 个 P90 包即占满，需保留策略 |
| DSH 容器内 **有** `tar`/`unzip`/`gzip`，**无** `ssh`/`scp`/`rsync`/`7z` | `kubectl -n hci-dsh exec deploy/dsh -c dsh -- sh -c 'command -v ...'` | 若同步在容器内执行，镜像必须补 `openssh-client`（+`rsync`） |
| `/sf/log` 以 **readOnly** 挂到容器 `/data/customer-logs` | `deploy/helm/hci-platform-dsh/templates/deployment.yaml:130-134` | 解压目录**绝不能**落在 `/data/customer-logs` |

| 镜像只装上游全局 npm 包 `@deepseek-ai/dsh@0.2.1-rc.2`，仓库**不自建任何 cordis 插件** | `dsh/Dockerfile:20-23` | 任何新增 UI 都必须自建插件包并打进镜像 |
| 首屏（无 session）只渲染 `conversation.hero.workspace` 与 `agentPreset`；`conversation.hero.options` 在 `sessionId === undefined` 时**不渲染** | `ui-conversation/.../ConversationContent.tsx:130` | 工单入口必须挂在 workspace 选择器链路上，不能靠 hero options |
| `conversation.hero.workspace.directoryFlow` 是 `single` 洞，**已被 browse 对话框占用** | `ui-workspace/src/client/contract/slots.ts:116-121` | 不能"再注册一个 occupant"，只能扩洞或扩菜单 |
| 上游 `ui-directory-picker-browse` **未导出** `DirectoryBrowser` 组件（exports 只有 `.`、`./client`、`./src/*`） | 该包 `package.json:15-32` | 无法在自己的 occupant 里复用现成浏览器 |

### 嵌套结构实测对照（决定解压深度的直接依据）

对 3 个不同工单做流式探测（`unzip -P <pwd> -p <zip> "sp_*.tgz" | tar -tz`），结果如下：

| 工单 | zip 内主体 | tgz 内结构 | 最终日志位置 | 层数 |
|---|---|---|---|---|
| `Q2026082001133`（7MB） | `sp_10.250.0.7.tgz` | **`cmd-output/log_slow_disk_*.tar.gz`** | `sf/data/local/raidlog/smartctl_info/<日期>/LOG_*.txt` | **3** |
| `Q2026082701130`（316MB） | `sp_172.28.33.130.tgz` | `sf/log/vn-blackbox/<日期>/...` | 同层 | 2 |
| `Q2026101400556`（53MB） | `sp_10.64.70.212.tgz` | `sf/log/kubelet/...`、`sf/log/10.tar.gz` | 同层 | 2 |

> **结论**：解压深度由**采集脚本**决定，是数据属性而非系统常量。若写死 2 层，`Q2026082001133` 这类工单会停在 `cmd-output/*.tar.gz`，Agent 拿不到 RAID 明细——而这类恰是慢盘/RAID 问题最需要分析的工单。

## 方案概述 (WHAT)

### 总体形态

```
浏览器 (DSH Web UI)
  │ ① 输入 Q2026xxxxxxxxx + zip 密码   ② 订阅进度流
  ▼
ticket-sync 客户端插件（新包 ui-ticket-sync）
  │ ③ ctx.remote.ticket.submit / follow
  ▼
ticket-sync 宿主插件（新包 host-ticket-sync，注册 namespace `ticket`）
  │ ④ 校验格式 → 入队（全局串行）
  ▼
TicketSyncer（可替换适配器，见 D1）
  ├─ HttpSyncer      0.2 只读静态服务 / 对方 HTTP 接口（推荐，见 D12）
  └─ SshRsyncSyncer  容器内 ssh+rsync（需镜像补包 + 注入私钥）
  │ ⑤ stat 探远端体积 → 容量预检 → /sf/tickets/<id>/pkg/<id>.zip 原子落地
  ▼
Extractor（密码来自密码来源，见 D10）
  ├─ ⑥a 密码预校验：解最小条目首字节，失败即 ticket/bad-password
  ├─ ⑥b zip → extract/（先校验条目禁止 .. 与绝对路径）
  └─ ⑥c 递归展开 extract/ 内所有压缩包（depth ≤ 4）：
          sp_<ip>.tgz、cmd-output/*.tar.gz 等逐条目 unzip -p | tar -x
          （流式管道，中间层不落盘；边解边统计水位，超限即中止）
  │ ⑦ extract/ 原子就位（rename）
  ▼
客户端 ⑧ onPicked(extract/) → 既有 owner 逻辑 createWorkspace + 开新会话
       （此后 workspace.path → session.header.cwd → prompt runtime context + 工具根，全部自动生效）
```

**关键分工**：DSH 侧只依赖一条事实——"给定合法工单号，`<工作根>/<id>/extract/` 最终出现完整目录"。同步的传输方式被收敛到一个适配器接口，**无论另一 agent 交付的是 HTTP 服务、宿主脚本还是 0.2 主动推送，都只替换适配器**。

### 存储布局（新增卷）

```text
宿主机 /sf/tickets/                    # hostPath，属主 1000:1000（必须宿主预置）
  Q2026101301363/
    pkg/Q2026101301363.zip             # 同步产物（.part 落盘后原子 mv；解压成功后可删）
    extract/                           # ★ 解压根 = Workspace Directory
      log_list.json                    # 清单：Agent 首轮索引就靠它
      collect_record.txt
      cfgmaster_ini
      _members
      sp_10.46.16.71/                  # ← tgz 展开后的明细日志（流式解出，中间层不落盘）
        var/log/...
      cmd-output/                      # ← log_slow_disk 型工单：此下 *.tar.gz 需继续递归解开
        sf/data/local/raidlog/...
    .state.json                        # 任务状态（供重进页面恢复；不含密码）
```

解压**完成后** `extract/` 才通过 `rename()` 出现在最终路径；在此之前只存在 `extract.tmp-<jobId>/`。因此 Agent 与 workspace 永远不会看到半成品。

容器内挂到 `/data/tickets`（**可写**）。与只读的 `/data/customer-logs`（即 `/sf/log`）严格分离：**读取源在 0.2，本地不写 `/sf/log`**。

### Remote 接口契约（`namespace: 'ticket'`）

```ts
/** 提交同步。幂等：同工单已有 running 任务时返回同一 jobId。 */
@Remote('submit') submit(request: {
  ticketId: string
  /** zip 密码；缺省回落到服务端默认密码，两者都无则立即 ticket/bad-password。只进内存，不落盘、不入日志。 */
  password?: string
}): Promise<{
  jobId: string
  phase: TicketPhase        // 返回时刻的阶段，通常 'queued'
}>

/** 密码预校验：在传输前确认密码可用，避免传完 1G 才发现解不开。 */
@Remote('verifyPassword') verifyPassword(request: {
  ticketId: string
  password: string
}): Promise<{ ok: boolean; reason?: 'no-archive' | 'archive-corrupt' }>

/** 订阅进度。首帧为当前阶段快照，随后增量，终态后正常关闭。 */
@Remote({ mode: 'stream' }) follow(jobId: string, signal: AbortSignal):
  AsyncIterable<TicketFrame>

@Remote('cancel') cancel(jobId: string): Promise<{ outcome: 'requested' | 'already-finished' }>

/** 页面重进时恢复：按工单号取最近一次任务与产物是否可用。 */
@Remote('inspect') inspect(ticketId: string): Promise<{
  job?: { jobId: string; phase: TicketPhase }
  extractedPath?: string    // 仅当 extract/ 完整就位
}>

/** 容量治理：列出本地已占用的工单与字节数（供 UI 提示与清理）。 */
@Remote('usage') usage(): Promise<{ tickets: { ticketId: string; bytes: number; lastUsedAt: string }[] }>

@Remote('remove') remove(ticketId: string): Promise<{ removed: boolean }>
```

帧类型：

```ts
type TicketFrame =
  | { kind: 'status';  phase: TicketPhase; startedAt: string }
  | { kind: 'log';     chunk: string }                       // 同步器/解压器输出，限长
  | { kind: 'progress'; bytes: number; total?: number }       // 有 total 时 UI 显示百分比
  | { kind: 'done';    extractedPath: string; bytes: number; durationMs: number }
  | { kind: 'failed';  code: TicketErrorCode; message: string }

type TicketPhase = 'queued' | 'verifying' | 'syncing' | 'extracting' | 'ready' | 'failed' | 'cancelled'
```

错误码（闭集，客户端只按 code 判别）：

| code | 触发条件 | 是否产生残留文件 |
|---|---|---|
| `ticket/invalid-id` | 不匹配 `^Q\d{13}$`（含 `.bak`、相对路径、超长） | 否 |
| `ticket/not-found` | 0.2 上无该工单目录或 zip | 否 |
| `ticket/too-large` | 远端 zip 超过 `maxTicketBytes`（默认 20Gi） | 否（先探大小再传） |
| `ticket/insufficient-storage` | 本地剩余 < zip × 预估展开系数（见 D11） | 否 |
| `ticket/bad-password` | 未提供密码，或密码预校验失败 | 否（预校验在传输前/解压前） |
| `ticket/archive-corrupt` | zip 结构损坏、条目数异常（如 1 字节占位包） | 否 |
| `ticket/space-exceeded` | 解压过程中水位超 `maxExtractBytes` 或剩余空间低于 `minFreeBytes` | 清 `extract.tmp-*`（保留 zip 以便重试） |
| `ticket/busy` | 串行队列已满（默认排队上限 3） | 否 |
| `ticket/sync-failed` | 传输失败/中断（附 stderr 尾部） | 清 `.part` |
| `ticket/extract-failed` | 条目含 `..`/绝对路径、解压非零退出 | 清 `extract.tmp-*` |
| `ticket/cancelled` | 操作者取消或连接断开超时 | 清 `.part` / `extract.tmp-*` |

### 状态机与并发

- 全局**串行队列**（并发 = 1）：带宽与磁盘是单机资源，两个大包并发只会互相拖慢且让容量不可控。
- 幂等键 = `ticketId`：已 `ready` 且 `extract/` 完整 → 直接返回既有路径（不重复传输）；`running` → 返回同一 `jobId`。
- 取消：`signal` 从 Remote 直达 `unzip`/传输进程，终止后清理 `.part` 与 `extract.tmp-*`；`extract/` 只在成功后由 `rename()` 原子就位，**半成品永不出现在 workspace 可见路径上**。
- Pod 重建：`/sf/tickets` 是 hostPath，产物保留；`.state.json` 里 `running` 状态在启动时一律降级为 `failed`（进程已死），由 `inspect` 引导重试。

### UI 落点

在"选择工作目录"的菜单里增加第二项，而不是另起入口（因为首屏只有这一个挂载点，见前置事实表）：

```
[ Workspace chip ▾ ]
  ├─ 已有工作区 A
  ├─ 已有工作区 B
  ├─ ＋ 添加工作区…            ← 既有（browse/native occupant）
  └─ ⇩ 从工单号同步…           ← 新增，打开本方案的对话框
```

对话框流程（单页，三段式）：

1. **输入**：工单号单行输入框（placeholder `Q2026012500018`）+ zip 密码框（`type=password`，可留空走服务端默认密码）。工单号在本地即时做格式校验（与服务端同一正则），非法时"确定"禁用并给出行内提示；密码不落 localStorage。
2. **进度**：确定后同一对话框切到进度态——阶段标签（排队/校验/同步/解压/就位）、`progress` 有 total 时显示百分比与已传字节、`log` 折叠区显示同步器尾部输出、"取消"按钮常驻。
3. **完成**：显示解压目录、文件数、耗时，自动调用 `onPicked(extractedPath)` 并关闭——owner 的 `adoptDirectory` 随即 `createWorkspace` 并把新会话 cwd 指向该目录（这是既有代码路径，零改动）。

失败走对话框**自身**的告警面（与既有 browse occupant 的约定一致：`flow.ts:24-32` "Browse failures stay inside the dialog's own alert surfaces"），不驱动 owner 的 `onError`。

| 卷 | 新增 hostPath `/sf/tickets` → `/data/tickets`（rw）；宿主机预置 `install -d -m 0750 -o 1000 -g 1000 /sf/tickets` |
| values | 新增 `tickets: { enabled, hostPath, mountPath, maxTicketBytes, maxExtractBytes, keepTickets }` |
| 凭证 | SSH 私钥走 Secret（`dsh-ticket-ssh`），仅 SshRsyncSyncer 需要；`HOME` 已可写，密钥落在 `/home/dsh/.ssh`（emptyDir，Pod 重建重播） |
| 隔离 | 同步/解压**不**进入 Agent 工具链，不占用 `ctx.shell` 的审批面；路径拼接前强制栅栏（见决策 D2） |
| CI | 复用既有 `dsh` 构建矩阵（`resolve_image_build_plan.py` 的 `OTHER_SERVICES` 已含 `dsh`），只改 Dockerfile 与构建上下文 |

## 决策依据（WHY）

### D1 为什么把同步抽象成适配器，而不是直接写死 ssh/rsync

同步功能由另一 agent 开发，其交付形态未知（容器内命令 / 宿主脚本 / HTTP 服务 / 0.2 主动推）。第一性原理上，本功能只依赖一个不可再分的事实：**目标目录最终出现完整文件**。因此把"怎么传"隔离在 `TicketSyncer` 单方法接口之后：

```ts
interface TicketSyncer {
  /** 把工单 zip 落到 destPath（绝对路径）；size 用于容量预检。 */
  fetch(ticketId: string, destPath: string, signal: AbortSignal): Promise<{ size: number; stderrTail: string }>
  /** 远端是否提供该工单与大小，用于在传输前快速失败。 */
  stat(ticketId: string): Promise<{ size: number } | null>
}
```

- 对方给 HTTP：实现 30 行的 `fetch` + `stat`，容器不需要 `ssh`/私钥。
- 对方给宿主脚本：容器内 `spawn` 该脚本。
- 对方给 0.2 推送：把 `fetch` 改成等待落盘事件（此时 `stat` 由本地文件大小代替）。

**不选**"直接在宿主插件里写死 `rsync -e ssh`"：一旦对方交付形态不同，改动会渗进队列/状态机/UI 三层。

### D2 为什么要服务端二次校验工单号，且必须"先校验再拼路径"

工单号会被拼进两条路径：远端 `/sf/log/<id>/<id>.zip` 与本地 `/sf/tickets/<id>/`。只做正则 `^Q\d{13}$` 是不够的推理终点——正则通过后仍需 `path.resolve` 后校验前缀：

```ts
const root = resolve(TICKETS_ROOT)
const dest = resolve(root, id)
if (dirName(dest) !== root) throw new RemoteError('ticket/invalid-id', ...)
```

理由：`\d` 在 JS 里只匹配 ASCII 数字，`.`/`/` 天然被排除，但**防御必须与攻击面同构**，而不是与当前正则的严格程度同构——将来有人放宽正则以支持别的前缀（如 `SR-`），前缀校验是唯一还站得住的栅栏。同理远端命令禁止用 shell 拼接（`argv` 数组直传，不经 `sh -c`）。

### D3 为什么解压目标必须是**新卷**，不能复用 `/work` 或 `/sf/log`

- `/work` = emptyDir 5Gi：中位工单（989M zip）解压后通常 2–5G，P70（2.5G zip）直接超限。`sizeLimit` 触顶时 kubelet 会驱逐 Pod，表现为"同步成功但页面突然 404"——这是最难排查的失败形态。
- `/sf/log` = readOnly 且属主 `support:support`：既不能写，写坏还会破坏整条日志回收链路（`values.yaml:140-146` 已明确这一风险）。
- 因此新增独立 hostPath `/sf/tickets`，与两者物理隔离，容量与权限各自独立。

**不选 PVC**：单节点 k3s 的 local-path 供给器同样落到宿主机目录，却额外引入 PV/PVC 生命周期与 `fsGroup` 传导风险（Pod 级 `fsGroup` 会波及只读的 `/sf/log`，`deployment.yaml:31-33` 已明确拒绝）；hostPath + 宿主预置属主是本场景最小方案。

### D4 为什么必须递归解到叶子，而不是停在第 2 层

- **为什么必须解开压缩层**：`file-reference-local` 的 `@` 索引与 `read`/`grep` 只作用于**目录树**，压缩包内部对 Agent 完全不可见。不展开，Agent 就得先写一条 `tar -xzf` 再猜路径，每次会话重复一遍；展开后明细日志成为 cwd 下的普通文件，`log_list.json` 里列出的每条路径都能在磁盘命中（**注意反向不成立**：递归后磁盘文件数多于清单，清单只覆盖采集项的顶层）。
- **为什么不落中间层**：实测 zip 对 `sp_*.tgz` 压缩率仅 4.4%（≈等身），先解开 tgz 再解 tar 会让峰值变成 `zip + tgz + 内容`。用 `unzip -p <zip> <entry> | tar -x -C <dest>` 管道后峰值降为 `zip + 内容`，对大包直接省掉一份 93G 级中间态。递归时同一策略逐层套用。
- **必须逐条目循环解，不能用通配**：实测 `unzip -p <zip> '*.tgz' | tar -x` 在多 tgz 包里会把多个归档串接进同一条管道，tar 在**第一个归档的 EOF 标记处即退出**，后续 tgz 被静默丢弃（989M 样本：通配只得到 0.62GB，逐条目才是 0.62+0.82=1.44GB）。实现必须 `for entry in $(unzip -Z1 <zip> | grep '\.tgz$')` 逐个管道，并在结束后校验"已解条目数 == zip 内 tgz 条目数"，否则报 `ticket/extract-failed` 而不是交付残缺目录。**递归的每一层都要套用这一条**，不能只在第一层做。
- **为什么不能停在 2 层（修正 v0.4 的结论）**：v0.4 以"递归会把空间与时间放大到无法预估"为由锁死 2 层，把剩余嵌套交给 Agent 按需处理。该权衡在三份实测样本前不成立：
  1. **功能残缺**：`Q2026082001133` 的 tgz 内是 `cmd-output/log_slow_disk_*.tar.gz`，停 2 层时 `extract/sp_10.250.0.7/` 下只有一个 `.tar.gz`，`sf/data/local/raidlog/` 不存在。Agent 虽能自己解，但每个会话都要重做，且 `log_list.json` 记录的路径与磁盘对不上，首轮索引必然走空。
  2. **失败是静默的**：2 层结构的工单（`Q2026082701130`、`Q2026101400556`）完全正常，只有 `cmd-output` 变体残缺。这种"多数正常、少数残缺"的形态在验收时极难被发现，而它恰好落在慢盘/RAID 这类最需要日志的工单上。
  3. **空间担忧已被 D11 覆盖**：递归的真实风险是总量不可预估，而 D11 已实现**事中水位监控**（每 2s 采样，超 `maxExtractBytes` 或低于 `minFreeBytes` 立即中止并清理）。既然有事后可中止的硬保护，就不必用"不递归"来换取可控性——那是用功能残缺换心理安全。
- **递归边界如何收敛**：深度上限 4（已知最深样本 3 层，留一层余量）；只解 `.zip/.tar.gz/.tgz`，其余类型原样保留；每层独立做路径穿越校验；每层解开后统计"新增压缩包数"，为 0 即收敛。`sf/log/10.tar.gz`、`LOG_ping_statistic.txt.zip` 这类日志轮转包也会被解开，属预期行为。
- **递归的代价**：解压时间随层数上升，但实测源端传输仅 45~51 MB/s，**传输是主耗时，解压不是瓶颈**（0.2 本地顺序读实测 5 GB/s，瓶颈在网络/加密而非磁盘）；需为每层记录 `unpacked_bytes`，供 D11 第 3 条护栏事后校准 `expansionFactor`。
- **每层必须做的两件清理**（v0.6 补充）：① **symlink 扫描**——tar 会原样创建链接，`../../` 或绝对路径链接可让 Agent 读到 workspace 之外，解完每层后 `find -type l` 并删除 `realpath` 落在 `extract/` 之外的链接；② **文件数累计**——递归会把文件数放大一个量级（实测 302MB 包第一层已 9257 个），超 `maxFiles`（默认 5 万）即 `ticket/too-many-files` 并回滚，避免把节点 inode 与 `file-reference-local` 的索引预算一起打穿。

**不选**"解压后删除 zip"作为默认：保留 `pkg/*.zip` 让失败重试与 Pod 重建后的重解都无需重传（93G 重传是不可接受的代价），只在容量治理时由操作者显式清理。

### D5 为什么入口必须"扩菜单"而不是"新增 occupant"

`conversation.hero.workspace.directoryFlow` 是 `single` 洞（`slots.ts:116-121`），且已由 `ui-directory-picker-browse` 占用；DSH 的洞语义是"一个洞只能有一个声明方/占用方"，第二个 occupant 会 loud fail。可选路径只有三条：

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A 扩菜单 + 新增 sibling 洞 | 改 `WorkspacePicker` 增加一项；我们的包占用新洞 | fork 内约 60 行 diff | **采用** |
| B 自家 occupant 取代 browse | 让我们的对话框独占原洞，自己实现目录浏览 | 上游未导出 `DirectoryBrowser`（`package.json:15-32`），需重写 50KB 级 Miller-column 浏览器 | 不选：重复造轮子且行为难对齐 |
| C 挂 `conversation.hero.options` 按钮 | 零上游改动 | 该洞在 `sessionId === undefined` 时不渲染（`ConversationContent.tsx:130`），而"输入工单号"恰恰发生在首屏无会话时 | 不选：不满足需求 1 的场景 |

方案 A 的 diff 被刻意压缩到 3 个文件、一个菜单项、一个 declare，是为了让上游从 `0.2.1-rc.2` 升级到后续版本时的冲突面最小；fork 侧维护 `PATCHES.md` 记录每处改动与上游对应锚点。

### D6 为什么"提交即返回"，而不是等同步完成再响应

93G 的极端包在千兆内网下单传输就 ≥13 分钟，P90（8.1G）约 1–2 分钟。任何同步等待式 HTTP 都会被网关超时切断（当前 nginx sidecar 默认 `proxy_read_timeout` 60s）。因此：一元 `submit` 只做校验与入队（毫秒级返回），进度走 `@Remote({mode:'stream'})`（与既有 `job.follow` 同构，天然支持断线重订阅），状态以 `.state.json` 持久化以便重进页面恢复。

### D7 为什么 workspace 目录选在 `extract/`，而不是 `<id>/`

`unzip -l` 已证实 zip 内是散文件而非单一目录。若把 `<id>/` 设为 workspace，Agent 首屏会看到 `pkg/`（压缩包）与 `extract/`（内容）两个兄弟目录，需要在提示里额外解释"去 extract 里找"；直接指向 `extract/` 则让 `log_list.json` 位于 cwd 根，`@` 文件补全与 `read` 工具的默认根都落在正确位置。这也符合 DSH 的既有语义：**workspace 路径 = 权限根 + 工具 cwd + 索引根**（`packages/workspace/workspace/README.md`、`file-reference-local` 均以 session cwd 为根）。

### D8 容量治理：为什么必须有上限与保留策略

剩余 746G、单包最大 93G、总量 2.2T。没有上限时，任何人连点 8 个 P90 工单就能把节点写满，进而让 k3s（同分区）与 `/sf/log` 一并受损。因此三层护栏：

1. **传输前**：`stat` 探远端大小，> `maxTicketBytes`（默认 20Gi）直接 `ticket/too-large`；
2. **传输前**：本地剩余 < 预估解压量（`zip × 21`，见 D11 的 20x 上界）→ `ticket/insufficient-storage`；
3. **就位后**：按 `lastUsedAt` 保留最近 `keepTickets`（默认 3）个，超出的由 UI 显式确认后 `remove`（**不自动删**——`packages/workspace/workspace/README.md:79` 的原则：注册不确立所有权，删除必须单独命名并明确确认）。

### D9 可观测性设计

| 维度 | 设计 |
|---|---|
| 链路 | 每次 `submit` 生成 `trace_id`（`crypto.randomUUID()`），贯穿 syncer → extractor → 就位；日志字段固定 `trace_id/ticket_id/job_id/phase`，与平台既有"唯一调用链"要求对齐 |
| 日志 | 结构化 JSON 写 stdout（由 `kubectl logs` / Loki 采集）；`log` 帧额外转发给浏览器，形成"操作者可见 + 平台可查"两条路径 |
| 指标 | P1：`dsh_ticket_jobs_total{result}`、`dsh_ticket_phase_seconds{phase}`、`dsh_ticket_bytes_total`。当前 chart 未暴露 `/metrics`，先以日志聚合替代，指标端点作为后续项（不在本期验收内） |
| 失败可诊断 | 每条失败都携带 `code` + 可操作 message（含远端 stderr 尾部 ≤ 4KB），避免"同步失败"这类无信息提示 |

### D10 密码：这条需求原本隐含的阻塞点

实测结论：抽样的 4 个工单包（113M / 989M / 8.1G / 5.5G）**全部条目加密**，`zipinfo -v` 输出 `file security status: encrypted`，`unzip -p` 连 `collect_record.txt` 都拒绝读。也就是说"同步后自动解压"在无密码时**必然失败**，这是原需求里没有写出、但决定成败的前提。

密码来源按优先级：

| 优先级 | 来源 | 适用场景 | 落地方式 |
|---|---|---|---|
| 1 | 操作者在对话框输入 | 一单一密 | `submit({ password })`，只驻留内存 |
| 2 | Secret `dsh-ticket-archive` 的 `defaultPassword` | 客户统一密码 | 服务端回落，UI 密码框可留空 |
| 3 | 同步适配器回传 `passwordHint` | 另一 agent 能从工单系统取到 | 扩展 `stat()` 返回值，UI 预填（仍可改） |

安全约束（对抗性审查后的硬要求）：

- 密码**不写** `.state.json`、**不进** `log` 帧、**不进** trace 字段、**不回显**在错误文案里。
- 优先用进程内库（如 `yauzl` 的 ZipCrypto 支持）传密码，避免 `unzip -P <pwd>` 把密码暴露在容器进程 `argv`（同 Pod 的 nginx sidecar 与任何 `exec` 都能看到）。
- 若只能用 `unzip -P`，则在文档与排障手册里明确该残留风险，且 Pod 内禁止再增容器。
- 密码错误限流：同工单连续 5 次失败 → 60s 冷却（ZipCrypto 对已知明文攻击本就脆弱，不能提供在线爆破通道）。

### D11 空间：为什么必须"事中水位监控"而不是"事前精确预估"

事前能拿到的只有 zip 大小与各条目 `uncompressed size`；而主体 `sp_*.tgz` 的 `uncompressed size` 就等于 tgz 自身大小（压缩率 4.4%，几乎不压），**tgz 真正展开多大只有解过才知道**。因此三层护栏：

**递归到叶子后，系数不再是 8x**（v0.6 修正）：五份实测样本的"zip → 全部解到叶子"比值在 **1.5x ~ 20x** 之间跳变，取决于采集脚本与日志的压缩特性：

| 工单 | zip | 解到叶子后的总量 | 比值 | 依据 |
|---|---|---|---|---|
| `Q2026082001133` | 7.0 MB | **139.8 MB**（L1 9.6MB + L2 139.8MB/63 条目） | **20.0x** | 慢盘采集包：内部再包一个高压缩比 tar.gz |
| `Q2026082701130` | 302 MB | **≈2.9 GB**（L1 1.92GB/9257 文件 + 15 个内部包再解 ≈1GB） | **≈10x** | 一级几乎不压（6.4x），内部 15 个 `.zip`（最大 104MB）再放大 |
| `Q2026101400556` | 51.3 MB | ≈300 MB（L1 140MB/3652 文件 + 3 个包再解） | ≈6x | |
| `Q2026101301363` | 118 MB | 0.813 GB（无内部包） | 6.9x | 2 层即叶子 |
| `Q2026052700688` | 965 MB | 1.44 GB（无内部包） | 1.5x | 2 层即叶子 |

因此参数改为"**绝对上限 + 动态水位**"，而不是"zip × 固定系数"：

| 参数 | 取值 | 依据 |
|---|---|---|
| `expansionFactor` | **20** | 递归实测上界；仅用于**事前粗筛与 UI 预估**，不作为放行判据 |
| `maxTicketBytes` | **20 GiB** | 不变：954 个工单中仅 5 个超限（0.5%） |
| `maxExtractBytes` | **动态**：`min(400 GiB, free_initial − minFreeBytes)` | 写死"zip×8=160GiB"会在 20GiB 工单（实际 ≈400GiB）**解到一半失败**，白等整个传输 |
| `minFreeBytes` | **60 GiB** | 不变 |
| `keepTickets` / `maxTotalBytes` | 3 个 / **400 GiB** | 不变；注意它必然拦住"3 个大包"的组合，淘汰时按 `lastUsedAt` 优先删最旧而非最大 |

三层护栏：

1. **事前**：`required = zip × (1 + 20)`（保留压缩包 + 按上界预估展开）；要求 `free − required ≥ minFreeBytes`，否则 `ticket/insufficient-storage`；`zip > maxTicketBytes` 即 `ticket/too-large`，**传输前拒绝**。这一层只做粗筛——它挡的是"明显装不下"，不是"精确判定"。
2. **事中**（**唯一可靠的判据**）：每 2s 采样 `extract.tmp-*` 体积与分区剩余；超 `maxExtractBytes`（动态，见上表）或剩余低于 `minFreeBytes` 立即中止、清理并 `ticket/space-exceeded`（保留 `pkg/*.zip` 供重试）。
3. **事后**：把实测展开比回写 `.state.json`，后续同工单重解时用实测值替代 20x（自我校准）。

**容量校验（按当前 746G 剩余）**：

- 最坏可处理工单 20GiB → 需要 420GiB，746 − 420 = 326GiB ✓（仍高于 60GiB 红线）；
- 3 个 P90（8.1G × ≈10x ≈ 81GiB each ≈ 243GiB）✓；
- 3 个 20GiB（≈1.26TB）✗ —— 由 `maxTotalBytes = 400GiB` 拦住，UI 提示先清理；这是"双约束"存在的意义。

**代价要说清**：20GiB 上限会拒绝那 5 个工单（含 92.5G）。这类包解开约 740G，在当前 746G 剩余空间上**物理不可行**——不是参数保守，而是硬约束。人工通道：由运维临时把 values 里的 `maxTicketBytes` 调高并重启 Pod，或用 Agent 的外部通道单独分析。

### D12 同步形态：为什么推荐 HTTP 而非 ssh/rsync

| 判据 | HTTP 只读静态服务 | ssh + rsync |
|---|---|---|
| 体积预检 | `HEAD` 一次拿 `Content-Length`，天然支持 | 需 `ssh stat` 或 `rsync --dry-run` 多一跳 |
| 断点续传 | `Range` 原生支持（93G 中断续传必需） | `rsync --partial` 可行 |
| 凭据暴露面 | 无凭据，可加 IP 白名单 | 私钥必须落容器卷，`exec` 即可取走 |
| 镜像依赖 | 零改动（Node `fetch`） | `apk add openssh-client`(+`rsync`)，镜像 +10MB |
| 0.2 侧改动 | **nginx 已安装**（`/usr/sbin/nginx`，当前未监听 80）；8080/8081/80/443 均空闲，新增一个只读 `server` 块即可 | 无需改动（SSH 已在 22468） |

结论：**首选 HTTP**（0.2 上只读静态服务）；若安全策略禁止新开端口，退回 ssh/rsync 并把私钥走 Secret + 固定 `known_hosts` 指纹。两者都实现 `TicketSyncer`，由 `tickets.syncer: http|ssh` 切换。

0.2 侧 nginx 只读 server 块的硬要求（已确认 nginx 已安装、8080/8081 空闲）：

```nginx
server {
  listen 8081;                      # 80/443/8080 均空闲，任选；建议不占 80
  allow 192.168.0.4;                # 只允许 0.4（k3s 节点）
  deny all;
  autoindex off;                    # 关闭目录列表，只能按精确 URL 取
  root /sf/log;                     # 精确路径 = /<ticketId>/<ticketId>.zip
  location ~ ^/(Q\d{13})/\1\.zip$ {  # 只放行工单包，其余一律 403
    add_header Accept-Ranges bytes; # 断点续传（nginx 默认已支持 Range）
  }
  limit_rate 100m;                  # 可配置：避免 93G 传输打满内网影响生产
}
```

`location` 的正则把可访问面收敛到"工单号与文件名必须一致"，即使 URL 编码/路径穿越也不越界——这与应用侧的 `^Q\d{13}$` 栅栏是两道独立防线（一道在网络层，一道在业务层）。

### D13 备选路径：若 fork 冲突不可控，可用「外壳入口 + 零 fork 插件」

主线选择 fork（见 D5 方案 A），理由是入口要长在 DSH 自己的 workspace 菜单里。但 fork 的代价是每次上游升级都要重放 patch（DSH 仍处 `0.2.1-rc` 快速迭代期）。若冲突成本超过承受阈值，有一条**零 fork 退路**：

| 维度 | 主线（fork + 扩洞） | 退路（零 fork） |
|---|---|---|
| 入口位置 | DSH workspace 菜单第二项 | `admin-ui`「DSH诊断」页顶部操作条 |
| 插件职责 | 注册 slot occupant + 对话框 | 仅监听 `postMessage` 并调 `remote.workspace.create({ path })` |
| 上游改动 | 3–4 文件约 60 行 | **0 行** |
| 跨 iframe 通道 | 不需要 | `postMessage`（`/admin/` 与 `/dsh/` **同域同端口，属同源**）+ `event.origin` 校验 |
| slot 占用 | 占新洞 | 不占任何洞，天然避开 `directoryFlow` 单例冲突 |

退路的前提事实（容器内实测）：存在 `dsh-client-ui-workspace`（含 `contract/slots.d.ts`、`WorkspacePicker.d.ts`），`WorkspacePickFlowProps.createWorkspace` 签名确认为 `(input: { path: string }) => Promise<WorkspaceView>`，且 `dsh-api-workspace-controller` 提供 `ctx.remote.workspace` namespace——**"程序化把目录注册为 workspace"是官方接缝，两条路径都成立**。

结论：主线不变（体验更原生），但把零 fork 退路写入方案，避免将来被 fork 维护成本逼到无路可走。

**两条必须说清的前提（v0.6 修正）**：

1. **"零 fork" ≠ "零插件"**：`ctx.remote.workspace.create` 是 DSH 进程内的 cordis 服务，admin-ui 的 `postMessage` 无法直接触达它——必须有一个**极小的 host 插件**在 DSH 内接收转发。镜像仍要装我们的包，只是**不维护上游 patch**。退路的真实形态是"0 行上游 diff + 1 个约 200 行的插件"，不是"什么都不用改"。
2. **D13 不能单独成立**：外壳入口只解决"把路径变成 workspace"，同步与解压能力仍要靠 D14（api-gateway 承担）。**D13 + D14 组合才是完整退路**；只上 D13 会得到一个"能登记目录但没有目录"的空壳。

### D14 同步执行者：可下沉到平台 api-gateway，避免镜像加装 ssh

主线把同步放在 DSH 容器内（`SshRsyncSyncer`），代价是镜像要 `apk add openssh-client`，且私钥要挂进 Agent 所在 Pod——**Agent 本身具备 shell 能力，等于把私钥暴露给被分析对象的同一执行环境**。

替代做法（若安全评审认为私钥不应进 DSH Pod）：由平台侧 `api-gateway` 承担传输与解压，`TicketSyncer` 增加第三种实现 `GatewayApiSyncer`（HTTP 调用平台接口），DSH 侧只等待产物出现在 `/sf/tickets/<id>/extract`。

| 维度 | 容器内（主线） | 平台侧（替代） |
|---|---|---|
| 镜像依赖 | 需 `openssh-client`(+`rsync`) | 零新增（`asyncssh==2.14.2` 已在 api-gateway 依赖中） |
| 私钥位置 | DSH Pod（Agent 同环境） | api-gateway Pod（与 Agent 隔离） |
| 跨命名空间 | 不涉及 | `hci-staging` ↔ `hci-dsh`，hostPath `/sf/tickets` 双挂载（单节点可行） |
| 适配器改动 | 已支持 | 新增 `GatewayApiSyncer`，队列/状态机/UI 全不变 |

因 D1 已把"怎么传"隔离在 `TicketSyncer` 之后，两种选择**不改变本方案其余全部设计**。建议 S1 先实现 `LocalFileSyncer`，S3 时按安全评审结论二选一。

**D14 落地前必须定的一个坑（v0.6 补充）**：`/sf/tickets` 双挂载时，**写入方与读取方的 UID 必须一致**。DSH 以 UID 1000 运行，且本 chart 刻意不设 `fsGroup`（为保护只读 `/sf/log` 的属主），若 api-gateway 以其他 UID 写产物，DSH 侧读 `extract/` 会 `EACCES`。两种可行做法：① api-gateway 侧也以 1000 运行；② 宿主目录 0770 + 双方共属一个附加组（`supplementalGroups` 只作用于该 Pod，不影响 `/sf/log`）。**不要用 0777 抹平**——那等于让集群里任何 Pod 都能篡改日志产物。

## 开发与验证回路（v0.8）

之前把"验证"绑在「建镜像 → 部署 → 人点页面」上，一次几十份钟；而绝大多数缺陷
（解压布局、水位、帧流、密码绑定、容量口径）都是纯逻辑问题，本应在**秒级**暴露。
把反馈环按改动范围拆成五层，每条改动只走最短的一条：

| 层 | 触发场景 | 命令 | 反馈时间 | 覆盖 |
|---|---|---|---|---|
| L1 纯逻辑 | 改 `src/*.ts`（extractor/syncer/queue/index） | `pnpm test:ticket:watch`（常驻） | **<1s** | 三层解压布局、无残留归档、symlink 拒绝、水位越界、帧流滑窗、容量口径 |
| L2 UI | 改 `*.tsx` / locale / 洞声明 | `pnpm dev:web --skip-build`（常驻）+ `pnpm verify:ticket-ui` | 重建 ~40ms，冒烟 5s | 菜单入口、对话框、工单号格式校验 |
| L3 类型/契约 | 改 Remote 动词或类型 | `npx tsc -b packages/api/ticket-sync/tsconfig.host.json` | 秒级 | typert 生成与客户端调用面 |
| L4 配置 | 改 Helm/patch 文件 | `helm template t deploy/helm/hci-platform-dsh` | <1s | values 注入、env、卷、策略 |
| L5 镜像 | 仅发布前 | CI `build-and-push` | 分钟级 | 运行时依赖（unzip）、整仓构建 |

**让 L1/L2 成立的四个前提（已落地）：**

1. **依赖注入**：`ExtractDeps` 收敛了 `run / freeBytes / measure / spawn` 四个外部依赖。
   测试可以注入"剩余空间只有 1 字节"或"命令不存在"，不需要真的写满盘或等 90 秒。
2. **fixture 工厂**：`tests/fixtures.ts` 在 `beforeAll` 里生成一次加密包（三层嵌套 /
   symlink / 损坏包），多个 spec 复用，避免每个用例都调 `zip`。
3. **无头浏览器冒烟**：`scripts/verify-ticket-ui.mjs` 用已安装的 chromium 打开
   `dev:web`，点 workspace chip → 断言菜单项 → 打开对话框 → 断言按钮禁用/启用，
   5 秒给出红绿，替代"人点页面"。
4. **测试不绑镜像**：镜像只承担"运行时依赖存在性"门禁（Dockerfile 在构建阶段
   跑该包测试，运行阶段显式 `apk add unzip`），逻辑回归一律在宿主机完成。

常驻两条命令即可覆盖 95% 的改动：

```bash
pnpm dev:web --skip-build        # 终端 A：tsc/tsdown/vite 三个 watcher + dsh web
pnpm test:ticket:watch           # 终端 B：保存即回归
pnpm verify:ticket-ui            # 需要时跑一次 UI 冒烟（5s）
```
