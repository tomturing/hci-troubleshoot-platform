## 一、巨文件二拆

### 1.1 切分依据：职责边界，不是行数等分

| 文件 | 拆分前 | 拆分后 | 边界 |
|---|---|---|---|
| `logcollect/log_collect.go` | 1613 | 702 + `log_collect_probe.go` 939 | **编排 vs 问节点**：`HandleLogCollect` 与失败归因留在原文件；命令构建、环境/专项探测、progress 与 help 解析、归档存在性归 probe |
| `delivery/delivery_runner.go` | 1926 | 968 + `delivery_transfer.go` 991 | **调度 vs 搬字节**：队列、租约归属、阶段推进、错误分类留在原文件；等采集、包归属校验、源包摘要、拉取、分片上传、完成回执、证据采样归 transfer |

### 1.2 零丢失校验

```
log_collect.go      函数数 28 → 28（702 + 939）
delivery_runner.go  函数数 59 → 59（968 + 991）
```

拆分方式为**逐字移动**（同一 `package`、同一 import 集合起步，编译后按未用报错裁剪），不重命名、不改函数体、不调控制流。因此：

- 18 + 81 例测试原样通过，未改任何断言；
- `go test ./...`、`-race`、双 tag、双 GOOS 全绿；
- `git diff` 表现为纯新增文件 + 原文件行数收缩，可逐块核对。

### 1.3 为什么不再往下拆

`HandleLogCollect` 单函数仍有 600+ 行，但它是一条**线性状态机**（create → 接单确认 → 轮询 → 上传 → 收尾），每段都读写同一组局部变量（taskID、节点、进度、票据）。继续拆函数需要把这些状态显式传参或收进结构体，属于"重构状态机"而非"拆文件"——风险与收益比不适合和纯移动混在一个 PR 里。

已有的收益（改动时不必在 1600/1900 行里定位）已经拿到。

## 二、部署口径订正

### 2.1 新旋钮入契约

`HCI_BRIDGE_LOG_OUTBOX_MAX_BYTES`（直传 outbox 磁盘预算，默认 8 MiB，超限 drop-oldest）此前只在代码与 README：

| 落点 | 改动 |
|---|---|
| `deploy/config/config-contract.yaml` | 登记 `helm_only_runtime` |
| `deploy/helm/hci-platform/values.yaml` | `terminalBridge.logOutboxMaxBytes: "8388608"` |
| `deploy/helm/hci-platform/templates/terminal-bridge/deployment.yaml` | 注入 env |

**为什么 values 用字符串**：Helm 渲染数字会得到 `8.388608e+06`，进程读到非整数。字符串 + `| quote` 与既有 `logFileMaxBytes` 保持一致。

`verify_config_contract.py` 通过（业务配置 125 / Helm 内部运行时变量 111 / values 路径引用 338）。

### 2.2 被 L1 推翻的旧口径

`docs/solution/events/2026-11-17-云端桥日志直传补全.md` 曾写"默认只扫 2 个文件、最多 5000 条"。L1 之后 `DefaultSeedMaxFiles/Entries` 是**单轮预算**：扫描范围是全量文件（含轮转件与当前文件），预算用尽记进度、下一轮继续。

处理：保留原记录（历史事实），追加"订正"标注；Helm values 的注释同步改为单轮预算语义。

### 2.3 #1586 的 27 条失效引用

`python3 scripts/ci/check_docs_rot.py --dir docs/plans` 显示 `2026-11-18-节点同步链路统一收口设计.md` 的 32 处旧路径**全部为"删除事实记录"语境豁免**（脚本识别到邻近否定语义词），无阻断项。结论：该债务在 #1586 合并时已消解，本次仅做复核留痕。
