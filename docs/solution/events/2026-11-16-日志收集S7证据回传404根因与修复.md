# 2026-11-16 日志收集 S7 证据回传 404 根因与修复

## 一、问题定性

用户反馈工单 `Q2026111600403` / `Q2026111600725`「日志服务器已上传成功，但面板 S7 显示失败、结论为有疑点」。

按第一性原理拆三层事实：

| 层次 | 事实 | 证据 |
|---|---|---|
| 交付事实 | 日志包已到日志服务器并通过核验 | `delivery_status=delivered`、`p1_check.verified=true`、`archived_size == expected_size`、`delivery_evidence=archive_verified` |
| 证据事实 | S7 证据回传全部失败，四张证据表全库 0 行 | `log_collect_artifact_manifest` / `log_collect_transfer_metric` / `log_collect_network_probe` / `log_collect_process_log` 行数均为 0 |
| 展示判据 | `quality=unknown` → `_conclusion()` 只能给 `partial`，`_build_stages()` 置 `S7=failed` 并挂 `LC-BRIDGE-005` | `backend/case-service/app/domain/log_collect_display.py` |

**结论：不是采集失败、不是上传失败、不需要重新收集。** 包内容清单（manifest）没有回传，平台无法证明「包里有日志」，因此只能显示「已交付 · 有疑点」。

## 二、全量影响面

staging 库 `hci_troubleshoot` 取证（2026-11-16）：

- 近 30 天 `delivery_status=delivered` 的工单 **181 个**，其中有 manifest 的 **0 个**；P1 `acli_direct` 72 个、P2 `bridge_relay` 109 个，**两种上传模式全部中招**。
- 四张证据表**全库 0 行**（不是近 30 天为 0，是建表以来从未写入成功）。
- `bridge_execution_logs` 中 404 事件时间分布：11-14（4 工单 / 1326 事件）、11-15（1 / 134）、11-16（14 / 4191），涉及 `artifact_manifest_failed`、`metric_failed`、`network_probe_failed`、`node_manifest_failed`、`process_log_failed` 五类。
- 与 `#1490` 引入证据数据面的时间吻合：此前桥不上报证据，故无 404 事件；上线后上报即 404。

## 三、根因与定责

### 3.1 隔离实验（先定责再修）

同一路径 `POST /api/direct/log-collect/tasks/{task_id}/metrics` 分别直打两个服务：

```
api-gateway:8000 → 404 {"detail":"Not Found"}
case-service:8001 → 422 {"detail":[{"type":"missing","loc":["body","seq"],...}]}
```

- 404 响应体是 FastAPI 默认格式，说明请求到达了一个 FastAPI 服务，但该服务没有注册此路由。
- case-service 返回 422（字段校验错误），说明路由存在且已注册（`backend/case-service/app/main.py` 中 `app.include_router(log_collect_evidence.router)`）。
- 桥日志原文：`证据上报 HTTP 404: {"detail":"Not Found"}` —— 与 api-gateway 返回值逐字一致。

### 3.2 配置缺口

`deploy/helm/hci-platform/templates/ingress.yaml` 与 `deploy/helm/hci-platform/templates/admin-ui/ingress.yaml` 中，数据面直连规则**只覆盖了** `/api/direct/log-collect-uploads`（分片上传），没有覆盖证据数据面 `/api/direct/log-collect/`。

Ingress 按最长前缀优先匹配：

- `/api/direct/log-collect-uploads/...` → 命中专属规则 → case-service（分片上传一直正常，这解释了为什么交付成功）。
- `/api/direct/log-collect/tasks/...` → 没有专属规则 → 被 `/api` 泛前缀吃掉 → api-gateway。
- api-gateway 只代理 `/api/log-collect/tasks{path:path}`（`backend/api-gateway/app/routes/log_collect.py`），没有 `/api/direct/log-collect/...`，于是返回 404。

### 3.3 责任边界

| 组件 | 判定 | 依据 |
|---|---|---|
| 客户侧 terminal_bridge | **无缺陷** | 按契约构造 `/api/direct/log-collect/tasks/{id}/...`，票据、TLS 放宽均正常；x509 不受信时已自动 `evidence_tls_relaxed` 并重试成功到达对端 |
| case-service | **无缺陷** | 路由已注册，直连返回 422 而非 404，证明端点可达 |
| api-gateway | **报错者，但非缺陷引入方** | 它忠实返回 404，因为确实没有该路由；证据数据面设计上就绕过网关（进程日志 gzip 正文可达 2 MiB，超过网关 1 MiB 上限），网关本就不该承载它 |
| Helm ingress 配置 | **缺陷引入方** | `#1490` 加证据数据面时只补了 case-service 路由与 `main.py` include，漏了 ingress 直连规则 |
| 契约文案 | **次要缺陷** | `LC-BRIDGE-005.admin_detail` 把原因写成「x509 或旧桥」，与本次 404 事实不符，会误导后续排查 |

## 四、修复内容

1. `deploy/helm/hci-platform/templates/ingress.yaml`：在 path 路由模式末尾追加 `/api/direct/log-collect/` → case-service 直连规则。
2. `deploy/helm/hci-platform/templates/admin-ui/ingress.yaml`：host / 无 host 两个分支各追加同样规则（管理域名的 `/api` 在 internal 模式下会被 admin-ui Nginx 代理，证据路径必须显式绕开）。
3. 路径带尾斜杠 `/api/direct/log-collect/`，与 `/api/direct/log-collect-uploads` 零重叠；追加在末尾，保持既有 `paths[i]` 索引不变。
4. `contracts/log_collect_display.json`：修正 `LC-BRIDGE-005.admin_detail` 与 `evidence`，把「ingress 漏配 → 网关 404」列为第一排查项，并重新生成 7 份契约产物。
5. 新增 helm unittest 测试 `deploy/helm/hci-platform/tests/evidence_ingress_test.yaml` 与 `deploy/helm/hci-platform/tests/evidence_admin_ingress_test.yaml`，锁死两个 ingress 的证据数据面路由。

**不做的事**：不改现场 5888（它只接收日志包，与证据数据面无关）；不改 api-gateway 增加证据代理（违反「绕过网关」的设计约束，且 1 MiB 上限会截断进程日志）；不为存量工单伪造 manifest 数据。

## 五、验证

- `helm unittest deploy/helm/hci-platform`：21 suite / 90 例全通过（含 3 个新增断言场景）。
- `helm template` 渲染确认：客户域名与管理域名两个 Ingress 均渲染出 `/api/direct/log-collect/` → `case-service`。
- `scripts/gen_log_collect_display.py --check`：契约生成物一致。
- `scripts/verify_log_collect_contract.py`：契约 v3，codes=91 / matchers=63 / 有序补码=85，唯一出处门禁通过。
- 隔离实验：api-gateway 404 / case-service 422，定责证据闭环。
- **待部署后验证**：合并 → staging 晋级 → hard refresh → 新工单触发证据上报 → 四张证据表出现新行 → 面板 S7 转成功。

## 六、存量工单的边界

修复只对**新下发**的采集任务生效：证据上报在 `create` 时由 `configureEvidence()` 初始化，是一次性动作，已完成的任务不会自动补传。

- 存量 181 单的 S7 仍会显示失败 / partial，这是**事实正确的展示**（证据确实没回传），不应通过伪造 manifest 把它改成 success。
- 如需存量工单的完整包内容清单，只能重新收集，或由后续专门的补传机制实现；**本修复不要求用户重采**，也不改变已交付日志包的任何数据。
