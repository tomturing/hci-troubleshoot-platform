# 交付路径落到任务上，并把「已采集完成」的补交付接成 direct

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |

## 一、第一性原理拆解

把「日志交付」还原到不可再分的物理事实，只有三条：

1. 交付 = 把节点上的 `<ticket>.zip` 送到日志服务器 5888；
2. 存在且仅存在两条物理链路：
   - **P1**：HCI 上的 acli 自己 `PUT` 到 5888（`log_collect create -u <url>`），平台**拿不到副本**；
   - **P2**：bridge 把包从节点拉到客户机 → 分片上传平台 → 平台代传 5888，平台**留副本**；
3. 采集与交付的耦合程度不同：P1 的"传"是 create 命令的一部分；P2 的"传"是独立动作。

由 3 直接推出两条硬约束（不是设计选择）：

- **C1：P1 没有"补传"能力。** 没有独立的 acli 重传子命令，包一旦没传出去，只能改走 P2。所以"已采集完成 → 直接上传"在物理上就等于 P2。
- **C2：补交付的充分必要条件只有两条**——节点上有完整的包、平台有上传会话。它与"采集是否还在跑"没有因果关系，因此不该要求先"恢复采集状态"。

## 二、现状与两个确定性缺陷

### 缺陷 A：交付路径只活在前端

`LogCollectPanel.vue` 的 `pathMode` 只决定两件事：P1 时把 `RELAY_URL` 塞进 `remote_url`，以及下发 bridge 时带 `remoteUrl`。`upload_mode` 全程没在创建时写，只由 `finishP1` / `runP2` 在交付完成时 PATCH。DB 里 64 条 staging 任务的 `upload_mode` 分布（`acli_direct` 16 / 空 48 / `bridge_relay` 0）就是这个缺口的直接画像。

### 缺陷 B：`mode=collect` 补交付会被 bridge 的"串味判定"误杀

`adoptNodeTask()`（`nodeAdoptMode==='deliver'`）当前做三件事：

```
PATCH status=collecting          ① 改写采集结论（对 completed 任务还会清空产物字段）
pollUntilCollected(adoptedDeliver)② 再读一遍 progress 等"完成"
runP2() → delivery_submit         ③ delivery_mode 恒为 'collect'
```

第 ③ 步的 `delivery_mode='collect'` 会让 bridge 进 `waitCollect`，其中有一条串味判定：

```go
// delivery_runner.go L351-363
if mtime.Before(startedAt.Add(-deliveryClockSkewTolerance)) {
    return fmt.Errorf("节点上的压缩包…早于本次采集开始…判定为上一次任务的产物")
}
// startedAt = job.CreatedAt，在 submit 时被赋为 time.Now()（delivery_runner.go L138）
// deliveryClockSkewTolerance = 5 * time.Minute（L39）
```

也就是说：**包产出于 5 分钟之前，点「继续交付」必然失败**，报"判定为上一次任务的产物"。这不是偶发，是判据用错了对象——串味判定回答的是"这份包是不是本次 create 的结果"，而补交付场景里本来就没有"本次 create"。bridge 早已为这种场景准备了 `direct` 模式（`prepareDirect`：只 stat + 校验 zip EOCD，完全不碰 progress），前端从未使用。

### 缺陷 C：平台 `completed` 被当成"已归档"

`decideNodeSync` 对 `platformStatus==='completed'` 只回 `none`（"平台已归档"），但 `completed` 只说明 acli 报采集完成（`schemas/log_collect.py` 的注释已经写明这一点）。当自动对账把 `completed` 写进库而交付从未发生时，结果页就只有「重新收集」——缺陷 B 因此对用户完全不可见，只表现为"只能重采"。

## 三、方案（WHAT）

```
创建：payload.upload_mode ──► log_collect_task.upload_mode（计划路径，创建即落库）
                              └─ P1 必须带 remote_url；P2 必须不带

交付：两条入口
  ├─ 采集中/刚采完（主流程）  → deliveryMode='collect'（既有，保留对"包还在写"的防护）
  └─ 已采集完成/平台无产物    → deliveryMode='direct'（新增，不碰 progress）
        stat(节点) → POST /deliver（begin_delivery 只动 delivery_*，status 不变）
        → delivery_submit(direct) → pollRelay → PATCH completed + upload_mode=bridge_relay
```

### 3.1 接口与数据模型变更

| 对象 | 变更 |
|---|---|
| `LogCollectTaskCreate.upload_mode` | 新增，`Literal['acli_direct','bridge_relay']`；`acli_direct` 必须同时给 `remote_url`，`bridge_relay` 不得给；两者都不给时按 `remote_url` 推断（兼容旧前端） |
| `LogCollectService.create_task` | 落 `upload_mode`（显式值优先，否则按 `remote_url` 推断） |
| `LogCollectService.begin_delivery` | 补交付即 P2：落 `upload_mode='bridge_relay'`（理由见 C1） |
| `LogCollectTaskPatch.detail` | 服务端改为**合并**语义，避免前端写降级审计时覆盖 `baseline_report_hash` |
| `POST /api/log-collect/tasks/{id}/deliver` | 语义明确为"P2 补交付"，行为不变（幂等/大小不一致自愈保留） |

不新增列、不加迁移：`upload_mode`（`desired_schema.sql` L3837）与 `detail` JSONB 都已存在，本来就是为这件事准备的。

### 3.2 前端

| 文件 | 变更 |
|---|---|
| `api/logCollect.ts` | `LogCollectTaskCreate` 增加 `upload_mode?` |
| `LogCollectPanel.vue` `handleStart` | 创建任务带 `upload_mode`（P1→`acli_direct`，P2→`bridge_relay`） |
| `utils/logCollectDelivery.ts` | `DeliverySubmitArgs.mode` 继续作为唯一开关（已有 `direct` 类型），`runDeliveryJob` 透传 |
| `LogCollectPanel.vue` `runP2` | 拆出 `deliverExistingPackage()`：仅 stat + `/deliver` + `delivery_submit(direct)` + `pollRelay` |
| `LogCollectPanel.vue` `adoptNodeTask` | `deliver` 模式改调 `deliverExistingPackage()`：不再 `PATCH collecting`、不再 `pollUntilCollected` |
| `services/logCollectSync.ts` `decideNodeSync` | 新增入参 `platformDelivered`；`completed` + 未交付 + 节点 completed + 有包 → `adopt(deliver)`；已交付 → `none` |
| `LogCollectPanel.vue` 结果态 | 「上传到平台」入口与文案；P1 计划路径时说明"P1 无重传接口，改经平台中转" |

### 3.3 为什么"补交付"不改采集状态机

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A：先 `PATCH collecting` 再走交付（现状） | 复用接管入口 | 抹掉"采集已完成"的事实；对 `completed` 会清空产物字段；依赖 `adoptedDeliver` 绕过归属判定，容易再死锁 | ✗ |
| B：新增状态 `delivering` | 语义清晰 | 状态机 + DB CHECK + 全部 UI 分支都要改，为一个动作扩一套状态，收益不抵成本 | ✗ |
| C：**交付只动 `delivery_*`，`status` 不动**（选中） | 与既有"交付状态正交"设计一致；`/deliver` 早已如此实现（`begin_delivery` 注释即为此写）；可重复执行 | 需要 UI 能同时表达"采集已完成 + 未交付" | ★★★★ |

`log_collect_task.delivery_status` 从 #1313 起就是为这件事存在的，方案 C 只是把它用起来。

## 四、对抗性审查

| 攻击场景 | 结果 | 处理 |
|---|---|---|
| 用户连点 3 次「上传到平台」 | `/deliver` 第二次起 `delivery_status in {pulling,uploading,relaying}` → 409 LC-PLATFORM-009；`delivery_submit` 同 job_id 复用 | 按钮执行期间置 `running`，且服务端幂等兜底 |
| 节点上包已被 P1 删除 | `stat` 失败 → 直接报"源包不存在"，不签发会话 | 前端先 `stat`，判定顺序保证不产生空会话 |
| 包只写了一半（acli 仍在写但已报 100%） | bridge `verifyArchiveComplete` 报"尾部无 zip 结束标记" | 不传半截包；错误码 LC-TRANSFER-* 原样透出 |
| 交付中途浏览器关闭 | bridge 作业独立执行；`delivery_status` 由数据面 complete 推进 | 重开面板 `status==='uploading'` 分支接回 `delivery_status` |
| 补交付时任务 `status=completed`，PATCH `completed` 再写一次 | `validate_transition(current==target)` 直接放行；`finished_at` 刷新 | 无需新增状态边 |
| `detail` 合并导致旧键永远无法删除 | 合并语义下值为 `null` 的键会被移除 | service 内显式处理 `None` → pop |
| 旧前端不传 `upload_mode` | 按 `remote_url` 推断，行为与今天一致 | 兼容路径有单测 |

## 八、修订（2026-10-28）：交付判据重构

### 8.1 现场故障（工单 Q2026102701193）

节点 `acli log_collect progress` 明确输出 `日志收集单发送状态：发送成功`，插件随即删除 zip；
平台 `delivery_status` 为空，于是对账判成「未交付 + 压缩包仍在节点」，产生三重后果：

1. 结果页常驻「请点『上传到平台』」；点下去 `stat` 对不存在的文件返回 1，顶部弹
   `Process exited with status 1`；
2. 点「重新收集」仍被前置守卫拦回同一句提示 —— **既不能新建、也补交付不了**；
3. 同一屏同时出现「压缩包仍在节点」与「已完成」两条互相矛盾的提示。

### 8.2 根因（三条判据各自错位）

| 判据 | 原实现 | 错在哪 |
|---|---|---|
| 交付是否成立 | `platformDelivered` 只看平台 DB（`delivery_status` / `relay_status`） | P1 对平台**零可观测**（无字节、无分片、无回执），套用 P2 的"平台有记录"标准必然误判 |
| 包是否仍在节点 | `snapshot.archive_path` 非空 | 路径只证明"曾生成过"。P1 成功后插件自删，报告里仍带路径 |
| 已终态任务能否补证据 | 只在 `patch_completed` 里写 `delivery_status` | `completed` 是终态，永不再进该分支 → 证据永不落库 |

外加一条流程错误：`preCreate` 守卫把 `adopt` 全量拦截，而 `adopt` 已包含"补交付"语义，
于是补交付待办把**新建任务**也锁死。acli 的 completed 任务并不与新的 `create` 互斥
（E_0073 只针对未完成任务），拦截缺乏物理依据。

### 8.3 修正后的判据

| 问题 | 唯一证据源 | 结论 |
|---|---|---|
| P1 交付成功与否 | 节点报告 `upload_state`（发送成功/失败） | 成功 → 补登 `delivery_status=delivered`；失败 → 进入补交付判断 |
| 包是否仍在节点 | bridge `stat`（`archive_exists`） | `true` → 补交付成立；`false` → 提示重新采集；缺省 → 不提供入口 |
| 平台是否已交付 | `delivery_status=delivered` 或 `relay_status=success` | 是 → 不再提示上传 |
| 是否阻止新建任务 | 节点是否有"未结束的采集任务" | 仅 `adopt(resume)` / `cancel_retry` / `warn_node_busy` 拦截 |

新增 `SyncActionKind='patch_delivered'`：`status` 不动，只补交付证据，避免把
"采集已完成"这个真实结论重写一遍。

### 8.4 契约变化

- `logCollectProgress`（bridge → 前端）新增 `archive_exists?: boolean`，**缺省≠false**：
  用指针区分"明确不存在"与"没探测"，前端只在明确 `true` 时提供补交付入口。
- `stat` 动作：文件不存在时仍返回 `status=ok` + `exists=false`，不再把 shell 退出码
  当动作失败抛给用户。
- 前端 `runP2` 支持 `options.totalSize`：补交付入口已 `stat` 过，直接复用，省一次往返。

### 8.5 新增回归用例

| 层 | 用例 |
|---|---|
| 前端纯判定 | 已完成 + 节点报发送成功 + 平台无记录 → `patch_delivered`（不是 `adopt`）；发送失败 + 包在 → `adopt(deliver)`；未探测 → `none` 且文案含"未确认" |
| 前端守卫 | `blocksCreate`：`adopt(deliver)` 不拦；`adopt(resume)` / `cancel_retry` / `warn_node_busy` 拦 |
| 前端组件 | 现场快照（`upload_state=发送成功` + `archive_exists=false` + DB 空）→ 自动 PATCH `delivery_status`，结果页显示「已由插件直传」，且**不出现**「上传到平台」 |
| bridge | `archive_exists` 三态序列化：`true` / `false` / 缺省（缺省时不得输出该字段） |

### 8.6 二次回归（同日）：`delivery_submit` 载荷在消息层被丢空

现象：点「上传到平台」→ `/deliver` 返回 200，bridge 立刻报 `source_path 不能为空`，
任务停在 `delivery_status=queued`。

根因不在载荷构造，而在**载荷 → WS 消息**这一跳：

| 环节 | 产出 | 问题 |
|---|---|---|
| `buildDeliverySubmitPayload` | snake_case 全字段（#1322 已修） | 正确 |
| `sendAndWait('delivery_submit', payload)` | 把 payload 当 `options` 透传 | 类型上被当成 `Record<string, unknown>` |
| `buildDeliveryMessage` | 按 **camelCase** 取 `options.sourcePath` 等 | 逐字段取空 |
| 实际发到 bridge | `{type, case_id, node_ip}` | `source_path`/`upload_token`/`total_size`/`exec_id` 全空 |

更严重的是 `DeliveryMessageOptions` 里根本没有 `delivery_mode` 与 `tls_insecure`，
因此 **direct 模式与证书授权从未送达 bridge** —— 这是 `bridge_relay` 至今零成功记录的真正原因，
#1322 修好载荷后被这一层翻译整体抵消。

修复：新增 `buildDeliverySubmitMessage(payload, caseId, nodeIp)`，把协议载荷**平铺**成消息，
不再做第二次字段名映射；`sendAndWait` 对 `delivery_submit` 走这条独立分支
（`status`/`resume`/`cancel` 字段少且都是单值，仍走通用构造）。

为什么三层测试都没发现：单测只断言 `buildDeliverySubmitPayload`；组件测试 mock 了
`buildDeliveryMessage` 并**直接透传 payload**。新增的契约用例刻意用真实函数组合
（payload → message → 解析断言每个字段），并把 `uploaded_parts=[]` 纳入断言——
漏传该字段会让续传静默变成全量重传。

### 8.7 三次回归（同日）：结果态展示了错误的记录

现象：用户选 **P2** 新建任务（16:40 发起、16:45 failed），打开面板却看到
「交付路径：P1 直传日志服务器」「归档状态：已由插件直传日志服务器」，于是质疑
"我明明选的 P2，你是怎么判断 P1/P2 的"。

根因：结果态取的是 **`items.find(status === 'completed')`**——"任意一条已完成"，
而不是"最近一次发起的那条"。同一工单当天有 4 条记录，用户刚失败的 P2 任务不在
completed 集合里，于是面板越过了它，展示早上 10:03 发起、18:05 才完成的 P1 任务。
交付路径、归档状态、上传入口全部跟着这条错任务走；#1325 又给 completed 任务加了
自动对账，让它持续产出提示，进一步像"当前任务"。

修正：
1. 新增 `pickDisplayTask(items)`：取**最近一次发起**的终态任务。基准用 `created_at`
   而非 `finished_at`——长采集（现场 8 小时 36 分）结束得晚，按结束时间会顶掉用户
   刚发起的尝试；
2. 结果卡标题按真实结论渲染（完成 / 失败 / 已取消），不再写死"已完成日志收集"；
3. 增加「展示记录」切换条（最近 5 条：时间 · 结论 · 交付路径），切换后重新对账；
4. 结果页显式化 `delivery_status=queued`（"交付已登记但未完成，可重试上传"），
   此前只会显示"采集完成，尚未交付"，看不出已试过一次。
