# 方案事件：日志收集核验证据链加固（回执、发送字节数、残留包基线）

## 背景与需求

[2026-11-27 归档体积误报修复](2026-11-27-日志收集归档体积误报修复.md) 用「期望值绑定观测来源」止住了红卡误报，但只解决了**结论口径**，没有解决**证据来源**。该文档列出的三项后续风险在本轮一并落地：

1. P2 链尾确认仍把 `object_size or archive_size` 当期望值，`archive_size` 是采集期的节点观测，同工单重收时可能是上一批次残留包的体积；
2. P1 核验只看 5888 归档目录里"有没有文件、多大"，上传窗口内目录仍挂着上一批次旧包（`Q2026111700614` 就是新包上传中读到 314 MB 旧包），且平台从未利用服务端上传会话回执；
3. 桥侧探测只报"路径上有文件、体积多少"，无法回答"这个字节是不是本次采集写的"——`Q2026112700769` 里旧包 4.17 GiB 在固定路径上压了 14 分钟。

## 方案概述（WHAT）

1. **P2 链尾期望值改用实际发送字节数**：`_confirm_archive` 新增 `sent_size`（本次逐片推给 5888 的平台副本字节数），它由平台自己读盘累加，可信；`object_size`（平台合并时自算）同样可信；只有 `archive_size`（节点观测）单独存在时按不可信处理，偏小返回 `archive_size_untrusted` 而非 `size_mismatch`。
2. **P1 核验优先用 5888 上传会话回执**：新增 `_probe_p1_archive` / `_judge_p1_probe`，先查 `/upload_progress?filename=`，只把**带 `upload_id` 的真实会话**当强证据：
   - `status=done` 且 `uploaded_size == file_size`、分片收齐 → 交给 `judge_archive` 做体积与代际判定，`mtime` 取会话 `start_time`（回答"这是哪一次上传"，比文件 mtime 准）；
   - `status` 非 `done` → `archive_missing`（仍在传/合片/服务端已判失败都只算本次未落地）；
   - 自称 `done` 但体积或分片数自相矛盾 → `archive_size_invalid`；
   - 会话缺失（旧版 5888、24h 过期、端点异常）→ 回退 `/archive_status`，票据照旧现签现用。
   后台复核 `reconcile_p1_archives_once` 复用同一套探测与判据，避免"后台说已交付、页面说未核验到"的双源矛盾。
3. **桥侧记录任务前归档基线并识别残留包**：`create` 前（旧包改名之后）量一次固定路径的 `size|mtime|inode`，按任务 ID 存快照；`progress` 探测到**完全一致**的文件时判为上一批次残留，`archive_size` 置 0、`archive_residual=true`，并落一条 `log_collect.archive_residual` 告警（每任务一条）。前端据此禁用「上传到平台」——文件确实在，但它不是本次采集的产物。

## 决策依据（WHY）

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| P2 期望值用发送字节数 | 平台自己数出来的字节，落盘更小只能是截断；无需新增字段 | 续传前进程退出时拿不到，仍需回退 | 选中 |
| P1 用 `/upload_progress`（按产物名） | 5888 已上线、无需改造 acli/bridge；带回 upload_id、收齐分片、摘要、会话起始时间 | 会话只按产物名索引，同工单后续成功交付也能满足旧任务核验 | 选中（边界已在代码注释与本文说明） |
| P1 改为存 `upload_id` 再查 `/upload_status` | 语义最精确 | P1 由节点 acli 自己 init，平台拿不到 upload_id；要改 acli → 桥 → 平台三处，且回执仅 24h | 否决 |
| 桥侧 mtime 阈值（文件早于任务 N 分钟） | 实现简单 | 取消到重收只隔 13 秒；旧任务包装阶段还可能晚于任务创建时间 | 否决 |
| 桥侧 size+mtime+inode 基线 | 从物理身份上证明"这个 inode 没被写过"，不依赖时钟 | 需 bridge 发版 + 现场重装 exe | 选中（叠加在其余两项之后） |
| 归档路径按批次隔离 | 根治同名冲突 | 冲击 5888 命名契约与 ticket-sync | 否决（本轮） |

## 详细设计

- `backend/case-service/app/services/log_collect_relay_service.py`：`_run` 把平台副本实际字节数传给 `_confirm_archive(..., sent_size=size)`；快照新增 `expected_size_trustworthy`、`sent_size`、`object_size` 便于事后复核。
- `backend/case-service/app/routes/log_collect.py`：
  - `_p1_receipt_view` 把回执翻译成判定输入（`done` / `pending` / `invalid`），并在 `start_time` 缺失、`upload_id` 为空时拒绝当强证据；
  - `_probe_p1_archive` 负责"回执优先、归档件兜底"；回执端点异常只降级、不抛错；
  - `_judge_p1_probe` 统一把回执状态与 `judge_archive` 结论合成 `(verified, reason, size, at)`；
  - 核验快照新增 `source`（`upload_progress` / `archive_status`）、`upload_id`、`session_status`、`received_chunks`、`chunk_total`、`started_at`、`digest_sha256`，写入 `detail.p1_archive_check`；
  - 后台复核的 `source` 仍为 `background_reconcile`，另加 `evidence_source` 区分拿到的是回执还是归档件，且期望值一律按不可信处理。
- `terminal_bridge/internal/logcollect/log_collect_archive_baseline.go`：`archiveBaseline{Path,Size,ModUnix,Inode}` + 任务级 `sync.Map`；`stat -c '%s|%Y|%i'` 单命令取全，解析失败即放弃（不猜）；`logCollectArchiveIsResidual` 只在 size、mtime、inode 全一致时返回 true，量不到一律返回 false（宁可多报一次，不能把本次真包静默掉）。
- `terminal_bridge/internal/logcollect/log_collect.go`：`create` 分支在 `archiveStaleLogCollectArchive` 之后登记基线（改名成功则无基线、改名失败正好覆盖残留）；`progress` 分支在探测后判残留，`archive_size` 置 0、置 `archive_residual`，证据字段同步落库。
- `terminal_bridge/internal/shared/acliout/acliout.go`：`Progress` 新增 `archive_residual`。
- `frontend/customer/src/services/logCollectSync.ts`、`frontend/customer/src/components/LogCollectPanel.vue`：快照透传 `archive_residual`；残留包既不进补交付入口，也不在 `failed` 终态下被接管交付，等待超时的文案不再建议"上传到平台"。

- 前端：`logCollectSync.spec.ts` **103 passed**、`LogCollectPanel.spec.ts` + `logCollectDelivery.spec.ts` **190 passed**；`vue-tsc -b` **0 error**。
- 桥侧：`go build ./...`、`go vet`、`gofmt -l` 均干净；`go test ./internal/logcollect/ ./internal/shared/...` 全绿（新增基线解析、残留判定、无基线不误判、量不到不误判、告警去重）。
- 真数据核对：staging 用 `Q2026112700769` 实测 `/upload_progress`，返回 `status=done`、15/15 分片、`uploaded_size=file_size=152850599`、sha256 `695631b7…`、`start_time=05:57:28`（晚于任务创建 05:43:34），正是本轮要优先采用的回执形态。

## 影响与回滚

- 服务端改动随 case-service 镜像生效；P1 核验从此多一次只读回执查询，异常自动回退，不改变"只有核验通过才写 delivered"的写入契约。
- 桥侧改动需重新构建 exe 并由现场重装：旧版桥没有基线，行为与本轮之前一致（残留包仍可能被上报），不会因为服务端升级而变得更差；`archive_residual` 缺省时前端按原逻辑判断。
- 已知边界：回执按产物名索引，同一工单后续另一次成功交付也会让旧任务的核验读到 `done`；`/archive_status` 原本就有同样边界，本轮未变差。
- 回滚：服务端还原 `_confirm_archive` 签名与 P1 探测分支即可；桥侧回滚只需还原两个调用点，无数据库迁移。
