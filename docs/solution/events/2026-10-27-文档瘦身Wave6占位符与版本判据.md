# 文档瘦身 Wave 6：C4 占位符与 C7 版本矛盾的判据治理

> 前五个 Wave 把「该阻断的」都升成了阻断（现行层 C1/C2/C3、frontmatter、变更历史节）。
> 这一轮处理的不是缺门禁，而是**有两道门禁在恒报**：C4 占位符与 C7 版本矛盾。
> 恒报的检查器比没有检查器更糟——它会训练评审直接忽略这一类输出。
> 口径已写入 [文档管理规范](../../文档管理规范.md) **§九 · C4 与 C7 的判据边界**。

## 背景与需求

C4/C5/C7 一直挂在 `docs-governance` 里只报告不阻断，长期输出如下（2026-10-27 全仓实测）：

| 类别 | 输出 | 实际构成 |
|------|------|---------|
| C4 占位符 | 172 条 | 现行层 57 条、事件/归档层 115 条 |
| C7 版本矛盾 | 1 条 | 一次报出 5 个版本号「互相矛盾」 |

结论不是「文档脏」，而是**判据本身不成立**。抽 57 条现行层 C4 逐条看，绝大多数是：

- 标识符与编号格式：`V-xxx / PIT-xxx`、`QYYYYMMDDXXXXX`、`revision_xxx`
- 示例值与掩码：`sk-xxxx`、`ghp_xxxx`、`secrets.XXX`、`job_id=xxx`、`tests/xxx/`
- 业务术语：工单状态枚举「待确认、已确认、处理中…」、风险等级「高危操作待确认」、
  模型推断标签「模型推断·待确认」，以及从「等**待确认**」里切出来的假命中
- 系统状态描述：「诊断未完成时…」「该逻辑**尚未实现**」「Capability 未实现」

C7 则更直接：命中的 5 个版本号（v2.1.1 / v2.1.2 / v2.1.3 / v2.1.4 / v2.23.0）全部来自
README 的**历史发布说明标题**。旧实现把「文件里出现的所有 `vX.Y.Z`」当成「当前版本声明」
并要求全局唯一——任何带发布历史的 README 都必然恒报。

顺带查出一个**静默失效**：旧实现的 `strong_markers` 清单里列了
`未实现 / 尚未实现 / 未完成 / 尚未完成`，但 `PLACEHOLDER_RE` 正则根本没收录这四个词。
清单与正则脱钩，这四个标记永远不可能触发，且当时没有任何测试能发现。

### 同时暴露的一处真实漂移

README 第 3 行本就写明「版本以 `pyproject.toml` 为唯一来源……请勿在本文件硬编码版本号」，
但第 63 行却写着 `### v2.23.0 当前里程碑（2026-08-06）`。事实来源一致指向 **2.31.0
（2026-10-21）**：`pyproject.toml`、`.release-please-manifest.json`、`CHANGELOG.md` 三者
互证。所以那句「当前里程碑」是自相矛盾的过期声明——文档违反了自己定的规则。

## 决策：判据收窄到「语境」，而不是继续堆豁免词

| 候选 | 结论 | 理由 |
|------|------|------|
| A. 继续往豁免正则里堆词（`env:xxx`、`service:xxx`…） | 否决 | 每加一条都在扩大射程且无法验收；下一批示例写法又会漏 |
| B. 把 C4/C7 从门禁里删掉 | 否决 | 真腐化仍有：本次实测就抓到 5 条现行层真缺陷 |
| C. 按语境重建判据 + 全部豁免确定性化 + 正反用例锁射程 | **采纳** | 豁免不再依赖词表穷举，而是按「这段文字是谁对谁说的」判定 |

选 C 的依据与 C1/C2/C3 同源：**门禁的正当性只来自「读者会照着文档行动」**。

## 方法：C4 与 C7 的新判据

### C4 占位符：三层过滤

1. **层**：只审现行层。`*/events/` 与 `docs/archive/` 是史料，当时写下的 TODO 就是
   当时的真实状态；把它「修掉」等于伪造历史（§8.3）。事件层 115 条由此不再输出。
2. **语境**（确定性规则，不靠词表）：
   - 行内代码内 → 字面示例（`` `sk-xxxx` ``、`` `tests/xxx/` ``）
   - 引号内 → 产品文案/示例值（`"工具：xxx，请先创建"`、`「建议走 SOP: xxx」`）
   - 与相邻字母数字/`-`/`_` 构成连续体 → 标识符（`V-xxx`、`Q20260310xxxxx`、`revision_xxx`）
3. **标记强弱分级**：

   | 级别 | 标记 | 判定 |
   |------|------|------|
   | 强 | `TODO` / `TBD` / `FIXME` / `待补充` / `待完善` / `待更新` | 作者对自己文字的交待，命中即报 |
   | 弱 | `待确认` / `待实现` / `待定` / `占位` / `此处填写` / `未实现` / `尚未实现` / `未完成` / `尚未完成` / `placeholder` 等 | 本身歧义，需同行存在**真正起作用**的强标记才上报 |

   关键细节：「真正起作用」意味着该强标记自身不得落在反引号或引号里。否则一句
   「被 `` `# TODO` `` 注释保留为未完成状态」会让同行的弱标记「未完成」借光上报——
   这是本次实测抓到的唯一残留误报。

### C7 版本矛盾：只认声明位

只有「当前版本 / 当前里程碑 / 最新版本 / 版本：」这类**显式声明位**（关键词与版本号同现
于一行，前后皆可）才算声明，且必须等于 `pyproject.toml`。历史发布说明里的 `vX.Y.Z` 是
记录不是声明。同时排除 `docs/文档管理规范.md`：它用 v2.10 给自己编号，与产品版本是两个
命名空间，混比必然互相误伤。`pyproject.toml` 缺 `version` 时报「无法判定」而不是静默通过。

### 判据自身的逃逸面（诚实披露）

| 逃逸面 | 性质 |
|--------|------|
| 把「本节待补充」改写成「本节仍在编写中」等不带强标记的同义句 | 实质风险：C4 只认固定词表，换词即可绕过。缓解手段是评审读 diff，不是机器 |
| 在 `## 变更历史` 里凑无意义行 | 见 Wave 5 的同类披露，机器只判结构不判意义 |
| 把真实过期声明改写成「里程碑」以外的措辞 | C7 只认固定声明位；有意为之——把「历史记录」与「当前声明」分开正是它的目的 |
| 「待确认」类真腐化被降级为弱标记 | 有意取舍：该项目里 `待确认` 是工单状态词，作为独立信号信噪比接近 0 |

### 回归用例（`scripts/ci/test_check_docs_rot_placeholders_version.py`，50 项）

覆盖：强弱标记与候选正则的自洽性（逐条断言，堵死本次发现的静默失效）、分级不重叠、
6 类真腐化正向用例、标识符/行内代码/引号字面/业务术语/系统状态/路线图/模板指令的反向用例、
弱标记共现分支仍有效、反引号 TODO 不给弱标记借光、事件层排除、代码围栏跳过、
C7 的真漂移/历史说明/一致声明/缺 version 四种情形、规范自身命名空间排除。

脚本自身从 `check_placeholders()` 内联判定中抽出两个纯函数
（`placeholder_in_scope()` / `classify_placeholder_line()`），否则只能靠造临时文件验证——
与 §九「判定逻辑必须可单测」是同一条要求。
