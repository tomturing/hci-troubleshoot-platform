# 发布滚动导致代传交还 pending 后无人接管

- 日期：2026-11-04
- 现场工单：Q2026110400024（7.06 GiB 包，P2 中转）
- 涉及：`backend/case-service`（`main.py` / `routes/log_collect.py` / `relay_service`）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 客户机 08:24:34 已完成交付 | `delivery.job_finished phase=done`，本地副本 `delivery.local_cleaned` |
| 界面停在"正在归档到日志服务器：第 220/723 片、90%" | 前端按 5s 轮询 `GET /relay` 恒 200 |
| `relay_status=pending`，`relay_chunk_index=228`，`relay_updated_at=08:28:22` | 43 分钟未更新（查看时 09:11） |
| 当天 08:23–08:30 有一次 case-service 滚动发布 | 同日 #1437 合并触发 |

## 二、根因

1. 代传是 case-service **进程内**的 asyncio 任务，进程退出即中断。
2. 优雅退出时 `relay_service.release()` 把仍在 `running` 的任务置回 `pending`，
   注释写明"交给下一个实例接管"。
3. 但**只有 `reconcile_relays_on_startup()` 在 lifespan 启动时跑一次** `claim_stale()`。
4. 滚动更新的实际顺序是：新 Pod 先启动（此时旧 Pod 仍持有 `running`，租约未过期，
   新实例不会抢）→ 旧 Pod 在 grace period 内才写 `pending`。
   启动那一刻看不到 pending，之后再无人检查 → 任务永久停在 `pending`。
5. 前端 `shouldRecoverRelayLease` 只处理 `running + stale`，明确把 `pending`
   留给"complete 或用户显式操作"，因此既不报错也不重试，界面一直转圈。

## 三、本次改动

| 位置 | 改动 |
| --- | --- |
| `routes/log_collect.py` | 抽出 `reconcile_relays_once()`（单轮，返回接管数）；`reconcile_relays_on_startup()` 保留为一次性入口；新增 `reconcile_relays_loop(interval=60s)` 周期接管 |
| `main.py` | lifespan 改为创建 `reconcile_relays_loop()`（关闭时仍 cancel） |
| 测试 | 新增 `test_reconcile_loop_keeps_claiming_after_startup`：验证启动窗口之后仍会持续 claim |

判据不变：只接管"有制品（`archive_path` 非空）"且 `pending` 或租约过期 `running` 的任务；
没有制品的中间态抢过来只会以 `LC-TRANSFER-001` 立即失败，那不是自愈。

## 四、现场恢复（本次实际使用）

把卡住的记录改成"租约已过期的 running"，让前端既有的自愈路径生效：

```sql
update log_collect_task
   set relay_status = 'running',
       relay_updated_at = now() - interval '10 minutes'
 where case_id = '<工单号>' and relay_status = 'pending';
```

前端下一轮轮询（5s）会调用 `POST /relay?force=true`，服务端抢占成功后从已传分片续跑，
不会重传整包。本次恢复后 `relay_chunk_index` 从 228 连续推进到 290+。

## 六、遗留

1. 前端仍只对 `running + stale` 自愈；服务端周期接管后这条路径不再是唯一保险，
   但若服务端长时间不可用，用户仍缺少"手动重试代传"的入口；
2. 代传进度目前只靠 `relay_chunk_index` 落库，长时间单分片合并期间界面无细粒度进度。
