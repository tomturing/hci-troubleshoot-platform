# 2026-11-06 日志收集会话归属三层门禁修复

## 背景

工单 Q2026110666667 多次出现界面判定「已完成 / 已交付」，但节点实际刚发起采集、或仍在采集。
根因是平台无法区分 acli 的回包属于哪一次下发：acli 单任务、无 run_id，节点上只能看到
「当前最后一次采集」的进度。旧判据在三种情况下把「上一次任务的残留报告」当成这次完成：

1. 基线取自前端陈旧快照 `progress.value`（`wait_refresh` 时本就不更新 progress），比节点实际
   报告落后一个版本（基线 `2698` 字节、节点已是 `2776` 字节），指纹比对失效；
2. 报告「变了」被直接采信为「属于本次任务」；
3. #1286 删除了 `archive_exists` 这条最硬的兜底证据。

现场铁证：22:56（UTC 14:56）用户点「重新收集」创建任务 `b7fa86c5`，**1.01 秒后**就收到
`completed / 100% / Success / archive_exists=false / archive_size=0 / raw_len=2776`（2776 正是
22:07 那轮上传阶段的旧报告），平台随即写入 `status=completed`，而真实采集直到 14:57:02 才
以 `running / 0%` 开始。

## 方案：L1 / L2 / L3 三层门禁

- **L1 采集起点门**：本次会话亲自 create 的任务，必须先观测到 `running`（采集起点）才允许写
  `completed`。冷启动窗口 10 分钟兜底出口，避免把**真实完成**永久卡在采集中。此门**只对本次
  下发启用**——接管历史任务时关闭，否则会重演 Q2026101401683（真实完成被永久卡住）。
- **L2 否决证据（不依赖归属正向判定，只做证伪）**：
  - L2-1 时间一致性：`报告自称总耗时 > 任务年龄 + 120s` → 必为更早任务的报告。依赖 bridge
    上报的 `total_time`（本次已让 bridge 落库，但需重建 bridge exe 才能到达客户机）。
  - L2-2/L2-3：`archive_exists=false && archive_size=0` 且从未观测到上传阶段 → 不写
    `delivered`，拦截 acli `Success → Sending → Success` 的采集阶段假信号
    （Q2026110666667 / `5ad6842a`）。同样**只对本次下发启用**，历史接管任务关闭，避免重演
    Q2026102701193（插件自删包 + 平台漏记时本应靠节点自述补登）。
- **L3 状态机单调**：平台终态（completed / failed / cancelled）上的 `patch_completed` /
  `patch_failed` 一律降级为 `warn_completed_conflict`——终态只能由用户显式点「纠正」离开，
  绝不被新报告自动改写或回退。

## 上线状态与遗留

- 前端（L1/L2/L3）与 bridge（落库 `total_time`）已随本 PR 提交，待部署。
- L2-1 在客户机上需 bridge exe 重建并现场重装后才生效；**L1 / L2-3 纯前端 + 后端即可生效**，
  不依赖任何桥侧更新，因此即便 bridge 未更新也能拦截「1 秒完成」这类故障。

  但当时未据此回滚 `completed`，属后续应补的防线（正确结论比写 completed 仅晚 37ms，却无人使用）。
