# 2026-09-24 统一认证系统 · 管理台强制认证落地

> 事件文档：需求 → 方案 → 分阶段落地。承接 [2026-09-23 统一认证系统设计方案](./2026-09-23-统一认证系统设计方案.md)。
> 09-23 方案确立了 RS256/JWKS + 账号密码登录的**结构**，但实现层遗留了三层"认证兜底"，导致**管理台实际未强制认证**。
> 本文用第一性原理 + 对抗性审查重新厘清根因，并给出分阶段灰度的强制认证落地方案。

---

## 一、问题定性：认证被架构性 bypass

09-23 方案明确要"移除 `INTERNAL_API_TOKEN` 静态令牌注入""管理面强制账号登录"，但落地后仍残留三层兜底，使"网络可达 = 管理员"未被真正闭环：

| 层 | 兜底行为 | 证据 | 后果 |
|----|---------|------|------|
| 入口 nginx | 客户端无 `Authorization` 时自动注入 `Bearer <INTERNAL_API_TOKEN>` | `frontend/admin/nginx.conf` | 匿名请求经管理入口被升格为 admin |
| 前端 fetch | 未登录时回退共享令牌，且默认值 `hci-dev-internal-token` 硬编码进 JS bundle | `frontend/admin/src/utils/auth.ts` | 未登录即带共享令牌；令牌泄露给任何查看源码者 |
| 网关 | `AUTHN_ENFORCE_ADMIN` 默认 `false` 且 chart 从未设置 → 持共享令牌者恒为 admin | `api-gateway/app/middleware/identity.py`、`config.py` | 共享令牌 = admin 后门永久开启，且无开关可关 |

叠加两个放大缺陷：

- **路由守卫不强制登录**：`router/index.ts` 的 `beforeEach` 只处理"已登录访问 /login 跳 dashboard"，未登录访问受保护页直接放行。
- **签名私钥是临时内存密钥**：`AUTH_RSA_PRIVATE_KEY_PEM` 在 staging 未注入，auth-service 每次重启生成新密钥 → JWKS 变更 → 已签发 JWT 全失效 → 全员掉线。在此地基上做强认证 = 随时把人锁门外。

## 二、第一性原理：认证系统的三条不可再分公理

| 公理 | 含义 |
|------|------|
| **A1 身份即凭证** | 身份只能来自请求者携带的、由可信方（auth-service）签名、可独立验签（JWKS）的 JWT。**任何中间层（nginx/前端）不得替请求者声明身份。** |
| **A2 默认拒绝** | 无有效凭证 → 受保护资源一律拒绝（后端 401/403），前端引导登录。安全是 deny-by-default，而非"默认放行 + 逐点加锁"。 |
| **A3 凭证分离·最小暴露** | 用户凭证（JWT）只在浏览器↔网关；服务间凭证（`INTERNAL_API_TOKEN`）只在网关↔下游，**绝不出现在浏览器 / nginx / JS bundle**。 |

用户诉求"认证通过→放行 / 未认证→跳登录 / 其余→403"正是 A1+A2+A3 的直接推论。当前所有 bug 都是这三条被违背的症状。

## 三、目标信任链（重构后）

```
浏览器 --(真实 JWT 或 无)--> admin-ui nginx(纯静态 + 透传，零身份注入) --> api-gateway
  api-gateway:
    白名单(登录/health/metrics/ws/direct 数据面) 外：
      有效 admin JWT(JWKS 验签) --> is_admin --> 用 INTERNAL_API_TOKEN 重签 --> 下游
      无 / 无效 JWT --> 401(WWW-Authenticate) --> 前端拦截 --> 跳 /login
  auth-service: 固定 RSA 私钥(Secret 注入) 签发 JWT；JWKS 跨重启稳定；登录限流
```

**关键事实**：网关早已对下游统一重签 `INTERNAL_API_TOKEN`（`cases.py:_admin_headers`、`kb.py:_internal_auth_headers`、`diagnosis.py`）。因此 nginx 的 fallback 注入对下游**完全冗余**，唯一作用就是替客户端伪造 admin 身份——剥离它是**纯删除**，不断下游链路。

## 四、问题清单与解决方案（对抗性审查）

### P0 认证被 bypass / 地基不稳

| # | 问题 | 解决方案 |
|---|------|---------|
| P0-1 | nginx 自动注入共享令牌 | 删除 fallback 注入，nginx 只透传客户端真实 `Authorization` |
| P0-2 | 网关共享令牌=admin 分支永久开启、无开关 | 删除/默认关闭该分支；chart 增 `apiGateway.authnEnforceAdmin` 开关 |
| P0-3 | 前端未登录回退共享令牌 + 硬编码令牌进 bundle | 删除 `FALLBACK_INTERNAL_TOKEN`；未登录不带 `Authorization`；内部令牌绝不进前端 |
| P0-4 | RSA 签名私钥是临时内存密钥（重启全员掉线） | Secret 注入固定私钥（Base64(PEM) 单行）；非 dev 缺私钥则 auth-service **fail-fast 拒绝启动** |
| P0-5 | 路由守卫不强制登录 | `beforeEach`：未登录且目标非 public → `/login?redirect=<原路径>`；fetch 收 401 清 token 跳登录 |

### P1 鉴权模型脆弱

| # | 问题 | 解决方案 |
|---|------|---------|
| P1-6 | `require_user` ≠ 认证（匿名 cookie 即满足） | 语义分离：admin 域一律 `require_admin`；`require_user` 仅限 customer 域 |
| P1-7 | 逐点加锁，非默认拒绝 | 网关默认拒绝：白名单外 admin 域无有效 JWT → 401 |
| P1-8 | JWT 验签失败静默回退（fail-open） | 验签失败明确 401，不回退共享令牌 |
| P1-9 | `INTERNAL_API_TOKEN` 身兼 4 职 | cookie HMAC 改用独立 `IDENTITY_COOKIE_KEY`；内部令牌仅网关↔下游 |

### P2 加固

| # | 问题 | 解决方案 |
|---|------|---------|
| P2-10 | 登录限流形同虚设（只 +1 不写 locked_until） | `failed_attempts ≥ N → set locked_until`；可选 IP 级限流 |

## 五、分阶段灰度落地（每步可回滚，杜绝锁死）

> 决策（2026-09-24 用户确认）：**范围仅 admin 管理台**（customer 客户侧维持现状，强认证属阶段2）；**分阶段灰度**；**chart Secret 注入固定私钥**。

| 阶段 | 内容 | 仓库 | 验证点 | 状态 |
|------|------|------|--------|------|
| **PR-A** | L0 enabler：secret 渲染固定私钥 + auth-service 注入 `ENVIRONMENT`/`AUTH_REQUIRE_PERSISTENT_KEY` + keys.py fail-fast（支持 B64）+ values 默认（开关 false，向后兼容） | main | helm lint/template 通过；合并后行为不变（私钥空、开关 false） | ✅ 本次 |
| **PR-B** | L0 activate：生成固定 RSA 私钥 → env-repo staging `secrets.authRsaPrivateKeyPemB64` + `authService.requirePersistentKey:true` | env | ArgoCD sync 后 auth-service 加载持久私钥；**手动重启 pod → JWKS kid 不变 → 旧 JWT 仍有效**；登录可用 | ⏳ 待办 |
| **PR-C** | L1+L2+L3+L4：删 nginx/前端 fallback + 前端守卫 + 401 拦截 + 网关默认拒绝/401/require_admin·user 分离 + `authnEnforceAdmin` 开关 + cookie HMAC 独立密钥 + 登录限流 | main | 未登录访问 → 跳 /login；登录 → admin 功能正常；匿名调 admin API → 401/403；customer 侧不回归 | ⏳ 待办 |

**灰度顺序硬约束**：PR-B（私钥固定并验证 JWKS 稳定）**必须先于** PR-C（剥离 fallback + 强制）。否则临时密钥遇重启即全员掉线，叠加 fallback 移除会把管理员锁在门外。

**回滚**：
- PR-C 出问题 → chart `apiGateway.authnEnforceAdmin=false` 回退网关强制（前端守卫/删 fallback 为纯前端，回滚需重新发版，故 PR-C 上线前必须 staging 验证登录闭环）。
- PR-B 出问题 → env-repo 移除 `authRsaPrivateKeyPemB64` + `requirePersistentKey:false`，auth-service 回退临时密钥（会掉线，仅应急）。
- 应急运维入口：`kubectl port-forward` 直连 + 临时令牌，**不保留常驻共享令牌 admin 后门**。

## 六、对抗性自审（方案在何条件下失败）

1. **固定私钥泄露** → 全站 JWT 可伪造。缓解：私钥入 Secret、支持 `kid` 多密钥轮换、JWKS 只暴露公钥。
2. **白名单漏列**（`/api/direct/*` 数据面、`/ws`、health）→ 误伤功能。缓解：白名单显式枚举 + 全量 E2E 回归。
3. **内部脚本/监控依赖匿名 admin** → 切强制后 401。缓解：切前观察网关日志，灰度放量。
4. **customer 域被误伤**：默认拒绝只作用于 admin 域；customer 维持现有身份模型（阶段2 再做强认证）。
5. **私钥入仓保管**：遵循 env-repo 既有 `secrets.*` 约定（与 `internalApiToken` 同级），env-repo 访问受控；后续可演进至 cert-manager / 外部 KMS。

---

## 七、可观测性

- auth-service：私钥加载成功/失败、fail-fast 拒绝启动均打日志（含 `kid`，不含私钥）；登录成功/失败/锁定写 `auth_audit`（含 `trace_id`）。
- api-gateway：验签失败 401、匿名拒绝、共享令牌后门命中（强制开启前）打结构化日志（含 `trace_id`、`realm`、`actor`）。
- 全链路沿用既有 `trace_id` 透传，认证拒绝事件可按调用链回溯。
