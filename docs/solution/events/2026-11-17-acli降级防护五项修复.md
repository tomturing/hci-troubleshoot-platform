# 2026-11-17 acli 降级防护与分发证据五项修复

## 背景与需求

工单 Q2026111700614 取证闭环后的批量修复。事故链：terminal_bridge 自动同步把节点预装的
acli 1.0.3（build 2026-11-09）误判为"落后"，用官方 latest 源上的 1.0.0（build 2026-05-20）
`--install --force` **降级重装**；安装器重装时清理集群节点插件目录且分发不完整（47 节点
`plugins/log_collect/plugin` 只剩空目录），而安装结论只看发起节点本机 `acli --version`，
"安装成功"掩盖了空壳；随后 core 专项 create 持续报 LC-PLUGIN-016，证据上报接口又因
asyncpg 参数类型推断失败持续 HTTP 500。取证过程与 A/B 日志对照见记忆档与桥日志
（`acli_sync.*` 事件），本文只写结论与修复。

## 修复一：版本判定改有序比较，禁止降级（terminal_bridge/main.go）

旧判定 `!sameBuildDate(current, remote)` 只比较日期**是否相等**、不比新旧，两侧日期不同
即触发重装——预装新包因此被旧包降级。改为：

- 新增 `remoteBuildNewer(current, remote)`：两侧 buildDate 均为标准 `YYYY-MM-DD...`
  （长度 ≥10）且远端字典序更新才返回 true；任一侧为空或格式异常一律 false（保守跳过）。
- 版本分支只在 `remoteBuildNewer` 为真时装；日期不同但远端**不更新**时落
  `acli_sync.downgrade_blocked` 观测日志并跳过安装。`sameBuildDate` 保留供相等性判断复用。

边界：本次**不改**官方 latest 源地址（`defaultAcliDownloadURL*`）；平台侧源包与节点版本
对齐由维护者人工负责。

## 修复二：安装后逐节点插件落盘校验（terminal_bridge/acli_package.go）

安装器退出码 0 只证明发起节点装好，分发可能在其他节点静默留下空目录。新增：

- `buildPluginProbeCommand`：`[ -x '<logCollectPluginBinary>' ] && printf 'OK\n'`，判可执行
  而非仅判存在（空目录残骸/半包不算落盘）。
- `verifyClusterPluginLanding`：复用 spc 扇出原语逐节点探测（本机直连、远端 ssh
  BatchMode，并发上限 `spcFanoutConcurrency`），输出 `nodePluginState` 集合。
- 挂钩在本地版本验证成功之后：落 `acli_sync.node_plugin_verify`（逐节点事实）；有缺失
  则 `acli_sync.node_plugin_missing` WARN，并在 installed 结果 Message 追加
  「节点 X 的 log_collect 插件未落盘，请重试安装」。**只警示不整体判失败**——本地已
  成功时把整单判错会诱导用户重复重装，重跑安装器正是清目录的动作。

## 修复三：spc 目录重置观测与被清目录重建（terminal_bridge/log_collect_spc*.go）

重装会清掉平台写入 spc 清单的固定目录。按定档决策**不新增**跨服务主动重发通道：

- `buildSpcDirProbe` 改为"缺失即创建"：`[ -d dir ] || mkdir -p dir` 后回读存在性再回显
  路径；`pickSpcDir`/`spcResolveDir` 语义不变（固定路径、无 find）。
- `buildSpcPrepareCommand` 在历史备份自愈与备份之前前置 `mkdir -p`（target 父目录），
  保证被清目录在下发清单时自动重建，不再卡 `spc_dir_missing`。
- 安装成功后落 `acli_sync.spc_reset` WARN，并在 installed Message 追加「场景清单将在
  下次采集自动重新下发」——清单由 create 时的 spc 扇出重新签发，无需人工搬运。

## 修复四：probe 回传节点真实枚举 + 前端非阻塞版本警示

平台专项目录恒补白名单全集（10 项含 core），与节点 help 真实枚举解耦；降级后
core 不在节点枚举内仍可勾选，create 必被拒。修复保持"警示但保留可选"：

- bridge：新增 `parseLogCollectHelpModules`（只报 help 真实命中的白名单专项，不补全），
  probe 结果新增 `node_modules` 字段；白名单专项不在其中时 `catalog_note` 追加
  「节点 help 未列出专项 core，可能因版本不匹配被拒」，并随 probe 日志落库。
- 前端：`ModuleOption.helpListed=false` 的选项渲染"节点可能不支持"徽标与汇总提示行
  （`title` 提示补充语境），**不置灰、不禁用**；`node_modules` 随探测快照落库留证。
  只在 `catalog_source=acli_help` 且 `node_modules` 非空时标注——旧版 bridge 或内置
  兜底目录一律不标，避免把"探测降级"误报成"版本不支持"。

### 后续修正（2026-11-24：英文 help 长标签误报）

25 节点英文 help 的 `slowdisk`（51 字符）与 `other`（72 字符）说明标签超过
`logCollectModuleOptionRe` 原 `{1,40}` 上限，整条枚举匹配失败；`node_modules` 因此
缺项，前端把"卡顿专项""默认收集专项"误标为"节点可能不支持"。本次修正：

- 标签匹配上限放宽到 `{1,120}`；白名单 key 仍精确匹配，不放宽枚举值本身。
- `logCollectHelpEnumBlock` 增加实机英文标题 `enumerate:` 与收尾 `Note:`，英文 help
  不再退化为全量文本扫描；中文 `枚举值 … 说明` 路径与命中门槛保持不变。
- 回归测试锁定 25 节点真实英文枚举行与英文标题识别
  （`terminal_bridge/internal/logcollect/log_collect_test.go`）。

## 修复五：artifact-manifest 上报 500（case-service/routes/log_collect_evidence.py）

`UPDATE log_collect_task` 用 `jsonb_build_object('artifact_reason', :reason)` 拼 detail，
该参数是**多态 any**：`:reason` 只出现在这一处时 asyncpg 报
`IndeterminateDatatypeError: could not determine data type of parameter $2`（现场日志已
坐实）。对 `:quality` / `:reason` 显式 `CAST(... AS text)`；WHERE 中的同名参数比较保持
不变。回归测试断言任务 UPDATE SQL 必须含两个 text cast。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| help 漏列但实际支持的版本被警示"吓退"用户 | 只加徽标不禁用勾选；catalog_note 措辞为"可能" |
| 逐节点校验增加安装尾耗时 | 并发扇出 + 单机单步 30s 上限、总预算 2 分钟，只警示不阻塞结论 |
| mkdir -p 引入误建目录 | 仅平台自有固定路径；探测/择一语义未放开 |
| 官方 latest 源仍是旧包 | 本次不降级即可安全共存；源包对齐由维护者负责（决策已记录） |
