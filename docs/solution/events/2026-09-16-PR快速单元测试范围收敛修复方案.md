# PR 快速单元测试范围收敛修复方案

## 1. 第一性原理

同 [主干后端门禁按影响范围收敛方案](2026-09-16-主干后端门禁按影响范围收敛方案.md)，
但这次针对 PR 分支：一个 job 的每一步只该为「输入在本次变更内」的测试付费。

PR 上已经有 `scripts/ci/resolve_pr_fast_test_targets.py` 这一层收敛机制，问题是它的
判定把两类**不是 pytest 输入**的东西当成了必须完整回归的理由，并在一处隐式推导上
把范围收敛到了错误的目录。

## 3. 根因

### 3.1 `.github/workflows/` 被当成"测试基础设施"

判定规则把工作流改动与共享依赖并列升级为完整回归。但工作流文件**不是**任何
测试的输入：它决定「怎么跑 CI」，不决定「跑出什么」。本次 PR 只是顺带改了
`ci.yml`，就让整个 job 从"跑 2 个服务"变成"跑 8 个服务 + 两套 Go + preflight"。

### 3.2 多服务上限过严

`MAX_FAST_SERVICES = 1`：只要 PR 同时触及 2 个服务就升级为完整回归。而
`backend/shared/**` 这类真正的跨服务耦合已经由全局依赖规则覆盖，服务之间相互
独立，因此 2～3 个服务的直接回归在证据上是充分的。

### 3.3 服务到测试范围的映射是隐式推导，对 kb-service 失效

`_service_test_target()` 通过把路径中的 `/tests/` 换成 `/app/` 反推服务名，再取
该服务的 `tests/unit/` 目录。对 `kb-service` 而言：

- 完整路径跑的是 `backend/kb-service/tests/`（581 个用例，CI 58s）；
- `backend/kb-service/tests/unit/` 目录**存在但没有任何测试文件**（仅剩 `.pyc` 残留）。

于是 kb-service 变更的快速路径会收集到 0 个用例：pytest 以退出码 5 结束，PR 假
失败，而该服务真正需要的 581 个用例从未在快速路径中运行过。这是本次发现的两个
问题里更严重的一个——它既产生假失败，又产生静默漏测。

### 3.4 快速路径的时间上界与范围不匹配

快速路径用 `timeout 20s` 兜底。20s 在"单服务、单文件"时代是合理的预算，但一旦
允许 2～3 个服务（或包含 kb-service），它必然把合法变更打成失败。

## 4. 修复

1. **显式镜像表**：`SERVICE_TEST_SCOPES` 逐条对齐 `ci.yml` 完整路径中该服务的实际
   调用范围，`kb-service` 映射到 `backend/kb-service/tests`。新增服务必须同时更新
   此处与 `ci.yml`，并由单元测试守护该不变量。
2. **多服务上限 1 → 3**：`backend/shared/**` 等真正的跨服务依赖仍走完整回归，
   无法归属的服务、超限服务数、超限目标数一律失败关闭。
3. **非测试输入不参与计划**：`.github/**`、`docs/**`、`scripts/ci/**` 只改变 CI 的
   组织方式，既不进入快速计划，也不再触发完整回归。安全网在主干：这些路径不在
   `resolve_main_test_scope.py` 的白名单内，main push 仍会运行完整后端门禁。
4. **补齐被单测直接导入的脚本**：`backend/kb-service/tests/` 中
   `from scripts.evaluate_multi_agent_extraction import ...`，该脚本是测试输入，
   因此加入全局依赖，改动它必须完整回归（修复一个既有的漏测口）。
5. **判定顺序**：全局依赖判定作用于**完整**变更清单而非过滤后的清单，保证本脚本
   自身被修改时一定回退完整回归；已审计的信号公共层快速路径优先于通用前缀规则，
   不会被 `backend/shared/` 前缀吞掉。
6. **时间上界 20s → 240s**：范围才是收敛手段，上界只用于防止挂起。同时把解析器与
   其测试纳入 `ci.yml` 的 `release_ci` 校验清单，并补齐前端解析器此前缺失的同类接线。

- 对 PR #1052 的真实变更清单，判定从 `full` 变为 `targeted`：
  `backend/agent-service/tests/unit` + `backend/conversation-service/tests/unit`。
- 对 kb-service 变更，判定从"空的 `tests/unit`"变为 `backend/kb-service/tests`。
- `scripts/ci` 白名单内 15 个文件的 `ruff check` / `ruff format --check` 与 8 个测试

预计该 PR 类型的 unit-tests job 从 229s 降到约 40s，整轮 run 的关键路径转为
integration-tests（113s），即从 4m13s 降到约 2m。

## 6. 安全网与回滚

- `unit-tests` 是 required context，名称与报告方式不变；判定为 `none` 时 job 整体
  `skipped`，与既有纯前端 PR 的行为一致（例如 #1051）。
- `.github/**`、`scripts/ci/**` 变更在 main push 上仍要求完整后端回归，合并后 2 分钟
  内即可获得完整证据；判定误跳过时可用 `workflow_dispatch` 手动触发完整门禁。
- 回滚方式：还原 `resolve_pr_fast_test_targets.py` 的 `MAX_FAST_SERVICES` /
  `NON_TEST_INPUT_PREFIXES` 与 `ci.yml` 的 `timeout` 即可恢复改前行为，无需数据迁移。

## 7. 遗留观察（不在本次范围）

1. kb-service 58.1s 的根因已定位并修复，见 §8，不再列为遗留项。
2. 本次修复后 `integration-tests`（113s）将成为 PR run 的新关键路径，是下一轮优化
   的候选。
3. `deploy/**` 目前既不在快速路径的白名单里，也不在失败关闭触发条件里，而
   `unit-tests` 中的 `config-contract-check` 会读取 Helm/Compose 输入。已在 §9.2

## 8. 补充修复：kb-service 58.1s 的真实根因（覆盖率追踪放大）

§2.3 中「CI 58.1s vs 本机 2.7s」曾被读成环境差异。实测发现两列口径不同：CI 的完整
回归带 `--cov=backend`，本机对照未开覆盖率。加上覆盖率后，同一套件在本机也能复现
21 倍，因此这不是 CI 环境问题，也不是测试本身慢。

### 8.1 证据链（本机，同一 581 用例集合）

| 条件 | 耗时 |
|---|---|
| `-n0` 无插桩 | 1.38s |
| `-n auto` 无插桩 | 2.71s（xdist 对"581 个极快用例"是负收益） |
| `-n auto` + `--cov=backend` | 31.05s |
| `-n0` + `--cov=backend` | 29.02s |
| `-n0` + `--cov=backend/kb-service`（缩小范围） | 28.91s |
| `-n0` + `--cov=backend`，排除 `test_jieba_hci.py` | **2.78s** |
| `test_jieba_hci.py` 单独跑，无插桩 | **0.26s** |

`--durations=12` 把耗时收敛到单点：
`test_jieba_hci.py::test_segment_splits_chinese_query_into_search_tokens` 占
**26.11s / 28.87s**；`cProfile` 进一步定位到
`jieba/finalseg/prob_emit.py:1(<module>)` 自身耗时 **26.024s**。

### 8.2 根因

`jieba/finalseg/prob_emit.py` 是 1.32 MB、35226 行的模块级字典字面量（HMM 分词的
发射概率表）。代价不在编译而在逐行执行：

- 无插桩导入：**0.01s**；
- coverage 追踪下导入：**25.51s**（约 2551 倍）。

`segment()` 调用的 `jieba.lcut(..., cut_all=False)` 走 HMM，首次调用即导入
`finalseg`，于是首个触达该路径的测试在插桩进程内一次性支付 25s。CI runner 单核性能
更低，实测放大约 55s，正好解释 kb-service 的 58.1s；其余套件不导入 jieba（全仓仅
kb-service 使用，已 `grep` 确认），所以只有它是异常值。

### 8.3 修复与收益

在 `ci.yml` 的 kb-service 批次把该文件移出插桩运行，并单独补一次不带覆盖率的调用：

```yaml
uv run pytest backend/kb-service/tests/ \
  --ignore=backend/kb-service/tests/test_jieba_hci.py \
  -x -q \
  --cov=backend --cov-report=xml --cov-report=term-missing --cov-append \
  -m "not integration and not slow"
uv run pytest backend/kb-service/tests/test_jieba_hci.py \
  -x -q --no-cov \
  -m "not integration and not slow"
```

- 用例仍全量执行、断言不变（本机实测 `2 passed, 0.26s`）；
- 覆盖面不缩水：jieba 属三方库，本就不计入 `backend` 覆盖率；被移出插桩的只有
  `app/utils/jieba_hci.py` 中由该文件独占的少量行；
- `config-contract-check` 与 `--cov-fail-under=60` 不受影响（后者作用于合并后的总体
  覆盖率）。

本机按上述两条命令实测：批次一 `579 passed, 4 skipped in 5.77s`、批次二
`2 passed in 1.08s`，合计 581 个用例仍全量执行（批次一的 skipped 比整目录少 3 个，
是被 `-m` 过滤掉的 integration 用例，非漏跑）。预计 CI 上 kb-service 批次从 58.1s
降到约 10～15s（本机 7.4s × CI 约 2 倍系数），完整单测步骤的最大单项被移除。

同时修正 PR 快速路径上方的注释：原文"kb-service 单独就要 58s"把覆盖率开销误当成测试
开销，而快速路径本就带 `--no-cov`，无插桩下该套件约 0.3s。

### 8.4 顺带落地的两项 CI 优化（同批）

1. **覆盖率报告只在最后一批渲染**：8 次 pytest 调用原本每次都带
   `--cov-report=xml --cov-report=term-missing`。`--cov-append` 已把数据累积进
   `.coverage`，前 7 批重复渲染是纯开销，而 codecov 消费的只是最后一次产出的
   `coverage.xml`；现在前 7 批只保留 `--cov=backend --cov-append`。本机冒烟验证：
   前批不带 report、末批带 report 时仍正常产出 `coverage.xml`（871 KB、213 个文件、
   line-rate 0.6339）。
2. **除 agent-service 外卖闭 xdist**：`pyproject.toml` 的 `addopts` 默认 `-n auto`，
   但这些套件的固定成本（worker 启动 + 每个 worker 重复导入与 conftest）高于并行
   收益。同一用例集合的对照实测（左 `-n0`／右 `-n auto`，秒）：`tests/unit`
   1.95↔3.08、`api-gateway` 8.00↔11.92、`case-service` 0.58↔1.74、`conversation`
   1.35↔2.47、`kb-service` 1.94↔2.97、`diagnosis` 9.34↔11.69、`scheduler`
   0.71↔2.00；仅 `agent-service` 4.57↔4.33 为平局，保留默认并行。合计约
   40.2s → 28.4s（本机 -29%）。某套件若在 CI 上反向变慢，删掉该行的 `-n0` 即可回到
   默认。

仍在观察：CI 每个套件有 6～12s 与用例数无关的固定开销（scheduler-service 仅 9 个
用例却 12.4s），来自进程启动、`uv run` 环境校验与覆盖率收尾。

## 9. 同批落地：`database/**` 假绿、`deploy/**` 零门禁与 Go 块拆分

§7.3 列出的三处结构性缺口在同批修复，共同判据是同一句第一性原理：**触发条件必须由
输入决定**——既不因为「顺带改了 CI 配置」而放大，也不因为「输入不在 backend filter 内」
而缩小到零。

### 9.1 A：`database/**` 由 `none` 回退完整回归

**根因**：`database/**` 在 `ci.yml` 的 `backend` filter 内，所以纯 schema PR 会启动
`unit-tests`；但快速计划对它没有映射（既不是 pytest 输入，也不是 `backend/*.py`），于是
落到「未修改 Python 测试或后端源码」分支被判为 `none`——job 变绿，一个用例都没跑。

**为什么既有 DB 门禁不足以覆盖**：`db-migration-test.yml`（DB Schema 声明式验证）确实按
`database/` 路径触发，但它只回答「DDL 能否应用」，既不验证服务与测试对新 schema 的
兼容性（`desired_schema.sql` 与 seeds 被 diagnosis-service 单测、kb/agent 样例契约测试
直接读取），也不在 ruleset 的必需检查内（`main-branch-protection` 只要求 Lint /
前端检查 / unit-tests / security-tests / integration-tests / docs-governance），
因此它无法阻断合并。

**修复**：把 `database/` 加入 `GLOBAL_DEPENDENCY_PREFIXES`。它满足全局依赖的定义（可能
影响任意服务的测试），无需新增特殊分支，同时让必需检查 `integration-tests`（会
`make db-sync` 把 schema 应用到真实 PostgreSQL）随之启动。

**代价与口径**：该类 PR 的关键路径从约 30s 变为完整回归的 `unit-tests`（约 170s）。这是
把「非阻断的声明式验证」升级为「阻断式完整回归」的必要代价，schema 变更频率低，可接受。

### 9.2 B：`deploy/**` 的配置契约按自身输入触发

**根因**：`config-contract-check` 读取 `.env.example`、`deploy/docker/docker-compose.yml`、
`deploy/helm/hci-platform/{values.yaml,templates}`，但这些路径都不在任何 filter 内
（`deploy/**` 与 `.env.example` 从未被登记）。于是 PR 只改部署配置时 `unit-tests` 整体
skipped，契约校验一次都不跑；主干侧虽被 `resolve_main_test_scope.py` 兜住（`deploy/`
不在其白名单内），PR 侧完全裸奔。

**修复**：新增 `deploy_config` filter（覆盖上述全部输入，外加校验器自身），并在
`unit-tests` 的 job 级 `if` 追加一个析取项。这类 PR 的 `unit_test_mode` 为 `none`，因此
job 只执行「校验部署配置契约」一步（其余步骤各自的 `if` 会按 mode 跳过），该步骤 CI
实测仅 2～3s，job 整体约 30s。

**为什么复用 `unit-tests` 而不是新建 job**：`unit-tests` 已是必需状态检查，而新建 job
的名字不在 ruleset 内，改不动 ruleset 就无法阻断合并；复用也避免了同一校验的重复执行。

### 9.3 C：Go 验证拆分为独立 job

**根因**：Go 验证（实测 `安装 Go` 14s + hci_sim 33s + offline-collector 4s ≈ 51s）挂在
`unit-tests` 内，它既不使用 uv 也不使用 `.venv`，却让 Python 回归的关键路径为它排队；
同时 `hci_sim/**` 与 `offline-collector/**` 都不在 `backend` filter 内，纯 Go 变更的 PR
既不启动 `unit-tests`，也没有任何 Go 校验。

**修复**：新增 `go-checks` job（`needs: [changes]`，按 `go_code` filter 触发；Merge Queue
与手动触发保持无条件执行，与 `unit-tests` 的合并队列语义一致），步骤逐条搬运、断言与
构建参数不变；`unit-tests` 不再安装 Go。两者并行，于是 Go 变更首次获得真实门禁，同时
不再占用 Python 关键路径。

**门禁接线**：`release-metadata` 与 `prepare` 的 `needs` 增加 `go-checks`，判定取
`success || skipped`：Go 输入未变更时 skipped 不是证据缺失，不构成阻断理由；但跑过就
必须成功，主干上 Go 变更无法在验证失败时晋级。

| 项 | 改前 | 改后 |
|---|---|---|
| `unit-tests` 内 Go 相关步骤 | 51s（含 setup-go 14s） | 0（迁移到并行 job） |
| 纯 Go 变更 PR 的 Go 验证 | 无（不启动任何 job） | `go-checks`（约 76s，与 unit-tests 并行） |
| Go 无关的完整回归 | 支付 51s | 0 |

### 9.4 验证

- `resolve_pr_fast_test_targets.py` 新增 3 个用例（纯 schema、纯种子、schema+服务混合），
  合计 22 个用例通过；实测纯 schema 变更判定由 `none` 变为 `full`。
- `ruff check` / `ruff format --check` 覆盖 `release_ci` 白名单 15 个文件全部通过；
  `scripts/ci` 8 个测试文件共 82 个用例通过。
- `ci.yml`（16 个 job）通过 YAML 解析与 job/needs 引用完整性校验。

### 9.5 回滚

三项互相独立，均可单点回滚：A 删除 `GLOBAL_DEPENDENCY_PREFIXES` 中的 `database/`；B 删除
`deploy_config` filter 与 `unit-tests` `if` 中的析取项；C 把两个 Go 步骤搬回 `unit-tests`
并删除 `go-checks` 及两处 `needs`/`if` 判定。无数据迁移，不涉及覆盖率口径与 required
context 名称。
