## 一、第一性原理拆解

把两个故障还原到不可再分的事实：

1. **会话存在性只有桥知道。** 桥的会话键是 `caseID@nodeIP`，一切 log_collect 动作必须路由回「pty 正在运行的那台机器」。前端显示的「已连接」只是「SSH 终端连接上一次收到 connected」的推断，不是「会话现在存在」的事实——两者之间没有任何确认机制。
2. **状态陈旧的后果由第一个失败请求揭示。** 无论 `ssh_disconnected` 事件是否送达，桥在会话缺失时对每个动作都会秒级返回 `LC-ENV-006`。这个结果码本身就是「会话已不存在」的权威判定，比事件是否送达更可靠。
3. **中继失败时包已经生成。** 节点侧采集成功的压缩包是不可再生产的成果；失败发生在「搬运」环节。搬运的瞬时失败（网络抖动、5888 暂不可达）与「无货可搬」（无制品/空文件）是两类完全不同的问题，不应共用同一种结局。

由 2、3 直接推出两条硬约束：

- **C1：UI 状态必须能被权威判定纠正。** 只要有「会话不存在」的权威结论到达前端，状态就必须立即归位，不能等下一次人工操作才暴露。
- **C2：重试的判定标准是错误类别，不是发生位置。** 网络类异常与 5xx 可重试；「无制品 LC-TRANSFER-001」「空文件 LC-TRANSFER-002」与 4xx 重试必然同样失败，必须立即落终态。

## 二、现场事实（2026-10-28）

| 事实 | 说明 |
|---|---|
| 8×/天 LC-ENV-006 | 全部为 P2 中继路径，create 阶段秒级失败；probe 曾在 2 分钟前成功，说明是会话中途消失而 UI 未感知 |
| 采集成功后交付判 failed | 采集成功生成 37 MB 包，中继 5888 不可达，`run()` 对任何异常一律 `_finish(failed)`，包被判死且无法自愈 |

## 三、修复设计

### 前端：按钮禁用 + 结果码自愈（LogCollectPanel.vue）

1. 「开始收集」按钮 `disabled` 增加 `!sshConnected`，文案切换「请先连接 SSH」——把点击后的 toast 前置成秒级视觉反馈。
2. `handleMessage` 是全部 `log_collect_result`（probe/create/progress）的单一收口。在此处判定：`error_code === 'LC-ENV-006'` 且当前为 `connected` 时，立即置 `sshConnectionState = 'disconnected'`。以桥的权威判定为准，不依赖 `ssh_disconnected` 事件是否送达；采集自身失败不携带该码，不会误清状态。

### 后端：中继瞬时错误退避重试（log_collect_relay_service.py）

1. `__init__` 新增 `max_attempts=3 / retry_base_delay=2.0 / retry_max_delay=30.0`（向后兼容，默认即启用重试）。
2. 新增 `_is_transient()`：`httpx.TimeoutException / ConnectError / TransportError` → 瞬时；`HTTPStatusError` 5xx → 瞬时、4xx → 永久；`SangforRelayError` 保留原始 code，仅 `LC-TRANSFER-001/002` 判永久。
3. `run()` 重写为重试循环：瞬时错误指数退避（封顶 30s）后重试，`_run` 复用持久化 `upload_id` 续传已完成分片；期间不调 `_finish`，`relay_status` 保持 `running`。仅永久错误或重试耗尽才 `_finish(failed)`，错误码保留异常原始分类。

## 四、为什么不选其他方案

- **后端 create 前加会话校验**：校验的仍是前端以为的状态，且 `create_task` 无法感知桥内存会话，治标不治本。
- **桥广播 ssh_disconnected 到所有连接**：改动面大（连接生命周期与订阅语义），且无法覆盖「事件发出时面板 WS 尚未建立」的窗口；以结果码自愈只需一处收口。
- **中继失败即 failed + 人工重发**：现场证明用户不会重发，包白白判死；且人工重发触发全量重传，续传能力被浪费。
