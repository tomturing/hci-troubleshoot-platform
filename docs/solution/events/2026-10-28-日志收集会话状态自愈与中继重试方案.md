## 一、第一性原理拆解

把两个故障还原到不可再分的事实：

1. **会话存在性只有桥知道。** 桥的会话键是 `caseID@nodeIP`，一切 log_collect 动作必须路由回「pty 正在运行的那台机器」。前端显示的「已连接」只是「SSH 终端连接上一次收到 connected」的推断，不是「会话现在存在」的事实——两者之间没有任何确认机制。
2. **状态陈旧的后果由第一个失败请求揭示。** 无论 `ssh_disconnected` 事件是否送达，桥在会话缺失时对每个动作都会秒级返回 `LC-ENV-006`。这个结果码本身就是「会话已不存在」的权威判定，比事件是否送达更可靠。
3. **中继失败时包已经生成。** 节点侧采集成功的压缩包是不可再生产的成果；失败发生在「搬运」环节。搬运的瞬时失败（网络抖动、5888 暂不可达）与「无货可搬」（无制品/空文件）是两类完全不同的问题，不应共用同一种结局。

由 2、3 直接推出两条硬约束：

- **C1：UI 状态必须能被权威判定纠正。** 只要有「会话不存在」的权威结论到达前端，状态就必须立即归位，不能等下一次人工操作才暴露。
- **C2：重试的判定标准是错误类别，不是发生位置。** 网络类异常与 5xx 可重试；「无制品 LC-TRANSFER-001」「空文件 LC-TRANSFER-002」与 4xx 重试必然同样失败，必须立即落终态。

## 二、现场事实（2026-10-28）

| 事实 | 说明 |
|---|---|
| 8×/天 LC-ENV-006 | 全部为 P2 中继路径，create 阶段秒级失败；probe 曾在 2 分钟前成功，说明是会话中途消失而 UI 未感知 |
| 采集成功后交付判 failed | 采集成功生成 37 MB 包，中继 5888 不可达，`run()` 对任何异常一律 `_finish(failed)`，包被判死且无法自愈 |

## 三、修复设计

### 前端：按钮禁用 + 结果码自愈（LogCollectPanel.vue）

1. 「开始收集」按钮 `disabled` 增加 `!sshConnected`，文案切换「请先连接 SSH」——把点击后的 toast 前置成秒级视觉反馈。
2. `handleMessage` 是全部 `log_collect_result`（probe/create/progress）的单一收口。在此处判定：`error_code === 'LC-ENV-006'` 且当前为 `connected` 时，立即置 `sshConnectionState = 'disconnected'`。以桥的权威判定为准，不依赖 `ssh_disconnected` 事件是否送达；采集自身失败不携带该码，不会误清状态。

### 后端：中继瞬时错误退避重试（log_collect_relay_service.py）

1. `__init__` 新增 `max_attempts=3 / retry_base_delay=2.0 / retry_max_delay=30.0`（向后兼容，默认即启用重试）。
2. 新增 `_is_transient()`：`httpx.TimeoutException / ConnectError / TransportError` → 瞬时；`HTTPStatusError` 5xx → 瞬时、4xx → 永久；`SangforRelayError` 保留原始 code，仅 `LC-TRANSFER-001/002` 判永久。
3. `run()` 重写为重试循环：瞬时错误指数退避（封顶 30s）后重试，`_run` 复用持久化 `upload_id` 续传已完成分片；期间不调 `_finish`，`relay_status` 保持 `running`。仅永久错误或重试耗尽才 `_finish(failed)`，错误码保留异常原始分类。

## 四、为什么不选其他方案

- **后端 create 前加会话校验**：校验的仍是前端以为的状态，且 `create_task` 无法感知桥内存会话，治标不治本。
- **桥广播 ssh_disconnected 到所有连接**：改动面大（连接生命周期与订阅语义），且无法覆盖「事件发出时面板 WS 尚未建立」的窗口；以结果码自愈只需一处收口。
- **中继失败即 failed + 人工重发**：现场证明用户不会重发，包白白判死；且人工重发触发全量重传，续传能力被浪费。

## 五、v1.1 补强：代传租约（发布/重启后的自愈）

v1.0 解决了「网络抖动」这一类失败，但没解决「执行者本身消失」：`relay_status=running` 只是写在 DB 里的一句声明，写它的进程可能在下一毫秒就被发布杀掉了。

### 根因

case-service 用 Recreate 发布（RWO 卷约束，见 chart 注释），旧 Pod 被 SIGTERM/SIGKILL 后：

1. 进程内的 `asyncio.Task` 随之消失，没有任何人把 `relay_status` 写成终态；
2. 前端 `pollRelay` 只认「不是终态就继续等」，于是空转到 2 小时上限才提示「结果未知」；
3. 用户点「上传到平台」→ `/deliver` 只拦 `pulling/uploading/relaying`，`queued` 被放行 → 重传整包 → complete 后 `trigger()` 因 `running` 返回 `started=false` → 代传依旧不启动，形成闭环死锁。

### 设计：把「running」从声明升级为租约

| 机制 | 位置 | 语义 |
|---|---|---|
| 心跳续租 | `run()` 内独立协程，默认 30s 一次 | 只在仍为 `running` 时刷新 `relay_updated_at`；被终态或别人接管则自动停 |
| 抢占 | `trigger()` 的 `_claimable()` | 除 `none/pending/failed` 外，**未带 force 也允许抢占「running 且心跳超过 `LOG_COLLECT_RELAY_STALE_SECONDS`（默认 120s）」** |
| 启动接管 | `lifespan` → `reconcile_relays_on_startup()` | 只捞**有制品**（`archive_path` 非空）的 `pending` 与租约过期 `running`，逐个 `trigger` 抢占后重跑；无制品者抢过来只会立即 LC-TRANSFER-001，属自毁 |
| 退出交还 | `shutdown_relays()`（关库之前） | 取消在飞任务并把 `running` 置回 `pending`，让下一个实例接管；**不写 failed**——任务并未得出「归档失败」的结论，5888 侧会话还有 24h 有效期 |
| 快照标记 | `snapshot()['stale']` | 前端据此判断「该发一次强制续跑」，而不是干等 2 小时 |

### 前端配套（`services/logCollectRelay.ts`）

`pollRelay` 每轮拿到快照后，若 `relay_status=running && stale=true` 且本轮尚未发过，则调用 `startRelay(taskId, true)` 触发一次强制续跑，**每轮轮询只发一次**，避免轮询风暴与多标签页互相夺权。强制续跑只重放搬运（`upload_id` 与已传分片均已落库），不重传数据；真正的抢占仍由服务端 `trigger(force)` 原子裁决，多客户端同时判定也只会有一个真正启动。

### 对抗性审查：这套方案在哪里会失效

| 失效条件 | 后果 | 兜底 |
|---|---|---|
| 心跳协程本身被调度饿死超过 120s | 健康任务被误判过期，两个实例同时跑同一包 | 5888 分片写按 `chunk_index` 幂等覆盖，重复上传不产生坏包，只是浪费带宽 |
| 进程被 SIGKILL，`shutdown_relays()` 没机会执行 | `pending` 写不进去 | 租约过期是同一个兜底；重启后启动接管从 `running+过期` 捞回 |
| 老记录 `relay_updated_at` 为 NULL | 无法判断存活 | `_expired(None)` 返回 true，视为过期可抢占（否则永远占位） |
| 多副本/多 worker 同时启动接管 | 同时抢同一任务 | `trigger` 是单条 `UPDATE ... WHERE relay_status 可抢占`，`rowcount=1` 才算抢到 |
| 5888 侧会话已过期（>24h） | 续传 404 | `upload_status` 返回 None → 重新 `init_upload`，`relay_restarts` 递增 |
