## 〇、结论摘要

1. **交付路径只有两条：P1 与 P3**。原设计中的 P2（HCI 直传平台）**已废弃**，因为 5888 与平台同处公网侧，可达性同源，不存在"HCI 到不了 5888 但能到平台"的独立区间。
2. **P1 平台不留副本**，仅记录任务状态与插件上报结果；**P3 平台保留副本，并负责代传 5888**（5888 是最终归档地）。
3. **平台不做任何自动清理**，也不提供删除 API；只做检测、弹框告警、给出可执行的清理命令，删除由用户（HCI 侧）或运维（平台侧）执行。
4. **断点续传分三段，三段均可续**：①HCI→PC 用 `rsync --append-verify`；②PC→平台 用分片位图；③平台→5888 已通过 `/acli` 源码确认支持旧 `upload_id` 续传（会话保留 24h、重传同 `chunk_index` 幂等）。
5. **HCI 存在 `TMOUT=600`**：交互式 shell 10 分钟无输入即退出。长任务因此**禁止绑定持久 shell**，必须使用单命令 `Run` 或 SFTP 子系统。

## 二、路径模型：P1 / P3 二分

### 2.1 为什么没有 P2

曾设计的 P2 条件为「HCI 到不了 5888 但能到平台」。该条件在真实拓扑中不成立：

| 事实 | 推论 |
|---|---|
| 5888 使用官方域名 `http://acli.sangfor.com.cn:5888/` | 与平台同处公网侧 |
| 二者共享同一条出口路径 | 能到平台 ⇒ 能到 5888 |
| 插件上传白名单硬编码 6 个官方 URL | 不受客户内网地址影响 |

因此判据收敛为单一二元问题：**HCI 能否出公网访问 5888**。是 → P1；否 → P3。

### 2.2 两条路径的契约

| 维度 | P1 | P3 |
|---|---|---|
| 触发 | 5888 可达 | 5888 不可达 |
| 链路 | HCI ─`acli -u`─► 5888 | HCI ─SFTP─► 客户 PC ─分块─► 平台 ─代传─► 5888 |
| 平台角色 | 只记状态，不接触数据 | 保留副本 + 代传 5888 |
| 平台存储占用 | 0 | 约等于包体（2–20 GiB / 任务） |
| HCI 出网要求 | 需要 | **不需要** |
| 客户 PC 占用 | 0 | 临时磁盘 ≥ 1.1× 包，双段带宽 |
| 完成判据 | `progress` 中「发送地址 + 状态：成功」 | 平台收包校验通过 **且** 5888 收齐并确认归档（会话消失） |
| 完整性凭证 | 无（包已被插件删除） | 源包 sha256 + 平台副本 sha256 |

**P1 的固有局限（必须向客户如实说明）**：插件上传全部成功后执行 `os.remove(zip)`，平台既拿不到包，也拿不到 `size/sha256`，无法做完整性校验，仅能以 `progress` 文本作为成功凭证。

### 2.3 对 PR-3b 的修正

PR-3b 中 `upload_mode` 的枚举 `acli_direct / platform_direct / bridge_relay / none` 需要收敛：

| 原值 | 处置 |
|---|---|
| `acli_direct` | 保留，语义等同 P1 |
| `platform_direct` | **废弃**（对应已删除的 P2） |
| `bridge_relay` | 保留，语义等同 P3 |
| `none` | 保留（不上传，仅本地采集） |

**不新增路径字段**：`acli_direct` 天然等价 P1，`bridge_relay` 天然等价 P3，语义已足够。因此只移除 `platform_direct`（迁移中把历史值回填为 `acli_direct`），不引入 `path_mode`，避免双字段并存与回填歧义。

## 四、端到端流程

### 4.1 P1

```
1. probe        uname -m / acli --version / curl 5888 / df
2. 判定          5888 可达 → upload_mode=acli_direct
3. create       acli log_collect create -s <ticket> ... -u http://acli.sangfor.com.cn:5888/
                （异步下发，秒级返回，SSH 连接可立即释放）
4. 轮询         acli log_collect progress（单命令，5s 间隔）
                → 解析「压缩包路径」「发送地址」「状态」
5. 终态         状态=成功 → completed
                状态=失败 → 包仍在本地 → 可降级 P3（需 bridge 在线）
```

说明：P1 全程**不需要长连接**。`create` 与 `progress` 均为单命令，采集与上传由 HCI 后台进程完成。

### 4.2 P3

```
1. probe          5888 不可达 → upload_mode=bridge_relay
2. create         同 P1，但**不带 -u**（避免插件尝试失败上传）
3. 采集完成       progress 显示 100%，zip 位于 /sf/data/local/acli/tmp/data/log_collect/<ticket>.zip
4. 段①  HCI→PC    rsync（或 SFTP Seek）拉取，断点靠 --partial/offset
5. 段②  PC→平台   HTTPS 分块 32 MiB，断点靠 uploaded_parts
6. 段③  平台→5888 复刻 init_upload/upload_chunk，断点靠 upload_id + chunk_index
7. 终态           平台有副本 + 5888 收齐且归档确认 → completed
                  平台有副本 + 5888 失败 → archived_only
```

P3 的 `create` 不传 `-u`：避免插件开启一条注定失败的 20 GiB 上传（浪费 27 分钟并可能留下半成品会话）。

## 五、状态机与终态

在 PR-3b 主干上增补 P3 的三个阶段：

```
P1: probing → collecting → uploading → completed
                                    └→ failed ⇒（包保留）→ 降级 P3 / 超时告警

P3: probing → collecting → pulling → uploading_platform → relaying → completed
                                                            └→ archived_only
```

终态定义：

| 终态 | 含义 | 展示 |
|---|---|---|
| `completed` | 5888 确认成功（P1 直传或 P3 代传） | 绿 |
| `archived_only` | 平台有副本，5888 未成功 | 黄 + 告警 + 重试入口 |
| `failed` | 采集或搬运阶段失败 | 红 |
| `cancelled` | 用户取消 | 灰 |

补充约束（继承 PR-3b）：

- 终态不可复活；`completed` 强制 `progress=100`。
- `archived_only` **不得**被任何逻辑自动提升为 `completed`，只能由代传结果驱动。
- 进度在 P3 各阶段内部按 `offset/part/chunk` 计算，**阶段间必须单调**。

## 六、断点续传

### 6.1 三段划分

| 段 | 传输 | 断点手段 | 可控性 | 单段耗时（20 GiB @100Mbps） |
|---|---|---|---|---|
| ① HCI → PC | rsync / SFTP | `--partial --append-verify` / `Seek(offset)` | 高 | ≈ 27 min |
| ② PC → 平台 | HTTPS 分块 32 MiB | `uploaded_parts` 位图 | 高 | ≈ 27 min（640 片） |
| ③ 平台 → 5888 | HTTP 分块 10 MiB | `upload_id` + `chunk_index` | **低** | ≈ 30 min（2048 块，含 sleep 开销） |

### 6.2 段①：HCI → 客户 PC

首选 rsync（HCI 实测存在，插件向仲裁节点分发即使用 rsync）：

```bash
rsync -av --partial --inplace --append-verify --bwlimit=20480 \
  root@<hci>:/sf/data/local/acli/tmp/data/log_collect/<ticket>.zip \
  <local_tmp>/log-collect/
```

| 参数 | 作用 |
|---|---|
| `--partial` | 保留半成品，中断不丢弃 |
| `--inplace` | 原地写，避免 2 倍磁盘占用 |
| `--append-verify` | 从断点续传并校验已有部分（需读取全部已传字节） |
| `--bwlimit` | 限速，避免打满客户内网 |

Windows 环境（bridge.exe）无 rsync 时，使用 SFTP `Seek(offset)` + `io.Copy`，`offset` 取自平台记录。

持久化频率：每 64 MiB 上报一次 `pull_offset`，避免 RPC 风暴。

### 6.3 段②：客户 PC → 平台

复用诊断服务的 multipart 协议（已在线验证）：

```
POST /api/log-collect/tasks/{task_id}/uploads          → upload_id, chunk_size, part_count
PUT  /api/direct/log-collect-uploads/{upload_id}/parts/{n}   （X-Upload-Token, X-Part-SHA256）
GET  /api/log-collect/tasks/{task_id}/uploads/{upload_id}    → uploaded_parts[]
POST /api/log-collect/tasks/{task_id}/uploads/{upload_id}/complete
```

约束：

- `init` 必须幂等（`UNIQUE(task_id)` 返回既有会话），否则重连产生孤儿分片；
- 数据面走 `direct` 路径，绕过 API Gateway 的 1 MiB / 10 MiB 限制；
- 分片幂等覆盖（先写 `.tmp` 再 `os.replace`）；
- 单块除最后一片外必须等于 `chunk_size`。

### 6.4 段③：平台 → 5888

协议见 §三 事实 4/5。设计要点：

```
持久化：relay_upload_id / relay_chunk_index / relay_chunk_total / relay_restarts

恢复：
  1. GET /upload_status/{relay_upload_id}
       200 → 会话有效，从 relay_chunk_index + 1 继续
       404 → 会话已过期或已归档，重新 init，chunk_index = 0，relay_restarts += 1
  2. 每块成功后**立即**持久化 chunk_index（不可批量）
```

**续传语义已在服务端源码确认**（`/acli/app.py`、`/acli/process_upload.py`）：

| 问题 | 结论 | 依据 |
|---|---|---|
| 旧 `upload_id` 可否续传 | **可以** | `upload_chunk` 仅校验会话存在且未过期，不要求从 0 开始 |
| 同 `chunk_index` 重传 | **幂等** | 分片 `{upload_id}_chunk_{index}.part` 覆盖写；`if key not in chunks` 才累加 `uploaded_size` |
| 会话保留时长 | **24 小时**（`SESSION_EXPIRE_HOURS = 24`），每次成功上传刷新 `last_updated` |
| 过期后行为 | 400 `Invalid or expired upload ID`，同时删除会话与全部分片 |
| 单文件上限 | **100 GiB**（`MAX_FILE_SIZE`），20 GiB 无风险 |
| 分片大小 | **10 MiB**（`CHUNK_SIZE`），以 `/init_upload` 返回值为准 |
| 上传鉴权 | 生产未启用（`/upload_status` 返回 404 而非 401，说明 `ACLI_UPLOAD_TOKEN` 未配置） |
| 归档路径 | `/sf/log/{工单号}/{工单号}.zip`，保留 ≥180 天（`COMPLIANCE_MIN_DAYS`） |

#### 6.4.1 三条必须遵守的服务端行为

1. **`status: "complete"` 仅代表「收齐并派发」**，不是归档完成。合片 + MD5 + move 由 `process_upload.py` 异步执行，失败只写 `fail_log`，不回传客户端。
2. **归档完成后服务端删除会话 JSON**。因此可用 `GET /upload_status/{upload_id}` 判定：`404` 且此前已收到 `complete` = 归档完成（需与 24h 过期窗口区分）。
3. **`complete` 之后不得再传任何分片**。异常分支只清理分片文件、不删会话，`chunks` 计数仍为满；再传任意一片会再次返回 `complete` 并重复派发，而后台必然失败。

### 6.5 持久化字段

| 字段 | 含义 | 写入频率 |
|---|---|---|
| `upload_mode` | `acli_direct`(P1) / `bridge_relay`(P3) | 任务创建 |
| `pull_offset_bytes` | 段① 已拉取字节数 | 每 64 MiB |
| `pull_sha256` | 段① 完成后源包哈希 | 段① 完成 |
| `relay_upload_id` | 段③ 会话 | init 时 |
| `relay_chunk_index` | 段③ 最后成功块（0 基） | **每块成功后立即** |
| `relay_chunk_total` | 段③ 总块数 | init 时 |
| `relay_restarts` | 段③ 重新 init 次数 | 每次重开 |

段② 的续传状态**不落库**：分片以 `/var/lib/log-collect/multipart/{upload_id}/` 目录为准，`upload_id` 由 `task_id` 派生，已传进度由目录项数计算。

### 6.6 恢复流程

| 中断源 | 恢复依据 | 动作 |
|---|---|---|
| bridge 重启 / PC 关机 | `pull_offset_bytes` 或 `uploaded_parts` | 重连后 `GET task` 取断点续传 |
| 平台 Pod 重启 | 全部落库 | worker 扫描 `pulling / uploading_platform / relaying` 重新调度 |
| 网络抖动 | 当前段 | 段① rsync 自动；段② 重试 3 次；段③ 按 §6.4 判定 |
| SSH 断开 | 不影响，见 §七 | 重新建连后继续 |

三段的重放必须幂等：`init` 幂等、分片覆盖写、`upload_chunk` 依赖服务端幂等。

### 6.7 不可续传场景（fail-fast）

| 场景 | 检测 | 处置 |
|---|---|---|
| HCI 源包被清理 | 续传前 `stat` 尺寸/时间不符 | `LC-TRANSFER-001`，提示重新采集 |
| 源包内容变化 | 首片 sha256 与记录不符 | 终止并要求重采 |
| 平台会话过期 | `GET upload` 返回 404 | 重新 `init`，段② 从 0 开始 |
| 5888 `upload_id` 失效 | `upload_chunk` 4xx | 重新 `init`，段③ 从 0 开始 |
| PC 磁盘不足 | 拉取前 `df` 预检 ≥ 1.1× 包 | 拒绝开始，不产生半成品 |

## 七、SSH 空闲超时（TMOUT=600）

### 7.1 实测

| 项 | 结果 |
|---|---|
| `TMOUT` | **600**（已导出至环境，`bash -ic` 同样为 600） |
| 注入来源 | `/etc/profile`、`profile.d`、`/etc/environment`、`/etc/security`、`sshd_config SetEnv` 均未命中，判定为深信服定制机制，**来源未定位** |
| `sshd_config` | `TCPKeepAlive yes`；**无** `ClientAliveInterval` |
| 表现 | 交互式 shell 10 分钟无输入即退出，与现场描述一致 |

### 7.2 影响面判定

bash 仅在**交互模式**检查 `TMOUT`，非交互执行与子系统不受影响：

| 通道 | 是否受 TMOUT | 说明 |
|---|---|---|
| `session.Run(cmd)`（单命令） | 否 | bash 非交互，不检查 TMOUT |
| `session.Shell()`（持久交互） | **是** | 10 分钟无输入即被终止 |
| SFTP 子系统 | 否 | 非 bash 进程 |
| rsync over ssh | 否 | 远端为 rsync 进程 |
| `acli log_collect create/progress/cancel` | 否 | 单命令 + PTY，秒级返回 |

### 7.3 架构约束（强制）

1. **日志收集的所有阶段禁止使用 `session.Shell()`**。现有终端代理路径（`terminal_bridge/main.go:776`）不得复用于本功能。
2. `create` / `progress` / `cancel` 使用 `RequestPty` + `Run`：**PTY 与持久 shell 是两件事**，PTY 只是分配伪终端，命令结束即退出，不受 TMOUT 影响。
3. 段① 传输使用独立 `Run("rsync …")` 或 SFTP 子系统；不得在持久 shell 内启动后再等待。
4. 复用 `ssh.Client` 时，每 30s 发送 `keepalive@openssh.com`，防止中间设备 NAT 超时断链（HCI 侧 `TCPKeepAlive` 只覆盖服务端视角）。

### 7.4 若必须使用持久 shell

仅限终端代理类交互功能，且必须满足：

- 每 ≤240s 注入无副作用心跳（如 `echo __hb__`），并在输出侧过滤该标记；
- 心跳失败立即重建会话，不静默重试；
- **不得**通过 `unset TMOUT` 规避——该变量属客户安全策略，清除会触发审计。

### 7.5 对交付链路的结论

| 链路 | TMOUT 影响 |
|---|---|
| P1（create + 轮询 progress） | 无。全程单命令，采集/上传在 HCI 后台 |
| P3 段①（rsync/SFTP） | 无。非交互进程 |
| P3 段②（PC→平台） | 无。与本机 SSH 无关 |
| P3 段③（平台→5888） | 无。平台出网，不涉及 HCI |

结论：**只要不用持久 shell，TMOUT 不构成威胁**；风险全部来自误用 `Shell()`。

## 八、数据保留与清理

### 8.1 原则

| # | 原则 |
|---|---|
| 1 | 平台**零自动删除**：无 TTL、无阈值触发、无定时任务 |
| 2 | 平台**不提供删除 API**，删除由运维介入 |
| 3 | 平台只做：检测 → 弹框告警 → 给清单与命令 → 记录用户确认 |
| 4 | 数据库记录永不自动删，仅标记 `archive_deleted`，审计可追溯 |

### 8.2 必须区分的四种删除

| 执行者 | 场景 | 平台可否阻止 |
|---|---|---|
| acli 插件 | P1 上传全部成功后删 zip（`sfd_main.py:725-727`） | 否，插件固有行为 |
| acli 插件 | `zip -rmjP` 的 `-m` 删源目录 + `rmtree(result_dir)` | 否 |
| 运维 | 平台副本 | 是（无 API，仅运维操作） |
| 用户 | HCI 源包 | 是（平台不碰，仅提示） |

UI 必须标注：P1 成功后包消失是**插件行为**，不是平台清理。

### 8.3 告警触发（只告警，不动作）

| 条件 | 对象 | 级别 |
|---|---|---|
| 平台存储使用率 ≥ 70% | 管理员 | 提示 |
| 平台存储使用率 ≥ 85% | 管理员 | 阻断新任务（不改动既有文件） |
| 任务包存在 > 30 天 | 管理员 | 提示 |
| P1 上传失败且 HCI 包仍在 > 24h | 操作人 | 警告（占用 20 GiB，会卡后续采集） |
| P3 搬运完成但 HCI 源包仍在 > 24h | 操作人 | 提示 |

同一文件只告警一次，用户确认后记 `cleanup_ack`，状态变化前不重复弹。

### 8.4 弹框结构

```
① 原因：本次检测到 3 个日志包占用 46.2 GiB（平台存储 78%）
② 清单：工单号 / 大小 / 采集时间 / 5888 归档状态
③ 位置：平台（运维处理） / HCI（客户自行处理）
④ HCI 命令：已填入实际路径，可复制
⑤ 禁止项：不得删除 plugins 与 tasks 目录
```

### 8.5 HCI 侧清理方法（交付文案）

```bash
# 1. 先确认占用
df -h /sf/data/local
ls -lh /sf/data/local/acli/tmp/data/log_collect/*.zip

# 2. 只删指定工单（逐条，勿用通配符）
rm -f /sf/data/local/acli/tmp/data/log_collect/<ticket>.zip

# 3. 复核
df -h /sf/data/local
ls -l  /sf/data/local/acli/tmp/data/log_collect/<ticket>.zip   # 应报 No such file
```

| 禁止命令 | 后果 |
|---|---|
| `rm -rf /sf/data/local/acli/tmp/data/log_collect/*` | 删除其他工单的中间产物 |
| `rm -rf /sf/data/local/acli/plugins/` | 卸载 acli 插件，后续采集全部失效 |
| `rm -rf /sf/data/local/acli/plugins/log_collect/tasks/` | 丢失任务状态，`progress` 异常 |
| 删除 `progress.json` / `cluster_progress.json` | 进度不可恢复 |

### 8.6 平台侧清理（运维）

```bash
# 对象路径：/var/lib/log-collect/objects/{case_id}/{task_id}.zip
kubectl -n <ns> exec <pod> -- rm -f /var/lib/log-collect/objects/<case_id>/<task_id>.zip
# 随后在 UI 标记已清理（仅更新状态，不改动文件）
```

删除前置条件：P3 任务必须 `relay_status = success`（5888 已有副本）；P1 任务平台无副本，无需删除。

平台删除不触碰：任务记录、审计日志、`collect_record.txt`。

### 9.1 收敛 `upload_mode` 枚举（不新增路径字段）

```sql
ALTER TABLE log_collect_task DROP CONSTRAINT IF EXISTS ck_log_collect_upload_mode;
ALTER TABLE log_collect_task ADD CONSTRAINT ck_log_collect_upload_mode
  CHECK ((upload_mode IS NULL) OR ((upload_mode)::text = ANY ((ARRAY['acli_direct'::character varying, 'bridge_relay'::character varying, 'none'::character varying])::text[])));
```

### 9.2 断点续传与清理字段

```sql
ALTER TABLE log_collect_task
  ADD COLUMN pull_offset_bytes   bigint,
  ADD COLUMN pull_sha256         char(64),
  ADD COLUMN relay_upload_id     text,
  ADD COLUMN relay_chunk_index   integer,
  ADD COLUMN relay_chunk_total   integer,
  ADD COLUMN relay_restarts      integer NOT NULL DEFAULT 0,

  ADD COLUMN cleanup_ack_by      varchar(64),
  ADD COLUMN cleanup_ack_at      timestamptz,
  ADD COLUMN archive_deleted     boolean NOT NULL DEFAULT false,
  ADD COLUMN archive_deleted_at  timestamptz,
  ADD COLUMN archive_deleted_by  varchar(64);
```

### 9.3 不建上传会话表

段②（PC → 平台）与任务严格 1:1，独立会话表只会多一个外键与一次 JOIN，故不建表：

| 原需存储 | 替代方案 |
|---|---|
| 已上传分片 | 文件系统目录 `/var/lib/log-collect/multipart/{upload_id}/` 的列目录结果 |
| `chunk_size` / `part_count` | 由 `archive_size` 与固定 32 MiB 推算 |
| 会话过期 | 目录 `mtime`，仅用于告警，不触发删除 |

约束：

- `cleanup_state` 仅作标记，**不得驱动任何删除操作**；
- `relay_chunk_index` 的写入必须在块成功之后，顺序不可颠倒；
- `upload_mode` 为唯一路径判定口径，不引入 `path_mode`。

## 十、安全

| 面 | 措施 |
|---|---|
| `ticket_no` | 服务端 + bridge 双重 `^[A-Za-z0-9_-]{1,32}$`，且 `shellQuote()` 转义（插件直接拼 shell） |
| 平台上传数据面 | `X-Upload-Token` 一次性、绑定 `upload_id`、24h 过期，不放 URL |
| 越权 | `init/complete/abort` 校验任务归属；数据面只认 token |
| 覆盖攻击 | 分片路径由服务端构造，禁止客户端指定 `object_key` |
| 磁盘 DoS | 单任务上限 25 GiB + 同工单仅 1 个活跃任务 + 全局在途配额 |
| 平台副本权限 | 落盘 `0o600`，下载走短期签名 URL |
| 5888 代传 | 仅允许内部 worker 调用，禁止对外暴露转发能力 |

## 十二、验收标准

| # | 场景 | 期望 |
|---|---|---|
| 1 | 5888 可达 | 走 P1，`progress` 显示发送成功，平台无副本，任务 `completed` |
| 2 | 5888 不可达 | 走 P3，段①②③ 全通，5888 返回 complete，任务 `completed` |
| 3 | P3 段③ 5888 失败 | 任务 `archived_only`，平台副本保留，UI 黄色告警 + 重试 |
| 4 | 段① 60% 断网 | 恢复后只补传剩余部分 |
| 5 | 段② 第 300 片断网 | 恢复后从 301 继续，`uploaded_parts` 不重传 |
| 6 | 段② bridge 重启 | `GET upload` 恢复，进度不归零 |
| 7 | 段③ 平台重启 | 复用 `relay_upload_id` 续传（若服务端支持）；否则 `relay_restarts+1` 并明确提示 |
| 8 | HCI 源包被删 | fail-fast，`LC-TRANSFER-001`，提示重新采集 |
| 9 | 传输超过 10 分钟 | SSH 不断开（未使用持久 shell） |
| 10 | 平台存储 85% | 拒绝新建任务，不删除任何文件 |
| 11 | 清理提示 | 弹框含清单与可复制命令，用户确认后不再重复弹 |
| 12 | 平台删除尝试 | 无 API，返回 404/405；仅运维可操作 |

## 十三、未决事项与风险

| # | 事项 | 影响 | 处置 |
|---|---|---|---|
| 1 | `TMOUT` 注入来源未定位 | 无法预判策略变更 | 每次 probe 记录 `TMOUT` 值，变化时告警 |
| 2 | `process_upload.py` 失败后会话未删 | 客户端再传分片会重复派发 | `complete` 后禁止再传；失败只重建新会话 |
| 3 | `status=complete` 不等于归档完成 | 早期判定会误报成功 | 以 `upload_status` 返回 404 或归档目录出现为终态 |
| 4 | P1 失败后包长期滞留 | 20 GiB 占盘会卡后续采集 | 24h 告警 + 弹框命令，不自动删 |
| 5 | P3 需客户 PC 可用磁盘 | 无磁盘则无法中转 | 拉取前 `df` 预检，不足则拒绝开始 |
| 6 | 平台存储无对象存储支撑 | 单机卷容量受限 | 85% 阻断新建，不改动既有数据 |
| 7 | 5888 归档保留仅 180 天下限 | 磁盘长期增长 | 交付文档提示客户关注 5888 容量 |
