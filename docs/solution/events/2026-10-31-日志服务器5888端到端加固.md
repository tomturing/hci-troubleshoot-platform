# 日志服务器（5888，现网）端到端加固

- 日期：2026-10-31
- 范围：`192.168.0.2:/acli`（5888 现网服务）+ 平台侧 `backend/case-service`
- 关联：Q2026102801062、Q2026103000994

## 一、审计发现（读码 + 现场状态，逐条有据）

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | 合片结果不校验大小 | `process_upload.py` 合片后 `size` 只写日志 | 分片切错时**静默产出坏包**并当成功归档 |
| 2 | 失败原因不落库、`/upload_status` 不返回状态 | 失败只打日志；状态接口只回 `uploaded_size/file_size/progress` | 平台只能等 `archive_timeout`（默认 1800s）才判失败 |
| 3 | `chunk_index` 无范围校验 | 仅 `int()` 转换后直接用；`all_received = len(chunks)==chunk_total` | 越界分片可让计数提前达标 → 缺片合片 |
| 4 | 单片大小无上限 | `chunk_data.save()` 前无校验，`MAX_REQUEST_SIZE=50MB` 而 `chunk_size=10MB` | 客户端切错被掩盖；单请求可放大 5 倍 |
| 5 | 归档同名直接覆盖 | `shutil.move(merged, {工单号}/{工单号}.zip)` | 同工单重传静默丢历史，无版本可追溯 |
| 6 | 5888 无进程托管 | 只有 `acli-7888.service`；5888 是手工启动的 root 进程，且**5 个 gunicorn 同时持有监听 fd** | 重启机器即丢服务；历史"重启"从未真正换掉老代码 |
| 7 | 孤儿分片永不回收 | `chunks` 子命令报"可清理 0 个（145 个活跃会话已保护）"，`/tmp/acli_upload_chunks` 达 **33G** | 磁盘只增不减；且系统里没有任何 cron 调度该脚本 |
| 8 | 会话过期是"访问时惰性删除" | `load_upload_session` 仅在被访问时判断过期 | 没人访问的陈旧会话永不过期 → 其分片被永久保护（#7 的根因） |

## 二、修复（5888 侧，本地仓库 commit `b3118a8`）

### `app.py`

- `upload_chunk` 增加 `0 <= chunk_index < chunk_total` 校验（否则 400）；
- 单片落盘后校验 `size <= CHUNK_SIZE`（否则 413 并删除该片）；
- `/upload_status` 增加 `status` / `error` 字段；
- 新增 `/healthz`（免鉴权，检查三个目录可写）。

### `process_upload.py`

- 合片后校验 `size == session['file_size']`，不符即失败（不进归档）；
- 失败时把 `status='failed'` + `error` **写回会话并保留会话**（删掉会被平台读成 404 → 误判成功）；
- 归档同名不覆盖，改存 `{工单号}-{时间戳}.zip`。

### `session_reaper.py`（新增）

回收 `last_updated` 超过 `SESSION_EXPIRE_HOURS`（默认 24h）的会话 JSON 与锁文件，默认 dry-run。
分片交给 `lifecycle_clean.py chunks` 按年龄回收，避免两处各写一套删除逻辑。

### 运维

- 新增 `acli-5888.service`（`Restart=always`、`WantedBy=multi-user.target`），替换手工进程；
  清理掉 5 个残留 gunicorn，收敛为 1 master + 4 workers；
- `/etc/cron.d/acli-5888-cleanup`：每小时 `17` 分回收过期会话、`23` 分回收孤儿分片（顺序不能颠倒）。

## 三、平台侧联动（本 PR）

`backend/case-service/app/services/log_collect_relay_service.py`：

1. `_await_archive` 读到 `status == 'failed'` 时**立即失败**并转述服务端给的原因，
   不再干等 `archive_timeout`；
2. 复用会话前的探测发现 `status == 'failed'` 时**丢弃旧会话**（失败路径已清理分片，续传不可能成功），
   重建会话后重传，并把原因写入 `relay_last_error`。

## 五、链尾内容校验（摘要回读）

### 5888 侧

- `merge_chunks` 在合片那一趟读盘里**同时算 sha256 与 md5**，并返回摘要；
  原来单独的 `get_file_md5` 会把整个包再读一遍（100GB 归档白白多读 100GB），本次直接去掉这次读盘；
- 成功后**不再删除会话**，改为写回 `status="done"` + `digest{sha256,md5,size}` + `target_path` + `finished_at`；
  会话仅 2KB 左右，由 `session_reaper.py` 24h 回收；
- `/upload_status` 透出 `digest` / `target_path` / `finished_at`；
- 终态会话（`done`/`failed`/`pending`）**拒绝继续收分片**（409），避免重复派发合片。

实测：`/upload_status` 返回的 `digest.sha256` 与归档文件 `sha256sum` **逐字节一致**；重复上片返回 `409 Upload already done`。

### 平台侧

`_await_archive` 在 `status == "done"` 时用 `digest.sha256` 与 `object_sha256` 比对：
不一致 → `LC-TRANSFER-002` 失败；服务端未回报摘要 → **不判失败**但记 warning（老版本兼容）。

## 六、鉴权（ACLI_UPLOAD_TOKEN）切换顺序

5888 的鉴权实现早已存在（`_require_auth`），本次只补平台侧的 Bearer 支持（`LOG_COLLECT_RELAY_TOKEN`，留空发空头）。

**顺序不可颠倒：**

1. 平台侧配置 `LOG_COLLECT_RELAY_TOKEN=<token>` 并部署（此时 5888 仍无鉴权，多发的头会被忽略）；
2. 确认平台确实带上了 Bearer（抓一次 `init_upload` 请求头）；
3. 再在 5888 的 `acli-5888.service` 加 `Environment=ACLI_UPLOAD_TOKEN=<token>` 并 `systemctl restart acli-5888`；
4. 回归：一次真实代传成功 + 一次故意错 token 得 401。

反过来（先开 5888）会让所有代传立刻 401。

免鉴权路径已确认：`/`、`/static/*`、`/healthz`。bridge 与前端只探测 `/` 可达性，不受影响。

## 七、已知边界

   必须等本 PR 部署后再翻转（见"六、切换顺序"），否则所有代传立刻 401。
