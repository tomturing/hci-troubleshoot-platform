# 日志收集大包直传等待上限误判失败

## 背景与触发

2026-11-24 同日两起同型现场，均为 P1 直传（`upload_mode=acli_direct`）的 10 GB 级日志包：

| 工单 | 任务 | 包大小 | 采集 | 平台写入的结论 | 节点实际状态 |
|---|---|---|---|---|---|
| `Q2026112400468` | `6ac37667-dbd5-4384-b2a4-bc3c5eb0f3c2` | 9.86 GiB | 8/8 完成 | `failed` / `LC-PLUGIN-010` / 采集未完成 | 发送中，2.5 小时后 `completed` |
| `Q2026091700436` | `60a0a2e6-b41f-46bc-a071-e59321bdc9f1` | 9.84 GiB | 9/9 完成 | `failed` / `LC-PLUGIN-010` / 采集未完成 | 发送中，5888 已落 66% |

第二起的硬证据（`bridge_execution_logs` + 5888 主机侧）：

- 16:21:34 节点向 `acli.sangfor.com.cn:5888` 发起 `UploadInit`，`file_size=10563438951`；
- 17:20~17:25 5888 分片从 609 片增长到 669 片（每片 10 MiB，约 1.99 MB/s）；
- 同一时段平台 `log_collect.progress` 全程 `node_state=running`、`exit_code=0`、`upload_state=发送中`、9/9 台 100%；
- 17:24:39 第 721 次 `progress` 调用结束，17:24:43 任务被写成 `failed`，`error_code=LC-PLUGIN-010`。

也就是说：**平台宣布失败的那一刻，节点正在以约 2 MB/s 正常上传，且已经传完 6.7 GB。**

## 根因

### 1. 等待上限用「次数 × 想象间隔」表达

`frontend/customer/src/components/LogCollectPanel.vue` 的 `pollUntilCollected` 原先写：

```ts
// 采集上限 1 小时（720 次 × 5s）：超时明确失败，避免面板无限转圈。
for (let attempt = 0; attempt < 720; attempt++) { ... await sleep(POLL_INTERVAL) }
```

每次 `sendAndWait('progress')` 自己的 RPC 耗时（实测 1~6 s）没有计入，真实耗尽点在 72~76 分钟，既不是注释里的 1 小时，也没有任何确定性。

### 2. 到点即「替节点下结论」

循环结束返回 `null`，调用方直接 `throw new Error('采集未完成')`，catch 统一 `PATCH { status: 'failed' }`。后端按关键词 `采集未完成 → LC-PLUGIN-010` 归因，而该码在码表里的定义是「PLUGIN 层：插件返回非零」，与现场（`exit_code=0`、9/9 完成、正在上传）完全相反。

预算的语义是「人愿意在页面上盯多久」，不是「这次采集应该多久跑完」。把它当成节点结论，就是把本端的耐心写成节点的事实。

### 3. 直传上传阶段显示了伪造的百分比

同一份界面把节点自报的 `percent`（在「采集 + 打包」结束时就封顶 85%，只有「发送成功」才跳 100%）拼在「发送中」后面：

```
正在发送到日志服务器：发送中（85%）
```

用户看到 40 分钟不变的 85%，只能得出「卡死了」，而正确的下一步（等它传完）与最贵的误操作（重新采集）在界面上无从区分——重新采集会与节点上正在跑的任务互斥，已传的几 GB 也白费。

## 修复

| 文件 | 改动 |
|---|---|
| `frontend/customer/src/services/logCollectWait.ts` | 新增：前台预算（1 小时，真实时钟）、观察间隔（15 s）、`planCollectWaitExpiry()` 到点结论 |
| `frontend/customer/src/components/LogCollectPanel.vue` | `pollUntilCollected` 返回判别联合 `completed / expired`；到点转「观察模式」，不写任何终态；新任务重置观察态 |
| `frontend/customer/src/services/logCollectProgress.ts` | 新增 `describeDirectUpload()`：直传文案只报阶段 + 包大小，不含百分比 |
| `frontend/customer/src/services/__tests__/logCollectWait.spec.ts` | 新增 7 例：到点结论、无证据不判失败、文案不得含后端会误归因的措辞 |
| `frontend/customer/src/services/__tests__/logCollectProgress.spec.ts` | 新增 4 例：直传文案不含 `%`、包大小未知时不编事实 |

关键设计：

1. **到点只有两条出路**。节点已 `completed` → `finalize`（把本该完成的收尾补完）；其余任何状态（`running` / `abnormal` / 一次都没采到）→ `observe`。没有失败证据时判失败，就是替节点撒谎。
2. **观察模式不写库**。只设置提示、把对账从 5 s 降到 15 s，节点传完后由既有 `decideNodeSync` 走 `patch_completed / patch_delivered`，与「接管」路径复用同一套判定，避免第二套完成逻辑分叉。
3. **提示保护**。观察期间通用对账文案（如「节点状态无法识别」）不得顶掉「平台已转后台跟踪」，否则用户只看到界面静止。
4. **文案白名单**。`planCollectWaitExpiry` 产出的提示不得包含「采集未完成」「执行失败」——后端词表会把它们翻成 `LC-PLUGIN-010`/`LC-PLUGIN-012`，这是本次误归因的传导路径。

## 验证

- `frontend/customer` 全量单测：58 文件 / 793 例通过；
- `vue-tsc -b` 退出码 0；`vite build` 产物正常；
- 新增用例覆盖两起工单的判定点：节点 `running + 发送中 + 9/9` 不得进 `failed`，且提示里不得出现「采集未完成」。

## 后续增强：观察模式可恢复与交接审计

首版观察模式只存在于当前页面内存：页面刷新后 `observeMode` 回到 false，仍为 `collecting` 的任务会重新按 5 秒轮询；同时库中没有记录“为什么转入后台观察”。

补充：

- `logCollectWait.ts` 新增 `buildObserveHandoffAudit()` 与 `hasObserveHandoff()`，只记录节点态、上传态、台数、包大小、提示语、`trace_id`，不写失败结论。
- `enterObserveMode()` 在转观察时把审计合并写入 `detail.observation_handoff`；审计写失败只留前端日志，不影响任务继续运行。
- `resumeTask()` 读取 `detail.observation_handoff`：只有 `status=collecting` 才恢复观察模式，页面重开后继续 15 秒对账，不退回 5 秒。
- 不改变 #1650 的判定不变量：观察模式仍不写终态，节点完成后仍由同一套 `decideNodeSync` 收敛。

## 遗留与边界

- 观察模式没有总时长上限：节点真卡死时会一直以 15 s 对账。这是刻意的——平台没有失败证据时不该单方面宣布失败，用户可随时关闭面板或手动「刷新进度」。
- 后端 `LC-PLUGIN-010` 的关键词表仍保留「采集未完成」：其它入口（旧版本前端、历史任务重放）仍可能带这条文案，本次只切断新的产生路径，未改码表语义。
- 直传仍无字节级进度可显示。若后续要让用户看到真实上传百分比，唯一可行来源是 5888 的上传会话（`uploaded_size / file_size`），需要平台侧新增查询通道，不在本次范围。
