# spc 场景数据模型与序列化

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-10 |
| 版本 | v1.0 |
| 范围 | case-service 场景模型 + 序列化 + 迁移 056（不含 bridge 扇出） |
| 前提 | 已确认占用 core 槽、bridge 为 root |

## 一、为什么模型要变

原模型只有 `{path, category, note}`，因为它服务的是 acli `-c`；而 `-c` 只能逐条 `cp -r`。
选 B 方案后，场景要能表达 spc 的全部能力（`action: copy|command|script`、`filters`、
`date_placeholders`、`docker`、`interpreter`），否则「能收 command/script」这个前提不成立。

## 二、条目模型

| 字段 | 说明 |
|---|---|
| action | copy / command / script，默认 copy（旧数据自动兼容） |
| path | copy=绝对路径（允许 * 与 {date}）；command=命令行；script=脚本文件名 |
| filters | 原样保留 include/exclude 与 START/END 时间条件，不做简化 |
| date_placeholders | 原样保留 {placeholder, format}，由插件按 -d 展开 |
| docker / interpreter | script 条目的执行环境 |
| note | 分组标题，插件会跳过，仅用于编辑器分组 |

## 三、两条通道，两套校验

同一份条目模型要服务两条下发通道，校验必须分开，否则一定有一边是错的：

| 通道 | 序列化 | 允许的条目 |
|---|---|---|
| `-c`（visual/json） | `{"paths":"a,b"}` | 仅 copy、无 `*`、无 filters |
| spc（spc） | spc JSON 数组 | 全部 action 与过滤条件 |

`schema` 层只校验条目自身合法性（绝对路径、禁 `..`、禁逗号、禁换行、脚本名白名单）；
「这个通道能不能用该条目」由 service 的 `_validate_items_for_source` 决定。
这样 `*` 在 schema 层合法（spc 需要），但走 `-c` 时会被明确拒绝，而不是被插件静默跳过。

## 四、安全边界的变化

`command` / `script` 本质是**在客户节点执行管理员定义的命令**，平台以前刻意不支持。
放开它必须同时满足三条，缺一不可：

1. 只有管理端接口可写（`INTERNAL_API_TOKEN`），客户侧只读元数据；
2. 每次保存写 `operation_audit`，记录操作人与完整 items；
3. `review_state` 默认 `pending_review`，未审批的场景不得被客户选用。
