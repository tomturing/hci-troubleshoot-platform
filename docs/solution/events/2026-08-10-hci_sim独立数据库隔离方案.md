# hci_sim 独立数据库隔离方案

## 1. 背景与需求

本方案响应 [hci_sim 独立数据库隔离需求](../../requirement/events/2026-08-10-hci_sim独立数据库隔离需求.md)。当前主库既保存客户业务事实，又保存 hci-sim 测试控制面元数据，违背最小权限、独立演进和故障隔离原则。

## 2. 第一性原理

数据库隔离不是“换一个数据库名”，而是同时隔离五种能力：

```text
身份（role/secret）
命名（database/schema/table）
迁移（migration history/job）
运行（connection pool/timeout/failure mode）
运营（backup/restore/retention/alert）
```

任一层仍复用主库，都会保留隐性耦合。目标不变量为：

1. hci-sim 运行时拿不到主库写权限；
2. 主业务运行时拿不到 hci_sim 写权限；
3. hci_sim 不可用时只影响仿真测试；
4. 主库 migration 不会创建 hci-sim 表；
5. 跨库关联使用不可变 ID 和 API，不使用跨数据库外键；
6. 删除源表之前始终存在已验证的备份和回滚路径。

## 3. 方案（WHAT）：目标架构

```text
PostgreSQL cluster（可同实例，逻辑隔离）
├── database hci_troubleshoot
│   ├── platform runtime role
│   ├── case/conversation/environment/kb/fact
│   └── platform migration history
│
└── database hci_sim
    ├── role hci_sim_owner       （建库/owner，不给应用）
    ├── role hci_sim_migrator    （DDL/migration job）
    ├── role hci_sim_runtime     （最小 DML）
    ├── schema control_plane
    ├── schema fixture
    ├── schema artifact
    ├── schema execution
    ├── schema audit
    └── independent migration history
```

第一阶段可与主库共用同一个 PostgreSQL StatefulSet，以降低运维复杂度；隔离的权威边界是 database + role + secret + migration。未来容量或故障域要求提高时，可把 `hci_sim` 迁移到独立实例，而无需改变业务 ownership。

## 4. 数据所有权模型

### 4.1 推荐 schema

| schema | 责任 | 表 |
|---|---|---|
| `control_plane` | Scenario、TestRun、Attempt、runtime capability | `agent_test_scenario/run/run_attempt/run_event/run_result/runtime_instance` |
| `fixture` | Bundle、dependency、provenance、approval、stale outbox | `agent_test_fixture_*` |
| `artifact` | Artifact metadata、scan、approval | `agent_test_artifact*` |
| `execution` | 仿真专用 Bridge/exec metadata | 审查后迁移的 `bridge_execution_*` 子集 |
| `audit` | 状态变更和管理员操作审计 | `agent_test_fixture_audit` 等 |

数据库级隔离是 P0；schema 分类需要同步修改所有 SQL/search_path，不能仅移动表。为降低一次性风险，迁移顺序可先保持 `public` 表名完成 database 切换，再以兼容 view/明确 schema 做第二次迁移。最终态不依赖模糊 search_path。

### 4.2 `bridge_execution_*` 判定规则

先按数据生产者和消费者标注：

- 只由 sim-ssh TestRun 产生/读取：迁入 `hci_sim.execution`；
- 同时服务真实 HCI 工单：保留平台表，并为 hci-sim 新建专用 execution 表；
- 不允许通过 `execution_mode` 一列长期混放而继续共享所有权限；迁移期可作为临时兼容，必须有退场日期。

## 5. 连接与权限设计

### 5.1 配置

运行时只接受：

```text
HCI_SIM_DATABASE_URL
```

或等价拆分字段：

```text
HCI_SIM_POSTGRES_HOST
HCI_SIM_POSTGRES_PORT
HCI_SIM_POSTGRES_DB=hci_sim
HCI_SIM_POSTGRES_USER=hci_sim_runtime
HCI_SIM_POSTGRES_PASSWORD
```

禁止 fallback 到 `DATABASE_URL`。缺少 hci-sim 配置时服务启动或相关 capability readiness 必须失败。

### 5.2 角色

```sql
hci_sim_owner     -- NOLOGIN 或仅受控管理
hci_sim_migrator  -- DDL，短期 Secret
hci_sim_runtime   -- LOGIN，SELECT/INSERT/UPDATE/DELETE 到指定表和 sequence
```

runtime 不能 `CREATE/DROP/ALTER`，不能访问主库。默认撤销 `PUBLIC` 对 database/schema 的 CREATE 权限。

### 5.3 Secret

- K8s Secret 分为 migrator 和 runtime；
- Admin UI 不接触数据库 Secret；只调用控制面 API；
- Secret 轮换不重建数据库对象，通过滚动更新连接池生效；
- values 中只引用 Secret 名，不保存密码。

## 6. 独立 migration 设计

目标目录：

```text
database/
├── atlas-migrations/          # hci_troubleshoot
└── hci-sim-migrations/        # hci_sim
```

要求：

- 独立 `atlas.sum` 和 history 表；
- CI 分别 lint/diff/test；
- hci-sim migration Job 只注入 migrator Secret；
- App 启动不自动做 DDL；
- migration 版本与 hci-sim 镜像兼容矩阵明确；
- expand migration 先于应用，contract migration 晚于观察窗口。

## 7. 跨数据库一致性

### 7.1 不使用跨库外键

`support_id/kbd_revision/checksum` 来自主库知识库，但 hci_sim 保存不可变快照：

```text
support_id
kbd_id
kbd_revision
kbd_checksum
bundle_digest
tool_contract_revision
policy_revision
```

hci_sim 依赖的是已解析快照，不在运行时 join 主库。KBD 变化通过 stale outbox/API 事件标记 Bundle stale。

### 7.2 一致性模式

采用“不可变快照 + outbox/reconciliation”，而不是分布式事务：

```text
KBD 发布
  → 主库提交
  → outbox/事件
  → hci-sim reconciliation
  → 对受影响 Bundle 标记 stale
```

事件丢失由周期 reconciliation 使用 revision/checksum 对账，保证最终一致。

## 8. 数据迁移策略

采用 expand → copy → verify → switch → observe → contract：

### 阶段 0：Inventory

- 表、列、主外键、索引、序列、触发器、RLS、view、函数；
- 代码 SQL、ORM、migration、报表和备份引用；
- 写入方、读取方、数据量和增长率；
- `bridge_execution_*` 真实/仿真占比。

### 阶段 1：Expand

- 创建 database/roles/schemas；
- 执行独立 schema migration；
- 发布支持显式 hci_sim 连接但仍读取旧库的兼容应用；
- 建立备份并完成恢复演练。

### 阶段 2：Copy

- 在一致性快照中按依赖顺序复制；
- 保留原主键和时间戳；
- 设置 sequence 到 `max(id)` 之后；
- 不复制 Lease 明文或被政策禁止的数据。

### 阶段 3：Verify

- 行数、PK 集合、FK orphan、唯一约束、索引、序列；
- 每表 checksum/分桶摘要；
- TestRun 业务级重放；
- 权限负向检查。

### 阶段 4：Switch

优先选择短暂停写切换，避免双写复杂度：

```text
drain 新 TestRun
→ 等待活动 TestRun 结束
→ final delta copy
→ 切换 Secret/config
→ 启动新写入
```

如果业务要求零停写，必须实现 durable outbox/CDC；禁止应用层“尽力双写”。

### 阶段 5：Observe 与 Contract

- 旧表只读保留至少一个约定观察窗口；
- 监控旧表无新写入；
- 完成备份恢复和回滚演练后才删除旧表；
- 删除使用独立 contract PR，不与切换 PR 合并。

## 9. 备份、恢复和生命周期

- hci_sim 独立逻辑备份，文件名/目录与主库区分；
- 定期恢复到临时 database，执行 schema 和业务校验；
- TestRun/event 按保留策略分区或归档，Artifact 原始内容仍在对象存储；
- 删除/归档有审计，不允许无界增长；
- 记录 RPO、RTO、最近恢复成功时间和备份年龄指标。

## 10. 可观测性

| 类别 | 指标/日志 |
|---|---|
| 连接池 | active/idle/wait/error，按 database/service 低基数维度 |
| migration | version、duration、failure、checksum mismatch |
| 数据一致性 | old/new row delta、stale outbox lag、reconciliation failures |
| 容量 | DB/schema/table/index size、增长率、dead tuples |
| 备份 | last success、age、restore validation |
| 安全 | permission denied、unexpected database access、secret rotation |

## 11. 对抗性审查

| 故障/攻击 | 失败模式 | 防御 |
|---|---|---|
| 应用缺少 HCI_SIM_DATABASE_URL | 回退污染主库 | 禁止 fallback，启动 fail |
| migration 使用 runtime 账号 | 权限过大 | 独立 migrator Secret |
| 复制后 sequence 未推进 | 新写入 PK 冲突 | sequence 校验门禁 |
| 隐藏 SQL 硬编码 `public.*` | 切换后运行报错 | 全仓引用扫描 + contract test |
| 双写一边成功一边失败 | 数据分叉 | 短暂停写或 durable outbox，拒绝 best-effort |
| 跨库 join/外键 | 部署耦合 | 不可变 ID + API/事件 |
| 备份命令成功但无法恢复 | 虚假安全 | 强制 restore drill |
| 过早 DROP 旧表 | 无法回滚 | 独立 contract PR + 观察窗口 |
| bridge 表错误归属 | 真实工单审计丢失 | 先按 producer/consumer inventory 分类 |

## 12. 决策依据（WHY：为什么选此方案，为什么不选其他方案）

### 选择独立 database，而不是仅独立 schema

schema 不能隔离连接串、备份、migration history 和 database-level 权限，应用误配置 search_path 仍可能写错表。独立 database 更符合模块故障域。

### 第一阶段可复用 PostgreSQL 实例

物理独立实例能提供更强故障隔离，但会立即增加 HA、备份、监控和成本。先完成逻辑 database/role/migration 隔离，再根据容量迁移实例，风险更可控。

### 不选择永久双写

应用双写引入分布式一致性问题，且本场景允许 drain TestRun 后短暂停写。短暂停写迁移更容易证明正确和回滚。

### 不直接复制所有 `bridge_execution_*`

这些表可能同时属于真实工单审计。所有权不明时整体迁移会破坏主平台；必须先 inventory 或拆域。

## 14. 验收标准

以 [hci_sim 独立数据库隔离验证](../../verify/events/2026-08-10-hci_sim独立数据库隔离验证.md) 为准。创建数据库、跑通 migration 但未完成权限负向测试、数据一致性和恢复演练，不视为完成。

## 15. 本迭代落地边界

本迭代（阶段二 PR-A）已落地独立迁移目录、四领域 schema、数据库初始化 Hook、三角色 Secret 模板和显式 opt-in 的存量复制脚本。由于当前 hci-sim 控制面仍是代码级内核，尚未有生产 Repository/应用写入方，不能把“新库可创建”写成 TestRun 已切换；PR-B 负责 copy/verify/switch，PR-C/contract 负责观察和旧表清理。

## 当前实现状态（2026-08-10）

- 代码/Helm/CI 已完成：`hci_sim` migration、schema、migrator/runtime role 和权限门禁；hci-sim Deployment 的 `HCI_SIM_DATABASE_REQUIRED=true` 与独立 URL 配置已声明。
- 现场证据：Runtime `/status` 显示 `database_configured=true`、`database_name=hci_sim`；Pod 启动日志正常。
- pending：PostgreSQL Repository/CAS/Outbox、存量 copy→verify→switch、应用写入切换、观察窗口和旧表清理尚未完成。
- capability_gap：当前运行面仍有内存控制面参考实现，不能把 hci_sim 数据库已可连接表述为 TestRun 持久化已完成。
- 不允许的产品声明：不得把 migration 通过或数据库存在宣称为数据隔离闭环；不得在主库和 hci_sim 之间隐式双写。
