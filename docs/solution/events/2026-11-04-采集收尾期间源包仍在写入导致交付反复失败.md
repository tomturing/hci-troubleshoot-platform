# 采集收尾期间源包仍在写入导致交付反复失败

- 日期：2026-11-04
- 现场工单：Q2026110400883（客户机 `sangfor`，Windows，P2 中转）
- 涉及：`terminal_bridge`（`delivery_runner.go` / `delivery_handlers.go`）、
  `case-service`（`log_collect_upload_service.py`）、`frontend/customer`（`LogCollectPanel.vue`）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 界面提示"源包已变化（提交上传时 882701883 字节，当前 889677835 字节），本次上传已作废" | `delivery.job_finished` phase=failed |
| 同一单先后出现三个不同的包大小 | 提交 882701883 → 拉取前探测 889677835 → 拉取完成 892074444 |
| 期间多次拉取命令失败 | `拉取中断（已拉 0 字节）: 拉取命令失败（源包可能已被清理）: Process exited with status 1`，attempt 3/4 |
| 页面状态是"节点采集已收尾，等待压缩包写入完成（尚未开始传输）" | 前端进度文案 |
| 等包稳定后重新点「上传到平台」即成功 | 107/107 片 `200 OK`，`integrity_state=verified`，`object_sha256` 与源包一致 |

## 二、根因

### 1. `done >= total` 不等于包写完了

`waitCollect` 只要 `acli log_collect progress` 报 `done >= total` 就放行进入拉取。
但 acli 的进度是**采集任务进度**，zip 仍在追加尾部。此时开始拉取：

- 拉取拿到的是"拉取那一刻"的中间产物；
- 包若在拉取期间继续增长，`tail` 读到的字节数超过拉取前 stat 的大小，
  或源包被重建导致拉取命令直接 `status 1`；
- 平台上传会话的 `total_size` / 分片方案在**提交那一刻**就冻结，
  副本一变，末片长度必然对不上，每一片都会失败。

这与 2026-10-30（#1380）的"提交后包被重新生成"是同一族问题，但触发窗口不同：
那次是采集早结束、包被重复采集覆盖；这次是**提交时包还没写完**。
`sourceSizeGuard` 把后者显式拦下，避免重演"N 片 500 × 8 轮"的空转。

### 2. relay 路径缺少 direct 路径已有的 EOCD 校验

`prepareDirect`（补交付/direct）会用 zip 尾部 EOCD 判断"包是否写完"，
而 relay（collect 模式）的 `waitCollect` 没有这道校验——两条路径对"包是否完整"
的判据不一致，relay 成了缺口。

### 3. 拉取失败被当成可重试的网络问题

包仍在写入时，拉取命令会以 `status 1` 或字节数不符失败。原实现：

- `errPullSizeMismatch` 判 fatal（但文案是"被覆盖或截断"，误导为包坏了）；
- `拉取命令失败（源包可能已被清理）` 走普通错误，重试 5 次——每轮都在追一个移动的目标，
  且每轮都会重新校验/重拉几十 GB。

### 4. 同一任务重试时会复用旧会话基线

`submit` 对同 `task_id` 的非终态作业直接复用，且 `SubmittedSize` "只写一次、永不覆盖"。
如果用户在上一次作业仍处于 `retrying` 时重新点上传，平台已签发新令牌/新分片方案，
bridge 却仍用旧基线，新会话每片都校验不过——**即使包已经稳定也永远失败**。

## 三、本次改动

| 位置 | 改动 |
| --- | --- |
| `waitCollect` | `done>=total` 后新增 `waitArchiveSettled`：连续两次 stat 大小相同 **且** 尾部存在 zip EOCD 才放行；取不到包路径时不再空转进入拉取，而是记 `delivery.archive_path_missing` 继续等 |
| `waitArchiveSettled` | 落定超时 5 分钟，判 `LC-TRANSFER-010`（源包仍在写入）；EOCD 命令不可用时降级为"仅大小稳定"，与 `prepareDirect` 同一取舍 |
| `pull` | 拉取失败后复量源包：与拉取前不同即判 010 并丢弃残包，不再按普通错误重试；`errPullSizeMismatch` 也归到 010 |
| `prepareDirect` | EOCD 缺失由普通错误改为 fatal 010：补交付路径同样不允许"半截包重试 5 次" |
| `submit` | 新增 `sameDeliverySession`：令牌/基线/分片数/分片大小/传输模式任一变化即视为新会话，终止旧作业并换新（旧作业 JobID 加 `-superseded` 后缀，避免收尾时覆盖磁盘记录） |
| 错误码 | 新增 `LC-TRANSFER-010`（源包仍在写入，owner=customer，manual，409），`deliveryFatalError` 支持携带规范码，`deliveryErrorCode` 统一透出 |
| 平台 | `upload_service.complete` 合并成功后直接写 `delivery_status=delivered`、`delivery_finished_at`，清空 `delivery_error`；终态不再依赖浏览器 PATCH |
| 前端 | 结果卡片按 010 展示"等文件大小不再变化后重试"；"包是否写完"仍只由 bridge 判定（不在前端做第二次 stat） |

## 四、审计中发现的其他问题（本批已修 / 已记录）

1. **已修**：同一任务重试复用旧会话基线（见上）。
2. **已修**：`waitCollect` 在 `progress.ArchivePath` 为空时仍进入拉取，
   后续每一步都在跟空路径较劲（现场同时出现 `digest_unavailable` 与拉取 status 1）。
3. **已修**：交付终态只由浏览器回写，页面关闭/断网会永久停在 `queued`
   （本次实测 07:55 时仍是 queued，07:56 前端 PATCH 后才 delivered）。
4. **未纳入**：`ensureSourceDigest` 的 `source_size` 与 digest 取样不是同一快照
   （曾出现"889677835 字节却与 892074444 字节文件的摘要相同"的诊断假象）。
   根因已由 `waitArchiveSettled` 消除（先稳定再取基线），事件字段暂不改。
5. **未纳入**：bridge 自身日志上报（`log_upload`）到平台时大量
   `TLS handshake timeout / no such host`，与源包问题无关，但会延迟事件可见性。
6. **未纳入**：客户机 bridge exe 仍需随镜像重建后现场重装，旧 exe 不会自动升级。
