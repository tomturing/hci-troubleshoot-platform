## 一、现象与可验证的物理事实

客户在日志收集面板把时间范围选成 `2026-05-30 ~ 2026-11-11`，点「开始收集」后界面弹出 `Request failed with status code 422`，看不到任何可执行信息。平台侧证据如下：

| 事实 | 证据 |
|------|------|
| 网关只有两处 422，均指向 `POST /api/log-collect/tasks`（02:59:01Z 走 P1、03:00:18Z 走 P2） | `api-gateway` 访问日志 |
| case-service 判定为参数校验失败，原因是 `收集范围不能超过 30 天`，请求体 `date_from=2026-05-30`、`date_to=2026-11-11` | `case-service` 日志 `event=request_validation_failed`、`code=REQUEST_VALIDATION_ERROR`，`trace_id=04caff95…`/`a9e35bc5…` |
| 第三次（03:01:55Z）把范围改成 `2026-11-11` 单日后创建成功，任务 `b4759a10` | `log_collect_task` |
| 该任务最终 `completed` / `progress=100` / `delivery_status=delivered`，P1 直传 21.26 MB | `log_collect_task.finished_at=03:07:56Z` |
| 采集链路自身健康：acli 由 `1.0.12-preview` 自动升级到 `1.0.0`（2026-05-20 构建），`create_ack=confirmed` 且节点 `running` | `bridge_execution_logs` 的 `acli_sync.*`、`log_collect.probe`、`log_collect.create_ack` |

**结论**：这不是采集、交付、SSH 或网关故障，而是**参数校验拒绝 + 错误信息丢失**。真实任务在用户缩小范围后成功完成。

### 已排除的干扰解释

- **SSH 终端异常**：同屏终端有正常 `ssh.output` 事件，422 与终端通道无关。
- **采集卡死**：progress 长期 `收集任务进行中！`、`percent=0` 是慢盘专项未收满，不是卡死；最终 100% 完成。
- **30 天上限本身不合理**：上限是既有契约，且本例改单日即成功；本条需要产品决策，不由本次缺陷修复承担。
- **网关/服务 OOM**：422 是业务校验结论（带结构化 code），不是 502/503/504 兜底。

## 二、三处缺陷

1. **前端无前置校验**。`handleStart` 只校验 `dateRange.length === 2`；日期选择器只禁未来日期，不限跨度。「最多 30 天」仅作为灰色提示文案存在，既非硬约束也非错误提示。用户一旦选超，必然发出一次注定失败的请求。
2. **422 的原因被拦截器吞掉**。FastAPI `RequestValidationError` 的响应体是 `{"detail": [ {type, loc, msg, ctx} ]}`，`detail` 是**数组**。`extractApiProblem` 只支持字符串与对象：数组走进对象分支后 `problem.detail` / `problem.message` 都不存在，得到全空 problem，`formatApiProblem` 返回空串，`error.message` 原样保留 axios 的 `Request failed with status code 422`。
3. **调用点直接透出 axios 原文**。`handleStart` 的 catch 用 `normalizeErrorMessage(error.message)` 展示，没有兜底翻译，最终界面上只有状态码。

## 三、修复内容

### 1. 错误可读化（通用层，收益覆盖所有接口）

`frontend/shared/src/api.ts`：

- 新增 `extractValidationMessages`：数组形态 `detail` 逐项取原因，**优先 `ctx.error`**（Pydantic v2 放原始 ValueError 的位置），缺省退回 `msg`，并去掉框架前缀 `Value error, `；多条去重后用「；」拼接。
- `extractApiProblem` 在对象分支之前显式判数组；解析不出任何原因时返回 `null`，保持「拿不到结构化 problem 就不改 axios 原行为」的既有契约，不造空 problem。

### 2. 提交前拦截跨度（客户前端）

- 新增纯函数模块 `frontend/customer/src/utils/logCollectDateRange.ts`：`MAX_DATE_RANGE_DAYS = 30`（与 `backend/case-service/app/schemas/log_collect.py` 同源）、`dateRangeSpanDays`（按 UTC 解析日期分量，避开时区与夏令时误差）、`checkDateRange`（返回可直接展示的原因）。
- `LogCollectPanel.handleStart` 在任何前置条件之前调用 `checkDateRange`：天数非法或超上限立即 `ElMessage.warning` 并返回，**不建任务、不打开 bridge 通道**。
- 提示原文案改为「单次最多 30 天，超出会在下发前拦下」，让限制在填写阶段可见。

### 3. 为什么不收紧日期选择器的可选范围

后端契约只有两条：结束不早于开始、跨度不超过 30 天，**没有「只能选最近 30 天」的窗口限制**。若用 `disabled-date` 把可选日期钉死为最近 30 天，会让「收集今年 1 月日志」这类合法需求直接不可选，属于用前端实现悄悄收窄产品能力。因此选择器仍只禁未来日期，跨度由提交前校验把守。

## 四、验收标准

1. 时间跨度 166 天点「开始收集」：不发 `POST /api/log-collect/tasks`、不发 `log_action=create`，界面给出含实际天数与上限的中文提示。
2. 跨度正好 30 天（含首尾）可正常下发；31 天被拦。
3. 任何接口返回 FastAPI 参数校验数组时，界面文案包含后端中文原因（例如「收集范围不能超过 30 天」），不再是 `Request failed with status code 422`。
4. `detail` 数组解析不出原因时保持 axios 原文（不出现空白提示）。
5. 单测覆盖：`dateRangeSpanDays` 的跨月/跨夏令时/非法输入；`checkDateRange` 的 30/31/166 天边界；组件级「超限不下发」。

---

## 五、回滚与失效边界

- 两处改动互相独立：回滚前端校验后，用户仍会收到 422，但文案已可读（第二处修复保证这一点）。
- `MAX_DATE_RANGE_DAYS` 是前端副本，与后端常量存在漂移风险；漂移时的表现是「前端放行、后端拒绝」，此时第 1 项修复兜底给出中文原因。若后续要配置化，应由服务端下发上限而不是再复制一份常量。
- 数组 `detail` 解析只取人类可读原因，不解析 `loc` 路径；同一批错误出现相同文案时按去重处理，不重复展示。
- 本次不改后端上限、不改采集链路，历史任务不受影响；Q2026111100469 已完成的采集与交付无需重跑。
