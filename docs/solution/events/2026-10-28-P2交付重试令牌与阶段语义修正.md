## 一、第一性原理：断点续传只依赖两件事实

一次交付失败后能"接着传"，物理上只需要两件事：

1. **凭据还能用**（否则平台无法区分"续传"和"陌生人写数据"）；
2. **执行方能知道上次卡在哪**（阶段 + 已传分片）。

这两件事都必须**在失败路径上仍然成立**。此前 #1319/#1322/#1327 三次修复都只覆盖了
"首次提交"这条路，而现场真正的复现路径是**失败后的重试**：

```
点上传 → /deliver 200 → bridge 拉包 → 分片 PUT 撞 x509
      → 前端确认信任证书 → 刷新会话 → 重新提交 → bridge 回 "task_id 与 upload_token 必填"
```

即：**首次提交的字段全对，重试那条路的令牌是空的。**

## 二、四个确定性缺陷

### D1 会话查询接口不签发令牌（本次现场直接原因）

`GET /api/log-collect/tasks/{id}/uploads` 的响应模型 `UploadStatusResponse` 不含
`upload_token`（只有 `chunk_size/part_count/uploaded_parts`），而前端 `getUploadStatus`
声明返回 `UploadInitResult`（含 token）。类型声明比服务端"多一个字段"，编译器相信了它，
运行时拿到 `undefined`，`JSON.stringify` 直接丢掉该键。

前端表现：`task_id 与 upload_token 必填`——**把证书问题伪装成参数问题**，这也是为什么
按错误文案定点修复三次仍在原地。

### D2 `failed` 同时表示"终态失败"和"稍后重试"

bridge 对非凭据错误会在后台退避重排（最多 5 次），但重排前写的是 `phase=failed`。
前端 `waitDeliveryJob` 见到 `failed` 即抛错，并按契约回写 `delivery_status=failed`。
于是同一时刻三份状态互相打脸：界面说失败、平台记 failed、字节其实还在往平台传。

### D3 `advance` 会把"失败作业"推进成 `done`

`advance` 的 `switch job.Phase` 没有 `phaseFailed` 分支，也没有 default；控制流掉出
switch 后无条件执行 `job.Phase = phaseDone`。重排条件里"既没拉过字节也没传过分片"的一类
（例如 SSH 拉取第一步就失败）在重排时不会改阶段，于是**下一次推进直接把它标成交付成功**。
失败至少还能重试，误标成功等于永久放弃。

### D4 `resume` 只清标志位，不清阶段

`needs_reauth` 时 `phase` 是 `failed`（终态）。`resume` 只把 `NeedsReauth=false`，
随后 `advance` 立刻以"终态拒绝推进"再次失败——用户点"继续"等于没点。

## 三、修复

| 缺陷 | 修复 |
|------|------|
| D1 | `UploadStatusResponse` 增加 `upload_token`，`status()` 每次重新签发（令牌绑定 task_id，跨任务不可用）；`/deliver` 的幂等短路分支改用 dict 覆盖，避免同名关键字冲突 |
| D2 | 新增 `phaseRetrying` 中间态；非凭据失败写 `retrying`，前端见到 `retrying` 只提示不判死 |
| D3 | 抽出纯函数 `normalizeDeliveryPhase`：统一把 `retrying` 归一化成可执行阶段，并对 `done/failed/未知` 返回错误；`advance` 先做该守卫再解析 SSH 会话 |
| D4 | `resume` 同时把阶段置为 `retrying`，交给 `advance` 按进度续 |

附带：前端轮询预算由 2 小时提高到 6 小时（与 bridge `deliveryJobTimeout` 对齐），
前 2 分钟 2s、之后 10s，避免长作业把请求量放大 6 倍；重试刷新后若令牌仍为空，
直接给出"上传会话令牌缺失或已过期"而不是把空串发给 bridge。

## 四、对抗性审查：这次修复覆盖不到的地方

1. **协议仍是 12 个字段穿越浏览器。** 只要字段还要经前端转发，D1 这类"某条路径少一个字段"
   就会反复出现。方向是让 bridge 直连平台取会话（需要新增数据面 `GET /uploads`），
   属于下一刀的架构减法，不在本次范围。
2. **`total_size` 仍有三处来源**（前端 stat / 平台会话 / bridge 本地文件），末片长度依赖三者一致。
3. **`needs_reauth` 没有恢复入口**：前端没有调用 `delivery_resume`，用户看到"需重新认证"后
   只能整轮重来。现在 `resume` 语义已正确，但入口仍未接线。
4. **bridge 是客户机二进制**，平台发布不会更新它；旧 bridge 会静默丢弃新字段，需要版本闸门。

## 五、验证

- Go：`normalizeDeliveryPhase` 逐分支用例（含"终态拒绝推进"）、`resume` 出终态并入队、
  `retrying` 保留进度；`go test ./...` 全绿。
- Python：`status()` 返回的令牌必须能通过 `verify_token`，且跨 task_id 不可用；
  case-service `tests/unit` 全绿。
- 前端：`isTerminalDeliveryFailure` 只认 `failed`，`retrying/done/进行中` 均不判死；
  `pnpm test` 与 `pnpm build`（含 `vue-tsc`）全绿。
- 端到端仍需现场确认：**库里出现第一条 `upload_mode=bridge_relay AND delivery_status=delivered`**。
