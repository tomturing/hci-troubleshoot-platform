## 一、问题：四个环节，零处 MD5

2026-10-28 对 P2 链路逐段核对后的结论（业务代码中 `md5`/`md5sum` 零命中）：

| 环节 | 原实现 | 能证明什么 |
|---|---|---|
| ① 节点 acli 打包 zip | 只 `stat` 大小 + 解析 progress 文本 | 文件存在、大小；补交付路径额外有 zip EOCD 尾部标记 |
| ② HCI → bridge | `tail -c +N` 续传；`localSize == remoteSize` 即认为拉完 | 字节数对得上 |
| ③ bridge → 平台 | 分片 `X-Part-SHA256` 双向比对 | 单跳传输未损坏 |
| ④ 平台 → 5888 | 按 `file_size` 分片发送，轮询会话 404 | 5888 收齐并完成归档 |

**关键缺陷**：没有任何一处把「平台上的包」与「节点上生成的包」直接比对过。分片哈希由
bridge 自己算、平台自己复核，只证明相邻两跳一致，证明不了上游是谁；平台合并后写入的
`object_sha256` 也没有比对对象，只是凭证。整条链的同一性靠大小与人工观察，属
「看起来校验了、其实没对账」。

## 二、设计：唯一基线 + 每跳收敛

第一性原理：能证明三处是同一份字节的锚点，只能在**源端**产生；之后每一跳都必须向它收敛。

```
① 节点: sha256sum / md5sum / acli system md5sum   ← 唯一基线
        │  写入 deliveryJob.SourceSHA256 / SourceMD5
② 拉取: MultiWriter(file, sha256) 流式摘要 + 字节数断言
        │  与基线比对，不一致 → fatal + 删除残包 + 清空分片进度
③ complete: payload.sha256 = 基线（或本地副本摘要）
        │  平台合并后复算并与声明比对 → integrity_state
④ 代传: 出站前重算平台副本摘要，与 object_sha256 比对
```

### 2.1 段①：节点摘要（`terminal_bridge/log_collect.go`）

- 命令优先级：`sha256sum` → `md5sum` → `acli system md5sum`。
  前两者与链路其余环节同算法（SHA-256）可直接比对；后者只作为老节点上的 md5 降级。
- 触发时机：`prepareDirect`（补交付）与 `waitCollect`（采集刚完成）之后、拉取之前。
  **必须在拉取前取**：拉完再取，节点上的包可能已被下一次采集同名覆盖，基线就不属于本次交付。
- 超时 8 分钟；失败**不阻断**交付，只把 `integrity` 降级为 `unverified` 并记录原因。

### 2.2 段②：拉取比对（`log_collect_transfer.go` / `delivery_runner.go`）

- `pullArchive` 改为边写边算 SHA-256，返回 `(written, sha256, error)`。
  续传时先把本地已有 `offset` 字节重新摘要，保证哈希覆盖整包而不是后半段。
- 字节数在拉取层收敛：`written != totalSize` 直接报错，避免把被截断的包当完整包上传。
- 比对失败归为 `deliveryFatalError`：源包内容已变，重试只会再白拉 20 GiB。
  同时 `discardLocalCopy` 删除残包、清空 `PulledBytes` 与 `UploadedParts`。
  **为什么清分片进度**：平台上的分片是按旧包算的哈希，继续跳过会拼出「前半旧包 + 后半新包」的杂交产物。

### 2.3 段③：平台整包复核（`log_collect_upload_service.py`）

- bridge 的 `complete` 请求新增 `sha256` 字段（优先节点基线，其次本地副本摘要）。
  没有摘要时字段缺省——空串会触发平台 `pattern` 422。
- 平台合并后复算整包 SHA-256，与 `declared_sha256 or expected_sha256` 比较；
  不一致 → 400 并删除 multipart。
- 结论落 `log_collect_task.integrity_state`：
  - `verified`：客户端声明过摘要且核对通过；
  - `unverified`：没有声明，只能证明传输一致。
- 每次 `begin_delivery` 重置为 `unverified`，避免上一次的结论被当成这一次的证据。

### 2.4 段④：代传前自证（`log_collect_relay_service.py`）

- 发送前核对：`object_size == 磁盘大小`、`object_sha256 == 重算摘要`。
- 任一不符 → `LC-TRANSFER-002`（永久错误，不重试），且一个字节都不发给 5888。
- 5888 协议不接收也不回传摘要（服务端 `process_upload.py` 自算 MD5 无对照值），
  因此**平台副本摘要就是本链路可留下的最终审计锚点**。

## 三、契约变更

| 位置 | 字段 | 说明 |
|---|---|---|
| `delivery_job`（bridge 落盘） | `source_sha256` / `source_md5` / `digest_source` | 节点基线；算法随结果记录，不猜测 |
| 同上 | `local_sha256` | 本地副本摘要；`complete` 的第二选择 |
| 同上 | `integrity` / `integrity_note` | `verified` / `unverified`；降级原因 |
| `delivery_result`（WS 回包） | `integrity` / `integrity_note` / `source_sha256` / `local_sha256` | 前端据此展示，不允许把 unverified 渲染成成功 |
| `POST /log-collect/tasks/{id}/uploads/complete` | 请求 `sha256`（已有） | bridge 现在真的会填；服务端此前只在客户端声明时才比对 |
| 同上 | 响应 `integrity_state` | 平台最终结论 |
| `log_collect_task` | `integrity_state varchar(16) NOT NULL DEFAULT 'unverified'` | `ck_log_collect_integrity_state` 限定两值 |

## 四、失败语义

| 场景 | 结果 | 是否重试 |
|---|---|---|
| 节点无任何摘要命令 | `unverified`，流程继续 | — |
| 拉取字节数 != 源包大小 | fatal，删残包、清分片 | 否 |
| 拉取摘要 != 基线 | fatal，删残包、清分片 | 否 |
| complete 声明的 sha256 != 平台合并结果 | 400，删除 multipart | 否（bridge 判 fatal） |
| 代传前副本摘要/大小 != 落库值 | `LC-TRANSFER-002`，不发任何请求 | 否 |

## 五、验收

1. `go test ./...`（terminal_bridge）：摘要命令语法/优先级/路径转义、解析严格性、
   `verifyPulledIntegrity` 每个分支、`buildCompletePayload` 不带空串、`discardLocalCopy` 重置。
2. `pytest backend/case-service/tests/unit`：`complete` 有声明 → `verified`；
   无声明 → `unverified`；大写十六进制不被误判；relay 摘要/大小不符时一个请求都不发。
3. 现场（待真机）：同一次 P2 交付后，平台任务 `integrity_state=verified`，
   `archive_sha256 == object_sha256 == bridge 日志 delivery.pull_verified.sha256`。
   若节点只有 md5，日志里 `algorithm=md5`，完整性仍成立（两段各自比对、传递性成立）。
