# 文档瘦身 Wave 5：把 §7.1 变更历史从「空头承诺」升为 CI 阻断门禁

> 本文承接 V-036 记录的最后一条「规范写着必须、却没有任何门禁执行」的缺口。
> Wave 3 已让 §7.3 frontmatter 与 §九 腐化检测有了脚本兑现，Wave 3 收口时把 §7.1
> 明写成「目前没有任何 CI 检查器强制」——本文就是来把这句话删掉的那一轮。
> 口径已写入 [文档管理规范](../../文档管理规范.md) **§7.1** 与 **§九**。

## 背景与需求

规范 §7.1 原文（v2.4 起）：

| 场景 | 要求 |
|------|------|
| 新建现行全量文档 | **必须**建节，至少写一行「初版」 |
| 存量文档被实质修改 | **必须**在节内追加一行（修订内容 + 关联事件文档） |
| 存量文档尚无该节 | 下次实质修改时一并补建，**不要求回溯补齐历史** |

而 v2.7 的执行方式段自己承认：「本节的三行口径**目前没有任何 CI 检查器强制**，
依赖 PR 评审人工比对 diff 与本表」。这正是 V-036 的判据——**规范里写着「必须」却没有
任何门禁执行，等于没有这条规范**。缺口的实际后果不是报错，而是「下次想查某次改动为什么
这么做时，才发现轨迹断了」，且断在发现的那一刻已经无法补救（`git log` 只能反推提交标题）。

## 决策（WHY）

三个候选里选第三个：

| 候选 | 内容 | 否决理由 |
|---|---|---|
| A 全量回填所有缺节文档 | 把 104 篇无节 + 7 篇缺行的存量一次性补齐 | 违反 §7.1 已定的「不回溯」：`git log` 反推不出「关联事件文档」，回填出的表格看着完整却不可信，等于把真信息涂成噪声 |
| B 继续靠人工评审 | 保持 v2.7 现状 | 就是 V-036 本身，已证明会长期无人发现 |
| **C 增量阻断门禁**（选定） | 只审本次 PR 改过的现行文档，结构不合规即阻断 | 与 §7.1「存量守增量」完全同构：不碰存量，只让「改了就忘」不再可能 |

**门禁的正当性边界（第一性原理）**：变更历史节相对 `git log` 的唯一增量价值，是
「关联事件文档」——一个 `git log` 拿不到、只在改动当下写得准的信息。所以门禁不该去
判断「这次改动够不够重要」（那是语义判断，机器做不到也不该假装做到），只需保证
**实质改动了却不留这行**这件事不再静默发生。

## 方法：判据与扫描范围

实现为 `scripts/ci/check_docs_changelog.py`，复用 `check_docs_rot.py` 的现行层口径
（`is_current_layer`）与 quoting-safe 的 git 采集管线（`list_changed_md_files` /
`list_changed_md_lines` / `list_content_changed_md_files`，即 V-034 修复过的那三个函数），
以 `merge-base(HEAD, origin/main)..HEAD` 为增量基准：

| 场景 | 机器如何判 | 触发门限 |
|------|-----------|---------|
| 新建 `docs/` 现行文档 | 须含 `## 变更历史` 节且 ≥1 行日期数据行 | 一律要求 |
| 实质修改存量文档（已有该节） | 节内须新增 ≥1 行本次改动的数据行 | 节外改动行 ≥ 3 |
| 实质修改存量文档（尚无该节） | 须补建节并写 ≥1 行 | 节外改动行 ≥ 3 |
| 小修 / 纯删除 | 不触发 | 节外改动行 < 3 |

「数据行」的判定是首列必须匹配 `YYYY-MM-DD`，据此天然排除表头「日期」行与 `|----|`
分隔行，也顺带挡住 `| | | |` 这类空壳。

扫描范围（**明文写进 §7.1，不留给机器猜**）：`is_current_layer` 且位于 `docs/` 之下，
再排除 `*/pitfalls/` 与 `_index.md`。有意**不含**仓库根 `README.md` / `AGENTS.md` 与
模块 README——它们不与事件文档互联，其变更理由 `git log` 已完整捕获，再套一节只会产出
与 `git log` 重复的第二份记录。这与 §7.1 早已对 pitfalls 目录的豁免同构。

存量实测基线（2026-10-27，用 `in_changelog_scope` 对全量 `docs/` 跑）：

| 分组 | 篇数 |
|------|------|
| 扫描范围内现行文档合计 | **193** |
| 已有变更历史节且含日期数据行 | 82 |
| 有节但缺数据行 | 7 |
| 完全无节 | 104 |

三档相加 82 + 7 + 104 = 193，与总数自洽。这 104 + 7 篇**不回溯**，只在其被实质修改时
由门禁要求补建/补行。

### 判据自身的四类逃逸面（对抗性审查，必须写在明面）

| 逃逸面 | 为什么机器抓不住 |
|--------|---------------|
| 单行就地改写关键结论 | Markdown 长段落通常是一个逻辑行，改一行=节外 1 行 < 3，落进「小修」豁免 |
| 把实质改动拆成多次更小 PR | 每次节外改动都 < 3，逐个豁免 |
| 凑一行无意义的日期数据行 | 机器只校结构（有无日期行），判不了行内容是否成立 |
| 纯删除旧内容 | 行号采集只登记新增/修改后的行，删除不产生区间，天然不触发 |

前两条是实质风险，后两条是有意取舍。处理方式与 §九「否定语境窗口」同源：不为此加
机器学习式的复杂度，而是把控制手段放在**可见性**上——门禁每次都打印「本次检查了 N 篇」，
凑行数与漏写都在 PR 上看得见，内容真伪仍归评审。

## 执行与实测证据

### 负向实测（门禁必须真的挡得住）

在临时提交里对两篇现行文档各插入 6 行正文（避开变更历史节）：一篇已有该节、一篇无节。
门禁输出（`EXIT=1`）：

```
变更历史门禁：本次增量检查 3 篇现行 docs 文档
❌ 2 篇实质改动未按 §7.1 追加变更历史行：
   [修改] docs/task/admin-ui/管理台任务.md —— 实质修改（节外改动 7 行）但变更历史节未新增数据行
   [修改] docs/task/agent/关键信号抽取验收报告.md —— 实质修改（节外改动 8 行）但无 `## 变更历史` 节，须补建并写≥1行
```

两篇分别命中「有节但未追加行」与「无节须补建」两条独立分支。

### 正向实测（合规改动不被误伤）

同一批次共检查 3 篇，第三篇就是本轮被实质改写的 `docs/文档管理规范.md`（§7.1 与 §九
整段重写、v2.10 数据行同时追加）。它**不在**上述违规清单里——说明「实质修改 + 补一行」
能正常通过，门禁不是「凡改必挡」。临时提交随后 `reset --soft` 撤销，两篇样例已还原为
0 处临时行（`grep -c 负向实测` = 0/0）。

### 用例与登记自证

- `scripts/ci/test_check_docs_changelog.py`：**13 项**全通过，覆盖无节/有节缺行/已合规/
  小修豁免/纯删除/补建、以及扫描范围 8 条边界（含根 README、AGENTS、模块 README、
  pitfalls、`_index.md` 形态上的豁免）；
- `ci.yml` 反向 grep 自证：`check_docs_changelog.py` 命中 5 处（docs filter / release_ci /
  ruff check / ruff format / 门禁步骤）、`test_check_docs_changelog.py` 命中 4 处
  （release_ci / ruff check / ruff format / pytest）——这正是 V-037 要求的「反向 grep
  自己的文件名，确认命中数 == 应参与的 job 数」；
- `ruff check` + `ruff format --check`（仓库锁定 0.15.4）均干净。
