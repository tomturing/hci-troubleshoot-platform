## 1. 背景与问题溯源

在工单 `Q2026082889116` 仿真诊断过程中，第 5 步 `[41398] 检查主机系统时间` 在仿真环境中有完整的基准命令输出（3 台主机的 `date` 结果），且在前端发起单步“试运行（DryRun）”时均稳定为 `PASS`；但在工单诊断流中该步骤却被判定为 `⚠️ 执行失败`。

### 现场数据复盘
查询 `tool_result` 表（ID `785e10ab-3f46-5438-a9ca-dd22a5682479`）记录：
```json
{
  "output_json": "HOSTS: 10.97.128.120 10.97.128.13 10.97.128.11\n10.97.128.120: ... Wed Aug 26 11:05:24 CST 2026 ...",
  "error": "QFK_AI_PROCESSING_FAILED: AI 处理调用或 JSON 解析失败: {\"code\": \"AI_TIMEOUT\", \"message\": \"AI 服务响应超时，请稍后重试\", \"detail\": \"phase=connect, type=ConnectTimeout, message=ConnectTimeout(''), url=POST https://coding.dashscope.aliyuncs.com/v1/chat/completions\"}"
}
```

**第一性原理根因分析**：
该信号在底层命令获取数据后，依赖下游 AI 进行智能推导（`mode=derive`，计算多主机时间差）。由于请求下游大模型接口时发生了瞬间网络抖动与建连超时（`ConnectTimeout`），信号提取层直接捕获异常并抛出 `QFK_AI_PROCESSING_FAILED`，导致整个诊断项失败。这暴露出平台在 AI 调用的韧性治理、重试策略与并发控制方面存在割裂和脆弱性。

## 3. 对抗性审查：现存架构的 3 大系统级脆弱点

1. **治理能力割裂（Kb-Service vs Shared AI Client）**：
   - `kb-service` 沉淀了并发舱壁信号量、429 智能退避、`Retry-After` 处理及带抖动的 Full-Jitter 重试；
   - 而 `agent-service`、`conversation-service` 与 `ai_extractor` 使用的是 `shared/clients/ai_client.py`，未接入统一并发舱壁，重试策略也未共享。
2. **信号提取对瞬态超时的容错不足（本次 41398 失败直接根因）**：
   - `ai_extractor.py` 在 `ai_client.invoke()` 发生 `ConnectTimeout` 时，直接将网络异常包装为 `QFK_AI_PROCESSING_FAILED`，导致整个诊断 Step 判定为失败，而没有做业务层的弹性重试或降级。
3. **流式调用单 Endpoint 脆弱性**：
   - `OpenClawAssistant.chat_completion_stream()` 目前只有在配置了多个不同 Endpoint 时才会在首 Token 前尝试 Fallback；单 Endpoint 遇到建连超时直接断流。

## 4. 统一治理优化方案 (Unified AI Governance Architecture)

从第一性原理出发，将全平台 AI 调用收敛到统一的治理核心：

```
                    ┌────────────────────────────────────────┐
                    │     各业务服务 (Agent / Signal / KB)    │
                    └───────────────────┬────────────────────┘
                                        │
                                        ▼
                    ┌────────────────────────────────────────┐
                    │  shared.governance.llm_governor        │
                    │  - 全局并发舱壁 (Semaphore)              │
                    │  - 瞬态错误分类器 (Timeout/429/5xx)     │
                    │  - 带抖动的 Full-Jitter 重试引擎        │
                    │  - 遵循 Retry-After 响应头             │
                    └───────────────────┬────────────────────┘
                                        │
                                        ▼
                    ┌────────────────────────────────────────┐
                    │  shared.clients.ai_client              │
                    │  - OpenClawAssistant (Stream / Invoke) │
                    │  - Langfuse 全链路 Tracing             │
                    │  - 单 Endpoint 首包重试保护            │
                    └────────────────────────────────────────┘
```

### 优化 1：沉淀 `shared.governance.llm_governor` 统一治理核心
将 `kb-service/llm_runtime.py` 中的成熟治理逻辑抽象下沉至 `shared.governance`，供全平台所有服务共用：
- **进程级/服务级并发舱壁**：通过 `asyncio.Semaphore` 限制最大并发调用数，防止高并发打爆 DashScope / 外部网关 QPM；
- **智能瞬态错误分类**：精确识别 `APITimeoutError`、`ConnectTimeout`、`ConnectError`、`RemoteProtocolError`、`RateLimitError(429)`、`5xx` 等瞬态错误；
- **Full-Jitter 指数退避重试**：
  $$\text{delay} = \min(\text{cap}, 2^{\text{attempt}-1}) \times \text{random}(0, 1)$$
  支持优先提取响应头 `Retry-After`，彻底避免重试流量雷暴。

### 优化 2：加固 `shared.signals.ai_extractor` 业务弹性
- 在 `_extract_ai_value_impl` 调用 `invoke()` 时接入统一治理引擎；
- 针对外部 AI 服务不可用或超时情况，区分**业务错误（如模型无法解析）**与**传输层瞬态故障（如 ConnectTimeout）**；
- 对传输层瞬态故障执行自动重试，确保信号不会因瞬时网络抖动而错误判负。

### 优化 3：加固 `chat_completion_stream()` 单 Endpoint 首包重试
- 在 `chat_completion_stream()` 中，若在未收到首个 Token 前发生 `ConnectTimeout` 或 `ConnectError`，在当前 Endpoint 上执行最多 2 次指数退避建连重试，避免单 Endpoint 环境下直接抛出 `AIStreamError`。

### 优化 4：可观测性与调用链全链路穿透
- 确保所有 AI 调用日志、Langfuse Tracing、Prometheus Metrics 均显式携带统一 `trace_id`、`case_id`、`conversation_id` 与 `signal_id`；
- 增加 Prometheus 指标：
  - `ai_governance_retries_total{operation, error_type}`
  - `ai_governance_concurrency_wait_seconds{operation}`

## 5. 实施路线图

1. **第一阶段（公共层下沉）**：在 `backend/shared/governance/` 创建 `llm_governor.py`，实现通用并发控制与 Full-Jitter 重试；
2. **第二阶段（客户端集成）**：改造 `OpenClawAssistant.invoke()` 和 `chat_completion_stream()`，接入统一治理器；
3. **第三阶段（信号提取层加固）**：在 `ai_extractor.py` 中强化异常分类与重试保护；
4. **第四阶段（服务收敛）**：将 `kb-service/llm_runtime.py` 迁移为引用 `shared.governance`，全平台统一治理。
