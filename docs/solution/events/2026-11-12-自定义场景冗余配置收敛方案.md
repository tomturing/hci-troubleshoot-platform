# 自定义场景冗余配置收敛方案

## 背景与需求

引用 [需求事件文档](../../requirement/events/2026-11-12-自定义场景冗余配置收敛需求.md)。059 收敛了默认场景两张表，但把 `log_collect_custom_scenario` 划在范围外；现场因此仍能看到「最后修改」列里打印内置管理员 UUID。本轮按用户授权把同一口径扩展到自定义场景。

## 方案概述 (WHAT)

一次提交同时收敛 UI、API 模型、ORM 与 DDL：删列表列与审核单选，删 5 个字段，物理删 5 列（迁移 060），保留 `operation_audit` 与结构化日志作为唯一追溯来源。`revision` 版本化、`spc`/`-c` 双通道、客户侧元数据契约全部不动。

## 详细设计

### 数据模型

`log_collect_custom_scenario` 保留 13 列：`scenario_id`、`revision`、`code`、`label`、`summary`、`applies_to`、`items`、`item_count`、`config_sha256`、`config_bytes`、`source`、`enabled`、`sort_order`。删除 `review_state`（含 `ck_log_collect_custom_scenario_review_state`）、`created_by`、`updated_by`、`created_at`、`updated_at`。后两列由 SQLAlchemy `TimestampMixin` 提供，因此 ORM 必须同步去掉该继承。

`desired_schema.sql` 同步删列、删 CHECK、删 `review_state` 列注释；`revision` 列注释与 `source` CHECK 文本逐字不动，避免 `atlas schema diff` 幂等失败。060 使用 `ALTER TABLE IF EXISTS ... DROP COLUMN IF EXISTS`，不写任何指向已删列的 `COMMENT ON COLUMN`（CI 会先按新 desired_schema 建表再 `ON_ERROR_STOP=1` 全量重放 data-migrations）。

### 接口设计

`LogCollectCustomScenarioCreate` / `Update` 删除 `review_state`；`Response` 删除 5 个字段；`ScenarioReviewState` 类型整体删除（全仓无其它后端引用）。管理端 API 路径不变，仅响应字段减少。客户侧 `LogCollectCustomScenarioClientItem` 本就只含 5 个元数据字段，契约零变化。

操作者继续由 api-gateway `X-Admin-User` / JWT `sub` 透传给 case-service：route 的 `operation_audit.details.updated_by`、结构化日志 `updated_by=` 与服务层日志 `actor=` 保留。这些是审计 JSON 键，不是数据库列，不能随全局替换误删。

### 关键技术点

- `service._COLUMNS` 从 18 列收敛为 13 列，`list_latest` / `get_latest` / `get_revision` 的 SQL 自动跟随；排序只依赖 `code / revision / sort_order`，过滤只依赖 `enabled`，不暗依赖时间列。
- `service.update()` 原本用 `current.review_state` 与 `current.created_by` 组装下一版 INSERT 参数，删 Response 字段后会 `AttributeError`；本轮改为不再写入这两项。
- `actor` 参数不再进入 SQL 绑定字典，但仍用于 `custom_scenario_created` / `custom_scenario_revised` 日志，保证「谁改的」可追溯。
- 前端 `CustomScenarioPanel.vue` 删除 `review_state` 的默认值/提交/重置/回填、表单单选、`formatTime()` 死代码与「最后修改」列；`logCollectCustomScenario.ts` 删除 `CustomScenarioReviewState` 类型与 5 个字段。

## 决策依据 (WHY)

### 方案选择

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. UI 隐藏 + DB 物理删列（选中） | 单一事实源，字段不会再被误用；消除 UUID 暴露与列名误导 | 需一次不可回滚的 DDL | 选中 |
| B. 只删 UI 列，保留 DB 列与 API 字段 | 改动最小 | 死字段留着必然被新代码误读，下次还要再改一次 | 不选 |
| C. 保留字段但把 UUID 映射成用户名 | 可读性略好 | 仍保留一个零消费的审核态与「创建时间冒充最后修改」，且引入一次用户表联查 | 不选 |

### 为什么选 A

第一性原理：一个字段要么被消费，要么不存在。`review_state` 全仓没有任何过滤或拦截逻辑，客户侧只按 `enabled` 判定；`created_by/updated_by/时间列` 的追溯职责已由 `operation_audit`（含 `actor`、`trace_id`）承担。把零消费字段留在 schema 里，等价于把「看起来有审核」的假承诺写进数据契约。界面上直接打印 `updated_by` 更把机器主键暴露给人看，属于展示层越界。

### 与 `AGENTS.md` §8.2 的关系

§8.2 要求删除 Pydantic 字段先 `deprecated=True` 过渡，其前提是存在跨版本滚动升级的外部调用方。本接口唯一消费方是同仓库、同 PR、同镜像整体部署的管理端前端，且 059 已对同一族接口采用直接删除并通过 CI；不存在新旧版本并存窗口。因此按既有先例直接删除，并在 changelog 中记录破坏范围。

### 权衡与妥协

- 不重写历史 revision 行：DDL 只删列，存量配置与任务引用保持原样。
- 不新增 `trace_id` 列：本表追溯走 `operation_audit.trace_id` 与请求链路，与 059 对 `log_collect_scenario` 的处理保持一致，避免把「收敛」变成「加列」。
- 不改写事件层史料：059 方案文档中「不动 `log_collect_custom_scenario`」是当时的真实决策，只在现行文档 changelog 里说明范围已扩展。

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| `update()` 读已删 Response 属性导致 500 | 高 | 中 | 同步改 INSERT 列与参数字典，单测覆盖通道切换更新 |
| 历史迁移重放引用已删列 | 高 | 低 | 核对 056/057/059 均不引用；060 用 IF EXISTS 且不写 COMMENT |
| 注释幂等 diff 失败 | 中 | 中 | `revision` 注释、`source` CHECK 文本逐字不动，仅删必须删的行 |
| 粗暴全局替换破坏审计 JSON 键 | 中 | 中 | 保留 route 的 `details["updated_by"]` 与日志 `updated_by=` |
| 测试只断言被 mock 的宿主页面 | 中 | 高 | 在真实 `CustomScenarioPanel` 单测中断言无「最后修改/待审核」 |
