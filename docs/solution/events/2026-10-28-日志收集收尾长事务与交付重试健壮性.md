# 收尾合并的事务边界，以及交付重试不该被 SSH 断连否决

## 一、第一性原理拆解

把「一次 P2 交付」还原到不可再分的物理事实：

1. 交付 = 把节点上的 `<工单>.zip` 送到日志服务器 5888；
2. 链路是四段：节点 → 客户机（SSH 拉取）→ 平台（分片 + 合并）→ 5888（代传）；
3. **每段对资源的依赖不同**：拉取依赖 SSH；上传与收尾只依赖本地副本 + 平台 HTTP；代传只依赖平台对象与 5888；
4. 合并是**纯文件 IO + 哈希**，与数据库无关：3.6 GiB 实测约 50s，20 GiB 会更久。

由 3、4 直接推出两条硬约束：

- **C1：DB 事务不得跨越合并。** 平台连接级 `idle_in_transaction_session_timeout = 30s`（`backend/shared/database/postgres.py`），事务只要开着，合并期间没有一条 SQL，PG 必然 terminate 连接；
- **C2：交付重试的必要条件按阶段判定。** 进入「上传 / 收尾」阶段后，SSH 已不是必要条件，此时节点掉线不构成"凭据失效"。

## 二、现场事实（Q2026102800720，2026-10-28）

| 时间(UTC) | 事实 |
|---|---|
| 06:16:20 | HCI 侧采集完成，包 3,670,776,038 B |
| 06:18:23 | 交付提交，`part_count=110`，chunk 32 MB |
| 06:31:33~06:34:19 | 4 次 complete 均 500；PG 日志 `terminating connection due to idle-in-transaction timeout` |
| 06:34:36 | case-service `InterfaceError: connection is closed`，SQL 为 `UPDATE log_collect_task SET archive_path/archive_sha256` |
| 06:34:53 | 第 5 次重试因 SSH 会话已回收 → `needs_reauth=true` → `delivery_status=failed` |

关键反差：平台 `objects/Q2026102800720/7be3a328-….zip` 存在，3,670,776,038 B，sha256 与那次失败 UPDATE 的参数完全一致 —— **包是好的，只是"元数据没落库"，代传因此永不触发，日志服务器上什么都没有**。

同窗口 Q2026102800880（318 MB，同为 P2）交付成功：它的合并只要几秒，没触发 30s 阈值。这说明故障是阈值效应，而非链路整体不可用。

## 三、三个确定性缺陷与修复

### 缺陷 1：complete 把长文件 IO 跨在事务里

`complete_upload` 先用请求级 session 读任务（开启事务），随后在同一事务内合并整包。合并期间无 SQL，30s 后 PG terminate 连接，`flush()` 必然失败 → 500。

修复：合并前显式 `commit()`（`LogCollectTaskRepository.commit`），把连接先还回池；合并后的写库落在新的短事务里。

### 缺陷 2：重试重写整包

失败重试共 4 次，每次都把 3.6 GiB 重新合并：峰值磁盘翻倍、每次又都超过 30s，重试原地打转。

修复：合并成功（原子 rename 之后）在 `meta.json` 写 `merged = {size, sha256}`；重试时若成品仍在且大小与 marker 一致，直接复用，不重写、也不重算 SHA-256（20 GiB 重算与重合并同价）。marker 生命周期止于 `delete_multipart`（成功收尾会删除整个分片目录）。

### 缺陷 3：交付重试被 SSH 断连否决

`advance()` 对所有阶段一刀切要求 SSH 会话，缺会话即 `deliveryAuthError`。而「上传 / 收尾」只读本地副本、只访问平台 HTTP。

修复：抽出 `deliveryPhaseNeedsNode`（`waiting_collect` / `pulling` 需要节点）与 `requireSessionForPhase`；上传/收尾阶段会话缺失不再判 needs_reauth。

## 四、对抗性审查

- **"包没传上去"？** 否。平台对象存在、大小与节点 stat 一致、sha256 自校验通过。
- **"日志服务器拒收"？** 否。`relay_status=none`，代传一次都没发起。
- **"网络整体故障"？** 否。同窗口 318 MB 的 P2 任务交付成功。
- **放宽会话依赖会不会把半截包搬走？** 不会。判据只放宽"上传/收尾"，而这两个阶段的输入是**已完整落盘的本地副本**；"包是否写完"仍由 `waiting_collect`/`pulling` 阶段的 EOCD 校验把关。
- **复用成品会不会用到坏对象？** marker 只在原子 rename 成功后写入，且复用前校验大小；大小不符即回落到完整合并。

- `terminal_bridge/delivery_session_test.go`：锁住各阶段对会话的依赖矩阵；
