# 日志收集失败兜底 P1（2026-11-23）

> 上一集：[2026-11-23 日志收集失败兜底 P0](./2026-11-23-日志收集失败兜底P0.md)
> 范围：8 项 P1 一次交付（bridge / case-service / 前端 / 契约 / 文档）。

## 1. 为什么做这一轮

P0 解决的是"失败时不要撒谎"：文案不再把平台瞬时不可用写成交付失败、错误码不再互相覆盖。
但 P0 之后仍然存在一个结构性问题——**失败一旦落库，证据链就断了**：

| 事实 | 后果 |
| --- | --- |
| 参数只存在于前端表单 | 重试 = 靠用户记忆重建一次采集，`modules` 还是被服务端改写过的投影 |
| 失败任务不登记产物位置 | 用户只剩"重新采集"，而这是唯一真正会丢日志的动作 |
| 终态后每 30s 无限轮询 | 页面挂一夜 = 2880 次读平台 + 探节点，还让用户以为任务在跑 |
| `{date}` 不按声明格式展开 | 同一份清单里 `%d` 与 `%Y%m%d` 并存，猜错的路径被静默判假 |
| 空包只有一句"未归因" | 排查者无法区分"包不存在 / 空包 / 偏小 / 不可读" |
| 安装降级只写在长文本里 | 用户读到开头"成功"就去 create，撞 `LC-INSTALL-010` |

## 2. 八项改动

### 2.1 终态停止轮询

`LogCollectPanel.vue` 引入 `TERMINAL_POLL_MAX_TICKS = 4`（30s × 4 = 2 分钟）：

- 任务处于 `completed / failed / cancelled` 且**证据不欠**时，每 30s 计一次预算；
- 出现**新事实**（`status / updated_at / progress / delivery_status / 同步动作` 的指纹变化）才重置预算；
- 预算耗尽 `stopAutoSync()`，并在刷新时间文案后追加「自动刷新已停止（任务已结束），可手动刷新」；
- 「刷新进度」与主流程退出都走 `resumeAutoSync()`：重置预算并重新起一轮。

对抗性审查：终态重启一个仍在节点上运行的任务时，接管入口会随自动刷新消失。取舍是显式的——
预算按"有没有新事实"续期，节点真在跑就会持续产生进度变化；真不动了就需要用户点一次刷新。
无限轮询的资源消耗与"看起来还在跑"的误导，代价高于多点一次刷新。

### 2.2 重试新建 task

- 后端建任务时落 `detail.request` 参数快照（见 2.5）；
- 前端新增 `retryAsNewTask()`：只对 `failed` 开放，先 `startRecollect(task)` 清理现场，再用
  `applyRequestSnapshot(task)` 重放服务端快照，最后 `handleStart()` 新建任务；
- `cancelAndRetry()` 同样优先按快照重放，不再读用户当前可能改过的表单；
- 自定义场景下**不回填 `modules`**：它只是投影（spc 会被改写成 `["core"]`），回填会让用户以为只勾了 core。

为什么必须新建：`failed` 是终态且平台禁止 `failed → completed`。复用旧行等于把进度归零、
把上一条错误清空——三次失败后就再也说不清"试过什么"。

### 2.3 failed 任务产物补登记

交付失败 ≠ 产物不存在。新增 `LogCollectService.backfill_failed_artifact()`：

- 只在 `failed / cancelled` 且 `archive_path` 为空时工作；
- 从 `log_collect_artifact_manifest` 取该任务最新一次清单；
- 只接受 `ok / suspect / incomplete` 质量：`invalid / unknown / 空` 一律不登记——
  把明知不可用的包登记成"产物位置"，等于把用户引去点一个必然失败的上传；
- 只写 `archive_path / archive_size / archive_sha256` 与 `detail.artifact_recovered`，
  **不碰 `status` / `delivery_status`**：产物还在 ≠ 已交付；
- 两个触发点：失败终态 PATCH 之后、清单晚到（`put_artifact_manifest` 之后），都是旁路 best-effort。

登记成功后，前端既有的 `canUploadFromNode` 会自动出现「上传到平台」入口，不需要新 UI。

### 2.4 `{date}` 格式统一

新增 `log_collect_date_placeholders.py`，成为唯一展开口径：

- 只支持 `{date}`（`{start}/{end}` 从未实现，放行等于让花括号路径去 `os.path.exists` 判假）；
- 格式白名单 `%Y-%m-%d / %Y%m%d / %Y%m / %d`，逐字符渲染，不走 `strftime`（避免 libc 本地化差异）；
- `expand_scenario_paths()` 按清单项自己的 `date_placeholders[].format` 展开，未声明时沿用历史 `YYYY-MM-DD`；
- 保存/校验/建任务三处共用 `validate_item_placeholders()`；过滤规则（`pattern`）同口径校验。

### 2.5 采集参数快照

`detail.request` 记录**服务端归一化后实际下发**的参数：

- `modules / date_from / date_to / ips / extra_paths / upload_mode / arch / acli_version / config_sha256 / path_count`；
- `remote_url` 只记 `remote_url_set`，URL 与 P1 票据永不入库；
- 目标集合超过 200 台、额外路径超过 100 条时截断，并显式给 `*_count` 与 `*_truncated`；
- 附 `sha256`（固定键序 + 紧凑分隔符）：后续任何改动都会让摘要对不上，可当证据用；
- `request / artifact_recovered / artifact_code` 加入 `_PUBLIC_DETAIL_RESERVED_KEYS`，客户端不可写。

### 2.6 安装降级（install_degraded）

- bridge：判据抽成 `installDegraded(diskProbed, missingPlugins)`，两种降级都置 `Degraded=true`；
  回执文案改为「安装降级：节点 X 的内置插件未落盘…」，不再只写一句"警示"；
- 前端：`AcliSyncFacts.degraded` 只在显式 `degraded === true` 时为真（老版本 bridge 不会误报），
  `acliManager` 在成功 resolve 前追加一条 `warn` 进度，面板同时 `ElMessage.warning`。
- 降级**不是失败**：工具确实装上了，直接判失败会把用户引去重装。

### 2.7 文案修正

契约内一次性改掉把责任/内部实现甩给用户的说法（`logCollectErrorHints.ts` 由契约生成）：

| 码 | 改前 | 改后 |
| --- | --- | --- |
| `LC-ENV-005` | 日志服务器不可达（error） | 日志服务器直连不可用（warning，说明会自动中转） |
| `LC-EXEC-003` | "这是节点侧拒绝，不是平台通道故障" | "本次下发被节点拒绝…无需重装 acli" |
| `LC-PLUGIN-015` | "与任务 ID 无关，不要按任务不存在处理" | "这是下发未生效，不是任务被删除" |
| `LC-PLATFORM-011` | "不要反复重试；先补齐证据" | "先点刷新重试一次，仍失败反馈工单号" |
| `LC-PLATFORM-012` | 平台内部错误 | 平台处理中断 |
| `LC-PLATFORM-013` | "僵尸会话 / 补交付" | "上传没有真正执行 / 上传到平台" |
| `LC-TRANSFER-008/009` | 客户机磁盘不足 / 客户机并发 | 本机磁盘空间 / 本机同时上传任务过多 |

面板内三处同步：`SSH_LOST_MESSAGE` 去掉 TMOUT 与"插件互斥"术语；两处"平台暂时不可用"
改为"暂时联系不上平台（或本机桥接端）"，避免被读成交付失败。

### 2.8 空包体检与错误码细分

- 桥侧 `archiveHealthVerdict()` 把结论写进清单 `evidence.archive_health`（`unreadable / missing /
  too_small / empty_archive / metadata_only / content_too_small / ok`），与平台同阈值；
  **只上报不阻断**：小于阈值也可能只是这台环境日志本来就少，直接判失败会丢掉唯一的包；
- 平台新增 `artifact_reason_code()`：按契约 `artifact_reason_code` 一对一映射，写入 `detail.artifact_code`；
- 新增三个运行时码（沿用 `TRANSFER` 层，符合"码前缀 = 层"的既有约定）：

| 码 | 含义 | 对应 reason |
| --- | --- | --- |
| `LC-TRANSFER-012` | 采集包内没有有效日志 | `empty_archive` / `metadata_only` |
| `LC-TRANSFER-013` | 采集包体积异常偏小 | `too_small` / `content_too_small` / `entry_count_low` |
| `LC-TRANSFER-014` | 采集包内容无法读取 | `unreadable` |

- 顺带修掉一个既有口径缺陷：路由写入 `quality=incomplete, reason=missing_hosts` 时，
  `incomplete` 不在质量枚举里被归一成 `unknown`，`missing_hosts` 也没有标签，
  页面于是同时显示「不完整」和「尚未探测包内容」。现在两者都是一等公民，
  `incomplete` 归入「产物可疑」，结论按 partial 处理。

## 4. 部署与验收

- 后端/前端随镜像发布即可生效；bridge 侧改动需要重建 exe 并现场人工重装（不会自动更新）。
- 验收顺序：
  1. 新任务详情出现 `detail.request`，`sha256` 稳定；
  2. 失败任务在清单已上报时出现 `archive_path` 与 `detail.artifact_recovered`，页面出现「上传到平台」；
  3. 失败结果页出现「重试（新建任务）」，点击后生成新 `task_id`，参数与快照一致；
  4. 终态任务 2 分钟后自动刷新停止，点「刷新进度」恢复；
  5. 造一个空包：`detail.artifact_code` 落 `LC-TRANSFER-012/013`，页面提示对应处置；
  6. 装一台缺插件节点：回执 `degraded=true`，页面对应警告。

## 5. 残留与边界

- 补登记的产物**不核验是否属于本次采集**：清单由 bridge 针对本次任务上报，但节点上若残留旧包，
  仍可能被登记。卡片附 `note` 说明"不代表已交付"，且不写交付终态；真正的归属核验仍在
  `LC-TRANSFER-011`（节点产物早于本次采集）信号侧。
- `{date}` 的 `%d` 语义按 strftime（两位日，如 `01`）。若现场实际是"时间戳/毫秒"等非常规命名，
  需要在管理端新增格式白名单项，而不是在代码里猜。
- 终态停止轮询后，节点侧后续变化只能靠手动刷新发现；这是有意的资源/误导权衡。
- 桥侧 `archive_health` 只对新 exe 生效；老 exe 的清单没有该字段，平台仍按体积/条目自行判定。
