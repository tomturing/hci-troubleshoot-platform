# 修复 SOP 提交变量值按钮失效问题设计方案

## 故障分析（第一性原理）

1. **前端交互行为**：
   - 用户在聊天界面填写变量（如 `is_sys_disk` 为 `"是"`）并点击「提交变量值」按钮时，前端触发 `handleInteractiveFreeText` / `handleInteractiveOption`。
   - 这两个方法向 `/api/conversations/{conversation_id}/interactive-response` 发送 POST 请求。
   - 发送时 Payload 仅包含 `request_id`、`acp_session_id` 和 `outcome`，**丢失了 `kind` 字段**和 **`metadata` 字段**（即变量名 `variable_name`）。

2. **后端路由行为**：
   - 接口 `/api/conversations/{conversation_id}/interactive-response` 接收请求，由于 Payload 没有 `kind` 字段，后端 Pydantic 模型将其默认为 `"sop_step"`。
   - 后端 `submit_interactive_response` 认为这是一个 `ops-agent` 专属的 ACP 交互卡片事件，于是直接调用 `self._agent_client.submit_interactive_response` 转发给 `ops-agent`。
   - 但由于当前是 HTP 排障诊断助手运行（并非 `ops-agent` 流程），`agent-service` 中没有该 ACP 会话，最终导致调用抛出异常或返回失败（503/500），前端捕获失败后不再进行后续消息流推送，导致按钮点击“没反应/没用”。

3. **正确的变量提交路径**：
   - SOP 变量的提交应当将数据写入当前工单的 SOP 变量池（`SopExecution.context_variables`），并将 SOP 执行状态从 `interrupted`（中断）更新为 `active`（活跃），从而使得 LLM 在下一步重新执行时能够读取到该变量值。
   - HTP 诊断引擎为 stateless 的 SSE 请求触发式。在完成变量库写入（状态恢复为 `active`）后，前端必须触发一条用户消息（如“是”），进而重新调用 `/api/conversations/{conversation_id}/message`。
   - 重新运行时，排障 Agent 检测到活跃的 SOP 状态，加载 `sop_resume_context` 恢复现场，重新进入 ReAct loop。由于变量库中已存在 `is_sys_disk` 的值，工具 `sop_request_variable` 会直接返回变量值而不再中断，流程得以继续推进。

## 拟修改的组件与文件

### 1. 前端应用组件

#### [MODIFY] [MessageBubble.vue](file:///aihci/hci-troubleshoot-platform/frontend/customer/src/components/MessageBubble.vue)
- 修改 `handleInteractiveFreeText` 和 `handleInteractiveOption` 两个方法：
  - 发送 `POST /api/conversations/{conversation_id}/interactive-response` 时，**将 `kind` 和 `metadata` 加入 Payload**。
  - **检测当前事件类型**：如果 `ev.kind` 是 `variable_input` 或 `variable_confirm`，则在后端响应成功后，不再执行 `chatStore.resumeOpsAgentStream()`（该方法只适用于 `ops-agent`），而是直接调用 `chatStore.sendMessage(value, { kind: 'interactive_response' })` 触发消息发送，将用户填入的变量值（或选择的选项）作为消息发送，从而唤醒排障 Agent 继续执行。

#### [MODIFY] [InteractiveRequestCard.vue](file:///aihci/hci-troubleshoot-platform/frontend/customer/src/components/InteractiveRequestCard.vue)
- 虽然该组件目前在 Chat 窗口中被注释掉了，但为了保持完整性并防止未来启用时引入同类 Bug，修改 `doSubmit` 方法，同样在 POST Payload 中包含 `kind: props.event.kind` 和 `metadata: props.event.metadata`。

---

### 2. 后端服务

#### [MODIFY] [conversations.py](file:///aihci/hci-troubleshoot-platform/backend/conversation-service/app/routes/conversations.py)
- 修改 `InteractiveResponseBody` Pydantic 模型，添加 `metadata: dict | None = None` 可选字段。
- 修改 `submit_interactive_response` 路由，将 `body.metadata` 传入 service。

#### [MODIFY] [conversation_service.py](file:///aihci/hci-troubleshoot-platform/backend/conversation-service/app/services/conversation_service.py)
- 修改 `submit_interactive_response` 的方法签名，接收 `metadata: dict | None = None` 参数。
- 修改方法逻辑：
  - 如果 `kind` 是 `variable_input` 或 `variable_confirm`：
    1. 校验 `metadata` 且从中提取 `variable_name`。
    2. 从 `outcome` 中提取用户提交的变量值（支持 `text` 或 `optionLabel`/`optionId`）。
    3. 调用 `SopExecutionRepository.set_variable` 将其写入数据库的变量库，恢复状态为 `active`，清理 `pending_variable_name`。
    4. 将用户的回复以 `user` 角色追加一条消息落库（保持与原逻辑一致的记录历史能力）。
    5. 返回 `True`（表示处理成功）。

## 验证方案

### 自动化测试
- 运行代码格式与质量门禁：
  ```bash
  make lint
  ```
- 运行单元测试保证没有破坏现有用例：
  ```bash
  make test
  ```

### 手动验证
- 重新测试诊断排障流程（如 `Q2026060555810`），当遇到变量确认节点（is_sys_disk）时，在文本框输入“是”或“否”并点击“提交变量值”按钮。
- 观察控制台网络请求，确认 `/api/conversations/{convId}/interactive-response` 返回 200。
- 确认界面能够自动生成一条用户气泡消息并唤醒排障 Agent。
- 确认排障 Agent 接收消息后，能够从中断状态恢复，并正确使用变量池中已写入的 `is_sys_disk` 值继续执行后续的 SOP 诊断节点。
