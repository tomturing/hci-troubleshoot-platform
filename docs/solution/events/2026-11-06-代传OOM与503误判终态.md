# 代传 OOM 与「成功被判成失败」（Q2026110600940）

## 现象

客户面板在日志收集最后一步「归档」报 `Case Service unavailable`，步骤条停在
探测✓ / 采集✓ / 上传✓ / 归档✗。表面看是归档失败，实际归档**已经成功**。

单号容易被读错一位（`Q2026110600940` 曾被误读成 `Q2026110600040`，后者在库中根本
不存在），排障时以「库里能查到 + 时间吻合」为准，不要只凭截图数字去找。

最终同一单出现矛盾记录：`relay_status=success`、`delivery_status=delivered`、
`archive_size=10294670673`、`integrity_state=verified`，但 `status=failed`、
`error_message='Case Service unavailable'`。

## 根因

### 1. 内存配额与「并发 × 分片」不匹配（直接原因）

P2 代传必须把 5888 在 `init_upload` 里指定的**整片**（实测约 10 MiB）读进内存再以
multipart 发出；单片大小由对端决定，平台无法调小（改成 chunked 流式需要 5888 支持，
风险更高）。因此进程 RSS 近似为：

```
RSS ≈ Python 基础运行时（约 120 MiB） + 并发数 N × 约 12 MiB + 数据面分片写入缓冲
```

`values.yaml` 里 `caseService.resources.limits.memory` 只有 `256Mi`，而代传任务
**没有并发上限**（`_spawn_relay` 每个任务一个 asyncio task）。多工单同时归档时峰值
不可控，9.59 GiB / 982 片这一单把进程撑到 OOM。

关键点：峰值由「同时跑了几个」决定，而不是「包有多大」——这正是缺上限时的隐患。

### 2. 网关把「连不上」翻译成与事实无关的文案（放大原因）

`api-gateway` 对下游 `httpx.RequestError` 一律兜底：

```python
raise HTTPException(status_code=503, detail="Case Service unavailable")
```

真实的 `message` 是 `All connection attempts failed`（`ConnectError`），说明是
**Pod 正在重启导致没有可用端点**，而不是"服务繁忙"或"归档失败"。这句文案同时
掩盖了连接失败与读超时两种完全不同的故障。

### 3. 前端把「问不到」当成「失败了」（致命一环）

`pollRelay` 直接 `await getRelay()`，任何异常都会冒泡到 `handleStart` 的 catch，
随后 `patchTask({ status: 'failed' })`。但代传是**服务端后台任务**，与前端这一次
HTTP 请求没有因果关系——请求失败只能证明"状态未知"。

原实现只对 `RelayPendingError`（2 小时轮询上限）做了"结果未知"处理，HTTP 层错误
漏在分支之外。

## 修复

1. **配额**：`caseService.resources` `limits.memory` `256Mi → 1Gi`，`requests`
   `96Mi → 128Mi`。
2. **并发闸门**：新增 `LOG_COLLECT_RELAY_MAX_CONCURRENCY`（默认 3），在
   `_run_relay_gated()` 内用进程级 `asyncio.Semaphore` 限制同时归档的任务数。
   排队超时（取租约的一半，最小 5s）时**交还租约**成 `pending`，交给下一轮
   `reconcile` 接管——因为排队中的协程没有心跳，干等会被其他实例判成"执行者已死"
   而抢占，导致同一个包两个进程同时上传。
3. **前端不写终态**：新增 `isTransientPlatformError()`，`502/503/504` 与
   「`isAxiosError` 但无 `response`」判为"这一刻问不到"；`pollRelay` 静默重试，
   连续 12 次（约 1 分钟）才落 `RelayPendingError`（结果未知，仍不写 failed）。
   业务代码自己 `throw new Error(...)` 不带 `isAxiosError`，仍按真失败处理。

## 发布影响：其他正在上传的工单会怎样

改 `values.yaml` 会触发 `case-service` 滚动更新（`RollingUpdate`，
`maxSurge=1`、`maxUnavailable=0`、`terminationGracePeriodSeconds=300`）。

| 环节 | 影响 | 说明 |
|---|---|---|
| 新 Pod 启动 | 先起后停，旧 Pod 继续服务 | `maxUnavailable=0`；新 Pod 需与旧 Pod 同节点共享 RWO 卷（local-path 允许同节点双挂载） |
| 在途数据面分片上传（bridge → `/api/direct/.../parts`） | 不中断 | 旧 Pod 在 300s 优雅期内把在途请求处理完；bridge 侧另有重试 |
| 在途 P2 代传（平台 → 5888） | **暂停数十秒**，随后自动续传 | SIGTERM 后 `shutdown_relays()` 取消在飞任务并把租约交还 `pending`（不写 failed），新 Pod 启动即 `reconcile_relays_on_startup()` 接管，最迟一个 60s 周期内恢复 |
| 已传分片 | 不重传 | 每片成功即落库 `relay_chunk_index`，续传从下一片继续；仅"取消瞬间正在传的那一片"会重传（5888 覆盖写，幂等） |
| 前端页面 | 不中断 | 纯静态资源；页面刷新后生效，上传本身由 bridge 与 case-service 完成 |
| 任务终态 | 不会被改写 | `shutdown` 与排队超时都只交还成 `pending`，不写 `failed` |

发布前建议确认在途代传数量，避免在最忙的时刻重启：

```sql
select count(*) from log_collect_task where relay_status = 'running';
```

分两种情形的判断：

- 该值为 0：直接发布，无在途影响。
- 该值 > 0：仍可发布，但会把这些任务推迟一个接管周期（≤60s）并重传至多 1 片；
  若包特别大且已接近完成，建议等它收尾。

需要重点盯的风险（与本次改动无直接关系，但发布时会被触发）：

1. 节点剩余内存不足 `128Mi` 时新 Pod 会 `Pending`，旧 Pod 继续服务（不会中断，
   但发布卡住）。
2. 集群若换成拒绝多挂载的 CSI，新 Pod 会卡 `ContainerCreating`，此时把
   `caseService.logCollectStorage.rollout.strategy` 改回 `Recreate` 即可恢复可发布性。

## 验收

1. `relay_status=running` 的任务在发布后被新 Pod 接管，最终 `success`；
   期间**不得**出现 `status=failed`。
2. 人为制造瞬时不可用（如 `kubectl delete pod` 一个副本）后，前端轮询应表现为
   继续等待，页面提示"平台暂时不可用，任务仍在后台进行"，而不是"归档失败"。
3. `kubectl top pod` 观察峰值内存，应稳定在配额 60% 以下；OOMKilled 计数不再增长。

## 遗留

- 网关的 `Case Service unavailable` 文案仍未区分连接失败与读超时，排障时必须以
  `log_collect_proxy_error` 里的 `message` 原文为准。
- 本次事故诱发的重复采集任务 `b272ad82…` 与已被误判为 `failed` 的任务
  `dea7ccec…` 需要数据订正（后者实际已交付 9.59 GiB，不应重传）。
