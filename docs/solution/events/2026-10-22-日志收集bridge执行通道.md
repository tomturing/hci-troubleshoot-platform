# 日志收集的 bridge 执行通道（PR-3a）

## 一、为什么必须放在 bridge

三条硬约束推导出的唯一位置：

1. **云端服务不可达客户私网 HCI**（v5.4 已确认，`acli_client._run_ssh` 废弃即此原因）；
2. **acli 插件命令要求 stdin 为 tty**，必须走 PTY（见 [terminal_bridge 强制 PTY](2026-10-22-terminal-bridge强制PTY.md)）；
3. **采集是异步长任务**，`create` 只下发，进度需后续轮询，且 `progress` 只反映**发起节点**的本地视图。

因此 bridge 承担：参数校验与转义 → PTY 执行 → 结果结构化。

## 二、消息协议

### 2.1 入站 `log_collect`

| 字段 | 说明 |
|---|---|
| `log_action` | `probe` / `create` / `progress` / `cancel` |
| `ticket_no` | `-s`，工单号，`^[A-Za-z0-9_-]{1,32}$` |
| `modules` | `-m` 枚举（10 个专项），缺省 `other`，自动去重 |
| `date_from` / `date_to` | `-d`，`YYYY-MM-DD`，跨度 ≤ 30 天 |
| `ips` | `-i`，`all` 或逗号分隔 IPv4（逐段 ≤ 255） |
| `extra_paths` | `-p`，绝对路径，禁 `..` 与 shell 元字符 |
| `remote_url` | `probe` 时为被探测地址；`create` 时为 `-u` 上传目标 |

### 2.2 出站 `log_collect_result`

| 字段 | 说明 |
|---|---|
| `log_action` | 回显动作 |
| `status` | `ok` / `error` |
| `log_data` | `probe` 为环境快照；`progress` 为结构化进度 |
| `raw` | 插件原始输出（解析失败时前端按原文展示） |
| `exit_code` / `error_type` / `message` | 失败语义 |

## 三、安全设计（bridge 是最后一道防线）

插件本身不防注入：`-s` 直接参与 `{save_filename}.zip` 路径拼接，`-p` 直接拼进 `nohup` 命令串。
因此 bridge 对所有外部输入做**白名单校验 + POSIX 单引号转义**：

| 输入 | 规则 |
|---|---|
| ticket_no | `^[A-Za-z0-9_-]{1,32}$` |
| modules | 10 项枚举 |
| date | `YYYY-MM-DD`，起止有序，≤ 30 天 |
| ips | `all` 或 IPv4 列表，逐段 ≤ 255 |
| extra_paths | `^/[A-Za-z0-9_./-]+$`，禁 `..` |
| remote_url | 仅 `http(s)://`，禁空白与 shell 元字符 |

转义函数：`shellQuote()`（`'` → `'\''`），单测覆盖含单引号场景。

## 四、环境探测（probe）

一次性返回前端确认安装与选择上传方式所需事实：

| 字段 | 来源 |
|---|---|
| `architecture` | `uname -m` |
| `acli_installed` / `acli_version` / `acli_build_time` | `acli --version` |
| `available_mb` | `df -P -m /sf/data/local` |
| `log_server_reachable` / `http_code` / `latency_ms` | `curl -o /dev/null -w '%{http_code} %{time_total}'` |

判定口径：HTTP 状态 **2xx/3xx/4xx 均视为网络可达**（401/403 也证明连通），仅连接失败或 5xx 视为不可达。

## 五、进度解析契约

`acli log_collect progress` 输出为中文纯文本（`--formatter json` 实测返回 `{"data":""}`，不可用），
因此必须解析文本：

| 结构化字段 | 来源行 |
|---|---|
| `status` | `状态：`（「发送地址」之前） |
| `archive_path` | `压缩包路径…：` |
| `percent` / `done` / `total` | `总进度：63% - 2/3` |
| `hosts[]` | `172.28.25.2  收集完成  100%` |
| `upload_url` / `upload_state` | `发送地址：` 及其后的 `状态：` |

**降级策略**：`parse_ok=false` 时前端展示 `raw`，**不得据此把任务判为失败**——插件文案可能随版本变化。

## 六、现场验证（HCI 6.11.1_R1）

```
probe: {Architecture:x86_64 AcliInstalled:true AcliVersion:1.0.0
        AcliBuildTime:2026-09-02 14:34:45 AvailableMB:104
        LogServerURL:http://acli.sangfor.com.cn:5888/
        LogServerReachable:true LogServerHTTPCode:200 LogServerLatencyMS:1274}
progress: exit=0 parse_ok=true status="收集任务不存在！"
```

复现命令：

```bash
HCI_TEST_ADDR=172.28.25.1:22 HCI_TEST_USER=root HCI_TEST_KEY=~/.ssh/id_ed25519 \
  go test -run TestManualLogCollectProbe -v ./...
```

现场观察到的两个事实（已写入文档，避免后续误判）：

1. `/sf/sbin/acli` 是 641B 的 bash wrapper，转发到 `/sf/bin/acli`；两者版本一致。
   该文件在本机 15:24 被替换为 1.0.0（此前为 1.0.1），**与本次改动无关**。
2. 该环境 `/sf/data/local` 仅剩 **104MB**，而 `log_collect` 要求每台目标机 ≥ 6GB。
   因此该环境可以 `probe/progress/cancel`，但 `create` 会被插件拒绝——属于环境限制，不是代码缺陷。
