# DSH 诊断集成方案

## 背景与需求

需求文档：[docs/requirement/events/2026-10-22-DSH诊断集成.md](../../../requirement/events/2026-10-22-DSH诊断集成.md)

要在单节点 k3s（`aihci`，对外域名 `acli.sangfor.com.cn`）上容器化部署 DSH（DeepSeek Harness `0.2.1-rc.2`），并在 admin-ui 的「可观测性」与「分类基线」之间内嵌「DSH诊断」。

### 关键前置事实（来自对上游仓库的取证，非推测）

| 事实 | 证据位置 | 对方案的约束 |
|---|---|---|
| 监听地址禁止 `0.0.0.0` | `docs/subsystems/web-server.md`："The unspecified address … is rejected at load" | 不能直连 Traefik，必须绑具体地址 |
| 无匿名模式，缺 cookie/token 直接 401 | `packages/client/connection/src/browser-auth.ts` | 不能沿用 Grafana 的匿名嵌入范式 |
| launch token 每进程随机、无 env 覆盖 | `browser-auth.ts` `processLaunchToken()` 用 `randomBytes` | token 必须运行时抓取，不可硬编码 |
| token 交换只在 `GET /` 生效，随后 302 到 `./` | `browser-auth.ts` + `public-deployments.md` | 反代必须能还原外部路径前缀 |
| 启动打印 `dsh web: <url>?token=xxx`，且为官方就绪信号 | `packages/bundle/web-app/src/index.ts:231` | entrypoint 可从 stdout 可靠抓取 |
| Host/Origin 栅栏：非 trusted-host 全部 API 403 | `public-deployments.md` | 必须配 `--trusted-host` |
| Cookie `Path=/; HttpOnly; SameSite=Strict` | `browser-auth.ts:138` | 同域嵌入可行；但 `Path=/` 会串到 `/admin/`、`/api/` |
| 未设置 X-Frame-Options / CSP | 全仓 grep 零命中 | **可直接 iframe**，优于 Grafana |
| 依赖 WebSocket | Agent 流式输出走 WS | 反代须转发 Upgrade |

## 方案概述 (WHAT)

新建独立 Helm Chart `hci-platform-dsh`，部署到独立 namespace `hci-dsh`。Pod 内为 **双容器**：

- `dsh` 主容器：监听 **127.0.0.1:3080**（仅本 Pod 可达），运行 `dsh --profile web`。
- `dsh-proxy` sidecar：nginx，监听 8080，承担对外/对内两件事。

对外链路（浏览器）：

```
浏览器 https://acli.sangfor.com.cn/dsh/?token=<t>
  → Traefik Ingress(ns hci-dsh, path /dsh, priority 2500，保留 Host、不剥离前缀)
  → nginx sidecar :8080  [剥离 /dsh 前缀 → 127.0.0.1:3080/；proxy_redirect / /dsh/；proxy_cookie_path / /dsh/；转发 WS Upgrade]
  → dsh 127.0.0.1:3080
```

对内链路（token 分发）：

```
dsh 进程 stdout "dsh web: https://acli.sangfor.com.cn/dsh/?token=<t>"
  → entrypoint 抓 token → 写入 emptyDir 共享卷 /run/dsh/token
  → nginx sidecar 暴露 /__internal/token（仅集群内，Ingress 不暴露此路径）
  → api-gateway 新增 GET /api/dsh/launch（require_admin 鉴权）
     经 Service dsh.hci-dsh.svc.cluster.local:8080 拉取 token
  → admin-ui 前端拼接 iframe src = /dsh/?token=<t>
```

## 详细设计

### 架构变更

新增独立 Chart `deploy/helm/hci-platform-dsh/`，与既有 `hci-platform-obs` 平级，遵循同样的 ArgoCD Application 命名规范（`hci-platform-dsh-staging.yaml` / `-prod.yaml` / `local/hci-platform-dsh-dev.yaml`）。

### 接口设计

| 接口 | 方法 | 位置 | 鉴权 | 说明 |
|---|---|---|---|---|
| `/api/dsh/launch` | GET | api-gateway（新增 `app/routes/dsh.py`） | `require_admin` | 返回 `{ "url": "/dsh/?token=<t>" }`，供 admin-ui 前端拼接 iframe |
| `/__internal/token` | GET | DSH Pod 内 nginx sidecar | 仅集群内可达（Ingress 不暴露） | 返回裸 token 文本 |

### 前端改动

| 文件 | 改动 |
|---|---|
| `frontend/admin/src/views/DshDiagnosisView.vue` | 新增。iframe 容器沿用 `ObservabilityView.vue` 的 `.iframe-wrapper` 结构与样式 |
| `frontend/admin/src/router/index.ts` | 新增路由 `path: '/dsh'`，`meta: { title: 'DSH诊断', icon: 'FirstAidKit', order: 4.5 }` |
| `frontend/admin/src/utils/__tests__/adminMenu.spec.ts` | 在 `'可观测性'` 与 `'分类基线'` 之间插入 `'DSH诊断'` |

菜单由 `meta.order` 排序（`utils/adminMenu.ts`），`4.5` 精确落在 4 与 5 之间；`App.vue` 与 `adminMenu.ts` **无需改动**（菜单自动从路由生成）。

### 容器镜像

- 基础镜像：`node:22-alpine`（DSH 要求 `^22.19.0 || >=24`）。
- 安装：`npm i -g @deepseek-ai/dsh@0.2.1-rc.2`。
- 入口脚本 `docker-entrypoint.sh` 负责：后台启动 dsh → 轮询 stdout 抓取 `dsh web: ` 行 → 原子写入 `/run/dsh/token` → 前台等待 dsh 退出。

### 存储与挂载

| 卷 | 类型 | 容器内路径 | 模式 | 用途 |
|---|---|---|---|---|
| 客户日志 | `hostPath: /sf/log` | `/data/customer-logs` | **只读** | DSH 读取 HCI 故障日志压缩包 |
| 工单产物 | `hostPath: /sf/tickets` | `/data/tickets` | **只读** | 宿主机同步服务解压后的工单目录树，见《工单日志宿主机同步服务》10.4 |
| 工作区 | `emptyDir` | `/work` | 读写 | DSH 解压/分析临时产物 |
| token 交换 | `emptyDir` | `/run/dsh` | 读写 | dsh 容器写、nginx 容器读 |
| DSH 家目录 | `emptyDir` | `/home/dsh` | 读写 | 暂存凭据与会话，随 Pod 重建丢失（见 values.yaml 的取舍说明） |

**权限说明（勘误）**：`/sf/log` 实测权限 `755`、属主 `support:support(1001)`。`755` 表示 others 已具备 `r-x`，因此**只读访问无需任何 `securityContext`**（既不需要 `fsGroup: 1001` 也不需要 `runAsUser`）。仅在需要写入时才涉及属主匹配——本方案为只读挂载，故不受影响。

### 安全基线

- 容器以非 root 用户运行（`runAsNonRoot: true`，`node` 用户 1000）。
- 只读根文件系统（`readOnlyRootFilesystem: true`），仅 `/work`、`/run/dsh`、家目录可写。
- 删除全部 Linux capabilities。
- 提供 NetworkPolicy 清单（默认 `enabled: false`，原因见风险 R3）。
- Ingress 仅暴露 `/dsh` 前缀，`/__internal/token` 不在 Ingress 路径内。
- 前端 iframe 与页面设置 `Referrer-Policy: no-referrer`，避免 token 经 Referer 外泄。

## 决策依据 (WHY)

### 决策 1：DSH 绑 127.0.0.1 + nginx sidecar，而不是绑 Pod IP 直连 Traefik

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **A（选中）loopback + nginx sidecar 反代** | 暴露面最小（DSH 仅同 Pod 可达）；无需注入会变动的 Pod IP；nginx 能同时解决前缀剥离、Location 重写、cookie Path 重写 | 多一个容器 | ★★★★★ |
| B. 绑 Pod IP + Traefik stripPrefix | 少一个容器 | **功能不成立**：官方明确 "the stripped backend cannot reconstruct that external path"，Traefik 无法反向重写 `Location: /`，浏览器会被 302 跳到域名根路径丢失 `/dsh`；且 `Path=/` cookie 会串到 `/admin/`、`/api/`；DSH 端口直接暴露在 Pod 网络 | ★☆☆☆☆ |
| C. Traefik + 独立子域名（不剥离前缀） | 无需处理前缀 | 需新增 DNS 记录与证书；与现有 Grafana/Langfuse 的路径范式不一致，前端 URL 推导要额外分支 | ★★★☆☆ |

**为什么选 A**：决策 B 的致命点是**功能性**而非体验性——Traefik 的 `stripPrefix` 只处理入站请求，不处理出站 `Location` 头，而 DSH 的 token 交换**必须**经过一次 302 到 `./`。这一跳转在 B 方案下必然把用户甩到域名根路径，直接被 customer-ui 的 `/` 路由吞掉，链路彻底断裂。nginx 的 `proxy_redirect` + `proxy_cookie_path` 是唯一能同时解决三件事（前缀剥离、Location 还原、cookie 作用域收敛）的位置。既然必须引入 nginx，让它承担反代即可，顺带把 DSH 收敛到 loopback，暴露面从"整个集群 Pod 网络"降到"本 Pod 内"。

**为什么不选 C**：技术上可行（`eTLD+1` 同为 `sangfor.com.cn`，`SameSite=Strict` 在子域下仍为 same-site），但需新增 DNS 与证书，且与现有 `/grafana`、`/langfuse` 路径范式不一致，会让前端的 URL 推导逻辑多出一个分支，长期维护成本更高。这里选择的理由是**与既有架构一致 + 零 DNS 成本**，而不是 cookie 原因——前期对子域的 SameSite 判断有误，此处更正。

### 决策 2：token 由 api-gateway 代持下发，而非硬编码或前端自取

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| **A（选中）api-gateway `require_admin` 鉴权后从 DSH Service 拉取** | 鉴权收敛到既有 JWT 体系；token 实时拉取，天然跟随 Pod 重建；不落盘到集群外 | 需改 api-gateway | ★★★★☆ |
| B. hostPath 落盘供 admin-ui Pod 读取 | 不改后端 | 跨 namespace 落盘耦合脏；nginx 无法在配置里动态引用外部文件；单节点假设 | ★★☆☆☆ |
| C. 前端直接访问 DSH 内部 token 接口 | 最省事 | **等价于公网公开 token = 公开 Agent 控制权**，不可接受 | ☆☆☆☆☆ |
| D. 放弃内嵌，改为新窗口打开 | 最安全 | 不满足需求 2 | ★★☆☆☆ |

**为什么选 A**：token 是进程凭据且随机，唯一可靠来源是运行时抓取。抓取后必须有一条受控的传递路径。C 完全不可接受（等于把 shell/ssh 执行权公开），B 的跨 namespace 文件耦合会引入单节点假设与权限问题。A 把分发口收敛到 api-gateway 的既有 `require_admin` 依赖上，任何能拿到 token 的人都已通过管理员 JWT 校验，与项目既有的管理端鉴权模型一致，且不新增鉴权体系。

### 决策 3：独立 Chart + 独立 namespace，而非并入 hci-platform

- DSH 是独立能力单元，且是唯一具备 Agent 执行能力的组件，独立 namespace 便于后续施加网络隔离与独立扩缩容。
- 与既有 `hci-platform-obs`（可观测性）保持同样的组织层级，符合现有 GitOps 目录规范。
- 并入 `hci-platform` 会让 DSH 与业务服务共享 namespace，未来施加 NetworkPolicy 时颗粒度变差。

### 决策 4：Ingress router.priority 设为 2500

现有：customer-ui 根 Ingress 有 `/` 路径，langfuse 显式 3000、grafana 2000。新 `/dsh` 若不设优先级，存在被 `/` 回退路由吞掉的历史风险（langfuse 就是为此显式设了 3000）。取值 2500 落在 grafana 与 langfuse 之间，满足"高于默认"且与既有取值不冲突。

### 权衡与妥协

1. **引入 sidecar 换取功能正确性**：多一个容器会增加一点资源与运维复杂度，但这是 DSH 反代契约的硬性要求，不是可选优化。
2. **保留完整 Agent 能力（用户决策）**：本次按用户选择不裁剪 `shell`/`ssh`/`computer-use`。相应地必须把"只读挂载 + 非 root + 只读根文件系统 + NetworkPolicy 清单"作为强制交付项一并落地，而不是留给后续。
3. **NetworkPolicy 默认关闭**：因为当前 CNI 不强制执行（见 R3），默认开启只会产生"看起来生效其实没生效"的假象，反而更危险。清单产出并默认关闭 + 文档明示，是诚实做法。

## 勘误与补充（2026-10-22 首次同步后实测发现）

首次 PR 合入后 ArgoCD 立即同步，Pod 停在 `ImagePullBackOff`。复盘发现本方案在
**镜像发布链路**上存在 5 处缺陷，均不影响 `helm lint` 与 CI 静态检查，因此此前未被拦截：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | `dsh/Dockerfile` 写作 `COPY docker-entrypoint.sh` | CI 构建上下文是仓库根，**构建阶段即失败** | 改为 `COPY dsh/docker-entrypoint.sh` |
| 2 | `dsh` 未注册进 `resolve_image_build_plan.py` 的 `OTHER_SERVICES` | CI **永不构建** DSH 镜像 | 注册 `("dsh", "dsh/Dockerfile", "dsh")` 并补路径映射分支 |
| 3 | chart 写死 `ghcr.io/tomturing/hci-dsh` | 与 CI 推送地址不符 → **ImagePullBackOff** | 改为 `<global.imageRegistry>dsh:<tag>` |
| 4 | `sync-env-repo-tags.sh` 的 `service_repository()` 无 `dsh` 分支 | tag 回写失败 | 增加 `dsh) echo "dsh" ;;` |
| 5 | chart 未声明 `imagePullSecrets` | ghcr 匿名拉取 **401**（私有仓库） | 在 `hci-dsh` 内自行渲染 `ghcr-pull-secret` |

### 第 5 条的根因值得单独说明

`hci-platform` chart 会把 `ghcr-pull-secret` 渲染到 `hci-staging`，而 **Secret 不能跨命名空间引用**。
DSH 部署在独立的 `hci-dsh`，因此必须在该命名空间内重新渲染一份同名 Secret，
不能指望复用 `hci-staging` 的凭证。这是"独立 namespace"这个决策带来的隐性成本。

### 为什么 CI 没能拦截

现有 CI 的 `Lint`、`helm lint`、`docs-governance` 均只做**语法与格式校验**，
没有任何 job 校验"chart 声明的镜像地址"与"构建计划实际推送的镜像地址"是否一致。
已补充两条回归测试以堵住其中一部分：

- `test_dsh_change_triggers_dsh_rebuild`：确保 `dsh/` 变更会触发构建且带 `deploy_key`
- `test_every_registered_service_dockerfile_exists`：确保每个注册服务的 Dockerfile 真实存在

仍未覆盖的是"镜像地址字符串一致性"，属于跨文件契约，后续可通过渲染 chart 并比对
构建矩阵的方式补测。

### `/sf/log` 容器内权限的实测结论（补充）

在 `uid=1000` 的临时 Pod 中挂载 `/sf/log` 实测：

```
目录：drwxr-xr-x 2 1001 1001   （UID/GID 数字原样透传，k3s 默认无 userns-remap）
挂载：ext4 ro,relatime
读：  OK
写：  Read-only file system
```

即 uid 1000 落在 `others` 位（`r-x`），可读可进入但不可写；写失败同时受
"只读挂载（EROFS）"与"others 无 w 位（EACCES）"双重保护。
**印证了不设 `fsGroup`、不需要 `runAsUser=1001` 的判断**。

## LLM 提供商接入（2026-10-22 补充）

### 配置载体

DSH 用 `$DSH_HOME/profiles/web/cordis.patch.yml` 声明 provider（`DSH_HOME` 默认 `~/.dsh`）。
本方案把它拆成三层：

| 层级 | 内容 | 位置 |
|---|---|---|
| 值声明 | `dsh.llm.*` | chart values + 环境仓库 |
| 配置文件 | `cordis.patch.yml` | ConfigMap `dsh-llm-config` |
| 凭证 | `DSH_QWEN_API_KEY` | Secret `dsh-llm-credentials`（由 `secrets.llmApiKey` 渲染） |

### 决策：用 initContainer 播种，而不是只读挂载 ConfigMap

只读挂载最省事，但 DSH 的「设置 → 模型」页同样会写这份文件，只读会让页面保存失败。
因此改为 initContainer 把 ConfigMap 拷进 emptyDir 家目录卷：
**GitOps 作为基线，运行时可改，Pod 重建后回到基线**。

代价是运行时的修改不会持久化——对诊断工具来说可接受，因为会话本身也是临时的。

### 三个 compat 取值全部来自实测，而非经验

这是本次最有价值的部分。三个取值如果凭"OpenAI 兼容"的常识去猜，会全部猜错：

| 取值 | 实测结论 |
|---|---|
| `api: openai-completions` | 端点路径为 `/compatible-mode/v1` |
| `compat.supportsDeveloperRole: false` | 实测 `role: developer` 返回 **400**：`developer is not one of ['system','assistant','user','tool','function']`。而 pi-ai 对**声明了推理能力**的模型默认用 `developer` 角色承载系统提示词，qwen3.8-flash 恰好返回 `reasoning_content` → 若不设此开关，**每个请求都会被拒** |
| 不覆写 `maxTokensField` | 实测 `max_completion_tokens` 返回 **200**，无需改成 `max_tokens`（文档建议的通用兜底在此反而多余） |

### 关闭思维链

`disableThinking: true` → `compat.thinkingFormat: qwen` + `reasoning: 'off'`，
DSH 据此下发 `enable_thinking=false`（已实测端点接受该参数且 `reasoning_content` 消失）。

原因：qwen3.8-flash 默认思考会让单次调用达到 70s 级，Agent 多轮调用不可用。
环境仓库既有服务也因同一原因统一关闭思维链。

⚠️ `'off'` 必须加引号——YAML 1.1 会把裸 `off` 解析成布尔 `false`。

### 未验证项

- 未做真实的 Agent 多轮会话验证（需要浏览器 WebSocket 会话），只验证了配置播种、
  凭证注入与端点连通性。若首次使用报 `UNSUPPORTED_REASONING_EFFORT`，
  应检查 `thinkingFormat: qwen` 与 `reasoningEfforts` 的组合是否符合 pi-ai 预期。

## 首轮会话即失败：默认模型路由与 reasoningEfforts（2026-10-23 修复）

上面"未验证项"留的坑在第一次真实对话时就炸了，而且是**两处独立缺陷**，
第二处被第一处挡住，只在修完第一处后才暴露。

### 症状

新建会话发送第一条消息即失败：

```
This turn failed
llm-deepseek: no API key for provider route "deepseek-official";
store DEEPSEEK_API_KEY through the credentials service (the web Models page writes it),
or export DEEPSEEK_API_KEY in the launching environment
```

极易误判为"阿里 MaaS 的 key 配错了"。事实上 `DSH_QWEN_API_KEY` 在容器里正常存在，
`aliyun-maas` 路由也已被正确合成（`dsh --profile web --dump-config` 可见）。

### 缺陷一：新建会话默认走 DeepSeek 官方路由

上游 `@deepseek-ai/dsh-base` 把 `agent-default-model` 固定为
`provider: deepseek-official / model: deepseek-flash`。本部署只声明了 `aliyun-maas` 路由，
从未覆盖这个默认值，于是**每个新会话的 `modelSelection` 都落在需要
`DEEPSEEK_API_KEY` 的路由上**——与用户是否选了 qwen 无关（选择器里 DeepSeek 分组
因无密钥已被隐藏，但默认值不会因此改变）。

同时 `agent-default-model` 只在**创建 agent 时**读取，所以会话里再改模型也不会
修复已存在的选择；修复必须落在配置层，且会话级选择也要重选一次。

修复：在 `cordis.patch.yml` 里追加

```yaml
- id: agent-default-model
  config:
    provider: <providerId>
    model: <model>
```

⚠️ patch 是**整段替换 `config`** 而非深合并（见 `dsh-base/README.zh.md`），
`provider` / `model` 必须成对重述，只写一个会丢掉另一个。

### 缺陷二：`reasoningEfforts` 只声明 `off` 会让整条路由不可用

原配置写的是：

```yaml
reasoningEfforts:
  'off':
```

`dsh-llm-pi-ai` 的模型解析要求 `reasoningEfforts` **至少给出一个 `off` 之外的档位**，
否则该模型解析失败（`offers no level beyond "off"`）。更糟的是这个错误在非严格读取
路径下会被记录成单模型诊断而非直接抛出，随后被 `compat` 校验顶掉，最终报出与真实
原因无关的：

```
INVALID_CONFIG: llm-pi-ai: provider "aliyun-maas" sets compat "supportsDeveloperRole",
but no model on the route speaks a protocol that takes it;
it exists on openai-completions, openai-responses, ...
```

（`compat.supportsDeveloperRole` 恰恰是 `openai-completions` 支持的开关——
报错文案在误导方向。）

修复：补一个可选档位，默认仍由 provider 级 `reasoning: 'off'` 关闭思维链。

```yaml
reasoning: 'off'
models:
  - id: qwen3.8-flash
    reasoningEfforts:
      'off':
      'high': 'high'
```

### 验证方式（可复用）

DSH 自带无头回合与配置导出，不必依赖浏览器：

```bash
# 1. 看合成后的 profile 树（不发请求）
DSH_HOME=/tmp/v/.dsh dsh --profile headless --dump-config

# 2. 用真实 key 跑一轮真实对话（在隔离 DSH_HOME 中进行，不干扰线上 web 进程）
DSH_HOME=/tmp/v/.dsh dsh --profile headless "只回复两个字符：ok，不要调用任何工具"
```

本次即用该方法验证了修复后的最终渲染产物：返回 `ok`，无 `reasoning` 输出
（说明 `enable_thinking=false` 生效），全程无报错。

### 遗留

`web` 服务的搜索提供方仍固定为 `deepseek-official`（`web-search-deepseek` 需要
`DEEPSEEK_API_KEY`）。因此 Agent 若调用 `web_search` 会报
`WEB_PROVIDER_CONFIGURED_UNAVAILABLE`；`web_fetch` 不受影响。当前部署没有
DeepSeek 密钥，如需联网搜索须另行提供该凭证。

## 端口与 Origin 校验（2026-10-23 修复）

### 症状

页面能打开、会话列表能渲染，但点击「Choose workspace」时目录选择器报：

```
client api: directoryPicker/list failed: transport failure for /api/directoryPicker/list: HTTP 403
```

左下角持续 `Reconnecting..`。`dsh-proxy` 访问日志里 `/dsh/api/remote.mux` 每 8 秒一条
`403 9`——9 字节的响应体是上游的 `Forbidden`，**不是 nginx 自己拒绝的**。

### 定位过程

用合法 token 换到 cookie 后，直接对上游（绕过 nginx）改 Host/Origin 组合：

| Host | Origin | 结果 |
|---|---|---|
| `acli.sangfor.com.cn` | `https://acli.sangfor.com.cn` | 200（cookie 也是该 authority 签发的） |
| `acli.sangfor.com.cn:4888` | `https://acli.sangfor.com.cn:4888` | 403（cookie 属于无端口 authority） |
| `acli.sangfor.com.cn:4888` | `https://acli.sangfor.com.cn` | 403 |
| 重新在 `:4888` authority 下换 token 后再请求 | 同上 | **200** |

结论：上游用 **Host 头**拼出期望 Origin 并与浏览器 `Origin` 精确比对（scheme + host + port）。
nginx 写的是 `proxy_set_header Host $host;`，`$host` 不含端口，于是：

- 上游期望 `https://acli.sangfor.com.cn`
- 浏览器实际发 `https://acli.sangfor.com.cn:4888`
- 不相等 → 所有带 `Origin` 的请求（WebSocket `remote.mux` 与 POST RPC）全部 403

GET 页面不带 Origin，所以「页面能开、功能全挂」这个组合看起来很像前端 bug。

### 修复

```nginx
proxy_set_header Host $http_host;   # 保留端口，而不是 $host
```

`X-Forwarded-Proto` 实测不影响该判定（http/https 均 200），保持 `$scheme` 不变。

附带影响：DSH 的会话 cookie 按 authority 签发（cookie 名与 `authority` 声明都随端口变化），
因此同一浏览器从 4888 切到 4443 需要各自换一次 token，属预期行为。

### 回归确认

修复后用真实入口（`:4888`）重放：换 token → 带 cookie 调 `POST /dsh/api/directoryPicker/list`
→ 200；把 Origin 改成不带端口 → 403（证明是精确匹配，而非"任意 Origin 放行"）。

### 附带修复：ConfigMap 变更不会自动生效

`nginx.conf` 是**单文件 subPath 挂载**，`dsh-llm-config` 由 initContainer 拷入 emptyDir，
两者都不会被 kubelet 热更新。而 Pod 模板里没有配置内容哈希，于是出现：

> PR 合了 → ArgoCD 显示 Synced → 跑着的 Pod 还是旧配置

本次修复 Host 头时就踩到了：ConfigMap 里已是 `$http_host`，容器内文件仍是 `$host`，
`nginx -s reload` 毫无效果，最终只能手工 `rollout restart`。

现在在 Pod 模板上挂两个内容哈希：

```yaml
annotations:
  checksum/proxy-config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
  checksum/llm-config: {{ include (print $.Template.BasePath "/configmap-llm.yaml") . | sha256sum }}
```

配置一改，哈希就变，Deployment 自动滚动，不再依赖人工重启。
