# 工单日志手动同步放开内容判定

## 背景与需求

见[需求事件文档](../../requirement/events/2026-11-25-工单日志手动同步放开内容判定.md)与[设计文档](../../../plans/2026-11-25-手动同步放开内容判定-design.md)。

自动巡检需要转储跳过保护；手动按钮代表人的显式判断，不应再被同一套内容规则拦截。

## 方案概述 (WHAT)

在执行分支按 `job.origin` 分流：

- `auto`：完整保留 `_filter_non_log_archives` → `_handle_all_non_log` → `non-log-payload` 终态链路；
- `manual`：跳过整个内容判定，包括远端列目录探测，所有待合并归档照常下载、解压、合并；成功消息不再追加转储提示。

`has_logs` 仍照实计算并写入 `.sync-meta.json` / `artifacts.hasLogs`，容量淘汰口径不变。

## 详细设计

### 分流点

`tools/ticket-sync/app/main.py` 的 `_run()` 中，在 `plan_pending()` 之后：

```text
if job.origin == ORIGIN_MANUAL:
    ignored = []
    INFO: 手动同步跳过内容判定 待合并归档=N
else:
    pending, ignored = await _filter_non_log_archives(job, pending)
    if not pending:
        _handle_all_non_log(...)   # 原逻辑，自动专用
        return
```

### 完成段

`if not has_logs:` 的提示拼接加 `and job.origin == ORIGIN_AUTO` 条件；手动任务保留同步统计消息。

### 可观测性

手动分流处一条 `INFO`，携带 `request_id/ticket/job/origin/待合并归档数`；自动路径日志与指标不变。

## 决策依据 (WHY)

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：给 `sp_` 目录开白名单 | 单一事实源 | 程序仍在替人判断，其他转储包继续被拦 | 否 |
| B：调用点过滤 | 改动最小 | 判定语义分裂 | 否 |
| C：抽共享谓词 | 消除漂移 | 仍保留程序判断，收益边际 | 否 |
| D：手动整体绕过判定 | 判断权完全交还用户；自动零回归 | 手动同步纯转储会占盘 | **采用** |

第一性原理：判断"该不该同步"只有程序规则与人的显式意图两种来源；手动点击已是后者，正确做法是让规则在该路径不生效，而不是继续细化规则。对抗性审查：若同时放开磁盘水位，重演 2026-11-12 写满盘全栈中断，因此安全闸门必须保留。

## 影响范围

- `tools/ticket-sync/app/main.py`：分流、提示、日志。
- `tools/ticket-sync/tests/`：auto/manual 双路径测试与回归。
- `tools/ticket-sync/README.md`：判定表按 origin 分列。
- 无 API / DB schema / 前端变更，无需迁移。

## 测试策略

1. 单测锁定双路径行为：auto 仍探测并终态；manual 不探测、不终态、可 `ready`。
2. 现有 ticket-sync 全量测试回归。
3. 部署后真实验收：`Q2026112500553` 手动同步，检查 `phase=ready`、解压产物、`error_code=null`，并确认自动扫描不再入队。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 手动同步大转储占磁盘 | 保留水位闸门；`hasLogs=false` 如实落盘，容量淘汰优先 |
| 存量终态被误以为自动恢复 | 文档明确逐点手动同步，不批量清终态 |
| 自动路径被改动带偏 | 分流只加 `if` 分支，自动分支代码原样保留并用测试锁定 |
