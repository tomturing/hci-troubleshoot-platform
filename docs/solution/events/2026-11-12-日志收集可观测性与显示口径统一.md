# 日志收集可观测性与显示口径统一方案

## 背景与需求

详见 [需求文档](../../requirement/events/2026-11-12-日志收集可观测性与显示口径统一.md)。

一句话：把「完成」从单枚举拆成 **执行阶段 / 业务结论 / 条件** 三维，结论只由产物与交付证据推导；同时补齐网络探测、逐跳速率/ETA、zip 内容证据、进程日志回传，并让三处界面共用一份契约常量。

## 方案概述

### 为什么是「A 与 C 融合」（方案 D）

- 写侧采用 C 的单一权威：前端不再直接写 `status/progress`，只提交 `node_observed` 事实；平台按证据推导。
- 读侧采用 A 的派生模型：展示由只读投影（API 派生字段，单一判定函数）产生，界面不做语义判断。
- 状态模型采用业界通行的多维表达（Kubernetes `phase` + `conditions`、GitHub Actions `status` vs `conclusion`）：单枚举装不下「交付成功但产物异常」「采集中但已停滞」，必然二次拼接，口径必然漂移。

### 三维状态定义

| 维度 | 语义 | 取值 | 写入者 |
|---|---|---|---|
| `phase` | 当前所处环节（互斥） | `queued` / `collecting` / `fetching` / `uploading` / `relaying` / `settled` | 平台派生 |
| `conclusion` | 业务结论（互斥，`pending` 表示未终结） | `pending` / `success` / `partial` / `failed` / `cancelled` | 平台派生，仅由证据 |
| `conditions[]` | 并存的观察事实（多值） | `artifact_verified` / `artifact_suspect` / `artifact_missing` / `artifact_uninspected` / `integrity_mismatch` / `handoff_pending` / `delivered_unverified` / `network_degraded` / `stalled` / `bridge_outdated` | 各探测点追加 |

**推导规则（唯一收口点：`backend/case-service/app/domain/log_collect_display.py`）**

```
conclusion:
  status == cancelled or delivery_status == cancelled               -> cancelled
  status == failed or delivery_status == failed                     -> failed
  phase != settled                                                  -> pending
  delivered and delivery_evidence_ok and quality == ok              -> success
  delivered                                                         -> partial   # 字节到了但产物不可用/未核验
  otherwise (已结束但从未交付)                                       -> failed    # 附 handoff_pending
phase:
  delivery_status in (pulling/uploading/relaying) 优先映射为 fetching/uploading/relaying
  status in (pending/probing/installing)                           -> queued
  status in (collecting/packaging/uploading)                       -> collecting
  status in (completed/failed/cancelled)                           -> settled
  其余                                                             -> queued
```

- `delivery_evidence_ok`：P2 要求 `relay_status == success`；P1 要求 `relay_status == success` 或 `detail.p1_archive_check.verified == true`。只有 acli 自报不算。
- 统计恒等式天然成立：`total = count(conclusion='pending') + count(conclusion in 终态)`；`conditions` 不参与分母。

**判定修订（对抗性审查后收敛，与原草案不同之处）**

1. **去掉「`artifact_quality == invalid` 一律 failed」**。该规则会让「已交付 608 字节空壳包」显示成失败，与「交付事实独立可见」冲突；改为：**已交付 + 产物不可用 → `partial`（有疑点，建议重采）**，未交付 + 无产物 → `failed`。
2. **去掉「otherwise → pending」**。已结束但从未交付的任务若显示 `pending`，界面会再次出现「已完成 100% + 交付未开始」的自相矛盾；而交付可以补，结论必须诚实，故定为 `failed` 并附 `handoff_pending`，补交付成功后自动翻转为 `success`。
3. **`artifact_quality` 与 `conditions` 解耦**。质量与交付是两件正交的事：608 字节包即便是「已交付 + 代传成功」，产物条件仍是 `artifact_missing`（未取到有效日志），结论是 `partial`。`artifact_quality` 只描述包本身，不描述交付。
4. **体积推断只在终态启用**。采集中「还没有包」不是缺陷证据；否则采集途中就会报「未取到有效日志」。非终态且无探测清单时质量为 `unknown`。
5. **合成进度分段计入**（采集 0-60 / 交付 60-90 / 终结 100）。没有传输样本时 `progress_percent = null`，界面显示 `—`——历史假进度正是「拿 status 当进度」造成的。**终结 100 只给已交付任务**：零产物/从未交付的终态取 `null`，否则管理端仍会出现「合成进度 100% + 交付事实 未开始」的同屏矛盾（真浏览器复核发现，见任务文档「实施与验证」）。

### 数据模型（迁移 065 起）

DDL 写 `database/desired_schema.sql`，DML/订正写 `database/data-migrations/065_*.sql`。

1. `log_collect_artifact_manifest`：`task_id / case_id / trace_id / source(node_zip|platform_object) / archive_path / archive_size / archive_sha256 / entry_count / entry_total_bytes / entries jsonb / has_encrypted / quality(ok|suspect|invalid|unknown) / reason / evidence jsonb / inspected_at`，唯一键 `(task_id, source, archive_sha256)`。
2. `log_collect_network_probe`：`probe_id / case_id / task_id / trace_id / upload_mode / target(log_server|platform_data) / reachable / samples jsonb / loss_rate / rtt_min_ms / rtt_avg_ms / rtt_max_ms / jitter_ms / dns_ms / connect_ms / http_code / up_bps / down_bps / grade(good|fair|poor|unknown) / advice / bridge_version / created_at`。
3. `log_collect_transfer_metric`：`task_id / trace_id / seq / stage / bytes_done / bytes_total / percent / elapsed_ms / rate_bps / eta_sec / stalled / source(bridge|platform) / created_at`，唯一键 `(task_id, seq)`，索引 `(task_id, created_at DESC)`；终态后按保留策略降采样。
4. `log_collect_process_log`：`task_id / case_id / trace_id / host / path / size / sha256 / content_gz bytea / truncated / status(ok|empty|error) / error / collected_at / created_at`，唯一键 `(task_id, host, path, sha256)`。

**不新增任务表状态列**：`phase/conclusion/conditions` 由 Python 派生层 `app/domain/log_collect_display.py` 计算（读 `status / delivery_status / relay_status / detail->>'artifact_quality' / detail->>'p1_archive_check'`）。**不建同规则 SQL 视图**：视图与派生层会是同一套判定规则的两份实现，一旦改规则必然只改一处而漂移；管理端汇总改为复用同一函数在应用层分桶，代价是每次多取一批瘦行（单工单任务量级为百级，可接受）。

`detail.artifact_quality` 由服务端在保存边界写入（终态按体积可判定时补快照），并列入公共 PATCH 保留键——客户端写不进证据字段。

### 接口

**数据面（bridge → case-service，不经网关，沿用现有 upload token 鉴权）**

- `POST /api/direct/log-collect/tasks/{task_id}/metrics`：一条传输样本（幂等键 `seq`；同时把最新样本写进 `detail.transfer` 快照，客户面板轮询零 N+1）。
- `POST /api/direct/log-collect/tasks/{task_id}/network-probe`：一次探测结果；`grade` 由平台按丢包/RTT/抖动推导，响应返回绑定 `probe_id` 的 10 分钟测速票据；同时把每目标最新一条写进 `detail.network_probes` 快照。
- `POST /api/direct/log-collect/tasks/{task_id}/process-logs`：一条进程日志（gzip + base64，白名单绝对路径，单文件 2 MiB / 单任务 20 MiB）。
- `POST /api/direct/log-collect/tasks/{task_id}/artifact-manifest`：包中央目录事实；`quality/reason` 由平台推导并回写 `detail.artifact_quality`，客户端声称的 quality/conclusion 一律忽略。
- `POST /api/direct/log-collect/network-probe/{probe_id}/uplink`、`GET .../downlink?bytes=N`：受控测速端点（单次 ≤4 MiB、body 即丢、固定字节流、需测速票据）。
- 所有数据面端点用 `X-Evidence-Ticket`（绑定 `task_id`、24h，只在 create 响应签发）；测速端点用 `X-Probe-Ticket`。不复用上传令牌：探测发生在上传会话存在之前，复用会全部 401。

**管理面（admin）**

- `GET /api/v1/log-collect/admin/tasks`：`_SELECT` 增加 `object_size / archive_path / archive_sha256 / acli_version / arch` 与只含六个证据键的 `detail` 子集（不拖整包 JSONB），返回派生 `display/artifact/transfer/network`（速率与探测各一次批量查询，不按行 N+1）；汇总改为取瘦行后复用派生层分桶，恒等式由响应模型校验器强制。
- `GET /api/v1/log-collect/admin/tasks/{task_id}`：单任务详情（列表字段 + 最新传输样本 + 网络探测结论）。
- `GET /api/v1/log-collect/admin/tasks/{task_id}/transfer-metrics`：读本地窄表（不查 5888），最新在前、显式 limit。
- `GET /api/v1/log-collect/admin/tasks/{task_id}/network-probe`、`GET .../process-logs`、`GET .../process-logs/{id}/content`（只读文本，路径段 UUID 白名单 + 绝对路径复核 + 2 MiB 回显上限）。
- `GET /api/v1/log-collect/admin/tasks/{task_id}/artifact-manifest`。
- 网关侧只做 admin JWT 验签、内部令牌重签与 URL 转发，不参与任何口径计算。

**客户面（custom-ui，经网关通配代理）**

- 任务响应增加 `display: {phase, conclusion, conditions[]}`、`artifact: {quality, reason, entry_count, entry_total_bytes}`、`transfer: {stage, bytes_done, bytes_total, percent, elapsed_ms, rate_bps, eta_sec, stalled}`、`network: {grade, targets[]}`。
- `PATCH /api/log-collect/tasks/{id}` 新增 `node_observed` 入参（白名单事实字段）；`status/progress` 为兼容保留，服务端按证据推导结论并写 `detail.write_audit`（`legacy` / `node_observed_keys` / `ignored`）审计。

### 探测（a）

- bridge 在 `probe` 与 `create` 前执行 `network_probe`，**分目标**：`log_server(5888)`、`platform_data(4443)`。
- 稳定性：N=5 次采样 → 成功率、RTT min/avg/max、抖动；带宽：受控小样本上行 + 下行（默认 1 MiB，可配）。
- 分级：`good`（成功率 100%、RTT<100ms、上行 ≥ 目标速率）/`fair`/`poor`；`unknown` 表示目标不可达或采样失败。
- **告警只按与当前 `upload_mode` 相关的目标**：P1 看 5888，P2 看 4443（5888 仅参考），避免 0624/1130 那种「5888 不可达但 P2 正常」被误报。
- 网络不佳 → custom-ui 橙色横幅 + 预计上传耗时 + 建议（切模式/换网络/缩时间范围），不阻断。

### 速率与 ETA（b）

- 桥侧维护阶段机，每 2s 通过现有 WS `delivery_result` 推送 `stage/bytes_done/bytes_total/percent/elapsed_ms/rate_bps/eta_sec/ts`；同时 2s 节流 POST `metrics` 落库（`seq` 单调，幂等）。
- 速率用 EMA（`0.7*prev + 0.3*instant`）；`rate_bps<=0` 时 `eta_sec=null`；60s 无增量置 `stalled=true`，界面显示「已停滞 N 秒」，ETA 冻结。
- **采集阶段（acli）与 P1 直传不计算速率/ETA**，界面显示「不适用」。
- 终态保留策略：每阶段首/末样本 + 最近 100 条，其余删除（由服务端在终态写入时执行）。

### zip 内容探测（c）

- P2：bridge 拉取完成后用 Go `archive/zip` 解析本地副本（精确、无命令依赖）。
- P1：节点侧 `unzip -Z` / `zipinfo` 摘要解析；不可用时降级为 `stat` + EOCD + 体积阈值。
- **禁止 `unzip -t`**：客户包全条目加密，密码错误会被误判损坏；只读中央目录。
- 判定：`invalid`（无包/过小/0 条目/只有元数据白名单/EOCD 缺失）、`suspect`（条目数或总字节低于期望）、`ok`。
- 结果写 `log_collect_artifact_manifest` + 快照 `detail.artifact_quality`；`conclusion` 随之变化，界面给红/橙提示与重采建议。
- P1 成功后包自删：仅在包存在时探测，不存在时结合上传/归档证据判定，不得直接判失败。

### 进程日志（d）

- bridge 任务运行期启动 tailer（独立 exec，避免被交互 shell 的 TMOUT 连坐），10s 轮询 `ls` 差异，增量读取 → 本地磁盘 spool（崩溃安全）→ 异步上报；终态再补一轮全量枚举。
- 上限：单文件 2 MiB、单任务 20 MiB；超限截断并 `truncated=true`；目录为空落一条 `status=empty`。
- 只读白名单路径 `/sf/log/today/acli/plugins/log_collect/`；不执行删除/写入；复用现有脱敏规则。
- 默认假设：各主机日志已由 acli 汇总到发起节点；扫描器做成可插拔接口，后续可扩展逐主机扇出。

### 兼容与降级（必须）

- 旧版 bridge 不上报新字段：`display.transfer=null`、`network=null`、`artifact.quality=unknown`，界面显示「桥接端版本较旧，暂无该数据」，**不得显示 0、空白或绿色成功**。
- 新 bridge + 旧平台：旧平台忽略未知字段（JSON 宽松），行为不变。
- 旧前端 + 新平台：新增响应字段为附加字段，旧字段语义保持，行为不变。

### 存量订正（迁移 065）

- 订正对象：`status=completed` 且 `artifact_quality` 可判定为 `invalid`（无包/过小/仅元数据）的历史任务，补写 `detail.artifact_quality` 与 `detail.display_audit`（含 before/after、依据、时间），可重跑。
- 不修改 `status` 历史值（避免破坏状态机语义），仅补证据字段，由派生层改变展示。
- 迁移内置不变量：`status='completed'` 且无包/过小的任务必须被标注为 `artifact_quality='invalid'`、被标为过小的体积确实小于阈值；展示结论由派生层按是否交付分别得 `failed` / `partial`，迁移本身不改 `status`。应用侧另有 `total = Σ五桶` 的模型校验器断言。
- 交付时给出可对账前后数字（面板各桶、异常任务数）。
