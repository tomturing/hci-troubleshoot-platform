# 日志收集包归属判定改为节点内相对时间

## 背景与需求

见[需求事件文档](../../requirement/events/2026-11-24-日志收集包归属时钟鲁棒性.md)。
现场 `Q2026112400585` 的包是本轮新产物，但 bridge 用节点 mtime 与自身墙钟比较，
节点慢约 6 分钟越过 5 分钟容差，两次交付均在拉取前被判 `LC-TRANSFER-011`。

## 方案概述 (WHAT)

把“包是否属于本轮采集”的判据从**跨时钟绝对时间比较**改为**节点内相对时间 + 测得偏移校正**：

1. 一条 SSH 命令同时取节点当前时间 `date +%s` 与包 `stat -c %Y`；
2. `age = node_now - mtime`，节点时钟静态偏移在相减中抵消；
3. 用同一次读数测得的偏移把 mtime 校正到 bridge 时钟，与交付作业创建时间比较；
4. **只有两个独立证据同时成立才判旧包**：`age > 30 分钟` 且校正后的 mtime 早于作业创建时间 5 分钟以上；
5. `mtime` 晚于 `node_now`（时钟回拨/未来时间）按新鲜放行；
6. 旧包错误改为 `deliveryFatalError`，带 `LC-TRANSFER-011` 结构化错误码，主流程统一把码写入 `job.LastErrorCode`；
7. 契约文案改为只陈述可证事实，并保留旧关键词用于历史归因。

## 详细设计

### 判定流程

```text
waitCollect 看到 done >= total
  └─ inspectArchiveAge(session, path)
       ├─ 命令: printf '%s %s\n' "$(date +%s)" "$(stat -c %Y <path>)"
       ├─ 解析失败 / stat 失败 → 跳过判定（沿用原有“宁可少判一次不误杀”）
       ├─ mtime > node_now + 2min → 视为新鲜，WARN 证据记录时钟回拨
       ├─ age <= deliveryArchiveStaleAfter(30min) → 放行
       └─ age > 阈值 → newFatal(LC-TRANSFER-011, 文案带 age/阈值/节点时间)
  └─ waitArchiveSettled → 取摘要 → 拉取
```

### 关键常量

| 常量 | 值 | 说明 |
|------|----|------|
| `deliveryArchiveStaleAfter` | 30 分钟 | 包在节点上的“年龄”上限；只用于 collect 模式，补交付 direct 模式不经过该判定 |
| `deliveryArchiveFutureTolerance` | 2 分钟 | mtime 晚于节点当前时间的容许量，超出视为时钟回拨并放行 |

删除 `deliveryClockSkewTolerance`（5 分钟跨时钟容差）与 `startedAt()`，
不再把 bridge 的 `CreatedAt` 当作“本次采集开始”。

### 错误码与文案

- bridge：`newFatal(logcontract.ErrTransferSourceStale, ...)`；主流程 `job.LastErrorCode = deliveryErrorCode(err)`。
- 契约 `fault_catalog.LC-TRANSFER-011`：
  - `problem` 改为“节点本地时间显示该压缩包生成于较早时刻，超过交付时效”；
  - `action` 改为“先确认节点时间是否准确；如要交付已采集完成的包，请使用「上传到平台」补交付；需要本轮最新内容请重新采集”；
  - `admin_detail` 记录新的证据事件与字段；
  - `match_keywords` / `fault_matchers` 新增“按节点本地时间”“超过允许的交付时效”；
  - `attribution_rules` 保留旧三条不变（新文案仍含“节点上的压缩包”，历史与新增数据都命中 011，避免改迁移）。
- 生成物通过 `python3 scripts/gen_log_collect_display.py` 重生成，禁止手改。

### 可观测性

新增证据事件 `delivery.archive_age_probe`，字段：

| 字段 | 含义 |
|------|------|
| `node_now` / `mtime` | 同一次节点命令取得的时间（RFC3339） |
| `mtime_on_bridge` | 按测得偏移校正到 bridge 时钟的 mtime |
| `job_started_at` | 交付作业创建时间 |
| `age_sec` | 节点内相对年龄 |
| `threshold_sec` | 当前陈旧阈值 |
| `clock_offset_sec` | bridge 当前时间减节点当前时间，用于校正与诊断 |
| `verdict` | `fresh` / `stale` / `clock_rollback` |

## 决策依据 (WHY)

### 方案选择

| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| A 节点内相对时间（选中） | 跨时钟偏移自动抵消；保留真旧包拦截；改动集中在 delivery + 契约 | 节点在打包后大幅向前跳仍可能误判（用回拨放行 + 证据兜底） | ★★★★☆ |
| B 纯状态转移 | 可用性最高；不碰时间 | 无法证明包身份，极端情况下会放过上一轮残留的 `done` | ★★★☆☆ |
| C 基线差分 | 最准确 | 需要 create 时记录基线并跨 logcollect/delivery 传字段，改动面大 | ★★★☆☆ |

### 为什么选 A

归属判定真正需要的证据是“包是否在本轮交付作业开始之后产出”，而不是“包的绝对时间早不早”。
节点 mtime 与节点当前时间来自同一时钟，做差先消除静态时钟偏差；
再把 mtime 用同一次读数测得的偏移校正到 bridge 时钟，就能与作业创建时间比较，
既不受用户侧时钟异常影响，也不会把“排队较久但确实是本轮产出”的包误杀。
旧包拦截能力也保留，不需要依赖 acli 是否提供 task_id。

### 为什么不选 B / C

- B 把正确性寄托在 `progress` 一定重置；现场已出现过 progress 全局态残留的历史（2026-10-27 `48f890d5`）。
- C 需要把基线写进任务 detail 并保证 create 与 delivery 两侧都能取到，跨模块状态同步成本高于收益。

### 权衡与妥协

- 30 分钟只是“最小陈旧年龄”，真正与作业时间挂钩的是校正后的 mtime；排队再久也不会因为 `now - mtime` 变大而误杀。
- 若节点时间在打包后大幅向前跳，两个条件可能同时成立；用 `clock_offset_sec` 留痕便于现场定位，补交付 `Direct` 模式不受影响。
- 两个条件取“与”而不取“或”：只要有一侧证明包是新的就放行，优先保证功能可用。

3. 改契约文案与关键词，重生成七份产物。

## 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 节点无 `date`/`stat` | 无法判定 | 低 | 探测失败跳过判定，沿用原行为并留 WARN |
| 打包后时钟向前跳 | 新包被误判 | 低 | 记录 `clock_offset_sec`；现场可校准时间后重试；补交付 direct 不受影响 |
| 旧文案存量无法归因 | 历史任务显示未知码 | 中 | 保留旧三条关键词，新增关键词只做增量 |

## 测试策略

- 纯函数：表驱动覆盖慢/快数小时、排队 40 分钟、mtime 未来、边界 30 分钟。
- bridge 集成：假 `NodeSession` 注入 `date`/`stat` 输出，验证放行/拒绝/探测失败。
- 归因：Python 单测验证新旧文案都命中 `LC-TRANSFER-011`。
- 前端：生成物提示包含“节点本地时间”，不再包含“早于本次采集开始”。

## 验收标准

- [ ] 节点慢 6 分钟场景放行，包进入拉取。
- [ ] 节点慢 6 小时、快 6 小时场景放行。

- [ ] 包年龄超过阈值场景返回 `LC-TRANSFER-011`，且 `LastErrorCode` 结构化上报。
- [ ] 契约生成物无漂移，历史关键词仍命中。
