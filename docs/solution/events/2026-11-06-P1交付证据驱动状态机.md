## 二、根因

不是「核验做得太早」，而是**系统用 `node_state` 一个布尔同时回答了两个问题**：
「采集是否结束」与「交付是否有结论」。acli 的完成报告可以早于打包/上传，
且不含上传结论（本案 `upload_state` 为空）。于是平台在完成瞬间：

1. 把空的 `upload_state` 当成「发送成功」写 `delivered`（假成功，`finishP1`）；
2. 又把一次瞬时的 `archive_missing` 当成终局写 `failed`（假失败，`syncNodeState`）；
3. 判终态后停止轮询，上传段后续发生的一切结构性不可观测。

「只把核验延后 N 秒」是时间补丁：它假设「等一会儿证据就出现」，
但 P1 成功后插件会自删包，`archive_exists` 永远等不到；且没有任何证据能定出 N。
正确解法是让**证据**决定是否写交付结论，并让等待有界、可重入。

## 三、本次改动

1. `logCollectSync.ts` 新增 `DELIVERY_EVIDENCE_WAIT_MS = 10 * 60 * 1000`（固定常量，
   先用指标观察真实打包耗时，再考虑调整，避免一上来引入自适应复杂度）。
2. `SyncInput` 增 `archiveVerified`（`delivered | failed | none`）与 `deliveryWaitElapsedMs`；
   新增 `wait_delivery` / `delivery_unknown` 两个动作及对应提示文案。
3. 证据优先级：落盘侧核验通过 > 节点明确报「发送成功」且核验不可用（旧后端兼容） >
   包仍在盘（仅代表可补交付，不是已交付）。
4. 核验返回 `failed` **不写库**：那只是「此刻服务器上没有」，大包可能还在上传途中；
   改为进入有界等待。窗口耗尽收敛为「结果未知」，不写 `failed`，保留人工入口。
5. `finishP1` 只在拿到正向证据时写 `delivery_status: 'delivered'`；
   证据不足时照常写 `status=completed`（采集结论），交付结论留空并进入等待。
6. 幂等：等待起点除内存单调时钟外，回退到任务 `updated_at`，
   关页面重开 / 换端接管不会被重置成永久等待。
7. 可观测性：每次状态转移输出唯一调用链
   `trace_id=lc-<caseId>-<taskId>`，带 `action / evidence / node_delivered /
   archive_exists / wait_ms / wait_limit_ms`，便于串起前端、bridge 与 5888 日志。

### 护栏（对抗性审查的重点）

历史修复 #1277 / #1284（工单 Q2026101401683）曾因「要求完成态自证」把真实完成
永久卡在 `collecting`。本次**只约束交付结论，绝不拦 `patch_completed`**：
`ACTIVE_STATUSES + nodeState=completed` 仍直接映射采集完成，并有单测守住这条回归线。
