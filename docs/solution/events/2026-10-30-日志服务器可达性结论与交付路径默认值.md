# 日志收集：日志服务器可达性只决定「建议路径」取值与交付路径默认值

- 日期：2026-10-30
- 现场工单：Q2026102801062（面板提示「日志服务器探测失败（HTTP 0）」，正文 `curl 探测失败：000 5.001368`）
- 涉及：`frontend/customer`（`LogCollectPanel.vue`）、`terminal_bridge`（`log_collect.go`）
- 前序事件：`2026-10-30-日志收集探测重试与事实复查.md`（同一段探测链路的成功标准与复查节奏）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 面板以 warning 弹出「日志服务器探测失败（HTTP 0）」 | 旧实现 `probeIssues` 对所有不可达统一 `type="warning"` |
| 正文是 `curl 探测失败：000 5.001368` | bridge 在 curl 非零退出时把 `-w` 原文塞进 `note`，前端直接展示 `note` |
| 同一屏「建议路径」已给出「P2 经平台中转（建议）」 | `deliveryModeFact` 在不可达时给的是 P2 建议，与上方「失败」文案自相矛盾 |
| 该 HCI 位于客户内网，出不了公网 | 内网隔离是 P2 路径存在的理由，不是异常 |
| 判据来自**一次** 5 秒的 curl | `5.001368` 正是 `--connect-timeout 5` 耗尽，即一次采样就否决了一条交付路径 |

## 二、根因

1. **把能力分支判定播报成系统故障**：这次探测只回答「HCI 能不能自己连上 5888」。
   连不上意味着该走 P2，与平台是否出问题无关；写成「探测失败」只会把人引去查平台。
2. **同一件事说了三遍，语气还互相矛盾**：探测结论一次就能说清「走 P1 还是 P2」，
   旧界面却同时用「建议路径」的取值、一条 warning 告警、交付路径下方的提示各说一次。
3. **契约错位**：bridge 回传的字段名是 `log_server_http_code`，前端声明并读取的却是
   `http_code`，真值永远落空。随任务落库的探测快照长期缺 `http_code`，
   事后无法判断「日志服务器当时是没回话，还是回了 5xx」。
4. **用一次采样给硬结论**：不可达之后 P1 直接置灰，属于硬约束；而单次超时既可能是
   「这里不通」，也可能只是「这几秒没通」。用一个 5 秒采样去否掉一条交付路径，
   代价要么是让用户白等一次注定失败的直传，要么是白绕一跳中转。
5. **把选择成本转嫁给用户**：P1/P2 不是偏好问题，答案只取决于平台已经知道的网络事实。

## 三、本次改动

### 3.1 「建议路径」的取值定死两个字符串

- 只允许 `P1 直传日志服务器` / `P2 经平台中转` 两种取值，不加「（建议）」「待探测」等修饰。
  探测结论已经由「取值是哪一个」说清，多一个字用户就要多判断一次。
- 有任务时取值来自 `upload_mode`（创建那一刻落库的决策），无任务时来自探测快照；
  两种来源共用同一套取值，界面不出现第二套措辞。
- 删掉日志服务器相关的一切告警：截图里那条提示不再存在，HTTP 码与 curl 原文只留在
  「探测历史」与落库的 `note` 里供排障。
- 仍保留的探测告警只剩一条：**节点清单获取失败**。它改变的是用户下一步要不要手填 IP，
  属于必须让用户知道且要动手的事。
- 「探测历史」折叠框样式与行为原封不动（默认折叠，需要时展开）。

### 3.2 交付路径：平台给答案，不给选择题

| 探测结论 | 建议路径 | 默认选择 | P1 可选性 | 用户动作 |
| --- | --- | --- | --- | --- |
| 可达（HTTP 200–499） | P1 直传日志服务器 | P1 | 可选 | 可主动改选 P2（要平台副本时） |
| 不可达（HTTP 0 / 5xx） | P2 经平台中转 | P2 | **置灰不可选** | 无需动作 |

- 实现为 `p1Disabled` + `applyDefaultPathMode()`：探测成功后立即落默认值；
  不可达是硬约束，即使用户之前选过 P1 也收回为 P2。
- 用户**已明确选过**的路径在下一次探测不会被默认值改回（`pathModeTouched`）。
- 从「判不可达」恢复为「可达」时，未被手改的默认值回到 P1——否则会永久停在
  比实际能力差一跳的 P2 上。

### 3.3 不可达必须有多次一致观测（bridge 有界重试）

- 只有**传输层失败**（curl 无非零退出、一个响应字节都没收到：超时 / 拒绝 / 解析失败 / PTY 异常）
  才重试；`confirmLogServerReachability` 封顶 3 次，间隔 1s、2s，任一次收到响应即判可达。
- 收到 HTTP 应答（含 5xx）不重试：网络已通，是服务端在表态，重试只拖长面板不改变结论。
- 两种结局都写进 `note`：中途恢复记「第 1 次无响应（原文），第 N 次收到响应」，
  全部失败记「连续 N 次 + 最后一次原文」。否则「网络抖过」与「确实不通」在历史里长得一样。
- 重试发生在**发布快照之前**：界面不会出现 P1 亮了又灰、灰了又亮的跳动，
  探测历史也不会因为一次打开面板多出三条记录。

### 3.4 契约归一（`normalizeProbe`）

- 入口处把 `log_server_http_code` 与 `http_code` 收敛成一个值写回 `http_code`，
  下游（落库快照）只读这一个字段；`log_server_url` / `log_server_latency_ms` 一并声明，
  让快照能自证「探的哪个地址、耗时多少」。

## 四、对抗性审查

- **与 2026-10-28 的旧结论相反，这里是有意推翻**：当时定的是「不可达时不静默选 P2，
  因为一次 10 秒的超时探测不足以替用户决定交付路径」。该结论保护的是
  「别把 P1 说成 P2 导致事后无法追溯」，代价却是把必然失败的选项留给用户。
  现在「默认值 + 禁选 + `upload_mode` 落库」三者同时具备：用户不用判断，
  事后仍能从任务记录看清实际走的哪条路。追溯性由落库保证，不再靠「让用户自己选」。
- **重试会把常见现场拖慢吗**：内网 HCI 出不了公网时三次都会耗到超时，最坏多花约 12 秒。
  这是刻意接受的代价——它是唯一能区分「没通」与「没通这一下」的手段；
  重试只在传输层失败时发生，收到应答（含 5xx）一次就收尾。
- **旧 bridge 兼容**：若只升级前端，仍按单次采样判不可达，退化为改动前行为，不会报错；
  若只升级 bridge，前端读不到 `log_server_http_code` 时 `normalizeProbe` 落 0，同样安全。
- **可达但 5888 抖动**：探测只是快照，用户仍可手动改选 P2，`upload_mode` 落库兜住误判。
- **采集中**：单选组整体 `disabled`，路径是任务既成事实，默认值逻辑不会改写进行中的任务。

## 五、验收

1. 不可达 → 面板无「日志服务器」告警；「建议路径」为 `P2 经平台中转`；
   交付路径默认选中 P2，P1 置灰且点击无效（前端单测）。
2. 可达 → 「建议路径」为 `P1 直传日志服务器`；默认选中 P1；改选 P2 后再探测不被改回（前端单测）。
3. 不可达且 `log_server_http_code=502` → 与 1 表现一致，界面不出现 HTTP 码（前端单测）。
4. 先不可达、重探可达 → 未被手改的默认值回到 P1（前端单测）。
5. 传输层失败两次后第 3 次收到 200 → 判可达，`note` 记「第 3 次收到响应」（bridge 单测）。
6. 连续 3 次传输层失败 → `log_server_http_code=0`、不可达，`note` 记「连续 3 次」（bridge 单测）。
7. HTTP 502 → 只采样 1 次即收尾，`note` 为空（bridge 单测）。
