# 交付等待阶段冻结与节点命令硬超时

## 现场现象

工单 `Q2026112400942`（任务 `78f301ee-29f9-4914-abb4-9bc6b00a2b3b`，节点 `10.10.0.150`，P2 中继 `bridge_relay`）：

- 采集侧成功：06:44:46Z `done=1/total=1`、`node_state=completed`，包 `39,662,580 B`、5 个条目、清单完整；
- 交付侧从 06:44:46Z 起 **149 分钟零字节**：`log_collect_transfer_metric` 共 4477 条采样全部 `stage=fetching`、`bytes_done=0`、`percent=0`；
- 平台 `delivery_status=queued`、multipart 目录下只有 `meta.json`、0 个分片；
- 期间节点 SSH 会话在 07:03:58Z / 07:40:55Z / 08:12:10Z 三次以 `remote_eof` 断开，输出均为 `timed out waiting for input: auto-logout`（节点 TMOUT 空闲 30 分钟自动登出，age 1836s / 1800s / 1800s）；08:12 之后 `sessions=0`，再无 `session.created`，也没有 `delivery-auto` 重连；
- 桥接侧 06:44:46Z 之后**没有任何交付阶段事件**（无 `delivery.collect_finished`、无 `delivery.stalled`）。

已排除：弱网（探测上行 2.61 MB/s、丢包 0）、磁盘满（可用 21382 MB）、包损坏（清单完整）、平台存储（0 分片但无写入错误）。

## 根因（三层叠加）

1. **命令没有自己的时间上限。** `RunQuickCommandStreams` 只 `select ctx.Done()`，而交付域传入的是整个作业的 ctx（`deliveryJobMaxTimeout = 48h`）。SSH 通道一旦半开（节点 TMOUT 静默登出、NAT 老化），`session.Run` 永不返回，上层 `waitArchiveSettled` / `waitCollect` 循环里的 deadline 检查永远到不了。
2. **等待阶段的停摆看门狗是关闭的。** `progressSignature` 对 `waiting_collect` 返回 `watched=false`，30 分钟无进展判据设计上不覆盖该阶段（这是对的：多节点串行采集可以长时间没有新字节）。但配合①就变成"作业永久冻结且永远不会被判死"。
3. **指标把"没开工"渲染成"传不动"。** 证据指标只有 `fetching` / `uploading` 两种 stage，等待采集阶段也被报成 `fetching` 且 `stalled=true`，面板显示"上传中 0/5 片 · 传输已停滞"，把排查方向引向带宽与磁盘。

## 修复

| # | 改动 | 位置 |
|---|---|---|
| 1 | 远端命令自带兜底上限 20 分钟，只收紧不放宽；`HCI_BRIDGE_COMMAND_CEILING_SEC` 可现场覆盖，非法值退回默认（失败关闭） | `internal/sshx/session.go` |
| 2 | 交付探测类命令显式 15 秒预算：`statArchiveSize`、`inspectArchiveAge`、`verifyArchiveComplete` | `internal/delivery/delivery_transfer.go` |
| 3 | 等待采集期间节点命令**连续失败 3 次**判定会话不可用，交回重排重建连接，并 emit `delivery.node_unreachable`（判据取"命令能否执行"，不取字节增量，避免误杀正常等待） | `internal/delivery/delivery_command_guard.go` + `waitCollect` |
| 4 | 校验尾部超时与"节点缺 tail/od/tr/grep"严格区分：前者返回 `errNodeCommandUnreachable` 直接上交重排，绝不降级放行（否则半截包会被当完整包上传） | `verifyArchiveComplete` |
| 5 | 证据指标新增 `waiting` 阶段（等待采集/等重排），契约 `transfer_stage` 同步，面板显示"等待采集"而不是"拉取/上传中 0 片" | `contracts/log_collect_display.json` + 生成物 |

## 对抗性审查

- **加大兜底上限会不会误杀慢任务？** 20 分钟只用于把"永久挂起"变成"可重试失败"；节点内 `cp` GB 级文件通常数分钟，且调用方给了更紧 deadline 时一律沿用（只收紧不放宽）。
- **连续失败 3 次会不会误判？** 任意一次成功即清零；只有"一条命令都执行不了"才累积，且取消/掐断先判 `ctx.Err()` 原样上交，不会被记成会话失效。
- **等待阶段为什么仍不进停摆看门狗？** 采集进度天然可能长时间不动，用字节判据会误杀正常采集。用命令健康度替代，既能在链路死掉时自救，也不干扰正常等待。
- **`waiting` 会不会破坏既有读数？** 只是新增枚举值，`transfer_stage` 标签表命中即显示"等待采集"；旧数据仍为 `fetching`，不需要回填。

## 遗留与下一步

- 本单现场的**第一现场证据仍缺**：需要客户机上 `delivery-jobs/dj-78f301ee-*.json` 里的 `phase` 字段，才能最终确认冻结发生在 `waiting_collect` 还是 `pulling`。修复对两种情形都生效（探测命令显式超时 + 连续失败重排），但归因结论仍需该文件。
- 客户机 bridge exe 未上报版本（`network_probe`/`transfer_metric` 的 `bridge_version` 均为空），大概率仍是旧包。**修复合入不等于现场生效，需重装 exe。**
- 30 秒级"作业整体冻结"独立看门狗（与阶段无关的绝对无动作检测）尚未做；当前依靠命令超时 + 失败重排收敛，最长收敛时间为 4 小时等待采集上限。
