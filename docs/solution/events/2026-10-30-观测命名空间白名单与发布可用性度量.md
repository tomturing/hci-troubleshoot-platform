# 观测白名单写死命名空间导致整环境盲区，发布可用性改为网关口径

- 日期：2026-10-30
- 涉及：`deploy/helm/hci-platform-obs`（Prometheus / Alloy / 告警规则）、`deploy/config/traefik-entrypoint-timeouts.yaml`
- 关联：`2026-10-28-日志收集会话状态自愈与中继重试方案.md`（同一次发布复盘的下游产出）

## 一、现场事实

| 事实 | 证据 |
| --- | --- |
| 实际命名空间是 `hci-staging` / `hci-sim-staging` / `hci-dsh` / `hci-observability` / `argocd` | `kubectl get ns` |
| Prometheus Pod 发现与 Alloy 采集白名单写死为 `hci|hci-sim-dev|hci-observability|argocd` | chart 渲染出的 `prometheus-config` / `alloy-config` |
| 因此 `hci-staging` 的业务指标与**全部 Pod 日志**都不入库 | `up{job="hci-services"}` 只有 2 条；Loki 只有 argocd 与 hci-observability |
| KSM 其实覆盖全部命名空间，只是标签被重命名 | `count(kube_deployment_status_replicas_available{exported_namespace="hci-staging"}) = 13` |
| 网关指标从未被采集 | Prometheus 活动目标只有 2 个（alloy、KSM），均在 `hci-observability`；traefik Pod 因命名空间不在白名单内，连发现都进不去 |
| 端口注解处于**集群漂移**状态：声明式文件里没有 `podAnnotations`，Helm release 的 user values 写 `8082`，实际 Deployment 却是 `9100` | `helm get values` 解出 `prometheus.io/port: "8082"`；Deployment 模板注解为 `9100` + `kubectl.kubernetes.io/restartedAt: 2026-09-22`（人工 patch，下一次 helm upgrade 会被打回 8082） |
| metrics 端点本身是好的 | `kubectl exec deploy/traefik -- wget -qO- 127.0.0.1:9100/metrics` 返回 489 个 `traefik_*` 序列 |
| staging 的 11 个业务 Pod **已经**带正确的 `prometheus.io/scrape/port/path` 注解 | `kubectl -n hci-staging get pods -o json` 统计：26 个 Pod 中 11 个带注解 |
| 去白名单不会撞权限 | Prometheus 用的是 `ClusterRole` + `ClusterRoleBinding`（`prometheus-hci`），本就允许全集群 `pods/endpoints/services` 的 get/list/watch |
| 5xx 的「增量」口径本身是瞎的：首次故障看不见 | case-service `code="502", method="GET"` 序列的首个样本就是 `10:47:49Z = 28`，此后每个样本都是 28；同一时刻 `sum(increase(traefik_service_requests_total{code=~"5.."}[15m])) = 0` |
| 但 5xx 绝对值一直都在：全站累计 109 次 | `sum(traefik_service_requests_total{code=~"5.."}) = 109`（9 条序列：case-service 500/PUT=47、502/GET=28、502/PUT=11，api-gateway 503 共 18，admin-ui 502/503 共 3） |

> 订正一：复盘初稿曾断言「staging 完全没有 K8s 指标」，实际是查错标签（Prometheus 为避免与目标自身的 `namespace` 标签冲突，把 KSM 的 `namespace` 重命名为 `exported_namespace`）。缺的是**业务指标 + 日志 + 网关指标**。
>
> 订正二：初稿写「Pod 注解写 8082 所以采不到」，只对了一半。根因是白名单不含 `kube-system`；注解 8082 是声明式文件的**漂移隐患**（集群上被人工改成了 9100），两者叠加才是「从来没数据」。

## 二、根因（第一性原理）

「有没有观测」不取决于采集器是否存在，而取决于**环境改名时白名单有没有被同步**。把命名空间名单写进配置，就等于把「新环境可见性」绑在「有人记得改配置」上——这是不可证伪的假设：漏了不会报错，只会安静地没有数据。

因此判定标准应当反过来：**只要能证明"没数据"，就说明白名单在起作用；证明不了，就是盲区。** 由此得出两条硬约束：

- C1：业务指标的发现不能依赖命名空间名单（改为注解门控，只有我们自己的 workload 会打 `prometheus.io/scrape`）。
- C2：可用性必须有**用户侧**口径。KSM 只能证明「Pod 换了」，不能证明「用户拿到 502」。
- C3：**「增量为 0」不等于「没有错」**。Prometheus 的 `rate` / `increase` / `delta` 都是「两个样本相减」，天然看不见「序列诞生之前已经发生的增量」。Traefik 的 `code` 标签是懒创建的，一个服务**第一次**出 5xx 时序列才诞生、Prometheus 拿到的第一个样本就已经是 N——于是首次故障在任何窗口上的增量都恒为 0。验收口径必须兼有「增量」与「绝对值」两种，缺任一种就会出现「指标干净、用户收到 502」。

## 三、修复设计

1. **Prometheus 去白名单**：`kubernetes_sd_configs` 不再声明 `namespaces`，改由 `prometheus.io/scrape=true` 注解门控。新环境开箱即有指标。
2. **Alloy 白名单补齐**：`scrapeNamespaces` 覆盖现有全部环境命名空间；日志量级不可控，这里保留显式名单（这是刻意的取舍，见第四节）。
3. **补上网关 5xx**：Traefik `--accesslog=true` + `--accesslog.format=json` + `--accesslog.filters.statuscodes=500-599`；Alloy 增加第二条采集链，只收 `kube-system` 中 `app.kubernetes.io/name=traefik` 的 Pod（两条 keep 是 AND，避免把 coredns/metrics-server 一起收进来）。
   - 不写 `--accesslog.bufferingSize=0`：`traefik --help` 确认该选项默认就是 0，显式写只会多一个写错的机会。
   - 不写 `--metrics.prometheus.addServicesLabels=true`：同样默认 true，`traefik_service_requests_total{service=...}` 已经带服务维度。
4. **把端口注解写回声明式文件**：`deployment.podAnnotations.prometheus.io/port: "9100"`。这一步不是为了修「现网 8082」——现网是人工改过的 9100；而是让声明式状态与现网一致，避免任何一次 `helm upgrade` 把注解打回 8082 后采集又静默消失。
5. **告警自守**：新增 `GatewayServerErrorSpike`（按服务 5xx 速率）与 `GatewayMetricsMissing`（`absent()` 15 分钟），后者专门用来发现「度量本身又静默消失了」。
6. **配置变更必须真的被消费**：Prometheus 与 Alloy 的 Pod 模板加 `checksum/config`（对整个 `configs.yaml` 取 sha256，Prometheus 另加告警规则文件哈希）。
   - 起因：这两个工作负载挂 ConfigMap 却没有 checksum，ArgoCD 自动同步完 ConfigMap 后 Pod 不会重启——Prometheus 不 reload、Alloy 不重读，**新采集链等于没上线**。
   - 为此把 `prometheus-config` 从 `prometheus.yaml` 移到 `configs.yaml`：checksum 必须指向一个不含 Deployment 的文件，否则 `include` 自己会递归。渲染 diff 已验证 ConfigMap 内容一字未变。
   - Grafana 不加：它的 datasources / dashboards 是 provisioning 轮询加载，不需要重启。
   - Tempo / Loki 同样没加，属于本次未覆盖的同类风险（详见第四节）。
7. **网关 5xx 加「首次出现」告警**：`GatewayServerErrorFirstSeen` = `(… code=~"5.." > 0) unless ((… code=~"5.." offset 10m) > 0)`。
   - 它不比较两个样本，只问「这条 5xx 序列是不是刚诞生」（10 分钟前不存在或为 0），因此能看见 `rate()` 永远看不见的那一段；
   - 是一次性事件告警：序列满 10 分钟后自动消解，不会长期占着告警列表；
   - 括号不能省：`offset` 只能紧跟向量选择器，写成 `… > 0 offset 10m` 会直接 parse error（实测）；
   - 原 `GatewayServerErrorSpike` 保留，负责「序列已存在之后的持续 5xx」；两者职责互补。

## 四、对抗性审查：什么条件下会失效

| 失效条件 | 后果 | 兜底 |
| --- | --- | --- |
| Traefik 重启以应用新的 `additionalArguments` | 单节点集群上 ingress 有数十秒空窗 | 一次性操作；重启后由 `GatewayMetricsMissing` 与 5xx 面板自证恢复 |
| `HelmChartConfig.valuesContent` 整体替换 user values | 漏写 `--entryPoints.web.http.tls=true` 会让管理后台退回 HTTP | 文件头已固定写明「删参数前先确认消费者」，本次在其原有内容上追加 |
| 全命名空间 Pod 发现带进系统组件 | 指标噪声 | 仅 `prometheus.io/scrape=true` 的 Pod 会被采集；KSM 与 alloy 自身的注解是有意保留的 |
| `hci-sim-staging` 有 default-deny 的 NetworkPolicy | 该命名空间即使去白名单也抓不到指标（网络层被拦） | 已知边界：本次只保证 `hci-staging` / `hci-observability` / `kube-system`（实测无 default-deny）。sim 环境要观测需单独放行 |
| 跨命名空间抓取依赖 Pod IP 直连 | 若以后给业务命名空间加 default-deny，指标会静默断 | 出现 `up == 0` 而非目标消失即为该症状；`GatewayMetricsMissing` 覆盖网关侧，业务侧靠 `up` 面板 |
| `configs.yaml` 任一 ConfigMap 变化都会重启 Prometheus | Grafana dashboard 改一个颜色，Prometheus 也跟着重启一次 | 刻意的「宁多不少」；相比「改了不生效」这个静默故障，重启 3~5 秒是可接受的代价 |
| Tempo / Loki 的 ConfigMap 仍无 checksum | 以后的配置变更仍会「合入了但不生效」 | 已知缺口，待下一次改动这两个组件时一并补；本次不扩大改动面 |
| 有人把 `scrapeNamespaces` 清空 | Alloy 正则变空 → 一条日志都采不到 | 模板加 `default (list .Values.scrapeNamespace)` 兜底；`GatewayMetricsMissing` 不覆盖日志，需人工看 Alloy 指标 |
| 5xx 过滤器把 4xx 业务错误也当成「不可用」 | 误判 | 只看 5xx；4xx 由业务埋点（`http_requests_total`）区分 |
| 拿 `rate()` / `increase()` 当唯一验收口径 | 首次 5xx 完全隐身（实测 28 个 502 在 6 小时以上的任何窗口里增量都是 0），「指标干净」与「用户收到 502」同时成立 | 验收同时看绝对值（发布前后各取一次 `sum(traefik_service_requests_total{code=~"5.."})`，必须相等）；告警加 `GatewayServerErrorFirstSeen` |
| 反过来只用「绝对值 > 0」做告警 | Traefik 进程内只要出过一次 5xx 就永远为真，告警不再有信息量 | 用 `offset 10m` 把条件收敛成「序列刚诞生」的事件告警，10 分钟后自动消解 |
| 依赖绝对值时必须保证没有新序列诞生 | 发布前后两次取样之间如果新出现了 5xx 序列，只比总和也能看出来（总和变大），但看不出是哪个服务 | 想归因就用 `sum by (service, code)` 比两次；总和只用于「是否发生过」 |
| 旧序列上只多了 1 次 5xx | 既不满足 `rate() > 0.05`、也不是新序列，两边都不报 | 刻意的取舍（逐次告警在生产环境会变成噪声）；发布验收用绝对值前后对比，不依赖告警 |
| 新告警规则文件写错导致 Prometheus 加载失败 | 整个规则组不生效，重蹈「MetricsMissing 也不报」 | 只能靠本地先把每条 expr 丢给真实 Prometheus 解析（本次 18/18 通过）；Prometheus 侧看 `prometheus_rule_group_last_evaluation_timestamp_seconds` 是否为 0 |

## 五、验收口径

发布一次后检查三条，缺一条即视为本轮改造未生效：

```promql
# 1. staging 业务指标已入库（此前为 0；预期 11 个 app）
count by (app) (up{job="hci-services", namespace="hci-staging"})

# 2. 网关指标可按服务归因（此前该指标一条都不存在）
sum by (service) (rate(traefik_service_requests_total{code=~"5.."}[5m]))

# 3. 发布窗口内是否真的有 5xx。不要用 rate()/increase() 单独下结论：
#    首次 5xx 会让序列诞生，而首个样本已经是 N，任何窗口的增量都是 0。
#    先在发布前取一次，发布后再取一次，两者必须完全相等。
sum by (service, code) (traefik_service_requests_total{code=~"5.."})

# 3b. 新序列告警本身是否在工作（有序列诞生时应能报出，事件型，10 分钟后自动消解）
(traefik_service_requests_total{code=~"5.."} > 0)
  unless ((traefik_service_requests_total{code=~"5.."} offset 10m) > 0)

# 4. 采集链路自守（traefik 目标必须存在且 up=1）
up{job="hci-services", namespace="kube-system"}
```

Loki 侧：`{namespace="hci-staging"}` 应有业务日志；`{namespace="kube-system", app="traefik"}` 应只在 5xx 时出现。
