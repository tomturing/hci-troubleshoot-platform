## 1. 问题是什么

管理台工单详情（`frontend/admin/src/views/CaseDetailView.vue`）当时只有「工单号 / 状态 / 客户ID /
Trace ID / 标题 / 描述 / 创建时间 / 关闭时间 / 关联 KBD」，以及对话、AI 上下文、终端历史三个标签页。
对一张日志收集工单（标题形如「日志收集任务 Q2026...」、描述为「由日志收集入口创建，仅承载日志采集任务」），
页面回答了"这单存在"，却回答不了三个真正的追问：

1. **用户当时选了什么**：哪些故障场景、哪个时间范围、哪些目标主机、走 P1 还是 P2；
2. **当时的环境是什么**：节点架构、acli 版本、日志服务器是否可达（这决定了"为什么建议走这条交付路径"）；
3. **AI 后来怎么诊断的**：用了哪些工具、看了哪些日志、最终结论是什么。

这三类事实当时分别落在 `log_collect_task`（有数据、但管理端没有任何读入口）、
`bridge_execution_logs`（探测原始事件）、DSH 容器家目录（会话文件、平台完全不可见）。

## 2. 第一性原理拆解

把「一张工单」还原成它唯一不可再分的用途：**它是排查过程的证据容器**。证据只有三类，
缺任何一类，事后复盘就必须重新去现场取证：

| 证据类别 | 唯一真源 | 当时状态 |
|---|---|---|
| 用户意图（选了什么） | `log_collect_task` + `log_collect_scenario` | 有数据、无出口 |
| 环境事实（当时是什么） | `bridge_execution_logs` 的 probe 事件 + 任务表的 arch/acli_version | 有数据、无出口 |
| 诊断过程与结论 | DSH 会话文件 | 不在平台，Pod 重建即丢 |

由此得到两条硬约束，方案不得绕过：

- **不得再造一个真源**：用户选项必须从任务表读，不能要求前端重新提交或另建"选项快照表"；
  否则两处数据必然漂移，且无法回答"当时到底选了哪个"。
- **不得复制推理**：DSH 是 Agent 运行时，平台不可能重放它的推理。能做的只有把会话文件
  解析成可检索投影；删掉投影必须能靠重扫恢复。

## 3. 约束（实测，不是推测）

| 约束 | 事实 | 影响 |
|---|---|---|
| DSH 无对外 API、无回调 | 平台只有 `/api/dsh/launch` 一个接口；会话通过 WebSocket `/dsh/api/remote.mux` | 不能"调用 DSH 拿记录"，只能读文件 |
| 会话文件是多帧 zstd | `session.v4.jsonl.zstd` 是逐批追加的多帧流；一次性 `decompress` 只解第一帧（实测 193 字节） | 解析器必须跨帧读取，否则得到"会话是空的"假结论 |
| 会话目录权限 0700 | 目录属主 uid=1000（容器 `node` 用户），`/sf/tickets` 亦为 `node:node` | case-service 必须与 DSH 同 uid（实测 uid=1000）才能读 |
| 会话正文含大量无关工单号 | 工具输出会 `ls /data/tickets/`，列出几十个 `Q...` | 不能按"出现次数最多"绑定工单，必须用确定性锚点 |
| 家目录是 emptyDir | 见 `deploy/helm/hci-platform-dsh/values.yaml` 的 `home` 注释 | 不落宿主目录，Pod 重建后记录永久消失 |

## 4. 方案

### 4.1 两条链路

```
用户选项 / 环境事实
  log_collect_task ──┐
  log_collect_scenario ──┤ GET /api/cases/admin/{case_id}/log-collect
  bridge_execution_logs ──┘        │
                                   ▼
                          管理台「日志收集」标签页

DSH 诊断记录
  DSH Pod: $DSH_HOME/sessions/**/session.v4.jsonl.zstd
        │ hostPath（DSH 写，uid=1000）
        ▼
  宿主机 /sf/dsh-home/.dsh/sessions ──只读 hostPath──► case-service（uid=1000）
        │  增量解析（size+mtime 判重，content sha256 兜底）
        ▼
  dsh_diagnosis_session ── GET /api/cases/admin/{case_id}/dsh-sessions
                                   │
                                   ▼
                          管理台「DSH 诊断」标签页
```

为什么 DSH 侧用 hostPath 而不是加一个 collector sidecar 推给平台：

- 不引入第二条网络链路和第二个令牌副本（sidecar 需要 `INTERNAL_API_TOKEN`），
  少一个失败点；
- 平台侧只读挂载，物理上不可能改写 DSH 的会话文件；
- 顺带解决 emptyDir 导致的历史会话丢失（DSH 自己的重连体验也受益）。

代价（已接受）：单节点前提，多节点需换共享存储并加节点亲和——与 `customerLogs`、`tickets` 同款取舍。

### 4.2 表

`dsh_diagnosis_session`（`database/desired_schema.sql`）：

- `session_id` 唯一，是重复解析的幂等键；
- `case_id` **不建外键**且允许为空：DSH 会话可能引用本平台不存在的工单号，
  外键会让整条记录入库失败，从而丢掉诊断证据本身；
- `messages` 是快照：单条按角色截断（user 4000 / assistant 12000 / tool 结果 800 字符），
  最多 300 条，超限时写 `truncated=true` 并在末尾追加一条 system 说明；
- `conclusion_markdown` 单独存最后一条助手消息：复盘先要答案，不必翻完整对话。

### 4.3 工单号绑定规则（顺序即优先级）

| 优先级 | 依据 | 示例 |
|---|---|---|
| 1 | `wecom_marker`：首条消息里的 `log task directory: "Q..."` | WeCom 插件注入，一字不差 |
| 2 | `cwd`：会话工作目录落在 `/tickets/<工单号>` | 按工单开工作区时 |
| 3 | `first_user`：首条用户消息里**唯一**出现的工单号 | 用户手打「看下 Q2026103000409」 |
| 4 | `title`：会话标题里唯一出现的工单号 | DSH 自动生成的标题 |
| 5 | `none`：留空，不展示 | 多义或缺失 |

反例（测试已固化）：首条消息写「对比 Q...154 和 Q...298 的区别」→ 两个号 → `none`；
正文里列出几十个目录工单号 → 不影响锚点判定。

### 4.4 接口

| 方法 | 路径（管理端，`require_admin`） | 说明 |
|---|---|---|
| GET | `/api/cases/admin/{case_id}/log-collect` | 任务列表（含用户选项、probe、建议路径、交付/代传/完整性、探测历史） |
| GET | `/api/cases/admin/{case_id}/dsh-sessions` | DSH 会话（完整对话 + 结论）；`refresh=true` 触发增量归档 |

网关侧（`backend/api-gateway/app/routes/cases.py`）两条路由均以 `INTERNAL_API_TOKEN`
重签下游身份，**不复用** `/api/log-collect` 前缀——那条代理会把 `X-Client-ID` 重签给下游，
任务按 `created_by` 过滤，管理端复用只会拿到空列表。

`dsh-sessions` 在网关单独设置 60s 超时：首次访问会解压会话文件（单会话最大十几 MB），
默认 5s 会把"正在解析"误报成 503。

### 4.5 界面

`frontend/admin/src/views/CaseDetailView.vue` 新增两个标签页（始终渲染，空态给解释，
避免"没数据就整页消失"导致用户无法触发首次归档）：

- **日志收集**：用户选项 → 环境与探测（含「建议路径」及其依据）→ 交付与产物 → 异常 →
  可折叠的探测原始记录；
- **DSH 诊断**：左侧会话列表（标题/时间/对话数/工具数/绑定依据），右侧「最终结论」
  （Markdown 渲染，`marked` + `DOMPurify`）+ 可折叠完整对话（工具调用保留名字与参数摘要）。

「建议路径」不落库，每次由 probe 事实重算（`log_server_reachable` → P1 / P2 / 未知）：
单独存一份"建议"只会与事实漂移。

## 5. 可观测性

| 事件 | 位置 | 关键字段 |
|---|---|---|
| `dsh_sessions_ingested` | case-service 日志 | `case_id`、`scanned/parsed/skipped/failed/unbounded` |
| `dsh_session_parse_failed` | case-service 日志 | `path`、异常信息（逐文件，不中断整批） |
| `dsh_sessions_dir_missing` | case-service debug 日志 | 挂载目录（配置错误的唯一线索） |
| `dsh_session_partial_frame` | debug 日志 | 已解出字节数（文件正在写入属正常） |

接口响应里的 `ingest` 字段把同一组计数返回给前端，页面可直接看出"扫了多少、新增多少"。

## 6. 对抗性审查：什么情况下会错

| 失败模式 | 表现 | 处置 |
|---|---|---|
| 挂载目录不存在 | 页面永远 0 条，没有任何报错 | 接口返回 `ingest.root_missing=true`，页面显式提示"未读到 DSH 会话目录" |
| 目录存在但 uid/权限不符 | 静默 0 条（`rglob` 不抛错） | 部署文档要求 `install -d -o 1000 -g 1000`；验收必须看到真实会话，不接受"目录存在" |
| Pod 重建 + 未配 hostPath | 历史记录消失 | 记录已入库则仍在平台；DB 才是展示口径，文件只是真源 |
| 会话仍在写入 | 最后一帧解压失败 | 解到哪算哪，下一次扫描补全（size 变化即重解析） |
| 文件被 touch 但内容未变 | 无意义的重复入库 | 解压后算 `content_sha256`，相同则只刷新判重字段 |
| 会话同时诊断多个工单 | 绑定歧义 | 只有唯一命中才绑定，否则 `none`，详情页不显示（宁缺勿错） |
| 单个会话异常巨大 | 内存/DB 膨胀 | 解压上限 16 MiB、消息 300 条、单条截断；`truncated=true` 明示 |
| 多个副本同时归档 | 重复劳动 | 进程内按 event loop 加锁 + `ON CONFLICT` 幂等；最多重复解压，不会写坏 |

## 7. 部署前置

1. 宿主机创建家目录：`install -d -o 1000 -g 1000 -m 0755 /sf/dsh-home`
   （不能用 `DirectoryOrCreate`：kubelet 建成 `root:root`，DSH 写不进 profile/session）；
2. DSH Chart 设置 `home.hostPath=/sf/dsh-home`；
3. 主 Chart 设置 `caseService.dshSessions.enabled=true`（`hostPath` 指向
   `/sf/dsh-home/.dsh/sessions` —— **两层**：`home.hostPath` 挂的是容器 `/home/dsh`，
   而 `DSH_HOME=$HOME/.dsh`，会话写入 `$DSH_HOME/sessions`；`mountPath=/var/lib/hci/dsh-sessions`）；
4. 表由 `database/desired_schema.sql` 收敛（纯 `database/` 变更不触发 db-migrate，需手动 apply）。

## 8. 验证口径（不信代理指标）

| 验证项 | 判据 |
|---|---|
| 多帧解码 | 单测构造两帧，断言第二帧内容可见（只解第一帧必红） |
| 绑定优先级 | 单测覆盖 marker / cwd / 唯一命中 / 多义 |
| 管理端鉴权 | 无 Token 请求两个端点必须 401/403 |
| 端到端 | 真实工单详情页出现「日志收集 (N)」与「DSH 诊断 (N)」，且能展开结论与对话 |
| 反向验证 | 拔掉挂载（或改名目录）后页面必须出现 `root_missing` 提示，而不是"看起来正常" |

## 9. 遗留

- DSH 会话与工单的绑定依赖会话正文里的工单号；若未来 DSH 支持按工作区/参数打开，
  应改为显式传入工单号，把 `binding_source` 升为 `launch_param`。
- `messages` 快照不保留 reasoning block（只留正文），若要做"AI 思考过程"回放需另行评估体积。
