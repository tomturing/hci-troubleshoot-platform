# acli 安装包全链路校验与重试兜底

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-30 | v1.0 | 初版：Q2026102901049 现场根因修复（下载/上传/安装三跳校验 + 可重试兜底） | 2026-10-24-acli同步会话缺失导致从未安装.md |

## 背景与需求

工单 Q2026102901049（2026-10-29 23:00–23:12，节点 10.122.216.224）现场，客户 UI 连续三次报：

> 上传 acli 安装包至 HCI 失败: context deadline exceeded (Client.Timeout or context cancellation while reading body)

排查结论有两条，缺一不可：

1. **直接触发**：链路带宽从历史的 ~9 MB/s 退化到 <203 KiB/s（18,718,164 B / 90 s），
   而 `http.Client{Timeout: 90s}` 的作用域覆盖 body 读完之后——历史上实现
   「下载 body 直接当 SSH stdin」，等于让 90 s 的**下载**预算去承担**上传**时长。
   三次失败间隔精确为 92 s / 92 s / 92 s，就是这条超时的指纹。
2. **结构性缺陷**：acli 安装包链路**零完整性校验**。日志压缩包有 5～6 个校验点
   （源端摘要锚点、分片 SHA-256、合并整包校验、`integrity_state` 透传），
   而安装包只把 `Content-Length` 写进日志，从未用于判定；上传结束也不比对远端
   字节数或摘要。于是「上传到 HCI 的包不对」既可能发生、也无法被发现。

用户提出的三条兜底要求即本次验收标准：

1. **上传工具失败后必须提供重新上传的按钮**，而不是报错后就不管；
2. **下载 → 上传 → 落地**每一跳都要有 MD5/SHA-256 校验，任何一跳失败都要给
   「重试」兜底，并把具体摘要值写进日志；
3. **下载、上传、执行安装命令都要记录详细日志**（含安装器的真实返回/报错），
   并同步到远端，让整条链路「有检查把关、有日志透明、有重试兜底」。

## 方案概述 (WHAT)

| 层次 | 改动 | 解决的问题 |
|------|------|-----------|
| 下载 | `downloadAcliPackage`：**先读完再上传**，`io.MultiWriter` 同时算 SHA-256 与 MD5，并与 `Content-Length` 比对 | 下载不完整可判定；下载超时不再冒充上传超时 |
| 上传 | `buildAcliRemoteWriteCommand`：`cat > tmp && 校验 && mv -f tmp dest`，校验嵌在 `mv` **之前** | 坏包永远到不了正式路径；校验结论以退出码 + 标记回显 |
| 安装 | `installAcliPackage`：stdout/stderr 分离保存，完整输出（头尾各 2 KB）随 `acli_sync_progress(status=install_output)` 回传 | 「装不上」时远端能看到安装器真实输出，不用再登录节点 |
| 并发 | `Bridge.acliMu` + `acliBusy[caseID@nodeIP]` 互斥 | 两个上传写同一 `destPath` 互相覆盖（LC-INSTALL-009） |
| 超时 | 下载 120 s / 上传 300 s / 安装 240 s 三段独立预算，会话总预算 720 s | 任何一段变慢都不再被误判成另一段超时 |
| 重试 | 传输失败自动重试 3 次（退避 2 s / 4 s）；前端提供「重试上传 / 重试安装」按钮，经 `retry_stage` 精确跳过已完成阶段 | 不自动重试就只能人工重头再来；从头再来等于再传 20 MB |
| 观测 | 每个阶段都写结构化 `blog`（含 `sha256`/`md5`/`remote_digest`/`integrity_state`/`attempts`），经 WS 回采落 `bridge_execution_logs` | 事后核对「传上去的是哪个包」无需登录节点 |

## 详细设计

### 1. 为什么必须「先读完再上传」

`http.Client.Timeout` 从发起请求计到 **body 读完之后**。历史实现把 `dlResp.Body`
直接当 SSH stdin，于是客户端在 90 s 到点后 cancel body，SSH 上传随之报
`context deadline exceeded`——错误文案指向「上传」，真因却是「下载预算不够」。
把包读进内存（实测 18～31 MB，上限 256 MiB 防呆）后连接立即释放，下载与上传
的超时彻底解耦，错误也能指向真实的失败环节。

### 2. 校验锚点从哪来（第一性原理）

官方源是 **HTTP 明文、无签名**，能拿到的权威锚点只有两个：

- 响应头 `Content-Length`：服务端声明字节数（唯一由对端产生、又与内容绑定的量）；
- 读取 body 时自己算出的 SHA-256 / MD5：本地客观事实。

因此校验只可能发生在两处：**下载读完**（已收字节 == 声明字节）与
**落盘之后**（远端 size/digest == 本地 size/digest）。不存在第三种"更权威"的来源，
所以不引入签名校验的假承诺。

### 3. 远端写入：校验必须嵌在 `mv` 之前

```sh
umask 077
if cat > <tmp>; then
  SIZE=$(wc -c < <tmp> ...); ALGO=size_only; DIG=""
  command -v sha256sum  -> ALGO=sha256; DIG=$(sha256sum <tmp>)
  elif command -v md5sum -> ALGO=md5;  DIG=$(md5sum <tmp>)
  echo "__ACLI_WRITE size=$SIZE algo=$ALGO digest=$DIG"
  [ "$SIZE" = "<期望>" ] || { echo "__ACLI_WRITE_FAIL size_mismatch"; rm -f <tmp>; exit 21; }
  [ sha256 且 DIG 不符   ] && { echo "__ACLI_WRITE_FAIL digest_mismatch"; rm -f <tmp>; exit 22; }
  mv -f <tmp> <dest> && chmod 0755 <dest> && echo "__ACLI_WRITE_OK" || { ...; exit 23; }
else
  echo "__ACLI_WRITE_FAIL cat_failed"; rm -f <tmp>; exit 20
fi
```

对抗性审查：如果只在「上传完成后 stat 一下」，SIGKILL / 通道中断时半包早已被
`mv` 上线，`stat` 只能证明盘上有文件，证明不了它是我们要的包。把校验嵌在 `mv`
之前，「坏包不可见」才是结构性事实，而不是靠调用方记得清理。

远端可能没有 `sha256sum`（安装场景下 acli 恰恰还没装），此时降级为 size-only，
但结果里必须显式标注 `integrity_state=size_only`，并在 UI 与日志里写明
「仅比对了字节数」——静默降级等于把「没校验」伪装成「校验通过」。

### 4. 分段超时与自动重试

- 下载 120 s、上传 300 s、安装 240 s，会话总预算 720 s（`handleAcliSync` 的 ctx）；
- 传输失败（含校验不符）自动重试至多 3 次，退避 2 s / 4 s，并且**丢弃缓存重新下载**：
  校验不符既可能是上传截断，也可能是下载侧被中转缓存污染，只重传同一份可疑字节
  无法排除后者；
- 安装失败**不**自动重试：那属于产品侧结论（集群环境不满足），自动重跑只会重复失败。

### 5. 重试兜底：三档 `retry_stage`

| retry_stage | bridge 行为 | 前端何时建议 |
|---|---|---|
| `upload` | 复用内存缓存（TTL 10 min）里的已校验包重传；缓存缺失时降级为重新下载 | `stage=download/upload/verify`（包尚未被证明正确） |
| `install` | 先探测节点上那份包的 size/digest，与本地基线一致才复用并跳过全部传输 | `stage=install`，或 `install_success=true` 但版本探测失败 |
| `all` | 完整流程（默认） | 阶段未知（旧版 bridge）时的保守建议 |

对抗性审查（为什么要探测而不是无脑复用）：上一轮正是「盘上那份包不对」才失败的，
无条件复用等于把同一个错误再执行一遍。因此 `verifyReusedRemotePackage` 要求
size 必须相等、digest 在远端可得时也必须相等；**本地没有基线（缓存过期）时直接拒绝复用**。

另一个对抗性审查点：用户点「重试上传」时，若版本判定先行算出「acli 已是最新」，
请求会被 `up_to_date` 分支吞掉——按钮点了却什么都不发生，与"报错不管"等价。
所以 `retry_stage != all` 被视为强制信号（`needInstall = true`）。同理，官网不可达
导致 filename 为空时，`findRemoteAcliPackage` 会先在节点上找真实存在的包，
保证「重试安装」在网络恢复前仍然可用。

### 6. 错误码

| 码 | 场景 | 层 / 责任方 / 可重试 | stage |
|---|---|---|---|
| `LC-INSTALL-007` | 落盘校验不符（size / digest） | INSTALL / customer / true | verify |
| `LC-INSTALL-008` | 安装包下载不完整（声明 vs 实际） | INSTALL / customer / true | install |
| `LC-INSTALL-009` | 同会话已有传输在进行（互斥拒绝） | INSTALL / platform / true | install |

Go 常量表与 `backend/shared/resolution/catalogs/log_collect_error_catalog.json`
必须同步，`TestErrorCatalogMatchesGoMeta` 强校验 code/layer/stage/owner/retryable。

### 7. 日志与远端同步

新增/强化的结构化事件（全部带 `trace_id`/`case_id`/`node_ip`）：

| event | 关键字段 |
|---|---|
| `acli_sync.download_verified` | `filename`、`size`、`declared_length`、`sha256`、`md5`、`duration_ms` |
| `acli_sync.upload_verified` | `dest_path`、`attempts`、`package_size`、`sha256`、`md5`、`remote_size`、`remote_algo`、`remote_digest`、`integrity_state` |
| `acli_sync.transfer_failed` | `attempt`、`remote_fail_reason`、`remote_size`、`remote_digest` |
| `acli_sync.install_failed` | `command`、`exit_code`、`duration_ms`、`stdout_bytes`、`stderr_bytes`、`output_preview` |
| `acli_sync.install_done` | 同上 + `integrity_state` + 包摘要 |
| `acli_sync.reuse_verified` / `reuse_rejected` | `remote_size`、`remote_algo`、`remote_digest` |

`blog` 经 WebSocket 的 `bridge_log` 推给前端，前端统一回采到
`conversation-service` 的 `bridge_execution_logs`，因此**不需要新增回采通道**：
装工具这一跳的完整证据链与其它 bridge 日志走同一条链路。

### 8. 前端兜底

- `parseAcliSyncFacts`（`api/terminal.ts`）统一解析完整性事实，进度与结果共用一套；
- `AcliSyncFailure` 携带 `facts` 与 `retrySuggestions`，把「哪一跳失败」变成可渲染的按钮；
- `LogCollectPanel.vue` 在固定提示区渲染失败卡片：错误码、失败环节、尝试次数、
  包名/字节数、本地 `sha256`/`md5`、节点摘要、校验强度、安装退出码与输出，并提供
  「重试上传（复用已校验包）」/「重试安装（复用节点上已校验包）」/「从头重试」；
- 前端超时预算 780 s > bridge 分段预算之和 660 s：前端先超时会让用户以为失败并
  再点一次，叠出第二次上传；
- 前端没有等待者的迟到回包（已超时/已切走）同样落成失败卡片，避免桥的结论被丢弃。

新增单测重点：

- `acli_package_test.go`：断言「校验片段索引 < `mv` 索引」（顺序反了就等于没校验）、
  `sha256`/`md5`/`size_only`/各失败原因的判定、无基线时拒绝复用、
  非法文件名收敛（`../../etc/passwd` → 默认名）、互斥与缓存 TTL。
- `acliManager.spec.ts`：`retry_stage` 只在显式重试时下发、重试建议与失败阶段一致、
  超时预算大于分段预算之和、完整性事实解析不抛错。
- `LogCollectPanel.spec.ts`：校验失败卡片展示摘要并下发 `retry_stage=upload`；
  安装失败只给「重试安装」；不可重试失败不给按钮。

> 单测在开发期就抓到一个真实缺陷：`acliWriteLineRe` 原写成 `algo=([a-z_]+)`，
> 而 `sha256`/`md5` 含数字——正则永远不匹配，远端校验回显会被解析成空结果，
> 表现为「校验静默失效」。已修正为 `[a-z0-9_]+`。

## 回滚

改动集中在 `terminal_bridge/acli_package.go`（新增）、`terminal_bridge/main.go`
（`handleAcliSync` 的 5～11 步）与前端三个文件，不涉及数据库与协议不兼容变更：
旧前端不认识 `retry_stage` 时等价于 `all`，旧 bridge 不认 `retry_stage` 时也只是
完整重来。回滚按普通 revert 处理。
