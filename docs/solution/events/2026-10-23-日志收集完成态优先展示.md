# 日志收集：完成态优先展示（重开面板不再要求重新收集）

## 一、问题

staging 实测：某工单已收完并归档（`status=completed`、`relay_status=success`），
关掉抽屉再打开，界面退回空白表单，右下角仍是「开始收集」。

用户看到的事实是"好像没收过"，实际平台已经存了完整记录。误判的代价是重复采集：
4~20 GiB 的包再跑一遍，既占 HCI 磁盘也占日志服务器空间。

## 二、第一性原理

1. **状态真值在平台，不在前端内存**。`log_collect_task` 已落 `status` / `finished_at` /
   `archive_path` / `archive_size` / `upload_mode` / `relay_status` / `archive_deleted`，
   足以还原"收了什么、什么时候收的、包在哪"。
2. **前端只在内存里维护了当次会话的完成态**。`stage=done` 是组件局部状态，卸载即丢；
   `maybeResumeRunningTask()` 只接管"非终态"任务 → 完成态没有任何恢复路径。
3. 因此缺的不是后端能力，而是**打开面板时的恢复顺序**：进行中 → 最近一次已完成 → 空白表单。
   "重新收集"必须是用户的显式选择，不能是默认动作。

## 三、方案

### 3.1 恢复顺序（`restoreTaskState`）

```
listTasks(caseId, 10)
├─ 有活跃任务（pending…uploading）→ 接管并轮询（原逻辑不变）
├─ 有 completed                    → 结果态（只读）
└─ 都没有                          → 空白表单（可开始收集）
```

`total` 用于告知当前客户端在该工单下的记录条数（后端 `list` 按 `created_by` 过滤，
所以文案写"当前客户端"，不承诺跨端全量）。

### 3.2 结果态（`viewMode = 'result'`）

只读展示，全部字段取自任务记录：

| 字段 | 来源 | 缺失时 |
|---|---|---|
| 完成时间 | `finished_at` → `updated_at` | 时间未记录 |
| 发起节点 | `origin_node_ip` | — |
| 交付路径 | `upload_mode`：`acli_direct`=P1 / `bridge_relay`=P3 | 未记录 |
| 收集场景 | `modules` + 目录标签映射 | 未记录 |
| 时间范围 | `date_from` ~ `date_to` | — |
| 目标主机 | `ips`（含 `all` → 全部在线节点） | 全部在线节点 |
| 压缩包大小 | `archive_size` | 未记录 |
| 归档状态 | P1=插件直传；P3=`relay_status` | 归档状态：xxx |
| 产物位置 | `archive_deleted` ? 已清理 : `archive_path` | 未记录 |

底部只给「重新收集」+「关闭」：完成是结论，不是待办。

### 3.3 重新收集

- 回到表单，并用上一次的 `modules` / `dateRange` / `ips` 预填（场景按当前目录收敛，
  避免提交时被判非法枚举）；
- 立即重新准备（目录/节点清单），不沿用旧探测结果；
- 新任务另起一条记录，旧任务不被覆盖。

### 3.4 让任务记录自描述（补齐回填字段）

`upload_mode` / `archive_path` / `archive_size` / `archive_sha256` 此前**没有任何代码写入**
（后端只有字段与 PATCH 契约），结果态只能显示"未记录"。现在完成时一并回填：

- P1：`upload_mode=acli_direct`，`archive_path` 取自进度快照；
- P3：`upload_mode=bridge_relay`，`archive_path` / `archive_size` / `archive_sha256`
  取自 `completeUpload` 返回值（sha256 需满足 64 位小写十六进制，格式不符则不写，
  避免整条 PATCH 被 422 拒绝）。

### 3.5 完成即切结果态

`markCompleted()` 成功后直接 `showResult(currentTask)`：**"刚收完"与"重开面板"走同一套渲染**，
避免内存态与平台态两套 UI 各说一套。PATCH 失败则不切（平台没有完成记录，重开也看不到，
一致性交给平台）。

## 四、对抗性审查

| 场景 | 结论 |
|---|---|
| 换工单 | 组件按 `props.caseId` 复用不重建 → 已加 `watch(caseId)` 清空完成态/任务/探测结论，否则会把 A 单结果显示给 B 单 |
| 采集中重开面板 | 活跃任务优先接管，不显示结果态 |
| 完成记录存在但产物已清理 | `archive_deleted=true` → 显示"压缩包已清理"，不再显示 rm 提示 |
| P1 无 `relay_status` | 按 `upload_mode` 判断归档文案，不用 `relay_status=none` 误判为失败 |
| 结果态点「刷新进度」 | 完成是终态，结果态隐藏该入口，避免把完成态刷成进行中 |
| PATCH 失败 | 不切结果态，仍提示"平台状态回填失败，请在任务列表确认" |
| 他人/其他浏览器发起 | 后端按 `created_by` 过滤，看不到即回表单，不虚构历史 |

## 五、验收

单测（`LogCollectPanel.spec.ts`，9 条）：

1. 平台已有完成记录 → 渲染结果态（交付路径/主机/场景/产物），且不出现「开始收集」；
2. 结果态点「重新收集」→ 回表单（随后立即重新探测）；
3. 有进行中任务时优先接管，即使同工单已有完成记录。

人工（staging）：收完一单 → 关闭抽屉 → 重新打开 → 应直接看到完成结果与「重新收集」。

## 七、老记录的字段兜底（2026-10-23 追加）

`upload_mode` / `archive_path` / `archive_size` 是本次才补写的字段，**此前完成的记录在库里是 NULL**。
直接按枚举渲染会出现「交付路径：未记录 / 归档状态：none」，把内部状态暴露给用户。

兜底规则（只用于展示，不回写）：

| 字段 | 兜底依据 | 结果 |
|---|---|---|
| 交付路径 | `remote_url` 非空 | P1 直传日志服务器 |
| 归档状态 | 交付路径为 P1 | 已由插件直传日志服务器 |
| 产物位置 | P1 且无 `archive_path` | 由插件上传后自动清理，路径未记录 |
| 清理提示 | P1 | 插件自动删除，无需人工清理（不再输出 rm 命令） |
| 未知 | 无 `remote_url` | 未记录（不输出 `none`） |

验证：新增用例「老记录缺 upload_mode 时按 remote_url 兜底展示 P1，不暴露内部枚举」，
`pnpm test` 180 passed。
