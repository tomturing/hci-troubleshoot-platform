# KBD 批量任务状态迁移说明

## 变更目的

KBD 管理页的批量识图、批量重新分类、批量抽取信号、批量通过和批量拒绝统一使用持久化任务。接口返回后，审核人员可以在页面刷新或服务重启后继续查看进度、逐条结果和失败原因。

本次增加 `KBD Batch Job（KBD 批量任务）` 和 `KBD Batch Job Item（KBD 批量任务明细）` 两张持久化表，使任务进度、逐条结果、失败原因和 `Trace ID（链路标识）` 可查询、可追溯。

## 数据库对象

- `kbd_batch_job`：保存任务类型、状态、提交范围、KBD 汇总计数、图片级工作计数和起止时间。
- `kbd_batch_job.request_json`：保存审核人、统一审核备注和提交时版本号等不可变请求快照，供中断恢复、失败重试和历史审计使用。
- `kbd_batch_job_item`：保存每条 KBD 的等待、执行、成功或失败状态，以及图片级进度、精简结果和结构化错误。
- 两张表均包含 `trace_id`，并通过 `updated_at` 触发器维护最后更新时间。
- 明细随任务删除；KBD 条目存在任务历史时禁止直接删除，避免审计记录悬空。

该变更只新增表、索引和触发器，不写入默认初始化数据，也不修改既有 KBD、SOP、在线诊断或离线诊断数据。

## 状态规则

任务状态如下：

- `pending（等待处理）`：任务和全部明细已落库，尚未开始执行。
- `running（处理中）`：至少已经启动后台执行。
- `completed（已完成）`：全部明细成功。
- `partial_failed（部分失败）`：同时存在成功和失败明细。
- `failed（失败）`：全部明细失败。
- `interrupted（已中断）`：服务或任务执行器退出，至少一条明细未完成；中断数与业务失败数分别统计。

单条明细状态为 `pending（等待处理）`、`running（处理中）`、`succeeded（成功）`、`failed（失败）` 或 `interrupted（已中断，可重试）`。

### 服务中断后的状态收敛

- 批量任务执行器随 `kb-service（知识库服务）` 进程运行。若服务异常退出，原进程中的执行任务不会自行恢复。
- 服务启动和管理页轮询会检查超过安全窗口仍无更新的 `pending/running（等待处理/处理中）` 任务。
- 已成功或已经失败的明细保持不变；尚未完成的明细标记为 `BATCH_PROCESS_INTERRUPTED（批量执行进程中断）`，并注明可以重新提交。
- 批次随后收敛为 `interrupted（已中断）`，写入完成时间；页面分别显示成功、业务失败和中断数量，不再永久停留在“处理中”或把中断误报为业务失败。
- 页面进度只按 `成功数 + 业务失败数` 计算实际处理比例；中断条目虽然已经收敛到终态，但不计入进度完成数。例如成功 33、失败 7、中断 47、总数 87 时显示“已处理 KBD 40/87（46%）· 中断 47”。
- 默认安全窗口为 600 秒，可通过 `KBD_BATCH_STALE_AFTER_SECONDS（KBD 批量任务无进展超时秒数）` 调整；窗口用于避免滚动发布期间新旧服务短暂重叠时误判仍在执行的任务。
- 活跃执行器会定期刷新批次心跳；即使单次模型调用耗时较长，只要执行进程仍存活就不会被超时检查误判为中断。
- 中断条目不会自动重跑，避免信号抽取重复生成提案修订；审核人员可在任务详情筛选失败条目后重新提交。

### 未成功记录重试

- 对存在 `failed（失败）` 或 `interrupted（已中断）` 明细的终态批次，管理页提供“重试未成功”操作。
- 重试只选取原批次中失败和中断的 KBD；成功记录不会重复执行。
- 重试会创建新的 `KBD Batch Job（KBD 批量任务）`，不会修改或清空原批次，原始结果继续用于审计。
- 新批次通过 `retry_of_batch_id（来源批次编号）` 关联原批次；原批次同时可查看直接派生的重试批次。
- 同一个批次最多直接创建一次重试，防止重复点击产生并发重复任务；若重试批次仍有未成功记录，可从该新批次继续重试，形成完整追溯链。

批量识图还维护 `work_total_count（图片总数）`、`work_completed_count（已处理图片数）` 和 `work_failed_count（失败图片数）`。因此审核人员无需等待整条 KBD 完成，也能看到图片级实时进度。分类、信号抽取、审核通过和审核拒绝任务的一条 KBD 视为一个工作单元。批量通过逐条复用单条发布门禁、Embedding（向量）生成和修订发布流程；批量拒绝要求统一拒绝原因，并逐条记录审核事实。

## 识图可靠性规则

- 支持两类模型输出：平台约定的结构化 `TYPE / FULL_TEXT / DESCRIPTION`，以及专用 OCR 模型直接返回的纯文本或 Markdown。纯 OCR 文本只作为“截图可见文字”保存，不自动生成语义结论。
- 连续返回空内容、`无文字/无描述` 或无法解析的结果时，本张图片明确失败，不能记为成功。
- 一条 KBD 的全量重新识图采用原子写回：任一图片失败，本轮全部结果不覆盖原有图片证据；全部成功后才生成新的 Vision Proposal（识图提案版本）。
- OpenAI SDK（开放式人工智能接口客户端）的内部重试关闭，统一由业务层控制总尝试次数，避免一次超时被多层重试放大。

## 部署与回退

部署时由声明式数据库同步应用 `database/desired_schema.sql`，随后由 `database/desired_extras.sql` 创建更新时间触发器。新接口依赖这两张表，因此应先完成数据库同步，再更新 `kb-service`、`api-gateway` 和 `admin-ui`。

回退旧版本应用时可以保留新增表，旧代码不会读取它们。若未来确需删除，应先确认没有审计保留要求并导出历史数据；常规版本回退不执行删表。

## 验证方式

1. 提交任一批量操作，确认响应包含 `batch_id`。
2. 在管理页“批量任务”区域观察图片数和 KBD 完成数自动增加。
3. 刷新页面，确认任务和进度仍然存在。
4. 打开详情，确认成功项显示结果摘要、失败项显示明确原因。
5. 使用任务的 `Trace ID（链路标识）` 检索服务日志，确认提交、逐条处理和任务完成日志可关联。
6. 执行批量任务期间重启 `kb-service（知识库服务）`，超过安全窗口后刷新页面，确认未完成条目显示可重试的中断原因，批次进入终态且完成时间已写入。
