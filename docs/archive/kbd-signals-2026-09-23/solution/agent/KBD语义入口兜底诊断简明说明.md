# KBD 语义入口兜底诊断简明说明

> 2026-09-23 更新：无信号案例可发布为“仅案例推荐”，直接按标题和问题描述检索，语义画像改为可选增强；不进入现场确诊和离线采集。下文的画像填写要求仅针对选择维护画像的案例。完整流程见 [无信号案例推荐与诊断能力分离](../../../../solution/agent/KBD无信号案例推荐与诊断能力分离.md)。

> 本文面向产品、运营和知识库审核人员，用于快速了解功能。技术规则、数据格式和验收记录见 [KBD 语义入口兜底诊断设计与需求](../../../../solution/agent/KBD语义入口兜底诊断设计与需求.md)。

## 一句话说清楚

当任务、告警、弹框等明确证据没有找到线索时，系统可以根据客户对故障现象的描述，找出几篇值得继续检查的 KBD（知识案例），再用现场证据验证或排除。

它是“找排查方向”的兜底入口，不是“凭一句话猜根因”。

## 为什么需要它

过去，系统更依赖任务失败记录、告警和弹框等结构化信息。但在一些场景中，这些信息可能已经消失、无法获取，或问题本身就不会产生这类记录。

此时，客户的原始描述往往是唯一入口。例如：

> “创建虚拟机时，提示镜像格式不支持。”

系统会利用“镜像格式不支持”这类有区分度的特征，找到相关 KBD。但这只能说明“值得检查”，不能直接宣布镜像损坏或给出确定根因。

## 实际使用时会怎么走

1. **先查明确证据**：优先查看任务、告警、弹框等高可信线索。
2. **再启用语义兜底**：明确证据已完整查询且未命中，或该类问题本来就没有这类入口时，可以根据客户描述找 KBD；如果查到记录但最终仍无法确诊，只允许继续提供“仅人工指引”，不会执行语义候选命令。
3. **筛选候选案例**：系统会结合问题分类、特征报错和适用范围，排除明显不适用的 KBD。
4. **候选太多就追问**：如果多篇 KBD 都很像，系统会请客户补充报错、版本或操作场景，而不是强行选第一名。
5. **用现场证据裁决**：对少量候选执行已审核的检查。最终结论看证据，不看文字相似度排名。

如果明确证据查询失败、权限不足或结果不完整，系统不会把它当成“未命中”并继续兜底，而会说明问题或转人工处理。

## 三种可交付结果

| 类型 | 客户能得到什么 |
|---|---|
| 可执行诊断 | 系统找到候选后，可以继续执行已审核的现场检查 |
| 仅人工指引 | 系统告诉客户还需补充哪些证据，但不自动确认根因 |
| 能力缺口 | 当前既无可信自动检查，也无成熟的补证指引，记录后转人工或待后续建设 |

“仅人工指引”的结果始终是“暂时无法确认”，不会被包装成低置信度的已确认结论。

## 知识库审核人员要做什么

每篇适合做语义入口的 KBD，需要准备一张简短的“入口说明卡”，主要包括：

- 客户通常会怎么描述这个问题；
- 至少要出现哪些特征报错或关键短语；
- 出现什么情况时不应选它；
- 适用的产品、版本、组件或操作场景；
- 它能自动验证，还是只能请客户补证。

发布前，审核人员应使用真实正例和容易混淆的反例试跑，并检查后续验证方法是否确实存在。草稿不会自动变成线上规则，仍需要专家审核发布。

## 系统明确不会做的事

- 不会因为描述相似，就直接确认根因。
- 不会从客户描述中猜测虚拟机、主机等执行对象。
- 不会在缺少必要参数时冒险执行命令。
- 不会因为候选排名高，就忽略反证、执行失败或证据不足。
- 不会让工作稿直接影响线上诊断，也不会用新规则重写旧证据的诊断结果。

## 用户能感知到的改变

- 以前“没有任务或告警线索就无法继续”的问题，现在多了一条可控的排查路径。
- 多篇知识都可能适用时，系统会说明为什么选、为什么不选，并请用户补充关键信息。
- 在线诊断和离线诊断遵循同一条原则：描述用来找方向，证据用来下结论。

## 当前状态

主要功能已接入知识生产、审核发布、在线与离线诊断，并完成自动化回归和本机隔离环境的全链路验证。正式上线前，仍需在目标预发布或生产环境核对实际镜像、采集、命令执行、诊断结果和观测记录。
