# 工单归档命名与"取最新包"（2026-11-06）

## 问题

工单 `Q2026110600493` 的日志包目录里出现两份 zip：

```
-rw-r--r-- 571632020 Nov  6 15:52 Q2026110600493-20261106155217.zip
-rw-r--r-- 335882103 Nov  6 11:37 Q2026110600493.zip
```

带时间戳的名字不是采集端产物，是 5888 归档服务（`/acli/process_upload.py`）在
"同名文件已存在"时避免覆盖的结果。该策略由 2026-10-31 01:27 的 acli 提交
`b3118a8`（"归档防覆盖"）引入，此前（2026-09-11 的 `c3eac85`）是 `shutil.move`
直接覆盖。

引入时的做法是**把新包改名加时间戳**，规范名保留旧包。副作用：

1. 规范名 `<工单号>.zip` 永远停留在首次上传的旧包，最新日志沉在时间戳名下；
2. ticket-sync 的扫描只认 `^/sf/log/(Q\d{13})/\1\.zip$`（`app/fetcher.py`
   `_parse_remote_archives`），带戳包被整体丢弃 → 平台知识库只能拿到过期日志；
3. 该工单本次的差值是 11:04 采集的 335M 与 12:06 采集的 545M——丢掉的是更完整的
   那一份；
4. `remoteMtime`/`remoteSize` 换包判据也发现不了：它比对的正是那份旧包，永远
   "没变"。

## 决策

**规范名必须指向最新包。** 保留历史的诉求不变，变的是"谁占规范名"：

| 侧 | 改动 | 位置 |
|---|---|---|
| 5888 归档 | 重传时把**已存在的旧包**改名加戳（时间戳取旧包 mtime），新包占用规范名 | `/acli/process_upload.py` |
| ticket-sync | 拉取前按 mtime 取目录内最新一份（同 mtime 时规范名优先），本地落盘名仍是 `<工单号>.zip` | `tools/ticket-sync/app/fetcher.py` |

两侧都要改的理由：5888 的修复只对**之后**的上传生效，历史目录（含本工单）仍需
ticket-sync 自己挑最新；而只改 ticket-sync 会让每个按契约取包的下游（人工、
`/archive_status` 之外的脚本）继续读旧包。

## 实现要点

- `_parse_remote_archives` 放宽为两种合法名：`<工单号>.zip` 与
  `<工单号>-\d{14}(-\d+)?\.zip`，且目录名必须等于文件名里的工单号（跨目录引用丢弃）；
- 同工单选 `mtime` 最大者；mtime 相同时优先规范名（对齐 11-06 之后的服务端约定）；
- `resolve_archive_path()` 在 `fetch()` 内部执行，自动任务/手动触发/CLI 三条入口
  共用同一套选取逻辑，漏改任一入口都会静默同步旧包；
- 列目录失败或无结果时回退规范名，不在这里臆造失败原因——错误码仍由随后的 rsync
  单一决定（`NOT_FOUND` / `SSH_FAILED`）；
- 5888 侧合并大小校验在改名之前执行，坏包不会被写进归档、也就不会把旧包挤成时间戳名。

## 验证

- `/acli/tests/test_archive_naming.py`：mtime 取戳、重传后规范名=新包、时间戳撞车
  追加序号、坏包不夺名（16 项）。
- `tools/ticket-sync/tests/test_archive_naming.py`：取最新、同 mtime 优先规范名、
  跨目录/畸形时间戳丢弃、`resolve_archive_path` 回退、`fetch` 用显式路径但本地落
  规范名（14 项）。

## 遗留

`/sf/log/Q2026110600493/` 里的历史两份包仍保持原状（规范名=旧包），由 ticket-sync
的新选取逻辑兜底；如需人工纠正，可把旧包改名、新包改回规范名（`/sf/log` 属 root，
需 sudo）。
