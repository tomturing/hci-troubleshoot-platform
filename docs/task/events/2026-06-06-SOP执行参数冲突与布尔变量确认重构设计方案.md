# SOP 执行参数冲突与布尔变量确认重构设计方案

本方案旨在从根本上解决排障平台 SOP 推进过程中的两项核心缺陷：
1. **工具执行冲突错误**：修复 ReAct 引擎在调用工具时，`SopToolExecutor.execute` 签名由于 `**kwargs` 参数解包重复传值导致的 `got multiple values for keyword argument 'conversation_id'` 异常。
2. **布尔变量输入与验证不可控（指标不治本的输入框）**：回滚后端的布尔值模糊文本强制归一化（Coercion）过渡方案，从源头上彻底规范用户输入。针对布尔类型等答案明确（可枚举）的变量，在变量池引擎层及前端展现层自动升级为 `user_confirm` 单选选项卡样式，屏蔽自由文本输入框，实现 100% 结构化精准提交。

---

## 1. 深度分析与第一性原理 (Root Cause & Paradigm Analysis)

### 1.1 CompositeToolExecutor 报错 got multiple values for keyword argument 'conversation_id'
- **问题现象**：在 ReAct 循环执行中报错 `CompositeToolExecutor.execute() got multiple values for keyword argument 'conversation_id'`。
- **问题本质**：
  - `ReactEngine` 内部在执行具体工具时，通过如下代码向 `active_executor` 发起调用：
    ```python
    result = await active_executor.execute(
        tool_name, tool_args, conversation_id=session_id, exec_id=exec_id
    )
    ```
  - 原 `SopToolExecutor.execute` 为了兼容不同工具，其签名设计为了 `async def execute(self, tool_name: str, args: dict[str, Any], **kwargs: Any) -> Any`。此时传入的 `conversation_id=session_id` 和 `exec_id=exec_id` 会被打包进 `kwargs`。
  - 在 `SopToolExecutor` 的内部实现中，对于非 SOP 导航类的常规诊断工具，会将其透传给默认的工具执行器：
    ```python
    return await self._default_executor.execute(
        tool_name, args, conversation_id=self._conversation_id, **kwargs
    )
    ```
  - **冲突发生点**：由于调用时既显式声明了 `conversation_id=self._conversation_id`，又解包了 `**kwargs`（而 `kwargs` 里已经包含由 `ReactEngine` 传入的 `conversation_id`），Python 解释器在解包 `kwargs` 并匹配函数实参时，发现 `conversation_id` 被提供了两次（一次是显式传值，一次是解包传值），从而抛出 `TypeError`。
- **治理方法**：
  - 必须在 `SopToolExecutor.execute` 的签名中显式捕获 `conversation_id`（通过 keyword-only 声明 `*, conversation_id: str | None = None`），避免其流入 `**kwargs`。
  - 在委派给 `_default_executor.execute` 时，进行变量合并 `effective_conversation_id = conversation_id or self._conversation_id`，然后统一通过 `conversation_id=effective_conversation_id` 显式下发，不再解包冲突的键。

### 1.2 为什么“后端文本归一化”治标不治本？
- **旧方案缺陷**：
  - 之前的改动为：前端仍然保留自由输入框（`variable_input`），后端变量提交路由与服务收到用户输入的文字（如“是”、“否”、“yes”、“对”）后，自行做 lower-case 匹配并翻译为 `"true"` / `"false"`。
  - **第一性原理反思**：既然变量在 schema 中已经明确是 `boolean` 类型（或者是其他有明确候选值范围的可枚举类型），让用户使用自由文本输入框本身就是有缺陷的交互设计（这引入了拼写错误、歧义文本、校验漏洞等不可控因素）。后端试图去穷举归一化所有人类的自然语言输入，将导致后端校验代码不断膨胀，却依然无法覆盖所有的输入边界情况。
- **高阶重构方案（源头规范）**：
  - **策略转换**：在 `sop_request_variable` 获取变量值时，如果发现该变量的 Schema `type == "boolean"`，即使其 `acquisition_strategy` 声明为 `user_input`，也应自动将其拦截并强制升轨为 `kind = "variable_confirm"`（单选确认卡片）。
  - **默认选项注入**：如果该变量未绑定自定义候选列表，则由变量池决策引擎自动注入布尔标准选项：
    - `Option 1`: `optionId = "true"`, `name = "是 (true)"`
    - `Option 2`: `optionId = "false"`, `name = "否 (false)"`
  - **纯按钮式交互（防错防呆）**：当把变量卡片标记为 `kind = "variable_confirm"` 且带有 `options` 选项时，后端应配置 `custom_input = False`。
  - **前端智能呈现**：
    - 前端 `MessageBubble.vue` 的 `variable_confirm` 卡片在检测到 `options` 列表长度大于 0 时，应自动隐藏分栏对比面板（隐藏“一键确认推荐值”与“修改或手动输入文本框”），直接呈现 `InteractiveOptions` 单选按钮组。
    - 前端 `InteractiveRequestCard.vue` 同样也会因 `custom_input = False` & `options` 存在而隐藏自由文本输入框。
  - **后端路由瘦身（彻底回滚）**：回滚 `conversation-service` 路由与服务中针对 boolean 的强制 Coercion 解析逻辑。因为当用户只能在界面上点击 `“是 (true)”` 或 `“否 (false)”` 按钮时，提交到后端的 `optionId` 将是严格的 `"true"` / `"false"`，后端无需做任何文本模糊猜测，直接原样存入变量库中即可。

## 3. 详细实现细节 (Implementation Details)

### 3.1 变量池引擎层布尔拦截 (`engine.py`)
在 `_request_user_input` 辅助函数中，针对 schema type 进行前置拦截：
```python
if var_schema.get("type") == "boolean":
    kind = "variable_confirm"
    if not options:
        options = [
            {"optionId": "true", "name": "是 (true)"},
            {"optionId": "false", "name": "否 (false)"},
        ]
```
同时修正 `strategy == "user_confirm"` 下的选项构造方式，将旧版的 `label`/`value` 键名归一化为符合前端 `<InteractiveOptions>` 组件所需的 `optionId`/`name`：
```python
options = [{"optionId": str(item), "name": str(item)} for item in candidates_result]
```

### 3.2 智能体层控制参数 (`react_engine.py`)
在创建 `AgentInteractiveRequest` 结构时，根据选项是否为空动态控制 `custom_input`：
```python
custom_input=not result.options,  # 当存在可点击选项时，关闭自由输入框
```

### 3.3 变量提交值解析修正 (`conversation_service.py`)
对于 `variable_confirm` 卡片在被点击单选按钮后，优先读取 `optionId` 作为要写入 DB 的真实值（例如 `"true"`），因为 `optionLabel` / `name`（如 `"是 (true)"`）属于面向用户的友好展示词：
```python
elif outcome.get("outcome") == "selected":
    value = outcome.get("optionId") or outcome.get("optionLabel")
```

### 3.4 前端呈现逻辑分叉 (`MessageBubble.vue`)
在 `MessageBubble.vue` 对应的 `Branch 2: variable_confirm` 模块中，插入选项模板支持：
```vue
<div v-if="!interactiveSubmitted">
  <!-- 如果有候选选项，展示选项按钮，不展示分栏对比与文本框 -->
  <div v-if="interactiveEvent.options?.length" class="ir-options-wrapper">
    <InteractiveOptions
      :options="interactiveEvent.options"
      :selected-option-id="selectedInteractiveOptionId"
      :force-disabled="interactiveSubmitted"
      :submitting="interactiveSubmitting"
      @select="handleInteractiveOption"
    />
  </div>
  <!-- 否则才展示常规的系统推荐值与微调输入框 -->
  <div v-else class="variable-split-panel">
    ...
  </div>
</div>
```

3. 运行 `uv run pytest backend/agent-service/tests/unit/test_skill_disk_lifetime.py` 验证变量池在无 Schema 定义时依然能够完好回滚/降级工作。

1. **启动测试环境** (`make dev-up`)
2. **步骤 1：创建 SOP 包含布尔变量的会话**
