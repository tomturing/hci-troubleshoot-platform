## 问题

同一个工单可以收集多次日志（换时间范围、换节点、换故障场景），5888 归档时会把
旧包改名加时间戳保留，新包占规范名，因此 `/sf/log/<工单号>/` 下可能有多份 zip。

旧实现（#1443 起）在同步侧按"**同一工单只取 mtime 最新的一份**"处理：

- `_parse_remote_archives` 每工单只保留一条；
- `resolve_archive_path` 拉取前也只取最新一份；
- 本地产物因此**只剩最后一次采集**的内容。

产品要求正好相反：设备上的 `/sf/tickets/<工单号>/` 必须是该工单**所有采集内容的
并集**——早先采集到的日志不能因为客户又采了一次就消失。

## 决策

### 合并规则

| 情形 | 处理 |
|---|---|
| 同一相对路径在多份包里都有 | **最新包赢**：mtime 大者；mtime 相同则规范名（`<工单号>.zip`）优先 |
| 路径只在一部分包里存在 | 全部保留 |
| 产物结构 | 每个路径只出现一次的"文件唯一"目录 |

"最新"的判据与自动巡检、换包重同步保持同一套：`mtime` 优先、同秒看规范名。
排序与比较必须同源（`fetcher.archive_sort_key` / `is_newer_archive`），否则
"谁算最新"会出现两个答案。

### 只拉增量，不重建

单包可达几十 GiB，"新增一次采集就把全部历史包重下"不可接受。做法：

1. 任务开始列**全部**归档，按 `.sync-meta.json` 的 `mergedArchives`（包身份
   `(mtime, size)`）算出未合并集合；
2. 已发布产物 → `build/` 做**硬链接克隆**（`merge.clone_tree`，不复制字节）；
3. 逐个拉取未合并包 → 各自解压到独立目录 → `merge_into(build)`（新包覆盖旧文件，
   旧包只补缺失）→ 删除该包的归档与解压目录；
4. `build/` 原子 `rename` 发布，旧产物进 `.trash`。

### 三个必须守住的实现约束

| 约束 | 原因 |
|---|---|
| 包身份是 `(mtime, size)` 而不是文件名 | 5888 重传时把旧规范名改名加戳且保留 mtime，按名字比会重拉同一份字节 |
| 克隆树与旧产物共享 inode，合并只准 `rename`/`unlink` 目录项 | 原地写文件内容会同时改坏 `.trash` 里待回退的旧产物 |
| 任一包失败即整单失败，且不发布 `build/` | 半套合并结果比"这次没同步"更糟：用户会以为日志齐了 |

### 升级兼容（不能重演 766 GiB 事故）

改造前的产物目录没有 `mergedArchives`，无法判断历史包是否已合并。默认策略：

- **自动任务**只合并"比 meta 里 `remoteMtime/remoteSize` 更新"的包，其余全部记入
  `baselineArchives`——升级首轮不会把存量工单的几百 GiB 历史包重拉一遍
  （2026-11-01 已因放宽扫描窗口一次性吃掉 766 GiB）；
- **手动 `POST /jobs`** 代表用户"我要全部内容"的判断，连 baseline 一起回填；
- 需要存量工单也自动补齐时显式打开 `TICKET_MERGE_BACKFILL_LEGACY=true`，
  盘量代价由运维在窗口期决策。

## 实现

| 文件 | 改动 |
|---|---|
| `tools/ticket-sync/app/merge.py`（新） | 包身份、pending 计算、硬链接克隆、按优先级合并、最终树统计 |
| `tools/ticket-sync/app/fetcher.py` | 拆出 `_parse_remote_archive_list`（全部归档）、新增 `list_ticket_archives`、`archive_sort_key`、`RemoteArchive.name`；`fetch` 支持 `target_name`，`list_remote_entries` 支持 `remote_path` |
| `tools/ticket-sync/app/main.py` | `_run` 改为"列全量 → 算 pending → 逐包拉取/解压/合并 → 发布"；逐包转储识别；`已是最新`快速收尾；解压前空间检查改为 fail-fast（原实现在解压前删归档"腾空间"，等于自毁输入） |
| `tools/ticket-sync/app/publisher.py` | 新增 `prepare_merge_workspace`：只保留 `archives/` 供续传 |
| `tools/ticket-sync/app/config.py` | 新增 `TICKET_MERGE_BACKFILL_LEGACY` |
| `tools/ticket-sync/deploy/ticket-sync.env.example` | 登记该开关 |

`.sync-meta.json` 新增/固定两个字段：

- `mergedArchives`：已合并进产物的包（`mtime` / `size` / `path`），是增量判据；
- `baselineArchives`：升级时有意跳过、可在手动同步时回填的历史包。

## 遗留与运维动作

1. staging/生产的 `hci-ticket-sync` 是"宠物"部署（不走 ArgoCD），需重跑
   `tools/ticket-sync/deploy/install-user.sh` 才会生效。
2. 存量工单（升级前已发布）默认不会被自动补齐历史包。需要"设备上必须有全部采集
   内容"的存量工单，按运维窗口逐单点「同步日志」，或临时打开
   `TICKET_MERGE_BACKFILL_LEGACY=true`。
3. 合并中间态不跨任务复用：重试会重新拉取"本次尚未发布成功"的包（已发布的包不会
   重拉），失败包的下载件保留在 `.tmp/<工单号>/archives/` 供 rsync 续传。
