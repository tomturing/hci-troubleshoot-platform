# 日志收集交付路径与补交付任务拆解

## 关联方案

[2026-10-27-日志收集交付路径与已采集包补交付](../../solution/events/2026-10-27-日志收集交付路径与已采集包补交付.md)

## 任务清单

### T1：创建任务落库交付路径（后端）

- **描述**：`LogCollectTaskCreate` 增加 `upload_mode`；`acli_direct` 强制 `remote_url`、`bridge_relay` 禁止 `remote_url`；未传时按 `remote_url` 推断；`create_task` 落库。
- **文件变更**：`backend/case-service/app/schemas/log_collect.py`、`app/services/log_collect_service.py`
- **验收标准**：三条校验分支各有一条单测；创建响应 `upload_mode` 立即可见
- **依赖**：无
- **状态**：已完成

### T2：补交付登记实际路径 + detail 合并写入（后端）

- **描述**：`begin_delivery` 落 `upload_mode='bridge_relay'`（补交付物理上只能 P2）；`update_task` 对 `detail` 改为合并（值为 `null` 时删键），供前端写降级审计而不丢基线指纹。
- **文件变更**：`app/services/log_collect_service.py`
- **验收标准**：单测覆盖"补交付后 upload_mode"与"detail 合并不覆盖 baseline_report_hash"
- **依赖**：T1
- **状态**：已完成

### T3：对账判定识别"平台已完成但未交付"（前端纯函数）

- **描述**：`SyncInput` 新增 `platformDelivered`；`completed` 分支拆成已交付 / 未交付有包 / 未交付无包三种结论。
- **文件变更**：`frontend/customer/src/services/logCollectSync.ts`
- **验收标准**：`logCollectSync.spec.ts` 新增 3 条用例
- **依赖**：无
- **状态**：已完成

### T4：补交付走 direct，不再改写采集状态（前端）

- **描述**：新增 `deliverExistingPackage()`（stat → `/deliver` → `delivery_submit(direct)` → `pollRelay` → PATCH completed）；`adoptNodeTask` 的 deliver 分支改调它；`runDeliveryJob` 支持 `mode` 入参；`runP2` 主流程仍用 `collect`。
- **文件变更**：`frontend/customer/src/components/LogCollectPanel.vue`、`src/utils/logCollectDelivery.ts`、`src/api/logCollect.ts`
- **验收标准**：组件用例断言 deliver 分支**没有** `create` / `progress` 请求，且 `delivery_submit` 的 `delivery_mode='direct'`
- **依赖**：T2、T3
- **状态**：已完成

### T5：创建任务带交付路径 + 结果态入口文案（前端）

- **描述**：`handleStart` 传 `upload_mode`；P1 失败降级 P2 时写 `detail` 审计；结果态「上传到平台」按钮与三种结论文案。
- **文件变更**：`LogCollectPanel.vue`、`api/logCollect.ts`
- **验收标准**：单测断言创建 payload 含 `upload_mode`；结果态文案与需求文档第五节一致
- **依赖**：T1、T4
- **状态**：已完成

### T6：bridge direct 回归护栏

- **描述**：补一条 Go 单测，断言 `Direct=true` 的作业不会进入 `waitCollect`（走 `prepareDirect`）。
- **文件变更**：`terminal_bridge/delivery_job_test.go`（或新增 `delivery_direct_test.go`）
- **验收标准**：`go test ./...` 通过；用例在把 `Direct` 分支改坏时会红
- **依赖**：无
- **状态**：已完成
