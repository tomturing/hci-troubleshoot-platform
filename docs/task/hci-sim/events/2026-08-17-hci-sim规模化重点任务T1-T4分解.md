# hci-sim 规模化重点任务 T1-T4 分解（供多 agent 协同）

> 来源：`docs/solution/hci-sim/events/2026-08-17-hci-sim环节细化与规模化构造及Bundle工厂双模式分析.md` 的结论转化。
> 排序依据：依赖顺序 × 价值密度。T1/T2 纯工程可立即启动；T3 组织级门控；T4 等 T1-T3 达成后收尾。
> 认领约定：各任务在本文勾选 `owner` 并在 PR 中引用本文；T1/T2 由本 agent 先行启动。

## T1 · Synthetic 批量编译管道自动化

| 属性 | 值 |
|---|---|
| 优先级 | P0（最快见效，无外部依赖） |
| 状态 | 已启动（本 agent） |
| 目标 | published KBD -> synthetic Bundle，零手工 JSON |

**为什么排第一**：C1 解析器（`backend/kb-service/app/services/hci_sim_resolver.py`）与 bootstrap 编译器（`hci_sim/internal/fixture/bootstrap.go:266-365`）已存在，缺的只是批处理编排层。KBD 供给增长（120 条未发布中任一条走完审核）可直接转化为环境覆盖率。

**任务拆解**：

- [ ] 批量编译入口：CLI 或脚本，输入 = 主库 published KBD 列表（`dynamic_resource_active` 快照）。
- [ ] 逐条调用 C1 resolution，收集 synthetic_routes 与 gap 码；gap 非空时明确跳过并输出报告（fail-closed，不得半编译）。
- [ ] 从 resolution 输出自动生成 manifest JSON（对齐 `deploy/helm/hci-sim/files/kbd-*-fixture-manifest.json` schema）。
- [ ] 本地 schema + 语义 lint（复用 fixture.Load 校验）。
- [ ] 产物落位 `deploy/helm/hci-sim/files/` 并自动更新 `values.yaml` 的 `fixture.manifestFiles` 与 `HCI_SIM_REQUIRED_BUNDLES` 声明。
- [ ] 输出编译报告：成功/跳过/gap 分布，供漏斗观测。

**验收**：对 dev 现有 6 条 published KBD 一键产出全部 synthetic manifest，`go test ./...` 与 CI 契约校验通过。

**边界**：不碰 realistic 轨道；不做发布自动化（Argo 仍人工触发）；单副本假设。

## T2 · Controlplane 生产化接线

| 属性 | 值 |
|---|---|
| 优先级 | P0（治理落地核心工程） |
| 状态 | 已启动（本 agent） |
| 目标 | 837 行参考内核（`hci_sim/internal/controlplane/`）从死代码变为生产路径 |

**为什么重要**：`main.go` 手写 handler + `simulationBuildable` 简化判定绕过了状态机、双角色审批、TestRun 全部治理语义。专家审核路径在接线前只是设计文档。

**任务拆解**：

- [ ] 修复 Atlas migration 目录重复版本历史债（`20260727000000` 双文件），恢复 versioned migration hash/lint 工作流。
- [ ] PostgreSQL BundleRepository：digest 唯一键、version CAS、审计写入。
- [ ] PostgreSQL ArtifactRepository：staged/scanned/approved/revoked 状态迁移 + `FOR UPDATE` 语义。
- [ ] stale outbox worker：`FOR UPDATE SKIP LOCKED` 领取、version CAS、pending/processing 超时 reconciliation。
- [ ] `main.go` 接线：以 controlplane Registry 替换/包装手写 handler，保留现有 API 兼容。
- [ ] Memory 实现降级为测试替身，生产 flag 强制 PG。

**验收**：bundle 状态机（draft->validated->approved->published->stale）与 artifact 四扫+双审在 PG 上有单测覆盖；现有 E2E 不回退。

**边界**：真实对象存储（OCI/S3/WORM）与 KMS 签名不在本任务（属 T3 前置基础设施）；不改双角色审批语义。

## T3 · 首条 realistic Bundle 冷启动（组织级门控）

| 属性 | 值 |
|---|---|
| 优先级 | P1（价值最高的证明，但治理先于工程） |
| 状态 | 待认领 |
| 目标 | 2 条 `ready_for_artifact_binding` KBD 完整走 采集->四扫->双审->编译 draft->审批->发布 一次 |

**阻塞项（非工程，需 Security/数据责任人决策）**：

- [ ] Artifact 采集范围、保留期、脱敏规则、许可证规则。
- [ ] 真实审批身份源（expert/security 角色的账号体系）。

**可并行推进（工程侧）**：

- [ ] staging 环境 OCI/S3/WORM 部署（不碰真实数据）。
- [ ] 生产级 DLP 扫描器选型与规则验证（用合成脏样本）。
- [ ] KMS 签名密钥方案。

**验收**：至少 1 条 realistic Bundle 进入 `published` 且 Runtime 可加载执行；全程审计可回放。

## T4 · 规模化验证（1000 KBD 量级）

| 属性 | 值 |
|---|---|
| 优先级 | P2（T1-T3 达成后） |
| 状态 | 待认领 |
| 目标 | 1000 已发布 KBD 的池加载与并发服务能力实证 |

**任务拆解**：

- [ ] ConfigMap 1MiB 上限实测：估算单 manifest 均值，确认 ~N KBD 后触顶；改 Volume 挂载或分片方案。
- [ ] 任一 Bundle 变更的全量滚动重启优化（分批/金丝雀）。
- [ ] 多副本 + 池分片（`HCI_SIM_REQUIRED_BUNDLES` 按副本子集声明）验证。
- [ ] Stale 引擎实战：KBD/Tool 依赖变更 -> outbox -> Bundle stale -> 重编译闭环。
- [ ] 100+ 并发 lease/build 压测与 20-repeat 稳定性补证（继承阶段 E 遗留）。

**验收**：容量报告 + 分片部署 runbook；P95 指标不随池规模线性劣化的证据。

## 依赖与协同关系

```text
KBD 供给(上游) ──> T1 批量synthetic ──> 环境覆盖正反馈
                        │
T2 controlplane接线 ────┤ (T1产物经T2治理发布; 可并行开发)
                        │
T3 realistic冷启动 ──> T4 规模化验证
(组织决策是关键路径, 越早发起越好)
```

## 双角色审批设计依据（为何不是单专家）

详见 `docs/solution/hci-sim/events/2026-08-17-hci-sim环节细化与规模化构造及Bundle工厂双模式分析.md` §2；核心四点：

1. 能力不对称：expert 审语义真实性，security 审数据安全性，一人难以兼具。
2. 扫描必要但不充分：四扫是启发式，security 角色是漏报的人工后盾。
3. 利益冲突隔离：双人规则使单个被攻陷/合谋 actor 无法注入恶意 fixture。
4. 成本不对称：Bundle 进 git+ConfigMap+对象存储，PII 泄漏不可撤回；双审成本仅每 artifact 一次点击。

注意：synthetic 轨道不含真实数据，**不需要** artifact 级双审（走代码评审即可）——双审成本被刻意只挂在携带真实数据的路径上。
