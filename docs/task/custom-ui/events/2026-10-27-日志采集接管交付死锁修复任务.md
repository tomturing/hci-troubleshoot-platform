# 日志采集「继续交付」接管死锁修复任务

## 关联方案

[2026-10-26-日志收集会话存活与保活修复.md](../../../solution/events/2026-10-26-日志收集会话存活与保活修复.md)

---

## 背景

工单 `Q2026102701294` 现场：节点侧 `acli log_collect` 已 100% 完成，压缩包 289 MiB 仍在节点磁盘上，平台任务却停在 `failed`。用户在面板上看到「继续交付」入口，点击后包始终交付不出去。

该工单前后经历了**两层**死锁，第一层已在 #1313（`bc19afb1`）修掉，第二层是本次修复对象。

---

## 第一层死锁：终态硬改被状态机拒绝（#1313 已修）

平台 `failed` 是终态，前端对账却试图直接 `PATCH status=completed`。后端状态机拒绝该边，返回 409；前端每 30 秒重试一次，20 分钟内刷了 16 次 409，包永远出不去。

正确做法不是「硬把终态改成完成」（平台确实没有产物记录，改成完成是说谎），而是承认节点真相，走唯一合法边 `failed → collecting`（接管），随后立刻按节点 `completed` 收尾并交付。

第一性原理拆解：此处需要的是**一条合法状态转移**，而不是**一个新的完成判定**。所以修复只做「换边」，判定逻辑保持单一来源。

---

## 第二层死锁：接管后报告已定格，被误判成旧报告

#1313 换边正确，但接管后的对账基线取错了：

```text
adoptNodeTask() 传入 baseline = readProgressHash()   ← 当前这份「已完成」报告的指纹
        ↓ PATCH failed → collecting
resumeTaskFlow → pollUntilCollected(baseline = 该指纹)
        ↓ 节点任务早已结束，报告不会再被重写
hashReport(raw) === baseline  →  reportRefreshed = false
        ↓
resolveOwnership 无条件判 stale
        ↓
decideNodeSync → wait_refresh（不退出、不落终态）
        ↓
720 次 × 5s = 60 分钟空转 → throw '采集未完成' → 再次 failed
```

根因不是阈值太严，而是**归属判定的前提被打破**：它的灵魂是「报告相对下发基线刷新过吗」，该判据成立的前提是任务还在跑、报告还会被重写。接管场景恰好让报告定格，于是 `reportRefreshed` 恒为 `false`，判据必然给出错误结论。

对抗性审查还发现测试为何没拦住：既有用例传的是 `reportRefreshed: true`（现实中接管时不可能成立的输入），于是逻辑再错也全绿。

## 修复内容

| 文件 | 改动 |
|---|---|
| `frontend/customer/src/services/logCollectSync.ts` | `SyncInput` 新增 `adoptedDeliver`；`decideNodeSync` 在归属判定之前短路：`adoptedDeliver && nodeState === 'completed'` 直接 `patch_completed` |
| `frontend/customer/src/components/LogCollectPanel.vue` | `pollUntilCollected` / `resumeTaskFlow` 增加 `adoptedDeliver` 透传；`adoptNodeTask` 在 deliver 模式传空基线并按 deliver 标记放行 |
| `frontend/customer/src/services/__tests__/logCollectSync.spec.ts` | 新增 3 条回归用例（接管必须收敛、未接管必须拦下、接管但节点在跑不得误判） |
| `frontend/customer/src/components/__tests__/LogCollectPanel.spec.ts` | 新增 1 条组件级接线用例（失败任务点「继续交付」后报告冻结也必须收敛为完成） |

设计取舍：

- **只对 `completed` 放行**，`running` / `abnormal` 仍走常规归属判定，避免把「接管」变成万能后门。
- **不引入 `archive_size > 0` 作为接管前置条件**。压缩包大小依赖 bridge 侧 `stat`，探测失败会留 0，用它当前置会把「包其实在盘」误判成「包已移除」，把可救的任务推去重采。宁可让接管后的交付流程自己去 `stat` 一次，快速失败也不长时空转。
- bridge 侧无需改动：`progress` 是每次实时执行 `acli log_collect progress` 读节点报告（`terminal_bridge/log_collect.go`），不依赖 bridge 内存，因此 bridge 重启不影响接管。

| 类型与构建 | `pnpm build`（`vue-tsc -b && vite build`）通过 |

## 未覆盖的风险

- 若压缩包已被 P1 直传插件自删，接管后交付会因 `stat` 失败而快速失败并提示重采，不会静默空转；这是刻意选择的失败形态。
- 本修复只影响前端接管链路，未改变后端状态机，`failed → collecting` 仍是唯一合法恢复边。
