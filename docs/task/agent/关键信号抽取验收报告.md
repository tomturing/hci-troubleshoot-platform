## 二、QKV/QFK 输入/输出配置能力验证

### 2.1 核心认知纠正

> **QKV/QFK 就是跟 acli/sop/scp 一样的 tool**，只是定位不同。
> 
> 关键差异在于它们需要支持**可配置的输入**和**可配置的输出**：
> - **可配置输入**：让 agent 知道传入什么参数
> - **可配置输出**：自定义解析哪些结果存到变量池

### 2.2 QKV 输入配置验证

| 参数 | 配置方式 | 示例 | 验证结果 |
|------|---------|------|---------|
| `keyword` | acquirer_args.keyword | "虚拟机镜像忙" | ✅ |
| `is_failed` | acquirer_args.is_failed | true | ✅ |
| `limit` | acquirer_args.limit | 20 | ✅ |
| `query` | acquirer 类型推断 | qkv.task → FrontendQueryType.TASK | ✅ |

### 2.3 QKV 输出配置验证（produces 动态提取）

| 案例 | produces 配置 | 提取结果 | 验证结果 |
|------|--------------|---------|---------|
| 27123 | [{name:VMID, path:vm\|object_id}, {name:HOST, path:host\|hostname}] | {'vmid': '7436939093432', 'host': 'host-005056b234ca'} | ✅ |
| 40750 | [{name:HOST, path:host}, {name:DISK_SN, path:target}] | {'host': 'host-192.168.1.10', 'disk_sn': 'WDXYZ1234567'} | ✅ |

**关键特性**：
- 支持**多路径容错**：`path: "vm|object_id"` 会依次尝试 `vm`、`object_id`
- 提取后的 dict key 是 `name.lower()`（如 `vmid`），变量池按 `name` 大写存储（如 `VMID`）

### 2.6 变量池传递验证

```
QKV 生产者 (s1)                    变量池                     QFK 消费者 (s2)
┌─────────────────┐            ┌───────────┐            ┌─────────────────┐
│ produces:       │            │ VMID: ... │            │ requires:       │
│   VMID←vm       │ ────────▶ │ HOST: ... │ ────────▶ │   VMID, HOST    │
│   HOST←hostname │            └───────────┘            │ sub_command:    │
└─────────────────┘                                     │   lsof | grep   │
                                                       │   {{VMID}}      │
                                                       └─────────────────┘
```

- 案例 27123：s1(producer) 产出 VMID/HOST → s2(consumer) 消费 → s3 消费 PID（由 s2 产出）
- 案例 40750：s1(producer) 产出 HOST/DISK_SN → s2/s3(consumer) 消费

## 六、总结

1. **新代码完全可用**：BackendSignal/FrontendSignal 模型构造成功，namespace 路由正确，HandlerRegistry 分发无误。

2. **命令构建正确**：所有测试场景的 acli 命令都能正确生成，包括 `system` namespace 的 lsof/ps/smartctl/lsblk 等子命令。

3. **produces 动态提取有效**：QKV parser 能按 produces 规格动态提取字段，硬编码兜底逻辑保留。

4. **覆盖率提升方向**：
   - 需要补充 `qfk.service`、`qfk.vm`、`qfk.network`、`qfk.storage` 等场景的案例
   - 需要验证 `regex`、`threshold`、`json_path`、`state`、`exists` matcher 类型

5. **架构改进效果**：
   - 去掉 `BackendSignalType` 枚举后，namespace 字符串路由更直观
   - `sub_command` 字段支持任意 acli 子命令，扩展性更强
   - `produces` 动态提取让 QKV 输出更灵活
