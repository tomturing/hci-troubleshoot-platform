# 2026-11-23 日志采集四项遗留关闭决策

## 结论

失败工单误标修复（2026-11-20）留下的四项「刻意未做」，逐条复核后全部收口：
一项部分落地，一项改向后落地，两项关闭。

| # | 原始诉求 | 决策 | 落地位置 |
|---|---|---|---|
| 1a | `stat` 不依赖节点命令 | **关闭**（已两级兜底，不再值 SFTP） | 现状即 `remote.ProbeArchive` |
| 1b | `exit=127` 单列 | **已落地** | PR #1628，`LC-ENV-009` |
| 2 | 会话断连置 `queued` | **改向后落地** | PR #1628，`progress_stalled` |
| 3 | `acli capabilities` 预检 | **关闭**（已在跑，剩下一层刻意不做） | 现状即 `LogCollectPanel.vue` 证据预检 |
| 4 | 5888 手工上传回流 | **关闭**（与伪证据防线冲突） | 现状即派生层禁止翻正 |

「关闭」不是「不做」，而是**有明确理由的不做**，理由和重启条件都写在下面。没有任何一条
应该在没有新证据时被重新打开。

## 1a. `stat` 不依赖节点命令：关闭

**原始诉求**：节点 shell 被裁剪到连 `stat` 都没有时，探测会失败，需要一条不依赖节点命令的路径。

**现状**（`terminal_bridge/internal/shared/remote/archive.go`）：

- 已是两级探测：`stat -c %s` 并发 `ls -l`，任一成功即可出结论；
- 三态结论：存在 / 明确不存在 / 无法确认。只有拿到 `no such file` 这类明确证据才判「不存在」；
- 126/127 优先判「命令不可用」，不会被 `cannot stat` 之类文本误判成「文件没了」。

**决策**：不再增加 SFTP 直读。

**理由**：第一性原理上，「不依赖节点命令」的唯一替代是 SFTP 子系统，而 SFTP 本身也可能被
禁（sshd 配置 `Subsystem sftp` 关掉、chroot 限制），把它作为首选会引入**第二个不确定源**；
并且两级 shell 都失败时结论落在「无法确认」，已经是安全侧——用户看到的是「测不准」，
而不是「包没了」。收益是极少数受限节点，成本是一条新的连接路径和新的失败模式。

**重启条件**：出现实测工单，节点 `stat` 与 `ls` 都不可用**且** SFTP 可用；或受限 shell 成为
多数客户的默认形态。

## 1b. `exit=127` 单列：已落地（PR #1628）

**原始诉求**：127 不能被混进「无法确认」的一团糊里，要有独立的码和动作。

**现状**：语义早已区分（126/127 判「命令不可用」），但上报码仍是 `LC-TRANSFER-006`
（通道异常），文案是「节点命令不可用或通道异常」——客户既不知道该重连还是该改节点。

**落地**：`ArchiveProbe.Unavailable` + `commandMissing()`，两级都缺命令时上报 `LC-ENV-009`
「节点缺少文件探测命令」，客户动作改为「恢复命令 / 放开白名单」。

**对抗性审查拦下的坑**：既有 `ArchiveProbeToolMissingRe` 含 `permission denied`。直接复用会
让权限拒绝也落到「缺命令」，客户被引去放开白名单，而真正要改的是目录权限。新判定刻意
不含权限，权限拒绝仍走 `LC-TRANSFER-006` 并在 diag 里保留 `Permission denied` 原文。

**重启条件**：若权限拒绝成为高频码，再为它单列一个码（动作是改权限），不要并入 `LC-ENV-009`。

## 2. 会话断连置 `queued`：改向后落地（PR #1628）

**原始诉求**：会话断开时，把采集中任务放回 `queued`，重连后继续。

**现状**：任务 `status` 枚举里没有 `queued`（`queued` 只存在于 `delivery_status`）；
状态机是 `collecting → {packaging, uploading, completed, failed, cancelled}`，没有回退边；
全仓也没有任何定时清理（scheduler 不碰 log_collect）。

**为什么原方向是错的**：回到 `queued` 会重新触发下发 `create`，而节点上的插件可能已经采了
一半——重下发就是**重复采集**，共用同一产物目录会互相踩，正是 Q2026111900421 的成因。
另外「置回队列」隐含「重连后能续」，但采集进度并不在平台侧，续不了。

**改向后做了什么**：不造状态，只回答「还该不该等」。`is_progress_stalled` 仅对
`status=collecting`、20 分钟无更新时提示「进度长时间未变化」。用户看到的是可判断的信号，
而不是一个假装可续的队列状态。

**为什么只认 collecting**：`probing/installing/packaging/uploading` 都有合法长静默（装 acli、
打十几 GB 的包、分片排队）。用同一阈值会把正常长任务报成中断，用户据此重采，反而制造产物。

**重启条件**：若真需要「断点续采」，那是 acli 侧的能力（包复用/断点），必须在 S4 决策门
（第二个 >10MB 且需 `retryStage` 的消费者）成立后再谈，不要用任务状态糊过去。

## 3. `acli capabilities` 预检：关闭

**原始诉求**：建任务前先发 `capabilities`，确认桥支持 `script_files`，避免旧桥静默忽略。

**现状**：

- 前端**已经在调** `capabilities`（`frontend/customer/src/components/LogCollectPanel.vue`），
  用 `log_collect_evidence` 做 fail-closed：探测失败就认为不支持新行为。这是真正在跑的门禁；
- `platform_scripts` 这一层刻意不做，理由写在 `terminal_bridge/internal/logcollect/log_collect.go`：
  旧桥会静默忽略未知字段，先探测要多一次往返，还会把「探测本身失败」变成**第二个静默分支**；
- 节点侧的插件完整性已由 #1617 的 `log_collect_preflight.go` 逐台校验（缺文件直接拒绝，
  给 `LC-INSTALL-010`），比「问桥你支持什么」更强。

**决策**：不增加 `platform_scripts` 门禁。

**重启条件**：出现「旧桥静默忽略字段导致数据错误」的实测工单；或桥版本探活机制统一到
capabilities 之外的单一路径时，再考虑合并门禁。

## 4. 5888 手工上传回流：关闭

**原始诉求**：手工上传到日志服务器的包，回流到采集任务，补上交付状态。

**现状**：`conversation-service` 已给手工上传打 `source=manual_upload`；派生层明确
「交付未登记（含手工上传）按失败处理，禁止翻正」（`backend/case-service/app/domain/log_collect_display.py`）。

**决策**：不回流，只保留来源标注。

**理由**：手工上传无法证明「这个包来自本次采集」。一旦回流成「已交付」，平台就会替一个
未经采样的包背书，直接重演 Q2026111900236 那类伪证据误判——而那道防线正是这次修复的
核心产出。回流看起来是补齐状态，实际是拆掉「交付必须有登记」的因果。

**重启条件**：手工上传时能同时提供可校验的采集标识（任务 ID + 节点侧摘要），使得「这个包
确实来自该任务」可被证明。只有那时才谈回流。

## 维护约定

- 新增「遗留项」时，必须写清**重启条件**，否则它会以「技术债」的形式无限续命；
- 关闭项被重新提起时，先核对本文的重启条件是否成立，再决定是否开工，不要凭「感觉该做」；
- 状态机不应为了「看起来能续」新增回退边；需要可续就该在真正的进度持有方（节点/acli）实现。
