# 2026-11-24 日志采集长尾观察窗口误判设计

## 背景

2026-11-24 工单 `Q2026112400468` 暴露了一个平台侧误判：

- 节点 8/8 台已完成采集，进度 85%，`upload_state=发送中`，`exit_code=0`；
- 包已在节点上，大小为 `10,592,819,584` 字节；
- 前端主流程在第 720 次 `log_collect.progress` 轮询后耗尽，抛出「采集未完成」；
- 前端 PATCH `status=failed / error_message=采集未完成`；
- case-service 按文案规则派生 `LC-PLUGIN-010`；
- 节点实际继续上传，14:15 才变为 `upload_state=成功 / node_state=completed`，任务最终 `completed`、`delivery_status=delivered`，归档件已核验。

根因不是插件失败，也不是 SSH 超时，而是**前端把“观察时长”当成“业务失败”**。`pollUntilCollected` 的 `720` 次上限按 `5s × 720 = 1h` 注释，但每次 `sendAndWait` 约 1s，实际约 72 分钟；大包 P1 直传长尾超过该窗口时，必然误写失败。

## 目标

1. 只要节点仍报告 `node_state=running`，前端不得因自身观察窗口耗尽写 `failed`。
2. 观察窗口耗尽只触发“主流程交接给后台对账”，不改变平台业务终态。
3. 不新增后端契约码，不改状态机，不要求 bridge/exe 更新。
4. 可观测：能事后从任务 `detail` 回答“何时、为什么从主流程交接”，包含节点态、上传态、进度、包大小。
5. 覆盖回归测试，防止以后又把观察预算改回“次数上限 + 写 failed”。

## 非目标

- 不新增 `LC-PLATFORM-*` 超时码。
- 不新增数据库状态枚举或迁移。
- 不改 `terminal_bridge`、acli、5888 日志服务器。
- 不自动重新采集、不自动取消节点任务。
- 不修改已终态任务（尤其不把 `failed` 自动改成 `completed`）。

## 核心不变量

> 观察窗口是**前端资源守卫**，不是**业务结论**。

节点是采集事实的唯一真相源。平台只有在以下情况才允许写 `failed`：

- 节点明确 `node_state=abnormal`；
- 节点 `node_state=none` 且已超过接单宽限；
- bridge 明确返回业务错误；
- 交付结论有确定性否定证据。

“前端看了很久还没看到 completed”不在上述列表内，只能进入“结果未决/继续观察”。

## 方案

### 1. 纯判定层：阶段化观察预算

在 `frontend/customer/src/services/logCollectSync.ts` 增加：

- `COLLECT_OBSERVE_BUDGET_MS = 60 * 60 * 1000`
  - 从主流程开始到首次出现 `upload_state=uploading` 之前；
- `UPLOAD_OBSERVE_BUDGET_MS = 120 * 60 * 1000`
  - 从首次出现 `upload_state=uploading` 起算；
- `ObservationPhase = 'collect' | 'upload'`
- `decideObservationWindow({ elapsedMs, phase }): 'continue' | 'handoff'`

预算只回答“主流程是否继续占用”，不回答“任务是否失败”。纯函数便于穷举边界。

### 2. 组件层：专用错误，不落终态

`LogCollectPanel.vue` 的 `pollUntilCollected`：

- 记录 `startedAt`；
- 首次看到 `classifyUploadState(snapshot.upload_state) === 'uploading'` 时记录 `uploadStartedAt`；
- 每轮按墙钟计算 `elapsedMs`，调用 `decideObservationWindow`；
- 达到预算且节点仍 `running` 时抛出 `CollectionObservationWindowError`，携带：
  - `elapsedMs`
  - `phase`
  - 当前 `ProgressSnapshot`
- 不再使用 `for (attempt < 720)` 作为终态判据；保留一个足够大的安全次数只用于防止死循环。

主流程 `catch` 中**先于** `isOutcomeUnknownError` 处理该错误：

- 不调用 `patchTask({ status: 'failed' })`；
- 不设置 `stage='failed'`，保持 `collecting` 或 `uploading`；
- 清空 `errorMessage`，设置 `nodeSyncHint`：
  - 采集阶段：“已连续观察 60 分钟，节点仍在采集；平台保持采集中，后台继续对账，完成后自动更新”
  - 上传阶段：“已连续观察 120 分钟，节点仍在发送；平台保持采集中，后台继续对账，完成后自动更新”
- 设置 `longTailObservation=true`；
- `finally` 的 `resumeAutoSync` 在该标记下使用 30 秒间隔，避免 5 秒一次 SSH 长尾空转；
- 新建任务、取消、重新收集、接管完成时复位标记。

### 3. 后台对账

主流程退出后，现有自动对账继续运行：

- 平台状态仍为 `collecting`；
- 节点 `running` → `decideNodeSync` 返回 `none`，不写终态；
- 节点变 `completed` → `patch_completed`，走原有完成/交付流程；
- 节点变 `abnormal` → `patch_failed`，仍按原有错误归因。

不新增轮询通道，不改变现有状态机单调性。

### 4. 可观测性

前端输出结构化日志：

```text
[log-collect] observation-window-handoff
task_id / trace_id / phase / elapsed_ms / node_state / upload_state / percent / archive_size
```

同时使用现有 `PATCH /api/log-collect/tasks/{id}` 的 `detail` 合并能力写入：

```json
{
  "observation_handoff": {
    "at": "2026-11-24T...Z",
    "phase": "upload",
    "elapsed_ms": 7200000,
    "node_state": "running",
    "upload_state": "发送中",
    "percent": 85,
    "archive_size": 10592819584,
    "trace_id": "lc-..."
  }
}
```

不新增后端端点、不新增指标字段；后续可按 `detail.observation_handoff` 做查询与统计。

### 5. 方案比较

| 方案 | 做法 | 结论 |
|---|---|---|
| A 只调大 720 次 | 改 2000 次或 2 小时 | 否决：只是推迟误杀，语义仍是“观察超时=失败” |
| B 观察窗口交接 | 到预算后不写 failed，保持采集中，交后台对账 | 采用：不动契约/状态机，从根上消除误判 |
| C 全链路超时码 | 新增契约码 + 状态语义 + 迁移 + 三端发布 | 暂不采用：成本远大于当前问题；需要跨工单统计时再评估 |

## 对抗性审查

1. **节点真的异常但一直 running？** 仍按现有 `node_state=abnormal` 触发 failed；观察窗口不覆盖真实异常。
2. **节点假死、永不变 completed？** 主流程交接后后台对账继续；不新增永久写库，页面仍可由用户取消/接管。
3. **页面重开/接管任务？** 预算从本次 `pollUntilCollected` 起点计算，不依赖历史时间；已终态任务不经过该路径。
4. **并发自动对账抢写？** 交接不写状态，只写 `detail`；自动对账仍走原有 `syncPatchBlocked`/单写者约束。
5. **状态机单调性？** 交接不改 status；只有节点 completed/abnormal 等原有路径才改终态。
6. **错误码误派生？** 不再产生「采集未完成」文案，因此不会命中 `LC-PLUGIN-010`。
7. **detail 写失败？** 审计是旁路，写失败不能反噬主流程；仅记录前端日志。
8. **长尾空转？** 交接后 30 秒对账，不保持 5 秒 SSH 轮询。

- 采集阶段 61 分钟 → `handoff`；
- 上传阶段 119 分钟 → `continue`；
- 上传阶段 121 分钟 → `handoff`；
- 720 次轮询后节点仍 running → 不写 failed、不产生 `采集未完成`。

### 人工验收

- 模拟长上传：节点保持 `running/发送中` 超过预算，页面不出现失败红条，出现长尾提示；

- 数据库任务保持 `collecting`，完成后 `completed`，不出现 `LC-PLUGIN-010`；
- 页面刷新/重开后仍能继续对账。

## 风险与回滚

- 风险：长尾提示可能让用户误以为“卡住”。缓解：文案明确“节点仍在发送，后台继续对账”，并提供刷新入口。
- 风险：交接后自动对账间隔 30 秒，完成感知比 5 秒慢。缓解：这是长尾模式，用户可手动刷新。
- 回滚：删除 `CollectionObservationWindowError` 分支，恢复原有轮询上限即可；不改数据库，无迁移回滚。
