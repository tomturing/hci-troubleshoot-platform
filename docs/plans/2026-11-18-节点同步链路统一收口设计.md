# 节点同步链路统一收口设计（2026-11-18，v2.0）

> **当前版本：v2.0**。核心原则：**用数据驱动的 reconcile 骨架消除四条链路的代码重复，
> 用构造性不变量消除安全隐患，用从简到复杂的消费者顺序控制落地风险。**
>
> v2.0 定稿要点：
> ① **插件链路收口为 acli_sync 的第二阶段**——浏览器触发 → 桥探测 + 执行，
> 阶段一（acli 工具同步）跑完后立即跑阶段二（插件差量同步），两阶段共用同一套骨架；
> ② **admin-ui 只保留插件规格维护**（类比日志收集「默认场景/自定义场景」编辑），
> relay 推送链路与「保存并下发」入口由 D1 阶段直接彻底删除；
> ③ 运行时语义对齐用户旅程：连接后总是走 acli_sync（桥凭版本比对自决跳过），
> spc/config 仍按日志收集任务触发；
> ④ 缺陷编号改用 B 前缀，与工程阶段编号（S0-S4/D1/P-1）彻底分离。

### 1.3 设计目标

1. **消灭双语言重复**：五组原语（写文件、探测、校验、传输、转义）各写一份 Go 实现，Python 旧插件脚本随 D1 删除
2. **新增链路不改骨架**：将来加新链路只需加一个 descriptor + Provider，不动编排
3. **安全不变量结构化**：回滚前提、扇出 written-set、主机键互斥从"记住别犯"变成"写不出来"
4. **P0 当天止血**：不等重构完成，先用最小改动消除数据破坏风险
5. **工具与插件同触发同骨架**：acli_sync 两阶段串行，插件差量收敛复用同一套 reconcile 逻辑

## 二、核心抽象

### 2.1 总体结构：两轴分离

```
terminal_bridge/internal/shared/
├── remote/                  # 横向原语·节点面（所有链路共享，反向链路也可 import）
│   ├── runner.go            # Runner 接口缝（端口定义，零逻辑）
│   ├── fs.go                # WriteFile: tmp+校验+mv+退出码 20-23
│   ├── probe.go             # 远端探测：exist/version/size/digest
│   ├── transfer.go          # Pull 断点+pace（合并 delivery×2, transfer×2；Push 归 uplink）
│   ├── exec.go              # Runner 消费层：远端命令执行、分片逐条 exit_code、超时
│   ├── marker.go            # 唯一设备标记协议；过渡期双协议适配
│   └── quote.go             # shellQuote 唯一实现（收口转义）
│
└── reconcile/               # 纵向骨架（reconcile 编排）
    ├── descriptor.go        # DesiredState + 声明式 Install/Smoke/Files
    ├── provider.go          # 期望值来源：LatestProbe / InlineMessage / PluginManifest
    ├── plan.go              # Compare → Install/Skip/BlockedDowngrade（差量三态）
    ├── activate.go          # 三钩子：OnFailRollback / OnSuccessRestore / KeepBackup
    ├── fanout.go            # 集合性写入/探测：BatchMode 逐台、written-set、只回滚已写入
    ├── guard.go             # 主机键互斥 + 租约 fencing + exec_id 入分片路径
    ├── state.go             # 节点事实（探测）vs 桥侧账本（持久化基线）
    ├── receipt.go           # Result{Status, Stage, ErrorCode, Retryable, Evidence[]}
    └── kinds/               # 消费者：acli（两阶段）/ spc / config
```

> **包名说明**：纵向骨架包名定为 `reconcile` 而非 `sync`——后者遮蔽标准库
> `sync`，包内 `sync.Mutex` 会变成自引用，所有 stdlib 同步原语都得别名，徒增摩擦。
> 公共模块统一落位 `internal/shared/` 下，对齐 backend/shared 仓库惯例（架构重构设计 §3.4）。

**关键约束**：

1. `reconcile/` 只能 import `remote/`，不能反向
2. `remote/` 不引入任何期望值语义——它只知道"把字节写过去"、"探测文件存不存在"
3. 反向链路（delivery、日志直传）只 import `remote/transfer` 和 `remote/exec`，不进 `reconcile/`
4. **`remote/` 与 `reconcile/` 都禁止 import `main` 包**（main 调用它们，反向 import 即循环依赖）。
   为此 `remote/runner.go` 定义最小接口缝，main 包的 `SSHSession` 提供适配器：

```go
// remote/runner.go —— 接口缝：remote/ 不认识 SSHSession，只认识 Runner。
type Runner interface {
    // RunQuickCommand 与 main 包 SSHSession.runQuickCommand 同签名。
    RunQuickCommand(ctx context.Context, command string) (stdout string, exitCode int, err error)
    // WriteStdin 向远端命令的 stdin 流式写入（cat > tmp 的字节通道）。
    WriteStdin(ctx context.Context, command string, r io.Reader) (stdout string, exitCode int, err error)
}
```

> 现有 `SSHSession.runQuickCommand` 签名即 `(ctx, cmd) → (string, int, error)`，
> 适配是零成本包装；`WriteStdin` 对应 acli 上传现有的 stdin 流式通道。
> **这是 S1 的第一天工作**：不先立接口缝，`WriteFile(ctx, s SSHSession, ...)`
> 这种签名在 Go 里编译不过。

### 2.2 Descriptor：数据驱动的差异建模

```go
// descriptor.go

// DesiredState 描述"某条链路在某台节点上应该达成什么状态"。
// 新增链路只需新增一个 DesiredState 值，不改骨架。
type DesiredState struct {
    Kind      string            // "acli_binary" | "spc_slot" | "config_file" | "plugin_bundle"
    NodeIP    string
    Files     []FileSpec        // 要写入的文件清单
    Install   InstallSpec       // 安装动作（声明式，不是命令字符串）
    Smoke     SmokeSpec         // 冒烟测试（声明式）
    Policy    ReconcilePolicy   // 失败/成功后的行为
    Version   VersionSpec       // 版本比对（插件差量三态）
    Metadata  map[string]string // 链路特有的透传字段
}
```

#### 补丁 1：Install/Smoke 必须声明式

**不能**将安装命令作为字符串放进 descriptor。理由：

1. `shellQuote` 收口目标要求所有命令渲染在 Go 侧完成
2. 命令注入面不能从 Go（受控）转移到 Python（拼接字符串）
3. acli_sync 的安装命令是硬编码常量、spc 的脚本是 Go 拼接、旧插件的是 Python 拼接——都不能直接搬进 descriptor

```go
// InstallSpec 声明"要达成什么"，reconcile/ 内部负责渲染成安全的 shell 命令。
type InstallSpec struct {
    Kind  string   // "acli_install" | "register_plugin" | "chmod_exec" | "none"
    Args  []string // 结构化参数，reconcile/ 内部转义与拼装
}

// SmokeSpec 声明"怎样证明成功"，不是"跑哪条 shell"。
type SmokeSpec struct {
    Kind  string   // "version_match" | "stdout_contains" | "sha256" | "none"
    Args  []string
}
```

#### 补丁 2：Files 引用化，大文件不走 WS JSON

插件包实测 20~31MB，走 WS JSON base64 会膨胀 33%，直接撞上已有的 10MB body 限制。

```go
// FileSpec 描述要写到节点上的一个文件。
// 大文件走传输原语（断点、分片、pace），descriptor 只带引用。
type FileSpec struct {
    Path   string   // 节点上的目标路径
    SHA256 string   // 期望摘要
    Size   int64    // 期望大小
    Mode   string   // 权限位，如 "0755"
    Source Source    // 内容来源
}

// Source 区分三种来源，避免把 20MB 的包序列化进 JSON。
type Source struct {
    Kind   string   // "package" | "inline" | "remote"
    URL    string   // Kind=package 时：下载地址（acli=官方源固定地址；plugin=平台票据下载端点）
    Offset int64    // Kind=package 时：断点偏移
    Data   []byte   // Kind=inline 时：小配置（<64KB）直接带
    Path   string   // Kind=remote 时：节点上已有的路径
}
```

#### 补丁 3：Reconcile Policy 三钩子

spc 的"终态还原"与插件的"失败回滚"是两件事。混在一个 policy 里必然出现"成功也回滚"或"失败不还原"。

```go
type ReconcilePolicy struct {
    OnFailRollback   RollbackSpec  // 任一步骤失败时的回滚动作
    OnSuccessRestore RestoreSpec   // 全部成功后的还原（spc 独有）
    KeepBackup       bool          // 成功后是否保留备份（插件保留 .old.$SYNC_ID）
}

type RollbackSpec struct {
    Strategy string // "restore_backup" | "unregister" | "none"
    // 实现约束：只接受"已登记写入集"的条目，未登记则跳过。
    // 这让 rollback() 里 rm -rf 在结构上不可能再出现（B1）。
}

type RestoreSpec struct {
    Strategy string // "restore_original" | "none"
    WaitFor  string // "task_terminal" | "immediate"
}
```

#### 补丁 4：inline 总量阈值与自动降级

补丁 2 只解决了"单个大文件"，没解决"多个 inline 文件累加"：一个 8 个文件、每份 2MB 的插件
仍然会拼出 16MB 的 WS 消息，被 `CLIENT_MAX_CMD_BYTES`（10MB）拦在桥门口。

规则写死在 `reconcile` 内部，**不依赖调用方自觉**：

| 条件 | 行为 |
|---|---|
| 单文件 `Source.Data` > 256KB | 自动改写为 `Source{Kind:"package"}`，走传输原语分片上传，`Data` 置空 |
| 同一次 descriptor 的 inline 总量 > 1MB | 同上，按 `Path` 逐个大文件降级，直到总量达标 |
| 降级后仍 > 10MB | 直接返回 `receipt{code:"descriptor_too_large"}`，不尝试发送（避免桥侧无回执超时） |

降级必须写进 `Evidence`（`inline_downgraded=2`），否则"为什么走了慢路径"无从解释。

#### 补丁 5：`Metadata` 只能是展示/trace，不得影响执行

约束：
1. `Metadata` 的 key 必须在 `descriptor.go` 的常量表里登记（`mdKeySPCSlot` 等），禁止裸字符串；
2. **`reconcile/` 内除 `receipt`/日志外，禁止读取 `Metadata` 做流程分支**；
3. CI 加静态检查：`reconcile/` 中出现 `Metadata[` 的读取点，必须在本文件的允许清单内。

真正需要新语义时，扩 `descriptor` 的强类型字段（宁可加一个 `Slot`/`RegisterEntry`），
而不是塞进 `Metadata`。

#### 2.4.1 activate.go — 构造性回滚不变量

```go
// activate.go

// Activator 管理"安装→验证→回滚/还原"的三阶段生命周期。
//
// 核心不变量：删除操作以备份存在 ∨ .old.$SYNC_ID 存在为前提。
// 违反此前提的调用会返回 error，而不是执行删除。
// 这让 "无备份即 rm -rf" 在结构上不可能发生（B1）。
type Activator struct {
    // writtenSet 登记本次实际写入的条目，文件与目录树均可登记。
    // 插件回滚是目录树粒度（rm -rf "$BASE/$NAME"），只登记文件会漏掉它。
    writtenSet map[string]WriteEntry
}

type WriteEntry struct {
    Path       string
    IsDirTree  bool   // true 时按目录树整体回滚
    BackupPath string // 任务/部署隔离的备份名，由调用方按 kind 给定：
                      //   spc:    <path>.platform.<taskID>.bak
                      //   plugin: $TMP/backup/<name> 与 <path>.old.<syncID>
                      // 禁止固定 .bak 后缀——spc 硬要求任务隔离，
                      // 固定名会让两次采集互相覆盖原件（log_collect_spc.go L101）。
}

// Rollback 只回滚 writtenSet 中登记过的条目。
// 未登记的条目即使传了路径也不会被删除。
func (a *Activator) Rollback(ctx context.Context, r remote.Runner, entries []WriteEntry) error {
    for _, e := range entries {
        if _, ok := a.writtenSet[e.Path]; !ok {
            continue // 未写入的不动
        }
        if e.BackupPath == "" {
            return fmt.Errorf("回滚前提不满足：%s 未登记备份，拒绝删除", e.Path)
        }
        // 探测备份存在（remote/probe）→ 存在才恢复；不存在则报错而非删除。
        // ...
    }
    return nil
}
```

## 三、reconcile 编排流程

每条链路的执行都遵循同一个流水线：

```
Provider.Desired()
    │
    ▼
state.Load()  ──→  plan.Compare(expected, actual)
                        │
                        ├── Skip（已是最新 / 无修改）
                        ├── BlockedDowngrade（版本回退，拒绝）
                        └── Install（新增 / 有修改）
                              │
                              ▼
                        guard.Acquire(hostKey)
                              │
                              ▼
                        fanout.WriteAll(files)   ← remote/fs.WriteFile
                              │
                              ▼
                        activate.Install(spec)   ← remote/exec.Run
                              │
                    ┌─────────┴──────────┐
                    │                    │
                 成功                  失败
                    │                    │
                    ▼                    ▼
         activate.Smoke(spec)    activate.Rollback(writtenSet)
                    │                    │
                    ▼                    ▼
         state.Save(result)      receipt.Error(stage, code)
                    │
                    ▼
         policy.OnSuccessRestore?  ── immediate → 流水线内还原
                    │                 task_terminal → 登记持久还原意图（见 §3.2）
                    ▼
         receipt.OK(evidence)
```

### 3.1 四条链路在流水线上的差异（全部由 descriptor 字段表达）

| 维度 | acli_sync 阶段一 | spc | config | plugin（acli_sync 阶段二） |
|------|-----------|-----|--------|--------------|
| Provider | LatestProbe | InlineMessage | InlineMessage | **PluginManifest**（票据拉平台 manifest） |
| Files.Source | package (官方源固定地址 HTTP 下载) | inline (<6.5KB) | inline (<256KB) | package (平台票据下载端点引用+sha256) |
| Install.Kind | acli_install | none | none | register_plugin |
| Smoke.Kind | version_match | sha256 | sha256 | stdout_contains |
| Fanout | 写单节点；**落盘验证多节点探测** | 是（集群写入） | 否（单节点） | 是（集群，与 acli 安装分发范围一致） |
| OnFailRollback | none（删 tmp） | restore_backup | none | restore_backup + unregister |
| OnSuccessRestore | none | restore_original（终态，§3.2） | none | none |
| KeepBackup | false | false | false | true (.old.$SYNC_ID) |
| Version 比对 | compareAcliVersions（版本优先+日期兜底+禁降级） | 无需（总是覆写） | 无需（按 task 隔离） | **spec_hash 差量三态**：新增→Install、有修改→Install、无修改→Skip（修 B4） |

### 3.2 spc 终态还原的生命周期归属

**还原不是流水线尾钩子。** spc 的 `OnSuccessRestore` 等待的是 task_terminal——
小时级、且跨越 bridge 进程重启。现行 spc 的抗崩溃性来自三件套，骨架必须原样继承：

1. **备份自描述**：`.platform.<taskID>.bak` 文件名编码任务，内存态丢失后仍可凭
   "重新探测目录 + 拼出的备份名"找回原件（`log_collect_spc_fanout.go` L122 注释：
   内存态不是唯一真相）；
2. **写前自愈**：下一次写入前先恢复历史备份，再备份本次——顺序不可颠倒，
   否则原件被平台内容永久覆盖；
3. **显式 restore_spc**：平台可兜底触发还原，不依赖桥内存。

因此 `WaitFor=task_terminal` 的实现是：**流水线返回前把还原意图持久化**
（备份路径+任务键，落在桥侧账本），由任务终态 watcher 消费；watcher 重启后
从账本+自描述备份恢复，而不是复活一个内存 goroutine。
**验收**：kill bridge 后重启，restore_spc 仍能还原；写前自愈在重启后首次写入时生效。

### 3.3 acli_sync 两阶段：运行时语义与插件差量同步

**顺序口径（必读）**：S2→S4 是**工程落地顺序**（消费者从简到复杂迁移验证），
**不是用户旅程顺序**。运行时顺序为：连接 → acli_sync 两阶段（工具同步 → 插件差量同步）
→（用户发起日志收集时）spc/config → 采集。四条链路运行时并存、各由自身动作触发。

**用户旅程对应**：

1. 打开 custom-ui，下载并启动 terminal_bridge；
2. 输入 HCI 登录方式并连接（ssh_connect）；
3. 连接后 custom-ui **总是**发 `acli_sync`（现状仅缺失时自动触发，新设计改为总是触发；
   桥凭版本比对自决 `up_to_date` 跳过安装），走阶段一完整流程：探测→下载→上传→安装→验证；
4. 阶段一成功后**立即**跑阶段二：以 admin-ui 定义好的插件规格为期望态，
   覆盖 acli 安装后默认自带的插件——只更新新增和有修改的，没有修改的跳过
   （语义类比日志收集「默认场景=覆写内置清单 / 自定义场景=新增」）；
5. 用户点击日志收集时，custom-ui 才获取 admin-ui 定义的默认/自定义场景；
6. 用户选定配置后，桥按任务覆写 spc 或写 config；
7. 执行日志收集命令。

**触发与契约**：

- WS 对外契约冻结：仍用 `acli_sync` / `acli_sync_progress` / `acli_sync_result`；
  消息仅**增**两个可选字段：`platform_url` + `plugin_ticket`（复用日志收集票据透传范式，
  `log_collect_evidence.go` 的 platform_url/ticket 先例）。
- 旧桥不认识新字段 → 阶段二不执行，阶段一与终端/日志业务不受影响（兼容路径）。

**票据模型（fail-closed）**：

| 维度 | 定稿 |
|---|---|
| 签发 | case-service 按 case 签发短期只读票据（`POST /api/acli-plugins/ticket`，require_user），TTL ≤10min |
| 权限 | 只读，仅覆盖 manifest 查询 + 包下载两个端点；不含工单/客户/拓扑，不可枚举其他 case |
| 携带 | custom-ui 取票后随 `acli_sync` 透传；桥只拿票据不拿管理凭证 |
| 传输 | 仅 HTTPS，`http://` 一律拒绝（网关+桥侧双重校验） |
| 校验 | case-service 自校验；网关只透传、不解析、不签发；任一异常 401 |
| 审计 | 每次拉取记录 case_id / 票据 id / 结果，落平台日志 |

**阶段二流水线**：

```
阶段一 receipt.OK
    │
    ▼
PluginManifest.Desired()  ── GET /internal/acli-plugins/manifest（票据）
    │   返回：[{name, version, spec_hash, size, sha256, package_ref}]
    ▼
逐插件 remote/probe 设备事实（注册表项 + 目录摘要）
    │
    ▼
plan.Compare 三态：新增→Install / 有修改→Install / 无修改→Skip
    │
    ▼
包下载：GET /internal/acli-plugins/package/{name}（票据，平台 PVC 流式直出）
    │
    ▼
fanout.WriteAll + activate.Install(register_plugin) + Smoke
    │
    ▼
receipt{stage:"plugin", Evidence: installed=n, overwritten=m, skipped=k}
```

- 包存储沿用诊断服务「持久卷 objects/」范式（`diagnosis-service/app/services/object_storage.py`）；
  **不引入独立签名 URL 机制**——下载端点本身票据鉴权、流式直出。
- 存储未配置时 manifest 端点 fail-closed 报错（照诊断服务 `RuntimeError` 拒绝启动口径），
  阶段二回执 `package_source_undefined`，不静默截断、不影响阶段一结论。
- admin-ui 插件页只保留规格维护（列表/编辑/包上传），**「保存并下发」与任务状态轮询删除**（D1）；
  插件到达节点完全由客户侧 acli_sync 触发驱动。

**失败语义**：

1. 阶段一失败 → 阶段二**不跑**（插件依赖 acli 就绪）；
2. 阶段二失败**不回滚阶段一**（工具安装是独立既成事实）；
3. 逐插件独立 written-set：某插件失败只回滚该插件已写入条目，不波及其余插件；
4. 无备份不删、只回滚已写入等构造性不变量同样约束阶段二（B1 结构性死亡）；
5. 节点被第三方清空（acli 重装清插件目录）→ 节点事实优先，差量判定 Install，不 Skip（B4 根治）。

## 五、state.go — 已应用状态的两个语义

必须区分两种不同的 state：

| 语义 | 说明 | 存储位置 | 举例 |
|------|------|---------|------|
| **节点事实** | 通过探测获得的远端真实状态 | 不持久化，每次 reconcile 现场探测 | `acli --version` 返回的版本、文件是否存在、插件注册表摘要 |
| **桥侧账本** | 桥自己记录的"上次成功同步了什么" | `/var/lib/terminal-bridge/reconcile/state/<kind>-<host>.json` | 上次安装的插件 spec_hash、config 的 SHA-256 |

```go
// state.go

// NodeFact 是通过 remote/probe 探测获得的节点当前事实。
type NodeFact struct {
    FileExists  bool
    FileSize    int64
    FileDigest  string
    Version     string
    BuildTime   string
}

// AppliedState 是桥侧持久化的"上次成功同步"记录。
type AppliedState struct {
    Kind        string
    NodeIP      string
    DesiredHash string    // 上次成功应用的 DesiredState 的 hash
    AppliedAt   time.Time
    Evidence    []Evidence
}

// Load 加载桥侧账本。
func Load(kind, nodeIP string) (*AppliedState, error)

// Save 持久化桥侧账本。
func Save(state *AppliedState) error
```

> **账本不是幂等的唯一依据**：节点可能被第三方改动（acli 重装清空插件目录，
> `terminal_bridge/main.go`（旧路径） L3862）。plan.Compare 的 Skip 判定必须同时满足
> "账本对齐 **且** 节点事实对齐"；只信账本会在节点被清空后永久 Skip（B4）。

> **落盘路径统一到 PVC**：`~/.bridge/reconcile/state/` 在 cluster 模式下是
> 容器内 HOME，Pod 重建即丢，账本退化成内存。统一改为
> `/var/lib/terminal-bridge/reconcile/state/<kind>-<host>.json`（已在 `terminal-bridge-data`
> PVC 内，与 `log_uploader` 的水位文件同目录族），落盘方式沿用"临时文件 + rename"；
> 桌面模式该目录由 `HCI_BRIDGE_LOG_DIR` 同源决定，不写死 HOME。

> **冲突裁决顺序**：`节点事实 > 桥侧账本 > 云端 spec`。
> 具体为：① 探测成功且与期望不一致 → 一律 Apply，忽略账本"已同步"；
> ② 探测失败（不可达/命令缺失）→ 才允许用账本快速 Skip，但 `receipt` 必须带
> `degraded=true` 与 `stage=probe`，前端不得显示"已是最新"；
> ③ 账本与设备真源（如 `plugin_register.json`）冲突时，以设备真源为准并覆盖账本。

## 十、术语表

| 术语 | 定义 |
|------|------|
| **reconcile** | 比较期望状态与实际状态，执行必要操作使二者一致 |
| **descriptor** | 描述期望状态的数据结构，不含具体命令 |
| **Provider** | 获取期望状态的接口（来源可以是 HTTP/WS/本地） |
| **PluginManifest** | acli_sync 阶段二拓扑：桥持短期只读票据拉平台插件清单（浏览器触发的拉模型） |
| **两阶段** | acli_sync 阶段一工具同步 + 阶段二插件差量同步，串行、同触发、同骨架 |
| **差量三态** | 新增→Install、有修改→Install、无修改→Skip |
| **票据** | case-service 按 case 签发的短期只读凭证，仅覆盖 manifest+包下载 |
| **Runner** | remote/ 定义的最小执行接口缝，main 包 SSHSession 提供适配器 |
| **fanout** | 对多台主机并发执行同一操作，跟踪 written-set |
| **guard** | 并发安全机制（互斥锁、fencing、基线持久化） |
| **written-set** | 记录哪些文件/目录树/主机已被成功写入，回滚时只操作这些 |
| **golden 对比** | 对同一输入比较新旧实现的输出，确保行为等价（仅适用行为保持路径） |
| **桥侧账本** | bridge 进程自己持久化的"上次同步了什么"记录 |
| **节点事实** | 现场探测得到的远端真实状态，不持久化 |
| **工程落地顺序** | S2→S4 消费者迁移验证顺序（从简到复杂），区别于用户旅程顺序 |
