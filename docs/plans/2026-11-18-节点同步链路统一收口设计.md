# 节点同步链路统一收口设计（2026-11-18）

> 本文合并两份独立方案的最优部分，经第三方裁决后定稿；v1.1 经对抗性审查修订。
> 核心原则：**用数据驱动的 reconcile 骨架消除四条链路的代码重复，
> 用构造性不变量消除安全隐患，用从简到复杂的消费者顺序控制落地风险。**
>
> v1.1 修订要点（证据均经 origin/main `bf8361bd` 逐行核实）：
> ① 订正 6 处事实错误（base64 校验描述倒退、幻影 Python 函数名、退出码归因、
> 分片归属、插件触发方式、版本比对基线）；② 解决 6 处架构自相矛盾
> （SSHSession 循环依赖、包名遮蔽 stdlib、golden 与原子写冲突、备份命名、
> spc 异步还原生命周期、插件 Provider 拓扑）；③ 重设计 P-1③ 幂等止血，
> 避免"修复引入新 bug"；④ 补齐 S8/S9/S10 三个遗漏缺陷进 S4 验收。
>
> v1.2 修订要点（落地可行性审查，全部指向"上线会炸"而非风格问题）：
> ① **S5 增加桥能力协商**——回退开关不能只做在 relay 侧，客户 exe 升级不可控，
> 旧桥收到 `plugin_apply` 会静默丢弃并让部署 240s 超时；② **S6 鉴权模型具体化**
> （只读、按实例签发、不可跨客户枚举）并补旧桥兼容路径；③ **descriptor 的
> inline 总量阈值 + 自动降级**写死为规则，不靠调用方自觉；④ **S4 拆 S4a/S4b**
> 两小步，使"每阶段可独立回滚"在 S4 内部也成立；⑤ **state 落盘统一到 PVC 路径**
> 并明确"节点事实优先于桥侧账本"；⑥ **S1 前置 exec 语义差异表**，防止
> `runQuickCommand` 替换悄悄改掉十几处错误处理；⑦ **S5 前置插件包存储与签名 URL**
> 设计，否则 `Source.URL` 是空的；⑧ **Metadata 使用约束 + CI 静态检查**，
> 防止逃生舱退化成新的分支地狱；⑨ **P-1⑤ 改为显式 ALTER 迁移**（旧表不会被
> `CREATE TABLE IF NOT EXISTS` 修正）。

## 一、问题定义

### 1.1 现状：四条同构链路各写各的

terminal_bridge 当前有四条"往 HCI 节点上同步东西"的链路，逻辑高度同构但实现完全独立：

| 链路 | 文件 | 职责 | 行数 |
|------|------|------|------|
| **acli_sync** | `terminal_bridge/main.go`（L3317 `handleAcliSync`）, `terminal_bridge/acli_package.go` | 检测→下载→上传→安装 acli 工具 | ~1300 |
| **spc（场景覆写）** | `terminal_bridge/log_collect_spc.go`, `terminal_bridge/log_collect_spc_fanout.go` | 逐节点写入场景文件、终态还原 | ~1500 |
| **config（自定义配置）** | `terminal_bridge/log_collect_config.go` | 写入 -c 配置文件到发起节点 | ~200 |
| **插件（plugin deploy）** | `backend/case-service/app/domain/acli_plugin_spec.py`（`build_deploy_script`） | 注册→备份→原子替换→冒烟测试插件 | ~750 |

四条链路共享同一组底层原语，却各自实现了一遍：

| 原语 | acli_sync | spc | config | 插件 |
|------|-----------|-----|--------|------|
| **远端写文件**（tmp+mv+校验） | `uploadAcliPackage` → `buildAcliRemoteWriteCommand`（tmp+校验+mv+退出码，唯一完整实现） | `buildSpcWriteCommand`（printf 直写目标，靠备份+失败回滚兜底） | `writeLogCollectConfig`（`printf > path`，**无 tmp+mv**，P0 隐患） | `build_deploy_script` 内 printf '%b' 分片写 stage（Python 拼接） |

### 1.3 设计目标

1. **消灭双语言重复**：五组原语（写文件、探测、校验、传输、转义）各写一份 Go 实现，Python relay 退化为声明式 manifest 下发器
2. **新增链路不改骨架**：将来加第五条链路（如 exe 云端拉取）只需加一个 descriptor + Provider，不动编排
3. **安全不变量结构化**：回滚前提、扇出 written-set、主机键互斥从"记住别犯"变成"写不出来"
4. **P0 当天止血**：不等重构完成，先用最小改动消除数据破坏风险（但止血本身不得引入新 bug，见 P-1③）

## 二、核心抽象

### 2.1 总体结构：两轴分离

```
terminal_bridge/internal/
├── remote/                  # 横向原语（所有链路共享，反向链路也可 import）
│   ├── fs.go                # WriteFile: tmp+校验+mv+退出码 20-23
│   ├── probe.go             # 远端探测：exist/version/size/digest
│   ├── transfer.go          # Pull/Push 断点+pace（合并 delivery×2, transfer×2）
│   ├── exec.go              # Runner 接口 + 远端命令执行：分片逐条 exit_code、超时
│   ├── marker.go            # 唯一设备标记协议；过渡期双协议适配
│   └── quote.go             # shellQuote 唯一实现（收口转义）
│
└── reconcile/               # 纵向骨架（reconcile 编排）
    ├── descriptor.go        # DesiredState + 声明式 Install/Smoke/Files
    ├── provider.go          # 期望值来源：LatestProbe / PlatformHTTP / InlineMessage / RelayPush
    ├── plan.go              # Compare → Install/Skip/BlockedDowngrade
    ├── activate.go          # 三钩子：OnFailRollback / OnSuccessRestore / KeepBackup
    ├── fanout.go            # 集合性写入/探测：BatchMode 逐台、written-set、只回滚已写入
    ├── guard.go             # 主机键互斥 + 租约 fencing + exec_id 入分片路径
    ├── state.go             # 节点事实（探测）vs 桥侧账本（持久化基线）
    └── receipt.go           # Result{Status, Stage, ErrorCode, Retryable, Evidence[]}
```

> **包名说明（v1.1）**：纵向骨架包名定为 `reconcile` 而非 `sync`——后者遮蔽标准库
> `sync`，包内 `sync.Mutex` 会变成自引用，所有 stdlib 同步原语都得别名，徒增摩擦。

**关键约束**：

1. `reconcile/` 只能 import `remote/`，不能反向
2. `remote/` 不引入任何期望值语义——它只知道"把字节写过去"、"探测文件存不存在"
3. 反向链路（delivery、日志直传）只 import `remote/transfer` 和 `remote/exec`，不进 `reconcile/`
4. **`remote/` 与 `reconcile/` 都禁止 import `main` 包**（main 调用它们，反向 import 即循环依赖）。
   为此 `remote/exec.go` 定义最小接口缝，main 包的 `SSHSession` 提供适配器：

```go
// remote/exec.go —— 接口缝：remote/ 不认识 SSHSession，只认识 Runner。
type Runner interface {
    // RunQuickCommand 与 main 包 SSHSession.runQuickCommand 同签名。
    RunQuickCommand(ctx context.Context, command string) (stdout string, exitCode int, err error)
    // WriteStdin 向远端命令的 stdin 流式写入（cat > tmp 的字节通道）。
    WriteStdin(ctx context.Context, command string, r io.Reader) (stdout string, exitCode int, err error)
}
```

> 现有 `SSHSession.runQuickCommand` 签名即 `(ctx, cmd) → (string, int, error)`，
> 适配是零成本包装；`WriteStdin` 对应 acli 上传现有的 stdin 流式通道。
> **这是 S1 的第一天工作**：不先立接口缝，`WriteFile(ctx, s SSHSession, ...)`
> 这种签名在 Go 里编译不过（v1.0 的签名违反自己的 import 纪律，已订正）。

### 2.2 Descriptor：数据驱动的差异建模

```go
// descriptor.go

// DesiredState 描述"某条链路在某台节点上应该达成什么状态"。
// 新增链路只需新增一个 DesiredState 值，不改骨架。
type DesiredState struct {
    Kind      string            // "acli_binary" | "spc_slot" | "config_file" | "plugin_bundle"
    NodeIP    string
    Files     []FileSpec        // 要写入的文件清单
    Install   InstallSpec       // 安装动作（声明式，不是命令字符串）
    Smoke     SmokeSpec         // 冒烟测试（声明式）
    Policy    ReconcilePolicy   // 失败/成功后的行为
    Version   VersionSpec       // 版本比对（插件补齐）
    Metadata  map[string]string // 链路特有的透传字段
}
```

#### 补丁 1：Install/Smoke 必须声明式

**不能**将安装命令作为字符串放进 descriptor。理由：

1. `shellQuote` 收口目标要求所有命令渲染在 Go 侧完成
2. 命令注入面不能从 Go（受控）转移到 Python（拼接字符串）
3. acli_sync 的安装命令是硬编码常量、spc 的脚本是 Go 拼接、插件的是 Python 拼接——三处都不能直接搬进 descriptor

```go
// InstallSpec 声明"要达成什么"，reconcile/ 内部负责渲染成安全的 shell 命令。
type InstallSpec struct {
    Kind  string   // "acli_install" | "register_plugin" | "chmod_exec" | "none"
    Args  []string // 结构化参数，reconcile/ 内部转义与拼装
}

// SmokeSpec 声明"怎样证明成功"，不是"跑哪条 shell"。
type SmokeSpec struct {
    Kind  string   // "version_match" | "stdout_contains" | "sha256" | "none"
    Args  []string
}
```

#### 补丁 2：Files 引用化，大文件不走 WS JSON

插件包实测 20~31MB，走 WS JSON base64 会膨胀 33%，直接撞上已有的 10MB body 限制。

```go
// FileSpec 描述要写到节点上的一个文件。
// 大文件走 remote/transfer（断点、分片、pace），descriptor 只带引用。
type FileSpec struct {
    Path   string   // 节点上的目标路径
    SHA256 string   // 期望摘要
    Size   int64    // 期望大小
    Mode   string   // 权限位，如 "0755"
    Source Source    // 内容来源
}

// Source 区分三种来源，避免把 20MB 的包序列化进 JSON。
type Source struct {
    Kind   string   // "package" | "inline" | "remote"
    URL    string   // Kind=package 时：下载地址
    Offset int64    // Kind=package 时：断点偏移
    Data   []byte   // Kind=inline 时：小配置（<64KB）直接带
    Path   string   // Kind=remote 时：节点上已有的路径
}
```

#### 补丁 3：Reconcile Policy 三钩子

spc 的"终态还原"与插件的"失败回滚"是两件事。混在一个 policy 里必然出现"成功也回滚"或"失败不还原"。

```go
type ReconcilePolicy struct {
    OnFailRollback   RollbackSpec  // 任一步骤失败时的回滚动作
    OnSuccessRestore RestoreSpec   // 全部成功后的还原（spc 独有）
    KeepBackup       bool          // 成功后是否保留备份（插件保留 .old.$DEPLOY_ID）
}

type RollbackSpec struct {
    Strategy string // "restore_backup" | "unregister" | "none"
    // 实现约束：只接受"已登记写入集"的条目，未登记则跳过。
    // 这让 rollback() 里 rm -rf 在结构上不可能再出现。
}

type RestoreSpec struct {
    Strategy string // "restore_original" | "none"
    WaitFor  string // "task_terminal" | "immediate"
}
```

#### 补丁 4：inline 总量阈值与自动降级（v1.2）

补丁 2 只解决了"单个大文件"，没解决"多个 inline 文件累加"：一个 8 个文件、每份 2MB 的插件
仍然会拼出 16MB 的 WS 消息，被 `CLIENT_MAX_CMD_BYTES`（10MB）拦在桥门口。

规则写死在 `reconcile` 内部，**不依赖调用方自觉**：

| 条件 | 行为 |
|---|---|
| 单文件 `Source.Data` > 256KB | 自动改写为 `Source{Kind:"package"}`，由 `remote/transfer` 分片上传，`Data` 置空 |
| 同一次 descriptor 的 inline 总量 > 1MB | 同上，按 `Path` 逐个大文件降级，直到总量达标 |
| 降级后仍 > 10MB | 直接返回 `receipt{code:"descriptor_too_large"}`，不尝试发送（避免桥侧无回执超时） |

降级必须写进 `Evidence`（`inline_downgraded=2`），否则"为什么走了慢路径"无从解释。

#### 补丁 5：`Metadata` 只能是展示/trace，不得影响执行（v1.2）

对抗性审查 #3 把 `Metadata` 当成"表达力不足的逃生舱"，风险是它退化成"每条链路塞一段 JSON，
`reconcile` 里再写一堆 `if md["kind"] == ...`"，等于把要消灭的分支又请回来。

约束：
1. `Metadata` 的 key 必须在 `descriptor.go` 的常量表里登记（`mdKeySPCSlot` 等），禁止裸字符串；
2. **`reconcile/` 内除 `receipt`/日志外，禁止读取 `Metadata` 做流程分支**；
3. CI 加静态检查：`reconcile/` 中出现 `Metadata[` 的读取点，必须在本文件的允许清单内。

真正需要新语义时，扩 `descriptor` 的强类型字段（宁可加一个 `Slot`/`RegisterEntry`），
而不是塞进 `Metadata`。

#### 2.4.1 activate.go — 构造性回滚不变量

```go
// activate.go

// Activator 管理"安装→验证→回滚/还原"的三阶段生命周期。
//
// 核心不变量：删除操作以备份存在 ∨ .old.$DEPLOY_ID 存在为前提。
// 违反此前提的调用会返回 error，而不是执行删除。
// 这让 "无备份即 rm -rf" 在结构上不可能发生。
type Activator struct {
    // writtenSet 登记本次实际写入的条目，文件与目录树均可登记。
    // 插件回滚是目录树粒度（rm -rf "$BASE/$NAME"），只登记文件会漏掉它。
    writtenSet map[string]WriteEntry
}

type WriteEntry struct {
    Path       string
    IsDirTree  bool   // true 时按目录树整体回滚
    BackupPath string // 任务/部署隔离的备份名，由调用方按 kind 给定：
                      //   spc:    <path>.platform.<taskID>.bak
                      //   plugin: $TMP/backup/<name> 与 <path>.old.<deployID>

                      // 固定名会让两次采集互相覆盖原件（log_collect_spc.go L101）。
}

// Rollback 只回滚 writtenSet 中登记过的条目。
// 未登记的条目即使传了路径也不会被删除。
func (a *Activator) Rollback(ctx context.Context, r remote.Runner, entries []WriteEntry) error {
    for _, e := range entries {
        if _, ok := a.writtenSet[e.Path]; !ok {
            continue // 未写入的不动
        }
        if e.BackupPath == "" {
            return fmt.Errorf("回滚前提不满足：%s 未登记备份，拒绝删除", e.Path)
        }
        // 探测备份存在（remote/probe）→ 存在才恢复；不存在则报错而非删除。
        // ...
    }
    return nil
}
```

## 三、reconcile 编排流程

每条链路的执行都遵循同一个流水线：

```
Provider.Desired()
    │
    ▼
state.Load()  ──→  plan.Compare(desired, actual)
                        │
                        ├── Skip（已是最新）
                        ├── BlockedDowngrade（版本回退，拒绝）
                        └── Install
                              │
                              ▼
                        guard.Acquire(hostKey)
                              │
                              ▼
                        fanout.WriteAll(files)   ← remote/fs.WriteFile
                              │
                              ▼
                        activate.Install(spec)   ← remote/exec.Run
                              │
                    ┌─────────┴──────────┐
                    │                    │
                 成功                  失败
                    │                    │
                    ▼                    ▼
         activate.Smoke(spec)    activate.Rollback(writtenSet)
                    │                    │
                    ▼                    ▼
         state.Save(result)      receipt.Error(stage, code)
                    │
                    ▼
         policy.OnSuccessRestore?  ── immediate → 流水线内还原
                    │                 task_terminal → 登记持久还原意图（见 §3.2）
                    ▼
         receipt.OK(evidence)
```

### 3.1 四条链路在流水线上的差异（全部由 descriptor 字段表达）

| 维度 | acli_sync | spc | config | plugin（S5） |
|------|-----------|-----|--------|--------------|
| Provider | LatestProbe | InlineMessage | InlineMessage | **RelayPush**（S6 exe 场景才是 PlatformHTTP） |
| Files.Source | package (HTTP 下载) | inline (<6.5KB) | inline (<256KB) | package (relay 给引用+sha256) |
| Install.Kind | acli_install | none | none | register_plugin |
| Smoke.Kind | version_match | sha256 | sha256 | stdout_contains |
| Fanout | 写单节点；**落盘验证多节点探测** | 是（集群写入） | 否（单节点） | 是（集群） |
| OnFailRollback | none（删 tmp） | restore_backup | none | restore_backup + unregister |
| OnSuccessRestore | none | restore_original（终态，§3.2） | none | none |
| KeepBackup | false | false | false | true (.old.$DEPLOY_ID) |
| Version 比对 | compareAcliVersions（版本优先+日期兜底+禁降级） | 无需（总是覆写） | 无需（按 task 隔离） | **补齐**：spec_hash + 版本判序 |

### 3.2 spc 终态还原的生命周期归属（v1.1 新增）

**还原不是流水线尾钩子。** spc 的 `OnSuccessRestore` 等待的是 task_terminal——
小时级、且跨越 bridge 进程重启。现行 spc 的抗崩溃性来自三件套，骨架必须原样继承：

1. **备份自描述**：`.platform.<taskID>.bak` 文件名编码任务，内存态丢失后仍可凭
   "重新探测目录 + 拼出的备份名"找回原件（`log_collect_spc_fanout.go` L122 注释：
   内存态不是唯一真相）；
2. **写前自愈**：下一次写入前先恢复历史备份，再备份本次——顺序不可颠倒，
   否则原件被平台内容永久覆盖；
3. **显式 restore_spc**：平台可兜底触发还原，不依赖桥内存。

因此 `WaitFor=task_terminal` 的实现是：**流水线返回前把还原意图持久化**
（备份路径+任务键，落在桥侧账本），由任务终态 watcher 消费；watcher 重启后
从账本+自描述备份恢复，而不是复活一个内存 goroutine。
**验收**：kill bridge 后重启，restore_spc 仍能还原；写前自愈在重启后首次写入时生效。

## 五、state.go — 已应用状态的两个语义

②③④ 没有"比对"不是忘了写，是没有持久化的已应用状态，无从比起。
但必须区分两种不同的 state：

| 语义 | 说明 | 存储位置 | 举例 |
|------|------|---------|------|
| **节点事实** | 通过探测获得的远端真实状态 | 不持久化，每次 reconcile 现场探测 | `acli --version` 返回的版本、文件是否存在 |
| **桥侧账本** | 桥自己记录的"上次成功同步了什么" | `~/.bridge/reconcile/state/<kind>-<host>.json` | 上次安装的插件版本 hash、config 的 SHA-256 |

```go
// state.go

// NodeFact 是通过 remote/probe 探测获得的节点当前事实。
type NodeFact struct {
    FileExists  bool
    FileSize    int64
    FileDigest  string
    Version     string
    BuildTime   string
}

// AppliedState 是桥侧持久化的"上次成功同步"记录。
type AppliedState struct {
    Kind        string
    NodeIP      string
    DesiredHash string    // 上次成功应用的 DesiredState 的 hash
    AppliedAt   time.Time
    Evidence    []Evidence
}

// Load 加载桥侧账本。
func Load(kind, nodeIP string) (*AppliedState, error)

// Save 持久化桥侧账本。
func Save(state *AppliedState) error
```

> **账本不是幂等的唯一依据（v1.1）**：节点可能被第三方改动（acli 重装清空插件目录，
> `terminal_bridge/main.go` L3862）。plan.Compare 的 Skip 判定必须同时满足
> "账本对齐 **且** 节点事实对齐"；只信账本会在节点被清空后永久 Skip（见 P-1③）。

> **落盘路径统一到 PVC（v1.2）**：`~/.bridge/reconcile/state/` 在 cluster 模式下是
> 容器内 HOME，Pod 重建即丢，账本退化成内存。统一改为
> `/var/lib/terminal-bridge/reconcile/state/<kind>-<host>.json`（已在 `terminal-bridge-data`
> PVC 内，与 `log_uploader` 的水位文件同目录族），落盘方式沿用"临时文件 + rename"；
> 桌面模式该目录由 `HCI_BRIDGE_LOG_DIR` 同源决定，不写死 HOME。

> **冲突裁决顺序（v1.2）**：`节点事实 > 桥侧账本 > 云端 spec`。
> 具体为：① 探测成功且与 desired 不一致 → 一律 Apply，忽略账本"已同步"；
> ② 探测失败（不可达/命令缺失）→ 才允许用账本快速 Skip，但 `receipt` 必须带
> `degraded=true` 与 `stage=probe`，前端不得显示"已是最新"；
> ③ 账本与设备真源（如 `plugin_register.json`）冲突时，以设备真源为准并覆盖账本。

**P-1③ 的重设计（v1.1，替代 v1.0 的"去 current_spec_hash 条件"）**：

v1.0 方案直接删条件会引入新 bug：succeeded 历史任务对同 spec_hash 的后续发布
**永久短路**——叠加 acli 重装清空插件目录（`terminal_bridge/main.go` L3862），
插件被清掉后管理员重发同规格永远命中旧 deploy_id，**插件再也装不回来**。
正确止血是拆分双判定 + 留 force 出口：

```sql
-- (a) in-flight 幂等：不看 current_spec_hash（它只在成功后推进，
--     带它会导致首次下发未成功时重复提交不命中、重复执行）
SELECT deploy_id, status FROM acli_plugin_deployment
 WHERE plugin_name = :name AND spec_hash = :hash AND env_code = :env
   AND status IN ('pending','claimed','running')
 ORDER BY created_at DESC LIMIT 1;

-- (b) succeeded 幂等：保留 current_spec_hash 对齐条件
--     （节点当前态确实等于该规格才算幂等命中）
SELECT deploy_id, status FROM acli_plugin_deployment
 WHERE plugin_name = :name AND spec_hash = :hash AND env_code = :env
   AND status = 'succeeded' AND current_spec_hash = :hash
 ORDER BY created_at DESC LIMIT 1;
```

请求增加 `force bool`：force=true 跳过 (b)（节点被清空后管理员显式重发的出口）。
**验收三态**：in-flight 重复提交返回同一 deploy_id；succeeded+对齐命中幂等；
节点清空后 force=true 可重新下发。根治（基于节点事实对账）在 S5 的 plan.Compare 完成。

**P-1 的核心论证**：S1 的后果是"一次 `flock -w 30` 超时就删掉正在运行的插件目录且无备份"。

1. 源文件改 `varchar(128)`（`acli_plugin_environment.env_code` 与 `acli_plugin_deployment.env_code` 两处）；

### S5：PluginBundle + 契约迁移

**目标**：插件执行端下沉到 Go，Python relay 退化为 manifest 下发器。

| 新增 | 内容 |
|------|------|
| `RelayPush` Provider | relay 经 WS 推送 descriptor JSON（**推模型**，校验 INTERNAL_API_TOKEN 来源） |
| plugin_apply descriptor | 插件安装的完整 descriptor（register + 备份 + 原子替换 + 冒烟） |
| relay 回退开关 | `ACLI_PLUGIN_EXECUTOR=legacy\|bridge`，relay 侧可切回旧 Python 脚本 |

**三方契约一次性对齐**：
- admin-ui：管理台发出的插件安装请求格式
- relay：从执行者退化为转发者，只发 descriptor JSON；心跳失败中止部署（修 S5 残留）
- bridge：接收 descriptor，执行 reconcile

#### S5 前置 1：桥能力协商（v1.2，硬性）

只做 relay 侧的 `ACLI_PLUGIN_EXECUTOR` 开关**不够**：客户自己下载 exe，升级不可控，
线上会长期存在不认识 `plugin_apply` 的旧桥。届时 relay 发出 descriptor → 旧桥
`unknown message type` 或静默丢弃 → `exec_result` 永不到达 → 部署在 240s 后超时失败，
而配置本身没有任何错。

必须做成**按桥能力自动判定**，而不是靠运维记得改环境变量：

1. `/status` 增加 `capabilities: ["plugin_apply", "descriptor_v1", "sync_marker_v1"]`；
2. relay 在 `get_context` 阶段读桥能力（复用既有的 WS 建连探测，不新增轮询）；
3. 桥不支持 `plugin_apply` → 自动回落 legacy 脚本生成，`receipt.stage=legacy_fallback` 留痕；
4. 桥支持但 descriptor 版本低于 relay 期望 → 按 `descriptor_v1` 降级字段，不得直接发新字段；
5. `ACLI_PLUGIN_EXECUTOR=bridge` 只用于**强制**新路径（灰度/验证），不允许作为唯一开关。

#### S5 前置 2：插件包存储与签名 URL（v1.2）

`FileSpec.Source{Kind:"package", URL:...}` 的 URL 从哪来，v1.0/v1.1 都没定义。S5 编码前必须定：

| 问题 | 需要定稿的答案 |
|---|---|
| 包存在哪 | 管理端上传后的落点（case-service 本地目录 / 对象存储 / PVC），必须与 `terminal-bridge-data` 之外持久化 |
| URL 谁签 | 服务端签短期只读 URL（建议 ≤10min），桥只拿 URL 不拿管理凭证 |
| 摘要从哪来 | 以 `acli_plugin_spec` 里登记的 `sha256` 为准；URL 侧不得自证 |
| 离线环境 | 无外网时由 relay 走 `remote/transfer` 分片直推（`Source.Kind:"package"` 的 `URL` 置空、走 WS 二进制块） |

未定稿前，`plugin_bundle` 的 `Files` 只能是 inline（≤阈值），任何 >1MB 的插件包一律报
`package_source_undefined` 而不是静默截断。

**消费者解析方迁移**：

| 消费者 | 现有格式 | 迁移方式 |
|--------|---------|---------|
| 前端 `frontend/customer/src/services/acliManager.ts` | `acli_sync_result` | 不变（S4 保持兼容） |
| relay | `ACP_RESULT` | 过渡期双格式写入，relay 解析新格式或旧格式均可 |
| log_collect | `SPC_*` | 不变（S3 保持兼容） |

**验收标准（必须包含）**：
1. rollback 前提不变量：模拟备份缺失 → 拒绝删除（S1 bug 在结构上死掉）
2. 分片逐条回执：模拟第 3 片 exit_code=1 → 中断上传（S3 bug 死掉）
3. fencing：模拟两个 relay 实例并发 → 分片路径不互写；心跳失败 → 部署中止（S5 bug 死掉）

5. 回退开关：`ACLI_PLUGIN_EXECUTOR=legacy` 时走旧 Python 脚本
6. **节点清空恢复**：acli 重装清空插件目录后，plan.Compare 凭节点事实判定 Install（不 Skip），force 出口可用

**目标**：补齐场景 4/5（exe 云端拉取），清理技术债。

#### S6 前置定稿：桥身份令牌模型（v1.2）

桥是**客户机器上的不受信进程**，这条通道一旦做错就是数据面后门。定稿如下：

| 维度 | 定稿 |
|---|---|
| 凭证形态 | **桥实例令牌**（`bridge_id` + 短期签名，随 exe 首次连云端时换取），不是 admin JWT、不是 `INTERNAL_API_TOKEN`、不是客户登录态 |
| 权限 | 只读、只返回 `desired`（插件名/版本/spec_hash/包 URL/摘要），不含工单、客户、拓扑信息 |
| 范围 | **不做客户过滤**：返回平台全局最新 desired（与"任何客户连上就收敛到云端最新"一致）；令牌只能证明"是一个桥"，不能枚举其他桥 |
| 时效 | 令牌有效期 ≤24h，桥侧自动续期；吊销按 `bridge_id` 单点失效 |
| 传输 | 仅 HTTPS；`http://` 一律拒绝（不得复制官方源的明文模式） |
| 旧桥 | 无令牌的旧桥 → 401 并**不阻断** SSH 业务（拉取失败只影响插件同步，不影响终端/日志） |
| 审计 | 每次拉取记录 `bridge_id / revision / 结果`，落平台日志（不入 `bridge_execution_logs`） |

**验收用例（必须覆盖）**：无凭证 → 401；伪造 `bridge_id` → 401；有效令牌 → 只拿到 desired；
令牌用于其他端点 → 403；旧桥（无令牌）→ 终端与日志业务不受影响。

| 内容 | 详情 |
|------|------|
| exe reconcile worker | SSH 连接后自动 reconcile（PlatformHTTP Provider 的消费者） |
| 反向链路整理 | delivery / 日志直传只 import `remote/transfer`，不进 `reconcile/` |
| 残骸清理 | 删除 #1513→#1518 残骸：死表 `acli_plugin_environment`、死模型、恒空 `/environments` 路由、relay 虚 LEFT JOIN、`load_credentials`、`build_ssh_connect_message`、Helm `credentialsSecret` 死配置 |

**验收标准**：
1. 任意客户 exe 连上任一 HCI，`spec_hash` 3 分钟内收敛
2. `grep` 零残留（指定的死代码全部删除）
3. `/environments` 删除后前端无 404
4. 拉取 API 鉴权用例：无凭证/客户凭证/admin 凭证各得其所

## 十、术语表

| 术语 | 定义 |
|------|------|
| **reconcile** | 比较期望状态与实际状态，执行必要操作使二者一致 |
| **descriptor** | 描述期望状态的数据结构，不含具体命令 |
| **Provider** | 获取期望状态的接口（来源可以是 HTTP/WS/本地） |
| **RelayPush** | S5 插件拓扑：relay 经 WS 推 descriptor（推模型） |
| **PlatformHTTP** | S6 exe 拓扑：桥经 HTTPS 拉 desired（拉模型） |
| **Runner** | remote/ 定义的最小执行接口缝，main 包 SSHSession 提供适配器 |
| **fanout** | 对多台主机并发执行同一操作，跟踪 written-set |
| **guard** | 并发安全机制（互斥锁、fencing、基线持久化） |
| **written-set** | 记录哪些文件/目录树/主机已被成功写入，回滚时只操作这些 |
| **golden 对比** | 对同一输入比较新旧实现的输出，确保行为等价（仅适用行为保持路径） |
| **桥侧账本** | bridge 进程自己持久化的"上次同步了什么"记录 |
| **节点事实** | 现场探测得到的远端真实状态，不持久化 |
