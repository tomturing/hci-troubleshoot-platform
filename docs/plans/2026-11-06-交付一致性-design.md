# 交付一致性与会话代际治理设计（2026-11-06）

> 本文已使用**第一性原理**（去伪存真、追溯根基、正向重构）与**对抗性审查**（主动找失败条件、极限施压）推导。业界范式只作为候选解接受检验，不作为权威。

## 一、不可再分的底层事实

| 编号 | 事实 | 推导出的硬约束 |
| --- | --- | --- |
| F1 | 一次交付的对象是**字节序列**，其身份是摘要；文件名 + 大小不是身份（同名文件可被重新采集覆盖） | 会话必须绑定「内容身份」，不能只绑 `total_size` |
| F2 | 分片几何（`part_count` / `chunk_size` / 末片长度）由 `meta.json` 的 `total_size` 在 init 时派生并冻结 | init 之后字节序列变化 ⇒ **每一片**都必然失败，重试不可能自愈 |
| F3 | 同一工单可产生多代交付作业（重复点击、重新采集、会话重建） | 旧代的任何写入（含 fatal 回写）必须对新代无效，需要 fencing |
| F4 | "产物到达"只能由持久化事实（服务端 complete / relay success / 归档核验）证明；浏览器一次 WS/HTTP 失败只证明**结果未知** | 终态只能由服务端单一写入者推进；客户端只读 |
| F5 | 客户机 bridge exe **不会自动升级**，合并代码 ≠ 到达现场 | 任何只有新 exe 才生效的修复都不是"彻底"；核心必须在服务端 + 前端独立闭环 |

现场证据（Q2026110601054）：15:51 重新采集使同名 zip 由 3,909,075,473 变 1,216,213,263 字节 → F1/F2 分叉；15:51:11 旧作业 `superseded`/`context canceled`，15:55:10 又 `collect_finished` → F3 缺失；`relay_status=success`/`delivery_status=delivered` 与 `status=failed` 并存 → F4 缺失。

## 二、候选范式（接受检验，不照搬）

| 范式 | 借鉴点 | 本场景是否适用 |
| --- | --- | --- |
| 内容寻址 / 不可变制品（OCI digest、Git blob） | 以摘要为身份，先 finalize 再发布 | ✅ 用于会话身份；但节点摘要在提交时拿不到 → 降级为「大小 + mtime + 稳定标记」指纹 |
| Fencing token / epoch（Kleppmann 分布式锁） | 单调递增代际，旧 owner 的迟到写被拒 | ✅ 解决旧作业复活与旧 relay 覆盖 |
| Single-writer + 状态机单调性（事件溯源） | 终态由唯一权威在事实发生后推进，不可逆 | ✅ 解决双写分叉 |
| Compare-and-swap / 乐观并发 | `update ... where <前置条件>` 原子判定 | ✅ 无需新列即可实现 |
| Cooperative cancellation（Go context） | 每个阶段入口检查 `ctx.Err()`；重排前做 membership 检查 | ✅ 补齐 `advance/pull/upload/complete` 入口 |
| Unknown ≠ Failed（分布式系统基本判据） | 请求失败置"结果未知"，不落终态 | ✅ 覆盖 WS 通道断开，不止 503 |

## 三、方案对比

| 方案 | 做法 | 优点 | 致命缺陷 | 结论 |
| --- | --- | --- | --- | --- |
| A 最小补丁 | 只加重排判据 + `BRIDGE_CHANNEL_LOST` 分类 + `_finish` 回写 `status` | 改动小、上线快 | F1/F2 未解：下次重采仍必现「源包已变化」，只是报错更清楚 | 否决 |
| **B 三支柱 + 纵深** | ①内容指纹 + 会话代际自动重建；②服务端单一权威终态 + CAS；③前端结果未知 + 自动重签会话；Go 侧 generation 为纵深 | 服务端/前端即可闭环（F5），从根上消除三类问题 | 改动面较大，需要兼容老前端/老 exe | **选中** |
| C 事件溯源重写 | 服务端统一编排全部交付，取消本地作业 | 架构最干净 | 数周工作量，且现场 exe 不升级 → 收益无法落地；YAGNI | 否决 |

### 为什么 B 是最优（而不是"更大"的方案）

F5 决定了：**不能把"提交上传会话"前移到节点摘要算完之后**，因为现场 exe 改不了、也拿不到摘要。于是第一性原理给出的不是"阻止分叉"，而是**让系统识别分叉并自愈**：会话携带内容指纹与代际，指纹一变就作废旧会话、用新基线重签，用户零操作。平台 `deliver_task` 已有 `LC-TRANSFER-004` 409 → abort 重建机制，复用它而非另起炉灶。

## 四、详细设计

### 支柱 1：内容指纹 + 会话代际（fencing）

- `DeliverRequest` / `UploadInitRequest` 新增**可选** `archive_fingerprint`（`{size}:{mtime_ns}:{stable}` 或 sha256）、`delivery_epoch`。老前端不传 → 回落现有 `total_size` 快照，不中断现场。
- `upload_service.init` 把指纹/代际写入 `meta.json`；重复 init 若**指纹不同**，判定「内容已变」→ 自动 abort 旧会话并按新基线重建（返回新 token），而不是把 409 抛给用户。指纹相同则保持幂等复用。
- `record_part` / `complete` 校验代际：旧代请求返回明确的 `LC-TRANSFER-011 会话已被新代替代`，不再逐片 500。
- `begin_delivery` 在 `detail` JSONB 递增 `delivery_epoch`（不新增 DB 列：Atlas 声明式库 DDL 早于 DML，加列有已知事故 056；`detail` 可作原子 CAS 条件）。

### 支柱 2：服务端单一权威终态

- `update_task`（公共 PATCH）**静默忽略**客户端对 `delivery_status` / `delivery_error` / `delivery_finished_at` / `relay_status` 的写入，并记一条结构化审计日志（老前端不会被 422 打断，只是写不动）。
- 当前已 `delivered` 时，拒绝把 `status` 回退为 `failed`（CAS：`update ... where delivery_status != 'delivered'`），已交付事实不可逆。
- `relay_service._finish(success)` 一次性收敛 `status=completed` + `delivery_status=delivered` + 清 `error_code/error_message/relay_last_error`，并带幂等前置条件；失败分支保留错误。
- `upload_service.complete` 与 P1 `verify_p1_archive` 走同一组服务端终态写入函数，不再各写各的。
- 所有终态写入携带 `task.trace_id`（唯一调用链），并新增四类可计数事件：`delivery.epoch_rejected`、`delivery.session_rebuilt`、`task.terminal_write_ignored`、`task.outcome_unknown`。

### 支柱 3：前端「结果未知」+ 自动重签会话

- `isTransientPlatformError` 泛化为 `isOutcomeUnknownError`：除 axios 502/503/504/无 response 外，覆盖 `BRIDGE_CHANNEL_LOST`（WS 通道断开）。命中 → 只提示「结果未知，请刷新」，**不 PATCH 任何终态**。
- `waitDeliveryJob` 收到 `LC-TRANSFER-011` / 源包变化类 fatal → 重新 stat 节点包 → 重新 `deliverTask` → 重新 `delivery_submit`，最多 2 次；旧代 job 结果按 epoch 丢弃。
- 「上传到平台」增加前置门禁：采集未收尾（`node_state != completed`）或包存在性三态未确认时禁止提交，明确提示等待。
- 移除前端对交付终态的 PATCH（`markCompleted` / `adoptNodeTask` 失败回写 / `patch_delivered`），改由服务端核验端点收敛。

### 支柱 4：Go 纵深（随 exe 发版）

- `deliveryJob` 增 `Generation` / `Superseded`；`submit` 顶替时置位，`runJob` 错误分类与重排前检查 `ctx.Err()`、membership（`r.jobs[id] == job`）、`Superseded`；`advance` / `pull` / `upload` / `complete` 阶段入口补 `ctx.Err()`。
- 被废弃的作业不对外暴露 `error_code`（前端不会再把旧代 fatal 写回平台）。
- 新错误码 `LC-TRANSFER-011`（会话需重建，可恢复）与错误目录、Go 常量双向一致。

## 五、对抗性审查：方案会在什么条件下失败

| # | 失败模式 | 加固 |
| --- | --- | --- |
| 1 | 提交时节点摘要取不到，强制 digest 卡死全部交付 | 指纹降级为 size+mtime+stable，digest 可选；老前端不传则回落 |
| 2 | 老 exe 忽略新增 WS 字段，仍把源包变化判 fatal | 服务端/前端自动重签链路独立生效；Go 改动只是纵深 |
| 3 | 服务端忽略客户端 `delivery_status` 后，老前端界面不更新 | 服务端返回权威状态，前端按响应渲染；不改响应契约、不返 422 |
| 4 | `failed → completed` 不在现有 `_ALLOWED_TRANSITIONS` 内 | 服务端终态收敛走专用写入函数并显式允许「已交付事实纠正误判」，留审计 |
| 5 | 自动重建会话被重复点击放大成风暴 | 指纹相同则幂等复用；重建上限 2 次；按 `task_id` 代际单调递增 |
| 6 | 旧 relay 迟到 success 覆盖新一代交付 | `_finish` 带 epoch CAS 前置条件 |
| 7 | 取消后仍有 in-flight upload worker 写平台 | 阶段入口 `ctx.Err()` + 代际校验双重拦截 |
| 8 | 新增 DB 列遇到 Atlas DDL/DML 顺序事故 | 不新增列，复用 `detail` JSONB + 既有 `trace_id` |
| 9 | 「结果未知」过宽，把真实业务失败也吞掉 | 判据只认通道类错误码/axios 属性；业务 `throw new Error` 仍判真失败 |
| 10 | 静默忽略客户端写终态导致可观测性丢失 | 每次忽略都落结构化日志（含 trace_id/case_id/task_id/字段），可计数 |

## 六、验收标准

- [ ] 重新采集（包变小/变大）后不再出现逐片 500 或需用户手动重点的「源包已变化」；系统自动按新基线重签并交付成功。
- [ ] 被 superseded 的作业不再复活、不再把 fatal 写回平台任务。
- [ ] relay success 后 `status` / `delivery_status` / `error_*` 一致（本单 `8bbe5e08` 类矛盾消失）。
- [ ] WS 通道断开不再把已交付任务写成 `failed`。
- [ ] 老前端/老 exe 组合下不出现 422 / 卡死；新字段缺省回落。
- [ ] Go / Python / 前端单测全通过；错误码目录双向一致；UI 模拟人工操作验证。
