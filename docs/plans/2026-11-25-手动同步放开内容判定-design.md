# 2026-11-25 手动同步放开内容判定

## 变更历史

| 日期 | 版本 | 变更摘要 | 关联 |
|------|------|---------|------|
| 2026-11-25 | v1.0 | 新建：手动同步不再做转储内容判定，自动路径保持不变 | 工单 Q2026112500553 |

## 背景与目标

`ticket-sync` 在下载前通过 SSH 列举远端归档条目，命中转储特征即返回 `non-log-payload` 并停止自动重试。该保护对自动巡检是必要的（曾因重复拉取 65 GiB 级 vmdumpcore 白烧带宽与磁盘），但页面上的**手动同步按钮**代表用户当下的显式判断：用户希望把 `sp_<宿主机IP>/vmdumpcore` 这类采集包也同步下来分析，不应被程序拦住。

目标：自动同步逻辑**一行不改**；手动同步**不做任何内容判定**，是否同步、是否解压完全由人决定。

非目标：不放开物理与资源约束（磁盘水位、归档密码、归档损坏/体积/层级超限）；不修改存量终态工单；不调整前端交互。

## 详细设计

### 1. 按 origin 分流（`tools/ticket-sync/app/main.py`）

`_run()` 中现有分支：

```
pending = plan_pending(...)
if not pending: _complete_without_new_archives(...)
pending, ignored = await _filter_non_log_archives(job, pending)   # ← 内容判定
if not pending: _handle_all_non_log(...)
```

改为：

```
if job.origin == ORIGIN_MANUAL:
    ignored = []
    logger.info("request_id=%s ticket=%s job=%s origin=manual 手动同步跳过内容判定 待合并归档=%d", ...)
else:
    pending, ignored = await _filter_non_log_archives(job, pending)
    if not pending:
        self._handle_all_non_log(job, final_dir, meta, archives, ignored)
        return
```

要点：

- 手动路径**不调用** `list_remote_entries`，连一列目录的 SSH 都不发，从源头消除误判可能；
- 不产生 `non-log-payload`，`_note_failure` 的确定性终态逻辑对手动不再触发；
- 自动路径的 `_filter_non_log_archives`、`_handle_all_non_log`、`looks_like_non_log_bundle` 全部原样保留；
- 磁盘水位 `ensure_waterline` 在分流之前，两类任务都必经。

### 2. 去掉手动路径的内容提示（`main.py` 完成段）

`has_logs` 仍由 `has_usable_logs(build_dir)` 计算并写入 `.sync-meta.json` / `artifacts.hasLogs`（内容事实，供容量淘汰使用），但仅在 `job.origin == ORIGIN_AUTO` 时把"产物中未发现日志清单……可能仅含转储文件"拼进 `job.message`。手动成功的消息只保留同步/解压统计。

### 3. 可观测性

- 手动分流处新增 `INFO`，字段含 `request_id/ticket/job/origin/待合并归档数`，与现有请求链路一致；
- 自动路径日志格式与指标口径不变；
- 不新增指标：本改动不产生新的运行态实体，现有 `ticket_sync_active_jobs_origin` 已可区分两类任务。

### 4. 文档与存量

- `tools/ticket-sync/README.md` 判定表按 origin 分列，说明手动通道无内容判定；
- 三层事件文档（需求/方案/任务）与本设计同批提交；
- 现有 11 个 `non-log-payload` 终态工单保持不动，需分析的由页面逐单点同步（手动 POST 本就不受终态限制）。

## 决策依据

| 方案 | 做法 | 优点 | 缺点 | 选择 |
|------|------|------|------|------|
| A | 修改 `looks_like_non_log_bundle`，给 `sp_` 目录开白名单 | 单一事实源 | 仍由程序判断"该不该同步"，其他转储形态继续被拦；不满足"不用程序" | 否 |
| B | 在调用点先过滤 `sp_` 包 | 改动最小 | 判定语义分裂成两处 | 否 |
| C | 抽共享 `is_sp_log_entry()` 谓词 | 消除 Python 侧漂移 | 仍保留程序判断；改动面大于收益 | 否 |
| **D** | 手动路径整体绕过内容判定，自动不变 | 完全交还判断权；自动保护零回归风险 | 用户手动同步纯转储会占磁盘，由容量淘汰兜底 | **是** |

第一性原理：判断"该不该同步"的依据只有两种——程序规则或人的显式意图。手动按钮就是后者，因此正确做法不是继续细化规则，而是让规则在手动路径上不生效。对抗性审查：若同时放开磁盘水位，单点击即可重演 2026-11-12 写满盘全栈中断，故安全闸门必须保留。

## 测试与验收

1. 单测：自动任务仍调用 `list_remote_entries` 并在全转储时置 `non-log-payload`；手动任务不调用探测、不产生该错误码、最终 `ready`。
2. 回归：现有 `test_payload.py`、`test_robustness.py`、`test_merge_flow.py`、`test_retry_terminal.py` 全绿。
3. 端到端：部署后重启本机 `hci-ticket-sync`，用 `Q2026112500553` 点手动同步；预期 `ready` 且解压产物含 `1125.dump`，`/artifacts` 中该工单不再显示 `non-log-payload`；自动扫描不得重新入队。
4. 安全闸门：手动同步时磁盘余量低于 `min_free_bytes` 仍应被水位闸门拒绝。

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 用户手动同步纯转储大包占磁盘 | 保留磁盘水位闸门；`hasLogs=false` 仍如实落盘，容量淘汰优先清理 |
| 手动与自动同工单并发导致竞态 | 沿用 `RUNNING_PHASES` 的同工单串行约束，不改动 |
| 误以为存量会自动恢复 | 文档明确"存量不动、手动逐单点"，不批量清终态 |
