# 配置契约清单

唯一机器可校验清单是 [config-contract.yaml](../../deploy/config/config-contract.yaml)。它说明每项配置在本地 Compose、`.env.example` 与 Kubernetes Helm 中的交付边界，而不是把三处的值强行做成相同字符串。

## 三类配置

| 类型 | 交付方式 | 示例 |
| --- | --- | --- |
| 跨环境运行时配置 | Compose 变量 + `.env.example` 声明；Helm 以 values/Secret 映射同名运行时变量 | `DATABASE_URL`、`LLM_API_KEY`、诊断签名/加密密钥 |
| 非 Compose 配置 | `.env.example` 不经 Compose 注入；如属于业务运行时配置，仍必须有 Helm 等价映射 | Vite 地址、Docker 端口、日志级别 |
| Helm 内部运行时配置 | 仅由工作负载模板注入，必须在契约白名单中 | `SERVICE_NAME`、PVC 路径、Kubernetes Job 参数 |

敏感值只允许在 `.env`、Kubernetes Secret 或外部密钥系统中提供。`.env.example` 与契约清单只保留变量名、空值或明确的开发默认值，不能保存真实 Token、API Key 或私钥。

## 校验方式

执行：

```bash
make config-contract-check
```

校验器会失败于以下情况：

- Compose 引用了 `.env.example` 未声明、或未登记 Helm 等价映射的变量；
- `.env.example` 有未分类的变量或重复变量；
- Helm 模板引用了 `values.yaml` 中不存在的路径；
- Helm 运行时变量未登记，或已登记的跨环境变量没有被模板注入；
- 本机安装 Helm 时，额外执行开启 Diagnosis Service 的渲染验证。

输出中的“业务配置”才是三端必须对齐的口径：每项 `.env.example` 配置都有 Helm values/Secret 等价映射。Compose 和 Helm 的变量数量不会相等，因为 Compose 只交付本地需要的部分，而 Helm 还会生成容器内部变量（例如 `SERVICE_NAME`、Job 参数和挂载路径）；“Helm values 路径引用”则是模板读取字段数，不是环境变量数。

新增配置先更新 `deploy/config/config-contract.yaml`，再修改目标部署文件并运行校验。Compose 的每一项业务配置必须映射到 Helm values/Secret；名称不同的派生配置也必须明确写出实际模板环境变量。这样本地开发、CI 与 Helm 发布共享同一套边界定义。

> **反面案例存档（D-027 后续）**：#1014 为修复 admin-ui nginx 启动期 crashloop，直接在 Deployment 模板新增 `TERMINAL_BRIDGE_UPSTREAM` env 而未先登记契约，合并后 main CI 被本校验拦截（`Helm 模板运行时变量未登记到配置契约`）。正确做法：该变量属于「Helm 内部运行时配置」（nginx upstream 容器内部变量，与 `API_GATEWAY_UPSTREAM`、`DIAGNOSIS_SERVICE_UPSTREAM` 同类，不做 `.env.example` 映射），应先登记进 `helm_only_runtime` 白名单，再修改模板。
