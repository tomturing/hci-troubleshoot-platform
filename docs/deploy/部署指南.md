### 二、快速部署

#### 2.1 镜像构建与导入

```bash
# 1. 构建所有业务镜像（脚本自动跳过未克隆的 openclaw 仓库）
cd /mnt/d/aihci/hci-troubleshoot-platform
bash scripts/ops/k3s-build.sh

# 2. 导入到 k3s containerd（k3s 不使用 Docker daemon）
IMAGE_TAG="$(git log -1 --format='%cd-%h' --date='format:%Y.%m.%d-%H%M')"
for svc in api-gateway case-service conversation-service scheduler-service kb-service customer-ui admin-ui; do
  docker save "hci-${svc}:${IMAGE_TAG}" | sudo -n k3s ctr images import -
done
```

> **注意**：k3s containerd 导入后镜像前缀为 `docker.io/library/`。由于 `imagePullPolicy=Never`，k8s 调度时自动补全前缀，正常工作。

#### 2.2 Helm 部署（单仓模式）

创建或确认 `.local/values-prod.override.yaml` 包含以下最小配置：

```yaml
global:
  domain: "hci.local"       # 避免触发 Helm chart 弱密码安全校验
  publicUrl: "http://172.26.101.255.nip.io"  # 必须是 DNS 名，不能是裸 IP

dataLayer:
  manage: true              # 让 Helm 管理 postgres + redis StatefulSet

openclaw:
  enabled: false            # 本地无 openclaw 镜像时关闭
learningclaw:
  enabled: false
productionclaw:
  enabled: false

config:
  assistantRegistryJson: '{}'  # 防止 scheduler 创建孤立 openclaw pool pods
```

执行部署：

```bash
helm upgrade --install hci-platform deploy/helm/hci-platform \
  -f deploy/helm/hci-platform/values.yaml \
  -f deploy/helm/hci-platform/values-dev.yaml \
  -f .local/values-prod.override.yaml \
  --namespace hci-dev \
  --create-namespace \
  --kubeconfig /etc/rancher/k3s/k3s.yaml \
  --timeout 15m
```

#### 2.3 双仓模式（GitOps）部署

使用独立的 `hci-platform-env` 环境仓库：

```bash
# env repo 须在 ../hci-platform-env 路径
bash scripts/ops/k3s-deploy-dualrepo.sh --env dev
```

**双仓 Helm values 叠加顺序**：

```
1. deploy/helm/hci-platform/values.yaml          ← chart 默认值
2. hci-platform-env/environments/dev/values.yaml  ← env repo 差异值
3. .local/values-dualrepo-local.yaml              ← 本地覆盖（不入 git）
```

**阶段一 K3s terminal_bridge（dev）**：环境仓库合并 `terminalBridge.enabled=true` 后，ArgoCD 会创建
单副本 `terminal-bridge` Deployment、ClusterIP Service、`/terminal-bridge` Ingress 路由和运行时配置。
部署前必须确认镜像已发布且 values 使用 `repository: terminal-bridge`（CI/ghcr 的实际包名），并保留：

```yaml
terminalBridge:
  enabled: true
  replicaCount: 1
  allowedOrigins: same-origin
  networkPolicy:
    enabled: true
    ingressNamespace: kube-system
    hciSimNamespace: hci-sim-dev
```

部署后检查：

```bash
kubectl -n hci-dev rollout status deploy/terminal-bridge --timeout=120s
kubectl -n hci-dev get svc,endpoints terminal-bridge
curl -fsS http://172.28.24.21/terminal-bridge/health/ready
curl -fsS http://172.28.24.21/runtime-config.js
```

浏览器 Network 必须看到同源 `/terminal-bridge` 的 WebSocket `101 Switching Protocols`，不能出现
`localhost:9999` 或旧 Linux Docker Bridge 地址。详细正/负向矩阵见 [阶段一验证文档](../verify/events/2026-08-10-K3s受管terminal_bridge启用验证.md)。

#### 2.4 验证健康状态

```bash
# 查看所有 Pod
sudo -n k3s kubectl get pods -n hci-dev

# 检查核心服务健康
curl -s http://172.26.101.255.nip.io/api/health | python3 -m json.tool
curl -s http://172.26.101.255.nip.io/api/cases/health | python3 -m json.tool
```

#### 2.5 terminal_bridge 日志治理与上传补采

自动回采链路（bridge → WebSocket → 浏览器 → 后端）依赖浏览器在线，断链时桥侧证据会丢失。
部署后需确认以下开关与保留策略：

| 配置项 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `bridgeLogs.uploadEnabled` | Helm values | `true` | Custom-UI「上传本地日志」入口开关；自动回采稳定后可置 `false` 屏蔽 |
| `terminalBridge.logLevel` | Helm values | `INFO` | bridge 日志级别阈值，排障期可临时调 `DEBUG` |
| `terminalBridge.logFileMaxBytes` | Helm values | `67108864` | 单文件上限，超限轮转 |
| `observability.loki.retentionHours` | Helm values | `336` | Loki 日志保留期（小时），避免工单复盘时历史日志已被回收 |

desktop 模式（Windows 客户端）默认把全量 JSONL 日志写到用户桌面
`HCI-TerminalBridge-Logs/bridge-<日期>-<实例>.log`，可用 `HCI_BRIDGE_LOG_DIR` 覆盖、
`HCI_BRIDGE_LOG_TO_DESKTOP=false` 关闭。日志路径可在 bridge 的 `/status`
（`log_path`、`log_dir_source`）中确认。

#### 3.1 数据库连接

通过 NodePort 直连 PostgreSQL（端口 30054）：

| 字段 | 值 |
|------|---|
| 主机 | `<节点IP>` 或 `localhost`（WSL 内） |
| 端口 | `30054` |
| 数据库 | `hci_troubleshoot` |
| 用户名 | `hci_admin` |
| 密码 | 见 `hci-platform-env/environments/dev/values.yaml` → `secrets.postgresPassword` |

```bash
# psql 命令行连接
psql -h localhost -p 30054 -U hci_admin -d hci_troubleshoot

# JDBC URL（DBeaver / DataGrip）
jdbc:postgresql://localhost:30054/hci_troubleshoot
```

> **Service 架构说明**：`postgres`（Headless，`clusterIP: None`）用于 StatefulSet governing service 和集群内 DNS 解析；
> `postgres-external`（NodePort）仅用于外部客户端访问，两者独立，避免 ArgoCD sync 时因 `clusterIP` 不可变导致 SyncFailed。

## 第二部分：生产环境（Ubuntu 22.04 / K3s）

> 适用环境：云端 Ubuntu 22.04.5 LTS，推荐 16C/32G，单机 K8s（K3s）。

### 四、部署原则（生产基线）

- 编排统一使用 Kubernetes（不再以 Docker Compose 作为生产入口）。
- 最小权限：宿主机与容器都尽量非 root。
- 配置分层：`values.yaml`（默认）+ `values-prod.yaml`（生产基线）+ 私有 override（密钥与域名）。
- 镜像不可变：使用版本 tag（如 `2026.03.02-1`），避免 `latest`。
- 可回滚：所有发布通过 `helm upgrade --install`，保留 revision，支持 `helm rollback`。

|------|------|

#### 10.4 运行时代码完整性（强制）

业务 Python 源码必须完全来自不可变镜像，不能由 ConfigMap、Secret、emptyDir、HostPath 或 PVC 挂载覆盖。各环境的 `hci-platform-infra` Chart 已部署 API Server 准入策略，正常情况下下面两条策略查询应成功、挂载扫描应返回 `true`：

```bash
kubectl -n hci-dev get deploy,statefulset,daemonset -o json | jq -e '
  [ .items[]
    | (.spec.template.spec.containers[]?, .spec.template.spec.initContainers[]?)
    | (.volumeMounts[]?
       | select(.mountPath | startswith("/app/app/") or startswith("/app/shared/") or endswith(".py")))
  ] | length == 0
'
```

发现命中时，先查 `managedFields` 定位外部 `kubectl-patch`，删除对应 `volumeMount`/`volume` 后滚动更新，确认 Pod 内源码包含本次修复，再删除过期 ConfigMap。完整排查与禁止事项见 [D-015](pitfalls/k8s.md#d-015临时-configmap-subpath-覆盖镜像源码导致新镜像旧运行代码)。

### 十三、扩容方案（单节点 → 多节点）

**阶段 A：单节点前置改造**
1. 镜像统一切到私有仓库（固定 tag），停止依赖本地导入
2. 所有发布走 `helm upgrade --install`，沉淀 `values-prod.override.yaml`
3. 评估 Stateful 组件存储方案（Longhorn/Ceph，或托管 PostgreSQL/Redis）

**阶段 B：扩容集群（先加节点，不改业务拓扑）**
1. 新增 worker 节点加入 K3s 集群
2. 保持当前 Helm release 不变，观察调度与网络
3. 验证 `kubectl get nodes/pods -o wide` 与联调脚本

**阶段 C：提升高可用**

1. 先分清「能扩」与「不能扩」——**扩副本在这个系统里不是无条件的好事**。
   渲染期守卫（`deploy/helm/hci-platform/templates/replica-guards.yaml`）会把不能扩的服务
   直接 `fail` 在 `helm template` 阶段，而不是等到业务侧发现数据错乱：

   | 服务 | 可否扩副本 | 依据（看代码，不看注释） |
   |---|---|---|
   | auth-service / case-service / conversation-service / customer-ui / admin-ui | **可** | 状态在 Redis/DB 或纯 nginx 静态+反代；staging 已扩为 2 副本 |
   | api-gateway | **不可** | terminal 会话的 SSH 连接、stdout/stderr 读取任务、WebSocket 句柄全在进程内字典（`_connections`/`_tasks`/`_websockets`），跨进程查不到 session |
   | scheduler-service | **不可** | warm-pool 的 `idle_pods`/`active_pods` 与 `ensure_warm_pool` 循环都在进程内，多副本等于每副本各建一池 |
   | kb-service | **不可** | `SignalJobManager`/`VisionJobManager` 是进程内存储，代码自带「多副本下 POST 与 GET /status 可能落到不同进程而 404」的警告 |
   | terminal-bridge | **不可** | 两层：`values.schema.json` 的 `maximum: 1`（默认路径先报这个）+ `_helpers.tpl` 的 `hci.terminalBridgeGuard`（仅跳 schema 且 enabled=true 时触发）|
   | ops-agent-service | **不可** | `deployment.yaml` 里 replicas 写死 1，无 values 开关 |
   | diagnosis-service / diagnosis-worker | **可**（不得加守卫） | worker 用 `FOR UPDATE SKIP LOCKED` + 租约取任务，本就为多消费者竞争同一张队列表设计 |
   | agent-service | **可** | 三处 `asyncio.create_task` 都是 fire-and-forget 的外部写入（fact_store 落 Redis + PG） |

   守卫的「解除条件」写在模板里（会话状态外置、池状态集中式、job 状态迁 Redis/DB）。
   **改代码时就地更新那个文件**，否则它会变成下一代人不敢删的化石。

2. PDB 由 `deploy/helm/hci-platform/templates/pdb.yaml` 的 `$targets` 列表自动渲染，
   **条件为 `replicas ≥ 2`**，`minAvailable` 统一取 `workloadDefaults.pdb.minAvailable`。
   新增服务必须往 `$targets` 加一行；漏加由 `scripts/ci/check_pdb_coverage.py` 兜住
   （它比的是**渲染结果**而不是模板源码——现网 PDB 为 0 的那次故障，源码看上去是「有模板」的）。
   两个边界必须知道：① `$targets` 现在是 **12 条而不是 13 个服务**，第 13 个
   `ops-agent-service` 的 `replicas: 1` 写死在模板里（无 values 开关），它永远进不了
   `replicas ≥ 2` 分支，要扩它先改成 values 驱动并同步入列；② 门禁自己也有回归测试
   `scripts/ci/test_check_pdb_coverage.py`（10 例）——它是被这份自测发现「文档声明的
   『selector 命中多个 Deployment』当时只实现了一半」。
3. 加 `topologySpreadConstraints`（多节点后才有意义）。
4. 引入 HPA（基于 CPU/内存或自定义指标）。

> ⚠️ **入口网关自己的重启不在以上任何一条的保护范围内**。实测 Traefik 滚动时
> 有 1.07 秒的 TCP 拒连空窗，且它在 5xx 指标与 accesslog 上都是 0（见 E-04b）。
> 缩短这段空窗靠网关自身多副本 + `publishedservice`/LB 后端摘除时序，不靠业务服务扩副本。

**阶段 D：状态服务高可用**
- 路线 1（推荐）：PostgreSQL/Redis 托管化（RDS/云 Redis）
- 路线 2：K8s 内自建高可用（需要成熟 Operator + 跨节点存储）

> ⚠️ 当前默认 `local-path` 存储适合单节点，不是多节点高可用最终形态。

**迁移关键控制点**：每次只改一类变量（先镜像 → 再副本 → 再调度策略 → 再状态层），每步后执行 `helm upgrade --wait` + 验证脚本，异常立即 `helm rollback`。

**E-04：Traefik Ingress 入口点与 TLS 配置必须匹配**

- 本地/开发环境：使用 `web`（HTTP）
- 生产环境：使用 `websecure`（HTTPS），需同时配置证书和 Traefik TLS resolver

**E-04a：入口点读超时必须覆盖最长请求（日志包分片上传）**

Traefik 3.x 的 `entryPoint.transport.respondingTimeouts.readTimeout` 默认只有 **60s**，
语义是「读完整个请求（含 body）」。日志包分片上传是唯一会把单请求拖到分钟级的接口，
默认值会让慢上行现场稳定失败，且桥侧只能看到「平台返回 HTTP 502」。

- 对外业务入口 `websecure` 必须显式放宽（当前声明为 600s），不要只改 `web`；
- 配置以 `deploy/config/traefik-entrypoint-timeouts.yaml`（HelmChartConfig）为准，
  用 `./scripts/ops/traefik-entrypoint-timeouts.sh` 落地并校验，不要 patch Deployment
  （K3s addon 会重装回滚）；
- 参数必须写在 `additionalArguments` 下：chart 39.x **不把 `globalArguments`
  渲染成容器参数**，写了也不报错、静默无效（这正是历史上「以为 web 放宽了 120s、
  实际两个入口都还在 60s」的原因）。改完用 `kubectl get deploy traefik -n kube-system
  -o json | jq -r '.spec.template.spec.containers[0].args[]' | grep respondingTimeouts`
  确认 args 里真的有；
- `valuesContent` 是整体替换 Helm user values，`--entryPoints.web.http.tls=true`
  必须一并保留，否则 admin-ui 的 4888 入口退回明文 HTTP；
- 分片大小 `caseService.logCollectStorage.chunkSizeBytes` 需与超时匹配：
  单分片耗时（= 分片大小 ÷ 现场上行）应显著小于超时窗口，默认 8 MiB。
- **数值型 values 注入容器环境变量时必须 `| int64 | quote`**：Helm 把 values 里的
  数字解析成 float64，直接 `| quote` 会用 `%v` 格式化，`8388608` 渲染成
  `"8.388608e+06"`，而容器侧是 pydantic `int` 字段，直接 ValidationError，
  整个服务起不来（2026-10-30 staging case-service CrashLoopBackOff 3 分钟）。
  `8001` 这类小整数碰巧不会退化，所以历史上一直没暴露；CI 的
  「数值型环境变量渲染格式检查」会拦住这类回归。

排障记录见 [2026-10-30 分片上传 HTTP 502 验证](../verify/events/2026-10-30-日志包分片上传HTTP502与网关读超时验证.md)。

**E-04b：5xx accesslog 必须开启，且它盖不住网关自己的重启**

Traefik 默认不写访问日志。没开时，发布窗口那几十个 502 事后**只剩一个计数器数字**：
不知道该请求走哪条路由、后端是哪个 Pod、耗时多少，无法定因。

- 三条参数（写在 `deploy/config/traefik-entrypoint-timeouts.yaml` 的 `additionalArguments`）：
  `--accesslog=true`、`--accesslog.format=json`、`--accesslog.filters.statuscodes=500-599`。
  只收 5xx，且理由不是「省那 2 Gi」。两个已核实的事实决定了真正的风险在另一层：
  ① `loki-data` 的 PVC 是 **2 Gi**（不是旧文档写的 20 Gi），但 `local-path` 供的是节点目录
  （`/var/lib/rancher/k3s/storage/…`），**不设配额**——在容器里 `df -h /loki` 看到的就是整块
  2.1 T 节点盘。写超 2 Gi 不会在 PVC 边界报错，而是继续吃节点盘；
  ② Loki 用的是镜像内置的 42 行 `local-config.yaml`，里面**没有任何 retention / compactor 配置**
  （`compactor.retention_enabled` 默认 false），即**数据只增不删**（本环境已跑 238 天）。
  所以全量访问日志不是一条「滚满就覆盖」的曲线，而是一条**必然吃光共享节点盘**的曲线，
  而同一块盘上还放着 PostgreSQL、Tempo、Prometheus TSDB 与容器镜像。
  只收 5xx 后这条链路每天只有寥寥数行；而 2xx 行不含新的定因信息。
- **参数名必须先在真实二进制里核对**：`kubectl -n kube-system exec deploy/traefik -- traefik --help | grep -i accesslog`。
  Traefik 对未知 CLI 参数是 **fail-fast**，写错一个字母就是 Pod 起不来 = 全网关下线。
- `valuesContent` 是**整体替换** Helm user values（`additionalArguments` 是替换不是合并），
  所以 apply 前必须逐条比对 live 与仓库清单，确认原有 timeout/tls/metrics 参数不会丢。
  `scripts/ops/traefik-entrypoint-timeouts.sh` 会从清单自动派生期望参数再逐条校验（不要手抄）。
- **HelmChartConfig 不是即时生效**：helm-install Job → Deployment 滚动，所以
  `kubectl rollout status` 会在**尚未变化的旧 RS** 上假成功；必须比 Pod 集合变化时刻。
- accesslog 落 Loki 的路径：容器 stdout → Alloy `loki.process "ingress_logs"` → Loki。
  只提**有索引收益且有界**的字段为 structured metadata：`downstream_status`/`origin_status`/
  `router_name`/`backend_service`。`duration`、`request_path` 曾因旧注释「不增 label 基数」而被
  读成「提什么字段都免费」；它们确实**不进 label 索引**（旧注释那句本身没错），但会按行拆碎
  查询结果（实测**3 次注入 = 3 条返回流**），而这两个值原始行里本来就能查 → 不提，已由 CI 门禁拦住。
  后端归因字段刻意叫 **`backend_service`** 而不复用 `service_name`：后者是**真正的 stream 标签**
  （`discovery.relabel "pod_logs"` 把 Pod 标签 `app.kubernetes.io/name` 写成了它，在网关链上值是 `traefik` 本身），
  一个 label、一个 metadata，同名两义会让「谁在 502」给出自信但错的答案。
- v3 的 accesslog JSON 字段名是 `DownstreamStatus`/`OriginStatus`/`RouterName`/`RequestPath`/`Duration`；
  **网关内部产生的 5xx（如 503 no available server）不写 `ServiceName`**（已把那 3 条 5xx 的完整 JSON
  解出来逐个字段核对过），所以「哪个后端在 502」只对「已转发到某个 Service 之后」的 5xx 可定因。
  日志行里**没有** `accessLog` 这个字面量，不能用它做 grep 判据。
- **查网关 5xx 必须用标签过滤（label filter）语法**——`| key="value"` 是 label filter 阶段，不是行过滤 `|=`/`|~`（这两个写法的差异已现网实测）：
  可用 `{app="traefik"} | downstream_status="503"`（实测命中 3 行）；
  **不可用** `{downstream_status="503"}`——metadata 不是 label，标签选择器永远返回 0 条。
  同理，`/loki/api/v1/labels` 全集里查不到这些键，**也不能拿 `/series` 的空结果当「无数据」**
  （本轮我先被这个不一致误导得出了「注入根本没入库」的错误结论，改用 `/query_range` 才拿到数据）。

**关键限制（不要误读指标）**：网关自身重启的用户损伤表现为 **TCP 拒连而不是 5xx**，
Prometheus 指标与 accesslog **双双覆盖不到**——因为 5xx 计数与 5xx 日志都由「接收了这个请求的
 Traefik 进程」写出，而 `connect()` 被内核拒掉时根本没有任何进程接收过该请求。

实测（2026-10-30T17:41:11Z 在 staging apply 上述配置，同时跑客户端自压测探针）：

| 阶段 | 请求数 | HTTP 5xx | 连接层失败 |
|---|---|---|---|
| apply 前基线 | 30,887 | 0 | 0 |
| 滚动窗口（apply 后 40s） | 10,136 | **0** | **159**（157 ConnectionRefused + 2 RemoteDisconnected） |
| 滚动之后 | 25,793 | 0 | 0 |

拒连集中在 **1.07 秒**（17:41:34.894 → 17:41:35.964），在三条探测路径上均匀分布，
且发生在**新旧两个 Traefik Pod 并存的区间内**（17:41:22 双 Pod → 17:41:46 仅剩新 Pod）。

所以：**「发布期间 5xx 为 0」不等于「发布期间无用户损伤」**；
入口层空窗只能由客户端侧探针量化。完整数据与测量脚本见
[网关空窗量化与观测持久化PDB覆盖](events/2026-10-31-网关空窗量化与观测持久化PDB覆盖.md)。

**E-06：Prometheus 的 TSDB 必须在 PVC 上，且单副本 + RWO PVC 必须 Recreate**

这不是「容量规划」问题而是**告警语义**问题。2026-10-30 的成片误报的物理根因就在这个卷上：
`emptyDir` 下 `checksum/rules` 一变 → Pod 重启 → TSDB 全清 →
`GatewayServerErrorFirstSeen` 的 `offset 10m` 落进本实例根本没有的数据区间 →
发布前早已存在的 9 条 5xx 序列全被判成「刚诞生」，一次性 firing 9 条 warning。

现在 `deploy/helm/hci-platform-obs/templates/prometheus.yaml` 的形态：

- `storage` 卷 = `persistentVolumeClaim: {claimName: prometheus-data}`（不再是 `emptyDir`）；
- `prometheus-data` PVC：ReadWriteOnce + **显式 `storageClassName`**，默认 `10Gi` / `local-path`；
- `strategy.type: Recreate`；
- 两条渲染期 `fail` 守卫：`prometheus.storage` / `prometheus.storageClass` 为空即 fail。

两个必须知道的连带约束：

1. **单副本 + RWO PVC ⇒ 必须 `Recreate`**。默认的 `RollingUpdate` 会先起新 Pod 再停旧 Pod，
   两个实例同时挂同一个 TSDB 目录时 Prometheus 会因 WAL 已锁定而启动失败。
   同 chart 的 loki/tempo/clickhouse 都已经踩过（clickhouse 当年是 exit 76 → CrashLoopBackOff → 应用 Degraded）。
2. **PVC 的 `storageClassName` 创建后不可变**。存量安装想换 `local-path-retain` 无法通过
   `helm upgrade` 完成，只能走「备份 → 删 PVC → 重建」窗口；这也是守卫把它钉成非空的原因。

容量 10Gi 不是拍脑袋：现网实测启动 78 分钟 TSDB 占用 **13.7 MB ≈ 253 MB/天**，
`retention 7d ≈ 1.8 GB`，取 10Gi 约 5 倍余量（每新增一个 5xx `code/service/method` 组合就多一条序列）；
单节点磁盘 2.1 T / 可用 1010 G，10Gi 占比可忽略。

验证（重启后必须仍能查到 7 天前的序列）：

```bash
# 1) 删 Pod 模拟重建
kubectl -n hci-observability delete pod -l app.kubernetes.io/name=prometheus --wait=false
kubectl -n hci-observability rollout status deploy/prometheus

# 2) 重启前后查同一个老序列，两端都必须有值（只看到重启后 = PVC 没生效）
#    PromQL：count_over_time(up{job="hci-services"}[7d])
```

> ⚠️ 持久化后 `GatewayServerErrorFirstSeen` 的门控判据才真正连续；
> 但反过来说，**空窗期丢掉的序列从此不会再被误报成「刚诞生」**，
> 所以也不能拿「告警再也不响」当健康证据。

## DSH 诊断工作台部署配置

Chart 路径：`deploy/helm/hci-platform-dsh`，由独立 ArgoCD Application `hci-platform-dsh` 管理，
部署在独立 namespace `hci-dsh`。

### 形态与三条硬约束

| 约束 | 说明 |
|---|---|
| 监听地址 | 上游在配置加载期直接拒绝 `0.0.0.0`，故 dsh 固定绑 `127.0.0.1:3080`，对外暴露由同 Pod 的 nginx sidecar 承担 |
| 会话鉴权 | 上游无匿名模式，访问必须携带 launch token；token 由 api-gateway 经管理员鉴权下发 |
| 长连接 | Agent 流式输出依赖 WebSocket，反代必须转发 `Upgrade` / `Connection` |

### 必须的 values 项

DSH 使用双仓 GitOps：平台仓的 `hci-platform-dsh` 只维护模板和安全默认值，实际环境
的镜像 tag、LLM provider/model/base URL、插件列表和密钥由 `hci-platform-env` 对应
环境的 values 文件覆盖。不要把 staging/prod 的实际 DSH 参数回填到平台仓默认 values。

| 键 | 示例 | 说明 |
|---|---|---|
| `global.publicUrl` | `https://acli.sangfor.com.cn` | 用于推导 dsh 的 `--public-url` 与 `--trusted-host`，以及 Ingress 的 host |
| `ingress.path` | `/dsh` | 必须与 api-gateway 的 `DSH_PUBLIC_PATH` 一致 |
| `dsh.llm.*` / `dsh.plugins.*` / `dsh.nodeSelector` | 由环境仓库注入 | DSH 的 provider、默认模型、插件 bundle、插件 patch 和节点架构均由环境 values 定义 |
| `dsh.llmSecretName` / `dsh.pluginSecretName` | 由环境仓库注入 | 分别引用 DSH LLM 与插件外部 Secret；不把真实凭据提交到环境 values |

### 客户日志挂载

`/sf/log` 以 `hostPath` **只读**方式挂载到容器内 `/data/customer-logs`，用于 DSH 读取客户 HCI
故障日志压缩包。

- 该目录实测权限 `755`、属主 `support:support`，others 已具备 `r-x`，**只读访问无需任何
  `securityContext` 补充组配置**。
- 本 Chart **刻意不设置 Pod 级 `fsGroup`**：一旦 kubelet 对该目录误改属主，会直接破坏整条
  日志回收链路，风险对称性上不值得为了便利去赌。
- ⚠️ **单节点前提**：`hostPath` 与当前节点绑定。集群扩容到多节点后必须改为共享存储或
  配合节点亲和，否则 Pod 被调度到其他节点将读不到日志。

### 工单产物挂载

`/sf/tickets` 以 `hostPath` **只读**方式挂载到容器内 `/data/tickets`，供 DSH 分析宿主机
同步服务解压归档后的工单目录树（详见《工单日志宿主机同步服务》10.4）：

| 键 | 默认值 | 说明 |
|---|---|---|
| `tickets.enabled` | `true` | 关闭后不渲染卷与挂载点 |
| `tickets.hostPath` | `/sf/tickets` | 宿主机路径，属主 `node:node`（uid 1000） |
| `tickets.mountPath` | `/data/tickets` | 容器内挂载点 |
| `tickets.readOnly` | `true` | 产物即证据，默认禁止 DSH 写入；临时文件走 `/work` |

- `hostPath.type` 固定为 `Directory`：用 `DirectoryOrCreate` 会让 kubelet 建出
  `root:root 755`，宿主机上的同步服务之后将写不进去。目录必须先由服务创建，
  否则 Pod 会卡在 `ContainerCreating`。
- 权限无需额外 `securityContext`：DSH 以 `runAsUser: 1000` 运行，与目录属主
  `node` 的 uid 一致，属主位 `rwx` 直接生效。

### 部署前检查清单

- [ ] 集群内已创建 LLM 凭证 Secret，并在 values 中通过 `dsh.llmSecretName` 引用
- [ ] `/sf/log` 目录在当前节点存在且非空
- [ ] `/sf/tickets` 目录已由同步服务创建（或手工 `install -d -o node -g node -m 750`），否则

- [ ] 若需网络隔离，先确认 CNI 为 Calico/Cilium（**k3s 默认 flannel 不会强制执行 NetworkPolicy**）

## DSH 镜像发布链路

DSH 镜像不单独走发布通道，而是复用仓库统一的 CI 构建矩阵。正因如此，有三处
**必须严格一致**，任何一处不一致都会表现为 `ImagePullBackOff`，且 CI 本身不会报错。

### 三处一致性要求

| 环节 | 必须一致的值 | 位置 |
|---|---|---|
| 构建计划注册 | `("dsh", "dsh/Dockerfile", "dsh")` | `scripts/ci/resolve_image_build_plan.py` 的 `OTHER_SERVICES` |
| 镜像地址 | `<imageRegistry>dsh:<tag>` | chart 的 `global.imageRegistry` + `dsh.image.repository` |
| tag 回写 | `dsh.image.tag` | `scripts/ops/sync-env-repo-tags.sh` 的 `service_repository()` |

### 三个已踩过的坑

1. **`repository` 写成完整路径或带 `hci-` 前缀**
   CI 实际推送的是 `ghcr.io/tomturing/hci-troubleshoot-platform/dsh`。
   写成 `ghcr.io/tomturing/hci-dsh` 会直接 NotFound。

2. **Dockerfile 的 `COPY` 没带目录前缀**
   CI 的 `matrix.context` 是**仓库根**（`"."`），不是 Dockerfile 所在目录。
   因此必须写 `COPY dsh/docker-entrypoint.sh ...`，否则构建阶段就报找不到文件。

3. **跨命名空间复用拉取凭证**
   `hci-platform` chart 只把 `ghcr-pull-secret` 渲染到 `hci-staging`，而 Secret
   不能跨命名空间引用。DSH 部署在 `hci-dsh`，因此**必须在该命名空间内单独渲染一份**，
   否则 ghcr 匿名拉取返回 401。

### 排查命令

```bash
# 1. 确认构建计划能识别 dsh（应输出 selected {'dsh'} 且 deploy_keys 为 'dsh'）
python3 -c "
import sys; sys.path.insert(0,'scripts/ci')
from resolve_image_build_plan import select_services, ALL_SERVICES
print(select_services(['dsh/docker-entrypoint.sh'], force_all=False))
print({s: k for s, _, k in ALL_SERVICES}['dsh'])
"

# 2. 确认渲染出的镜像地址与 CI 推送地址一致
helm template dsh deploy/helm/hci-platform-dsh \
  --set global.publicUrl=https://acli.sangfor.com.cn:4443 \
  --set global.imageRegistry=ghcr.io/tomturing/hci-troubleshoot-platform/ \
  --set global.imagePullSecretName=ghcr-pull-secret \
  --set global.imagePullUser=<user> --set secrets.ghcrToken=dummy \
  | grep 'image:'

# 3. 确认镜像确实已推送（私有仓库返回 401 表示"存在但需认证"，404 表示"不存在"）
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://ghcr.io/v2/tomturing/hci-troubleshoot-platform/dsh/manifests/latest"

# 4. 确认 tag 已回写到环境仓库
grep -A3 '^dsh:' ../hci-platform-env/environments/staging/values.yaml
```

## DSH 的 LLM 配置

DSH 是 Agent 运行时，没有 LLM 就只能启动、不能干活。配置落在
`$DSH_HOME/profiles/web/cordis.patch.yml`（`DSH_HOME` 默认 `~/.dsh`，
容器内即 `/home/dsh/.dsh`）。

### 三层结构

| 层级 | 内容 | 位置 |
|---|---|---|
| 值声明 | `dsh.llm.{providerId,apiKeyEnv,api,baseUrl,model,disableThinking}` | chart values + 环境仓库 |
| 配置文件 | `cordis.patch.yml` | ConfigMap `dsh-llm-config` |
| 凭证 | `DSH_QWEN_API_KEY` | 外部 Secret `dsh-llm-credentials`（由 `dsh.llmSecretName` 引用） |

凭证通过 `apiKeyEnv` 以环境变量方式引用，**密钥本身不进入配置文件**。

### 为什么不直接只读挂载 ConfigMap

DSH 的「设置 → 模型」页也会写这份文件，只读挂载会让页面保存失败。
因此改用 initContainer 一次性播种到家目录卷（emptyDir）：
**GitOps 是基线，运行时可改，Pod 重建后回到基线**。

### DSH 插件、默认模型与 Docker Compose

上游 DSH 的 profile 由 `package.json` 中的 `dsh.profile.bundles` 和 profile 自己的
`cordis.patch.yml` 组成。部署时不要只在 patch 中填写一个不存在的 npm 包名：外部插件
必须先安装为 profile bundle，随后才由 patch 覆盖其 `id`、`disabled` 或 `config`。

环境仓库 values 支持两类扩展：

```yaml
dsh:
  plugins:
    # 本地离线 bundle：Pod 启动时执行 dsh plugin add，不需要发布 npm。
    packages:
      - "/opt/dsh-plugins/deepseek-harness-wecom-offline-0.1.22.tgz"
    # 已随 DSH 镜像携带的插件行，或上面 bundle 的配置覆盖
    entries:
      - id: tool-web
        name: "@deepseek-ai/dsh-tool-web"
        config:
          fetch: true

  # 非敏感参数直接作为环境变量；Secret 参数放 secrets.dshPluginEnv
  pluginEnv:
    WECOM_WORKSPACE_ROOT: /work/wecom

secrets:
  dshPluginEnv:
    WECOM_BOT_ID: "<由环境仓库填写>"
    WECOM_BOT_SECRET: "<由环境仓库填写>"
```

`packages` 会在 DSH 入口启动前安装到 `web` profile；安装失败会阻止 Pod 就绪，避免
插件配置静默失效。`entries` 会在 bundle 之后写入 `cordis.patch.yml`。如果插件直接从
进程环境读取 `WECOM_*`，不需要把 Secret 写进 patch 文件；如果插件另有 `config` 字段
契约，再将非敏感配置放进对应的 `plugins.entries[].config`。npm bundle 应固定版本；
本地 bundle 则使用镜像内 `/opt/dsh-plugins/<目录名>` 路径。配置默认模型时
必须同时覆盖 provider 和 model，当前 chart 已按 LLM values 生成：

```yaml
- id: agent-default-model
  config:
    provider: aliyun-maas
    model: qwen3.8-flash
```

该行决定新建 Agent 的默认路由；已有会话不会被强制改写。`provider` 必须与上面
`dsh.llm.providerId` 和 `models[].id` 对应，否则首轮请求会因路由不可用失败。

Docker Compose 复用同一镜像入口，并以 `network_mode: service:dsh` 让 nginx sidecar
与 DSH 共享 loopback，保持与 Helm 相同的安全形态：

```bash
cp .env.example .env
# 至少填写 DSH_QWEN_API_KEY；如需插件，填写空格分隔的 DSH_PLUGIN_PACKAGES
docker compose --env-file .env -f deploy/docker/docker-compose.yml up -d dsh dsh-proxy
```

Compose 的管理台通过 `http://localhost:3002/dsh/` 同源访问，DSH proxy 另发布宿主机
`3080` 端口供管理台容器反代；`DSH_SERVICE_URL=http://dsh:8080` 让 API Gateway 能在
容器网络内读取 launch token。默认日志目录是仓库下的 `dsh/data/` 占位目录；实际部署
时将 `.env` 中的 `DSH_CUSTOMER_LOGS_PATH` / `DSH_TICKETS_PATH` 改为宿主机的
`/sf/log` / `/sf/tickets` 即可。

### 三个 compat 取值是实测结论，不要凭经验"优化"

| 取值 | 实测依据 |
|---|---|
| `api: openai-completions` | 端点路径是 `/compatible-mode/v1` |
| `compat.supportsDeveloperRole: false` | 端点实测拒绝 developer 角色：`400 developer is not one of ['system','assistant','user','tool','function']`。而 pi-ai 对**声明了推理能力**的模型默认用 `developer` 角色承载系统提示词，qwen3.8-flash 恰好会返回 `reasoning_content` |
| 不覆写 `maxTokensField` | 端点实测接受 `max_completion_tokens`，无需改成 `max_tokens` |

### 为什么要关闭思维链

`disableThinking: true` 会渲染出 `compat.thinkingFormat: qwen` 与 `reasoning: 'off'`，
DSH 据此下发 `enable_thinking=false`。

原因：qwen3.8-flash 默认思考会让单次调用达到 **70s 级**，Agent 多轮调用不可用。
环境仓库里的其他服务也因同一原因统一关闭了思维链。

⚠️ `'off'` 必须加引号 —— YAML 1.1 会把裸 `off` 解析成布尔 `false`，
导致 DSH 读不到该等级。

### 常见故障对应

| 现象 | 原因 |
|---|---|
| `MISSING_CREDENTIAL` | Secret 未渲染或键名与 `apiKeyEnv` 不一致 |
| `UNKNOWN_MODEL` | 模型 ID 写错，或 `models` 未声明 |
| 每个请求都被网关拒绝 | `supportsDeveloperRole` 未设 false（本配置已处理） |
| 单次调用 70s+ | `disableThinking` 未生效，检查 `'off'` 是否被 YAML 解析成布尔 |
