# prod 误同步事故与镜像拉取策略固化

> 本文记录 2026-10-31 一次**由我自己触发的生产事故**：为让 staging 的 Loki 配置变更生效，
> 我用关键词批量触发 ArgoCD 同步，通配同时命中了手工同步的 prod 应用，
> 把积压 8 周的变更一起推上生产，并因 `imagePullPolicy: Always` 让 prod Loki 停机约 2.5 分钟。
> 结论已回写进[部署设计](../部署设计.md) §1.3 与「发布可用性的四条部署不变量」（不变量四），
> 修复本身是一条 CI 断言（观测栈渲染不变量第 5 组）。

## 1. 事故经过（本地时间 UTC+8，对应 UTC 02:0x）

| 时刻 | 事件 |
|---|---|
| 10:06:2x | PR #1404 合并（Loki 配置入 Git）。为验证线上，我循环触发 obs 应用同步，命令写作 `grep -i obs` |
| 10:06:36 | 通配同时命中 `hci-platform-obs-staging` 与 **`hci-platform-obs-prod`**，两者都被 patch 了 `operation.sync` |
| 10:06:47 | prod 同步 `Succeeded`，**39 个资源**被推上生产；该应用上次成功同步是 **2026-09-04**，即 8 周积压一次性释放 |
| 10:06:5x | prod `loki` 因 `checksum/config` 变化被 Recreate；新 Pod 拉取 `grafana/loki:3.4.2` 失败 |
| 10:06:5x–10:08:14 | prod Loki 处于 `ImagePullBackOff`；实际不可用窗口从旧 Pod 被删起算 |
| 10:08:14 | 我把 prod 的 `imagePullPolicy` patch 为 `IfNotPresent`，节点命中本地缓存（事件原文 `Container image "grafana/loki:3.4.2" already present on machine`） |
| 10:09:1x | 新 Pod 通过 readiness，Loki 恢复 `1/1 Running` |

> 不可用时长按**事件时间戳**推算（`02:06:47Z` 同步完成 → `02:09:1x` 就绪），约 **2 分 28 秒**；
> 不是凭感觉的「十来分钟」。事后核对事件可知：Pod 在 `02:08:14Z` 重建，`4m9s ago` 仍在报
> `Readiness probe failed: 503`，之后转绿。

## 2. 损失面（逐项实测核对，不估算）

| 对象 | 结论 | 证据 |
|---|---|---|
| prod Loki 数据 | **无损** | `loki-data` PVC 未变（218 天）；`index/stats` 查 90 天前窗口仍为 16 streams / 17 chunks / 18511 entries |
| prod Loki 可用性 | 停机约 2 分 28 秒 | Pod 事件 `Failed to pull image ... dial tcp 173.252.88.67:443: i/o timeout`；patch 后事件显示 `already present on machine` → 恢复后 `1/1 Running` |
| prod Prometheus 指标 | **清零**（不可恢复） | TSDB 由 `emptyDir` 切到 10 Gi `prometheus-data` PVC，这是本应人工发布的变更；新 PVC 内仅 232 KiB WAL，2026-09-04 以来的数据随旧 `emptyDir` 一起消失 |
| prod langfuse-server | 重建后正常 | 该容器本就 `IfNotPresent`，新 Pod 1/1 Running |
| prod grafana / langfuse-minio | 与本次无关，但**已连续 119 天 ImagePullBackOff** | Pod AGE = 119d，同一根因（见 §3） |

## 3. 根因：不是「忘了写策略」，而是「策略由 tag 推导且被固化」

拆到底层事实：

1. `imagePullPolicy` **不是** `values.yaml` 里的既定项——本 Chart 十个容器**一个都没声明**（修复前 `grep imagePullPolicy` 全空）。
2. 字段缺省时，K8s 按 **tag** 推导：`:latest`（或不写 tag）= `Always`，其他 = `IfNotPresent`。
3. **这个推导结果一旦写进 Deployment 就固化了**。prod 的 `loki` RS 是 218 天前用 `grafana/loki:latest` 建的（当时策略 `Always`），后来 tag 改成 `3.4.2`，策略**仍是** `Always`。
4. 于是 ArgoCD 无从纠正：Chart 不声明该字段 → 同步时不比较它 → 我 patch 成 `IfNotPresent` 后应用反而回到 `Synced`。
5. 而 prod 集群（`aiops`，192.168.0.3）**无法访问 docker.io**：`dial tcp 173.252.88.67:443: i/o timeout`。节点只能靠本地缓存。
6. 合起来：`Always` + 无外网 = **每次 Pod 重建必然失败**，与「镜像在不在节点上」无关。

同根因的旁证：`grafana/loki`、`minio/minio:latest`、`langfuse-*` 里，凡是 `:latest` 的都是 `Always`；
prod 的 `grafana` 与 `langfuse-minio` 自 119 天前就 `ImagePullBackOff`，一直没人归因——它们不是「偶发拉不动」，而是**每次都被强制去拉、每次都超时**。

## 4. 修法

| 层 | 改动 |
|---|---|
| values | 顶层 `imagePullPolicy: IfNotPresent`，注释说明为什么不能依赖默认值 |
| 模板 | 十个容器（含 `initContainers`）逐个显式渲染，支持 `<组件>.imagePullPolicy` 覆盖 |
| 门禁 | CI「观测栈渲染不变量」新增第 5 组断言：**每个容器必须显式声明且不得为 `Always`**，否则失败 |

不选「只修 prod live」的理由：那只解决一台集群的当下，同一个 Chart 下次部署到别的无外网环境会原样复现。
不选「CI 同时禁止 `:latest`」的理由：`minio/minio:latest` 是现行 values 里的真实值，
一禁就红；改 tag 又需要先知道 prod 节点缓存的是哪个 digest（本机查不到）——那是独立议题，
不能夹在事故修复里扩大到「镜像版本治理」。

## 5. 门禁自证（负例逐条实跑）

| 变异 | 门禁输出 | rc |
|---|---|---|
| 全局 `imagePullPolicy: Always` | 逐容器报「镜像 tag 固定时 Always 只多一次 digest 校验，却让无外网集群的 Pod 重建必失败」（10 条） | 1 |
| 删掉 `loki.yaml` 的显式声明 | 「Deployment/loki[loki] 未显式声明 imagePullPolicy：缺省值由 tag 推导且会固化」 | 1 |
| 未变异（正例） | 打印「所有容器的 imagePullPolicy 均已显式声明且非 Always」 | 0 |

## 6. 教训

- **验证动作本身是写操作**。`kubectl patch application ... .operation.sync` 不是「查看」，
  而 `grep -i obs` 这种关键词通配把「一个环境」放大成了「两个环境 + 8 周积压」。
  批量操作必须按**精确应用名清单**，且手工同步（`syncPolicy` 无 `automated`）的应用不应出现在任何批量路径上。
- **缺省值不是安全值**。凡是「由别处推导出来的默认值」（tag → policy、副本数 → PDB、目录 → 存储），
  都应在模板里显式写死，并由门禁断言；否则它会随历史配置一起固化，且不产生任何 Diff。
- **无外网集群把「每次都拉」变成「每次都挂」**。这类环境里 `Always` 的收益恒为零，代价是可用性。
- **事故的旁证就在隔壁**：119 天前就挂着的 `grafana` / `minio` 与我今天踩的是同一个坑，
  当时只被记成「镜像拉不动」，没有继续问「为什么它非得去拉」。

## 7. 遗留

- `minio/minio:latest` 等 `:latest` tag 的版本治理（需要先确认 prod 节点缓存版本，另开）。
- prod `grafana` / `langfuse-minio` 恢复：同属该根因，需在 prod 侧确认可用镜像后重发。
- prod 同步仍需人工决策：本次是**误触发**释放了 8 周积压，正常发布流程见[发布指南](../发布指南.md)。
