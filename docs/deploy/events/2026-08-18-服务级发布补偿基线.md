# 服务级发布补偿基线

## 背景

主干发布的镜像矩阵是按改动服务最小化构建的。若某次运行被取消，后续运行即使
成功构建并晋级了 `admin-ui`，也不能证明 `api-gateway` 或 `hci-sim` 已经发布。
将任意一个成功镜像作为全局发布基线，会使前端先于控制面上线并返回 404。

## 规则

CI 现在保存每个服务最后一次成功发布的源码提交：普通业务服务必须同时满足镜像
构建成功和非生产环境晋级成功；`hci-sim` 还必须通过 immutable GitOps digest 校验。
主干构建计划会逐服务比较该提交与当前提交，发现改动未被对应服务发布时自动补建。

镜像矩阵采用“本地构建 → Trivy 扫描 → 推送”顺序。扫描只产生安全信号并上传 SARIF，
不会成为 GHCR 发布的单点故障；只要本地构建成功，推送步骤就会执行，避免扫描服务、
漏洞数据库或网络抖动再次把镜像发布变成 skipped。正式标签仍绝不在扫描前写入 GHCR，
并且推送只依赖构建成功。每个矩阵任务的审计摘要包含服务、源码 SHA、镜像标签、
扫描结果、推送结果和 GitHub Actions run ID，用于沿唯一调用链回溯一次发布。
独立的 `hci-openclaw` 手动构建工作流也复用同一顺序和审计字段，不能成为绕过发布
纪律的旁路。

`db-migrate` 另外拆分扫描边界：PostgreSQL/Alpine OS 层与 Atlas 上游管理工具的
library 结果分别上传 SARIF；两者都不阻断已成功构建镜像的推送。这样供应商二进制、
漏洞数据库或扫描网络的故障不会阻塞平台服务，同时保留完整审计证据，后续由安全
治理流程处理可修复漏洞。

## 对抗性用例

- 上一轮 `api-gateway` 构建被取消，下一轮只成功发布 `admin-ui`：必须补建 Gateway。
- `hci-sim` 镜像构建成功但 GitOps digest 未更新：不得视为已发布。
- 某服务没有可验证的发布基线：必须 fail-closed 地重建该服务。
- 镜像扫描失败或扫描工具异常：不得因此跳过正式 tag 推送；必须在审计摘要和
  GitHub Security 中保留失败信号，并由安全治理流程跟进。只有镜像构建失败才
  阻止该服务推送和本轮对应服务晋级。
