# CI 发布链路补偿闭环

## 1. 背景与事实

PR #698 已经合入应用仓库 `main`，但 staging 仍运行合并前的镜像。排查结果显示：

```text
PR #699 合并提交 1954f0a0
  → main push CI 成功
  → 镜像 20260806-2341-1954f0a 晋级 dev/staging

PR #698 合并提交 6addcf34
  → 未发现对应的 main push CI 运行
  → 未构建包含 PR #698 的镜像
  → 未更新 hci-platform-env 的 staging values
  → ArgoCD 正常部署旧 Desired State
```

因此，故障边界在 GitHub Actions 的“main push → 构建/晋级”入口，不在 ArgoCD Controller、Kubernetes 或 staging Pod。

## 2. 原有设计缺口

原 `auto-deploy-non-prod` 只接受 `push && refs/heads/main`。这对正常发布是正确的，但没有补偿入口：

- `pull_request` CI 通过只代表代码检查通过，不会写环境仓库；
- `workflow_dispatch` 可以构建镜像，但原逻辑会跳过环境晋级；
- `release-please` 的 staging Job 只输出“可手动晋级”，不是实际同步；
- push 事件丢失时没有自动告警或可重复的“一键补偿”路径。

## 3. 决策

在同一个 `ci.yml` 中增加显式手动补偿能力，同时保留正常 main push 自动发布：

1. `workflow_dispatch` 新增 `promote_target`，取值为 `none`、`dev`、`staging`、`both`。
2. 默认值为 `none`，避免普通手动构建意外改变环境。
3. 选择非 `none` 时，必须从 `main` 分支触发；feature 分支直接失败并输出明确错误。
4. `both` 严格按 `dev → staging` 串行晋级；`dev`/`staging` 支持单环境补偿。
5. 晋级前核验所有受管服务和必要的 `dbMigrate` tag；推送后从环境仓库远端 `main` 再读一次并核验，防止“脚本执行成功但实际值未写入”。
6. 将 source SHA、image tag、目标环境、环境仓库提交写入 GitHub Actions Summary，便于审计和后续 ArgoCD/Pod 验收。

## 4. 未采用的方案

### 4.1 让所有 `workflow_dispatch` 自动晋级

不采用。手动运行经常用于 feature 分支构建或 Dockerfile 验证，若默认晋级会把未合并代码写入 dev/staging；历史 hci-sim 验证已证明该风险真实存在。

### 4.2 只继续使用 `env-repo-sync.yml`

不作为首选。该入口适合“已有镜像标签”的环境仓库同步，不能保证镜像已经由当前源码构建并推送，无法闭合本次事件丢失后的构建与晋级链路。

### 4.3 直接让 ArgoCD 跟踪应用代码仓库提交

不采用。当前双仓模型中，环境仓库是环境 Desired State 的唯一来源；绕过环境仓库会破坏审批、回滚和审计边界。

## 5. 验收标准

- `main push`：构建成功后自动按 dev → staging 更新环境仓库；行为与原流程兼容。
- `workflow_dispatch + promote_target=none`：可构建镜像，但不会修改环境仓库。
- `workflow_dispatch + promote_target=dev/staging/both` 且 ref 为 `main`：完成构建、镜像推送、环境仓库更新和远端 tag 核验。
- 非 `main` 分支选择晋级目标：Job 失败且日志包含明确原因，不产生环境仓库提交。
- 任一服务 tag 漏更新、环境仓库 push 失败或远端核验失败：Job 失败，不输出成功结论。
- 发布成功后仍需按发布指南核验 ArgoCD Desired/Live State、Pod 镜像 digest 和容器内源码。
