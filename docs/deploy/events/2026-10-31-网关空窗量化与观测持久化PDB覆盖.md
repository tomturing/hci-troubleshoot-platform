# 发布可用性硬化：网关空窗量化、TSDB 持久化与 PDB 覆盖面

> 本文是 2026-10-30/31 一轮部署侧可用性硬化的事件记录（WHY + 实测证据）。
> 现行操作口径已回写进[部署指南](../部署指南.md) E-04a/E-04b/E-06、
> [部署设计](../部署设计.md) §1.2 与「发布可用性的三条部署不变量」整节、[发布指南](../发布指南.md) §5.2.2/§5.5、
> [可观测性设计](../../solution/可观测性设计.md) §4.2/§6.2/§10.1、
> [架构设计](../../solution/架构设计.md) §8.1。

## 背景与需求

上一轮链路（#1391 全量 preStop、#1392 5xx 告警盲区门控、#1394 门控反向验证）收尾后，
遗留三项当时无法闭环的问题：

| # | 遗留项 | 当时的表现 |
|---|---|---|
| 1 | Prometheus 数据目录是 `emptyDir` | `checksum/rules` 变化触发重启后 TSDB 全清，`GatewayServerErrorFirstSeen` 一次 firing 9 条 warning（全是发布前就存在的存量序列） |
| 2 | Traefik 未启用 accesslog | 发布窗口那 54 个 502 只剩一个数字，没有任何逐请求证据可归因 |
| 3 | 13 个服务全单副本且现网零 PDB | 非发布路径（并发删 Pod）实测 503×1971 + 502×187 |

### 第一性原理拆解

「发布可用性」不可再分的底层事实只有三条，其余都是派生：

1. **是否有请求真的失败** —— 唯一权威判据在客户端（用户是否拿到错误响应），不在服务端指标；
2. **失败能否被定因** —— 服务端指标是按 `(code, service, method)` 聚合的计数器，只能告诉你「有多少」，
   不能告诉你「哪一个请求、走哪条路由、当时后端是哪个 Pod」；
3. **判据本身是否连续** —— 任何「与十分钟前的自己比较」的告警，都依赖观测后端**保有十分钟前的数据**。

三项遗留正好各卡一条：项 2 卡第 2 条，项 1 卡第 3 条，项 3 卡第 1 条。
因此本轮的验收标准从「改了什么」改成「三条判据各自是否成立」。

## 方案（WHAT）

### 项 2：Traefik 5xx accesslog（已在 staging 生效）

`deploy/config/traefik-entrypoint-timeouts.yaml` 的 `additionalArguments` 追加三条，
经 `./scripts/ops/traefik-entrypoint-timeouts.sh` 落地：

```
--accesslog=true
--accesslog.format=json
--accesslog.filters.statuscodes=500-599
```

同时把 live 漂移的 `deployment.podAnnotations`（`prometheus.io/port: "9100"`）收编进声明式配置。
只收 5xx：全量访问日志体积过大且不含新增信息，5xx 才是「用户真的拿到 502/504」的直接证据。

### 项 2b：Alloy `ingress_logs` 采集链收敛（连带发现的真实缺陷）

原 `deploy/helm/hci-platform-obs/templates/configs.yaml` 的注释写着
「structured_metadata 不增 label 基数」——**这句在 label 索引层面是对的**，错的是它被读成
「提什么字段都免费」：`stage.structured_metadata` 写入的是 Loki 3.x 原生 structured metadata，
**不是** stream label（四条实测见下文「metadata 与 label 的分界」），但它**参与查询结果的
stream 分组**，而它当时抽取了 `duration`（每请求唯一）和 `request_path`（用户可控路径）。

收敛后只保留有索引收益且值域有界的四个字段，并且**把后端服务名从 `service_name` 改名为
`backend_service`**：`service_name` 是**真正的 stream 标签**（在 `/loki/api/v1/labels` 全集里，
由 `discovery.relabel "pod_logs"` 把 `__meta_kubernetes_pod_label_app_kubernetes_io_name` 写成了它），
与「网关转发到哪个后端」同名不同义（取证见下文「`service_name` 标签的真实来源」）。
`duration` / `request_path` 留在原始 JSON 行里，LogQL `| json | Duration > 60000000000` 一样可查。

### 项 1：Prometheus TSDB → 10Gi PVC

`deploy/helm/hci-platform-obs/templates/prometheus.yaml`：

- `storage` 卷 `emptyDir: {}` → `persistentVolumeClaim: {claimName: prometheus-data}`；
- 新增 `prometheus-data` PVC（ReadWriteOnce，`storageClassName` 显式取自 values）；
- Deployment 补 `strategy.type: Recreate`；
- 新增两条渲染期 `fail` 守卫：`prometheus.storage` / `prometheus.storageClass` 不得为空。

容量推导：`13.7 MB / 78 min ≈ 253 MB/天`，`retention 7d ≈ 1.8 GB`，取 **10Gi（约 5 倍余量）**；
占节点可用 1010 G 的 1%，可忽略。

### 项 3：PDB 列表化 + 不可扩副本守卫

- `deploy/helm/hci-platform/templates/pdb.yaml` 由「手工复制 6 个服务」重写为 `$targets` 列表驱动，
  覆盖 12 个 values 可控服务（第 13 个 `ops-agent-service` 的 replicas 写死为 1、无 values 键，由 CI 渲染结果兜住）；
- 新增 `deploy/helm/hci-platform/templates/replica-guards.yaml`：3 条渲染期 `fail` 守卫
  （api-gateway / scheduler-service / kb-service）；
- 新增 `scripts/ci/check_pdb_coverage.py`：比对渲染结果里的副本数与 PDB selector，双向拦截；
- `.github/workflows/ci.yml` 的 `helm-validate` job 新增「PDB 覆盖面 + 单副本守卫」步骤，
  并在观测栈渲染检查里加入 TSDB PVC / Recreate / `structured_metadata` 标签白名单三条不变量。

### 配套：apply 脚本判据修复

`scripts/ops/traefik-entrypoint-timeouts.sh` 的 `grep -qxF "$want"` 缺 `--` 分隔符——
`$want` 以 `--` 开头时被当作 grep 选项，报 `unrecognized option`，导致验证段 8 项**全部假失败**。
改为 `grep -qxF -- "$want"`，并让期望参数列表从清单文件自动派生（不再手抄）。

## 实测结果：网关重启的真实 ingress 空窗

### 测量方法

`deploy/config` 的 HelmChartConfig 于 **2026-10-30T17:41:11Z** apply。
同时运行一个自压测探针：3 个 host/path 组合 × 3 线程、间隔 20 ms，
逐条 jsonl **追加落盘并 flush**（进程被杀也不丢数据），每条带 wall-clock UTC；
另以 0.3 s 粒度采样 `app.kubernetes.io/name=traefik` 的 Pod 集合。
探针打到 `192.168.0.4:31576`（web entrypoint 的 NodePort）。

### 数据

探测区间 17:39:06Z → 17:43:31Z（266 s），共 **66,816** 次请求：

| 阶段 | 请求数 | 200 | 404 | HTTP 5xx | 连接层失败 |
|---|---|---|---|---|---|
| apply 前基线（17:39:06→17:41:11） | 30,887 | 23,128 | 7,759 | **0** | **0** |
| 滚动窗口（apply 后 40 s） | 10,136 | 7,431 | 2,546 | **0** | **159** |
| 滚动之后 | 25,793 | 19,291 | 6,502 | **0** | **0** |

连接层失败 159 次的构成与时刻：

| 类型 | 次数 | 首末时刻 | 跨度 |
|---|---|---|---|
| `ConnectionRefusedError` | **157** | 17:41:34.894 → 17:41:35.964 | **1.07 秒** |
| `RemoteDisconnected` | 2 | 17:41:34 | 与拒连同秒 |

拒连在三条探测路径上均匀分布（`/admin/` 59、`/` 58、`/api/health` 40），
比例与各自总请求数一致 → **入口层整体拒连，不是某条路由或某个后端故障**。

Traefik Pod 集合变化点：

| 时刻 (UTC) | 事件 |
|---|---|
| 17:41:11 | apply HelmChartConfig |
| 17:41:22 | 新 Pod `traefik-787646cbb-gw97k` 出现，与旧 Pod `traefik-65458fcd9b-dcclc` 并存 |
| 17:41:34–35 | 空窗 1.07 s（**发生在双 Pod 并存区间内**） |
| 17:41:46 | 仅剩新 Pod（apply → 单 Pod 共 **35 s**） |

前后两段各 30,887 / 25,793 请求零失败，空窗夹在中间 → 归因闭合，不是客户端抖动或网络噪声。

### 结构性盲区（本轮最重要的新认知）

**网关自身重启造成的中断，Prometheus 指标与 Traefik accesslog 双双覆盖不到。**

原因在物理层：5xx 计数与 5xx 访问日志都由**处理该请求的 Traefik 进程**写出。
空窗期间客户端是 `connect()` 被内核拒掉（`ECONNREFUSED`），没有任何 Traefik 进程
接收到这个请求，因此既没有 `traefik_service_requests_total{code="502"}`，也没有 accesslog 行。
能观测到的只有 kube-state-metrics / Pod 事件那一层，而它不携带「哪些请求受影响」。

推论（写入口径）：

- 「发布期间 5xx 为 0」**不等于**「发布期间无用户损伤」；
- 网关入口的空窗必须用**客户端侧探针**量化，不能靠服务端指标反推；
- 想缩短这段空窗，方向不是 preStop（它管的是后端服务，不是网关自己），
  而是 Traefik 的多副本 + `publishedservice` / LB 后端摘除时序。

`/api/health` 全程返回 404 属基线噪声（该 host+path 在本环境无匹配 router，由 Traefik 直接回 404），
不影响结论：判据只用 200/5xx/连接层失败三类，404 单独计数不参与失败判定。

## 项 2b 的实测证据

注入 3 次 503（构造一个「存在但没有 Endpoints」的 Service，配
`allowEmptyServices=true` 让 Traefik 自己回 503 `no available server`）。

### metadata 与 label 的分界（四条命令定语义）

上一轮我把这一节写成了「structured_metadata 就是把值写成 Loki label」，**那句话是错的**，
本轮用四条互相独立的命令重测（Loki 3.4.2，镜像内置 `/etc/loki/local-config.yaml`，42 行、
未设 `allow_structured_metadata`，即取 3.2+ 的默认开启）：

```bash
kubectl -n hci-observability port-forward svc/loki 3100:3100 &
NOW=$(date +%s); START=$((NOW - 86400))
# 1) label 全集——只有 7 个，无 duration / downstream_status
curl -sG http://127.0.0.1:3100/loki/api/v1/labels --data-urlencode "start=$START" --data-urlencode "end=$NOW"
# 2) 拿 metadata 键当标签选择 → 空
curl -sG http://127.0.0.1:3100/loki/api/v1/query_range --data-urlencode 'query={downstream_status="503"}' \
  --data-urlencode "start=${START}000000000" --data-urlencode "end=${NOW}000000000"
# 3) 拿它当标签过滤（label filter：`| key="value"`）→ 命中
curl -sG http://127.0.0.1:3100/loki/api/v1/query_range --data-urlencode 'query={app="traefik"} | downstream_status="503"' \
  --data-urlencode "start=${START}000000000" --data-urlencode "end=${NOW}000000000"
# 4) `/label/<k>/values` 与 `/series` 对 metadata 键一律空
curl -sG http://127.0.0.1:3100/loki/api/v1/label/duration/values --data-urlencode "start=$START" --data-urlencode "end=$NOW"
```

实测：命令 1 返回 `app/container/filename/namespace/pod/service_name/stream` 七个；命令 2 返回
**0 条**；命令 3 返回 **3 条 stream / 3 行**；命令 4 返回空。
→ 这些键**不是 label**，旧注释「不增 label 基数」字面没错。

### 但它仍把查询结果按行拆碎了（真正的代价）

```bash
curl -sG http://127.0.0.1:3100/loki/api/v1/query_range \
  --data-urlencode 'query={app="traefik"}' \
  --data-urlencode "start=$(( $(date +%s) - 86400 ))000000000" \
  --data-urlencode "end=$(date +%s)000000000" --data-urlencode limit=1000
```

返回 **6 条 stream**，其中 3 条各只装 1 行，标签集多出的四个键就是 metadata：
`downstream_status` / `duration` / `request_path` / `router_name`，三条的 `duration` 分别为
`90270` / `85618` / `110726`。一个每条请求都唯一的值进了 metadata，结果就是每条日志一条返回流。

> 本轮两次误判都源于**只拿一个接口下结论**：
> - 先用 `/series?match[]={downstream_status=~".+"}` 的空结果判「注入根本没入库」；
> - 又用 `query_range` 把结果拆成 3 条流这件事判「它们就是 label」。
>
> 两个结论都只看到了现象的一半。正确口径必须同时跑上面四条命令：标签索引看不到、标签选择器查不到、
> 标签过滤（`| key="value"`）能命中、而结果分组又确实按它拆——这正是原生 structured metadata 的行为。

**同现象在全平台链上也存在**（本轮新发现，只登记不改配置）：`{namespace="hci-staging"} |= "trace_id"`
近 2h 抽样 50 行 → 分成 **18 条返回流**，来的是 `pod_logs` 里 `trace_id`/`span_id`/`event` 那组 metadata。
它与 `duration` 的区别不在机制而在价值：`trace_id` 支持的是全局规则要求的「按调用链查日志」，
`duration` 支持的是原始行里本来就能算出的东西。

### `service_name` 标签的真实来源（本轮闭合的开放项）

现象：`kube-system/traefik` 的**所有** stream（包括走 `ingress_logs` 采集链的 5xx 行）都带着
`service_name="traefik"`，但 `ingress_logs` 链里没有任何地方设置过它。

取证（三层，全部可复现）：

1. **日志行本身没有这个字段**。把那 3 条 5xx 的完整 JSON 解出来，字段为
   `ClientAddr`/`ClientHost`/`ClientPort`/`ClientUsername`/`DownstreamContentSize`/`DownstreamStatus`/
   `Duration`/`GzipRatio`/`OriginContentSize`/`OriginDuration`/`OriginStatus`/`Overhead`/
   `RequestAddr`/`RequestContentSize`/`RequestCount`/`RequestHost`/`RequestMethod`/`RequestPath`/
   `RequestPort`/`RequestProtocol`/`RequestScheme`/`RetryAttempts`/`RouterName`/`StartLocal`/`StartUTC`/
   `TLSCipher`/`TLSVersion`/`entryPointName`/`level`/`msg`/`time` —— **无 `ServiceName`**。
2. **`ingress_logs` 的 relabel 没设这个标签**。`discovery.relabel "ingress_logs"` 只写
   `__path__`/`pod`/`container`/`namespace`/`app`。
3. **`pod_logs` 的 relabel 设了**。同一份 ConfigMap 里 `discovery.relabel "pod_logs"` 有一条
   `source_labels = ["__meta_kubernetes_pod_label_app_kubernetes_io_name"] → target_label = "service_name"`。
   而 Traefik Pod 的 `app.kubernetes.io/name` 正好是 `traefik`。

两个 `discovery.relabel` 块都从同一个 `discovery.kubernetes.pods.targets` 取 target，
所以最合理的解释是**标签 map 按引用共享、pod_logs 那条规则原地改写了共享对象**。
这一层属于 Alloy 实现细节，本轮不再往下钻（时间盒），但它已经足以支撑一个确定结论：

> **`service_name` 在 ingress 采集链上不可用作「谁在 502」的归因键** —— 它的值是
> 「网关自己的 Pod 标签」而不是「后端 Service」，且当 Traefik 真的写出 `ServiceName` 时
> 两个语义会撞在同一个标签名上。

因此本次把抽取字段改名为 `backend_service`（仍取自 `ServiceName`），并在
`.github/workflows/ci.yml` 的门禁里显式拦住「`service_name` 出现在 ingress_logs 的
`structured_metadata.values` 里」这一写法（负例已实跑，rc=1）。

### 另两条字段事实

- Traefik v3.6.9 的 accesslog JSON 里，网关内部产生的 5xx **不写 `ServiceName`**（上面第 1 点直接证实）；
- 日志行里**没有** `accessLog` 这个字面量，不能用它做 grep 判据（本轮我因此误判过一次「0 条」）。

## 决策依据（WHY）

| 决策 | 被否的备选 | 否决理由 |
|---|---|---|
| 网关 accesslog **只过滤 5xx** | 全量访问日志入 Loki | 先说错一个理由：本文曾写「全量体积把 20 GiB 的 `loki-data` 打穿」，而现网 `loki-data` 实际只有 **2 Gi**（那个 20 Gi 来自[部署设计](../部署设计.md) §1.2 旧表，我没核对现网就沿用了）。真正的理由更强：`local-path` **不设配额**，PVC 声明值不是硬边界；而 Loki 镜像内置配置里**无任何 retention/compactor 项**，数据只增不删——所以全量日志不是「满后覆盖」而是一条**必然吃光共享节点盘**的曲线，同一盘上还有 PostgreSQL、Tempo、TSDB 与容器镜像。2xx 行另外还不含新的定因信息 |
| `duration`/`request_path` **不进 structured_metadata** | 保留以便「按耗时过滤」 | 它们不会进 label 索引（实测 `{duration="90270"}` 空），但会按行拆碎查询结果（实测 3 条 5xx = 3 条返回流）；而原始 JSON 行里本来就有这两个值，`| json | Duration > 60000000000` 一样可查 → 只有代价、没有收益 |
| 后端归因字段叫 `backend_service` | 沿用 `service_name` | 写它的时候没发现：`service_name` 已经是 stream 标签（来自 `pod_logs` 的 relabel，值是网关自己的 Pod 标签）。同名两义会在「谁在 502」上给出自信但错误的答案，而现网实测的 5xx 行里**根本没有 `ServiceName` 这个键**（取证见上文）——这条是本轮补做的对抗性审查推翻新假设的结果 |
| Prometheus 用 `local-path` 10Gi | 立即换 `local-path-retain` | PVC 的 `storageClassName` **创建后不可变**，存量 release 改它会让 upgrade 直接失败；换 Retain 需另走备份恢复窗口 |
| `strategy: Recreate` | 保持默认 RollingUpdate | RWO PVC + 两实例并存 = 第二个实例抢不到 TSDB 目录（WAL 已锁）。同 chart 的 loki/tempo/clickhouse 都因此改过，先例见[部署设计](../部署设计.md) v1.54 |
| PDB 只渲染给 `replicas ≥ 2` | 给全部 13 个服务加 PDB | 单副本 + `minAvailable: 1` 会让 `kubectl drain` **永久卡住且不报错**，把保护变成故障（比缺 PDB 更难排查） |
| 副本数直接引用各服务自己的 values 键 | 在 pdb.yaml 里另建一份副本数表 | 两处真相迟早不一致；一旦不一致，PDB 条件就退化成「看起来有保护其实没有」——正是本轮要根治的原始故障形态 |
| 不可扩副本用**渲染期 `fail`** | 只写文档约定 / 只加 CI 检查 | 这类服务的失败模式是「Pod Running、readiness 通过、指标健康，只有跨进程 session 查不到」。CI 若只查渲染产物而不构造反例，正常 values 下永远绿；文档约定挡不住一次容量需求的顺手改 |

### 与先前估计的偏离（必须显性记录）

先前计划「给约 8 个有状态服务加不可扩副本守卫」，**实际只加了 3 条**。
偏离不是偷懒，是逐条读源码后证据不足的部分必须撤销：

| 服务 | 结论 | 证据 |
|---|---|---|
| api-gateway | **加守卫** | `backend/api-gateway/app/services/terminal.py` 把 SSH 连接、stdout/stderr 读取任务、WebSocket 句柄全存在进程内字典 `_connections`/`_tasks`/`_websockets`，靠 `_cleanup_loop` 单进程回收 |
| scheduler-service | **加守卫** | `backend/scheduler-service/app/services/pod_pool.py` 的 `idle_pods`/`active_pods` 是进程内计数，`main.py` 启动时各建一份预热池 → 多副本等于池翻倍且互不可见 |
| kb-service | **加守卫** | `backend/kb-service/app/services/signal_job_manager.py`、`vision_job_manager.py` 的代码里**自带警告**：「多 worker/多副本部署下 POST 与 GET /status 可能落到不同进程而 404」 |
| diagnosis-service / diagnosis-worker | **不加**（撤销原计划） | worker 取任务用 `SELECT ... FOR UPDATE SKIP LOCKED` + `worker_lease_expired` 租约，**本身就是为多个消费者竞争同一张队列表设计的**，加守卫是错的 |
| agent-service | **不加**（撤销原计划） | 三处 `asyncio.create_task` 都是 fire-and-forget 的外部写入（fact_store 落 Redis + PG），不持有跨请求进程内状态 |
| terminal-bridge | **不重复加** | 守卫已在 `_helpers.tpl` 的 `hci.terminalBridgeGuard` 里，与 wildcard Origin 检查同处 |
| ops-agent-service | **无需守卫** | `deployment.yaml` 里 replicas 写死 1，没有 values 开关；要扩副本必须先改 values 驱动，届时补守卫 |

教训固化进 `replica-guards.yaml` 的注释：**守卫必须以源码证据为准，不能以「听起来有状态」为准。**

### 保守扩 5 个服务

`hci-platform-env/environments/staging/values.yaml` 给 5 个服务加 `replicaCount: 2`，
每个都附证据：auth-service（状态在 Redis/DB，无进程内态）、case-service（已有 DB 租约，
且 prod 侧先例为 2）、conversation-service（prod 先例为 2，`create_task` 是 fire-and-forget）、
customer-ui / admin-ui（nginx 静态 + 反向代理，无状态）。
其余 8 个保持 1 副本，由守卫或渲染结果说明原因。

它就是「文档里的命令必须实跑」这条规矩的存在理由。

### 上线后回归：`config.alloy` 缺逗号 → Alloy CrashLoop

第 23 处与前面 22 处性质不同：它不是「判据写错」，而是**这轮改动上线之后造成的真实中断**。
记在这里，因为它是「门禁只做正则」这件事的最终代价。

**现象**。合并（dc90ccf6）后第一次 ArgoCD 轮询，`alloy-pmwl2` 进入 `CrashLoopBackOff`：

```text
Error: /etc/alloy/config.alloy:188:29: missing ',' in field list
Error: could not perform the initial load successfully
```

日志采集因此中断约 3 分钟。指标与网关 5xx 采集不受影响（Prometheus 是另一条独立管线），
所以 SLO 面板不会亮——**采集器自己挂掉，恰恰是它自己采不到的那类故障**。

**根因**。对比合并前的 e157920d：`stage.json` 与 `stage.structured_metadata` 两张表本来每行
都以逗号结尾。72f1eedf 整块重写表内容时，把尾逗号一起删了。River 的规则是分裂的——
表项（`{ a = "x", b = "y", }`）**必须**逗号分隔，块体属性（`source_labels = [...]`）
**必须不**要逗号，抄错一半就是解析失败。

**为什么门禁没拦住**。同一份 `ci.yml` 当时有三条 Alloy 断言（命名空间白名单覆盖、
`values` 表只含有界字段、锚点自证），全绿。它们都是正则/字符串判据：能证明
「我写了我想写的字」，证明不了「这串字解析器收不收」。这是正则门禁的结构性上限，
不是漏写了某一条正则——再补十条正则也还是同一个上限。

**修复与新门禁**。

- 配置：两张表补回尾逗号，注释里直接写「漏逗号 = Alloy CrashLoop」；
- 门禁：[`check_alloy_syntax.py`](../../../scripts/ci/check_alloy_syntax.py) 把渲染出来的
  `config.alloy` 从 stdin 喂给 **alloy 自己的解析器**，rc=0 才算过；
- 解析器版本不写死：镜像坐标取自渲染结果里 Alloy DaemonSet 的容器镜像，与线上同版本；
- **双向自证**：每次运行先跑两份常量夹具——缺逗号的必须失败且报 `missing ','`，
  逗号补齐的必须成功。自证不过整体失败，绝不把「门禁自己坏了」读成「配置没问题」；
- 自测 [`test_check_alloy_syntax.py`](../../../scripts/ci/test_check_alloy_syntax.py)（8 例）
  专攻「门禁静默失真」：解析器永远 rc=0 / 环境失败 / 永远非 0 / 检查对象丢失。

**两个实测出来的坑（都改变了方案）**：

| 坑 | 实测现象 | 结论 |
|---|---|---|
| `alloy fmt --test` 当语法判据 | 语法修好后仍报 `Error: file /etc/alloy/config.alloy is not formatted correctly`、rc=1 | `--test` 比的是**排版风格**，helm 渲染出来的缩进必然不满足 → 用它等于永久假红。只用 `alloy fmt`（解析失败才非 0）|
| 「rc≠0 就说明检出了 bug」 | 第一版负例把两个 ConfigMap 挂到同一路径互相覆盖，`alloy fmt` 报 `stat ...: no such file`，rc=1 | 环境错误会冒充「检出 bug」。负例必须核对**报错文案**（含 `missing ','`），只看 rc 不算通过——与第 14 处同一条规矩 |

## 订正记录

### 订正一（2026-10-31）：「structured_metadata 不增 label 基数」与我对它的订正

本节有**两层**：上一轮我推翻了旧注释，本轮我又推翻了我自己那句推翻。只记第一层会留下
一个比原错更难发现的新错，所以两层都保留。

#### 第一层：被证伪的旧注释

| 位置 | 原断言 |
|---|---|
| `deploy/helm/hci-platform-obs/templates/configs.yaml` 的 `ingress_logs` 注释（本文改动前） | 「可检索字段提为 structured metadata，既不增 label 基数，又能直接按 service_name 过滤」 |

错在后半句：`service_name` 在网关链上的值是「网关自己」而不是后端（取证见上文
「`service_name` 标签的真实来源」）；前半句字面不错，但它在仓库里被当成了
「提什么字段都免费」的许可证，这属于注释的误用而不是注释的错。

#### 第二层：被证伪的我上一轮的订正

| 位置 | 上一轮写下的断言 | 本轮结论 |
|---|---|---|
| 本文、[部署设计](../部署设计.md)、[部署指南](../部署指南.md)、`configs.yaml` 注释、`ci.yml` 门禁注释 | 「`stage.structured_metadata` 的语义就是把抽取值**写成 Loki label**」 | **错**。它是 Loki 3.x 原生 structured metadata，不进 label 索引 |

证伪证据（四条命令同时跑，全部可复现，输出已记在上文「metadata 与 label 的分界」）：
`/labels` 全集只有 7 个不含这些键；`{downstream_status="503"}` 返回 0 条；
`{app="traefik"} | downstream_status="503"` 命中 3 行；`/label/duration/values` 返回空。

上一轮只拿了其中一条证据（`query_range` 把 3 行拆成 3 条返回流）就反推「它们一定是 label」，
这是典型的从单一现象倒推机制。同一个现象的兼容解释至少还有「原生 metadata 也参与结果分组」。

#### 现在能站住的心智模型

- `structured_metadata` **不是** label：不进 `/labels`，不能用 `{key="value"}` 选择，只能用
  `| key="value"` **标签过滤（label filter）**——注意它不是行过滤，行过滤是 `|=` / `|~`，
  匹配的是日志正文；查询语法必须这样写，否则会得到错误的 0 结果并误判为「无数据」；
- **写错 label 不报错，只安静返回空**：2026-10-31 实测
  `{namespace="kube-system", app_kubernetes_io_name="traefik"}` 返回 HTTP 200、**0 条流**（同一查询两次
  测量耗时 22.3 s 与 0.23 s，耗时不可作判据）；换成 `{namespace="kube-system", service_name="traefik"}`
  是 1 条流。流选择器只碰索引标签，未知键既不报错也不返回提示——因此**本项目文档里的每一条 LogQL
  判据都必须是真跑过的**，否则「0 条」会被读成「没有 5xx」。本文验收判据 #1 最初就是这么写错的（bug #17）；
- 但它**不是免费的**：实测它参与查询结果的 stream 分组（3 条 5xx = 3 条返回流；
  `hci-staging` 的 50 行 trace_id 日志 = 18 条返回流）；
- 因此字段取舍的判据从「会不会增 label 基数」改为「**有没有对应的索引收益**」：
  无界且原始行里已可查的字段（耗时、路径、客户端地址、时间戳）不提；
  有界且需要直接过滤的字段（状态码、路由名、后端服务名）提。
- 该约束由 CI 门禁 `helm-validate` 的「ingress_logs metadata 白名单」检查兜住，
  并因第二层翻车额外补了一条**锚点自证**（取到的表里必须有 `downstream_status`，
  否则报「门禁自己不可信」）——负例已实跑，见上表。

### 订正二（2026-10-31）：「网关重启可以从 5xx 指标看出」

#### 被证伪的原断言

上一轮在 [全量 preStop 与发布瞬间零 502](../../solution/events/2026-10-30-全量preStop与发布瞬间零502.md)
的思路里，默认「发布期间的用户损伤会以 5xx 的形式反映在 `traefik_service_requests_total` 上」。

#### 实测证据

1.07 秒空窗内 157 次 `ConnectionRefusedError` + 2 次 `RemoteDisconnected`，
同期 HTTP 5xx 计数为 **0**，accesslog 行数也为 **0**。

#### 正确的心智模型

5xx 指标与 5xx 访问日志都由**接收到请求的那个 Traefik 进程**写出。
TCP 层被拒时没有任何进程接收过该请求，两条观测通道天然不可能记录它。
所以「入口自身重启」的用户损伤只能由**客户端侧探针**量化；
服务端指标的 0 值在这里不是「无损伤」的证据，而是「无观测」的证据。
