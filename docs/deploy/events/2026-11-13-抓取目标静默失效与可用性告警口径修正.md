## 1. 起点：一个静默 7 天的 target

`up{instance="10.42.0.126:8000", job="hci-services"}` 恒为 0，Pod 是
`semantica/knowledge-explorer-5695f7fb8c-mp72p`。

隔离实验（同一目标、同一端口，只换发起方）：

| 发起方 | 结果 |
|---|---|
| 容器内 `127.0.0.1:8000/metrics` | 200，但 `content-type: text/html`，返回的是 SPA 首页 |
| 宿主机 `10.42.0.126:8000/api/health` | 200 |
| `semantica` 命名空间内临时探针 → `/metrics` | 200（同一份 HTML） |
| Prometheus Pod（`hci-observability`） | `connection refused` |

**定责**：

- **谁报错**：Prometheus 抓取 `10.42.0.126:8000/metrics` 被拒。
- **谁引入**：`semantica` 侧两处——`NetworkPolicy` 的 ingress 白名单只放行
  `kube-system` 与同命名空间 Pod（漏了 `hci-observability`）；同时应用没有
  `/metrics` 端点，SPA 的 catch-all 让所有路径假返回 200 HTML。
- **不是**：Prometheus 配置缺陷（三个注解都写对了）、也不是本仓 #1494 引入。

**关键判断**：只放行 NetworkPolicy 是错的修法。放行后只是把
`connection refused` 变成"解析 HTML 失败"，`up` 依然是 0。所以 semantica 侧
的完整补丁是**把 `prometheus.io/scrape` 显式设为 `false`**，让声明回到事实，
并把"将来接入指标必须同时做三件事"写进注释；本仓侧则补上能发现这类静默
失效的告警规则。详见第 3 节。

## 2. 顺带查出的另外两个同源缺陷

查 `service_name` 标签时实测：

```
count(up{job=~"api-gateway|case-service|conversation-service|scheduler-service|kb-service"})  → 空向量
count(up{job="kb-service"})                                                                  → 空向量
count(up{job="hci-services"})                                                                → 21
```

**本集群所有注解发现的 Pod 都归在同一个 `job="hci-services"` 里**，服务名在
`service_name` 标签上（`api-gateway`、`kb-service`、`traefik`、
`knowledge-explorer` 等）。所以：

- `ServiceDown`（`up{job=~"api-gateway|..."} == 0`，critical）——**自上线起从未执行过一次判断**；
- `KBServiceDown`（`up{job="kb-service"} == 0`，critical）——同样恒无数据；
- 而且原有规则只盯 5 个核心服务，其余十几个 target 掉线完全静默——这正是
  semantica 那个 target 能静默 7 天的原因。

这与 11-12 的 `DiskUsageHigh` 属于**同一失效模式**：规则写在、通道也在，
但表达式引用的序列根本不存在，而"没有数据"在告警层面与"一切健康"长得一样。

## 3. 改动

### 3.1 本仓（`deploy/helm/hci-platform-obs/rules/alert_rules.yml`）

| 规则 | 改动 |
|---|---|
| `ScrapeTargetDown` | **新增**：`up{job="hci-services"} == 0` for 10m，warning，覆盖所有注解发现的 target |
| `ServiceDown` | 表达式改为按 `service_name` 聚合：`sum by (service_name) (up{job="hci-services", service_name=~"api-gateway\|..."} ) == 0`；annotation 的 `{{ $labels.job }}` 同步改为 `service_name` |
| `KBServiceDown` | 改为 `up{job="hci-services", service_name="kb-service"} == 0` |

`ScrapeTargetDown` 用 `for: 10m`：Pod 正常重启只有秒级抖动，10 分钟不会误报；
而 semantica 这种持续 7 天的静默失效会被立刻抓到。

**已知边界**：`sum by (...) up == 0` 在"服务完全没有 target"（Deployment 缩容到 0、
Pod 被驱逐导致服务发现无目标）时同样返回空向量、不触发。要覆盖这种情况需要
`absent(up{...})`，本次未做，登记为后续项。

### 3.2 `deploy/helm/hci-platform-obs/rules/alert_rules_test.yml`

新增 6 个 promtool 用例：

- `ScrapeTargetDown`：正例（掉线 12m）、反例（健康）、反例（掉线 6m 未达 `for`）
- `ServiceDown`：正例（全部副本掉线）、反例（只有一个副本掉线，另一个健康）
- `KBServiceDown`：正例

**反向验证**：把两条规则里的 `job="hci-services"` 临时改成不存在的 job，
`ServiceDown` 与 `KBServiceDown` 的正例立刻 `FAILED`；还原后 `SUCCESS`。
这证明用例真的钉住了标签口径，而不是只跑绿。

### 3.3 semantica 仓库（另一个仓库，本次只给补丁未提交）

下表三个文件**全部属于 semantica 仓库**，分别位于该仓库 Kubernetes 配置的
aihci overlay 与 base 层，不属于本仓。此处只列文件名，不写成带目录前缀的
本仓相对路径，以免本仓 C3 文档门禁把外部仓库路径误判为"仓库路径不存在"。

| 文件 | 改动 |
|---|---|
| `patch-deployment.yaml`（aihci overlay 的 Deployment patch） | `prometheus.io/scrape: "true"` → `"false"`，并把三层坑写进注释 |
| `observability-notes.yaml`（同 overlay 的 ConfigMap 说明） | 修正"三个注解就是全部集成面"的错误说法，写明 NetworkPolicy 与 HTML fallback 两道阻塞 |
| `networkpolicy.yaml`（base 层 NetworkPolicy） | 修正 "Same-namespace traffic: prometheus scrapes" 的误导注释，说明 `podSelector: {}` 隐式限定本命名空间 |

验证：在 semantica 仓库执行 `kubectl kustomize deploy/kubernetes/overlays/aihci`
渲染通过，注解为
`scrape=false`，NetworkPolicy 的两条 ingress 规则完整保留（放行入口的规则没被
误删，否则网站会直接黑洞）。

## 5. 上线后的预期行为

semantica 补丁**尚未 apply**，集群里那个 Pod 仍是 `scrape=true`。因此本 PR
合并、ArgoCD 同步后，`ScrapeTargetDown` 会立刻 firing 一条针对
`10.42.0.126:8000` 的 warning——**这是正确的、也是一次自然的端到端验证**。
等 semantica 补丁部署后（Pod 重建、注解变为 false），该 target 消失，告警自动
resolve。

若用户希望保留 semantica 的指标接入，则需要按 semantica 注释里的三件事同时做：
应用实现真正的 `/metrics`、注解改回 `true`、NetworkPolicy 用 JSON6902 `/-`
追加放行 `hci-observability`。单独做其中任何一件都只会得到另一种形式的假接入。
