# 运行时代码完整性修复与防护

## 背景与问题

工单 `Q2026072748256` 在 PR #628 合并、镜像 `20260727-1349-8f7a79a` 部署、ArgoCD 显示 `Synced / Healthy` 后，仍重现两项旧行为：KBD 的 QFK `produces` 被“缺少 matcher”门禁过滤；`human_escalation` 确认仍被回传到 ops-agent 并以 404 → 500 → 503 失败。

运行时检查确认：2026-07-26 用 `kubectl create/patch` 写入的 ConfigMap 以 `subPath` 覆盖镜像文件。`conversation-service` 覆盖 `conversation_service.py`，`kb-service` 覆盖 `playbooks.py` 与 `main.py`，`agent-service` 覆盖 9 个 `/app/app`/`/app/shared` Python 文件。字段所有者是 `kubectl-patch`，而非 Helm/ArgoCD。

## 方案（WHAT）

1. 精确移除三个 Deployment 的 12 个源码 `volumeMount` 和 3 个 `cdd-code` volume，滚动更新服务。
2. 运行态断言新分支已实际加载：conversation-service 存在 `human_escalation` 本地确认分支；kb-service 存在 `has_match / has_produces` 互斥门禁；agent-service 存在 QFK 产出提取与 host→IP 归一化逻辑。
3. 仅在确认无其他工作负载引用后，删除 9 个 `cdd-*-code-20260726*` 临时 ConfigMap。
4. 在集群级 `hci-platform-infra` Chart 声明 `ValidatingAdmissionPolicy` 与 Binding。对 `hci-dev`、`hci-staging`、`hci-prod` 中 Deployment、StatefulSet、DaemonSet 的 CREATE/UPDATE，在 API Server 写入前拒绝任意 `/app/app/`、`/app/shared/` 或 `*.py` volumeMount。
5. 将策略存在性和源码卷挂载扫描加入发布后必检项。

## 决策依据（WHY）

选择 API Server 准入策略而非“更新旧 ConfigMap”或只增加告警：

| 方案 | 结论 | 原因 |
|---|---|---|
| 更新旧 ConfigMap | 不采用 | 延续镜像与运行代码双源，后续每次发布仍可能漂移 |
| 发布后巡检/告警 | 不单独采用 | 只能事后发现，无法阻止错误 Deployment 写入 |
| ArgoCD `prune` | 不足 | prune 处理资源归属，不能可靠清除另一个字段管理器写入的 Deployment 列表项 |
| ValidatingAdmissionPolicy `Fail + Deny` | 采用 | 在持久化前阻断任意卷覆盖源码，Kubernetes 原生、无额外 webhook 服务、适合该集群已支持的 v1 API |

该策略限制的是“运行时替换应用源码”，不限制镜像内源码、常规 ConfigMap 配置、数据卷或 Nginx 模板目录；范围与事故根因严格一致。
