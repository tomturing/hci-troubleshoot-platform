# hci-sim 制品晋级状态修复

## 1. 第一性原理解构

发布链只有三个不可混淆的事实：

1. **制品已构建**：某个 source SHA 生成了可验证的 OCI digest；
2. **晋级意图已持久化**：GitOps 候选声明希望环境使用该 digest；
3. **环境已部署**：ArgoCD Desired/Live 与 Pod 实际 digest 一致且健康。

创建 PR 不能证明第三项，重复构建也不能修复第二项。无关源码合并没有改变 hci-sim 构建输入，因而不得生成新制品。

## 2. 根因

`resolve_release_baseline.py` 仍以旧展示名 `校验 hci-sim immutable GitOps digest` 查找成功 job，工作流已经改名为自动钉入 job。Jobs API 无法匹配后，hci-sim 服务基线永久缺失；补偿逻辑在每个 `main` push 中无条件重建 hci-sim。每次重建又产生新 digest，最终形成“合并 → 重建 → 新 PR”的反馈回路。

旧实现还以 digest 作为 PR 幂等键。不同 digest 会创建不同分支，多个候选可以并存、冲突或乱序合并，不能表达“dev 当前只有一个待晋级版本”这一事实。

## 3. 修复后的状态机

```text
hci-sim 构建输入变化
        ↓
构建镜像并写入 OCI source revision
        ↓
校验 source SHA + digest
        ↓
创建或更新 ci/promote-hci-sim-dev 唯一 PR
        ↓
人工审查并合并
        ↓
ArgoCD 同步与运行态验收（独立状态）
```

无关 `main` 合并在第一步即停止，不触发 hci-sim 构建或 promotion。

## 4. 不变量

- hci-sim 服务基线只接受稳定机器名 `hci-sim-promotion-request`，避免展示文案漂移。
- 构建成功但 promotion 失败时不记录新服务基线，下一次补偿保持 fail-closed。
- 其他矩阵服务失败时仍检查 hci-sim 镜像是否真实存在；服务级基线可从部分失败的 completed run 恢复，但全局发布基线仍只接受整轮成功。
- promotion PR 的唯一键为 `service=hci-sim, environment=dev`，而不是 digest。
- 新候选强制更新固定分支，并关闭历史 `ci/pin-hci-sim-digest-*` PR。
- GitOps 清单同时更新 `digest` 与 `hci-platform.dev/image-source-revision`。
- CI 必须从镜像 OCI label 读取 source revision，并与触发构建的完整 `github.sha` 相等。
- tag 只用于发现 digest；拉取和身份校验必须使用同一个 `repository@digest` 不可变引用，避免检查期间 tag 被置换。
- 手动 promotion 只接受 `refs/heads/main`，feature 分支即使选择 dev 也不得写入 GitOps 候选。
- promotion job 成功只记录“晋级请求已持久化”，不得作为 ArgoCD 或 Pod 已部署证明。
- CI 对发布协议脚本运行独立 Ruff 与 pytest 回归，且测试直接校验基线机器名与 workflow 一致，禁止再次静默漂移。

## 5. 对抗性审查

| 攻击场景 | 预期防护 |
|---|---|
| 合并纯文档或其他服务 PR | 已有 hci-sim 基线且构建输入无变化，不进入构建矩阵 |
| 连续两次 hci-sim 构建 | 第二次 force-with-lease 更新同一 promotion PR，不新增候选 |
| 人工尝试合并旧 digest PR | 新 promotion 建立后自动关闭所有旧命名候选 |
| 镜像 digest 合法但来自其他源码 | OCI revision 与 `github.sha` 不一致，promotion job 失败 |
| 在解析 digest 后、拉取镜像前改写 tag | 拉取和 OCI 身份校验绑定已解析的 `repository@digest`，不再读取可变 tag |
| 清单只改 digest、不改 source revision | 不满足无漂移条件；更新器强制两个字段原子变化 |
| 利用文档豁免修改其他 annotation | 精确字段白名单拒绝，docs-governance 继续阻断 |
| promotion PR 已创建但 ArgoCD 未同步 | Summary 明确标记 pending，发布后必须另验 Desired/Live/Pod |

## 6. 可观测性与验收

GitHub Actions Summary 必须记录 source SHA、image digest、promotion PR URL 和状态语义。合并 promotion 后按以下顺序验收：

1. ArgoCD Desired manifest 的 digest/source revision；
2. ArgoCD Application 的 Sync/Health；
3. Pod `imageID` 的真实 digest；
4. 镜像 `org.opencontainers.image.revision`；
5. hci-sim 健康探针与关键请求链路。

本次只修复现有应用仓库内的异常发布反馈回路。将 hci-sim 声明迁入 `hci-platform-env`、与其他服务统一环境所有权，需作为独立迁移执行，避免同时改变发布协议与 ArgoCD 拓扑。

对应避坑规则：`docs/deploy/pitfalls/shell.md` D-026。
