# 网关 5xx 的度量维度盲区与 Loki 抓取补齐

> 一句话（P1）：**网关返回 503 时，Loki 里有日志、入口计数器在涨，但告警全静默**——
> 因为三条网关告警都只查 `traefik_service_requests_total`，而这类 5xx 走不到 service 层。

## 1. 怎么发现的

这不是计划内的排查。起因是复核「staging 三项改造是否闭环」时，有一条现象对不上账：

1. `index/stats` 显示 `hci-staging` 近 1 小时 12071 条、`hci-observability` 3389 条，
   而 `kube-system`（网关日志所在）**0 条**；
2. 近 24 小时查 `{app="traefik"} | json | DownstreamStatus >= 500` 得 0 条。

第一步先排除了「链路断了」：`{namespace="kube-system"}` 近 7 天有 593 条、3 条流，
且 `{service_name="traefik"}` 命中同样 593 条；用 `direction=backward` 取最后一条，
时间戳是 **2026-10-31T17:41:31Z**，与 `kubectl logs` 里 traefik 自己的最后一条
（`A new release of Traefik has been found`）**完全一致**，Pod `0 重启`。

结论：采集没断，是 **Traefik 这段时间确实没有输出**——
`--accesslog.filters.statuscodes=500-599` 只记录 5xx，而过去 8 小时没有 5xx。

但「没 5xx」和「采不到 5xx」在数据上长得一模一样，
所以必须做**正向注入**才能断言链路活着（这也是原验收判据 #1 的要求）。

## 2. 注入与意外

注入方式特意选了零镜像依赖的：建一个**没有 endpoint** 的 Service + 指向它的 Ingress，
请求必然被网关判为不可用。

```console
$ curl -sk -o /dev/null -w "%{http_code}" -H "Host: accesslog-probe.local" \
    https://127.0.0.1:18443/probe1     # 走 websecure（web 入口也启用了 TLS）
503
$ curl -sk -o /dev/null -w "%{http_code}" -H "Host: acli.sangfor.com.cn" \
    https://127.0.0.1:18443/           # 正向对照
200
```

Loki 侧完全符合预期：

```console
判据#1：返回流数 3 | 条目数 3   （/probe1 /probe2 /probe3，status=503）
判据#2：返回流数 1 | 条目数 3   （metadata: downstream_status=503 origin_status=0 router_name=…）
```

**问题出在 Prometheus 侧**：

```console
$ # 5xx 序列数（service 维度）
0
$ # 入口维度
web 503 3     websecure 503 10
```

同一个故障、同一时刻：**日志有、入口计数有、service 维度一条序列都没有**。

## 3. 是测试方法的问题，还是规则的盲区

必须先排除「我这种注入方式太偏门」。于是补了对照组——
Service **有** endpoint，但 `targetPort` 故意指到一个没人监听的端口（真实转发失败）：

```console
$ curl ... -H "Host: probe-backend-down.local"    # 3 次
502  502  502
$ # 40 秒后（等一轮 scrape）
service 维度 5xx 序列数: 1
  code=502  service=hci-staging-probe-backend-down-80@kubernetes  v=3
入口维度: websecure 502 3
```

并且告警**正常响了**：

```console
GatewayServerErrorFirstSeen: state=firing alerts=1
  -> {alertname:…, code:"502", service:"hci-staging-probe-backend-down-80@kubernetes", …}
alertmanager 中告警数: 1  - GatewayServerErrorFirstSeen | state=active
```

所以：

| 故障形态 | service 维度 | 既有三条告警 |
|---|---|---|
| 有 endpoint 但后端连不上（502） | 有序列 `v=3` | ✅ firing |
| **没有 endpoint（503）** | **0 条序列** | ❌ **全静默** |

后者正是「路由 host/path 写错」「Service selector 不匹配 Pod」「middleware 直接拒绝」
这类**配置类故障**——它们走不到 service 层，只会出现在
`traefik_entrypoint_requests_total` 上。

也就是说：`GatewayServerErrorSpike` / `GatewayServerErrorFirstSeen` /
`GatewayMetricsMissing` 三条都建立在 service 维度，对这整类故障**结构性失明**。
而且失明的表现恰好是「0 告警」——与健康态无法区分。

## 4. 为什么能确认「不是指标没开」

同一份数据里可以先验证两个维度的口径关系（这决定了修法能不能用减法）：

```console
code=200  entrypoint 47313 / service 47313   diff 0
code=201  entrypoint 2     / service 2       diff 0
code=401  entrypoint 9034  / service 9034    diff 0
code=403  entrypoint 7     / service 7       diff 0
code=404  entrypoint 7715  / service 7531    diff 184
```

- 2xx/4xx 差值**全为 0** → service 是 entrypoint 的真子集，两者口径没有额外偏差；
- 唯一不为 0 的是 404，差 184 —— 路由未匹配，**与 503 是同一类现象**。

这个验证同时否掉了一个看起来更简单的方案（见 §5.2）。

## 5. 修法

### 5.1 新规则：`GatewayRouterServerErrorFirstSeen`

```promql
(
  (sum by (code) (traefik_entrypoint_requests_total{code=~"5.."}) > 0)
  unless on (code)
  (sum by (code) (traefik_entrypoint_requests_total{code=~"5.."} offset 10m) > 0)
  unless on (code)
  (sum by (code) (traefik_service_requests_total{code=~"5.."}) > 0)
)
and on()
(count by () (traefik_entrypoint_requests_total offset 10m) > 0)
```

三段语义，逐段都可单独证伪：

| 段 | 语义 | 去掉会怎样 |
|---|---|---|
| 入口 5xx 有值 | 该 code 正在发生 | 规则永不触发 |
| `unless` 入口 offset 10m | **刚出现**，不是历史存量 | 退化成永久告警（反例二） |
| `unless` service 同 code | service 维度没有它 = **不是后端造成的** | 与 FirstSeen 重复告警（反例一） |
| `and on()` offset 有数据 | 数据连续性门控，防重启后成片误报 | 沿用既有守卫的理由 |

### 5.2 被否掉的做法：两个计数器做减法

`entrypoint 5xx - service 5xx` 看起来更精确，实测不可用：

```console
$ (sum by (code) (traefik_entrypoint_requests_total)) - on(code) (sum by (code) (traefik_service_requests_total))
code=404  diff=184
# 注意：code=503 根本没有出现在结果里
```

因为 service 侧**完全没有** 503 序列，`- on(code)` 找不到匹配的右操作数，
整条序列被丢弃——**恰好丢掉的就是本规则要抓的那一类**。
补齐右操作数（`or 0 * …`）能修，但会让表达式变成三段嵌套的数学技巧，
可读性换不来精度，故不取。

### 5.3 Loki 加抓取注解（顺带闭合一个开放项）

开放项「structured metadata 的分组发生在写入侧还是查询响应侧」一直无法定论，
判据是 `loki_ingester_memory_streams` 这类写入侧指标。实测：

```console
$ count(loki_ingester_memory_streams)
{"status":"success","data":{"resultType":"vector","result":[]}}   # 空向量，不是 0
```

Loki 从来没有 `prometheus.io/scrape` 注解 → Prometheus 的 `kubernetes_sd` 直接跳过它。
**「拿不到数字」被反复读成「没有这个指标」**，这才是那个开放项一直关不掉的原因。
本次给 Loki 的 Pod 模板补上 `scrape/port/path` 三个注解，让判据可查。

## 6. 门禁自证（每条都实跑过负例）

| 门禁 | 正例 | 负例 |
|---|---|---|
| `promtool test rules`（新增 `alert_rules_test.yml`） | 正例：入口新出现 503 + service 无 503 → **firing**，`SUCCESS` | ① service 维度也有 503 → 必须静默；② 503 早已存在 → 必须静默。删掉对应 `unless` 段后两者均 **rc=1 FAILED**；还原后 `SUCCESS`，md5 与改动前一致 |
| CI 渲染断言（Loki 抓取注解） | 渲染含三注解 → 通过 | 用 YAML 解析精确删掉 loki podTemplate 的三注解 → **rc=1**，报「缺 prometheus.io/scrape」 |
| CI 渲染断言（新规则存在） | 含 `GatewayRouterServerErrorFirstSeen` → 通过 | 改名冒充删除 → **rc=1** |
| CI 渲染断言（新规则的维度） | 引用 `entrypoint` → 通过 | 把 `entrypoint` 全替换回 `service` → **rc=1**，报「维度又退回 service」 |

> 期间抓到一次自己的假验证：第一版负例脚本用文本替换删注解，`replace(..., 1)`
> 命中的是**别的资源**上的同名注解，于是「删了注解却仍然通过」。改用 YAML 解析
> 定位 loki 的 podTemplate 后才真正失败。**验证手段本身也会空转，必须让负例先红。**

## 7. 边界（明确不主张的部分）

- 本规则只覆盖「service 维度**完全没有**该 code」的情形。如果同一个 code
  既然后端产生、又有网关自身产生（service 侧存在该序列），`unless` 会整体放弃，
  **混合场景仍然看不见**。要补需要 `increase()` 差值，而低流量下 `increase()`
  有首样本盲区（既有规则注释里已记录），另议。
- `gateway_availability` 组仍以 service 维度为主口径。本规则是**补充**，
  不替代 `GatewayServerErrorFirstSeen`——后者才是发布窗口的主要判据。
- 本次不动 Loki 保留期（`retention_period` / `compactor` 仍为空）。CI 里有一条
  显式断言：一旦配置里出现这两个键就失败，强制先改可观测性设计的 P1。

## 8. 遗留

1. 混合场景（同 code 双来源）的覆盖，见 §7。
2. `service_name` 泄漏到 `ingress_logs` 返回流的**机制层解释**仍未闭合
   （上一份事件文档的开放项 #1），本次没有推进。
3. 落地后需要在 staging 观察一次真实触发：本环境 503 序列已经存在，
   「刚诞生」的现场无法复现，因此线上验证以「规则已加载 + 表达式与单测一致」为准，
   不主张「已亲眼见过它 firing」。

### 9.1 一次会重演的误报：重建 Loki 会点亮 `AlloyLokiWriteRetriesHigh`

Loki 是 `Recreate` + 单副本，本次因 podTemplate 注解变化**重建了一次**（Pod 从
`76847b7c89` 换成 `bc59d47c4`）。重建窗口内 Alloy 的写入重试累计 **19 次**，把
`AlloyLokiWriteRetriesHigh`（`increase(loki_write_batch_retries_total[10m]) > 5`，`for: 2m`）
从 `pending` 推到 `firing`。

```console
$ # Loki 已恢复后的同一时刻
increase(..._retries_total[2m])        0        # 不再新增
increase(loki_write_sent_bytes_total[2m])  147731   # 写入正常
loki_write_dropped_bytes_total         0        # 无丢弃
$ # 10 分钟窗口滑出后
19 条规则全部 inactive（02:46:44Z 复查），Alertmanager 0 条
```

> 结论：这是**自身滚动部署的瞬态**，不是新规则或抓取注解带来的常驻噪声——但它会在
> 每次重建 Loki 时重演。看到这条告警，先问「最近 10 分钟有没有动过 Loki」，
> 再去查 Alloy 配置。

### 9.2 仍然不主张的

没有亲眼见到新规则 `firing`：本环境的 503 序列已经存在，「刚诞生」的现场无法复现，
§7 的边界在此同样适用。线上只主张「规则已加载、表达式与单测一致」，
表达式正确性由 `promtool test rules` 钉住。
