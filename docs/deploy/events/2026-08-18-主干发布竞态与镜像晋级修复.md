# 主干发布竞态与镜像晋级修复

## 背景

PR788 与 PR789 连续合并时，前一轮 main CI 已识别 `admin-ui` 需要构建，但被后一轮 main push 取消。后一轮与前一轮代码树相同，按相邻 commit 计算为零差异，导致镜像构建和环境仓库 tag 晋级都被跳过。ArgoCD 仍显示 `Synced/Healthy`，但它同步的是旧的 admin-ui 镜像 tag。

## 修复

- PR CI 保留自动取消；main 发布 CI 禁止被后续 main push 取消。
- main 发布计划从最近一次同时完成业务镜像构建和非生产晋级的 CI run 计算基线；找不到时才退回 `event.before`。
- admin-ui 镜像构建写入 `build-info.json`，并在镜像构建阶段断言 Bundle 工厂路由已进入最终静态资源。
- K3s 发布验证不再只检查 admin-ui HTML 返回 200，同时检查运行时静态 JS 是否包含 Bundle 工厂路由。
- 镜像发布统一采用“本地构建 → Trivy 扫描 → 推送”顺序。扫描失败只进入 SARIF
  和发布摘要，不会把正式 tag 写入 GHCR；只有构建成功才允许推送。
- `db-migrate` 同时分别记录 OS 层和 Atlas/library 扫描结果，避免数据库迁移镜像
  复用业务镜像的模糊安全结论。手动触发的 hci-openclaw 工作流也遵守相同顺序。

每个服务摘要都包含源码 SHA、镜像标签、扫描结果、推送结果和 run ID，便于按唯一
调用链回溯“构建了什么、扫描了什么、最终推送了什么”。

## 验收

发布后执行：

```bash
KUBECTL='k3s kubectl' bash scripts/ops/k3s-verify.sh
```

其中 `admin-ui: Bundle 工厂路由已进入静态资源` 必须通过；失败表示环境仍在提供旧镜像或旧静态资源，不能仅以 ArgoCD `Synced/Healthy` 判定发布完成。
