# DSH 诊断集成需求

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-22 | v1.0 | 初版：k3s 容器化部署 DSH、admin-ui 内嵌「DSH诊断」、挂载 /sf/log | 本文件 |

## 背景与问题

- **业务背景**：客户侧的 HCI 故障日志压缩包会统一回收到本机 `/sf/log/` 目录（属主 `support:support`，权限 755）。当前缺少一个能对这些日志做自动化分析并给出诊断结论的能力入口。
- **核心痛点**：
  1. 日志压缩包分散在宿主机目录，分析动作无法在线完成，依赖人工下载+本地分析。
  2. 分析结果没有统一的展示入口，排障人员需要在多个系统间切换。
  3. 缺乏可对外提供服务、可持续二开的载体。
- **影响范围**：排障工程师、运维人员。目标是让 HCI 故障日志分析在产品内闭环。

## 需求描述

- **功能概述**：将 DSH（DeepSeek Harness，开源 Agent 运行时）以容器服务形式部署到现有 k3s 集群，并在 admin-ui 中新增「DSH诊断」菜单内嵌其 Web UI，容器只读挂载宿主机 `/sf/log/`，使 DSH 能直接读取客户故障日志压缩包并给出诊断结论。
- **用户场景**：排障人员在 admin-ui 侧边栏点击「DSH诊断」→ 页面内直接出现 DSH 的 Web 界面 → 在其中对 `/sf/log` 下的日志压缩包发起分析 → 得到诊断结论。
- **预期收益**：日志分析与诊断在产品内闭环，无需本地工具；DSH 以容器化方式对外提供服务，支撑后续二开。

### DSH 术语澄清

DSH = **DeepSeek Harness**（`https://github.com/deepseek-ai/deepseek-harness`），版本 `0.2.1-rc.2`。它不是诊断工具，而是一个 **AI Agent 运行时**（everything-is-a-plugin 架构，基于 Cordis），包含 `shell`、`subprocess`、`ssh`、`computer-use`、`browser-use`、`terminal` 等能力包。本需求是借助其 Agent 能力完成日志分析诊断。

## 功能需求

1. **k3s 容器化部署**（必须有）
   - DSH 以独立 Helm Chart 交付，纳入现有 GitOps（ArgoCD Application）管理。
   - 支持后续二开：源码/配置在仓库内可维护。
   - 对外提供服务：通过 Traefik Ingress 在现有域名 `acli.sangfor.com.cn` 下暴露为 `/dsh` 路径。
2. **admin-ui 新增「DSH诊断」**（必须有）
   - 位置：侧边栏「可观测性」与「分类基线」之间。
   - 内嵌方式：参照现有「可观测性」中 Grafana / Langfuse 的 iframe 形式。
3. **挂载 `/sf/log/`**（必须有）
   - 容器挂载宿主机 `/sf/log/`，用途为 **DSH 读取其中的客户 HCI 故障日志压缩包进行分析诊断**。
   - 因用途为只读分析，采用只读挂载。

## 非功能需求

- **性能要求**：DSH Web UI 页面可正常加载与交互；WebSocket 长连接（Agent 流式输出）不被反代中断。
- **可用性要求**：Pod 重建后服务可自恢复；DSH 的 launch token 随进程变化，访问入口须能自动获取最新 token 而无需人工介入。
- **安全要求**：
  - DSH 的访问入口必须置于 admin-ui 的登录鉴权之后，不接受匿名访问（DSH 自身也不提供匿名模式）。
  - DSH 容器以非 root 用户运行。
  - 提供集群内网络隔离清单（NetworkPolicy）并说明当前生效情况。
- **可维护性**：全部清单纳入 Helm Chart 与 ArgoCD，配置集中在 values。日志、指标、链路追踪遵循现有可观测性设计。
- **可观测性**：容器日志输出到 stdout 供集群日志采集；提供健康探针。

## 验收标准

- [ ] 标准 1：集群内新增 DSH 工作负载，Pod 处于 Running 且就绪探针通过。
- [ ] 标准 2：浏览器访问 `https://acli.sangfor.com.cn/dsh/` 能加载 DSH Web UI 并完成会话建立（不出现 401 / 403）。
- [ ] 标准 3：admin-ui 侧边栏中「DSH诊断」显示在「可观测性」（order 4）与「分类基线」（order 5）之间，点击后页面内 iframe 可用。
- [ ] 标准 4：DSH 容器内可读取 `/sf/log/` 下的文件（只读），且不可写入该目录。
- [ ] 标准 5：全部部署清单以 Helm Chart 形式入库，并有对应的 ArgoCD Application 清单（local 与 cloud 两套）。
- [ ] 标准 6：DSH 的 launch token 通过 admin-ui 后端接口下发，且该接口受 JWT 管理员鉴权保护（未携带有效 JWT 返回 401/403）。
- [ ] 标准 7：相关文档（架构/部署/接口）已同步更新，文档门禁 CI 通过。

## 约束条件

- **技术约束**：
  - DSH 的 Web 监听器**禁止**绑定 `0.0.0.0`（官方在配置加载期直接拒绝 unspecified address），必须绑定具体地址。
  - DSH **无匿名访问模式**，访问必须经由 launch token 交换或已签发的 session cookie；launch token 为每个进程随机生成，且**不可通过环境变量固定**。
  - DSH session cookie 为 `Path=/; HttpOnly; SameSite=Strict`。
  - DSH 依赖 WebSocket 进行 Agent 流式输出。
  - 被嵌服务必须能接收来自同域的 iframe 嵌入。
- **资源约束**：当前设备为单节点 k3s（`aihci`），对外域名 `acli.sangfor.com.cn`。
- **依赖约束**：DSH 作为 Agent 需要可用的 LLM 服务凭证才能实际执行分析（本需求仅完成部署与嵌入链路，LLM 凭证由环境仓库注入）。

## 风险与假设

- **已知风险**：
  1. DSH 处于 developer preview，官方声明未经过安全审计（SAFETY.md）。
  2. 保留完整 Agent 能力（含 shell / ssh / computer-use）时，若被诱导执行，具备较大破坏面。
  3. 当前集群 CNI 为 flannel，NetworkPolicy 不会被强制执行。
  4. `hostPath` 与单节点绑定，后续扩容到多节点时挂载点行为会变化。
- **假设条件**：
  1. `/sf/log/` 在本机持续存在且属主/权限不变。
  2. DSH 上游 npm 包 `@deepseek-ai/dsh` 版本 `0.2.1-rc.2` 可用。
  3. 现有域名与 Traefik Ingress 路径可继续复用。
