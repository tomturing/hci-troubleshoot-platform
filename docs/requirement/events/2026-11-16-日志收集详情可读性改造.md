# 日志收集任务详情（只读）可读性改造

## 背景与问题

管理员在 admin-ui → 日志收集 → 工单详情 → 「日志收集任务详情（只读）」中反馈四类可读性缺陷，截图工单为 `Q2026111600624`（任务 `1a057c59-0620-4cb5-a071-cf273731ece5`）：

1. 「逐台明细」「结构化原文」显示空值或 `0`，管理员无法判断是任务未上报还是界面没读到。
2. 「链路定界」页签中的段/组件表是固定设计说明，问题描述列窄导致行高极大，且与具体工单无关。
3. S1-S8 时间线状态列无颜色区分；S1/S2 恒为「未知」，与数据库里已有的探针事实矛盾。
4. 「传输时间线」「网络探测」「进程日志」统一显示「该环节尚无上报记录」，不解释为什么没有。

## 需求描述

- 目标：详情面板必须区分「数据未上报」「上报失败」「未进入该环节」「平台未读到」，且不把平台读不到的事实伪装成现场失败。
- 用户场景：管理员打开任一工单只读详情，先看到可信的首个异常点与阶段状态，再按需展开证据与设计说明。

## 功能需求

1. 单任务详情接口的完整 `detail` 必须回写到抽屉，结构化原文给出可读 JSON；逐台明细为空时给出含义说明。
2. 固定设计说明移出常驻页签：在 S1-S8 标题右侧放感叹号，点击弹框阅读，弹框采用窄列友好的卡片布局。
3. S1-S8 状态列对成功/失败/未知等状态着色并保留文字标签；未知状态给出「无客观证据≠失败」的解释。
4. 四张证据页签的空态按归因码与 S7 状态给出准确原因，并附调用链 ID。
5. 修正管理端详情 SQL 的 detail 白名单，使 `derive()` 能看到探针字段，消除 S1/S2 假阴性。

## 验收标准

- [ ] 截图工单的结构化原文显示完整 detail JSON，不再出现 `0`/`{}` 裸值。
- [ ] 「逐台明细」为空时说明节点未回传逐台输出且不影响交付。
- [ ] 链路定界不再作为独立页签常驻；感叹号弹框可读且不出现横向长表。
- [ ] S1-S8 成功绿、失败红、未知灰，悬停未知可见解释。
- [ ] 截图工单的证据页签显示「证据上报失败，请按调用链查看上报错误」及调用链 ID，而非笼统「尚无上报记录」。
- [ ] 含探针的工单 S1/S2 由未知修正为成功；工单结论与统计分桶保持不变。
- [ ] 单测、类型检查、构建、真浏览器验收全部通过。

## 约束条件

- 页面严格只读，不出现删除命令或猜测的节点路径。
- 文案优先复用 `contracts/log_collect_display.json` 生成物；展示层颜色映射不得替代文字。
- 存量任务的 S7 失败是事实，不得伪造 manifest 或改写历史状态。

## 风险与假设

- 扩大列表 detail 字段会增加单行体积，但只增加探针等小字段，不拉回逐台明细/原始输出。
- S1/S2 由未知变成功是事实修正，不是结论口径变化；需要在方案文档中留痕。
