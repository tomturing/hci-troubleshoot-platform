# CI 最小激活与快速门禁需求

## 1. 背景与问题

CI 的第一性原理目标不是“让更多 job 运行”，而是对即将合入的变更提供足够独立、可重复、可追溯的证据。当前仓库存在三类偏差：

1. 一个模块变化会启动其他模块的全量检查；
2. 不同 job 重复 checkout、安装同一依赖或重复渲染同一产物；
3. 无关 job 的等待关系把并行验证人为串成一条慢链路。

这会同时增加 runner 调度时间、网络失败概率和 Actions 分钟消耗，并降低失败信号的可解释性。

## 2. 目标

### 2.1 PR 激活目标

| 变更类型 | 必须激活 | 明确不激活 |
|---|---|---|
| 仅 `hci_sim/**` | `hci-sim Go quality gate`、`published bundle and Helm gate`、`docs-governance` | `terminal bridge simulation-auth gate`、Python/前端/平台 Helm 测试 |
| 仅 `terminal_bridge/**` | `terminal bridge simulation-auth gate`、`docs-governance` | hci-sim Go、Manifest/Helm、Windows exe 构建 PR job |
| 仅 `deploy/helm/hci-sim/**` | `published bundle and Helm gate`、`docs-governance` | hci-sim Go、Bridge、平台 Helm 探针对齐 |
| 仅平台后端 | `Lint`、unit/integration/security、`docs-governance` | 前端、Helm（除非同时修改对应路径） |
| 仅 `frontend/**`（不含 CI 生成的 exe） | 前端检查、`docs-governance` | Python/Go/Helm |
| 仅文档 | `docs-governance`、文档命名、模块文档同步（按各自路径） | 代码、镜像、数据库、hci-sim |

跳过的 job 必须由 GitHub 记录为 `skipped`，不能通过删除必需检查名称来“伪造成功”。当前 main ruleset 的六个必需上下文名称保持不变。

### 2.2 时间与可靠性目标

- 不相关模块 PR 的 CI 关键路径目标：变更探测 + 文档门禁 ≤ 60 秒（不含 GitHub runner 排队）；
- 单模块 PR 的关键路径目标：只包含受影响门禁，依赖安装命中缓存时 ≤ 5 分钟；
- Python、Go、pnpm、Helm job 均设置有限超时，任何网络/工具卡死不得无限占用 runner；
- 同一分支新提交取消旧运行，避免排队运行已经过时的 SHA。

## 3. 非目标与事实边界

- 本需求不降低测试断言、不把安全扫描改成通过、不绕过数据库迁移验证；
- `main` 的发布构建、镜像推送和环境晋级仍由现有发布链路负责；
- 本轮不将本地命令替代 GitHub 独立 runner，CI 仍是合并门禁的独立证据；
- GitHub Hosted Runner 的排队时间不属于 YAML 可完全控制的执行时间，需单独观测。

## 4. 验收条件

1. 修改任一 hci-sim 子目录时，只有对应的 runtime job 被执行，其他 job 显示 skipped；
2. 修改 `terminal_bridge/**` 的 PR 不再执行 Windows exe 回写 workflow；
3. backend PR 的 unit/integration/security 不再等待 Helm 或探针对齐 job；
4. Schema 契约检查仍在 backend 质量门禁中执行，且不再单独安装一份 Python 依赖；
5. required status context（Lint、前端检查、unit-tests、security-tests、integration-tests、docs-governance）名称不变；
6. 所有变更后的 workflow 可通过 YAML/actionlint 检查，且本地等价命令全部通过。
