# hci-sim 阶段 E：产品级验证与规模化运营需求

## 1. 背景

阶段 D 建立通用 TestRun，不代表结果可信度、容量、稳定性和运营闭环已经达到产品级。阶段 E 以真实 HCI Oracle、差分测试、mutation、核心 KBD 覆盖、容量梯度和持续回归证明系统可用于规模化质量治理。

## 2. 产品目标

1. 证明 sim observation 与真实 HCI 在允许差异内契约等价。
2. 证明 Fixture/Matcher 不会因共同来源形成自洽假通过。
3. 证明 100+ Scenario 逻辑隔离和过载行为。
4. 建立 10～20 个核心 KBD 的 validated 基线。
5. 建立持续回归、漂移检测、质量趋势和运营责任制。

## 3. 功能需求

### E-FR-01 real/sim differential

- real 与 sim 必须是两个独立 Run，使用 `calibration_group_id` 关联。
- 比较层覆盖 command fingerprint、stdout/stderr shape、exit、变量、Matcher、Signal outcome、Conclusion 和证据引用。
- 允许差异和禁止差异必须版本化。
- 差异超阈值使 Bundle 进入 blocked/stale，不允许继续作为 validated 基线。

### E-FR-02 Mutation 测试

每个核心 Bundle 至少执行：

- 关键字删除/大小写/近似词；
- 数值阈值上下边界；
- stdout/stderr 移位；
- host/node/container/path 改写；
- producer 输出缺失/多值/类型错误；
- 命令参数变化和顺序扰动；
- timeout/permission/disconnect/truncation；
- Signal 顺序变化和依赖缺失。

Mutation detection rate 必须成为发布指标。

### E-FR-03 核心 KBD 认证

- 首批选择 10～20 个覆盖不同 Tool、Matcher、变量链和故障域的 KBD。
- 每个 KBD 必须有 owner、approved Artifact、published Bundle、variant matrix、差分结果和稳定性报告。
- 不能自动编译的 KBD 必须有 capability gap 和人工补充计划。
- “validated KBD”必须绑定确切 revision，不能只绑定 support ID。

### E-FR-04 稳定性和 flaky 治理

- Golden positive 每个核心 KBD 至少重复 20 次。
- 记录 pass rate、flaky rate、重试前后结果和失败分类。
- 禁止通过自动重试隐藏首次失败。
- flaky 超阈值时不得进入持续回归基线。

### E-FR-05 容量梯度

按 1/10/50/100/200 Scenario 梯度验证：

- p50/p95/p99；
- queue wait、reject、throughput；
- CPU/RSS/GC/goroutine；
- SSH session/channel；
- output bytes；
- cache hit/miss；
- Redis/CAS；
- cross-scenario contamination；
- timeout/cancel cleanup。

100+ Agent、100+ SSH Scenario 和 100 个浏览器是不同声明，必须分别验收。

### E-FR-06 持续回归与变更影响

- KBD/Signal/Tool/Policy/Compiler/Runtime/Bridge/Agent 变更可计算受影响 Bundle。
- PR 执行小型 affected suite；nightly 执行核心 suite；周期任务执行容量和 real/sim calibration。
- 退化必须阻断或生成带 owner/SLA 的显式豁免。

### E-FR-07 运营 UI 和报告

至少展示：

- KBD testability；
- 当前 validated revision；
- Bundle 状态和 stale 原因；
- 最近 Run/variant；
- Signal/Conclusion 指标；
- mutation/differential/flaky；
- 容量和成本；
- capability gap；
- owner 和待办。

### E-FR-08 SLO 和告警

定义并监控：

- Runtime availability；
- Fixture hit/miss；
- lease reject；
- queue overload；
- TestRun success/inconclusive；
- stale backlog；
- mutation detection；
- differential drift；
- cross-scenario contamination；
- cleanup leak。

任何串线、真实 HCI 非预期访问或 secret 泄漏都属于 P0 安全事件并立即停止测试。

## 4. 非功能需求

| 编号 | 要求 |
|---|---|
| E-NFR-01 | 所有产品声明必须由可重复证据支持，禁止把设计或单次通过写成已完成。 |
| E-NFR-02 | 容量参数以实测更新，不以初始假设作为结论。 |
| E-NFR-03 | 结果和报告可长期追溯到代码 SHA、镜像 digest、KBD revision 和 Bundle digest。 |
| E-NFR-04 | prod 默认不部署 sim；校准真实 HCI 必须只读、授权、限额和审计。 |
| E-NFR-05 | 数据保留、脱敏、删除和访问控制符合平台安全规范。 |

## 5. 产品级完成定义

只有同时满足以下条件，才可宣称“支持指定 KBD 自动构建仿真环境并验证效果”：

- 指定 support ID 可解析当前 revision；
- Compiler 可生成或明确拒绝并说明 gap；
- Bundle 经机器门禁和专家发布；
- Scheduler/Runner 完成真实 Bridge/Agent E2E；
- expected/actual、mutation 和 differential 可解释；
- 核心 KBD 稳定性达标；
- 100 Scenario 容量和零串线通过；
- 可持续运行而非一次性脚本。

## 6. 范围外

- 不承诺完整 HCI 内核、网络拓扑或所有强状态故障的虚拟化。
- 不用 sim 取代真实 HCI Oracle。
- 不把 100 Scenario 等同 100 浏览器。
- 不允许未审核 Bundle 进入持续回归基线。

## 7. 验收标准

- [ ] 10～20 个核心 KBD 达到 validated revision 状态。
- [ ] 每个核心 KBD 的关键 variants、20 次稳定性和 mutation 达标。
- [ ] real/sim differential 有版本化允许差异并通过。
- [ ] 1/10/50/100/200 容量报告完整，100 场景零串线。
- [ ] 过载、timeout、cancel、Pod 重启和 Redis 故障均显式降级且不污染其他 Run。
- [ ] PR/nightly/周期校准流水线运行并产出趋势。
- [ ] testability、stale、gap、flaky、drift 和 owner 可在运营入口查看。
- [ ] 安全演练证明无真实凭据泄漏、无 sim→real fallback、无非预期真实 HCI 访问。
