# KBD 27123 三信号执行闭环需求

## 背景

工单 `Q2026072747493` 命中分类 `虚拟机-003` 和 KBD `27123`。该 KBD 只有三个信号：

1. `qkv_task` 查询最近一次虚拟机启动失败任务，产出 `VM/HOST/END`；
2. `qfk_system` 在 `HOST` 执行 `lsof`，按 `VM` 定位占用进程并产出 `PID`；
3. `qfk_system` 查询 `PID` 对应进程，产出 `PNAME`。

人工回归发现：页面长期显示“正在等待输出……”，QKV/QFK 参数列表为空，terminal_bridge 只看到 `platform node list` 而没有 KBD 声明的 `task get`，变量链无法继续。

## 必须满足的产品需求

1. KBD QKV 是一次可审计的现场 acquisition，必须真实执行声明的 aCLI 命令；预取环境事实不能静默代替。
2. 每个工具卡片必须显示参数，并在成功、失败、超时、流中断时进入明确终态，不能永久 `running`。
3. 非 JSON 大输出不得先完整穿过 terminal_bridge、WebSocket、浏览器和 HTTP 后才提取；安全行筛选应尽量靠近输出源流式执行。
4. 安全转换能力不开放 `|`、grep、awk、正则或脚本执行，只接受平台定义的字面量行筛选协议。
5. `QKV` 必须只有产出变量且 `match=null`；`QFK` 必须在关键字判断和产出变量之间二选一。
6. 工具调用和结果必须以同一个 `exec_id` 关联并持久化，参数、结果、状态字段在 Agent、conversation-service 和 Custom-UI 间一致。
7. KBD 27123 的三步变量链必须通过自动测试；人工只需新建工单、建立 SSH、选择分类，即可一次完成。

## 验收标准

- terminal_bridge 日志依次出现 `task get`、`platform node list`、`lsof`、定向 `ps -p ...`。
- `task get` 规范化后为 `acli --formatter json task get -k 启动虚拟机 -s failed -l 1`（是否显示 shell 引号不影响语义）。
- 页面三张卡片的参数非空，均不残留“正在等待输出……”。
- 变量池依次出现 `VM/HOST/END/PID/PNAME`。
- `lsof` 即使产生数十 MB 原始输出，也只回传 VM ID 命中的行；无命中、筛选后仍超限、超时均 Fail Closed。
- 保存/发布带有 QKV 残留 matcher 的 KBD 时返回 422；运行时快照也不得把它标为可执行。
