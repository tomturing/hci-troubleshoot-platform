# KBD 关键信号抽取反馈闭环与版本治理需求

## 背景

专家在 KBD30880 重新抽取关键信号后发现两个相互关联的问题：

1. 页面显示“相对 AI Proposal 修改 36 项”，但本轮只有 AI 重抽，专家尚未作任何修改；
2. 新 Proposal 丢失历史版本能够识别的 `qkv_task`，并生成读取配置文件全文、产出 `GPU_INFO_CONTENT` 但没有任何下游消费者的 `qfk_system` producer。

进一步讨论产生了版本治理问题：数据库究竟应只保留“当前 AI Proposal + 当前专家稿”，还是保留全部历史；页面数字代表完整版本内容还是只代表差异数。

## 产品语义

### 专家修改统计

“专家修改：N 条关键信号”的唯一含义是：

```text
当前专家稿相对它所审核的 AI Proposal 基线，
新增、删除或修改了多少个稳定 signal_id。
```

- 同一信号修改多个内部字段只计 1 条；
- AI 重抽产生的 AI→AI 变化不得计入专家修改；
- Prompt、模型指纹、Tool Contract、Evidence 元数据变化不得计入；
- 当前没有专家稿时必须为 0；
- 重抽完成后页面必须刷新 revision 和校验状态，不能继续显示上一轮数据。

### 页面与数据库的边界

- 专家主页面只展示当前 AI Proposal、当前专家稿，以及必要时折叠的当前生效版；
- 页面差异数只是由两份完整快照计算的摘要，不是版本存储本身；
- 后台应保留对模型改进有价值的不可变历史，但保留历史不等于允许其自动进入训练集；
- 不允许按 history 第一项、最后一项、相邻版本号或当前 latest proposal 猜测专家基线。

## KBD30880 抽取验收

KBD30880 的案例语义简单，重新抽取目标为：

```text
1 条 qkv_task：失败任务生产 HOST、VM
2 条 qfk_system：分别判断配置文件中的两个诊断事实
```

并满足：

- 不生成配置文件全文的无人消费 producer；
- QFK 直接判断配置事实时使用 matcher，而不是产出全文变量；
- 故障截图和正常参考截图各自保持正确证据边界；
- 所有自动生成的 QKV/QFK 默认 timeout 为 120 秒；
- `qfk_system` 使用 `command + command_args`，不生成 `resource_keyword`；
- 不以 `support_id=30880` 编写硬编码特判。

## 持续学习目标

持续优化 LLM 至少需要保留以下事实链：

```text
Source/Evidence
→ exact Model/Prompt/Tool Contract
→ AI Proposal
→ Expert Revision + 修改原因
→ Published Runtime Revision
→ 实际运行 outcome
```

只保留当前两份内容会丢失模型回归和 Prompt 版本效果；无差别把所有自动保存都作为训练样本则会造成重复、半成品和错误标签污染。因此需要将“活动状态”“不可变血缘”和“训练/评估数据集”分层治理。

## 非目标

- 本轮不建设重型审批流、双审或完整 Event Sourcing；
- 不把当前未认证审核稿宣称为 Expert Gold；
- 不直接物理删除历史 revision；
- 不把静态 Schema 校验冒充真实客户环境执行；
- 不在本轮实现自动 GC，保留期清理必须在引用完整性和数据集锁定机制完成后单独上线。
