# 日志收集：交付路径设置 与「已采集完成」补交付

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-27 | v1.0 | 初版：把交付路径（P1/P2）从"前端内存态"升级为可落库的任务属性；明确「acli 已采集完成」时补交付必须走 P2 direct，不重新下发采集 | 无 |

---

## 一、背景与问题

用户提出的两件事，落到代码上其实是两个不同层面的缺口：

1. **交付路径可选**：面板已有 `P1 直传日志服务器 / P2 经平台中转` 单选（`LogCollectPanel.vue` 交付路径表单项），但选择结果**没有落到任务上**——创建任务时只把 P1 变成 `remote_url`，`upload_mode` 要到交付完成时才被 PATCH 写入。后果：
   - 采集过程中的任务、以及交付失败的任务，`upload_mode` 为空，结果页对 P2 显示「未记录」；
   - P1 直传失败降级 P2 之后，库里只剩 `bridge_relay`，无法区分"用户本来就选 P2"与"P1 失败后降级"；
   - 事后审计只能靠 `remote_url` 反推，而 `remote_url` 又是"上传地址"不是"交付决策"。

2. **已采集完成后无法直接上传**：`acli` 侧采集已 `completed`、压缩包仍在节点磁盘，而平台没有任何产物（`archive_path` 空、`delivery_status=none`）。此时面板给出的唯一出口是「重新收集」。这不是交互问题，是**能力缺口**：包已经在盘上，物理上只需要"搬走"，却被要求重采一遍（几分钟到几十分钟 + 重新占用集群 IO）。

## 二、需求描述

### 2.1 交付路径可设置且可追溯

- 创建收集任务时必须显式声明交付路径：`P1 直传日志服务器`（`acli_direct`）或 `P2 经平台中转`（`bridge_relay`）；
- 该选择在任务创建那一刻落库，采集过程中即可在平台侧读到；
- 交付路径实际发生切换（P1 直传失败 → P2 中转）时，必须留痕：谁切了、切到哪、为什么。

### 2.2 已采集完成 → 直接上传，不重新下发采集

- 判据是**节点物理事实**：`acli log_collect progress` 报 `completed` 且压缩包存在（bridge 侧进一步校验 zip 完整性）；
- 命中时平台提供「上传到平台」入口，点击后直接走 P2 中转（拉包 → 分片上传 → 代传 5888）；
- 全程**不得**：重新下发 `log_collect create`、把平台采集状态改写回 `collecting`、重新轮询 `progress` 等 completion。

## 三、功能需求

| # | 需求 | 优先级 |
|---|------|--------|
| F1 | 创建任务携带 `upload_mode`（P1/P2），服务端校验与 `remote_url` 一致（P1 必带地址，P2 不得带） | 必须 |
| F2 | 结果态/对账态识别「平台已完成但无交付证据 + 节点仍有包」，给出「上传到平台」入口 | 必须 |
| F3 | 补交付使用 bridge `delivery_mode=direct`，跳过"等采集完成"，不改采集状态机 | 必须 |
| F4 | 补交付成功后 `upload_mode=bridge_relay`、`delivery_status=delivered`，结果页显示实际交付路径 | 必须 |
| F5 | P1 直传失败降级 P2 时，`detail` 记录原路径与降级原因（服务端合并写，不覆盖基线指纹） | 必须 |

## 四、非功能需求

- **可观测性**：补交付入口点击、`delivery_submit(direct)`、代传终态必须各有一条带 `case_id/task_id` 的日志；沿用既有 `log_collect.*` / `delivery.*` 事件名，不新增盲目指标。
- **幂等**：重复点击不得产生第二个上传会话（`/deliver` 已有非 force 短路 + `begin_delivery` 计数）；
- **不依赖浏览器**：交付提交后由 bridge 作业继续执行，关页面不影响。

## 五、验收标准

- [ ] 选 P1 创建 → 任务 `upload_mode=acli_direct` 且 `remote_url` 非空；选 P2 → `upload_mode=bridge_relay` 且 `remote_url` 为空（创建后立刻可查）。
- [ ] 构造"节点采集完成 + 压缩包在 + 平台 completed 无产物"场景，面板出现「上传到平台」按钮；点击后 bridge 侧日志为 `delivery.direct_ready`（不是 `delivery.collect_finished`），平台任务不被改回 `collecting`。
- [ ] 补交付成功：平台 `delivery_status=delivered`、`relay_status=success`、`upload_mode=bridge_relay`，结果页交付路径显示「P2 经平台中转」。
- [ ] 包已被删除（P1 直传成功）时不得出现「上传到平台」，文案说明包已移除。
- [ ] P1 失败自动降级 P2 后，任务 `detail` 中有降级记录，且原 `baseline_report_hash` 未被清掉。

## 六、约束条件

- **P1 无法补传**：`acli` 的上传是 `log_collect create -u` 的同一次执行，没有独立"重传"子命令。因此"已采集完成后的补交付"只存在 P2 一条路，UI 不得提供 P1 选项。
- 不新增数据库列（`upload_mode` / `detail` 已存在），避免为一个语义修正引入迁移。
- 不改 bridge 的 `direct` 实现（已具备 stat + zip EOCD 完整性校验），只把前端接上。

## 七、风险与假设

| 风险/假设 | 说明 |
|---|---|
| 假设：`completed` 平台上不等价于"已交付" | 2026-10-27 现场已证明二者会背离（`completed` + 零产物）；因此引入"交付证据"判据，而不是新增状态 |
| 风险：对账轮询（30s）频繁读 progress | 既有行为，本次不加大频率；补交付只由用户点击触发 |
| 风险：`direct` 模式移除"串味判定"保护 | 由 bridge `verifyArchiveComplete`（zip EOCD）+ 前端路径来源（本次任务 progress 的 `archive_path`）共同保证 |
