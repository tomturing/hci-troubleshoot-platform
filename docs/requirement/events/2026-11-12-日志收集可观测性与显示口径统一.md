## 背景与问题

### 现场证据（staging，2026-11-12）

| 工单 | 任务 | 落库状态 | 真实事实 |
|---|---|---|---|
| Q2026111201130 | `519c8644…` | `completed` / `progress=100` / `delivery_status=none` | 节点报「收集任务已完成！」，但 `archive_exists=false`、`archive_probe_level=missing`，`stat`+`ls` 双证包不存在；平台零产物 |
| Q2026111201130 | `9c2701f2…` | `collecting` / `progress=0` | 880+ 次轮询恒为 running，无任何字节传输；WS 断开后悬挂 |
| Q2026111200624 | `3e3b5c8b…` | `completed` / `delivery_status=none` | 产出 608 字节包，从未交付 |
| Q2026111200624 | `3666833a…` | `completed` / `delivered` / `relay=success` / `verified` | 交付链路无损，但包内仅 `_members`、`cfgmaster_ini` 两个配置条目，无主机日志 |

两单均为 P2（`upload_mode=bridge_relay`）。0624 全链路 sha256 四点一致（节点源包、桥本地副本、平台成品、5888 链尾），证明**传输无责、空包在 acli 采集源头**；1130 **零字节传输**，排除带宽，卡在 acli 生成 zip 之前，并被「节点文案即完成」的状态机放大成假成功。

### 面板矛盾（管理端截图）

同一行同时出现「P2 中转 / 已完成 100%」「包大小 —」「交付结论 未开始」「日志服务器真实进度 —」。汇总条 `168` 与分桶 `5 + 82 + 5 + 54 = 146` 无法对账。

### 根因（第一性原理）

1. **两套状态机 + 两个写入者**：`status/progress` 由客户前端经公共 PATCH 自由写（`backend/case-service/app/routes/log_collect.py:926-938`），`delivery_status` 只有服务端权威路径可写。二者被并排展示成同一件事。
2. **「完成」被压成一个枚举**：执行阶段与业务结论物理不同步，单枚举装不下「交付成功但产物异常」「采集中但已停滞」等组合态，界面只能二次拼接，口径必然漂移。
3. **没有产物证据层**：全链路只校验 sha256 与体积存在性，没有 manifest 级内容证据，故 608 字节空壳被判 success。
4. **没有速率/ETA 数据**：全仓无 `*_bytes_per_second`、`eta_seconds` 字段；`pulled_bytes` 仅存在于浏览器内存。
5. **探测只有单次连通性**：仅 `curl` 一次 `http_code/latency_ms`，无丢包/抖动/带宽，无法事先告知客户网络是否够用。
6. **进程日志无回传通道**：`/sf/log/today/acli/plugins/log_collect/` 全仓 0 命中；`sftp_op` 只落 bridge 本机，`/api/bridge-logs/upload` 需人工选文件。
7. **常量三套、终态集合四份、体积格式化三套**：`frontend/shared` 中日志收集常量 0 命中，三处界面各自硬编码。

## 需求描述

### 1. 平台显示完整修改（P0）

- 以「执行阶段 / 业务结论 / 条件」三维表达，取代单枚举：`phase`（互斥按序）、`conclusion`（互斥终态）、`conditions[]`（多值并存）。
- **结论只由证据推导**：`completed` 文案不再等于成功；无产物即 `failed`，包内容异常则不得展示绿色成功。
- 统计必须**互斥完备可对账**：`total = Σ在途 phase + Σ终态 conclusion`；`conditions` 只做交叉筛选。
- 收口写入权威：前端只能提交 `node_observed` 观测事实，`status/progress` 由平台状态机按证据推导；保留旧字段与旧 API 语义以兼容存量。
- 前后端共用同一份常量/文案/体积格式化规则，禁止两侧各写一份。

### a. 网络稳定性与带宽探测（P1）

- P1、P2 下发前均由 `terminal_bridge` 探测客户环境到目标端的网络质量。
- **分目标**：节点→日志服务器(5888)、节点→平台数据面(4443)；**按 `upload_mode` 决定哪些目标参与判定**，避免「5888 不可达但 P2 走 4443 正常」被误报为网络差。
- 指标：多次采样的成功率、RTT min/avg/max、抖动、丢包率、上行/下行带宽、分级（优/中/差）与建议。
- 网络不佳时在 custom-ui 明确提示（含预计上传耗时与替代建议），不阻断流程。
- 探测结果落库，管理端可查。

### b. P2 各阶段速率 / 百分比 / 耗时 / ETA（P1）

- 采集（acli，无平台字节流）→ 拉取（节点→bridge）→ 上传（bridge→平台）→ 代传（平台→5888）逐跳展示：当前速率、已完成百分比、已耗时、预计完成时间。
- custom-ui 实时（秒级）感知；数据同时入云端，管理端可在列表中看到阶段、速率、进度、耗时、预计完成。
- 采集阶段与 P1 直传明确标注「不适用」，不得编造数字。

### c. acli 完成后 zip 内容探测（P1）

- acli 报完成后，对 HCI 侧 zip 做内容级探测，产出 `artifact_manifest`（条目清单、总字节、sha256、加密标记）。
- 无包、包过小、无有效日志条目、清单与期望不符时，custom-ui 及时提示，且业务结论不得为成功。
- 只读中央目录，不做全量解压；加密包不得因 `unzip -t` 失败被误判损坏。

### d. 采集进程日志回传云端（P1）

- 无论成功失败，acli 收集结束后将各采集主机 `/sf/log/today/acli/plugins/log_collect/` 下的文件同步到云端数据库。
- 运行期持续采集 + 本地磁盘 spool，终态补一轮，避免「失败时目录无文件/进程被 TMOUT 杀掉」导致证据丢失。
- 目录为空或无文件时也要落一条 `empty` 记录，以区分「没日志」与「没回传」。
- 单文件与单任务总量设上限，超限截断并标记；敏感信息脱敏；只读，不执行任何删除/写入。

## 约束条件

- Python 使用 uv，前端使用 pnpm，Go 侧 `go test -race`。
- DDL 只能改 `database/desired_schema.sql` / `desired_extras.sql`，DML 走 `database/data-migrations/065_*.sql` 起（061–064 已占）。
- 新增运行时 env 必须登记 `deploy/config/config-contract.yaml`。
- 文档与代码同 PR；bridge 侧能力需随 exe 重建并现场重装才能到达客户机。

## 风险与假设

- **假设**：`d` 项各主机进程日志已由 acli 汇总到发起节点目录；实现为可插拔目录扫描器，若需逐台 SSH 扇出可扩展（需另行验证主机清单与权限）。
- **风险**：收回写入权威会触碰 `logCollectSync.ts` 的 `patch_completed` 分支，是全案唯一高风险点；通过保留旧字段/旧 API 语义 + 双写断言验证控制。
- **风险**：`fix/p1-archive-verify-honest` 分支（未合并）改动 `log_collect.py`、`LogCollectPanel.vue`、`logCollectDelivery.ts`，实施时需避开其已改段落并保持可 rebase。
- **风险**：旧版 bridge 不认识新增字段，必须做能力协商与降级展示。
