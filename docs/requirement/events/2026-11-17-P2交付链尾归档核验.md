# 2026-11-17 P2 交付链尾归档核验需求

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-11-17 | v1.0 | 初版：用 5888 `/archive_status` 作为 P2 交付终态判据 | [方案](../../solution/events/2026-11-17-P2交付链尾归档核验.md) |

## 背景与问题

全库 458 个任务 / 251 个唯一工单使用 `GET /archive_status` 逐单核对后发现：4 张任务在平台侧为 `delivered`（其中 2 张 P2 为 `relay_status=success`），但 5888 上并无归档。根因是 P2 只把 relay 回执当成交付终态，而 relay success 只证明"平台把字节发完"，不能证明"包在日志服务器落盘"。

同时确认 5888 对早期工单日志有水位驱动的正常清理机制。因此不能把"现在查不到"直接等同于"当初没成功"：对新任务必须在落盘时刻取证，对历史任务不能批量反转结论。

## 功能需求

1. 确认 `/archive_status` 的真实检查逻辑与返回边界，文档化它回答的是什么、不回答什么。
2. P2 relay success 后，写 `delivery_status=delivered` 之前必须调用 `/archive_status` 做链尾核验。
3. 核验通过才写 delivered；未通过写 queued 并给出明确原因，不得伪造交付成功。
4. 核验结果以快照形式落库（是否通过、原因、文件名、体积、mtime、探测次数、时间）。
5. 探测策略：新任务单任务探测、有界重试；已确认成功的任务不得重复探测；不做周期性全表轮询。
6. 历史任务不因后续正常清理被自动改判；历史对账只作为只读报告。

## 验收标准

- [ ] `/archive_status` 的检查路径确认为 `/sf/log/{工单号}/`，候选为精确名或带时间戳的同工单 `.zip`，返回 mtime 最新一条。
- [ ] 新 P2 任务成功前调用 `/archive_status`，请求文件名为 `Q{工单号}.zip`。
- [ ] 归档存在且体积足够时写 delivered；缺失/截断/历史同名包不写 delivered，写 queued 与 `归档链尾未确认` 条件。
- [ ] 归档确认快照写入 detail 且客户端 PATCH 不能覆盖。
- [ ] 只做一次有界探测（最多 3 次，仅 `archive_missing` 重试），确认成功的任务不再进入探测。
- [ ] 历史工单在没有任何确认快照时维持原展示口径，不因清理批量翻转。
