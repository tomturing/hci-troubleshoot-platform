# 日志上传统计口径修复与僵尸任务清理

## 变更历史

## 背景与问题

### 业务背景
管理端「日志上传」面板展示所有工单的日志收集与上传情况。面板汇总条包含：总数、传输中、已交付、未核验、失败、P1直传/P2中转、传输中P1/P2。

### 核心痛点
通过 staging 数据库实测（30 天范围，343 条任务），发现三个严重问题：

1. **「传输中」虚高 42 个（53 中仅 1 个真正正常）**
   - 统计口径 `_TRANSFERRING` 用 `OR` 条件：`status IN (活跃) OR delivery_status IN (queued,...)`
   - 当采集已终态（failed/completed/cancelled）但 `delivery_status` 仍为 `queued` 时，任务被错误计入「传输中」
   - 实测：42 个任务采集早已终态（23 failed + 12 completed + 7 cancelled），但 delivery 停在 queued 几百小时不推进

2. **42 个僵尸 delivery_status=queued 永远不会自然推进**
   - 这些任务的 bridge 侧早已无人在跑，queued 状态无人清理
   - 面板数字永久虚高，运维无法判断真实在途量

3. **64.4% 的失败任务没有 error_code（76/118）**
   - bridge 侧和 case-service 写 `error_message` 时未同步写 `error_code`
   - 导致无法按错误码聚合分析，归因缺失

### 影响范围
- 面板统计数字不准确，误导运维决策
- 僵尸任务占据列表，真正在传的任务被淹没
- 失败原因不可量化，无法定向优化

## 需求描述

### 功能概述
1. 修复统计口径：采集已终态的任务不应计入「传输中」
2. 清理历史僵尸数据：把 42 个僵尸 delivery_status 从 queued 改为正确终态
3. 补齐 error_code：代码层确保后续所有失败任务都有 error_code

### 用户场景
- 运维人员打开面板，看到的「传输中」数字应该真实反映正在传输的任务数
- 失败任务应该有明确的错误码，便于按码聚合分析

## 功能需求

1. **统计口径修复（显示问题，必须永久修复）**
   - `delivery_status=queued/pulling/uploading/relaying` 只有在 `status` 也是活跃态（非 failed/completed/cancelled）时才算「传输中」
   - 修复后面板数字必须与真实在途量一致

2. **僵尸数据清理（一次性数据订正）**
   - 对 `status IN ('failed','cancelled') AND delivery_status='queued'` 的任务，delivery_status 改为 `failed`
   - 对 `status='completed' AND delivery_status='queued'` 的任务，delivery_status 改为 `failed`（已 completed 但交付未启动=交付失败）
   - 必须写审计记录到 detail.data_correction

3. **error_code 补齐（代码层修复，确保后续不再出现空码）**
   - 所有写入 error_message 的路径必须同步写入对应的 error_code
   - 已有 error_message 但无 error_code 的历史数据，按 message 模式批量回填

## 验收标准

- [ ] 面板「传输中」数字只包含采集活跃且交付未终结的任务
- [ ] 42 个僵尸 delivery_status=queued 全部清理，面板「传输中」从 53 降到真实值
- [ ] 新增失败任务 100% 有 error_code（代码层保证）
- [ ] 历史 76 个空码失败任务按 message 模式回填 error_code
- [ ] 单元测试覆盖新统计口径
- [ ] 数据订正有审计记录

## 约束条件

- Python 环境使用 uv
- 前端包管理使用 pnpm
- 使用 worktree 开发
- 数据库订正必须备份

## 风险与假设

- 已知风险：统计口径变更后面板数字会突降，需告知运维这是修正而非故障
- 假设条件：delivery_status=queued 且 status 已终态的任务，bridge 侧确实不再处理
