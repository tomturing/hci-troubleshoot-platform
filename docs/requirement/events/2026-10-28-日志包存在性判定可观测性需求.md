# 日志包存在性判定：结论必须可自证，不得把「没探测到」说成「已删除」

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-28 | v1.0 | 初版：来自工单 Q2026102701403 现场 | 2026-10-27-日志收集交付路径与补交付需求.md |

## 背景与问题

- 业务背景：日志收集面板在采集失败后，需要判断「节点上是否还有可补交付的压缩包」，据此决定是否给出「上传到平台」。
- 核心痛点（Q2026102701403，2026-10-27 20:13 现场）：节点上 `Q2026102701403.zip` 实为 455 MiB 且路径完全合法，面板却断言「压缩包已不在」，只留「重新收集」；用户被迫重采 455 MiB。
- 排查代价：库里 `log_collect.progress` 事件没有 `archive_exists` 字段，只能靠 `archive_size` 有值反推「桥侧其实量到了」；失败原因（分片上传 x509 证书不受信)在界面上也无处可看，只能查库。
- 影响范围：所有「采集完成但交付失败」的工单；桥与前端版本不同步时必然复现。

## 需求描述

- 功能概述：让「包在不在」的探测结论在**节点日志**与**界面**上都可自证；「未探测到」与「明确不存在」必须给出不同说法。
- 用户场景：现场工程师看到「压缩包已不在」时，能区分是自己该去节点核对、还是桥版本过旧；支持人员按工单号查日志即可还原判定输入。
- 预期收益：消除「包明明在盘上却被判删除」的误导，减少无谓重采与二次工单。

## 功能需求

1. `log_collect.progress` 事件必须记录 `archive_exists`、实际探测路径、路径来源（插件上报/约定推导）与探测失败诊断。
2. 平台失败 + 节点已完成 + `archive_exists` 缺省时，文案不得出现「压缩包已不在」，须表达「未确认」并给出确认途径。
3. 结果态必须渲染失败原因（错误码 + 错误信息），使顶部提示的「失败原因见下方错误信息」名副其实。

## 非功能需求

- 可观测性：新增字段只追加、不改名；空诊断不落键，避免日志噪音。
- 兼容性：WS 消息只增字段；旧前端忽略新字段仍可工作。
- 可维护性：判定分支必须有单测护栏，防止文案再次合并。

## 验收标准

- [x] 进度事件含 `archive_exists` / `archive_probe_path` / `archive_probe_source`，探测失败时含 `archive_probe_diag`。
- [x] `archiveExists` 为 `undefined` 时 reason 含「未确认」且不含「压缩包已不在」；为 `false` 时仍明确「已不在」。
- [x] 结果态在 failed / cancelled 时展示 `error_code` 与 `error_message`。
- [x] 前端单测与 `vue-tsc` 构建通过；`terminal_bridge` 编译与测试通过。

## 约束条件

- 技术约束：物理事实的唯一来源仍是 bridge 的 `stat`；平台够不着客户内网节点，不得新增平台侧文件探测。
- 资源约束：不改状态机、不引入新接口。
- 依赖约束：依赖 bridge 与前端各自发版，故「未探测到」必须是一等状态。

## 风险与假设

- 已知风险：旧版 bridge 长期不升级时，用户会持续看到「未确认」，需在文案中指向升级/核对动作。
- 假设条件：`archive_exists` 只在明确 true 时才允许「上传到平台」的既有约束不变。
