# 交付期间 SSH 会话掉线自动重连（需求）

## 背景

日志收集交付（pull 节点压缩包 → 分片上传平台）常跑十几分钟。过程中 SSH 会话可能因两类原因消失：

1. **节点侧 10 分钟会话上限**：现场 `ssh.disconnected reason=remote_eof duration_seconds=600` 整点出现，是节点/中间设备的硬上限，与桥的 keepalive 无关。
2. **面板 WebSocket 抖动**：会话由建立它的浏览器连接持有，连接一断会话随之被释放。

会话一旦消失，交付就停在 `needs_reauth`（「交付需要重新认证：请重新连接 SSH 后继续」），只能由用户回面板手动重连再续传。工单 Q2026102701403 现场正是传到 4/15 片后被打断，靠人工续传才收尾。

## 现状事实

- 桥**已经**持久化每个工单最近一次 `ssh_connect` 的认证信息（`Bridge.lastAuth`，`main.go:4231`），并已有 `autoConnectNode` 复用它对节点自动建连——但该函数依赖浏览器 `ws`，交付这样的后台作业没有、也不该绑定某个连接。
- 交付作业进度已落盘（`UploadedParts` 保留），重连后可从断点续传。

## 需求

交付进行中若节点 SSH 会话掉线，桥应**在后台用已存的认证信息自动重连节点并续传**，无需用户回面板手动重连。

约束：

- 仅在「本阶段确实需要节点」时尝试重连（上传/收尾只读本地副本与平台，不该为它们去敲一条 SSH 连接）。
- 仅在桥持有该工单认证信息时尝试；若从未建立过 SSH 连接（裸交付），仍走人工重连，不得假装能自愈。
- 重连失败必须如实转成 `needs_reauth`（人工介入），不能无限重试掩盖故障。
- 重连动作须留痕（新增事件 `delivery.session_reconnected`），便于云端按工单聚合与告警。

## 验收

- 会话掉线后，交付自动恢复并完成，库内 `delivery_status` 最终为 `delivered`，无需人工点重连。
- 无认证信息时，行为不变（仍 `needs_reauth`）。
- 重连过程在桥日志中可观测。
