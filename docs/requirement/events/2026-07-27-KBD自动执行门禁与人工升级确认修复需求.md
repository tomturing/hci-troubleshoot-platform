# KBD 自动执行门禁与人工升级确认修复需求

## 触发事件

在开发环境工单 `Q2026072769668` 中，用户确认分类“虚拟机-003”后，页面提示“分类 虚拟机-003 下的 KBD 均未通过自动执行契约”。用户点击“我知道了”后，确认请求又返回 503。

现场事实：

- 会话 `355fefc0-79c1-4478-8551-f3f4f7b6819c` 正确进入 HTP Agent 的 S1，分类为 `虚拟机-003`。
- 分类下无 SOP，有且仅有一条已发布 KBD：内部 `id=1`、业务 KBD `27123`。
- KBD 的 `sig_002`、`sig_003` 是 v2 合法的 QFK 产出变量模式：`match=null`，分别产生 `PID`、`PNAME`。
- 分类清单却把它标为 `executable=false`，错误原因为“缺少确定性 matcher”。
- HTP Agent 随后产生 `AgentEscalation`；前端确认卡的本地占位 request 被错误转发到 ops-agent ACP 接口，ops-agent 对不存在的请求返回 404，页面被转换成 503。

## 用户需求

1. 分类快照的 KBD 自动执行资格必须与 QFK v2 保存/执行契约一致：合法的“产出变量”模式不能被误判为不可执行。
2. HTP 产生的人工升级提示必须可见、可确认、可在会话历史中追溯；其确认不应依赖 ops-agent。
3. 真实 ops-agent ACP 交互仍必须保持既有回传机制，不能被本次修复破坏。
4. 用单元测试覆盖两类模式和错误分流，避免以后再次出现“保存合法、运行前被过滤”的契约漂移。

## 非目标

- 不修改 KBD 27123 的业务内容、发布状态或现场数据库数据。
- 不降低 QFK `match` / `orchestrate.produces` 二选一的保存安全契约。
- 不要求 ops-agent 为 HTP 人工升级生成虚假的 ACP session/request。
