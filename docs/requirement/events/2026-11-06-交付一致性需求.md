# 需求事件：交付一致性（2026-11-06）

## 背景与问题

工单 `Q2026110601054` 现场出现三类叠加故障：

1. 15:51 重新采集（模块 `vm_suspend` → `other`）后，同名 zip 由 3,909,075,473 变 1,216,213,263 字节；旧上传会话仍按提交时冻结的 `total_size` 校验 → 界面报「源包已变化，请重新点击上传到平台」，并在 16:01 边采边传时重演。
2. 15:51:11 被新会话顶替的旧作业（`superseded` / `context canceled`）在 15:55:10 又 `collect_finished` → 拉取 1.2GB → 落 fatal，并把错误写回平台任务（`status=completed` 却挂「源包已变化」）。
3. 服务端已把 `relay_status=success` / `delivery_status=delivered` / `delivery_finished_at=16:05` 落库，前端却因 WS 通道断开写了 `status=failed` + `error_message=与 terminal_bridge 的连接已断开`，无人回写，界面与事实矛盾。

## 需求描述

- 重新采集/包变化后，系统应自动识别内容变化并重签上传会话，交付继续成功，用户无需手动重点。
- 被顶替或取消的交付作业不得复活、不得把错误写回任务终态。
- 任务终态只由服务端在拿到持久化事实后推进；客户端请求失败只表示「结果未知」。
- 现场 bridge exe 不会自动升级：核心修复必须在服务端与前端独立生效，exe 侧改动只是纵深。

## 验收标准

- [ ] 包大小变化后不再逐片失败，也不再要求用户手动重新点击。
- [ ] superseded 作业不再产生 `collect_finished` / `pull_verified` / 落库失败。
- [ ] relay success 后 `status`、`delivery_status`、`error_*` 三者一致。
- [ ] WS 通道断开不写终态。
- [ ] 老前端/老 exe 组合不出现 422、不卡死。
- [ ] 全量单测 + UI 模拟人工验证通过。

## 约束条件

- Python 用 `uv`，前端用 `pnpm`；代码注释、commit、PR 用中文。
- 文档门禁：改动代码必须同 commit/PR 同步 `docs/`。
- 数据库为 Atlas 声明式，新增列有已知顺序事故，本次不新增列。
- 所有请求日志使用唯一调用链 `trace_id`。
