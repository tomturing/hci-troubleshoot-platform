# KBD 关键信号只读边界需求

## 背景

KBD30880 的案例正文把“缺少”误写为“取消”。模型据此把自然语言理解为删除
配置项，并生成 `phase=solution` 的 `qfk_system` 候选。现有门禁最终因该候选同时
缺少 `match` 和 `produces` 而拒绝，但错误只显示结构二选一失败，专家无法直接判断
源内容实际混入了处置动作。

KBD 信号抽取只消费标题、问题描述、告警信息和有效排查步骤。这四部分按业务定义
应描述现象和排查事实，不应承载配置修改、删除、重启等解决方案。如果识别出处置
动作，更可能表示案例内容需要专家修正，而不是平台应该把动作转成可执行 Signal。

## 用户语义

- KBD Signal 只能是只读事实采集、确定性判定或变量生产；
- 写入、配置变更、启停/重启、删除、迁移等处置动作不能保存为 Signal；
- 自动抽取发现变更动作时，保留原候选和明确原因，交由专家审核；
- 正常只读 Signal 不得被误伤；
- 不自动修改 KBD 正文，不针对 KBD30880 或 `sed` 建立专用规则，不建设通用 Shell 风险引擎。

## 验收标准

1. KBD 自动抽取中，`phase=solution` 或现有明确写动作词表命中的候选在结构二选一校验前被拒绝；
2. `rejected_candidates` 保留完整候选与“处置动作不属于 KBD 关键信号”的可读原因；
3. 专家草稿保存、维护发布、审核发布和重新发布不能绕过只读边界；
4. Agent 对历史 `phase=solution` 或明确写动作 Signal 保持阻断，不自动执行；
5. 正常 `cat/list/get/status/show/check` 等只读采集、Matcher 和变量生产继续通过；
6. SOP 通用 Signal Schema 与 SOP 保存语义不因 KBD 专用门禁被修改；
7. Prompt seed 与已部署环境 data migration 使用同一规则，且没有旧的“写操作可生成 solution Signal”引导。
