# KBD 数据管道稳定性与可观测性需求

## 背景与需求

批量导入 KBD 时，VISION、CLASSIFY、EXTRACT_SIGNALS 的 LLM 调用存在超时、限流、空响应和 JSON 不完整等问题。现行 DAG 将 VISION 与 CLASSIFY 阶段串行，且前置失败会把未执行的下游任务显示为失败或跳过，导致操作者无法区分技术失败、质量警告和依赖阻断。

业务确认：KBD 截图包含大量诊断事实，截图识别结果会直接影响关键信号抽取质量。因此 VISION 是 EXTRACT_SIGNALS 的硬依赖；只有截图识别成功且分类成功的 KBD 才允许进入信号抽取。VISION 与 CLASSIFY 之间不存在硬依赖，应在 IMPORT 成功后并行执行。

## 需求范围

- 在不改变 FETCH/IMPORT 数据语义的前提下，重构六阶段 Pipeline 的阶段依赖和案例级状态聚合。
- 统一 VISION、CLASSIFY、EXTRACT_SIGNALS 的 API 超时、429/5xx/传输错误重试、Retry-After 和抖动退避策略。
- 保证图片级结果不会被错误投影为 KBD 级结果；发现 API 与数据库状态不一致时必须显式告警。
- 保留非交互 CLI 兼容性，新增中文交互向导、中文总结、JSON/JSONL 排障输出和可恢复提示。
- 文档必须同时形成需求、方案、任务和验证事件，并更新现行全量文档及 README 冷启动入口。

## 非目标

- 本次不新增 KBD 管理页面导入入口。
- 本次不把 VISION 降级为 EXTRACT_SIGNALS 的软依赖。
- 本次不在未完成 Redis/多副本状态契约验证前仓促迁移 JobManager 持久化实现。

## 验收标准

- VISION 和 CLASSIFY 在 IMPORT 后并行调度；分类不因 Vision 失败而不执行。
- EXTRACT_SIGNALS 的输入集合严格为 Vision 成功案例与分类成功案例的交集。
- `blocked_by_dependency`、`failed`、`warning/needs_review`、`skipped_existing` 可区分且终端摘要可读。
- 20 个 KBD 故障注入测试能定位失败 ID、阶段、错误码、可重试性和下一步命令。
