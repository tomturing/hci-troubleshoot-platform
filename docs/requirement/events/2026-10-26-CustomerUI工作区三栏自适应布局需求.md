# Customer UI 工作区三栏自适应布局需求

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-26 | v1.0 | 初版：左右抽屉同时展开时内容挤压换行，要求按抽屉数量切换展开/侧滑/压缩三态 | 本文 |

## 背景与问题

Custom UI 的主界面由「中央会话 + 左侧抽屉（日志收集 / 历史工单）+ 右侧抽屉（SSH 终端）」组成。
2026-10-26 现场截图显示：左侧日志收集与右侧 SSH 终端同时展开时，左侧面板内
`el-descriptions` 的字段名被压成一字一行（发起节点、压缩包大小、归档状态等），
值的可读性显著下降；右侧终端列数不足，命令输出折行。

根因不是"屏幕不够宽"，而是**宽度分配没有按内容的最小宽度求解**：

1. 旧的 `getDefaultPanelWidth()` 只按
   `(innerWidth - 900) / 2` 计算两侧留白，中央会话区在任何情况下都固定占 900px，
   抽屉只能拿"剩下的边角料"；
2. 视口不足时该函数直接退化为 `85% 视口宽`，左右抽屉各自 85% 会互相覆盖，
   且完全没有考虑抽屉内部内容所需宽度；
3. 抽屉内部布局是静态的（`el-descriptions :column="2"`、`el-form label-width="90px"`），
   不随容器宽度切换密度，窄容器必然换行；
4. 左侧「日志收集」与「历史工单」共用左侧位置，但没有互斥约束，可能同时展开互相遮挡。

## 需求描述

工作区应作为一个整体自适应，而不是三个各自为政的浮层：

- **无抽屉（展开态）**：中央会话保持现有阅读宽度（≤900px）居中，两侧留白，视觉大气；
- **单抽屉（侧滑态）**：抽屉以「推挤」方式占用侧边空间，中央会话在剩余空间内重新居中，
  抽屉宽度足以完整展示表格/终端，不出现一字一行；
- **双抽屉（压缩态）**：中央会话可被压缩，但保留最小可读宽度；两侧抽屉按内容权重分配剩余宽度；
- **极端窄屏**：三栏无法并存时自动降级为覆盖式抽屉（保留现有遮罩交互），不强行挤压。

抽屉宽度由「内容最小宽度」驱动，用户拖拽只调整偏好，窗口尺寸变化时重新求解而不是重置为魔法数字。

## 功能需求

1. 中央会话区随抽屉开合平滑让位与复位（有过渡，无跳动）。
2. 左右抽屉宽度按内容类型求解：左侧（表格/列表）与右侧（终端）权重不同。
3. 抽屉内部在窄容器下切换密度：描述表列数、表单标签位置随容器宽度变化。
4. 左侧「日志收集」与「历史工单」互斥，同一时刻只允许一个占用左侧。
5. 双抽屉在 < 1440px 视口降级为覆盖式，避免中央会话被压到不可读。
6. 抽屉拖拽调整宽度时中央会话实时跟随，且不允许拖到破坏最小宽度。

## 非功能需求

- 布局求解必须是纯函数，可单元测试覆盖 0/1/2 抽屉与多分辨率组合；
- 不改变现有业务数据流、SSE、SSH 通道行为；
- 布局变化不得引发终端反复重排（xterm fit 需要防抖）；
- 过渡动画时长与 Element Plus 抽屉动画一致，避免错位感。

## 验收标准

- [ ] 1920×1080：双抽屉同时展开，左侧描述表正常两列/单列展示无逐字换行，右侧终端 ≥ 80 列，中央会话 ≥ 520px；
- [ ] 1920×1080：单开任一侧，中央会话仍为 900px 居中，未被视觉挤压；
- [ ] 1600×900、1440×900：双开时中央会话分别 ≥ 560px / ≥ 460px，无横向滚动条；
- [ ] 1366×768：双开自动降级为覆盖式，遮罩与点外部关闭行为正常；
- [ ] 0 抽屉时界面与改造前一致（中央 900px 居中）；
- [ ] 左侧日志收集与历史工单不会同时展开；
- [ ] 拖拽右抽屉至最窄时终端仍可用，中央会话不低于最小宽度；
- [ ] 单元测试覆盖布局求解器全部分支，前端 `pnpm test` 与 `vue-tsc` 通过。

## 约束条件

- 前端包管理必须使用 `pnpm`；
- 文档门禁：改动 `frontend/` 必须在同一 PR 更新 `docs/` 或 `README.md`；
- 不允许引入新的 UI 依赖，沿用 Element Plus 与现有 `workspace-drawer.css` 体系。

## 风险与假设

- 假设主流现场分辨率为 1920×1080 与 1440×900；1366 及以下按降级处理；
- 风险：`el-drawer` 是覆盖式组件，推挤效果依赖主区让位而非文档流列，动画期间可能出现 1~2 帧错位；
- 风险：移除"钉住"交互会改变用户习惯，需要在方案中明确取舍。
