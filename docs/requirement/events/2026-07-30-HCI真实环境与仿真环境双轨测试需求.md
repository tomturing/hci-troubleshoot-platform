# HCI 真实环境与仿真环境双轨测试需求

## 1. 背景

Terminal Bridge P0 端到端可观测性改造已经完成真实案例验证，平台能够以 `trace_id/exec_id/artifact_id/evaluation_id` 关联 Custom UI、Terminal Bridge、SSH、HCI 命令结果、Agent 工具结果和诊断结论。下一阶段需要用 KBD 构造可重复的 Agent 能力测试。

真实 HCI 对最终正确性不可替代，但大量故障难以安全、稳定地复现，也无法经济地提供 100+ 相互隔离的环境。因此，需要在不改变 Agent 和 Terminal Bridge 核心执行契约的前提下，引入 hci-sim。

本需求是对 [2026-07-28 Agent 并发测试与 KBD 驱动 HCI 仿真环境需求](2026-07-28-Agent并发测试与KBD驱动HCI仿真环境需求.md) 的补充，重点冻结真实环境与模拟环境的职责、运行互斥、安全和部署约束。原需求内容继续有效，不删减、不替代。

## 2. 核心业务结论

平台必须支持 hci-real 和 hci-sim 双轨共存，但一次 Agent 运行必须且只能选择一轨：

| 场景 | 轨道 |
|---|---|
| 生产诊断 | 仅 hci-real |
| 日常自动回归、100+ 并发和故障变体 | 仅 hci-sim |
| HCI/aCLI 版本校准 | real 与 sim 各创建一次独立运行，再比较 |
| UI/协议人工 smoke | 显式选择 real 或 sim，并标记模式 |

禁止同次运行混用 real/sim，禁止 sim 失败后自动 fallback 到 real，禁止将模拟证据解释为真实环境事实。

## 3. hci-sim 能力需求

### 3.1 协议保真

- Agent 仍通过既有工具、Custom UI 协议和 Terminal Bridge 执行命令；
- Terminal Bridge 仍通过 SSH 连接目标，不增加 KBD 特判；
- hci-sim 必须兼容 SSH auth、exec、受控 PTY/env、stdout、stderr、exit-status、timeout 和 cancel；
- real/sim 使用相同 result envelope、Matcher、CDD 和 Artifact 语义；
- hci-sim 只增加明确的 simulation/scenario/fixture 字段。

### 3.2 KBD 场景生成

- 输入绑定不可变 KBD revision 和 `signals_json`；
- 支持 producer/consumer 变量依赖；
- 支持 positive-minimal、positive-realistic、negative、near-miss、timeout、permission-denied 和 unknown；
- 真实 Artifact 可作为 realistic fixture 来源，但必须脱敏、参数化、记录 hash 和 provenance；
- KBD revision、工具 schema、Matcher 或 policy 变化后，旧 fixture 必须标记 stale；
- 图片/OCR 只能辅助起草，不能自动成为可信 observation；
- fixture 必须经过 lint、验证和审批后才能进入批量回归。

### 3.3 100+ 并发与隔离

“100+ 环境”首期定义为 100+ 逻辑隔离 Scenario，而不是 100 套完整 HCI 或 100 个 Pod。每个 Scenario 必须独立拥有：

- `test_run_id/scenario_id`；
- fixture manifest 和 variant；
- virtual node/container；
- 变量 profile 和按需 state overlay；
- SSH 会话/命令/输出/时限配额；
- trace、exec、artifact、evaluation namespace。

相同命令在不同 Scenario 中可以返回不同结果，且不得串线。一个 Scenario 的 timeout、断连、unknown 或大输出不得拖垮其他 Scenario。

### 3.4 运行时和部署

- hci-sim 以 OCI 容器运行于 dev/test K3s；
- 使用独立 `hci-sim-dev` namespace 和独立 Helm release；
- P0 单副本，P1 支持 2～4 副本和 100～200 active Scenario；
- 不要求每场景创建 Pod；仅强状态、版本或网络隔离场景允许使用独立 Pod/shard；
- prod 默认禁止部署和启用；
- fixture 只读，大 Artifact 使用对象存储或内容寻址 bundle，不塞入 ConfigMap/数据库大字段；
- 必须具有 bounded worker pool、backpressure、per-scenario semaphore 和 run 总预算。

### 3.5 Scenario Lease

- Scheduler/后端签发短时、不可篡改的 Scenario Lease；
- Lease 至少绑定 test run、scenario、fixture manifest、mode、过期时间和配额；
- 浏览器只能中继不透明 token，不能自行选择 fixture；
- hci-sim 在 SSH 认证阶段校验 Lease，将场景身份绑定到 connection context；
- 不在 aCLI 命令中拼接 scenario id；
- 未知、过期、撤销、mode 不符的 Lease 必须 fail closed；
- token、签名和凭据不得进入日志或 Artifact。

## 4. 真实 HCI Oracle 需求

真实 HCI 仅用于低频 L3 Oracle 与只读 smoke：

- 校准 SSH、PTY、quote、stdout/stderr、exit code 和 aCLI 输出；
- 采集经审批的真实 Artifact，生成 realistic fixture；
- 对 real/sim 两次独立运行做差异比较；
- 发现 HCI/aCLI 版本漂移并使相关 fixture stale。

真实 HCI 凭据只能存放于受控 Secret/凭据系统，不进入 Git、文档、fixture、日志或 hci-sim。hci-sim 不得持有凭据，也不得具有访问真实 HCI 网段的网络权限。

## 5. 可观测性需求

每次模拟运行必须能从下列关系完整互查：

```text
trace_id
  -> exec_id
    -> hci-sim command span
      -> fixture_id / artifact_id
        -> scenario_id / KBD revision / signal_id
          -> evaluation_id
            -> candidate state / conclusion
```

SSH 边界必须显式传播 W3C `traceparent`。日志和指标必须区分 `execution_mode=ssh|sim-ssh|replay`，模拟结果不得进入生产成功率。未知 fixture、queue overload、lease reject、timeout、cancel 和输出截断必须是明确事件和指标。

## 6. 安全需求

- hci-sim 不提供任意 shell、scp、sftp 或端口转发；
- 不使用 privileged、Docker-in-Docker、hostPath 或宿主 runtime socket；
- Pod 使用 non-root、只读根文件系统、drop all capabilities 和 RuntimeDefault seccomp；
- namespace 默认 deny all；只允许指定 Terminal Bridge 访问 SSH 数据面；
- 显式阻断真实 HCI 和非必要内网网段；
- fixture 扫描 password、token、私钥和客户敏感信息；
- unknown command、fixture miss、revision drift 和 lease 错误必须 fail closed；
- 所有测试资源和状态必须有 TTL/清理策略。

## 7. 测试运行形态

并发验收分为两类，不能互相替代：

1. Golden UI E2E：少量真实浏览器/Playwright context，验证 Custom UI 渲染和交互；
2. Bulk Agent E2E：headless runner 实现与 Custom UI 相同的命令中继协议，经同一 Terminal Bridge 和 hci-sim 执行 100+ conversation。

如要宣称“100 浏览器并发”，必须单独运行 100 个隔离 browser context 并报告前端资源数据；Bulk headless 通过不能替代该结论。

## 8. 首个 Golden Scenario

P0 应选择 dev 已发布且已有真实验收 Trace 的 KBD 27123，覆盖 task → HOST/VM/END、lsof → PID、ps → CMD 的 producer/consumer 链。现有真实 Trace 只作为 provenance，fixture 仍需脱敏、参数化和审批。

概念示例 `acli log get -k "too many file" ...` 可在后续对应 KBD 发布后加入，不应为了演示而绕过当前真实 KBD 数据。

## 9. 非目标

- 首期不虚拟化完整 HCI 控制面、存储、网络和数据库；
- 不让 hci-sim 自动执行真实 shell；
- 不让 Terminal Bridge 理解 KBD 或维护 fixture；
- 不默认每 KBD/Scenario 创建 Pod 或 VM；
- 不用模拟测试替代生产诊断或真实 Oracle；
- 不在 P0 先实现完整管理 UI、1000 场景或全部 KBD；
- 不把“返回预期关键字”作为 Agent 能力通过的唯一标准。

## 10. 成功标准

在宣称 hci-sim MVP 和 100+ 并发能力完成前，必须满足：

- KBD 27123 real/sim 独立运行的协议与诊断契约等价；
- `trace_id -> exec_id -> fixture_id -> evaluation_id -> conclusion` 完整；
- unknown/timeout/permission/negative/near-miss 不被错误转成 PASS；
- 100 active Scenario 和 200 压力梯度均完成，串线数为 0；
- 队列、并发、输出和时限均有界，过载明确拒绝；
- hci-sim 多副本下 Stateless 场景不依赖 Pod 内隐式状态；
- NetworkPolicy 验证 hci-sim 无法访问真实 HCI；
- real/sim 指标和 Artifact 明确隔离；
- 至少 10～20 个核心 KBD 进入 validated fixture 集；
- 新增 KBD 的主要工作变为 fixture 审核，而不是构造完整真实故障环境。
