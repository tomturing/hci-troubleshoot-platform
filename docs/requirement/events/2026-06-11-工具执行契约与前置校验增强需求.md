# 工具执行契约与前置校验增强需求

## 背景与问题

PR #443 已将 SSH 终端代理改造成双通道隔离执行，`terminal_bridge` 能把标准输出和标准错误物理分离回传。再次验证后，执行链路本身已经正常，但暴露出新的工具契约问题：

1. `bash_exec` 当前只接收自由文本 `command`，没有显式执行边界。LLM 可以把容器选择、运行时进入方式、实际命令混在同一个字符串里，服务端无法可靠审计“命令到底在哪个容器内执行”。
2. 命令失败时，真实 `stderr` 未能稳定展示。双通道结果在 `exit_code != 0` 时触发后端解析异常，页面看到的是“结果解析失败：cannot access local variable 'output'...”，而不是远端返回的标准错误。
3. 当前工具调用主要依赖执行后报错纠偏。`ToolCallValidator` 只校验 JSON Schema 形状，无法判断 `bash_exec` 是否指定容器、`acli_exec` 是否命中官方支持命令、`--formatter` 等全局参数位置是否合法。
4. 工具管理页面允许直接编辑 JSON Schema，但缺少类似 SOP 管理的发布校验和分级问题反馈。错误的工具契约可能在保存时成功，运行时才失败。
5. SOP 消费链路可能把文档里的命令文本直接交给 Agent 推理，缺少与工具契约的一致性校验。SOP 发布成功不代表运行时工具调用一定合法。

## 核心需求

### R1：`bash_exec` 必须显式指定容器

`bash_exec` 的工具契约必须包含必填参数 `container`，且只能取平台允许的容器枚举。当前从 aCLI 官方文档首页 `acli --help` 可确认的枚举值为：

- `asv-con`
- `vn-con`
- `vn-agent`
- `vs-cp-manager`

LLM 不允许在 `command` 内手写 `docker exec`、`kubectl exec`、`nsenter` 或其他进入容器的前缀。容器进入方式只能由服务端执行适配器拼装。

### R2：执行边界必须结构化且可审计

工具调用、审计日志、前端工具卡片都必须展示以下信息：

- `exec_id`
- `tool_name`
- `node_ip`
- `container`
- 原始 `command`
- 服务端拼装后的实际执行命令
- `stdout`
- `stderr`
- `exit_code`
- `duration_ms`
- `trace_id`

### R3：标准错误必须原样保留并展示

当远端命令 `exit_code != 0` 时：

- 不得因为解析逻辑异常覆盖真实 `stderr`
- 前端工具卡片必须展示 `stderr`
- LLM 的工具观察消息必须包含 `stderr`
- 审计表与 FactStore 应保留结构化 `stdout/stderr/exit_code`

### R4：工具调用必须在真实执行前完成基础校验

在向 terminal_bridge 下发 `agent_exec_command` 前，服务端必须先完成两层校验：

1. JSON Schema 形状校验：必填、类型、枚举、正则、`additionalProperties`
2. 语义校验：工具特有规则、命令路径、容器边界、aCLI catalog 命中、风险分级前置条件

语义校验失败时，不应触发真实 SSH 执行，也不应向前端展示为“命令执行失败”。系统应把校验失败作为一条工具规划反馈注入 ReAct 循环，让 LLM 重新思考并生成合法 tool_call。

### R5：`acli_exec` 必须校验官方支持命令

`acli_exec` 调用前必须解析命令 token，并基于 aCLI 官方命令列表校验命令路径是否受支持。官方命令列表来源：

- 首选：`http://acli.sangfor.com.cn:6888/commandList`
- 备选：目标环境执行 `acli acli command list`
- 运行时：使用仓库内随版本提交的本地 catalog 快照，禁止依赖外部站点实时可用性

### R6：工具管理要具备发布前校验

工具管理页面和后端 API 必须增加“校验”能力，至少覆盖：

- JSON 是否合法
- 是否满足 OpenAI function/tool schema 基础约束
- 内置工具参数是否与底层执行器强绑定字段一致
- `bash_exec` 是否包含必填 `container`
- `acli_exec` 是否保留必填 `command/reason`
- `usage_template` 占位符是否能在 `parameters_schema.properties` 中找到

校验结果沿用 SOP 管理经验，分为：

- `error`：阻断发布或保存
- `warning`：允许保存，但必须展示风险说明

### R7：SOP 发布需要校验工具调用可执行性

SOP 管理发布或重解析时，应对识别出的命令/工具调用草案进行校验：

- 可结构化映射为 `acli_exec` 的命令，必须命中 aCLI catalog
- 可结构化映射为 `bash_exec` 的命令，必须能补齐 `container`
- 不能确定容器或命令路径时，生成 `warning`
- 明确违反工具契约时，生成 `error`

## 非功能需求

- **安全性**：所有高危/越权命令必须 fail-closed，不得在校验服务异常时放行。
- **可观测性**：新增校验失败指标、catalog 版本日志、校验耗时、按工具名聚合的失败原因。
- **可维护性**：命令 catalog 使用本地快照，配套同步脚本；运行时只读快照。
- **兼容性**：短期内保留旧字段兼容，但所有新工具调用必须走 v2 schema。
- **用户体验**：基础校验失败应表现为 Agent 自我修正，不应把用户暴露在低级命令拼写错误和缺容器错误中。

## 验收标准

- [x] `bash_exec` 未传 `container` 时，在服务端真实执行前被拦截，并触发 LLM 重新规划。
- [x] `bash_exec` 传入非法 `container` 时被 enum 校验拦截。
- [x] `bash_exec.command` 中包含 `docker exec`、`kubectl exec`、`nsenter`、`acli` 前缀时被拒绝。
- [ ] 双通道回传 `exit_code != 0` 且 `stderr` 非空时，页面展示真实 `stderr`，不出现 `cannot access local variable 'output'`。（后端链路已修复，页面展示需人工验证）
- [x] `acli_exec` 调用不在 catalog 中的命令时，不下发到 terminal_bridge，并向 LLM 返回可修正的规划反馈。
- [x] `acli_exec` 调用 catalog 中的命令时，保留现有风险分级和确认流程。
- [x] 工具管理保存/校验能返回 `error/warning` 列表，并能定位到具体字段。
- [ ] SOP 发布能对命令可执行性产生 `validation_issues`。
- [x] 所有新增日志包含 `trace_id`、`exec_id`、`tool_name`、`validation_code`。

## 约束条件

- Python 依赖管理必须使用 `uv`。
- 前端依赖管理必须使用 `pnpm`。
- 代码注释必须使用中文。
- 涉及 `backend/`、`frontend/`、`database/` 改动时，同一 PR 必须同步更新 `docs/`。
- 不在本需求内实现容器运行时的任意自动探测写操作；容器执行适配器只能使用只读或明确授权的方式确认运行时。
