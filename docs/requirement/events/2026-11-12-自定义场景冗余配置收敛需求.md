# 自定义场景冗余配置收敛需求

## 背景与问题

2026-11-11 的「默认场景两级页签与配置收敛」（PR #1483 / 迁移 059）按用户决定删掉了默认场景的「待审核」状态与「最后修改」信息，并物理删除对应的零消费列。但当时方案明确划定边界「不动 `log_collect_custom_scenario`」，因此自定义场景页仍保留同类冗余。

现场截图（管理台「日志收集 → 自定义场景」列表）显示「最后修改」单元格里出现两行：`2026-11-11 11:30` 与 `00000000-0000-0000-0000-000000000001`。经查库确认：

- 第二行是 `updated_by`，值为内置管理员 `admin` 的 `user_id`（`database/seeds/05_authn_default_admin.sql`），被前端当作人读信息原样打印；
- 第一行是 `updated_at`（UTC `2026-11-11 03:30:03Z` 按浏览器 +8 显示），且该行 `created_at = updated_at`，即场景创建后从未修改，「最后修改」实际显示的是创建时间，列名本身有误导。

用户判断这类注释、审核态、最后修改信息属于过度设计，交互符合直觉即可，已授权「一起收掉」。

## 需求描述

1. **界面**：自定义场景列表删除「最后修改」整列；编辑抽屉删除「待审核 / 已审核」单选，表单标签同步收敛；不再出现内部主键 UUID。
2. **接口与模型**：管理端自定义场景 CRUD 的请求/响应不再携带 `review_state`、`created_by`、`updated_by`、`created_at`、`updated_at`。
3. **数据库**：`log_collect_custom_scenario` 物理删除上述 5 列（迁移 060），`desired_schema.sql` 同步删除列、CHECK 约束与列注释；ORM 去掉 `TimestampMixin` 继承。
4. **审计不降级**：操作者仍由 `X-Admin-User` / JWT `sub` 透传，写入 `operation_audit.details.updated_by` 与结构化日志（含 `trace_id`）；只是不再落业务表、不再摆到界面。
5. **测试守护**：单测断言响应模型与落库参数不再含这 5 个字段；前端契约测试直接挂载自定义场景面板断言无「最后修改」「待审核」，不再只靠宿主页面里被 mock 的断言。

## 功能需求

- 自定义场景的新增、编辑、启用/停用、删除、保存前试算、spc 清单勾选等既有功能行为零变化。
- 列表列收敛为：场景名称、标识（只读）、通道、条目数、版本、状态、操作。
- `revision` 版本化机制与 `(scenario_id, revision)` 历史回溯能力保持不变。
- 客户侧只读元数据契约保持不变（客户端响应模型本就不含这 5 个字段）。

## 非功能需求

- 迁移 060 必须兼容空库路径与 CI「先按 `desired_schema.sql` 建表、再全量重放 data-migrations」的顺序；不得留下引用已删列的 `COMMENT ON COLUMN`。
- `atlas schema diff` 幂等校验必须通过：`revision` 列注释、`source` CHECK 文本等既有文本逐字保持不变。
- 不改动 Go bridge，不重建 `terminal_bridge.exe`，不新增现场交付动作。
- 文档门禁：现行全量文档、README 与三层事件文档随同一 PR 更新。

## 验收标准

- [ ] 管理台自定义场景列表与编辑抽屉不再出现「最后修改」「待审核」「已审核」及管理员 UUID。
- [ ] 管理端 API 响应不含 5 个已删字段；创建/更新仍生成正确 `revision` 与下发摘要。
- [ ] staging 库 `information_schema` 中该表仅剩 13 列，`ck_log_collect_custom_scenario_review_state` 消失。
- [ ] 后端单测、两端前端单测、`vue-tsc` + `pnpm build`、ruff、docs 三类门禁全通过。
- [ ] 真浏览器模拟人工：自定义场景页签可正常渲染列表、打开编辑抽屉、保存前试算，且控制台零错误。
- [ ] PR CI 全绿后 squash 合并，合并后 main CI 全绿、部署镜像晋级、worktree 与分支清理完成。

## 约束条件

- 不改 `log_collect_task`（排障证据）、不改 Go bridge 下发契约、不改客户侧可见文案。
- 审计链路由 `operation_audit` + 日志承担，业务表不新增替代列。
- 遵循仓库 `AGENTS.md`：worktree 开发、中文注释与 commit、commit/PR 标识、文档门禁。

## 风险与假设

- 风险：`service.update()` 从 Response 对象读取 `current.review_state` / `current.created_by`，删字段后会 `AttributeError` 500；必须同步改 SQL 与参数字典。
- 风险：CI 注释幂等 diff 对 `desired_schema.sql` 与历史迁移的文本一致性敏感，只改必须改的行。
- 假设：该表唯一消费方是同仓库同 PR 更新的管理端前端，不存在需要跨版本兼容的外部调用方。
