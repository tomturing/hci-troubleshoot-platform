# KBD 专家信号修复与删除可用性需求

## 背景

KBD30880 的 `exists` Matcher 携带模型生成的 `pattern: null`。JSON Schema 将显式 `null` 与字段缺失区别处理，审核页却只显示“None is not valid under any of the given schemas”，既没有稳定 Signal ID、字段位置，也没有可执行的修复动作。专家把候选恢复到本地草稿后，删除任一信号又会把所有未保存草稿合并为整份文档提交，导致另一条无效草稿阻断删除。

## 需求

1. 可省略 Matcher 字段的显式 `null` 必须在抽取和专家保存边界确定性归一；必填字段的 `null` 不得静默吞掉。
2. 校验失败必须返回稳定 `signal_id`、字段路径、中文位置、原因和处理动作；前端须定位并展开对应卡片。
3. 删除已持久化 Signal 必须以稳定 ID 表达意图，由后端基于权威工作稿执行；不得携带其他未保存草稿。
4. 删除本地新增或恢复候选只撤销本地状态，不发起远端写请求。
5. 删除后必须重建 Verification Contract，并保持乐观锁、工作稿和发布门禁。
6. KBD 写动作门禁必须检查真实执行向量，同时区分 wrapper 执行目标与只读命令的数据参数。

## 验收标准

- KBD30880 的 `exists.pattern=null` 可恢复、保存；`keyword.pattern=null` 仍精确报错。
- 错误可定位到具体 Signal 和 `match.pattern`，不再展示 `anyOf/None` 内部术语。
- 一条无效未保存草稿不再阻断删除另一条已持久化 Signal。
- `sf_cli disk light off`、`soft_raid_lit --off`、`strace ... sfscp` 进入 `write_signal`；`ls -l /sf/bin/sfscp` 不误报写动作。
- KBD32300、33510、33882、34094、34164 完成同批真实重抽和逐 Candidate 审查。
