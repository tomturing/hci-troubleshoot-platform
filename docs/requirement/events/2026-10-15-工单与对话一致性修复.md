# 工单与对话一致性修复（case_id 契约对齐 + 会话原子创建）

## 变更历史
| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-10-15 | v1.0 | 初版 | [方案](../../solution/events/2026-10-15-工单与对话一致性修复.md) |

## 背景与问题
- staging 于 2026-10-15 出现工单异常（来源：api-gateway / conversation-service 日志 + `case`/`conversation` 表反查）：
  - `Q2026101566937` 工单已写入 `case` 表，但 `conversation` 表该 case 的会话数为 0（当天其余 16 个工单均有会话）。
  - `Q2026101566935` / `Q2026101566936` 被前端访问，但 `case` 表不存在，conversation-service 返回 404「工单不存在」。
- 根因（第一性原理 + 对抗性审查坐实）：
  1. `case_service._generate_case_id()` 用 `random.randint(0,99999)` 生成，与 schema 注释及 DB 函数 `generate_case_id()` 承诺的「当天从 00001 自增」契约冲突；random 预占不回收、理论碰撞，产生孤儿 ID。
  2. 工单创建与首条 conversation 创建非原子：前端 `completeCaseCreationFlow` 先建工单再 `createConversation()`，后者失败则出现「工单存在但无会话」。
  3. 前端对「工单不存在」缺友好降级，裸 404 直接暴露给用户。

## 需求描述
- 功能概述：统一 case_id 为 DB 自增；工单创建与首条会话幂等确保；前端对不存在工单优雅降级。
- 用户场景：用户创建工单后应立即能对话；不应再出现「工单存在但无会话」或「访问不存在工单」的异常。
- 预期收益：消除孤儿工单 ID 与会话缺失，提升工单链路可靠性与可排查性。

## 功能需求
1. case_id 改用 DB `generate_case_id()` 自增（删除 service 随机版）。
2. conversation 创建改为幂等 ensure（已存在则返回已有，否则建）。
3. 前端对 404「工单不存在」做提示 + 引导重建，不裸 404。

## 非功能需求
- 性能：`generate_case_id()` 加 advisory lock，同天串行，开销可接受。
- 安全：case_id 仍由服务端生成，前端不接管。
- 可维护性：与 schema 注释契约一致，便于日志排查。

## 验收标准
- [ ] 新建工单 case_id 形如 `QYYYYMMDDNNNNN` 且当天连续自增。
- [ ] 每个新建工单在创建流程结束时有且仅有 1 条 conversation（无「工单存在无会话」）。
- [ ] 访问不存在工单时前端显示友好提示而非裸 404，且不抛未捕获异常。
- [ ] 回归：现有 17 个工单对话正常加载。

## 约束条件
- 仅后端 case-service / conversation-service + 前端 customer-ui 改动，不涉其他服务。
- DB 函数 `generate_case_id()` 已在 staging 实装，无需新增 migration。

## 风险与假设
- 现有 17 个 random 工单序号不连续，切换自增后新 ID 从当日 MAX+1 起；已验证当日 MAX=93432，新 ID 不与现有冲突。
- 假设 conversation-service create 接口可安全改为按 case_id 幂等（case 与 conversation 1:1）。
