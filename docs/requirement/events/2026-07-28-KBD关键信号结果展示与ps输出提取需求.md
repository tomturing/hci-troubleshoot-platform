# KBD 关键信号结果展示与 ps 输出提取需求

## 背景

KBD 27123 的三条关键信号已能依次执行，但工单最终报告中的【关键信号执行结果】仍直接展示内部 ID、完整参数 JSON 和原始工具输出。`lsof` 的 stderr、QKV Observation、命令回显与技术字段混在一行，用户无法快速回答“检查了什么、是否成功、得到了什么”。

同时，两次使用相同现场数据的重跑出现了看似矛盾的结果：

| 工单 | 第三步命令 | 结果 |
|---|---|---|
| `Q2026072804914` | `ps -p 10134 -o pid=,args=` | PASS，但只得到 PID `10134` |
| `Q2026072803376` | `ps -p 10134 -o cmd=` | ERROR，提示 stdout 为空 |

现场手工执行证明 `ps -p {{PID}} -o cmd=` 才能在当前 HCI 的 `acli system ps` 包装下取得命令行。产品必须区分“命令执行失败”和“命令成功但结果被提取规则过滤”，不能让用户因错误提示回退到实际不正确的命令。

## 业务语义确认

第三条信号的业务目标是：

1. 使用第二步产出的 PID 定向查询进程；
2. 该 PID 对应的进程必须存在，且命令行仍包含目标 `VM`，才能产出 `CMD` 并通过；
3. 不要求进程名为 `ClwDRDBClient`，不维护特定进程名关键字列表；
4. 进程不存在时 stdout 为空；进程存在但命令行不包含目标 `VM` 时也不通过。

## 用户体验需求

【诊断结论】和【已评估参考案例】保持现状。只优化【关键信号执行结果】及命中案例下的同类现场证据展示：

1. 每条关键信号按执行顺序独立成块。
2. 第一眼可看到检查说明和用户态状态。
3. 明确区分已完成、未满足预期、执行失败、无法判断和未执行。
4. 只展示结构化产出事实，如 VM、HOST、END、PID、CMD。
5. 不在主报告展示 `exec_id`、`evaluation_id`、工具名、参数 JSON 和原始 stdout/stderr。
6. 内部 ID、参数和原始输出继续保留在工具事件、数据库审计和日志中，不能因界面简化而丢失可追溯性。
7. 多行、大输出和 stderr 噪音不得直接进入报告；变量值应单行化并设置合理展示上限。
8. 稳定错误码应转换为用户可理解的中文结果，不能把 `QFK_OUTPUT_EMPTY` 等内部实现细节作为主要文案。

## 验收标准

- `ps -p {{PID}} -o cmd=` 配合 `include=["{{VM}}"]`、`exactly_one`、`whole` 能产出 `CMD`。
- 对同一命令错误保留 `include=["{{PID}}"]` 时，测试稳定复现零匹配；对命令行不含 `{{VM}}` 的进程也必须不通过。
- 三步成功报告包含 VM/HOST/END/PID/CMD 的中文标签和值。
- 报告不包含 exec/evaluation ID、参数 JSON、QKV 原始 Observation 或 `lsof: no pwd entry` 噪音。
- ERROR 与 BLOCKED 有明确、可行动的用户态解释。
- 【诊断结论】与【已评估参考案例】的既有文本和门禁语义不变。
