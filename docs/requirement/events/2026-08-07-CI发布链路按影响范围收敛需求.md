# CI 发布链路按影响范围收敛需求

## 背景

当前 PR 门禁已经按目录分流，但 main push 的发布链仍固定启动 11 个业务镜像构建。只修改一个服务时，其它没有变化的镜像、db-migrate runner 和环境同步仍会被启动，增加 Actions 分钟消耗、GHCR 网络失败概率和发布尾部延迟。

## 目标

1. 质量门禁保持不降级：Python、Go、前端、Helm、数据库和镜像安全扫描的断言不删除。
2. main push 只构建受变更影响的镜像；共享代码或锁文件变化必须安全扇出到所有受影响镜像。
3. 只有实际生成的业务镜像才同步到 `hci-platform-env`；hci-sim 独立镜像不误写平台 values。
4. 无数据库变更时不启动 db-migrate runner。
5. 所有可能受网络、runner 或外部工具影响的 job 都有明确超时。
6. 第三方 Actions 固定不可变 commit SHA，避免 tag 漂移。
7. 时延观测只手动触发，不增加 PR/main push 的 runner。

## 非目标

- 不把本地测试当作 GitHub 合并门禁；
- 不改变 required status context 名称；
- 不减少现有测试断言或把安全扫描改为阻断/通过以外的伪状态；
- 不改变 hci-platform-env 的镜像 tag 语义。

## 验收条件

- 仅修改一个 backend service 时，发布 matrix 只包含该服务；
- 修改 `backend/shared/` 时所有 backend 镜像进入 matrix；修改 `.dockerignore` 时所有业务镜像进入 matrix；根 `pyproject.toml`/`uv.lock` 未被服务 Dockerfile COPY，不产生镜像；
- 仅修改 hci-sim 时，只构建 hci-sim，且不向环境仓库写业务 tag；
- 仅修改 database migration 输入时，只构建 db-migrate；
- 文档治理仅占用已有 `docs-governance` runner，不再产生两个独立 workflow run；
- 仓库 workflow 中不再使用可变 action tag；
- 静态 YAML、脚本单测和发布计划模拟验证通过。
