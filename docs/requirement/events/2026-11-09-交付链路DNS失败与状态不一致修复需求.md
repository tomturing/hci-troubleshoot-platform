# 交付链路 DNS 失败与状态不一致修复需求

## 变更历史

| 日期 | 版本 | 变更内容 | 关联事件文档 |
|------|------|---------|------------|
| 2026-11-09 | v1.0 | 首版：基于工单 Q2026110900185 的现场证据，登记三条交付链路缺陷与验收标准 | 本文件 |

## 背景

2026-11-09 工单 `Q2026110900185` 交付连续失败，现场表现为「上传中断（已传 0/339 片）：分片 1 上传失败：平台连接失败（暂时不可用，将退避重试）」。

实际根因与文案描述的不一致，且失败后平台状态停留在错误取值：

- 包是完整的：`delivery.pull_verified` 记录 `size=2836834502`、`sha256=d3ac86f5…`、`integrity=verified`；
- 失败点只有一个：`dial tcp: lookup acli.sangfor.com.cn: no such host`（客户机 DNS 解析失败）；
- 同工单另一条任务传到 **184/333 片**才失败，说明域名并非一直不可解析，而是**长任务中途 DNS 失效**；
- 桥侧 07:50:08 已 `phase=failed`，平台 `delivery_status` 仍为 `queued`。

## 现状事实

| 编号 | 事实 | 代码位置 |
|------|------|---------|
| F1 | 传输层错误统一按 `net.Error` 判为「暂时不可用」，`*net.DNSError` 实现了该接口，因此 DNS 失败被归为可重试的瞬时故障 | `terminal_bridge/delivery_runner.go` `isTransientTransportError` |
| F2 | 该分类生成的文案为「平台连接失败（暂时不可用，将退避重试）」，指向平台而非本机解析 | 同文件 `wrapTransientTransport` |
| F3 | 瞬时故障预算为 8 次、退避上限 60s；DNS 持续不可用时用户会在约 4~5 分钟内反复看到同一句误导文案 | 同文件 `maxDeliveryTransientAttempts`、`deliveryBackoff` |
| F4 | 桥侧终态只写本地 journal 与 `delivery.job_finished` 事件，不主动回写平台 | 同文件 `job_finished` 分支 |
| F5 | 平台 `delivery_status` 的写入点是前端 PATCH 与服务端 relay/核验端点；页面关闭时无人回写 | `backend/case-service/app/routes/log_collect.py` |
| F6 | 公共 PATCH 对 `delivery_status` 静默忽略，必须走服务端权威入口 | 同文件 `attest` / `verify_archive` 的 `server_authoritative=True` |
| F7 | 分片上传使用默认 `http.Client`，无 DNS 结果缓存；解析失败即中断整轮 | `terminal_bridge/log_collect_transfer.go`、`delivery_runner.go` `platformHTTPClient` |

## 需求

### R1 DNS 失败必须被识别并给出可执行文案

- 桥侧错误分类新增 `platform_dns_error`：`*net.DNSError`（或错误链中包含该类型）优先于通用 `net.Error` 判定；
- 文案必须回答「谁的问题、怎么修」：明确为本机无法解析平台域名，提示检查 hosts / DNS / 代理 / VPN，而不是「平台暂时不可用」；
- 重试策略与平台 5xx 分离：DNS 抖动可能自愈，但不应沿用 8 次 × 60s 的长退避；建议 2~3 次短退避后转终态，并标记需要人工介入；
- 该分类必须穿透 `%w` 包装（沿用 `errors.As` 口径），否则被「上传中断（已传 N/M 片）」包装后再次退化。

### R2 桥侧终态必须回写平台

- 作业进入 `failed` / `cancelled` 终态时，桥侧主动调用服务端权威入口写入 `delivery_status`、`delivery_error`、`delivery_finished_at`；
- 写入必须带作业代际（fencing token / `upload_id`），旧作业不得覆盖新会话的状态；
- 幂等：同一作业重复上报不改变首次结论与时间戳；
- 页面关闭、浏览器休眠、换端接管三种场景下，平台状态都必须收敛，不得长期停留在 `queued` / `uploading`。

### R3 DNS 失效不应导致整轮白传

- 优先复用已成功解析的地址：作业级 DNS 缓存（带 TTL），新建连接失败时回落到缓存地址；TLS 仍按原域名做 SNI 与证书校验，**不得借机放宽证书校验**；
- 保留本地已拉取副本与已上传分片清单，DNS 恢复后的重试必须续传，不得重新拉取整包（现场单包 2.6 GiB）；
- 若平台地址被配置为 IP 字面量，允许直连，但证书校验策略须显式声明（复用既有自签放宽流程，不新增隐式放宽）。

## 非目标

- 不修改 acli 插件行为；
- 不修改采集侧（`log_collect create/progress`）逻辑；
- 不新增「自动重采」：交付失败与采集成败解耦，重采由用户显式触发。

## 验收标准

- [ ] 构造 `*net.DNSError` 时，错误分类为 `platform_dns_error`，文案包含「无法解析平台域名」与 hosts/代理提示；
- [ ] DNS 失败的尝试次数显著少于平台 5xx 的 8 次，且不出现「平台暂时不可用」的误导表述；
- [ ] 页面关闭状态下让作业失败，平台 `delivery_status` 在终态后变为 `failed`，并带 `delivery_error`；
- [ ] 旧作业的终态上报不会覆盖同一任务新会话的 `uploading` 状态；
- [ ] DNS 恢复后重试从已有分片续传，拉取字节数不归零；
- [ ] 自签证书放宽逻辑行为不变，且不被 DNS 分类顺带触发。

## 风险与约束

1. **DNS 缓存的安全性**：缓存地址必须与域名绑定并在 TTL 后失效，避免长期指向已变更的入口；
2. **回写入口的权限**：桥侧只能使用平台签发的交付令牌（绑定 `task_id` + 代际），不得新增可跨任务写入的接口；
3. **误判为终态**：若把短时 DNS 抖动直接判死，会放大现场影响；因此采用「短重试 + 明确文案」而非「不重试」；
4. 本次不改变 `delivery_status` 的枚举，新增分类只体现在错误码与文案层。
