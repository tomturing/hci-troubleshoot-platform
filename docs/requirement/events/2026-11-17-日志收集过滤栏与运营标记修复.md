## 背景与问题

管理端任务进展页的过滤栏被反馈"完全不能使用"：选择「交付结论 = 待补交付」并查询后，表格仍显示已取消、失败等不匹配行，统计总数也不变。第一性审查发现两类独立原因：前端下拉提供的值未与后端白名单闭合（选中必 400），而 400 后页面保留旧表格与旧统计，视觉上等同于过滤失效。

上一轮审计还提出两项待办：把停滞任务与真在途分开；把压测工单打标并从运营看板默认过滤。同时用户指出「续传/补交付」入口早已存在，且当前环境可从 0.4 免密登录 0.2（5888 后端，端口 22468）核对归档事实。

## 功能需求

1. 前端下拉可选项与后端枚举白名单必须闭合：任何可见选项都不得返回 400。
2. 所有筛选项（周期、工单号、节点 IP、交付路径、采集状态、交付结论）变化后立即生效；文本输入支持回车查询；保留「查询/重置/刷新」按钮。
3. 查询失败时必须清空旧表格与统计并显式告警，不得让旧结果冒充新条件的结果。
4. `derive()` 增加两个可观测条件：`task_stalled`（任务级长时间无进展）与 `synthetic_test`（验证/压测任务），与既有 60 秒传输停滞 `stalled` 明确区分。
5. 压测清理不再显示为失败信号：归因改为 info 级「验证 / 压测清理」，运营看板默认排除，可用开关显式包含。
6. 核对三张「未完成 · 待补交付」工单在 5888 的真实归档状态，纠正上一轮关于入口缺失与压测数量的错误结论。

## 验收标准

- [ ] 选择「采集状态 = 任务下发中 / 平台中转中」与「交付结论 = 已取消 / 待补交付」均返回 200。
- [ ] 浏览器中选择任一筛选项后请求参数随之变化，无需点「查询」。
- [ ] 模拟 400 后页面显示「加载失败」且旧工单号与旧统计消失。
- [ ] 近 7 天 191 单中 13 张压测单被默认排除，保留 178 张；全部归因到 `LC-HTP-004`（info）。
- [ ] 停滞超过 24 小时且未终结的任务带 `task_stalled` 条件，新任务不带。
- [ ] 三张待补交付工单的归档事实有 SSH 取证记录，文档不再声称缺少补交付入口。
