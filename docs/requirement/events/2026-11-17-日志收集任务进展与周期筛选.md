# 2026-11-17 日志收集任务进展与周期筛选需求

## 背景与问题

管理端「日志收集」页当前默认打开「默认场景」，而管理员进入该页的第一诉求是看任务状态，场景配置是低频操作；原「日志上传」页签名称与页面内「交付路径」等术语并列时容易被理解成手工上传入口，实际该页只读展示任务进展。

筛选区只提供近 7/14/30 天，无法查看全量历史；且修改周期后必须再点一次「查询」才生效，用户容易误以为筛选未生效而重复操作。

此外需要对近 7 天全部任务做一次结果态审计：确认顶部第一排标签是否与实际数据一致，并对非「已交付」标签给出具体问题与改进建议。

## 需求描述

- 功能概述：调整日志收集入口的默认落点与页签文案，扩展时间范围并让周期选择即时生效；同步产出近 7 天任务状态审计结论。
- 用户场景：管理员点击左侧「日志收集」后直接看到任务进展；需要看历史全量任务时选择「全部」，页面自动刷新。
- 预期收益：减少一次页签点击与一次「查询」点击；消除"选择周期但看到旧数据"的误解；为后续治理提供可核对的数据基线。

## 功能需求

1. 点击「日志收集」默认打开原「日志上传」页签，且该页签文案改为「任务进展」。
2. 时间范围选项扩展为：近 7 天、近 14 天、近 30 天、全部。
3. 选择任一周期后立即刷新列表、统计与分页（重置到第 1 页），无需手动点击「查询」；「查询」按钮保留。
4. 「全部」必须真正取消时间边界，不得用超大天数模拟。
5. 分析近 7 天所有任务：确认第一排标签准确性；说明除「已交付」外各标签工单的具体问题并给出改进建议。

## 非功能需求

- 可观测性：列表读取的结构化日志必须记录查询周期（`days=0` 表示全部），保留 trace_id。
- 兼容性：原 `days` 参数继续兼容 1~90；新增 0 为合法值，负数与大于 90 仍拒绝。
- 只读性：页面不得新增写操作入口，也不展示删除类命令。

## 验收标准

- [ ] 进入 `/admin/log-collect-scenarios` 默认激活「任务进展」，页面不再出现「日志上传」文案。
- [ ] 周期下拉含四个选项，选中「全部」后列表请求 `days=0`，且后端 SQL 不含 `created_at >=`。
- [ ] 切换周期后无需点击「查询」即可看到新数据，分页回到第 1 页。
- [ ] 前端定向单测与后端定向单测全绿。
- [ ] 近 7 天任务审计结论与权威 `derive()` 分桶一致，恒等式成立。
